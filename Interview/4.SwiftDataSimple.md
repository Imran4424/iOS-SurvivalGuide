## 1. Fundamentals

### Q1. What is SwiftData? `[Fundamental]`
SwiftData is Apple's **Swift-first framework for saving app data on the device** (iOS 17+): you write normal Swift classes, mark them with `@Model`, and SwiftData stores, loads, and updates them for you.

- No separate model file (`.xcdatamodeld`). The model is just Swift code.
- Works smoothly with SwiftUI (`@Query`, `.modelContainer`).
- Can sync to iCloud with CloudKit.
- Under the hood, it saves to SQLite using Core Data's proven storage engine.

```swift
@Model
final class Note {
    var text: String
    var createdAt: Date
    init(text: String, createdAt: Date = .now) {
        self.text = text
        self.createdAt = createdAt
    }
}
```

**Follow-ups:**
- **Is SwiftData a database?** It's a layer on top of one. By default it stores data in a SQLite file.
- **Does it work without SwiftUI?** Yes. You can use it from UIKit or plain Swift code, but you lose `@Query`.
- **What's the minimum iOS version?** iOS 17.

### Q2. What are the core building blocks of SwiftData? `[Fundamental]`
The main pieces are **the model** (`@Model`), **the container** (the database), and **the context** (where you make changes), plus tools to **fetch** data and to **work in the background**.

| Piece | What it is, in simple words |
|---|---|
| `@Model` | Turns a class into something SwiftData can save |
| `Schema` | The list of your model types |
| `ModelConfiguration` | **How** and **where** data is stored (file, in memory, iCloud, read-only) |
| `ModelContainer` | The database itself |
| `ModelContext` | A scratchpad: you insert, change, and delete here, then `save()` |
| `@Query` | Fetches data in a SwiftUI view and keeps it up to date |
| `FetchDescriptor` / `#Predicate` / `SortDescriptor` | Describe what to fetch and in what order |
| `ModelActor` | An actor with its own context, for background work |
| `PersistentIdentifier` | A safe ID for a record that you can pass between threads |

```swift
let container = try ModelContainer(for: Note.self)     // the database
let context = container.mainContext                    // the scratchpad
context.insert(Note(text: "Hello"))                    // change
try context.save()                                     // write to disk
```

**Follow-ups:**
- **Container vs context?** The container is the database. A context is a workspace for changes before saving.
- **How many containers does an app usually have?** One, unless you have truly separate databases.
- **Which of these can be passed between threads?** `ModelContainer` and `PersistentIdentifier`. Not contexts or models.

### Q3. Walk through a minimal SwiftData app. `[Fundamental]`
You need **three steps**: define a model with `@Model`, add `.modelContainer(for:)` to the app, and use `@Query` to read and `modelContext` to write in your views.

- `.modelContainer(for:)` creates the database and puts a context into the environment.
- `@Query` reads data and updates the list automatically.
- The main context **saves automatically**, so you don't need to call `save()` here.

```swift
import SwiftData
import SwiftUI

@Model
final class Trip {                                      // 1. the model
    var name: String
    var startDate: Date
    var isFavorite: Bool = false

    init(name: String, startDate: Date) {
        self.name = name
        self.startDate = startDate
    }
}

@main
struct TripsApp: App {
    var body: some Scene {
        WindowGroup { TripListView() }
            .modelContainer(for: Trip.self)             // 2. the database
    }
}

struct TripListView: View {
    @Environment(\.modelContext) private var modelContext                       // write
    @Query(sort: \Trip.startDate, order: .reverse) private var trips: [Trip]    // read

    var body: some View {
        NavigationStack {
            List {
                ForEach(trips) { Text($0.name) }
                    .onDelete { offsets in
                        for index in offsets { modelContext.delete(trips[index]) }
                    }
            }
            .toolbar {
                Button("Add", systemImage: "plus") {
                    modelContext.insert(Trip(name: "New Trip", startDate: .now))
                }
            }
        }
    }
}
```

**Follow-ups:**
- **Why no `save()` call?** The main context saves automatically from time to time and when the app goes to the background.
- **How does the list update after inserting?** `@Query` watches the data and refreshes the view.
- **Where does the data live?** In a SQLite file in the app's Application Support folder.

### Q4. Why are SwiftData models classes and not structs? `[Senior]`
Because a saved record needs **one shared object** that the context can track. A struct would be **copied**, and changes to the copy wouldn't reach the database.

- The context watches each model object for changes. That only works if everyone shares the same object.
- Relationships (a trip and its activities) need objects that point to each other.
- Models are also `Observable`, which requires classes.
- Mark models `final` unless you use inheritance (iOS 26+).

```swift
let trip = trips[0]
trip.name = "Japan 2027"      // the context sees this change on the shared object
try modelContext.save()       // and saves it

// With a struct, this would change a copy, and the database would never know
```

**Follow-ups:**
- **Why mark models `final`?** It's clearer and slightly faster. Only remove `final` if you need inheritance (iOS 26+).
- **Can you use structs inside a model?** Yes, as `Codable` property values (see Q15).
- **Are models thread-safe?** No. A model must stay on the thread (actor) of its context.

### Q5. What does the `@Model` macro generate? `[Senior]`
`@Model` **rewrites your class** so each property reads and writes through SwiftData's storage, makes the class **observable**, and adds the **information SwiftData needs** to save it.

- Adds `PersistentModel` conformance (which includes `Identifiable` and `Hashable`) and `Observable`.
- Turns each stored property into a computed one that talks to SwiftData's storage ("backing data").
- Adds schema information about properties and relationships.
- Adds an `init(backingData:)` that SwiftData uses when loading records.
- You can see the generated code in Xcode: right-click `@Model` → **Expand Macro**.

```swift
@Model
final class Trip {
    var name: String          // becomes: get/set through SwiftData's storage, with observation
    init(name: String) { self.name = name }
}

// Because of the macro, Trip is Identifiable, Hashable and Observable:
let id = trip.persistentModelID
```

**Follow-ups:**
- **Why does observation matter?** SwiftUI views update automatically when a model property they read changes.
- **How do you see what the macro generated?** Right-click → Expand Macro in Xcode.
- **Can you add normal methods to a model?** Yes. Methods and computed properties work as usual.

### Q6. Which types can a model property store? `[Fundamental]`
A model can store **basic Swift types**, **optionals and arrays** of them, **`Codable` structs and enums**, and **relationships** to other models.

- **Basic types:** `String`, `Int`, `Double`, `Float`, `Bool`, `Date`, `Data`, `URL`, `UUID`, `Decimal`.
- **Optionals and arrays** of those.
- **`Codable` structs and enums.**
- **Other models** (one, or an array).
- **Types you don't own:** iOS 27's `@Attribute(.codable)`, or a `ValueTransformer` with `.transformable`.

```swift
@Model
final class Recipe {
    var title: String                 // basic type
    var tags: [String] = []           // array of a basic type
    var rating: Double?               // optional
    var nutrition: Nutrition?         // Codable struct
    var ingredients: [Ingredient] = [] // relationship to other models
    init(title: String) { self.title = title }
}
```

**Follow-ups:**
- **Can you store a `UIColor`?** Not directly. Store simple values (like a hex string), or use a transformer (see Q18).
- **Can you filter on values inside a `Codable` struct?** Only in a limited way. Move the field to a top-level property if you need to filter on it.
- **What is `@Attribute(.codable)` (iOS 27)?** It stores a `Codable` type as encoded data. Good for types you don't own.

### Q7. Does SwiftData replace Core Data? `[Senior]`
**Not completely**: SwiftData is Apple's modern choice for new projects, but Core Data is still supported and still does some things SwiftData can't.

- Core Data still has: public and shared CloudKit databases, batch updates, `NSFetchedResultsController` for UIKit, and more control over migrations.
- The two can **share the same database file**, so you can migrate gradually (see Section 14).

```swift
// Both can point at the same store file during a gradual migration
let config = ModelConfiguration(url: existingCoreDataStoreURL)
let container = try ModelContainer(for: Trip.self, configurations: config)
```

**Follow-ups:**
- **Is Core Data deprecated?** No, it's still supported.
- **What is SwiftData built on?** Core Data's storage engine by default.
- **What did iOS 27 add that Core Data already had?** Sectioned fetching, with `@Query(sectionBy:)`.

### Q8. What is the minimum OS for SwiftData, and how does that affect adoption? `[Senior]`
SwiftData needs **iOS 17 / macOS 14**, so apps that still support iOS 16 can't use it without keeping a Core Data version too.

- Important fixes and features came in iOS 17.4, iOS 18, iOS 26, and iOS 27.
- Many teams wait until their minimum is iOS 17 or 18.
- Always test the features you need on your **lowest** supported iOS version, because behavior changed between releases.

```swift
// If you still support iOS 16, SwiftData code must be behind an availability check
if #available(iOS 17, *) {
    // SwiftData path
} else {
    // Core Data path
}
```

**Follow-ups:**
- **Why test on the minimum OS specifically?** Bugs fixed in newer iOS versions may still exist there.
- **Is keeping two persistence stacks a good idea?** Usually not. It doubles the work. Teams often wait for the minimum to reach iOS 17.
- **Which features need newer versions?** For example `#Unique` and `#Index` (iOS 18), inheritance (iOS 26), and sectioned queries (iOS 27).

## 2. Defining Models

### Q9. What is `@Attribute`, and what options does it support? `[Senior]`
`@Attribute` lets you **customize how one property is stored**, for example "must be unique" or "store this large data in a separate file."

| Option | What it does |
|---|---|
| `.unique` | No two records can have the same value. Inserting a duplicate **updates** the existing one (upsert) |
| `.externalStorage` | Stores large data (images, files) outside the main database file |
| `.transformable(by:)` | Stores a custom type using a `ValueTransformer` |
| `.codable` (iOS 27) | Stores a `Codable` type as encoded data |
| `.allowsCloudEncryption` | Encrypts the value in iCloud |
| `.spotlight` | Makes the value searchable in Spotlight |
| `.ephemeral` | Tracks changes but doesn't save the value |
| `.preserveValueOnDeletion` | Keeps the value in history after the record is deleted (iOS 18) |
| `originalName:` | Says "this property used to have a different name," for renames |

```swift
@Model
final class Photo {
    @Attribute(.unique) var remoteID: String                 // no duplicates
    @Attribute(.externalStorage) var imageData: Data?        // big data in a separate file
    @Attribute(originalName: "title") var caption: String    // renamed from "title"
    var takenAt: Date

    init(remoteID: String, caption: String, takenAt: Date) {
        self.remoteID = remoteID
        self.caption = caption
        self.takenAt = takenAt
    }
}
```

**Follow-ups:**
- **Can you combine options?** Yes, for example `@Attribute(.unique, .spotlight)`.
- **What is an upsert?** "Update if it exists, insert if it doesn't."
- **Why does `originalName` matter?** Without it, a rename loses the old data (see Q70).

### Q10. What happens when you insert a model whose `.unique` value already exists? `[Senior]`
SwiftData does an **upsert**: it doesn't create a duplicate or throw an error, it **updates the existing record** with the new values when you save.

- Great for server data: insert models mapped from the server, and duplicates merge automatically.
- **Caveat 1:** unique constraints don't work with CloudKit sync.
- **Caveat 2:** related objects attached to the new model may need their own deduplication.

```swift
modelContext.insert(Product(sku: "A1", price: 10))
try modelContext.save()

modelContext.insert(Product(sku: "A1", price: 12))   // same sku
try modelContext.save()
// Result: one product "A1" with price 12
```

**Follow-ups:**
- **Why don't unique constraints work with CloudKit?** CloudKit can't check uniqueness across all of the user's devices.
- **What happens to relationships on an upsert?** Test it. Related objects may also need unique IDs to avoid duplicates.
- **What if you need uniqueness on two fields together?** Use `#Unique` (iOS 18, see Q11).

### Q11. What is `#Unique`, and how does it differ from `@Attribute(.unique)`? `[Senior]`
`#Unique` (iOS 18) makes a **combination of properties** unique, like "name + start date," while `@Attribute(.unique)` makes **one property** unique.

- You can list several unique rules in one `#Unique`.

```swift
@Model
final class Trip {
    #Unique<Trip>([\.name, \.startDate])   // the pair (name, startDate) must be unique

    var name: String
    var startDate: Date
    var endDate: Date

    init(name: String, startDate: Date, endDate: Date) {
        self.name = name
        self.startDate = startDate
        self.endDate = endDate
    }
}

// Several rules: id alone is unique, AND (name, startDate) together is unique
// #Unique<Trip>([\.id], [\.name, \.startDate])
```

**Follow-ups:**
- **What happens on a duplicate combination?** An upsert, the same as `.unique`.
- **Does it work with CloudKit?** No, same as `.unique`.
- **What OS do you need?** iOS 18.

### Q12. What is `@Transient`? `[Fundamental]`
`@Transient` marks a property that is **not saved** to the database, which is useful for temporary values like "is this row selected."

- It needs a default value.
- It goes back to that default every time the model is loaded again.
- You can't filter or sort on it.

```swift
@Model
final class Document {
    var title: String
    @Transient var isSelected = false   // in memory only, never saved

    init(title: String) { self.title = title }
}
```

**Follow-ups:**
- **Why does it need a default value?** SwiftData uses it whenever the model is loaded from the database.
- **Can you use it in a `#Predicate`?** No. It isn't in the database, so the database can't filter on it.
- **Should UI state live in a model at all?** Often it's better in the view's `@State`. Use `@Transient` only when the state truly belongs to the object.

### Q13. Can models have computed properties? `[Fundamental]`
**Yes**, but they're **not saved** and you **can't use them in `#Predicate` or sorting**, because the database only knows about saved properties.

- Good for display values, like a formatted date or a full name.
- If you need to filter or sort on a value, store it as a real property and keep it updated.

```swift
@Model
final class Person {
    var firstName: String
    var lastName: String

    var fullName: String { "\(firstName) \(lastName)" }   // fine for display, not for queries

    init(firstName: String, lastName: String) {
        self.firstName = firstName
        self.lastName = lastName
    }
}
```

**Follow-ups:**
- **What happens if you use a computed property in `#Predicate`?** It fails at compile time or at runtime (see Q116).
- **How do you sort by full name, then?** Sort by `lastName`, then `firstName`, which are stored.
- **Are computed properties observed?** Yes, through the stored properties they read.

### Q14. How do you store enums in a model and query them? `[Senior]`
`Codable` enums can be stored directly, but **filtering on enums in `#Predicate` has been unreliable**, so the safe pattern is to **store the raw value** and add a computed property for the enum.

- Store `priorityRawValue: Int`.
- Expose `priority: Priority` as a computed property.
- Filter on the raw value.

```swift
enum Priority: Int, Codable, CaseIterable {
    case low, medium, high
}

@Model
final class TodoItem {          // don't name a model `Task`: it clashes with Swift concurrency
    var title: String
    var priorityRawValue: Int = Priority.medium.rawValue      // what's saved

    var priority: Priority {                                   // what your code uses
        get { Priority(rawValue: priorityRawValue) ?? .medium }
        set { priorityRawValue = newValue.rawValue }
    }

    init(title: String, priority: Priority = .medium) {
        self.title = title
        self.priorityRawValue = priority.rawValue
    }
}

let highRaw = Priority.high.rawValue
let urgent = #Predicate<TodoItem> { $0.priorityRawValue == highRaw }   // filter on the raw value
```

**Follow-ups:**
- **Why capture `highRaw` outside the predicate?** Predicates can't call code like `Priority.high.rawValue` inside them.
- **What if the saved raw value is unknown (an old app version)?** The computed property falls back to a default, like `.medium`.
- **Why avoid naming a model `Task`?** It clashes with Swift concurrency's `Task` type.

### Q15. How do you store `Codable` structs in a model? What are the limits? `[Senior]`
Just declare a property whose type is a **`Codable` struct**, and SwiftData stores it inside the record, but you **can't easily filter or sort** on fields inside it.

- **Limit 1:** to filter by `city`, move `city` to a top-level property or a related model.
- **Limit 2:** changing the struct's shape later can break reading old data.

```swift
struct Address: Codable {
    var street: String
    var city: String
    var postalCode: String
}

@Model
final class Customer {
    var name: String
    var address: Address?          // stored inside the Customer record

    init(name: String, address: Address? = nil) {
        self.name = name
        self.address = address
    }
}
```

**Follow-ups:**
- **When should the struct be its own `@Model` instead?** When you need to filter, sort, or share it between records.
- **What's the iOS 27 `.codable` attribute for?** For `Codable` types SwiftData can't model, often types you don't own. It stores them as one opaque value.
- **How do you change the struct safely?** Add new fields as optional, so old data still decodes.

### Q16. When should you use `.externalStorage`? `[Senior]`
Use `.externalStorage` for **large binary data** like images, PDFs, and audio, so SwiftData can keep those bytes in **separate files** and keep the main database small and fast.

- Even so, don't load big data in list screens.
- Show thumbnails in lists, and keep full-size data in a separate model loaded only when needed.

```swift
@Model
final class Attachment {
    var fileName: String
    @Attribute(.externalStorage) var data: Data?   // stored outside the main database file

    init(fileName: String, data: Data?) {
        self.fileName = fileName
        self.data = data
    }
}
```

**Follow-ups:**
- **Is the data always stored outside?** SwiftData decides. Small values may still stay inside the database.
- **How do you keep lists fast?** Store a small thumbnail separately and load the full data only on the detail screen.
- **Should you put files on disk yourself instead?** Sometimes. Saving a file path in the model is also a valid choice for very large files.

### Q17. Why does a model need an initializer, and how should you handle defaults? `[Fundamental]`
`@Model` classes need **your own `init`** (Swift class rules, SwiftData doesn't write one for you), and you should give properties **default values** where it makes sense.

- Default values make adding new properties a simple, automatic migration.
- CloudKit sync **requires** every property to be optional or have a default.

```swift
@Model
final class Habit {
    var name: String
    var streak: Int = 0               // default value
    var createdAt: Date = Date.now    // default value

    init(name: String) {              // you must write the init
        self.name = name
    }
}
```

**Follow-ups:**
- **Why do defaults help migrations?** A new property with a default can be added to old records automatically.
- **What does CloudKit require?** Every property optional or with a default value.
- **Can the `init` have default parameters?** Yes, like `init(name: String, streak: Int = 0)`.

### Q18. How do you use a custom type with `.transformable`? `[Lead/Expert]`
Write a **`ValueTransformer`** that converts your type to `Data` and back, then mark the property with `@Attribute(.transformable(by:))`.

- Register the transformer at launch, **before** creating the container.
- The stored value is **opaque**: you can't filter or sort on it.
- Prefer simple values (like a hex color string) when you can.

```swift
@objc(ColorTransformer)
final class ColorTransformer: NSSecureUnarchiveFromDataTransformer {
    override class var allowedTopLevelClasses: [AnyClass] { [UIColor.self] }
}

@Model
final class Tag {
    var name: String
    @Attribute(.transformable(by: ColorTransformer.self)) var color: UIColor?

    init(name: String, color: UIColor? = nil) {
        self.name = name
        self.color = color
    }
}

// At launch, before creating the container:
// ValueTransformer.setValueTransformer(ColorTransformer(), forName: NSValueTransformerName("ColorTransformer"))
```

**Follow-ups:**
- **What's a simpler alternative?** Store the color as a hex string or a small `Codable` struct with RGB values.
- **When would you use iOS 27's `.codable` instead?** When the type is already `Codable`. It needs no transformer.
- **What happens if you forget to register the transformer?** Saving or loading that property fails.

### Q19. What is the `persistentModelID`? `[Senior]`
`persistentModelID` is every model's **built-in ID** (type `PersistentIdentifier`), and it's **safe to pass between threads** because it's `Sendable`.

- It's also `Hashable` and `Codable`.
- Use it to: pass a record to a background actor, identify rows in a diffable data source, or fetch the same record in another context.
- **Before the first save, the ID may be temporary.** Save first before handing it to another context (see Q121).

```swift
let tripID = trip.persistentModelID                 // safe to send to another actor
try await processor.process(tripID: tripID)

// In another context, get the record back:
let sameTrip = otherContext.model(for: tripID) as? Trip
```

**Follow-ups:**
- **Why not pass the model itself?** Models aren't `Sendable`. They must stay on their context's actor.
- **What is a temporary ID?** An ID given before saving. Other contexts can't find the record yet.
- **Can you store a `PersistentIdentifier` long-term?** It's `Codable`, but for server sync or deep links a UUID you control is more reliable.

### Q20. Should you add your own `id` property? `[Senior]`
You **don't need one for SwiftUI** (models are already `Identifiable`), but you **should add one** when you need a stable ID **outside the app**, like for a server, deep links, or other devices.

- Use a `UUID` or the server's ID as a `String`.
- Make it unique (`@Attribute(.unique)` or `#Unique`), unless you use CloudKit.

```swift
@Model
final class Order {
    @Attribute(.unique) var remoteID: String      // the server's ID
    var total: Decimal

    init(remoteID: String, total: Decimal) {
        self.remoteID = remoteID
        self.total = total
    }
}
```

**Follow-ups:**
- **Why not use `persistentModelID` for the server?** It's local to this database. The server and other devices don't know it.
- **What if you use CloudKit?** You can't make it unique, so you must handle duplicates yourself (see Q77).
- **Can you name it `id`?** Yes, and then SwiftUI uses it as the identity. A name like `remoteID` makes it clearer that it comes from the server.

## 3. Relationships

### Q21. How do you define one-to-many relationships? `[Fundamental]`
Give the parent an **array of the child model** and the child an **optional reference back** to the parent, then use `@Relationship` to set the **delete rule** and the **inverse** (the matching property on the other side).

- Just using another model as a property type creates a relationship.
- `@Relationship` customizes it.
- Write `inverse:` on **one side only**.
- Adding a child to an inserted parent inserts the child automatically.

```swift
@Model
final class Trip {
    var name: String

    @Relationship(deleteRule: .cascade, inverse: \Activity.trip)   // delete trip → delete activities
    var activities: [Activity] = []

    init(name: String) { self.name = name }
}

@Model
final class Activity {
    var title: String
    var trip: Trip?                                                   // the back reference

    init(title: String) { self.title = title }
}

// Usage
let trip = Trip(name: "Japan")
modelContext.insert(trip)
trip.activities.append(Activity(title: "Visit Kyoto"))   // the activity is inserted too
```

**Follow-ups:**
- **Why is the back reference optional?** An activity can exist briefly without a trip, and CloudKit requires optional relationships.
- **What happens if you set the inverse on both sides?** It can cause a compile error (a circular reference). One side is enough.
- **Is `activity.trip` set automatically when you append?** Yes, the inverse keeps both sides in sync.

### Q22. What delete rules are available? `[Fundamental]`
A delete rule says **what happens to related objects when you delete the owner**: keep them (`.nullify`), delete them (`.cascade`), block the delete (`.deny`), or do nothing (`.noAction`).

| Rule | When the owner is deleted |
|---|---|
| `.nullify` (default) | Related objects stay. Their link back is set to `nil` |
| `.cascade` | Related objects are deleted too |
| `.deny` | The delete is refused while related objects exist |
| `.noAction` | Nothing happens to related objects (can leave broken links, rarely right) |

- **Tip:** when you rely on `.cascade`, also define the `inverse`. Cascade without an inverse has caused bugs.

```swift
@Relationship(deleteRule: .cascade, inverse: \Comment.post)
var comments: [Comment] = []          // delete a post → its comments go too

@Relationship(deleteRule: .nullify, inverse: \Post.author)
var posts: [Post] = []                // delete an author → posts stay, with author = nil
```

**Follow-ups:**
- **Which rule is the default?** `.nullify`.
- **When would you use `.deny`?** When deleting would break important data, like a category that still has products. (Not allowed with CloudKit.)
- **How do you verify cascade works?** A unit test: delete the parent, save, and check the child count is 0.

### Q23. How do you model many-to-many relationships? `[Senior]`
Give **both models an array of the other** and set the **inverse on one side**, then adding to one side automatically updates the other.

- If the link itself has data (like an enrollment date or grade), create a **join model** (`Enrollment`) between the two instead.

```swift
@Model
final class Student {
    var name: String
    var courses: [Course] = []
    init(name: String) { self.name = name }
}

@Model
final class Course {
    var title: String
    @Relationship(inverse: \Student.courses)
    var students: [Student] = []
    init(title: String) { self.title = title }
}

student.courses.append(course)   // course.students now contains student too
```

**Follow-ups:**
- **When do you need a join model?** When the relationship has its own data, like "enrolled on" or "grade."
- **What delete rule fits many-to-many?** Usually `.nullify`, since deleting a student shouldn't delete the course.
- **Is the order of these arrays kept?** No (see Q24).

### Q24. Are to-many relationship arrays ordered? `[Lead/Expert]`
**No**, and this is a classic gotcha: the order of a relationship array is **not kept** after saving and loading again.

- If order matters (playlists, steps, checklists), store a **position** number and sort by it.

```swift
@Model
final class Playlist {
    var name: String
    @Relationship(deleteRule: .cascade, inverse: \PlaylistEntry.playlist)
    var entries: [PlaylistEntry] = []

    var orderedEntries: [PlaylistEntry] {              // always sort by position
        entries.sorted { $0.position < $1.position }
    }

    init(name: String) { self.name = name }
}

@Model
final class PlaylistEntry {
    var position: Int                                  // the order you want
    var songTitle: String
    var playlist: Playlist?

    init(position: Int, songTitle: String) {
        self.position = position
        self.songTitle = songTitle
    }
}
```

**Follow-ups:**
- **How do you reorder items?** Update the `position` values of the moved items.
- **Why use spaced numbers like 10, 20, 30?** You can insert between items without renumbering everything.
- **Why doesn't SwiftData keep the order?** In the database, to-many relationships are stored as an unordered set.

### Q25. What are `minimumModelCount` and `maximumModelCount`? `[Senior]`
They are `@Relationship` settings that **limit how many related objects are allowed**, for example "a team needs 1 to 11 players."

- Breaking the rule causes an error when you **save**.

```swift
@Model
final class Team {
    var name: String

    @Relationship(deleteRule: .cascade, minimumModelCount: 1, maximumModelCount: 11)
    var players: [Player] = []

    init(name: String) { self.name = name }
}
```

**Follow-ups:**
- **When is the rule checked?** When you save. The save throws an error if the rule is broken.
- **Should you also check in the UI?** Yes. Disable the "Add player" button at 11 so users don't hit a save error.
- **Does this replace validation logic?** No, it's a safety net. Keep clear validation in your own code too.

### Q26. Why might you get "Illegal attempt to establish a relationship between objects in different contexts"? `[Lead/Expert]`
You connected **two models from different `ModelContext`s**, for example one fetched on a background actor and one from the main context, and SwiftData doesn't allow links across contexts.

- **Fix:** fetch both models in the **same** context using their IDs, then connect them.

```swift
// ❌ activity comes from a background context, trip from the main context
trip.activities.append(activity)

// ✅ get both from the same context, then connect
let trip = context.model(for: tripID) as? Trip
let activity = context.model(for: activityID) as? Activity
if let trip, let activity { trip.activities.append(activity) }
```

**Follow-ups:**
- **How does this happen in practice?** Mixing models returned from a background service with models from the UI.
- **How do you prevent it?** Return IDs or simple structs from background code, never models.
- **Can one model belong to two contexts?** No. Each model object belongs to exactly one context.

### Q27. How should you handle relationships when importing data? `[Senior]`
**Insert the parent first, then attach children**, and **look up existing records by ID** (or rely on unique upserts) so you don't create duplicates.

- Appending a child to an inserted parent inserts the child automatically.
- For big imports: import parents, save, then import children in batches to control memory.

```swift
func importTrip(_ dto: TripDTO, context: ModelContext) throws {
    let trip = Trip(remoteID: dto.id, name: dto.name)   // unique remoteID → upsert
    context.insert(trip)                                // 1. parent first
    for activityDTO in dto.activities {
        trip.activities.append(Activity(remoteID: activityDTO.id, title: activityDTO.title))   // 2. children
    }
}
```

**Follow-ups:**
- **How do you avoid duplicate children?** Give children a unique remote ID too.
- **Why save in batches?** Unsaved objects stay in memory. Saving in batches keeps memory low.
- **Where should imports run?** On a background `@ModelActor`, not the main context (see Q64).

### Q28. How do relationships affect loading? `[Senior]`
Related objects are loaded **lazily**: reading `trip.activities` triggers a **separate database query** the first time, so a list that reads a relationship in every row makes **one extra query per row** (the "N+1 problem").

- **Fix 1:** prefetch with `relationshipKeyPathsForPrefetching`.
- **Fix 2:** store a summary value on the parent, like `activityCount` (see Q85).

```swift
var descriptor = FetchDescriptor<Trip>()
descriptor.relationshipKeyPathsForPrefetching = [\.activities]   // load activities with the trips
let trips = try modelContext.fetch(descriptor)
```

**Follow-ups:**
- **What does "N+1" mean?** One query for the list, plus one more for each of the N rows.
- **How do you spot it?** Turn on SQL logging and look for many similar queries (see Q84).
- **Is lazy loading bad?** No, it saves memory. It's only a problem when every row needs the related data.

## 4. ModelContainer & ModelConfiguration

### Q29. What is a `ModelContainer`? `[Fundamental]`
A `ModelContainer` is **the database for your app**: it knows your model types and manages the file where data is stored.

- Usually one per app.
- It creates the **`mainContext`** (for the main thread) and lets you create more contexts.
- It's `Sendable`, so you can pass it to background actors.

```swift
let container = try ModelContainer(for: Trip.self, Activity.self)
let mainContext = container.mainContext          // for UI code
let importer = TripImporter(modelContainer: container)   // background actor gets the container
```

**Follow-ups:**
- **Why is it safe to share the container but not a context?** The container is `Sendable`. Contexts aren't.
- **When would you have more than one container?** For truly separate databases, which is rare.
- **What happens if creating the container fails?** It throws. Handle it instead of crashing (see Q30 and Q73).

### Q30. How do you create a container explicitly with error handling? `[Senior]`
Create the container **yourself in the `App`'s `init`** with `try`, so you can **handle failures** (like a failed migration) instead of crashing.

- `.modelContainer(for:)` is convenient but hides errors.
- Creating it yourself also lets you share it with widgets, App Intents, and background tasks.

```swift
@main
struct TripsApp: App {
    let container: ModelContainer

    init() {
        do {
            let schema = Schema([Trip.self, Activity.self])
            let configuration = ModelConfiguration(schema: schema)
            container = try ModelContainer(for: schema, configurations: configuration)
        } catch {
            // In production: log it, try to recover, or show a recovery screen
            fatalError("Failed to create ModelContainer: \(error)")
        }
    }

    var body: some Scene {
        WindowGroup { ContentView() }
            .modelContainer(container)
    }
}
```

**Follow-ups:**
- **Why is `fatalError` risky here?** If a migration fails, the app crashes on every launch.
- **What's a better recovery?** Back up the store, log the error, and recreate the store if data can be downloaded again.
- **How do other targets use the same container?** Put the creation code in a shared package and use an App Group (see Q97).

### Q31. What is `ModelConfiguration` used for? `[Senior]`
`ModelConfiguration` describes **how and where a store is saved**: a file location, in memory only, read-only, shared with an App Group, or synced with iCloud.

```swift
// In memory only (tests, previews)
let memory = ModelConfiguration(isStoredInMemoryOnly: true)

// Read-only database shipped in the app bundle
let seed = ModelConfiguration(url: Bundle.main.url(forResource: "Seed", withExtension: "store")!,
                              allowsSave: false)

// Shared with widgets through an App Group
let shared = ModelConfiguration(groupContainer: .identifier("group.com.example.trips"))

// Never sync to iCloud, even if the app has the CloudKit capability
let localOnly = ModelConfiguration(cloudKitDatabase: .none)
```

**Follow-ups:**
- **When do you use in-memory storage?** In tests and previews, so nothing is written to disk.
- **What does `allowsSave: false` mean?** The store is read-only, for example bundled reference data.
- **Why use `cloudKitDatabase: .none`?** For data that must stay on the device, like a cache.

### Q32. How do you use multiple stores in one container? `[Lead/Expert]`
Pass **several configurations**, each with **its own set of models**, for example user data synced to iCloud plus a local-only cache.

- **Relationships can't cross stores.** Models that link to each other must be in the same store.

```swift
let synced = ModelConfiguration("UserData",
                                schema: Schema([Trip.self, Activity.self]),
                                cloudKitDatabase: .automatic)         // synced

let cache = ModelConfiguration("Cache",
                               schema: Schema([CachedImage.self]),
                               cloudKitDatabase: .none)               // local only

let container = try ModelContainer(for: Trip.self, Activity.self, CachedImage.self,
                                   configurations: synced, cache)
```

**Follow-ups:**
- **Why split stores?** To keep caches out of iCloud, or to delete a cache store without touching user data.
- **Can a `Trip` link to a `CachedImage` here?** No, they're in different stores. Store an ID instead.
- **Is one context enough for both stores?** Yes, the container's context works across all its stores.

### Q33. Where is the SwiftData store file, and how do you find it? `[Fundamental]`
By default it's in **Application Support** as `default.store`, and you can **print its exact path** from the container's configuration.

- Useful for opening the SQLite file in a database browser while debugging.

```swift
print(container.configurations.first?.url.path(percentEncoded: false) ?? "unknown")
// Default: <App Sandbox>/Library/Application Support/default.store
```

**Follow-ups:**
- **What will you see in the database file?** Core Data-style table names like `ZTRIP` and columns like `Z_PK`.
- **How do you change the file name?** Create a `ModelConfiguration` with a name or a custom URL.
- **Can you open the file while the app is running?** Yes, but read only, to avoid damaging it.

### Q34. How do you enable undo/redo? `[Fundamental]`
Pass **`isUndoEnabled: true`** to `.modelContainer`, then use the environment's **`undoManager`** to undo and redo.

- Outside SwiftUI, set `container.mainContext.undoManager = UndoManager()` yourself.

```swift
WindowGroup { ContentView() }
    .modelContainer(for: Trip.self, isUndoEnabled: true)

struct EditorView: View {
    @Environment(\.undoManager) private var undoManager

    var body: some View {
        HStack {
            Button("Undo") { undoManager?.undo() }.disabled(!(undoManager?.canUndo ?? false))
            Button("Redo") { undoManager?.redo() }.disabled(!(undoManager?.canRedo ?? false))
        }
    }
}
```

**Follow-ups:**
- **Does shake-to-undo work?** Yes, once undo is enabled, the system undo gestures work too.
- **Does undo work for background changes?** No, only for changes in the context that has the undo manager.
- **How do you group several changes into one undo step?** Use `undoManager.beginUndoGrouping()` and `endUndoGrouping()`.

### Q35. Can you create a model instance before any container exists? `[Senior]`
**Not safely**: SwiftData must know your schema first, so creating a model before any container exists can crash with **"Failed to find any currently loaded container for Trip."**

- This often happens in previews, tests, or static sample data that is created too early.
- **Fix:** create the container first (an in-memory one in tests and previews), then create the models.

```swift
// ❌ Static sample data created before any container exists
static let sample = Trip(name: "Sample", startDate: .now)

// ✅ Create the container first, then the models
let container = try ModelContainer(for: Trip.self,
                                   configurations: ModelConfiguration(isStoredInMemoryOnly: true))
let sample = Trip(name: "Sample", startDate: .now)
container.mainContext.insert(sample)
```

**Follow-ups:**
- **Why do static properties cause it?** They may be created before your test or preview sets up the container.
- **How do you make sample data safe?** Use a static computed property or a function, called after the container exists.
- **Does this happen in the real app?** Rarely, because the container is created at launch.

## 5. ModelContext: CRUD, Saving & Undo

### Q36. What is a `ModelContext`? `[Fundamental]`
A `ModelContext` is a **scratchpad for your data**: you fetch, insert, change, and delete models in it, and nothing is written to disk until it **saves**.

- It keeps track of every change you make.
- **It's not thread-safe (`Sendable`):** use it only on the actor that created it.
- `mainContext` belongs to the main actor (the UI).

```swift
let context = container.mainContext
let trip = Trip(name: "Iceland", startDate: .now)
context.insert(trip)          // in memory only
trip.name = "Iceland 2027"    // tracked
try context.save()            // now written to disk
```

**Follow-ups:**
- **Can other contexts see unsaved changes?** No. Only saved changes are shared.
- **How do you make a background context?** Use a `@ModelActor` (see Q60).
- **Why isn't a context thread-safe?** It holds mutable state, so using it from two threads at once can corrupt it.

### Q37. Show basic CRUD operations. `[Fundamental]`
**Create** with `insert`, **read** with `fetch`, **update** by changing properties, **delete** with `delete`, and **persist** with `save()`.

```swift
// Create
let trip = Trip(name: "Iceland", startDate: .now)
modelContext.insert(trip)

// Read
let descriptor = FetchDescriptor<Trip>(
    predicate: #Predicate<Trip> { $0.name.localizedStandardContains("ice") },
    sortBy: [SortDescriptor(\.startDate)]
)
let trips = try modelContext.fetch(descriptor)

// Update: just change it; the context notices
trip.name = "Iceland 2027"

// Delete
modelContext.delete(trip)

// Save everything to disk
try modelContext.save()
```

**Follow-ups:**
- **Do you need an "update" method?** No. Changing a property is enough. The context tracks it.
- **Does `fetch` include unsaved inserts?** Yes, by default (`includePendingChanges` is true).
- **What does `localizedStandardContains` do?** A search that ignores upper/lower case and accents, like Finder search.

### Q38. How does autosave work? `[Senior]`
The **main context saves automatically** from time to time and on events like the app going to the background, but **contexts you create yourself don't**, so you must call `save()` there.

- Autosave timing isn't exact.
- Call `save()` yourself **right before** something important: updating a widget, starting a server sync, or a risky operation.

```swift
// Main context: autosave is on
container.mainContext.autosaveEnabled      // true

// Background context (e.g. in a @ModelActor): save explicitly
modelContext.insert(Trip(name: "Imported", startDate: .now))
try modelContext.save()                    // don't rely on autosave here
```

**Follow-ups:**
- **When can autosaved changes be lost?** If the app is killed right after a change, like stopping it from Xcode.
- **Should you turn autosave off for big imports?** Yes, and save in batches yourself (see Q64).
- **Does autosave throw errors?** Not to you. Explicit `save()` lets you see and handle errors.

### Q39. What do `hasChanges` and `rollback()` do? `[Fundamental]`
`hasChanges` tells you **whether there are unsaved changes**, and `rollback()` **throws away all unsaved changes** in that context.

- **Careful:** `rollback()` on the main context throws away **every** unsaved change in the app, not just the current screen's.

```swift
if modelContext.hasChanges {
    try modelContext.save()      // save only when needed
}

modelContext.rollback()          // undo ALL unsaved changes in this context
```

**Follow-ups:**
- **Why is `rollback()` dangerous on the main context?** Other screens' unsaved edits are lost too (see Q123).
- **What should you use for a Cancel button?** A draft struct or a separate editing context (see Q41).
- **Does `rollback()` undo saved changes?** No, only changes since the last save.

### Q40. How do you save multiple changes atomically? `[Senior]`
Wrap the changes in **`modelContext.transaction { }`**, so they're **saved together**: either all of them, or none.

- "Atomic" means all-or-nothing, like a bank transfer: take money from one account **and** add it to the other.

```swift
try modelContext.transaction {
    let source = account(named: "Checking")
    let target = account(named: "Savings")
    source.balance -= 100
    target.balance += 100
    modelContext.insert(Transfer(from: source, to: target, amount: 100))
}
// All three changes are saved together when the block ends
```

**Follow-ups:**
- **What happens if the block throws?** None of the changes are saved.
- **Do you call `save()` inside?** No. The transaction saves when the block finishes.
- **When does this matter?** When partial changes would leave data wrong, like money leaving one account but not arriving.

### Q41. How do you implement an edit screen with Cancel and Save? `[Lead/Expert]`
SwiftData has **no child contexts** (unlike Core Data), so the simplest way is to **edit a draft copy** and **copy it back to the model only on Save**.

- **Option A (recommended): a draft struct.** Cancel just closes the screen.
- **Option B: a separate editing context** with autosave off. Save it on Save, throw it away on Cancel.
- **Option C:** undo grouping on the main context. Works, but it's tied to global undo.

```swift
// Option A: edit a draft, apply it on Save
struct TripDraft {
    var name: String
    var startDate: Date

    init(trip: Trip) {
        name = trip.name
        startDate = trip.startDate
    }

    func apply(to trip: Trip) {
        trip.name = name
        trip.startDate = startDate
    }
}

struct EditTripView: View {
    let trip: Trip
    @State private var draft: TripDraft
    @Environment(\.dismiss) private var dismiss

    init(trip: Trip) {
        self.trip = trip
        _draft = State(initialValue: TripDraft(trip: trip))
    }

    var body: some View {
        Form {
            TextField("Name", text: $draft.name)
            DatePicker("Start", selection: $draft.startDate, displayedComponents: .date)
        }
        .toolbar {
            Button("Cancel") { dismiss() }                         // nothing to undo
            Button("Save") { draft.apply(to: trip); dismiss() }    // copy changes to the model
        }
    }
}

// Option B: a separate editing context
let editingContext = ModelContext(container)
editingContext.autosaveEnabled = false
let editableTrip = editingContext.model(for: trip.persistentModelID) as? Trip
// Save:   try editingContext.save()
// Cancel: just throw editingContext away
```

**Follow-ups:**
- **Why not use `rollback()` for Cancel?** It would also throw away unsaved changes from other screens.
- **When is Option B better?** When the edit touches relationships or many objects that are hard to copy into a struct.
- **What is a "child context"?** A Core Data feature: a context whose saves go to a parent context. SwiftData doesn't have it.

### Q42. How do you delete many objects efficiently? `[Senior]`
Use **`modelContext.delete(model:where:)`**, which deletes all matching records **without loading them** into memory one by one.

- Delete rules (like cascade) still apply.

```swift
let cutoff = Calendar.current.date(byAdding: .year, value: -2, to: .now)!
try modelContext.delete(model: Trip.self, where: #Predicate<Trip> { $0.endDate < cutoff })
try modelContext.save()
```

**Follow-ups:**
- **Why is it faster than a loop?** It doesn't create a Swift object for each record before deleting it.
- **Do cascade rules still run?** Yes.
- **How do you delete everything of one type?** Call `delete(model: Trip.self)` with no predicate.

### Q43. What happens if you access a model after it has been deleted? `[Senior]`
Reading a **deleted (and saved) model** can **crash**, because its data no longer exists in the store.

- Common cause: a detail screen still showing a record that was deleted somewhere else (another screen, a background sync, or iCloud).
- **Protect yourself:** check `model.isDeleted` or `model.modelContext == nil`, drive lists with `@Query` so deleted rows disappear, and close detail screens when their model is deleted.

```swift
struct TripDetailView: View {
    let trip: Trip
    @Environment(\.dismiss) private var dismiss

    var body: some View {
        Group {
            if trip.isDeleted || trip.modelContext == nil {
                ContentUnavailableView("Trip deleted", systemImage: "trash")
            } else {
                Text(trip.name)
            }
        }
    }
}
```

**Follow-ups:**
- **Why does `@Query` help?** Deleted records disappear from its results automatically.
- **What does `modelContext == nil` mean?** The model isn't attached to any context anymore.
- **How do you close the screen automatically?** Watch for the deletion (for example with `onChange` on a query of that ID) and call `dismiss()`.

### Q44. Can a model belong to multiple contexts? `[Senior]`
**No**: a model **object** belongs to exactly **one** context, but the **same database record** can be loaded as different objects in different contexts.

- To use a record in another context, pass its `persistentModelID` and load it there.

```swift
let tripID = trip.persistentModelID                       // from the main context

let backgroundContext = ModelContext(container)
let sameRecord = backgroundContext.model(for: tripID) as? Trip   // a different object, same record
```

**Follow-ups:**
- **Are the two objects equal?** They represent the same record, but they're different objects in memory.
- **Do changes in one object show in the other?** Only after saving, when the other context picks up the change.
- **What error appears if you mix them?** "Illegal attempt to establish a relationship…" (see Q26).

### Q45. Do changes saved in one context appear in another? `[Senior]`
**Yes, after saving**: when a context saves, the container shares the changes, and other contexts (including the main context behind `@Query`) pick them up.

- **Unsaved** changes are never visible to other contexts.
- Early iOS 17 versions had bugs where background saves didn't refresh `@Query` quickly. Test this on your minimum iOS.

```swift
// Background actor
modelContext.insert(Trip(name: "Imported", startDate: .now))
try modelContext.save()          // now the main context and @Query can see it

// SwiftUI view
@Query private var trips: [Trip]  // updates after the background save
```

**Follow-ups:**
- **What if a manual fetch doesn't update?** Fetch again after saves, for example on `ModelContext.didSave` (see Q89).
- **What was the iOS 17 issue?** `@Query` sometimes didn't refresh after a background save.
- **What is iOS 27's `ResultsObserver` for?** Auto-updating fetch results outside SwiftUI views (see Q47).

## 6. Querying: `@Query`, `FetchDescriptor` & `#Predicate`

### Q46. What is `@Query`, and how does it work? `[Fundamental]`
`@Query` is a SwiftUI property wrapper that **fetches models and keeps them up to date**: when matching data is added, changed, or deleted, the view refreshes automatically.

- You can give it a filter, a sort order, and an animation.
- It uses the `modelContext` from the view's environment.

```swift
struct FavoritesView: View {
    @Query(filter: #Predicate<Trip> { $0.isFavorite },     // only favorites
           sort: \Trip.startDate,
           order: .reverse,
           animation: .default)                            // animate changes
    private var favorites: [Trip]

    @Query(sort: [SortDescriptor(\Trip.startDate, order: .reverse), SortDescriptor(\Trip.name)])
    private var allTrips: [Trip]                           // sorted by two keys

    var body: some View {
        List(favorites) { Text($0.name) }
    }
}
```

**Follow-ups:**
- **Where does `@Query` get its data from?** The `modelContext` in the environment, set by `.modelContainer`.
- **Can you change the filter later?** Not directly. Rebuild the query in the view's `init` (see Q48).
- **What did iOS 27 add?** A `sectionBy:` parameter to group results into sections (see Q57).

### Q47. Can you use `@Query` in a view model? `[Senior]`
**No**: `@Query` only works **inside SwiftUI views**, because it needs the view's environment.

- **Before iOS 27:** in a view model, fetch manually with `modelContext.fetch` and fetch again when data changes (for example on `ModelContext.didSave`).
- **iOS 27:** `ResultsObserver` gives you auto-updating results outside views, built on Observation.

```swift
@MainActor @Observable
final class TripsViewModel {
    private(set) var trips: [Trip] = []
    private let context: ModelContext

    init(context: ModelContext) {
        self.context = context
        reload()
    }

    func reload() {                                    // call again after changes
        trips = (try? context.fetch(FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate)]))) ?? []
    }
}
```

**Follow-ups:**
- **What do you lose without `@Query`?** Automatic updates and animations. You must refresh yourself.
- **How do you know when to refresh?** Listen for `ModelContext.didSave`, or (iOS 27) use `ResultsObserver`.
- **Is it OK to keep `@Query` in the view and logic in the view model?** Yes, a common mix (see Q86).

### Q48. How do you make a `@Query` dynamic (filter or sort from user input)? `[Senior]`
Build the query **in the view's `init`** from values passed in, and when the parent passes new values, SwiftUI creates the view again with a **new query**.

- `@Query`'s filter and sort are fixed once created.
- So put the list in a child view that takes the search text and sort order as inputs.

```swift
struct TripListView: View {
    @Query private var trips: [Trip]

    init(searchText: String, sortOrder: SortOrder) {
        let predicate = #Predicate<Trip> { trip in
            searchText.isEmpty || trip.name.localizedStandardContains(searchText)
        }
        _trips = Query(filter: predicate, sort: \Trip.startDate, order: sortOrder)   // new query
    }

    var body: some View {
        List(trips) { Text($0.name) }
    }
}

struct TripSearchScreen: View {
    @State private var searchText = ""
    @State private var sortOrder = SortOrder.reverse

    var body: some View {
        NavigationStack {
            TripListView(searchText: searchText, sortOrder: sortOrder)   // new values → new query
                .searchable(text: $searchText)
        }
    }
}
```

**Follow-ups:**
- **Why the underscore in `_trips`?** It sets the `Query` wrapper itself, not the array.
- **Is recreating the query on every keystroke slow?** It's usually fine, and you can debounce the search text if needed.
- **Why can `searchText` be used inside the predicate?** It's a captured value, not a function call.

### Q49. What is `#Predicate`? `[Fundamental]`
`#Predicate` turns a **Swift closure into a database filter**, so filtering happens **inside the database** (as SQL), not in memory.

- It's **type-checked**: a typo in a property name is a compile error (unlike old `NSPredicate` strings).

```swift
let now = Date.now
let search = "tokyo"

let upcoming = #Predicate<Trip> { trip in trip.startDate > now }
let matching = #Predicate<Trip> { trip in trip.name.localizedStandardContains(search) }
let busy = #Predicate<Trip> { trip in trip.activities.count > 5 }
let parisActivities = #Predicate<Activity> { activity in activity.trip?.name == "Paris" }
let favoritesInFuture = #Predicate<Trip> { trip in trip.isFavorite && trip.startDate > now }
```

**Follow-ups:**
- **Why is filtering in the database better?** Only matching records are loaded, which saves memory and time.
- **How is it better than `NSPredicate`?** It's checked by the compiler. `NSPredicate` uses strings that fail only at runtime.
- **Can you use relationships in it?** Yes, like `activity.trip?.name == "Paris"`.

### Q50. What are the limitations of `#Predicate`? `[Lead/Expert]`
`#Predicate` supports **only a small part of Swift**: simple comparisons, logic, and some built-in methods, but **not your own functions, computed properties, or function calls** like `Date.now`.

- **Supported:** `==`, `<`, `&&`, `||`, math, optional chaining, `??`, and methods like `contains`, `starts(with:)`, `localizedStandardContains`, `isEmpty`, `count`, `contains(where:)`.
- **Not supported:** your own functions, computed or `@Transient` properties, calls like `Date.now` inside the closure.
- **Capture values outside** the closure as constants.
- Some unsupported things **compile but fail at runtime**, so test every predicate with real data.

```swift
// ❌ Calls Date.now inside, and uses a computed property
let bad = #Predicate<Trip> { $0.startDate > Date.now && $0.isUpcomingSoon }

// ✅ Capture values first; use only stored properties
let now = Date.now
let soon = Calendar.current.date(byAdding: .day, value: 7, to: now)!
let good = #Predicate<Trip> { $0.startDate > now && $0.startDate < soon }
```

**Follow-ups:**
- **What does "expression too complex" mean?** The compiler gave up on a long predicate. Split it into smaller ones (see Q51).
- **Why do some predicates fail only at runtime?** They compile as Swift but can't be turned into SQL.
- **How do you catch these failures early?** Unit test each predicate against an in-memory store (see Q92).

### Q51. How do you combine predicates? `[Lead/Expert]`
Since iOS 17.4, you can **call one predicate inside another** with `.evaluate(...)`, which lets you build a filter from smaller pieces.

- Useful when the user picks several filters (search + category + date range).

```swift
let now = Date.now
let isFavorite = #Predicate<Trip> { $0.isFavorite }
let isUpcoming = #Predicate<Trip> { $0.startDate > now }

let combined = #Predicate<Trip> { trip in
    isFavorite.evaluate(trip) && isUpcoming.evaluate(trip)     // both must be true
}
```

**Follow-ups:**
- **Why not write one big predicate?** Big predicates are hard to read and can hit "expression too complex."
- **How do you skip a filter the user didn't choose?** Use a predicate that's always true, like `#Predicate<Trip> { _ in true }`.
- **What OS do you need for `evaluate`?** iOS 17.4.

### Q52. What is a `FetchDescriptor`, and what options does it have? `[Senior]`
A `FetchDescriptor` describes **exactly what to fetch**: the filter, the sort order, how many, which properties, and which relationships to load in advance.

```swift
var descriptor = FetchDescriptor<Trip>(
    predicate: #Predicate<Trip> { $0.isFavorite },               // filter
    sortBy: [SortDescriptor(\.startDate, order: .reverse)]       // order
)
descriptor.fetchLimit = 20                                       // at most 20 results
descriptor.fetchOffset = 40                                      // skip the first 40 (page 3)
descriptor.propertiesToFetch = [\.name, \.startDate]             // load only these properties
descriptor.relationshipKeyPathsForPrefetching = [\.activities]   // load activities too (avoid N+1)
descriptor.includePendingChanges = true                          // include unsaved changes (default)

let trips = try modelContext.fetch(descriptor)
```

**Follow-ups:**
- **Can `@Query` use a descriptor?** Yes: `@Query(Self.recentTripsDescriptor) private var recent: [Trip]`.
- **What does `propertiesToFetch` save?** Memory and time, when a list needs only a few fields.
- **Why prefetch relationships?** To avoid one extra query per row (see Q28).

### Q53. How do you count records without loading them? `[Fundamental]`
Use **`fetchCount`**, which asks the database for **just the number**, without loading any objects.

- Much cheaper than `fetch(...).count`. Great for badges and totals.

```swift
let openCount = try modelContext.fetchCount(
    FetchDescriptor<TodoItem>(predicate: #Predicate { !$0.isDone })
)
```

**Follow-ups:**
- **Why is `fetch(...).count` worse?** It loads every object into memory just to count them.
- **Can you count with a filter?** Yes, pass a predicate in the descriptor.
- **Where is this useful?** Badges, "12 items" labels, and "is the database empty?" checks.

### Q54. How do you paginate results? `[Senior]`
Set **`fetchLimit`** (page size) and **`fetchOffset`** (how many to skip), and **always sort**, so each page has a stable order.

- For very large tables, **keyset pagination** is faster: instead of skipping rows, ask for rows after the last one you saw (for example `startDate < lastSeenDate`).

```swift
func fetchPage(_ page: Int, pageSize: Int = 50) throws -> [Trip] {
    var descriptor = FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate, order: .reverse)])
    descriptor.fetchLimit = pageSize            // how many per page
    descriptor.fetchOffset = page * pageSize    // how many to skip
    return try modelContext.fetch(descriptor)
}
```

**Follow-ups:**
- **Why must you sort?** Without a sort, the database can return rows in any order, so pages can overlap or skip items.
- **Why is a large offset slow?** The database still walks over all the skipped rows.
- **Do you need pagination with `@Query`?** For huge lists, a `fetchLimit` on the query's descriptor helps.

### Q55. How do you iterate over a huge result set without loading everything? `[Lead/Expert]`
Use **`modelContext.enumerate`**, which loads records **in batches** (for example 500 at a time), so memory stays low.

- Good for maintenance jobs and data fixes.
- Pass **`allowEscapingMutations: true`** if you change models inside the loop and save afterwards.

```swift
try modelContext.enumerate(FetchDescriptor<Photo>(), batchSize: 500, allowEscapingMutations: true) { photo in
    photo.needsReindex = true
}
try modelContext.save()
```

**Follow-ups:**
- **What happens without `allowEscapingMutations`?** If you change models inside the block, the enumeration reports an error.
- **How do you choose the batch size?** Start around a few hundred, and measure memory with Instruments.
- **Where should this run?** On a background `@ModelActor`, not the main thread.

### Q56. How do you fetch only identifiers? `[Senior]`
Use **`fetchIdentifiers`**, which returns just the **IDs** of matching records, without loading full objects.

- IDs are small and `Sendable`, so you can pass them to another actor or use them in a diffable data source.

```swift
let ids: [PersistentIdentifier] = try modelContext.fetchIdentifiers(
    FetchDescriptor<Trip>(predicate: #Predicate { $0.isFavorite })
)
```

**Follow-ups:**
- **Why are IDs useful for UIKit?** Diffable data sources need `Hashable` IDs, and `PersistentIdentifier` is `Hashable`.
- **How do you get the model back from an ID?** `modelContext.model(for: id)`.
- **Is it faster than a normal fetch?** Yes, because it doesn't create model objects.

### Q57. How do you group results into sections? `[Senior]`
**On iOS 27**, add **`sectionBy:`** to `@Query` and read the groups from `_trips.sections`. **Before iOS 27**, fetch sorted results and **group them in memory** yourself.

- The normal `trips` array stays a flat list, so existing code keeps working.
- Each section has an `id` (the value it's grouped by) and contains its models.

```swift
// iOS 27: sectioned query
@Query(sort: \Trip.startDate, sectionBy: \.destination) private var trips: [Trip]

var body: some View {
    List {
        ForEach(_trips.sections) { section in
            Section(section.id) {                       // e.g. "Japan"
                ForEach(section) { trip in Text(trip.name) }
            }
        }
    }
}

// Before iOS 27: group in memory
private var tripsByYear: [(year: Int, trips: [Trip])] {
    Dictionary(grouping: trips) { Calendar.current.component(.year, from: $0.startDate) }
        .sorted { $0.key > $1.key }
        .map { (year: $0.key, trips: $0.value) }
}
```

**Follow-ups:**
- **Why sort by the same key you section by?** So each section's items are together and the sections appear in order.
- **Where should in-memory grouping happen for big lists?** In the model layer, not in `body`, so it isn't redone on every update.
- **What's Core Data's equivalent?** `@SectionedFetchRequest`.

### Q58. How do you sort by multiple keys or by a relationship property? `[Senior]`
Pass **several `SortDescriptor`s**: the first one sorts, and the next ones break ties.

- Sorting on `Bool`s or optional relationship paths has had limits in some iOS versions.
- If a sort isn't supported, **store a sortable value** on the model (for example `destinationName: String`).

```swift
@Query(sort: [
    SortDescriptor(\Trip.isFavorite, order: .reverse),   // favorites first
    SortDescriptor(\Trip.startDate)                      // then by date
])
private var trips: [Trip]
```

**Follow-ups:**
- **How do you sort by a related model's name?** Try `SortDescriptor(\Trip.destination?.name)`. If it fails on your OS, copy the name into the trip.
- **Does the order of descriptors matter?** Yes. The first is the main sort, and later ones only break ties.
- **Can you sort by a computed property?** No. The database only knows stored properties.

## 7. Concurrency & `ModelActor`

### Q59. What are SwiftData's concurrency rules? `[Senior]`
Only the **container** and **IDs** can be shared between threads. **Contexts and models must stay on the actor (thread) that created them**.

| Type | Safe to share between actors? | Rule |
|---|---|---|
| `ModelContainer` | ✅ Yes | Pass it anywhere |
| `ModelContext` | ❌ No | Use only on the actor that created it |
| `@Model` objects | ❌ No | Use only on their context's actor |
| `PersistentIdentifier` | ✅ Yes | Pass it across, then fetch the model on the other side |

- In Swift 6 mode, the compiler stops you from passing models or contexts across actors.

```swift
let container = modelContext.container          // ✅ shareable
let tripID = trip.persistentModelID             // ✅ shareable

Task.detached {
    let importer = TripImporter(modelContainer: container)
    try await importer.refresh(tripID: tripID)  // the actor fetches its own copy
}
```

**Follow-ups:**
- **What does `Sendable` mean?** The type is safe to pass between threads.
- **What happens in Swift 5 mode?** It may compile, but sharing a model across threads is a data race.
- **How do you send data back to the UI?** As IDs or simple `Sendable` structs (see Q62).

### Q60. What is `@ModelActor`? `[Senior]`
`@ModelActor` turns an actor into a **background worker with its own `ModelContext`**, so heavy database work (imports, sync, processing) doesn't slow down the UI.

- It gets `modelContainer` and `modelContext` properties automatically.
- Only one task at a time uses its context, which keeps it safe.
- **Always call `save()`** in it. Background contexts don't autosave.

```swift
@ModelActor
actor TripImporter {
    func importTrips(_ dtos: [TripDTO]) throws {
        for dto in dtos {
            modelContext.insert(Trip(name: dto.name, startDate: dto.startDate))
        }
        try modelContext.save()               // background contexts must save
    }
}

struct TripDTO: Sendable, Decodable {          // simple data from the server
    let name: String
    let startDate: Date
}

// Usage
let importer = TripImporter(modelContainer: container)
try await importer.importTrips(dtos)
```

**Follow-ups:**
- **What is a DTO?** A "data transfer object": a simple struct holding data from the server, safe to pass between threads.
- **Does it always run in the background?** Not always (see Q63).
- **How does the UI see the imported data?** After `save()`, `@Query` in the main context picks it up.

### Q61. How do you work with a specific model on a background actor? `[Senior]`
**Pass the model's ID** (which is safe to share), and **fetch the model again inside the actor** before using it.

```swift
@ModelActor
actor PhotoProcessor {
    func generateThumbnails(forTrip tripID: PersistentIdentifier) throws {
        let descriptor = FetchDescriptor<Trip>(predicate: #Predicate { $0.persistentModelID == tripID })
        guard let trip = try modelContext.fetch(descriptor).first else { return }   // fetch it here

        for photo in trip.photos where photo.thumbnailData == nil {
            photo.thumbnailData = ThumbnailRenderer.render(photo.imageData)
        }
        try modelContext.save()
    }
}

// From the UI (main actor): send the ID, not the model
let processor = PhotoProcessor(modelContainer: modelContext.container)
try await processor.generateThumbnails(forTrip: trip.persistentModelID)
```

**Follow-ups:**
- **Why not pass the `Trip` itself?** It belongs to the main context and isn't safe to use on another actor.
- **What about `modelContext.model(for:)`?** It also works. A predicate fetch confirms the record really exists.
- **What if the record was deleted in the meantime?** The fetch returns nothing, so the `guard` exits safely.

### Q62. How do you return results from a background actor to the UI? `[Senior]`
Return **`Sendable` values**: either **IDs** (and fetch the models in the main context) or **simple structs** with the data the UI needs.

```swift
struct TripSummary: Sendable, Identifiable {     // simple, safe to send
    let id: PersistentIdentifier
    let name: String
    let activityCount: Int
}

@ModelActor
actor TripReportService {
    func summaries() throws -> [TripSummary] {
        try modelContext.fetch(FetchDescriptor<Trip>()).map {
            TripSummary(id: $0.persistentModelID, name: $0.name, activityCount: $0.activities.count)
        }
    }
}
```

**Follow-ups:**
- **IDs or structs, which is better?** Structs for read-only display. IDs when the UI needs to edit the real model.
- **Why can't you return `[Trip]`?** Those models belong to the actor's context and can't cross to the main actor.
- **Does the struct update when data changes?** No, it's a snapshot. Fetch again to refresh.

### Q63. Does a `@ModelActor` always run off the main thread? `[Lead/Expert]`
**Not always**: developers have reported that a `@ModelActor` **created on the main actor** can run its database work **on the main thread**, because of how its default executor is set up.

- **Safer pattern:** create the actor from a background task.
- **Check it** during development with Instruments or `Thread.isMainThread`.
- Mentioning this shows real experience, but hedge it, because behavior can change between iOS versions.

```swift
let container = modelContext.container
Task.detached(priority: .utility) {                    // create it off the main actor
    let importer = TripImporter(modelContainer: container)
    try await importer.importTrips(dtos)
}
```

**Follow-ups:**
- **How do you check which thread it runs on?** Print `Thread.isMainThread` inside a method during development, or use Instruments.
- **Why does creation location matter?** The actor's context may be tied to the queue it was created on.
- **Is this fixed in newer iOS versions?** Don't assume it. Developers still report threading problems, so check it on every iOS version you support.

### Q64. How do you import thousands of records without freezing the UI or exhausting memory? `[Lead/Expert]`
Run the import on a **`@ModelActor`**, **save in batches**, use **unique IDs for upserts**, and **check for cancellation** between batches.

- Decode JSON off the main thread too.
- Saving in batches keeps memory low. For huge imports, you can also create a fresh context from time to time.
- Don't fetch each record one by one to check for duplicates. Let unique upserts handle it.
- Report progress to the UI with simple `Sendable` values.

```swift
@ModelActor
actor CatalogImporter {
    func importProducts(_ dtos: [ProductDTO]) throws {
        modelContext.autosaveEnabled = false
        for (index, dto) in dtos.enumerated() {
            modelContext.insert(Product(dto: dto))        // unique remoteID → upsert
            if (index + 1).isMultiple(of: 1_000) {
                try modelContext.save()                   // save every 1,000 items
                try Task.checkCancellation()              // stop if the user cancelled
            }
        }
        try modelContext.save()
    }
}
```

**Follow-ups:**
- **Why not save after every insert?** Each save has a cost. Thousands of small saves are slow.
- **Why not save only once at the end?** All unsaved objects stay in memory until then.
- **How do you show progress?** Send a `Sendable` progress value (like a percentage) back to the main actor.

### Q65. What's the problem with passing a model into a `Task` or actor? `[Senior]`
Models are **not `Sendable`**, so passing one to another actor is a **data race**: in Swift 6 it's a **compile error**, and in Swift 5 it may compile but can crash randomly.

- **Fix:** pass the ID (or a `Sendable` struct) instead.

```swift
// ❌ Swift 6 error: non-Sendable 'Trip' crosses an actor boundary
let trip = trips.first!
Task.detached {
    await uploader.upload(trip)
}

// ✅ Pass the ID
let tripID = trip.persistentModelID
Task.detached {
    try await uploader.upload(tripID: tripID)
}
```

**Follow-ups:**
- **What is a data race?** Two threads using the same data at the same time, where at least one changes it.
- **Why might Swift 5 code "work" anyway?** Races are timing-dependent, so they crash only sometimes.
- **Is a plain `Task { }` from the main actor also a problem?** It stays on the main actor, so it's fine. `Task.detached` or another actor is the problem.

### Q66. How do you keep UI-bound code safe with SwiftData in Swift 6? `[Lead/Expert]`
Use **`mainContext` only on the main actor** (views and `@MainActor` view models), do heavy work in **`@ModelActor` services**, and pass only **`Sendable` values** between them.

- **Avoid `@unchecked Sendable`** wrappers around models or contexts. They hide the compiler error without fixing the race.

```swift
@MainActor @Observable
final class TripsScreenModel {
    private let context: ModelContext                 // main context, main actor only
    private let importer: TripImporter                // background work

    init(container: ModelContainer) {
        context = container.mainContext
        importer = TripImporter(modelContainer: container)
    }

    func refresh(with dtos: [TripDTO]) async throws {
        try await importer.importTrips(dtos)          // only Sendable DTOs cross over
    }
}
```

**Follow-ups:**
- **Why is `@unchecked Sendable` dangerous here?** It tells the compiler "trust me," but the race still exists.
- **Where should `mainContext` be used?** Only in main-actor code: views and `@MainActor` classes.
- **What crosses actor boundaries?** IDs, DTO structs, and the container. Never models or contexts.

## 8. Schema Migration

### Q67. Which schema changes are handled by lightweight migration? `[Senior]`
**Simple, additive changes migrate automatically** ("lightweight migration"), but changes that need **data to be moved or fixed** need a **custom migration**.

- **Automatic (lightweight):**
  - Adding a property that is optional or has a default value.
  - Removing a property.
  - Renaming a property with `@Attribute(originalName:)`.
  - Adding a new model, or a new optional relationship.
  - Changing delete rules.
- **Needs a custom migration:**
  - Adding a unique constraint when duplicates may already exist.
  - Changing a property's type, or splitting or merging properties.
  - Moving data between relationships.

```swift
// Lightweight: a new property with a default value. Nothing else needed.
@Model
final class Trip {
    var name: String
    var notes: String = ""          // new in version 2
    init(name: String) { self.name = name }
}
```

**Follow-ups:**
- **What is a "migration"?** Updating the data already saved on users' devices to match the new model.
- **Why does a new non-optional property need a default?** Old records don't have a value for it, so SwiftData needs one to fill in.
- **What happens if a needed migration is missing?** The container fails to open, often a crash at launch.

### Q68. How do you version schemas and write a migration plan? `[Lead/Expert]`
Put each shipped version of your models in a **`VersionedSchema`** (V1, V2…), then write a **`SchemaMigrationPlan`** that lists the versions and the **steps (stages)** to move between them.

- **`willMigrate`** runs with the **old** models, before the change (for example, remove duplicates).
- **`didMigrate`** runs with the **new** models, after the change (for example, fill in new fields).
- Use `MigrationStage.lightweight` for steps that need no custom code.

```swift
enum TripSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [Trip.self] }

    @Model
    final class Trip {
        var name: String
        var destination: String
        init(name: String, destination: String) {
            self.name = name
            self.destination = destination
        }
    }
}

enum TripSchemaV2: VersionedSchema {
    static let versionIdentifier = Schema.Version(2, 0, 0)
    static var models: [any PersistentModel.Type] { [Trip.self] }

    @Model
    final class Trip {
        @Attribute(.unique) var name: String     // new: names must be unique
        var destination: String
        var notes: String = ""                   // new: property with a default
        init(name: String, destination: String) {
            self.name = name
            self.destination = destination
        }
    }
}

enum TripMigrationPlan: SchemaMigrationPlan {
    static var schemas: [any VersionedSchema.Type] { [TripSchemaV1.self, TripSchemaV2.self] }
    static var stages: [MigrationStage] { [migrateV1toV2] }

    static let migrateV1toV2 = MigrationStage.custom(
        fromVersion: TripSchemaV1.self,
        toVersion: TripSchemaV2.self,
        willMigrate: { context in
            // Remove duplicate names BEFORE the unique rule is applied
            let trips = try context.fetch(FetchDescriptor<TripSchemaV1.Trip>())
            var seen = Set<String>()
            for trip in trips where !seen.insert(trip.name).inserted {
                context.delete(trip)
            }
            try context.save()
        },
        didMigrate: nil
    )
}

// The rest of the app always uses the latest version
typealias Trip = TripSchemaV2.Trip

let container = try ModelContainer(for: Trip.self, migrationPlan: TripMigrationPlan.self)
```

**Follow-ups:**
- **Why the `typealias Trip`?** So the rest of the app writes `Trip`, and you only change the alias when a new version ships.
- **What if `willMigrate` doesn't remove duplicates?** Adding the unique rule fails, and the container can't open.
- **When do you use `didMigrate`?** To fill new fields from old data, for example converting values (see Q71).

### Q69. Why use `VersionedSchema` even before you need a migration? `[Senior]`
Because wrapping your **first shipped models in V1 from day one** gives you an **exact, frozen copy** of what's on users' devices, which makes every future migration much easier.

- Adding versioning later, when you no longer have the exact old model code, is painful and risky.

```swift
// Ship version 1 already wrapped, even with no migrations yet
enum NotesSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [Note.self] }

    @Model final class Note {
        var text: String = ""
        init(text: String) { self.text = text }
    }
}

typealias Note = NotesSchemaV1.Note
```

**Follow-ups:**
- **What is "frozen" here?** The V1 code never changes again, because it describes data already on devices.
- **What do you do for V2?** Copy V1 into a new `NotesSchemaV2`, change it there, and add a stage to the plan.
- **Does it cost anything early on?** Only a little boilerplate.

### Q70. What happens if you rename a property without `originalName`? `[Senior]`
SwiftData treats it as **deleting the old property and adding a new one**, so **the old data is lost**, and if the new property has a default value, it happens **silently**.

- Always use `@Attribute(originalName: "oldName")` when renaming.

```swift
// Version 1:  var title: String
// Version 2, correct rename:
@Model
final class Book {
    @Attribute(originalName: "title") var name: String   // keeps the old "title" data
    init(name: String) { self.name = name }
}
```

**Follow-ups:**
- **Why is it silent?** With a default value, the new property is filled with the default, so no error appears.
- **How would you notice?** Users report their data is gone, or a migration test catches it.
- **Is `originalName` enough for a type change too?** No, a type change needs a custom migration (see Q71).

### Q71. How do you change a property's type (e.g. `String` price → `Decimal`)? `[Lead/Expert]`
Do it in **steps with custom migrations**: add a new property of the new type, **copy and convert** the values, then **remove the old property** in a later version.

1. **V2:** add `priceDecimal: Decimal?` next to the old `price: String`.
2. **`didMigrate` (V1 → V2):** convert each old value into the new property.
3. **V3:** remove the old `price`, and optionally rename `priceDecimal` to `price` with `originalName`.

- Test with **real copies of old databases** from each shipped version, not only fresh installs.

```swift
static let migrateV1toV2 = MigrationStage.custom(
    fromVersion: ShopSchemaV1.self,
    toVersion: ShopSchemaV2.self,
    willMigrate: nil,
    didMigrate: { context in
        let products = try context.fetch(FetchDescriptor<ShopSchemaV2.Product>())
        for product in products {
            product.priceDecimal = Decimal(string: product.price)   // convert String → Decimal
        }
        try context.save()
    }
)
```

**Follow-ups:**
- **Why not change the type in one step?** SwiftData can't automatically convert existing values between types.
- **What if some old values can't be converted?** Decide a fallback, like `nil` or `0`, and log how many failed.
- **Why test with real old databases?** Real data has surprises that fresh test data doesn't.

### Q72. How do you test migrations? `[Lead/Expert]`
**Keep a copy of the database file from every shipped version** in your tests, open each one with the new container and migration plan, and **check the data is still correct**.

- Copy the old store to a temporary folder first, so the test file isn't changed.
- Check counts, values, and relationships.
- Test **skipped versions** too (V1 → V3), because users don't update every release.
- Run these tests in CI.

```swift
@Test func migratesV1StoreToLatest() throws {
    let fixture = Bundle.module.url(forResource: "v1", withExtension: "store")!
    let tempURL = FileManager.default.temporaryDirectory.appending(path: "\(UUID()).store")
    try FileManager.default.copyItem(at: fixture, to: tempURL)          // don't touch the fixture

    let container = try ModelContainer(for: Trip.self,
                                       migrationPlan: TripMigrationPlan.self,
                                       configurations: ModelConfiguration(url: tempURL))
    let trips = try container.mainContext.fetch(FetchDescriptor<Trip>())
    #expect(trips.count == 42)                                          // nothing lost
}
```

**Follow-ups:**
- **Where do the old store files come from?** Save one from each released version of the app (for example, from a test device).
- **Why test V1 → V3 directly?** Some users skip updates, so they migrate across several versions at once.
- **What do you check besides counts?** Specific values, relationships, and that the app can read and save afterwards.

### Q73. What should happen if a migration fails in production? `[Lead/Expert]`
**Never just crash**: log the error, **back up the store**, try to **recover** (retry, or start fresh if the data can be downloaded again), and **tell the user** if data may be lost.

- A `fatalError` on container creation means a crash on **every** launch for affected users.
- **Prevent it:** migration tests, staged rollouts, and watching launch crash rates after each release.

```swift
func makeContainer() -> ModelContainer {
    do {
        return try ModelContainer(for: Trip.self, migrationPlan: TripMigrationPlan.self)
    } catch {
        logger.error("Migration failed: \(error)")
        backUpStoreFile()                                     // keep the old data safe
        deleteStoreFile()                                     // start fresh
        if let fresh = try? ModelContainer(for: Trip.self) {
            return fresh                                      // data can be downloaded again
        }
        // Last resort: in memory, so the app still opens and can show an error screen
        return try! ModelContainer(for: Trip.self,
                                   configurations: ModelConfiguration(isStoredInMemoryOnly: true))
    }
}
```

**Follow-ups:**
- **Why back up before deleting?** So you might recover the data later with a fixed app version.
- **When is starting fresh acceptable?** When the data can be re-downloaded from a server or iCloud.
- **How do you catch problems before users do?** Migration tests in CI and a staged (phased) App Store rollout.

## 9. CloudKit Sync

### Q74. How do you enable iCloud sync with SwiftData? `[Fundamental]`
Add the **iCloud (CloudKit)** capability and the **Remote notifications** background mode, and SwiftData **syncs the private database automatically**.

1. Add **iCloud** → **CloudKit**, with a container like `iCloud.com.example.Trips`.
2. Add **Background Modes** → **Remote notifications**, so pushes can trigger sync.
3. SwiftData syncs automatically (`.automatic`), or you can name the container yourself.

```swift
let configuration = ModelConfiguration(cloudKitDatabase: .private("iCloud.com.example.Trips"))
let container = try ModelContainer(for: Trip.self, configurations: configuration)

// For a store that must stay local:
let localOnly = ModelConfiguration(cloudKitDatabase: .none)
```

**Follow-ups:**
- **Which iCloud database does it use?** The user's **private** database.
- **What does the push notification do?** It tells the app that new changes are waiting, so it can sync.
- **Do models need changes for CloudKit?** Yes (see Q75).

### Q75. What model constraints does CloudKit sync impose? `[Senior]`
For CloudKit sync, models must be **flexible**: **no unique constraints**, **every property optional or with a default**, **every relationship optional**, and **no `.deny` delete rule**.

- Once your schema is in the **production** CloudKit environment, you can only **add** fields, not delete or rename them. Plan carefully.

```swift
@Model
final class Trip {
    var name: String = ""                       // has a default
    var startDate: Date = Date.now              // has a default

    @Relationship(deleteRule: .cascade, inverse: \Activity.trip)
    var activities: [Activity]? = []            // optional relationship

    init(name: String, startDate: Date) {
        self.name = name
        self.startDate = startDate
    }
}
```

**Follow-ups:**
- **Why no unique constraints?** CloudKit can't check uniqueness across all of the user's devices.
- **Why must everything be optional or have a default?** Records can arrive from iCloud in parts, or from older app versions.
- **What's the risk of renaming a field later?** You can't rename in production CloudKit. You must add a new field instead.

### Q76. Which CloudKit databases does SwiftData support? `[Senior]`
SwiftData syncs only the user's **private** database. For **public** data or **sharing** records between users, you still need **Core Data** (`NSPersistentCloudKitContainer`) or the CloudKit APIs directly.

- Check the latest release notes, as this may change.

```swift
// Supported: private database
ModelConfiguration(cloudKitDatabase: .private("iCloud.com.example.Trips"))

// Sharing a trip with another user: needs Core Data + NSPersistentCloudKitContainer
```

**Follow-ups:**
- **What is the public database?** Data every user can read, like a shared catalog.
- **What is a shared database?** Records one user shares with specific other users, like a shared shopping list.
- **Can you mix SwiftData and Core Data for this?** Yes. They can share a store (see Q106), but it adds complexity.

### Q77. How do you handle duplicates and conflicts with CloudKit sync? `[Lead/Expert]`
CloudKit sync is **eventually consistent** (devices catch up over time), and conflicts resolve as **last writer wins**. Without unique constraints, **duplicates can happen**, so you must design for them.

- **Common cause:** seed data inserted on two devices before they sync.
- **Avoid:** inserting default data on every device.
- **Fix:** use your own stable IDs, detect duplicates after sync (history tracking helps), and merge them.
- **UI:** expect data to arrive later, and don't assume it's there immediately.

```swift
// Merge duplicates that share the same stable ID
func removeDuplicates(context: ModelContext) throws {
    let trips = try context.fetch(FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.createdAt)]))
    var seen = Set<UUID>()
    for trip in trips where !seen.insert(trip.uuid).inserted {
        context.delete(trip)              // keep the oldest one
    }
    try context.save()
}
```

**Follow-ups:**
- **What does "last writer wins" mean?** If two devices change the same record, the later change replaces the earlier one.
- **How do you know when to deduplicate?** After sync brings new records, which history tracking can tell you (see Q96).
- **Can you control when sync happens?** No. The system decides, so the UI must handle late data.

### Q78. How do you debug CloudKit sync issues? `[Senior]`
Use the **CloudKit Console** to inspect records, **test with two devices**, check **device logs**, and make sure the schema is **deployed to Production** before release.

- **Classic mistake:** sync works in development but not for App Store users, because the schema wasn't deployed to Production.
- Check the user is signed into iCloud and iCloud is enabled for the app.

```swift
// Check iCloud availability before blaming sync
let status = try await CKContainer(identifier: "iCloud.com.example.Trips").accountStatus()
if status != .available {
    print("iCloud not available: \(status)")
}
```

**Follow-ups:**
- **Development vs Production environments?** Development is for testing. App Store builds use Production, which needs the schema deployed.
- **Why two devices?** Sync is between devices, so you need two to see changes travel.
- **What logs help?** Device console messages from CloudKit and Core Data mirroring.

## 10. Performance

### Q79. What are the most common SwiftData performance problems? `[Senior]`
Most slow SwiftData code **loads too much data** or **does work in the wrong place**.

- Loading far more records than needed (big `@Query` results with no limit, big images in lists).
- One extra query per row for relationships (N+1).
- Filtering and sorting in Swift instead of in the predicate.
- Missing indexes on properties you filter or sort by.
- Imports and heavy work on the main context.
- Saving after every single insert in a big loop.

```swift
// ❌ Loads every trip, then filters in memory
@Query private var allTrips: [Trip]
var favorites: [Trip] { allTrips.filter(\.isFavorite) }

// ✅ The database does the filtering
@Query(filter: #Predicate<Trip> { $0.isFavorite }) private var favorites: [Trip]
```

**Follow-ups:**
- **What do you check first?** How much data each screen loads, and whether it's filtered in the database.
- **How do you see the queries?** Turn on SQL logging (see Q84).
- **Why is the main context a problem for imports?** Heavy work there freezes the UI.

### Q80. How do you add indexes? `[Senior]`
Use the **`#Index` macro** (iOS 18) on the properties you **filter or sort by often**, so the database can find rows quickly instead of scanning everything.

- You can index one property or a combination.
- Indexes make reads faster but writes slightly slower, and the file bigger. Don't index everything.

```swift
@Model
final class Trip {
    #Index<Trip>([\.name], [\.startDate, \.endDate])   // one single and one compound index

    var name: String
    var startDate: Date
    var endDate: Date

    init(name: String, startDate: Date, endDate: Date) {
        self.name = name
        self.startDate = startDate
        self.endDate = endDate
    }
}
```

**Follow-ups:**
- **What is an index, simply?** Like a book's index: it lets the database jump straight to matching rows.
- **What is a compound index?** One index on several properties together, for queries that use them together.
- **How do you know which to index?** Look at your most common filters and sorts, and measure with SQL logging.

### Q81. Why filter in the predicate rather than in Swift? `[Fundamental]`
Because a predicate makes the **database return only matching rows**, while filtering in Swift **loads every row into memory first**, which is much slower for big data.

```swift
// ❌ Loads every trip, then filters
@Query private var allTrips: [Trip]
var favorites: [Trip] { allTrips.filter(\.isFavorite) }

// ✅ Only favorites are loaded
@Query(filter: #Predicate<Trip> { $0.isFavorite }) private var favorites: [Trip]
```

**Follow-ups:**
- **When is filtering in Swift acceptable?** For small data sets, or when the predicate can't express the rule.
- **Does the same apply to sorting?** Yes. Sort in the descriptor so the database does it.
- **What if a filter needs a computed value?** Store that value as a real property (see Q85).

### Q82. How do you keep large binary data from slowing things down? `[Senior]`
**Keep big data away from list queries**: use external storage, store **thumbnails separately**, put heavy data in a **separate related model**, and fetch only the properties a list needs.

```swift
@Model
final class Photo {
    var caption: String
    var thumbnail: Data?                                       // small, shown in lists
    @Relationship(deleteRule: .cascade) var asset: PhotoAsset? // big data, loaded only when needed
    init(caption: String) { self.caption = caption }
}

@Model
final class PhotoAsset {
    @Attribute(.externalStorage) var fullImage: Data           // big, stored outside the database
    init(fullImage: Data) { self.fullImage = fullImage }
}
```

**Follow-ups:**
- **Why a separate model for the full image?** Relationships load lazily, so lists never touch the big data.
- **What does `propertiesToFetch` add?** It loads only the columns a list needs.
- **Should huge files be in SwiftData at all?** Sometimes it's better to save them as files and store only the path.

### Q83. How do you avoid N+1 queries? `[Senior]`
**Prefetch the relationship** in the `FetchDescriptor`, so the related objects are loaded **together with the main results** instead of one query per row.

```swift
var descriptor = FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate)])
descriptor.relationshipKeyPathsForPrefetching = [\.activities]   // load activities with the trips
let trips = try modelContext.fetch(descriptor)
```

**Follow-ups:**
- **How do you see N+1 happening?** SQL logging shows many small, similar queries.
- **What if you use `@Query`?** Create the query from a `FetchDescriptor` that has the prefetch set.
- **What's another fix?** Store a summary (like `activityCount`) on the parent (see Q85).

### Q84. How do you measure SwiftData performance? `[Senior]`
Turn on **SQL logging** to see the real database queries, use **Instruments** for time and memory, and test with **realistic amounts of data** on **older devices**.

- **SQL logging:** add the launch argument `-com.apple.CoreData.SQLDebug 1` (SwiftData's store uses Core Data underneath).
- **Instruments:** Time Profiler for slow main-thread code, Allocations for memory during imports.

```text
Xcode → Product → Scheme → Edit Scheme → Run → Arguments → Arguments Passed On Launch:
-com.apple.CoreData.SQLDebug 1
```

**Follow-ups:**
- **What does the SQL log show?** Each query, how many there are, and how long they take.
- **Why test with lots of data?** Problems only show up with thousands of rows, not ten.
- **Why older devices?** Slowness hidden on a new iPhone is obvious on old hardware.

### Q85. When would you denormalize data in SwiftData? `[Lead/Expert]`
**Denormalizing** means **storing a copy of a calculated value**, like `activityCount` on a trip, so lists don't need to load every related object just to count or summarize them.

- **Trade-off:** you must keep the copy correct. Update it in **one place**, like a repository method.

```swift
@Model
final class Trip {
    var name: String
    var activityCount: Int = 0                         // stored copy, cheap to show in lists
    @Relationship(deleteRule: .cascade, inverse: \Activity.trip)
    var activities: [Activity] = []

    func addActivity(_ activity: Activity) {            // the one place that updates both
        activities.append(activity)
        activityCount = activities.count
    }

    init(name: String) { self.name = name }
}
```

**Follow-ups:**
- **What's the risk?** The stored value can get out of sync if some code changes activities without updating it.
- **How do you reduce that risk?** Only change relationships through one method, and test it.
- **Can you filter or sort by it?** Yes, because it's a stored property. That's another benefit.

## 11. Architecture & SwiftData Outside SwiftUI

### Q86. Should views use `@Query` directly, or should data go through view models? `[Lead/Expert]`
**Both are valid**: `@Query` in views is the simplest and updates automatically, while view models make logic **testable** but need you to **refresh data yourself**, so many teams use a **mix**.

- **`@Query` in views:** least code, automatic updates and animations, Apple's recommended path. Downside: the view is tied to the database, and logic in views is hard to test.
- **View models / repositories:** testable, the database is hidden behind protocols, works with UIKit. Downside: no automatic updates (before iOS 27's `ResultsObserver`), and more code.
- **Common mix:** `@Query` for read-only lists, saving and business rules in services or `@ModelActor`s, and view models for complex screens.

```swift
// Read in the view with @Query…
struct TripListView: View {
    @Query(sort: \Trip.startDate) private var trips: [Trip]
    let service: TripService                         // …write through a service

    var body: some View {
        List(trips) { trip in
            Text(trip.name)
                .swipeActions {
                    Button("Delete", role: .destructive) {
                        Task { try await service.delete(trip.persistentModelID) }
                    }
                }
        }
    }
}
```

**Follow-ups:**
- **What does Apple recommend for SwiftUI apps?** `@Query` in views for reading.
- **What's the main downside of view models here?** You must refresh data yourself when it changes.
- **How do you decide for a team?** Pick one rule, write it down, and apply it everywhere.

### Q87. How would you abstract SwiftData behind a repository? `[Lead/Expert]`
Define a **protocol** for the data operations the app needs, implement it with a **`@ModelActor`**, and **return simple `Sendable` structs** instead of models, so the rest of the app never touches SwiftData directly.

- **Benefits:** easy to mock in tests, and you could swap the storage later.
- **Costs:** mapping code, and you must tell the UI when data changes.

```swift
struct TripSummary: Sendable, Identifiable, Hashable {
    let id: PersistentIdentifier
    let name: String
    let startDate: Date
}

protocol TripRepository: Sendable {
    func upcomingTrips() async throws -> [TripSummary]
    func addTrip(name: String, startDate: Date) async throws
    func deleteTrip(id: PersistentIdentifier) async throws
}

@ModelActor
actor SwiftDataTripRepository: TripRepository {
    func upcomingTrips() throws -> [TripSummary] {
        let now = Date.now
        let descriptor = FetchDescriptor<Trip>(
            predicate: #Predicate { $0.startDate > now },
            sortBy: [SortDescriptor(\.startDate)]
        )
        return try modelContext.fetch(descriptor).map {
            TripSummary(id: $0.persistentModelID, name: $0.name, startDate: $0.startDate)
        }
    }

    func addTrip(name: String, startDate: Date) throws {
        modelContext.insert(Trip(name: name, startDate: startDate))
        try modelContext.save()
    }

    func deleteTrip(id: PersistentIdentifier) throws {
        try modelContext.delete(model: Trip.self, where: #Predicate { $0.persistentModelID == id })
        try modelContext.save()
    }
}
```

**Follow-ups:**
- **How do you test code that uses the repository?** Write a simple mock that conforms to `TripRepository` and returns fixed data.
- **How does the UI learn about changes?** Fetch again after each call, or listen for `ModelContext.didSave`.
- **Is this always worth it?** No. It's most useful for big apps or complex business rules.

### Q88. Is it a good idea to use `@Model` types as your domain models everywhere? `[Lead/Expert]`
**For small and medium apps, yes, it's practical**. For **large apps or complex domains**, it's better to **map to `Sendable` structs** at the edge of the data layer.

- **Pros:** no mapping code, models are observable, fast to build.
- **Cons:** non-`Sendable` models spread everywhere (Swift 6 friction), business logic is tied to the database, and tests need a container.

```swift
// Small app: use the model directly in the UI
struct TripRow: View {
    let trip: Trip
    var body: some View { Text(trip.name) }
}

// Large app: map to a simple struct at the boundary
struct TripValue: Sendable { let name: String; let startDate: Date }
extension Trip { var value: TripValue { TripValue(name: name, startDate: startDate) } }
```

**Follow-ups:**
- **Why do non-`Sendable` models cause friction in Swift 6?** They can't be passed between actors, so concurrent code gets compile errors.
- **What is "the boundary"?** The point where data leaves the persistence layer, like a repository's return values.
- **What's a sign you should start mapping?** Business logic that's hard to test without a database.

### Q89. How do you use SwiftData in a UIKit app? `[Senior]`
Create the container yourself, use **`container.mainContext` on the main thread**, **fetch manually**, and **refresh when data is saved** (for example by listening to `ModelContext.didSave`).

- There's no `@Query` and no fetched results controller in UIKit.
- `PersistentIdentifier` is `Hashable` and `Sendable`, so it works well as a diffable data source ID.
- **iOS 27:** `ResultsObserver` can replace the manual "fetch again on save" step (see the follow-up below).

```swift
final class TripsViewController: UIViewController {
    private let context: ModelContext
    private var dataSource: UICollectionViewDiffableDataSource<Int, PersistentIdentifier>!
    private var saveObserver: NSObjectProtocol?

    init(container: ModelContainer) {
        self.context = container.mainContext
        super.init(nibName: nil, bundle: nil)
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() {
        super.viewDidLoad()
        // ... set up the collection view and dataSource ...
        saveObserver = NotificationCenter.default.addObserver(
            forName: ModelContext.didSave, object: nil, queue: .main     // refresh after any save
        ) { [weak self] _ in
            MainActor.assumeIsolated { self?.reload() }
        }
        reload()
    }

    deinit {
        if let saveObserver { NotificationCenter.default.removeObserver(saveObserver) }
    }

    private func reload() {
        let ids = (try? context.fetchIdentifiers(
            FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate)]))) ?? []
        var snapshot = NSDiffableDataSourceSnapshot<Int, PersistentIdentifier>()
        snapshot.appendSections([0])
        snapshot.appendItems(ids)
        dataSource.apply(snapshot, animatingDifferences: true)
    }
}
```

**Follow-ups:**
- **What is iOS 27's `ResultsObserver`?** An object that keeps fetch results up to date outside SwiftUI, using Observation. Check the exact type name in your SDK.
- **Can cells update when a model property changes?** Yes. UIKit's automatic observation tracking (on by default in iOS 26) works with `@Model` objects, because they're `Observable`.
- **Why use IDs in the snapshot instead of models?** IDs are `Hashable` and stable, and the cell can fetch the model when it's shown.

### Q90. How do you inject the model context into non-view code? `[Senior]`
**Pass the `ModelContainer`** (it's safe to share) to services and let them create `@ModelActor`s, or pass **`container.mainContext`** explicitly to main-actor code through its initializer.

- In SwiftUI, a view can read `@Environment(\.modelContext)` and pass `modelContext.container` to services it creates.

```swift
struct TripsScreen: View {
    @Environment(\.modelContext) private var modelContext
    @State private var viewModel: TripsViewModel?

    var body: some View {
        content
            .task {
                if viewModel == nil {
                    viewModel = TripsViewModel(context: modelContext)    // pass it in explicitly
                }
            }
    }
}
```

**Follow-ups:**
- **Why not use a global singleton context?** Contexts aren't thread-safe, and singletons hide dependencies and make tests harder.
- **What do background services need?** Just the container, to create their own `@ModelActor`.
- **Why create the view model in `.task`?** The environment's `modelContext` isn't available in the view's `init`.

### Q91. How do you sync SwiftData with a REST backend? `[Lead/Expert]`
**Pull** server data into SwiftData with **upserts by a remote ID**, **push** local changes with an **outbox** or **history tracking**, and pick a clear **conflict rule**.

- **Download:** decode JSON into `Sendable` DTO structs, then save them in a `@ModelActor`.
- **Avoid duplicates:** a unique `remoteID`, so re-imports update instead of duplicating.
- **Server deletions:** use server "tombstones" (deleted-item lists) or compare full lists to delete local records.
- **Upload:** an outbox table of pending changes, or history tracking since the last sync (see Q96).
- **Conflicts:** server wins, client wins, or merge by timestamp.
- **When to sync:** at launch, pull-to-refresh, push notifications, and background refresh.

```swift
@ModelActor
actor SyncService {
    func pull(api: TripsAPI) async throws {
        let dtos = try await api.fetchTrips()                 // Sendable structs
        for dto in dtos {
            modelContext.insert(Trip(remoteID: dto.id, name: dto.name))   // upsert by remoteID
        }
        try modelContext.save()
    }
}
```

**Follow-ups:**
- **What is an outbox?** A local table of changes waiting to be sent, retried until the server confirms them.
- **How do you avoid sending server changes back to the server?** Tag changes by author and skip the server's (iOS 27's `HistoryObserver` can filter by author).
- **What is a sync cursor?** A saved marker of "what I've already downloaded," so the next sync asks only for newer changes.

## 12. Testing & Previews

### Q92. How do you unit test SwiftData code? `[Senior]`
Create a **fresh in-memory container for each test**, so tests are **fast** and **don't affect each other**.

- Test predicates against a real (in-memory) store, because some predicate errors only appear at runtime.

```swift
import Testing
import SwiftData
@testable import Trips

@MainActor
struct TripModelTests {
    let container: ModelContainer
    let context: ModelContext

    init() throws {
        container = try ModelContainer(
            for: Trip.self, Activity.self,
            configurations: ModelConfiguration(isStoredInMemoryOnly: true)   // fresh, in memory
        )
        context = container.mainContext
    }

    @Test func deletingTripCascadesToActivities() throws {
        let trip = Trip(name: "Japan", startDate: .now)
        context.insert(trip)
        trip.activities.append(Activity(title: "Kyoto"))
        try context.save()

        context.delete(trip)
        try context.save()

        #expect(try context.fetchCount(FetchDescriptor<Activity>()) == 0)   // cascade worked
    }

    @Test func upcomingPredicateExcludesPastTrips() throws {
        context.insert(Trip(name: "Past", startDate: .now.addingTimeInterval(-86_400)))
        context.insert(Trip(name: "Future", startDate: .now.addingTimeInterval(86_400)))
        try context.save()

        let now = Date.now
        let upcoming = try context.fetch(FetchDescriptor<Trip>(predicate: #Predicate { $0.startDate > now }))
        #expect(upcoming.map(\.name) == ["Future"])
    }
}
```

**Follow-ups:**
- **Why in-memory?** It's fast and starts empty every time, so tests don't depend on each other.
- **Why `@MainActor` on the suite?** The tests use `mainContext`, which belongs to the main actor.
- **What should you test?** Predicates, delete rules, upserts, and migrations.

### Q93. How do you test a `@ModelActor`? `[Senior]`
Create the actor with an **in-memory container**, call its methods with `await`, then **check the results with a separate context**.

```swift
@Test func importerUpsertsByRemoteID() async throws {
    let container = try ModelContainer(for: Product.self,
                                       configurations: ModelConfiguration(isStoredInMemoryOnly: true))
    let importer = CatalogImporter(modelContainer: container)

    try await importer.importProducts([ProductDTO(remoteID: "1", name: "Old name")])
    try await importer.importProducts([ProductDTO(remoteID: "1", name: "New name")])   // same ID

    let context = ModelContext(container)                      // check with a fresh context
    let products = try context.fetch(FetchDescriptor<Product>())
    #expect(products.count == 1)                                // no duplicate
    #expect(products.first?.name == "New name")                 // updated
}
```

**Follow-ups:**
- **Why check with a new context?** It proves the actor really saved, not just kept changes in memory.
- **What if the test shows 0 products?** The actor probably forgot to call `save()`.
- **Can you test cancellation?** Yes. Cancel the task mid-import and check that a partial save is handled correctly.

### Q94. How do you set up SwiftUI previews with SwiftData? `[Fundamental]`
Create a **shared in-memory preview container** filled with **sample data**, and attach it with `.modelContainer(...)`.

- Create sample models **after** the container exists, or you'll hit the "no container" crash (see Q35).
- iOS 18: a `PreviewModifier` can share one container across many previews (see the SwiftUI file, Q110).

```swift
@MainActor
extension ModelContainer {
    static let preview: ModelContainer = {
        do {
            let container = try ModelContainer(for: Trip.self, Activity.self,
                                               configurations: ModelConfiguration(isStoredInMemoryOnly: true))
            for trip in Trip.sampleTrips {          // created after the container
                container.mainContext.insert(trip)
            }
            return container
        } catch {
            fatalError("Failed to create preview container: \(error)")
        }
    }()
}

#Preview {
    TripListView()
        .modelContainer(.preview)
}
```

**Follow-ups:**
- **Why in-memory?** Previews start clean and never touch real data.
- **How should `sampleTrips` be defined?** As a static computed property (or function), so it runs after the container exists.
- **Is `fatalError` OK here?** Yes, in preview-only code. A broken preview should fail loudly.

## 13. Advanced Features (History, App Groups, Custom Stores, Inheritance)

### Q96. What is SwiftData history tracking, and why use it? `[Lead/Expert]`
History tracking (iOS 18) gives you a **log of every insert, update, and delete** saved to the store, **including changes made by widgets, extensions, or other contexts**, so you can process **"what changed since last time."**

- **Uses:** sending local changes to a server, refreshing UI after a widget or extension changed data.
- **Tokens:** you save a **history token** (a bookmark) and next time ask for changes after it.
- **`@Attribute(.preserveValueOnDeletion)`:** keeps chosen values (like a remote ID) in the record of a deleted item, so you know what to delete on the server.
- **iOS 27:** `HistoryObserver` tells you when new history arrives, so you don't have to poll.

```swift
func changes(since token: DefaultHistoryToken?) throws -> (inserted: [PersistentIdentifier], newToken: DefaultHistoryToken?) {
    var descriptor = HistoryDescriptor<DefaultHistoryTransaction>()
    if let token {
        descriptor.predicate = #Predicate { $0.token > token }   // only newer changes
    }

    let transactions = try modelContext.fetchHistory(descriptor)
    var inserted: [PersistentIdentifier] = []

    for transaction in transactions {
        for change in transaction.changes {
            switch change {
            case .insert(let insert):
                inserted.append(insert.changedPersistentIdentifier)
            case .update, .delete:
                break                                              // handle as needed
            @unknown default:
                break
            }
        }
    }
    return (inserted, transactions.last?.token)                    // save this token for next time
}
```

**Follow-ups:**
- **Where do you store the token?** Somewhere simple, like `UserDefaults`, after processing.
- **Does history grow forever?** Delete old history with `deleteHistory(_:)` once it's processed.
- **How does iOS 27's `HistoryObserver` help?** Its `eventCounter` property increases when new history arrives. Watch it, then fetch the new changes.

### Q97. How do you share SwiftData with widgets and app extensions? `[Senior]`
Put the store in a **shared App Group** container that **both the app and the extension** open, and **reload widget timelines** after saving changes the widget shows.

- Add the same App Group capability to the app and the extension targets.
- **Widgets should only read.** Writes from extensions can conflict with the app.
- History tracking helps the app notice changes made by extensions or App Intents.

```swift
// Shared code used by both the app and the widget
enum SharedStore {
    static let container: ModelContainer = {
        let configuration = ModelConfiguration(groupContainer: .identifier("group.com.example.trips"))
        do {
            return try ModelContainer(for: Trip.self, configurations: configuration)
        } catch {
            fatalError("Shared container failed: \(error)")
        }
    }()
}

// In the app, after saving something the widget shows
try modelContext.save()
WidgetCenter.shared.reloadAllTimelines()
```

**Follow-ups:**
- **What is an App Group?** A shared folder that several of your app's targets can access.
- **Why save before reloading the widget?** The widget reads from disk, so unsaved changes are invisible to it.
- **Must every target use the same schema version?** Yes. Ship them together, with the same models.

### Q98. What is a custom `DataStore`? `[Lead/Expert]`
A custom `DataStore` (iOS 18) lets you **replace SwiftData's storage engine** with your own, like a JSON file, while still using `@Model`, `@Query`, and predicates.

- You implement the `DataStore` protocol and a matching `DataStoreConfiguration`.
- **Trade-off:** very powerful, but you must handle fetching and saving correctly yourself. Most apps should use the default store.

```swift
// Sketch: a store that saves models to a JSON file
final class JSONStore: DataStore {
    typealias Configuration = JSONStoreConfiguration
    typealias Snapshot = DefaultSnapshot
    // implement fetch(_:) and save(_:) to read and write the JSON file
}
```

**Follow-ups:**
- **When would you build one?** To read an existing file format, or to back SwiftData with another database.
- **What's the main risk?** Bugs in your fetch or save logic can corrupt data.
- **Do `@Query` and predicates still work?** Yes, through the protocol, if your store handles them correctly.

### Q99. Does SwiftData support model inheritance? `[Senior]`
**Yes, from iOS 26**: a `@Model` class can **subclass another `@Model` class**, and querying the **parent type returns all subclasses** too.

- Good for real "is-a" relationships with shared queries (for example `Media` → `Movie`, `Podcast`).
- If subclasses differ only a little, an **enum property** or composition is simpler.

```swift
@available(iOS 26, *)
@Model
class Media {                                     // not final: it has subclasses
    var title: String
    init(title: String) { self.title = title }
}

@available(iOS 26, *)
@Model
final class Movie: Media {
    var durationMinutes: Int
    init(title: String, durationMinutes: Int) {
        self.durationMinutes = durationMinutes
        super.init(title: title)
    }
}

// @Query private var allMedia: [Media]     // includes Movie objects
```

**Follow-ups:**
- **How do you fetch only movies?** Query `Movie` directly.
- **When is inheritance the wrong choice?** When the types share little, or differ only by one field. Use an enum then.
- **What's the cost?** A more complex schema and migrations.

### Q100. How would you seed initial data? `[Senior]`
Either **insert default data on first launch when the store is empty**, or **ship a ready-made database** in the app bundle.

- **Option 1:** on first launch, check `fetchCount == 0` and insert. Use a background actor if it's large.
- **Option 2:** ship a prebuilt read-only store (`allowsSave: false`), or copy it to Application Support on first launch if it needs to be editable.
- **With CloudKit:** don't insert seed data on every device, or you'll get duplicates after sync.

```swift
@MainActor
func seedIfNeeded(context: ModelContext) throws {
    guard try context.fetchCount(FetchDescriptor<Category>()) == 0 else { return }   // already seeded
    for name in ["Food", "Travel", "Work"] {
        context.insert(Category(name: name))
    }
    try context.save()
}
```

**Follow-ups:**
- **Why check the count first?** So you don't insert the defaults again on every launch.
- **Why do seeds cause duplicates with CloudKit?** Each device inserts them, then sync brings the other device's copies too.
- **When is a bundled store better?** For large reference data, like a dictionary or a product catalog.

### Q101. How do you implement Spotlight search for SwiftData content? `[Senior]`
Mark properties with **`@Attribute(.spotlight)`** for simple indexing, or index items **yourself with Core Spotlight** or **App Entities** for full control.

- Doing it yourself lets you set custom titles, thumbnails, and a stable ID to open the right screen.

```swift
@Model

    var steps: String
    init(title: String, steps: String) {
        self.title = title
        self.steps = steps
    }
}
```

**Follow-ups:**
- **How does tapping a Spotlight result open the right screen?** Index with a stable ID, then handle it as a deep link.
- **When do you need Core Spotlight instead?** For custom titles, descriptions, or thumbnails.
- **What about App Intents?** App Entities can also make content searchable and usable from Siri and Shortcuts.

### Q102. How do you protect sensitive data stored with SwiftData? `[Senior]`
Rely on **iOS file encryption (Data Protection)**, **never store secrets** like passwords or tokens in SwiftData (use the **Keychain**), and encrypt very sensitive fields **yourself**.

- With CloudKit, mark sensitive properties `@Attribute(.allowsCloudEncryption)`.

```swift
@Model
final class HealthNote {
    var date: Date
    @Attribute(.allowsCloudEncryption) var symptoms: String   // encrypted in iCloud
    init(date: Date, symptoms: String) {
        self.date = date
        self.symptoms = symptoms
    }
}

// Tokens and passwords: Keychain, never SwiftData
```

**Follow-ups:**
- **What is Data Protection?** iOS encrypts app files while the device is locked, based on the file's protection level.
- **Why not store tokens in SwiftData?** The database file is less protected than the Keychain, which is built for secrets.
- **When do you encrypt fields yourself?** For extra-sensitive data, like medical or financial details.

## 14. SwiftData vs Core Data

### Q103. Compare SwiftData and Core Data. `[Senior]`
SwiftData is **newer, simpler, and Swift-first**, while Core Data is **older, more mature, and has more advanced features**.

| | SwiftData | Core Data |
|---|---|---|
| Minimum OS | iOS 17 | iOS 3+ |
| Model definition | Swift code with `@Model` | `.xcdatamodeld` editor (+ generated classes) |
| Queries | Type-safe `#Predicate`, `FetchDescriptor` | `NSPredicate` strings, `NSFetchRequest` |
| SwiftUI | `@Query` (sections via `sectionBy:` on iOS 27), Observation | `@FetchRequest`, `@SectionedFetchRequest` |
| UIKit | Manual fetch, or `ResultsObserver` (iOS 27) | `NSFetchedResultsController` |
| Concurrency | `@ModelActor`, Swift 6 checking | `perform`/`performAndWait`, one context per queue |
| Child contexts | No | Yes (parent/child) |
| Batch operations | Batch delete | Batch insert, update, and delete |
| CloudKit | Private database | Private, public, and shared databases |
| Migration | `VersionedSchema` + `MigrationStage` | Lightweight, mapping models, staged migration |
| Maturity | Newer, changes every year | 20 years, very mature |

```swift
// SwiftData
let trips = try context.fetch(FetchDescriptor<Trip>(predicate: #Predicate { $0.isFavorite }))

// Core Data
let request = NSFetchRequest<CDTrip>(entityName: "Trip")
request.predicate = NSPredicate(format: "isFavorite == YES")
let cdTrips = try viewContext.fetch(request)
```

**Follow-ups:**
- **What's the biggest daily difference?** Models and queries are plain, type-checked Swift in SwiftData.
- **What can Core Data do that SwiftData still can't?** CloudKit sharing and public databases, child contexts, and batch inserts and updates.
- **Which is faster?** They use the same storage underneath. Core Data offers more fine-tuning options.

### Q104. When would you still choose Core Data for a new project? `[Lead/Expert]`
When you need something **SwiftData can't do yet**, or an **old iOS version**. Otherwise, SwiftData is usually the better default for new Swift and SwiftUI apps.

- You must support **iOS 16 or earlier**.
- You need **CloudKit sharing** or the **public database**.
- You need **`NSFetchedResultsController`**, batch inserts or updates, or derived attributes.
- You have **very large data** and need fine performance control.
- Your team already has **deep Core Data expertise** and a stable setup.

```swift
// Example reason: sharing records with other users needs Core Data's CloudKit container
let container = NSPersistentCloudKitContainer(name: "SharedLists")
// ... configure a shared database store ...
```

**Follow-ups:**
- **Is "the team knows Core Data" a good reason?** It's a real factor, especially with a tight deadline.
- **Did iOS 27 remove any reason?** Yes, sectioned fetching now exists in SwiftData through `@Query(sectionBy:)`.
- **Can you start with SwiftData and add Core Data later?** Yes, they can share a store, but plan carefully.

### Q105. How do you migrate an existing Core Data app to SwiftData? `[Lead/Expert]`
**Generate matching SwiftData models**, keep **names and types identical**, point SwiftData at the **existing store file**, and **move screens over step by step**.

1. Generate `@Model` classes: open the `.xcdatamodeld` in Xcode, then **Editor → Create SwiftData Code**.
2. Keep entity names, attribute names, and types **exactly** the same.
3. Point `ModelConfiguration(url:)` at the existing store file.
4. Wrap the generated models in a `VersionedSchema` as V1.
5. Move screens over gradually, and test with real store copies from production-like devices.

```swift
enum AppSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [Trip.self] }
    @Model final class Trip { var name: String = ""; init(name: String) { self.name = name } }  // generated
}

let storeURL = URL.applicationSupportDirectory.appending(path: "Trips.sqlite")   // the existing file
let container = try ModelContainer(for: AppSchemaV1.Trip.self,
                                   configurations: ModelConfiguration(url: storeURL))
```

**Follow-ups:**
- **Why keep names identical?** So SwiftData reads the existing tables and columns without a migration.
- **Do you have to move everything at once?** No. Both can run together on the same store (see Q106).
- **What's the biggest risk?** A small model mismatch that breaks opening the store, so test with real old data.

### Q106. Can Core Data and SwiftData use the same store at the same time? `[Lead/Expert]`
**Yes**, they can work together on the same database, which allows a **gradual migration**, as long as **schemas match** and **persistent history tracking** is on in Core Data.

- Both point to the **same store URL**.
- Entity names and schemas must match.
- Turn on **persistent history tracking** in Core Data (`NSPersistentHistoryTrackingKey`). SwiftData relies on it.
- Avoid class name clashes: name Core Data classes differently (like `CDTrip`), but keep the entity name `Trip`.

```swift
// Core Data side
let description = NSPersistentStoreDescription(url: storeURL)
description.setOption(true as NSNumber, forKey: NSPersistentHistoryTrackingKey)   // required
persistentContainer.persistentStoreDescriptions = [description]

// SwiftData side: same file
let container = try ModelContainer(for: Trip.self,
                                   configurations: ModelConfiguration(url: storeURL))
```

**Follow-ups:**
- **Why rename the Core Data class to `CDTrip`?** Two Swift classes named `Trip` in one module would clash.
- **Why is history tracking required?** So each side can see changes made by the other.
- **Do changes on one side appear on the other?** Yes, through the shared store and history.

### Q107. What alternatives to SwiftData and Core Data exist, and when might you pick them? `[Lead/Expert]`
The main alternatives are **GRDB/SQLite** (full SQL control), **Realm** (object database), **plain files with Codable** (small data), and **a server-first design** with a simple cache.

- **GRDB / SQLite:** full SQL, great performance, value-type records, solid migrations. Good for complex queries or big data.
- **Realm:** an object database. MongoDB deprecated its Atlas Device Sync, which affects Realm's long-term sync future.
- **Files + `Codable`:** small, simple data like settings or caches.
- **Server-first + cache:** when the real data lives on the server.
- **Decide by:** data size, query complexity, sync needs, minimum OS, team skills, and long-term vendor risk.

```swift
// Small data: Codable + a file is often enough
struct Settings: Codable { var theme: String; var fontSize: Int }
let data = try JSONEncoder().encode(settings)
try data.write(to: URL.documentsDirectory.appending(path: "settings.json"))
```

**Follow-ups:**
- **Why might a team choose GRDB?** Complex SQL queries, predictable performance, and full control.
- **What is "vendor risk"?** The risk that a third-party library is abandoned or changes direction.
- **When is SwiftData overkill?** For a few settings or a small cache, a file is simpler.

## 15. Debugging & Common Crashes

### Q108. How do you inspect what SwiftData is doing? `[Senior]`
Turn on **SQL logging**, **open the database file** in a database browser, and **log errors from `save()`** instead of hiding them with `try?`.

- Launch argument `-com.apple.CoreData.SQLDebug 1` (or `3` for more detail) prints every SQL query.
- Print the store path and open the SQLite file. Tables use Core Data names like `ZTRIP` and `Z_PK`.

```swift
print(container.configurations.first?.url.path(percentEncoded: false) ?? "")   // where the file is

do {
    try modelContext.save()
} catch {
    logger.error("Save failed: \(error)")      // don't hide it with try?
}
```

**Follow-ups:**
- **Why avoid `try?` on `save()`?** It hides failures, so data is lost silently.
- **What does level 3 SQL logging add?** More detail, including the values bound to each query.
- **What tools open the file?** Any SQLite browser, such as DB Browser for SQLite.

### Q109. What are the most common SwiftData crashes and their causes? `[Senior]`
Most SwiftData crashes come from **using models in the wrong place** (wrong thread, wrong context, after deletion) or from **failed migrations and unsupported predicates**.

| Symptom | Likely cause | Fix |
|---|---|---|
| "Failed to find any currently loaded container" | Model created before any container exists | Create the container first (tests, previews, static data) |
| Crash reading a model's property | The model was deleted, or its context was released | Check `isDeleted`, drive UI from `@Query`, keep the context alive |
| "Illegal attempt to establish a relationship…" | Models from different contexts connected | Fetch both in the same context by ID |
| Crash on launch after an update | Failed migration (duplicates + new unique rule, type change) | Versioned schemas, custom migration, migration tests |
| Crash on fetch | Unsupported `#Predicate` or sort | Simplify, use stored properties, test predicates |
| Random crashes / data races | Models or contexts used on the wrong thread | `@ModelActor`, pass IDs, enable Swift 6 checking |

```swift
// The most common fix in one line: pass IDs, not models, across actors
let tripID = trip.persistentModelID
try await backgroundService.process(tripID: tripID)
```

**Follow-ups:**
- **Which one is hardest to debug?** Data races, because they crash randomly. Swift 6 checking finds them at compile time.
- **Which one hurts users most?** A failed migration, because the app crashes on every launch.
- **How do you prevent "no container" crashes in tests?** Create an in-memory container at the start of each test.

### Q110. Why might a model created in a local `ModelContext` crash later? `[Lead/Expert]`
Because models **depend on their context** to read their data, so if you create a context **inside a function**, return its models, and the context is **released**, using those models later can crash.

- **Fix:** keep the context alive (store it) as long as you use its models, or return IDs or simple structs instead.

```swift
// ❌ The context is released when the function returns
func loadTrips(container: ModelContainer) throws -> [Trip] {
    let context = ModelContext(container)
    return try context.fetch(FetchDescriptor<Trip>())
}

// ✅ Return plain values instead
func loadTripNames(container: ModelContainer) throws -> [String] {
    let context = ModelContext(container)
    return try context.fetch(FetchDescriptor<Trip>()).map(\.name)
}
```

**Follow-ups:**
- **Why does a model need its context?** Its property values are read through the context's storage.
- **How do you keep the context alive?** Store it as a property of the object that uses the models.
- **What's the cleanest fix?** Return IDs or `Sendable` structs, not models.

### Q111. Why isn't my data saved after the app is killed? `[Senior]`
Because changes are **only on disk after a save**: background contexts don't autosave, and even the main context may not have **autosaved yet** when the app is killed.

- Common while debugging: stopping the app from Xcode right after a change.
- **Fix:** call `save()` yourself after important changes.

```swift
func addExpense(_ expense: Expense) throws {
    modelContext.insert(expense)
    try modelContext.save()        // important data: save now, don't wait for autosave
}
```

**Follow-ups:**
- **Does pressing Stop in Xcode count as killing the app?** Yes, so recent unsaved changes are lost.
- **Should you save after every change?** For important user actions, yes. For many quick edits, save at sensible moments.
- **What about background actors?** They never autosave, so always call `save()` there.

### Q112. Why does my UI not update after a background import? `[Senior]`
Usually because the background context **never called `save()`**, or the UI uses a **one-time fetch** instead of `@Query`.

- **Check 1:** did the background actor call `save()`? Unsaved changes are invisible to other contexts.
- **Check 2:** is the UI using `@Query` (auto-updating) or a manual fetch (needs a refresh)?
- **Check 3:** on early iOS 17 versions, `@Query` sometimes missed background changes. Test on your minimum OS, and add a manual refresh as a fallback.

```swift
@ModelActor
actor Importer {
    func importAll(_ dtos: [TripDTO]) throws {
        for dto in dtos { modelContext.insert(Trip(name: dto.name, startDate: dto.startDate)) }
        try modelContext.save()      // without this, the UI never sees the new trips
    }
}
```

**Follow-ups:**
- **How do you refresh a manual fetch?** Fetch again on `ModelContext.didSave`, or use iOS 27's `ResultsObserver`.
- **How do you confirm the save happened?** Check with a fresh context, or look at the SQL log.
- **Can a background import trigger animations in `@Query`?** Yes, if the query has an `animation` parameter.

### Q113. Relationship order `[Senior]`
```swift
let playlist = Playlist(name: "Road Trip")
modelContext.insert(playlist)
playlist.songs.append(contentsOf: [songA, songB, songC])   // songs: [Song]
```

**Answer:** The order is **not guaranteed** to be `[A, B, C]`.

**Why:** To-many relationships are stored without order. Add a `position` property and sort by it (see Q24).

**Follow-ups:**
- **Why does it often look correct in quick tests?** The order may happen to match, until it doesn't after a relaunch or sync.
- **How do you insert a song in the middle?** Give it a position between its neighbors, for example 15 between 10 and 20.

### Q114. Unique constraint `[Senior]`
```swift
@Model final class Product {
    @Attribute(.unique) var sku: String
    var price: Decimal
    init(sku: String, price: Decimal) { self.sku = sku; self.price = price }
}

modelContext.insert(Product(sku: "A1", price: 10))
try modelContext.save()
modelContext.insert(Product(sku: "A1", price: 12))
try modelContext.save()

print(try modelContext.fetchCount(FetchDescriptor<Product>()))
```
**Answer:** `1`.

**Why:** The second insert is an **upsert**. It updates the existing `A1` record, so its price becomes `12`.

**Follow-ups:**
- **What would happen without `.unique`?** You'd get `2`, two products with the same SKU.
- **Would this work with CloudKit sync?** No. CloudKit doesn't support unique constraints.

### Q115. Function call inside a predicate `[Fundamental]`
```swift
let upcoming = #Predicate<Trip> { $0.startDate > Date.now }
```
**Answer:** Not supported.

**Why:** `Date.now` is a function call inside the predicate. Capture it first: `let now = Date.now`, then compare with `now`.

**Follow-ups:**
- **Why is capturing allowed but calling not?** A captured value is a fixed constant the database can use. A function call can't be turned into SQL.
- **Does the same apply to `Calendar` calculations?** Yes. Calculate the date outside, then capture it.

### Q116. Computed property in a predicate `[Senior]`
```swift
@Model final class Trip {
    var startDate: Date
    var endDate: Date
    var durationDays: Int { Calendar.current.dateComponents([.day], from: startDate, to: endDate).day ?? 0 }
    // ...
}
let longTrips = #Predicate<Trip> { $0.durationDays > 7 }
```
**Answer:** It fails, either at compile time or at runtime.

**Why:** Computed properties aren't stored in the database, so the database can't filter on them. Store `durationDays` as a real property, or filter in memory for small data.

**Follow-ups:**
- **Is there another way without a new property?** Compare stored dates directly if you can express the rule with them.
- **Why might it compile but crash?** The macro may accept it, but turning it into SQL fails at runtime.

### Q117. `@Transient` after refetch `[Senior]`
```swift
trip.isSelected = true          // @Transient var isSelected = false
try modelContext.save()
// Later, the same trip is fetched in a new context
print(otherContextTrip.isSelected)
```
**Answer:** `false`.

**Why:** `@Transient` values are never saved, so they go back to their default when the model is loaded again.

**Follow-ups:**
- **What if you read it from the same object?** It's still `true` on that object, until it's loaded again.
- **Where should selection state usually live?** In the view's `@State`, not in the model.

### Q118. Background insert without saving `[Senior]`
```swift
@ModelActor
actor Importer {
    func addSample() {
        modelContext.insert(Trip(name: "Sample", startDate: .now))
    }

try await Importer(modelContainer: container).addSample()

```
**Answer:** The new trip **doesn't appear** in the view, and it's **lost** when the actor is released.

**Why:** Background contexts don't autosave. The method must call `try modelContext.save()`.

**Follow-ups:**
- **Would the main context see it without saving?** No. Unsaved changes are only visible in their own context.
- **How do you catch this in tests?** After the call, fetch with a new context and check the count.

### Q119. `@Query` in a view model `[Senior]`
```swift
@Observable
final class TripsViewModel {
    @Query var trips: [Trip]

```
**Answer:** It doesn't work.

**Why:** `@Query` only works inside SwiftUI views, because it needs the view's environment. In a view model, fetch with a `ModelContext`, or use iOS 27's `ResultsObserver`.

**Follow-ups:**
- **What's the simplest fix?** Keep `@Query` in the view and pass the results in.
- **What does `ResultsObserver` give you?** Fetch results that stay up to date outside a view.

### Q120. Passing a model to another actor `[Senior]`
```swift
let trip = trips[0]
Task.detached {
    await syncService.upload(trip)
}
```
**Answer:** In **Swift 6**, a compile error. In **Swift 5**, it compiles but it's a data race.

**Why:** `Trip` isn't `Sendable`. Pass `trip.persistentModelID` and fetch the trip again on the other actor.

**Follow-ups:**
- **Why is a data race dangerous if it "works"?** It can corrupt data or crash randomly, depending on timing.
- **What if the other side only needs the name?** Pass a `Sendable` struct with just the name.

### Q121. Temporary identifiers `[Lead/Expert]`
```swift
let trip = Trip(name: "Lisbon", startDate: .now)

```
**Answer:** Probably `not found`.

**Why:** Before saving, the ID is **temporary**, and the trip exists only in the main context. Call `try modelContext.save()` before passing the ID.

**Follow-ups:**
- **Does the ID change after saving?** Yes, a temporary ID becomes a permanent one.
- **How do you know an ID is safe to share?** Save first, then read `persistentModelID`.

### Q122. Renaming a property `[Senior]`
```swift
// Version 1 shipped with:  var title: String
// Version 2 changes it to: var name: String = ""
```
**Answer:** After the update, every existing record's `name` is `""`.

**Why:** SwiftData sees a removed `title` and a new `name`, so the old data is dropped. Fix: `@Attribute(originalName: "title") var name: String`.

**Follow-ups:**
- **Why no error or crash?** The default value fills the new property, so it fails silently.
- **Can you recover the lost data after shipping?** Only if you still have the old column, which is usually gone. Prevent it with migration tests.

### Q123. `rollback()` on the main context `[Senior]`
```swift
// Screen A edits trip.name (unsaved). Screen B, still open, edits another trip's notes (unsaved).
// The user taps Cancel on Screen A, which calls:
modelContext.rollback()
```
**Answer:** **Both** sets of unsaved edits are thrown away, including Screen B's.

**Why:** `rollback()` affects the whole context, not one screen. Use a draft or a separate editing context for Cancel (see Q41).

**Follow-ups:**
- **Would autosave have saved Screen B's edits first?** Maybe, depending on timing. That's why relying on it is unpredictable.
- **What's the safest Cancel design?** Edit a draft struct and only copy it to the model on Save.

### Q124. Deleted model in a detail view `[Senior]`
```swift
// TripDetailView(trip: trip) is on screen.
// Meanwhile, a background sync deletes that trip and saves.
// The user taps a button that reads trip.name.
```
**Answer:** It may **crash** or show **invalid data**.

**Why:** The model's data no longer exists in the store. Check `trip.isDeleted` or `trip.modelContext == nil`, and close or update the detail screen when its model is deleted (see Q43).

**Follow-ups:**
- **How can the detail screen notice the deletion?** Query that trip by ID with `@Query`, and react when the result becomes empty.
- **Can iCloud sync cause this too?** Yes. Another device can delete the record at any time.

## 18. Senior / Lead Scenario Questions

> These have no single correct answer. Interviewers look at how you think and explain trade-offs. Give the short answer first, then the steps.

### Q125. You're starting a new app. How do you choose a persistence technology? `[Lead/Expert]`
I **start from the requirements**, match them to the tool that fits, and **try the riskiest part first** before deciding.

1. **Requirements:** how much data, how complex the queries are, offline needs, sync (iCloud private? sharing? own server?), minimum iOS, widgets and extensions.
2. **SwiftData** if: iOS 17+, a SwiftUI app, moderate data, private iCloud sync or a custom server.
3. **Core Data** if: older iOS, CloudKit sharing or public data, heavy `NSFetchedResultsController` use in UIKit, batch updates.
4. **GRDB / SQLite** if: complex SQL, very large data, full control over performance.
5. **Prototype** the riskiest requirement (like sync), then write the decision in an ADR (Architecture Decision Record).

```swift
// A quick spike to test the riskiest requirement: 100,000 records with a filter
let start = Date.now
let count = try context.fetchCount(FetchDescriptor<Trip>(predicate: #Predicate { $0.isFavorite }))
print("Counted \(count) in \(Date.now.timeIntervalSince(start))s")
```

**Follow-ups:**
- **What is an ADR?** A short document that records a decision, the options, and why you chose one.
- **Why prototype first?** To find a deal-breaker before you're committed.
- **What usually decides it?** Sync needs and the minimum iOS version.

### Q126. Your Core Data app has 2 million users. How would you migrate to SwiftData? `[Lead/Expert]`
First **ask whether it's worth it**. If yes, migrate **gradually on the same store**, test with **real old databases**, and **roll out slowly** with a way back.

- **Why migrate?** Compare the benefits (faster development, Swift 6 safety, SwiftUI) with the risk. "Don't migrate" is a valid answer.
- **Plan:** generate matching `@Model` classes, run both on the same store with persistent history tracking, move read-only screens first, then writing screens, and keep Core Data for unsupported features.
- **Safety:** test with real store copies from every shipped schema version, use feature flags and a staged rollout, watch launch crashes and data checks, and have a rollback plan.
- **Team:** training, guidelines for contexts and actors, and a review checklist.

```swift
// Feature flag: move one screen at a time
if FeatureFlags.swiftDataTripsList {
    TripsListSwiftData()           // new path
} else {
    TripsListCoreData()            // old path, kept as a fallback
}
```

**Follow-ups:**
- **Why move read-only screens first?** They can't damage data if something goes wrong.
- **What do you monitor after release?** Launch crash rate, save errors, and data consistency checks.
- **What is your rollback plan?** Turn off the feature flag, so users go back to the Core Data path.

### Q127. Design an offline-first app backed by a REST API. `[Lead/Expert]`
SwiftData is the **single source of truth** on the device: the UI reads **only** from it, and a background **sync service** pulls server changes in and pushes local changes out.

- **Pull:** in a `@ModelActor`, decode DTOs, upsert by `remoteID`, handle server deletions, and save a sync cursor.
- **Push:** an outbox of pending changes (or history tracking), retried with increasing delays, with requests that are safe to repeat.
- **Conflicts:** version numbers or `updatedAt` timestamps, with a clear rule (server wins by default).
- **When:** launch, foreground, pull-to-refresh, silent push, background refresh.
- **Testing:** in-memory containers, a mocked API, and tests for conflicts and deletions.

```swift
struct FeedView: View {
    @Query(sort: \Post.createdAt, order: .reverse) private var posts: [Post]   // reads local data only
    @Environment(SyncService.self) private var sync

    var body: some View {
        List(posts) { Text($0.title) }
            .refreshable { await sync.syncNow() }    // updates SwiftData; @Query updates the list
    }
}
```

**Follow-ups:**
- **Why should the UI read only local data?** It works offline, and there's one place the data comes from.
- **What does "safe to repeat" (idempotent) mean?** Sending the same request twice has the same result as once.
- **How do you handle a deletion made while offline?** Record it in the outbox, and keep the remote ID (for example with `.preserveValueOnDeletion`).

### Q128. After a release, crash reports spike with launch crashes in `ModelContainer` creation. What do you do? `[Lead/Expert]`
**Stop the damage first**, then find the cause, fix it with a safe migration and recovery code, and **prevent it from happening again**.

1. **Contain:** pause the phased rollout, and check how many users are affected.
2. **Diagnose:** read the error (failed migration? duplicates with a new unique rule? missing version in the plan?), and reproduce it with a store from the previous version.
3. **Fix:** add or repair the migration stage (for example, remove duplicates first), and replace `fatalError` with recovery code (back up, recreate, resync).
4. **Prevent:** migration tests with stored files from every shipped version in CI, and a release checklist item for schema changes.
5. **Communicate:** update stakeholders, and tell users if data may be lost.

```swift
// Repair: remove duplicates before the unique rule is applied
static let migrateV1toV2 = MigrationStage.custom(
    fromVersion: SchemaV1.self, toVersion: SchemaV2.self,
    willMigrate: { context in
        let trips = try context.fetch(FetchDescriptor<SchemaV1.Trip>())
        var seen = Set<String>()
        for trip in trips where !seen.insert(trip.name).inserted { context.delete(trip) }
        try context.save()
    },
    didMigrate: nil
)
```

**Follow-ups:**
- **Why pause the rollout first?** To stop more users from getting the broken update while you fix it.
- **How do you reproduce it?** Install the previous version, add data, then upgrade to the new build.
- **What do you add to CI afterwards?** A migration test for every shipped version (see Q72).

### Q129. A list of 100,000 records is slow. How do you fix it? `[Lead/Expert]`
**Measure first**, then make the database do less work: **filter and sort in predicates**, **add indexes**, **load fewer rows and columns**, and **keep row views cheap**.

- Measure with SQL logging and Instruments.
- Filter and sort in predicates, and add `#Index` for those properties.
- Limit results with pagination, and use `fetchCount` for totals.
- Load only needed properties, and move big data (images, long text) into separate models.
- Avoid N+1 by prefetching or storing summary values.
- Keep row views simple. Don't calculate values per row in `body`.

```swift
var descriptor = FetchDescriptor<Trip>(
    predicate: #Predicate { $0.isArchived == false },     // filter in the database
    sortBy: [SortDescriptor(\.startDate, order: .reverse)]
)
descriptor.fetchLimit = 100                               // load one page
descriptor.propertiesToFetch = [\.name, \.startDate]      // only what the row shows
```

**Follow-ups:**
- **Which fix usually helps most?** Filtering in the database plus a page limit.
- **How do you know an index helped?** Compare query times in the SQL log before and after.
- **Does `List` itself handle 100,000 rows?** It's lazy, but loading 100,000 models is the real cost, so limit the fetch.

### Q130. How would you design data sharing between the app, widgets, and App Intents? `[Lead/Expert]`
Put the **models and one container factory** in a **shared Swift package** using an **App Group**, let the **app and App Intents write**, let **widgets only read**, and **reload widgets after writes**.

- Use history tracking in the app to notice changes made by intents or extensions.
- Keep the schema versioned. All targets must ship with the same version.

```swift
// Shared package, used by the app, the widget, and App Intents
public enum SharedModelContainer {
    public static func make() throws -> ModelContainer {
        let config = ModelConfiguration(groupContainer: .identifier("group.com.example.trips"))
        return try ModelContainer(for: Trip.self, configurations: config)
    }
}

// After a write in the app or an App Intent
WidgetCenter.shared.reloadAllTimelines()
```

**Follow-ups:**
- **Why should widgets only read?** Writes from several processes at once can conflict.
- **How does the app learn about an intent's changes?** With history tracking, or iOS 27's `HistoryObserver`.
- **Why one factory function?** So every target opens the store the same way, with the same settings.

### Q131. What do you look for when reviewing SwiftData code? `[Lead/Expert]`
I check **six areas**: concurrency, saving, queries, modeling, migrations, and testability.

- **Concurrency:** no models or contexts crossing actors, background work in `@ModelActor`, only IDs or DTOs passed across.
- **Saving:** explicit `save()` in background contexts and after important changes, and errors handled, not hidden with `try?`.
- **Queries:** filtering and sorting in predicates, no unsupported expressions, limits on big results, indexes where needed.
- **Modeling:** correct delete rules and inverses, explicit ordering where needed, unique rules (unless CloudKit), defaults for new properties.
- **Migrations:** schema changes in a new `VersionedSchema`, renames with `originalName`, migration tests added.
- **Testability:** in-memory containers in tests, and business logic in services or repositories.

```swift
// Typical review comments
try? modelContext.save()                         // ❌ handle or log the error
Task.detached { await upload(trip) }             // ❌ pass trip.persistentModelID instead
var name: String = ""   // renamed from title    // ❌ needs @Attribute(originalName: "title")
@Query private var all: [Trip]                   // ❓ filter in the predicate, not in Swift?
```

**Follow-ups:**
- **Which issue is most serious?** A missing migration or an unsafe rename, because users lose data.
- **How do you make reviews consistent?** A written checklist that everyone uses.
- **What can tools catch automatically?** Swift 6 strict concurrency catches models crossing actors.

### Q132. How would you explain `ModelContext` and `ModelActor` to a junior engineer? `[Senior]`
I'd use a **library analogy**: the container is the **library**, a context is **your desk** where you work with books, and nothing changes in the library until you **return them** (`save()`).

- Each desk belongs to one person (actor). You can't hand your open book to someone at another desk, but you can give them the **catalog number** (`PersistentIdentifier`) so they get their own copy.
- A `@ModelActor` is a **colleague with their own desk in a back room**, doing heavy work so the front desk (the UI) stays free for customers.
- Then I'd show a short `@ModelActor` example and the Swift 6 error you get when passing a model across actors.

```swift
@ModelActor
actor BackRoomWorker {                                  // a colleague with their own desk
    func renameTrip(id: PersistentIdentifier, to name: String) throws {
        guard let trip = modelContext.model(for: id) as? Trip else { return }   // their own copy
        trip.name = name
        try modelContext.save()                         // return the book to the library
    }
}

// Front desk (UI): pass the catalog number, not the book
try await worker.renameTrip(id: trip.persistentModelID, to: "Japan 2027")
```

**Follow-ups:**
- **What would you show next?** The compile error from passing the model itself, and how the ID fixes it.
- **How do you check they understood?** Ask them to predict what happens without `save()` (see Q118).
- **What is the interviewer testing here?** How clearly you explain and mentor, not only what you know.

### Final Tips
- SwiftData interviews reward **production experience**: unordered relationships, temporary IDs, `@ModelActor` threading behavior, migration failures, and CloudKit constraints. Prepare a story for at least two of these.
- Know the **trade-offs** with Core Data and when you'd still choose it. Lead interviews value balanced judgment over excitement about the newest API.
- Be ready to **write from memory**: a model with relationships, a dynamic `@Query`, a `#Predicate`, and a `@ModelActor` importer.
- Know what **iOS 27** added (sectioned `@Query`, `@Attribute(.codable)`, `ResultsObserver`, `HistoryObserver`), and check the latest WWDC "What's new in SwiftData" before your interview.
