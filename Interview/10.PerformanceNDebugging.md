## 1. Performance Fundamentals

### Q1. What does "performance" mean for an iOS app? `[Fundamental]`
**Key points:** Several dimensions, each with its own tools and metrics:

| Dimension | User experiences it as | Typical metric |
|---|---|---|
| **Launch** | "The app takes forever to open" | Time to first frame, time to first content |
| **Responsiveness** | "The app froze when I tapped" | Hang rate, input latency |
| **Smoothness** | "Scrolling stutters" | Hitch time ratio, dropped frames |
| **Memory** | "The app keeps restarting" | Footprint, memory terminations (jetsam) |
| **Energy** | "The app drains my battery" | CPU time, wakeups, radio/GPU/location usage |
| **Network** | "Content loads slowly" / "uses all my data" | Latency, bytes transferred, cache hit rate |
| **Disk** | (Indirect) slowness, storage complaints, device wear | Writes per day, storage size |
| **Size** | "Too big to download on cellular" | Download/install size |

### Q2. Why should you measure before optimizing? `[Fundamental]`
**Key points:**
- Intuition about bottlenecks is frequently wrong; optimizing the wrong code wastes time and adds complexity.
- Measurement gives a **baseline**, identifies the **actual hot spot**, and proves the fix worked.
- Workflow: **reproduce → measure (Instruments/metrics) → form a hypothesis → change one thing → measure again → guard with a test or monitor.**
- Classic quote: "Premature optimization is the root of all evil" (Knuth). The full quote continues: "...yet we should not pass up our opportunities in that critical 3%." Find the 3%.

### Q3. Why must you profile Release builds on real devices? `[Fundamental]`
**Key points:**
- **Debug builds** use `-Onone`: no inlining, no generic specialization, extra checks. Swift code can be 10× slower or more than in Release. A "slow" function in Debug may be fine in Release, and vice versa.
- **Simulators** run on the Mac's CPU, memory, and GPU, with different performance characteristics and no real memory limits, thermal throttling, or cellular radios.
- Profile on the **oldest supported device** to see what your slowest users experience.
- Xcode's **Profile** action (⌘I) builds with the Release configuration by default.

### Q4. What is perceived performance, and how do you improve it? `[Senior]`
**Key points:**
- How fast the app **feels**, which can differ from raw speed.
- Techniques:
  - Show **cached content immediately**; refresh in the background.
  - **Skeleton screens** and placeholders sized like real content (no layout jumps).
  - **Optimistic updates** (likes, sends) that don't wait for the server.
  - **Immediate feedback** for every tap (highlight, haptic, spinner) within ~100 ms.
  - **Prefetching** data and images the user is likely to need next.
  - Animations that mask latency (but never slow down fast operations artificially).

### Q5. What are performance budgets? `[Lead/Expert]`
**Key points:** Explicit, measurable limits the team agrees to stay within, checked in CI and production.

| Area | Example budget |
|---|---|
| Cold launch to first frame | < 400 ms on the oldest supported device (Apple's guidance for first frame) |
| Time to first content (home feed) | < 1 s with cached data, < 2.5 s from network |
| Scrolling | Hitch time ratio < 5 ms/s (Apple: < 5 good, 5–10 warning, > 10 critical) |
| Hang rate | No main-thread blocks ≥ 250 ms in core flows |
| Memory | Peak footprint < 300 MB on a 3 GB RAM device in the feed |
| App download size | < 100 MB |
| Idle CPU | ~0% when the app is idle in the foreground |

- Budgets turn performance from an occasional firefight into a continuously enforced requirement.

### Q6. What are the most common causes of poor iOS app performance? `[Senior]`
**Key points:**
- Work on the **main thread** that doesn't belong there (synchronous I/O, JSON decoding, image decoding, heavy computation).
- **Oversized images** (decoding and memory).
- **Inefficient algorithms** (O(n²) loops over growing collections).
- **Excessive layout/rendering work** (deep hierarchies, offscreen rendering, constraint churn, SwiftUI over-invalidation).
- **Memory growth** (leaks, unbounded caches) leading to terminations.
- **Chatty networking** (many small requests, no caching, polling).
- **Too much work at launch** (eager SDK initialization).

### Q7. What is the difference between latency and throughput? `[Fundamental]`
**Key points:**
- **Latency**: time for one operation (tap → screen updated). Users feel latency directly.
- **Throughput**: amount of work per unit of time (images decoded per second, records imported per minute).
- Optimizations can trade one for the other: batching improves throughput but may delay the first result; prioritizing the first visible item improves latency.

### Q8. How do you prioritize performance work? `[Lead/Expert]`
**Key points:**
- **Impact × reach**: how bad is it, and how many users are affected (Organizer/MetricKit data by device and OS)?
- Focus on **core flows** (launch, feed, checkout) before edge screens.
- Weigh against **effort and risk**; prefer fixes that also simplify code.
- Tie to **business metrics** where possible (faster launch → retention; fewer hangs → conversion).
- Track improvements with dashboards so wins are visible and regressions are caught.

## 2. Tooling Overview

### Q9. Which Instrument answers which question? `[Senior]`
| Question | Tool |
|---|---|
| Where is CPU time spent? | **Time Profiler** |
| Why is launch slow? | **App Launch** template |
| Why did the UI freeze? | **Hangs** (and Time Profiler on the main thread) |
| Why does scrolling stutter? | **Animation Hitches** (+ Core Animation, Time Profiler) |
| Why is memory growing? | **Allocations** (generations), **VM Tracker** |
| Is something leaking? | **Leaks**, Xcode **Memory Graph Debugger** |
| Why is the battery draining? | **Energy Log / Power Profiler**, CPU and location instruments, MetricKit |
| What's happening on the network? | **Network / HTTP Traffic** instrument |
| What files are being read/written? | **File Activity**, disk I/O instruments |
| Why are SwiftUI views updating so much? | **SwiftUI** instrument |
| What are my tasks/actors doing? | **Swift Concurrency** (Swift Tasks, Swift Actors) |
| What is the whole system doing (threads, scheduling, I/O)? | **System Trace** |
| Custom timing of my own code? | **os_signpost / Points of Interest** |

### Q10. How does the Time Profiler work, and how do you read it? `[Senior]`
**Key points:**
- It **samples** each thread's call stack at regular intervals (~1 ms) and aggregates where time is spent.
- Tips for reading:
  - Filter to the **main thread** for UI problems.
  - Enable **"Hide System Libraries"** and **"Invert Call Tree"** to see the heaviest leaf functions in your code; disable inversion to see which high-level call paths are expensive.
  - Select a **time range** around the slow interaction instead of profiling the whole session.
  - Use signposts to mark the interaction of interest.
- It shows **where** time is spent, not **why** a thread was waiting (use System Trace or Thread State views for blocking).

### Q11. What do Xcode's debug gauges show? `[Fundamental]`
**Key points:**
- The Debug navigator shows live **CPU, Memory, Energy, Disk, and Network** usage while running from Xcode.
- Useful for quick sanity checks (memory climbing as you navigate back and forth? CPU busy while idle?), then switch to Instruments for detail.
- Note: values come from Debug builds with the debugger attached, so they're indicative, not exact.

### Q12. What is the Memory Graph Debugger? `[Senior]`
**Key points:**
- Pauses the app and shows all live objects and the references between them.
- Use it to answer **"why is this object still alive?"**: select a view controller that should have been deallocated and inspect the reference chain keeping it alive.
- Purple "!" icons flag detected leaks (cycles unreachable from roots), but many problems (objects kept alive by a singleton, a stored closure, or a long-running task) aren't flagged as leaks. You must inspect manually.
- Enable **Malloc Stack Logging** (scheme Diagnostics, "Live Allocations Only") to see the **backtrace where each object was allocated**.
- Export a `.memgraph` file to analyze later or share; command-line tools `leaks`, `heap`, and `vmmap` work on it.

### Q13. What are signposts, and why use them? `[Senior]`
```swift
import os

let signposter = OSSignposter(subsystem: "com.example.app", category: .pointsOfInterest)

func loadFeed() async throws -> [Post] {
    let state = signposter.beginInterval("LoadFeed", id: signposter.makeSignpostID())
    defer { signposter.endInterval("LoadFeed", state) }

    let data = try await api.fetchFeedData()
    return try signposter.withIntervalSignpost("DecodeFeed") {
        try JSONDecoder().decode([Post].self, from: data)
    }
}

// Single moments in time
signposter.emitEvent("FirstContentDisplayed")
```
**Key points:**
- Signposts mark **intervals and events** in your own code. They appear in Instruments timelines (Points of Interest), aligned with CPU, memory, and other tracks, so you can see exactly what happened during "LoadFeed."
- Very low overhead (designed to stay in Release builds).
- Signpost intervals can be measured in performance tests with `XCTOSSignpostMetric` (Q136).

### Q14. What does Xcode Organizer provide for performance? `[Senior]`
**Key points:**
- Aggregated, privacy-preserving metrics from users who opted in to share analytics, per app version: **launch time, hang rate, memory, battery usage, disk writes, scrolling hitch rate, terminations**, plus crash and hang **reports** with stack traces.
- Metrics are segmented by device class and percentile, which is great for spotting regressions after a release.
- Includes **regression detection** and comparison across versions.

### Q15. What is MetricKit? `[Senior]`
**Key points:**
- A framework delivering **on-device performance metrics and diagnostics** to your app:
  - `MXMetricPayload` (typically daily): launch times, hang time, memory peaks, CPU and GPU time, disk writes, network transfer, cellular conditions, app exit reasons (including memory and watchdog terminations).
  - `MXDiagnosticPayload` (delivered promptly on recent iOS versions): **crash, hang, CPU exception, disk write exception, and app launch diagnostics** with call stacks.
- Lets you send data to **your own backend**, segment by your own dimensions (feature flags, user cohorts), and alert on it. (Code: Mobile System Design file, Q87.)

### Q16. What simulator and device debug options help with performance? `[Fundamental]`
**Key points:**
- Simulator **Debug menu**: Color Blended Layers, Color Off-screen Rendered, Color Copied Images, Color Misaligned Images, Slow Animations.
- **Network Link Conditioner** (device Settings → Developer, or Additional Tools for Xcode on Mac): simulate 3G, high latency, packet loss.
- Device **Settings → Developer**: on-device **hang detection** notifications, network conditioning, and logging options.
- Xcode **Environment Overrides**: Dynamic Type sizes, Dark Mode, and accessibility settings while running, so you can test layout performance with large text.

## 3. App Launch Performance

### Q17. What are the types of app launches? `[Fundamental]`
| Launch type | State | Typical cost |
|---|---|---|
| **Cold** | App not in memory (after reboot or long inactivity) | Highest: loading binaries, dyld work, initialization |
| **Warm** | App terminated recently; parts still in the system's caches | Medium |
| **Resume** | App suspended in the background, brought back | Lowest: no relaunch, just resume |

- Measure and optimize **cold launch** on older devices; it's the worst case users experience.

### Q18. What happens during app launch? `[Senior]`
```
1. Process creation (kernel)
2. dyld: load and link dynamic libraries/frameworks, rebase/bind pointers,
   Objective-C runtime setup, run static initializers (+load, C++ constructors)
3. main() → UIApplicationMain → UIApplication + app delegate created
4. application(_:didFinishLaunchingWithOptions:)
5. Scene connection: scene(_:willConnectTo:options:) → root view controller / SwiftUI root
6. First frame rendered (layout, drawing, Core Animation commit)
7. "Extended launch": loading data until meaningful content is visible
```
- Steps 1–2 are often called **pre-main**; 3–6 **post-main**. Apple's launch metric is time to **first frame**; users care about time to **first meaningful content**.

### Q19. How do you reduce pre-main launch time? `[Senior]`
**Key points:**
- **Fewer dynamic frameworks**: each one adds loading and binding work. Prefer static linking for internal modules, or Xcode 15's **mergeable libraries** (dynamic in Debug for fast iteration, merged into the binary for Release).
- **Avoid static initializers**: Objective-C `+load` methods, C++ global constructors, and `__attribute__((constructor))` run before `main`. Swift globals and static properties are **lazily** initialized, so they don't cost launch time unless accessed.
- **Remove unused code and dependencies**; audit third-party SDKs that do work at load time.
- Modern dyld (dyld4) caches much of the linking work, but these costs still matter on older devices.

### Q20. How do you reduce post-main launch time? `[Senior]`
**Key points:**
- Keep `didFinishLaunching` and scene setup minimal: crash reporting and core dependency setup only.
- **Defer** analytics, remote config fetches, non-critical SDKs, prefetching, and cache warming until after the first screen appears, and run them at low priority.
- **Lazy-initialize** services on first use.
- Render the first screen from **local data** (cache, database) rather than waiting for the network.
- Avoid synchronous disk I/O, large `UserDefaults` reads, keychain access, or heavy view hierarchies (e.g. eagerly building every tab) on the launch path.

```swift
@main
struct ShopApp: App {
    @State private var container = AppContainer()      // cheap: services created lazily inside

    var body: some Scene {
        WindowGroup {
            RootView()
                .environment(container)
                .task(priority: .background) {
                    await container.startDeferredServices()  // analytics, remote config, prefetch: after first frame
                }
        }
    }
}
```

### Q21. How do you measure launch time? `[Senior]`
**Key points:**
- **Instruments → App Launch** template: shows process creation, dyld, static initializers, `UIApplication` setup, initial frame rendering, and what each thread was doing.
- **XCTest**: `XCTApplicationLaunchMetric` in a UI test target for repeatable lab measurements (Q135).
- **Production**: Xcode Organizer launch metrics and MetricKit's launch histograms (time to first draw, resume time).
- **Extended launch**: measure until meaningful content with MetricKit or signposts:

```swift
import MetricKit

// As early as possible during launch
try? MXMetricManager.extendLaunchMeasurement(forTaskID: "home-feed")

// When the first meaningful content is on screen
try? MXMetricManager.finishExtendedLaunchMeasurement(forTaskID: "home-feed")
```

### Q22. What is app prewarming, and why does it matter? `[Lead/Expert]`
**Key points:**
- Since iOS 15, the system may **prewarm** your app: run its launch sequence (up to, but not including, `UIApplicationMain`) ahead of time, so the real launch is faster.
- Implications:
  - Code that runs before `main` (static initializers) may execute **long before** the user taps the icon. Don't record "launch start" timestamps or do user-facing work there.
  - Timing measured from process start can look misleadingly long.
  - You can detect prewarming via the `ActivePrewarm` environment variable.

```swift
let isPrewarmed = ProcessInfo.processInfo.environment["ActivePrewarm"] == "1"
```

### Q23. What happens if launch takes too long? `[Senior]`
**Key points:**
- The **watchdog** terminates apps that take too long to launch (on the order of 20 seconds), resume, or respond to certain system events. The crash report shows exception code **`0x8badf00d`** ("ate bad food").
- Common causes: synchronous network calls at launch, large database migrations on the main thread, waiting on a lock or semaphore, deadlocks.
- Watchdog timeouts are **disabled when the debugger is attached**, so these bugs often appear only in production.

### Q24. How do you handle long but necessary launch work, like a database migration? `[Lead/Expert]`
**Key points:**
- Move it **off the main thread** and show a lightweight UI (e.g. "Updating your data…") so the app is responsive and the watchdog isn't triggered.
- Make it **resumable** (if the app is killed mid-migration, it can continue next time).
- Measure migration duration on large real-world datasets and old devices.
- Where possible, migrate **lazily** (per record on access) or in the background after launch.

### Q25. Why can SwiftUI or UIKit view construction slow down launch? `[Senior]`
**Key points:**
- Building all tabs or a complex first screen eagerly creates many views, view models, and services at once.
- Fixes: create tab contents lazily, keep the first screen simple, defer heavy subviews (e.g. below-the-fold content) with lazy containers, avoid expensive work in view initializers and `body`.

### Q26. How do you prevent launch time regressions? `[Lead/Expert]`
**Key points:**
- Automated launch performance tests on dedicated devices in CI, compared against a baseline with tolerance.
- A **launch path owner** and code review checklist ("does this add work at launch?").
- Track Organizer/MetricKit launch percentiles per release; alert on regressions.
- Require new SDKs to justify launch impact (measure before and after integration).

## 4. Responsiveness & Hangs

### Q27. What is a hang? `[Fundamental]`
**Key points:**
- The main thread is busy or blocked and can't process user input or render frames, so the app feels **frozen**.
- People start noticing delays around **100 ms**; Apple's hang reporting (Organizer, on-device hang detection) flags main-thread unresponsiveness of **250 ms or more**.
- Two kinds:
  - **Busy main thread**: doing too much work (CPU-bound).
  - **Blocked main thread**: waiting on something (lock, semaphore, synchronous I/O, `DispatchQueue.sync` onto a busy queue).

### Q28. How do you find what causes a hang? `[Senior]`
**Key points:**
- **Instruments → Hangs** marks each hang interval; combine with **Time Profiler** (busy) or **Thread State / System Trace** (blocked: what was the main thread waiting on?).
- **Pause in the debugger** during the freeze and inspect the main thread's backtrace (`bt`).
- **Production**: Organizer hang reports and MetricKit `MXHangDiagnostic` with call stacks; on-device hang detection in Developer settings during testing.

### Q29. What work should never run on the main thread? `[Fundamental]`
**Key points:**
- Synchronous network calls (`Data(contentsOf:)` with remote URLs!).
- Large file reads/writes and database queries or migrations.
- JSON decoding/encoding of large payloads.
- Image decoding and resizing of large images.
- Heavy computation (filtering/sorting huge arrays, cryptography, compression).
- Waiting on locks, semaphores, or `DispatchGroup.wait()`.

```swift
// ❌ Blocks the main thread while downloading
let data = try Data(contentsOf: remoteURL)

// ✅ Suspends instead of blocking
let (data, _) = try await URLSession.shared.data(from: remoteURL)
```

### Q30. How do you move heavy work off the main thread with Swift Concurrency? `[Senior]`
```swift
@MainActor
@Observable
final class ReportViewModel {
    private(set) var report: Report?

    func generate(from entries: [Entry]) async {
        report = await ReportBuilder.build(from: entries)   // heavy work runs off the main actor
    }
}

enum ReportBuilder {
    @concurrent                                          // Swift 6.2: always on the concurrent pool
    static func build(from entries: [Entry]) async -> Report {
        Report(entries: entries.sorted(by: { $0.date < $1.date }))
    }
}
```
- Remember: `Task { }` created from main-actor code still runs on the main actor, so synchronous heavy work inside it still hangs the UI (Async/Await file, Q85).

### Q31. What is the Thread Performance Checker? `[Senior]`
**Key points:**
- An Xcode runtime diagnostic (enabled in the scheme's Diagnostics) that flags **priority inversions** (a high-priority thread waiting on lower-priority work) and **non-UI work on the main thread**, such as certain synchronous APIs.
- Issues appear as purple runtime warnings during development.

### Q32. What is priority inversion? `[Lead/Expert]`
**Key points:**
- A high-priority thread (e.g. the main thread, user-interactive QoS) waits for a resource held by a lower-priority thread (e.g. background QoS) that gets little CPU time, so the high-priority work is delayed.
- Common cause: the main thread calling `DispatchQueue.sync` on a queue whose work runs at `.background` QoS, or waiting on a semaphore signaled by background work. Semaphores **don't** propagate priority (unlike locks such as `os_unfair_lock` and Swift Concurrency awaits, where the system can boost priority).
- Fix: avoid making the main thread wait; use consistent QoS; prefer async APIs and Swift Concurrency.

### Q33. How can a deadlock freeze the app? `[Senior]`
```swift
// ❌ Deadlock: sync onto the main queue while already on the main thread
func updateUI() {
    DispatchQueue.main.sync {        // waits for the main queue... which is waiting for this call
        label.text = "Done"
    }
}

// ❌ Deadlock-prone: main thread waits for work that needs the main thread
let semaphore = DispatchSemaphore(value: 0)
Task { @MainActor in
    await refresh()
    semaphore.signal()
}
semaphore.wait()                      // if called on main: the Task can never run
```
**Key points:**
- Symptoms: complete freeze; the debugger shows the main thread waiting in `__DISPATCH_WAIT_FOR_QUEUE__`, `semaphore_wait_trap`, or a lock function.
- In production: watchdog terminations (`0x8badf00d`) or users force-quitting.
- Prevention: never wait synchronously for async work on the main thread; use `dispatchPrecondition(condition: .notOnQueue(.main))` in functions that must not run on main.

### Q34. How do you build a simple main-thread watchdog for debug builds? `[Lead/Expert]`
```swift
/// Debug-only: logs when the main thread fails to respond within `threshold`
final class HangWatchdog: @unchecked Sendable {      // mutable state is confined to `queue`
    private let queue = DispatchQueue(label: "hang-watchdog", qos: .utility)
    private let threshold: DispatchTimeInterval
    private var awaitingResponse = false

    init(threshold: DispatchTimeInterval = .milliseconds(250)) {
        self.threshold = threshold
    }

    func start() {
        queue.async { self.ping() }
    }

    private func ping() {
        awaitingResponse = true
        DispatchQueue.main.async {                    // runs only when the main thread is free
            self.queue.async { self.awaitingResponse = false }
        }
        queue.asyncAfter(deadline: .now() + threshold) {
            if self.awaitingResponse {
                print("⚠️ Main thread unresponsive for longer than the threshold")
                // A real tool would capture the main thread's stack here and report it
            }
            self.ping()
        }
    }
}
```
- Production apps should rely on MetricKit hang diagnostics and Organizer instead of custom watchdogs, which can't easily capture symbolicated main-thread stacks safely.

## 5. Rendering & Scrolling

### Q35. What is a hitch, and how is scrolling smoothness measured? `[Senior]`
**Key points:**
- A **hitch** is a frame that appears on screen later than expected, so motion visibly stutters.
- **Hitch time ratio** = total hitch time (ms) / scroll duration (s). Apple's guidance: **< 5 ms/s good**, 5–10 ms/s noticeable, **> 10 ms/s critical**.
- Frame deadlines: ~16.7 ms at 60 Hz, ~8.3 ms at 120 Hz (ProMotion), so the budget is tight on newer devices.
- Measure with Instruments **Animation Hitches**, Xcode Organizer's scrolling hitch rate, MetricKit animation metrics, and `XCTOSSignpostMetric` scroll metrics in tests.

### Q36. What are commit hitches and render hitches? `[Lead/Expert]`
**Key points:**
- **Commit hitch**: your app's main thread took too long to prepare the frame (layout, view creation, drawing, image decoding, cell configuration). Fix in your code.
- **Render hitch**: the render server/GPU took too long to draw the layer tree (offscreen passes, too many blended layers, large blurs, complex masks). Fix by simplifying layers.
- The Animation Hitches instrument classifies each hitch, which tells you where to look.

### Q37. What are the most common causes of scrolling hitches? `[Senior]`
**Key points:**
- Expensive cell configuration: creating formatters, parsing, attributed string building, synchronous image decoding.
- Large images displayed without downsampling.
- Offscreen rendering: shadows without `shadowPath`, `cornerRadius` + `masksToBounds` with content, masks, group opacity.
- Deep view hierarchies and Auto Layout churn (adding/removing constraints in `cellForRow`).
- Inaccurate size estimates causing layout jumps; SwiftUI views invalidating too often.
- (Detailed UIKit fixes: UIKit file Q64, Q95–Q101; SwiftUI: SwiftUI file Section 13.)

### Q38. How do you investigate a janky list step by step? `[Senior]`
1. Reproduce on an older device with a **Release** build and realistic data (long text, many images).
2. Record with **Animation Hitches** + **Time Profiler**; select the hitch intervals.
3. Commit hitches → inspect main-thread stacks during those frames: which cell configuration or layout code is expensive?
4. Render hitches → check offscreen rendering and blending (Simulator color debug options, Core Animation instrument).
5. Fix the top offender, re-measure, repeat. Add a scroll performance test to prevent regressions.

### Q39. How do you prepare cell content ahead of time? `[Senior]`
**Key points:**
- **Prefetching APIs** (`UICollectionViewDataSourcePrefetching`, SwiftUI `onAppear` thresholds) to start image downloads and data loads early.
- **Precompute view data** off the main thread: formatted strings, attributed text, computed heights. Cache them in the view model keyed by item ID.
- **Decode images in the background** (`byPreparingThumbnail(ofSize:)`, ImageIO downsampling), then set the ready-to-draw image on the main thread.
- iOS 15's cell **prefetching for layout** in collection views prepares cells before they're needed.

### Q40. Why are SwiftUI views sometimes slow, and how do you find out? `[Senior]`
**Key points:**
- Common causes: broad dependencies (large `ObservableObject`s), unstable identity, expensive `body` computations, `AnyView`, non-lazy containers for long lists.
- Tools: `let _ = Self._printChanges()` in `body` (prints which dependency changed), `Self._logChanges()` (iOS 17+, logs to the unified log), the **SwiftUI instrument** (body update counts and durations; redesigned in Xcode 26), Time Profiler.
- (Full details: SwiftUI file, Q97–Q104.)

### Q41. How do animations affect performance? `[Senior]`
**Key points:**
- Prefer animating **transform and opacity** (cheap for the render server) over properties that trigger layout every frame (frame changes with Auto Layout, `layoutIfNeeded` per frame).
- Avoid animating blurs, shadows without paths, and masks on large layers.
- Use `UIViewPropertyAnimator`/Core Animation instead of timer-driven manual frame updates.
- Respect Reduce Motion and Low Power Mode by simplifying animations.

## 6. Memory

### Q42. How does memory work on iOS, and what happens when an app uses too much? `[Senior]`
**Key points:**
- iOS has **no swap to disk** for app memory. Under pressure it **compresses** memory and reclaims **clean** pages (e.g. read-only code, memory-mapped files), but **dirty** memory (allocated, written data) must stay resident.
- Each app has a memory limit that depends on the device. Exceeding it, or using a lot of memory while in the background under system pressure, leads to termination by **jetsam**.
- Jetsam terminations aren't crashes in the usual sense: there's often **no crash report** in your crash reporter. Users just see the app restart. Detect them with MetricKit exit metrics and Organizer.

### Q43. What are clean, dirty, and compressed memory? `[Lead/Expert]`
| Type | Description | Counts toward footprint? |
|---|---|---|
| **Clean** | Pages that can be reloaded from disk (app binary code, memory-mapped read-only files) | No (the system can discard them) |
| **Dirty** | Pages your app has written (heap allocations, decoded images, globals) | Yes |
| **Compressed** | Dirty pages the system compressed because they weren't recently used | Yes (at their uncompressed size for footprint purposes) |

- **Footprint** (what jetsam limits care about) ≈ dirty + compressed memory. Decoded images and large caches are typical dirty-memory culprits.

### Q44. What's the difference between a leak, abandoned memory, and cached memory? `[Senior]`
**Key points:**
- **Leak**: memory no longer reachable from your code but never freed (e.g. a retain cycle between two objects nothing else references). The Leaks instrument can find these.
- **Abandoned memory**: still **reachable** but never used again (an ever-growing array of old events, view controllers retained by a singleton). Leak detectors **don't** flag this; use Allocations generations.
- **Cached memory**: intentionally kept for reuse, but should be bounded and evictable (`NSCache`, size limits, eviction on memory warnings).

### Q45. How do you find memory growth with the Allocations instrument? `[Senior]`
**Key points:** The **generational analysis** (Mark Generation) workflow:
1. Start recording; reach a steady state (e.g. the home screen).
2. **Mark Generation**.
3. Perform an action that should be memory-neutral (open a detail screen, then go back).
4. Mark Generation again. Repeat several times.
5. Each generation shows objects allocated in that window that are **still alive**. If repeating the action keeps adding persistent objects, you've found growth. Inspect their allocation stack traces.
- Combine with the Memory Graph Debugger to see who retains the surviving objects.

### Q46. What are the most common causes of retain cycles? `[Fundamental]`
**Key points:**
- Closures stored on an object capturing `self` strongly (completion handlers, Combine `sink`, observation callbacks).
- Strong delegates (`var delegate` without `weak`).
- `Timer` / `CADisplayLink` targets; block-based `NotificationCenter` observers.
- Long-running `Task`s capturing `self` (loops over async sequences).
- Parent-child object graphs without a `weak` back-reference; child coordinators never removed.
- (Examples and fixes: Swift file Q46–Q49, UIKit file Q111–Q113, Async/Await file Q107–Q110.)

### Q47. How do you write a test that catches memory leaks? `[Senior]`
```swift
import XCTest

extension XCTestCase {
    func assertNoMemoryLeak(_ instance: AnyObject, file: StaticString = #filePath, line: UInt = #line) {
        addTeardownBlock { [weak instance] in
            XCTAssertNil(instance, "Instance should have been deallocated. Potential memory leak.",
                         file: file, line: line)
        }
    }
}

final class ProfileViewModelTests: XCTestCase {
    @MainActor
    func testViewModelIsDeallocated() async {
        let viewModel = ProfileViewModel(api: StubProfileAPI())
        assertNoMemoryLeak(viewModel)
        await viewModel.load()
    }

```
- Add this to tests for view models, view controllers, and coordinators so leaks are caught in CI rather than in production.

### Q48. Why do images consume so much memory, and how do you reduce it? `[Senior]`
**Key points:**
- Decoded image memory = **width × height × bytes per pixel** (usually 4 for RGBA), regardless of file size. A 4032×3024 photo uses about **48 MB** decoded, even if the JPEG file is 3 MB and it's shown in a 100×100 point thumbnail.
- Fixes: **downsample** to the display size (ImageIO thumbnails, `preparingThumbnail(of:)`), cache downsampled images (not originals), bound caches with `NSCache` cost limits, release images for off-screen content.
- `UIGraphicsImageRenderer` automatically picks efficient pixel formats; avoid creating unnecessary full-size bitmaps when drawing.

### Q49. How should an app respond to memory pressure? `[Senior]`
```swift
import os
import UIKit

final class MemoryPressureHandler {
    private let caches: [any PurgeableCache]

    init(caches: [any PurgeableCache]) {
        self.caches = caches
        NotificationCenter.default.addObserver(
            forName: UIApplication.didReceiveMemoryWarningNotification, object: nil, queue: .main
        ) { [weak self] _ in
            self?.caches.forEach { $0.removeAll() }
        }
    }

    /// Proactive check before memory-hungry work (e.g. processing a batch of photos)
    func hasHeadroom(for bytes: Int) -> Bool {
        os_proc_available_memory() > bytes      // remaining bytes before the app's memory limit
    }
}

protocol PurgeableCache: AnyObject {
    func removeAll()
}
```
**Key points:**
- Clear rebuildable caches on memory warnings and when the app enters the background (smaller footprint makes the app less likely to be terminated while suspended).
- `NSCache` evicts automatically under pressure.
- `os_proc_available_memory()` (iOS 13+) lets you check headroom before allocating large buffers.
- Apps with genuinely large memory needs (e.g. professional editing) can request the increased memory limit entitlement on supported devices.

### Q50. When do you need `autoreleasepool` in Swift? `[Senior]`
```swift
for fileURL in photoURLs {                 // thousands of files
    autoreleasepool {
        if let image = UIImage(contentsOfFile: fileURL.path) {
            let thumbnail = makeThumbnail(image)
            save(thumbnail)
        }
    }   // autoreleased Objective-C objects are released each iteration, not at the end of the loop
}
```
- Pure Swift objects are released immediately by ARC, but Objective-C framework APIs (UIKit, Foundation, Core Image) may return **autoreleased** objects that pile up until the surrounding pool drains. In tight loops this causes huge temporary memory spikes.

### Q51. How do you investigate memory terminations (jetsam) in production? `[Lead/Expert]`
**Key points:**
- Organizer shows **memory terminations** and memory metrics per version; MetricKit's `MXAppExitMetric` reports foreground/background exits due to memory limits.
- Correlate with the screens and flows users were in (breadcrumbs, analytics events before the termination).
- Reproduce on low-memory devices; profile peak memory with Allocations and VM Tracker during those flows (large images, video, PDF rendering, huge JSON).
- Fix by reducing peak usage (streaming, downsampling, windowing large lists, smaller caches) and test on the lowest-RAM supported device.

### Q52. What memory problems do value types and copy-on-write cause? `[Lead/Expert]`
**Key points:**
- Large value types (big structs containing arrays) are cheap to copy only while **CoW** buffers stay shared. Mutating one copy duplicates the entire buffer, which can cause unexpected memory spikes and CPU cost in loops.
- Struct-heavy state trees in SwiftUI or reducers (e.g. a state struct holding a 50,000-item array) can copy large buffers on every mutation if references aren't unique.
- Fixes: mutate in place (`inout`, mutating methods), avoid accidental extra references during mutation, consider reference-type storage for very large collections, and measure with Allocations.

### Q53. How do you use the `leaks`, `heap`, and `vmmap` command-line tools? `[Lead/Expert]`
```bash
# Export from Xcode: Debug Memory Graph → File → Export Memory Graph…
leaks MyApp.memgraph                  # reports leaked objects and cycles (with backtraces if malloc logging was on)
heap MyApp.memgraph --sortBySize      # live heap objects grouped by class, sorted by total size
vmmap --summary MyApp.memgraph        # virtual memory regions: dirty, swapped/compressed, clean, by type
```
- Useful for sharing a memory snapshot from QA, comparing snapshots before/after a fix, or scripting checks in CI.

### Q54. What is the difference between `weak` and `unowned` in terms of debugging? `[Senior]`
**Key points:**
- Accessing an `unowned` reference after the object is deallocated **traps** ("Attempted to read an unowned reference but object was already deallocated"), which shows up as an `EXC_BREAKPOINT` crash.
- A `weak` reference silently becomes `nil`, so the bug may manifest as missing behavior instead of a crash.
- Prefer `weak` unless the lifetime relationship is guaranteed; when debugging "nothing happens" bugs, check for `weak` references that became `nil` too early.

### Q55. How do you reduce the memory footprint of a large feed or document? `[Senior]`
**Key points:**
- **Lazy containers** with cell reuse; don't keep views for off-screen items.
- **Windowing**: keep only nearby items fully loaded; release others (keep IDs) and reload from the local database when scrolled back.
- **Downsampled images** with bounded caches; video players pooled and released.
- **Streaming parsers** for large files instead of loading everything into memory; `Data` reads with `.mappedIfSafe` for large read-only files (memory-mapped, counted as clean memory).

## 7. CPU & Swift Performance

### Q56. How do algorithmic complexity mistakes show up in apps? `[Senior]`
```swift
// ❌ O(n × m): `contains` on an array inside a loop
let blockedIDs: [String] = loadBlockedIDs()          // 5,000 items
let visible = posts.filter { !blockedIDs.contains($0.authorID) }   // 10,000 posts → 50 million comparisons

// ✅ O(n + m): Set membership is O(1) on average
let blockedSet = Set(loadBlockedIDs())
let visibleFast = posts.filter { !blockedSet.contains($0.authorID) }
```
**Key points:**
- Code that's fine with 50 test items becomes unusable with 50,000 real ones. Test with production-sized data.
- Watch for nested loops over growing collections, repeated linear searches, and sorting inside loops.

### Q57. Why can a computed property cause an expensive copy-on-write? `[Lead/Expert]`
```swift
final class PlaylistStore {
    private var storage = Storage()

    // ❌ `songs.append(x)` calls get (a second reference to the buffer), appends to the temporary
    //    (buffer not unique → full copy), then calls set. O(n) per append
    var songs: [Song] {
        get { storage.songs }
        set { storage.songs = newValue }
    }

    // ✅ Mutate the storage directly: the buffer is uniquely referenced, so append is amortized O(1)
    func append(_ song: Song) {
        storage.songs.append(song)
    }
}

struct Storage { var songs: [Song] = [] }
```
- The same issue appears with dictionary values:

```swift
// ❌ Copies the array each time (the dictionary still references the old buffer)
var list = groups[key] ?? []
list.append(item)
groups[key] = list

// ✅ Mutates in place
groups[key, default: []].append(item)
```

### Q58. What is the performance difference between existentials and generics? `[Lead/Expert]`
```swift
protocol AreaProviding {
    var area: Double { get }
}

// Existential: each element is boxed; calls use dynamic dispatch through witness tables
func totalArea(_ shapes: [any AreaProviding]) -> Double {
    shapes.reduce(0) { $0 + $1.area }
}

// Generic: the compiler can specialize for the concrete type: static dispatch, inlining, no boxing
func totalArea<S: AreaProviding>(_ shapes: [S]) -> Double {
    shapes.reduce(0) { $0 + $1.area }
}
```
- Existentials are fine for most app code (and necessary for heterogeneous collections), but in **hot paths** (tight loops, rendering, parsing) generics or concrete types can be significantly faster.

### Q59. How do `final`, access control, and whole-module optimization help performance? `[Senior]`
**Key points:**
- They let the compiler prove a method can't be overridden, enabling **static dispatch and inlining** instead of vtable dispatch.
- `final` classes and `private`/`fileprivate` members are statically dispatched; whole-module optimization (default in Release) can infer `final` for `internal` classes without subclasses.
- Cross-module calls can't be specialized or inlined unless declared `@inlinable` (or with cross-module optimization), relevant for performance-critical packages.

### Q60. What is ARC traffic, and when does it matter? `[Lead/Expert]`
**Key points:**
- Every copy of a reference increments/decrements its reference count (atomic operations). Structs containing **many class references** (or `String`/`Array` buffers) perform retain/release for each one when copied.
- In hot loops, this "ARC traffic" can dominate the profile (look for `swift_retain`/`swift_release` in Time Profiler).
- Mitigations: avoid unnecessary copies (use `borrowing`/`inout`, iterate with indices only when needed), reduce reference-type fields in frequently copied structs, use `final` classes and unowned/unmanaged references only in measured, critical code.

### Q61. What string operations are expensive in Swift? `[Senior]`
**Key points:**
- `count` and integer-offset indexing are **O(n)** (Unicode grapheme clusters). Looping with `index(offsetBy:)` from the start each time is O(n²).
- Bridging to `NSString` repeatedly, regex creation in loops, and building large strings with repeated `+` in non-amortized ways.
- Faster options: iterate characters directly, work on the `utf8` view for ASCII protocols, precompile regexes once, use `reserveCapacity` when building large strings.

```swift
// ❌ O(n²)
for i in 0..<text.count {
    let character = text[text.index(text.startIndex, offsetBy: i)]
    process(character)
}

// ✅ O(n)
for character in text {
    process(character)
}
```

### Q62. Why should you avoid creating formatters repeatedly? `[Fundamental]`
```swift
// ❌ DateFormatter creation is expensive; this runs for every cell
func configure(with post: Post) {
    let formatter = DateFormatter()
    formatter.dateStyle = .medium
    dateLabel.text = formatter.string(from: post.createdAt)
}

// ✅ Reuse a cached formatter, or use FormatStyle (cached internally by the system)
func configureFast(with post: Post) {
    dateLabel.text = post.createdAt.formatted(date: .abbreviated, time: .omitted)
}
```
- The same applies to `NumberFormatter`, `JSONDecoder` setup with custom strategies, `NSRegularExpression`, and `CIContext` (very expensive to create).

### Q63. How do collection APIs affect performance? `[Senior]`
**Key points:**
- `reserveCapacity(_:)` when the final size is known, to avoid repeated reallocations.
- `lazy` to avoid intermediate arrays in chains (`items.lazy.filter { … }.map { … }.first`).
- `first(where:)`/`contains(where:)` instead of `filter { … }.first` / `filter { … }.count > 0`, which scan everything and allocate.
- `Dictionary(grouping:by:)` and `Set` for lookups instead of repeated linear scans.
- `removeAll(where:)` instead of removing elements one by one in a loop (O(n²)).

### Q64. How do you speed up JSON decoding of large payloads? `[Senior]`
**Key points:**
- Decode **off the main thread**; it's CPU-heavy for large responses.
- Decode only needed fields (lighter `Decodable` models or a BFF with smaller payloads).
- Reuse configured `JSONDecoder` instances.
- Paginate instead of fetching huge arrays.
- For very large or high-frequency data, consider binary formats (Protobuf) or streaming parsers.
- Measure with Time Profiler and XCTest performance tests using real payloads.

### Q65. Can logging hurt performance? `[Senior]`
**Key points:**
- `print` writes synchronously to stdout and formats strings eagerly; in hot loops it can noticeably slow the app (and it's still compiled into Release builds unless removed).
- `os.Logger` is optimized: messages are formatted lazily and stored efficiently. Debug-level messages are cheap when not being collected.
- Avoid building expensive strings for logs that aren't needed (wrap verbose debug logging in compile-time or runtime checks).

### Q66. How do you know if code is CPU-bound or waiting? `[Senior]`
**Key points:**
- **Time Profiler** high CPU on a thread during the slow period → CPU-bound: optimize algorithms or move work off the main thread.
- Low CPU but slow → **waiting**: network, disk, locks, or other threads. Use System Trace / Thread State to see blocked states and what the thread was waiting on; check network timings and file activity.

### Q67. How does Swift Concurrency affect CPU performance? `[Lead/Expert]`
**Key points:**
- The cooperative pool limits threads to roughly the number of cores, avoiding thread explosion; but **blocking** a pool thread (semaphores, synchronous I/O) reduces throughput and can deadlock.
- Too many tiny tasks or excessive actor hops add overhead; batch work and design coarse-grained actor methods.
- Actor **contention** (many tasks waiting on one actor) shows up in the Swift Actors instrument; split responsibilities or move pure computation out of the actor.
- Long CPU loops should periodically call `Task.yield()` and check cancellation.

### Q68. When is it worth dropping to lower-level optimizations? `[Lead/Expert]`
**Key points:**
- Only after measuring a real hot path that matters to users, e.g. image processing, audio, parsing large data, custom rendering.
- Options: `Accelerate` (vDSP, vImage), `Metal` compute, `withUnsafeBufferPointer` to avoid bounds checks and ARC in tight loops, `ContiguousArray`, `InlineArray`/`Span` (Swift 6.2) for fixed-size, allocation-free storage.
- Keep such code isolated, well tested, and documented; readability costs are real.

## 8. Battery & Energy

### Q69. What drains battery in iOS apps? `[Senior]`
**Key points:**
- **CPU**: continuous work, busy loops, frequent timers, excessive wakeups.
- **Networking**: frequent small requests keep the cellular radio in high-power states (the radio stays powered for several seconds after each transfer).
- **Location**: high-accuracy continuous GPS.
- **GPU/display**: heavy animations, blurs, high frame rates, video.
- **Background activity**: excessive background refreshes, audio, location, or Bluetooth modes.

### Q70. How do you reduce energy usage from timers and wakeups? `[Senior]`
```swift
let timer = Timer.scheduledTimer(withTimeInterval: 60, repeats: true) { _ in
    refreshIfNeeded()
}
timer.tolerance = 10      // allows the system to coalesce wakeups with other work
```
**Key points:**
- Prefer event-driven updates (push, notifications, observation) over polling.
- Add **tolerance** to timers; stop timers and display links when screens disappear or the app backgrounds.
- Excessive wakeups or CPU usage in the background can trigger `EXC_RESOURCE` diagnostics or termination.

### Q71. How do you make networking more energy-efficient? `[Senior]`
**Key points:**
- **Batch and coalesce** requests (send analytics in batches; fetch data for a screen in one request).
- Use **discretionary background transfers** for non-urgent uploads/downloads (system picks Wi-Fi and charging).
- **Cache** effectively to avoid repeated downloads; prefetch on Wi-Fi.
- Avoid frequent polling; use push or WebSockets only while in the foreground.

### Q72. How do you measure energy impact? `[Senior]`
**Key points:**
- Xcode's **Energy gauge** while debugging (rough overall impact and contributors).
- Instruments: CPU profiling, Location, Network, and the power-focused instruments (Energy Log on older setups; the **Power Profiler** in recent Xcode versions) to see energy impact per subsystem over time.
- **Production**: Organizer battery usage metrics, MetricKit CPU/GPU time, cellular and location activity.

### Q73. How should an app react to thermal state and Low Power Mode? `[Lead/Expert]`
```swift
final class QualityController {
    private(set) var reduceEffects = false

    init() {
        NotificationCenter.default.addObserver(
            forName: ProcessInfo.thermalStateDidChangeNotification, object: nil, queue: .main
        ) { [weak self] _ in self?.update() }
        NotificationCenter.default.addObserver(
            forName: .NSProcessInfoPowerStateDidChange, object: nil, queue: .main
        ) { [weak self] _ in self?.update() }
        update()
    }

    private func update() {
        let info = ProcessInfo.processInfo
        let isHot = info.thermalState == .serious || info.thermalState == .critical
        reduceEffects = isHot || info.isLowPowerModeEnabled
        // e.g. lower video bitrate, disable autoplay and particle effects, reduce frame rate, pause prefetching
    }
}
```
- Under serious thermal states the system throttles CPU/GPU, so reducing work keeps the app smooth and prevents further heating.

### Q74. How do location features affect battery, and how do you minimize the impact? `[Senior]`
**Key points:**
- Use the **lowest accuracy** that meets the requirement (`kCLLocationAccuracyHundredMeters` or reduced accuracy vs best).
- Prefer **significant-change**, **visit**, or **region/condition monitoring** over continuous updates when possible.
- Stop updates as soon as they're not needed; use activity-specific configurations (e.g. fitness, navigation) so the system can optimize.
- Background location only when the feature truly requires it, with a clear user benefit (and App Review justification).

## 9. Network Performance

### Q75. What contributes to network latency on mobile? `[Senior]`
**Key points:**
```
DNS lookup → TCP connect → TLS handshake → request sent → server processing → first byte → download
```
- On cellular networks, each round trip can cost 50–300 ms or more, so **the number of round trips** usually matters more than bandwidth for API calls.
- Optimizations: connection reuse (one shared `URLSession`), HTTP/2 multiplexing and HTTP/3 (faster handshakes, better on lossy networks), fewer requests per screen (aggregation/BFF), CDN edge servers close to users, caching to skip requests entirely.

### Q76. How do you measure request timing in the app? `[Senior]`
```swift
final class NetworkMetricsDelegate: NSObject, URLSessionTaskDelegate {
    func urlSession(_ session: URLSession, task: URLSessionTask,
                    didFinishCollecting metrics: URLSessionTaskMetrics) {
        guard let transaction = metrics.transactionMetrics.last else { return }

        func duration(_ start: Date?, _ end: Date?) -> String {
            guard let start, let end else { return "-" }
            return String(format: "%.0f ms", end.timeIntervalSince(start) * 1000)
        }

        let summary = """
        \(task.originalRequest?.url?.path() ?? "?") \
        protocol=\(transaction.networkProtocolName ?? "?") \
        reused=\(transaction.isReusedConnection) \
        dns=\(duration(transaction.domainLookupStartDate, transaction.domainLookupEndDate)) \
        connect=\(duration(transaction.connectStartDate, transaction.connectEndDate)) \
        tls=\(duration(transaction.secureConnectionStartDate, transaction.secureConnectionEndDate)) \
        ttfb=\(duration(transaction.requestStartDate, transaction.responseStartDate)) \
        total=\(String(format: "%.0f ms", metrics.taskInterval.duration * 1000))
        """
        Logger.networking.debug("\(summary, privacy: .public)")
    }
}
```
- `URLSessionTaskMetrics` breaks down each phase, showing whether time goes to DNS, connection setup, TLS, server processing (time to first byte), or transfer. Aggregate percentiles (p50/p95) in production analytics.

### Q77. What does the Instruments network tooling show? `[Senior]`
**Key points:**
- The **HTTP Traffic / Network** instrument (Xcode 13+) shows each request made through `URLSession`: timing, size, status, headers, and which task made it, on the same timeline as CPU and signposts.
- Useful for spotting request waterfalls (sequential requests that could run concurrently), duplicate requests, oversized responses, and requests during launch.

### Q78. How do you reduce the number and cost of requests? `[Senior]`
**Key points:**
- **Deduplicate** identical in-flight requests; **cache** responses (HTTP cache, ETags, local database).
- **Parallelize** independent requests (`async let`, task groups) instead of sequential waterfalls.
- **Aggregate** screen data into one request; **batch** writes and analytics.
- **Paginate** and use **delta sync**.
- Shrink payloads: compression, trimmed fields, right-sized images.

### Q79. How do you make networking robust to poor connectivity without hurting performance? `[Senior]`
**Key points:**
- Reasonable **timeouts** (don't wait 60 seconds by default for interactive requests), **retries with exponential backoff and jitter** for idempotent requests only.
- `waitsForConnectivity` for non-urgent requests instead of failing immediately.
- **Cancel** requests no longer needed (screen dismissed, query changed).
- Show cached data while loading; avoid blocking UI on non-critical requests.

### Q80. How do you test app behavior on slow networks? `[Fundamental]`
**Key points:**
- **Network Link Conditioner** profiles (3G, Edge, Very Bad Network, 100% loss) on device (Settings → Developer) and Mac.
- Test launch, feed loading, uploads, and error states; ensure spinners, timeouts, retries, and offline UI behave well.
- Automated tests with stubbed latency (`URLProtocol` stubs that delay responses).

## 10. Disk I/O & Storage

### Q81. Why does disk I/O matter for performance? `[Senior]`
**Key points:**
- Synchronous reads/writes on the main thread cause hangs, especially on older devices or under system I/O load.
- Excessive writes wear flash storage and consume battery; iOS reports **disk write exceptions** when an app writes an unusually large amount in a short period (MetricKit `MXDiskWriteExceptionDiagnostic`, Organizer disk write reports).
- Large storage usage leads users to delete the app.

### Q82. What are common disk I/O mistakes? `[Senior]`
**Key points:**
- **Large data in `UserDefaults`**: the whole plist is loaded into memory and rewritten on changes. Store only small preferences there.
- **Rewriting an entire file** for small changes (e.g. re-encoding a large JSON file after every edit). Use a database or append-only logs.
- **Many tiny writes** instead of batching (e.g. saving after each item in an import).
- **Writing caches** that are never read, or re-downloading and re-writing the same data repeatedly.
- **Main-thread I/O** for large reads (images, documents).

### Q83. How do you make database writes efficient? `[Senior]`
```swift
// SQLite-based stores (GRDB example): batch many inserts in one transaction
try dbQueue.write { db in                          // one transaction for the whole batch
    for record in records {
        try record.insert(db)
    }
}

// SwiftData: save in batches during large imports (see SwiftData file Q64)
for (index, dto) in dtos.enumerated() {
    modelContext.insert(Product(dto: dto))
    if (index + 1).isMultiple(of: 1_000) { try modelContext.save() }
}
try modelContext.save()
```
**Key points:**
- Wrap bulk writes in **transactions** (one fsync instead of thousands).
- Use **indexes** for frequent queries; avoid N+1 query patterns.
- SQLite **WAL mode** (default in Core Data/SwiftData stores) improves concurrent reads and writes.
- Perform heavy database work on background contexts/actors.

### Q84. What does the termination code `0xdead10cc` mean? `[Lead/Expert]`
**Key points:**
- The system terminated the app because it **held a file lock or SQLite database lock** while being suspended (commonly on a file in a shared App Group container used by extensions).
- Fixes: finish or cancel database transactions before suspension; request extra time with `beginBackgroundTask` to complete writes; avoid long-held locks on shared files; close databases or use configurations that release locks promptly.

### Q85. How do you manage app storage responsibly? `[Senior]`
**Key points:**
- Put regenerable data in `Caches/` (the system may purge it), user data in `Documents/` or `Application Support/`.
- Set size limits and eviction for caches (images, media, downloads); expose storage usage and cleanup in Settings for media-heavy apps.
- Exclude large regenerable files from iCloud backup (`isExcludedFromBackup`).
- Clean temporary files after use (`FileManager.default.temporaryDirectory`).

## 11. App Size & Build Performance

### Q86. Why does app size matter, and how do you measure it? `[Senior]`
**Key points:**
- Larger downloads reduce conversion (especially on cellular or in emerging markets), take longer to update, and use more device storage.
- Measure the **download and install sizes per device** from App Store Connect, or create an App Store export and inspect the **App Thinning Size Report** in Xcode.
- Track size per release in CI to catch sudden growth.

### Q87. How do you reduce app size? `[Senior]`
**Key points:**
- Asset catalogs (enable app thinning), compressed/HEIC images, vector assets and SF Symbols, remove unused assets (and duplicate images across targets).
- Audit third-party SDKs (often the biggest contributors) and remove unused ones.
- Dead code stripping, avoiding unnecessary generics bloat, and removing unused localizations or large bundled resources.
- Move large optional content to **on-demand resources** or **Background Assets** downloaded after install.

### Q88. How do you diagnose slow build times? `[Senior]`
```bash
# Add to "Other Swift Flags" temporarily to find slow type-checking
-Xfrontend -warn-long-function-bodies=100
-Xfrontend -warn-long-expression-type-checking=100
```
**Key points:**
- Xcode's **Build Timeline** (Report navigator, "Assistant: Build Timeline") shows which targets and files take longest and how well the build parallelizes.
- Fix slow expressions with explicit types and smaller expressions; split huge files; reduce dependencies between modules.
- (Architecture-level fixes like modularization: Architecture file, Q82–Q90 and Q159.)

### Q89. Do debug-only tools affect release performance? `[Senior]`
**Key points:**
- Sanitizers, Zombie Objects, Malloc Scribble, and the Main Thread Checker only run when enabled in the scheme, not in App Store builds.
- But code you add (debug menus, verbose logging, assertions) can leak into Release if not guarded by build configurations (`#if DEBUG`) or runtime flags.
- `assert` is removed in optimized builds; `precondition` remains (and traps); `fatalError` always remains.

## 12. LLDB & the Debugger

### Q90. What is the difference between `po`, `p`, and `v` in LLDB? `[Senior]`
| Command | What it does | When to use |
|---|---|---|
| `v` / `frame variable` | Reads variables directly from memory, **without running code** | Fast and safe inspection of locals and properties |
| `p` | Since Xcode 15, `dwim-print`: uses `v` when possible, otherwise evaluates as an expression | Default choice for printing |
| `po` | Evaluates an expression and prints its **object description** (`debugDescription`/`description`) | Objects with custom descriptions, Objective-C objects |
| `e` / `expression` | Evaluates arbitrary code, including side effects | Changing state while paused |

```
(lldb) v viewModel.items.count
(lldb) p items.first?.title
(lldb) po viewModel
(lldb) e viewModel.isLoading = false
```
- `po` and `e` compile and execute code in the paused process, which is slower and can fail in optimized builds; `v` works even when expression evaluation doesn't.

### Q91. What LLDB commands should a senior iOS engineer know? `[Senior]`
```
(lldb) bt                              # backtrace of the current thread
(lldb) bt all                          # all threads: essential for deadlocks
(lldb) thread list                     # list threads and where they're stopped
(lldb) frame select 3                  # jump to frame 3 of the backtrace
(lldb) up / down                       # move between frames
(lldb) finish                          # run until the current function returns
(lldb) thread return                   # return early from the current function (careful!)
(lldb) br set -n viewDidLoad           # breakpoint on all methods named viewDidLoad
(lldb) br set -E swift                 # stop whenever a Swift error is thrown
(lldb) br list / br disable 2          # manage breakpoints
(lldb) watchpoint set variable self.count   # stop when the value changes
(lldb) image lookup -a 0x100f2c3a4     # which function/file contains this address
(lldb) image lookup -rn "CartViewModel"     # search symbols by regex
(lldb) register read                   # CPU registers (e.g. at a crash)
(lldb) memory read --size 8 --count 4 0x16fdff7a0
```

### Q92. How do you modify the running app while paused? `[Senior]`
```
(lldb) e viewModel.isPremium = true                       # change state to test a code path
(lldb) e headerView.backgroundColor = UIColor.systemRed   # tweak UI
(lldb) e CATransaction.flush()                            # render UIKit changes without resuming
(lldb) e -l objc -- (void)[[UIApplication sharedApplication] sendAction:@selector(resignFirstResponder) to:nil from:nil forEvent:nil]
```
- Saves rebuild cycles when exploring UI states or reproducing edge cases. `CATransaction.flush()` makes UIKit changes visible while the app is still paused.

### Q93. What are conditional breakpoints and breakpoint actions? `[Senior]`
**Key points:**
- **Condition**: stop only when an expression is true (e.g. `order.id == "A1B2"` or `items.count > 100`).
- **Ignore count**: skip the first N hits.
- **Actions**: log a message (with `@expression@` interpolation), run debugger commands (`po`, `bt`), play a sound, capture a GPU frame.
- **"Automatically continue after evaluating actions"**: turns a breakpoint into a **logpoint**, adding logging without recompiling or modifying code.

```
Breakpoint at CartViewModel.swift:42
  Condition:  quantity > 10
  Action:     Log Message → "Large quantity: @quantity@ for @productID@"
  ☑ Automatically continue after evaluating actions
```

### Q94. What are symbolic and exception breakpoints? `[Senior]`
**Key points:**
- **Symbolic breakpoints** stop on a function name, even in system frameworks:
  - `UIViewAlertForUnsatisfiableConstraints` (Auto Layout conflicts).
  - `-[UIApplication sendAction:to:from:forEvent:]` (see which action fires).
  - `swift_willThrow` (any Swift error thrown).
  - `objc_exception_throw` (Objective-C exceptions).
- **Exception breakpoint** (Objective-C/C++): stops where an exception is **thrown**, instead of at the crash in `main` after it propagates, which is much more useful.
- **Swift Error breakpoint**: stops when a Swift error is thrown.
- **Runtime Issue breakpoints**: stop on Main Thread Checker, Thread Sanitizer, or other runtime issues.

### Q95. How do you inspect an object from a raw memory address? `[Lead/Expert]`
```
(lldb) e -l objc -O -- 0x7f8b5c40a2b0                        # print an Objective-C object at an address
(lldb) e -l objc -O -- [(UIView *)0x7f8b5c40a2b0 recursiveDescription]   # private, debugging only
(lldb) e -l swift -- import UIKit
(lldb) e -l swift -- let view = unsafeBitCast(0x7f8b5c40a2b0, to: UIView.self); print(view.frame)
```
- Useful when you have an address from the View Debugger, Memory Graph, or a log.

### Q96. Why are variables "optimized out" when debugging, and what can you do? `[Senior]`
**Key points:**
- In optimized builds, the compiler may keep values only in registers, reorder code, or remove variables entirely, so the debugger can't show them.
- Options: reproduce in a Debug build; use `register read` and disassembly for crashes in Release; temporarily lower optimization for a specific file (e.g. per-file compiler flags) while investigating; add targeted logging.

### Q97. How do you debug code you can't easily reach, like extensions or background launches? `[Senior]`
**Key points:**
- **Attach to process by name** (Debug → Attach to Process by PID or Name… with "Wait for executable to be launched"), then trigger the extension, push notification, or background launch.
- Scheme option **"Wait for the executable to be launched"** for testing launches from notifications or URLs.
- Simulate background fetch/refresh: `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.example.refresh"]` (private, debugging only).
- Push notifications in the simulator: drag an `.apns` file onto the simulator or use `xcrun simctl push`.

### Q98. How do you debug a problem that only happens on a specific device or iOS version? `[Senior]`
**Key points:**
- Collect details: crash/hang reports, device model, OS version, locale, settings (Low Power Mode, accessibility, Dynamic Type), network type.
- Reproduce on that device/OS (device lab, simulator runtime for that OS version, TestFlight build for the reporter).
- Check for OS-specific API behavior changes and availability checks (`#available`).
- Add targeted logging or a remote-configurable diagnostics mode for affected users.

### Q99. What are useful scheme Diagnostics options? `[Fundamental]`
**Key points:**
- **Runtime sanitizers**: Address Sanitizer, Thread Sanitizer, Undefined Behavior Sanitizer.
- **Runtime API checking**: Main Thread Checker, Thread Performance Checker.
- **Memory management**: Malloc Scribble, Malloc Guard Edges, Guard Malloc, Zombie Objects, Malloc Stack Logging.
- **Logging**: dynamic linker API usage, library loads.
- Turn them on regularly during development and in CI test runs (some are mutually exclusive, e.g. ASan and TSan).

**How to read it:**
- **Header**: app version, OS, device. Check whether crashes cluster on specific versions or devices.

### Q101. What do common exception types mean? `[Senior]`
| Exception | Typical cause |
|---|---|
| `EXC_BREAKPOINT (SIGTRAP)` | **Swift runtime trap**: force-unwrapping `nil`, array index out of range, integer overflow, failed `as!` cast, `fatalError`/`precondition`, accessing a deallocated `unowned` reference |
| `EXC_BAD_ACCESS (SIGSEGV/SIGBUS)` | Invalid memory access: dangling pointer, use-after-free (often Objective-C/C/unsafe Swift), data races corrupting memory; `KERN_INVALID_ADDRESS at 0x0…` suggests a null-ish pointer |
| `EXC_CRASH (SIGABRT)` | `abort()`: usually an **uncaught Objective-C exception** (`NSInvalidArgumentException`, `NSRangeException`, `NSInternalInconsistencyException`) or a failed assertion in system code |
| `EXC_CRASH (SIGKILL)` | Killed by the system: watchdog (`0x8badf00d`), held locks at suspension (`0xdead10cc`), thermal (`0xc00010ff`) |
| `EXC_RESOURCE` | Exceeded CPU, memory, or wakeup limits |
| `EXC_GUARD` | Violated a guarded resource (e.g. closed a file descriptor owned by the system) |
| Memory terminations (jetsam) | Usually **no crash report**; visible in MetricKit/Organizer terminations |

### Q102. How do you diagnose an `EXC_BREAKPOINT` crash in Swift code? `[Senior]`
**Key points:**
- Go to the top frame in your code and line number; the trap is almost always one of: `!` on `nil`, `try!`, `as!`, out-of-bounds index, arithmetic overflow, `fatalError`, `precondition`, or `unowned` access.
- Reason about which values could be invalid in production but not in your tests (empty arrays, missing JSON fields, race conditions, unexpected server data).
- Fix by handling the case properly (guard, optional binding, validation at the boundary), and add a test for it.

```swift
// Crash at line 42: `items[0]` when the cart is empty
var featuredItem: CartItem { items[0] }              // ❌ traps on empty arrays

var featuredItemSafe: CartItem? { items.first }      // ✅ handle the empty case explicitly
```

### Q103. How do you diagnose `NSInternalInconsistencyException` or other Objective-C exceptions? `[Senior]`
**Key points:**
- The crash report's **"Last Exception Backtrace"** (or the exception reason in the crash reporter) shows where the exception was thrown and its message, e.g. "Invalid update: invalid number of items in section 0."
- Common sources: table/collection view batch updates out of sync with data, KVO misuse, invalid arguments to UIKit/Foundation APIs (`nil` in collections, out-of-range indexes), UI updates from background threads.
- Reproduce with an **exception breakpoint**; fix the underlying state mismatch (e.g. diffable data sources for list updates).

### Q104. What is symbolication, and how does it work? `[Senior]`
**Key points:**
- Crash reports from users contain **memory addresses**. Symbolication maps them back to function names, files, and line numbers using **dSYM** files (debug symbols) matching the exact build (by **UUID**).
- Xcode Organizer and crash reporting services symbolicate automatically if they have the right dSYMs. **Upload dSYMs from CI for every release build**, including those for frameworks.
- Manual symbolication:

```bash
# Check that the dSYM matches the crashed binary's UUID (from "Binary Images")
dwarfdump --uuid MyApp.app.dSYM

# Symbolicate one address: -l is the binary's load address from "Binary Images"
atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp -l 0x100f00000 0x100f2c3a4
# → CartViewModel.total.getter (in MyApp) (CartViewModel.swift:42)
```

### Q105. How do you investigate a crash you can't reproduce? `[Lead/Expert]`
**Talking points:**
- **Gather patterns** across many reports: app version, OS, device, locale, time since launch, memory state, background/foreground, feature flags, the last screens and actions (breadcrumbs).
- Read **all threads**, not just the crashed one: another thread may be mutating shared state (a race), or the main thread may be waiting.
- Form hypotheses (race condition, unexpected server data, memory corruption, OS-specific behavior) and test them: stress tests, Thread Sanitizer, Address Sanitizer, fuzzing inputs, Network Link Conditioner.
- Add **targeted logging or assertions** behind a feature flag to capture more context in the next release.
- Ship a defensive fix if the root cause is unclear, while continuing to investigate; monitor whether the crash rate drops.

### Q106. What are crash-free users and crash-free sessions? `[Senior]`
**Key points:**
- **Crash-free sessions**: percentage of sessions without a crash. **Crash-free users**: percentage of users who didn't experience any crash in the period.
- Top apps typically target **99.8–99.9%+ crash-free users**. Track per version during phased rollouts, and include hangs and memory terminations in your reliability picture (they hurt users as much as crashes but don't appear in crash-free metrics).

### Q107. How do you prioritize which crashes to fix? `[Lead/Expert]`
**Key points:**
- Rank by **number of affected users** (not just event count), trend (new or rising in the latest version), and severity (crash on launch or in checkout vs a rare settings screen).
- Fix **launch crashes and regressions** in new releases immediately (pause the phased rollout if needed).
- Group duplicates (same root cause, different stacks) and track ownership by team/module.

### Q108. What are watchdog terminations, and how do you fix them? `[Senior]`
**Key points:**
- Code `0x8badf00d`: the app didn't respond in time for a system event (launch, resume, suspend, or a scene transition), usually because the **main thread was blocked**.
- The report includes the main thread's stack at termination, showing what blocked it (synchronous network, database migration, deadlock, waiting on a semaphore).
- Fix by moving work off the main thread and avoiding synchronous waits; test with realistic data volumes (large databases) on old devices, **without the debugger attached** (watchdogs are disabled under the debugger).

### Q109. What should a good crash-handling setup include? `[Lead/Expert]`
**Key points:**
- A crash reporter (or MetricKit diagnostics) with automatic **dSYM upload** in CI.
- **Breadcrumbs** (recent screens and actions), feature flag states, app state (foreground/background), and anonymized user IDs attached to reports.
- **Alerting** on crash spikes, new crash signatures, and launch crashes during phased rollouts.
- A **triage process**: owners per module, SLAs for top crashes, regular review in team rituals.
- Avoid installing multiple crash reporters that compete for signal handlers.

## 14. Sanitizers & Runtime Diagnostics

### Q110. What does Address Sanitizer (ASan) detect? `[Senior]`
**Key points:**
- Memory errors at runtime: **use-after-free**, **buffer overflows** (heap, stack, global), double frees, use of stack memory after return.
- Most relevant for C/C++/Objective-C code and unsafe Swift (`UnsafeMutablePointer`, `withUnsafeBytes`, C interop).
- Adds roughly 2× slowdown and memory overhead; enable for test runs and when investigating `EXC_BAD_ACCESS` crashes.

```swift
// ASan reports a heap-buffer-overflow here
let buffer = UnsafeMutablePointer<Int>.allocate(capacity: 4)
buffer[4] = 42          // one past the end
buffer.deallocate()
```

### Q111. What does Thread Sanitizer (TSan) detect? `[Senior]`
**Key points:**
- **Data races** (unsynchronized concurrent access with at least one write), plus some lock misuse.
- Essential for code not yet checked by Swift 6 strict concurrency, Objective-C/C code, and code using `@unchecked Sendable` or `nonisolated(unsafe)`.
- It reports races that **actually happen during the run**, so exercise concurrent code paths (stress tests with many iterations).

```swift
// TSan reports a data race on `cache`
final class UnsafeCache {
    var cache: [String: Int] = [:]
}

let shared = UnsafeCache()
DispatchQueue.concurrentPerform(iterations: 100) { index in
    shared.cache["key\(index)"] = index          // concurrent writes to a dictionary
}
```

### Q112. What do Zombie Objects and Malloc diagnostics do? `[Senior]`
**Key points:**
- **Zombie Objects** (`NSZombieEnabled`): deallocated Objective-C objects are turned into "zombies" that log an error when messaged, revealing which object was used after deallocation. Also available as an Instruments template with retain/release history.
- **Malloc Scribble**: fills freed memory with a pattern, making use-after-free bugs crash more predictably.
- **Guard Malloc / Malloc Guard Edges**: place allocations next to protected pages to catch buffer overruns immediately.
- **Malloc Stack Logging**: records allocation backtraces for the Memory Graph and Allocations.

### Q113. What do the Main Thread Checker and Undefined Behavior Sanitizer catch? `[Fundamental]`
**Key points:**
- **Main Thread Checker**: UIKit/AppKit (and some other) APIs called from background threads, reported as runtime issues with stack traces. Enabled by default in Debug.
- **Undefined Behavior Sanitizer (UBSan)**: C/Objective-C undefined behavior such as signed integer overflow, misaligned pointers, invalid shifts, null dereferences in C code. (Swift already traps on many of these.)

### Q114. How do you integrate runtime diagnostics into CI? `[Lead/Expert]`
**Key points:**
- Separate test plans (Xcode **Test Plans**) with configurations: one with ASan + UBSan, one with TSan (they can't run together), one plain for speed.
- Run sanitizer configurations nightly or on main-branch merges if too slow for every PR.
- Treat runtime issues as **test failures** (enable "Treat runtime issues as failures" where possible) so they don't accumulate.

## 15. Debugging Concurrency Issues

### Q115. How do you debug a deadlock? `[Senior]`
**Key points:**
1. When the app freezes, **pause in the debugger** (or capture a stackshot/sysdiagnose on device).
2. Run `bt all` and look for threads waiting on each other: `__DISPATCH_WAIT_FOR_QUEUE__` (a `sync` call), `semaphore_wait_trap`, `__psynch_mutexwait` (locks), `_dispatch_group_wait`.
3. Identify the cycle: thread A holds X and waits for Y; thread B holds Y and waits for X (or the main thread waits for work that needs the main thread).
4. Fix by removing synchronous waits (use async APIs), enforcing a consistent lock order, or restructuring with actors.

```swift
// A guard that catches accidental main-thread blocking during development
func loadLargeFile(at url: URL) throws -> Data {
    dispatchPrecondition(condition: .notOnQueue(.main))   // crashes in debug if called on main
    return try Data(contentsOf: url)
}
```

### Q116. How do you find data races? `[Senior]`
**Key points:**
- **Swift 6 language mode** eliminates most data races at compile time; adopt it module by module.
- **Thread Sanitizer** for remaining code (Swift 5 modules, `@unchecked Sendable`, Objective-C/C).
- Symptoms in production: random crashes in `Dictionary`/`Array` internals, `EXC_BAD_ACCESS` in Swift runtime functions (`swift_retain`, `swift_release`), corrupted values.
- Stress tests that hammer shared state concurrently help reproduce races under TSan.

### Q117. How do you debug Swift Concurrency code? `[Lead/Expert]`
**Key points:**
- Xcode shows **async backtraces** (the logical chain of `await`s across suspension points) in the debug navigator.
- **Swift Concurrency instrument**: Swift Tasks (how many tasks, their states, creation/completion) and Swift Actors (queue sizes and contention), plus task names (Swift 6.2 `Task(name:)`).
- Runtime warnings for **leaked continuations** ("SWIFT TASK CONTINUATION MISUSE … leaked its continuation") point to callback paths that never resume.
- **Isolation crashes** ("Incorrect actor executor assumption") indicate `@MainActor` code running on the wrong thread, often via `@preconcurrency` conformances or callbacks from Objective-C APIs (Swift Concurrency file, Q74).
- Use `MainActor.assertIsolated()` / `preconditionIsolated()` to validate assumptions during development.

### Q118. How do you debug ordering bugs between tasks? `[Lead/Expert]`
**Key points:**
- Unstructured `Task`s and actor calls from different tasks have no guaranteed order; bugs appear as "sometimes the old value wins."
- Add signposts or logs with task identifiers and timestamps to reconstruct the actual order.
- Fix by making the dependency explicit: await sequentially within one task, cancel superseded tasks, or funnel work through a single consumer (e.g. an `AsyncStream`).
- Write deterministic tests with controllable dependencies (continuation-based fakes) to force specific interleavings.

### Q119. How do priority issues show up with GCD and Swift Concurrency? `[Lead/Expert]`
**Key points:**
- The **Thread Performance Checker** flags priority inversions (e.g. a user-interactive thread waiting on a background-QoS queue).
- In Swift Concurrency, awaiting a lower-priority task or actor **escalates** its priority automatically, but blocking primitives (semaphores, condition variables) don't participate in escalation.
- Symptoms: UI waits on work that runs slowly at background priority. Fix by avoiding synchronous waits and assigning appropriate priorities.

## 17. Debugging Networking

### Q124. How do you inspect the network traffic your app sends? `[Senior]`
**Key points:**
- **HTTP Traffic / Network instrument** in Instruments for `URLSession` traffic, without extra setup.
- **Proxy tools** (Proxyman, Charles, mitmproxy): view and modify requests/responses, simulate errors, throttle bandwidth. HTTPS inspection requires installing and trusting the proxy's root certificate on the device; **certificate pinning blocks it** (by design), so debug builds may disable pinning.
- Log request IDs, status codes, and timings (without sensitive data) to correlate with backend logs.

### Q125. How do you get more detailed networking logs from the system? `[Lead/Expert]`
**Key points:**
- Set the environment variable **`CFNETWORK_DIAGNOSTICS=3`** in the scheme for verbose CFNetwork/URLSession logs (connection setup, TLS, redirects, caching decisions) in the console.
- Inspect ATS (App Transport Security) failures in console logs when connections are rejected.
- `nscurl --ats-diagnostics https://api.example.com` on macOS tests a server's compatibility with ATS requirements.

### Q126. How do you debug HTTP caching behavior? `[Senior]`
**Key points:**
- Check response headers (`Cache-Control`, `ETag`, `Last-Modified`, `Vary`) in the network instrument or proxy.
- Verify whether responses come from cache via `URLSessionTaskMetrics.transactionMetrics` (`resourceFetchType` is `.localCache` for cache hits) or 304 responses.
- Common surprises: responses too large for the `URLCache` capacity aren't stored; `Authorization` headers and `Cache-Control: private/no-store` affect caching; custom `requestCachePolicy` overrides server headers.

### Q127. How do you reproduce bugs that depend on network conditions? `[Senior]`
**Key points:**
- Network Link Conditioner (high latency, packet loss, 3G/Edge); airplane mode toggling during requests; switching between Wi-Fi and cellular.
- Proxy tools to inject errors (500s, timeouts, malformed JSON), slow responses, or specific payloads.
- `URLProtocol` stubs in automated tests to simulate failures deterministically.

## 18. Production Monitoring & Debugging

### Q128. What should production performance monitoring include? `[Lead/Expert]`
**Key points:**
- **Apple sources**: Xcode Organizer (launch, hangs, memory, battery, disk writes, scrolling, terminations, crash and hang reports) and **MetricKit** payloads sent to your backend.
- **Custom metrics**: time to first content, API latency percentiles from the client, screen load times, sync duration, frame/hitch metrics for key screens (via signposts or custom measurement).
- **Segmentation**: app version, OS, device model, region, network type, feature flags/experiments.
- **Alerting**: regressions per release, spikes in crashes/hangs/terminations, latency SLO breaches.

### Q129. How can users' devices provide logs for debugging? `[Senior]`
```swift
import OSLog

/// Collects this process's recent log entries (iOS 15+), e.g. to attach to a support report with user consent
func recentLogEntries(lastMinutes minutes: Double = 30) throws -> [String] {
    let store = try OSLogStore(scope: .currentProcessIdentifier)
    let start = store.position(date: Date.now.addingTimeInterval(-minutes * 60))

    return try store.getEntries(at: start)
        .compactMap { $0 as? OSLogEntryLog }
        .filter { $0.subsystem == "com.example.app" }
        .map { "\($0.date.formatted(date: .omitted, time: .standard)) [\($0.category)] \($0.composedMessage)" }
}
```
**Key points:**
- `OSLogStore` with `.currentProcessIdentifier` reads only the **current process's** logs (since launch), so include a "Send diagnostics" option in the app's support flow.
- For deeper issues (QA or beta testers): **sysdiagnose** (button combination on device) or `log collect --device` on a connected Mac, then inspect in Console.app.
- Remember privacy: dynamic values logged as `.private` are redacted unless explicitly public.

### Q130. What are breadcrumbs, and why are they valuable? `[Senior]`
**Key points:**
- A rolling log of recent significant events (screens viewed, buttons tapped, network requests and results, background/foreground transitions, memory warnings) attached to crash and error reports.
- They turn a bare stack trace into a story: "User opened cart → applied coupon → network error → tapped retry → crash."
- Keep them small, privacy-safe (no PII), and bounded in memory.

### Q131. How do you debug issues affecting only some users in production? `[Lead/Expert]`
**Key points:**
- Segment metrics and reports to find the common factor (device, OS, locale, account type, feature flag, network).
- Use **remote configuration** to enable verbose logging or extra diagnostics for an affected cohort or a specific user (with consent).
- Use feature flags to **disable the suspected code path** for affected users while investigating.
- Reach out via support to obtain sysdiagnose/logs from a reproducing user; provide a TestFlight build with extra diagnostics.

### Q132. How do you detect performance regressions after a release? `[Lead/Expert]`
**Key points:**
- Compare key metrics (launch percentiles, hang rate, memory, crash-free rate, TTFC) between the new version and the previous one for the same device classes.
- Use **phased release** to watch early cohorts; pause on regressions.
- Organizer highlights regressions across versions; MetricKit data in your pipeline lets you alert within days rather than weeks.
- Correlate with release contents (changelog, feature flags enabled) to narrow down the cause.

### Q133. What's the difference between Organizer metrics, MetricKit, and third-party tools? `[Senior]`
| Source | Strengths | Limitations |
|---|---|---|
| **Xcode Organizer** | Zero setup, Apple-collected, broad metrics, regression detection | Only opted-in users, aggregated, delayed (days) |
| **MetricKit** | Same metric families + diagnostics delivered to your app; custom segmentation | Requires your own pipeline; payloads periodic |
| **Third-party APM/crash tools** | Real-time dashboards, breadcrumbs, custom traces, alerting | SDK cost (size, launch impact, privacy), vendor dependency |

- Mature teams combine them: Organizer for validation, MetricKit/third-party for real-time alerting and deep context.

## 19. Performance Testing & Regression Prevention

### Q134. How do you write performance tests with XCTest? `[Senior]`
```swift
import XCTest

final class FeedParserPerformanceTests: XCTestCase {
    func testParsingLargeFeed() throws {
        let data = try Data(contentsOf: XCTUnwrap(Bundle(for: Self.self).url(forResource: "feed_large",
                                                                              withExtension: "json")))
        let options = XCTMeasureOptions()
        options.iterationCount = 10

        measure(metrics: [XCTClockMetric(), XCTCPUMetric(), XCTMemoryMetric()], options: options) {
            _ = try? FeedParser().parse(data)
        }
    }
}
```
**Key points:**
- `measure` runs the block several times and reports averages and standard deviation. Set a **baseline** in Xcode; the test fails if results regress beyond the allowed deviation.
- Metrics: `XCTClockMetric` (wall time), `XCTCPUMetric`, `XCTMemoryMetric`, `XCTStorageMetric` (disk writes), `XCTOSSignpostMetric`, `XCTApplicationLaunchMetric`.
- Swift Testing doesn't offer a `measure` equivalent at the time of writing, so performance tests typically stay in XCTest.

### Q135. How do you measure launch time and scrolling in UI tests? `[Senior]`
```swift
final class LaunchPerformanceTests: XCTestCase {
    func testColdLaunch() {
        measure(metrics: [XCTApplicationLaunchMetric(waitUntilResponsive: true)]) {
            XCUIApplication().launch()
        }
    }

    func testFeedScrolling() {
        let app = XCUIApplication()
        app.launchArguments = ["-uiTesting", "-mockFeedLarge"]
        app.launch()
        let feed = app.collectionViews["feed"]

        let options = XCTMeasureOptions()
        options.invocationOptions = [.manuallyStop]

        measure(metrics: [XCTOSSignpostMetric.scrollDecelerationMetric], options: options) {
            feed.swipeUp(velocity: .fast)
            stopMeasuring()
            feed.swipeDown(velocity: .fast)     // reset position outside the measured interval
        }
    }
}
```
- Scroll metrics report hitch time ratio and frame data, so scrolling regressions can fail CI.

### Q136. How do you measure custom code paths with signposts in tests? `[Senior]`
```swift
func testHomeLoadSignpost() {
    let app = XCUIApplication()
    app.launchArguments = ["-uiTesting"]

    let homeLoad = XCTOSSignpostMetric(subsystem: "com.example.app", category: "home", name: "LoadHome")
    measure(metrics: [homeLoad]) {
        app.launch()
        _ = app.staticTexts["home.title"].waitForExistence(timeout: 5)
        app.terminate()
    }
}
```
- The same `OSSignposter` intervals used in Instruments (Q13) become testable metrics, so "time to first content" can be tracked automatically.

### Q137. How do you make performance tests reliable in CI? `[Lead/Expert]`
**Key points:**
- Run on **dedicated, consistent hardware** (same device model, OS, charge state, thermal conditions); avoid shared simulators for timing-sensitive tests.
- Use realistic but deterministic data (fixtures, mocked network).
- Multiple iterations, baselines per device, and tolerances that account for noise.
- Track results over time (dashboards) rather than relying only on pass/fail thresholds; investigate trends early.
- Run heavier performance suites nightly; keep a small smoke set on PRs.

### Q138. Beyond tests, how do you prevent performance regressions? `[Lead/Expert]`
**Key points:**
- **Budgets** (Q5) with owners and dashboards.
- **Code review checklist**: main-thread work, image sizes, launch-path additions, new SDKs, O(n²) patterns, memory retention.
- **SDK governance**: measure launch/size/memory impact before adding third-party SDKs.
- **Release monitoring** with phased rollouts and alerts.
- **Profiling rituals**: profile key flows before each major release on the oldest supported device.

### Q139. How do you build a performance culture on a team? `[Lead/Expert]`
**Key points:**
- Make performance **visible**: dashboards in team channels, release notes with metric changes, celebrating wins.
- Teach tools: Instruments workshops, documented "how to profile X" playbooks, pairing on investigations.
- Assign **ownership** for key metrics (launch, scrolling, memory) and include them in planning, not just firefighting.
- Treat severe regressions like bugs with SLAs; budget time each quarter for performance work.

## 20. "Spot the Problem" Questions

### Q140. Formatter in a cell `[Fundamental]`
```swift
func configure(cell: PostCell, with post: Post) {
    let formatter = DateFormatter()
    formatter.dateFormat = "MMM d, yyyy"
    cell.dateLabel.text = formatter.string(from: post.createdAt)
}
```
**Problem:** `DateFormatter` is expensive to create, and this runs for every cell during scrolling, causing hitches.
**Fix:** reuse a cached formatter or use `post.createdAt.formatted(.dateTime.month().day().year())`.

### Q141. Membership check in a loop `[Senior]`
```swift
let mutedUserIDs: [String] = settings.mutedUserIDs     // thousands of IDs
let visiblePosts = posts.filter { !mutedUserIDs.contains($0.authorID) }
```
**Problem:** O(n × m) linear searches.
**Fix:** `let muted = Set(settings.mutedUserIDs)` then `!muted.contains($0.authorID)`.

### Q142. Synchronous loading on the main thread `[Fundamental]`
```swift
override func viewDidLoad() {
    super.viewDidLoad()
    let data = try? Data(contentsOf: profile.avatarURL)   // remote URL
    avatarView.image = data.flatMap(UIImage.init(data:))
}
```
**Problem:** a synchronous network request blocks the main thread (hang; watchdog risk at launch).
**Fix:** load asynchronously with `URLSession` (or an image pipeline) and downsample off the main thread.

### Q143. Full-resolution images in thumbnails `[Senior]`
```swift
cell.thumbnailView.image = UIImage(contentsOfFile: photo.fileURL.path)   // 12 MP photos
```
**Problem:** each decoded image uses ~48 MB; a grid of 20 thumbnails can exceed a gigabyte → memory terminations and scroll hitches from decoding on the main thread.
**Fix:** downsample to thumbnail size in the background (ImageIO or `byPreparingThumbnail(ofSize:)`) and cache the small versions.

### Q144. Copy-on-write through a computed property `[Lead/Expert]`
```swift
final class MessageStore {
    private var state = ChatState()            // struct with `var messages: [Message]`
    var messages: [Message] {
        get { state.messages }
        set { state.messages = newValue }
    }
}

for incoming in batch {
    store.messages.append(incoming)            // called thousands of times
}
```
**Problem:** each append copies the entire array (getter returns a second reference, so the buffer isn't unique), making the loop O(n²).
**Fix:** add a method that mutates `state.messages` directly (or appends the whole batch at once).

### Q145. Filtering just to check existence `[Fundamental]`
```swift
if orders.filter({ $0.status == .pending }).count > 0 {
    showPendingBanner()
}
```
**Problem:** scans the entire array and allocates a new array just to check for existence.
**Fix:** `if orders.contains(where: { $0.status == .pending })`.

### Q146. Large data in UserDefaults `[Senior]`
```swift
UserDefaults.standard.set(try JSONEncoder().encode(allCachedArticles), forKey: "articles")  // several MB
```
**Problem:** `UserDefaults` loads its entire plist into memory (often at launch) and rewrites it on changes, slowing launch and wasting memory and disk writes.
**Fix:** store large data in files or a database; keep `UserDefaults` for small preferences.

### Q147. Eager logging in a hot path `[Senior]`
```swift
func process(_ points: [DataPoint]) {
    for point in points {                        // 100,000 points
        print("Processing point \(point) with metadata \(point.metadata.debugDescription)")
        transform(point)
    }
}
```
**Problem:** `print` formats strings eagerly and writes synchronously; the loop becomes dramatically slower (and logs flood the console).
**Fix:** remove it, or use `Logger.debug` (lazily formatted) only where needed, ideally outside the loop.

### Q148. Shadow without a path in a cell `[Senior]`
```swift
override func layoutSubviews() {
    super.layoutSubviews()
    layer.shadowOpacity = 0.2
    layer.shadowRadius = 10
    layer.cornerRadius = 12
}
```
**Problem:** without `shadowPath`, Core Animation computes the shadow shape from content every frame (offscreen rendering → render hitches).
**Fix:** `layer.shadowPath = UIBezierPath(roundedRect: bounds, cornerRadius: 12).cgPath`.

### Q149. N+1 database queries `[Senior]`
```swift
let trips = try context.fetch(FetchDescriptor<Trip>())
for trip in trips {
    let count = trip.activities.count          // faults each trip's activities separately
    rows.append(TripRow(name: trip.name, activityCount: count))
}
```
**Problem:** one query for trips plus one per trip for activities: slow for large lists.
**Fix:** prefetch relationships (`relationshipKeyPathsForPrefetching`), store a denormalized count, or query counts in bulk.

### Q150. Timer keeping a screen alive `[Senior]`
```swift
final class LiveScoreViewController: UIViewController {
    var timer: Timer?
    override func viewDidLoad() {
        super.viewDidLoad()
        timer = Timer.scheduledTimer(timeInterval: 1, target: self,
                                     selector: #selector(refresh), userInfo: nil, repeats: true)
    }
    @objc func refresh() { /* fetch scores */ }
    deinit { timer?.invalidate() }
}
```
**Problem:** the run loop retains the timer and the timer retains `self`, so `deinit` never runs. The screen leaks and keeps polling the network after being dismissed (memory, battery, data).
**Fix:** block-based timer with `[weak self]`, and invalidate in `viewDidDisappear`.

### Q151. Waiting for async work on the main thread `[Senior]`
```swift
func currentUserSync() -> User? {
    let semaphore = DispatchSemaphore(value: 0)
    var user: User?
    Task {
        user = try? await api.fetchCurrentUser()
        semaphore.signal()
    }
    semaphore.wait()
    return user
}
// Called from viewDidLoad
```
**Problem:** blocks the main thread for the duration of a network request (hang, possible watchdog kill); if the task needs the main actor, it **deadlocks**.
**Fix:** make the caller async (`await api.fetchCurrentUser()`) and update the UI when the result arrives.

### Q152. Decoding on the main actor `[Senior]`
```swift
@MainActor
func loadCatalog() async throws {
    let (data, _) = try await URLSession.shared.data(from: catalogURL)   // 15 MB JSON
    catalog = try JSONDecoder().decode(Catalog.self, from: data)        // heavy, synchronous
}
```
**Problem:** the download suspends correctly, but decoding 15 MB of JSON runs synchronously on the main actor and freezes the UI.
**Fix:** decode in a `@concurrent`/nonisolated function or a background actor, then assign on the main actor; also consider pagination or a smaller payload.

### Q153. SwiftUI recomputing expensive data in `body` `[Senior]`
```swift
struct ReportView: View {
    let transactions: [Transaction]                    // 20,000 items

    var body: some View {
        let grouped = Dictionary(grouping: transactions, by: \.category)   // recomputed on every update
            .mapValues { $0.reduce(0) { $0 + $1.amount } }
            .sorted { $0.value > $1.value }
        List(grouped, id: \.key) { category, total in
            Text("\(category): \(total)")
        }
    }
}
```
**Problem:** grouping and sorting 20,000 items runs every time `body` is evaluated (any parent update, any state change).
**Fix:** compute once in a model (when transactions change) and pass the precomputed summary to the view.

## 22. Senior / Lead Scenario Questions

### Q154. Users say the app "feels slow." Where do you start? `[Lead/Expert]`
**Talking points:**
1. **Clarify**: which flows (launch, feed, search, checkout)? Which devices and OS versions? Since which release?
2. **Check data**: Organizer and MetricKit (launch percentiles, hang rate, hitch rate, memory), analytics (screen load times), reviews and support tickets.
3. **Reproduce and profile** the worst flows on old devices with Release builds.
4. **Prioritize** by impact and reach; fix the biggest offenders first (often launch work, main-thread I/O, images).
5. **Verify** with metrics after release; add budgets and regression tests so the improvements stick.

### Q155. Cold launch time regressed by 40% in the latest release. How do you investigate? `[Lead/Expert]`
**Talking points:**
- Confirm with Organizer/MetricKit by device class; reproduce with the App Launch template comparing old and new builds.
- Diff the release: new SDKs, new dynamic frameworks, changes to `didFinishLaunching`, new work on the first screen, database migrations, larger asset loading, new static initializers.
- Look at pre-main vs post-main split; check main-thread work and blocking before the first frame.
- Fix (defer or remove work), add a launch performance test in CI with the new baseline, and add a launch-path review rule.

### Q156. Memory terminations doubled after adding a new photo editing feature. What do you do? `[Lead/Expert]`
**Talking points:**
- Confirm with MetricKit exit metrics and Organizer by device RAM class; correlate with breadcrumbs (were users in the editor?).
- Profile peak memory in the editor with Allocations/VM Tracker on the lowest-RAM device: full-resolution images, multiple copies (original + preview + filters), Core Image contexts, undo history snapshots.
- Fixes: work on downsampled previews and apply full-resolution processing only on export; reuse a single `CIContext`; limit undo history or store diffs; release resources on memory warnings; check `os_proc_available_memory()` before large allocations.
- Add a memory budget test for the editor flow.

### Q157. Battery complaints increased after a release. How do you find the cause? `[Lead/Expert]`
**Talking points:**
- Check Organizer battery metrics and MetricKit CPU/GPU/location/network metrics between versions.
- Look for new polling timers, background tasks, location usage, autoplay video, animations, or retry loops that never stop (e.g. a failing request retried rapidly).
- Profile with energy-related instruments over a realistic session, including background periods.
- Fix and verify with metrics; add guards (timer tolerances, backoff, stopping work when off-screen or backgrounded).

### Q158. Crash reports for the new release are unsymbolicated. What went wrong, and how do you fix the process? `[Senior]`
**Talking points:**
- The dSYMs for that exact build weren't uploaded (or don't match by UUID), e.g. a CI step failed or a different build was submitted.
- Retrieve dSYMs from the archive (Xcode Organizer → Archives → Download Debug Symbols, or App Store Connect) and upload them.
- Fix the pipeline: upload dSYMs automatically for every release build, verify UUIDs match, alert if upload fails.

### Q159. The hang rate increased after enabling Swift 6.2 approachable concurrency. Why might that be? `[Lead/Expert]`
**Talking points:**
- With `NonisolatedNonsendingByDefault` and default main-actor isolation, async functions that previously ran on the concurrent pool now run **on the caller's actor**, often the main actor. Heavy synchronous work inside them now blocks the UI.
- Find them with the Hangs instrument and Time Profiler on the main thread; Organizer hang reports point to the functions.
- Mark CPU-heavy functions `@concurrent` (or move them to dedicated actors), keep main-actor code lightweight, and add hang-focused performance tests for key flows.

### Q160. A crash happens only for 0.1% of users and you can't reproduce it. How do you approach it? `[Lead/Expert]`
**Talking points:**
- Analyze all reports for patterns (device, OS, locale, time after launch, memory state, background state, feature flags); read all threads for races.
- Hypothesize and test with TSan/ASan stress tests, fuzzed inputs (unusual server data, long strings, locales like Arabic/Thai), and network fault injection.
- Add targeted logging/breadcrumbs behind a remote flag; ship a defensive fix if safe.
- Track the crash signature across releases to verify the fix.

### Q161. How would you design a performance monitoring system for a large app? `[Lead/Expert]`
**Talking points:**
- **Collection**: MetricKit metrics/diagnostics, custom signpost-based timings (TTFC per screen, API latency), frame metrics for key screens, crash/hang reports with breadcrumbs.
- **Pipeline**: batched, privacy-safe uploads; backend aggregation by version, device, OS, region, network, experiment.
- **Visualization and alerting**: dashboards with percentiles; alerts on regressions vs the previous version during phased rollouts.
- **Ownership**: metrics mapped to teams/screens; regular reviews; budgets enforced in planning.
- **Lab + field**: CI performance tests catch regressions before release; field data validates real-world impact.

### Q162. How do you evaluate the performance impact of a new third-party SDK? `[Lead/Expert]`
**Talking points:**
- Measure **before and after** integration: app size, cold launch (pre-main and post-main), memory footprint, network calls at launch, CPU while idle, disk writes.
- Review its threading behavior (main-thread work, swizzling), privacy manifest, and initialization requirements (can it be deferred or lazily loaded?).
- Integrate behind a feature flag to measure impact in production and allow remote disabling.
- Document the results in an ADR; set an SDK budget for the app.

### Q163. How would you teach a junior engineer to debug a crash? `[Senior]`
**Talking points:**
- Walk through a real crash report: header, exception type, crashed thread, first frame in our code, other threads.
- Map the exception type to likely causes (e.g. `EXC_BREAKPOINT` → force unwrap/index out of range).
- Reproduce with the right tools (breakpoints, exception breakpoints, sanitizers), fix the root cause (not just the symptom), and add a regression test.
- Encourage writing a short post-mortem note: what happened, why, how it was fixed, how to prevent it.

### Final Tips
- **Always measure first**, profile **Release** builds on **old devices**, and verify fixes with numbers.
- Know **which tool answers which question** (Q9) and be ready to describe an investigation step by step: reproduce → measure → hypothesize → fix → verify → prevent.
- Be fluent with **crash reports** (Q100–Q104) and **LLDB** beyond `po` (`v`, `bt all`, conditional breakpoints, logpoints, watchpoints, `CATransaction.flush()`).
- Memory questions are very common: images (Q48), retain cycles vs abandoned memory (Q44–Q46), jetsam (Q42, Q51).
- Have **two real stories** ready: a performance improvement you measured (with before/after numbers) and a hard bug you debugged (how you narrowed it down). Lead candidates should add how they **prevented regressions** afterwards.
