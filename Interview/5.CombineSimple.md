## 1. Fundamentals

### Q1. What is Combine? `[Fundamental]`
Combine is Apple's framework for handling **values that arrive over time**, like typing, network responses, or timers, by connecting them in a **pipeline**.

- A **publisher** sends values.
- **Operators** change or filter them along the way.
- A **subscriber** receives the final values.
- Common uses: UI bindings, form validation, search-as-you-type, networking, notifications, timers, and KVO.

```swift
import Combine

let cancellable = [1, 2, 3, 4, 5].publisher   // publisher
    .filter { $0.isMultiple(of: 2) }          // operator: keep even numbers
    .map { $0 * 10 }                          // operator: multiply by 10
    .sink { print($0) }                       // subscriber
// 20
// 40
```

**Follow-ups:**
- **What iOS version do you need?** iOS 13.
- **Does anything happen without a subscriber?** No. Most pipelines do nothing until something subscribes.
- **Does Combine work on Linux?** No. It's Apple-only, so it can't be used in server-side Swift on Linux.

### Q2. What is reactive programming? `[Fundamental]`
Reactive programming means treating events and data changes as **streams** that you **transform and combine**, instead of handling each callback separately.

- **Benefits:** async logic is easy to combine, you need fewer "isLoading" style flags, and UI, network, and timer events all work the same way.
- **Costs:** a learning curve, harder debugging (long type names, stack traces through operators), and memory pitfalls.

```swift
// Imperative: handle each callback, keep flags yourself
textField.addTarget(self, action: #selector(textChanged), for: .editingChanged)

// Reactive: describe what should happen to the stream of text
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .removeDuplicates()
    .sink { print("Search for \($0)") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What's the biggest benefit in practice?** Combining several event sources (text, filters, network) without lots of state flags.
- **What's the biggest downside?** Debugging: errors point into Combine's internals, not your code.
- **Is SwiftUI reactive?** Yes, in spirit. The UI reacts automatically to state changes.

### Q3. What are the core protocols in Combine? `[Fundamental]`
The core pieces are the **`Publisher`** (sends values), the **`Subscriber`** (receives them), and the **`Subscription`** (the link between them), plus **subjects**, **schedulers**, and **cancellables**.

| Protocol | What it does, in simple words |
|---|---|
| `Publisher` | Sends values of type `Output`, then may finish or fail with a `Failure` |
| `Subscriber` | Receives a subscription, then values (`Input`), then a completion |
| `Subscription` | The link between them. It handles "how many values do you want?" (demand) and cancelling |
| `Subject` | A publisher you can push values into yourself with `send` |
| `Scheduler` | Decides **when** and **on which thread** work happens |
| `Cancellable` | Something you can cancel. `AnyCancellable` cancels itself when released |

```swift
let subject = PassthroughSubject<Int, Never>()                  // Subject (a Publisher)
let cancellable: AnyCancellable = subject                       // Cancellable
    .receive(on: DispatchQueue.main)                            // Scheduler
    .sink { print($0) }                                         // Subscriber
subject.send(1)
```

**Follow-ups:**
- **Which of these do you use most?** Publishers, operators, `sink`, and `AnyCancellable`.
- **When do you deal with `Subscription` directly?** Only when writing custom publishers or subscribers.
- **Is a subject a publisher?** Yes, one that you can also send values into.

### Q4. What are a publisher's `Output` and `Failure` types? `[Fundamental]`
Every publisher says **what type of values it sends** (`Output`) and **what type of error it can fail with** (`Failure`), and these types must match along the whole pipeline.

- `Failure == Never` means the publisher **can't fail** (like `Just` or `@Published`).
- Some APIs, like `sink(receiveValue:)` and `assign(to:on:)`, only work when `Failure == Never`.

```swift
let a: Just<Int> = Just(5)                                  // Output: Int, Failure: Never
let b: AnyPublisher<Data, URLError> = URLSession.shared
    .dataTaskPublisher(for: url)
    .map(\.data)
    .eraseToAnyPublisher()                                  // Output: Data, Failure: URLError
```

**Follow-ups:**
- **Why does `Never` matter?** A publisher that can't fail is safe to bind directly to UI.
- **How do you turn a failing publisher into a `Never` one?** Handle the error with `replaceError` or `catch`.
- **What happens if types don't match?** A compile error, often "Failure types don't match" (see Q55).

### Q5. Describe the lifecycle of a subscription. `[Senior]`
A subscription goes through **six steps**: subscribe, get a subscription, ask for values, receive values, receive **one** completion, and it can be **cancelled** at any time.

1. The subscriber calls `publisher.subscribe(subscriber)`.
2. The publisher creates a `Subscription` and gives it to the subscriber.
3. The subscriber **asks for values** (demand), for example "unlimited" or "2."
4. The publisher sends values, never more than requested.
5. The publisher sends **one** completion: `.finished` or `.failure(error)`. After that, nothing else.
6. The subscriber can **cancel** at any point, which ends everything.

```swift
let cancellable = [1, 2].publisher
    .print("demo")                 // prints each lifecycle step
    .sink { _ in }
// demo: receive subscription: ([1, 2])
// demo: request unlimited
// demo: receive value: (1)
// demo: receive value: (2)
// demo: receive finished
```

**Follow-ups:**
- **Who asks for values, the publisher or the subscriber?** The subscriber. That's how backpressure works (see Q68).
- **How many completions can there be?** At most one.
- **What does `sink` ask for?** Unlimited values.

### Q6. What is the "contract" a publisher must follow? `[Senior]`
A publisher must send **zero or more values, then at most one completion**, and **nothing after that**. It must also never send more values than requested, and never send two events at the same time.

- After a completion (success or failure), nothing more is delivered.
- Values never exceed the subscriber's demand.
- Events arrive **one at a time** (not in parallel).
- **Important result:** an error **ends the stream**. Most error-handling patterns come from this (see Section 9).

```swift
let subject = PassthroughSubject<Int, Never>()
subject
    .sink(receiveCompletion: { print("done: \($0)") }, receiveValue: { print($0) })
    .store(in: &cancellables)

subject.send(1)                      // 1
subject.send(completion: .finished)  // done: finished
subject.send(2)                      // ignored: the stream is over
```

**Follow-ups:**
- **Why does "an error ends the stream" matter so much?** One failed network call can stop a whole search or refresh pipeline.
- **Can a subject "restart" after finishing?** No. You must create a new subject.
- **Who enforces the contract?** Built-in publishers do. Custom publishers must follow it themselves (see Q89).

### Q7. Are Combine publishers lazy (cold) or eager (hot)? `[Senior]`
Most publishers are **cold**: they do nothing until someone subscribes, and **each subscriber starts the work again**. **Hot** sources like subjects send values whether or not anyone is listening.

- **Cold:** `dataTaskPublisher`, sequence publishers. Two subscribers = two network requests.
- **Hot:** subjects, `@Published`, `NotificationCenter`, timers. Late subscribers miss earlier values (except `CurrentValueSubject` and `@Published`, which give the current value).
- **Exception:** `Future` starts its work **immediately when created**.

```swift
// Cold: each subscriber triggers a new request
let request = URLSession.shared.dataTaskPublisher(for: url)
request.sink(receiveCompletion: { _ in }, receiveValue: { _ in }).store(in: &cancellables)  // request 1
request.sink(receiveCompletion: { _ in }, receiveValue: { _ in }).store(in: &cancellables)  // request 2

// Hot: values sent before subscribing are missed
let events = PassthroughSubject<Int, Never>()
events.send(1)                                          // nobody listening, lost
events.sink { print($0) }.store(in: &cancellables)
events.send(2)                                          // prints 2
```

**Follow-ups:**
- **How do you avoid duplicate requests with a cold publisher?** Share it with `share()` (see Q63).
- **Why is `Future` surprising?** It runs right away, even with no subscriber (see Q114).
- **How do you make `Future` lazy?** Wrap it in `Deferred` (see Q11).

### Q8. What is a marble diagram? `[Fundamental]`
A marble diagram is a **timeline drawing** of a stream's values and its end, used to explain what an operator does.

- Each dash is time passing, each value is a "marble," `|` means finished, and `X` means failed.
- Drawing one in an interview shows you think clearly about timing.

```swift
// input:         ──1──2──3──4──|
// map { $0*10 }: ──10─20─30─40─|
// filter(even):  ─────2─────4──|

[1, 2, 3, 4].publisher
    .filter { $0.isMultiple(of: 2) }
    .sink { print($0) }          // 2, 4
    .store(in: &cancellables)
```

**Follow-ups:**
- **Which operators are easiest to explain with marbles?** Timing ones like `debounce` and `throttle`, and combining ones like `combineLatest` and `switchToLatest`.
- **What does `X` mean in a diagram?** The stream failed with an error.
- **Where can you see interactive marbles?** Sites like RxMarbles show the same ideas used in RxSwift.

## 2. Built-in Publishers

### Q9. What are `Just`, `Empty`, `Fail`, and sequence publishers? `[Fundamental]`
They are **simple ready-made publishers**: `Just` sends one value, `Empty` sends nothing, `Fail` sends an error, and a sequence publisher sends each element of a collection.

- Often used as fallbacks in `catch`, in tests, or to start a pipeline.

```swift
Just(42)                                          // sends 42, then finishes (can't fail)
Empty<Int, Never>()                               // finishes right away, no values
Empty<Int, Never>(completeImmediately: false)     // never sends anything, never finishes
Fail<Int, URLError>(error: URLError(.badURL))     // fails right away
[1, 2, 3].publisher                               // sends 1, 2, 3, then finishes
```

**Follow-ups:**
- **When would you use `Empty(completeImmediately: false)`?** When you need a publisher that stays open but never sends, for example in tests.
- **When do you use `Fail` in real code?** In mocks, or to return an error early from a function that returns a publisher.
- **Can `Just` fail?** No. Its `Failure` is `Never`. Use `setFailureType` if you need it to match a failing type.

### Q10. What is `Future`, and what are its gotchas? `[Senior]`
`Future` produces **one value or one error later**, which makes it useful for **wrapping completion-handler APIs**, but it **starts immediately** and **runs only once**.

- **Gotcha 1:** the work starts **when `Future` is created**, not when someone subscribes.
- **Gotcha 2:** it runs **once** and gives the same saved result to every subscriber, so `retry` can't redo the work.
- **Fix:** wrap it in `Deferred` to make it lazy and repeatable.

```swift
func fetchUser(id: Int) -> AnyPublisher<User, Error> {
    Deferred {                                       // create a new Future per subscriber
        Future { promise in
            legacyAPI.fetchUser(id: id) { result in  // old completion-handler API
                promise(result)
            }
        }
    }
    .eraseToAnyPublisher()
}
```

**Follow-ups:**
- **What is the `promise`?** A function you call once with `.success(value)` or `.failure(error)`.
- **What if you call the promise twice?** Only the first call counts.
- **Why does `retry` not work on a plain `Future`?** It gives the same saved failure again instead of running the work again.

### Q11. What is `Deferred`? `[Senior]`
`Deferred` **waits until someone subscribes**, then creates a **fresh publisher for that subscriber**.

- It makes eager publishers like `Future` lazy.
- It lets `retry` actually run the work again.

```swift
let lazyRequest = Deferred {
    Future<Int, Never> { promise in
        print("Work started")         // runs only when subscribed, once per subscriber
        promise(.success(42))
    }
}
```

**Follow-ups:**
- **What happens with two subscribers?** The closure runs twice, once for each.
- **Is the work cancelled if the subscriber cancels?** `Deferred` itself doesn't cancel work already started inside `Future`.
- **Where else is `Deferred` useful?** To read a value at subscribe time, not at creation time, like the current date.

### Q12. Which Foundation types provide publishers? `[Fundamental]`
Foundation gives you publishers for **notifications**, **timers**, **URL requests**, **KVO**, and **sequences**.

```swift
// NotificationCenter
NotificationCenter.default.publisher(for: UIApplication.didBecomeActiveNotification)

// Timer (starts ticking when connected; autoconnect does that on first subscription)
Timer.publish(every: 1, on: .main, in: .common).autoconnect()

// URLSession
URLSession.shared.dataTaskPublisher(for: url)

// KVO on NSObject subclasses with @objc dynamic properties
player.publisher(for: \.timeControlStatus)

// Sequences
(1...5).publisher
```

**Follow-ups:**
- **Why does a timer need `autoconnect()`?** `Timer.publish` doesn't start until connected (see Q66).
- **Can `dataTaskPublisher` fail?** Yes, with `URLError`.
- **Which thread do notification publishers use?** The thread that posted the notification.

### Q13. How do you observe KVO properties with Combine? `[Senior]`
Call **`publisher(for: \.keyPath)`** on an `NSObject`, and you get a publisher of that property's values.

- Works for KVO-compliant properties. For your own classes, the property must be `@objc dynamic`.

```swift
final class PlayerObserver {
    private var cancellables = Set<AnyCancellable>()

    init(player: AVPlayer, onStatus: @escaping (AVPlayer.TimeControlStatus) -> Void) {
        player.publisher(for: \.timeControlStatus, options: [.initial, .new])
            .removeDuplicates()
            .receive(on: DispatchQueue.main)
            .sink(receiveValue: onStatus)
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **What does `.initial` do?** Sends the current value right away when you subscribe.
- **Why add `removeDuplicates`?** KVO can report the same value more than once.
- **What's the modern alternative for your own models?** `@Observable` and Observation, not KVO.

### Q14. What is the `Record` publisher? `[Lead/Expert]`
`Record` **plays back a fixed list of values and a completion**, which is handy in **tests and previews** to fake a stream in a predictable way.

```swift
let recorded = Record<Int, Never>(output: [1, 2, 3], completion: .finished)

recorded
    .sink { print($0) }        // 1, 2, 3
    .store(in: &cancellables)
```

**Follow-ups:**
- **How is it different from `[1, 2, 3].publisher`?** `Record` can also end with a failure.
- **Can it replay timing?** No, values are sent immediately. Use a test scheduler for timing.
- **Where is it most useful?** Mocks that need a known sequence ending in an error.

## 3. Subscribers

### Q15. What are the built-in subscribers? `[Fundamental]`
There are two main built-in subscribers: **`sink`** (run closures for values and completion) and **`assign`** (write values into a property).

- `sink(receiveCompletion:receiveValue:)`: closures for values and the end. Asks for unlimited values.
- `sink(receiveValue:)`: only when `Failure == Never`.
- `assign(to:on:)`: writes values to an object's property (needs `Never`).
- `assign(to: &$property)` (iOS 14): writes to a `@Published` property, with no cancellable needed.

```swift
let cancellable = URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)
    .sink(
        receiveCompletion: { completion in
            if case .failure(let error) = completion {
                print("Failed: \(error)")
            }
        },
        receiveValue: { data in
            print("Received \(data.count) bytes")
        }
    )
```

**Follow-ups:**
- **Which one do you use most?** `sink`, because it's the most flexible.
- **Which `assign` is safest?** `assign(to: &$property)`, because it can't create a retain cycle (see Q17).
- **Can you write your own subscriber?** Yes, but you rarely need to (see Q69).

### Q16. Why does `sink(receiveValue:)` sometimes fail to compile? `[Fundamental]`
Because it **only exists when the publisher can't fail** (`Failure == Never`), so for a failing publisher you must **also handle completion**, or **remove the error first**.

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)
    .replaceError(with: Data())      // now Failure is Never
    .sink { data in print(data.count) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why did Apple design it that way?** So you can't ignore errors by accident.
- **What other ways remove the error?** `catch` with a fallback publisher, or `assertNoFailure` in tests.
- **Is `replaceError` always a good idea?** No. It hides the error, so use it only when a default value is truly fine.

### Q17. What is the difference between `assign(to:on:)` and `assign(to: &$property)`? `[Senior]`
`assign(to:on:)` writes to **any object's property** but **strongly keeps that object alive**, while `assign(to: &$property)` only writes to **`@Published` properties** but **can't create a retain cycle**.

| `assign(to:on:)` | `assign(to: &$property)` |
|---|---|
| Any class property | Only `@Published` properties |
| Returns an `AnyCancellable` you must store | Returns nothing. Its lifetime follows the `@Published` property |
| **Keeps the target object alive** until the publisher completes | No retain cycle |
| `assign(to: \.x, on: self)` stored in `self.cancellables` = **retain cycle** | Safe for your own properties |

```swift
final class ProfileViewModel: ObservableObject {
    @Published var name = ""
    @Published private(set) var greeting = ""

    init() {
        $name
            .map { $0.isEmpty ? "Hello!" : "Hello, \($0)!" }
            .assign(to: &$greeting)   // no cancellable, no cycle
    }
}
```

**Follow-ups:**
- **Why does `assign(to:on: self)` leak?** `self` owns the cancellable, and the cancellable owns `self`, until the publisher completes. Long-lived sources like `@Published` never complete.
- **When is `assign(to:on:)` safe?** When the target isn't the owner, for example `assign(to: \.text, on: label)`.
- **Which iOS added `assign(to: &$property)`?** iOS 14.

### Q18. What happens when a subscriber receives a completion? `[Fundamental]`
The subscription **ends**: `.finished` means it ended normally, `.failure(error)` means it failed, and **no more values arrive after that**.

- Even if the source (like a subject) sends more later, this subscriber won't get them.

```swift
[1, 2].publisher
    .sink(receiveCompletion: { completion in
        switch completion {
        case .finished: print("finished normally")
        case .failure(let error): print("failed: \(error)")
        }
    }, receiveValue: { print($0) })
    .store(in: &cancellables)
// 1, 2, finished normally
```

**Follow-ups:**
- **How do you keep receiving values after a failure?** Handle errors inside a `flatMap` so the outer stream never fails (see Q51).
- **Does the cancellable need to be cancelled after completion?** No, the subscription is already over.
- **Can you subscribe again after completion?** Yes, a new subscription starts fresh (for cold publishers, the work runs again).

## 4. Subjects & `@Published`

### Q19. What is a `Subject`? `[Fundamental]`
A subject is a **publisher you can push values into yourself** with `send(_:)`, which **connects normal code** (button taps, delegates, callbacks) **to Combine pipelines**.

- Subjects are **hot**: they send to everyone currently subscribed.
- They can also be finished with `send(completion:)`.

```swift
let buttonTapped = PassthroughSubject<Void, Never>()

buttonTapped
    .sink { print("tapped") }
    .store(in: &cancellables)

buttonTapped.send(())      // "tapped"
```

**Follow-ups:**
- **What are the two built-in subjects?** `PassthroughSubject` and `CurrentValueSubject` (see Q20).
- **Can several subscribers listen to one subject?** Yes, they all receive each value.
- **Should you expose a subject publicly?** No. Expose it as `AnyPublisher` (see Q22).

### Q20. What is the difference between `PassthroughSubject` and `CurrentValueSubject`? `[Fundamental]`
`PassthroughSubject` is for **events** and **doesn't remember** anything, while `CurrentValueSubject` is for **state** and **always holds the latest value**, which new subscribers get immediately.

| `PassthroughSubject` | `CurrentValueSubject` |
|---|---|
| No starting value | Needs a starting value |
| Doesn't store values | Stores the latest value (`.value`) |
| New subscribers get only **future** values | New subscribers get the **current** value right away, then future ones |
| Good for **events** (taps, "did finish") | Good for **state** (current user, settings) |

```swift
let taps = PassthroughSubject<Void, Never>()
let isLoggedIn = CurrentValueSubject<Bool, Never>(false)

taps.send(())
isLoggedIn.send(true)        // or: isLoggedIn.value = true
print(isLoggedIn.value)      // true
```

**Follow-ups:**
- **Which one is like `@Published`?** `CurrentValueSubject`, because both give new subscribers the current value.
- **Can you read the last value of a `PassthroughSubject`?** No, it doesn't keep one.
- **Is setting `.value` the same as `send`?** Yes, both update the value and notify subscribers.

### Q21. How does `@Published` work? `[Senior]`
`@Published` is a property wrapper that turns a class property into a **publisher** (`$property`), which **sends the current value to new subscribers** and **sends new values before the property actually changes**.

- It behaves like a `CurrentValueSubject`.
- **Gotcha:** it sends in `willSet`, so inside the subscriber, reading the property still gives the **old** value. Use the value passed into the closure.
- In an `ObservableObject`, any `@Published` change also fires `objectWillChange`.

```swift
final class Counter: ObservableObject {
    @Published var count = 0
}

let counter = Counter()
let cancellable = counter.$count.sink { newValue in
    print("emitted: \(newValue), property now: \(counter.count)")
}
counter.count = 1
// emitted: 0, property now: 0
// emitted: 1, property now: 0   ← the property isn't updated yet
```

**Follow-ups:**
- **Can you use `@Published` in a struct?** No, only in classes.
- **Why does it send before the change?** So SwiftUI's `objectWillChange` can prepare before the new value is set.
- **How do you skip the first (current) value?** Add `.dropFirst()`.

### Q22. Why should you expose subjects as `AnyPublisher` instead of exposing the subject itself? `[Senior]`
So that **only the owner can send values**. If you expose the subject, **any caller can push values or finish it**, which breaks your data flow.

```swift
final class CartService {
    private let itemsSubject = CurrentValueSubject<[Item], Never>([])   // private: only we send

    var itemsPublisher: AnyPublisher<[Item], Never> {                    // public: read only
        itemsSubject.eraseToAnyPublisher()
    }

    func add(_ item: Item) {
        itemsSubject.value.append(item)
    }
}
```

**Follow-ups:**
- **What could go wrong if the subject is public?** Another class could send fake values or finish it forever.
- **Can callers cast `AnyPublisher` back to the subject?** No, `AnyPublisher` hides the real type.
- **How do you expose `@Published` read-only?** Use `@Published private(set) var`, and `$property` is still readable.

### Q23. Is it safe to call `send` from multiple threads? `[Lead/Expert]`
**Not really**: Combine expects events to arrive **one at a time**, so sending into a subject from several threads at once can deliver values **at the same time** to code that isn't built for it.

- Send from **one place**: a serial queue, an actor, or always the main thread.
- Use `receive(on:)` to control which thread receives the values.
- `subscribe(on:)` does **not** change the thread a subject sends on. Values arrive on whatever thread called `send`.

```swift
final class EventBus {
    private let subject = PassthroughSubject<Event, Never>()
    private let queue = DispatchQueue(label: "event-bus")     // one serial queue for all sends

    var events: AnyPublisher<Event, Never> { subject.eraseToAnyPublisher() }

    func post(_ event: Event) {
        queue.async { self.subject.send(event) }              // sends never overlap
    }
}
```

**Follow-ups:**
- **What can go wrong?** Two values processed at the same time, causing data races in operators or the subscriber.
- **Does `receive(on:)` fix concurrent sends?** It controls the delivery thread, but sending itself should still happen from one place.
- **What's the Swift Concurrency equivalent?** Send from inside an actor, which guarantees one-at-a-time access.

### Q24. What happens if you send a completion to a subject? `[Fundamental]`
The subject **finishes forever**: current subscribers get the completion, later `send` calls are **ignored**, and new subscribers **only get the completion**.

- Don't finish long-lived event subjects (like "button tapped") unless the source really ends.

```swift
let subject = PassthroughSubject<Int, Never>()
subject.send(completion: .finished)

subject.send(1)                                  // ignored
subject
    .sink(receiveCompletion: { print($0) }, receiveValue: { print($0) })
    .store(in: &cancellables)                    // prints only "finished"
```

**Follow-ups:**
- **Can you "restart" a finished subject?** No. Create a new one.
- **When is finishing a subject correct?** When the source truly ends, like a finished download.
- **What happens with a failure completion?** Same thing: it's over, and everyone gets the error.

## 5. Memory Management & Cancellation

### Q25. What is `AnyCancellable`, and why must you store it? `[Fundamental]`
`AnyCancellable` is the **ticket for a subscription**, and when it's **released, the subscription is cancelled**, so if you don't store it, async work like a network request is cancelled almost immediately.

- `sink` and `assign(to:on:)` return an `AnyCancellable`.
- Store it in a property or a `Set<AnyCancellable>` to keep the subscription alive.

```swift
final class FeedViewModel {
    private var cancellables = Set<AnyCancellable>()

    func load() {
        api.fetchFeed()
            .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.items = $0 })
            .store(in: &cancellables)      // keeps the subscription alive
    }
}
```

**Follow-ups:**
- **Why does a forgotten `Just(5).sink` still print?** `Just` sends synchronously before the cancellable is released (see Q109).
- **When are stored subscriptions cancelled?** When the owner (and its set) is released.
- **Do you need to cancel manually in `deinit`?** No. Releasing the set cancels them all.

### Q26. How do retain cycles happen in Combine, and how do you avoid them? `[Senior]`
A cycle happens when **`self` owns the subscription** and the **subscription's closure owns `self`**, so neither can be released. Fix it with **`[weak self]`** or by **assigning to something that isn't `self`**.

- Cycle 1: `self` → cancellables → `sink` closure → `self`.
- Cycle 2: `assign(to: \.x, on: self)` stored in `self.cancellables` (it retains `self`).

```swift
// ❌ Retain cycles
viewModel.$title
    .sink { self.titleLabel.text = $0 }
    .store(in: &cancellables)

viewModel.$title
    .assign(to: \.title, on: self)
    .store(in: &cancellables)

// ✅ Fixes
viewModel.$title
    .sink { [weak self] in self?.titleLabel.text = $0 }
    .store(in: &cancellables)

viewModel.$title
    .assign(to: \.text, on: titleLabel)   // retains the label, not self
    .store(in: &cancellables)

$name.map { "Hello, \($0)" }
    .assign(to: &$greeting)               // for @Published targets
```

**Follow-ups:**
- **How do you know there's a leak?** `deinit` never runs, or the Memory Graph Debugger shows the cycle.
- **Is `[unowned self]` OK here?** Risky. If `self` is gone when a value arrives, the app crashes.
- **Does a one-shot request also leak?** It holds `self` until it finishes, which usually isn't a lasting leak but can delay release.

### Q27. How do you cancel subscriptions? `[Fundamental]`
**Call `cancel()`** on the cancellable, **remove it from the set**, or simply **let the owner be released**.

- Cancelling also stops the work upstream, for example the network request in a `dataTaskPublisher` pipeline.

```swift
// Cancel one subscription
searchCancellable?.cancel()
searchCancellable = nil

// Cancel all subscriptions in a set
cancellables.removeAll()       // releasing each AnyCancellable cancels it

// Automatic: when the owner (and its cancellables) is released
```

**Follow-ups:**
- **Does cancelling send a completion?** No. Cancelled subscriptions just stop, with no completion.
- **Does cancelling stop the network request?** Yes, `dataTaskPublisher` cancels the `URLSessionTask`.
- **How do you run code on cancel?** Use `handleEvents(receiveCancel:)`.

### Q28. When is it appropriate to cancel and replace a subscription? `[Senior]`
When a **new request should replace an old one**, like reloading a screen or changing filters: keep that subscription in **its own `AnyCancellable?` property**, and assigning a new one **cancels the old one**.

- Inside a single pipeline, `switchToLatest` does this for you (see Q41).

```swift
private var loadCancellable: AnyCancellable?

func reload(category: Category) {
    loadCancellable = api.products(in: category)   // assigning cancels the previous request
        .receive(on: DispatchQueue.main)
        .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.products = $0 })
}
```

**Follow-ups:**
- **Why not store it in the shared set?** Then old requests would keep running and could overwrite newer results.
- **What problem does this prevent?** Stale results arriving after newer ones (a race condition).
- **When is `switchToLatest` better?** When the requests come from a stream, like search text.

### Q29. Why do cell bindings with Combine cause duplicate updates? `[Senior]`
Because **cells are reused**: if you bind in `configure` without cancelling the old bindings, a reused cell **keeps listening to the previous item** too, causing flicker or wrong data.

- **Fix:** cancel bindings in `prepareForReuse`.

```swift
final class ProductCell: UICollectionViewCell {
    private var cancellables = Set<AnyCancellable>()
    private let favoriteButton = UIButton()

    func bind(to viewModel: ProductCellViewModel) {
        viewModel.$isFavorite
            .receive(on: DispatchQueue.main)
            .sink { [weak self] in self?.favoriteButton.isSelected = $0 }
            .store(in: &cancellables)
    }

    override func prepareForReuse() {
        super.prepareForReuse()
        cancellables.removeAll()   // drop the previous item's bindings
    }
}
```

**Follow-ups:**
- **What symptom do users see?** Cells briefly showing another item's state, or flickering.
- **Is `prepareForReuse` the only fix?** You can also cancel at the start of `bind`. Either way, old bindings must go.
- **Does this apply to SwiftUI?** Less so. SwiftUI manages view lifetimes for you.

## 6. Transforming & Filtering Operators

### Q30. What are `map`, `tryMap`, and `compactMap`? `[Fundamental]`
`map` **changes each value**, `compactMap` **changes each value and drops `nil`s**, and `tryMap` is `map` that **can throw**, which turns the failure type into `Error`.

- Most operators have a `try` version (`tryFilter`, `tryCompactMap`, `tryScan`…).

```swift
["1", "2", "x", "4"].publisher
    .compactMap { Int($0) }          // drops nil: 1, 2, 4
    .map { $0 * 2 }                  // 2, 4, 8
    .sink { print($0) }
    .store(in: &cancellables)

// tryMap can throw; the Failure type becomes Error
URLSession.shared.dataTaskPublisher(for: url)
    .tryMap { output -> Data in
        guard (output.response as? HTTPURLResponse)?.statusCode == 200 else {
            throw URLError(.badServerResponse)
        }
        return output.data
    }
```

**Follow-ups:**
- **What happens when `tryMap` throws?** The stream fails and ends.
- **Why does the failure type become `Error`?** The closure can throw any error, so Combine uses the general type.
- **How do you get a specific error type back?** Use `mapError` after it.

### Q31. What does `flatMap` do? `[Senior]`
`flatMap` turns **each value into a new publisher** and **merges all their results into one stream**, which is how you chain one async call after another.

- All inner publishers stay active, so results can arrive in any order.
- **`flatMap` vs `switchToLatest`:** `flatMap` keeps **all** inner publishers. `switchToLatest` keeps only the **newest** (see Q41).

```swift
userIDs.publisher
    .flatMap { id in api.fetchUser(id: id) }   // one request per ID, results arrive as they finish
    .collect()
    .sink(receiveCompletion: { _ in }, receiveValue: { users in print(users.count) })
    .store(in: &cancellables)
```

**Follow-ups:**
- **Are results in the same order as the IDs?** Not guaranteed. They arrive as each request finishes.
- **How do you limit parallel requests?** `flatMap(maxPublishers: .max(3))` (see Q32).
- **When would `flatMap` cause a bug in search?** Old searches can finish after newer ones and overwrite them.

### Q32. How do you limit concurrency with `flatMap`? `[Lead/Expert]`
Pass **`maxPublishers: .max(n)`**, and `flatMap` runs **at most n inner publishers at the same time**.

- It works with demand: `flatMap` asks for the next value only when one inner publisher finishes.

```swift
imageURLs.publisher
    .flatMap(maxPublishers: .max(3)) { url in   // at most 3 downloads at once
        downloader.download(url)
            .replaceError(with: nil)
    }
    .compactMap { $0 }
    .collect()
    .sink { images in print("Downloaded \(images.count) images") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What does `.max(1)` give you?** One at a time, in order, like a serial queue.
- **Does this work with a subject upstream?** Subjects can't wait, so extra values may be dropped. Add a `buffer` (see Q70).
- **Why limit downloads?** To save memory, battery, and avoid overloading the server.

### Q33. What is the difference between `scan` and `reduce`? `[Fundamental]`
Both combine values into a running result, but **`scan` sends every step**, while **`reduce` sends only the final result when the stream finishes**.

```swift
[1, 2, 3, 4].publisher
    .scan(0, +)          // sends each step: 1, 3, 6, 10
    .sink { print($0) }
    .store(in: &cancellables)

[1, 2, 3, 4].publisher
    .reduce(0, +)        // sends once, at the end: 10
    .sink { print($0) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What happens with `reduce` on a subject that never finishes?** It never sends anything (see Q119).
- **What is `scan` good for?** Running totals, counters, and building up state.
- **What's the Swift array equivalent of `reduce`?** The same `reduce` method on arrays.

### Q34. What does `collect` do? `[Fundamental]`
`collect` **gathers values into arrays**: all of them at the end, a fixed number at a time, or by time window.

- `collect()` with no limit **waits until the stream finishes**, so don't use it on endless streams.

```swift
publisher.collect()                                                   // one array, at the end
publisher.collect(3)                                                  // arrays of 3 values
publisher.collect(.byTime(DispatchQueue.main, .seconds(5)))           // every 5 seconds
publisher.collect(.byTimeOrCount(DispatchQueue.main, .seconds(5), 20)) // whichever comes first
```

**Follow-ups:**
- **Why is `collect()` risky on a subject?** It keeps buffering forever and never sends.
- **What's `.byTimeOrCount` good for?** Batching events, like analytics uploads (see Q48).
- **What happens if the stream fails?** The collected values are lost, and the failure is sent.

### Q35. What do `filter` and `removeDuplicates` do? `[Fundamental]`
`filter` **keeps only values that pass a test**, and `removeDuplicates` **skips a value if it's the same as the one just before it**.

- `removeDuplicates` only compares **neighbors**: `1, 1, 2, 1` becomes `1, 2, 1`.

```swift
$searchText
    .filter { $0.count >= 2 }     // ignore very short queries
    .removeDuplicates()           // ignore the same text twice in a row (needs Equatable)

$location
    .removeDuplicates { old, new in old.distance(from: new) < 50 }   // custom "same" rule
```

**Follow-ups:**
- **Why does `removeDuplicates` need `Equatable`?** To compare values, unless you give your own comparison.
- **Does it remove all duplicates?** No, only back-to-back ones.
- **Why use it before a network call?** To avoid searching for the same text twice.

### Q36. What operators select specific values? `[Fundamental]`
Combine has operators to **pick values by position or condition**: the first, the last, the first few, skip some, or ignore all values.

| Operator | What it does |
|---|---|
| `first()` / `first(where:)` | First (matching) value, then finishes |
| `last()` / `last(where:)` | Last value, sent when the stream finishes |
| `prefix(n)` / `prefix(while:)` | First n values / while a condition is true, then finishes |
| `dropFirst(n)` / `drop(while:)` | Skip the first n values / while a condition is true |
| `output(at:)` / `output(in:)` | The value at an index / in a range |
| `ignoreOutput()` | Only passes on the completion |

```swift
viewModel.$results
    .dropFirst()          // skip the current value @Published sends on subscription
    .sink { print("Results changed: \($0.count)") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why is `dropFirst()` so common with `@Published`?** `@Published` sends its current value immediately, which you often don't need.
- **Does `last()` work on endless streams?** No, it waits for the stream to finish.
- **What does `first()` do to the subscription?** It cancels upstream after the first value and finishes.

### Q37. What do `prefix(untilOutputFrom:)` and `drop(untilOutputFrom:)` do? `[Senior]`
`prefix(untilOutputFrom:)` **passes values until another publisher sends something, then finishes**. `drop(untilOutputFrom:)` **ignores values until another publisher sends something, then passes them**.

```swift
// Show progress until the user taps Cancel
downloadProgress
    .prefix(untilOutputFrom: cancelTapped)   // finishes when cancelTapped sends
    .sink { print("Progress: \($0)") }
    .store(in: &cancellables)

// Ignore location updates until tracking is turned on
locationUpdates
    .drop(untilOutputFrom: trackingEnabled)
    .sink { print($0) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What's a typical use of `prefix(untilOutputFrom:)`?** Stopping a stream when a screen closes or the user cancels.
- **Does `drop(untilOutputFrom:)` start again later?** No. Once the trigger fires, it passes all later values.
- **Does the trigger's value matter?** No, only that it sent something.

### Q38. What other operators are useful to know? `[Senior]`
A few **helper operators** come up often: replacing `nil` or empty results, simple checks like `contains`, side effects, debugging, and `Codable` encoding.

| Operator | Use |
|---|---|
| `replaceNil(with:)` | Use a default when the value is `nil` |
| `replaceEmpty(with:)` | Send a value if the stream finishes without sending any |
| `contains`, `allSatisfy`, `count`, `min`, `max` | Checks and totals (sent when the stream finishes) |
| `handleEvents` | Side effects, like showing a loading spinner or logging |
| `breakpoint`, `print` | Debugging (Section 20) |
| `encode`, `decode` | `Codable` encoding and decoding in a pipeline |
| `map(\.keyPath)` | Pick a property: `.map(\.data)` |

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)                                           // key path map
    .decode(type: [Post].self, decoder: JSONDecoder())     // Codable decoding
    .replaceEmpty(with: [])                                // default if nothing arrives
    .handleEvents(receiveOutput: { print("Got \($0.count) posts") })
```

**Follow-ups:**
- **Is `handleEvents` OK for app logic?** Use it for side effects like logging or spinners, not core logic.
- **When does `count` send?** When the stream finishes.
- **What does `decode` need?** A publisher of `Data` and a decoder like `JSONDecoder`.

## 7. Combining Operators

### Q39. How does `combineLatest` work? `[Fundamental]`
`combineLatest` **waits until every input has sent at least one value**, then sends a **tuple of the latest values** **every time any input changes**.

- Great for state that depends on several inputs, like form validation.
- It finishes when **all** inputs finish, and fails if **any** input fails.

```swift
let username = CurrentValueSubject<String, Never>("")
let password = CurrentValueSubject<String, Never>("")

username.combineLatest(password)
    .map { user, pass in user.count >= 3 && pass.count >= 8 }
    .removeDuplicates()
    .sink { print("Form valid: \($0)") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **How many publishers can you combine?** Up to four with `combineLatest` or `Publishers.CombineLatest3/4`.
- **Why might it never send?** One input hasn't sent its first value yet.
- **Why use `CurrentValueSubject` here?** It has a starting value, so `combineLatest` can send right away.

### Q40. Compare `combineLatest`, `zip`, and `merge`. `[Senior]`
`combineLatest` sends the **latest values together** when **any** input changes, `zip` **pairs values in order** (first with first), and `merge` **mixes values of the same type into one stream**.

| Operator | Sends when | Sends | Use for |
|---|---|---|---|
| `combineLatest` | Any input sends (after all have sent once) | Tuple of latest values | State built from several inputs |
| `zip` | Every input has a **new, unpaired** value | Tuple paired in order | Waiting for parallel results |
| `merge` | Any input sends | One value (same type for all) | Combining similar events |

```swift
// zip: wait for both requests, then use both results
api.fetchProfile()
    .zip(api.fetchSettings())
    .sink(receiveCompletion: { _ in }, receiveValue: { profile, settings in
        render(profile, settings)
    })
    .store(in: &cancellables)

// merge: one stream of "refresh" events from several sources
let refreshTriggers = pullToRefresh
    .merge(with: appBecameActive, retryTapped)   // all Publisher<Void, Never>
```

**Follow-ups:**
- **Which one for "show the screen when both requests finish"?** `zip`.
- **Which one for "enable the button when all fields are valid"?** `combineLatest`.
- **Can `merge` combine different types?** No. Map them to the same type first.

### Q41. What does `switchToLatest` do? `[Senior]`
`switchToLatest` works on a **stream of publishers**: when a **new inner publisher arrives**, it **cancels the previous one** and only passes on values from the **newest**.

- It's the standard tool for search-as-you-type: old requests are cancelled automatically.
- With `flatMap`, all requests would finish, and old results could overwrite newer ones.

```swift
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .removeDuplicates()
    .map { query in
        api.search(query).replaceError(with: [])   // one inner publisher per query
    }
    .switchToLatest()                               // keep only the newest request
    .receive(on: DispatchQueue.main)
    .assign(to: &$results)
```

**Follow-ups:**
- **Why `map` and not `flatMap` before it?** `map` creates the publishers, and `switchToLatest` picks the newest.
- **Why is `replaceError` inside the `map`?** So one failed search doesn't end the whole stream (see Q51).
- **Does it really cancel the network request?** Yes. Cancelling a `dataTaskPublisher` cancels its task.

### Q42. How do you combine a dynamic number of publishers? `[Senior]`
Use **`Publishers.MergeMany`** with an array of publishers, then **`collect()`** to get all the results together.

- Results arrive in **completion order**, not request order.
- To keep the original order, attach an index, then sort after collecting.

```swift
let requests = productIDs.map { api.fetchProduct(id: $0) }

Publishers.MergeMany(requests)
    .collect()                     // [Product], in the order they finished
    .sink(receiveCompletion: { _ in }, receiveValue: { products in print(products.count) })
    .store(in: &cancellables)

// Keep the original order
Publishers.MergeMany(
    productIDs.enumerated().map { index, id in
        api.fetchProduct(id: id).map { (index, $0) }   // remember each position
    }
)
.collect()
.map { pairs in pairs.sorted { $0.0 < $1.0 }.map(\.1) }  // sort back into order
```

**Follow-ups:**
- **What if one request fails?** The whole result fails. Handle errors per request if partial results are OK.
- **How do you limit how many run at once?** Use `flatMap(maxPublishers:)` on the IDs instead.
- **Why not `zip`?** `zip` only takes a fixed number of publishers.

### Q43. What do `prepend` and `append` do? `[Fundamental]`
`prepend` **adds values before** a stream starts, and `append` **adds values after** a stream finishes.

```swift
api.fetchItems()
    .prepend(cachedItems)          // show cached items first, then fresh data
    .append(Just([]))              // something after the stream finishes (rarely needed)

loadingStates
    .prepend(.idle)                // give a stream a starting value
```

**Follow-ups:**
- **What's a classic use of `prepend`?** Showing cached data first, then network data (see Q132).
- **When does `append` send?** Only after the upstream finishes, so not with endless streams.
- **Can you prepend a whole publisher?** Yes, `prepend` also accepts another publisher.

### Q44. Build a sign-up form validation pipeline. `[Senior]`
Turn each field into a **validation stream** with `map`, **combine them with `combineLatest`**, and **assign the result** to `@Published` properties the UI reads.

```swift
final class SignUpViewModel: ObservableObject {
    @Published var email = ""
    @Published var password = ""
    @Published var confirmPassword = ""
    @Published private(set) var isValid = false
    @Published private(set) var passwordError: String?

    init() {
        let isEmailValid = $email
            .map { $0.contains("@") && $0.contains(".") }       // simple email check

        let passwordValidation = $password.combineLatest($confirmPassword)
            .map { password, confirm -> String? in
                if password.count < 8 { return "Password must be at least 8 characters" }
                if password != confirm { return "Passwords don't match" }
                return nil                                       // no error
            }

        passwordValidation
            .assign(to: &$passwordError)

        isEmailValid.combineLatest(passwordValidation)
            .map { emailValid, passwordError in emailValid && passwordError == nil }
            .removeDuplicates()
            .assign(to: &$isValid)                               // drives the button
    }
}
```

**Follow-ups:**
- **Why `removeDuplicates` at the end?** So the button state only updates when it actually changes.
- **Why `assign(to: &$...)` instead of `sink`?** No cancellable to store and no retain cycle.
- **How would you avoid showing errors before the user types?** Add `.dropFirst()` on the error stream, or track whether the field was edited.

## 8. Timing Operators

### Q45. What is the difference between `debounce` and `throttle`? `[Senior]`
`debounce` **waits for a pause** in the values and then sends the last one, while `throttle` sends **at most one value per time interval** while values keep coming.

| `debounce(for:scheduler:)` | `throttle(for:scheduler:latest:)` |
|---|---|
| Waits for a **quiet period**, then sends the last value | Sends **at most one value per interval** |
| Constant input → nothing sent until input stops | Constant input → steady sends, one per interval |
| Search fields, autosave after typing stops | Scroll events, fast button taps, sensor data |

```swift
// input:     a-b-c-d-------e-f---------
// debounce:  -------------d---------f--   (sends after a quiet period)
// throttle:  a-----c-----d-----f-------   (one per interval)

saveButtonTaps
    .throttle(for: .seconds(1), scheduler: DispatchQueue.main, latest: false)  // stop double submits
    .sink { [weak self] in self?.save() }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What does `latest:` mean in `throttle`?** `true` sends the newest value in each interval. `false` sends the first.
- **Which one for a search field?** `debounce`, so you search only when the user stops typing.
- **Which one for a "Pay" button?** `throttle` with `latest: false`, so only the first tap counts.

### Q46. Build a complete search-as-you-type view model. `[Senior]`
Chain **`debounce` → clean up → `removeDuplicates` → `filter` → `map` to a request (with errors handled inside) → `switchToLatest` → `receive(on:)`**, and explain **why each operator is in its position**.

- `debounce`: wait until typing pauses.
- `removeDuplicates`: don't search the same text twice.
- `replaceError` **inside** the `map`: one failed request doesn't kill the search stream (see Q51).
- `switchToLatest`: cancel old requests.
- The scheduler is **injected**, so tests can control time (see Q94).

```swift
final class MovieSearchViewModel: ObservableObject {
    @Published var query = ""
    @Published private(set) var results: [Movie] = []
    @Published private(set) var isLoading = false

    private var cancellables = Set<AnyCancellable>()

    convenience init(api: MovieAPI) {
        self.init(api: api, scheduler: DispatchQueue.main)
    }

    init<S: Scheduler>(api: MovieAPI, scheduler: S) {     // inject a test scheduler in tests
        $query
            .debounce(for: .milliseconds(300), scheduler: scheduler)  // 1. wait for a pause
            .map { $0.trimmingCharacters(in: .whitespacesAndNewlines) }
            .removeDuplicates()                                        // 2. skip repeats
            .filter { !$0.isEmpty }                                    // 3. skip empty text
            .handleEvents(receiveOutput: { [weak self] _ in self?.isLoading = true })
            .map { query in
                api.search(query)
                    .replaceError(with: [])                            // 4. errors handled per request
            }
            .switchToLatest()                                          // 5. cancel old requests
            .receive(on: scheduler)                                    // 6. back to main
            .sink { [weak self] movies in
                self?.isLoading = false
                self?.results = movies
            }
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **Why `removeDuplicates` after trimming?** So "dune" and "dune " count as the same search.
- **What if `replaceError` were after `switchToLatest`?** The first error would end the whole search stream.
- **How would you show an error message instead of empty results?** Map each request to a state enum, like `.failed(message)`.

### Q47. How do `delay` and `timeout` work? `[Fundamental]`
`delay` **sends each value later** by a fixed time, and `timeout` **ends the stream if nothing arrives in time**.

- **Gotcha:** without `customError`, `timeout` **finishes normally**, which can hide a failure.

```swift
toastShown
    .delay(for: .seconds(3), scheduler: DispatchQueue.main)   // hide after 3 seconds
    .sink { [weak self] in self?.hideToast() }
    .store(in: &cancellables)

api.fetchConfig()
    .timeout(.seconds(10), scheduler: DispatchQueue.main, customError: { APIError.timeout })
    .sink(receiveCompletion: { print($0) }, receiveValue: { print($0) })
    .store(in: &cancellables)
```

**Follow-ups:**
- **What happens without `customError`?** The stream finishes successfully, as if nothing went wrong (see Q124).
- **Does `delay` also delay the completion?** Yes, completion is delayed too.
- **When does the timeout clock restart?** After each value, so it measures the gap between values.

### Q48. How would you batch analytics events with Combine? `[Senior]`
Send events into a **subject**, **group them** with `collect(.byTimeOrCount)`, and **upload one batch at a time** with `flatMap(maxPublishers: .max(1))`.

```swift
final class AnalyticsBatcher {
    private let events = PassthroughSubject<AnalyticsEvent, Never>()
    private var cancellables = Set<AnyCancellable>()

    init(uploader: AnalyticsUploader) {
        events
            .collect(.byTimeOrCount(DispatchQueue.global(qos: .utility), .seconds(30), 50))  // 30s or 50 events
            .filter { !$0.isEmpty }
            .flatMap(maxPublishers: .max(1)) { batch in            // one upload at a time
                uploader.upload(batch).replaceError(with: ())
            }
            .sink { }
            .store(in: &cancellables)
    }

    func track(_ event: AnalyticsEvent) {
        events.send(event)
    }
}
```

**Follow-ups:**
- **What happens to events while an upload is running?** With `.max(1)`, the next batch waits. Add a `buffer` if batches must not be dropped.
- **What happens to failed uploads?** Here they're ignored. In production, save them and retry later.
- **What about events when the app is closed?** Save unsent events to disk and send them on next launch.

## 9. Error Handling

### Q49. How do errors propagate in a Combine pipeline? `[Fundamental]`
An error **travels down to the subscriber and ends the whole subscription**: every operator stops, and no more values flow.

- Error-handling operators (`catch`, `replaceError`, `retry`) catch the failure and decide what happens next.

```swift
[1, 2, 3].publisher
    .tryMap { value -> Int in
        if value == 2 { throw URLError(.badURL) }   // fails here
        return value
    }
    .sink(receiveCompletion: { print($0) }, receiveValue: { print($0) })
    .store(in: &cancellables)
// 1
// failure(...)   ← 3 is never processed
```

**Follow-ups:**
- **Can a stream continue after an error?** Not the same stream. You can replace it (`catch`) or start a new one (`retry`).
- **Where should you handle errors for long-lived streams?** Inside a `flatMap`, per request (see Q51).
- **Does an error cancel upstream work?** Yes, everything above is torn down.

### Q50. What do `catch` and `tryCatch` do? `[Fundamental]`
`catch` **replaces the failed stream with a backup publisher**, and when that backup finishes, **the whole stream finishes**. **The original stream does not continue**.

- `tryCatch` is the same, but the handler can throw, for example to pass certain errors on.

```swift
api.fetchFeed()
    .catch { error -> Just<[Post]> in
        logger.error("Feed failed: \(error)")
        return Just(cachedPosts)          // the backup publisher
    }
    .sink { posts in render(posts) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What happens to values the original stream would send later?** They never arrive. That stream is gone.
- **When is `catch` at the end of a pipeline OK?** For one-shot requests, where ending after one result is fine.
- **When is it a bug?** On long-lived streams like button taps (see Q51 and Q110).

### Q51. How do you handle errors without killing a long-lived stream? `[Lead/Expert]`
**Handle errors inside the `flatMap`** (or inside `map` + `switchToLatest`), on **each inner request**, so a failed request is replaced while the **outer stream (taps, text) keeps working**.

- This is one of the **most important Combine ideas** for interviews.

```swift
enum FeedState {
    case loading, loaded([Post]), failed(String)
}

// ❌ One failure ends the whole pipeline: later refreshes do nothing
refreshTapped
    .flatMap { _ in api.fetchFeed() }
    .map(FeedState.loaded)
    .catch { Just(FeedState.failed($0.localizedDescription)) }
    .assign(to: &$state)

// ✅ Errors handled per request: refreshTapped keeps working
refreshTapped
    .flatMap { _ in
        api.fetchFeed()
            .map(FeedState.loaded)
            .catch { Just(FeedState.failed($0.localizedDescription)) }   // inside
            .prepend(.loading)
    }
    .receive(on: DispatchQueue.main)
    .assign(to: &$state)
```

**Follow-ups:**
- **Why does the first version stop working?** The error ends the outer stream, so later taps go nowhere.
- **What does the outer stream's failure type become in the fixed version?** `Never`, because every inner error is handled.
- **How would you test this?** Make the first request fail, tap refresh again, and check the second request runs.

### Q52. How does `retry` work, and when doesn't it help? `[Senior]`
`retry(n)` **subscribes again** up to n times after a failure, so it **only helps when subscribing restarts the work** (a "cold" publisher, like a network request).

- **Useless with:** `Future` without `Deferred` (it gives the same saved failure) and subjects (a completion is final).
- It retries **immediately**, with no wait.
- **Careful:** retrying requests that change data (like a payment POST) can do the action twice.

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .retry(2)                                 // up to 3 tries in total
    .map(\.data)
    .decode(type: Config.self, decoder: JSONDecoder())
```

**Follow-ups:**
- **How many attempts does `retry(2)` make?** Three: the first try plus two retries.
- **How do you add a delay between retries?** Build it with `catch` and `delay` (see Q53).
- **Which errors should you retry?** Temporary ones, like timeouts and 5xx server errors, not 4xx.

### Q53. How do you retry with a delay (exponential backoff)? `[Lead/Expert]`
Write a small operator: on error, **wait** (with `delay`), then **subscribe again**, **doubling the wait each time**, and give up after a set number of tries.

- "Exponential backoff" = waiting 1s, then 2s, then 4s…
- Needs a cold upstream. In production, add some randomness ("jitter") and retry only temporary errors.

```swift
extension Publisher {
    func retry<S: Scheduler>(
        _ retries: Int,
        initialDelay: S.SchedulerTimeType.Stride,
        scheduler: S
    ) -> AnyPublisher<Output, Failure> {
        self.catch { error -> AnyPublisher<Output, Failure> in
            guard retries > 0 else {
                return Fail(error: error).eraseToAnyPublisher()        // out of retries
            }
            return Just(())
                .delay(for: initialDelay, scheduler: scheduler)          // wait
                .flatMap { _ in
                    self.retry(retries - 1, initialDelay: initialDelay * 2, scheduler: scheduler)  // double it
                }
                .eraseToAnyPublisher()
        }
        .eraseToAnyPublisher()
    }
}

// Usage: retries after 1s, 2s, 4s
api.fetchFeed()
    .retry(3, initialDelay: .seconds(1), scheduler: DispatchQueue.main)
```

**Follow-ups:**
- **Why add jitter (randomness)?** So thousands of phones don't all retry at the exact same moment.
- **How do you retry only some errors?** Check the error in `catch` and return `Fail` for errors you don't retry.
- **How do you test it fast?** Inject a test scheduler and advance time (see Q94).

### Q54. What are `replaceError`, `mapError`, `setFailureType`, and `assertNoFailure`? `[Senior]`
They **change or remove the error type**: `replaceError` swaps errors for a default value, `mapError` converts errors to your own type, `setFailureType` gives a non-failing publisher an error type, and `assertNoFailure` crashes if an error happens.

```swift
// Use a default on any error. Failure becomes Never
api.fetchBanner().replaceError(with: .placeholder)

// Convert errors to your own type
api.fetchUser()
    .mapError { error -> AppError in
        (error as? URLError).map(AppError.network) ?? .unknown(error)
    }

// Make a Never-failing publisher match a failing one
Just(cachedUser)
    .setFailureType(to: AppError.self)
    .merge(with: api.fetchUser())     // both now have Failure == AppError

// Crash on error: only for "impossible" failures, like bundled data in tests
Just(bundledJSON).decode(type: Config.self, decoder: JSONDecoder()).assertNoFailure()
```

**Follow-ups:**
- **When is `replaceError` a bad idea?** When the user should know something went wrong.
- **Why use `mapError` in a service layer?** So callers deal with your domain errors, not `URLError` or `DecodingError`.
- **Is `assertNoFailure` safe in production?** Only for truly impossible errors. Otherwise it's a crash waiting to happen.

### Q55. Why do you get "Failure types don't match" errors, and how do you fix them? `[Senior]`
Because operators like **`flatMap`, `merge`, `combineLatest`, `zip`, and `switchToLatest`** need **both sides to have the same error type**. Fix it by **converting the error types** so they match.

- `setFailureType(to:)` on publishers that can't fail (`Never`).
- `mapError` to convert to one shared error type.
- Handle the error first (`replaceError`, `catch`) to get `Never`.
- Since iOS 14, `flatMap` handles some `Never`/failing combinations automatically.

```swift
// ❌ Just<User> (Never) merged with AnyPublisher<User, APIError>
// Just(cachedUser).merge(with: api.fetchUser())

// ✅ Make the error types match
Just(cachedUser)
    .setFailureType(to: APIError.self)
    .merge(with: api.fetchUser())
```

**Follow-ups:**
- **What is the most common case?** Combining `Just` (can't fail) with a network publisher (can fail).
- **Why not make everything `Error`?** You lose precise error types that callers can switch over.
- **What did iOS 14 improve?** `flatMap` overloads that connect failing and non-failing publishers without extra code.

### Q56. How should you design error types for Combine pipelines? `[Lead/Expert]`
Use **your own error types at service boundaries**, **convert low-level errors there**, and **turn errors into UI state** before they reach the view, so UI publishers never fail.

- Typed errors, like `AnyPublisher<User, APIError>`, let callers handle each case.
- Map `URLError` and `DecodingError` into domain errors in the service, not in views.
- Convert errors into **state** (`.failed(message)`) so UI publishers have `Failure == Never`.

```swift
enum APIError: Error { case offline, server(Int), decoding }

// Service: typed errors
func fetchUser() -> AnyPublisher<User, APIError> { /* ... */ }

// View model: errors become state, so the UI stream can't fail
api.fetchUser()
    .map(ProfileState.loaded)
    .catch { error in Just(ProfileState.failed(error.userMessage)) }
    .receive(on: DispatchQueue.main)
    .assign(to: &$state)
```

**Follow-ups:**
- **Why shouldn't views see `URLError`?** Views should show friendly messages, not technical details.
- **Where do you log technical details?** In the service, when mapping the error.
- **Why should UI publishers have `Failure == Never`?** So bindings like `assign` work and a failure can't break the screen.

## 10. Schedulers & Threading

### Q57. What is a scheduler in Combine? `[Fundamental]`
A scheduler decides **when and on which thread** work happens. `DispatchQueue`, `OperationQueue`, and `RunLoop` are all schedulers.

- Timing operators (`debounce`, `throttle`, `delay`, `timeout`) take a scheduler.
- Thread-switching operators (`receive(on:)`, `subscribe(on:)`) take one too.
- `ImmediateScheduler` runs work right away, on the current thread.

```swift
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)   // timing on main
    .receive(on: DispatchQueue.global())                                // continue on a background queue
    .sink { print("Searching \($0)") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why do timing operators need a scheduler?** They need a clock and a place to run when time passes.
- **Why is the scheduler useful for testing?** You can pass a test scheduler and control time (see Q94).
- **Which scheduler is most common?** `DispatchQueue.main`.

### Q58. What is the difference between `receive(on:)` and `subscribe(on:)`? `[Senior]`
`receive(on:)` changes the thread for **everything after it** (values and completion), while `subscribe(on:)` changes the thread where the **upstream starts its work**.

| `receive(on:)` | `subscribe(on:)` |
|---|---|
| Moves **downstream** events to a scheduler | Moves the **upstream** subscription and requests to a scheduler |
| Position matters: affects everything after it | Affects where an upstream does work that starts on subscription |
| Common: switch to main before UI updates | Rare: start heavy synchronous work off the main thread |

- `subscribe(on:)` does **not** affect sources that send on their own threads (subjects, `URLSession`, notifications).

```swift
Just(largeImageData)
    .subscribe(on: DispatchQueue.global(qos: .userInitiated))  // Just sends on subscribe → background
    .map { UIImage(data: $0) }                                  // decoding runs in the background
    .receive(on: DispatchQueue.main)                            // UI updates on main
    .sink { [weak self] in self?.imageView.image = $0 }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Which one do you use 95% of the time?** `receive(on: DispatchQueue.main)` before UI work.
- **Does the position of `subscribe(on:)` matter?** Usually not much. It affects the whole upstream.
- **Why doesn't `subscribe(on:)` move `URLSession` work?** `URLSession` delivers on its own queue no matter what.

### Q59. On which thread does `dataTaskPublisher` deliver values? `[Fundamental]`
On a **background thread** (URLSession's queue), so updating UI directly in `sink` is a **threading bug**. Add **`.receive(on: DispatchQueue.main)`** first.

- SwiftUI logs a runtime warning if `@Published` changes from a background thread.

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)
    .decode(type: [Post].self, decoder: JSONDecoder())   // decoding stays in the background
    .receive(on: DispatchQueue.main)                     // switch to main for the UI
    .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.posts = $0 })
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why decode before switching to main?** Decoding can be slow, so keep it off the main thread.
- **What warning does SwiftUI show?** "Publishing changes from background threads is not allowed."
- **Should the API client call `receive(on:)`?** No. The caller (view model) decides its thread (see Q75).

### Q60. `RunLoop.main` or `DispatchQueue.main` with `receive(on:)`? `[Lead/Expert]`
Use **`DispatchQueue.main`** for UI updates, because **`RunLoop.main` pauses delivery while the user is scrolling**.

- `RunLoop.main` runs work in the run loop's default mode. During scrolling the main run loop is in "tracking" mode, so delivery waits until scrolling stops.
- That pause can be useful on purpose, for example to delay loading images until scrolling ends.

```swift
liveScores
    .receive(on: DispatchQueue.main)      // ✅ updates even while scrolling
    .sink { [weak self] in self?.scoreLabel.text = $0 }
    .store(in: &cancellables)

imageRequests
    .receive(on: RunLoop.main)            // waits until scrolling stops, on purpose
    .sink { [weak self] in self?.loadImage($0) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What is "tracking mode"?** The run loop mode used while touches are being tracked, like during scrolling.
- **What bug would users notice with `RunLoop.main`?** Live data that freezes while they scroll (see Q123).
- **When is the delay helpful?** For work that shouldn't compete with smooth scrolling.

### Q61. Does `receive(on: DispatchQueue.main)` deliver synchronously if you're already on main? `[Lead/Expert]`
**No**, it always **schedules the work for later**, even if you're already on the main thread, which can cause a **one-frame flicker**, like a placeholder showing briefly.

- If the source already sends on main, skip `receive(on:)`.
- Or use a custom "UI scheduler" that runs immediately when already on main (for example Point-Free's `UIScheduler`).

```swift
// Already on main, but this still waits for the next run loop turn
Just("Hello")
    .receive(on: DispatchQueue.main)
    .sink { [weak self] in self?.label.text = $0 }   // runs a moment later
    .store(in: &cancellables)
```

**Follow-ups:**
- **When does this flicker matter?** In cells or screens that show a placeholder first, then the real value.
- **How does a UI scheduler avoid it?** It checks "am I on main?" and runs right away if yes.
- **Is the delay long?** No, one run loop turn, but that can be one visible frame.

### Q62. How does Combine interact with Swift 6 actor isolation? `[Lead/Expert]`
`receive(on: DispatchQueue.main)` puts you on the main thread **at runtime**, but **the compiler can't see that**, so a `sink` touching `@MainActor` state can cause **Swift 6 errors**.

- **Options:** `MainActor.assumeIsolated { }` inside the closure (crashes if you're wrong), or turn the publisher into an async sequence with `.values` and read it in a `@MainActor` task.
- Most Combine types aren't marked `Sendable`, which adds friction in strict mode. That's one reason teams move new async code to Swift Concurrency.

```swift
@MainActor
final class ProfileViewController: UIViewController {
    private var cancellables = Set<AnyCancellable>()
    private let nameLabel = UILabel()

    func bind(_ viewModel: ProfileViewModel) {
        viewModel.$name
            .receive(on: DispatchQueue.main)
            .sink { [weak self] name in
                MainActor.assumeIsolated {      // tell the compiler: we're on the main actor
                    self?.nameLabel.text = name
                }
            }
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **What does `assumeIsolated` do if you're wrong?** It crashes, so only use it after `receive(on: DispatchQueue.main)`.
- **What's the cleaner Swift 6 option?** `for await name in viewModel.$name.values` inside a `@MainActor` `Task`.
- **Why isn't Combine marked `Sendable`?** It was designed before Swift's strict concurrency checking existed.

## 11. Sharing & Multicasting

### Q63. Why would you need to share a publisher? `[Senior]`
Because a cold publisher **runs its work once per subscriber**, so two subscribers to one network pipeline make **two requests**. **`share()`** runs the work **once** and sends the result to everyone.

```swift
let profile = api.fetchProfile()      // AnyPublisher<Profile, Error>
    .share()                          // one request for all subscribers

profile
    .map(\.name)
    .replaceError(with: "")
    .assign(to: \.text, on: nameLabel)
    .store(in: &cancellables)

profile
    .map(\.avatarURL)
    .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.loadAvatar($0) })
    .store(in: &cancellables)
```

**Follow-ups:**
- **How do you prove two requests happen without `share()`?** Add `.print()` or `handleEvents(receiveSubscription:)` and count subscriptions.
- **Is `share()` always safe?** No, late subscribers can miss values (see Q64).
- **What other tool helps with late subscribers?** `multicast` with `connect()` (see Q65).

### Q64. What are the gotchas of `share()`? `[Lead/Expert]`
`share()` starts when the **first subscriber** arrives, so **later subscribers miss values** already sent, and if the work already finished, they **only get the completion**.

- With synchronous sources (like `[1, 2, 3].publisher` or `Just`), the first subscriber gets everything before the second one even subscribes (see Q117).
- `share()` does **not** replay the last value. For that, use `multicast` with a `CurrentValueSubject`, or keep state in a `CurrentValueSubject` or `@Published` property.

```swift
let shared = api.fetchProfile().share()

shared.sink(receiveCompletion: { _ in }, receiveValue: { print("A: \($0)") })
    .store(in: &cancellables)

// Seconds later, after the request finished:
shared.sink(receiveCompletion: { print("B completion: \($0)") }, receiveValue: { print("B: \($0)") })
    .store(in: &cancellables)    // B gets only the completion, not the profile
```

**Follow-ups:**
- **How do you give late subscribers the last value?** Store it in a `CurrentValueSubject` (see Q67).
- **Why is this dangerous with synchronous publishers?** Everything happens during the first subscription.
- **What is `share()` made of?** `multicast` with a `PassthroughSubject`, plus `autoconnect()`.

### Q65. What are `multicast` and `connect`? `[Lead/Expert]`
`multicast` makes a **publisher that waits for you to call `connect()`**, so you can **attach all subscribers first** and then start the work **once**.

- This avoids the late-subscriber problem of `share()`.

```swift
let multicasted = api.fetchProfile()
    .multicast { PassthroughSubject<Profile, Error>() }

multicasted
    .sink(receiveCompletion: { _ in }, receiveValue: { print("A: \($0.name)") })
    .store(in: &cancellables)

multicasted
    .sink(receiveCompletion: { _ in }, receiveValue: { print("B: \($0.name)") })
    .store(in: &cancellables)

multicasted
    .connect()                 // now start the single request
    .store(in: &cancellables)
```

**Follow-ups:**
- **What does `connect()` return?** A `Cancellable`. Store it, or the work is cancelled.
- **Can you use a `CurrentValueSubject` in `multicast`?** Yes, to also replay the latest value to later subscribers.
- **When is this better than `share()`?** When you know all subscribers up front and none may miss anything.

### Q66. What are `makeConnectable()` and `autoconnect()`? `[Senior]`
`makeConnectable()` turns a publisher into one that **waits for `connect()`**, and `autoconnect()` **connects automatically** when the first subscriber arrives.

- That's why `Timer.publish(...)` is usually followed by `.autoconnect()`.
- `makeConnectable()` needs `Failure == Never`.

```swift
let ticker = Timer.publish(every: 1, on: .main, in: .common)   // waits to be connected
    .autoconnect()                                              // starts on first subscription

let numbers = [1, 2, 3].publisher.makeConnectable()
numbers.sink { print($0) }.store(in: &cancellables)
numbers.connect().store(in: &cancellables)                       // starts now
```

**Follow-ups:**
- **What happens if you forget `autoconnect()` on a timer?** It never ticks.
- **When would you use `makeConnectable()`?** To control exactly when a shared publisher starts.
- **Does `autoconnect()` reconnect after all subscribers leave?** It disconnects when everyone cancels. A new subscriber connects it again.

### Q67. How do you cache the result of a request for multiple, possibly late, subscribers? `[Lead/Expert]`
Store the result in a **`CurrentValueSubject`**, so **every subscriber, even a late one, gets the latest value immediately**.

```swift
final class ConfigService {
    private let configSubject = CurrentValueSubject<Config?, Never>(nil)
    private var cancellables = Set<AnyCancellable>()

    /// Sends the cached config right away if there is one, so late subscribers get it too
    var config: AnyPublisher<Config, Never> {
        configSubject.compactMap { $0 }.eraseToAnyPublisher()
    }

    func refresh(using api: ConfigAPI) {
        api.fetchConfig()
            .map(Optional.some)
            .replaceError(with: configSubject.value)   // keep the old value on failure
            .sink { [weak self] in self?.configSubject.send($0) }
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **Why `compactMap { $0 }`?** To hide the starting `nil`, so subscribers only see real configs.
- **What happens when refresh fails?** The old config stays, because the error is replaced with the current value.
- **How is this better than `share()`?** Late subscribers always get the latest value.

## 12. Backpressure & Demand

### Q68. What is backpressure, and how does Combine implement it? `[Senior]`
Backpressure lets a **slow subscriber say how many values it can handle**, so a fast publisher doesn't overwhelm it. In Combine the subscriber does this by asking for a **demand**.

- Demand can be `.unlimited`, `.max(n)`, or `.none`.
- Demand adds up: each value received can ask for more.
- `sink` and `assign` ask for `.unlimited`, so most apps never deal with demand. It matters for custom subscribers, `flatMap(maxPublishers:)`, and `buffer`.

```swift
(1...5).publisher
    .print("upstream")
    .flatMap(maxPublishers: .max(2)) { Just($0) }   // flatMap limits how many it takes
    .sink { _ in }                                  // sink asks for unlimited
    .store(in: &cancellables)
// upstream: request max: (2)   ← flatMap asks for only 2 at first
```

**Follow-ups:**
- **Who controls the speed, the publisher or the subscriber?** The subscriber, by asking for a demand.
- **Why don't most apps notice demand?** `sink` and `assign` always ask for unlimited values.
- **What happens when a hot source has no demand?** Values are dropped (see Q71).

### Q69. Write a custom subscriber that controls demand. `[Lead/Expert]`
Conform to **`Subscriber`**, **ask for a small demand** when you get the subscription, and **return extra demand** from `receive(_:)` only when you're ready for more.

```swift
final class BatchSubscriber: Subscriber {
    typealias Input = Int
    typealias Failure = Never

    private var subscription: Subscription?

    func receive(subscription: Subscription) {
        self.subscription = subscription
        subscription.request(.max(2))          // start by asking for 2 values
    }

    func receive(_ input: Int) -> Subscribers.Demand {
        print("Processing \(input)")
        return input.isMultiple(of: 2) ? .max(2) : .none   // ask for more only after even numbers
    }

    func receive(completion: Subscribers.Completion<Never>) {
        print("Completed: \(completion)")
    }
}

(1...6).publisher.subscribe(BatchSubscriber())
```

**Follow-ups:**
- **What does returning `.none` mean?** "I don't want more right now."
- **How do you ask for more later?** Call `subscription.request(.max(n))` again.
- **When would you need this in a real app?** Rarely. Usually for processing large streams in controlled batches.

### Q70. What does `buffer` do? `[Lead/Expert]`
`buffer` **stores values** when the downstream can't take them yet, so a fast source doesn't lose them, up to a size limit.

- `whenFull` decides what happens when it's full: `.dropOldest`, `.dropNewest`, or `.customError` to fail.
- Useful when the source can't slow down (sensors, subjects) and the downstream handles one item at a time.

```swift
sensorReadings
    .buffer(size: 100, prefetch: .keepFull, whenFull: .dropOldest)   // hold up to 100 readings
    .flatMap(maxPublishers: .max(1)) { reading in                     // upload one at a time
        uploader.upload(reading).replaceError(with: ())
    }
    .sink { }
    .store(in: &cancellables)
```

**Follow-ups:**
- **What does `prefetch: .keepFull` mean?** Ask upstream for enough values to keep the buffer full.
- **What does `.byRequest` mean instead?** Only ask upstream when downstream asks.
- **Which `whenFull` option for sensor data?** Usually `.dropOldest`, because the newest data matters most.

### Q71. What happens to values sent into a `PassthroughSubject` when a subscriber has no demand? `[Lead/Expert]`
They're **dropped** for that subscriber, because a subject **can't pause its source**, so there's nowhere to keep the value.

- This matters with custom subscribers, `flatMap(maxPublishers:)`, and `.values` async loops (see Q101).
- Add a `buffer` if values must not be lost.

```swift
let subject = PassthroughSubject<Int, Never>()

subject
    .flatMap(maxPublishers: .max(1)) { value in
        Just(value).delay(for: .seconds(1), scheduler: DispatchQueue.main)   // slow work
    }
    .sink { print($0) }
    .store(in: &cancellables)

subject.send(1)   // processed
subject.send(2)   // dropped: flatMap is busy and has no demand
```

**Follow-ups:**
- **Why doesn't `sink` lose values?** It asks for unlimited demand.
- **How does `buffer` fix it?** It keeps values until the downstream asks for them.
- **Do cold publishers lose values like this?** No, they wait for demand before producing values.

## 13. Type Erasure

### Q72. Why use `eraseToAnyPublisher()`? `[Fundamental]`
`eraseToAnyPublisher()` **hides a pipeline's long, complicated type** behind a simple `AnyPublisher<Output, Failure>`, so you can **change the pipeline without changing your API**.

- Without it, the type looks like `Publishers.ReceiveOn<Publishers.Map<Publishers.Debounce<…>>>`.
- It also stops callers from casting back to a subject to call `send`.

```swift
protocol WeatherService {
    func forecast(for city: String) -> AnyPublisher<Forecast, WeatherError>   // simple, stable type
}

func forecast(for city: String) -> AnyPublisher<Forecast, WeatherError> {
    api.request(forecastURL(city))
        .decode(type: Forecast.self, decoder: JSONDecoder())
        .mapError { _ in WeatherError.unavailable }
        .eraseToAnyPublisher()                                                // hide the real type
}
```

**Follow-ups:**
- **Why does this matter for protocols?** A protocol needs one type that any implementation can return.
- **Does it change behavior?** No, only the visible type.
- **Is there a modern alternative?** `some Publisher<Output, Failure>` (see Q73).

### Q73. What does type erasure cost, and what are the alternatives? `[Lead/Expert]`
Type erasure has a **small runtime cost** (extra wrapping and indirect calls) that rarely matters, and since Swift 5.7 you can return **`some Publisher<Output, Failure>`** to hide the type **without erasing it**.

- Avoid erasing inside very hot loops.
- `AnyPublisher` is still the right choice in **protocols** and **stored properties**.

```swift
func searchResults(for query: String) -> some Publisher<[Movie], Never> {   // hidden but not erased
    api.search(query).replaceError(with: [])
}
```

**Follow-ups:**
- **Why can't a protocol requirement use `some Publisher`?** Each implementation could return a different type, and the protocol can't express that.
- **Is the cost noticeable in apps?** Almost never.
- **What made `some Publisher<…>` possible?** Primary associated types in Swift 5.7.

### Q74. What are `AnySubscriber` and `AnyCancellable`? `[Senior]`
`AnySubscriber` **hides a subscriber's real type** (useful inside custom publishers), and `AnyCancellable` **hides a cancellable's type and cancels automatically when released**.

- Wrap any `Cancellable` in `AnyCancellable(...)` to get the auto-cancel behavior.

```swift
// Inside a custom publisher: store any kind of subscriber
let stored = AnySubscriber(subscriber)

// Turn any Cancellable into one that cancels when released
let connection = publisher.makeConnectable().connect()
let autoCancel = AnyCancellable(connection)
```

**Follow-ups:**
- **Where do you see `AnySubscriber`?** In custom publishers and subscriptions (see Q90).
- **Why is auto-cancel useful?** You don't need to remember to cancel in `deinit`.
- **What's the difference between `Cancellable` and `AnyCancellable`?** `Cancellable` is a protocol. `AnyCancellable` is a class that also cancels on release.

## 14. Networking with Combine

### Q75. Write a generic API client using Combine. `[Senior]`
Use **`dataTaskPublisher`**, **check the status code** in `tryMap`, **decode** the data, **convert errors** into your own `APIError`, and **return `AnyPublisher<T, APIError>`**.

- No `receive(on:)` here: the client shouldn't choose the caller's thread. The view model adds `receive(on: DispatchQueue.main)`.

```swift
enum APIError: Error {
    case invalidResponse
    case httpStatus(Int)
    case decoding(Error)
    case network(URLError)
    case unknown(Error)
}

struct APIClient {
    var session: URLSession = .shared
    var decoder = JSONDecoder()

    func request<T: Decodable>(_ url: URL, as type: T.Type = T.self) -> AnyPublisher<T, APIError> {
        session.dataTaskPublisher(for: url)
            .tryMap { output in                                   // 1. check the response
                guard let http = output.response as? HTTPURLResponse else {
                    throw APIError.invalidResponse
                }
                guard (200..<300).contains(http.statusCode) else {
                    throw APIError.httpStatus(http.statusCode)
                }
                return output.data
            }
            .decode(type: T.self, decoder: decoder)               // 2. decode
            .mapError { error in                                   // 3. convert errors
                switch error {
                case let apiError as APIError: return apiError
                case let urlError as URLError: return .network(urlError)
                case is DecodingError: return .decoding(error)
                default: return .unknown(error)
                }
            }
            .eraseToAnyPublisher()
    }
}
```

**Follow-ups:**
- **How would you test this client?** Inject a `URLSession` with a custom `URLProtocol` that returns fake responses.
- **Where would you add an auth token?** Build a `URLRequest` with the header before calling `dataTaskPublisher`.
- **Why keep `receive(on:)` out of the client?** Different callers may want different threads.

### Q76. How do you chain dependent requests? `[Fundamental]`
Use **`flatMap`**: when the first request finishes, use its result to **start the second request**.

```swift
func loadDashboard(userID: Int) -> AnyPublisher<Dashboard, APIError> {
    api.request(userURL(userID), as: User.self)
        .flatMap { user in                                       // after the user loads…
            api.request(ordersURL(user.accountID), as: [Order].self)
                .map { orders in Dashboard(user: user, orders: orders) }   // …load their orders
        }
        .eraseToAnyPublisher()
}
```

**Follow-ups:**
- **What happens if the first request fails?** The second never starts, and the error is passed on.
- **What's the async/await version?** `let user = try await …` then `let orders = try await …`.
- **Why `map` inside the `flatMap`?** To combine the user and orders into one result.

### Q77. How do you run requests in parallel and combine results? `[Senior]`
For a **fixed number** of requests, use **`zip`**. For a **changing number**, use **`MergeMany` + `collect`**.

- With `zip`, **one failure fails everything**. To allow partial success, turn each request's errors into a `Result` first.

```swift
// Fixed number: zip runs all three at the same time
api.request(profileURL, as: Profile.self)
    .zip(api.request(settingsURL, as: Settings.self),
         api.request(notificationsURL, as: [AppNotification].self))
    .map { profile, settings, notifications in
        HomeScreenData(profile: profile, settings: settings, notifications: notifications)
    }

// Dynamic number: MergeMany + collect (see Q42 for keeping the order)
Publishers.MergeMany(ids.map { api.request(itemURL($0), as: Item.self) })
    .collect()
```

**Follow-ups:**
- **How do you allow partial success?** Map each request to `Result<T, Error>` and replace errors with `.failure`.
- **Do `zip` requests run at the same time?** Yes, all start when you subscribe.
- **What's the async/await equivalent?** `async let` for a fixed number, a task group for a changing number.

### Q78. How do you poll an endpoint periodically? `[Senior]`
Use a **timer publisher**, **start a request on each tick** (with errors handled inside), and use **`switchToLatest`** so a slow request is dropped when the next tick comes.

- Stop polling by cancelling the subscription, or with `prefix(while:)` when a condition is met.

```swift
Timer.publish(every: 30, on: .main, in: .common)
    .autoconnect()
    .prepend(Date())                                     // also fire right away
    .map { _ in
        api.request(statusURL, as: OrderStatus.self)
            .map(Optional.some)
            .replaceError(with: nil)                    // errors don't stop polling
    }
    .switchToLatest()                                    // drop a slow request if the next tick comes
    .compactMap { $0 }
    .removeDuplicates()
    .receive(on: DispatchQueue.main)
    .sink { [weak self] status in self?.render(status) }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why `prepend(Date())`?** So the first request happens immediately, not after 30 seconds.
- **How do you stop when the order is delivered?** Add `.prefix(while: { $0 != .delivered })`.
- **Should you poll in the background?** No. Stop when the screen disappears, and consider push notifications instead.

### Q79. How do you make sure requests are cancelled when the screen goes away? `[Fundamental]`
**Store the subscriptions in the screen's view model or view controller**, so when it's released, the subscriptions **cancel automatically**, which also cancels the network task.

- Avoid strong `self` in `sink`. It would keep the object (and its requests) alive after the screen closes.

```swift
final class OrderViewModel {
    private var cancellables = Set<AnyCancellable>()      // released with the view model

    func load() {
        api.request(orderURL, as: Order.self)
            .receive(on: DispatchQueue.main)
            .sink(receiveCompletion: { _ in },
                  receiveValue: { [weak self] in self?.order = $0 })   // weak: no cycle
            .store(in: &cancellables)
    }
}
// Screen closes → view model released → cancellables released → request cancelled
```

**Follow-ups:**
- **How can you check the request was cancelled?** Add `handleEvents(receiveCancel:)` and log it.
- **What if the view model is shared and lives longer?** Then cancel explicitly when the screen disappears.
- **Does cancelling a request save data or battery?** Yes, the network task stops.

## 15. Combine with UIKit

### Q80. How do you bind a view model to a UIKit view controller with Combine? `[Senior]`
**Inputs:** send UI events (text changes) **into** the view model. **Outputs:** subscribe to the view model's `@Published` properties and **update the UI on the main thread**.

```swift
final class LoginViewController: UIViewController {
    private let viewModel = LoginViewModel()
    private var cancellables = Set<AnyCancellable>()
    private let emailField = UITextField()
    private let passwordField = UITextField()
    private let loginButton = UIButton(configuration: .filled())
    private let errorLabel = UILabel()

    override func viewDidLoad() {
        super.viewDidLoad()
        bindInputs()
        bindOutputs()
    }

    private func bindInputs() {                                      // UI → view model
        NotificationCenter.default.publisher(for: UITextField.textDidChangeNotification, object: emailField)
            .compactMap { ($0.object as? UITextField)?.text }
            .assign(to: \.email, on: viewModel)     // retains the view model, which doesn't own us: no cycle
            .store(in: &cancellables)

        NotificationCenter.default.publisher(for: UITextField.textDidChangeNotification, object: passwordField)
            .compactMap { ($0.object as? UITextField)?.text }
            .assign(to: \.password, on: viewModel)
            .store(in: &cancellables)
    }

    private func bindOutputs() {                                     // view model → UI
        viewModel.$isLoginEnabled
            .receive(on: DispatchQueue.main)
            .assign(to: \.isEnabled, on: loginButton)
            .store(in: &cancellables)

        viewModel.$errorMessage
            .receive(on: DispatchQueue.main)
            .sink { [weak self] message in
                self?.errorLabel.text = message
                self?.errorLabel.isHidden = message == nil
            }
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **Why is `assign(to:on: viewModel)` safe here?** The view model doesn't own the view controller, so there's no cycle.
- **Why bind in `viewDidLoad`?** It runs once, so bindings aren't duplicated.
- **How would you test the bindings?** Test the view model's logic directly. The binding code itself stays thin.

### Q81. How do you get a publisher for UIControl events? `[Senior]`
UIKit **doesn't give you publishers for controls**, so you use **notifications** (for text fields), a **subject fed by `UIAction`**, or a **custom publisher**.

- Options: `NotificationCenter` for text fields, a `PassthroughSubject` with `UIAction`, a custom publisher (Q90), or a library like CombineCocoa.

```swift
let saveTapped = PassthroughSubject<Void, Never>()
saveButton.addAction(UIAction { _ in saveTapped.send(()) }, for: .touchUpInside)

saveTapped
    .throttle(for: .seconds(1), scheduler: DispatchQueue.main, latest: false)   // no double taps
    .sink { [weak self] in self?.viewModel.save() }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why use `UIAction` instead of target-action?** It's closure-based and simple to connect to a subject.
- **When is a custom publisher better?** When you want a reusable `control.publisher(for: .valueChanged)` API.
- **What's the downside of a library?** One more dependency to maintain.

### Q82. How do you handle keyboard notifications with Combine? `[Senior]`
**Turn the keyboard show and hide notifications into heights**, **merge** them into one stream, and update your layout from it.

- On iOS 15+, `keyboardLayoutGuide` often removes the need for this.

```swift
let willShow = NotificationCenter.default.publisher(for: UIResponder.keyboardWillShowNotification)
    .compactMap { ($0.userInfo?[UIResponder.keyboardFrameEndUserInfoKey] as? NSValue)?.cgRectValue.height }

let willHide = NotificationCenter.default.publisher(for: UIResponder.keyboardWillHideNotification)
    .map { _ in CGFloat(0) }

willShow.merge(with: willHide)
    .removeDuplicates()

        self?.scrollView.contentInset.bottom = height
    }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why `merge`?** Both streams produce a `CGFloat`, so one stream of heights is simpler.
- **What does `keyboardLayoutGuide` do?** Lets Auto Layout follow the keyboard, with no notification code.
- **How would you animate the change?** Read the animation duration from the notification and animate inside `sink`.

## 16. Combine with SwiftUI

### Q83. How do `ObservableObject` and `@Published` relate to Combine? `[Fundamental]`
`ObservableObject` gives SwiftUI an **`objectWillChange` publisher**, and every **`@Published` change fires it before the change**, which makes SwiftUI redraw. `@Published` also gives you **`$property` publishers** for your own pipelines.

```swift
final class SettingsStore: ObservableObject {
    @Published var username = ""
    @Published private(set) var isUsernameAvailable = true

    init(api: UsernameAPI) {
        $username                                                  // a Combine publisher
            .debounce(for: .milliseconds(400), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { name in api.isAvailable(name).replaceError(with: false) }
            .switchToLatest()
            .receive(on: DispatchQueue.main)
            .assign(to: &$isUsernameAvailable)
    }
}
```

**Follow-ups:**
- **Why "will" change, not "did" change?** So SwiftUI can prepare before the new value is set.
- **What's the iOS 17 replacement?** `@Observable`, which doesn't use Combine (see Q86).
- **Does any `@Published` change redraw every view watching the object?** Yes, which is a performance downside compared with `@Observable`.

### Q84. How do you subscribe to a publisher inside a SwiftUI view? `[Fundamental]`
Use **`.onReceive(publisher)`**, and the closure runs **every time the publisher sends a value**.

- Make sure the publisher sends on the main thread (add `receive(on:)` upstream).
- **Don't create new publishers inside `body`**. They'd be re-subscribed on every redraw.

```swift
struct OrderStatusView: View {
    let statusUpdates: AnyPublisher<OrderStatus, Never>
    @State private var status: OrderStatus = .pending

    var body: some View {
        Text(status.description)
            .onReceive(statusUpdates) { newStatus in     // runs for each new value
                status = newStatus
            }
    }
}
```

**Follow-ups:**
- **Why not create the publisher in `body`?** `body` runs often, so the subscription would restart each time.
- **What's the async alternative?** `.task { for await value in publisher.values { … } }`.
- **Does `onReceive` need a cancellable?** No. SwiftUI manages it for the view's lifetime.

### Q85. When would you call `objectWillChange.send()` manually? `[Senior]`
When your `ObservableObject` has **state that isn't `@Published`**, like data inside a legacy object, and you need **SwiftUI to refresh** after it changes.

```swift
final class LegacyBridge: ObservableObject {
    private let manager: LegacyManager

    init(manager: LegacyManager) { self.manager = manager }

    var items: [Item] { manager.items }      // not @Published

    func reload() {
        objectWillChange.send()               // tell SwiftUI a change is coming
        manager.reload()
    }
}
```

**Follow-ups:**
- **Should you call it before or after the change?** Before, which is what "will change" means. `@Published` does the same.
- **What if you forget it?** The view shows stale data until something else triggers a redraw.
- **Is there an `@Observable` equivalent?** With `@Observable`, stored properties are tracked automatically. For outside data, use `access` and `withMutation` in the model.

### Q86. With `@Observable` (iOS 17+), where does Combine fit in SwiftUI? `[Lead/Expert]`
`@Observable` models **don't use Combine** and have **no `$property` publishers**, so in SwiftUI Combine moves to **services and data layers**, and pipelines on model properties need a small **bridge**.

- **Bridges:** `didSet` feeding a private subject, `withObservationTracking`, Swift 6.2's `Observations` async sequence, or async code like `.task(id:)` for debouncing.
- Combine is still useful for streams from sockets, sensors, and legacy APIs.

```swift
@Observable
final class SearchModel {
    var query = "" {
        didSet { querySubject.send(query) }      // bridge property changes into Combine
    }
    private(set) var results: [Movie] = []

    @ObservationIgnored private let querySubject = PassthroughSubject<String, Never>()
    @ObservationIgnored private var cancellables = Set<AnyCancellable>()

    init(api: MovieAPI) {
        querySubject
            .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { api.search($0).replaceError(with: []) }
            .switchToLatest()
            .receive(on: DispatchQueue.main)
            .sink { [weak self] in self?.results = $0 }
            .store(in: &cancellables)
    }
}
```

**Follow-ups:**
- **Why `@ObservationIgnored` on the subject?** It's internal plumbing, so it shouldn't trigger view updates.
- **What's the pure-SwiftUI way to debounce?** `.task(id: query)` with a short `Task.sleep`.
- **What does Swift 6.2's `Observations` do?** Turns property changes into an async sequence of values.

### Q87. What is the best way to run a timer in SwiftUI? `[Senior]`
**`TimelineView`** for display updates, or a **`.task` loop with `Task.sleep`**, which **stops automatically**. `Timer.publish` with `.onReceive` works but can restart when the view is recreated.

```swift
// Display updates every second
TimelineView(.periodic(from: .now, by: 1)) { context in
    Text(context.date, style: .time)
}

// Work every second, cancelled when the view disappears
.task {
    while !Task.isCancelled {
        await model.refresh()
        try? await Task.sleep(for: .seconds(1))
    }
}
```

**Follow-ups:**
- **Why can `Timer.publish` stored on a view restart?** The view struct is recreated, so a new timer publisher may be created.
- **When is `TimelineView` the right choice?** When you only need to redraw on a schedule, like a clock.
- **Why is the `.task` loop safe?** It's cancelled automatically when the view goes away.

## 17. Custom Publishers, Subscribers & Operators

### Q88. How do you write a custom operator? `[Senior]`
Write an **extension on `Publisher`** that **combines existing operators** into one reusable step, which is the safest and most common way.

```swift
extension Publisher where Output == String, Failure == Never {
    /// Cleans up and debounces text input for search
    func searchQuery<S: Scheduler>(
        debounce interval: S.SchedulerTimeType.Stride,
        scheduler: S,
        minimumLength: Int = 2
    ) -> AnyPublisher<String, Never> {
        self
            .debounce(for: interval, scheduler: scheduler)
            .map { $0.trimmingCharacters(in: .whitespacesAndNewlines) }
            .removeDuplicates()
            .filter { $0.count >= minimumLength }
            .eraseToAnyPublisher()
    }
}

extension Publisher {
    /// Sends (previous, current) pairs
    func withPrevious() -> AnyPublisher<(previous: Output?, current: Output), Failure> {
        scan((previous: Output?.none, current: Output?.none)) { state, new in
            (previous: state.current, current: new)
        }
        .compactMap { state in state.current.map { (previous: state.previous, current: $0) } }
        .eraseToAnyPublisher()
    }
}

// Usage
$query.searchQuery(debounce: .milliseconds(300), scheduler: DispatchQueue.main)
$selectedTab.withPrevious().sink { print("from \(String(describing: $0.previous)) to \($0.current)") }
```

**Follow-ups:**
- **Why build on existing operators?** They already follow Combine's rules, so you can't break the contract by accident.
- **Why constrain with `where Output == String`?** So the operator only appears on publishers it makes sense for.
- **How would you test `withPrevious()`?** Feed `[1, 2, 3].publisher` and check the pairs `(nil, 1)`, `(1, 2)`, `(2, 3)`.

### Q89. When should you write a custom `Publisher` instead of composing operators? `[Lead/Expert]`
Only when you're **wrapping an event source that has no publisher** (like `UIControl` events or a C callback API) and a **subject isn't enough**, for example because each subscriber needs its own setup and cleanup.

- A correct custom publisher must: respect demand, send events one at a time, stop after completion or cancel, and clean up on cancel.
- That's easy to get wrong, so prefer existing publishers, `Deferred`, `Future`, or subjects when you can.

```swift
// Usually enough: a subject wrapped by a small type
final class ShakeDetector {
    private let subject = PassthroughSubject<Void, Never>()
    var shakes: AnyPublisher<Void, Never> { subject.eraseToAnyPublisher() }
    func deviceDidShake() { subject.send(()) }    // called from motion events
}
// Write a full custom Publisher only if each subscriber needs its own setup/teardown (see Q90)
```

**Follow-ups:**
- **What is "per-subscriber setup"?** Each subscriber gets its own resources, like its own observer, that start and stop with it.
- **What's the most common bug in custom publishers?** Sending values without demand, or after cancel.
- **What's a safer middle ground?** A subject plus `handleEvents(receiveSubscription:receiveCancel:)` to start and stop the source.

### Q90. Implement a custom publisher for UIControl events. `[Lead/Expert]`
Create a **`Publisher`** that, for each subscriber, makes a **`Subscription`** object which **adds itself as the control's target**, **sends the control only when there's demand**, and **removes itself on cancel**.

- The subscriber (the `sink`'s cancellable) keeps the subscription alive, and the control holds the target weakly, so there's no retain cycle.

```swift
import Combine
import UIKit

extension UIControl {
    struct EventPublisher: Publisher {
        typealias Output = UIControl
        typealias Failure = Never

        let control: UIControl
        let events: UIControl.Event

        func receive<S: Subscriber>(subscriber: S) where S.Input == UIControl, S.Failure == Never {
            let subscription = EventSubscription(
                subscriber: AnySubscriber(subscriber),
                control: control,
                events: events
            )
            subscriber.receive(subscription: subscription)        // hand over the subscription
        }
    }

    final class EventSubscription: NSObject, Subscription {
        private var subscriber: AnySubscriber<UIControl, Never>?
        private weak var control: UIControl?
        private var demand: Subscribers.Demand = .none

        init(subscriber: AnySubscriber<UIControl, Never>, control: UIControl, events: UIControl.Event) {
            self.subscriber = subscriber
            self.control = control
            super.init()
            control.addTarget(self, action: #selector(handleEvent), for: events)   // listen for events
        }

        func request(_ demand: Subscribers.Demand) {
            self.demand += demand                                  // remember how many are wanted
        }

        func cancel() {
            control?.removeTarget(self, action: #selector(handleEvent), for: .allEvents)   // clean up
            subscriber = nil
        }

        @objc private func handleEvent() {
            guard let control, let subscriber, demand > 0 else { return }   // respect demand
            demand -= 1
            demand += subscriber.receive(control)
        }
    }

    func publisher(for events: UIControl.Event) -> EventPublisher {
        EventPublisher(control: self, events: events)
    }
}

// Usage
slider.publisher(for: .valueChanged)
    .compactMap { ($0 as? UISlider)?.value }
    .sink { print("Slider: \($0)") }
    .store(in: &cancellables)
```

**Follow-ups:**
- **Why check `demand > 0`?** The Combine contract says never send more than the subscriber asked for.
- **Why does cancel set `subscriber = nil`?** So no events are sent after cancelling, and the subscriber can be released.
- **Why is `control` weak?** So the subscription doesn't keep the control alive.

### Q91. How do you wrap a delegate-based API in Combine? `[Senior]`
Make the wrapper the **delegate**, **forward delegate callbacks into a subject**, expose it as `AnyPublisher`, and **start and stop the underlying work** when someone subscribes or cancels.

- With several subscribers, one cancelling would stop updates for everyone. Add reference counting or `share()` in production.
- On iOS 17+, `CLLocationUpdate.liveUpdates()` gives an async sequence instead.

```swift
final class LocationPublisher: NSObject, CLLocationManagerDelegate {
    private let manager = CLLocationManager()
    private let subject = PassthroughSubject<CLLocation, Error>()

    var locations: AnyPublisher<CLLocation, Error> {
        subject
            .handleEvents(
                receiveSubscription: { [weak self] _ in self?.manager.startUpdatingLocation() },  // start
                receiveCancel: { [weak self] in self?.manager.stopUpdatingLocation() }           // stop
            )
            .eraseToAnyPublisher()
    }

    override init() {
        super.init()
        manager.delegate = self
    }

    func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
        locations.forEach { subject.send($0) }               // delegate → subject
    }

    func locationManager(_ manager: CLLocationManager, didFailWithError error: Error) {
        subject.send(completion: .failure(error))
    }
}
```

**Follow-ups:**
- **What happens with two subscribers and one cancels?** Location updates stop for both. Use `share()` or count subscribers.
- **Why `[weak self]` in `handleEvents`?** The publisher shouldn't keep the wrapper alive.
- **What's the modern alternative?** `CLLocationUpdate.liveUpdates()`, an async sequence (iOS 17).

## 18. Testing Combine

### Q92. How do you test a synchronous Combine pipeline? `[Fundamental]`
If nothing in the pipeline **changes threads or waits for time**, values arrive **immediately**, so you can **collect them in an array and check right away**, with no expectations needed.

```swift
final class SignUpViewModelTests: XCTestCase {
    func testFormBecomesValidWhenAllFieldsAreCorrect() {
        let viewModel = SignUpViewModel()
        var values: [Bool] = []
        let cancellable = viewModel.$isValid.sink { values.append($0) }   // collect values

        viewModel.email = "ana@example.com"
        viewModel.password = "password1"
        viewModel.confirmPassword = "password1"

        XCTAssertEqual(values, [false, true])                              // check right away
        cancellable.cancel()
    }
}
```

**Follow-ups:**
- **Why does the first value appear as `false`?** `@Published` sends its current value when you subscribe.
- **What breaks this approach?** `receive(on:)`, `debounce`, or other async steps in the pipeline.
- **Why cancel at the end?** To clean up. The subscription would also end when the test finishes.

### Q93. How do you test asynchronous publishers with expectations? `[Fundamental]`
Create an **`XCTestExpectation`**, **fulfill it in `sink`** when the value arrives, and **wait** for it.

- It works, but real waiting makes tests **slow and possibly flaky**. Prefer injected schedulers (see Q94).

```swift
func testSearchPublishesResults() {
    let viewModel = MovieSearchViewModel(api: MockMovieAPI(results: [.sample]))
    let expectation = expectation(description: "Results published")
    var cancellables = Set<AnyCancellable>()

    viewModel.$results
        .dropFirst()                          // skip the starting empty array
        .sink { results in
            XCTAssertEqual(results, [.sample])
            expectation.fulfill()
        }
        .store(in: &cancellables)

    viewModel.query = "Dune"
    wait(for: [expectation], timeout: 1)      // really waits for the 300 ms debounce
}
```

**Follow-ups:**
- **Why are these tests flaky?** A busy CI machine can be slower than the timeout.
- **Why `dropFirst()`?** To skip the empty starting value from `@Published`.
- **What's the better approach?** A test scheduler, so time is controlled, not waited for.

### Q94. How do you test time-based operators deterministically? `[Lead/Expert]`
**Inject the scheduler** into your type: pass `DispatchQueue.main` in the app and a **test scheduler** in tests, then **move time forward yourself**.

- Point-Free's `CombineSchedulers` library provides `DispatchQueue.test`.
- The test runs **instantly** and **never flakes**, which is a strong sign of senior testing practice.

```swift
import CombineSchedulers

func testSearchWaitsForDebounce() {
    let scheduler = DispatchQueue.test
    let viewModel = MovieSearchViewModel(api: MockMovieAPI(results: [.sample]), scheduler: scheduler)

    viewModel.query = "Dune"

    scheduler.advance(by: .milliseconds(299))
    XCTAssertTrue(viewModel.results.isEmpty)        // still waiting

    scheduler.advance(by: .milliseconds(1))
    XCTAssertEqual(viewModel.results, [.sample])    // debounce fired
}
```

**Follow-ups:**
- **Why does this need the scheduler injected?** Otherwise the code uses real time, which the test can't control.
- **What is `AnySchedulerOf<DispatchQueue>`?** A type-erased scheduler from the same library, handy for stored properties.
- **Can you write a test scheduler yourself?** Yes, but the library is well tested and saves time.

### Q95. How do you test publishers with Swift Testing? `[Senior]`
For **finite, cold** publishers, loop over **`.values`** with `for try await`. Cold publishers wait for demand, so **no values are lost**.

- For **hot** sources (subjects, `@Published`), collect values in a `sink` instead. `.values` can drop values sent while the test isn't waiting (see Q101).

```swift
import Testing

struct ItemRepositoryTests {
    @Test func emitsCachedThenFreshItems() async throws {
        let repository = ItemRepository(
            cache: MockCache(items: [.cached]),
            api: MockItemAPI(items: [.fresh])          // returns Just(...).setFailureType(to: Error.self)
        )

        var received: [[Item]] = []
        for try await items in repository.items().values {   // repository uses .prepend(cache)
            received.append(items)
        }

        #expect(received == [[.cached], [.fresh]])
    }
}
```

**Follow-ups:**
- **When does the `for await` loop end?** When the publisher finishes.
- **What if the publisher never finishes?** The test hangs. Add `.prefix(n)` or `.first()`.
- **Why are hot sources a problem?** Values sent while the loop is busy have no demand and are dropped.

### Q96. How do you mock publisher-based dependencies? `[Senior]`
Put the dependency behind a **protocol that returns publishers**, and write mocks that return **`Just`/`Fail`** for instant results, or a **subject** when the test needs to **control the timing**.

- The controllable mock lets you check in-between states (like `isLoading == true`) and that old requests are ignored.

```swift
protocol MovieAPI {
    func search(_ query: String) -> AnyPublisher<[Movie], Error>
}

// Instant result
struct MockMovieAPI: MovieAPI {
    var results: [Movie] = []
    var error: Error?

    func search(_ query: String) -> AnyPublisher<[Movie], Error> {
        if let error {
            return Fail(error: error).eraseToAnyPublisher()
        }
        return Just(results).setFailureType(to: Error.self).eraseToAnyPublisher()
    }
}

// Controllable timing: the test sends responses when it wants
final class ControllableMovieAPI: MovieAPI {
    let responses = PassthroughSubject<[Movie], Error>()
    private(set) var queries: [String] = []

    func search(_ query: String) -> AnyPublisher<[Movie], Error> {
        queries.append(query)
        return responses.eraseToAnyPublisher()
    }
}
```

**Follow-ups:**
- **How do you test that old searches are ignored?** Start two searches, send a response, and check only the latest result shows.
- **Why record `queries`?** To check debounce and `removeDuplicates` sent the right searches.
- **Why return `AnyPublisher` in the protocol?** So mocks and real code can return different publisher types.

## 19. Combine & Swift Concurrency

### Q97. Compare Combine and async/await. `[Senior]`
Combine is best for **streams of values over time** and reactive bindings, while async/await is best for **one-shot async work** and **easy-to-read code**, and it's where Apple is investing now.

| | Combine | Swift Concurrency |
|---|---|---|
| Best at | Streams over time, bindings, timing operators | One-shot async work, structured tasks |
| Style | Chains of operators | Normal-looking code with `await` |
| Cancellation | `AnyCancellable` lifetime | Structured task cancellation |
| Thread safety | Schedulers, not `Sendable`-annotated | Actors, `Sendable`, compile-time data race checks |
| Errors | Typed `Failure`, errors end streams | `throws` (typed throws in Swift 6) |
| Debugging | Long types, hard stack traces | Linear code, easier to read |
| Apple's investment | Stable, almost no new features | Actively evolving |

- **Senior answer:** new async code should usually use Swift Concurrency. Combine is still a good fit for complex event streams and existing reactive code. Know how to connect them.

```swift
// Combine
api.fetchUser().sink(receiveCompletion: { _ in }, receiveValue: { print($0) }).store(in: &cancellables)

// async/await
let user = try await api.fetchUser()
print(user)
```

**Follow-ups:**
- **When would you still pick Combine?** For complex timing logic across many event sources, like debounce + combineLatest + switchToLatest.
- **What does async/await do better?** Readability, cancellation, and Swift 6 safety checks.
- **Can you mix them?** Yes, at clear boundaries (see Q104).

### Q98. How do you consume a publisher with async/await? `[Senior]`
Every publisher has a **`.values` property** (iOS 15+) that turns it into an **async sequence**, which you read with **`for await`** (or `for try await` if it can fail).

```swift
// Failure == Never → AsyncPublisher
Task {
    for await isOnline in reachability.$isOnline.values {
        banner.isHidden = isOnline
    }
}

// Failure: Error → AsyncThrowingPublisher
Task {
    do {
        for try await message in socket.messages.values {
            handle(message)
        }
    } catch {
        showError(error)
    }
}
```

**Follow-ups:**
- **When does the loop end?** When the publisher finishes, fails, or the task is cancelled.
- **Does cancelling the `Task` cancel the subscription?** Yes.
- **What's the catch with hot publishers?** Values can be dropped while the loop body runs (see Q101).

### Q99. How do you await a single value from a publisher? `[Senior]`
Loop over **`.values`** and **return the first value**. Leaving the loop **cancels the subscription**.

```swift
extension Publisher {
    func firstValue() async throws -> Output {
        for try await value in values {
            return value                   // leaving the loop cancels the subscription
        }
        throw PublisherError.finishedWithoutValue
    }
}

enum PublisherError: Error { case finishedWithoutValue }

// Usage
let user = try await api.fetchUser(id: 42).firstValue()
```

**Follow-ups:**
- **What if the publisher finishes without a value?** It throws `finishedWithoutValue`.
- **Is this good for migrating old code?** Yes, new async code can call old publisher-based APIs this way.
- **What if the publisher never sends?** The `await` waits forever, so add a timeout if that's possible.

### Q100. How do you expose an async function as a publisher? `[Senior]`
Wrap it in **`Deferred { Future { … } }`** and run the async work in a **`Task`** inside, calling the promise with the result.

- **Caveat 1:** cancelling the subscription does **not** cancel the inner `Task`. The work continues, and its result is thrown away. Full cancellation needs a custom publisher.
- **Caveat 2:** in Swift 6 mode, capturing the non-`Sendable` `promise` in a `Task` may cause warnings.

```swift
func publisher<Output>(
    from operation: @escaping @Sendable () async throws -> Output
) -> AnyPublisher<Output, Error> {
    Deferred {                       // runs once per subscriber, only when subscribed
        Future { promise in
            Task {
                do { promise(.success(try await operation())) }
                catch { promise(.failure(error)) }
            }
        }
    }
    .eraseToAnyPublisher()
}

// Usage in a Combine pipeline
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .map { query in publisher { try await api.search(query) }.replaceError(with: []) }
    .switchToLatest()
```

**Follow-ups:**
- **Why `Deferred`?** Without it, the `Future` would start immediately, even with no subscriber.
- **Why does cancellation matter here?** With `switchToLatest`, old searches keep running in the background.
- **How would you make cancellation work?** A custom publisher that keeps the `Task` and calls `task.cancel()` on cancel.

### Q101. What is the gotcha with `.values` on hot publishers? `[Lead/Expert]`
`.values` asks for **one value at a time**, so a **hot source** like `PassthroughSubject` that sends while your loop is still busy has **no demand**, and those values are **dropped**.

- **Fix:** add `.buffer(...)` before `.values`, or use an `AsyncStream` with a buffering policy.

```swift
for await event in eventSubject
    .buffer(size: 50, prefetch: .byRequest, whenFull: .dropOldest)   // keep up to 50 waiting
    .values {
    await process(event)   // slow work no longer loses events
}
```

**Follow-ups:**
- **Why don't cold publishers have this problem?** They wait for demand before producing the next value.
- **How would you notice the bug?** Missing events, especially when processing is slow.
- **What's the AsyncStream alternative?** `AsyncStream(bufferingPolicy: .bufferingNewest(50))`.

### Q102. What are Swift Concurrency equivalents of common Combine features? `[Lead/Expert]`
Most Combine features have an async equivalent, often in Apple's **AsyncAlgorithms** package. The main gap is **multi-subscriber sharing**, which has no standard equivalent.

| Combine | Swift Concurrency / AsyncAlgorithms |
|---|---|
| `PassthroughSubject` | `AsyncStream` (one consumer) or `AsyncChannel` (AsyncAlgorithms) |
| `@Published` / `CurrentValueSubject` | `@Observable` properties, Swift 6.2 `Observations` |
| `debounce` | `debounce(for:)` (AsyncAlgorithms), or `.task(id:)` + `Task.sleep` in SwiftUI |
| `throttle` | `throttle` (AsyncAlgorithms) |
| `combineLatest`, `merge`, `zip` | Same-named functions in AsyncAlgorithms |
| `flatMap(maxPublishers:)` | `TaskGroup` with limited concurrency |
| `switchToLatest` | Cancel the previous `Task`, or `.task(id:)` |
| `Timer.publish` | `AsyncTimerSequence` (AsyncAlgorithms) or a `Task.sleep` loop |
| `retry` | A loop with `do/catch` |
| `share()` | No standard equivalent: needs custom code or a library |
| `AnyCancellable` | `Task` handles and structured cancellation |

```swift
import AsyncAlgorithms

for await query in queryStream.debounce(for: .milliseconds(300)) {   // like Combine's debounce
    results = try await api.search(query)
}
```

**Follow-ups:**
- **What is AsyncAlgorithms?** An open-source Apple package with async versions of operators like `debounce` and `combineLatest`.
- **Why is `AsyncStream` "one consumer"?** Each value goes to only one reader, unlike a subject that sends to all.
- **What's hardest to replace?** `share()`: sending one stream to many listeners.

### Q103. How would you migrate a Combine-heavy codebase to Swift Concurrency? `[Lead/Expert]`
**Don't rewrite everything**: move **one-shot calls** to async/await first, **bridge the two at boundaries**, **keep Combine where it's clearly better**, and migrate **step by step with tests**.

1. **Start with one-shot calls:** `AnyPublisher<T, Error>` → `async throws -> T` for network and database calls.
2. **Bridge:** new async callers use `.values` or `firstValue()`. Old Combine callers use a publisher adapter.
3. **UI layer:** `ObservableObject` + `@Published` → `@Observable` (iOS 17+), with `didSet`, `.task(id:)`, or async sequences replacing `$property` pipelines.
4. **Keep Combine** for complex timing-based streams until async code covers them cleanly.
5. **Order:** services first, then view models, then UI, and turn on Swift 6 checks one module at a time.
6. **Write tests first** for debounce and cancellation behavior, because it's easy to change by accident.

```swift
// Step 1: add an async version next to the old one
protocol UserService {
    func fetchUserPublisher(id: Int) -> AnyPublisher<User, Error>   // old, kept for now
    func fetchUser(id: Int) async throws -> User                     // new
}
```

**Follow-ups:**
- **Why not rewrite everything at once?** Too risky. Behavior like debounce timing is easy to break.
- **How do you measure progress?** Count remaining publisher-returning APIs per module.
- **What's a "characterization test"?** A test that records how the current code behaves, so you can check the new code matches.

### Q104. Is it a problem to mix Combine and async/await in one feature? `[Senior]`
**It's fine at clear boundaries**, like a Combine service read through `.values` in a `@MainActor` task, but **avoid switching back and forth** inside one pipeline.

- **Watch for:** lost cancellation when bridging (Q100), dropped values with `.values` on hot sources (Q101), and Swift 6 errors when Combine closures touch main-actor state (Q62).

```swift
// ✅ One clear boundary: Combine service, async consumer
@MainActor
func observeConnection() async {
    for await state in connectionService.statePublisher.values {
        banner.update(for: state)
    }
}
```

**Follow-ups:**
- **What does "ping-pong" look like?** Publisher → async → publisher → async inside one flow, which is hard to follow and to cancel.
- **Where should the boundary usually be?** At the service layer: services expose one style, and callers adapt once.
- **What's the risk of mixing without rules?** Hidden bugs in cancellation and threading.

## 20. Debugging

### Q105. How do you debug a Combine pipeline? `[Fundamental]`
Add **`.print()`** to log every event, **`handleEvents`** for custom logging, and **`breakpointOnError()`** or **`breakpoint`** to pause in the debugger.

```swift
api.search(query)
    .print("search")                     // logs subscribe, demand, values, completion, cancel
    .handleEvents(
        receiveSubscription: { _ in print("subscribed") },
        receiveOutput: { print("value: \($0.count) items") },
        receiveCompletion: { print("completion: \($0)") },
        receiveCancel: { print("cancelled") },
        receiveRequest: { print("demand: \($0)") }
    )
    .breakpointOnError()                 // pause in the debugger on failure
    .breakpoint(receiveOutput: { $0.isEmpty })   // pause when a condition is true
    .sink(receiveCompletion: { _ in }, receiveValue: { _ in })
    .store(in: &cancellables)
```

**Follow-ups:**
- **Where should you put `.print()`?** At several points, to see exactly where events stop.
- **Should these ship in production?** No. Remove them or wrap them in `#if DEBUG`.
- **What does the label in `.print("search")` do?** It prefixes each line, so you can tell pipelines apart.

### Q106. A pipeline "does nothing." What do you check? `[Senior]`
Go through a **checklist**, starting with the most common cause: **is the cancellable stored?**

1. Is the `AnyCancellable` **stored**? (The most common cause.)
2. Did the stream **fail or finish earlier** (for example, `catch` outside a `flatMap`)?
3. Did you subscribe to a **hot** source **after** it sent its value?
4. Is a `Future` giving an old saved result, or is `combineLatest` waiting for an input that never sent?
5. Is delivery delayed by `receive(on: RunLoop.main)` during scrolling, or a `debounce` that keeps restarting?
6. Is demand limited (custom subscriber, `flatMap(maxPublishers:)`)?

- Add `.print()` at several points to see where events stop.

```swift
// The #1 cause: the cancellable is thrown away
_ = api.fetchFeed().sink(receiveCompletion: { _ in }, receiveValue: { print($0) })   // ❌ nothing arrives

api.fetchFeed()
    .sink(receiveCompletion: { _ in }, receiveValue: { print($0) })
    .store(in: &cancellables)                                                          // ✅
```

**Follow-ups:**
- **How does `.print()` help here?** It shows whether you got "cancel" right away, which means the cancellable wasn't stored.
- **What does a `combineLatest` that never sends tell you?** One of its inputs hasn't sent a first value.
- **Why can a previous error cause this?** A failed stream is over, so later events go nowhere.

### Q107. How do you find Combine-related memory leaks? `[Senior]`
Look for **objects that never get released** or **subscriptions that keep firing after a screen closes**, then use the **Memory Graph Debugger**, **`deinit` logs**, and **leak tests** to find the cause.

- **Symptoms:** view models never released, events after a screen is closed, duplicate events after reopening a screen.
- **Usual causes:** strong `self` in `sink`, `assign(to:on: self)`, subscriptions stored in a long-lived singleton, cells not cancelling on reuse.

```swift
func testViewModelIsReleased() {
    var viewModel: FeedViewModel? = FeedViewModel(api: MockAPI())
    weak var weakViewModel = viewModel
    viewModel?.load()
    viewModel = nil
    XCTAssertNil(weakViewModel, "FeedViewModel leaked")     // fails if a sink captured self strongly
}
```

**Follow-ups:**
- **What do you look for in the Memory Graph?** Closures held by `Subscribers.Sink` that point back to your object.
- **Why do leaks cause duplicate events?** Old, leaked objects keep reacting alongside the new ones.
- **How do you prevent leaks in code review?** Check every `sink` for `[weak self]` and every `assign(to:on:)` target.

### Q108. Not storing the cancellable (async publisher) `[Fundamental]`
```swift
func load() {
    _ = URLSession.shared.dataTaskPublisher(for: url)
        .sink(receiveCompletion: { print("completion: \($0)") },
```

**Answer:** Nothing prints.

**Why:** The `AnyCancellable` is thrown away immediately, which cancels the request before it finishes.

**Follow-ups:**
- **How do you fix it?** Store it: `.store(in: &cancellables)` on an object that lives long enough.
- **Why no "completion" print either?** A cancelled subscription doesn't send a completion.

### Q109. Not storing the cancellable (synchronous publisher) `[Senior]`
```swift
_ = Just(5).sink { print($0) }
```
**Answer:** Prints `5`.

**Why:** `Just` sends its value immediately while subscribing, before the cancellable is thrown away. That's why "forgot to store it" bugs sometimes don't show up in simple tests.

**Follow-ups:**
- **Is this code still wrong?** As a habit, yes. With any async publisher it would print nothing.
- **Which other publishers behave like `Just` here?** Sequence publishers like `[1, 2, 3].publisher`.

### Q110. `catch` ends the stream `[Senior]`
```swift
enum DemoError: Error { case boom }
let subject = PassthroughSubject<Int, DemoError>()

subject
    .catch { _ in Just(-1) }
    .sink(receiveCompletion: { print("completion: \($0)") }, receiveValue: { print($0) })
    .store(in: &cancellables)

subject.send(1)
subject.send(completion: .failure(.boom))
subject.send(2)
```
**Answer:** `1`, `-1`, `completion: finished`.

**Why:** The original stream failed, `catch` replaced it with `Just(-1)`, and `Just` finished. The value `2` is never received.

**Follow-ups:**
- **Would `2` arrive if the subject hadn't failed?** Yes. Only the failure ended the stream.
- **How do you keep a long-lived stream alive?** Handle errors inside a `flatMap` (see Q51).

### Q111. `combineLatest` `[Fundamental]`
```swift
let a = PassthroughSubject<Int, Never>()
let b = PassthroughSubject<String, Never>()

a.combineLatest(b).sink { print($0) }.store(in: &cancellables)

a.send(1)
a.send(2)
b.send("x")
a.send(3)
b.send("y")
```
**Answer:** `(2, "x")`, `(3, "x")`, `(3, "y")`.

**Why:** Nothing is sent until both have a value. After that, every new value is paired with the other's latest value.

**Follow-ups:**
- **Why is `1` never printed?** By the time `b` sent its first value, `a`'s latest was already `2`.
- **How would you get a value immediately?** Use `CurrentValueSubject`s, which have starting values.

### Q112. `zip` `[Fundamental]`
```swift
// Same subjects and sends as Q111, but with zip:
a.zip(b).sink { print($0) }.store(in: &cancellables)
```
**Answer:** `(1, "x")`, `(2, "y")`.

**Why:** `zip` pairs values in order: first with first, second with second. `3` waits for a third string.

**Follow-ups:**
- **What happens to `3`?** It waits in `zip` until `b` sends a third value.
- **When is `zip` the right tool?** When values must be paired one-to-one, like two parallel requests.

### Q113. Late subscribers to subjects `[Fundamental]`
```swift
let current = CurrentValueSubject<Int, Never>(1)
let passthrough = PassthroughSubject<Int, Never>()

current.send(2)
passthrough.send(2)

current.sink { print("current: \($0)") }.store(in: &cancellables)
passthrough.sink { print("passthrough: \($0)") }.store(in: &cancellables)

current.send(3)
passthrough.send(3)
```
**Answer:** `current: 2`, `current: 3`, `passthrough: 3`.

**Why:** `CurrentValueSubject` gives new subscribers its current value (2). `PassthroughSubject` keeps nothing, so its 2 was lost.

**Follow-ups:**
- **Which one behaves like `@Published`?** `CurrentValueSubject`.
- **Why isn't `1` printed?** It was replaced by `2` before anyone subscribed.

### Q114. `Future` is eager `[Senior]`
```swift
let future = Future<Int, Never> { promise in
    print("Future started")
    promise(.success(42))
}
print("Before subscribing")
future.sink { print("A: \($0)") }.store(in: &cancellables)
future.sink { print("B: \($0)") }.store(in: &cancellables)
```
**Answer:** `Future started`, `Before subscribing`, `A: 42`, `B: 42`.

**Why:** The closure runs once, as soon as the `Future` is created. Both subscribers get the saved result.

**Follow-ups:**
- **How do you make it lazy?** Wrap it in `Deferred` (see Q115).
- **Why is this a problem with `retry`?** The work never runs again. Retry just gets the same saved result.

### Q115. `Deferred` + `Future` `[Senior]`
```swift
let deferred = Deferred {
    Future<Int, Never> { promise in
        print("Work started")
        promise(.success(42))
    }
}
print("Before subscribing")
deferred.sink { print("A: \($0)") }.store(in: &cancellables)
deferred.sink { print("B: \($0)") }.store(in: &cancellables)
```
**Answer:** `Before subscribing`, `Work started`, `A: 42`, `Work started`, `B: 42`.

**Why:** `Deferred` creates a new `Future` for each subscriber, so the work is lazy and runs once per subscriber.

**Follow-ups:**
- **How would you run the work once and share it?** Add `.share()` after `Deferred`.
- **Why is this version good for `retry`?** Each retry creates a fresh `Future`, so the work really runs again.

### Q116. Multiple subscribers to a cold publisher `[Senior]`
```swift
let pipeline = [1, 2, 3].publisher
    .handleEvents(receiveSubscription: { _ in print("subscribed") })
    .map { $0 * 2 }

pipeline.sink { print("A \($0)") }.store(in: &cancellables)
pipeline.sink { print("B \($0)") }.store(in: &cancellables)
```
**Answer:** `subscribed`, `A 2`, `A 4`, `A 6`, `subscribed`, `B 2`, `B 4`, `B 6`.

**Why:** Each subscriber runs the whole pipeline separately. With a network publisher, that would be two requests.

**Follow-ups:**
- **How do you run it only once?** Use `share()`, but watch out for Q117.
- **Is this bad for a sequence publisher?** No, it's cheap. It matters for expensive work like requests.

### Q117. `share()` with a synchronous upstream `[Lead/Expert]`
```swift
let shared = [1, 2, 3].publisher
    .handleEvents(receiveSubscription: { _ in print("subscribed") })
    .map { $0 * 2 }
    .share()

shared.sink { print("A \($0)") }.store(in: &cancellables)
shared.sink { print("B \($0)") }.store(in: &cancellables)
```
**Answer:** `subscribed`, `A 2`, `A 4`, `A 6`. B receives **nothing** (only the completion).

**Why:** The upstream ran and finished completely during A's subscription. Use `multicast` + `connect()` to attach all subscribers first.

**Follow-ups:**
- **Would this happen with a network request?** Only if B subscribes after the response arrives.
- **How does `multicast` fix it?** Nothing starts until `connect()`, so both subscribers are ready first (see Q65).

### Q118. An error terminates the stream `[Fundamental]`
```swift
struct BadValue: Error {}

[1, 2, 3].publisher
    .tryMap { value -> Int in
        if value == 2 { throw BadValue() }
        return value * 10
    }
    .sink(receiveCompletion: { print("completion: \($0)") }, receiveValue: { print($0) })
```

**Answer:** `10`, then `completion: failure(BadValue())`.

**Why:** The error at `2` ends the stream, so `3` is never processed.

**Follow-ups:**
- **How would you skip bad values instead?** Use `compactMap` and return `nil` for bad values.
- **How would you keep going after each error?** Process each value in its own `flatMap` with error handling inside.

### Q119. `reduce` on a never-ending publisher `[Senior]`
```swift
let subject = PassthroughSubject<Int, Never>()
subject.reduce(0, +).sink { print("reduce: \($0)") }.store(in: &cancellables)
subject.scan(0, +).sink { print("scan: \($0)") }.store(in: &cancellables)

subject.send(1)
subject.send(2)
```
**Answer:** `scan: 1`, `scan: 3`.

**Why:** `reduce` only sends when the stream **finishes**, and this subject never finishes. `scan` sends every step.

**Follow-ups:**
- **What would make `reduce` print?** `subject.send(completion: .finished)`. Then it prints `reduce: 3`.
- **Which one fits a running total in the UI?** `scan`.

### Q120. `removeDuplicates` `[Fundamental]`
```swift
[1, 1, 2, 2, 1, 3, 3].publisher
    .removeDuplicates()
    .sink { print($0) }
    .store(in: &cancellables)
```
**Answer:** `1`, `2`, `1`, `3`.

**Why:** Only **back-to-back** duplicates are removed. The second `1` isn't next to the first, so it stays.

**Follow-ups:**
- **How would you remove all duplicates?** Keep a `Set` of seen values and filter with it.
- **Why is "back-to-back only" useful?** For UI updates, you only want to skip a value that didn't change.

### Q121. `assign(to:on: self)` `[Senior]`
```swift
final class TitleViewModel {
    var title = ""
    private var cancellables = Set<AnyCancellable>()

    init(source: AnyPublisher<String, Never>) {
        source.assign(to: \.title, on: self).store(in: &cancellables)
    }

    deinit { print("deinit") }
}

let source = CurrentValueSubject<String, Never>("Hi")     // never completes
var viewModel: TitleViewModel? = TitleViewModel(source: source.eraseToAnyPublisher())
viewModel = nil
```
**Answer:** Nothing prints. `deinit` never runs.

**Why:** `assign(to:on:)` strongly keeps `self` alive until the publisher completes, and `self` owns the cancellable. The subject never completes, so it's a retain cycle.

**Follow-ups:**
- **How do you fix it?** Make `title` `@Published` and use `assign(to: &$title)`, or use `sink` with `[weak self]`.
- **Would it leak with `Just("Hi")` as the source?** No. `assign` lets go of the object when the publisher completes, and `Just` completes immediately, so `deinit` runs. The leak happens with sources that never complete, like subjects and `@Published`.

### Q122. `sink(receiveValue:)` on a failing publisher `[Fundamental]`
```swift
URLSession.shared.dataTaskPublisher(for: url)
    .sink { output in print(output.data.count) }
```
**Answer:** It doesn't compile.

**Why:** `sink(receiveValue:)` needs `Failure == Never`, but `dataTaskPublisher` can fail with `URLError`. Use `sink(receiveCompletion:receiveValue:)`, or handle the error first.

**Follow-ups:**
- **What's the quickest fix?** Add `receiveCompletion:` to handle errors.
- **Is `.replaceError(with:)` a good fix?** Only if a default value is truly acceptable.

### Q123. `RunLoop.main` while scrolling `[Lead/Expert]`
```swift
liveScores
    .receive(on: RunLoop.main)
    .sink { [weak self] in self?.scoreLabel.text = $0 }
    .store(in: &cancellables)
```
**Question:** What happens to score updates while the user is scrolling a table view?

**Answer:** They're delayed until scrolling stops.

**Why:** `RunLoop.main` runs work in the default mode, but during scrolling the run loop is in tracking mode. Use `DispatchQueue.main` for live updates.

**Follow-ups:**
- **Are the updates lost?** No, they arrive when scrolling stops.
- **When is this delay useful?** For work that shouldn't slow down scrolling, like loading images.

### Q124. `timeout` without a custom error `[Senior]`
```swift
slowPublisher       // never sends anything
    .timeout(.seconds(2), scheduler: DispatchQueue.main)
    .sink(receiveCompletion: { print("completion: \($0)") }, receiveValue: { print($0) })
    .store(in: &cancellables)
```
**Answer (after 2 seconds):** `completion: finished`.

**Why:** Without `customError`, a timeout finishes **successfully**, which can hide a failure. Pass `customError:` to fail instead.

**Follow-ups:**
- **How do you make it fail?** `.timeout(.seconds(2), scheduler: DispatchQueue.main, customError: { APIError.timeout })`.
- **Why is the silent finish dangerous?** The UI may treat it as "no data" instead of showing an error.

## 23. Senior / Lead Scenario Questions

### Q125. Should a new codebase use Combine in 2026? `[Lead/Expert]`
**Mostly no**: use **Swift Concurrency** for async work and **Observation** for SwiftUI state by default, and use **Combine only where it clearly helps**, like complex event streams.

- **Default:** Swift Concurrency and Observation. They're where Apple is investing, they have compile-time data race checks, and they're easier for new team members.
- **Use Combine for:** complex stream logic (debounce + combine + switch-to-latest across many sources), Combine-based SDKs, or a team with strong Combine experience.
- **Avoid:** mixing delegates, Combine, and async/await randomly. Write down when to use each.
- **Note:** Combine only runs on Apple platforms, which matters if you share code with server-side Swift on Linux.

```swift
// New default: async/await + Observation
@MainActor @Observable
final class FeedModel {
    private(set) var posts: [Post] = []
    func load() async throws { posts = try await api.fetchFeed() }
}
```

**Follow-ups:**
- **Is Combine deprecated?** No. It's stable and supported, but Apple adds almost nothing to it.
- **When would you still choose it for new code?** For timing-heavy streams that async code makes awkward.
- **How do you stop the team mixing styles?** A short written guideline, plus examples in the codebase.

### Q126. Your app has a large Combine-based networking layer. How do you modernize it? `[Lead/Expert]`
**Add async versions of the API client** next to the Combine ones, **move call sites feature by feature**, **test that behavior matches**, and **remove the old versions** when nobody uses them.

1. Add `async` methods built on `URLSession`'s async APIs.
2. Keep the publisher methods for now as thin adapters over the async ones.
3. Migrate call sites feature by feature, starting with simple one-shot requests.
4. Write tests first for retry, cancellation, and error mapping, and check the async version matches.
5. Remove the Combine adapters once nobody calls them, and track progress per module.
6. Share the plan and guidelines with the team.

```swift
struct APIClient {
    func request<T: Decodable>(_ url: URL, as type: T.Type) async throws -> T {   // new
        let (data, _) = try await URLSession.shared.data(from: url)
        return try JSONDecoder().decode(T.self, from: data)
    }

    func requestPublisher<T: Decodable>(_ url: URL, as type: T.Type) -> AnyPublisher<T, Error> {  // old API, thin adapter
        publisher { try await request(url, as: type) }     // the helper from Q100
    }
}
```

**Follow-ups:**
- **Why keep the publisher versions as adapters?** So old code keeps working while you migrate.
- **What behavior is easiest to break?** Retry and cancellation, so test those first.
- **How do you know you're done?** No callers of the publisher methods remain, and you can delete them.

### Q127. Multiple requests fail with 401 at the same time. How do you refresh the token only once? `[Lead/Expert]`
Keep **one shared "refresh in progress" publisher**: every request that gets a 401 **waits for that same refresh**, then **retries once** with the new token.

- Protect the shared state with a serial queue (or an actor in async code).
- If the refresh fails, log the user out.
- **Caveat:** `share()` has the late-subscriber problem. A request that starts waiting after the refresh already finished only gets the completion. Keeping the latest token in a `CurrentValueSubject` avoids that. In async code, an actor holding a `Task<Token, Error>` is simpler.

```swift
final class TokenRefresher {
    private let queue = DispatchQueue(label: "token-refresher")
    private var inFlight: AnyPublisher<Token, Error>?
    private let authAPI: AuthAPI

    init(authAPI: AuthAPI) { self.authAPI = authAPI }

    func refreshedToken() -> AnyPublisher<Token, Error> {
        queue.sync {
            if let inFlight { return inFlight }                  // reuse the refresh in progress

            let publisher = authAPI.refreshToken()
                .handleEvents(receiveCompletion: { [weak self] _ in
                    self?.queue.async { self?.inFlight = nil }   // clear when done
                })
                .share()                                         // all waiting requests share it
                .eraseToAnyPublisher()

            inFlight = publisher
            return publisher
        }
    }
}

// In the API client
func authorized<T: Decodable>(_ request: URLRequest, as type: T.Type) -> AnyPublisher<T, Error> {
    send(request, token: tokenStore.current, as: type)
        .catch { [weak self] error -> AnyPublisher<T, Error> in
            guard let self, case .httpStatus(401)? = error as? APIError else {   // APIError from Q75
                return Fail(error: error).eraseToAnyPublisher()
            }
            return self.refresher.refreshedToken()
                .flatMap { token in self.send(request, token: token, as: type) }   // retry once
                .eraseToAnyPublisher()
        }
        .eraseToAnyPublisher()
}
```

**Follow-ups:**
- **Why only retry once?** To avoid an endless loop if the new token is also rejected.
- **What's the async/await version?** An actor that stores the current refresh `Task` and returns it to every caller.
- **What if the refresh token is expired too?** The refresh fails, so log the user out and show the login screen.

### Q128. Design a real-time stream (e.g. WebSocket chat) using Combine. `[Lead/Expert]`
A **connection service** exposes **two streams that never fail**, messages and connection state. It **decodes in the background**, **reconnects with backoff**, and **turns errors into a state** instead of ending the streams.

- Keep subjects private. Expose `AnyPublisher<Message, Never>` and `AnyPublisher<ConnectionState, Never>`.
- Decode on a background queue. Switch to main only at the UI.
- Reconnect with exponential backoff. Errors become `.disconnected`, not stream failures.
- Use `buffer` for bursts, `share()` so several screens don't open several sockets, and heartbeats with `Timer.publish`.
- Test with a fake socket and a test scheduler.

```swift
enum ConnectionState { case connecting, connected, disconnected(retryIn: TimeInterval) }

final class ChatConnection {
    private let messagesSubject = PassthroughSubject<Message, Never>()
    private let stateSubject = CurrentValueSubject<ConnectionState, Never>(.connecting)

    var messages: AnyPublisher<Message, Never> { messagesSubject.share().eraseToAnyPublisher() }
    var state: AnyPublisher<ConnectionState, Never> { stateSubject.eraseToAnyPublisher() }

    private func handleSocketError() {
        stateSubject.send(.disconnected(retryIn: nextBackoff()))   // error becomes state, not failure
        scheduleReconnect()
    }
}
```

**Follow-ups:**
- **Why shouldn't the message stream fail?** A failure would end it, and every screen would stop receiving messages.
- **How do you avoid two sockets for two screens?** One shared connection service, with `share()` on the streams.
- **How do you test reconnect timing?** Inject a test scheduler and advance time.

### Q129. Users report duplicate network calls and UI updates after navigating back and forth. How do you investigate? `[Lead/Expert]`
Suspect **subscriptions created more than once** or **objects that leaked**. **Count subscriptions** with logging, **check for leaks** with the Memory Graph, then **bind once, cancel properly, and break cycles**.

- **Suspects:** subscriptions created in `viewWillAppear` without cancelling old ones, cells not cancelling on reuse, leaked view models still reacting, cold publishers subscribed several times without `share()`.
- **Investigate:** `.print()` or `handleEvents(receiveSubscription:)` counters, the Memory Graph Debugger, and `deinit` logs.
- **Fix:** bind once (in `viewDidLoad`) or replace a stored cancellable, cancel in `prepareForReuse`, break cycles, share expensive publishers.
- **Prevent:** leak tests, a review checklist, and team rules for who owns subscriptions.

```swift
// ❌ A new subscription every time the screen appears
override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)
    viewModel.$items.sink { [weak self] in self?.render($0) }.store(in: &cancellables)
}

// ✅ Bind once
override func viewDidLoad() {
    super.viewDidLoad()
    viewModel.$items.sink { [weak self] in self?.render($0) }.store(in: &cancellables)
}
```

**Follow-ups:**
- **How do you count subscriptions quickly?** Add `handleEvents(receiveSubscription: { _ in print("subscribed") })`.
- **Why do leaks cause duplicates?** Old view models stay alive and keep reacting alongside new ones.
- **What test catches this?** A leak test that checks the view model is released after the screen closes.

### Q130. What do you look for when reviewing Combine code? `[Lead/Expert]`
I check **six areas**: lifetime, errors, threading, correctness, API design, and readability.

- **Lifetime:** cancellables stored by the right owner, no strong `self` in `sink`, no `assign(to:on: self)`.
- **Errors:** errors handled inside `flatMap` so long-lived streams survive, no `replaceError` hiding real problems, typed errors at boundaries.
- **Threading:** `receive(on: DispatchQueue.main)` before UI work, no `RunLoop.main` for live updates, no unnecessary thread hops.
- **Correctness:** `switchToLatest` vs `flatMap` chosen on purpose, `Future` wrapped in `Deferred` when needed, `share()` where there are several subscribers.
- **API design:** subjects private and exposed as `AnyPublisher`, schedulers injectable for tests.
- **Readability:** long chains split into named steps or custom operators.

```swift
// Typical review comments
.sink { self.render($0) }                       // ❌ strong self: use [weak self]
.assign(to: \.title, on: self)                  // ❌ retain cycle: use assign(to: &$title)
refresh.flatMap { api.load() }.catch { … }      // ❌ catch outside flatMap kills the stream
.receive(on: RunLoop.main)                      // ❓ live data? use DispatchQueue.main
```

**Follow-ups:**
- **Which issue is most serious?** Errors ending long-lived streams, because features silently stop working.
- **What can tools catch?** Leak tests and the Memory Graph catch cycles. Linters can flag `assign(to:on: self)`.
- **How do you keep reviews consistent?** A shared checklist that everyone uses.

### Q132. Design a repository that shows cached data first, then fresh data. `[Senior]`
**Send the cached data first** with `prepend`, then **fresh data from the network**, **save fresh data to the cache** as a side effect, and **turn errors into a state** so the UI **keeps showing the cached content**.

- The API publisher is cold, so pull-to-refresh simply subscribes again.

```swift
final class ArticleRepository {
    private let cache: ArticleCache
    private let api: ArticleAPI

    init(cache: ArticleCache, api: ArticleAPI) {
        self.cache = cache
        self.api = api
    }

    /// Sends cached articles right away (if any), then fresh ones. Never fails:
    /// errors become a state, so the UI can keep showing cached content.
    func articles() -> AnyPublisher<RepositoryState<[Article]>, Never> {
        let cached = cache.load().map { RepositoryState.cached($0) }

        let fresh = api.fetchArticles()
            .handleEvents(receiveOutput: { [cache] in cache.save($0) })   // save as a side effect
            .map { RepositoryState.fresh($0) }
            .catch { Just(RepositoryState<[Article]>.failed($0)) }        // error → state

        return fresh
            .prepend(cached.map { [$0] } ?? [])                          // cached first
            .eraseToAnyPublisher()
    }
}

enum RepositoryState<Value> {
    case cached(Value)
    case fresh(Value)
    case failed(Error)
}
```

**Follow-ups:**
- **Why does the UI keep the cached content on failure?** The `.failed` state arrives after `.cached`, so the view can show a banner without clearing the list.
- **Why save in `handleEvents`?** It's a side effect that doesn't change the values flowing through.
- **How does pull-to-refresh work here?** Subscribe to `articles()` again. The cold API publisher makes a new request.
