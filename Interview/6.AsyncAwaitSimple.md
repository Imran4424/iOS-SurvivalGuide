## 1. Fundamentals

### Q1. What problem does async/await solve? `[Fundamental]`
async/await lets you write asynchronous code that **reads like normal top-to-bottom code**, instead of **nested completion handlers** that are hard to read and easy to get wrong.

- **Problems with completion handlers:** deep nesting ("pyramid of doom"), forgetting to call the completion (or calling it twice), clumsy error handling with `Result`, and manual thread switching.
- **With async/await:** normal `if`, loops, `try/catch`, and `defer`, errors checked by the compiler, and built-in cancellation.

```swift
// Completion handlers: nested and easy to get wrong
func loadProfile(completion: @escaping (Result<Profile, Error>) -> Void) {
    fetchUser { userResult in
        switch userResult {
        case .failure(let error): completion(.failure(error))
        case .success(let user):
            fetchAvatar(for: user) { avatarResult in
                switch avatarResult {
                case .failure(let error): completion(.failure(error))
                case .success(let avatar): completion(.success(Profile(user: user, avatar: avatar)))
                }
            }
        }
    }
}

// async/await: reads top to bottom
func loadProfile() async throws -> Profile {
    let user = try await fetchUser()
    let avatar = try await fetchAvatar(for: user)
    return Profile(user: user, avatar: avatar)
}
```

**Follow-ups:**
- **What is the "pyramid of doom"?** Callbacks nested inside callbacks, pushing code further and further right.
- **Which bug does async/await make impossible?** Forgetting to call the completion handler on some path. The compiler makes every path return or throw.
- **Does async/await make code run faster?** Not by itself. It makes async code clearer and safer.

### Q2. What does the `async` keyword mean? `[Fundamental]`
`async` marks a function that **can pause** while it waits for something, like a network response.

- You can only call an `async` function from async code, using `await`.
- `async` is part of the function's type: `() async -> Int` is different from `() -> Int`.
- It can be used on functions, closures, read-only properties, and initializers.

```swift
func fetchTemperature() async -> Double {          // can pause while waiting
    let reading = await sensor.read()
    return reading.celsius
}

let temperature = await fetchTemperature()          // must use await
```

**Follow-ups:**
- **Does `async` mean the function runs in the background?** No. It only means it **can** pause. Where it runs depends on isolation (see Q81).
- **Can a sync function call an async one?** Not directly. Create a `Task` first (see Q19).
- **Can an async function call a sync one?** Yes, always.

### Q3. What does `await` mean? `[Fundamental]`
`await` marks a place where the function **may pause**, freeing the thread to do other work, and **continues later** when the result is ready.

- While paused, the thread isn't blocked. It runs other work.
- When it continues, it may be on a **different thread** (unless it belongs to an actor like the main actor).
- `await` also warns the reader: "things may have changed while we were paused."

```swift
func refresh() async {
    print("Before")
    let items = await api.fetchItems()     // may pause here; the thread does other work
    print("After: \(items.count)")         // continues when the result is ready
}
```

**Follow-ups:**
- **Does `await` always pause?** No. It's a **possible** pause. If the result is ready, it may continue right away.
- **Why does `await` make you rethink state?** Other code may have changed shared state while you were paused.
- **Is `await` the same as waiting on a semaphore?** No. A semaphore blocks the thread. `await` frees it (see Q4).

### Q4. What is the difference between suspending and blocking? `[Senior]`
**Suspending** (`await`) **gives the thread back** so it can do other work, while **blocking** (like a semaphore or `sleep`) **holds the thread** and keeps it doing nothing.

| Blocking (`semaphore.wait()`, `sleep()`) | Suspending (`await`) |
|---|---|
| The thread sits idle, waiting | The thread is free to do other work |
| Wastes a limited resource (threads) | Cheap: the function's state is saved |
| On the main thread: freezes the UI | On the main actor: the UI stays responsive |
| Can deadlock Swift's small thread pool | Designed for that thread pool |

- Interview phrase: **"`await` gives up the thread. Blocking holds it hostage."**

```swift
// ❌ Blocking: the thread does nothing for 2 seconds
Thread.sleep(forTimeInterval: 2)

// ✅ Suspending: the thread is free for 2 seconds
try await Task.sleep(for: .seconds(2))
```

**Follow-ups:**
- **Why is blocking especially bad in async code?** Swift has only about one thread per CPU core for async work. Blocking a few can stop everything (see Q82).
- **What happens if you block the main thread?** The UI freezes.
- **Where is the paused function's state kept?** In memory on the heap, not on the thread's stack (see Q6).

### Q5. What is a suspension point, and what can happen at one? `[Senior]`
A suspension point is **an `await` where the function may pause**, and while it's paused, **other code can run, the task can be cancelled, and it may come back on another thread**.

- Only `await` (and a few hidden spots, like the end of an `async let` scope) can pause.
- While paused:
  - Other code on the same actor can run, so **actor state can change** (called reentrancy, see the Concurrency file).
  - The task can be **cancelled**.
  - Non-actor code may **continue on a different thread**.
- Code **between** two `await`s runs without interruption from other tasks on the same actor.

```swift
actor BankAccount {
    var balance = 100

    func withdraw(_ amount: Int) async {
        guard balance >= amount else { return }
        await audit.log("withdraw \(amount)")   // suspension point: balance may change here!
        balance -= amount                       // re-check if it must still be valid
    }
}
```

**Follow-ups:**
- **What is the bug in the example?** Another withdrawal can run during the `await`, so the balance check may no longer be true.
- **How do you fix it?** Change state before the `await`, or check the condition again after it.
- **Is code between two `await`s safe from other tasks on the same actor?** Yes, it runs without interruption.

### Q6. How does async/await work under the hood (at a high level)? `[Lead/Expert]`
The compiler **splits an async function into pieces at each `await`**, keeps its local variables **on the heap instead of the thread's stack**, and the runtime **schedules the next piece** when the awaited work finishes.

- Each piece after an `await` is called a "continuation."
- Because the state is on the heap, the thread can be reused while the function waits.
- When the result is ready, the runtime runs the next piece on the right **executor**: the main actor, an actor, or the global pool (about one thread per CPU core).

```swift
func loadProfile() async throws -> Profile {
    let user = try await fetchUser()            // piece 1 ends here; state saved on the heap
    let avatar = try await fetchAvatar(for: user)   // piece 2 ends here
    return Profile(user: user, avatar: avatar)  // piece 3
}
```

**Follow-ups:**
- **What is an executor?** The thing that decides where a piece of async code runs, like the main actor or a thread pool.
- **Why doesn't a paused function use a thread?** Its state lives on the heap, so the thread is free.
- **Is this like GCD?** No. GCD runs closures on queues, while async functions are split and resumed by the Swift runtime.

### Q7. What is a `Task`? `[Fundamental]`
A `Task` is **the unit of async work** in Swift: every async function runs inside some task, and a task carries a **priority**, a **cancellation flag**, and **task-local values**.

- **Child tasks** (structured): created by `async let` and task groups.
- **Unstructured tasks:** `Task { }` (copies some context from where it's created) and `Task.detached { }` (copies nothing).

```swift
let task = Task {                         // an unstructured task
    try await api.fetchConfig()
}
task.cancel()                             // tasks can be cancelled
let config = try await task.value          // and awaited for their result
```

**Follow-ups:**
- **Is a `Task` a thread?** No. Many tasks share a small pool of threads.
- **What does a task carry with it?** Priority, cancellation state, and task-local values.
- **What's the difference between child and unstructured tasks?** Child tasks are tied to a parent and cancelled with it. Unstructured ones are independent (see Q8).

### Q8. What is structured concurrency? `[Senior]`
Structured concurrency means **child tasks live inside a scope**, like local variables: the parent **can't finish until its children finish**, **cancelling the parent cancels the children**, and **children's errors go up to the parent**.

- Tools: `async let` and task groups.
- **Benefit:** no forgotten work running in the background. "When this function returns, all its work is done."

```swift
func loadDashboard() async throws -> Dashboard {      // parent task
    async let profile = api.fetchProfile()             // child task
    async let orders = api.fetchOrders()               // child task
    async let promotions = api.fetchPromotions()       // child task
    return try await Dashboard(profile: profile, orders: orders, promotions: promotions)
}   // can't return until all three children finish or are cancelled
```

**Follow-ups:**
- **What is "unstructured" then?** `Task { }`: it lives on its own and isn't cancelled with its creator.
- **Why prefer structured concurrency?** Cancellation and errors work automatically, and nothing leaks.
- **Can a child outlive its parent?** No. That's the main rule.

### Q9. How does async/await compare with GCD, completion handlers, and Combine? `[Senior]`
async/await gives you **linear, readable code** with **built-in cancellation** and **compiler-checked thread safety**, while GCD and completion handlers need everything done by hand, and Combine is best for **streams of values over time**.

| | GCD + completion handlers | Combine | async/await |
|---|---|---|---|
| Readability | Nested callbacks | Operator chains | Linear, top-to-bottom code |
| Errors | Manual (`Result`) | Typed `Failure`, ends the stream | `throws`, `try/catch` |
| Cancellation | Manual flags | `AnyCancellable` | Built in, passed down to children |
| Threading | Manual queue switching | Schedulers | Actors, checked by the compiler |
| Too many threads? | Yes (many blocked threads) | Depends | No (small shared pool) |
| Best for | Old code, low-level control | Streams, reactive bindings | Most async work |

```swift
// GCD
DispatchQueue.global().async {
    let data = loadData()
    DispatchQueue.main.async { self.render(data) }
}

// async/await
Task { @MainActor in
    let data = await loadData()
    render(data)
}
```

**Follow-ups:**
- **When would you still use GCD?** For low-level code or very old code you can't change yet.
- **When would you still use Combine?** For complex streams with timing operators, like debounce plus combineLatest.
- **What is "thread explosion"?** GCD creating hundreds of threads when many are blocked (see Q130).

### Q10. What are the minimum OS requirements for async/await? `[Fundamental]`
The **language feature works back to iOS 13**, but most **system async APIs** (like `URLSession.data(from:)`) need **iOS 15+**, and some newer ones need iOS 16+.

- `Task.sleep(for:)` and `Clock` need iOS 16+.
- On older iOS versions, wrap callback APIs yourself with continuations (Section 9).

```swift
if #available(iOS 15, *) {
    let (data, _) = try await URLSession.shared.data(from: url)    // system async API
} else {
    let data = try await legacyDownload(url)                        // your own continuation wrapper
}
```

**Follow-ups:**
- **What Xcode version is needed for iOS 13 back-deployment?** Xcode 13.2 or later.
- **Why do system APIs need iOS 15?** Apple added the async versions in that SDK.
- **What do you do on iOS 13–14?** Wrap completion-handler APIs with `withCheckedThrowingContinuation`.

## 2. Async Functions, Properties, Initializers & Protocols

### Q11. How do you declare async functions, throwing async functions, and async closures? `[Fundamental]`
Write **`async`** (and **`throws`** if it can fail) after the parameters, and call it with **`try await`**.

- Order: `async throws` in the declaration, `try await` at the call site.

```swift
func fetchTemperature() async -> Double { ... }                          // can pause, can't fail
func fetchForecast(for city: String) async throws -> Forecast { ... }    // can pause and fail

let loader: (URL) async throws -> Data = { url in                         // async closure
    let (data, _) = try await URLSession.shared.data(from: url)
    return data
}

let forecast = try await fetchForecast(for: "Dhaka")
```

**Follow-ups:**
- **Why `async throws` but `try await`?** That's just the grammar: declarations say what it is, call sites say what you're doing.
- **How does Swift know a closure is async?** From its type, or because it contains `await`.
- **Can an async function be generic?** Yes, like any other function.

### Q12. Can properties and subscripts be async? `[Senior]`
**Yes, read-only ones**: computed properties and subscripts can have an `async` (and `throws`) **getter**, but **setters can't be async**.

```swift
struct RemoteDocument {
    let url: URL

    var contents: String {
        get async throws {                                       // async getter
            let (data, _) = try await URLSession.shared.data(from: url)
            return String(decoding: data, as: UTF8.self)
        }
    }
}

let text = try await document.contents
```

**Follow-ups:**
- **Why can't setters be async?** Assignment is expected to finish immediately, and an async setter would make that unclear.
- **When is an async property a good idea?** When reading the value naturally needs waiting, like a remote value.
- **When is a function clearer?** When the work is expensive or has side effects. A function name makes that obvious.

### Q13. Can initializers be async? `[Senior]`
**Yes**: an initializer can be `async` (and `throws`) when the object **can't exist until some async setup finishes**.

- **Alternatives:** a static async factory method, or a cheap `init` plus an async `start()`.

```swift
final class DatabaseConnection {
    private let handle: Handle

    init(url: URL) async throws {
        handle = try await Handle.open(url)   // async setup before the object exists
    }
}

let connection = try await DatabaseConnection(url: dbURL)
```

**Follow-ups:**
- **When is a factory method better?** When you want a clearer name, like `connect(to:)`, or might return a cached instance.
- **Can a SwiftUI view have an async init?** No. Start async work in `.task` instead.
- **What's the downside of an async init?** Every caller must be async, which can spread `await` to places that don't need it.

### Q14. Can protocols declare async requirements? `[Senior]`
**Yes**, and a **synchronous implementation can satisfy an async requirement**, which gives implementations flexibility (network, database, cache, or a simple mock).

```swift
protocol UserRepository {
    func user(id: User.ID) async throws -> User
    var currentUser: User? { get async }
}

// A synchronous implementation is allowed
struct InMemoryUserRepository: UserRepository {
    var users: [User.ID: User]

    func user(id: User.ID) throws -> User {           // no async needed
        guard let user = users[id] else { throw RepositoryError.notFound }
        return user
    }

    var currentUser: User? { users.values.first }
}
```

**Follow-ups:**
- **Can an async implementation satisfy a sync requirement?** No. A caller using the sync requirement can't await.
- **Why make requirements async?** So real implementations can do async work, while mocks can stay simple.
- **Do callers still need `await`?** Yes, when calling through the protocol.

### Q15. Can you overload a function on `async`? `[Senior]`
**Yes**: you can have a sync and an async function **with the same name**, and the compiler picks the **async** one in async code and the **sync** one in sync code.

- That's how many APIs offer both, and how Xcode's "Add Async Alternative" refactoring works.

```swift
func loadSettings() -> Settings { ... }              // sync version
func loadSettings() async -> Settings { ... }        // async version

func sync() { let s = loadSettings() }                // picks the sync one
func asyncCaller() async { let s = await loadSettings() }   // picks the async one
```

**Follow-ups:**
- **Is it confusing to readers?** It can be. Clear documentation helps.
- **How do you force the sync one inside async code?** Call it from a sync helper function.
- **Where do you see this in practice?** In code being migrated, where both versions exist for a while.

### Q16. Why can't you use `await` inside `map`, `filter`, or `forEach`? `[Fundamental]`
Because `map`, `filter`, and `forEach` take **normal (sync) closures**, so they **can't wait** for async work.

- **Options:** a `for` loop (one at a time), a task group (all at once), or an `AsyncSequence` with async `map`.

```swift
// ❌ Compile error: 'async' call in a function that does not support concurrency
let images = try urls.map { try await loadImage(from: $0) }

// ✅ One at a time
var images: [UIImage] = []
for url in urls {
    images.append(try await loadImage(from: url))
}

// ✅ All at the same time (see Section 5)
let concurrentImages = try await withThrowingTaskGroup(of: UIImage.self) { group in
    for url in urls { group.addTask { try await loadImage(from: url) } }
    return try await group.reduce(into: []) { $0.append($1) }   // in completion order
}
```

**Follow-ups:**
- **Which option is faster?** The task group, because the work runs at the same time.
- **Does the task group keep the order?** No. Return an index with each result to keep the order (see Q34).
- **Could you write an async `map` yourself?** Yes, as an extension using a `for` loop or a task group.

### Q17. Can `defer` and `async` be used together? `[Senior]`
**Yes**: `defer` works normally in async functions, and **since Swift 6.4 you can also `await` inside a `defer` block**.

- `defer` runs on every exit: normal return, thrown error, or cancellation.
- **Before Swift 6.4,** `await` inside `defer` was a compile error, so async cleanup had to be done by hand before returning.
- **Careful:** an async `defer` still sees cancellation. If cleanup must finish even when cancelled, wrap it in `withTaskCancellationShield` (Swift 6.4, see Q55).

```swift
func refresh() async {
    isLoading = true
    defer { isLoading = false }          // runs no matter how the function exits
    await reloadData()
}

// Swift 6.4: async cleanup in defer
func syncSession() async throws {
    let session = await Session.open()
    defer { await session.close() }      // awaited before the function returns
    try await session.upload()
}
```

**Follow-ups:**
- **When does an async `defer` run?** It's awaited and finishes before the function returns.
- **What did people do before Swift 6.4?** Clean up by hand before each return, or start a separate `Task` for cleanup.
- **Why might async cleanup fail when the task is cancelled?** The cleanup's own `await`s can see the cancellation and stop early, so use a cancellation shield.

### Q18. What is the difference between `async` functions and functions that return a `Task`? `[Senior]`
An **`async` function** lets the **caller decide** how to run it and keeps it **inside the caller's task**, so cancellation and errors flow through. A function that **creates a `Task` inside** starts **independent** work that the caller can't cancel or wait for easily.

- **Prefer `async` functions** in APIs.
- Create `Task`s only at the edges: UI event handlers and app entry points.

```swift
// ✅ The caller decides, and cancellation works
func loadFeed() async throws -> [Post] { try await api.fetchFeed() }

// ❌ The caller loses control: the work keeps running even if the caller is cancelled
func startLoadingFeed() -> Task<[Post], Error> {
    Task { try await api.fetchFeed() }
}
```

**Follow-ups:**
- **Why is the `async` version easier to test?** Tests can just `await` it.
- **When is returning a `Task` OK?** When the caller really needs a handle to work that should outlive the call, like a shared download.
- **What does "edge" mean here?** The point where sync code (like a button tap) starts async work.

## 3. Calling Async Code

### Q19. How do you call an async function from synchronous code? `[Fundamental]`
**Create a `Task`**, which gives you an async context to call it from.

- The sync function returns **immediately**, and the task runs on its own.
- In SwiftUI, prefer `.task { }` for work tied to a view (Section 14).

```swift
// UIKit button action (sync)
@objc private func refreshTapped() {
    Task {
        await viewModel.refresh()
    }
}
```

**Follow-ups:**
- **Does `refreshTapped()` wait for the refresh?** No, it returns right away.
- **Which thread does this `Task` run on?** It inherits the main actor from the view controller (see Q41).
- **Should you keep a handle to this task?** If it may need cancelling, yes (see Q44).

### Q20. What async entry points exist besides `Task`? `[Fundamental]`
Besides `Task`, you can start async code from an **async `main`**, **top-level code**, and **framework hooks** like SwiftUI's `.task`, async tests, and App Intents.

```swift
// 1. An async main
@main
struct Tool {
    static func main() async throws {
        let data = try await fetchReport()
        print(data.count)
    }
}

// 2. Top-level code in main.swift or scripts can use await directly
let report = try await fetchReport()

// 3. Framework hooks: SwiftUI .task/.refreshable, async test methods, App Intents' perform() async
```

**Follow-ups:**
- **Why is `.task` better than `Task` in SwiftUI?** It's cancelled automatically when the view disappears.
- **Can test methods be async?** Yes, in both XCTest and Swift Testing.
- **Where do App Intents run their async work?** In `perform() async`.

### Q21. Can you call a synchronous function from an async function? `[Fundamental]`
**Yes, always**, but a **long-running** sync call (heavy computing or blocking I/O) **holds the thread** the whole time.

- On the main actor, that freezes the UI.
- On Swift's thread pool, it takes a thread away from other tasks.
- Move heavy sync work off the main actor (Section 11), and never block in async code.

```swift
@MainActor
func showReport() async {
    let report = ReportBuilder.build()     // ⚠️ if this takes 2 seconds, the UI freezes
    present(report)
}
```

**Follow-ups:**
- **How do you move the heavy part off the main actor?** Put it in a `@concurrent` async function (Swift 6.2) or a background actor.
- **Is a quick sync call fine?** Yes. Only long or blocking work is a problem.
- **What counts as "blocking"?** Semaphores, `sleep()`, synchronous network or file reads, and waiting on other threads.

### Q22. Can you wait synchronously for an async function's result? `[Senior]`
**Not safely**: blocking a thread until a `Task` finishes can **deadlock** (on the main thread) or **starve Swift's thread pool** (inside async code).

- **Fix:** make the caller async, or deliver the result later through a callback or a state update.

```swift
// ❌ Deadlock: blocks the main thread while the Task needs the main actor
func loadSync() -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result = Data()
    Task { @MainActor in
        result = await loadData()
        semaphore.signal()
    }
    semaphore.wait()     // the main thread waits forever
    return result
}
```

**Follow-ups:**
- **Why does it deadlock?** The task needs the main thread to run, but the main thread is waiting for the task.
- **What if an old API forces a sync return?** Return a placeholder now and update later (see Q106).
- **Is this ever OK in a command-line tool?** Still risky. Use an async `main` instead.

### Q23. What does `await` on a `Task`'s `value` do? `[Fundamental]`
`await task.value` **waits for the task to finish** and gives you its result (rethrowing its error), while `await task.result` gives you a **`Result`** without throwing.

- Several callers can await the same task, and **the work runs only once**. That's useful for avoiding duplicate requests (Q114).

```swift
let task = Task { try await api.fetchConfig() }

// Later, anywhere async:
let config = try await task.value      // waits, and rethrows errors
let outcome = await task.result        // Result<Config, Error>, never throws
```

**Follow-ups:**
- **What happens if two callers await the same task?** Both get the same result, and the work runs once.
- **Does awaiting `value` start the task?** No, the task started when it was created.
- **When is `result` handy?** When collecting outcomes of several tasks without stopping at the first error.

### Q24. When should you create a `Task` vs make the function `async`? `[Senior]`
Make the function **`async`** when the caller is already async and should wait, and **create a `Task`** only where you **can't** be async, like UI event handlers and delegate callbacks.

- **Code-review smell:** `Task { }` sprinkled deep inside business logic ("fire and forget"). It makes ordering, cancellation, and testing unpredictable.

```swift
// ✅ Business logic stays async
func saveDraft(_ draft: Draft) async throws {
    try await store.save(draft)
    try await uploader.upload(draft)
}

// ✅ The Task is created only at the edge
@objc func saveTapped() {
    Task { try? await saveDraft(currentDraft) }
}
```

**Follow-ups:**
- **Why is fire-and-forget hard to test?** Tests can't await something they have no handle to.
- **Where are the "edges" in an app?** Button actions, delegate callbacks, notifications, and app lifecycle events.
- **What does SwiftUI give you instead?** `.task` and `.refreshable`, which handle the task for you.

### Q25. What is the ordering of tasks created in sequence? `[Senior]`
**There is no guaranteed order**: two `Task`s created one after another can run in any order, so if order matters, do the work **one after another in a single task**.

- Tasks on the same actor start roughly in order, but they can still interleave at `await`s.
- For a queue of ordered jobs, use an `AsyncStream` (see Q115).

```swift
// ❌ No guarantee "save" finishes before "upload" starts
Task { await store.save(draft) }
Task { await uploader.upload(draft) }

// ✅ Clear order
Task {
    await store.save(draft)
    await uploader.upload(draft)
}
```

**Follow-ups:**
- **Why don't actors guarantee order?** While one task is paused at an `await`, another can run.
- **How do you build an ordered queue?** An `AsyncStream` of jobs read by one loop (see Q115).
- **Does `Task.immediate` help?** It starts the body right away, but later work after an `await` still isn't ordered against other tasks.

## 4. Structured Concurrency: `async let`

### Q26. What is `async let`? `[Fundamental]`
`async let` **starts a child task right away** that runs **at the same time** as the rest of your code, and you **`await` its value later** when you need it.

- Best for a **fixed, known number** of independent operations (like 3 requests for one screen).
- Total time is about **the slowest** request, not the sum of all of them.

```swift
func loadDashboard() async throws -> Dashboard {
    async let profile = api.fetchProfile()          // starts now
    async let orders = api.fetchOrders()            // starts now, runs at the same time
    async let promotions = api.fetchPromotions()    // starts now, runs at the same time

    // Wait for all three here
    return try await Dashboard(profile: profile, orders: orders, promotions: promotions)
}
// If each takes 1 second, the total is about 1 second, not 3
```

**Follow-ups:**
- **Is `async let` structured?** Yes. The children are cancelled and awaited if the scope exits.
- **Where does the `try` go?** On the `await` that reads the value, not on the `async let` line.
- **Can you pass an `async let` value to another function before awaiting?** No. You must `await` it first.

### Q27. What's the difference between sequential `await`s and `async let`? `[Fundamental]`
**Sequential `await`s** run **one after another**, so times add up, while **`async let`** runs them **at the same time**, so you wait only for the slowest.

- Only run things concurrently if they're **independent**. If `fetchB` needs `a`'s result, it has to be sequential.

```swift
// Sequential: about 3 seconds if each call takes about 1 second
let a = try await fetchA()
let b = try await fetchB()
let c = try await fetchC()

// Concurrent: about 1 second
async let a2 = fetchA()
async let b2 = fetchB()
async let c2 = fetchC()
let results = try await (a2, b2, c2)
```

**Follow-ups:**
- **When must you use sequential `await`s?** When one call needs the result of another.
- **Is concurrent always better?** No. It uses more resources at once, and some servers limit parallel requests.
- **How do you prove the speed-up?** Time it, or look at the requests overlapping in Instruments.

### Q28. What happens if you never await an `async let`? `[Senior]`
When the scope ends, Swift **automatically cancels the unawaited child and waits for it to finish**, then **throws away its result** (and any error).

- This guarantees no child outlives its scope.
- **Surprise:** a slow, unawaited `async let` still **delays the function's return** until it responds to cancellation.

```swift
func loadProfile() async throws -> Profile {
    async let profile = api.fetchProfile()
    async let analytics = api.sendAnalytics()   // never awaited

    return try await profile
    // At the end of the scope, `analytics` is cancelled AND awaited.
    // If sendAnalytics() ignores cancellation, this function waits for it.
}
```

**Follow-ups:**
- **Why does Swift wait for it?** To keep the rule that children never outlive their parent.
- **How do you fire something without waiting?** Use an unstructured `Task`, on purpose, and own its lifetime.
- **Is the unawaited child's error reported?** No, it's thrown away.

### Q29. How do errors work with `async let`? `[Lead/Expert]`
An error from an `async let` child **only shows up when you `await` that child**, so `async let` **doesn't fail fast** by itself.

- If you await `slow` first and `fast` fails early, you still wait for `slow` before you see `fast`'s error.
- When the error leaves the scope, the other children are cancelled and awaited.
- **For true fail-fast** (cancel everything as soon as any child fails), use a throwing task group and read results with `next()`.

```swift
async let slow = fetchSlow()     // takes 5 seconds
async let fast = fetchFast()     // fails after 0.1 seconds

// The tuple awaits `slow` first, so you see fast's error only after about 5 seconds
let result = try await (slow, fast)
```

**Follow-ups:**
- **How would you make it fail fast?** Use a throwing task group. The first error from `next()` cancels the rest.
- **Does awaiting `fast` first help?** Yes, in this example, but you can't know in general which one fails first.
- **Are the other children cancelled after the error?** Yes, when the error leaves the scope.

### Q30. Can you use `async let` in a loop or with a dynamic number of operations? `[Senior]`
**No**: each `async let` is a **fixed variable** in a scope, so you can't make an array of them, and for a **dynamic number** of operations you use a **task group**.

```swift
// ❌ Each loop iteration's async let is cancelled at the end of that iteration
for url in urls {
    async let data = download(url)
}

// ✅ A dynamic number of tasks: use a task group
let allData = try await withThrowingTaskGroup(of: Data.self) { group in
    for url in urls { group.addTask { try await download(url) } }
    return try await group.reduce(into: []) { $0.append($1) }
}
```

**Follow-ups:**
- **What happens with `async let` inside a loop?** Each one is cancelled and awaited at the end of its iteration, so nothing actually runs in parallel across iterations.
- **Is there a fixed-size alternative?** If the count is small and known, write several `async let`s.
- **What does a task group add?** Any number of children, plus control over results and cancellation.

### Q31. Does `async let` inherit the current actor and priority? `[Senior]`
Child tasks inherit the **priority** and **task-local values**, and they're **cancelled with the parent**, but **where the code runs** depends on the function being called.

- A `@MainActor` function still runs on the main actor.
- A `nonisolated` async function follows the rules in Q86–Q87.

```swift
@MainActor
func loadScreen() async throws {
    async let user = api.fetchUser()          // runs wherever fetchUser() is isolated
    async let banner = renderBanner()         // @MainActor func, so it runs on the main actor
    show(try await user, await banner)
}

@MainActor func renderBanner() async -> Banner { ... }
```

**Follow-ups:**
- **Does `async let` copy task-local values?** Yes, children see the parent's task-local values.
- **What if the parent is cancelled?** The `async let` children are cancelled too.
- **Does `async let` make main-actor code run in the background?** No. Isolation comes from the called function.

## 5. Task Groups

### Q32. What is a task group? `[Fundamental]`
A task group is a **structured way to run a dynamic number of child tasks at the same time** and collect their results.

- All children must finish (or be cancelled) before the group returns.
- Results arrive in **completion order** (see Q34).
- Swift 6.1 can often infer the child result type, so `of:` may be left out.

```swift
func fetchThumbnails(for ids: [Photo.ID]) async throws -> [Photo.ID: UIImage] {
    try await withThrowingTaskGroup(of: (Photo.ID, UIImage).self) { group in
        for id in ids {
            group.addTask {                            // one child per id
                (id, try await thumbnailService.thumbnail(for: id))
            }
        }

        var thumbnails: [Photo.ID: UIImage] = [:]
        for try await (id, image) in group {           // results in completion order
            thumbnails[id] = image
        }
        return thumbnails
    }
}
```

**Follow-ups:**
- **Why return the id with the image?** Results come back in any order, so you need to know which is which.
- **Can the group's body mutate local state?** Yes. The body runs one step at a time, so collecting into a dictionary is safe.
- **What happens if the parent is cancelled?** All children are cancelled.

### Q33. What is the difference between `withTaskGroup` and `withThrowingTaskGroup`? How do errors behave? `[Senior]`
In **`withTaskGroup`** children **can't throw**, while in **`withThrowingTaskGroup`** they can, and a child's error **only comes out when you read that child's result**.

- You read results with `next()`, `for try await`, or `waitForAll()`.
- When the body throws (like rethrowing a child error), the group **cancels all remaining children** and waits for them before rethrowing.
- **Errors you never read are lost.** Always read results (or call `waitForAll()`) in throwing groups.

```swift
try await withThrowingTaskGroup(of: Void.self) { group in
    for photo in photos {
        group.addTask { try await uploader.upload(photo) }
    }
    try await group.waitForAll()      // rethrows the first error and cancels the rest
}
```

**Follow-ups:**
- **What if you never call `next()` or `waitForAll()`?** The group still waits for children at the end, but their errors are not thrown.
- **Which one should you pick?** Use the throwing version only if children can fail.
- **How do you keep going after one failure?** Catch inside each child and return a `Result` (see Q61).

### Q34. In what order do task group results arrive? How do you preserve input order? `[Senior]`
Results arrive in **completion order** (fastest first), not the order you added them, so to **keep the input order**, return the **index** with each result and put them back in place.

```swift
func loadAll(_ urls: [URL]) async throws -> [Data] {
    try await withThrowingTaskGroup(of: (Int, Data).self) { group in
        for (index, url) in urls.enumerated() {
            group.addTask { (index, try await download(url)) }   // tag with the index
        }

        var results = [Data?](repeating: nil, count: urls.count)
        for try await (index, data) in group {
            results[index] = data                                 // put it back in its slot
        }
        return results.compactMap { $0 }
    }
}
```

**Follow-ups:**
- **Why is the order random?** Each child finishes whenever its own work is done.
- **What's another way to keep order?** Return a dictionary keyed by id and map the input ids over it.
- **Does `async let` keep order?** Yes, because you await each one by name.

### Q35. How do you limit the number of concurrent child tasks? `[Lead/Expert]`
**Start only N tasks at first**, and **each time one finishes, add the next one**, so you never have more than N running at once.

- This avoids flooding the network or memory with thousands of operations at the same time.

```swift
func downloadAll(_ urls: [URL], maxConcurrent: Int = 4) async throws -> [URL: Data] {
    try await withThrowingTaskGroup(of: (URL, Data).self) { group in
        var results: [URL: Data] = [:]
        var pending = urls.makeIterator()

        // 1. Start the first batch
        for _ in 0..<maxConcurrent {
            guard let url = pending.next() else { break }
            group.addTask { (url, try await download(url)) }
        }

        // 2. Each completion frees a slot for the next URL
        while let (url, data) = try await group.next() {
            results[url] = data
            if let nextURL = pending.next() {
                group.addTask { (nextURL, try await download(nextURL)) }
            }
        }
        return results
    }
}
```

**Follow-ups:**
- **Why not start all 1,000 at once?** It wastes memory and can overload the server or the network.
- **How would you pick N?** Measure. For network work, 4–6 is a common start.
- **Can an actor do this instead?** Yes, with a semaphore-like actor, but the task group version is simpler and structured.

### Q36. What do `cancelAll()` and `addTaskUnlessCancelled` do? `[Senior]`
**`cancelAll()`** cancels every running child and marks the group as cancelled, while **`addTaskUnlessCancelled`** adds a child **only if the group isn't cancelled**.

- `addTaskUnlessCancelled` returns `false` when it skips, so you don't start pointless work.
- `addTask` on a cancelled group still starts the child, but it starts **already cancelled**.

```swift
await withTaskGroup(of: Void.self) { group in
    for item in items {
        let added = group.addTaskUnlessCancelled {
            await process(item)
        }
        if !added { break }            // the group was cancelled: stop adding work
    }
}
```

**Follow-ups:**
- **Does `cancelAll()` stop children immediately?** No. Cancellation is cooperative, so children must check for it.
- **When would you call `cancelAll()`?** When you have the answer you need, like the first result in a race (Q38).
- **Why prefer `addTaskUnlessCancelled` in long loops?** It avoids creating many children that start cancelled.

### Q37. What are discarding task groups? `[Lead/Expert]`
Discarding task groups (`withDiscardingTaskGroup`, Swift 5.9) **throw away each child's result as soon as it finishes**, so memory doesn't grow over time.

- Ideal for long-running "do many side effects" work, like handling incoming connections or events.
- In the **throwing** version, the **first child error cancels the whole group** and is rethrown, giving fail-fast behavior without calling `next()`.

```swift
try await withThrowingDiscardingTaskGroup { group in
    for try await connection in server.connections {
        group.addTask { try await handle(connection) }   // results are not collected
    }
}
```

**Follow-ups:**
- **Why does a normal group grow in memory here?** It keeps every finished child's result until you read it.
- **Can children return values?** No. They return `Void`.
- **How is the throwing version different?** The first error cancels everything else and is rethrown.

### Q38. How do you get the first result and cancel the rest (racing)? `[Senior]`
**Start all the tasks in a group**, take the **first result** with `next()`, then call **`cancelAll()`** to stop the others.

- **Watch out:** if the first child to finish **throws**, `next()` rethrows and the whole group fails.
- To get the first **successful** result, catch errors inside each child (return an optional) and keep calling `next()` until you get a success.

```swift
func fastestMirror(_ mirrors: [URL]) async throws -> Data {
    try await withThrowingTaskGroup(of: Data.self) { group in
        for mirror in mirrors {
            group.addTask { try await download(mirror) }
        }
        guard let first = try await group.next() else {
            throw DownloadError.noMirrors
        }
        group.cancelAll()            // stop the slower downloads
        return first
    }
}
```

**Follow-ups:**
- **What if you forget `cancelAll()`?** The group still waits for every slower download before returning.
- **How is this used for timeouts?** Race the operation against a sleep (see Q111).
- **Do the cancelled downloads stop?** Yes, `URLSession` responds to cancellation.

### Q39. Can child tasks mutate a shared variable? `[Senior]`
**No**: the closures you pass to `addTask` **can't capture and change local `var`s**, which **prevents data races at compile time**, so you **return values** and collect them in the group's body.

- The group's body runs one step at a time, so collecting there is safe.

```swift
// ❌ Compile error: mutation of captured var in concurrently-executing code
var total = 0
await withTaskGroup(of: Void.self) { group in
    for file in files { group.addTask { total += await size(of: file) } }
}

// ✅ Return values and add them up in the body
let total2 = await withTaskGroup(of: Int.self) { group in
    for file in files { group.addTask { await size(of: file) } }
    return await group.reduce(0, +)
}
```

**Follow-ups:**
- **Why is this a data race?** Many children could write `total` at the same time.
- **What marks the closure as unsafe to share?** It's `sending`/`@Sendable`, so it can't capture mutable local state.
- **Could you use an actor to hold the total?** Yes, but returning values is simpler and faster.

### Q40. When do you use `async let`, a task group, or `Task`? `[Senior]`
Use **`async let`** for a **fixed** number of tasks, a **task group** for a **dynamic** number, and **`Task`** only to **start async work from sync code**.

| Tool | Number of tasks | Structured? | Typical use |
|---|---|---|---|
| `async let` | Fixed, known when you write the code | ✅ | Load profile + orders + settings together |
| Task group | Dynamic | ✅ | Download N images, process a list in parallel |
| Discarding task group | Dynamic, results not needed | ✅ | Handle a stream of events or connections |
| `Task { }` | One | ❌ (inherits context) | Start async work from a button tap |
| `Task.detached { }` | One | ❌ (inherits nothing) | Rare: work that must not inherit actor or priority |

- **Rule of thumb:** prefer structured concurrency. Use unstructured tasks only at the edges.

```swift
async let user = api.fetchUser()                       // fixed: 1 of 2
async let settings = api.fetchSettings()               // fixed: 2 of 2

let images = await withTaskGroup(of: UIImage?.self) { group in   // dynamic count
    for url in imageURLs { group.addTask { try? await load(url) } }
    return await group.reduce(into: []) { $0.append($1) }
}

Button("Save") { Task { await save() } }               // sync edge: Task
```

**Follow-ups:**
- **Why prefer structured tools?** Cancellation and errors flow automatically, and nothing outlives its scope.
- **When is `Task.detached` justified?** Rarely (see Q43).
- **Which tool for "first result wins"?** A task group with `next()` and `cancelAll()`.

## 6. Unstructured Tasks: `Task` & `Task.detached`

### Q41. What does `Task { }` inherit from its creator? `[Senior]`
`Task { }` inherits the creator's **actor**, **priority**, and **task-local values**, but **not cancellation**: it's independent, so cancelling the creator doesn't cancel it.

- Example: a `Task` created on the main actor runs its body on the main actor.
- The creator doesn't wait for it.

```swift
@MainActor
final class ProfileViewModel {
    var name = ""

    func load() {
        Task {                                        // runs on the main actor (inherited)
            let profile = try await api.fetchProfile()   // pauses; the main thread stays free
            name = profile.name                       // safe: back on the main actor
        }
    }
}
```

**Follow-ups:**
- **Does the main thread wait for the network?** No. The `await` pauses the task, and the main thread is free while the network work happens.
- **Is this `Task` cancelled when the view model goes away?** No. You must cancel it yourself (see Q44).
- **What does `Task.detached` inherit?** Nothing (see Q42).

### Q42. What is `Task.detached`, and how does it differ? `[Senior]`
`Task.detached` creates a task that **inherits nothing**: no actor, no priority, no task-local values, so it runs on the **global thread pool**.

- You must hop back to the main actor yourself for UI work.

```swift
@MainActor
func exportTapped() {
    Task.detached(priority: .utility) { [document] in
        let pdf = PDFRenderer.render(document)   // heavy work, off the main actor
        await MainActor.run {
            self.shareSheet(for: pdf)            // hop back explicitly for UI
        }
    }
}
```

**Follow-ups:**
- **Why capture `[document]`?** To pass a copy of the value into the task instead of reaching back into `self`.
- **Why `.utility` priority?** A detached task doesn't inherit priority, so you set one that fits the work.
- **What's a cleaner Swift 6.2 option?** A `@concurrent` async function (see Q43 and Q86).

### Q43. When should you use `Task.detached`? `[Lead/Expert]`
**Rarely**: Apple recommends `Task { }` or structured concurrency, and you use `Task.detached` only when the work **must not inherit** the current actor, priority, or task-local values.

- **Valid cases:**
  - Heavy synchronous work started from the main actor.
  - A low-priority cleanup job started from a high-priority context.
- **In Swift 6.2+:** a `@concurrent` async function is usually a clearer way to say "run this off the actor."

```swift
// Swift 6.2+: clearer than Task.detached
@concurrent
func renderPDF(_ document: Document) async -> Data {
    PDFRenderer.render(document)          // always runs on the thread pool
}

@MainActor
func exportTapped() async {
    let pdf = await renderPDF(document)   // main actor stays free
    shareSheet(for: pdf)
}
```

**Follow-ups:**
- **Why is `@concurrent` better?** It's structured: the caller awaits it, and cancellation flows through.
- **Does a detached task get cancelled with its creator?** No.
- **What do you lose with `Task.detached`?** Task-local values like trace IDs, and the caller's priority.

### Q44. How do you store and cancel an unstructured task? `[Fundamental]`
**Keep the `Task` in a property**, call **`.cancel()`** on the old one before starting a new one, and **cancel it when the owner goes away**.

```swift
final class SearchController {
    private var searchTask: Task<Void, Never>?

    func search(_ query: String) {
        searchTask?.cancel()                    // 1. cancel the previous search
        searchTask = Task {                     // 2. start and store the new one
            let results = (try? await api.search(query)) ?? []
            guard !Task.isCancelled else { return }   // 3. don't show stale results
            render(results)
        }
    }

    deinit {
        searchTask?.cancel()                    // 4. cancel when the owner goes away
    }
}
```

**Follow-ups:**
- **Why check `Task.isCancelled` after the await?** `try?` hides the cancellation error, so without the check stale results could be shown.
- **Will `deinit` always run here?** Only if the task doesn't hold `self` strongly forever (see Q109).
- **What does SwiftUI give you instead?** `.task(id:)`, which cancels and restarts for you.

### Q45. What's new for creating tasks in Swift 6.2? `[Lead/Expert]`
Swift 6.2 added **task names**, for debugging, and **`Task.immediate`**, which **starts running right away** on the current actor until its first `await`.

- **Task names:** `Task(name: "LoadFeed") { ... }` shows up in the debugger and Instruments.
- **`Task.immediate`:** normal tasks are queued to run later. `Task.immediate` runs its first part **before the calling function returns**.
- **Use it when:** UI state must change right away in an event handler, before the first `await`.

```swift
@MainActor
func likeTapped() {
    Task.immediate {
        isLiked = true                  // runs right now, before likeTapped() returns
        try? await api.like(postID)     // then pauses like a normal task
    }
}

let task = Task(name: "LoadFeed") {     // named, for debugging
    await feed.load()
}
```

**Follow-ups:**
- **Why not just set `isLiked` before creating the task?** You can. `Task.immediate` matters when the setup must happen inside the task's context.
- **Does `Task.immediate` block?** No. It runs synchronously only until the first `await`.
- **Where do task names show up?** In the debugger and in Instruments' concurrency views.

### Q46. Is an unstructured `Task` cancelled when the task that created it is cancelled? `[Senior]`
**No**: an unstructured `Task` is **independent**, so you must **keep a handle and cancel it yourself**, while children from `async let` and task groups **are** cancelled with their parent.

- This is a very common misunderstanding in interviews.

```swift
let parent = Task {
    async let child = longWork()             // cancelled with the parent ✅
    Task { await otherWork() }               // NOT cancelled with the parent ❌
    _ = await child
}
parent.cancel()
```

**Follow-ups:**
- **How do you make the inner work cancel with the parent?** Use `async let` or a task group instead of `Task { }`.
- **What if you must use `Task { }`?** Store it and cancel it, or use `withTaskCancellationHandler` to forward cancellation.
- **Does cancellation ever flow up?** No, only down (see Q53).

### Q47. What are the problems with "fire-and-forget" tasks? `[Senior]`
Fire-and-forget tasks **lose errors**, **can't be cancelled**, have **no order**, are **hard to test**, and **keep captured objects alive**.

- **Lost errors:** errors are thrown away unless someone awaits `value` (Q62). Swift 6.4 warns about this.
- **No cancellation:** work continues after the screen is gone.
- **No order:** two tasks can run in any order (Q25).
- **Hard to test:** tests can't wait for them.
- **Memory:** they keep captured objects alive until they finish (Section 15).

```swift
func save() {
    Task { try await store.save(draft) }   // ❌ error lost, can't cancel, can't test
}

func save() async throws {
    try await store.save(draft)            // ✅ caller can await, catch, cancel, and test
}
```

**Follow-ups:**
- **What does Swift 6.4 warn about?** An unused throwing `Task` whose errors are never handled.
- **When is fire-and-forget acceptable?** For truly unimportant work like analytics, with errors handled inside.
- **How do you make one testable?** Store the task so tests can await it (see Q119).

### Q48. What happens to a running `Task` when the object that created it is deallocated? `[Senior]`
**Nothing**: the task **keeps running** until it finishes, and if it holds `self` strongly, **`self` can't be deallocated** until then.

- Dropping the `Task` handle **doesn't cancel it** (unlike Combine's `AnyCancellable`).
- Cancel it yourself when the owner goes away, or use APIs that cancel for you, like SwiftUI's `.task`.

```swift
final class Uploader {
    func start() {
        Task {                              // holds self strongly
            await self.uploadEverything()   // self can't be freed until this finishes
        }
    }
}

var uploader: Uploader? = Uploader()
uploader?.start()
uploader = nil          // the task keeps running, and keeps the Uploader alive
```

**Follow-ups:**
- **Is that a leak?** Only temporarily, unless the task never ends (see Q108).
- **How is this different from Combine?** Dropping an `AnyCancellable` cancels the work. Dropping a `Task` doesn't.
- **How do you stop it?** Keep the handle and call `cancel()`.

## 7. Cancellation

### Q49. How does cancellation work in Swift Concurrency? `[Fundamental]`
Cancellation is **cooperative**: `task.cancel()` **only sets a flag**, and your code must **check the flag and stop**.

- Nothing is forced to stop.
- Code usually stops by throwing `CancellationError` or returning partial results.
- Cancellation **flows down to child tasks**, but not to unstructured tasks.
- **Analogy:** it's a polite "please stop" note, not pulling the plug.

```swift
let task = Task {
    for page in 1...100 {
        try Task.checkCancellation()        // checks the flag, throws if set
        try await download(page: page)
    }
}

task.cancel()                               // only sets the flag
```

**Follow-ups:**
- **Why not stop tasks by force?** Forced stops could leave state half-updated, like an open file or a broken lock.
- **What happens if code never checks?** It keeps running until it finishes.
- **Do system APIs check for you?** Many do, like `Task.sleep` and `URLSession` (see Q51).

### Q50. How do you check for cancellation? `[Fundamental]`
Use **`try Task.checkCancellation()`** to **throw** `CancellationError`, or **`Task.isCancelled`** to **check without throwing**.

- `checkCancellation()`: in throwing code, to stop right away.
- `Task.isCancelled`: when you want to return partial results or clean up gently.

```swift
func processAll(_ items: [Item]) async throws -> [Output] {
    var outputs: [Output] = []
    for item in items {
        try Task.checkCancellation()            // throws CancellationError if cancelled
        outputs.append(try await process(item))
    }
    return outputs
}

func loadPreview() async -> Preview? {
    guard !Task.isCancelled else { return nil } // no throw: just return early
    return await renderPreview()
}
```

**Follow-ups:**
- **Where should you check?** At the start of loops and before expensive steps.
- **Can a non-throwing function stop on cancellation?** Yes, with `Task.isCancelled` and an early return.
- **Is `Task.isCancelled` a static property?** Yes, it reads the current task's flag.

### Q51. Which APIs respond to cancellation automatically? `[Senior]`
**`Task.sleep`**, **`URLSession`**, **`AsyncStream` iteration**, and **task groups / `async let`** all respond to cancellation, but **your own loops don't** unless you check.

- **`Task.sleep`:** throws `CancellationError` right away.
- **`URLSession` async methods:** cancel the request and throw **`URLError(.cancelled)`**, not `CancellationError`.
- **`AsyncStream`:** iteration ends (returns `nil`) when the consuming task is cancelled.
- **Task groups and `async let`:** pass cancellation to children.

```swift
// One helper for both kinds of cancellation error
func isCancellation(_ error: Error) -> Bool {
    error is CancellationError || (error as? URLError)?.code == .cancelled
}
```

**Follow-ups:**
- **Why does `URLSession` throw a different error?** It reports its own cancelled request as a `URLError`.
- **What happens to a `for await` loop on cancellation?** The stream returns `nil`, so the loop just ends.
- **Do CPU-heavy loops stop?** No. You must add checks (see Q56).

### Q52. What is `withTaskCancellationHandler`? `[Lead/Expert]`
`withTaskCancellationHandler` runs an **`onCancel` closure immediately** when the task is cancelled, **even while the work is paused**, so you can cancel **non-async work** like a `URLSessionTask` or a callback API.

- `onCancel` can run **at the same time** as the work and **on any thread**, so it must be thread-safe.
- If the task is already cancelled, `onCancel` runs immediately.
- **Race to handle:** `onCancel` might run before you've stored the task. The box should remember "cancelled" and cancel the task when it's set.

```swift
func download(_ url: URL) async throws -> Data {
    let box = TaskBox()   // thread-safe holder (for example, using a lock)

    return try await withTaskCancellationHandler {
        try await withCheckedThrowingContinuation { continuation in
            let task = URLSession.shared.dataTask(with: url) { data, _, error in
                if let error {
                    continuation.resume(throwing: error)
                } else {
                    continuation.resume(returning: data ?? Data())
                }
            }
            box.set(task)     // if already cancelled, the box cancels the task here
            task.resume()
        }
    } onCancel: {
        box.cancel()          // cancelling the data task makes its callback fire with an error
    }
}
```

**Follow-ups:**
- **Why can't you just check `Task.isCancelled`?** The task is paused inside the continuation, so nothing would run the check.
- **Why must `onCancel` be thread-safe?** It can run on another thread while the operation is running.
- **Who resumes the continuation after cancelling?** The callback, which fires with a cancellation error.

### Q53. How does cancellation propagate in structured vs unstructured concurrency? `[Senior]`
Cancellation **flows down the tree** to every structured child, but **never up**, and **never into unstructured tasks**.

```
Task A (cancelled)
 ├── async let B        → cancelled automatically
 ├── group child C      → cancelled automatically
 │    └── async let D   → cancelled automatically
 └── Task { E }         → NOT cancelled (unstructured)
```

- A cancelled child doesn't cancel its parent, but its thrown `CancellationError` may travel up as an error.

```swift
let a = Task {
    async let b = work("B")                         // cancelled with A
    await withTaskGroup(of: Void.self) { group in
        group.addTask { await work("C") }           // cancelled with A
    }
    Task { await work("E") }                        // keeps running
    _ = await b
}
a.cancel()
```

**Follow-ups:**
- **Can a child cancel its parent?** No, but its error can make the parent fail.
- **How do you cancel E?** Keep a handle to it and cancel it yourself.
- **Does a group's `cancelAll()` cancel the parent?** No, only the group's children.

### Q54. How should UI code treat cancellation errors? `[Senior]`
**Ignore them**: cancellation is usually **expected** (the user left the screen or typed a new search), so **don't show an error alert** for it.

```swift
func load() async {
    do {
        items = try await api.fetchItems()
    } catch is CancellationError {
        // replaced by a newer request, or the view disappeared: ignore
    } catch let error as URLError where error.code == .cancelled {
        // URLSession cancellation: ignore
    } catch {
        errorMessage = error.localizedDescription      // real errors only
    }
}
```

**Follow-ups:**
- **Why catch two different errors?** `URLSession` throws `URLError(.cancelled)`, not `CancellationError`.
- **What's the user-facing bug if you don't?** A "cancelled" alert pops up every time they leave the screen.
- **Should you log cancellations?** Usually at debug level only. They're not failures.

### Q55. How do you clean up when a task is cancelled? `[Senior]`
Use **`defer`** for cleanup on every exit, **`withTaskCancellationHandler`** for work outside Swift Concurrency, and **`onTermination`** for streams.

- `defer` runs on every exit, including cancellation errors.
- **Swift 6.4:** `defer` can `await` (Q17), and **`withTaskCancellationShield { }`** lets short cleanup finish even when the task is cancelled. Inside the shield, `Task.isCancelled` reads `false`.

```swift
func record() async throws {
    let session = try AudioSession.start()
    defer { session.stop() }               // runs even if cancelled
    while true {
        try Task.checkCancellation()
        try await session.captureNextBuffer()
    }
}

// Swift 6.4: async cleanup that must finish even when cancelled
func saveTransaction() async throws {
    let transaction = try await db.begin()
    defer {
        await withTaskCancellationShield {
            await transaction.rollbackIfNeeded()   // not cut short by cancellation
        }
    }
    try await transaction.write(changes)
}
```

**Follow-ups:**
- **Why would cleanup need a shield?** Async cleanup can see the cancellation and stop early, leaving things half done.
- **Should you shield long work?** No. Shields are for short cleanup or rollback, not for hiding cancellation.
- **What cleans up a stream?** `onTermination` (see Q76).

### Q56. How do you make a CPU-bound loop cancellable and cooperative? `[Lead/Expert]`
**Check for cancellation** and **call `Task.yield()`** every so often inside the loop, so it **stops when cancelled** and **shares the thread** with other tasks.

- Without these, a cancelled task keeps burning CPU, and a long loop hogs one of Swift's few pool threads.

```swift
func computeHashes(for chunks: [Data]) async throws -> [String] {
    var hashes: [String] = []
    for (index, chunk) in chunks.enumerated() {
        if index.isMultiple(of: 100) {
            try Task.checkCancellation()   // stop if cancelled
            await Task.yield()             // let other tasks use this thread
        }
        hashes.append(sha256(chunk))
    }
    return hashes
}
```

**Follow-ups:**
- **Why every 100 items and not every item?** Checking has a small cost. Pick a balance that still responds quickly.
- **Does `Task.yield()` guarantee another task runs?** No, it's only a chance to switch (see Q89).
- **Is this enough for very heavy work?** Consider moving it to its own thread or `@concurrent` function, and still check for cancellation.

### Q57. What's wrong with `try? await Task.sleep(...)`? `[Senior]`
`try?` **swallows the cancellation error**, so the code **carries on right away** as if the sleep finished, which **defeats cancellation**.

- `Task.sleep` throws `CancellationError` when the task is cancelled.
- With `try?`, the next line runs anyway, like a search request that should have been cancelled.

```swift
// ❌ After cancellation, this continues immediately and searches anyway
try? await Task.sleep(for: .seconds(0.3))
let results = try await api.search(query)

// ✅ Let cancellation stop the function
try await Task.sleep(for: .seconds(0.3))
let results2 = try await api.search(query)
```

**Follow-ups:**
- **What if the function can't throw?** Use `try?`, then check `Task.isCancelled` and return.
- **Where does this bug show up?** Debounced search: cancelled searches still fire network requests.
- **Is `try?` ever OK with `Task.sleep`?** Only if you check cancellation right after.

## 8. Error Handling

### Q58. How do errors propagate in async code? `[Fundamental]`
Errors work **exactly like in normal throwing code**: `try await` passes the error up to the caller, and `do/catch` handles it.

- In structured concurrency, a child's error reaches the parent **when the parent awaits that child** (Q29, Q33).

```swift
func loadSettings() async -> Settings {
    do {
        return try await api.fetchSettings()      // error goes to the catch below
    } catch {
        logger.error("Settings failed: \(error)")
        return .defaults                          // fall back instead of failing
    }
}
```

**Follow-ups:**
- **Does the error come back on the same thread?** It comes back in the caller's context, like any return value.
- **What about errors in an unstructured `Task`?** They're stored in the task until someone reads `value` (see Q62).
- **Can `defer` see the error?** No, but it runs on the error path too.

### Q59. Can async functions use typed throws? `[Senior]`
**Yes**: since Swift 6, an async function can say **exactly which error type** it throws, with `throws(ErrorType)`.

- Prefer plain `throws` for most public APIs, because they may need new errors later.
- Use typed throws for **small, closed, internal** error sets.

```swift
enum ProfileError: Error {
    case notFound
    case network(URLError)
}

func fetchProfile(id: String) async throws(ProfileError) -> Profile {
    do {
        let (data, _) = try await URLSession.shared.data(from: profileURL(id))
        guard let profile = try? JSONDecoder().decode(Profile.self, from: data) else {
            throw ProfileError.notFound
        }
        return profile
    } catch let error as URLError {
        throw .network(error)            // convert to our error type
    } catch let error as ProfileError {
        throw error
    } catch {
        throw .notFound
    }
}

// The caller's catch knows the type: error is ProfileError
do { _ = try await fetchProfile(id: "42") } catch { handle(error) }
```

**Follow-ups:**
- **What's the benefit for the caller?** It can `switch` over every case without a default.
- **What's the downside?** Adding a new error case later breaks callers.
- **Can a `Task` have a typed error?** Yes, Swift 6.4 adds typed throwing `Task` initializers, like `Task<String, URLError>`.

### Q60. How do `Task.value` and `Task.result` differ? `[Fundamental]`
**`try await task.value`** gives you the result and **rethrows** the error, while **`await task.result`** gives you a **`Result`** and **never throws**.

- `result` is handy when collecting outcomes from several tasks without stopping at the first error.
- **Swift 6.4:** `Result` also has an async initializer, `await Result { try await work() }`.

```swift
let task = Task { try await api.fetchConfig() }

// Option 1: rethrows
let config = try await task.value

// Option 2: never throws
switch await task.result {
case .success(let config): apply(config)
case .failure(let error): logger.error("\(error)")
}

// Swift 6.4: capture any async throwing call as a Result
let outcome = await Result { try await api.fetchConfig() }
```

**Follow-ups:**
- **Can you read `value` more than once?** Yes. The task runs once, and every reader gets the same result.
- **When would you use `result` in a loop?** When you want to report each task's success or failure separately.
- **Does reading `result` cancel the task?** No.

### Q61. How do you allow partial failures when running many tasks? `[Senior]`
**Catch errors inside each child** and return a **`Result`**, so **one failure doesn't cancel the others**, and the screen can show what succeeded.

- Use a **non-throwing** group, so nothing fails the whole group.

```swift
func loadWidgets(_ ids: [Widget.ID]) async -> [Widget.ID: Result<Widget, Error>] {
    await withTaskGroup(of: (Widget.ID, Result<Widget, Error>).self) { group in
        for id in ids {
            group.addTask {
                do { return (id, .success(try await api.fetchWidget(id))) }
                catch { return (id, .failure(error)) }    // a failure doesn't cancel the others
            }
        }
        var results: [Widget.ID: Result<Widget, Error>] = [:]
        for await (id, result) in group {
            results[id] = result
        }
        return results
    }
}
// The UI shows the widgets that loaded and placeholders for the ones that failed
```

**Follow-ups:**
- **Why not use a throwing group?** Its first rethrown error would cancel all the other widgets.
- **How could Swift 6.4 shorten the child?** `group.addTask { (id, await Result { try await api.fetchWidget(id) }) }`.
- **When is fail-fast the right choice?** When the screen is useless without every piece.

### Q62. What happens to an error thrown inside `Task { }` that nobody awaits? `[Senior]`
The error is **silently thrown away**: the `Task` stores it until someone reads `value`, and if nobody does, **it's lost**.

- **Swift 6.4** warns about this: "Unstructured throwing task was not used."
- **Fixes:**
  - Catch errors **inside** the task (log, update UI state).
  - Keep the handle and `try await task.value`.
  - Write `_ = Task { ... }` if ignoring failure is really intended.

```swift
// ❌ Errors vanish (Swift 6.4 warns here)
Task {
    try await syncService.sync()
}

// ✅ Handle errors inside the task
Task {
    do {
        try await syncService.sync()
    } catch {
        logger.error("Sync failed: \(error)")
        syncStatus = .failed
    }
}
```

**Follow-ups:**
- **Why didn't the compiler stop this before?** A `Task` that throws is a valid `Task<Success, Error>` value, so it compiled without complaint.
- **What does `_ = Task { }` say to readers?** "I know errors are ignored, and that's on purpose."
- **Which errors should still be shown to the user?** Real failures, but not cancellation (see Q54).

## 9. Continuations: Bridging Callbacks & Delegates

### Q63. What is a continuation? `[Fundamental]`
A continuation is **"the rest of a paused async function"** as an object: you **give it to callback code**, and the callback **calls `resume`** to continue the function with the result.

- You get one from `withCheckedContinuation` (and its throwing version).
- It's how you turn completion-handler and delegate APIs into `async` functions.
- **Analogy:** a restaurant pager. You hand it over, and when the food is ready, the buzz brings you back.

```swift
func currentBatteryLevel() async -> Float {
    await withCheckedContinuation { continuation in     // the function pauses here
        deviceMonitor.readBattery { level in
            continuation.resume(returning: level)       // the function continues with `level`
        }
    }
}
```

**Follow-ups:**
- **What happens if you never call `resume`?** The function waits forever (see Q66).
- **Can you call `resume` from any thread?** Yes.
- **Is this the same "continuation" as in Q6?** Same idea: the rest of the function, but here you control when it resumes.

### Q64. How do you wrap a completion-handler API with a continuation? `[Fundamental]`
Call the old API **inside `withCheckedThrowingContinuation`** (or `withCheckedContinuation` if it can't fail), and **resume the continuation once** from the completion handler.

```swift
// Old API
func fetchUser(id: Int, completion: @escaping (Result<User, Error>) -> Void) { ... }

// Async wrapper
func fetchUser(id: Int) async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        fetchUser(id: id) { result in
            continuation.resume(with: result)      // resume exactly once
        }
    }
}

// Version that can't fail
func currentBatteryLevel() async -> Float {
    await withCheckedContinuation { continuation in
        deviceMonitor.readBattery { level in
            continuation.resume(returning: level)
        }
    }
}
```

**Follow-ups:**
- **What does `resume(with: result)` do?** Returns the success value or throws the failure, in one call.
- **What if the callback gives `(Data?, Error?)`?** Check each case and resume exactly once on every path.
- **Can Xcode generate this?** Yes, "Add Async Wrapper" creates it (see Q123).

### Q65. What is the difference between checked and unsafe continuations? `[Senior]`
**Checked** continuations **catch mistakes at runtime** (crash on double resume, warning on never resuming), while **unsafe** ones do **no checks** and are slightly faster.

| Checked (`withCheckedContinuation`) | Unsafe (`withUnsafeContinuation`) |
|---|---|
| Runtime checks for misuse | No checks |
| Resume twice: **crash** with a clear message | Undefined behavior |
| Never resume: a **warning** is logged | Silent leak |
| Tiny extra cost | Slightly faster |

- Use **checked** by default. Switch to unsafe only for proven hot paths after good testing.

```swift
// Same shape, different safety
let a = await withCheckedContinuation { c in api.load { c.resume(returning: $0) } }
let b = await withUnsafeContinuation { c in api.load { c.resume(returning: $0) } }
```

**Follow-ups:**
- **Why does checked crash on a double resume?** Resuming twice is always a bug, so it fails loudly and early.
- **What does the "never resumed" warning say?** That the continuation leaked, meaning a task is stuck forever.
- **Is the speed difference usually noticeable?** No, only in very hot code.

### Q66. What are the rules for resuming a continuation? `[Senior]`
**Resume exactly once on every code path**: **never** resuming hangs the task forever, and resuming **twice** crashes.

- **Never resuming:** the awaiting task waits forever (a leaked task). Checked continuations log a "leaked its continuation" warning.
- **Resuming twice:** crash (checked) or undefined behavior (unsafe).
- **Watch for callbacks that fire many times** (progress, then completion) or **never** (on some error paths). Guard with a flag, or use `AsyncStream` for multi-value callbacks.

```swift
func requestPermission() async -> Bool {
    await withCheckedContinuation { continuation in
        permissionManager.request { granted, error in
            if error != nil {
                continuation.resume(returning: false)
                return                              // ✅ return, so we don't resume again
            }
            continuation.resume(returning: granted)
        }
    }
}
```

**Follow-ups:**
- **What's the bug if you forget the `return`?** Both resumes run on the error path, so it crashes.
- **What if the callback never fires on some path?** The caller hangs, so audit every path of the old API.
- **What do you use for callbacks that fire many times?** `AsyncStream` (see Q73).

### Q67. How do you bridge a one-shot delegate API to async? `[Lead/Expert]`
**Store the continuation** in a property, **resume it from the delegate callbacks**, **set it to `nil`** right after resuming, and **reject (or queue) overlapping requests**.

- On iOS 17+, `CLLocationUpdate.liveUpdates()` gives you location as a native `AsyncSequence`.

```swift
@MainActor
final class LocationProvider: NSObject, CLLocationManagerDelegate {
    private let manager = CLLocationManager()
    private var continuation: CheckedContinuation<CLLocation, Error>?

    override init() {
        super.init()
        manager.delegate = self
    }

    func currentLocation() async throws -> CLLocation {
        guard continuation == nil else { throw LocationError.requestInProgress }   // one at a time
        return try await withCheckedThrowingContinuation { continuation in
            self.continuation = continuation          // 1. store it
            manager.requestLocation()
        }
    }

    nonisolated func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
        MainActor.assumeIsolated {     // the manager calls back on the thread that created it (main)
            guard let location = locations.last else { return }
            continuation?.resume(returning: location)   // 2. resume it
            continuation = nil                          // 3. clear it, so it can't resume twice
        }
    }

    nonisolated func locationManager(_ manager: CLLocationManager, didFailWithError error: Error) {
        MainActor.assumeIsolated {
            continuation?.resume(throwing: error)
            continuation = nil
        }
    }
}

enum LocationError: Error { case requestInProgress }
```

**Follow-ups:**
- **Why reject a second request?** There's only one continuation slot, and overwriting it would leave the first caller hanging forever.
- **Why `MainActor.assumeIsolated`?** The delegate is `nonisolated`, but the manager calls back on the main thread, so we tell the compiler that.
- **How would you support many callers at once?** Store an array of continuations and resume them all.

### Q68. How do you support cancellation in a continuation-based wrapper? `[Lead/Expert]`
Continuations **don't know about cancellation**, so wrap them in **`withTaskCancellationHandler`**, **cancel the underlying work in `onCancel`**, and let the old API's callback **resume with an error**.

- Make sure cancellation still leads to **exactly one** resume.
- See Q52 for a full `URLSession` example.

```swift
func fetchReport() async throws -> Report {
    let request = ReportRequest()                    // old, cancellable, thread-safe API
    return try await withTaskCancellationHandler {
        try await withCheckedThrowingContinuation { continuation in
            request.start { result in
                continuation.resume(with: result)    // the only resume, also on cancellation
            }
        }
    } onCancel: {
        request.cancel()     // the old API then calls back with a "cancelled" error
    }
}
```

**Follow-ups:**
- **Why not resume inside `onCancel`?** The callback would then resume a second time and crash.
- **What if the old API can't be cancelled?** Ignore the result when it arrives, and check `Task.isCancelled` after the `await`.
- **What if `onCancel` runs before `start` is called?** Make `cancel()` remember it, and have `start` fail right away.

### Q69. How are Objective-C completion-handler APIs imported into Swift? `[Senior]`
Objective-C methods whose **last parameter is a completion block** are **automatically given an `async` version** in Swift.

- This is how PhotoKit, HealthKit, StoreKit, Contacts, and many other frameworks got async methods.

```swift
// Objective-C:
// - (void)requestAuthorizationWithOptions:(...) completionHandler:(void (^)(BOOL, NSError *))handler;

// Swift sees an async throwing version
let granted = try await UNUserNotificationCenter.current()
    .requestAuthorization(options: [.alert, .badge, .sound])
```

**Follow-ups:**
- **How does Swift know it can throw?** The block has an `NSError *` parameter.
- **Does this work for your own Objective-C code?** Yes, if it follows the naming pattern.
- **Can you control the async name?** Yes, with Objective-C annotations like `NS_SWIFT_ASYNC_NAME`.

## 10. `AsyncSequence` & `AsyncStream`

### Q70. What is an `AsyncSequence`? `[Fundamental]`
An `AsyncSequence` is **like a normal `Sequence`, but each value arrives over time**, and you loop over it with **`for await`** (or `for try await` if it can throw).

- The iterator's `next()` is `async`, and returns `nil` when the sequence ends.
- The loop **pauses between values**, so it doesn't block the thread.

```swift
for try await line in fileURL.lines {     // each line arrives when it's read
    print(line)
}
print("Done")                             // runs after the last line
```

**Follow-ups:**
- **How does the loop end?** When `next()` returns `nil`, the task is cancelled, or an error is thrown.
- **Can you `break` out?** Yes. That also tells the sequence the consumer has stopped.
- **How is it different from a Combine publisher?** It's pull-based: the consumer asks for the next value.

### Q71. What built-in async sequences exist? `[Fundamental]`
Built-in async sequences include **lines and bytes** of files and URLs, **notifications**, **Combine publishers** (through `.values`), and many **framework APIs** like StoreKit and Core Location.

```swift
// Lines and bytes from files and URLs
for try await line in url.lines { }
let (bytes, _) = try await URLSession.shared.bytes(from: url)
for try await byte in bytes { }

// Notifications
for await notification in NotificationCenter.default.notifications(named: .NSCalendarDayChanged) { }

// Combine publishers (iOS 15+)
for await value in publisher.values { }

// Framework APIs: StoreKit Transaction.updates, CLLocationUpdate.liveUpdates(),
// CLMonitor events, Network framework, MusicKit, and more
for await update in Transaction.updates { }
```

**Follow-ups:**
- **What's a common mistake with `Transaction.updates`?** Not listening from app launch, so purchases get missed.
- **Can `publisher.values` lose values?** Yes, if the publisher sends faster than the loop reads.
- **How do you stop a notifications loop?** Cancel the task that runs it.

### Q72. What operators can you use on an `AsyncSequence`? `[Senior]`
`AsyncSequence` has the **familiar operators** like `map`, `filter`, `prefix`, `first(where:)`, and `reduce`, and Apple's **swift-async-algorithms** package adds **time and combining operators** like `debounce` and `merge`.

- **Built in:** `map`, `compactMap`, `flatMap`, `filter`, `prefix`, `dropFirst`, `drop(while:)`, `first(where:)`, `contains`, `reduce`, `min`, `max`, `allSatisfy`.
- **swift-async-algorithms:** `debounce`, `throttle`, `merge`, `combineLatest`, `zip`, `chunked`, `AsyncChannel`, `AsyncTimerSequence`.

```swift
let errorLines = logURL.lines
    .filter { $0.contains("ERROR") }
    .map { $0.uppercased() }
    .prefix(10)                                   // only the first 10

for try await line in errorLines { print(line) }

let firstFatal = try await logURL.lines.first { $0.hasPrefix("FATAL") }
let lineCount = try await logURL.lines.reduce(0) { count, _ in count + 1 }
```

**Follow-ups:**
- **Are these operators lazy?** Yes. Nothing runs until you iterate.
- **Where's `debounce`?** Not in the standard library. It's in swift-async-algorithms.
- **Does `first(where:)` stop reading?** Yes, it stops as soon as it finds a match.

### Q73. What is `AsyncStream`, and how do you create one from callbacks? `[Senior]`
`AsyncStream` is **the easiest way to make your own async sequence**: you get a **continuation**, call **`yield`** for each value, and **`finish()`** at the end.

- Ideal for turning **multi-value** callbacks, delegates, and notifications into a `for await` loop.
- Set **`onTermination`** to clean up when the consumer stops.

```swift
final class BatteryMonitor {
    func levels() -> AsyncStream<Float> {
        AsyncStream { continuation in
            UIDevice.current.isBatteryMonitoringEnabled = true
            let observer = NotificationCenter.default.addObserver(
                forName: UIDevice.batteryLevelDidChangeNotification, object: nil, queue: .main
            ) { _ in
                continuation.yield(UIDevice.current.batteryLevel)   // send each value
            }
            continuation.onTermination = { _ in
                NotificationCenter.default.removeObserver(observer) // clean up when the consumer stops
            }
        }
    }
}

// Consumer
for await level in monitor.levels() {
    batteryLabel.text = "\(Int(level * 100))%"
}
```

**Follow-ups:**
- **How is this different from a continuation (Q63)?** A checked continuation resumes once. A stream continuation can yield many values.
- **What happens if nobody calls `finish()`?** The stream stays open until the consumer stops.
- **What if values come faster than they're read?** They're buffered, based on the buffering policy (Q75).

### Q74. What is `AsyncStream.makeStream(of:)`? `[Senior]`
`makeStream(of:)` (Swift 5.9) gives you **the stream and its continuation as a pair**, which is cleaner when **values are sent from several places**, like methods in a class.

```swift
final class ChatConnection {
    let messages: AsyncStream<Message>
    private let continuation: AsyncStream<Message>.Continuation

    init() {
        (messages, continuation) = AsyncStream.makeStream(
            of: Message.self,
            bufferingPolicy: .bufferingNewest(100)
        )
    }

    func didReceive(_ message: Message) {   // called by the socket delegate
        continuation.yield(message)
    }

    func close() {
        continuation.finish()               // ends every `for await` loop
    }
}
```

**Follow-ups:**
- **What did people do before `makeStream`?** Stored the continuation from inside the closure in an implicitly unwrapped optional.
- **Who should own the continuation?** The producer only. Keep it private.
- **What happens after `finish()`?** Later `yield` calls are ignored.

### Q75. What buffering policies does `AsyncStream` support? `[Senior]`
`AsyncStream` can **keep everything** (`.unbounded`), **keep the oldest N** (`.bufferingOldest`), or **keep the newest N** (`.bufferingNewest`) when the consumer is slower than the producer.

| Policy | When the consumer is slower than the producer |
|---|---|
| `.unbounded` (default) | Keeps everything, so memory can grow without limit |
| `.bufferingOldest(n)` | Keeps the oldest n values, and drops new ones when full |
| `.bufferingNewest(n)` | Keeps the newest n values, and drops old ones when full |

- `.bufferingNewest(1)` is ideal for **"latest state"** streams, like location or progress.
- `yield` returns a result (`.enqueued`, `.dropped`, `.terminated`) if you need to know what happened.

```swift
let (progress, continuation) = AsyncStream.makeStream(
    of: Double.self,
    bufferingPolicy: .bufferingNewest(1)     // only the latest progress matters
)

let result = continuation.yield(0.42)
if case .dropped = result { print("An older value was dropped") }
```

**Follow-ups:**
- **When is `.unbounded` dangerous?** With a fast producer and a slow consumer, like sensor data.
- **When would you want `.bufferingOldest`?** When the first values matter most and later ones can be skipped.
- **Does `AsyncStream` slow down the producer?** No. There's no backpressure, only buffering.

### Q76. What is `onTermination`, and why is it important? `[Senior]`
`onTermination` is **called when the stream ends**, either because the producer called `finish()` or because the **consumer stopped** (left the loop or was cancelled), and you use it to **stop the underlying work**.

- Examples: remove observers, stop sensors, cancel network tasks.
- **Forgetting it leaks resources** that keep producing values nobody reads.

```swift
func headingUpdates() -> AsyncStream<Double> {
    AsyncStream { continuation in
        let sensor = CompassSensor()
        sensor.onHeading = { continuation.yield($0) }
        sensor.start()

        continuation.onTermination = { reason in
            sensor.stop()                     // stop the hardware when nobody listens
            print("Stream ended: \(reason)")  // .finished or .cancelled
        }
    }
}
```

**Follow-ups:**
- **What are the two termination reasons?** `.finished` (the producer finished) and `.cancelled` (the consumer stopped).
- **Does `break` in the loop trigger it?** Usually yes. Once nothing holds the stream any more, it ends with `.cancelled`.
- **Is `onTermination` called on the main thread?** Not necessarily, so keep it thread-safe.

### Q77. Build an `AsyncThrowingStream` that reports download progress. `[Lead/Expert]`
Start the download in a **`Task` inside the stream**, **yield progress** events as bytes arrive, **finish with the data** (or the error), and **cancel the task in `onTermination`**.

- Reading byte by byte is simple but slow for big files. Production code would use a download delegate for progress.

```swift
enum DownloadEvent: Sendable {
    case progress(Double)
    case finished(Data)
}

func download(_ url: URL) -> AsyncThrowingStream<DownloadEvent, Error> {
    AsyncThrowingStream { continuation in
        let task = Task {
            do {
                let (bytes, response) = try await URLSession.shared.bytes(from: url)
                let expected = response.expectedContentLength
                var data = Data()
                if expected > 0 { data.reserveCapacity(Int(expected)) }

                for try await byte in bytes {
                    data.append(byte)
                    if expected > 0, data.count.isMultiple(of: 64 * 1024) {
                        continuation.yield(.progress(Double(data.count) / Double(expected)))
                    }
                }
                continuation.yield(.finished(data))
                continuation.finish()                         // success
            } catch {
                continuation.finish(throwing: error)          // failure
            }
        }
        continuation.onTermination = { _ in task.cancel() }   // consumer stopped: cancel the download
    }
}

// Consumer
for try await event in download(fileURL) {
    switch event {
    case .progress(let fraction): progressView.progress = Float(fraction)
    case .finished(let data): save(data)
    }
}
```

**Follow-ups:**
- **Why check `expected > 0`?** The server may not send a length, so `expectedContentLength` can be -1.
- **Why yield every 64 KB?** Updating the UI for every byte would be far too often.
- **What happens if the consumer leaves the loop?** `onTermination` cancels the download task.

### Q78. How do you write a custom `AsyncSequence`? `[Lead/Expert]`
Make a type that conforms to **`AsyncSequence`**, with an **iterator** whose **`async next()`** returns the next value, or **`nil` when done**.

- Swift 6 adds a `Failure` type to `AsyncSequence` (typed throws), so non-throwing sequences don't need `try`.

```swift
/// Fetches pages until the API returns an empty page
struct PagedResults<Item: Sendable>: AsyncSequence {
    typealias Element = [Item]
    let fetchPage: @Sendable (Int) async throws -> [Item]

    struct AsyncIterator: AsyncIteratorProtocol {
        let fetchPage: @Sendable (Int) async throws -> [Item]
        var page = 0
        var isFinished = false

        mutating func next() async throws -> [Item]? {
            guard !isFinished else { return nil }
            try Task.checkCancellation()
            let items = try await fetchPage(page)
            if items.isEmpty {
                isFinished = true
                return nil                     // nil ends the loop
            }
            page += 1
            return items
        }
    }

    func makeAsyncIterator() -> AsyncIterator {
        AsyncIterator(fetchPage: fetchPage)
    }
}

// Usage
for try await page in PagedResults(fetchPage: { try await api.products(page: $0) }) {
    products.append(contentsOf: page)
}
```

**Follow-ups:**
- **When is a custom sequence better than `AsyncStream`?** When values are pulled on demand, like pages, so nothing runs ahead of the consumer.
- **Why check cancellation in `next()`?** So the loop stops early when the task is cancelled.
- **Why is `next()` `mutating`?** The iterator keeps its own state, like the current page.

### Q79. Can multiple consumers iterate the same `AsyncStream`? `[Lead/Expert]`
**Not as a broadcast**: `AsyncStream` is built for **one consumer**, and if several tasks read it, **each value goes to only one of them** (and some versions may trap), so for many listeners, **give each one its own stream**.

- **Options for broadcasting:**
  - Keep a list of continuations, one stream per subscriber (below).
  - Use a library solution.
  - For "latest value" updates, use `@Observable` state with Swift 6.2's `Observations`.

```swift
actor EventBroadcaster<Event: Sendable> {
    private var continuations: [UUID: AsyncStream<Event>.Continuation] = [:]

    func subscribe() -> AsyncStream<Event> {
        let (stream, continuation) = AsyncStream.makeStream(of: Event.self)
        let id = UUID()
        continuations[id] = continuation
        continuation.onTermination = { [weak self] _ in
            Task { await self?.remove(id) }     // forget subscribers that stopped
        }
        return stream
    }

    func send(_ event: Event) {
        for continuation in continuations.values { continuation.yield(event) }   // everyone gets it
    }

    private func remove(_ id: UUID) { continuations[id] = nil }
}
```

**Follow-ups:**
- **Why is there a `Task` inside `onTermination`?** `onTermination` is synchronous, but removing from the actor needs `await`.
- **How is this like Combine's `share()`?** Both deliver one value to many subscribers.
- **Do late subscribers get old events?** No, only events sent after they subscribe.

### Q80. How do you create a polling stream? `[Senior]`
Use **`AsyncStream(unfolding:)`**, which **creates the next value when the consumer asks for it**: sleep, fetch, return the value, or **return `nil` to end** the stream.

- Returning `nil` (including when the fetch fails, as written here) **finishes** the stream. Return a wrapper value instead if errors shouldn't stop polling.

```swift
func statusUpdates(every interval: Duration) -> AsyncStream<OrderStatus> {
    AsyncStream(unfolding: {
        try? await Task.sleep(for: interval)
        guard !Task.isCancelled else { return nil }          // nil ends the stream
        return try? await api.fetchOrderStatus()             // a failed fetch also ends it
    })
}

for await status in statusUpdates(every: .seconds(10)) {
    render(status)
    if status == .delivered { break }    // leaving the loop stops the polling
}
```

**Follow-ups:**
- **Why is `try?` on the sleep OK here?** The next line checks `Task.isCancelled` (compare Q57).
- **Does polling continue after `break`?** No. The next value is only made when the loop asks for it.
- **How would you keep polling after a failed fetch?** Return an enum like `.failed(error)` instead of `nil`.

## 11. Threads, Executors & the Main Actor

### Q81. Which thread does async code run on? `[Senior]`
It depends on **isolation**, not on where you called from: **`@MainActor` code runs on the main thread**, **actor code runs on that actor**, and **nonisolated code runs on Swift's thread pool** (or, with Swift 6.2's new default, on the caller's actor).

- **Actor code:** runs one piece at a time, on some pool thread.
- **Nonisolated async code:** runs on the global thread pool, or on the caller's actor with Swift 6.2's default (Q86).
- After an `await`, non-main-actor code may continue on a **different thread**.
- **Think in actors and isolation, not threads.**

```swift
@MainActor func updateLabel() { }         // main thread

actor Cache { func store() { } }          // the Cache actor, one task at a time

nonisolated func parse() async { }        // Swift 6.2 default: the caller's actor
@concurrent func resize() async { }       // always the global thread pool
```

**Follow-ups:**
- **Can you choose a specific thread?** Not normally. You choose an actor, and the actor decides.
- **Does calling from the main thread mean it runs on the main thread?** Only if the function is main-actor isolated, or nonisolated with the Swift 6.2 default.
- **How do you check where code runs while debugging?** Use `MainActor.assertIsolated()` or `dispatchPrecondition`, not thread names.

### Q82. What is the cooperative thread pool, and why must you never block it? `[Lead/Expert]`
Swift runs tasks on a **small pool of threads, about one per CPU core**, and tasks **share them by pausing at `await`**, so **blocking a thread** (semaphores, `sleep()`) can **deadlock** the whole app.

- This avoids GCD's **thread explosion** (hundreds of blocked threads, lots of memory, constant switching).
- The runtime needs **forward progress**. Each blocked thread is one less thread in the pool.
- Block enough of them, and the tasks that would unblock them **can't get a thread**, so everything stops.

```swift
// ❌ Never do this in async code
func badFetch() async -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result = Data()
    Task {
        result = await fetch()
        semaphore.signal()
    }
    semaphore.wait()        // blocks a pool thread, which can deadlock under load
    return result
}

// ✅ Just await
func goodFetch() async -> Data {
    await fetch()
}
```

**Follow-ups:**
- **Why does it work in testing but hang in production?** With low load there are free threads. Under load, every thread can get blocked.
- **What does "forward progress" mean?** Every task that is waiting will eventually get a thread to continue.
- **How do you wrap a truly blocking API?** Run it on its own thread or `DispatchQueue`, and bridge with a continuation.

### Q83. How do you run code on the main actor? `[Fundamental]`
**Mark the function or type with `@MainActor`** (the best option), or **hop there with `await MainActor.run { }`**, or **start a `Task { @MainActor in }`**.

- Prefer `@MainActor` on types and functions. The compiler then checks it for you.
- The Concurrency file covers this in depth.

```swift
// 1. Mark the function or type
@MainActor
func updateUI(with items: [Item]) {
    tableView.reloadData()
}

// 2. Hop to the main actor from nonisolated async code
await MainActor.run {
    progressView.isHidden = true
}

// 3. Start a main-actor task from anywhere
Task { @MainActor in
    statusLabel.text = "Done"
}

// 4. Calling a @MainActor function from elsewhere needs await (it may hop)
await updateUI(with: items)
```

**Follow-ups:**
- **Why prefer `@MainActor` over `MainActor.run`?** It's checked at compile time and can't be forgotten.
- **Is `MainActor.run` like `DispatchQueue.main.async`?** Similar, but it's awaited and returns a value.
- **Why does option 4 need `await`?** The call might have to wait to get onto the main actor.

### Q84. After an `await` in a `@MainActor` function, where does execution resume? `[Senior]`
**Back on the main actor**: isolation is **kept across `await`s**, so you can update UI right after a network call **without dispatching to the main queue**.

```swift
@MainActor
func refresh() async {
    spinner.startAnimating()                     // main actor
    let items = try? await api.fetchItems()      // pauses; the main thread stays free
    spinner.stopAnimating()                      // main actor again
    self.items = items ?? []
}
```

**Follow-ups:**
- **Does the network call block the main thread?** No. The task pauses, and the main thread is free.
- **Is this true for any actor?** Yes. Code on an actor always comes back to that actor.
- **What can change during the `await`?** Other main-actor code can run and change state (see Q5).

### Q85. Why does wrapping heavy work in `Task { }` still freeze the UI? `[Senior]`
`Task { }` **inherits the actor**, so a task created from main-actor code **runs its body on the main actor**, and heavy **synchronous** work inside it **still blocks the main thread**.

- **`async` doesn't mean "background."** Only work that pauses (awaits) frees the thread.
- **Fix:** put the heavy work in a `@concurrent` function (Swift 6.2), or a detached task.
- Before Swift 6.2 (or without the new default), a plain `nonisolated` async function also ran off the main actor.

```swift
@MainActor
func applyFilterTapped() {
    // ❌ Still on the main actor: the UI freezes during the filter
    Task {
        let filtered = ImageFilter.apply(to: image)   // synchronous, CPU-heavy
        imageView.image = filtered
    }

    // ✅ Run the heavy work off the main actor
    Task {
        let filtered = await ImageFilter.applyInBackground(to: image)
        imageView.image = filtered                    // back on the main actor
    }
}

enum ImageFilter {
    static func apply(to image: UIImage) -> UIImage { /* heavy work */ image }

    @concurrent   // Swift 6.2: always runs on the global thread pool
    static func applyInBackground(to image: UIImage) async -> UIImage {
        apply(to: image)
    }
}
```

**Follow-ups:**
- **How would you spot this in Instruments?** Long blocks of work on the main thread in Time Profiler, plus hangs.
- **Is `UIImage` safe to send to another thread?** `UIImage` is `Sendable`, so yes.
- **What's the most common version of this bug?** JSON decoding or image resizing inside a main-actor `Task`.

### Q86. How did Swift 6.2 change where nonisolated async functions run? `[Lead/Expert]`
Before Swift 6.2, a nonisolated async function **always left the caller's actor** for the thread pool, while in Swift 6.2 (with Approachable Concurrency) it **stays on the caller's actor** by default, and you mark it **`@concurrent`** to run it on the thread pool.

- **Before (Swift 5.7–6.1):** always hopped **off** the caller's actor. This surprised people and caused data-race errors when non-`Sendable` values were passed from the main actor.
- **Swift 6.2:** the `NonisolatedNonsendingByDefault` feature (turned on by "Approachable Concurrency" in Xcode 26) makes them **run on the caller's actor** (`nonisolated(nonsending)`).
- **`@concurrent`:** use it when you want the thread pool, like for heavy work.
- **Interview tip:** explain both behaviors, and say you'd check the project's build settings, because the same code runs differently depending on the setting.

```swift
// Swift 6.2 with Approachable Concurrency turned on
struct ImageProcessor {
    // Runs on whatever actor calls it (like the main actor)
    nonisolated func metadata(for data: Data) async -> ImageMetadata { ... }

    // Always runs on the global thread pool: use for heavy work
    @concurrent
    nonisolated func thumbnail(for data: Data) async -> UIImage { ... }
}
```

**Follow-ups:**
- **Why did Apple change it?** Most code doesn't need to leave the main actor, and the old hop caused confusing `Sendable` errors.
- **What's the risk of the new default?** Heavy work in a nonisolated function now runs on the main actor unless you mark it `@concurrent`.
- **How do you get the old behavior for one function?** Mark it `@concurrent`.

### Q87. What is default main-actor isolation? `[Lead/Expert]`
Swift 6.2 lets a module make **everything `@MainActor` by default** (build setting **"Default Actor Isolation = MainActor"**), which removes most annotations and data-race errors in UI-heavy app code.

- You then opt specific code **out** with `nonisolated`, `@concurrent`, or dedicated actors for background work.
- New Xcode 26 app projects turn these settings on. Existing projects keep their old behavior until you change them.

```swift
// With Default Actor Isolation = MainActor, this class is @MainActor automatically
final class FeedViewModel {
    var posts: [Post] = []
    func reload() async { posts = await api.fetchPosts() }
}

// Opt out for background work
@concurrent
func decodeFeed(_ data: Data) async throws -> [Post] {
    try JSONDecoder().decode([Post].self, from: data)
}
```

**Follow-ups:**
- **Is this good for a networking package?** Usually not. Libraries should stay nonisolated, and app targets use the main-actor default.
- **What's a common surprise after turning it on?** Heavy code now runs on the main actor until you mark it `@concurrent`.
- **Can different modules use different defaults?** Yes, it's a per-module setting.

### Q88. Can you rely on thread-local storage or `Thread.current` in async code? `[Lead/Expert]`
**No**: a task can **continue on a different thread** after any `await`, so anything tied to a thread is unreliable, and you use **task-local values** (`@TaskLocal`, Q91) instead.

- Unreliable: thread dictionaries, `Thread.current` checks, and thread-bound locks held across `await`.
- Swift 6 doesn't allow `Thread.current` inside async functions.
- **Never hold a lock** (`NSLock`, `os_unfair_lock`) across an `await`.

```swift
// ❌ The lock may be unlocked on a different thread than it was locked on
func update() async {
    lock.lock()
    await save()          // may continue on another thread
    lock.unlock()
}

// ✅ Use an actor for shared state, and task-locals for per-request context
actor Store {
    func update() async { await save() }
}
```

**Follow-ups:**
- **Why is holding a lock across `await` dangerous?** The thread may be reused by another task, causing deadlocks, or the unlock may happen on another thread.
- **What replaces thread-local logging context?** `@TaskLocal` values.
- **Is a short lock with no `await` inside OK?** Yes, `Mutex` or `OSAllocatedUnfairLock` for quick sync work is fine.

### Q89. What does `Task.yield()` do? `[Senior]`
`Task.yield()` **briefly pauses the current task** so **other tasks get a chance to run** on the thread, then continues.

- Useful inside **long loops of sync work** in async functions (Q56).
- It's **not** a way to move heavy work off the main actor.
- There's no guarantee another task runs. It's only a chance.

```swift
func indexAllDocuments(_ docs: [Document]) async {
    for (i, doc) in docs.enumerated() {
        index(doc)                              // sync work
        if i.isMultiple(of: 50) {
            await Task.yield()                  // let other tasks run
        }
    }
}
```

**Follow-ups:**
- **Does `Task.yield()` help on the main actor?** It lets other main-actor work run in between, but the total work is still on the main thread.
- **Is it the same as `Task.sleep(0)`?** Similar effect, but `yield()` states the intent clearly and doesn't throw.
- **Should you combine it with cancellation checks?** Yes, check cancellation at the same points.

## 12. Priorities, Task-Local Values, Clocks & Sleeping

### Q90. How do task priorities work? `[Senior]`
A task's priority is a **scheduling hint** (`.high`, `.medium`, `.low`, `.background`) that **children inherit**, and the runtime **raises a low priority** when high-priority work is waiting on it.

- `TaskPriority` values: `.high`/`.userInitiated`, `.medium`, `.low`/`.utility`, `.background`.
- `Task { }` inherits the creator's priority. `Task(priority:)` sets it.
- **Priority escalation:** if a high-priority task awaits lower-priority work, that work is boosted to avoid "priority inversion."
- **It's a hint**, not a promise about order.

```swift
Task(priority: .background) {
    await cache.pruneExpiredEntries()      // low-importance cleanup
}

print(Task.currentPriority)                // the current task's priority
```

**Follow-ups:**
- **What is priority inversion?** High-priority work stuck waiting on low-priority work.
- **Does `.high` guarantee my task runs first?** No.
- **Does `Task.detached` inherit priority?** No, you set it or it uses the default.

### Q91. What are task-local values? `[Lead/Expert]`
Task-local values are **values attached to a task** (and **inherited by its children** and `Task { }`), like thread-local storage, but **safe for async code**.

- Good for: request IDs, logging context, tracing, and test configuration.
- **Not** a general way to share app state or inject dependencies.
- `Task.detached` does **not** inherit them.

```swift
enum RequestContext {
    @TaskLocal static var requestID: String?
}

func handleCheckout() async throws {
    try await RequestContext.$requestID.withValue(UUID().uuidString) {
        try await validateCart()     // can read RequestContext.requestID
        try await chargeCard()       // child tasks see the same value
    }
}

func log(_ message: String) {
    print("[\(RequestContext.requestID ?? "-")] \(message)")
}
```

**Follow-ups:**
- **Can you change a task-local value directly?** No. You bind a new value for a scope with `withValue`.
- **What happens after `withValue` ends?** The old value comes back.
- **Why not use a global variable for the request ID?** Concurrent requests would overwrite each other's ID.

### Q92. How do you sleep in async code? `[Fundamental]`
Use **`try await Task.sleep(for:)`**, which **pauses without blocking a thread** and **throws `CancellationError`** if the task is cancelled.

- **Never** use `Thread.sleep` or `sleep()` in async code. They block.

```swift
try await Task.sleep(for: .seconds(2))                 // iOS 16+
try await Task.sleep(for: .milliseconds(300), tolerance: .milliseconds(50))
try await Task.sleep(nanoseconds: 2_000_000_000)       // iOS 13+
try await Task.sleep(until: .now + .seconds(5), clock: .continuous)
```

**Follow-ups:**
- **What is `tolerance` for?** It lets the system group timers together to save battery.
- **Why does `Task.sleep` throw?** So cancellation can stop the wait right away.
- **What's wrong with `try?` here?** It hides cancellation (see Q57).

### Q93. What is the difference between `ContinuousClock` and `SuspendingClock`? `[Senior]`
**`ContinuousClock` keeps counting while the device sleeps**, so use it for real-world timeouts, while **`SuspendingClock` pauses during sleep**, so use it to measure active work.

- Clocks can also measure how long work takes.

```swift
let elapsed = try await ContinuousClock().measure {
    try await api.fetchCatalog()
}
print("Catalog loaded in \(elapsed)")

try await Task.sleep(for: .seconds(30), clock: .continuous)   // counts device sleep too
```

**Follow-ups:**
- **Which clock for a "code expires in 5 minutes" timer?** `ContinuousClock`, because real time passes while the device sleeps.
- **Which clock for benchmarking?** `SuspendingClock` (or `ContinuousClock` for short tests where the device stays awake).
- **Why use clocks instead of `Date`?** Clocks don't jump when the user changes the system time.

### Q94. How do you make time-based async code testable? `[Lead/Expert]`
**Inject a clock** (`any Clock<Duration>`) instead of calling `Task.sleep` directly, so **production uses a real clock** and **tests use a fake clock** that moves time forward instantly.

- Production: `ContinuousClock()`.
- Tests: a controllable clock like `TestClock` or `ImmediateClock` from Point-Free's swift-clocks.

```swift
@MainActor
@Observable
final class OTPViewModel {
    private(set) var secondsRemaining = 30
    private let clock: any Clock<Duration>

    init(clock: any Clock<Duration> = ContinuousClock()) {   // real clock by default
        self.clock = clock
    }

    func startCountdown() async {
        while secondsRemaining > 0 {
            do {
                try await clock.sleep(for: .seconds(1))       // uses the injected clock
            } catch {
                return                                        // cancelled
            }
            secondsRemaining -= 1
        }
    }
}
// The test is in Q122.
```

**Follow-ups:**
- **Why not just wait in the test?** A 30-second test is slow and can still be flaky.
- **What's the difference between `TestClock` and `ImmediateClock`?** `TestClock` moves only when you advance it. `ImmediateClock` never waits.
- **Is this the same idea as injecting a network client?** Yes, time is just another dependency.

### Q95. How do you run periodic work with async/await? `[Senior]`
Run a **`while !Task.isCancelled` loop** that **does the work and then sleeps**, inside a stored `Task` that you **cancel to stop**.

- `try?` on the sleep is OK here, because the `while` check ends the loop right after.
- In SwiftUI, prefer `.task { }`, which cancels the loop when the view disappears.
- **Alternative:** `AsyncTimerSequence` from swift-async-algorithms.

```swift
@MainActor
final class LiveScoresViewModel {
    private var pollingTask: Task<Void, Never>?

    func startPolling() {
        pollingTask?.cancel()
        pollingTask = Task { [weak self] in
            while !Task.isCancelled {
                await self?.refreshScores()
                try? await Task.sleep(for: .seconds(15))   // ends early on cancellation, then the loop exits
            }
        }
    }

    func stopPolling() {
        pollingTask?.cancel()
        pollingTask = nil
    }

    private func refreshScores() async { /* fetch and update state */ }
}
```

**Follow-ups:**
- **Why `[weak self]`?** So the loop doesn't keep the view model alive forever (see Q108).
- **Is this loop still a leak risk?** `self?.refreshScores()` holds `self` only during each call, so the view model can be freed between calls.
- **How would you write it with `AsyncTimerSequence`?** `for await _ in AsyncTimerSequence(interval: .seconds(15), clock: .continuous) { ... }`.

## 13. Networking with Async/Await

### Q96. What async APIs does `URLSession` provide? `[Fundamental]`
`URLSession` has async methods for **data**, **downloads**, **uploads**, and **streaming bytes**, and they **all cancel automatically**, throwing `URLError(.cancelled)`.

```swift
let (data, response) = try await URLSession.shared.data(from: url)
let (data2, response2) = try await URLSession.shared.data(for: request)
let (fileURL, response3) = try await URLSession.shared.download(from: url)   // move the file before returning
let (body, response4) = try await URLSession.shared.upload(for: request, from: payload)
let (bytes, response5) = try await URLSession.shared.bytes(from: url)       // stream bytes or lines

// Per-task delegate for auth challenges, metrics, or progress (iOS 15+)
let (data3, _) = try await URLSession.shared.data(for: request, delegate: progressDelegate)
```

**Follow-ups:**
- **Why move the downloaded file right away?** It's a temporary file that the system may delete.
- **Does `data(from:)` check the HTTP status code?** No. A 404 is still a "success," so check it yourself.
- **What is `bytes(from:)` good for?** Streaming responses, like server-sent events or line-by-line data.

### Q97. Write a generic async API client. `[Senior]`
Make an **`Endpoint<Response>`** type that knows its path and response type, and an **`APIClient.send`** that **builds the request, awaits the data, checks the status code, and decodes**.

```swift
enum APIError: Error {
    case invalidResponse
    case httpStatus(Int, Data)
    case decoding(Error)
}

struct Endpoint<Response: Decodable> {
    var path: String
    var method = "GET"
    var body: Data?
}

struct APIClient {
    let baseURL: URL
    var session: URLSession = .shared
    var decoder = JSONDecoder()

    func send<Response>(_ endpoint: Endpoint<Response>) async throws -> Response {
        // 1. Build the request
        var request = URLRequest(url: baseURL.appending(path: endpoint.path))
        request.httpMethod = endpoint.method
        request.httpBody = endpoint.body
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")

        // 2. Send it
        let (data, response) = try await session.data(for: request)

        // 3. Check the status code
        guard let http = response as? HTTPURLResponse else { throw APIError.invalidResponse }
        guard (200..<300).contains(http.statusCode) else {
            throw APIError.httpStatus(http.statusCode, data)
        }

        // 4. Decode
        do {
            return try decoder.decode(Response.self, from: data)
        } catch {
            throw APIError.decoding(error)
        }
    }
}

// Usage
extension Endpoint where Response == [Product] {
    static var products: Endpoint { Endpoint(path: "products") }   // generic types can't have static stored properties
}
let products = try await client.send(.products)
```

**Follow-ups:**
- **Why put the response type on the endpoint?** The compiler then knows what `send` returns, with no casting.
- **How would you add auth?** Get a valid token from a token store before sending (see Q100).
- **How would you test it?** Inject a `URLSession` with a mock `URLProtocol`, or put the client behind a protocol.

### Q98. How do you load a screen's data concurrently while tolerating optional failures? `[Senior]`
Use **`async let`** for every request, with **`try`** on the **required** ones and **`try?`** on the **optional** ones, so optional failures just become `nil`.

```swift
func loadHome() async throws -> HomeData {
    async let profile = api.send(.profile)               // required
    async let feed = api.send(.feed)                     // required
    async let banners = try? api.send(.banners)          // optional: failure becomes nil

    return try await HomeData(
        profile: profile,
        feed: feed,
        banners: banners ?? []                           // show no banners instead of failing
    )
}
```

**Follow-ups:**
- **What happens if `feed` fails?** The function throws, and the other requests are cancelled.
- **Does `try?` hide cancellation for `banners`?** Yes, but the whole scope is being cancelled then anyway.
- **How would you show partial content when `feed` fails too?** Use `Result` values (see Q61).

### Q99. How do you report upload or download progress with async/await? `[Senior]`
`data(for:)` **doesn't report progress**, so use a **per-task delegate**, **`bytes(for:)` while counting**, or a **classic download task bridged into an `AsyncStream`**.

- **Per-task `delegate:`** (`URLSessionTaskDelegate`): get progress callbacks for that one request.
- **`bytes(for:)`:** count bytes while iterating (Q77).
- **Download task + delegate:** send progress events into an `AsyncStream`.

```swift
final class UploadProgressDelegate: NSObject, URLSessionTaskDelegate {
    let onProgress: @Sendable (Double) -> Void

    init(onProgress: @escaping @Sendable (Double) -> Void) { self.onProgress = onProgress }

    // Called as the request body is sent
    func urlSession(_ session: URLSession, task: URLSessionTask, didSendBodyData bytesSent: Int64,
                    totalBytesSent: Int64, totalBytesExpectedToSend: Int64) {
        guard totalBytesExpectedToSend > 0 else { return }
        onProgress(Double(totalBytesSent) / Double(totalBytesExpectedToSend))
    }
}

let delegate = UploadProgressDelegate { print("Upload: \(Int($0 * 100))%") }
let (_, response) = try await URLSession.shared.upload(for: request, from: payload, delegate: delegate)
```

**Follow-ups:**
- **How do you get download progress?** Observe the task's `progress` from `urlSession(_:didCreateTask:)` (iOS 16+), or use a download task with a delegate.
- **Why is byte-by-byte counting slow?** Each byte is a separate async step. Read in chunks for large files.
- **How do you show progress in SwiftUI?** Send values into an `AsyncStream` or update an `@Observable` model on the main actor.

### Q100. How do you refresh an expired auth token only once when many requests fail together? `[Lead/Expert]`
Use an **actor that stores the in-flight refresh `Task`**: the **first caller starts it**, and **everyone else awaits the same task**, so only **one** refresh request is made.

- **Key detail:** store the `Task` **before** the first `await`. Otherwise, a second caller can slip in during the `await` and start another refresh (actor reentrancy, see the Concurrency file).

```swift
actor TokenStore {
    private var token: Token
    private var refreshTask: Task<Token, Error>?
    private let authAPI: AuthAPI

    init(initialToken: Token, authAPI: AuthAPI) {
        self.token = initialToken
        self.authAPI = authAPI
    }

    func validToken() async throws -> Token {
        if let refreshTask { return try await refreshTask.value }   // join a refresh in progress
        if !token.isExpired { return token }
        return try await refresh()
    }

    func refresh() async throws -> Token {
        if let refreshTask { return try await refreshTask.value }

        let task = Task { [authAPI, token] in
            try await authAPI.refresh(using: token.refreshToken)
        }
        refreshTask = task                 // stored BEFORE the first await
        defer { refreshTask = nil }

        token = try await task.value
        return token
    }
}

// In the API client: on a 401, call tokenStore.refresh(), then retry the request once.
```

**Follow-ups:**
- **What happens if the refresh fails?** All waiting callers get the error, and the user is usually logged out.
- **Why retry only once?** To avoid an endless loop if the new token is also rejected.
- **Why an actor and not a class with a lock?** The actor protects `token` and `refreshTask` across `await`s without manual locking.

### Q101. Can you use async/await with background URLSession transfers? `[Lead/Expert]`
**No**: background sessions (transfers that continue while the app is suspended or closed) **need the delegate-based API**, and the async convenience methods **aren't supported** for them.

- Use a background `URLSessionConfiguration` with a delegate.
- Handle `application(_:handleEventsForBackgroundURLSession:completionHandler:)`.
- If you like, share the results with the rest of the app through an `AsyncStream` or state updates.

```swift
final class BackgroundDownloader: NSObject, URLSessionDownloadDelegate {
    private lazy var session: URLSession = {
        let config = URLSessionConfiguration.background(withIdentifier: "com.app.downloads")
        return URLSession(configuration: config, delegate: self, delegateQueue: nil)
    }()

    let (events, continuation) = AsyncStream.makeStream(of: URL.self)   // async view for the app

    func start(_ url: URL) {
        session.downloadTask(with: url).resume()        // delegate-based, not async
    }

    func urlSession(_ session: URLSession, downloadTask: URLSessionDownloadTask,
                    didFinishDownloadingTo location: URL) {
        let saved = moveToDocuments(location)           // move the temp file right away
        continuation.yield(saved)
    }
}
```

**Follow-ups:**
- **Why don't async methods work here?** The app may be terminated, and an `await` can't survive that.
- **What must you do in `handleEventsForBackgroundURLSession`?** Store the completion handler and call it when the session finishes its events.
- **Can you upload from memory in the background?** No. Background uploads must come from a file.

## 14. Async/Await in SwiftUI & UIKit

### Q102. How do you run async work tied to a SwiftUI view's lifetime? `[Fundamental]`
Use **`.task { }`**, which **starts when the view appears** and is **cancelled when it disappears**, **`.task(id:)`** to **restart when a value changes**, and **`.refreshable`** for pull-to-refresh.

- More details are in the SwiftUI file (Section 9).

```swift
struct OrdersView: View {
    @State private var model = OrdersModel()
    @State private var searchText = ""

    var body: some View {
        List(model.orders) { OrderRow(order: $0) }
            .task {                                   // starts on appear, cancelled on disappear
                await model.loadIfNeeded()
            }
            .task(id: searchText) {                   // cancels the old one and restarts when searchText changes
                try? await Task.sleep(for: .milliseconds(300))
                guard !Task.isCancelled else { return }
                await model.search(searchText)
            }
            .refreshable {                            // the spinner stays until the work finishes
                await model.reload()
            }
            .searchable(text: $searchText)
    }
}
```

**Follow-ups:**
- **Why is `.task(id:)` a free debounce?** Each keystroke cancels the previous task's sleep.
- **Why `loadIfNeeded()` and not `load()`?** `.task` runs again every time the view reappears.
- **Which actor does `.task` run on?** The main actor, because `View` is main-actor isolated.

### Q103. How do you manage tasks in a UIKit view controller? `[Senior]`
**Store the `Task`**, **start it when the view appears**, and **cancel it when the view disappears**, because UIKit has **no automatic `.task`**.

```swift
final class OrdersViewController: UIViewController {
    private let viewModel: OrdersViewModel
    private var loadTask: Task<Void, Never>?

    init(viewModel: OrdersViewModel) {
        self.viewModel = viewModel
        super.init(nibName: nil, bundle: nil)
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) { fatalError() }

    override func viewIsAppearing(_ animated: Bool) {
        super.viewIsAppearing(animated)
        loadTask = Task { [weak self] in
            await self?.viewModel.load()      // start when visible
            self?.render()
        }
    }

    override func viewDidDisappear(_ animated: Bool) {
        super.viewDidDisappear(animated)
        loadTask?.cancel()                    // UIKit doesn't cancel for you
        loadTask = nil
    }

    private func render() { /* update UI from viewModel state */ }
}
```

**Follow-ups:**
- **Why `viewIsAppearing`?** The view has its size and traits by then, and it runs every time the view appears.
- **Why `[weak self]`?** So a slow request doesn't keep a closed screen alive.
- **Does `[weak self]` make `self` nil during `load()`?** No. `self?.viewModel.load()` keeps `self` for that call only.

### Q104. Should view model methods be `async`, or should they create `Task`s internally? `[Lead/Expert]`
**Prefer `async` methods**: the **caller decides** how to run them (SwiftUI `.task`, UIKit `Task`, or a test's `await`), and **cancellation flows through**.

- Internal `Task`s are sometimes needed (debounced search, polling, reacting to property changes).
- If you create one, **keep the handle**, so you can cancel it and tests can await it.

```swift
@MainActor
@Observable
final class ProfileViewModel {
    private(set) var profile: Profile?

    // ✅ Testable: `await viewModel.load()`
    func load() async {
        profile = try? await api.fetchProfile()
    }

    // ⚠️ Harder to test: when is it done?
    func loadFireAndForget() {
        Task { profile = try? await api.fetchProfile() }
    }
}
```

**Follow-ups:**
- **How does a test wait for `loadFireAndForget`?** It can't easily. It would need polling or a stored task (see Q119).
- **When is an internal `Task` the right choice?** When the view model reacts to its own changes, like search text.
- **Does an `async` method still update UI safely?** Yes, the view model is `@MainActor`.

### Q105. How do you prevent duplicate submissions (double taps) with async actions? `[Senior]`
Keep an **`isSubmitting` flag** on a **`@MainActor` view model**, **check and set it before the first `await`**, and **disable the button** while it's true.

- Because the view model is `@MainActor`, the check and the set happen **before any pause**, so it's race-free.
- For real safety, also make the server endpoint **idempotent** (for example, with an idempotency key).

```swift
@MainActor
@Observable
final class CheckoutViewModel {
    private(set) var isSubmitting = false

    func placeOrder() async {
        guard !isSubmitting else { return }    // ignore taps while a request is running
        isSubmitting = true                    // set before the first await
        defer { isSubmitting = false }
        do {
            try await api.placeOrder(cart)
        } catch {
            // show error state
        }
    }
}

// SwiftUI
Button("Place Order") { Task { await viewModel.placeOrder() } }
    .disabled(viewModel.isSubmitting)
```

**Follow-ups:**
- **Why isn't disabling the button enough?** Two taps can arrive before the UI updates.
- **What breaks if you set the flag after the `await`?** A second tap can start a second order during the pause.
- **What is an idempotency key?** A unique ID per order, so the server ignores duplicates.

### Q106. How do you bridge async work into an `@objc` target-action or delegate callback that must return a value synchronously? `[Lead/Expert]`
You **can't wait synchronously** (Q22), so **return a placeholder now and update later**, **use the API's async variant** if it has one, or **start a `Task` and call the completion handler when done**.

- Many delegate protocols gained async methods, like `UNUserNotificationCenterDelegate` and WebKit navigation delegates.

```swift
// Option 1: use the async delegate variant
func userNotificationCenter(_ center: UNUserNotificationCenter,
                            didReceive response: UNNotificationResponse) async {
    await router.handle(notification: response.notification)
}

// Option 2: return something now, update later
func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {
    let cell = tableView.dequeueReusableCell(withIdentifier: "Cell", for: indexPath) as! ImageCell
    let item = items[indexPath.row]
    cell.photoView.image = placeholder                      // return right away
    cell.loadTask = Task {                                   // update later
        cell.photoView.image = await loader.image(for: item)
    }
    return cell
}
```

**Follow-ups:**
- **What's the cell-reuse bug in option 2?** A reused cell may show the wrong image, so cancel the old task in `prepareForReuse`.
- **Why not block with a semaphore?** It freezes or deadlocks the main thread (Q22).
- **How do completion-based delegate methods fit in?** Start a `Task`, and call the completion handler at the end.

## 15. Memory Management with Tasks

### Q107. Does a `Task` retain the objects it captures? `[Senior]`
**Yes**: a `Task` closure **holds strong references** to everything it uses, **including `self`**, and keeps them alive **until the task finishes**.

- `Task` closures allow **implicit `self`**, so the capture is easy to miss.
- **Short tasks:** usually fine. The object is freed a little later.
- **Long-running tasks** (endless loops, stream loops, polling): the object can **never** be freed.

```swift
final class ProfileScreen {
    var name = ""

    func load() {
        Task {
            let profile = try await api.fetchProfile()
            name = profile.name          // implicit self: the Task holds self strongly
        }
    }
}
// The screen stays alive until fetchProfile() finishes. Fine for one request.
```

**Follow-ups:**
- **Why does `Task` allow implicit `self`?** Because most tasks finish soon, so holding `self` is usually harmless.
- **When does it become a real leak?** When the task never ends, like an endless `for await` loop.
- **How do you spot it?** Use the Memory Graph debugger, or put a log in `deinit` and see if it runs.

### Q108. How do you avoid leaks in long-running tasks? `[Lead/Expert]`
Capture **`[weak self]`** and **unwrap `self` inside the loop**, so the task holds `self` **only for one step at a time**, and **cancel the task** when the owner goes away.

```swift
final class FeedViewModel {
    private var updatesTask: Task<Void, Never>?

    func startObserving(_ updates: AsyncStream<FeedUpdate>) {
        updatesTask = Task { [weak self] in
            for await update in updates {
                guard let self else { return }   // strong only for this one step
                self.apply(update)
            }
        }
    }

    deinit {
        updatesTask?.cancel()                    // works, because the task doesn't keep self alive
    }

    private func apply(_ update: FeedUpdate) { }
}
```

- **Common mistake:** unwrapping `self` **before** the loop.

```swift
updatesTask = Task { [weak self] in
    guard let self else { return }   // ❌ strong `self` for the WHOLE loop: the leak is back
    for await update in updates {
        self.apply(update)
    }
}
```

**Follow-ups:**
- **Why doesn't `[weak self]` alone fix it?** Unwrapping it once before the loop makes it strong again for the whole loop.
- **Does the task stop when `self` is freed?** Only at the next value, when `guard let self` fails. `deinit` cancelling it is what stops it right away.
- **What if `updates` never sends again?** The task waits forever, so cancelling in `deinit` matters.

### Q109. Why might `deinit { task.cancel() }` never run? `[Senior]`
If the task **holds `self` strongly**, `self` **can't be freed** while the task runs, so `deinit` (where you planned to cancel the task) **never runs**: each one waits for the other.

- **Fixes:**
  - Capture `self` weakly (Q108).
  - Cancel based on **lifecycle events** (`viewDidDisappear`, SwiftUI `.task`), not `deinit`.

```swift
final class Ticker {
    private var task: Task<Void, Never>?

    func start() {
        task = Task {
            while !Task.isCancelled {
                tick()                                   // ❌ strong self, forever
                try? await Task.sleep(for: .seconds(1))
            }
        }
    }

    deinit { task?.cancel() }                            // never runs: the task keeps self alive
    private func tick() { }
}
```

**Follow-ups:**
- **Why is this a cycle?** `self` owns the task, and the task holds `self`.
- **Would `stop()` called from the screen help?** Yes. Cancelling from a lifecycle event breaks the cycle.
- **Does SwiftUI's `.task` have this problem?** No. It's cancelled when the view disappears.

### Q110. Do you always need `[weak self]` in a `Task`? `[Senior]`
**No**: for **short, one-off work** (one request, then update state) a **strong capture is fine** and often clearer, and you use **`[weak self]`** for **long-running** tasks or work that's **pointless once the owner is gone**.

- With a strong capture, the object simply lives until the request finishes.
- SwiftUI's `.task` and structured concurrency usually make this a non-issue.

```swift
// ✅ Fine: one request, then done
func save() {
    Task {
        try await api.save(draft)
        isSaved = true
    }
}

// ✅ [weak self]: long-running loop
func observe() {
    task = Task { [weak self] in
        for await event in events {
            self?.handle(event)
        }
    }
}
```

**Follow-ups:**
- **What's the cost of adding `[weak self]` everywhere?** Noise, plus `self?` checks that can quietly skip work.
- **When is a short task still a problem?** When it's slow and updates a closed screen, like showing an alert after dismissal.
- **Is `[weak self]` needed in SwiftUI `.task`?** No. Views are structs, and the task is cancelled with the view.

## 16. Common Patterns (Timeout, Retry, Debounce, Deduplication, Limited Concurrency)

### Q111. How do you add a timeout to an async operation? `[Lead/Expert]`
**Race the operation against a sleep** in a task group: whichever **finishes first wins**, and the other is **cancelled**.

- The operation **must respond to cancellation**. Otherwise the group still waits for it, even after the timeout fires.

```swift
struct TimeoutError: Error {}

func withTimeout<T: Sendable>(
    _ duration: Duration,
    operation: @escaping @Sendable () async throws -> T
) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask { try await operation() }        // racer 1: the real work
        group.addTask {                                // racer 2: the timer
            try await Task.sleep(for: duration)
            throw TimeoutError()
        }
        defer { group.cancelAll() }                    // cancel whichever is still running
        guard let result = try await group.next() else { throw TimeoutError() }
        return result
    }
}

// Usage
let config = try await withTimeout(.seconds(5)) {
    try await api.fetchConfig()
}
```

**Follow-ups:**
- **What if the operation ignores cancellation?** The timeout error is thrown only after the operation finally ends.
- **Why does `T` need to be `Sendable`?** The result moves from a child task to the parent.
- **Doesn't `URLSession` have its own timeout?** Yes, `timeoutInterval`, but this helper works for any async work.

### Q112. How do you retry with exponential backoff? `[Senior]`
**Loop**: try the operation, and on a **retryable** error, **sleep**, **double the delay**, and try again, up to a **maximum number of attempts**.

- **Never retry cancellation.**
- In production, add **jitter** (randomness), **cap the delay**, and don't retry **non-idempotent** requests (like "charge card").

```swift
func withRetry<T>(
    maxAttempts: Int = 3,
    initialDelay: Duration = .seconds(1),
    shouldRetry: (Error) -> Bool = { _ in true },
    operation: () async throws -> T
) async throws -> T {
    var attempt = 0
    var delay = initialDelay

    while true {
        attempt += 1
        do {
            return try await operation()
        } catch {
            let isCancellation = error is CancellationError
            guard attempt < maxAttempts, !isCancellation, shouldRetry(error) else { throw error }
            try await Task.sleep(for: delay)      // cancellation stops the retrying
            delay *= 2                            // 1s, 2s, 4s...
        }
    }
}

// Retry only temporary failures
let feed = try await withRetry(shouldRetry: { ($0 as? URLError)?.code == .timedOut }) {
    try await api.fetchFeed()
}
```

**Follow-ups:**
- **Why add jitter?** So thousands of phones don't all retry at the same moment.
- **Which errors are worth retrying?** Timeouts, lost connections, and 5xx/429 responses, but not 4xx or decoding errors.
- **Why should `URLError(.cancelled)` also stop retrying?** It's cancellation too. Add it to the check.

### Q113. How do you debounce with async/await (without Combine)? `[Senior]`
On each change, **cancel the previous task** and **start a new one that sleeps first**: if another change arrives during the sleep, the old task is cancelled before it searches.

- In SwiftUI, `.task(id: query)` with a short sleep does the same with less code (Q102).

```swift
@MainActor
@Observable
final class SearchViewModel {
    var query = "" { didSet { scheduleSearch() } }
    private(set) var results: [Movie] = []
    private(set) var searchTask: Task<Void, Never>?   // readable, so tests can await it

    private let api: MovieAPI
    private let clock: any Clock<Duration>

    init(api: MovieAPI, clock: any Clock<Duration> = ContinuousClock()) {
        self.api = api
        self.clock = clock
    }

    private func scheduleSearch() {
        searchTask?.cancel()                       // 1. cancel the previous pending search
        let currentQuery = query
        searchTask = Task {
            do {
                try await clock.sleep(for: .milliseconds(300))   // 2. the debounce wait
                results = try await api.search(currentQuery)     // 3. only runs if not cancelled
            } catch {
                // CancellationError: replaced by a newer query, so ignore
            }
        }
    }
}
```

**Follow-ups:**
- **Why capture `currentQuery`?** So the task searches the text from when it was scheduled.
- **Why is `try` (not `try?`) on the sleep important?** `try?` would hide cancellation and search anyway (Q57).
- **How do you test this quickly?** Inject `ImmediateClock` and await `searchTask` (Q119).

### Q114. How do you deduplicate concurrent requests for the same resource? `[Lead/Expert]`
Keep a **dictionary of in-flight `Task`s** in an **actor**: if a request for the same key is already running, **await that task** instead of starting another.

- Ten cells asking for the same avatar make **one** download.
- In production, use `NSCache` (it frees memory under pressure) and downsample images.

```swift
actor ImageLoader {
    private var cache: [URL: UIImage] = [:]
    private var inFlight: [URL: Task<UIImage, Error>] = [:]

    func image(for url: URL) async throws -> UIImage {
        if let cached = cache[url] { return cached }                           // 1. cached
        if let existing = inFlight[url] { return try await existing.value }    // 2. join the running request

        let task = Task<UIImage, Error> {                                      // 3. start a new one
            let (data, _) = try await URLSession.shared.data(from: url)
            guard let image = UIImage(data: data) else { throw URLError(.cannotDecodeContentData) }
            return image
        }
        inFlight[url] = task                       // store BEFORE awaiting (handles reentrancy)
        defer { inFlight[url] = nil }

        let image = try await task.value
        cache[url] = image
        return image
    }
}
```

**Follow-ups:**
- **Why store the task before the `await`?** During the `await`, another caller can enter the actor and must see the running task.
- **What if one caller cancels?** The shared task keeps running for the others, because unstructured tasks don't inherit cancellation.
- **How is this like the token refresh in Q100?** Same pattern: one shared task, many waiters.

### Q115. How do you process work items serially in order? `[Senior]`
Put jobs into an **`AsyncStream`** and have **one loop** read them and **await each job before starting the next**, so the order is guaranteed.

- Separate `Task`s (Q25) don't guarantee order.
- **Actors don't guarantee** this kind of order across `await`s either.

```swift
/// Runs submitted jobs one at a time, in the order they were added
final class SerialJobQueue: Sendable {
    private let continuation: AsyncStream<@Sendable () async -> Void>.Continuation

    init() {
        let (stream, continuation) = AsyncStream.makeStream(of: (@Sendable () async -> Void).self)
        self.continuation = continuation
        Task {
            for await job in stream {
                await job()                     // the next job starts only after this one finishes
            }
        }
    }

    func enqueue(_ job: @escaping @Sendable () async -> Void) {
        continuation.yield(job)
    }
}

// Usage: analytics events are uploaded strictly in order
queue.enqueue { await analytics.upload(eventA) }
queue.enqueue { await analytics.upload(eventB) }
```

**Follow-ups:**
- **Why don't actors keep this order?** While one call is paused at an `await`, the next call can start.
- **How would you stop the queue?** Call `continuation.finish()`, and the loop ends after the remaining jobs.
- **What if a job throws?** Catch errors inside the job, or the queue's design must decide whether to continue.

### Q116. How do you poll until a condition is met, with a deadline? `[Senior]`
Put a **polling loop** (check, then sleep) **inside the timeout helper** from Q111, so it stops when the **condition is met** or the **deadline passes**.

```swift
func waitForPaymentConfirmation(paymentID: String) async throws -> PaymentStatus {
    try await withTimeout(.seconds(60)) {                 // from Q111: overall deadline
        while true {
            let status = try await api.paymentStatus(paymentID)
            if status != .pending { return status }       // condition met
            try await Task.sleep(for: .seconds(2))        // cancellable wait between checks
        }
    }
}
```

**Follow-ups:**
- **How does the timeout stop the loop?** It cancels the task, and `Task.sleep` throws.
- **Why `try` and not `try?` on the sleep?** `try?` would keep the loop running after cancellation.
- **What's better than polling, if available?** Push updates, like a WebSocket or a push notification.

## 17. Testing Async Code

### Q117. How do you write async tests in XCTest and Swift Testing? `[Fundamental]`
**Mark the test `async`** and **`await` the code** directly, with **no expectations or sleeps** needed.

- That's a big win over callback-based code.

```swift
// XCTest
final class ProfileServiceTests: XCTestCase {
    func testFetchProfileDecodesResponse() async throws {
        let service = ProfileService(api: MockAPI(json: profileJSON))
        let profile = try await service.fetchProfile()
        XCTAssertEqual(profile.name, "Ana")
    }
}

// Swift Testing
import Testing

struct ProfileServiceSuite {
    @Test func fetchProfileDecodesResponse() async throws {
        let service = ProfileService(api: MockAPI(json: profileJSON))
        let profile = try await service.fetchProfile()
        #expect(profile.name == "Ana")
    }
}
```

**Follow-ups:**
- **What happens if the test throws?** The test fails and shows the error.
- **Do async tests run in parallel?** Swift Testing runs tests in parallel by default. XCTest runs them one by one unless configured.
- **Can XCTest and Swift Testing work together?** Yes, and Swift 6.4 improves how the two work together.

### Q118. How do you test `@MainActor` view models? `[Senior]`
**Mark the test suite `@MainActor`**, so the tests **run on the same actor** as the view model, and **await the view model's async methods**.

```swift
@MainActor
struct ProfileViewModelTests {
    @Test func loadSetsProfile() async {
        let viewModel = ProfileViewModel(api: MockProfileAPI(result: .success(.sample)))
        await viewModel.load()
        #expect(viewModel.profile == .sample)          // no await needed: same actor
    }

    @Test func loadFailureSetsError() async {
        let viewModel = ProfileViewModel(api: MockProfileAPI(result: .failure(URLError(.notConnectedToInternet))))
        await viewModel.load()
        #expect(viewModel.errorMessage != nil)
    }
}
```

**Follow-ups:**
- **What if the suite isn't `@MainActor`?** Every property read needs `await`, and setup gets noisy.
- **Does a `@MainActor` suite slow tests down?** Those tests run on the main actor, so they can't run in parallel with each other.
- **How do you inject the mock?** Through the initializer, as a protocol type.

### Q119. How do you test code that starts its own internal `Task`? `[Lead/Expert]`
**Best:** refactor so the work is an **`async` method** you can await (Q104). **Otherwise:** **expose the task handle** and **await it** in the test.

- **Avoid `Task.sleep` in tests** to "wait a bit." It's slow and flaky.

```swift
@MainActor
@Test func searchShowsResultsAfterDebounce() async {
    let viewModel = SearchViewModel(api: MockMovieAPI(results: [.sample]), clock: ImmediateClock())
    viewModel.query = "Dune"                // starts the internal task (Q113)
    await viewModel.searchTask?.value       // wait for that task to finish
    #expect(viewModel.results == [.sample])
}
```

**Follow-ups:**
- **Why `ImmediateClock`?** So the 300 ms debounce takes no time in the test.
- **Isn't exposing `searchTask` bad design?** `private(set)` keeps it read-only, and it's a small price for a reliable test.
- **What if you can't change the code at all?** Use `confirmation` or poll for the state with a timeout, as a last resort.

### Q120. How do you test callback-based or event-based code in Swift Testing? `[Senior]`
Use **`confirmation`**, which checks that **an event happened a certain number of times** before the closure returns.

- `confirmation` replaces `XCTestExpectation` for "this happened N times" checks.
- The event must happen **before the closure returns**, so the code under test should be awaitable.

```swift
@Test func uploaderReportsCompletionOnce() async {
    await confirmation("completion called", expectedCount: 1) { confirm in
        let uploader = Uploader(onComplete: { confirm() })
        await uploader.upload(.sample)     // confirm() must be called before this closure returns
    }
}
```

**Follow-ups:**
- **What if the callback fires later, after the closure returns?** The test fails, so bridge it with a continuation and await it.
- **How do you check "never called"?** Use `expectedCount: 0`.
- **What's the XCTest equivalent?** `XCTestExpectation` with `await fulfillment(of:)`.

### Q121. How do you test cancellation behavior? `[Lead/Expert]`
**Start the work in a `Task`**, **cancel it**, then check that it **throws `CancellationError`** and that **no side effects happened**.

```swift
@Test func cancellingStopsTheDownload() async {
    let api = SlowMockAPI()                       // sleeps 10s with Task.sleep (cancellable)
    let task = Task { try await api.downloadLargeFile() }

    task.cancel()

    await #expect(throws: CancellationError.self) {
        try await task.value
    }
    #expect(await api.completedDownloads == 0)    // nothing was saved
}
```

**Follow-ups:**
- **Why does the mock use `Task.sleep`?** So it responds to cancellation like real async work.
- **What else should you check?** That cleanup ran, like a temp file being deleted.
- **What if the code uses `URLSession`?** Expect `URLError(.cancelled)` instead of `CancellationError`.

### Q122. How do you test time-based code without waiting in real time? `[Lead/Expert]`
**Inject a `TestClock`** and **move time forward manually** with `advance(by:)`, so a 30-second countdown is tested in milliseconds.

- Async scheduling can still add some randomness. Point-Free's `swift-concurrency-extras` (`withMainSerialExecutor`) can make such tests reliable.

```swift
import Clocks   // Point-Free swift-clocks

```

**Follow-ups:**
- **What else can you test this way?** Debounce, timeouts, retries, and polling.
- **Why might it still be flaky?** The task may not have reached its `sleep` before you advance the clock.
- **Can you write your own test clock?** Yes, by conforming to `Clock`, but swift-clocks saves the work.

## 18. Migration & Interoperability

### Q123. How do you migrate completion-handler APIs to async/await? `[Senior]`
Use **Xcode's refactorings** to add async versions, **make the async version the real one**, and **mark the old API deprecated** so the compiler guides callers over.

- Xcode refactorings (right-click → **Refactor**):
  - **Convert Function to Async:** rewrites the function.
  - **Add Async Alternative:** adds an async version and makes the old one call it.
  - **Add Async Wrapper:** adds an async version that wraps the old one with a continuation.

```swift
// New main API
func fetchUser(id: Int) async throws -> User {
    let (data, _) = try await session.data(from: userURL(id))
    return try decoder.decode(User.self, from: data)
}

// Old API kept for a while for existing callers
@available(*, deprecated, renamed: "fetchUser(id:)")
func fetchUser(id: Int, completion: @escaping @Sendable (Result<User, Error>) -> Void) {
    Task {
        do { completion(.success(try await fetchUser(id: id))) }
        catch { completion(.failure(error)) }
    }
}
```

**Follow-ups:**
- **Which direction should the wrapping go?** The old API should call the new async one, so the logic lives in one place.
- **What does `renamed:` give you?** Xcode offers a fix-it that points callers to the new API.
- **Which thread does the old completion run on now?** Wherever the `Task` runs, so document it or hop to the main actor.

### Q124. What are async/await equivalents of common GCD patterns? `[Senior]`
Main queue becomes **`@MainActor`**, background queues become **`@concurrent`** functions, `DispatchGroup` becomes **`async let` / task groups**, and serial queues guarding state become **actors**.

| GCD | Swift Concurrency |
|---|---|
| `DispatchQueue.main.async { }` | `@MainActor` functions or types, `await MainActor.run { }` |
| `DispatchQueue.global().async { }` | `@concurrent` async function, `Task.detached`, or nonisolated async (before 6.2) |
| `DispatchGroup` (wait for many) | `async let`, task groups |
| Serial queue protecting state | `actor` |
| `DispatchSemaphore` limiting concurrency | Task group with N running (Q35) |
| `asyncAfter(deadline:)` | `try await Task.sleep(for:)` |
| `DispatchWorkItem.cancel()` | `task.cancel()` plus cancellation checks |
| Barrier for reader/writer | `actor` (or a lock for quick sync access) |

```swift
// GCD
let group = DispatchGroup()
group.enter(); loadA { a = $0; group.leave() }
group.enter(); loadB { b = $0; group.leave() }
group.notify(queue: .main) { show(a, b) }

// Swift Concurrency
async let a = loadA()
async let b = loadB()
await show(a, b)
```

**Follow-ups:**
- **What replaces a serial queue used as a lock?** An actor, or a `Mutex` for quick sync work.
- **Is an actor exactly like a serial queue?** No. It can run other calls while one is paused at an `await`.
- **What about `DispatchQueue.concurrentPerform`?** A task group, or keep `concurrentPerform` for pure CPU loops.

### Q125. How do you bridge between Combine and async/await? `[Senior]`
**Publisher to async:** use **`publisher.values`** (an `AsyncSequence`), and **async to publisher:** wrap the call in **`Deferred { Future { ... } }`** with a `Task` inside.

- **Watch out:**
  - `.values` can drop values from fast "hot" publishers.
  - `Future` doesn't cancel the inner `Task` when the subscriber cancels.
- Full examples are in the Combine file (Section 19).

```swift
// Publisher → async
for await temperature in sensor.$temperature.values {
    print(temperature)
}

// Async → publisher
func profilePublisher() -> AnyPublisher<Profile, Error> {
    Deferred {
        Future { promise in
            Task {
                do { promise(.success(try await api.fetchProfile())) }
                catch { promise(.failure(error)) }
            }
        }
    }
    .eraseToAnyPublisher()
}
```

**Follow-ups:**
- **Why `Deferred`?** `Future` starts work right away. `Deferred` waits until someone subscribes.
- **How do you get just the first value of a publisher?** `for await value in publisher.values { return value }`, or a `firstValue()` helper.
- **Which should new code use?** Async/await, with Combine only where operators like `combineLatest` really help.

### Q126. How do you modernize a delegate-heavy SDK wrapper? `[Lead/Expert]`
Turn **one-shot** callbacks into **`async` functions** (continuations, Q67), and **multi-value** callbacks into **`AsyncStream`s** (Q73), while **keeping the delegate internal**.

- Expose only async APIs.
- Decide how overlapping calls work: one request at a time, or a queue.

```swift
public final class ScannerClient {
    private let delegateBridge = ScannerDelegateBridge()   // internal, owns the delegate

    // One-shot: connect → async function
    public func connect() async throws -> Device {
        try await delegateBridge.connect()                  // continuation inside
    }

    // Many values: scans → AsyncStream
    public func scans() -> AsyncStream<ScanResult> {
        delegateBridge.scanStream()                         // yields from delegate callbacks
    }
}
```

**Follow-ups:**
- **Why hide the delegate?** So callers can't mix both styles and confuse the state.
- **What about calls made at the same time?** Reject them, queue them, or share one result, and document the choice.
- **How do you clean up the SDK when a stream stops?** In `onTermination`.

### Q127. Does async/await replace every completion handler? `[Senior]`
**Mostly, for one-shot results**, but **values over time** fit `AsyncSequence` better, **sync APIs** must stay sync, some **system APIs stay delegate-based**, and **libraries for older OS versions** may keep completion handlers.

- **Values over time:** `AsyncSequence` (or Combine).
- **Sync APIs callers can't await:** like `UITableViewDataSource`.
- **Delegate-based system APIs:** like background `URLSession`.

```swift
func fetchUser() async throws -> User { ... }           // ✅ one result: async

func locationUpdates() -> AsyncStream<CLLocation> { ... }   // ✅ many results: stream

func tableView(_ tableView: UITableView,               // ❌ must stay sync
               numberOfRowsInSection section: Int) -> Int { items.count }
```

**Follow-ups:**
- **When would you keep a completion handler in a library?** When you must support callers who can't use async.
- **Is a callback ever simpler?** For a quick fire-once event with no result, sometimes.
- **How do you offer both?** Make async the main API, and have the callback version call it.

## 19. Debugging & Performance

### Q128. How do you debug async code? `[Senior]`
Use **Xcode's async backtraces**, the **Swift Concurrency template in Instruments**, **named tasks**, **Thread Sanitizer**, and the **warnings from checked continuations**.

- **Async backtraces:** Xcode shows the chain of `await`s, not just the current thread's stack.
- **Instruments:** Swift Tasks (how many, their states, how long they live) and Swift Actors (queue lengths, contention).
- **Task names** (Swift 6.2): `Task(name:)`.
- **Thread Sanitizer:** finds remaining data races, especially in code not yet in Swift 6 mode.
- **Checked continuations:** log leaked or double-resumed continuations.

```swift
let task = Task(name: "SyncOrders") {        // shows up by name in Instruments
    await syncEngine.run()
}

func legacyDidFinish() {                     // called by old code that should be on the main thread
    MainActor.assertIsolated()               // stops in debug builds if it isn't
}
```

**Follow-ups:**
- **What would you look for in Instruments for a hang?** A long task running on the main actor, or a task that never finishes.
- **How do you find a stuck task?** Look in Swift Tasks for tasks that stay "suspended" forever, often a continuation never resumed.
- **Why aren't thread stacks enough?** A paused task isn't on any thread, so it doesn't show up in thread stacks.

### Q129. What are the performance considerations of async/await? `[Lead/Expert]`
Async calls are cheap, but **too many tasks**, **too many actor hops**, and **blocking the thread pool** all cost performance.

- **Async frames:** each pause uses a little memory. Don't make tight inner loops async without need.
- **Creating tasks** has overhead. Don't make one task per tiny item. Batch work, or limit concurrency (Q35).
- **Actor hops** cost context switches. Do all the work off the main actor, then update the UI once.
- **Never block** the thread pool (Q82).
- **Long CPU work:** run it off the main actor, and check cancellation and yield (Q56).

```swift
// ❌ Hops to the main actor 10,000 times
for item in items {
    let row = await process(item)
    await MainActor.run { rows.append(row) }
}

// ✅ Do the work first, update the UI once
let newRows = await processAll(items)
await MainActor.run { rows.append(contentsOf: newRows) }
```

**Follow-ups:**
- **Is a single `await` expensive?** No. If there's no actor switch and no pause, it's close to a normal call.
- **When does making something async hurt?** When it's fast sync code, because it adds hops and pause points for nothing.
- **How do you measure it?** Use the Swift Concurrency template in Instruments, plus Time Profiler.

### Q130. How does Swift Concurrency avoid thread explosion compared with GCD? `[Lead/Expert]`
GCD **creates more threads** when queue work blocks, so busy apps could end up with **hundreds of threads**, while Swift Concurrency keeps **about one thread per CPU core** and tasks **pause instead of blocking**.

- **The cost of GCD's approach:** lots of memory, lots of thread switching, and a risk of hitting the thread limit.
- **Swift's trade-off:** the **forward progress rule**. Code must never block, or the small pool can run out.

```swift
// GCD: each blocked block can make GCD add another thread
for url in urls {
    DispatchQueue.global().async {
        let data = try? Data(contentsOf: url)   // blocking network read
    }
}

// Swift Concurrency: tasks pause, threads stay at about one per core
await withTaskGroup(of: Void.self) { group in
    for url in urls {
        group.addTask { _ = try? await URLSession.shared.data(from: url) }
    }
}
```

**Follow-ups:**
- **Why are too many threads bad?** Each has its own stack memory, and switching between them wastes CPU.
- **What happens if you block in Swift Concurrency?** The pool doesn't grow, so you can deadlock (Q82).
- **Can you still run 1,000 tasks?** Yes. Tasks are cheap, and they share the few threads.

### Q131. When is async/await **not** the right tool? `[Lead/Expert]`
Async/await isn't the right tool for **fast sync operations**, **complex time-based streams**, **real-time callbacks**, or **tiny critical sections** where a simple lock is better.

- **Fast sync operations:** making them async adds complexity and pause points for nothing.
- **Complex time-based stream logic:** Combine or swift-async-algorithms may be clearer.
- **Real-time work** (audio render callbacks, Metal frame callbacks): must not allocate memory or pause.
- **Tiny critical sections:** a lock (`Mutex` from Swift 6's Synchronization module, or `OSAllocatedUnfairLock`) can be simpler and faster than an actor.

```swift
import Synchronization

final class Counter: Sendable {
    private let value = Mutex(0)

    func increment() {                    // sync and fast: no actor, no await needed
        value.withLock { $0 += 1 }
    }
}
```

**Follow-ups:**
- **Why is an actor overkill for a counter?** Every caller must `await`, even for a nanosecond of work.
- **Why can't audio callbacks use `await`?** They run on a real-time thread with strict deadlines, and pausing would cause glitches.
- **Which OS version has `Mutex`?** iOS 18 and later.

## 20. "What's the Output?" Questions

### Q132. `async let` ordering `[Fundamental]`
```swift
func work(_ name: String, seconds: Double) async -> String {
    try? await Task.sleep(for: .seconds(seconds))
    print("finished \(name)")
    return name
}

async let a = work("A", seconds: 2)
async let b = work("B", seconds: 1)
print("started")
let results = await [a, b]
print(results)
```
**Answer:**
```
started
finished B
finished A
["A", "B"]
```
**Why:** Both children start right away, so `B` (1 second) finishes before `A` (2 seconds). But the array is built in the order you **wrote** it, so the result is still `["A", "B"]`.

**Follow-ups:**
- **Why does "started" print first?** The children are sleeping, and the parent keeps running until it awaits.
- **How long does the whole thing take?** About 2 seconds, the slowest child.
- **What changes if you swap the sleep times?** "finished A" prints first, but the result is still `["A", "B"]`.

### Q133. Sequential vs concurrent timing `[Fundamental]`
```swift
let start = ContinuousClock.now
let x = await work("X", seconds: 1)
let y = await work("Y", seconds: 1)
print(ContinuousClock.now - start)        // ?

let start2 = ContinuousClock.now
async let p = work("P", seconds: 1)
async let q = work("Q", seconds: 1)
_ = await (p, q)
print(ContinuousClock.now - start2)       // ?
```
**Answer:** About **2 seconds** for the first part, and about **1 second** for the `async let` part.

**Why:** Sequential `await`s wait for each call in turn, so times add up. `async let` runs both at the same time, so you wait only for the slowest.

**Follow-ups:**
- **When can't you use the faster version?** When `Y` needs `X`'s result.
- **Would a task group give the same timing?** Yes, about 1 second.
- **Why use `ContinuousClock` for timing?** It's a steady clock that doesn't jump if the system time changes.

### Q134. When does a new `Task` run? `[Senior]`
```swift
@MainActor
func handleTap() {
    Task { print("2: inside task") }
    print("1: after creating task")
}
```
**Answer:** `1: after creating task`, then `2: inside task`.

**Why:** The task is **queued** on the main actor. The main actor is busy running `handleTap()`, so the task can only start after `handleTap()` returns.

**Follow-ups:**
- **What changes with `Task.immediate`?** `2` prints **first**, because the body starts right away until its first `await` (Swift 6.2).
- **Is the order guaranteed with a plain `Task`?** Yes here, because both run on the busy main actor.
- **What if `handleTap()` were not on the main actor?** The task could start on another thread at any moment, so the order would not be guaranteed.

### Q135. Cancellation is cooperative `[Senior]`
```swift
let task = Task {
    for i in 1...5 {
        print(i)
        expensiveSynchronousWork()      // no cancellation checks, no awaits
    }
}
task.cancel()
```
**Answer:** `1 2 3 4 5`. Everything prints.

**Why:** `cancel()` only sets a flag, and the loop never checks it.

**Follow-ups:**
- **How do you make it stop early?** Add `try Task.checkCancellation()` in the loop (the closure becomes throwing).
- **Would adding `await Task.yield()` stop it?** No. `yield()` doesn't check cancellation.
- **Would `try await Task.sleep` inside the loop stop it?** Yes, it throws `CancellationError`.

### Q136. `Task.sleep` and cancellation `[Fundamental]`
```swift
let task = Task {
    do {
        try await Task.sleep(for: .seconds(5))
        print("woke up")
    } catch {
        print("caught: \(error)")
    }
}
task.cancel()
```
**Answer:** `caught: CancellationError()`, printed **right away**, not after 5 seconds.

**Why:** `Task.sleep` checks for cancellation and throws `CancellationError` as soon as the task is cancelled.

**Follow-ups:**
- **Does "woke up" ever print?** No.
- **What if the task was cancelled before it started?** Same result. The sleep throws right away.
- **What would `Thread.sleep` do here?** Block for the full 5 seconds and ignore the cancellation.

### Q137. Swallowing cancellation with `try?` `[Senior]`
```swift
let task = Task {
    try? await Task.sleep(for: .seconds(5))
    print("still running, cancelled = \(Task.isCancelled)")
}
task.cancel()
```
**Answer:** `still running, cancelled = true`, printed right away.

**Why:** The sleep threw `CancellationError`, but `try?` swallowed it, so the code carried on.

**Follow-ups:**
- **Why is this dangerous in real code?** The next line (like a network call) runs even though the task was cancelled (Q57).
- **How do you fix it without throwing?** Add `guard !Task.isCancelled else { return }` after the sleep.
- **Is the flag still set?** Yes. `try?` hides the error, not the flag.

### Q138. Child vs unstructured task cancellation `[Lead/Expert]`
```swift
func report(_ label: String) async {
    try? await Task.sleep(for: .seconds(1))
    print("\(label) cancelled: \(Task.isCancelled)")
}

let parent = Task {
    Task { await report("unstructured") }   // not a child
    async let child: Void = report("child") // a child task
    await child
}
parent.cancel()
```
**Answer:**
```
child cancelled: true          ← right away
unstructured cancelled: false  ← after about 1 second
```
**Why:** The `async let` child is cancelled with the parent, so its sleep throws right away. The unstructured `Task` is independent, so it sleeps the full second and isn't cancelled.

**Follow-ups:**
- **Why does "child" print immediately?** Its sleep throws `CancellationError`, and `try?` swallows it.
- **How would you make the unstructured task cancel too?** Use `async let` or a task group instead.
- **Is this the most common cancellation misunderstanding?** Yes. People expect `Task { }` to be a child.

### Q139. Task group result order `[Fundamental]`
```swift
let values = await withTaskGroup(of: Int.self) { group in
    for seconds in [3, 1, 2] {
        group.addTask {
            try? await Task.sleep(for: .seconds(seconds))
            return seconds
        }
    }
    var collected: [Int] = []
    for await value in group { collected.append(value) }
    return collected
}
print(values)
```
**Answer:** `[1, 2, 3]`.

**Why:** Task group results arrive in **completion order**, not the order they were added.

**Follow-ups:**
- **How long does it take?** About 3 seconds, the slowest child.
- **How would you get `[3, 1, 2]` back?** Return the index with each value and sort or place them (Q34).
- **Is completion order guaranteed with equal times?** No. Equal times can finish in any order.

### Q140. Heavy work inside a main-actor `Task` `[Senior]`
```swift
@MainActor
func generateReportTapped() {
    spinner.startAnimating()
    Task {
        let report = ReportBuilder.buildSynchronously()   // 3 seconds of CPU work
        spinner.stopAnimating()
        show(report)
    }
}
```
**Question:** Does the spinner animate during those 3 seconds?

**Answer:** **No.** The spinner freezes.

**Why:** The `Task` inherits the main actor, so the synchronous work **blocks the main thread**. Fix it by moving the work off the main actor (a `@concurrent` async function, `Task.detached`, or a background actor).

**Follow-ups:**
- **Would making `buildSynchronously` `async` fix it?** Not by itself. It must actually run off the main actor.
- **What would the fixed line look like?** `let report = await ReportBuilder.build()`, where `build()` is `@concurrent`.
- **Which tool shows this freeze?** The Hangs and Time Profiler instruments.

### Q141. `await` inside `map` `[Fundamental]`
```swift
let users = try ids.map { try await api.fetchUser(id: $0) }
```
**Answer:** **Compile error.**

**Why:** `map` takes a **synchronous** closure, so it can't contain `await`. Use a `for` loop (one at a time) or a task group (all at once).

**Follow-ups:**
- **What's the one-at-a-time fix?** `for id in ids { users.append(try await api.fetchUser(id: id)) }`.
- **What's the all-at-once fix?** A throwing task group that keeps the order (Q34).
- **Does `AsyncSequence.map` allow `await`?** Yes, its closure is async.

### Q142. Which error does a cancelled `URLSession` request throw? `[Senior]`
```swift
let task = Task {
    do {
        _ = try await URLSession.shared.data(from: url)
    } catch is CancellationError {
        print("CancellationError")
    } catch {
        print("Other: \(error)")
    }
}
task.cancel()
```
**Answer:** `Other: Error Domain=NSURLErrorDomain Code=-999 "cancelled"…`

**Why:** `URLSession` throws **`URLError(.cancelled)`**, not `CancellationError`. Check for both when filtering out cancellation.

**Follow-ups:**
- **What is error code -999?** `NSURLErrorCancelled`.
- **What's the risk in a UI?** A "cancelled" error alert shows up when the user leaves the screen.
- **How do you handle both cleanly?** One helper: `error is CancellationError || (error as? URLError)?.code == .cancelled` (Q51).

### Q143. Continuation misuse `[Senior]`
```swift
func value() async -> Int {
    await withCheckedContinuation { continuation in
        legacy.fetch { result in
            continuation.resume(returning: result)
            continuation.resume(returning: result)   // A
        }
    }
}
```
**Question:** What happens at line A? What if the callback were never called?

**Answer:** Line A **crashes**. If the callback never fires, the caller **hangs forever**, and the runtime logs a warning that the continuation leaked.

**Why:** A continuation must be resumed **exactly once**. Checked continuations catch the double resume and stop the app.

**Follow-ups:**
- **What would an unsafe continuation do at line A?** Undefined behavior, which may be a random crash later.
- **How do you protect against callbacks that fire twice?** Keep a flag, or set the stored continuation to `nil` after resuming.
- **How do you find the "never resumed" bug?** Look for the "leaked its continuation" log and stuck tasks in Instruments.

### Q144. Unobserved error in a `Task` `[Senior]`
```swift
Task {
    try await api.deleteAccount()      // throws URLError(.notConnectedToInternet)
}
print("requested")
```
**Answer:** `requested`, and nothing else.

**Why:** The error is stored in the task and then **thrown away**, because nobody awaits it. Swift 6.4 warns about this pattern.

**Follow-ups:**
- **How do you fix it?** Catch the error inside the task and update the UI or log it.
- **Does the account get deleted?** No. The request failed, and the user never finds out.
- **How do you silence the Swift 6.4 warning on purpose?** Write `_ = Task { ... }`.

### Q145. Strong `self` in a long-running task `[Lead/Expert]`
```swift
final class TickerViewModel {
    private var task: Task<Void, Never>?

    init(prices: AsyncStream<Double>) {
        task = Task {
            for await price in prices {
                self.latestPrice = price      // strong self, the loop never ends
            }
        }
    }

    var latestPrice = 0.0
    deinit { task?.cancel(); print("deinit") }
}

var viewModel: TickerViewModel? = TickerViewModel(prices: priceStream)
viewModel = nil
```
**Answer:** **Nothing** prints. `deinit` never runs.

**Why:** The task holds `self` strongly for as long as the stream is open, so the view model can't be freed, and the `deinit` that would cancel the task never runs.

**Follow-ups:**
- **How do you fix it?** `[weak self]`, with `guard let self` **inside** the loop (Q108).
- **What if you put `guard let self` before the loop?** The leak comes back.
- **Would it end on its own?** Only if the price stream finishes.

### Q146. An `async let` that is never awaited `[Lead/Expert]`
```swift
func refresh() async {
    async let analytics: Void = sendAnalytics()   // takes 3 seconds, ignores cancellation
    print("refresh done")
}

await refresh()
print("returned")
```
**Answer:** `refresh done`, then `returned` about **3 seconds later**.

**Why:** At the end of the scope, the unawaited child is **cancelled and then awaited**. `sendAnalytics()` ignores cancellation, so `refresh()` waits for it.

**Follow-ups:**
- **How do you really fire and forget?** Use an unstructured `Task`, on purpose.
- **What if `sendAnalytics()` checked cancellation?** `refresh()` would return almost right away.
- **Is the analytics result kept?** No, it's thrown away.

## 22. Senior / Lead Scenario Questions

### Q147. How would you migrate a large completion-handler networking layer to async/await? `[Lead/Expert]`
Migrate **bottom-up**: convert the **HTTP client first**, keep **deprecated callback wrappers** so nothing breaks, then move **services and view models feature by feature**, with **tests** guarding each step.

1. **Bottom-up:** convert the lowest layer (the HTTP client) first, using `URLSession`'s async APIs.
2. **Compatibility:** keep completion-handler wrappers marked `@available(*, deprecated, renamed:)`. The deprecation warnings become your to-do list.
3. **Feature by feature:** migrate services and view models. Replace callback chains with straight-line code, and use `async let` or task groups for parallel requests.
4. **Tests first:** add tests for error mapping, retries, and cancellation. Async tests are simpler than callback tests.
5. **Team guidelines:** where tasks may be created, how to handle cancellation, main-actor rules, and no blocking.
6. **Finish:** remove the wrappers once unused, and turn on stricter concurrency checking module by module.

```swift
// Step 1: the new core
func send<R: Decodable>(_ endpoint: Endpoint<R>) async throws -> R { ... }

// Step 2: old callers keep compiling, with a warning pointing to the new API
@available(*, deprecated, renamed: "send(_:)")
func send<R: Decodable>(_ endpoint: Endpoint<R>,
                        completion: @escaping @Sendable (Result<R, Error>) -> Void) {
    Task { completion(await Result { try await send(endpoint) }) }   // Swift 6.4 async Result
}

// Step 3: a migrated view model, loading two things at once
func load() async throws {
    async let user = client.send(.user)
    async let orders = client.send(.orders)
    state = try await .loaded(user, orders)
}
```

**Follow-ups:**
- **Why bottom-up and not top-down?** Upper layers can't be truly async until the layers below them are.
- **How do you track progress?** Count the deprecation warnings left.
- **What's the biggest risk?** Changing which thread callbacks arrive on, so check UI code that assumed the main queue.

### Q148. Design an image loading pipeline for a large feed using async/await. `[Lead/Expert]`
Use an **`ImageLoader` actor** with **memory and disk caches** and **request deduplication**, **decode and downsample off the main actor**, **cancel loads for cells that scroll away**, and **limit how many downloads run at once**.

- **Caching:** `NSCache` in memory, plus a disk cache.
- **Deduplication:** one download per URL (Q114).
- **Decoding off the main actor:** a `@concurrent` function, or `byPreparingThumbnail(ofSize:)`.
- **Cancellation:** cancel in `prepareForReuse` (UIKit), or let `.task(id: url)` do it (SwiftUI).
- **Concurrency limits:** avoid hundreds of downloads at once (limited task group or a semaphore-like actor).
- **Prefetching:** load upcoming rows early, at a lower priority.
- **Metrics and tests:** cache hit rate, decode time, memory use, and a mock `URLProtocol`.

```swift
actor ImageLoader {
    private let memory = NSCache<NSURL, UIImage>()
    private var inFlight: [URL: Task<UIImage, Error>] = [:]

    func image(for url: URL, size: CGSize) async throws -> UIImage {
        if let cached = memory.object(forKey: url as NSURL) { return cached }
        if let running = inFlight[url] { return try await running.value }

        let task = Task {
            let (data, _) = try await URLSession.shared.data(from: url)
            return try await Self.downsample(data, to: size)    // off the actor
        }
        inFlight[url] = task
        defer { inFlight[url] = nil }

        let image = try await task.value
        memory.setObject(image, forKey: url as NSURL)
        return image
    }

    @concurrent
    static func downsample(_ data: Data, to size: CGSize) async throws -> UIImage { ... }
}

// SwiftUI cell: cancelled automatically when it scrolls away
.task(id: url) { image = try? await loader.image(for: url, size: thumbSize) }
```

**Follow-ups:**
- **Why downsample?** A full-size photo in a small cell wastes a lot of memory.
- **Should a cancelled cell cancel the shared download?** Not if other cells still need it, so count waiters, or let it finish into the cache.
- **Why `NSCache` and not a dictionary?** It frees memory automatically when the system needs it.

### Q149. After adopting async/await, users report the app freezing. How do you investigate? `[Lead/Expert]`
Look for **heavy sync work on the main actor** first (the most common cause), then **blocking calls**, **continuations never resumed**, **busy actors**, and the **Swift 6.2 change** that keeps nonisolated functions on the caller's actor.

- **Main actor busy with sync work** inside `Task { }` or `@MainActor` functions (Q85, Q140). Check with Time Profiler and the Hangs instrument.
- **Blocking calls in async code** (semaphores, `DispatchGroup.wait`, sync I/O) that starve the thread pool or deadlock (Q82).
- **Continuations never resumed**, so tasks wait forever (look for "leaked its continuation" logs).
- **Actor contention:** one busy actor doing too much work in a row (Swift Actors instrument).
- **Swift 6.2 change:** a nonisolated async function that used to run in the background now runs on the main actor (Q86). Mark heavy functions `@concurrent`.
- **Then:** fix it, add a regression test, and watch hang rates in the Xcode Organizer.

```swift
// Before (Swift 6.2 with Approachable Concurrency): runs on the caller's actor, the main actor
nonisolated func parseFeed(_ data: Data) async throws -> [Post] {
    try JSONDecoder().decode([Post].self, from: data)     // 800 ms on the main thread
}

// After: always runs on the thread pool
@concurrent
nonisolated func parseFeed(_ data: Data) async throws -> [Post] {
    try JSONDecoder().decode([Post].self, from: data)
}
```

**Follow-ups:**
- **Why did this appear right after upgrading Xcode?** The new project setting changed where nonisolated functions run.
- **How do you tell a freeze from a deadlock?** A freeze ends eventually. A deadlock never does, and the stack shows a thread waiting.
- **How do you stop it coming back?** Add a performance test or a hang alert, and team guidance about `@concurrent`.

### Q150. Design a sync engine that uploads pending changes and downloads updates. `[Lead/Expert]`
Use a **`SyncEngine` actor** that runs **one sync at a time** (new requests **join** the running one), **uploads with limited concurrency**, then **downloads**, with **retries**, **per-item results**, and **cancellation between batches**.

- **One run at a time:** store the current run's `Task`. New requests await it.
- **Each run:** upload pending changes with a limited-concurrency task group, then download updates. Use `withRetry` for temporary failures, and idempotent requests.
- **Cancellation:** respect backgrounding and sign-out. Check cancellation between batches, and save progress so the next run continues.
- **Errors:** record failures per item (`Result`), instead of failing the whole run.
- **Triggers:** app foreground, push notification, `BGAppRefreshTask`, and connection restored (an `AsyncStream` from `NWPathMonitor`).
- **Testability:** inject the API, the store, and the clock.

```swift
actor SyncEngine {
    private var currentRun: Task<SyncReport, Error>?

    func sync() async throws -> SyncReport {
        if let currentRun { return try await currentRun.value }   // join the running sync

        let run = Task { try await performSync() }
        currentRun = run
        defer { currentRun = nil }
        return try await run.value
    }

    private func performSync() async throws -> SyncReport {
        let uploads = await uploadPending(maxConcurrent: 4)   // per-item Results
        try Task.checkCancellation()                          // stop between phases
        let downloads = try await withRetry { try await api.fetchChanges(since: cursor) }
        return SyncReport(uploads: uploads, downloaded: downloads.count)
    }
}
```

**Follow-ups:**
- **What if a sync is requested while one is running?** It joins the current run, or schedules one more run after it.
- **Why idempotent requests?** A retry after a timeout might repeat an upload that actually succeeded.
- **How does sign-out stop the sync?** Cancel `currentRun`, and the cancellation checks stop it.

### Q151. What do you look for when reviewing async/await code? `[Lead/Expert]`
Check **structure**, **cancellation**, **errors**, **threading**, **memory**, **continuations**, **state after `await`**, and **tests**.

- **Structure:** `async` functions and structured concurrency first. `Task { }` only at the edges. No `Task.detached` without a reason.
- **Cancellation:** long loops check it. No `try?` hiding `Task.sleep` cancellation. No user-facing errors for cancellation. Stored tasks are cancelled.
- **Errors:** no errors silently dropped in fire-and-forget tasks (Swift 6.4 now warns).
- **Threading:** no heavy sync work on the main actor. No blocking. No locks held across `await`.
- **Memory:** long-running tasks don't hold `self` strongly. `weak self` is unwrapped in the right place.
- **Continuations:** resumed exactly once on every path.
- **State after `await`:** assumptions are checked again after each pause (actor reentrancy).
- **Tests:** async methods awaited directly, clocks injected, no sleeping in tests.

```swift
// A snippet with four review comments
func refresh() {
    Task {                                         // 1. untracked task: can't cancel or test
        try? await Task.sleep(for: .seconds(1))    // 2. try? hides cancellation
        let items = parseHugeJSON(data)            // 3. heavy sync work on the main actor
        self.items = items                         // 4. no error handling, holds self strongly
    }
}
```

**Follow-ups:**
- **Which issue is most common?** Heavy sync work on the main actor.
- **How do you make reviews consistent?** A written checklist and lint rules where possible.
- **What's hardest to catch in review?** State assumptions that break after an `await`.

### Q152. How do you finish important async work when the app moves to the background? `[Lead/Expert]`
Ask for **extra time with `beginBackgroundTask`**, run the work in a **`Task`**, **cancel it in the expiration handler**, and **always end the background task**.

- `beginBackgroundTask` gives only a **short** amount of extra time.
- **Deferrable work:** use `BGTaskScheduler` (cancel the `Task` in `expirationHandler`, then call `setTaskCompleted`), or SwiftUI's `.backgroundTask(.appRefresh("id")) { await ... }`.
- **Large transfers:** use background `URLSession` (delegate-based, Q101).

```swift
@MainActor
func sceneDidEnterBackground(_ scene: UIScene) {
    var saveTask: Task<Void, Never>?
    let backgroundID = UIApplication.shared.beginBackgroundTask(withName: "SaveDraft") {
        saveTask?.cancel()                         // time ran out: stop politely
    }

    saveTask = Task {
        await draftStore.flushPendingChanges()     // must respond to cancellation
        UIApplication.shared.endBackgroundTask(backgroundID)
    }
}
```

**Follow-ups:**
- **What happens if you never call `endBackgroundTask`?** The system may terminate the app.
- **Should the expiration handler also end the background task?** Yes, in production it should end it too, after cancelling the work.
- **How much time do you get?** Not guaranteed. Treat it as a few seconds.

### Q153. How would you explain async/await to a junior engineer? `[Senior]`
Use a **restaurant analogy**: **blocking** is standing at the counter until your food is ready, so nobody else can order, while **awaiting** is **taking a buzzer and sitting down**, so the cashier (the thread) serves other people until you're called back.

- Show a completion-handler pyramid next to the async version.
- Then teach three rules:
  1. **Don't block.**
  2. **Check cancellation in long work.**
  3. **Know which actor your code runs on** (the main actor for UI).

```swift
// Before: callbacks inside callbacks
fetchUser { user in
    fetchOrders(for: user) { orders in
        DispatchQueue.main.async { show(orders) }
    }
}

// After: reads like a recipe
let user = try await fetchUser()
let orders = try await fetchOrders(for: user)
show(orders)                 // on the main actor
```

**Follow-ups:**
- **What's the first mistake juniors usually make?** Thinking `async` means "runs in the background."
- **How would you explain cancellation?** It's a polite request, so the code has to check for it.
- **Which exercise would you give them?** Convert one callback function, then add `async let` to load two things at once.

### Q154. Where should tasks be created in a well-architected app? `[Lead/Expert]`
**Lower layers** expose **`async` functions and `AsyncSequence`s**, **view models** expose **`async` methods** (plus a few owned tasks), and the **UI layer creates the tasks** at the edges.

- **Lower layers** (networking, storage, services): almost never create unstructured tasks, except for deliberate coordination like a sync engine or a deduplicating cache.
- **View models:** `async` methods for user actions (`load()`, `refresh()`, `save()`), plus a few owned, cancellable tasks for debounce or observation.
- **UI layer:** creates tasks at the boundary, with SwiftUI `.task`/`.refreshable`, UIKit event handlers, and delegate callbacks.
- **Result:** cancellation, errors, and testing stay predictable, because most code is plain `async` functions that tests can await.

```swift
// Service: plain async
struct OrderService { func orders() async throws -> [Order] { ... } }

// View model: async intent
@MainActor @Observable
final class OrdersViewModel {
    var orders: [Order] = []
    func load() async { orders = (try? await service.orders()) ?? [] }
}

// UI: the only place a task is created
List(viewModel.orders) { OrderRow(order: $0) }
    .task { await viewModel.load() }
```

**Follow-ups:**
- **Why keep services free of `Task { }`?** So callers control cancellation, and tests can await them.
- **When may a service own a task?** For shared long-lived work, like a refresh shared by many callers (Q100).
- **How does this help testing?** Tests call `await viewModel.load()` and check the state, with no waiting.
