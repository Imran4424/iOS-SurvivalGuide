## 1. Fundamentals

### Q1. What is Combine? `[Fundamental]`
**Key points:**
- Apple's declarative framework for processing **values over time** (iOS 13+).
- You build pipelines: a **publisher** emits values, **operators** transform them, and a **subscriber** consumes them.
- Typical uses: UI bindings, form validation, search-as-you-type, networking pipelines, reacting to notifications, timers, and KVO.

```swift
import Combine

let cancellable = [1, 2, 3, 4, 5].publisher
    .filter { $0.isMultiple(of: 2) }
    .map { $0 * 10 }
    .sink { print($0) }
// 20
// 40
```

### Q2. What is reactive programming? `[Fundamental]`
**Key points:**
- Treating events and data changes as **streams** you can transform and combine declaratively, instead of handling each callback imperatively.
- Benefits: composable async logic, fewer state flags, unified handling of different event sources (UI, network, timers).
- Costs: learning curve, harder debugging (long generic types, stack traces through operators), and memory management pitfalls.

### Q3. What are the core protocols in Combine? `[Fundamental]`
| Protocol | Role |
|---|---|
| `Publisher` | Emits a sequence of values of type `Output`, then optionally completes with success or a `Failure` |
| `Subscriber` | Receives a subscription, values (`Input`), and a completion |
| `Subscription` | The connection between publisher and subscriber; handles demand (`request(_:)`) and cancellation |
| `Subject` | A publisher you can send values into imperatively |
| `Scheduler` | Defines when and where (which thread/queue) work happens |
| `Cancellable` | Something you can cancel (`AnyCancellable` cancels on deinit) |

### Q4. What are a publisher's `Output` and `Failure` types? `[Fundamental]`
**Key points:**
- Every publisher declares `Output` (the value type) and `Failure` (an `Error` type). The full type is part of the pipeline's compile-time contract.
- `Failure == Never` means the publisher **can't fail** (e.g. `Just`, `@Published`). Some APIs like `sink(receiveValue:)` and `assign(to:on:)` require `Never`.
- Operators must line up types: a subscriber's `Input`/`Failure` must match the upstream `Output`/`Failure`.

### Q5. Describe the lifecycle of a subscription. `[Senior]`
1. The subscriber calls `publisher.subscribe(subscriber)`.
2. The publisher creates a `Subscription` and calls `subscriber.receive(subscription:)`.
3. The subscriber **requests demand** (`subscription.request(.unlimited)` or `.max(n)`).
4. The publisher sends values (`subscriber.receive(_:)`), never more than requested.
5. The publisher sends **one** completion: `.finished` or `.failure(error)`. After that, no more values.
6. At any point the subscriber can **cancel**, which tears down the subscription.

```
Publisher ──subscription──▶ Subscriber
Subscriber ──request(demand)──▶ Subscription
Publisher ──value, value, …──▶ Subscriber
Publisher ──completion (finished | failure)──▶ Subscriber
```

### Q6. What is the "contract" a publisher must follow? `[Senior]`
**Key points:**
- Zero or more values, followed by **at most one** completion.
- After a completion (success or failure), nothing else is delivered.
- Values are never delivered beyond the subscriber's demand.
- Events are delivered **serially** (not concurrently) to a subscriber.
- Consequence: **an error terminates the stream.** This drives most error-handling patterns in Section 9.

### Q7. Are Combine publishers lazy (cold) or eager (hot)? `[Senior]`
**Key points:**
- Most publishers are **cold/lazy**: no work happens until something subscribes, and each subscriber triggers its own execution (e.g. each subscription to `dataTaskPublisher` makes a new network request).
- **Hot** sources emit regardless of subscribers: subjects, `@Published`, `NotificationCenter` publishers, timers once connected. Late subscribers miss earlier values (except `CurrentValueSubject`/`@Published`, which replay the current value).
- **`Future` is an exception**: it runs its closure **immediately** at creation and caches the result.

### Q8. What is a marble diagram? `[Fundamental]`
**Key points:**
- A visual timeline of a stream's values and completion, used to explain operators.

```
input:      ──1──2──3──4──|
map(x * 10) ──10─20─30─40─|
filter(even)────2─────4──|
             (| = finished, X = failure)
```
- Useful when explaining operators like `debounce`, `combineLatest`, or `switchToLatest` in an interview. Sketching one shows clarity of thinking.

## 2. Built-in Publishers

### Q9. What are `Just`, `Empty`, `Fail`, and sequence publishers? `[Fundamental]`
```swift
Just(42)                                   // emits 42, then finishes. Failure == Never
Empty<Int, Never>()                        // finishes immediately with no values
Empty<Int, Never>(completeImmediately: false)  // never emits, never completes
Fail<Int, URLError>(error: URLError(.badURL))  // fails immediately
[1, 2, 3].publisher                        // emits each element, then finishes
```
- Commonly used as fallbacks in `catch`, in tests, or to start a pipeline.

### Q10. What is `Future`, and what are its gotchas? `[Senior]`
**Key points:**
- Produces a **single** value or failure asynchronously via a `promise` callback. Useful for wrapping completion-handler APIs.
- Gotchas:
  - It executes **immediately when created**, not when subscribed.
  - It runs **once** and replays the cached result to every subscriber, so `retry` doesn't redo the work.
- Wrap it in `Deferred` to make it lazy and re-executable.

```swift
func fetchUser(id: Int) -> AnyPublisher<User, Error> {
    Deferred {
        Future { promise in
            legacyAPI.fetchUser(id: id) { result in   // completion-handler API
                promise(result)
            }
        }
    }
    .eraseToAnyPublisher()
}
```

### Q11. What is `Deferred`? `[Senior]`
**Key points:**
- Waits until a subscriber attaches, then calls its closure to create a fresh publisher **for each subscriber**.
- Makes eager publishers lazy (`Future`) and lets `retry` re-run work.

### Q12. Which Foundation types provide publishers? `[Fundamental]`
```swift
// NotificationCenter
NotificationCenter.default.publisher(for: UIApplication.didBecomeActiveNotification)

// Timer (a connectable publisher; autoconnect starts it on first subscription)
Timer.publish(every: 1, on: .main, in: .common).autoconnect()

// URLSession
URLSession.shared.dataTaskPublisher(for: url)

// KVO on NSObject subclasses with @objc dynamic properties
player.publisher(for: \.timeControlStatus)

// Sequences
(1...5).publisher
```

### Q13. How do you observe KVO properties with Combine? `[Senior]`
```swift
final class PlayerObserver {
    private var cancellables = Set<AnyCancellable>()

    init(player: AVPlayer, onStatus: @escaping (AVPlayer.TimeControlStatus) -> Void) {
        player.publisher(for: \.timeControlStatus, options: [.initial, .new])
            .removeDuplicates()
            .receive(on: DispatchQueue.main)
            .sink(receiveValue: onStatus)
            .store(in: &cancellables)
    }
}
```
- Works for any key path on an `NSObject` subclass whose property is KVO-compliant (`@objc dynamic` for your own classes).

### Q14. What is the `Record` publisher? `[Lead/Expert]`
**Key points:**
- Replays a pre-recorded sequence of values and a completion. Handy in tests and previews to simulate a stream deterministically.

```swift
let recorded = Record<Int, Never>(output: [1, 2, 3], completion: .finished)
```

## 3. Subscribers

### Q15. What are the built-in subscribers? `[Fundamental]`
**Key points:**
- `sink(receiveCompletion:receiveValue:)`: closures for values and completion. Requests unlimited demand.
- `sink(receiveValue:)`: only when `Failure == Never`.
- `assign(to:on:)`: writes values to a key path on an object (requires `Never`).
- `assign(to: &$publishedProperty)` (iOS 14): writes to a `@Published` property; no cancellable needed.

```swift
let cancellable = URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)
    .sink(
        receiveCompletion: { completion in
            if case .failure(let error) = completion {
                print("Failed: \(error)")
            }
        },
        receiveValue: { data in
            print("Received \(data.count) bytes")
        }
    )
```

### Q16. Why does `sink(receiveValue:)` sometimes fail to compile? `[Fundamental]`
**Key points:**
- It's only available when `Failure == Never`. For failing publishers, use `sink(receiveCompletion:receiveValue:)`, or handle the error first (`replaceError`, `catch`) to turn the failure type into `Never`.

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .map(\.data)
    .replaceError(with: Data())      // Failure becomes Never
    .sink { data in print(data.count) }
    .store(in: &cancellables)
```

### Q17. What is the difference between `assign(to:on:)` and `assign(to: &$property)`? `[Senior]`
| `assign(to:on:)` | `assign(to: &$property)` |
|---|---|
| Any class key path | Only `@Published` properties |
| Returns `AnyCancellable` you must store | Returns nothing; lifetime tied to the `@Published` property |
| **Strongly retains** the target object | No retain cycle |
| `assign(to: \.x, on: self)` + storing in `self.cancellables` = **retain cycle** | Safe for assigning to your own properties |

```swift
final class ProfileViewModel: ObservableObject {
    @Published var name = ""
    @Published private(set) var greeting = ""

    init() {
        $name
            .map { $0.isEmpty ? "Hello!" : "Hello, \($0)!" }
            .assign(to: &$greeting)   // no cancellable, no cycle
    }
}
```

### Q18. What happens when a subscriber receives a completion? `[Fundamental]`
**Key points:**
- The subscription ends. `.finished` means normal completion; `.failure(error)` means the stream failed.
- No further values arrive, even if the upstream source (e.g. a subject) later sends more.

## 4. Subjects & `@Published`

### Q19. What is a `Subject`? `[Fundamental]`
**Key points:**
- A publisher that also lets you **inject** values imperatively with `send(_:)` and `send(completion:)`. It bridges imperative code (delegates, callbacks, actions) into Combine pipelines.
- Subjects are hot and multicast to all current subscribers.

### Q20. What is the difference between `PassthroughSubject` and `CurrentValueSubject`? `[Fundamental]`
| `PassthroughSubject` | `CurrentValueSubject` |
|---|---|
| No initial value | Requires an initial value |
| Doesn't store values | Stores the latest value (`.value`) |
| New subscribers receive only **future** values | New subscribers immediately receive the **current** value, then future values |
| Good for **events** (button taps, "did finish") | Good for **state** (current user, settings) |

```swift
let taps = PassthroughSubject<Void, Never>()
let isLoggedIn = CurrentValueSubject<Bool, Never>(false)

taps.send(())
isLoggedIn.send(true)        // or isLoggedIn.value = true
print(isLoggedIn.value)      // true
```

### Q21. How does `@Published` work? `[Senior]`
**Key points:**
- A property wrapper (classes only) whose projected value `$property` is a publisher of the property's values.
- It behaves like a `CurrentValueSubject`: new subscribers immediately receive the current value.
- **It emits in `willSet`**, before the property is actually updated. Inside a subscriber, reading the property itself still gives the **old** value. Use the emitted value instead.
- In an `ObservableObject`, changing any `@Published` property triggers `objectWillChange`.

```swift
final class Counter: ObservableObject {
    @Published var count = 0
}

let counter = Counter()
let cancellable = counter.$count.sink { newValue in
    print("emitted: \(newValue), property now: \(counter.count)")
}
counter.count = 1
// emitted: 0, property now: 0
// emitted: 1, property now: 0   ← property hasn't been updated yet
```

### Q22. Why should you expose subjects as `AnyPublisher` instead of exposing the subject itself? `[Senior]`
**Key points:**
- Encapsulation: only the owner should be able to `send`. Exposing the subject lets any caller inject values or complete it.

```swift
final class CartService {
    private let itemsSubject = CurrentValueSubject<[Item], Never>([])

    var itemsPublisher: AnyPublisher<[Item], Never> {
        itemsSubject.eraseToAnyPublisher()
    }

    func add(_ item: Item) {
        itemsSubject.value.append(item)
    }
}
```

### Q23. Is it safe to call `send` from multiple threads? `[Lead/Expert]`
**Key points:**
- Combine expects events to be delivered **serially** to subscribers. Sending into a subject from multiple threads at the same time can cause concurrent delivery into downstream operators and subscribers that aren't designed for it.
- Serialize sends (a serial queue, an actor, or always sending from the main thread), and use `receive(on:)` to control the delivery thread.
- Note: `subscribe(on:)` doesn't change the thread on which a subject emits; values arrive on whatever thread called `send`.

### Q24. What happens if you send a completion to a subject? `[Fundamental]`
**Key points:**
- All current subscribers receive the completion, and the subject stops delivering values forever. Later `send` calls are ignored, and new subscribers immediately receive the completion.
- Don't complete long-lived event subjects (like a "button tapped" subject) unless the source truly ends.

## 5. Memory Management & Cancellation

### Q25. What is `AnyCancellable`, and why must you store it? `[Fundamental]`
**Key points:**
- `sink` and `assign(to:on:)` return an `AnyCancellable`. When it's **deallocated**, it **cancels** the subscription.
- If you don't store it, the subscription is cancelled as soon as the returned value goes out of scope, so async publishers (network, timers) deliver nothing.

```swift
final class FeedViewModel {
    private var cancellables = Set<AnyCancellable>()

    func load() {
        api.fetchFeed()
            .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.items = $0 })
            .store(in: &cancellables)      // keeps the subscription alive
    }
}
```

### Q26. How do retain cycles happen in Combine, and how do you avoid them? `[Senior]`
**Key points:**
- `self` owns `cancellables` → the subscription → the `sink` closure → captures `self` strongly → cycle.
- `assign(to: \.property, on: self)` stored in `self.cancellables` → cycle (it retains `self`).

```swift
// ❌ Retain cycle
viewModel.$title
    .sink { self.titleLabel.text = $0 }
    .store(in: &cancellables)

viewModel.$title
    .assign(to: \.title, on: self)
    .store(in: &cancellables)

// ✅ Fixes
viewModel.$title
    .sink { [weak self] in self?.titleLabel.text = $0 }
    .store(in: &cancellables)

viewModel.$title
    .assign(to: \.text, on: titleLabel)   // retains the label, not self
    .store(in: &cancellables)

$name.map { "Hello, \($0)" }
    .assign(to: &$greeting)               // for @Published targets
```

### Q27. How do you cancel subscriptions? `[Fundamental]`
```swift
// Cancel one subscription
searchCancellable?.cancel()
searchCancellable = nil

// Cancel all subscriptions in a set
cancellables.removeAll()       // deallocating each AnyCancellable cancels it

// Automatic: when the owner (and its cancellables) is deallocated
```
- Cancellation propagates upstream: a network request in a `dataTaskPublisher` pipeline is cancelled too.

### Q28. When is it appropriate to cancel and replace a subscription? `[Senior]`
**Key points:**
- When a new request should supersede an old one (e.g. reloading a screen, changing filters). Store that specific subscription in its own `AnyCancellable?` property and replace it; the old one cancels when overwritten.
- Within a single pipeline, `switchToLatest` handles this automatically (Q41).

```swift
private var loadCancellable: AnyCancellable?

func reload(category: Category) {
    loadCancellable = api.products(in: category)   // assigning cancels the previous request
        .receive(on: DispatchQueue.main)
        .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.products = $0 })
}
```

### Q29. Why do cell bindings with Combine cause duplicate updates? `[Senior]`
**Key points:**
- Cells are reused. If you bind in `configure` without cancelling old subscriptions, a reused cell keeps listening to the previous item's publisher too, causing flickering or wrong data.
- Cancel bindings in `prepareForReuse`.

```swift
final class ProductCell: UICollectionViewCell {
    private var cancellables = Set<AnyCancellable>()
    private let favoriteButton = UIButton()

    func bind(to viewModel: ProductCellViewModel) {
        viewModel.$isFavorite
            .receive(on: DispatchQueue.main)
            .sink { [weak self] in self?.favoriteButton.isSelected = $0 }
            .store(in: &cancellables)
    }

    override func prepareForReuse() {
        super.prepareForReuse()
        cancellables.removeAll()   // drop the previous item's bindings
    }
}
```

## 6. Transforming & Filtering Operators

### Q30. What are `map`, `tryMap`, and `compactMap`? `[Fundamental]`
```swift
["1", "2", "x", "4"].publisher
    .compactMap { Int($0) }          // drops nils: 1, 2, 4
    .map { $0 * 2 }                  // 2, 4, 8
    .sink { print($0) }
    .store(in: &cancellables)

// tryMap can throw; the Failure type becomes `Error`
URLSession.shared.dataTaskPublisher(for: url)
    .tryMap { output -> Data in
        guard (output.response as? HTTPURLResponse)?.statusCode == 200 else {
            throw URLError(.badServerResponse)
        }
        return output.data
    }
```
- Most operators have a `try` variant (`tryFilter`, `tryCompactMap`, `tryScan`, …) that converts the failure type to `Error`.

### Q31. What does `flatMap` do? `[Senior]`
**Key points:**
- Transforms each value into a **new publisher** and flattens their outputs into one stream. All inner publishers stay active, so outputs can interleave.
- Classic use: chaining dependent async operations (fetch user → fetch that user's posts).

```swift
userIDs.publisher
    .flatMap { id in api.fetchUser(id: id) }   // one request per ID; results arrive as they finish
    .collect()
    .sink(receiveCompletion: { _ in }, receiveValue: { users in print(users.count) })
    .store(in: &cancellables)
```
- `flatMap` vs `map + switchToLatest`: `flatMap` keeps **all** inner publishers; `switchToLatest` keeps only the **latest** (Q41).

### Q32. How do you limit concurrency with `flatMap`? `[Lead/Expert]`
```swift
imageURLs.publisher
    .flatMap(maxPublishers: .max(3)) { url in   // at most 3 downloads in flight
        downloader.download(url)
            .replaceError(with: nil)
    }
    .compactMap { $0 }
    .collect()
    .sink { images in print("Downloaded \(images.count) images") }
    .store(in: &cancellables)
```
- `maxPublishers` uses backpressure: `flatMap` requests a new upstream value only when an inner publisher completes.

### Q33. What is the difference between `scan` and `reduce`? `[Fundamental]`
```swift
[1, 2, 3, 4].publisher
    .scan(0, +)          // emits every intermediate result: 1, 3, 6, 10
    .sink { print($0) }

[1, 2, 3, 4].publisher
    .reduce(0, +)        // emits once, when upstream finishes: 10
    .sink { print($0) }
```
- `reduce` never emits for an upstream that never completes (e.g. a subject or `@Published`). `scan` is useful for running totals and state accumulation.

### Q34. What does `collect` do? `[Fundamental]`
```swift
publisher.collect()                                     // all values into one array, on completion
publisher.collect(3)                                    // arrays of 3 values
publisher.collect(.byTime(DispatchQueue.main, .seconds(5)))           // batch by time window
publisher.collect(.byTimeOrCount(DispatchQueue.main, .seconds(5), 20)) // whichever comes first
```
- `collect()` buffers unboundedly and emits only when upstream finishes, so avoid it on infinite streams.

### Q35. What do `filter` and `removeDuplicates` do? `[Fundamental]`
```swift
$searchText
    .filter { $0.count >= 2 }     // ignore too-short queries
    .removeDuplicates()           // ignore same value emitted twice in a row (requires Equatable)

$location
    .removeDuplicates { old, new in old.distance(from: new) < 50 }   // custom comparison
```
- `removeDuplicates` only compares **consecutive** values: `1, 1, 2, 1` becomes `1, 2, 1`.

### Q36. What operators select specific values? `[Fundamental]`
| Operator | Behavior |
|---|---|
| `first()` / `first(where:)` | First (matching) value, then finishes |
| `last()` / `last(where:)` | Last value, emitted when upstream finishes |
| `prefix(n)` / `prefix(while:)` | First n values / while condition holds, then finishes |
| `dropFirst(n)` / `drop(while:)` | Skip the first n values / while condition holds |
| `output(at:)` / `output(in:)` | Value at an index / range |
| `ignoreOutput()` | Only forwards completion |

```swift
viewModel.$results
    .dropFirst()          // skip the initial value @Published emits on subscription
    .sink { print("Results changed: \($0.count)") }
    .store(in: &cancellables)
```

### Q37. What do `prefix(untilOutputFrom:)` and `drop(untilOutputFrom:)` do? `[Senior]`
```swift
// Emit progress updates until the user taps Cancel
downloadProgress
    .prefix(untilOutputFrom: cancelTapped)   // finishes when cancelTapped emits
    .sink { print("Progress: \($0)") }
    .store(in: &cancellables)

// Ignore location updates until the user enables tracking
locationUpdates
    .drop(untilOutputFrom: trackingEnabled)
    .sink { print($0) }
    .store(in: &cancellables)
```

### Q38. What other operators are useful to know? `[Senior]`
| Operator | Use |
|---|---|
| `replaceNil(with:)` | Substitute a default for `nil` values |
| `replaceEmpty(with:)` | Emit a value if upstream finishes without emitting |
| `contains`, `allSatisfy`, `count`, `min`, `max` | Aggregate checks (emit on completion) |
| `handleEvents` | Side effects for debugging or loading indicators |
| `breakpoint`, `print` | Debugging (Section 20) |
| `encode`, `decode` | `Codable` encoding/decoding in pipelines |
| `map(\.keyPath)` | Key path mapping: `.map(\.data)` |

## 7. Combining Operators

### Q39. How does `combineLatest` work? `[Fundamental]`
**Key points:**
- Waits until **every** input has emitted at least once, then emits a tuple of the **latest** values whenever **any** input emits.
- Typical use: deriving state from multiple sources (form validation, filters).

```swift
let username = CurrentValueSubject<String, Never>("")
let password = CurrentValueSubject<String, Never>("")

username.combineLatest(password)
    .map { user, pass in user.count >= 3 && pass.count >= 8 }
    .removeDuplicates()
    .sink { print("Form valid: \($0)") }
    .store(in: &cancellables)
```
- Variants: `combineLatest(_:_:)` up to three other publishers; `Publishers.CombineLatest3/4`.
- A combined stream finishes when **all** inputs finish, and fails when **any** input fails.

### Q40. Compare `combineLatest`, `zip`, and `merge`. `[Senior]`
| Operator | Emits when | Output | Use case |
|---|---|---|---|
| `combineLatest` | Any input emits (after all emitted once) | Tuple of latest values | Derived state |
| `zip` | Every input has a **new, unpaired** value | Tuple of values paired in order | Pairing parallel results (request A + request B) |
| `merge` | Any input emits | Single value (same type for all inputs) | Combining similar event sources |

```swift
// zip: wait for both requests, then use both results
api.fetchProfile()
    .zip(api.fetchSettings())
    .sink(receiveCompletion: { _ in }, receiveValue: { profile, settings in
        render(profile, settings)
    })
    .store(in: &cancellables)

// merge: one stream of refresh triggers from several sources
let refreshTriggers = pullToRefresh
    .merge(with: appBecameActive, retryTapped)   // all Publisher<Void, Never>
```

### Q41. What does `switchToLatest` do? `[Senior]`
**Key points:**
- Works on a publisher of publishers. When a new inner publisher arrives, it **cancels** the previous one and forwards values only from the latest.
- The go-to operator for search-as-you-type: stale requests are cancelled automatically.

```swift
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .removeDuplicates()
    .map { query in
        api.search(query).replaceError(with: [])   // inner publisher per query
    }
    .switchToLatest()                               // keep only the newest request
    .receive(on: DispatchQueue.main)
    .assign(to: &$results)
```
- With `flatMap`, all requests would complete and old results could overwrite newer ones (a race condition).

### Q42. How do you combine a dynamic number of publishers? `[Senior]`

### Q44. Build a sign-up form validation pipeline. `[Senior]`

```swift
final class SignUpViewModel: ObservableObject {
```

## 8. Timing Operators

### Q45. What is the difference between `debounce` and `throttle`? `[Senior]`
| `debounce(for:scheduler:)` | `throttle(for:scheduler:latest:)` |
|---|---|
| Waits for a **pause** of the given duration, then emits the last value | Emits at most **one value per interval** while values keep coming |
| Continuous input → nothing emitted until input stops | Continuous input → steady emissions every interval |
| Search fields, autosave after typing stops | Scroll events, rapid button taps, sensor data |

```
input:     a-b-c-d-------e-f---------
debounce:  -------------d---------f--   (emits after a quiet period)
throttle:  a-----c-----d-----f-------   (at most one per interval)
```

```swift
saveButtonTaps
    .throttle(for: .seconds(1), scheduler: DispatchQueue.main, latest: false)  // prevent double submits
    .sink { [weak self] in self?.save() }
    .store(in: &cancellables)
```

### Q46. Build a complete search-as-you-type view model. `[Senior]`
```swift
final class MovieSearchViewModel: ObservableObject {
    @Published var query = ""
    @Published private(set) var results: [Movie] = []
    @Published private(set) var isLoading = false

    private var cancellables = Set<AnyCancellable>()

    convenience init(api: MovieAPI) {
        self.init(api: api, scheduler: DispatchQueue.main)
    }

    init<S: Scheduler>(api: MovieAPI, scheduler: S) {     // inject a test scheduler in tests (Q94)
        $query
            .debounce(for: .milliseconds(300), scheduler: scheduler)  // wait for typing to pause
            .map { $0.trimmingCharacters(in: .whitespacesAndNewlines) }
            .removeDuplicates()                                        // skip identical queries
            .filter { !$0.isEmpty }
            .handleEvents(receiveOutput: { [weak self] _ in self?.isLoading = true })
            .map { query in
                api.search(query)
                    .replaceError(with: [])                            // keep the outer stream alive
            }
            .switchToLatest()                                          // cancel stale requests
            .receive(on: scheduler)                                    // main queue in production
            .sink { [weak self] movies in
                self?.isLoading = false
                self?.results = movies
            }
            .store(in: &cancellables)
    }
}
```
**Walk the interviewer through each operator and why its position matters.** For example, `replaceError` must be **inside** the `map` so one failed request doesn't kill the whole search stream (Q51).

## 9. Error Handling

### Q49. How do errors propagate in a Combine pipeline? `[Fundamental]`
**Key points:**
- When any publisher or operator fails, the failure travels downstream and **terminates the entire subscription**. Every operator is torn down; no more values flow.
- Error-handling operators (`catch`, `replaceError`, `retry`) intercept failures and decide what happens next.

### Q50. What do `catch` and `tryCatch` do? `[Fundamental]`
```swift
api.fetchFeed()
    .catch { error -> Just<[Post]> in
        logger.error("Feed failed: \(error)")
        return Just(cachedPosts)          // replace the failed upstream with a fallback publisher
    }
    .sink { posts in render(posts) }
    .store(in: &cancellables)
```
- `catch` replaces the **failed upstream** with a new publisher. When that fallback finishes, the whole stream finishes. **The original upstream isn't resumed.**
- `tryCatch` lets the handler throw, e.g. to rethrow certain errors.

### Q51. How do you handle errors without killing a long-lived stream? `[Lead/Expert]`
**Key points:**
- Handle errors **inside** a `flatMap`/`map + switchToLatest`, on each inner publisher. The inner request can fail and be replaced, while the outer stream (button taps, search text) stays alive.

```swift
enum FeedState {
    case loading, loaded([Post]), failed(String)
}

// ❌ One failure terminates the pipeline: later refreshes do nothing
refreshTapped
    .flatMap { _ in api.fetchFeed() }
    .map(FeedState.loaded)
    .catch { Just(FeedState.failed($0.localizedDescription)) }
    .assign(to: &$state)

// ✅ Errors are handled per request; refreshTapped keeps working
refreshTapped
    .flatMap { _ in
        api.fetchFeed()
            .map(FeedState.loaded)
            .catch { Just(FeedState.failed($0.localizedDescription)) }
            .prepend(.loading)
    }
    .receive(on: DispatchQueue.main)
    .assign(to: &$state)
```
- This is one of the most important Combine concepts for interviews.

### Q52. How does `retry` work, and when doesn't it help? `[Senior]`
**Key points:**
- `retry(n)` **resubscribes** to the upstream up to `n` times after a failure.
- It only redoes work if the upstream is **cold** (re-executes on subscription), like `dataTaskPublisher` or `Deferred { Future { } }`.
- It does nothing useful for `Future` without `Deferred` (cached failure), or for subjects (completion is permanent).
- It retries immediately, without delay; retrying non-idempotent requests (e.g. POST payments) can duplicate side effects.

```swift
URLSession.shared.dataTaskPublisher(for: url)
    .retry(2)                                 // up to 3 attempts in total
    .map(\.data)
    .decode(type: Config.self, decoder: JSONDecoder())
```

### Q53. How do you retry with a delay (exponential backoff)? `[Lead/Expert]`
```swift
extension Publisher {
    func retry<S: Scheduler>(
        _ retries: Int,
        initialDelay: S.SchedulerTimeType.Stride,
        scheduler: S
    ) -> AnyPublisher<Output, Failure> {
        self.catch { error -> AnyPublisher<Output, Failure> in
            guard retries > 0 else {
                return Fail(error: error).eraseToAnyPublisher()
            }
            return Just(())
                .delay(for: initialDelay, scheduler: scheduler)
                .flatMap { _ in
                    self.retry(retries - 1, initialDelay: initialDelay * 2, scheduler: scheduler)  // double the delay
                }
                .eraseToAnyPublisher()
        }
        .eraseToAnyPublisher()
    }
}

// Usage: retries after 1s, 2s, 4s
api.fetchFeed()
    .retry(3, initialDelay: .seconds(1), scheduler: DispatchQueue.main)
```
- Requires a cold upstream. In production, also add jitter and retry only on transient errors (timeouts, 5xx), not 4xx.

### Q54. What are `replaceError`, `mapError`, `setFailureType`, and `assertNoFailure`? `[Senior]`
```swift
// Replace any error with a default value. Failure becomes Never
api.fetchBanner().replaceError(with: .placeholder)

// Convert errors to your own type
api.fetchUser()
    .mapError { error -> AppError in
        (error as? URLError).map(AppError.network) ?? .unknown(error)
    }

// Make a Never-failing publisher compatible with a failing one
Just(cachedUser)
    .setFailureType(to: AppError.self)
    .merge(with: api.fetchUser())     // both now have Failure == AppError

// Crash if an error occurs (only for "impossible" failures, e.g. in tests)
Just(bundledJSON).decode(type: Config.self, decoder: JSONDecoder()).assertNoFailure()
```

### Q55. Why do you get "Failure types don't match" errors, and how do you fix them? `[Senior]`
**Key points:**
- Operators like `flatMap`, `merge`, `combineLatest`, and `zip` require matching `Failure` types (and `switchToLatest` requires the inner and outer failures to match).
- Fixes:
  - `setFailureType(to:)` on publishers with `Never`.
  - `mapError` to convert to a common error type.
  - Handle the error first (`replaceError`, `catch`) to get `Never`.
- Since iOS 14, `flatMap` has overloads that bridge `Never` and failing publishers automatically in common cases.

### Q56. How should you design error types for Combine pipelines? `[Lead/Expert]`
**Key points:**
- Use typed domain errors at service boundaries (`AnyPublisher<User, APIError>`), so consumers can switch exhaustively.
- Map low-level errors (`URLError`, `DecodingError`) into domain errors in the service layer, not in views.
- Convert errors into **state** (`.failed(message)`) before they reach the UI, so the UI-facing publishers have `Failure == Never`.

## 10. Schedulers & Threading

### Q57. What is a scheduler in Combine? `[Fundamental]`
**Key points:**
- A protocol describing **when** and **where** to run work. `DispatchQueue`, `OperationQueue`, and `RunLoop` all conform. `ImmediateScheduler` runs work synchronously.
- Time-based operators (`debounce`, `throttle`, `delay`, `timeout`) and thread-switching operators (`receive(on:)`, `subscribe(on:)`) take a scheduler.

### Q58. What is the difference between `receive(on:)` and `subscribe(on:)`? `[Senior]`
| `receive(on:)` | `subscribe(on:)` |
|---|---|
| Changes the scheduler for **downstream** events (values, completion) | Changes the scheduler for **upstream** subscription, requests, and cancellation |
| Position matters: affects everything after it | Usually affects where an upstream does its work when the work starts on subscription/request |
| Most common: switch to main before UI updates | Occasionally: start expensive synchronous work off the main thread |

```swift
Just(largeImageData)
    .subscribe(on: DispatchQueue.global(qos: .userInitiated))  // Just emits on request → background
    .map { UIImage(data: $0) }                                  // decoding happens in the background
    .receive(on: DispatchQueue.main)                            // UI updates on main
    .sink { [weak self] in self?.imageView.image = $0 }
    .store(in: &cancellables)
```
- `subscribe(on:)` doesn't affect sources that emit on their own threads (subjects, `URLSession`, notifications).

### Q59. On which thread does `dataTaskPublisher` deliver values? `[Fundamental]`
**Key points:**
- On a **background** thread (URLSession's delegate queue). Updating UI directly in `sink` is a threading bug.
- Add `.receive(on: DispatchQueue.main)` before UI updates or before assigning to `@Published` properties observed by SwiftUI (which logs a runtime warning for background publishing).

### Q60. `RunLoop.main` or `DispatchQueue.main` with `receive(on:)`? `[Lead/Expert]`
**Key points:**
- `RunLoop.main` schedules work in the run loop's **default mode**. During scrolling, the main run loop is in tracking mode, so delivery is **delayed until scrolling stops**.
- `DispatchQueue.main` delivers even during scrolling.
- Use `DispatchQueue.main` for UI updates in general; `RunLoop.main` can intentionally defer work (like image loading) until scrolling ends.

### Q61. Does `receive(on: DispatchQueue.main)` deliver synchronously if you're already on main? `[Lead/Expert]`
**Key points:**
- No. It always schedules asynchronously, so values arrive on a later run loop iteration. That can cause a one-frame flicker (e.g. a placeholder briefly showing).
- If you know the source already emits on main, skip `receive(on:)`, or use a custom "UI scheduler" that runs immediately when already on the main thread (e.g. Point-Free's `UIScheduler`).

### Q62. How does Combine interact with Swift 6 actor isolation? `[Lead/Expert]`
**Key points:**
- `receive(on: DispatchQueue.main)` guarantees main-thread delivery at runtime, but the compiler can't see that, so a `sink` closure touching `@MainActor` state may produce isolation errors in Swift 6 mode.
- Options: `MainActor.assumeIsolated { }` inside the closure (crashes if wrong); bridge to an `AsyncSequence` with `.values` and consume it in a `@MainActor` `Task`; or keep the subscriber in a `@MainActor` class with care.
- Most Combine types aren't annotated `Sendable`, which adds friction in strict concurrency mode. That's one reason teams move new async code to Swift Concurrency.

```swift
@MainActor
final class ProfileViewController: UIViewController {
    private var cancellables = Set<AnyCancellable>()
    private let nameLabel = UILabel()

    func bind(_ viewModel: ProfileViewModel) {
        viewModel.$name
            .receive(on: DispatchQueue.main)
            .sink { [weak self] name in
                MainActor.assumeIsolated {      // tell the compiler we're on the main actor
                    self?.nameLabel.text = name
                }
            }
            .store(in: &cancellables)
    }
}
```

## 11. Sharing & Multicasting

### Q63. Why would you need to share a publisher? `[Senior]`
**Key points:**
- Cold publishers run their work **once per subscriber**. Two subscribers to the same `dataTaskPublisher` pipeline make **two network requests**.
- Sharing (multicasting) runs the upstream once and delivers values to all subscribers.

```swift
let profile = api.fetchProfile()      // AnyPublisher<Profile, Error>
    .share()                          // one request for all subscribers

profile
    .map(\.name)
    .replaceError(with: "")
    .assign(to: \.text, on: nameLabel)
    .store(in: &cancellables)

profile
    .map(\.avatarURL)
    .sink(receiveCompletion: { _ in }, receiveValue: { [weak self] in self?.loadAvatar($0) })
    .store(in: &cancellables)
```

### Q64. What are the gotchas of `share()`? `[Lead/Expert]`
**Key points:**
- `share()` starts the upstream when the **first** subscriber attaches. Subscribers that attach later **miss** values already emitted. If the upstream already completed, they get only the completion.
- With synchronous upstreams (like `[1, 2, 3].publisher` or `Just`), the first subscriber receives everything before the second even subscribes (see Q117).
- `share()` doesn't replay the last value. For "replay latest" behavior, use `multicast` with a `CurrentValueSubject`, or store state in a `CurrentValueSubject`/`@Published` property.

### Q65. What are `multicast` and `connect`? `[Lead/Expert]`
**Key points:**
- `multicast(_:)` returns a **connectable** publisher: subscribers can attach first, and the upstream starts only when you call `connect()`. This avoids the late-subscriber problem.

```swift
let multicasted = api.fetchProfile()
    .multicast { PassthroughSubject<Profile, Error>() }

multicasted
    .sink(receiveCompletion: { _ in }, receiveValue: { print("A: \($0.name)") })
    .store(in: &cancellables)

multicasted
    .sink(receiveCompletion: { _ in }, receiveValue: { print("B: \($0.name)") })
    .store(in: &cancellables)

multicasted
    .connect()                 // start the single request after both subscribers are attached
    .store(in: &cancellables)
```

### Q66. What are `makeConnectable()` and `autoconnect()`? `[Senior]`
**Key points:**
- `makeConnectable()` turns a publisher with `Failure == Never` into a connectable publisher.
- `autoconnect()` connects automatically when the first subscriber attaches, which is why `Timer.publish(...)` is usually followed by `.autoconnect()`.

```swift
let ticker = Timer.publish(every: 1, on: .main, in: .common)   // a ConnectablePublisher
    .autoconnect()                                              // starts ticking on first subscription
```

### Q67. How do you cache the result of a request for multiple, possibly late, subscribers? `[Lead/Expert]`
```swift
final class ConfigService {
    private let configSubject = CurrentValueSubject<Config?, Never>(nil)
    private var cancellables = Set<AnyCancellable>()

    /// Emits the cached config immediately if available; late subscribers get it too
    var config: AnyPublisher<Config, Never> {
        configSubject.compactMap { $0 }.eraseToAnyPublisher()
    }

    func refresh(using api: ConfigAPI) {
        api.fetchConfig()
            .map(Optional.some)
            .replaceError(with: configSubject.value)   // keep the old value on failure
            .sink { [weak self] in self?.configSubject.send($0) }
            .store(in: &cancellables)
    }
}
```

## 12. Backpressure & Demand

### Q68. What is backpressure, and how does Combine implement it? `[Senior]`
**Key points:**
- Backpressure lets a **slow subscriber** control how many values it receives, so a fast publisher doesn't overwhelm it.
- Subscribers express **demand** via `Subscribers.Demand`: `.unlimited`, `.max(n)`, or `.none`. Demand is additive: each `receive(_:)` return value adds to the outstanding demand.
- `sink` and `assign` request `.unlimited`, so most apps never deal with demand directly. It matters for custom subscribers, `flatMap(maxPublishers:)`, and `buffer`.

### Q69. Write a custom subscriber that controls demand. `[Lead/Expert]`
```swift
final class BatchSubscriber: Subscriber {
    typealias Input = Int
    typealias Failure = Never

    private var subscription: Subscription?

    func receive(subscription: Subscription) {
        self.subscription = subscription
        subscription.request(.max(2))          // start by asking for 2 values
    }

    func receive(_ input: Int) -> Subscribers.Demand {
        print("Processing \(input)")
        return input.isMultiple(of: 2) ? .max(2) : .none   // ask for more only after even numbers
    }

    func receive(completion: Subscribers.Completion<Never>) {
        print("Completed: \(completion)")
    }
}

(1...6).publisher.subscribe(BatchSubscriber())
```

### Q70. What does `buffer` do? `[Lead/Expert]`
```swift
sensorReadings
    .buffer(size: 100, prefetch: .keepFull, whenFull: .dropOldest)
    .flatMap(maxPublishers: .max(1)) { reading in uploader.upload(reading).replaceError(with: ()) }
    .sink { }
    .store(in: &cancellables)
```
- Buffers values when downstream demand is lower than the upstream's production rate.
- `whenFull`: `.dropOldest`, `.dropNewest`, or `.customError` to fail the stream.
- Useful when a source can't be slowed down (sensors, subjects) and the downstream processes one item at a time.

### Q71. What happens to values sent into a `PassthroughSubject` when a subscriber has no demand? `[Lead/Expert]`
**Key points:**
- They're **dropped** for that subscriber. Subjects can't pause their source, so without demand there's nowhere to put the value.
- This matters with custom subscribers, `flatMap(maxPublishers:)`, and when bridging to `AsyncSequence` with `.values` (Q101). Add a `buffer` if values must not be lost.

## 13. Type Erasure

### Q72. Why use `eraseToAnyPublisher()`? `[Fundamental]`
**Key points:**
- Combine operators produce deeply nested generic types:
  `Publishers.ReceiveOn<Publishers.Map<Publishers.Debounce<Published<String>.Publisher, DispatchQueue>, String>, DispatchQueue>`.
- `AnyPublisher<Output, Failure>` hides these implementation details at API boundaries, so you can change the pipeline without changing the public type, and callers can't downcast to the subject to call `send`.

```swift
protocol WeatherService {
    func forecast(for city: String) -> AnyPublisher<Forecast, WeatherError>
}
```

### Q73. What does type erasure cost, and what are the alternatives? `[Lead/Expert]`
**Key points:**
- A small runtime cost (boxing and dynamic dispatch) and lost compiler optimizations. Negligible for most app code, but avoid erasing inside hot inner loops.
- Since Swift 5.7, `Publisher` has primary associated types, so you can return `some Publisher<Output, Failure>` to hide the concrete type while keeping it static.

```swift
func searchResults(for query: String) -> some Publisher<[Movie], Never> {
    api.search(query).replaceError(with: [])
}
```
- `AnyPublisher` is still preferred in protocols (where opaque types can't express "any implementation") and for stored properties.

### Q74. What are `AnySubscriber` and `AnyCancellable`? `[Senior]`
**Key points:**
- `AnySubscriber` type-erases a subscriber, which is useful when building custom publishers or subscriptions that store subscribers of unknown concrete types (see Q90).
- `AnyCancellable` type-erases a cancellable and adds **cancel-on-deinit** behavior. Wrap any `Cancellable` with `AnyCancellable(cancellable)` to get that behavior.

## 14. Networking with Combine

### Q75. Write a generic API client using Combine. `[Senior]`
```swift
enum APIError: Error {
    case invalidResponse
    case httpStatus(Int)
    case decoding(Error)
    case network(URLError)
    case unknown(Error)
}

struct APIClient {
    var session: URLSession = .shared
    var decoder = JSONDecoder()

    func request<T: Decodable>(_ url: URL, as type: T.Type = T.self) -> AnyPublisher<T, APIError> {
        session.dataTaskPublisher(for: url)
            .tryMap { output in
                guard let http = output.response as? HTTPURLResponse else {
                    throw APIError.invalidResponse
                }
                guard (200..<300).contains(http.statusCode) else {
                    throw APIError.httpStatus(http.statusCode)
                }
                return output.data
            }
            .decode(type: T.self, decoder: decoder)
            .mapError { error in
                switch error {
                case let apiError as APIError: return apiError
                case let urlError as URLError: return .network(urlError)
                case is DecodingError: return .decoding(error)
                default: return .unknown(error)
                }
            }
            .eraseToAnyPublisher()
    }
}
```
- Note there's no `receive(on:)` here: the client shouldn't decide the consumer's thread. The view model adds `receive(on: DispatchQueue.main)`.

### Q76. How do you chain dependent requests? `[Fundamental]`
```swift
func loadDashboard(userID: Int) -> AnyPublisher<Dashboard, APIError> {
    api.request(userURL(userID), as: User.self)
        .flatMap { user in
            api.request(ordersURL(user.accountID), as: [Order].self)
                .map { orders in Dashboard(user: user, orders: orders) }
        }
        .eraseToAnyPublisher()
}
```

### Q77. How do you run requests in parallel and combine results? `[Senior]`
```swift
// Fixed number of requests: zip
api.request(profileURL, as: Profile.self)
    .zip(api.request(settingsURL, as: Settings.self),
         api.request(notificationsURL, as: [AppNotification].self))
    .map { profile, settings, notifications in
        HomeScreenData(profile: profile, settings: settings, notifications: notifications)
    }

// Dynamic number of requests: MergeMany + collect (see Q42 for preserving order)
Publishers.MergeMany(ids.map { api.request(itemURL($0), as: Item.self) })
    .collect()
```
- With `zip`, if any request fails the whole result fails. To allow partial success, map each request's errors into a `Result` first.

### Q78. How do you poll an endpoint periodically? `[Senior]`
```swift
Timer.publish(every: 30, on: .main, in: .common)
    .autoconnect()
    .prepend(Date())                                     // fire immediately on subscription
    .map { _ in
        api.request(statusURL, as: OrderStatus.self)
            .map(Optional.some)
            .replaceError(with: nil)                    // don't stop polling on errors
    }
    .switchToLatest()                                    // drop a slow request if the next tick arrives
    .compactMap { $0 }
    .removeDuplicates()
    .receive(on: DispatchQueue.main)
    .sink { [weak self] status in self?.render(status) }
    .store(in: &cancellables)
```
- Stop polling by cancelling the subscription (e.g. when the screen disappears or the order completes, using `prefix(while:)`).

### Q79. How do you make sure requests are cancelled when the screen goes away? `[Fundamental]`
**Key points:**
- Store subscriptions in the view model or view controller's `cancellables`. When that object is deallocated, the subscriptions cancel and `dataTaskPublisher` cancels the underlying `URLSessionTask`.
- Avoid strong `self` captures in `sink`, which would keep the object (and requests) alive after the screen is dismissed.

## 15. Combine with UIKit

### Q80. How do you bind a view model to a UIKit view controller with Combine? `[Senior]`
```swift
final class LoginViewController: UIViewController {
    private let viewModel = LoginViewModel()
    private var cancellables = Set<AnyCancellable>()
    private let emailField = UITextField()
    private let passwordField = UITextField()
    private let loginButton = UIButton(configuration: .filled())
    private let errorLabel = UILabel()

    override func viewDidLoad() {
        super.viewDidLoad()
        bindInputs()
        bindOutputs()
    }

    private func bindInputs() {
        NotificationCenter.default.publisher(for: UITextField.textDidChangeNotification, object: emailField)
            .compactMap { ($0.object as? UITextField)?.text }
            .assign(to: \.email, on: viewModel)        // retains the view model, which doesn't own us: no cycle
            .store(in: &cancellables)

        NotificationCenter.default.publisher(for: UITextField.textDidChangeNotification, object: passwordField)
            .compactMap { ($0.object as? UITextField)?.text }
            .assign(to: \.password, on: viewModel)
            .store(in: &cancellables)
    }

    private func bindOutputs() {
        viewModel.$isLoginEnabled
            .receive(on: DispatchQueue.main)
            .assign(to: \.isEnabled, on: loginButton)
            .store(in: &cancellables)

        viewModel.$errorMessage
            .receive(on: DispatchQueue.main)
            .sink { [weak self] message in
                self?.errorLabel.text = message
                self?.errorLabel.isHidden = message == nil
            }
            .store(in: &cancellables)
    }
}
```

## 16. Combine with SwiftUI

### Q83. How do `ObservableObject` and `@Published` relate to Combine? `[Fundamental]`
**Key points:**
- `ObservableObject` provides an `objectWillChange` publisher. Each `@Published` property change sends `objectWillChange` **before** the change, and SwiftUI re-renders views observing the object.
- `@Published` properties also expose `$property` publishers for Combine pipelines (validation, debouncing).

```swift
final class SettingsStore: ObservableObject {
    @Published var username = ""
    @Published private(set) var isUsernameAvailable = true

    init(api: UsernameAPI) {
        $username
            .debounce(for: .milliseconds(400), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { name in api.isAvailable(name).replaceError(with: false) }
            .switchToLatest()
            .receive(on: DispatchQueue.main)
            .assign(to: &$isUsernameAvailable)
    }
}
```

### Q84. How do you subscribe to a publisher inside a SwiftUI view? `[Fundamental]`
```swift
struct OrderStatusView: View {
    let statusUpdates: AnyPublisher<OrderStatus, Never>
    @State private var status: OrderStatus = .pending

    var body: some View {
        Text(status.description)
            .onReceive(statusUpdates) { newStatus in    // delivered on the thread the publisher emits on
                status = newStatus
            }
    }
}
```
- Make sure the publisher delivers on the main thread (add `receive(on:)` upstream), and avoid creating new publishers inside `body`, which causes resubscription on every render.

### Q85. When would you call `objectWillChange.send()` manually? `[Senior]`
**Key points:**
- When an `ObservableObject` has state that isn't `@Published` (e.g. values stored in a non-published dictionary, a wrapped legacy object, or computed from external storage) and you need SwiftUI to refresh.

### Q86. With `@Observable` (iOS 17+), where does Combine fit in SwiftUI? `[Lead/Expert]`
**Key points:**
- `@Observable` models don't use Combine and have no `$property` publishers. SwiftUI tracks property reads directly, with finer-grained updates than `ObservableObject`.
- If you need reactive pipelines on an `@Observable` model's properties: use `didSet` to feed a private subject; use `withObservationTracking` or Swift 6.2's `Observations` async sequence; or move the logic into async code (`.task(id:)` for debouncing).
- Combine remains useful in services and data layers (streams from sockets, sensors, legacy APIs) even when the UI uses Observation.

```swift
@Observable
final class SearchModel {
    var query = "" {
        didSet { querySubject.send(query) }      // bridge property changes into Combine
    }
    private(set) var results: [Movie] = []

    @ObservationIgnored private let querySubject = PassthroughSubject<String, Never>()
    @ObservationIgnored private var cancellables = Set<AnyCancellable>()

    init(api: MovieAPI) {
        querySubject
            .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { api.search($0).replaceError(with: []) }
            .switchToLatest()
            .receive(on: DispatchQueue.main)
            .sink { [weak self] in self?.results = $0 }
            .store(in: &cancellables)
    }
}
```

### Q87. What is the best way to run a timer in SwiftUI? `[Senior]`
**Key points:**
- `Timer.publish(...).autoconnect()` with `.onReceive` works, but publishers stored on a view struct get recreated as the view is recreated.
- Often better: `TimelineView(.periodic(from:by:))` for display-driven updates, or `.task { while !Task.isCancelled { …; try? await Task.sleep(for: .seconds(1)) } }`, which is cancelled automatically.


## 17. Custom Publishers, Subscribers & Operators

### Q88. How do you write a custom operator? `[Senior]`
**Key points:**
- Usually as an extension on `Publisher` that composes existing operators. This is the safest and most common approach.

```swift
extension Publisher where Output == String, Failure == Never {
    /// Normalizes and debounces text input for search
    func searchQuery<S: Scheduler>(
        debounce interval: S.SchedulerTimeType.Stride,
        scheduler: S,
        minimumLength: Int = 2
    ) -> AnyPublisher<String, Never> {
        self
            .debounce(for: interval, scheduler: scheduler)
            .map { $0.trimmingCharacters(in: .whitespacesAndNewlines) }
            .removeDuplicates()
            .filter { $0.count >= minimumLength }
            .eraseToAnyPublisher()
    }
}

extension Publisher {
    /// Emits pairs of (previous, current) values
    func withPrevious() -> AnyPublisher<(previous: Output?, current: Output), Failure> {
        scan((previous: Output?.none, current: Output?.none)) { state, new in
            (previous: state.current, current: new)
        }
        .compactMap { state in state.current.map { (previous: state.previous, current: $0) } }
        .eraseToAnyPublisher()
    }
}

// Usage
$query.searchQuery(debounce: .milliseconds(300), scheduler: DispatchQueue.main)
$selectedTab.withPrevious().sink { print("from \(String(describing: $0.previous)) to \($0.current)") }
```

### Q89. When should you write a custom `Publisher` instead of composing operators? `[Lead/Expert]`
**Key points:**
- When wrapping an event source that has no publisher (UIControl events, a delegate-based SDK, a C callback API) and a subject-based wrapper isn't enough (e.g. you need per-subscriber setup/teardown).
- A correct custom publisher must respect the Combine contract: honor demand, deliver events serially, stop after completion or cancellation, and clean up resources on cancel. That's easy to get wrong, so prefer composing existing publishers, `Deferred`, `Future`, or subjects when possible.

### Q90. Implement a custom publisher for UIControl events. `[Lead/Expert]`
```swift
import Combine
import UIKit

extension UIControl {
    struct EventPublisher: Publisher {
        typealias Output = UIControl
        typealias Failure = Never

        let control: UIControl
        let events: UIControl.Event

        func receive<S: Subscriber>(subscriber: S) where S.Input == UIControl, S.Failure == Never {
            let subscription = EventSubscription(
                subscriber: AnySubscriber(subscriber),
                control: control,
                events: events
            )
            subscriber.receive(subscription: subscription)
        }
    }

    final class EventSubscription: NSObject, Subscription {
        private var subscriber: AnySubscriber<UIControl, Never>?
        private weak var control: UIControl?
        private var demand: Subscribers.Demand = .none

        init(subscriber: AnySubscriber<UIControl, Never>, control: UIControl, events: UIControl.Event) {
            self.subscriber = subscriber
            self.control = control
            super.init()
            control.addTarget(self, action: #selector(handleEvent), for: events)
        }

        func request(_ demand: Subscribers.Demand) {
            self.demand += demand
        }

        func cancel() {
            control?.removeTarget(self, action: #selector(handleEvent), for: .allEvents)
            subscriber = nil
        }

        @objc private func handleEvent() {
            guard let control, let subscriber, demand > 0 else { return }   // respect demand
            demand -= 1
            demand += subscriber.receive(control)
        }
    }

    func publisher(for events: UIControl.Event) -> EventPublisher {
        EventPublisher(control: self, events: events)
    }
}

// Usage
slider.publisher(for: .valueChanged)
    .compactMap { ($0 as? UISlider)?.value }
    .sink { print("Slider: \($0)") }
    .store(in: &cancellables)
```
- The subscription is retained by the subscriber (`sink`'s cancellable), and the control holds the target weakly, so there's no retain cycle.

### Q91. How do you wrap a delegate-based API in Combine? `[Senior]`
```swift
final class LocationPublisher: NSObject, CLLocationManagerDelegate {
    private let manager = CLLocationManager()
    private let subject = PassthroughSubject<CLLocation, Error>()

    var locations: AnyPublisher<CLLocation, Error> {
        subject
            .handleEvents(
                receiveSubscription: { [weak self] _ in self?.manager.startUpdatingLocation() },
                receiveCancel: { [weak self] in self?.manager.stopUpdatingLocation() }
            )
            .eraseToAnyPublisher()
    }

    override init() {
        super.init()
        manager.delegate = self
    }

    func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
        locations.forEach { subject.send($0) }
    }

    func locationManager(_ manager: CLLocationManager, didFailWithError error: Error) {
        subject.send(completion: .failure(error))
    }
}
```
- With multiple subscribers, cancelling one would stop updates for all. Add reference counting or `share()` in production.
- On iOS 17+, `CLLocationUpdate.liveUpdates()` provides an `AsyncSequence` instead.

### Q94. How do you test time-based operators deterministically? `[Lead/Expert]`
**Key points:**
- Inject the scheduler into the type under test. In production pass `DispatchQueue.main`; in tests pass a **test scheduler** you advance manually. Point-Free's `CombineSchedulers` library provides `DispatchQueue.test` and type-erased `AnySchedulerOf<DispatchQueue>`.

```swift
import CombineSchedulers

func testSearchWaitsForDebounce() {
    let scheduler = DispatchQueue.test
    let viewModel = MovieSearchViewModel(api: MockMovieAPI(results: [.sample]), scheduler: scheduler)

    viewModel.query = "Dune"

    scheduler.advance(by: .milliseconds(299))
    XCTAssertTrue(viewModel.results.isEmpty)        // still debouncing

    scheduler.advance(by: .milliseconds(1))
    XCTAssertEqual(viewModel.results, [.sample])    // debounce fired; mock responded immediately
}
```
- The test runs instantly and never flakes. This is a strong signal of senior testing practice.

### Q95. How do you test publishers with Swift Testing? `[Senior]`
**Key points:**
- For finite, **cold** publishers, iterate `.values` with `for try await`. Cold publishers honor demand, so no values are lost.

```swift
import Testing

struct ItemRepositoryTests {
    @Test func emitsCachedThenFreshItems() async throws {
        let repository = ItemRepository(
            cache: MockCache(items: [.cached]),
            api: MockItemAPI(items: [.fresh])          // returns Just(...).setFailureType(to: Error.self)
        )

    }

```
- For hot sources (subjects, `@Published`), collect values synchronously in a `sink` instead; `.values` can drop values emitted while the test isn't awaiting (Q101).

## 19. Combine & Swift Concurrency

### Q97. Compare Combine and async/await. `[Senior]`
| | Combine | Swift Concurrency |
|---|---|---|
| Best at | Streams of values over time, reactive bindings, time-based operators | One-shot async work, structured tasks, sequential async code |
| Style | Declarative operator chains | Imperative-looking code with `await` |
| Cancellation | `AnyCancellable` lifetime | Structured task cancellation |
| Thread safety | Schedulers; not `Sendable`-annotated | Actors, `Sendable`, compile-time data race checks (Swift 6) |
| Errors | Typed `Failure`; errors terminate streams | `throws` (typed throws in Swift 6) |
| Debugging | Long generic types, harder stack traces | Linear code, easier to read and debug |
| Apple's investment | Stable, few new features | Actively evolving |

- Senior answer: new async code should generally use Swift Concurrency; Combine is still a good fit for complex event-stream logic and existing reactive codebases. Know how to bridge both ways.

### Q98. How do you consume a publisher with async/await? `[Senior]`
```swift
// iOS 15+: every publisher exposes `values` as an AsyncSequence
Task {
    for await isOnline in reachability.$isOnline.values {        // Failure == Never → AsyncPublisher
        banner.isHidden = isOnline
    }
}

Task {
    do {
        for try await message in socket.messages.values {         // Failure: Error → AsyncThrowingPublisher
            handle(message)
        }
    } catch {
        showError(error)
    }
}
```

### Q99. How do you await a single value from a publisher? `[Senior]`
```swift
extension Publisher {
    func firstValue() async throws -> Output {
        for try await value in values {
            return value                   // leaving the loop cancels the subscription
        }
        throw PublisherError.finishedWithoutValue
    }
}

enum PublisherError: Error { case finishedWithoutValue }

// Usage

```

### Q100. How do you expose an async function as a publisher? `[Senior]`
```swift
func publisher<Output>(
    from operation: @escaping @Sendable () async throws -> Output
) -> AnyPublisher<Output, Error> {
    Deferred {                       // run once per subscriber, only when subscribed
        Future { promise in
            Task {
                do { promise(.success(try await operation())) }
                catch { promise(.failure(error)) }
            }
        }
    }
    .eraseToAnyPublisher()
}

// Usage in a Combine pipeline
$query
    .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
    .map { query in publisher { try await api.search(query) }.replaceError(with: []) }
    .switchToLatest()
```
**Caveats to mention:**
- Cancelling the subscription does **not** cancel the inner `Task`; the work continues and its result is discarded. Full cancellation needs a custom publisher that cancels the task on `cancel()`.
- In Swift 6 mode, capturing the non-`Sendable` `promise` in a `Task` may produce diagnostics.

### Q101. What is the gotcha with `.values` on hot publishers? `[Lead/Expert]`
**Key points:**
- `AsyncPublisher` requests **one value at a time** (demand of 1) as the loop asks for the next element.
- Hot sources like `PassthroughSubject` can't wait. Values sent while the loop body is still processing the previous value have **no demand** and are **dropped**.
- Fix: add `.buffer(size:prefetch:whenFull:)` before `.values`, or use an `AsyncStream` with an appropriate buffering policy.

```swift
for await event in eventSubject
    .buffer(size: 50, prefetch: .byRequest, whenFull: .dropOldest)
    .values {
    await process(event)   // slow processing no longer causes lost events (up to 50 buffered)
}
```

### Q102. What are Swift Concurrency equivalents of common Combine features? `[Lead/Expert]`
| Combine | Swift Concurrency / AsyncAlgorithms |
|---|---|
| `PassthroughSubject` | `AsyncStream` (single consumer) or `AsyncChannel` (AsyncAlgorithms) |
| `@Published` / `CurrentValueSubject` | `@Observable` properties; Swift 6.2 `Observations` sequence |
| `debounce` | `debounce(for:)` (AsyncAlgorithms), or `.task(id:)` + `Task.sleep` in SwiftUI |
| `throttle` | `throttle` (AsyncAlgorithms) |
| `combineLatest`, `merge`, `zip` | Same-named functions in AsyncAlgorithms |
| `flatMap(maxPublishers:)` | `TaskGroup` with limited concurrency |
| `switchToLatest` | Cancel the previous `Task`, or `.task(id:)` |
| `Timer.publish` | `AsyncTimerSequence` (AsyncAlgorithms) or a `Task.sleep` loop |
| `retry` | A loop with `do/catch` |
| `share()` | No standard-library equivalent; multi-consumer broadcast needs custom code or a library |
| `AnyCancellable` | `Task` handles and structured cancellation |

### Q103. How would you migrate a Combine-heavy codebase to Swift Concurrency? `[Lead/Expert]`
**Talking points:**
- **Don't rewrite everything.** Migrate where async/await is clearly better: one-shot network calls (`AnyPublisher<T, Error>` → `async throws -> T`), persistence calls, and sequential flows.
- **Bridge at boundaries**: wrap existing publishers with `.values`/`firstValue()` for new async callers; wrap new async APIs with a publisher adapter for old Combine callers.
- **UI layer**: move `ObservableObject` + `@Published` to `@Observable` (iOS 17+), replacing `$property` pipelines with `didSet`, `.task(id:)`, or async sequences.
- **Keep Combine** where it shines (complex time-based event streams) until AsyncAlgorithms or your own code covers them cleanly.
- **Order**: leaf services first, then view models, then UI; enable Swift 6 checks per module.
- Track progress, and write tests before migrating behavior-heavy pipelines (debounce/cancellation semantics are easy to change accidentally).

### Q104. Is it a problem to mix Combine and async/await in one feature? `[Senior]`
**Key points:**
- It's fine at **clear boundaries** (e.g. a Combine-based service consumed via `.values` in a `@MainActor` task), but avoid ping-ponging between the two inside one pipeline.
- Watch for: lost cancellation when bridging (Q100), dropped values with `.values` on hot sources (Q101), and actor isolation warnings when Combine closures touch main-actor state (Q62).

### Q105. How do you debug a Combine pipeline? `[Fundamental]`

### Q106. A pipeline "does nothing." What do you check? `[Senior]`
**Checklist:**
1. Is the `AnyCancellable` **stored**? (Most common cause.)
2. Did the upstream **fail or complete earlier**, terminating the stream (e.g. an earlier error, or a `catch` placed outside a `flatMap`)?
3. Are you subscribing to a **hot** source after it emitted (late subscriber with `PassthroughSubject` or `share()`)?
4. Is `Future` caching an old result, or is `combineLatest` waiting for an input that never emitted?
5. Is delivery delayed by `receive(on: RunLoop.main)` during scrolling, or by a `debounce` that keeps resetting?
6. Is demand limited (custom subscriber, `flatMap(maxPublishers:)`)?
- Add `.print()` at several points to see where events stop.

### Q107. How do you find Combine-related memory leaks? `[Senior]`
**Key points:**
- Symptoms: view models or view controllers never deallocated; subscriptions keep firing after screens are dismissed; duplicate events after reopening a screen.
- Tools: Memory Graph Debugger (look for closures held by `Subscribers.Sink`), `deinit` logs, leak tests asserting deallocation.
- Usual causes: strong `self` in `sink`, `assign(to:on: self)`, subscriptions stored in a long-lived singleton's set, cells not cancelling bindings on reuse.

### Q108. Not storing the cancellable (async publisher) `[Fundamental]`

### Q110. `catch` ends the stream `[Senior]`

```swift
    promise(.success(42))
}
print("Before subscribing")
future.sink { print("A: \($0)") }.store(in: &cancellables)
future.sink { print("B: \($0)") }.store(in: &cancellables)
```
**Output:** `Future started`, `Before subscribing`, `A: 42`, `B: 42`. The closure runs once at creation; both subscribers get the cached result.

### Q116. Multiple subscribers to a cold publisher `[Senior]`

### Q117. `share()` with a synchronous upstream `[Lead/Expert]`

### Q121. `assign(to:on: self)` `[Senior]`

### Q122. `sink(receiveValue:)` on a failing publisher `[Fundamental]`
```swift

```
**Answer:** Compile error. `sink(receiveValue:)` requires `Failure == Never`, but `dataTaskPublisher` fails with `URLError`. Use `sink(receiveCompletion:receiveValue:)` or handle the error first.

### Q123. `RunLoop.main` while scrolling `[Lead/Expert]`
```swift

    .sink { [weak self] in self?.scoreLabel.text = $0 }
    .store(in: &cancellables)
```
**Question:** What happens to score updates while the user is scrolling a table view?

**Answer:** They're delayed until scrolling stops, because `RunLoop.main` schedules in the default mode and the run loop is in tracking mode during scrolling. Use `DispatchQueue.main` for live updates.

### Q124. `timeout` without a custom error `[Senior]`

## 23. Senior / Lead Scenario Questions

### Q125. Should a new codebase use Combine in 2026? `[Lead/Expert]`
**Talking points:**
- **Default**: Swift Concurrency for async work and Observation for SwiftUI state. They're Apple's actively evolving direction, offer compile-time data race safety, and are easier for new team members to read.
- **Use Combine selectively**: complex event-stream logic (debounce + combine + switch latest across many sources), integration with Combine-based SDKs, or teams with strong Combine expertise and existing infrastructure.
- **Avoid**: mixing three paradigms (delegates, Combine, async/await) arbitrarily in one codebase. Document when each is appropriate in team guidelines.

### Q126. Your app has a large Combine-based networking layer. How do you modernize it? `[Lead/Expert]`
**Talking points:**
- Add `async` counterparts to the API client, implemented natively with `URLSession`'s async APIs; keep publisher-returning methods temporarily as thin adapters over the async versions (or vice versa during the transition).
- Migrate call sites feature by feature, starting with simple one-shot requests.
- Write characterization tests first for retry, cancellation, and error-mapping behavior, then verify the async version matches.
- Remove Combine adapters once no callers remain; track progress per module.
- Communicate the plan, timeline, and coding guidelines to the team.

### Q127. Multiple requests fail with 401 at the same time. How do you refresh the token only once? `[Lead/Expert]`
**Talking points:**
- Keep a single **in-flight refresh publisher**, shared among all requests that need it; clear it when it completes.
- Each request catches 401, waits for the shared refresh, then retries once with the new token.
- Protect the shared state with a serial queue (or an actor in async code), and handle refresh failure by logging the user out.

```swift
final class TokenRefresher {
    private let queue = DispatchQueue(label: "token-refresher")
    private var inFlight: AnyPublisher<Token, Error>?
    private let authAPI: AuthAPI

    init(authAPI: AuthAPI) { self.authAPI = authAPI }

    func refreshedToken() -> AnyPublisher<Token, Error> {
        queue.sync {
            if let inFlight { return inFlight }

            let publisher = authAPI.refreshToken()
                .handleEvents(receiveCompletion: { [weak self] _ in
                    self?.queue.async { self?.inFlight = nil }
                })
                .share()                         // all waiting requests share one refresh
                .eraseToAnyPublisher()

            inFlight = publisher
            return publisher
        }
    }
}

// In the API client
func authorized<T: Decodable>(_ request: URLRequest, as type: T.Type) -> AnyPublisher<T, Error> {
    send(request, token: tokenStore.current, as: type)
        .catch { [weak self] error -> AnyPublisher<T, Error> in
            guard let self, case .httpStatus(401)? = error as? APIError else {   // APIError from Q75
                return Fail(error: error).eraseToAnyPublisher()
            }
            return self.refresher.refreshedToken()
                .flatMap { token in self.send(request, token: token, as: type) }   // retry once
                .eraseToAnyPublisher()
        }
        .eraseToAnyPublisher()
}
```
- Mention the late-subscriber caveat of `share()`: a request that starts waiting after the refresh already completed gets only the completion. Caching the latest token (e.g. in a `CurrentValueSubject`) avoids that. In async code, an actor holding a `Task<Token, Error>` is a simpler solution.

### Q128. Design a real-time stream (e.g. WebSocket chat) using Combine. `[Lead/Expert]`
**Talking points:**
- A connection service exposes `AnyPublisher<Message, Never>` for messages and `AnyPublisher<ConnectionState, Never>` for status; internal subjects are private.
- Decode on a background queue; `receive(on: DispatchQueue.main)` only at the UI boundary.
- Reconnect with exponential backoff on failure, without terminating the public streams (errors become `ConnectionState.disconnected` values, not stream failures).
- Use `buffer` for bursts, `share()` so multiple screens don't open multiple sockets, and heartbeats with `Timer.publish`.
- Test with a controllable fake socket and a test scheduler.

### Q129. Users report duplicate network calls and UI updates after navigating back and forth. How do you investigate? `[Lead/Expert]`
**Talking points:**
- Suspects: subscriptions re-created on every `viewWillAppear` without cancelling old ones; cells binding without cancelling on reuse; view models leaking (strong `self`), so old instances keep reacting; cold publishers subscribed multiple times without `share()`.
- Investigate with `.print()`/`handleEvents(receiveSubscription:)` counters, Memory Graph Debugger, and `deinit` logs.
- Fix: bind once (e.g. in `viewDidLoad`) or replace a stored cancellable; cancel in `prepareForReuse`; break cycles; share expensive publishers.
- Prevent: leak tests, a review checklist, and team guidelines for subscription ownership.

### Q130. What do you look for when reviewing Combine code? `[Lead/Expert]`
**Talking points:**
- **Lifetime**: cancellables stored by the right owner; no strong `self` in `sink`; no `assign(to:on: self)`.
- **Errors**: error handling placed so long-lived streams survive (inside `flatMap`); no silent `replaceError` hiding real problems; typed errors at boundaries.
- **Threading**: `receive(on: DispatchQueue.main)` before UI work; no `RunLoop.main` for live updates; no unnecessary thread hops.
- **Correctness**: `switchToLatest` vs `flatMap` chosen deliberately; `Future` wrapped in `Deferred` when laziness/retry matters; `share()` where multiple subscribers exist.
- **API design**: subjects private, exposed as `AnyPublisher`; schedulers injectable for tests.
- **Readability**: long chains split into named, documented steps or custom operators.

### Q131. How would you explain Combine to a junior engineer? `[Senior]`
**Talking points:**
- Analogy: a **water pipeline**. The publisher is the source, operators are filters and valves, the subscriber is the tap. Nothing flows until a tap is opened (subscription), and closing the tap (cancelling) stops the flow.
- Draw a marble diagram for `map`, `filter`, and `debounce` on a whiteboard.
- Show the three bugs every beginner hits: not storing the cancellable, strong `self` in `sink`, and updating UI from a background thread. Then show the fixes.

### Q132. Design a repository that shows cached data first, then fresh data. `[Senior]`
```swift
final class ArticleRepository {
    private let cache: ArticleCache
    private let api: ArticleAPI

    init(cache: ArticleCache, api: ArticleAPI) {
        self.cache = cache
        self.api = api
    }

    /// Emits cached articles immediately (if any), then fresh ones. Never fails;
    /// errors are surfaced as state so the UI can keep showing cached content.
    func articles() -> AnyPublisher<RepositoryState<[Article]>, Never> {
        let cached = cache.load().map { RepositoryState.cached($0) }

        let fresh = api.fetchArticles()
            .handleEvents(receiveOutput: { [cache] in cache.save($0) })
            .map { RepositoryState.fresh($0) }
            .catch { Just(RepositoryState<[Article]>.failed($0)) }

        return fresh
            .prepend(cached.map { [$0] } ?? [])
            .eraseToAnyPublisher()
    }
}

enum RepositoryState<Value> {
    case cached(Value)
    case fresh(Value)
    case failed(Error)
}
```
- Talking points: the UI never loses cached content on failure; saving to cache is a side effect in `handleEvents`; the API layer can be cold so pull-to-refresh simply resubscribes.
