## 1. Processes & Threads: OS Fundamentals

### Q1. What is the difference between a process and a thread? `[Fundamental]`
| | Process | Thread |
|---|---|---|
| What it is | A running program: an isolated container of resources | A path of execution **inside** a process |
| Memory | Own **virtual address space**; can't read another process's memory | **Shares** the process's memory (heap, globals, code) with other threads |
| Owns | Address space, open files, ports, sandbox, security identity, at least one thread | Its own **stack**, registers (including program counter), thread-local storage, scheduling priority |
| Creation cost | High (address space, kernel structures, loading code) | Lower (~stack + kernel thread structures) |
| Communication | IPC (XPC, Mach ports, pipes, shared files) | Directly through shared memory (needs synchronization) |
| Failure isolation | A crash kills only that process | A crash in one thread kills the **whole process** |

**One-line answer:** "A process is the unit of **isolation** (memory, security); a thread is the unit of **execution** (what the CPU schedules)."

### Q2. What does a process's memory look like? `[Fundamental]`
```
High addresses
┌──────────────────────────┐
│ Stack (main thread)      │  grows ↓  local variables, return addresses
├──────────────────────────┤
│ Stacks of other threads  │  each thread has its own stack (512 KB default on iOS)
├──────────────────────────┤
│ Memory-mapped region     │  dylibs/frameworks, mapped files, shared cache
├──────────────────────────┤
│           ↑              │
│ Heap                     │  grows ↑  class instances, malloc, large buffers
├──────────────────────────┤
│ Data / BSS               │  globals, static variables
├──────────────────────────┤
│ Text (__TEXT)            │  machine code (read-only, executable)
└──────────────────────────┘
Low addresses           (layout randomized by ASLR at every launch)
```
- **Stack**: per thread, fast, automatic, limited size; overflowing it (deep recursion) crashes with `EXC_BAD_ACCESS`.
- **Heap**: shared by all threads; that's where races happen.
- Details of virtual memory, paging and ASLR: OS Fundamentals & Linker file.

### Q3. What do threads share, and what is private to each thread? `[Fundamental]`
| Shared by all threads in a process | Private to each thread |
|---|---|
| Heap objects (class instances, closures' captured boxes) | Stack (local value types, function frames) |
| Global and static variables | CPU registers, program counter, stack pointer |
| Code, loaded frameworks | Thread-local storage |
| Open files, sockets, Mach ports | Scheduling state, priority/QoS |
| Process memory limits | Signal mask, `errno` |

So a **local struct** is safe without locks (each thread has its own copy), but a **class instance** or **global variable** reached by two threads needs synchronization.

### Q4. What are thread states, and what is a context switch? `[Senior]`
```
         create
 New ─────────────▶ Runnable ◀──────────── Blocked/Waiting
                     │    ▲  preempted       ▲  (lock, I/O, sleep, semaphore)
            scheduled│    │  (time slice     │
                     ▼    │   over)          │
                   Running ─────────────────┘
                     │
                     ▼ returns / exits
                 Terminated
```
- **Context switch**: the kernel saves one thread's registers and loads another's. Switching between threads of **different processes** also switches address spaces (more expensive: TLB and cache effects).
- Cost: a few microseconds directly, more indirectly (cold CPU caches). Thousands of switches per second from too many threads waste CPU and battery. That's one reason GCD and Swift Concurrency limit thread counts.

### Q5. What is the difference between concurrency and parallelism? `[Fundamental]`
- **Concurrency**: dealing with many things at once, by structure. Tasks make progress interleaved, even on **one** core.
- **Parallelism**: doing many things at **the same instant**, on **multiple cores**.

```
Concurrency on 1 core:   A A B B A C C A B     (interleaved)
Parallelism on 2 cores:  core 1: A A A A A
                         core 2: B B B C C
```
- A network request and UI updates are concurrent (the CPU is idle while waiting).
- Image filtering split across cores is parallel (`DispatchQueue.concurrentPerform`, task groups).

### Q6. How does the OS scheduler decide which thread runs? `[Senior]`
- XNU (the iOS/macOS kernel) uses **preemptive, priority-based** scheduling: higher-priority runnable threads run first; each thread gets a **time slice** (quantum); a higher-priority thread becoming runnable can **preempt** a lower one.
- Apple Silicon has **performance (P) cores** and **efficiency (E) cores**; the scheduler uses the thread's **QoS** (Q24) to decide: `userInteractive`/`userInitiated` work prefers P-cores, `background` work may run only on E-cores.
- Threads that block (waiting on I/O or a lock) give up the CPU immediately.
- **Starvation** protection: priority decay for CPU-hungry threads; **priority inheritance/donation** to resolve inversions when the lock owner is known (Q59).

### Q7. How do Mach threads, pthreads, `Thread` and GCD relate? `[Senior]`
```
Swift Concurrency (tasks)  ──┐
GCD (queues, work items)   ──┼──▶ run on worker threads managed by libdispatch / the concurrency runtime
OperationQueue             ──┘        (OperationQueue is built on GCD)
Foundation Thread (NSThread) ─────▶ wraps a pthread
POSIX pthreads ────────────────────▶ wraps a Mach thread
Mach threads (XNU kernel) ─────────▶ what the scheduler actually runs on CPU cores
```
- Every abstraction ends up as **kernel threads**. Queues and tasks are **work**, not threads: many queues/tasks are multiplexed onto a small pool of threads.
- You almost never create threads yourself on iOS; you submit work to queues or tasks.

### Q8. Why do some systems use multiple processes instead of threads? `[Senior]`
- **Isolation**: a crash or exploit in one process can't corrupt the others' memory.
- **Security**: each process can have a tighter sandbox (least privilege).
- **Resource control**: the OS can limit or kill one process (memory, CPU).

Apple examples:
- **WKWebView** runs web content in separate **WebContent** and **Networking** processes; if a page crashes, your app gets `webViewWebContentProcessDidTerminate` instead of crashing. (Old `UIWebView` ran in-process.)
- **App extensions** (widgets, keyboards, share extensions) are separate processes from the host app (Q14).
- System **daemons** (e.g. for push, location, media) run as separate processes; apps talk to them over **XPC**.

Cost: inter-process communication is slower and more complex than sharing memory between threads.

### Q9. Can an iOS app create child processes? `[Fundamental]`
- **No.** `fork`, `exec`, `posix_spawn`, `system()` and `Process` (`NSTask`) aren't available/allowed for App Store iOS apps. The sandbox forbids spawning processes.
- On **macOS**, apps can use `Process` and **XPC services** bundled inside the app (helper processes with their own sandbox).
- iOS apps get "extra processes" only through **app extensions**, which the **system** launches and manages.

### Q10. How expensive is a thread, and how many can an app have? `[Senior]`
- Each thread needs kernel data structures and a **stack**: by default **1 MB for the main thread** and **512 KB for secondary threads** on iOS (virtual memory reserved; pages are committed as used).
- Creating a thread takes tens of microseconds (Apple's threading guide cites roughly 90 µs).
- There's no small fixed limit you'll hit in normal code, but hundreds of threads mean memory use, scheduling overhead and contention. GCD historically caps its worker pool at around **64 threads**; when they're all blocked, new work stalls (Q38).
- Swift Concurrency uses roughly **one thread per CPU core** in its cooperative pool, which is why blocking those threads is so harmful (Async/Await Q82).

## 2. The iOS Process Model

### Q11. What is an iOS app process? `[Fundamental]`
- Each app runs as **one sandboxed process**, launched by the system (launchd, coordinated by RunningBoard/SpringBoard) when the user taps the icon or when the system needs it (push, background fetch, location, prewarming).
- The **sandbox** restricts it to its own container directories, entitlements-gated system services, and no access to other apps' data.
- All of the app's scenes/windows (iPad multitasking, multiple windows) run in **the same process**.
- Launch path (detail in OS Fundamentals & Linker): kernel creates the process → **dyld** loads frameworks and runs initializers → `main` → `UIApplicationMain` → app delegate/scene delegate → first frame.

### Q12. What app states exist, and how do they map to the process? `[Fundamental]`
| State | Process exists? | Code runs? | Typical cause |
|---|---|---|---|
| Not running | No | No | Never launched, or terminated |
| Inactive (foreground) | Yes | Yes, but no events | Launching, incoming call overlay, app switcher |
| Active (foreground) | Yes | Yes | User is using the app |
| Background | Yes | Yes, **for a limited time** | Just left foreground, or launched for a background task |
| Suspended | Yes (in memory) | **No** (threads frozen) | After background time ends; system can kill it without notice |

```swift
// Scene-based lifecycle (SwiftUI)
@main
struct MyApp: App {
    @Environment(\.scenePhase) private var scenePhase
    var body: some Scene {
        WindowGroup { ContentView() }
            .onChange(of: scenePhase) { _, phase in
                switch phase {
                case .active: resumeRealtimeConnection()
                case .inactive: break
                case .background: saveDraftsAndScheduleRefresh()   // last reliable moment to save
                @unknown default: break
                }
            }
    }
}
```
**Key point:** when suspended, **no code runs** (no timers, no network callbacks, no sockets). When killed from suspended, **no callback** runs either. So save state when entering the background, not "on termination".

### Q13. When does iOS terminate your process? `[Senior]`
| Reason | What happens | How you notice |
|---|---|---|
| **Memory pressure (jetsam)** | Suspended/background apps are killed first; a foreground app that exceeds its memory limit is killed too | No crash report; a JetsamEvent report; MetricKit `MXAppExitMetric` foreground/background memory exits |
| **Watchdog** | Main thread blocked too long at launch, resume, or in certain callbacks | Crash report with exception code **`0x8badf00d`** ("ate bad food") |
| **Background time expired** | Background task not ended in time | Termination; MetricKit background exit counts |
| **Crash** | Uncaught exception, `EXC_BAD_ACCESS`, Swift runtime trap (force unwrap, out of bounds) | Crash report |
| **CPU / disk write limits** | Excessive resource use in background | `EXC_RESOURCE` reports, MetricKit diagnostics |
| **User** | Swipes app away in the app switcher | Next launch is a cold start; no callback while suspended |
| **System update, low storage cleanup, permission changes** | Process killed | — |

**Interview line:** "My app must be ready to be killed at any moment after it's backgrounded, so state is saved incrementally and restored at launch."

### Q14. Why do app extensions run in separate processes, and what does that imply? `[Senior]`
- Each extension (widget, notification service, share, keyboard, intents) is a **separate executable and process**, launched by the system or the host app, with its **own sandbox and much lower memory limit** (tens of MB; the notification service extension limit is commonly measured around 24 MB).
- Implications:
  - **No shared memory** with the containing app: singletons, in-memory caches and `UserDefaults.standard` are **different instances**.
  - Share data through **App Groups**, the **Keychain access group**, or the network (Q15).
  - Exceeding the memory limit kills the extension (e.g. a notification arrives without the image you tried to attach).
  - Static SDKs are duplicated in each extension binary (Framework Distribution Q53).
  - Extensions can run **at the same time** as the app: concurrent writes to shared files/databases need **cross-process** coordination (file coordination, SQLite locking, or one writer).

### Q15. How do an app and its extensions share data and signal each other? `[Senior]`
| Need | Mechanism |
|---|---|
| Shared files / database | **App Group** container: `FileManager.default.containerURL(forSecurityApplicationGroupIdentifier:)` |
| Small settings | `UserDefaults(suiteName: "group.com.example.app")` |
| Secrets/tokens | Keychain with a shared **access group** |
| Tell the widget to refresh | `WidgetCenter.shared.reloadTimelines(ofKind:)` |
| "Something changed" signal between processes | **Darwin notifications** (`CFNotificationCenterGetDarwinNotifyCenter`): no payload, just a name |
| Coordinated file access | `NSFileCoordinator` / `NSFilePresenter` |
| Shared Core Data / SwiftData store | Store in the App Group container; enable **persistent history tracking** so each process merges the other's changes |

```swift
import Foundation

enum SharedStore {
    static let groupID = "group.com.example.app"

    static var containerURL: URL {
        FileManager.default.containerURL(forSecurityApplicationGroupIdentifier: groupID)!
    }
    static let defaults = UserDefaults(suiteName: groupID)!
}

/// Cross-process "ping": no payload, so the receiver re-reads shared storage
enum DarwinNotification {
    static func post(_ name: String) {
        CFNotificationCenterPostNotification(CFNotificationCenterGetDarwinNotifyCenter(),
                                             CFNotificationName(name as CFString), nil, nil, true)
    }
}

// Notification service extension, after saving a message to the shared store:
DarwinNotification.post("com.example.app.newMessage")
```

### Q16. What is XPC? `[Lead/Expert]`
- **XPC** is Apple's inter-process communication system built on Mach messages: structured messages, connection lifecycle, and automatic launching of the service process on demand.
- On **iOS**, apps don't create their own XPC services, but they use XPC constantly **through system frameworks**: `UNUserNotificationCenter`, `CLLocationManager`, pasteboard, WKWebView's processes, StoreKit all talk to system daemons via XPC.
- On **macOS**, apps bundle **XPC services** (and use `NSXPCConnection` with protocols) to isolate risky work (parsing untrusted files, privileged helpers).
- Interview value: explains why some system calls are slower than they look (they're IPC), why they're async, and why calling them on the main thread can cause hangs.

### Q17. What is app prewarming? `[Senior]`
- Since **iOS 15**, the system may **launch your process ahead of time** (before the user taps the icon), running the early launch stages (dyld, static initializers), then suspending it until the user actually opens the app.
- Consequences:
  - Don't assume "process start = user opened the app". Measure launch time from `UIApplication`/scene activation, not from process start (a prewarmed launch is flagged by the `ActivePrewarm` environment variable).
  - Code in static initializers or `+load` may run long before the UI; don't depend on it for timestamps or session starts.
  - Avoid work at process start that needs the user's data protection to be unlocked: the device may be locked.

### Q18. What does "protected data unavailable" mean for background processes? `[Lead/Expert]`
- With **Data Protection**, files and Keychain items with stricter protection classes are **encrypted while the device is locked**.
- Your process can be launched or resumed **while the device is locked** (push, background refresh, location): reading a `.complete`-protected file or a Keychain item with `kSecAttrAccessibleWhenUnlocked` **fails**.
- Classic bug: background launch reads the database → fails → app "logs out" or wipes data.
- Fix: use `completeUntilFirstUserAuthentication` / `kSecAttrAccessibleAfterFirstUnlock` for data needed in the background; check `UIApplication.shared.isProtectedDataAvailable`; observe `protectedDataDidBecomeAvailableNotification`.

### Q19. How does background execution extend the life of your process? `[Senior]`
| API | Gives you |
|---|---|
| `beginBackgroundTask(withName:expirationHandler:)` | A short extension (~30 s, not guaranteed) to **finish** work started in the foreground |
| `BGAppRefreshTask` | Short, system-scheduled refresh (~30 s) based on usage patterns |
| `BGProcessingTask` | Longer maintenance work, often while charging and idle |
| `BGContinuedProcessingTask` (iOS 26) | User-initiated long work that continues in the background with system UI showing progress |
| Background `URLSession` | Transfers run in a **system daemon**, even if your process is suspended or killed; the app is relaunched to handle completion |
| Background modes (audio, location, VoIP, Bluetooth) | Keeps the process running while that activity is ongoing |
| Silent push | Wakes the app briefly (best effort, throttled) |

```swift
/// Wraps the identifier so the expiration handler and the work can both end it exactly once
@MainActor
final class BackgroundTaskToken {
    private var id: UIBackgroundTaskIdentifier = .invalid

    func begin(name: String) {
        id = UIApplication.shared.beginBackgroundTask(withName: name) { [weak self] in
            self?.end()                 // expiration: end it now, or the process is killed
        }
    }

    func end() {
        guard id != .invalid else { return }
        UIApplication.shared.endBackgroundTask(id)
        id = .invalid
    }
}

@MainActor
func saveBeforeSuspension() {
    let token = BackgroundTaskToken()
    token.begin(name: "SaveDrafts")
    Task {
        await DraftStore.shared.flushToDisk()   // should also stop early if time runs out
        token.end()
    }
}
```
A mutable `var taskID` captured by both closures (the common Stack Overflow version) is a compile error in Swift 6, because the expiration handler is a `@Sendable` closure; the `@MainActor` token class keeps both paths on the main actor.

### Q20. Can parts of one app run in different processes on iOS? `[Senior]`
- Your **own code** runs in your app process, or in your **extensions'** processes.
- Some work you start runs in **system processes** on your behalf: background `URLSession` transfers (nsurlsessiond), WKWebView content, push delivery, Live Activities/widgets rendering (the widget's timeline is generated in your extension, rendered by the system).
- That's why these features use **serializable data** (Codable payloads, files, URLs) rather than closures or object references: data has to cross a process boundary.

## 3. Threads, the Main Thread & Run Loops

### Q21. Why must UI work happen on the main thread? `[Fundamental]`
- UIKit and AppKit aren't thread-safe; they assume a single thread owns the view hierarchy, so they need no locks (faster, simpler).
- The **main thread runs the main run loop**: it receives touch events, runs your event handlers, performs layout, and **commits rendering** (Core Animation transactions) at the end of each loop iteration.
- If you update UI from another thread: crashes, missed updates, corrupted layout, or the Main Thread Checker warning (Q65).
- If you **block** the main thread: no events, no rendering → the app freezes (a **hang**), and the watchdog may kill it.
- In Swift Concurrency, this rule is expressed as **`@MainActor`** (Swift Concurrency file, Section 4).

### Q22. What is a run loop? `[Senior]`
A run loop is an **event-processing loop** attached to a thread: it waits for input, handles it, and sleeps when there's nothing to do (no busy CPU).

```
while app is alive {
    notify observers: about to process timers / sources
    handle input sources (touches, ports, performSelector)
    fire due timers
    run main queue blocks (DispatchQueue.main / main actor jobs)
    notify observers: about to sleep  ← Core Animation commits UI changes here
    sleep until a port message, timer or event arrives
}
```
- **Main thread**: has a run loop that `UIApplicationMain` runs forever.
- **Secondary threads**: have a run loop object, but it **doesn't run** unless you run it. That's why a `Timer` or `NSURLConnection`-era delegate scheduled on a background thread never fires.
- **Modes** filter which sources run (Q23).

### Q23. Why does a `Timer` stop firing while the user scrolls? `[Senior]`
- `Timer.scheduledTimer` schedules in the **`.default`** run loop mode.
- While a scroll view is tracking a finger, the main run loop runs in **`.tracking`** mode (`UITrackingRunLoopMode`), so default-mode timers wait.
- `.common` is a set that includes both.

```swift
let timer = Timer(timeInterval: 1, repeats: true) { _ in
    MainActor.assumeIsolated { updateCountdownLabel() }    // timer fires on the main run loop
}
RunLoop.main.add(timer, forMode: .common)                  // fires during scrolling too
```
Alternatives: `DispatchSourceTimer` (not tied to run loop modes), `CADisplayLink` for per-frame animation work, or an async loop with `Task.sleep` (Async/Await Q95).

### Q24. What are the Quality of Service (QoS) classes? `[Fundamental]`
| QoS | Use for | Example | Scheduling effect |
|---|---|---|---|
| `.userInteractive` | Work on the main thread or needed **this frame** | Animations, event handling | Highest priority, P-cores |
| `.userInitiated` | User is **waiting** for the result | Opening a document, loading a tapped item | High |
| `.default` | Fallback when no QoS is given | — | Between userInitiated and utility |
| `.utility` | Long tasks the user knows about, with progress | Downloads, imports | Balanced for energy |
| `.background` | Work the user doesn't see | Prefetching, backups, indexing, cleanup | Lowest; I/O throttled; may run only on E-cores; may pause in Low Power Mode |
| `.unspecified` | No QoS information (legacy threads) | — | Inferred |

QoS affects **CPU priority, which cores run the thread, I/O priority and timer coalescing** (energy). Task priorities in Swift Concurrency map onto these (`.high` ≈ userInitiated, `.low` ≈ utility, `.background`).

### Q25. How does QoS propagate, and how does the system fix priority inversion? `[Lead/Expert]`
- **Propagation**: `DispatchQueue.async` captures the submitter's QoS (unless the queue or work item says otherwise), so work started from a user tap stays `userInitiated`.
- **Overrides (priority donation)**: when a high-QoS thread **waits** on something whose owner is known, the system temporarily **raises** the owner's QoS:
  - `queue.sync` from a userInitiated thread onto a background serial queue → the queue's current work is boosted.
  - `os_unfair_lock`, `Mutex`, `pthread_mutex` record their owner → the owner is boosted.
  - Awaiting a Swift `Task`'s value or an actor → the runtime escalates priority.
- **No donation** when the waiter can't know who will unblock it: **`DispatchSemaphore`**, `DispatchGroup.wait`, `NSCondition`. A main thread waiting on a semaphore signaled by background-QoS work can wait a long time → **priority inversion** → hang. That's a key reason to avoid semaphores for waiting on async work (Q34, Q59).

### Q26. When would you create a `Thread` directly? `[Senior]`
Almost never in modern iOS code. Legitimate cases:
- A long-lived thread with its **own run loop** for a legacy API that needs one (some streams, older networking or audio APIs).
- Real-time or special-priority work where you need explicit control (audio engines usually provide their own threads).
- Integrating a C library that blocks a thread for its lifetime.

```swift
/// A dedicated thread with a running run loop (for legacy run-loop based APIs)
final class RunLoopThread: Thread, @unchecked Sendable {
    private let ready = DispatchSemaphore(value: 0)
    private(set) var runLoop: RunLoop!      // set once on the thread before `ready` is signaled

    override func main() {
        runLoop = RunLoop.current
        // A run loop with no sources exits immediately: add a port to keep it alive
        runLoop.add(NSMachPort(), forMode: .default)
        ready.signal()
        while !isCancelled { runLoop.run(mode: .default, before: .distantFuture) }
    }

    func waitUntilReady() { ready.wait() }    // fine here: called once at setup, not on the main thread
}

let thread = RunLoopThread()
thread.name = "com.example.legacy-stream"
thread.qualityOfService = .userInitiated
thread.start()
```
For everything else: GCD queues, OperationQueue or Swift Concurrency.

### Q27. What is thread-local storage, and why is it risky in modern code? `[Senior]`
- Values stored per thread (`Thread.current.threadDictionary`, `pthread_getspecific`).
- Works when code always runs on the same thread. With **queues**, consecutive blocks may run on **different** threads; with **Swift Concurrency**, a task can resume on a different thread after every `await`.
- Use **task-local values** (`@TaskLocal`) for context in async code (Async/Await Q91), or pass context explicitly.

### Q28. What counts as a hang, and how does the system react? `[Senior]`
- A **hang** is when the main thread can't handle events for a noticeable time. Apple's tools report hangs from about **250 ms**; anything above ~100 ms already feels sluggish.
- Detection: Xcode Organizer **Hangs** report (from users' devices), Instruments **Hangs** and **Time Profiler**, on-device hang detection in Developer settings, MetricKit `MXHangDiagnostic`.
- The **watchdog** kills apps that block the main thread for too long during launch, resume or certain system callbacks (`0x8badf00d`).
- Common causes: synchronous I/O or networking on main, `DispatchQueue.main.sync` / semaphores waiting for other work, lock contention, heavy layout or image decoding, large JSON parsing on main, Core Data fetches on the main context.

## 4. Grand Central Dispatch

### Q29. What is Grand Central Dispatch? `[Fundamental]`
- GCD (libdispatch) lets you submit **work items** (closures) to **queues**; the system runs them on a **pool of threads** it manages.
- You think in **queues and ordering**, not threads: the system decides how many threads to use based on cores, load and QoS.
- Still widely used in UIKit-era code, C/Objective-C APIs and as the engine underneath `OperationQueue`. New Swift code usually uses Swift Concurrency, but you must read and fix GCD code in interviews and real codebases.

### Q30. What kinds of queues exist? `[Fundamental]`
| Queue | Type | Use |
|---|---|---|
| `DispatchQueue.main` | Serial, runs on the main thread | UI updates |
| `DispatchQueue.global(qos:)` | Concurrent, shared system queues | Independent background work (don't use barriers here) |
| `DispatchQueue(label:)` | **Serial** private queue | Protect state; run work in order |
| `DispatchQueue(label:, attributes: .concurrent)` | Concurrent private queue | Reader-writer patterns with barriers |

- **Serial**: one work item at a time, in FIFO order (not necessarily on the same thread each time).
- **Concurrent**: items **start** in FIFO order but may run at the same time and finish in any order.

### Q31. What is the difference between `sync` and `async`? `[Fundamental]`
- `async`: enqueue the work and **return immediately**.
- `sync`: enqueue the work and **block the current thread until it finishes**.
- Both are about the **caller**, not the queue: a serial queue is still serial either way.

```swift
let queue = DispatchQueue(label: "com.example.serial")

print("1")
queue.async { print("2") }
print("3")
queue.sync { print("4") }
print("5")
```
**Output:** `1`, then `3` and `2` in either order (usually `1 3 2` because the caller continues immediately), then `4`, then `5`. `2` always prints before `4`: the queue is serial, and `sync` waits behind the earlier `async` block.

### Q32. Why does `sync` onto the current serial queue deadlock? `[Fundamental]`
```swift
let queue = DispatchQueue(label: "com.example.serial")
queue.async {
    queue.sync {            // ❌ deadlock: waits for itself
        print("never runs")
    }
}

// The classic version:
DispatchQueue.main.sync { updateUI() }   // ❌ called on the main thread → crash/deadlock
```
- `sync` waits for the block to finish; the block can't start until the **current** block on that serial queue finishes; the current block is the one waiting. Circular wait.
- `DispatchQueue.main.sync` from the main thread crashes immediately (libdispatch detects it: "dispatch_sync called on queue already owned by current thread").
- Less obvious variants: queue A `sync` to B while B `sync` to A (lock ordering, Q58); a nested call path that re-enters the same queue through a callback.

### Q33. How do you build a thread-safe reader-writer cache with GCD? `[Senior]`
Many concurrent readers, exclusive writers: a **concurrent queue + barrier**.

```swift
final class ThreadSafeCache<Key: Hashable & Sendable, Value: Sendable>: @unchecked Sendable {
    private var storage: [Key: Value] = [:]           // only touched on `queue`
    private let queue = DispatchQueue(label: "com.example.cache", attributes: .concurrent)

    func value(for key: Key) -> Value? {
        queue.sync { storage[key] }                    // readers run concurrently
    }

    func set(_ value: Value, for key: Key) {
        queue.async(flags: .barrier) {                 // waits for running readers, runs alone
            self.storage[key] = value
        }
    }
}
```
- A **barrier** block waits until all earlier blocks on that queue finish, runs **alone**, then lets later blocks proceed.
- Barriers only work on **your own concurrent queues**; on a global queue they behave like plain `async`.
- Is it worth it? For small, fast critical sections, a simple lock (`Mutex`, `OSAllocatedUnfairLock`) is usually faster and simpler (Q50). Reader-writer only pays off when reads are frequent **and** slow.

### Q34. What is `DispatchSemaphore` for, and how is it misused? `[Senior]`
A counter: `wait()` decrements (blocks if it would go below zero); `signal()` increments.

**Legitimate use: limiting concurrency** (on background threads):
```swift
let limit = DispatchSemaphore(value: 3)                 // at most 3 at once
let workQueue = DispatchQueue(label: "com.example.uploads", attributes: .concurrent)

DispatchQueue.global(qos: .utility).async {             // the waiting happens off the main thread
    for file in files {
        limit.wait()
        workQueue.async {
            defer { limit.signal() }
            upload(file)
        }
    }
}
```
**Misuse: making async code synchronous**
```swift
// ❌ Blocks the caller; deadlocks if the completion needs the blocked thread (e.g. main);
//    no priority donation (Q25); never do this in Swift Concurrency (Async/Await Q82)
func fetchUserSync() -> User? {
    let semaphore = DispatchSemaphore(value: 0)
    var result: User?
    api.fetchUser { user in result = user; semaphore.signal() }
    semaphore.wait()
    return result
}
```
Modern alternatives: `async` functions; task groups or `OperationQueue.maxConcurrentOperationCount` to limit concurrency.

### Q35. How does `DispatchGroup` work? `[Fundamental]`
Tracks a set of work items and tells you when all have finished.

```swift
let group = DispatchGroup()
let results = OSAllocatedUnfairLock(initialState: [String: Data]())   // thread-safe collection

for id in ["a", "b", "c"] {
    group.enter()                                       // +1 before starting async work
    api.fetch(id) { data in
        if let data { results.withLock { $0[id] = data } }
        group.leave()                                   // -1 exactly once per enter, on every path
    }
}

group.notify(queue: .main) {                            // runs when the count reaches zero; doesn't block
    let all = results.withLock { $0 }
    render(all)
}
```
- `enter`/`leave` must balance: an extra `leave` crashes; a missing one means `notify` never fires.
- `group.wait()` blocks (same caveats as semaphores).
- For work submitted directly: `queue.async(group: group) { ... }` enters/leaves automatically (only for **synchronous** work inside the block).
- Swift Concurrency equivalent: `async let` / task groups (Async/Await Section 4–5).

### Q36. How do you cancel GCD work? `[Senior]`
- Blocks submitted with `async` can't be cancelled.
- `DispatchWorkItem` supports `cancel()`: a **not-yet-started** item won't run; a **running** item keeps running unless it checks `isCancelled` itself.

```swift
/// Debounced search: only the last keystroke within 300 ms triggers a request
@MainActor
final class SearchDebouncer {
    private var pending: DispatchWorkItem?

    func queryChanged(_ query: String) {
        pending?.cancel()
        let item = DispatchWorkItem { [weak self] in
            MainActor.assumeIsolated { self?.performSearch(query) }   // scheduled on the main queue below
        }
        pending = item
        DispatchQueue.main.asyncAfter(deadline: .now() + .milliseconds(300), execute: item)
    }

    private func performSearch(_ query: String) { /* start request */ }
}
```
`OperationQueue` (Section 5) and Swift tasks have richer cancellation models.

### Q37. `Timer`, `asyncAfter` or `DispatchSourceTimer`? `[Senior]`
| | `Timer` | `asyncAfter` | `DispatchSourceTimer` |
|---|---|---|---|
| Needs a run loop | Yes (main or a running one) | No | No |
| Affected by run loop modes (scrolling) | Yes (Q23) | No | No |
| Repeating | Yes | No (one-shot) | Yes |
| Cancellable | `invalidate()` | Only via `DispatchWorkItem` | `cancel()` |
| Leeway (energy) | `tolerance` | — | `leeway` |

```swift
final class Heartbeat: @unchecked Sendable {
    private let queue = DispatchQueue(label: "com.example.heartbeat")
    private var timer: DispatchSourceTimer?                 // only touched on `queue`

    func start(every interval: DispatchTimeInterval, _ tick: @escaping @Sendable () -> Void) {
        queue.async {
            let timer = DispatchSource.makeTimerSource(queue: self.queue)
            timer.schedule(deadline: .now() + interval, repeating: interval, leeway: .milliseconds(100))
            timer.setEventHandler(handler: tick)
            timer.resume()                                  // sources start suspended
            self.timer = timer
        }
    }

    func stop() {
        queue.async {
            self.timer?.cancel()
            self.timer = nil
        }
    }
}
```
Gotchas: releasing a `DispatchSourceTimer` without cancelling it, or cancelling a **suspended** source, crashes; keep a strong reference or the timer never fires.

### Q38. What is thread explosion in GCD? `[Lead/Expert]`
- When a block on a concurrent queue **blocks** (sync I/O, a lock, a semaphore), GCD assumes the CPU is free and **creates another thread** to keep cores busy.
- Submitting hundreds of blocking items → hundreds of threads → memory for stacks, heavy context switching, lock contention. Once the pool limit (historically ~64 worker threads) is reached, **new work can't start** at all, which can deadlock if the blocked items wait for work that can't get a thread.

```swift
// ❌ 1,000 blocks that each block a thread → thread explosion
for url in urls {
    DispatchQueue.global().async {
        let data = try? Data(contentsOf: url)         // synchronous network/disk I/O
        process(data)
    }
}
```
Fixes:
- Use **asynchronous APIs** (`URLSession`) instead of blocking ones.
- **Limit concurrency** (semaphore on a background thread, `OperationQueue.maxConcurrentOperationCount`, task groups with a fixed width).
- Use **fewer, well-defined queues** (one per subsystem) with target queues (Q39).
- Swift Concurrency avoids explosion by design (one thread per core, suspension instead of blocking) **as long as you don't block** (Async/Await Q130).

### Q39. What are target queues? `[Lead/Expert]`
- Every queue **targets** another queue; work ultimately executes on the target's threads. By default, private queues target a global queue.
- Making several serial queues target **one** serial queue gives a hierarchy: they keep their own identities and labels, but **never run at the same time** (all serialized through the target).
- Apple's guidance (WWDC 2017 "Modernizing GCD Usage"): use **a small number of serial queues per subsystem**, arranged in a hierarchy, instead of creating many independent queues.

```swift
let databaseQueue = DispatchQueue(label: "com.example.db")                       // subsystem root
let readsQueue  = DispatchQueue(label: "com.example.db.reads",  target: databaseQueue)
let writesQueue = DispatchQueue(label: "com.example.db.writes", target: databaseQueue)
// reads and writes never overlap, and the system uses at most one thread for the whole subsystem
```

### Q40. How do you run a CPU-heavy loop in parallel with GCD? `[Senior]`
`DispatchQueue.concurrentPerform` splits iterations across all cores and **returns when every iteration has finished** (it blocks the caller, so call it off the main thread).

```swift
func grayscale(_ pixels: [RGBA]) -> [UInt8] {
    var output = [UInt8](repeating: 0, count: pixels.count)
    output.withUnsafeMutableBufferPointer { out in
        let chunkSize = 4_096                                    // big chunks: per-iteration overhead stays small
        let chunks = (pixels.count + chunkSize - 1) / chunkSize
        DispatchQueue.concurrentPerform(iterations: chunks) { chunk in
            let start = chunk * chunkSize
            let end = min(start + chunkSize, pixels.count)
            for i in start..<end {                               // each iteration writes only its own range
                let p = pixels[i]
                out[i] = UInt8((Int(p.r) * 30 + Int(p.g) * 59 + Int(p.b) * 11) / 100)
            }
        }
    }
    return output
}
```
- Iterations must be **independent** (no shared mutable state, or each writes only its own slots).
- Choose a chunk size so each iteration does meaningful work; one iteration per pixel would be dominated by overhead.
- The compiler can't prove the ranges don't overlap; that's your responsibility. If a stricter SDK rejects capturing the buffer pointer (it isn't `Sendable`), wrap it in a tiny `@unchecked Sendable` struct, which documents that promise.
- Swift Concurrency alternative: a task group with one child task per chunk (Async/Await Q32).

### Q41. How do you assert which queue or thread code is running on? `[Senior]`
```swift
let stateQueue = DispatchQueue(label: "com.example.state")

func mutateState() {
    dispatchPrecondition(condition: .onQueue(stateQueue))     // traps in debug and release if wrong
    // ...
}

func updateUI() {
    dispatchPrecondition(condition: .onQueue(.main))
}
```
- Prefer `dispatchPrecondition` over checking `Thread.isMainThread` for queues: a serial queue can run on any thread, so thread checks don't prove you're on the queue.
- In Swift Concurrency code, isolation (`@MainActor`, actors) is checked by the **compiler** instead, and `MainActor.assumeIsolated` / `MainActor.preconditionIsolated()` check at runtime when bridging from callbacks.

### Q42. How do GCD patterns map to Swift Concurrency? `[Senior]`
| GCD | Swift Concurrency |
|---|---|
| `DispatchQueue.main.async { }` | `@MainActor` function, `await MainActor.run { }`, or `Task { @MainActor in }` |
| Serial queue protecting state | `actor` (or `Mutex` for tiny synchronous sections) |
| `DispatchQueue.global().async` | `Task { }` / `@concurrent` function (Swift 6.2) |
| `DispatchGroup` + `notify` | `async let` / `withTaskGroup` |
| `DispatchSemaphore` limiting width | Task group that adds a new child as each one finishes |
| `DispatchWorkItem.cancel()` | `Task.cancel()` + cooperative checks |
| `asyncAfter` | `try await Task.sleep(for:)` |
| `concurrentPerform` | Task group over chunks |
| Barrier reader-writer | Actor (readers serialize too, which is usually fine) |
| `queue.sync` to read state | `await actor.property` (suspends, doesn't block) |

More mappings: Async/Await Q124.

### Q43. Should new code still use GCD? `[Lead/Expert]`
- **Prefer Swift Concurrency** for new Swift code: compile-time data-race safety, cancellation, structured lifetimes, no thread explosion.
- **GCD is still right** for:
  - APIs that require a queue (`DispatchSource`, `AVCaptureVideoDataOutput.setSampleBufferDelegate(_:queue:)`, Network.framework `NWConnection.start(queue:)`, Core Bluetooth).
  - C/Objective-C interop and existing code that works.
  - Synchronous, non-suspending critical sections (though `Mutex`/locks are often simpler).
  - Custom actor executors backed by a serial queue (Swift Concurrency Section 13).
- Migrate gradually: wrap queue-based components behind `async` APIs; don't mix `queue.sync` and actors on the same state.

## 5. OperationQueue

### Q44. What does `OperationQueue` add on top of GCD? `[Fundamental]`
| Feature | GCD | OperationQueue |
|---|---|---|
| Dependencies between tasks | Manual (groups, nesting) | `op2.addDependency(op1)`, even across queues |
| Cancellation | `DispatchWorkItem` only before start | `cancel()` / `cancelAllOperations()`; operations check `isCancelled` |
| Max concurrency | Semaphores, target queues | `maxConcurrentOperationCount` |
| Observing state | No | KVO on `isExecuting`, `isFinished`, `operationCount`; `progress` |
| Pause/resume | `suspend()` (risky) | `isSuspended` (stops starting new operations) |
| Reusable, subclassable units | Closures | `Operation` subclasses |
| Overhead | Lower | Higher (objects, KVO) |

### Q45. How do dependencies and concurrency limits work? `[Senior]`
```swift
let queue = OperationQueue()
queue.name = "com.example.export"
queue.maxConcurrentOperationCount = 2           // 1 = serial
queue.qualityOfService = .utility

let download = BlockOperation { downloadAssets() }
let resize   = BlockOperation { resizeImages() }
let upload   = BlockOperation { uploadResults() }

resize.addDependency(download)
upload.addDependency(resize)
// Dependencies can point at operations on OTHER queues (e.g. a final step on OperationQueue.main)

queue.addOperations([download, resize, upload], waitUntilFinished: false)
```
- An operation becomes ready only when **all dependencies have finished** (finished includes cancelled: a dependent still runs unless it checks whether its dependencies were cancelled).
- Dependency cycles = operations that never run.

### Q46. How do you write an asynchronous `Operation` subclass? `[Lead/Expert]`
By default an operation is "finished" when `main()` returns. For async work (a network request), you must manage `isExecuting`/`isFinished` yourself, **with KVO notifications**, or the queue never learns it finished.

```swift
class AsyncOperation: Operation, @unchecked Sendable {
    private enum State { case ready, executing, finished }
    private let lock = NSLock()
    private var _state = State.ready                       // guarded by `lock`

    private var state: State {
        get { lock.withLock { _state } }
        set {
            willChangeValue(forKey: "isExecuting"); willChangeValue(forKey: "isFinished")
            lock.withLock { _state = newValue }
            didChangeValue(forKey: "isFinished"); didChangeValue(forKey: "isExecuting")
        }
    }

    override var isAsynchronous: Bool { true }
    override var isExecuting: Bool { state == .executing }
    override var isFinished: Bool { state == .finished }

    override func start() {
        if isCancelled { state = .finished; return }      // must still finish when cancelled before start
        state = .executing
        execute()
    }

    /// Subclasses do their async work here and call `finish()` exactly once
    func execute() { fatalError("Subclasses must override execute()") }

    final func finish() { state = .finished }
}

final class DownloadOperation: AsyncOperation, @unchecked Sendable {
    private let url: URL
    private var task: URLSessionDataTask?
    private(set) var result: Result<Data, Error>?

    init(url: URL) { self.url = url }

    override func execute() {
        task = URLSession.shared.dataTask(with: url) { [weak self] data, _, error in
            guard let self else { return }
            self.result = data.map { .success($0) } ?? .failure(error ?? URLError(.badServerResponse))
            self.finish()
        }
        task?.resume()
    }

    override func cancel() {
        super.cancel()
        task?.cancel()            // the completion handler still runs (with an error) and calls finish()
    }
}
```
Common bugs: forgetting KVO notifications (queue stalls), never calling `finish()` on some path (queue stalls forever), calling `finish()` twice, overriding `main()` instead of `start()` for async work.

The `fatalError` in the base class flags a programming error (a subclass that forgot to override); it's not reachable in correct code.

### Q47. How does cancellation work for operations? `[Senior]`
- `cancel()` only sets `isCancelled = true`; the operation must **check** it (`main()` or long loops) and stop.
- An operation cancelled **before** it starts is still started by the queue, so `start()` must notice and finish immediately (as above).
- `cancelAllOperations()` cancels queued and running operations; dependents of a cancelled operation are still run unless they check.

```swift
final class ThumbnailOperation: Operation, @unchecked Sendable {
    let images: [URL]
    init(images: [URL]) { self.images = images }

    override func main() {
        for url in images {
            if isCancelled { return }            // cooperative cancellation between units of work
            makeThumbnail(for: url)
        }
    }
}
```

### Q48. When would you choose `OperationQueue` today? `[Senior]`
- Existing codebases with complex **dependency graphs** of work (import pipelines, sync engines) that work well.
- When you need **KVO-observable** progress/state for UI (older UIKit code).
- When you must limit concurrency for **synchronous**, blocking work with a simple setting.
- For new Swift code, structured concurrency (task groups, `async let`) usually expresses the same graphs more simply, with automatic cancellation propagation.

## 6. Synchronization Primitives

> Swift Concurrency covers `Mutex`, pre-iOS 18 locks, atomics and "lock vs actor" in its Section 12 (Q100–Q106). This section adds the classic OS-level primitives interviewers still ask about.

### Q49. Why isn't `count += 1` thread-safe? `[Fundamental]`
`count += 1` is three steps: **read** `count`, **add** 1, **write** it back. Two threads can interleave:

```
Thread A: read 5 ─────────── add → 6 ── write 6
Thread B:        read 5 ── add → 6 ────────────── write 6      → final value 6, not 7 (lost update)
```
- A **read-modify-write** or **check-then-act** sequence (`if cache[key] == nil { cache[key] = load() }`) must happen **atomically**: inside one lock, one queue block, one actor method without an `await` in the middle, or one atomic operation.
- Making each individual access thread-safe isn't enough: two thread-safe calls in a row (`if !set.contains(x) { set.insert(x) }`) are still a race.
- Data race vs race condition: Swift Concurrency Q3.

### Q50. Compare the synchronization primitives available on Apple platforms. `[Senior]`
| Primitive | Kind | Notes |
|---|---|---|
| Serial `DispatchQueue` | Queue | Simple; `sync` to read, `async` to write; per-call overhead higher than a lock |
| Concurrent queue + barrier | Reader-writer | Pays off only for slow, frequent reads (Q33) |
| `NSLock` | Mutex | Objective-C object; `withLock` in Swift; not recursive |
| `NSRecursiveLock` | Recursive mutex | Same thread may lock again; usually a design smell (Q54) |
| `os_unfair_lock` | Low-level mutex | Fast; owner-aware (priority donation); must have a **stable address** (Q51) |
| `OSAllocatedUnfairLock<State>` (iOS 16) | Mutex + protected state | Safe Swift wrapper around `os_unfair_lock`; `Sendable` |
| `Mutex<State>` (iOS 18, Synchronization) | Mutex + protected state | Preferred in Swift 6; non-copyable; `Sendable` |
| `pthread_rwlock_t` | Reader-writer lock | Many readers or one writer (Q52) |
| `NSCondition` / `pthread_cond_t` | Condition variable | Wait until a condition holds (Q53) |
| `DispatchSemaphore` | Counting semaphore | Limit concurrency; **no** priority donation (Q25, Q34) |
| `Atomic<T>` (iOS 18, Synchronization) | Lock-free | Counters, flags; single-value operations only (Swift Concurrency Q103) |
| `actor` | Isolation | Async access; no blocking; reentrant at `await` |

**Default choice in Swift 6:** an actor (or `@MainActor`) for async code; `Mutex`/`OSAllocatedUnfairLock` for tiny synchronous critical sections.

### Q51. Why is using `os_unfair_lock` directly from Swift dangerous? `[Lead/Expert]`
- `os_unfair_lock` is a C struct that must live at a **fixed memory address** while in use.
- Swift may **move or copy** stored properties, and `&lockProperty` passes the address of a **temporary** copy. Two threads can end up locking different copies, so the lock silently protects nothing.

```swift
// ❌ Unsafe: `&lock` may point to a temporary
final class Counter: @unchecked Sendable {
    private var lock = os_unfair_lock()
    private var value = 0
    func increment() {
        os_unfair_lock_lock(&lock); value += 1; os_unfair_lock_unlock(&lock)
    }
}

// ✅ iOS 16+: the lock is heap-allocated with a stable address, and it owns the state
final class SafeCounter: Sendable {
    private let value = OSAllocatedUnfairLock(initialState: 0)
    func increment() { value.withLock { $0 += 1 } }
    var current: Int { value.withLock { $0 } }
}
```
Other rules: unlock on the **same thread** that locked (it's "unfair" and owner-tracked); never hold it across an `await` or any blocking call.

### Q52. When would you use a reader-writer lock? `[Senior]`
- Many threads read often, writes are rare, and reads take long enough that letting them run in parallel matters (e.g. a large in-memory index).
- For short reads, a plain mutex is faster: reader-writer locks have more overhead and can **starve writers** under constant reads.

```swift
final class ReadWriteLock: @unchecked Sendable {
    private let rwlock: UnsafeMutablePointer<pthread_rwlock_t> = {
        let pointer = UnsafeMutablePointer<pthread_rwlock_t>.allocate(capacity: 1)   // stable address
        pthread_rwlock_init(pointer, nil)
        return pointer
    }()

    deinit {
        pthread_rwlock_destroy(rwlock)
        rwlock.deallocate()
    }

    func read<T>(_ body: () throws -> T) rethrows -> T {
        pthread_rwlock_rdlock(rwlock); defer { pthread_rwlock_unlock(rwlock) }
        return try body()
    }

    func write<T>(_ body: () throws -> T) rethrows -> T {
        pthread_rwlock_wrlock(rwlock); defer { pthread_rwlock_unlock(rwlock) }
        return try body()
    }
}
```

### Q53. What is a condition variable? Implement a blocking producer-consumer queue. `[Lead/Expert]`
A condition variable lets a thread **sleep until a condition becomes true**, releasing the lock while it waits, then reacquiring it when woken.

```swift
/// Bounded blocking queue for dedicated worker THREADS (not for Swift tasks: never block the cooperative pool)
final class BlockingQueue<Element: Sendable>: @unchecked Sendable {
    private var items: [Element] = []
    private let capacity: Int
    private let condition = NSCondition()

    init(capacity: Int) { self.capacity = capacity }

    func put(_ item: Element) {
        condition.lock(); defer { condition.unlock() }
        while items.count >= capacity { condition.wait() }      // `while`, not `if`: spurious wakeups happen
        items.append(item)
        condition.broadcast()                                   // wake consumers waiting for items
    }

    func take() -> Element {
        condition.lock(); defer { condition.unlock() }
        while items.isEmpty { condition.wait() }
        let item = items.removeFirst()
        condition.broadcast()                                   // wake producers waiting for space
        return item
    }
}
```
- Always re-check the condition in a **`while`** loop (spurious wakeups, or another thread took the item first).
- In async code, the equivalent is an `AsyncStream` (with a buffering policy) or an actor-based queue; consumers **suspend** instead of blocking.

### Q54. Why are recursive locks considered a design smell? `[Senior]`
- `NSRecursiveLock` lets the **same thread** lock again without deadlocking (a counter tracks depth).
- They hide unclear ownership: code that re-enters a locked section is usually calling out (callbacks, delegates) while holding a lock, or public methods calling other public methods that also lock.
- Invariants may be broken at the moment of re-entry (the outer call is half-way through an update).
- Better: split into public methods that take the lock and **private** methods that assume it's held (`_unlocked` suffix), and don't call external code while locked (Q62).

### Q55. Which common Swift and Foundation things are thread-safe? `[Senior]`
| Thing | Thread-safe? |
|---|---|
| `static let` and global `let` initialization | **Yes**: lazily initialized exactly once (uses `swift_once`, like `dispatch_once`) |
| `lazy var` | **No**: two threads can both run the initializer |
| `Array`, `Dictionary`, `Set`, `String` | **No** for concurrent mutation (value semantics protect **copies**, not one shared variable) |
| Reading an immutable `let` value shared across threads | Yes |
| `NSCache` | Yes |
| `UserDefaults` | Yes |
| `DateFormatter` / `ISO8601DateFormatter` | Yes for use since iOS 7 (avoid mutating configuration while others use it); creation is expensive, so cache them |
| `URLSession` | Yes |
| `NotificationCenter` | Yes to post/observe; **delivery happens on the posting thread** (Q64) |
| UIKit / AppKit views | **No**: main thread only (a few exceptions like `UIImage` creation, `UIGraphicsImageRenderer`) |
| Core Data `NSManagedObjectContext` / objects | **No**: confined to the context's queue (Q61) |
| Objective-C `atomic` properties | Single get/set is atomic; **compound operations aren't** (Q57) |

### Q56. What happened to `OSSpinLock`, and when are spin locks appropriate? `[Lead/Expert]`
- A **spin lock** busy-waits (loops checking the lock) instead of sleeping. Good only when critical sections are extremely short **and** all threads have equal priority.
- With QoS on iOS, a low-priority thread could hold the spin lock while a high-priority thread spins forever, **never letting the owner run** (priority inversion that turns into a livelock). `OSSpinLock` was deprecated in iOS 10 for this reason.
- Replacement: `os_unfair_lock` (sleeps in the kernel and donates priority to the owner), now usually through `OSAllocatedUnfairLock` or `Mutex`.

### Q57. Are Objective-C `atomic` properties enough for thread safety? `[Senior]`
- `@property (atomic)` (the default in Objective-C) makes each individual **getter or setter** atomic: you never read a half-written pointer.
- It doesn't make **sequences** safe: `self.count = self.count + 1` is still a lost-update race; `atomic` NSMutableArray property doesn't make the array's own methods thread-safe.
- Swift has no `atomic` keyword for properties. Use a lock/`Mutex`, an actor, or `Atomic<T>` for single values.

## 7. Classic Concurrency Bugs

### Q58. What causes deadlocks, and how do you prevent them? `[Senior]`
A deadlock needs all four **Coffman conditions**:
1. **Mutual exclusion**: resources can't be shared.
2. **Hold and wait**: a thread holds one resource while waiting for another.
3. **No preemption**: resources can't be taken away.
4. **Circular wait**: A waits for B's resource while B waits for A's.

```swift
// ❌ Lock-ordering deadlock: two threads take the same locks in opposite order
func transfer(from a: Account, to b: Account, amount: Int) {
    a.lock.lock(); defer { a.lock.unlock() }
    b.lock.lock(); defer { b.lock.unlock() }          // thread 1: A→B, thread 2: B→A → circular wait
    a.balance -= amount; b.balance += amount
}

// ✅ Global lock ordering breaks circular wait
func safeTransfer(from a: Account, to b: Account, amount: Int) {
    let (first, second) = a.id < b.id ? (a, b) : (b, a)
    first.lock.lock(); defer { first.lock.unlock() }
    second.lock.lock(); defer { second.lock.unlock() }
    a.balance -= amount; b.balance += amount
}
```
Apple-platform deadlock patterns:
- `DispatchQueue.main.sync` from the main thread, or `sync` onto the current serial queue (Q32).
- Main thread waits on a semaphore/group for work that needs the main thread to complete (e.g. a completion handler dispatched to main).
- Calling a delegate or completion handler **while holding a lock**, and that callback calls back into the locked object (Q62).
- Two serial queues `sync`-ing into each other.

Prevention: lock ordering, never block the main thread, don't hold locks across callbacks or `await`, use `async` instead of `sync`, prefer actors (which can't deadlock on each other because they suspend, though they can still wait forever on logic bugs).

### Q59. What is priority inversion? `[Lead/Expert]`
A **high-priority** thread waits for a resource held by a **low-priority** thread, while **medium-priority** threads keep the CPU busy, so the low-priority owner rarely runs and the high-priority thread effectively runs at low priority.

```
Main thread (userInteractive) ──waits on lock/semaphore─────────────────────▶ (hang!)
Background thread (background) holds lock ── preempted by ──┐
Utility threads (utility) ──── keep CPUs busy ─────────────┘
```
- Famous case: the Mars Pathfinder resets (1997).
- On Apple platforms:
  - **Owner-aware primitives** (`os_unfair_lock`, `Mutex`, `pthread_mutex`, `dispatch_sync` onto a serial queue, awaiting tasks/actors) **boost the owner's priority** automatically.
  - **Semaphores, groups, condition variables** can't (no single known owner) → inversions → main-thread hangs. Xcode's Thread Performance Checker warns about some of these at runtime ("Hang Risk: thread running at User-interactive QoS is waiting on a lower QoS thread").
- Fixes: don't block high-priority threads at all; if you must wait, use owner-aware primitives; give shared serial queues an appropriate QoS; avoid doing user-visible work on `background` QoS.

### Q60. What are livelock and starvation? `[Senior]`
- **Livelock**: threads aren't blocked, they keep **responding to each other** without progress (two people stepping aside in a corridor in sync). Example: two threads that each `tryLock` both locks, back off, and retry in lockstep. Fix: randomized backoff, a single coordinator, or lock ordering.
- **Starvation**: a thread **never gets** the resource or CPU because others always win: writers starved by constant readers in a reader-writer lock; background-QoS work never running under constant high-priority load; a spin lock owner starved by spinning waiters (Q56).

### Q61. What is thread confinement, and which Apple frameworks require it? `[Senior]`
**Thread confinement**: an object is only ever used from one thread or queue, so it needs no locks.
- **UIKit/AppKit**: confined to the main thread.
- **Core Data**: each `NSManagedObjectContext` belongs to its queue; access it and its objects only inside `perform`/`performAndWait` (or on the main thread for a main-queue context). Pass **`NSManagedObjectID`**s between contexts, never objects.
- **SwiftData**: `ModelContext` and models are confined to their actor; use `@ModelActor` for background work and pass `PersistentIdentifier`s.
- **Realm**: objects are thread-confined; use thread-safe references or frozen objects.

```swift
// Core Data: background import, then the UI refetches by ID
container.performBackgroundTask { context in
    let item = Item(context: context)
    item.title = "Imported"
    try? context.save()
    let id = item.objectID                                  // NSManagedObjectID is safe to pass between threads
    Task { @MainActor in
        let viewContext = PersistenceController.shared.container.viewContext
        show(viewContext.object(with: id))                  // re-fetch on the main context
    }
}
```
Enable `-com.apple.CoreData.ConcurrencyDebug 1` in the scheme to trap any cross-queue access.

### Q62. Why is calling out to unknown code while holding a lock dangerous? `[Lead/Expert]`
- The callback (delegate, closure, notification observer, KVO) can:
  - Call back into your object → **deadlock** with a non-recursive lock, or broken invariants with a recursive one.
  - Take **other locks** → lock-ordering deadlocks you can't see.
  - Run slowly → everyone else waits on your lock.

```swift
final class Downloader: @unchecked Sendable {
    private let lock = NSLock()
    private var observers: [@Sendable (Progress) -> Void] = []

    // ❌ Callbacks run while the lock is held
    func notifyBad(_ progress: Progress) {
        lock.withLock { observers.forEach { $0(progress) } }
    }

    // ✅ Copy what you need under the lock; call out after releasing it
    func notify(_ progress: Progress) {
        let snapshot = lock.withLock { observers }
        snapshot.forEach { $0(progress) }
    }
}
```
The same rule applies to actors in spirit: state may change across an `await` (actor reentrancy, Swift Concurrency Section 3).

### Q63. Why can code with a data race "work fine" in testing? `[Lead/Expert]`
- Races depend on **timing**: the bad interleaving may need a specific core count, load, or thermal state.
- The **compiler and CPU reorder** memory operations; without synchronization, another thread may see writes late, in a different order, or never (a flag in a loop can be hoisted out of the loop and never re-read).
- ARM (all iPhones) has a **weaker memory model** than x86: code that seemed fine on an Intel simulator can fail on devices.
- Locks, queues, actors and atomics include **memory barriers** that guarantee visibility and ordering; "it seems to work" without them isn't safety.
- Tools: Thread Sanitizer (Q66), Swift 6 strict concurrency (compile time).

### Q64. On which thread are notifications, KVO and delegate callbacks delivered? `[Senior]`
| Mechanism | Delivered on |
|---|---|
| `NotificationCenter.post` | The **posting** thread, synchronously (unless the observer was added with a `queue:`) |
| KVO | The thread that **changed** the property |
| `URLSession` delegate/completion | The session's `delegateQueue` (a background serial `OperationQueue` by default) |
| `CLLocationManager` delegate | The thread/run loop the manager was **created** on (create it on main) |
| `NWConnection`/`NWPathMonitor` handlers | The queue passed to `start(queue:)` |
| AVFoundation capture outputs | The queue you set (`setSampleBufferDelegate(_:queue:)`) |
| Combine `sink` | Wherever the upstream emits, unless you `receive(on:)` |
| Async notifications (`NotificationCenter.default.notifications(named:)`) | Your task's isolation (e.g. main actor in a `@MainActor` task) |

**Classic bug:** a background thread posts a notification, and the observer updates UI directly → Main Thread Checker warning or crash. Document which thread your own callbacks use.

## 8. Debugging & Tools

### Q65. What does the Main Thread Checker do? `[Fundamental]`
- A runtime check (on by default in Debug runs) that detects **UIKit, AppKit and other main-thread-only APIs called from a background thread**, and pauses with a purple runtime issue showing the stack.
- Small overhead; keep it enabled in development and in UI test runs.
- It doesn't catch data races in your own code; that's Thread Sanitizer.

### Q66. What does Thread Sanitizer find, and what are its limits? `[Senior]`
- **TSan** instruments memory accesses at compile time and detects **data races** at runtime (two threads, at least one write, no synchronization), plus some lock misuse.
- Enable it in the scheme (Diagnostics → Thread Sanitizer), on the **simulator** (not supported on devices), and run tests and real flows with it in CI.
- Limits: only finds races that **actually happen** in that run; 2–20× slower and much more memory; can't be combined with Address Sanitizer.
- Swift 6's compile-time checking prevents most data races in Swift code; TSan still matters for `@unchecked Sendable` types, C/Objective-C code and legacy modules (Swift Concurrency Q129).

### Q67. How do you diagnose a deadlock or a hang? `[Senior]`
1. **Reproduce and pause** in the debugger: look at the main thread's backtrace, then all threads (`bt all` in LLDB, or the Debug navigator).
2. **Identify what the main thread waits on**: `semaphore_wait_trap`, `__ulock_wait` (lock), `_dispatch_sync_f_slow` (`sync` onto a queue), `mach_msg` (IPC to a system service).
3. **Find who holds it**: the thread inside the locked section, or the queue blocked by your `sync`.
4. **Instruments**: **Hangs** (main thread unresponsive intervals), **System Trace / Thread State Trace** (why each thread was blocked and who unblocked it), **Time Profiler** for busy hangs (CPU work on main).
5. **Production**: Xcode Organizer **Hangs** reports, MetricKit `MXHangDiagnostic` (includes the main thread's stack), on-device hang detection (Settings → Developer).

```
(lldb) bt all
* thread #1, queue = 'com.apple.main-thread', stop reason = signal SIGSTOP
  frame #0: libsystem_kernel.dylib`semaphore_wait_trap
  frame #1: libdispatch.dylib`_dispatch_semaphore_wait_slow
  frame #2: MyApp`ProfileService.fetchUserSync() at ProfileService.swift:42     ← waiting on a semaphore
  thread #7, queue = 'com.example.network'
  frame #0: MyApp`closure #1 in ProfileService.fetchUserSync() ...
  frame #1: libdispatch.dylib`_dispatch_client_callout
  ...                                                       ← tries DispatchQueue.main.async → never runs
```

### Q68. What thread information does a crash report give you? `[Senior]`
- **Exception type and code**: e.g. `EXC_BAD_ACCESS (SIGSEGV)` (bad memory access, often a race or use-after-free), `EXC_BREAKPOINT (SIGTRAP)` (Swift runtime trap: force unwrap, out of bounds, `fatalError`), `EXC_CRASH (SIGABRT)` with an exception reason, termination reason `0x8badf00d` (watchdog).
- **Triggered by Thread: N** and that thread's stack: start here.
- **All other threads' stacks**: essential for deadlocks/watchdog kills (what was the main thread waiting on?) and races (what was another thread doing to the same object?).
- **Queue names** appear next to threads (`Thread 3 name: Dispatch queue: com.example.db`), which is why naming queues matters (Q69).
- **Binary images** with UUIDs, for symbolication.
- Crashes that move around (different stacks, `EXC_BAD_ACCESS` in `swift_retain`, `objc_msgSend`, `Dictionary` internals) are a strong signal of a **data race**.

### Q69. How do naming and tooling make threading problems easier to find? `[Senior]`
- **Name every queue** with a reverse-DNS label (`com.example.app.imageDecode`) and name dedicated threads; names appear in the debugger, Instruments and crash reports.
- Use **`os_signpost`** intervals around important work to see it on the Instruments timeline next to thread states.
- **Instruments templates**: Time Profiler (CPU per thread), System Trace (thread states, context switches, priority), Swift Concurrency (tasks and actors), Hangs, Thread State Trace.
- **Xcode Thread Performance Checker** (Diagnostics): flags priority inversions and main-thread I/O at runtime.
- Count threads: the Debug navigator shows live threads; a growing thread count during scrolling or loading points to thread explosion (Q38).

## 9. "Spot the Problem" & "What's the Output?" Questions

### Q70. What's the output (called on the main thread)? `[Fundamental]`
```swift
print("A")
DispatchQueue.main.async { print("B") }
print("C")
DispatchQueue.global().async {
    print("D")
    DispatchQueue.main.async { print("E") }
}
print("F")
```
**Answer:** `A C F` always come first, in that order (the main thread keeps running its current code). `B` runs on a later main run loop iteration. `D` runs on a background thread at some point (it can appear before, between or after the main-thread prints). `E` always comes after both `D` and `B` (main queue is serial FIFO and `E` is enqueued after `B`).
A typical run: `A C F D B E` or `A C F B D E`. The guaranteed constraints: A<C<F, F<B, D<E, B<E.

### Q71. Does this deadlock? `[Senior]`
```swift
let concurrent = DispatchQueue(label: "com.example.concurrent", attributes: .concurrent)

concurrent.async {
    concurrent.sync { print("1") }            // (a)
}

concurrent.async(flags: .barrier) {
    concurrent.sync { print("2") }            // (b)
}
```
**Answer:**
- (a) **No deadlock**: a `sync` onto a concurrent queue from a block on that queue can run immediately alongside the current block.
- (b) **Deadlock**: inside a **barrier** the queue behaves as serial (nothing else may run until the barrier finishes), but the barrier is waiting for the inner block → circular wait.

### Q72. What's wrong with this singleton? `[Senior]`
```swift
final class ImageCache {
    static var shared: ImageCache { _shared }
    private static var _instance: ImageCache?
    private static var _shared: ImageCache {
        if _instance == nil { _instance = ImageCache() }      // check-then-act
        return _instance!
    }
    var images: [URL: UIImage] = [:]
}
```
**Problems:**
1. Hand-rolled lazy initialization is a **race**: two threads can both see `nil` and create two caches.
2. `static var` global mutable state is rejected in Swift 6 (not concurrency-safe).
3. `images` is an unsynchronized dictionary mutated from many threads (image loading callbacks) → crashes.

**Fix:** `static let shared = ImageCache()` (initialized once, thread-safe, Q55) and protect `images` (use `NSCache`, which is thread-safe, or a `Mutex`/actor).

### Q73. What's wrong with this network callback? `[Fundamental]`
```swift
func loadProfile() {
    URLSession.shared.dataTask(with: profileURL) { data, _, _ in
        let profile = try? JSONDecoder().decode(Profile.self, from: data ?? Data())
        self.nameLabel.text = profile?.name                   // ❌
        self.activityIndicator.stopAnimating()                 // ❌
    }.resume()
}
```
**Problems:**
1. `URLSession` completion handlers run on a **background** queue → UIKit called off the main thread (Main Thread Checker warning, glitches, crashes). In Swift 6 this is a compile error when the view controller is `@MainActor`.
2. Errors are silently ignored (empty `Data()` decode).

**Fix:** `let (data, _) = try await URLSession.shared.data(from: profileURL)` inside a `@MainActor` method (decode heavy payloads off main if needed), or hop with `DispatchQueue.main.async` in legacy code.

### Q74. Why doesn't this timer ever fire? `[Senior]`
```swift
DispatchQueue.global().async {
    Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { _ in
        print("tick")
    }
}
```
**Problem:** `scheduledTimer` adds the timer to the **current thread's run loop**. GCD worker threads don't run their run loops, and the thread returns to the pool as soon as the block ends, so the timer never fires (Q22).

**Fix:** schedule on the main run loop (`RunLoop.main.add(timer, forMode: .common)`), use a `DispatchSourceTimer` on a queue (Q37), or an async loop with `Task.sleep`.

### Q75. What's wrong with this `DispatchGroup` code? `[Senior]`
```swift
func loadAll(ids: [String], completion: @escaping @Sendable ([Item]) -> Void) {
    let group = DispatchGroup()
    var items: [Item] = []
    for id in ids {
        group.enter()
        api.item(id) { result in
            guard case .success(let item) = result else { return }    // ❌ no leave on failure
            items.append(item)                                       // ❌ concurrent appends
            group.leave()
        }
    }
    group.wait()                                                     // ❌ blocks the caller
    completion(items)
}
```
**Problems:**
1. **`leave()` missing on the failure path** → the group never empties → `wait` blocks forever (and `notify` would never fire).
2. **Data race**: completion handlers may run concurrently and append to the same array (Swift 6 rejects mutating a captured `var` from a `@Sendable` closure).
3. **`group.wait()`** blocks the calling thread; deadlocks if called on the main thread while callbacks need main.

**Fix:** `defer { group.leave() }` at the top of the callback; collect results under a lock (or on a serial queue); `group.notify(queue:)` instead of `wait()`; or rewrite with a task group (Async/Await Q32).

### Q76. What's wrong with this barrier? `[Senior]`
```swift
func save(_ value: Value, for key: Key) {
    DispatchQueue.global(qos: .utility).async(flags: .barrier) {
        self.storage[key] = value
    }
}
```
**Problem:** barriers have **no effect on global queues** (the system doesn't let one client block a shared queue). The write runs concurrently with readers → data race.

**Fix:** use a **private** concurrent queue for both reads and writes (Q33), or a lock/`Mutex`.

### Q77. What's wrong with this "thread-safe" array usage? `[Senior]`
```swift
final class SafeArray<Element: Sendable & Equatable>: @unchecked Sendable {
    private var items: [Element] = []
    private let lock = NSLock()
    func contains(_ e: Element) -> Bool { lock.withLock { items.contains(e) } }
    func append(_ e: Element) { lock.withLock { items.append(e) } }
}

// Called from many threads:
if !subscribers.contains(id) {
    subscribers.append(id)                 // ❌ another thread may have appended `id` in between
}
```
**Problem:** each method is atomic, but the **check-then-act** sequence isn't (Q49). Duplicates appear under load.

**Fix:** add an atomic operation to the type, e.g. `func appendIfMissing(_ e: Element) -> Bool` that checks and appends inside one `withLock`. Thread-safe types need **operations** that match how callers use them, not just locked getters/setters.

### Q78. What's wrong with this reentrant callback? `[Lead/Expert]`
```swift
final class SessionStore: @unchecked Sendable {
    private let queue = DispatchQueue(label: "com.example.session")
    private var token: String?
    var onTokenChange: (@Sendable (String?) -> Void)?

    func setToken(_ newValue: String?) {
        queue.sync {
            token = newValue
            onTokenChange?(newValue)              // ❌ calls out while "holding" the queue
        }
    }

    func currentToken() -> String? { queue.sync { token } }
}

// Somewhere else:
store.onTokenChange = { _ in
    analytics.identify(store.currentToken())      // re-enters queue.sync → deadlock
}
```
**Problem:** the callback runs **inside** `queue.sync`; when it calls `currentToken()`, that's a `sync` onto the same serial queue from within it → deadlock (Q32, Q62).

**Fix:** update state inside the queue, then invoke callbacks **after** leaving it (or asynchronously on a documented queue):
```swift
func setToken(_ newValue: String?) {
    let callback = queue.sync { () -> (@Sendable (String?) -> Void)? in
        token = newValue
        return onTokenChange
    }
    callback?(newValue)
}
```

### Q79. Why does this notification service extension sometimes show no image? `[Senior]`
```swift
override func didReceive(_ request: UNNotificationRequest,
                         withContentHandler contentHandler: @escaping (UNNotificationContent) -> Void) {
    let url = URL(string: request.content.userInfo["image"] as! String)!
    let data = try! Data(contentsOf: url)                              // full-size download into memory
    let image = UIImage(data: data)!                                   // full-size decode
    let resized = image.preparingThumbnail(of: CGSize(width: 2000, height: 2000))!
    // ... write to a temp file, attach, call contentHandler
}
```
**Problems:**
1. The extension is a **separate process with a small memory limit** (Q14): downloading and **decoding** a large image (a 4000×3000 photo is ~48 MB decoded) gets the process **killed by jetsam**, and the system shows the original notification without the image.
2. **Synchronous network I/O** with `Data(contentsOf:)` on the extension's thread, with a ~30 s time budget.
3. Force unwraps/`try!`: a missing key or bad URL crashes the extension.

**Fix:** download to a file with `URLSession.downloadTask`, attach the **file** (the system handles display), or downsample with ImageIO (`CGImageSourceCreateThumbnailAtIndex`) without decoding the full image; handle `serviceExtensionTimeWillExpire`; no force unwraps.

### Q80. Two processes write the same database. What can go wrong? `[Lead/Expert]`
Scenario: the app and its widget/notification extension both write a SQLite (or Core Data/SwiftData) store in the App Group container.

**Problems:**
- In-process locks and actors **don't protect across processes**.
- Each process caches its own view of the data → stale reads (widget shows old data after the app changed it).
- Concurrent writes can hit `SQLITE_BUSY` / lock errors; a crash mid-write without WAL/journaling risks corruption.
- An app **suspended while holding a file lock** on a shared container file can be **killed by the system** (`0xdead10cc` termination) to avoid deadlocking other processes.

**Fix:**
- Let SQLite handle cross-process locking (WAL mode, busy timeout), or keep a **single writer** (the app) and have extensions append to a small inbox file the app imports.
- Core Data: **persistent history tracking** + merging remote changes; SwiftData handles this for App Group stores.
- Release file locks and finish writes before suspension (background task, Q19).
- Signal changes with Darwin notifications or `WidgetCenter.reloadTimelines` (Q15).

## 10. Senior / Lead Scenario Questions

### Q81. Crash reports show random `EXC_BAD_ACCESS` crashes inside `Dictionary` and `swift_retain`. How do you investigate? `[Senior]`
1. Treat it as a probable **data race**: crash sites vary, but they're all inside collection or reference-counting internals.
2. Look at **other threads** in the reports: which code was touching the same object (Q68)?
3. Run the suspected flows with **Thread Sanitizer** on the simulator, with stress (many concurrent requests, fast navigation).
4. Audit **shared mutable state**: singletons with `var` dictionaries, caches updated from network callbacks, delegates called on background queues, `@unchecked Sendable` types.
5. Fix by **confining** state (actor, `@MainActor`, serial queue) or protecting it (`Mutex`), and turn on Swift 6 strict concurrency for the module to stop new races at compile time.

### Q82. Users report the app being killed at launch with `0x8badf00d`. What do you do? `[Senior]`
- It's the **watchdog**: the main thread didn't finish launching in time.
- Get the crash reports: the **main thread's stack** shows what it was doing (synchronous network, a big database migration, Keychain reads, a semaphore wait, heavy SDK `configure`).
- Fixes: move work off the main thread, defer non-essential setup until after the first frame, make migrations incremental/async with a lightweight UI, lazy-load SDKs.
- Prevent: measure launch with the App Launch instrument and MetricKit launch metrics; add a launch-time budget to CI; watch for slow devices and cold launches after updates.

### Q83. A feed stutters while scrolling and loading images. Design the threading. `[Senior]`
```
Main thread / @MainActor:  cell configuration, setting already-decoded images, layout (nothing heavy)
Network (URLSession):       async downloads; HTTP cache
Decode/resize (background): downsample to the cell's pixel size with ImageIO (decode off main!)
Memory cache (NSCache):     decoded thumbnails, thread-safe
Disk cache (actor):         file I/O serialized per cache
Prefetching:                UITableView/UICollectionView prefetch APIs start loads early; cancel on cancelPrefetching
```
- Decoding a JPEG lazily on the main thread at first display is a common hidden hang: decode/downsample **before** handing the image to UIKit (`UIImage.byPreparingForDisplay()` / `preparingThumbnail(of:)`, iOS 15+).
- **Cancel** loads for cells that went off-screen (task per cell, cancelled in `prepareForReuse`); check that the cell still shows the same item when the image arrives.
- Limit concurrent decodes (e.g. 4) to avoid thread explosion and memory spikes.
- Verify with Instruments: Hangs, Time Profiler (main thread), Animation Hitches.

### Q84. Users lose their drafts when they switch apps. What's going on, and how do you fix it? `[Senior]`
- After backgrounding, the app gets a short time, then is **suspended**; it can later be **killed without any callback** (jetsam, user swipe, update) (Q12–Q13).
- The app probably saved only "on termination" (`applicationWillTerminate` isn't called for suspended apps) or kept drafts only in memory.
- Fix:
  - Save **incrementally** (debounced, e.g. 1 s after typing stops) to disk.
  - On `scenePhase == .background` / `sceneDidEnterBackground`, flush pending writes inside a **background task** (Q19).
  - Restore on launch (state restoration / `SceneStorage` for UI state).
  - Use file protection that allows writes when locked if saving can happen at lock time.

### Q85. You're leading the migration of a GCD-heavy codebase to Swift 6. What's your plan? `[Lead/Expert]`
1. **Inventory** queues and shared state: which queue protects what? Name queues; add `dispatchPrecondition` checks to document assumptions.
2. **Turn on strict concurrency checking** module by module (warnings first) to see the real race surface.
3. **Leaf modules first**: models become `Sendable` value types; services that used a serial queue become **actors**; UI code becomes `@MainActor`.
4. Replace **semaphore/group waiting** with `async` APIs; wrap callback APIs with continuations at the boundaries.
5. Keep GCD where APIs require queues (capture, Network.framework) and wrap those components behind `async` interfaces.
6. Don't mix `queue.sync` and actor access for the same state; one owner per piece of state.
7. Use `@unchecked Sendable` only for documented, reviewed lock-based types; track them as tech debt.
8. Measure: hangs, crash-free rate, and race-related crash signatures before/after.

### Q86. Design the threading model for a real-time camera filter feature. `[Lead/Expert]`
```
AVCaptureSession configuration ──▶ dedicated serial "session" queue (startRunning() blocks: never on main)
Camera frames ──▶ AVCaptureVideoDataOutput delegate on a serial "video" queue (high QoS)
                    │  alwaysDiscardsLateVideoFrames = true  (drop frames rather than queue them)
                    ▼
           Metal / Core Image processing on the same queue (or a GPU command queue), reuse buffers (CVPixelBufferPool)
                    │
                    ▼
           MTKView draws on the main thread / display link ──▶ screen
Recording (AVAssetWriter) ──▶ its own serial queue, appends processed buffers in order
UI state (buttons, zoom, errors) ──▶ @MainActor view model; sends commands to the session queue
```
Key points:
- **Frame budget**: 33 ms at 30 fps (16.7 ms at 60 fps). If processing is slower, drop frames; never let a queue grow.
- **No allocation per frame**: pools for pixel buffers and Metal textures; avoid copying.
- **One owner per resource**: the session queue owns the `AVCaptureSession`; UI sends intents, it never touches the session directly.
- Handle **interruptions** (phone call, Split View, thermal state) by observing notifications and pausing work; reduce frame rate or filter complexity under `ProcessInfo.thermalState == .serious`.
- Swift Concurrency fits around the edges (permissions, setup, UI); the frame pipeline stays on queues because AVFoundation delivers frames to queues and per-frame `Task` creation would add overhead and break ordering.

## 11. Last-Day Cheat Sheet

### Process vs thread
| | Process | Thread |
|---|---|---|
| Unit of | Isolation (memory, security) | Execution (scheduling) |
| Memory | Own address space | Shares heap/globals; own stack (iOS: 1 MB main, 512 KB others) |
| Crash | Kills itself only | Kills the whole process |
| iOS | One per app + one per extension; can't spawn others | Managed for you by GCD / Swift Concurrency |

### iOS process lifecycle
- Not running → Inactive → Active → Background (limited time) → **Suspended (no code runs)** → may be **killed silently**.
- Save state when entering the background; never rely on `applicationWillTerminate`.
- Kill reasons: jetsam (memory), watchdog `0x8badf00d`, background time expired, `0xdead10cc` (file lock held when suspended), crashes, user swipe.
- Extensions = separate processes with small memory limits; share via App Groups, Keychain groups, Darwin notifications.
- Protected data may be unavailable when launched in the background while locked.

### Threads & run loops
- UI only on the main thread (`@MainActor`); never block it (hangs from ~250 ms; watchdog at launch).
- Run loop modes: `.default`, `.tracking` (scrolling), `.common` (both) → timers stop during scroll unless `.common`.
- Background GCD threads don't run run loops → `Timer.scheduledTimer` there never fires.
- QoS: userInteractive > userInitiated > default > utility > background (affects CPU, cores, I/O, energy).

### GCD in one line each
| | Remember |
|---|---|
| `async` vs `sync` | About the caller: return now vs block until done |
| `main.sync` on main / `sync` to current serial queue | Deadlock |
| Barrier | Only on your own concurrent queue; no effect on global queues |
| Group | `enter`/`leave` balanced on every path; prefer `notify` over `wait` |
| Semaphore | OK to limit width off main; never to make async code synchronous; no priority donation |
| `DispatchWorkItem` | Cancels only before it starts (or if the block checks) |
| Thread explosion | Blocking work on concurrent queues → many threads → stalls at pool limit |
| Target queues | Few serial queues per subsystem |
| `concurrentPerform` | Parallel loop, blocks until done, chunk the work |

### Synchronization picks (Swift 6)
1. Value types + immutability.
2. `@MainActor` for UI state; `actor` for async shared state.
3. `Mutex` (iOS 18) / `OSAllocatedUnfairLock` (iOS 16) for tiny synchronous sections.
4. `Atomic` for counters/flags.
5. Serial queue where an API needs a queue anyway.
6. Never: raw `os_unfair_lock` as a stored property, `OSSpinLock`, locks or semaphores across `await`.

### Bug → cause → fix
| Symptom | Likely cause | Fix |
|---|---|---|
| Random crashes in collections/retain | Data race | Confine or lock; TSan; Swift 6 checking |
| UI freeze, stack in `semaphore_wait` / `_dispatch_sync_f_slow` | Main thread waiting | Async APIs; never block main |
| Deadlock | Lock order, `sync` re-entry, callbacks under lock | Lock ordering; call out after unlocking |
| Main thread slow despite "background" work | Priority inversion (semaphore) | Owner-aware primitives; correct QoS |
| Growing thread count, stalls | Thread explosion | Async I/O, limit width |
| Duplicates under load | Check-then-act | Atomic compound operations |
| Purple runtime warning | UIKit off main | `@MainActor` / hop to main |
| Extension silently fails | Memory limit (jetsam) | Stream to files, downsample, small footprint |

### Phrases that show seniority
- "A process is the unit of isolation; a thread is the unit of execution."
- "Queues and tasks are work, not threads; the system maps them onto a small pool."
- "After backgrounding, assume the process can disappear without a callback."
- "I never block the main thread, and I don't wait on semaphores, because they can't donate priority."
- "Each piece of mutable state has exactly one owner: the main actor, an actor, a serial queue or a lock."
- "Thread-safe types need atomic operations that match how callers use them."
