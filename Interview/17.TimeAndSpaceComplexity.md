## 1. Fundamentals & Notation

### Q1. What is complexity analysis, and why do we use it instead of measuring time? `[Fundamental]`
- **Complexity analysis** describes how an algorithm's **running time** (time complexity) or **memory use** (space complexity) **grows as the input size grows**.
- We count **basic operations** (comparisons, assignments, arithmetic, array accesses) as a function of the input size `n`, then keep only the **growth rate**.
- Why not just measure with a stopwatch?
  - Measurements depend on the device, compiler optimizations, other running processes and the specific input.
  - A measurement at `n = 1,000` doesn't tell you what happens at `n = 1,000,000`. Growth rate does.
- Both matter in practice: complexity predicts **scaling**; profiling (Instruments) finds **actual** bottlenecks.

**Interview line:** "Complexity tells me how the cost scales with input size, independent of hardware. I use it to choose an approach, then profile to confirm."

### Q2. What is "input size", and what if there are several inputs? `[Fundamental]`
- **n** is whatever measures the input: number of elements in an array, characters in a string, nodes in a tree, digits/bits of a number.
- With **several independent inputs**, keep separate variables: an algorithm over an array of `n` items and a string of `m` characters might be `O(n + m)` or `O(n · m)`. Don't merge them into one `n`.
- For **graphs**: `V` (vertices) and `E` (edges), e.g. BFS is `O(V + E)`.
- For **numbers**: "input size" is technically the number of **bits** (`log n`), which matters for questions like "is checking primality up to √n polynomial?" (Q62).
- Also name the **output size** when it dominates: generating all subsets is `O(2ⁿ · n)` because the output itself is that big.

### Q3. What do best, worst and average case mean? `[Fundamental]`
| Case | Meaning | Linear search for `x` in `n` items |
|---|---|---|
| **Best** | Cheapest input of size `n` | `x` is first: **1** comparison → `O(1)` |
| **Worst** | Most expensive input of size `n` | `x` is last or missing: **n** comparisons → `O(n)` |
| **Average** | Expected cost over a distribution of inputs | `x` equally likely anywhere: about **n/2** → `O(n)` |

- Interviews default to the **worst case** unless you say otherwise. It's a guarantee.
- **Average** needs an assumption about the input distribution (e.g. "random order", "good hash function").
- **Expected** (randomized algorithms): average over the algorithm's own random choices, for **any** input (randomized quicksort: expected `O(n log n)` on every input).
- **Amortized** is different again: the average cost **per operation over a sequence** of operations, with no probability involved (Section 5).
- Best case is rarely useful ("bubble sort is O(n) on sorted input" is true but not a selling point).

### Q4. What are Big-O, Big-Omega and Big-Theta formally? `[Senior]`
For functions `f(n)` (the algorithm's cost) and `g(n)` (a simple reference function):

| Notation | Meaning | Formal definition | Analogy |
|---|---|---|---|
| `f(n) = O(g(n))` | **Upper bound**: grows **no faster** than `g` | ∃ `c > 0`, `n₀` such that `f(n) ≤ c·g(n)` for all `n ≥ n₀` | ≤ |
| `f(n) = Ω(g(n))` | **Lower bound**: grows **at least** as fast as `g` | ∃ `c > 0`, `n₀` such that `f(n) ≥ c·g(n)` for all `n ≥ n₀` | ≥ |
| `f(n) = Θ(g(n))` | **Tight bound**: grows **exactly** like `g` | Both `O(g)` and `Ω(g)` | = |
| `f(n) = o(g(n))` | Strictly slower | `f(n)/g(n) → 0` | < |
| `f(n) = ω(g(n))` | Strictly faster | `f(n)/g(n) → ∞` | > |

**Worked example:** `f(n) = 3n² + 5n + 20`.
- Upper bound: for `n ≥ 1`, `3n² + 5n + 20 ≤ 3n² + 5n² + 20n² = 28n²` → `O(n²)` with `c = 28`, `n₀ = 1`.
- Lower bound: `3n² + 5n + 20 ≥ 3n²` for all `n ≥ 1` → `Ω(n²)` with `c = 3`.
- So `f(n) = Θ(n²)`.
- It's also **technically** `O(n³)` (a looser upper bound), but that's not a useful answer.

**Common misconceptions to avoid in interviews:**
- "Big-O means worst case": no. Big-O is an upper bound on **a function**; you can give a Big-O for the best, average or worst case. ("Quicksort's best case is `Θ(n log n)`, worst case `Θ(n²)`.")
- In everyday interview language, "O" is used to mean the tight bound. That's fine, but know the difference if asked.

### Q5. Why do we drop constants and lower-order terms? `[Fundamental]`
- As `n` grows, the **highest-order term dominates**: for `n = 1,000,000`, `n² = 10¹²` while `1000n = 10⁹`, a 1000× difference.
- Constant factors depend on the machine and implementation details, not the algorithm's structure.

| Expression | Simplifies to | Why |
|---|---|---|
| `5n + 100` | `O(n)` | Drop constant factor and constant term |
| `n² + n log n + n` | `O(n²)` | `n²` dominates |
| `n/2` | `O(n)` | Constant factor ½ |
| `2ⁿ + n¹⁰⁰` | `O(2ⁿ)` | Exponential beats any polynomial, eventually |
| `log₂ n`, `log₁₀ n`, `ln n` | `O(log n)` | Bases differ by a constant factor: `log₂ n = log₁₀ n / log₁₀ 2` |
| `n + m` (independent inputs) | `O(n + m)` | **Can't** drop either; you don't know which is bigger |
| `2^(2n)` | `O(4ⁿ)`, **not** `O(2ⁿ)` | A constant in the **exponent** is not a constant factor |

**Caveat:** constants still matter in practice (Section 8). `O(n)` with a huge constant can lose to `O(n log n)` for realistic sizes.

### Q6. What are the common growth rates, and how fast do they grow? `[Fundamental]`
| Complexity | Name | n = 10 | n = 1,000 | n = 1,000,000 | Typical example |
|---|---|---|---|---|---|
| `O(1)` | Constant | 1 | 1 | 1 | Array index, dictionary lookup (average) |
| `O(log n)` | Logarithmic | 3 | 10 | 20 | Binary search, balanced BST, heap push/pop |
| `O(√n)` | Square root | 3 | 32 | 1,000 | Trial-division primality |
| `O(n)` | Linear | 10 | 1,000 | 10⁶ | Single loop, linear search |
| `O(n log n)` | Linearithmic | 33 | 10⁴ | 2×10⁷ | Merge sort, Swift's `sort()`, heap sort |
| `O(n²)` | Quadratic | 100 | 10⁶ | 10¹² | Nested loops over the same input, bubble sort |
| `O(n³)` | Cubic | 1,000 | 10⁹ | 10¹⁸ | Naive matrix multiplication, Floyd–Warshall |
| `O(2ⁿ)` | Exponential | 1,024 | ~10³⁰¹ | — | All subsets, naive Fibonacci |
| `O(n!)` | Factorial | 3.6×10⁶ | — | — | All permutations, brute-force TSP |

```
n = 1,000,000 at roughly 10⁸ simple operations per second:
O(log n)     ~20 operations      instant
O(n)         10⁶                 ~0.01 s
O(n log n)   2 × 10⁷             ~0.2 s
O(n²)        10¹²                ~3 hours
O(2ⁿ)        2^1,000,000         never finishes
```
**Rule of thumb:** a modern CPU does very roughly 10⁸–10⁹ simple operations per second. `10¹²` operations (`n²` at a million) is minutes to hours, unusable on a phone (Q63).

### Q7. Order these functions by growth rate: `n log n`, `2ⁿ`, `n²`, `log n`, `n!`, `√n`, `nⁿ`, `n`, `1`, `log(n!)`, `n^1.5`, `(log n)²`. `[Senior]`
`1` < `log n` < `(log n)²` < `√n` < `n` < `n log n` = `log(n!)` < `n^1.5` < `n²` < `2ⁿ` < `n!` < `nⁿ`

Notes interviewers look for:
- **`log(n!)` is `Θ(n log n)`** (Stirling's approximation: `log(n!) ≈ n log n − n log e`). This is why comparison sorting needs `Ω(n log n)` comparisons (Q58).
- **Polylog vs polynomial**: any power of `log n` grows slower than any positive power of `n`: `(log n)¹⁰⁰ = o(n^0.01)`.
- **`n!` vs `2ⁿ`**: `n!` grows faster (for `n ≥ 4`); `nⁿ` faster still (`n! = o(nⁿ)`).

### Q8. What are the rules for combining complexities? `[Fundamental]`
| Code structure | Rule | Example |
|---|---|---|
| Sequential blocks | **Add**, keep the dominant term | `O(n)` loop then `O(n²)` loop → `O(n + n²)` = `O(n²)` |
| Nested loops | **Multiply** | Loop of `n` containing a loop of `m` → `O(n·m)` |
| `if/else` | **Max** of the branches (worst case) | `O(n)` vs `O(1)` branch → `O(n)` |
| Function call | Cost of the **callee** for those arguments | Calling an `O(n)` helper inside a loop of `n` → `O(n²)` |
| Loop with early exit | Worst case: as if no exit; also state best case | Linear search: `O(n)` worst, `O(1)` best |

## 2. Calculating Time Complexity: Loops & Statements

> **Method:** (1) decide what `n` is; (2) find the **innermost** work and its cost; (3) count **how many times** each loop runs, working outward; (4) sum or multiply; (5) simplify. When loop bounds depend on outer variables, **write the sum** and evaluate it.

### Q9. What's the complexity of simple statements and a single loop? `[Fundamental]`
```swift
func sumAndMax(_ numbers: [Int]) -> (sum: Int, max: Int)? {
    guard let first = numbers.first else { return nil }   // O(1)
    var sum = 0                                          // O(1)
    var maxValue = first                                 // O(1)
    for x in numbers {                                   // runs n times
        sum += x                                         //   O(1)
        if x > maxValue { maxValue = x }                 //   O(1)
    }
    return (sum, maxValue)                               // O(1)
}
```
- Body cost `O(1)` × `n` iterations + `O(1)` setup = **`O(n)` time**.
- Extra variables: a fixed number → **`O(1)` extra space**.
- Note: a constant number of loops in sequence (two passes, three passes) is still `O(n)`: `2n` and `3n` are `O(n)`.

### Q10. What about nested loops over the same input? `[Fundamental]`
```swift
func hasDuplicate(_ a: [Int]) -> Bool {
    for i in 0..<a.count {               // n iterations
        for j in 0..<a.count where j != i {   // n iterations each
            if a[i] == a[j] { return true }   // O(1)
        }
    }
    return false
}
```
- `n × n` iterations of `O(1)` work → **`O(n²)`**.
- Improving it: start `j` at `i + 1` (Q11), which halves the work but stays `O(n²)`; a `Set` makes it `O(n)` (Q90).

### Q11. How do you count a nested loop whose inner bound depends on the outer variable? `[Fundamental]`
```swift
for i in 0..<n {
    for j in (i + 1)..<n {      // runs n − i − 1 times
        work(i, j)              // O(1)
    }
}
```
Write the sum of inner iterations:
```
i = 0: n − 1
i = 1: n − 2
...
i = n − 2: 1
i = n − 1: 0
Total = 0 + 1 + 2 + … + (n − 1) = n(n − 1)/2
```
- `n(n − 1)/2 = ½n² − ½n` → **`Θ(n²)`**. Halving the work doesn't change the class.
- This is the number of **pairs** `C(n, 2)`. Triple nested loops with `i < j < k` give `C(n, 3) = n(n−1)(n−2)/6` → `Θ(n³)`.

**Useful sums to memorize:**
| Sum | Closed form | Order |
|---|---|---|
| `1 + 1 + … + 1` (n terms) | `n` | `Θ(n)` |
| `1 + 2 + … + n` | `n(n+1)/2` | `Θ(n²)` |
| `1² + 2² + … + n²` | `n(n+1)(2n+1)/6` | `Θ(n³)` |
| `1 + 2 + 4 + … + 2ᵏ` | `2ᵏ⁺¹ − 1` | `Θ(2ᵏ)` (dominated by the last term) |
| `n + n/2 + n/4 + … + 1` | `< 2n` | `Θ(n)` |
| `1 + 1/2 + 1/3 + … + 1/n` (harmonic) | `≈ ln n` | `Θ(log n)` |
| `log 1 + log 2 + … + log n` | `log(n!)` | `Θ(n log n)` |

### Q12. Why does a loop that doubles (or halves) its counter run in `O(log n)`? `[Fundamental]`
```swift
var i = 1
while i < n {          // i = 1, 2, 4, 8, …, 2ᵏ
    i *= 2             // O(1)
}
```
- After `k` iterations, `i = 2ᵏ`. The loop stops when `2ᵏ ≥ n`, i.e. `k ≥ log₂ n`.
- So it runs `⌈log₂ n⌉` times → **`O(log n)`**.
- Same for halving: `var i = n; while i > 0 { i /= 2 }` → `O(log n)`.
- Same for any constant factor: multiplying by 3 → `log₃ n`, still `O(log n)` (Q5).
- **Intuition:** "how many times can you halve `n` before reaching 1?" That's binary search, balanced tree height, and the number of digits/bits of a number (`n` has `⌊log₂ n⌋ + 1` bits, `⌊log₁₀ n⌋ + 1` decimal digits).

```swift
func digitCount(_ n: Int) -> Int {     // O(log n): one iteration per decimal digit
    var n = abs(n), count = 1
    while n >= 10 { n /= 10; count += 1 }
    return count
}
```

### Q13. What's the complexity of a loop whose counter grows by squaring, or runs to √n? `[Senior]`
```swift
// (a) Runs while i * i <= n: i = 1, 2, 3, …, √n
var i = 1
while i * i <= n { i += 1 }                     // O(√n)

// (b) Counter squares each time: 2, 4, 16, 256, 65536, …  (i = 2^(2^k))
var j = 2
while j < n { j = j * j }                       // O(log log n)
```
- (a) The loop stops when `i > √n` → `√n` iterations → **`O(√n)`**. Used in trial-division primality testing and finding divisors.
- (b) After `k` steps `j = 2^(2ᵏ)`; it stops when `2^(2ᵏ) ≥ n` → `2ᵏ ≥ log₂ n` → `k ≥ log₂ log₂ n` → **`O(log log n)`**. (`log log n` is ≈ 5 for a 64-bit number.)

```swift
func isPrime(_ n: Int) -> Bool {          // O(√n) time, O(1) space
    guard n >= 2 else { return false }
    var d = 2
    while d * d <= n {
        if n % d == 0 { return false }
        d += 1
    }
    return true
}
```

### Q14. How do you analyze a nested loop where the inner loop is logarithmic? `[Fundamental]`
```swift
for i in 0..<n {                 // n times
    var j = 1
    while j < n { j *= 2 }       // log n times
}
// Total: n · log n → O(n log n)
```
And when the **outer** loop is logarithmic and the inner one linear in a shrinking bound:
```swift
var size = n
while size > 0 {                 // log n iterations: n, n/2, n/4, …
    for _ in 0..<size { work() } // size iterations
    size /= 2
}
// Total: n + n/2 + n/4 + … + 1 < 2n → O(n), NOT O(n log n)
```
**Lesson:** don't just multiply "outer count × max inner count" when the inner bound shrinks: **sum the actual work**. A geometric series is dominated by its largest term.

### Q15. What's the complexity of the harmonic loop `for i in 1...n { for j in stride(from: i, through: n, by: i) }`? `[Senior]`
```swift
var count = 0
for i in 1...n {
    for _ in stride(from: i, through: n, by: i) {   // runs about n / i times
        count += 1
    }
}
```
- Total = `n/1 + n/2 + n/3 + … + n/n = n · (1 + 1/2 + … + 1/n) = n · Hₙ ≈ n ln n` → **`O(n log n)`**.
- This pattern appears in the **Sieve of Eratosthenes** (which is even better, `O(n log log n)`, because it only sieves with primes) and in "for each divisor" computations.

```swift
/// Sieve of Eratosthenes: all primes up to n. O(n log log n) time, O(n) space.
func primes(upTo n: Int) -> [Int] {
    guard n >= 2 else { return [] }
    var isComposite = [Bool](repeating: false, count: n + 1)
    var p = 2
    while p * p <= n {
        if !isComposite[p] {
            for multiple in stride(from: p * p, through: n, by: p) { isComposite[multiple] = true }
        }
        p += 1
    }
    return (2...n).filter { !isComposite[$0] }
}
```

### Q16. Why is a two-pointer loop `O(n)` even though it looks nested? `[Senior]`
```swift
/// Length of the longest substring without repeating characters (sliding window)
func longestUniqueSubstring(_ s: String) -> Int {
    let chars = Array(s)                       // O(n) once: random access afterwards
    var lastSeen: [Character: Int] = [:]
    var left = 0, best = 0
    for right in 0..<chars.count {             // right moves n times in total
        if let previous = lastSeen[chars[right]], previous >= left {
            left = previous + 1                // left only moves forward
        }
        lastSeen[chars[right]] = right
        best = max(best, right - left + 1)
    }
    return best
}
```
- Count **total pointer movements**, not "loop inside loop". `right` advances `n` times; `left` only ever moves **forward** and never past `right`, so it moves at most `n` times **in total**.
- Total work `O(n + n)` = **`O(n)`** time; dictionary of at most `k` distinct characters → `O(min(n, k))` space.
- The same reasoning applies to the classic version with an inner `while` loop that shrinks the window: the inner loop's iterations **across the whole run** are bounded by `n` (an aggregate/amortized argument, Section 5).

### Q17. What if the loop involves two different inputs? `[Fundamental]`
```swift
func commonElements(_ a: [Int], _ b: [Int]) -> [Int] {
    var result: [Int] = []
    for x in a {                 // n = a.count
        if b.contains(x) {       // O(m) linear search, m = b.count
            result.append(x)
        }
    }
    return result
}
// Time: O(n · m).  With let setB = Set(b): O(n + m) average.
```
- Keep **both** variables. Saying `O(n²)` here is a common mistake; if `a` has 10 items and `b` has a million, `O(n · m)` tells the real story.
- `O(n + m)` means "one pass over each"; `O(n · m)` means "every pair".

### Q18. How do hidden costs inside a loop body change the complexity? `[Senior]`
The loop body's cost isn't always `O(1)`. Every call has its own complexity:

```swift
var result = ""
for word in words {                   // n words
    result = result + word + " "      // `+` creates a new String: copies the whole result so far
}
// Copies 1 + 2 + … + n chunks ≈ O(n²) characters copied in total (for n words of similar length)
// Fix: result += word (appends in place, amortized O(len(word))) or words.joined(separator: " ") → O(total length)
```
Common hidden linear costs in Swift: `array.contains`, `array.firstIndex(of:)`, `array.removeFirst()`, `array.insert(_:at: 0)`, `string.count`, `Array(someSequence)`, `sorted()`, `+` on arrays/strings, `index(_:offsetBy:)` on `String` (Section 6, Section 12).

### Q19. How do you analyze a `while` loop with a non-obvious step? `[Senior]`
Find **what quantity changes** on each iteration and how fast it approaches the stop condition.

```swift
// Euclid's GCD: O(log(min(a, b)))
func gcd(_ a: Int, _ b: Int) -> Int {
    var (a, b) = (a, b)
    while b != 0 { (a, b) = (b, a % b) }
    return a
}
```
- Every **two** iterations, the larger number at least **halves** (if `b ≤ a/2`, then `a % b < b ≤ a/2`; otherwise `a % b = a − b < a/2`). So the number of iterations is `O(log min(a, b))`, which is linear in the number of **digits**.

```swift
// Collatz: unknown! No proven bound on the number of steps.
var x = n
while x != 1 { x = x.isMultiple(of: 2) ? x / 2 : 3 * x + 1 }
```
Good interview move: if you can't bound a loop, say so and explain what you **can** say (e.g. "terminates for all tested values; no known proof").

### Q20. How do you handle `break`, `continue` and early returns? `[Fundamental]`
- **Worst case:** assume the exit condition is hit as **late as possible** (or never).
- **Best case:** as early as possible.
- If the early exit is guaranteed after a bounded amount of work, use that bound.

```swift
func firstNegativeIndex(_ a: [Int]) -> Int? {
    for (i, x) in a.enumerated() where x < 0 { return i }   // best O(1), worst O(n)
    return nil
}

// "continue" doesn't change the count of iterations, only skips the rest of the body:
for x in a {
    guard x.isMultiple(of: 2) else { continue }   // still n iterations
    expensive(x)                                   // runs for the even ones: worst case all n
}
```

### Q21. What is the complexity of operations on numbers themselves? `[Lead/Expert]`
- Fixed-width integers (`Int`, `Double`): arithmetic is **`O(1)`** (hardware instructions). Interviews assume this.
- **Arbitrary-precision** numbers (big integers, crypto): cost depends on the number of digits `d = O(log value)`:
  - Addition: `O(d)`. Schoolbook multiplication: `O(d²)`; Karatsuba `O(d^1.585)`.
- **Exponentiation by squaring**: computing `xⁿ` with `O(log n)` multiplications instead of `n`.

```swift
/// Modular exponentiation: O(log exponent) multiplications
func modPow(_ base: Int, _ exponent: Int, _ modulus: Int) -> Int {
    precondition(modulus > 1 && exponent >= 0)
    var result = 1, b = ((base % modulus) + modulus) % modulus, e = exponent   // handles negative bases
    while e > 0 {
        if e & 1 == 1 { result = Int((Int64(result) * Int64(b)) % Int64(modulus)) }
        b = Int((Int64(b) * Int64(b)) % Int64(modulus))
        e >>= 1                                         // halves each iteration → O(log e)
    }
    return result
}
```
(For moduli above ~3×10⁹, `Int64` products can overflow; use `multipliedFullWidth(by:)` or a big-integer library.)

### Q22. What's the complexity of iterating over every subset, permutation or combination? `[Senior]`
| Enumeration | Count | Cost to produce each | Total time |
|---|---|---|---|
| All subsets of `n` items | `2ⁿ` | `O(n)` to build/copy one | `O(n · 2ⁿ)` |
| All permutations | `n!` | `O(n)` | `O(n · n!)` |
| All `k`-combinations | `C(n, k)` | `O(k)` | `O(k · C(n, k))` |
| All pairs | `n(n−1)/2` | `O(1)` | `O(n²)` |
| All substrings | `n(n+1)/2` | `O(length)` to copy | `O(n³)` if each is copied; `O(n²)` if only indices |

```swift
/// All subsets with a bitmask: 2ⁿ masks × n bits each → O(n · 2ⁿ) time; output itself is O(n · 2ⁿ)
func subsets<T>(_ items: [T]) -> [[T]] {
    let n = items.count
    precondition(n < Int.bitWidth - 1, "2ⁿ subsets won't fit")
    var result: [[T]] = []
    result.reserveCapacity(1 << n)
    for mask in 0..<(1 << n) {
        var subset: [T] = []
        for i in 0..<n where mask & (1 << i) != 0 { subset.append(items[i]) }
        result.append(subset)
    }
    return result
}
```
When the **output** is exponential, no algorithm can be faster than the output size: say "this is optimal up to the output size".

## 3. Recursion, Recurrences & the Master Theorem

### Q23. How do you analyze a recursive function? `[Fundamental]`
1. Write a **recurrence**: `T(n) = (number of recursive calls) × T(size of each subproblem) + (work done in this call outside the recursive calls)`.
2. Solve it with one of: **unrolling/substitution**, a **recursion tree**, or the **Master theorem**.
3. For space, find the **maximum recursion depth** × space per frame (Q34).

```swift
func sum(_ a: [Int], _ i: Int = 0) -> Int {
    guard i < a.count else { return 0 }     // base case: O(1)
    return a[i] + sum(a, i + 1)            // one call on a problem 1 smaller, O(1) extra work
}
```
- Recurrence: `T(n) = T(n − 1) + O(1)`, `T(0) = O(1)`.
- Unroll: `T(n) = T(n−1) + c = T(n−2) + 2c = … = T(0) + n·c` → **`O(n)` time**.
- Depth `n` → **`O(n)` stack space** (and a stack overflow for very large `n`; Q35).

### Q24. How does the recursion tree method work? `[Senior]`
Draw the calls as a tree, write the **work per node** (excluding recursive calls), sum **per level**, then sum the levels.

**Merge sort:** `T(n) = 2T(n/2) + cn`
```
Level 0:                 cn                         → cn
Level 1:         cn/2          cn/2                 → cn
Level 2:     cn/4   cn/4   cn/4   cn/4              → cn
  ...                    ...                          ...
Level log n: c c c c c c c c … (n leaves)           → cn
                                         Total: cn × (log₂ n + 1) = O(n log n)
```

**Naive Fibonacci:** `T(n) = T(n−1) + T(n−2) + c`
```
                    fib(5)
              /                \
         fib(4)                fib(3)
        /      \              /      \
    fib(3)    fib(2)      fib(2)    fib(1)
    /    \     /   \       /   \
 fib(2) fib(1) …                          Each level has up to 2× the nodes of the previous one;
                                          depth n → at most 2ⁿ nodes → O(2ⁿ)
                                          (tight bound: Θ(φⁿ), φ ≈ 1.618)
```
**General shortcut** for recursion with `b` branches and depth `d` doing `O(1)` per call: about **`O(bᵈ)`** calls.

### Q25. State the Master theorem and show how to apply it. `[Senior]`
For recurrences of the form **`T(n) = a·T(n/b) + f(n)`** with `a ≥ 1`, `b > 1`:
- `a` = number of subproblems, `n/b` = size of each, `f(n)` = work to split and combine.
- Compare `f(n)` with **`n^(log_b a)`** (the total work at the leaves: there are `a^(log_b n) = n^(log_b a)` leaves).

| Case | Condition | Result | Intuition |
|---|---|---|---|
| **1** | `f(n) = O(n^(log_b a − ε))` for some `ε > 0` | `T(n) = Θ(n^(log_b a))` | Leaves dominate |
| **2** | `f(n) = Θ(n^(log_b a))` | `T(n) = Θ(n^(log_b a) · log n)` | Equal work on every level |
| **3** | `f(n) = Ω(n^(log_b a + ε))` and `a·f(n/b) ≤ k·f(n)` for some `k < 1` | `T(n) = Θ(f(n))` | Root dominates |

(Extended case 2: if `f(n) = Θ(n^(log_b a) · logᵏ n)`, then `T(n) = Θ(n^(log_b a) · logᵏ⁺¹ n)`.)

**Worked examples:**
| Algorithm | Recurrence | `n^(log_b a)` | Case | Result |
|---|---|---|---|---|
| Binary search | `T(n) = T(n/2) + O(1)` | `n⁰ = 1` | 2 | `O(log n)` |
| Merge sort | `T(n) = 2T(n/2) + O(n)` | `n¹` | 2 | `O(n log n)` |
| Tree traversal (balanced) | `T(n) = 2T(n/2) + O(1)` | `n¹` | 1 | `O(n)` |
| Karatsuba multiplication | `T(n) = 3T(n/2) + O(n)` | `n^1.585` | 1 | `O(n^1.585)` |
| Strassen matrix multiplication | `T(n) = 7T(n/2) + O(n²)` | `n^2.807` | 1 | `O(n^2.807)` |
| Quickselect (good pivots) | `T(n) = T(n/2) + O(n)` | `n⁰ = 1` | 3 | `O(n)` |
| Naive 8-way matrix multiply | `T(n) = 8T(n/2) + O(n²)` | `n³` | 1 | `O(n³)` |

**When it doesn't apply:** subproblems of **unequal** sizes (`T(n) = T(n/3) + T(2n/3) + n`; use a recursion tree → `O(n log n)`), subtract-style recurrences (`T(n) = T(n−1) + …`), or `f(n)` that falls between cases (e.g. `T(n) = 2T(n/2) + n/log n`). The **Akra–Bazzi** theorem generalizes it.

### Q26. How do you solve "subtract-and-conquer" recurrences? `[Senior]`
Unroll them (Master theorem doesn't apply):

| Recurrence | Unrolled | Result | Example |
|---|---|---|---|
| `T(n) = T(n−1) + O(1)` | `c + c + … ` (n times) | `O(n)` | Recursive sum, linked list traversal |
| `T(n) = T(n−1) + O(n)` | `n + (n−1) + … + 1` | `O(n²)` | Recursive selection sort, quicksort worst case |
| `T(n) = T(n−1) + O(log n)` | `log n + log(n−1) + …` = `log(n!)` | `O(n log n)` | Inserting n items into a heap one by one |
| `T(n) = 2T(n−1) + O(1)` | `1 + 2 + 4 + … + 2ⁿ` | `O(2ⁿ)` | Towers of Hanoi, all subsets |
| `T(n) = T(n−1) + T(n−2) + O(1)` | Fibonacci growth | `O(φⁿ)` ≈ `O(1.618ⁿ)` | Naive Fibonacci |
| `T(n) = n·T(n−1) + O(1)` | `n · (n−1) · …` | `O(n!)` | Generating permutations |

```swift
/// Towers of Hanoi: T(n) = 2T(n−1) + 1 = 2ⁿ − 1 moves → O(2ⁿ) time, O(n) stack space
func hanoi(_ n: Int, from: String, to: String, via: String, moves: inout [(String, String)]) {
    guard n > 0 else { return }
    hanoi(n - 1, from: from, to: via, via: to, moves: &moves)
    moves.append((from, to))
    hanoi(n - 1, from: via, to: to, via: from, moves: &moves)
}
```

### Q27. Why is quicksort `O(n log n)` on average but `O(n²)` in the worst case? `[Senior]`
- **Best/average:** pivots split the array roughly in half: `T(n) = 2T(n/2) + O(n)` → `O(n log n)`. Even a consistent **10%/90%** split gives `T(n) = T(n/10) + T(9n/10) + O(n)` → depth `log_{10/9} n` → still `O(n log n)`.
- **Worst:** the pivot is always the smallest or largest element (e.g. first-element pivot on sorted input): `T(n) = T(n−1) + O(n)` → `O(n²)`, with recursion depth `n`.
- Fixes: **random pivot** (expected `O(n log n)` for every input), **median-of-three**, **introsort** (switch to heapsort when recursion gets too deep, guaranteeing `O(n log n)`).
- Space: `O(log n)` stack on average if you recurse into the **smaller** partition first; `O(n)` worst case otherwise.

```swift
/// In-place quicksort with a random pivot (Lomuto partition). Expected O(n log n) time.
func quicksort(_ a: inout [Int], _ low: Int = 0, _ high: Int? = nil) {
    var low = low
    var high = high ?? a.count - 1
    while low < high {
        let p = partition(&a, low, high)
        // Recurse into the smaller side, loop on the larger: stack depth O(log n) guaranteed
        if p - low < high - p {
            quicksort(&a, low, p - 1); low = p + 1
        } else {
            quicksort(&a, p + 1, high); high = p - 1
        }
    }
}

private func partition(_ a: inout [Int], _ low: Int, _ high: Int) -> Int {
    a.swapAt(Int.random(in: low...high), high)          // random pivot moved to the end
    let pivot = a[high]
    var i = low
    for j in low..<high where a[j] < pivot {
        a.swapAt(i, j); i += 1
    }
    a.swapAt(i, high)
    return i
}
```

### Q28. How does memoization change complexity? `[Senior]`
**Rule:** with memoization, time = **number of distinct states × work per state** (ignoring the cache lookup cost, `O(1)` average for a dictionary).

```swift
// Naive: O(φⁿ) time, O(n) stack space
func fibNaive(_ n: Int) -> Int { n < 2 ? n : fibNaive(n - 1) + fibNaive(n - 2) }

// Memoized (top-down): n + 1 states × O(1) work → O(n) time, O(n) space (memo + stack)
func fibMemo(_ n: Int) -> Int {
    var memo: [Int: Int] = [:]
    func go(_ k: Int) -> Int {
        if k < 2 { return k }
        if let cached = memo[k] { return cached }
        let value = go(k - 1) + go(k - 2)
        memo[k] = value
        return value
    }
    return go(n)
}

// Bottom-up with two variables: O(n) time, O(1) space
func fibIterative(_ n: Int) -> Int {
    var (a, b) = (0, 1)
    for _ in 0..<n { (a, b) = (b, a + b) }
    return a
}
```
(Fibonacci overflows `Int` after `n = 92`; fine for complexity discussion. There's also an `O(log n)` method with matrix exponentiation.)

Apply the rule to classic DP problems:
| Problem | States | Work per state | Time | Space |
|---|---|---|---|---|
| Climbing stairs / Fibonacci | `n` | `O(1)` | `O(n)` | `O(1)` with rolling variables |
| Longest common subsequence (`m`, `n`) | `m·n` | `O(1)` | `O(m·n)` | `O(m·n)`, or `O(min(m, n))` with two rows |
| 0/1 knapsack (`n` items, capacity `W`) | `n·W` | `O(1)` | `O(n·W)` (pseudo-polynomial, Q62) | `O(W)` with one row |
| Longest increasing subsequence (simple DP) | `n` | `O(n)` | `O(n²)` | `O(n)` |
| LIS with patience sorting + binary search | `n` | `O(log n)` | `O(n log n)` | `O(n)` |
| Edit distance | `m·n` | `O(1)` | `O(m·n)` | `O(min(m, n))` |
| Matrix chain multiplication | `n²` | `O(n)` | `O(n³)` | `O(n²)` |

### Q29. What's the complexity of backtracking algorithms? `[Lead/Expert]`
Backtracking explores a **tree of choices**; the cost is roughly **(number of nodes in the search tree) × (work per node)**. Pruning reduces the node count, but the worst-case bound usually stays exponential.

```swift
/// All permutations: n! leaves, each copied in O(n) → O(n · n!) time; O(n) recursion depth
func permutations(_ items: [Int]) -> [[Int]] {
    var result: [[Int]] = []
    var current: [Int] = []
    var used = [Bool](repeating: false, count: items.count)

    func backtrack() {
        if current.count == items.count { result.append(current); return }   // O(n) copy
        for i in items.indices where !used[i] {
            used[i] = true; current.append(items[i])
            backtrack()
            current.removeLast(); used[i] = false
        }
    }
    backtrack()
    return result
}
```
| Problem | Search space | Typical bound |
|---|---|---|
| Subsets | Each item in/out | `O(n · 2ⁿ)` |
| Permutations | `n!` orderings | `O(n · n!)` |
| N-Queens | ≤ `n!` placements (one per row, distinct columns) | `O(n!)` worst case; pruning makes it far faster in practice |
| Sudoku | ≤ `9^(empty cells)` | Exponential; constraint propagation prunes heavily |
| Word search in a grid (`m×n`, word length `L`) | Each cell × 4 then 3 directions per step | `O(m · n · 3^L)` |
| Combination sum (target `T`, smallest candidate `m`) | Branching factor `k` candidates, depth `T/m` | `O(k^(T/m))` |

### Q30. What's the complexity of recursive tree and graph traversals? `[Fundamental]`
```swift
final class TreeNode {
    var value: Int
    var left: TreeNode?
    var right: TreeNode?
    init(_ value: Int, left: TreeNode? = nil, right: TreeNode? = nil) {
        self.value = value; self.left = left; self.right = right
    }
}

func height(_ node: TreeNode?) -> Int {
    guard let node else { return 0 }
    return 1 + max(height(node.left), height(node.right))
}
```
- Each node is visited **once** with `O(1)` work → **`O(n)` time**, regardless of shape.
- Space = recursion depth = **height `h`**: `O(log n)` for a balanced tree, `O(n)` for a degenerate (linked-list-shaped) tree.
- Graphs: DFS/BFS visit each vertex once and each edge once (twice for undirected) → **`O(V + E)`** with an adjacency list; `O(V²)` with an adjacency matrix (checking all possible neighbors per vertex).

**Trap:** calling `height` from inside another recursive function on every node (e.g. a naive "is balanced?" check) makes it `O(n log n)` on balanced trees and `O(n²)` on skewed ones. Return heights and results together to stay `O(n)`.

```swift
/// O(n): one pass returns both "balanced?" and height (−1 marks unbalanced)
func isBalanced(_ root: TreeNode?) -> Bool {
    func check(_ node: TreeNode?) -> Int {
        guard let node else { return 0 }
        let l = check(node.left);  if l < 0 { return -1 }
        let r = check(node.right); if r < 0 { return -1 }
        return abs(l - r) > 1 ? -1 : 1 + max(l, r)
    }
    return check(root) >= 0
}
```

### Q31. How do you analyze divide and conquer with uneven or overlapping work? `[Lead/Expert]`
- **Uneven splits:** `T(n) = T(n/3) + T(2n/3) + n`. Recursion tree: each level does at most `n` work; the longest path follows the `2n/3` branch, depth `log_{3/2} n`. Total `O(n log n)`.
- **Median of medians (deterministic selection):** `T(n) = T(n/5) + T(7n/10) + O(n)`. Since `1/5 + 7/10 = 9/10 < 1`, the work shrinks geometrically per level → **`O(n)`**.
- **Rule of thumb:** if the subproblem sizes sum to **less than** `n` (fraction < 1) and the extra work is linear, the total is `O(n)`; if they sum to **exactly** `n`, you get `O(n log n)`; if **more**, it grows faster.

### Q32. What is the complexity of binary search, and what are its variants? `[Fundamental]`
```swift
/// First index i such that a[i] >= target (lower bound). O(log n) time, O(1) space.
func lowerBound(_ a: [Int], _ target: Int) -> Int {
    var low = 0, high = a.count                   // search in [low, high)
    while low < high {
        let mid = low + (high - low) / 2         // avoids overflow of (low + high)
        if a[mid] < target { low = mid + 1 } else { high = mid }
    }
    return low
}
```
- Each iteration halves the range: `T(n) = T(n/2) + O(1)` → **`O(log n)`**; iterative version uses `O(1)` space (a recursive one uses `O(log n)` stack).
- Requires **random access** (`O(1)` indexing): on a linked list, finding the middle is `O(n)`, making binary search pointless.
- **Binary search on the answer:** when the answer is a number in `[lo, hi]` and "is `x` feasible?" is monotonic, binary search the answer: total `O(log(range) × cost of the feasibility check)`. Example: minimum ship capacity to deliver packages in `D` days → `O(n · log(sum of weights))`.

## 4. Space Complexity

### Q33. What is space complexity, and what's the difference between total and auxiliary space? `[Fundamental]`
- **Space complexity**: how much memory the algorithm needs as a function of input size.
- **Auxiliary (extra) space**: memory used **beyond the input** (temporary arrays, hash maps, recursion stack). Interviews usually mean this.
- **Total space**: input + auxiliary.
- Say which one you mean: "`O(n)` total, `O(1)` auxiliary."
- Also count: **recursion stack**, **output** (often excluded if it's required by the problem; say so), and **hidden copies** (Q37).

| Algorithm | Auxiliary space |
|---|---|
| Sum of an array (loop) | `O(1)` |
| Reverse an array in place | `O(1)` |
| Merge sort (array) | `O(n)` for the merge buffer + `O(log n)` stack |
| Heapsort | `O(1)` |
| Quicksort (in place) | `O(log n)` expected stack (`O(n)` worst without the smaller-side trick) |
| BFS | `O(V)` for the queue and visited set |
| DFS (recursive) | `O(V)` visited + `O(depth)` stack |
| Memoized DP with `k` states | `O(k)` |

### Q34. How do you calculate the space used by recursion? `[Fundamental]`
- Each active call has a **stack frame** (parameters, locals, return address). Space = **maximum depth** of the recursion (not the total number of calls) × frame size.
- Naive Fibonacci makes `O(2ⁿ)` calls but the deepest chain is `n` → **`O(n)` space**: at any moment only one path from the root is on the stack.
- Merge sort: depth `O(log n)` for the stack, but the merge buffers add `O(n)`.
- Binary tree DFS: `O(h)` where `h` is the height.

### Q35. Does Swift optimize tail recursion? `[Senior]`
- A **tail call** is a call that is the last action of a function (`return f(x)` with nothing left to do). Some languages guarantee **tail-call optimization** (TCO), reusing the frame so recursion uses `O(1)` stack.
- **Swift does not guarantee TCO.** The optimizer may do it in Release builds, but not in Debug builds, and ARC/`defer` cleanup work often prevents it. Deep recursion can **overflow the stack** (512 KB on secondary threads, 1 MB on the main thread on iOS).
- For depth that grows with input size (linked lists, skewed trees, large `n`), prefer **iteration** or an explicit stack.

```swift
// Recursive: O(n) stack depth; may crash for very long lists
func lengthRecursive(_ node: ListNode?) -> Int {
    guard let node else { return 0 }
    return 1 + lengthRecursive(node.next)        // not even a tail call: the addition happens after
}

// Iterative: O(1) space
func lengthIterative(_ head: ListNode?) -> Int {
    var count = 0, node = head
    while let current = node { count += 1; node = current.next }
    return count
}

final class ListNode {
    var value: Int
    var next: ListNode?
    init(_ value: Int, next: ListNode? = nil) { self.value = value; self.next = next }
}
```
(Bonus Swift trap: releasing a very long linked list of class nodes can itself overflow the stack, because each node's `deinit` releases the next one recursively. Break the chain iteratively in `deinit` for huge lists.)

### Q36. What does "in place" mean, and is it always `O(1)` space? `[Senior]`
- **In place**: the algorithm transforms the input using only a small amount of extra memory, typically `O(1)` or `O(log n)`.
- Quicksort is called in-place although it uses `O(log n)` stack; heapsort is truly `O(1)`.
- In Swift, `inout` parameters and `mutating` methods (`sort()`, `reverse()`, `swapAt`) operate in place **if the storage is uniquely referenced**; otherwise copy-on-write makes a full `O(n)` copy first (Q37).

```swift
/// Reverse in place: O(n) time, O(1) auxiliary space
func reverseInPlace(_ a: inout [Int]) {
    var i = 0, j = a.count - 1
    while i < j { a.swapAt(i, j); i += 1; j -= 1 }
}
```

### Q37. How does Swift's copy-on-write affect time and space complexity? `[Senior]`
- `Array`, `Dictionary`, `Set` and `String` are value types backed by shared buffers. **Copying** the value is `O(1)` (it shares the buffer); the **first mutation** of a shared buffer triggers an `O(n)` copy.
- This can silently turn an `O(1)` operation into `O(n)` and an `O(n)` loop into `O(n²)`:

```swift
var history: [[Int]] = []
var current: [Int] = []
for x in input {
    current.append(x)            // normally amortized O(1)…
    history.append(current)      // …but `history` now shares current's buffer,
}                                 // so the NEXT append to `current` copies it: O(k) each time → O(n²) total
```
- Here the `O(n²)` is real anyway (storing `n` prefixes needs `O(n²)` space), but the same effect causes accidental quadratic behavior when you keep a reference "just for later".
- Other hidden copies: passing an array to a function that mutates a **copy** of it; capturing an array in a closure and then mutating it; `ArraySlice` → `Array(slice)` conversions (`O(k)`); storing a struct containing an array in two places then mutating one.
- `isKnownUniquelyReferenced(&object)` is how custom COW types decide whether to copy.

### Q38. What's the space complexity of slicing and substrings in Swift? `[Senior]`
- `array[2..<10]` returns an **`ArraySlice`** that **shares** the original storage: `O(1)` time and space to create. But it **keeps the whole original buffer alive** as long as the slice exists (a memory "leak" pattern if you keep a small slice of a huge array).
- `Array(slice)` copies → `O(k)` time and space.
- `Substring` works the same way for `String`: `O(1)` to create, shares storage, keeps the original alive; `String(substring)` copies.
- Indices of a slice are the **original** indices (`slice.startIndex` may be 2, not 0): a classic bug in recursive algorithms that pass slices.

```swift
// Recursive binary search with slices: O(log n) time, no copying (slices share storage)
func contains(_ a: ArraySlice<Int>, _ target: Int) -> Bool {
    guard !a.isEmpty else { return false }
    let mid = a.startIndex + a.count / 2           // NOT a.count / 2: slices keep original indices
    if a[mid] == target { return true }
    return a[mid] < target ? contains(a[(mid + 1)...], target) : contains(a[..<mid], target)
}

// ❌ Same algorithm with Array(...) conversions: each level copies half → n/2 + n/4 + … = O(n) time
```

### Q39. What are space-time trade-offs? Give examples. `[Senior]`
| Technique | Extra space | Time saved |
|---|---|---|
| Hash set for lookups instead of linear search | `O(n)` | `O(n)` → `O(1)` per lookup (`O(n²)` → `O(n)` overall) |
| Memoization / DP table | `O(states)` | Exponential → polynomial |
| Prefix sums | `O(n)` | Range sum queries `O(n)` → `O(1)` |
| Precomputed lookup tables (e.g. bit counts per byte) | `O(256)` | Per-query work drops to a table read |
| Caching (LRU) | `O(capacity)` | Repeated work avoided |
| Indexes in a database | Disk space | Queries `O(n)` → `O(log n)` |
| Sorting a copy to keep the original | `O(n)` | — (pays space to keep input unmodified) |
| Two rows instead of a full DP table | Saves `O(m·n)` → `O(n)` | Same time, but can't reconstruct the path without extra work |

On iOS, memory is constrained (jetsam limits), so the "free" space side of a trade-off isn't always free: an `O(n)` cache of decoded images can kill the app.

### Q40. How do you reduce space in dynamic programming? `[Senior]`
If each row of the DP table depends only on the **previous row**, keep **two rows** (or one, updated in the right order).

```swift
/// Edit distance: O(m·n) time, O(min(m, n)) space
func editDistance(_ s: String, _ t: String) -> Int {
    var a = Array(s), b = Array(t)
    if a.count < b.count { swap(&a, &b) }         // make b the shorter one: row length = min(m, n) + 1
    if b.isEmpty { return a.count }               // also covers both empty
    var previous = Array(0...b.count)             // distances from "" to prefixes of b
    var current = [Int](repeating: 0, count: b.count + 1)
    for i in 1...a.count {
        current[0] = i
        for j in 1...b.count {
            current[j] = a[i - 1] == b[j - 1]
                ? previous[j - 1]
                : 1 + min(previous[j - 1], previous[j], current[j - 1])
        }
        swap(&previous, &current)
    }
    return previous[b.count]
}
```
```swift
/// 0/1 knapsack: O(n·W) time, O(W) space (iterate capacity DOWNWARD so each item is used once)
func knapsack(weights: [Int], values: [Int], capacity: Int) -> Int {
    var best = [Int](repeating: 0, count: capacity + 1)
    for (w, v) in zip(weights, values) where w <= capacity {
        for c in stride(from: capacity, through: w, by: -1) {
            best[c] = max(best[c], best[c - w] + v)
        }
    }
    return best[capacity]
}
```

## 5. Amortized Analysis

### Q41. What is amortized complexity, and how is it different from average case? `[Senior]`
- **Amortized cost** = total cost of a **sequence** of `m` operations ÷ `m`, in the **worst case** over all sequences. Individual operations can be expensive, but they're rare enough that the average **per operation** is small.
- **No probability** is involved: it's a guarantee for every sequence.
- **Average case** is about random **inputs**; **expected** is about random **choices** inside the algorithm.

| Term | "On average over…" | Example |
|---|---|---|
| Amortized | A sequence of operations (deterministic) | `Array.append`: amortized `O(1)` |
| Average case | Random inputs | Quicksort with fixed pivot on random arrays: `O(n log n)` |
| Expected | The algorithm's random choices | Randomized quicksort: expected `O(n log n)` on **any** input |

**Interview line:** "Append is amortized O(1): an individual append can be O(n) when the buffer grows, but n appends cost O(n) in total."

### Q42. Why is `Array.append` amortized `O(1)`? `[Senior]`
When the buffer is full, Swift allocates a **larger buffer** (roughly **double** the capacity) and copies the elements.

**Aggregate method:** appending `n` elements, starting from capacity 1:
```
Copies at each growth: 1 + 2 + 4 + 8 + … + n/2 < n
Writes of new elements: n
Total work < 2n  →  O(n) for n appends  →  O(1) amortized per append
```
**Why doubling (geometric growth) matters:** if the capacity grew by a **constant** amount (+10 each time), you'd copy `10 + 20 + 30 + … + n ≈ n²/20` elements → `O(n)` amortized per append, `O(n²)` total.

```swift
var numbers: [Int] = []
numbers.reserveCapacity(10_000)    // one allocation up front: no regrowth copies at all
for i in 0..<10_000 { numbers.append(i) }
print(numbers.capacity >= 10_000)  // true
```
- `reserveCapacity` helps when you know the size (avoids `log n` reallocations and copies), but calling it **repeatedly** with slightly larger sizes can defeat the geometric growth and cause **quadratic** behavior.
- `removeLast()` is `O(1)`; Swift doesn't shrink the buffer automatically on removal (`removeAll(keepingCapacity:)` makes the choice explicit).

### Q43. What are the accounting and potential methods? `[Lead/Expert]`
Two formal ways to prove amortized bounds:
- **Accounting (banker's) method:** charge each cheap operation a little **extra** and save it as "credit"; expensive operations spend the saved credit. If credit never goes negative, the charged amount is the amortized cost.
- **Potential method:** define a potential function `Φ` (stored-up work) on the data structure's state; amortized cost = actual cost + `ΔΦ`. If `Φ` starts at 0 and never goes negative, the total amortized cost bounds the total actual cost.

**Example: binary counter increment.** Incrementing flips the trailing 1s to 0 and one 0 to 1. One increment can flip `log n` bits, but:
- Bit 0 flips every increment, bit 1 every 2nd, bit 2 every 4th… → total flips for `n` increments `< n + n/2 + n/4 + … < 2n` → **amortized `O(1)`**.
- Accounting view: charge 2 per increment: 1 to set a bit to 1, 1 saved on that bit to pay for resetting it to 0 later.

**Example: stack with `multipop(k)`.** A single `multipop` can pop `n` items, but each item is popped at most once after being pushed, so `n` operations cost `O(n)` total → amortized `O(1)` each.

### Q44. What's the real complexity of hash table operations? `[Senior]`
| Operation | Average / expected | Worst case |
|---|---|---|
| Lookup, insert, remove | `O(1)` | `O(n)` (all keys collide) |
| Insert causing a resize | `O(n)` for that insert | — |
| Insert, amortized over many | `O(1)` | — |
| Iterate all entries | `O(capacity)` ≈ `O(n)` | — |

- `O(1)` assumes a **good hash function** that spreads keys evenly and a bounded **load factor** (the table grows, e.g. doubles, when it gets too full; rehashing is amortized like `Array.append`).
- Each lookup also **hashes the key**: `O(1)` for an `Int`, but `O(L)` for a `String` of length `L`, and equality checks on collisions are `O(L)` too. So a dictionary keyed by long strings is `O(L)` per lookup.
- **Hash flooding**: attackers send keys that collide on purpose to force `O(n)` per operation. Swift's `Hasher` uses **per-process random seeding** to make this hard.
- A broken `Hashable` conformance (e.g. `hash(into:)` that hashes nothing) makes every key collide → silent `O(n)` lookups.

```swift
struct BadKey: Hashable {
    let id: Int
    func hash(into hasher: inout Hasher) { }   // ❌ every BadKey hashes the same → O(n) lookups
}
struct GoodKey: Hashable { let id: Int }        // ✅ synthesized conformance hashes `id`
```

### Q45. Give two more data structures with good amortized bounds. `[Lead/Expert]`
**Queue from two stacks:** each element is moved from `inbox` to `outbox` **at most once** → amortized `O(1)` per operation.

```swift
struct TwoStackQueue<Element> {
    private var inbox: [Element] = []
    private var outbox: [Element] = []

    mutating func enqueue(_ e: Element) { inbox.append(e) }            // O(1) amortized

    mutating func dequeue() -> Element? {
        if outbox.isEmpty {                                           // occasionally O(n)…
            while let e = inbox.popLast() { outbox.append(e) }
        }
        return outbox.popLast()                                       // …but O(1) amortized
    }
}
```

**Union-Find (disjoint set) with path compression and union by rank:** `m` operations on `n` elements cost `O(m · α(n))`, where `α` is the inverse Ackermann function (≤ 4 for any practical `n`), effectively constant.

```swift
struct UnionFind {
    private var parent: [Int]
    private var rank: [Int]

    init(count: Int) {
        parent = Array(0..<count)
        rank = [Int](repeating: 0, count: count)
    }

    mutating func find(_ x: Int) -> Int {
        var root = x
        while parent[root] != root { root = parent[root] }
        var node = x
        while parent[node] != root {                 // path compression: point everything at the root
            let next = parent[node]; parent[node] = root; node = next
        }
        return root
    }

    @discardableResult
    mutating func union(_ a: Int, _ b: Int) -> Bool {
        var (ra, rb) = (find(a), find(b))
        guard ra != rb else { return false }
        if rank[ra] < rank[rb] { swap(&ra, &rb) }     // attach the shorter tree under the taller
        parent[rb] = ra
        if rank[ra] == rank[rb] { rank[ra] += 1 }
        return true
    }
}
```
Used in Kruskal's minimum spanning tree (`O(E log E)`, dominated by sorting edges), connected components, and cycle detection.

### Q48. Why is `String.count` `O(n)`, and what does that mean for algorithms? `[Senior]`
- A Swift `Character` is an **extended grapheme cluster**: one user-perceived character can be several Unicode scalars (`"é"` can be 1 or 2 scalars; `"👨‍👩‍👧"` is 5 scalars, 18 UTF-8 bytes, but **one** `Character`).
- So `String` can't know where the `k`-th character is without **walking** from the start:
  - `s.count` → `O(n)`.
  - `s.index(s.startIndex, offsetBy: k)` → `O(k)`.
  - `String` is a `BidirectionalCollection`, **not** a `RandomAccessCollection`.
- `isEmpty` is `O(1)`; `s.utf8.count` is `O(1)` for native Swift strings (UTF-8 storage), but it counts **bytes**, not characters.

```swift
// ❌ O(n²): every iteration computes an index by walking from the start
func isPalindromeSlow(_ s: String) -> Bool {
    for i in 0..<s.count / 2 {                                     // s.count: O(n) (evaluated once here)
        let a = s[s.index(s.startIndex, offsetBy: i)]              // O(i)
        let b = s[s.index(s.endIndex, offsetBy: -(i + 1))]         // O(i)
        if a != b { return false }
    }
    return true
}

// ✅ O(n): walk two indices toward each other
func isPalindrome(_ s: String) -> Bool {
    guard !s.isEmpty else { return true }
    var i = s.startIndex
    var j = s.index(before: s.endIndex)
    while i < j {
        if s[i] != s[j] { return false }
        s.formIndex(after: &i)
        s.formIndex(before: &j)
    }
    return true
}

// ✅ Also O(n): convert once to [Character] for random access (O(n) extra space)
let chars = Array("racecar")       // then chars[i] is O(1)
```
Interview tip: for character-indexed algorithms, say "I'll convert to `Array(s)` (or `Array(s.utf8)` for ASCII input) once, in `O(n)`, to get `O(1)` indexing."

### Q49. Which collection protocols guarantee which complexities? `[Senior]`
| Protocol | Guarantees | Examples |
|---|---|---|
| `Sequence` | Iterate once; nothing about cost or repeatability | `AnyIterator`, `stride` results, `zip` |
| `Collection` | Multi-pass iteration, indices; `count` may be `O(n)` | `Set`, `Dictionary`, `String` |
| `BidirectionalCollection` | Can walk backwards (`index(before:)`); `last` is `O(1)` | `String`, `ReversedCollection` |
| `RandomAccessCollection` | `index(_:offsetBy:)`, `distance`, and `count` are **`O(1)`** | `Array`, `ArraySlice`, `ContiguousArray`, `Range`, `UnsafeBufferPointer` |
| `MutableCollection`, `RangeReplaceableCollection` | Element mutation; insert/remove ranges | `Array`, `String` (range-replaceable but not random access) |

- Generic algorithms adapt: `Collection.count` is `O(1)` on a `RandomAccessCollection` and `O(n)` otherwise. Writing a generic binary search constrained to `RandomAccessCollection` documents the `O(log n)` assumption in the type system.

```swift
extension RandomAccessCollection where Element: Comparable {
    /// O(log n) because index arithmetic is O(1) on random-access collections
    func binarySearch(_ target: Element) -> Index? {
        var low = startIndex, high = endIndex
        while low < high {
            let mid = index(low, offsetBy: distance(from: low, to: high) / 2)
            if self[mid] == target { return mid }
            if self[mid] < target { low = index(after: mid) } else { high = mid }
        }
        return nil
    }
}
```

### Q50. What should you know about sorting in Swift? `[Senior]`
- `sort()` / `sorted()` / `sort(by:)`: **`O(n log n)`** comparisons. Since Swift 5 the implementation is a **stable**, merge-based (Timsort-like) algorithm, which also makes already-sorted or nearly-sorted input fast (close to `O(n)`).
- `sorted()` allocates a new array: `O(n)` extra space. `sort()` sorts in place, but the merge-based algorithm still uses a temporary buffer.
- The **comparison** cost multiplies in: sorting `n` strings of length `L` is `O(n log n · L)`. Expensive key extraction in the closure (e.g. computing `count` of a string, or a date formatter) runs `O(n log n)` times; precompute keys once (`O(n)`) instead:

```swift
// ❌ The key (an O(L) computation) is recomputed in every comparison: O(n log n · L)
let byLength = words.sorted { $0.count < $1.count }

// ✅ Compute each key once: O(n · L) + O(n log n)
let byLengthFast = words
    .map { (word: $0, length: $0.count) }
    .sorted { $0.length < $1.length }
    .map(\.word)
```
- Need only the top `k`? A **heap** gives `O(n log k)` instead of `O(n log n)` (Q93); `min()`/`max()` are `O(n)`.
- Sorting an already sorted array **every time** something is inserted is `O(n log n)` per insert: insert at the binary-searched position instead (`O(log n)` search + `O(n)` shift).

### Q51. How do lazy sequences affect complexity? `[Senior]`
```swift
let numbers = Array(1...1_000_000)

// Eager: filter processes all 1,000,000 elements and allocates an array, THEN takes the first
let firstEven = numbers.filter { $0.isMultiple(of: 2) }.first           // O(n) time, O(n) space

// Lazy: stops at the first match (the 2nd element)
let firstEvenLazy = numbers.lazy.filter { $0.isMultiple(of: 2) }.first  // O(1) here, O(n) worst; O(1) space

// Even simpler and clearer
let firstEvenDirect = numbers.first { $0.isMultiple(of: 2) }
```
- Lazy chains avoid **intermediate arrays** (`map` → `filter` → `map` allocates three arrays eagerly).
- **Pitfall:** a lazy collection **recomputes** on every access/iteration. Iterating a `lazy.map { expensive($0) }` twice runs `expensive` twice per element; indexing into it repeatedly can multiply the cost. Materialize with `Array(...)` if you'll reuse the results.
- `lazy.filter(...).count` is `O(n)` (it must evaluate everything); `lazy.filter(...).first` short-circuits.

### Q52. How do you implement an efficient queue in Swift? `[Senior]`
`Array.removeFirst()` is `O(n)`, so using an array as a queue makes BFS `O(V²)` instead of `O(V + E)`.

| Implementation | Enqueue | Dequeue | Notes |
|---|---|---|---|
| `Array` + `removeFirst()` | `O(1)` amortized | **`O(n)`** | Simple but quadratic overall |
| `Array` + head index | `O(1)` amortized | `O(1)` | Memory grows until you compact (compact when head > half the array) |
| Two stacks (Q45) | `O(1)` amortized | `O(1)` amortized | |
| `Deque` (swift-collections) | `O(1)` amortized | `O(1)` amortized | Ring buffer; also `O(1)` at both ends |

```swift
/// BFS shortest path lengths in an unweighted graph: O(V + E)
func bfsDistances(adjacency: [[Int]], from source: Int) -> [Int?] {
    var distance = [Int?](repeating: nil, count: adjacency.count)
    distance[source] = 0
    var queue = [source]
    var head = 0                                   // dequeue by moving an index: O(1)
    while head < queue.count {
        let node = queue[head]; head += 1
        for neighbor in adjacency[node] where distance[neighbor] == nil {
            distance[neighbor] = distance[node]! + 1
            queue.append(neighbor)
        }
    }
    return distance
}
```
Each vertex is enqueued once (`O(V)`) and each adjacency list is scanned once (`O(E)`) → `O(V + E)` time, `O(V)` space.

### Q58. Why can't comparison-based sorting beat `O(n log n)`, and how do counting and radix sort get around it? `[Lead/Expert]`
**Decision tree argument:**
- A comparison sort can be modeled as a binary tree of comparisons; each leaf is one possible output ordering.
- There are `n!` possible orderings, so the tree needs at least `n!` leaves.
- A binary tree with `n!` leaves has height at least `log₂(n!)`, and `log₂(n!) = Θ(n log n)` (Q7).
- So **some input requires `Ω(n log n)` comparisons** for any comparison sort. Merge sort and heapsort are therefore **asymptotically optimal**.

**Non-comparison sorts** use the **values themselves** (as array indexes or digits), so the bound doesn't apply:

```swift
/// Counting sort for values in 0..<k: O(n + k) time and space, stable when done this way
func countingSort(_ a: [Int], maxValue k: Int) -> [Int] {
    var counts = [Int](repeating: 0, count: k + 1)
    for x in a { counts[x] += 1 }                       // O(n)
    if k > 0 { for v in 1...k { counts[v] += counts[v - 1] } }   // prefix sums: O(k)
    var output = [Int](repeating: 0, count: a.count)
    for x in a.reversed() {                             // reversed keeps equal keys in order (stable)
        counts[x] -= 1
        output[counts[x]] = x
    }
    return output
}
// Example: sorting 1,000,000 ages (0...130): O(n + 131), linear.
```
- Worth it when `k = O(n)`. Sorting 10 numbers in the range `0..<10⁹` with counting sort would be terrible (`O(10⁹)`).
- **Radix sort** applies a stable counting sort per digit: `O(d · (n + b))`; for 32-bit integers with base 256, `d = 4` passes.

## 8. Beyond Big-O: Practical Performance

### Q59. When can an algorithm with worse Big-O be faster in practice? `[Senior]`
- **Small `n`**: `10n²` beats `1000 n log n` until `n` is in the hundreds. That's why real sorts (Timsort, introsort) switch to **insertion sort** for small ranges (~16–64 elements).
- **Constant factors**: memory allocation, ARC retain/release, dynamic dispatch, bounds checks, hashing costs. A dictionary lookup is `O(1)` but much slower than scanning a 5-element array.
- **Cache locality** (Q60): a linear scan over a contiguous array can beat a "faster" pointer-chasing structure.
- **Average vs worst case**: quicksort's `O(n²)` worst case is rare with random pivots, and it's often faster than heapsort's guaranteed `O(n log n)`.
- **Input characteristics**: nearly sorted data makes insertion sort `O(n)`; small value ranges enable counting sort.

**Interview line:** "Big-O tells me how it scales; for the sizes we actually have, I'd measure. With n ≤ 20, the simple linear scan is clearer and probably faster."

### Q60. How does memory layout affect real performance? `[Lead/Expert]`
- CPUs read memory in **cache lines** (64 bytes; 128 bytes on Apple silicon). Accessing contiguous memory uses every byte fetched and lets the hardware **prefetch**.
- Approximate latency: L1 cache ~1 ns, main memory ~100 ns. A cache miss on every access (linked lists, trees of class nodes, dictionaries of objects) can make an `O(n)` traversal 10–100× slower than an array scan of the same `n`.
- Swift specifics:
  - `[Int]`, `[Double]` and arrays of **structs** with trivial fields are stored **contiguously**.
  - Arrays of **class instances** store **references**: iterating touches memory all over the heap (plus retain/release traffic).
  - `ContiguousArray` avoids Objective-C bridging checks for class element types.
- Data-oriented layout: a **struct of arrays** (`xs: [Float]`, `ys: [Float]`) can be faster than an array of structs when you only process one field.

### Q61. How does complexity show up in iOS UI performance? `[Senior]`
- The main thread has **~16.7 ms per frame at 60 Hz** and **~8.3 ms at 120 Hz** (ProMotion) for everything: your code, layout and rendering commits. An `O(n²)` step over 2,000 items (4 million operations) can blow the budget on its own.
- Typical traps:
  - Computing heights/text layout for **all** rows up front instead of lazily.
  - `O(n)` work per cell configuration → `O(n²)` while scrolling (e.g. `items.firstIndex(of:)` inside `cellForRowAt`).
  - Diffing large lists: `UICollectionViewDiffableDataSource` / SwiftUI identity diffing are roughly linear with hashing, but reapplying snapshots for every keystroke over thousands of items adds up; debounce and diff off the main thread where the API allows.
  - Sorting/filtering a large array on every keystroke on the main actor.
- Move heavy `O(n log n)`+ work off the main thread, paginate, precompute, and cache results keyed by input.

### Q62. What are pseudo-polynomial time, P and NP? `[Lead/Expert]`
- **Pseudo-polynomial**: polynomial in the **numeric value** of the input, but exponential in its **size in bits**. 0/1 knapsack's `O(n · W)` looks polynomial, but `W` can be `2^(bits)`; doubling the number of bits of `W` squares the running time. Trial division primality (`O(√n)`) is likewise exponential in the number of digits.
- **P**: problems solvable in polynomial time (sorting, shortest paths, matching).
- **NP**: problems whose solutions can be **verified** in polynomial time (given a route, checking its length is easy).
- **NP-complete**: the hardest problems in NP (SAT, knapsack decision, traveling salesman decision, graph coloring, subset sum); a polynomial algorithm for one would give one for all. Whether **P = NP** is unknown.
- **NP-hard**: at least as hard as NP-complete problems (may not be in NP).
- **What to say in an interview** when a problem is NP-hard: "There's no known polynomial algorithm, so I'd use the constraints: small `n` → exponential search with pruning or bitmask DP (`O(2ⁿ · n²)` TSP for `n ≤ 20`); small numeric values → pseudo-polynomial DP; otherwise approximation algorithms or heuristics (greedy, local search)."

### Q63. How do you guess the target complexity from the input constraints? `[Senior]`
Assuming roughly 10⁸ simple operations per second and a 1–2 second limit:

| Max `n` | Feasible complexity | Typical approach |
|---|---|---|
| ≤ 10–12 | `O(n!)`, `O(n · n!)` | Permutations, brute force |
| ≤ 20–25 | `O(2ⁿ)`, `O(n · 2ⁿ)` | Subsets, bitmask DP, meet in the middle (≤ 40) |
| ≤ 100–500 | `O(n³)` | Floyd–Warshall, interval DP |
| ≤ 2,000–5,000 | `O(n²)` | Pairwise DP, nested loops |
| ≤ 10⁵–10⁶ | `O(n log n)` | Sorting, heaps, binary search, segment trees |
| ≤ 10⁷–10⁸ | `O(n)` | Single pass, two pointers, hashing, prefix sums |
| ≥ 10⁹ (or a single huge number) | `O(log n)`, `O(√n)`, `O(1)` | Binary search on answer, math formula, fast exponentiation |

On a phone's main thread, divide by ~100: you have milliseconds, not seconds.

### Q64. How do you verify complexity empirically? `[Senior]`
- **Doubling experiment**: run with `n`, `2n`, `4n`, `8n` and look at the time ratio when `n` doubles:
  - ~1× → `O(1)` or `O(log n)` (log adds a constant each doubling)
  - ~2× → `O(n)`; slightly more than 2× → `O(n log n)`
  - ~4× → `O(n²)`; ~8× → `O(n³)`
  - Squares → exponential
- On a **log-log plot**, the slope of time vs `n` is the exponent.
- Measure in **Release** builds (`-O`), with warm-up runs, several repetitions, and realistic data; Debug builds can be 10–100× slower and distort constants.

```swift
import Foundation

func measure(_ label: String, sizes: [Int], _ work: (Int) -> Void) {
    let clock = ContinuousClock()
    var previous: Duration?
    for n in sizes {
        let elapsed = clock.measure { work(n) }
        let ratio = previous.map { elapsed / $0 }.map { String(format: "%.1f×", $0) } ?? "-"
        print("\(label) n=\(n): \(elapsed)  (vs previous: \(ratio))")
        previous = elapsed
    }
}

measure("sort", sizes: [100_000, 200_000, 400_000, 800_000]) { n in
    var a = (0..<n).map { _ in Int.random(in: 0..<1_000_000) }
    a.sort()
}
// Expect ratios a little above 2× → consistent with O(n log n)
```
In tests, `XCTest`'s `measure(metrics:)` or a custom Swift Testing benchmark with baselines catches complexity regressions; Instruments' Time Profiler shows where the time goes.

## 9. Discussing Complexity in an Interview

### Q65. How should you present complexity during a coding interview? `[Fundamental]`
1. **Define the variables**: "Let `n` be the number of words and `L` the maximum word length."
2. **State time and space separately**, for the **worst case** unless asked otherwise.
3. **Justify briefly** by pointing at the code: "The outer loop runs `n` times, the dictionary lookup is `O(L)` to hash the key, so `O(n · L)` time."
4. **Mention hidden costs** you considered: hashing strings, copying arrays, recursion stack, sorting.
5. **Mention trade-offs and alternatives**: "We could do it in `O(1)` extra space by sorting first, at `O(n log n)` time."
6. **Don't overclaim**: say "amortized" or "average" when that's what it is.

Example answer:
> "This is `O(n log n)` time because of the sort; the two-pointer pass after it is `O(n)`. Space is `O(n)` for the sorted copy; if we're allowed to sort the input in place, it's `O(1)` extra, ignoring the sort's own buffer."

### Q66. What are the most common optimization patterns, and what do they buy you? `[Senior]`
| Pattern | Typical improvement | Example problem |
|---|---|---|
| Hash set/map for lookups | `O(n²)` → `O(n)` | Two sum, duplicates, anagram groups |
| Sort first, then two pointers / binary search | `O(n²)` → `O(n log n)` | 3-sum (`O(n³)` → `O(n²)`), closest pair in 1D |
| Sliding window | `O(n·k)` or `O(n²)` → `O(n)` | Longest substring without repeats, max sum of size-`k` window |
| Prefix sums (+ hash map) | `O(n)` per query → `O(1)`; subarray sums `O(n²)` → `O(n)` | Range sums, subarray sum equals `k` |
| Heap | `O(n log n)` → `O(n log k)` | Top-`k`, merge `k` sorted lists, running median |
| Monotonic stack/queue | `O(n²)` → `O(n)` | Next greater element, sliding window maximum, largest rectangle in histogram |
| Binary search on the answer | Linear search over answers → `O(log range)` checks | Minimum capacity, Koko eating bananas |
| Memoization / DP | Exponential → polynomial | Fibonacci, coin change, edit distance |
| Greedy (with proof) | Exponential search → `O(n log n)` | Interval scheduling, meeting rooms |
| Union-find | Repeated BFS `O(n·(V+E))` → near `O(1)` per query | Dynamic connectivity, accounts merge |
| Bit manipulation | Extra space → `O(1)` | Single number (XOR), subsets via masks |
| Precomputation / caching | Repeated work removed | Sieve of primes, factorials mod p |

### Q67. How do you answer "Can you do better?" `[Senior]`
- Compute the **Best Conceivable Runtime (BCR)**: what's the minimum any solution must do?
  - You must **read the input**: `Ω(n)` for most array problems.
  - You must **produce the output**: listing all pairs is `Ω(n²)` if there are `n²` of them.
  - Known **lower bounds**: comparison sorting `Ω(n log n)`; searching unsorted data `Ω(n)`.
- If your solution equals the BCR, say so: "This is optimal: any algorithm has to look at every element at least once."
- Otherwise look for: **repeated work** (memoize, precompute), **unnecessary work** (early exit, pruning), **better data structures** (hashing, heaps), **sorted-input structure** (binary search, two pointers), or a **space-for-time trade** (Q39).
- Consider other dimensions if time is optimal: less space, fewer passes, streaming (one pass, `O(1)` memory), parallelism, simpler code.

## 10. "What's the Complexity?" Practice

> Try each one before reading the answer. Assume `n` is the input size, arithmetic is `O(1)`, and `work()` is `O(1)` unless stated.

### Q68. Constant inner loop `[Fundamental]`
```swift
for i in 0..<n {
    for j in 0..<10 {
        work(i, j)
    }
}
```
**Answer:** `O(n)` time, `O(1)` space. The inner loop runs a **constant** 10 times: `10n` → `O(n)`. Nested loops only multiply complexities when **both** depend on the input.

### Q69. Three dependent nested loops `[Senior]`
```swift
for i in 0..<n {
    for j in 0..<i {
        for k in 0..<j {
            work(i, j, k)
        }
    }
}
```
**Answer:** `O(n³)` time. The body runs once for every triple `k < j < i`, which is `C(n, 3) = n(n−1)(n−2)/6` times → `Θ(n³)` (about `n³/6`).

### Q70. Halving outer loop with a full inner loop `[Fundamental]`
```swift
var i = n
while i > 1 {
    for _ in 0..<n { work() }      // always n, not i
    i /= 2
}
```
**Answer:** `O(n log n)`. The outer loop runs `log₂ n` times and the inner loop is always `n`. (Compare Q14, where the inner bound shrank with the outer variable and the total was `O(n)`.)

### Q71. Logarithmic inner loop that depends on `i` `[Senior]`
```swift
for i in 1..<n {
    var j = i
    while j > 0 { j /= 2 }         // about log₂ i iterations
}
```
**Answer:** `O(n log n)`. Total = `log 1 + log 2 + … + log(n−1) = log((n−1)!)` = `Θ(n log n)` (Q7). Half of the `i` values are ≥ `n/2`, each costing at least `log(n/2)`, so the sum is at least `(n/2) · log(n/2)`.

### Q72. A pointer that never resets `[Senior]`
```swift
var j = 0
for i in 0..<n {
    while j < n && a[j] < a[i] * 2 {
        j += 1
    }
    count += j
}
```
**Answer:** `O(n)`. `j` only increases and never exceeds `n`, so the inner `while` body runs **at most `n` times in total**, not per `i`. Total `O(n + n)`. (Amortized/aggregate counting, Q16.)

### Q73. Two recursive calls on halves with `O(1)` work `[Senior]`
```swift
func countNodes(_ low: Int, _ high: Int) -> Int {
    if low >= high { return 0 }
    let mid = (low + high) / 2
    return 1 + countNodes(low, mid) + countNodes(mid + 1, high)
}
```
**Answer:** `O(n)` time, `O(log n)` space. `T(n) = 2T(n/2) + O(1)`: Master theorem case 1, `n^(log₂ 2) = n` dominates → `Θ(n)`. Depth is `log n`.

### Q74. Two recursive calls on halves with linear work `[Senior]`
```swift
func process(_ a: ArraySlice<Int>) {
    guard a.count > 1 else { return }
    for x in a { work(x) }                      // O(n) at this level
    let mid = a.startIndex + a.count / 2
    process(a[..<mid])
    process(a[mid...])
}
```
**Answer:** `O(n log n)` time, `O(log n)` space (slices share storage). `T(n) = 2T(n/2) + O(n)`: Master theorem case 2. Same shape as merge sort.

### Q75. Two recursive calls on `n − 1` `[Senior]`
```swift
func f(_ n: Int) -> Int {
    if n <= 0 { return 1 }
    return f(n - 1) + f(n - 1)
}
```
**Answer:** `O(2ⁿ)` time, `O(n)` space. `T(n) = 2T(n−1) + O(1)` → `2ⁿ⁺¹ − 1` calls. Only one chain of `n` frames is on the stack at once. **Fix:** compute `f(n − 1)` once and double it → `T(n) = T(n−1) + O(1)` → `O(n)` (or just `1 << n`).

### Q76. Fast power: one call vs two calls `[Senior]`
```swift
func powerA(_ x: Double, _ n: Int) -> Double {
    if n == 0 { return 1 }
    let half = powerA(x, n / 2)
    return n.isMultiple(of: 2) ? half * half : half * half * x
}

func powerB(_ x: Double, _ n: Int) -> Double {
    if n == 0 { return 1 }
    return n.isMultiple(of: 2)
        ? powerB(x, n / 2) * powerB(x, n / 2)
        : powerB(x, n / 2) * powerB(x, n / 2) * x
}
```
**Answer:**
- `powerA`: `T(n) = T(n/2) + O(1)` → **`O(log n)`** time, `O(log n)` stack.
- `powerB`: `T(n) = 2T(n/2) + O(1)` → **`O(n)`** time (Master case 1): the duplicated call throws away the whole benefit. Storing a repeated subresult in a variable is the simplest form of memoization.

### Q77. Pairwise string comparison `[Senior]`
```swift
func countEqualPairs(_ words: [String]) -> Int {
    var count = 0
    for i in words.indices {
        for j in words.indices where j > i {
            if words[i] == words[j] { count += 1 }
        }
    }
    return count
}
```
**Answer:** `O(n² · L)` time, where `L` is the maximum word length (string equality compares characters). `O(1)` space. Better: count occurrences with a dictionary (`O(n · L)`), then add `c·(c−1)/2` for each count `c`.

### Q78. Prepending to a string `[Senior]`
```swift
func reversedString(_ s: String) -> String {
    var result = ""
    for ch in s {
        result = String(ch) + result         // builds a brand-new string each time
    }
    return result
}
```
**Answer:** `O(n²)` time. Each `String(ch) + result` creates a new string by copying the current `result` (length `0, 1, 2, …, n−1`) → `n(n−1)/2` character copies. **Fix:** `String(s.reversed())` → `O(n)`.

### Q79. Array as a queue in BFS `[Senior]`

var queue = [start]
var visited: Set<Int> = [start]

### Q80. Sorting inside a loop `[Fundamental]`

for query in queries {                          // q queries

**Answer:** `O(q · n log n)`. The sort doesn't depend on the query: hoist it out → `O(n log n + q log n)`.

### Q81. Grouping anagrams `[Senior]`

func groupAnagrams(_ words: [String]) -> [[String]] {
    var groups: [String: [String]] = [:]
    for word in words {

**Answer:** `O(n · L log L)` time, `O(n · L)` space. Alternative key: a 26-letter count signature (for lowercase ASCII) gives `O(n · L)`.

### Q82. Searching each element of one array in another `[Fundamental]`
```swift
let sortedB = b.sorted()                        // O(m log m)
for x in a {                                    // n times
    if binarySearch(sortedB, x) { found += 1 }  // O(log m)
}
```
**Answer:** `O(m log m + n log m)` = `O((n + m) log m)` time, `O(m)` space. A `Set(b)` gives `O(n + m)` average; sorting both and using two pointers gives `O(n log n + m log m)` with `O(1)` extra space if sorting in place is allowed.

### Q83. Grid paths with memoization `[Senior]`
```swift
func uniquePaths(_ rows: Int, _ cols: Int) -> Int {
    var memo: [Int: Int] = [:]
    func paths(_ r: Int, _ c: Int) -> Int {
        if r == rows - 1 || c == cols - 1 { return 1 }
        let key = r * cols + c
        if let cached = memo[key] { return cached }
        let result = paths(r + 1, c) + paths(r, c + 1)
        memo[key] = result
        return result
    }
    return paths(0, 0)
}
```
**Answer:** `O(rows · cols)` time and space (states × `O(1)` work; recursion depth `rows + cols`). Without the memo: `O(2^(rows + cols))`. A bottom-up version needs only one row: `O(cols)` space. (There's also a closed form, `C(rows + cols − 2, rows − 1)`.)

### Q84. Generating balanced parentheses `[Lead/Expert]`
```swift
func generateParentheses(_ n: Int) -> [String] {
    var result: [String] = []
    func build(_ current: String, open: Int, close: Int) {
        if current.count == 2 * n { result.append(current); return }
        if open < n { build(current + "(", open: open + 1, close: close) }
        if close < open { build(current + ")", open: open, close: close + 1) }
    }
    build("", open: 0, close: 0)
    return result
}
```
**Answer:** the number of valid strings is the **Catalan number** `Cₙ ≈ 4ⁿ / (n^(3/2) √π)`. Each result has length `2n`, so time is about **`O(4ⁿ / √n)`** (output size × length), and space is `O(n)` for the recursion plus the output. Interview-acceptable simplification: "exponential, bounded by `O(2²ⁿ)` = `O(4ⁿ)`; tighter bound is the Catalan number." (Note: `current.count` is `O(n)` here; tracking the length in a parameter avoids it.)

### Q85. Merging `k` sorted arrays `[Senior]`
```swift
// Approach A: merge them one by one into a growing result
var result: [Int] = []
for list in lists { result = merge(result, list) }      // merge is O(|result| + |list|)

// Approach B: a min-heap holding the current head of each list
```
**Answer:** with `N` total elements across `k` lists of about `N/k` each:
- **A:** merging copies the growing result every time: `N/k + 2N/k + … + kN/k` ≈ `O(N · k)`.
- **B:** each of the `N` elements is pushed and popped once from a heap of size `k` → **`O(N log k)`** time, `O(k)` extra space (plus output).
- **C (divide and conquer):** merge pairs of lists in rounds: `log k` rounds × `O(N)` per round → also `O(N log k)`.

### Q86. Striding loop `[Fundamental]`
```swift
for i in stride(from: 0, to: n, by: k) {
    for j in i..<min(i + k, n) {
        work(j)
    }
}
```
**Answer:** `O(n)`. The outer loop runs `n/k` times and the inner loop `k` times: `n/k × k = n`. Each element is processed exactly once (this is chunked processing).

### Q87. Recursion that copies the array `[Senior]`
```swift
func sumRecursive(_ a: [Int]) -> Int {
    guard let first = a.first else { return 0 }
    return first + sumRecursive(Array(a.dropFirst()))      // copies n−1 elements
}
```
**Answer:** `O(n²)` time and **`O(n²)` total memory allocated** (`n−1 + n−2 + … ` copies), `O(n)` stack depth (with up to `O(n²)` alive at once if the optimizer can't free them early). Pass an index or an `ArraySlice` (`a.dropFirst()` without `Array(...)`) to make it `O(n)`; or just `a.reduce(0, +)`.

### Q88. Flood fill on a grid `[Senior]`
```swift
func fill(_ grid: inout [[Int]], _ r: Int, _ c: Int, from old: Int, to new: Int) {
    guard grid.indices.contains(r), grid[r].indices.contains(c),
          grid[r][c] == old, old != new else { return }
    grid[r][c] = new
    fill(&grid, r + 1, c, from: old, to: new)
    fill(&grid, r - 1, c, from: old, to: new)
    fill(&grid, r, c + 1, from: old, to: new)
    fill(&grid, r, c - 1, from: old, to: new)
}
```
**Answer:** `O(R · C)` time: each cell is recolored at most once and each recolored cell makes 4 calls. **Space `O(R · C)`** in the worst case for the recursion stack (a snake-shaped region forces a path through every cell), which can **overflow the stack** on a large image. Use BFS with an explicit queue (`O(R · C)` heap memory instead of stack) for big grids.

### Q89. Nested loops over a dictionary and an array `[Fundamental]`
```swift
for (userID, purchases) in purchasesByUser {         // U users
    for p in purchases {                             // total P purchases across all users
        totals[userID, default: 0] += p.amount
    }
}
```
**Answer:** `O(U + P)`, **not** `O(U · P)`: the inner loop's iterations across **all** outer iterations add up to the total number of purchases. Always ask "how many times does the innermost line run **in total**?"

## 11. From Brute Force to Optimal

### Q90. Contains duplicate `[Fundamental]`
| Approach | Time | Space |
|---|---|---|
| Compare every pair | `O(n²)` | `O(1)` |
| Sort, then compare neighbors | `O(n log n)` | `O(1)` extra if sorting in place (else `O(n)`) |
| Hash set | `O(n)` average | `O(n)` |

```swift
func containsDuplicate(_ nums: [Int]) -> Bool {
    var seen = Set<Int>()
    seen.reserveCapacity(nums.count)
    for x in nums {
        if !seen.insert(x).inserted { return true }    // early exit on the first repeat
    }
    return false
}
```
**Discussion point:** the sort-based version wins when memory is tight; the set wins on time.

### Q91. Two sum `[Fundamental]`
Find indices of two numbers that add up to `target`.

```swift
// Brute force: O(n²) time, O(1) space
func twoSumBrute(_ nums: [Int], _ target: Int) -> (Int, Int)? {
    for i in nums.indices {
        for j in (i + 1)..<nums.count where nums[i] + nums[j] == target { return (i, j) }
    }
    return nil
}

// One-pass hash map: O(n) time, O(n) space
func twoSum(_ nums: [Int], _ target: Int) -> (Int, Int)? {
    var indexByValue: [Int: Int] = [:]
    for (i, x) in nums.enumerated() {
        if let j = indexByValue[target - x] { return (j, i) }
        indexByValue[x] = i
    }
    return nil
}
```
If the array is **already sorted**: two pointers from both ends → `O(n)` time, `O(1)` space.

### Q92. Maximum subarray sum `[Senior]`
| Approach | Time | Space |
|---|---|---|
| Every subarray, sum each from scratch | `O(n³)` | `O(1)` |
| Every subarray with a running sum | `O(n²)` | `O(1)` |
| Divide and conquer | `O(n log n)` | `O(log n)` |
| **Kadane's algorithm** | **`O(n)`** | **`O(1)`** |

```swift
/// Kadane: the best subarray ending at i either extends the best ending at i−1 or starts fresh at i
func maxSubarraySum(_ nums: [Int]) -> Int? {
    guard var bestEndingHere = nums.first else { return nil }
    var best = bestEndingHere
    for x in nums.dropFirst() {
        bestEndingHere = max(x, bestEndingHere + x)
        best = max(best, bestEndingHere)
    }
    return best
}
```

### Q93. Top `k` most frequent elements `[Senior]`
| Approach | Time | Space |
|---|---|---|
| Count, then sort all distinct values by count | `O(n + u log u)` (`u` = distinct values) | `O(u)` |
| Count, then a min-heap of size `k` | `O(n + u log k)` | `O(u + k)` |
| Count, then **bucket by frequency** | `O(n)` | `O(n)` |

```swift
func topKFrequent(_ nums: [Int], _ k: Int) -> [Int] {
    var counts: [Int: Int] = [:]
    for x in nums { counts[x, default: 0] += 1 }                    // O(n)

    // buckets[f] = values that appear exactly f times; f ≤ n
    var buckets = [[Int]](repeating: [], count: nums.count + 1)
    for (value, frequency) in counts { buckets[frequency].append(value) }   // O(u)

    var result: [Int] = []
    for frequency in stride(from: nums.count, through: 1, by: -1) {   // O(n)
        for value in buckets[frequency] {
            result.append(value)
            if result.count == k { return result }
        }
    }
    return result
}
```
The heap approach is better when `k` is small and you're **streaming** values (you can't keep everything). Swift has no heap in the standard library; `Heap` is in the swift-collections package.

### Q94. Count subarrays with sum equal to `k` `[Senior]`
```swift
// Brute force with running sums: O(n²) time, O(1) space
func subarraySumBrute(_ nums: [Int], _ k: Int) -> Int {
    var count = 0
    for start in nums.indices {
        var sum = 0
        for end in start..<nums.count {
            sum += nums[end]
            if sum == k { count += 1 }
        }
    }
    return count
}

// Prefix sums + hash map: O(n) time, O(n) space
// sum(i..<j) == k  ⇔  prefix[j] − prefix[i] == k  ⇔  prefix[i] == prefix[j] − k
func subarraySum(_ nums: [Int], _ k: Int) -> Int {
    var countOfPrefix: [Int: Int] = [0: 1]          // empty prefix
    var prefix = 0, count = 0
    for x in nums {
        prefix += x
        count += countOfPrefix[prefix - k, default: 0]
        countOfPrefix[prefix, default: 0] += 1
    }
    return count
}
```
Two pointers/sliding window **don't** work here when numbers can be negative (the window sum isn't monotonic), which is why the prefix-sum approach is the standard answer.

### Q95. Product of array except self (no division) `[Senior]`
```swift
// Brute force: O(n²)
// Prefix and suffix products: O(n) time, O(1) extra space (the output array doesn't count)
func productExceptSelf(_ nums: [Int]) -> [Int] {
    var result = [Int](repeating: 1, count: nums.count)
    var prefix = 1
    for i in nums.indices {                    // result[i] = product of everything left of i
        result[i] = prefix
        prefix *= nums[i]
    }
    var suffix = 1
    for i in nums.indices.reversed() {         // multiply by product of everything right of i
        result[i] *= suffix
        suffix *= nums[i]
    }
    return result
}
```
Shows two classic ideas: **precompute from both directions**, and **reuse the output array** to reach `O(1)` auxiliary space.

### Q96. Next greater element `[Senior]`
For each element, find the next element to its right that is larger (or `-1`).

```swift
// Brute force: O(n²) — scan right from every position
// Monotonic stack: O(n) time, O(n) space
func nextGreater(_ nums: [Int]) -> [Int] {
    var result = [Int](repeating: -1, count: nums.count)
    var stack: [Int] = []                       // indices whose answer is still unknown; values decreasing
    for (i, x) in nums.enumerated() {
        while let top = stack.last, nums[top] < x {
            result[top] = x                     // x is the next greater element for `top`
            stack.removeLast()
        }
        stack.append(i)
    }
    return result
}
```
**Why `O(n)` despite the nested `while`:** each index is pushed once and popped at most once → at most `2n` stack operations in total (aggregate analysis, Q43).

## 12. "Spot the Hidden Cost" Questions

### Q97. What's slow about this queue processing? `[Fundamental]`
```swift
var pending = loadTasks()                  // 50,000 tasks
while !pending.isEmpty {
    let task = pending.removeFirst()
    run(task)
}
```
**Problem:** `removeFirst()` is `O(n)`: total `O(n²)` (~1.25 billion element moves for 50,000 tasks).
**Fix:** iterate directly (`for task in pending`), reverse once and use `popLast()`, use an index, or use `Deque`. All `O(n)`.

### Q98. What's slow about this string loop? `[Senior]`
```swift
var i = 0
var vowels = 0
while i < text.count {                                 // O(n) on every check!
    let ch = text[text.index(text.startIndex, offsetBy: i)]   // O(i)
    if "aeiou".contains(ch) { vowels += 1 }
    i += 1
}
```
**Problem:** `String.count` and `index(_:offsetBy:)` are both `O(n)` (Q48) → `O(n²)` overall.
**Fix:** `for ch in text where "aeiou".contains(ch) { vowels += 1 }` → `O(n)`; or `text.count(where: { "aeiou".contains($0) })`.

### Q99. What's slow about this order-preserving deduplication? `[Fundamental]`
```swift
func unique(_ items: [String]) -> [String] {
    var result: [String] = []
    for item in items where !result.contains(item) {   // O(result.count · L)
        result.append(item)
    }
    return result
}
```
**Problem:** `contains` on an array is a linear scan → `O(n² · L)`.
**Fix:** track seen items in a `Set` → `O(n · L)` average:
```swift
func unique(_ items: [String]) -> [String] {
    var seen = Set<String>()
    return items.filter { seen.insert($0).inserted }
}
```
(`OrderedSet(items)` from swift-collections does the same.)

### Q100. What's slow about this `reduce`? `[Senior]`
```swift
let flattened = arrays.reduce([]) { $0 + $1 }         // [[Int]] → [Int]
let csv = rows.reduce("") { $0 + $1 + "\n" }
```
**Problem:** `reduce` passes the accumulator **by value**; `$0 + $1` builds a **new** array/string each step, copying everything accumulated so far → `O(N²)` in the total size `N`.
**Fix:** `arrays.flatMap { $0 }` or `Array(arrays.joined())`; `rows.joined(separator: "\n")`; or `reduce(into: [])` with `append(contentsOf:)`. All `O(N)`.

### Q101. What's slow about finding the top scorer repeatedly? `[Fundamental]`
```swift
for _ in 0..<rounds {
    let leader = players.sorted { $0.score > $1.score }.first!   // O(n log n) per round
    reward(leader)
}
```
**Problems:** sorting to get one maximum is `O(n log n)` (and allocates); doing it every round multiplies it.
**Fix:** `players.max { $0.score < $1.score }` → `O(n)`, `O(1)` space; if scores change incrementally across rounds, maintain a **heap** or an ordered structure (`O(log n)` per update).

### Q102. What's slow about building a reversed array like this? `[Fundamental]`
```swift
var reversedItems: [Item] = []
for item in items {
    reversedItems.insert(item, at: 0)      // shifts every existing element
}
```
**Problem:** `insert(_:at: 0)` is `O(n)` → `O(n²)` total.
**Fix:** `Array(items.reversed())` → `O(n)`; or append and `reverse()` once at the end.

### Q103. What's slow about counting occurrences like this? `[Fundamental]`
```swift
for word in uniqueWords {
    let frequency = allWords.filter { $0 == word }.count     // full scan + array allocation per word
    print(word, frequency)
}
```
**Problem:** `O(u · n · L)`: one full pass over all `n` words for each of the `u` unique words, plus an intermediate array each time.
**Fix:** one pass to build counts: `let counts = allWords.reduce(into: [:]) { $0[$1, default: 0] += 1 }` → `O(n · L)`; then look up each word in `O(L)`.

### Q104. What's slow about this table view data source? `[Senior]`
```swift
func tableView(_ tableView: UITableView, cellForRowAt indexPath: IndexPath) -> UITableViewCell {
    let cell = tableView.dequeueReusableCell(withIdentifier: "Cell", for: indexPath)
    let sortedContacts = contacts.sorted { $0.name < $1.name }          // O(n log n) per cell!
    let contact = sortedContacts[indexPath.row]
    let isFavorite = favorites.contains(contact.id)                     // favorites: [String] → O(f)
    cell.textLabel?.text = contact.name + (isFavorite ? " ★" : "")
    return cell
}
```
**Problems:**
1. Sorting the whole list **for every cell**: displaying `v` visible cells while scrolling costs `O(v · n log n)` per screen and `O(n² log n)` to scroll through everything, on the main thread.
2. `favorites` is an array → `O(f)` lookup per cell.

**Fix:** sort **once** when the data changes and store the sorted array; make `favorites` a `Set<String>` (`O(1)` average lookup). Each cell is then `O(1)` work.

## 13. Last-Day Cheat Sheet

### Notation
| | Meaning |
|---|---|
| `O(g)` | Upper bound (grows no faster than `g`) |
| `Ω(g)` | Lower bound (grows at least as fast) |
| `Θ(g)` | Tight bound (both) |
| Worst / average / best | Which inputs you're bounding |
| Amortized | Average per operation over any sequence (no probability) |
| Expected | Average over the algorithm's random choices |

**Simplify:** drop constants and lower-order terms; log base doesn't matter; keep independent variables (`n + m`, `n · m`); constants **in exponents** matter (`4ⁿ ≠ 2ⁿ`).

### Growth order
`1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < n! < nⁿ`

### How to calculate (time)
1. Define the variables (`n`, `m`, `L`, `V`, `E`, `k`).
2. Sequential blocks → **add**; nested loops → **multiply**; branches → **max**.
3. Loop counter `×2` or `÷2` → `log n`; `i*i ≤ n` → `√n`; harmonic `n/i` → `n log n`.
4. Dependent bounds → **write the sum** (`1 + 2 + … + n = n²/2`; geometric `n + n/2 + … = 2n`).
5. Pointers that never move back → count total moves (`O(n)`).
6. Include the cost of **every call** in the loop body (hashing, `contains`, `count`, copies).
7. Recursion → recurrence → unroll / recursion tree / Master theorem.
8. Memoized recursion → **states × work per state**.

### Master theorem `T(n) = a·T(n/b) + f(n)`
Compare `f(n)` with `n^(log_b a)`: smaller → `Θ(n^(log_b a))`; equal → `Θ(n^(log_b a) log n)`; larger → `Θ(f(n))`.
| Recurrence | Result |
|---|---|
| `T(n/2) + 1` | `log n` |
| `T(n/2) + n` | `n` |
| `2T(n/2) + 1` | `n` |
| `2T(n/2) + n` | `n log n` |
| `T(n−1) + 1` | `n` |
| `T(n−1) + n` | `n²` |
| `2T(n−1) + 1` | `2ⁿ` |
| `T(n−1) + T(n−2) + 1` | `φⁿ ≈ 1.618ⁿ` |

### Space
- Count auxiliary memory: new collections, hash maps, DP tables, **recursion depth** (max depth, not total calls).
- Swift doesn't guarantee tail-call optimization; deep recursion can overflow the stack.
- Copy-on-write: copying is `O(1)`, the first mutation of a shared buffer is `O(n)`.
- Slices/substrings share storage (`O(1)`), keep the original alive, use original indices.

### Swift hidden costs
| Looks cheap | Actually |
|---|---|
| `array.removeFirst()`, `insert(_:at: 0)`, `remove(at:)` | `O(n)` |
| `array.contains`, `firstIndex(of:)` | `O(n)` |
| `string.count`, `index(_:offsetBy: k)` | `O(n)`, `O(k)` |
| `a + b`, `s1 + s2` | `O(n + m)` copy |
| `reduce([]) { $0 + [$1] }` | `O(n²)` |
| `sorted().first` | `O(n log n)` (use `min()`) |
| Dictionary lookup with `String` keys | `O(L)` to hash |
| Lazy chains iterated twice | Recomputed each time |

### Patterns that cut complexity
Hash map/set (`n²` → `n`) · sort + two pointers · sliding window · prefix sums · heap for top-`k` (`n log k`) · monotonic stack · binary search (on data or on the answer) · memoization/DP · union-find · precomputation.

### Input size → target complexity
`n ≤ 10`: `n!` · `n ≤ 20`: `2ⁿ` · `n ≤ 500`: `n³` · `n ≤ 5,000`: `n²` · `n ≤ 10⁶`: `n log n` · `n ≤ 10⁸`: `n` · larger: `log n` / `O(1)`.

### Phrases that show seniority
- "Let me define the variables first: `n` words, maximum length `L`."
- "That inner loop looks nested, but the pointer never moves back, so it's `O(n)` in total."
- "Append is amortized `O(1)`, not worst-case `O(1)`."
- "With memoization it's states times work per state: `O(n · W)`, which is pseudo-polynomial."
- "This matches the lower bound: we have to read every element, so `O(n)` is optimal."
- "For our sizes, constants and cache behavior matter more; I'd measure in a Release build."
