## 1. Fundamentals

### Q1. What is SwiftData? `[Fundamental]`
**Key points:**
- Apple's Swift-native persistence framework (iOS 17+), for modeling, storing, querying, and syncing app data.
- Models are plain Swift classes annotated with the `@Model` macro; no `.xcdatamodeld` file.
- Deep SwiftUI integration (`@Query`, `.modelContainer`, `@Environment(\.modelContext)`), Observation support, and optional iCloud sync via CloudKit.
- Under the hood, the default store is built on Core Data's proven SQLite persistence.

### Q2. What are the core building blocks of SwiftData? `[Fundamental]`
| Component | Role |
|---|---|
| `@Model` | Turns a class into a persistent model |
| `Schema` | The set of model types and their versions |
| `ModelConfiguration` | Describes **how** a store is persisted (location, in-memory, CloudKit, read-only) |
| `ModelContainer` | Owns the schema and persistent store(s); the "database" |
| `ModelContext` | A scratchpad for fetching, inserting, changing, deleting, and saving models |
| `@Query` | SwiftUI property wrapper that fetches and keeps results updated |
| `FetchDescriptor` / `#Predicate` / `SortDescriptor` | Describe what to fetch and in which order |
| `ModelActor` | An actor with its own context for background work |
| `PersistentIdentifier` | A stable, `Sendable` ID for a model, safe to pass across actors |

### Q3. Walk through a minimal SwiftData app. `[Fundamental]`
```swift
import SwiftData
import SwiftUI

@Model
final class Trip {
    var name: String
    var startDate: Date
    var isFavorite: Bool = false

    init(name: String, startDate: Date) {
        self.name = name
        self.startDate = startDate
    }
}

@main
struct TripsApp: App {
    var body: some Scene {
        WindowGroup {
            TripListView()
        }
        .modelContainer(for: Trip.self)   // creates the container and injects mainContext
    }
}

struct TripListView: View {
    @Environment(\.modelContext) private var modelContext
    @Query(sort: \Trip.startDate, order: .reverse) private var trips: [Trip]

    var body: some View {
        NavigationStack {
            List {
                ForEach(trips) { trip in
                    Text(trip.name)
                }
                .onDelete { offsets in
                    for index in offsets { modelContext.delete(trips[index]) }
                }
            }
            .toolbar {
                Button("Add", systemImage: "plus") {
                    modelContext.insert(Trip(name: "New Trip", startDate: .now))
                }
            }
        }
    }
}
```
- No explicit `save()` here: the main context autosaves.

### Q4. Why are SwiftData models classes and not structs? `[Senior]`
**Key points:**
- Persistent objects need **identity**: the same database row must map to the same in-memory object so changes are tracked and relationships form a graph.
- The context tracks mutations on that shared instance; a struct would be copied, losing the connection to the store.
- Models are also `Observable`, which requires reference semantics.
- Mark models `final` unless you intentionally use inheritance (iOS 26+).

### Q5. What does the `@Model` macro generate? `[Senior]`
**Key points:**
- Conformance to `PersistentModel` (and therefore `Identifiable`, `Hashable`) and to `Observable`.
- Converts each stored property into a computed property backed by the model's **backing data** (the context-managed storage), with observation tracking on reads and writes.
- Schema metadata describing properties, attributes, and relationships.
- An `init(backingData:)` used by SwiftData when materializing models from the store.
- You can inspect the expansion in Xcode via right-click → **Expand Macro**.

### Q6. Which types can a model property store? `[Fundamental]`
**Key points:**
- Basic value types: `String`, `Int`, `Double`, `Float`, `Bool`, `Date`, `Data`, `URL`, `UUID`, `Decimal`.
- Optionals of those.
- `Codable` structs and enums (stored as composite/encoded values).
- Arrays of supported value types.
- Relationships to other `@Model` types (single or arrays).
- Other types via `@Attribute(.transformable(by:))` with a `ValueTransformer`.

### Q7. Does SwiftData replace Core Data? `[Senior]`
**Key points:**
- Not entirely. SwiftData is the modern, Swift-first API and Apple's direction for new projects, but Core Data remains supported and still has capabilities SwiftData lacks or only recently gained (sectioned fetching, batch updates, public/shared CloudKit databases, fetched results controller for UIKit, fine-grained migration control).
- They can **coexist** on the same store (see Section 14).

### Q8. What is the minimum OS for SwiftData, and how does that affect adoption? `[Senior]`
**Key points:**
- iOS 17 / macOS 14. Several important fixes and features arrived in iOS 17.4, iOS 18, and iOS 26.
- Teams supporting iOS 16 can't adopt it without a parallel Core Data path. Many teams wait until their minimum target is iOS 17 or 18.
- When evaluating, test the features you need on your **minimum** OS version, since behavior has changed between releases.

## 2. Defining Models

### Q9. What is `@Attribute`, and what options does it support? `[Senior]`
| Option | Purpose |
|---|---|
| `.unique` | Value must be unique; inserting a duplicate performs an **upsert** |
| `.externalStorage` | Store large data (images, files) outside the main database file |
| `.transformable(by:)` | Persist a custom type via a `ValueTransformer` |
| `.allowsCloudEncryption` | Encrypt the value in CloudKit |
| `.spotlight` | Index the value for Spotlight search |
| `.ephemeral` | Track changes but don't persist the value |
| `.preserveValueOnDeletion` | Keep the value in history tombstones after deletion (iOS 18) |
| `originalName:` | Map a renamed property to its old name for lightweight migration |

```swift
@Model
final class Photo {
    @Attribute(.unique) var remoteID: String
    @Attribute(.externalStorage) var imageData: Data?
    @Attribute(originalName: "title") var caption: String   // renamed from `title`
    var takenAt: Date

    init(remoteID: String, caption: String, takenAt: Date) {
        self.remoteID = remoteID
        self.caption = caption
        self.takenAt = takenAt
    }
}
```

### Q10. What happens when you insert a model whose `.unique` value already exists? `[Senior]`
**Key points:**
- SwiftData performs an **upsert**: instead of creating a duplicate row or throwing, it updates the existing record with the new values when saved.
- That's useful for syncing server data keyed by a remote ID: insert DTO-mapped models and duplicates merge automatically.
- Caveats: unique constraints aren't supported with CloudKit sync; and you should test upsert behavior for relationships, since related objects on the incoming model may also need deduplication.

### Q11. What is `#Unique`, and how does it differ from `@Attribute(.unique)`? `[Senior]`
**Key points:**
- iOS 18 macro for **compound** uniqueness across multiple properties (e.g. name + start date). `@Attribute(.unique)` handles a single property.

```swift
@Model
final class Trip {
    #Unique<Trip>([\.name, \.startDate])   // the combination must be unique

    var name: String
    var startDate: Date
    var endDate: Date

    init(name: String, startDate: Date, endDate: Date) {
        self.name = name
        self.startDate = startDate
        self.endDate = endDate
    }
}
```
- You can list several uniqueness constraints: `#Unique<Trip>([\.id], [\.name, \.startDate])`.

### Q12. What is `@Transient`? `[Fundamental]`
**Key points:**
- Marks a stored property that should **not** be persisted (temporary UI state, caches).
- It must have a default value, and it resets to that default whenever the model is re-materialized from the store.
- Transient properties can't be used in predicates or sort descriptors.

```swift
@Model
final class Document {
    var title: String
    @Transient var isSelected = false   // in-memory only

    init(title: String) { self.title = title }
}
```

### Q13. Can models have computed properties? `[Fundamental]`
**Key points:**
- Yes. Computed properties aren't persisted, so they're free to derive values from stored properties.
- They **can't** be used in `#Predicate` or `SortDescriptor`, because queries run in the store against persisted columns.
- If you need to filter or sort on a derived value, store it as a real property and keep it updated.

### Q14. How do you store enums in a model and query them? `[Senior]`
**Key points:**
- `Codable` enums can be stored directly. But filtering on enum values inside `#Predicate` has historically been unreliable.
- A robust pattern: persist the raw value and expose a typed computed property.

```swift
enum Priority: Int, Codable, CaseIterable {
    case low, medium, high
}

@Model
final class TodoItem {          // avoid naming a model `Task` (clashes with Swift Concurrency)
    var title: String
    var priorityRawValue: Int = Priority.medium.rawValue

    var priority: Priority {
        get { Priority(rawValue: priorityRawValue) ?? .medium }
        set { priorityRawValue = newValue.rawValue }
    }

    init(title: String, priority: Priority = .medium) {
        self.title = title
        self.priorityRawValue = priority.rawValue
    }
}

// Query on the stored raw value
let highRaw = Priority.high.rawValue
let urgent = #Predicate<TodoItem> { $0.priorityRawValue == highRaw }
```

### Q15. How do you store `Codable` structs in a model? What are the limits? `[Senior]`
```swift
struct Address: Codable {
    var street: String
    var city: String
    var postalCode: String
}

@Model
final class Customer {
    var name: String
    var address: Address?     // stored as a composite value

    init(name: String, address: Address? = nil) {
        self.name = name
        self.address = address
    }
}
```
**Limits:**
- Querying or sorting on fields **inside** a `Codable` value is limited compared to top-level attributes. If you need `WHERE city == "Paris"`, promote `city` to a top-level property or a related model.
- Changing the struct's shape later can break decoding of existing data; plan versioning carefully.

### Q16. When should you use `.externalStorage`? `[Senior]`
**Key points:**
- For large binary data (images, PDFs, audio). SwiftData can store the bytes in separate files and keep only a reference in the database, keeping the database small and fetches fast.
- Still avoid loading large data in lists: fetch thumbnails separately, or keep large blobs in a separate model referenced by relationship so they're loaded only when needed.

### Q17. Why does a model need an initializer, and how should you handle defaults? `[Fundamental]`
**Key points:**
- `@Model` classes need a designated `init` (Swift class rules); SwiftData doesn't synthesize one.
- Give properties default values in their declarations where sensible. This also makes adding new properties a lightweight migration and is required for CloudKit compatibility.

### Q18. How do you use a custom type with `.transformable`? `[Lead/Expert]`
```swift
@objc(ColorTransformer)
final class ColorTransformer: NSSecureUnarchiveFromDataTransformer {
    override class var allowedTopLevelClasses: [AnyClass] { [UIColor.self] }
}

@Model
final class Tag {
    var name: String
    @Attribute(.transformable(by: ColorTransformer.self)) var color: UIColor?

    init(name: String, color: UIColor? = nil) {
        self.name = name
        self.color = color
    }
}

// Register once at launch, before creating the container:
// ValueTransformer.setValueTransformer(ColorTransformer(), forName: NSValueTransformerName("ColorTransformer"))
```
- Prefer storing simple value types (e.g. a hex string or RGBA components in a `Codable` struct) when possible; transformable values are opaque to queries.

### Q19. What is the `persistentModelID`? `[Senior]`
**Key points:**
- Every model has a `persistentModelID` of type `PersistentIdentifier`: `Sendable`, `Hashable`, and `Codable`.
- Use it to pass references across actors, as diffable data source identifiers, or to refetch a model in another context.
- Before the first save, the ID may be **temporary**. Save before handing IDs to another context (see Q121).

### Q20. Should you add your own `id` property? `[Senior]`
**Key points:**
- `@Model` types are already `Identifiable` via `persistentModelID`, so SwiftUI works out of the box.
- Add your own `UUID`/`String` ID when you need a **stable, external** identifier: syncing with a server, deep links, or cross-device references. Make it unique (`@Attribute(.unique)` or `#Unique`) unless you use CloudKit.

## 3. Relationships

### Q21. How do you define one-to-many relationships? `[Fundamental]`
```swift
@Model
final class Trip {
    var name: String

    @Relationship(deleteRule: .cascade, inverse: \Activity.trip)
    var activities: [Activity] = []

    init(name: String) { self.name = name }
}

@Model
final class Activity {
    var title: String
    var trip: Trip?

    init(title: String) { self.title = title }
}

// Usage
let trip = Trip(name: "Japan")
modelContext.insert(trip)
trip.activities.append(Activity(title: "Visit Kyoto"))   // related model is inserted automatically
```
- Declaring a property whose type is another model (or an array of models) creates a relationship; `@Relationship` customizes it.
- Specify `inverse` on **one** side only.

### Q22. What delete rules are available? `[Fundamental]`
| Rule | Effect when the owner is deleted |
|---|---|
| `.nullify` (default) | Related objects remain; their back-reference is set to `nil` |
| `.cascade` | Related objects are deleted too |
| `.deny` | Deletion is refused while related objects exist |
| `.noAction` | Nothing happens to related objects (can leave dangling references; rarely appropriate) |

- Senior tip: explicitly define the inverse when relying on `.cascade`; cascade behavior without a defined inverse has been a source of bugs.

### Q23. How do you model many-to-many relationships? `[Senior]`
```swift
@Model
final class Student {
    var name: String
    var courses: [Course] = []
    init(name: String) { self.name = name }
}

@Model
final class Course {
    var title: String
    @Relationship(inverse: \Student.courses)
    var students: [Student] = []
    init(title: String) { self.title = title }
}

// Adding to one side updates the other automatically
student.courses.append(course)   // course.students now contains student
```
- If the relationship has its own data (enrollment date, grade), model a join entity (`Enrollment`) with two to-one relationships instead.

### Q24. Are to-many relationship arrays ordered? `[Lead/Expert]`
**Key points:**
- **No.** This is a classic gotcha. The array's order is not guaranteed to be preserved after saving and refetching.
- If order matters (playlists, steps, checklists), store an explicit position property and sort.

```swift
@Model
final class Playlist {
    var name: String
    @Relationship(deleteRule: .cascade, inverse: \PlaylistEntry.playlist)
    var entries: [PlaylistEntry] = []

    var orderedEntries: [PlaylistEntry] {
        entries.sorted { $0.position < $1.position }
    }

    init(name: String) { self.name = name }
}

@Model
final class PlaylistEntry {
    var position: Int
    var songTitle: String
    var playlist: Playlist?

    init(position: Int, songTitle: String) {
        self.position = position
        self.songTitle = songTitle
    }
}
```

### Q25. What are `minimumModelCount` and `maximumModelCount`? `[Senior]`
**Key points:**
- `@Relationship` parameters that enforce how many related objects are allowed (e.g. a team must have at least 1 and at most 11 players). Violations surface as save errors.

```swift
@Relationship(deleteRule: .cascade, minimumModelCount: 1, maximumModelCount: 11)
var players: [Player] = []
```

### Q26. Why might you get "Illegal attempt to establish a relationship between objects in different contexts"? `[Lead/Expert]`
**Key points:**
- You connected two models that belong to **different** `ModelContext`s (e.g. a model fetched on a background actor and one from the main context).
- Fix: refetch both models in the same context using their `persistentModelID`, then connect them.

### Q27. How should you handle relationships when importing data? `[Senior]`
**Key points:**
- Insert the parent into the context, then set relationships (appending children auto-inserts them).
- When importing related objects keyed by remote IDs, look up existing objects first (or rely on unique upserts) to avoid duplicates.
- For large graphs, import parents first, save, then import children in batches to control memory.

### Q28. How do relationships affect loading? `[Senior]`
**Key points:**
- Related objects are loaded **lazily** (faulting): accessing `trip.activities` triggers a fetch if not already loaded.
- In a list where every row reads a relationship, this causes N+1 fetches. Use `relationshipKeyPathsForPrefetching` in a `FetchDescriptor`, or store a denormalized count/summary property when appropriate (see Q85).

## 4. ModelContainer & ModelConfiguration

### Q29. What is a `ModelContainer`? `[Fundamental]`
**Key points:**
- Manages the schema and the persistent stores for your app. Usually one per app (or per distinct database).
- Creates the `mainContext` (main-actor-bound) and lets you create additional contexts.
- `ModelContainer` is `Sendable`, so it can be passed to background actors.

### Q30. How do you create a container explicitly with error handling? `[Senior]`
```swift
@main
struct TripsApp: App {
    let container: ModelContainer

    init() {
        do {
            let schema = Schema([Trip.self, Activity.self])
            let configuration = ModelConfiguration(schema: schema)
            container = try ModelContainer(for: schema, configurations: configuration)
        } catch {
            // Production apps should log, attempt recovery, or show a recovery UI instead of crashing
            fatalError("Failed to create ModelContainer: \(error)")
        }
    }

    var body: some Scene {
        WindowGroup { ContentView() }
            .modelContainer(container)
    }
}
```
- The `.modelContainer(for:)` modifier is convenient but hides errors. Creating it yourself lets you handle failures (e.g. a failed migration) and share it with app intents, widgets, and background tasks.

### Q31. What is `ModelConfiguration` used for? `[Senior]`
**Key points:**
- Describes a store: name, `schema` subset, file `url`, `isStoredInMemoryOnly`, `allowsSave` (read-only), `groupContainer` (app groups), and `cloudKitDatabase`.

```swift
// In-memory (tests, previews)
let memory = ModelConfiguration(isStoredInMemoryOnly: true)

// Read-only bundled database
let seed = ModelConfiguration(url: Bundle.main.url(forResource: "Seed", withExtension: "store")!, allowsSave: false)

// Shared with widgets via an app group
let shared = ModelConfiguration(groupContainer: .identifier("group.com.example.trips"))

// No iCloud sync even if the app has the CloudKit entitlement
let localOnly = ModelConfiguration(cloudKitDatabase: .none)
```

### Q32. How do you use multiple stores in one container? `[Lead/Expert]`
**Key points:**
- Pass multiple configurations, each with its own schema subset, e.g. user data synced to iCloud plus a local-only cache.

```swift
let synced = ModelConfiguration("UserData",
                                schema: Schema([Trip.self, Activity.self]),
                                cloudKitDatabase: .automatic)

let cache = ModelConfiguration("Cache",
                               schema: Schema([CachedImage.self]),
                               cloudKitDatabase: .none)

let container = try ModelContainer(for: Trip.self, Activity.self, CachedImage.self,
                                   configurations: synced, cache)
```
- Relationships can't span different stores.

### Q33. Where is the SwiftData store file, and how do you find it? `[Fundamental]`
```swift
print(container.configurations.first?.url.path(percentEncoded: false) ?? "unknown")
// Default: <App Sandbox>/Library/Application Support/default.store
```
- Useful for inspecting the SQLite file with a database browser during debugging.

### Q34. How do you enable undo/redo? `[Fundamental]`
```swift
WindowGroup { ContentView() }
    .modelContainer(for: Trip.self, isUndoEnabled: true)

struct EditorView: View {
    @Environment(\.undoManager) private var undoManager

    var body: some View {
        HStack {
            Button("Undo") { undoManager?.undo() }.disabled(!(undoManager?.canUndo ?? false))
            Button("Redo") { undoManager?.redo() }.disabled(!(undoManager?.canRedo ?? false))
        }
    }
}
```
- Outside SwiftUI, assign an `UndoManager` to `container.mainContext.undoManager`.

### Q35. Can you create a model instance before any container exists? `[Senior]`
**Key points:**
- Creating `@Model` instances requires SwiftData to know the schema. If no container for that model has been created yet, you can hit a crash like "Failed to find any currently loaded container for Trip."
- This often appears in previews, unit tests, or static sample data initialized too early.
- Fix: create the container first (e.g. an in-memory container in tests/previews), then create and insert models.

## 5. ModelContext: CRUD, Saving & Undo

### Q36. What is a `ModelContext`? `[Fundamental]`
**Key points:**
- An object that tracks models you fetch, insert, change, and delete, and writes them to the store on `save()`.
- Think of it as a scratchpad: changes live in memory until saved.
- **Not `Sendable`**: a context (and the models it manages) must be used from the actor that created it. The `mainContext` belongs to the main actor.

### Q37. Show basic CRUD operations. `[Fundamental]`
```swift
// Create
let trip = Trip(name: "Iceland", startDate: .now)
modelContext.insert(trip)

// Read
let descriptor = FetchDescriptor<Trip>(
    predicate: #Predicate<Trip> { $0.name.localizedStandardContains("ice") },
    sortBy: [SortDescriptor(\.startDate)]
)
let trips = try modelContext.fetch(descriptor)

// Update: just mutate; the context tracks changes
trip.name = "Iceland 2026"

// Delete
modelContext.delete(trip)

// Persist
try modelContext.save()
```

### Q38. How does autosave work? `[Senior]`
**Key points:**
- The main context (from `.modelContainer`) has `autosaveEnabled = true`: it saves periodically and on certain events (e.g. app moving to the background).
- Contexts you create yourself (`ModelContext(container)`, or inside a `ModelActor`) should be saved explicitly with `try modelContext.save()`. Don't rely on autosave there.
- Autosave timing isn't precise. If data must be persisted at a specific moment (before sharing to a widget, before a network sync, before a crash-prone operation), call `save()` explicitly.

### Q39. What do `hasChanges` and `rollback()` do? `[Fundamental]`
```swift
if modelContext.hasChanges {
    try modelContext.save()
}

// Discard ALL unsaved changes in this context
modelContext.rollback()
```
- Careful: `rollback()` on the main context discards every unsaved change across the app, not just the current screen's edits.

### Q40. How do you save multiple changes atomically? `[Senior]`
```swift
try modelContext.transaction {
    let source = account(named: "Checking")
    let target = account(named: "Savings")
    source.balance -= 100
    target.balance += 100
    modelContext.insert(Transfer(from: source, to: target, amount: 100))
}
// All changes are saved together when the block completes
```

### Q41. How do you implement an edit screen with Cancel and Save? `[Lead/Expert]`
**Key points:** SwiftData has no child contexts (unlike Core Data), so you need a strategy:

**Option A: Edit a draft value, apply on Save** (simple and explicit)
```swift
struct TripDraft {
    var name: String
    var startDate: Date

    init(trip: Trip) {
        name = trip.name
        startDate = trip.startDate
    }

    func apply(to trip: Trip) {
        trip.name = name
        trip.startDate = startDate
    }
}

struct EditTripView: View {
    let trip: Trip
    @State private var draft: TripDraft
    @Environment(\.dismiss) private var dismiss

    init(trip: Trip) {
        self.trip = trip
        _draft = State(initialValue: TripDraft(trip: trip))
    }

    var body: some View {
        Form {
            TextField("Name", text: $draft.name)
            DatePicker("Start", selection: $draft.startDate, displayedComponents: .date)
        }
        .toolbar {
            Button("Cancel") { dismiss() }
            Button("Save") {
                draft.apply(to: trip)
                dismiss()
            }
        }
    }
}
```

**Option B: A separate editing context**
```swift
let editingContext = ModelContext(container)
editingContext.autosaveEnabled = false
guard let editableTrip = editingContext.model(for: trip.persistentModelID) as? Trip else { return }
// Bind the form to editableTrip.
// Save:   try editingContext.save()   (main-context queries pick up the change)
// Cancel: discard editingContext
```
- Option C: undo grouping on the main context (works but couples to global undo state).

### Q42. How do you delete many objects efficiently? `[Senior]`
```swift
let cutoff = Calendar.current.date(byAdding: .year, value: -2, to: .now)!
try modelContext.delete(model: Trip.self, where: #Predicate<Trip> { $0.endDate < cutoff })
try modelContext.save()
```
- Deletes matching records without fetching and looping in Swift. Check delete rules: cascades still apply.

### Q43. What happens if you access a model after it has been deleted? `[Senior]`
**Key points:**
- Accessing properties of a deleted (and saved) model can crash, because its backing data no longer exists.
- Common cause: a detail view still showing a model that was deleted from another screen, a background actor, or iCloud sync.
- Mitigations: check `model.isDeleted` / `model.modelContext == nil` before use; drive UI from `@Query` so deleted rows disappear; pop or dismiss detail screens when their model is deleted.

### Q44. Can a model belong to multiple contexts? `[Senior]`
**Key points:**
- A model **instance** belongs to exactly one context. The same database record can be represented by different instances in different contexts.
- To use a record in another context, pass its `persistentModelID` and fetch it there.

### Q45. Do changes saved in one context appear in another? `[Senior]`
**Key points:**
- Yes: when a context saves, the container merges changes, and other contexts (including the main context driving `@Query`) pick them up.
- Early iOS 17 releases had issues with background saves not refreshing `@Query` results promptly; these improved in later releases. Test this flow on your minimum OS version.
- Unsaved changes in one context are invisible to others.

## 6. Querying: `@Query`, `FetchDescriptor` & `#Predicate`

### Q46. What is `@Query`, and how does it work? `[Fundamental]`
**Key points:**
- A SwiftUI property wrapper that fetches models from the environment's `modelContext` and **automatically updates** the view when matching data changes.
- Supports filter, sort, animation, and full `FetchDescriptor`s.

```swift
struct FavoritesView: View {
    @Query(filter: #Predicate<Trip> { $0.isFavorite },
           sort: \Trip.startDate,
           order: .reverse,
           animation: .default)
    private var favorites: [Trip]

    @Query(sort: [SortDescriptor(\Trip.startDate, order: .reverse), SortDescriptor(\Trip.name)])
    private var allTrips: [Trip]

    var body: some View {
        List(favorites) { Text($0.name) }
    }
}
```

### Q47. Can you use `@Query` in a view model? `[Senior]`
**Key points:**
- No. `@Query` is a `DynamicProperty` that only works inside SwiftUI views (it needs the view's environment).
- In view models or services, use `modelContext.fetch(_:)` manually. You then lose automatic updates and must refetch when data changes (e.g. after saving, or by observing `ModelContext.didSave`; see Q89).
- This is a key architectural trade-off (see Section 11).

### Q48. How do you make a `@Query` dynamic (filter or sort from user input)? `[Senior]`
**Key points:**
- `@Query` parameters are fixed at declaration. Create the query in the view's `init` from inputs, and let the parent pass new values (which recreates the child view with a new query).

```swift
struct TripListView: View {
    @Query private var trips: [Trip]

    init(searchText: String, sortOrder: SortOrder) {
        let predicate = #Predicate<Trip> { trip in
            searchText.isEmpty || trip.name.localizedStandardContains(searchText)
        }
        _trips = Query(filter: predicate, sort: \Trip.startDate, order: sortOrder)
    }

    var body: some View {
        List(trips) { Text($0.name) }
    }
}

struct TripSearchScreen: View {
    @State private var searchText = ""
    @State private var sortOrder = SortOrder.reverse

    var body: some View {
        NavigationStack {
            TripListView(searchText: searchText, sortOrder: sortOrder)
                .searchable(text: $searchText)
        }
    }
}
```

### Q49. What is `#Predicate`? `[Fundamental]`
**Key points:**
- A macro (from Foundation) that converts a Swift closure into a type-safe `Predicate` expression tree. SwiftData translates it into a SQL query, so filtering happens **in the database**, not in memory.
- Type-checked at compile time: typos in property names fail to compile (unlike `NSPredicate` format strings).

```swift
let now = Date.now
let search = "tokyo"

let upcoming = #Predicate<Trip> { trip in trip.startDate > now }
let matching = #Predicate<Trip> { trip in trip.name.localizedStandardContains(search) }
let busy = #Predicate<Trip> { trip in trip.activities.count > 5 }
let parisActivities = #Predicate<Activity> { activity in activity.trip?.name == "Paris" }
let favoritesInFuture = #Predicate<Trip> { trip in trip.isFavorite && trip.startDate > now }
```

### Q50. What are the limitations of `#Predicate`? `[Lead/Expert]`
**Key points:**
- Only a **subset** of Swift is supported: comparisons, logical operators, arithmetic, optional chaining/`??`, and specific methods (`contains`, `starts(with:)`, `localizedStandardContains`, `isEmpty`, `count`, `allSatisfy`, `contains(where:)`, etc.).
- **Not supported**: calling your own functions, computed or `@Transient` properties, arbitrary method calls (e.g. `Date.now` inside the closure), some `String` APIs.
- Capture values as local constants **outside** the predicate.
- Complex predicates can hit "expression too complex" compile errors; split them or combine sub-predicates.
- Unsupported expressions may compile but fail **at runtime** when translated to SQL, so test every predicate with real data.

```swift
// ❌ Calls Date.now inside the predicate and uses a computed property
let bad = #Predicate<Trip> { $0.startDate > Date.now && $0.isUpcomingSoon }

// ✅ Capture values outside; use stored properties only
let now = Date.now
let soon = Calendar.current.date(byAdding: .day, value: 7, to: now)!
let good = #Predicate<Trip> { $0.startDate > now && $0.startDate < soon }
```

### Q51. How do you combine predicates? `[Lead/Expert]`
```swift
// iOS 17.4+: evaluate one predicate inside another
let isFavorite = #Predicate<Trip> { $0.isFavorite }
let isUpcoming = #Predicate<Trip> { $0.startDate > now }

let combined = #Predicate<Trip> { trip in
    isFavorite.evaluate(trip) && isUpcoming.evaluate(trip)
}
```
- Useful for building filters from user-selected options (search + category + date range) without one giant closure.

### Q52. What is a `FetchDescriptor`, and what options does it have? `[Senior]`
```swift
var descriptor = FetchDescriptor<Trip>(
    predicate: #Predicate<Trip> { $0.isFavorite },
    sortBy: [SortDescriptor(\.startDate, order: .reverse)]
)
descriptor.fetchLimit = 20                                  // page size
descriptor.fetchOffset = 40                                 // skip (page 3)
descriptor.propertiesToFetch = [\.name, \.startDate]        // partial fetch
descriptor.relationshipKeyPathsForPrefetching = [\.activities]  // avoid N+1
descriptor.includePendingChanges = true                     // include unsaved changes (default)

let trips = try modelContext.fetch(descriptor)
```
- Pass a descriptor to `@Query` too: `@Query(Self.recentTripsDescriptor) private var recent: [Trip]`.

### Q53. How do you count records without loading them? `[Fundamental]`
```swift
let count = try modelContext.fetchCount(
    FetchDescriptor<TodoItem>(predicate: #Predicate { !$0.isDone })
)
```
- Much cheaper than `fetch(...).count`. Use it for badges and summaries.

### Q54. How do you paginate results? `[Senior]`
```swift
func fetchPage(_ page: Int, pageSize: Int = 50) throws -> [Trip] {
    var descriptor = FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate, order: .reverse)])
    descriptor.fetchLimit = pageSize
    descriptor.fetchOffset = page * pageSize
    return try modelContext.fetch(descriptor)
}
```
- Always sort when paginating, otherwise pages are inconsistent.
- For very large tables, keyset pagination (filter by `startDate < lastSeenDate`) is faster than large offsets.

### Q55. How do you iterate over a huge result set without loading everything? `[Lead/Expert]`
```swift
try modelContext.enumerate(FetchDescriptor<Photo>(), batchSize: 500, allowEscapingMutations: true) { photo in
    photo.needsReindex = true
}
try modelContext.save()
```
- `enumerate` fetches in batches, keeping memory bounded, which is useful for maintenance jobs and migrations.
- Pass `allowEscapingMutations: true` when you mutate models inside the block and save afterwards; otherwise the enumeration reports an error for unsaved mutations.

### Q56. How do you fetch only identifiers? `[Senior]`
```swift
let ids: [PersistentIdentifier] = try modelContext.fetchIdentifiers(
    FetchDescriptor<Trip>(predicate: #Predicate { $0.isFavorite })
)
```
- Lightweight and `Sendable`: hand IDs to another actor or use them as diffable data source item identifiers.

### Q57. How do you group results into sections? `[Senior]`
**Key points:**
- SwiftData has no built-in sectioned fetch (Core Data's `@SectionedFetchRequest` has no direct equivalent).
- Fetch sorted results and group in memory, ideally in a computed property or model layer rather than in `body` for large datasets.

```swift
@Query(sort: \Trip.startDate) private var trips: [Trip]

private var tripsByYear: [(year: Int, trips: [Trip])] {
    Dictionary(grouping: trips) { Calendar.current.component(.year, from: $0.startDate) }
        .sorted { $0.key > $1.key }
        .map { (year: $0.key, trips: $0.value) }
}
```

### Q58. How do you sort by multiple keys or by a relationship property? `[Senior]`
```swift
@Query(sort: [
    SortDescriptor(\Trip.isFavorite, order: .reverse),
    SortDescriptor(\Trip.startDate)
])
private var trips: [Trip]
```
- Sorting on `Bool` values or optional relationship key paths has had limitations in some OS versions. If a sort isn't supported, store a sortable derived value (e.g. `destinationName: String`) on the model.

## 7. Concurrency & `ModelActor`

### Q59. What are SwiftData's concurrency rules? `[Senior]`
| Type | `Sendable`? | Rule |
|---|---|---|
| `ModelContainer` | ✅ Yes | Share freely across actors |
| `ModelContext` | ❌ No | Use only on the actor that created it |
| `@Model` instances | ❌ No | Use only within their context's actor |
| `PersistentIdentifier` | ✅ Yes | Pass across actors, refetch on the other side |

- In Swift 6 language mode, the compiler rejects passing models or contexts across actor boundaries.

### Q60. What is `@ModelActor`? `[Senior]`
**Key points:**
- A macro that turns an actor into one with its own `modelContainer`, `modelContext`, and a model executor that serializes access to that context.
- Use it for background work: imports, sync, heavy processing, and batch updates, keeping the main actor responsive.

```swift
@ModelActor
actor TripImporter {
    func importTrips(_ dtos: [TripDTO]) throws {
        for dto in dtos {
            modelContext.insert(Trip(name: dto.name, startDate: dto.startDate))
        }
        try modelContext.save()   // background contexts must save explicitly
    }
}

struct TripDTO: Sendable, Decodable {
    let name: String
    let startDate: Date
}

// Usage
let importer = TripImporter(modelContainer: container)
try await importer.importTrips(dtos)
```

### Q61. How do you work with a specific model on a background actor? `[Senior]`
**Key points:**
- Pass the `persistentModelID` (Sendable), and refetch the model inside the actor.

```swift
@ModelActor
actor PhotoProcessor {
    func generateThumbnails(forTrip tripID: PersistentIdentifier) throws {
        let descriptor = FetchDescriptor<Trip>(predicate: #Predicate { $0.persistentModelID == tripID })
        guard let trip = try modelContext.fetch(descriptor).first else { return }

        for photo in trip.photos where photo.thumbnailData == nil {
            photo.thumbnailData = ThumbnailRenderer.render(photo.imageData)
        }
        try modelContext.save()
    }
}

// From the UI (main actor)
let processor = PhotoProcessor(modelContainer: modelContext.container)
try await processor.generateThumbnails(forTrip: trip.persistentModelID)
```
- `modelContext.model(for:)` and `registeredModel(for:)` are alternatives; a predicate fetch confirms the record actually exists.

### Q62. How do you return results from a background actor to the UI? `[Senior]`
**Key points:**
- Return **Sendable** values: `PersistentIdentifier`s (then fetch in the main context), or plain DTO structs.

```swift
struct TripSummary: Sendable, Identifiable {
    let id: PersistentIdentifier
    let name: String
    let activityCount: Int
}

@ModelActor
actor TripReportService {
    func summaries() throws -> [TripSummary] {
        try modelContext.fetch(FetchDescriptor<Trip>()).map {
            TripSummary(id: $0.persistentModelID, name: $0.name, activityCount: $0.activities.count)
        }
    }
}
```

### Q63. Does a `@ModelActor` always run off the main thread? `[Lead/Expert]`
**Key points:**
- Not necessarily. Developers have reported that a `@ModelActor` created **on the main actor** may execute its context work on the main thread, because of how its default executor is set up.
- Defensive pattern: create the actor from a background context, and verify with Instruments or `Thread.isMainThread` during development.

```swift
let container = modelContext.container
Task.detached(priority: .utility) {
    let importer = TripImporter(modelContainer: container)
    try await importer.importTrips(dtos)
}
```
- Mentioning this shows real production experience. Hedge appropriately, since behavior can change between OS releases.

### Q64. How do you import thousands of records without freezing the UI or exhausting memory? `[Lead/Expert]`
```swift
@ModelActor
actor CatalogImporter {
    func importProducts(_ dtos: [ProductDTO]) throws {
        modelContext.autosaveEnabled = false
        for (index, dto) in dtos.enumerated() {
            modelContext.insert(Product(dto: dto))   // unique remoteID makes this an upsert
            if (index + 1).isMultiple(of: 1_000) {
                try modelContext.save()               // save in batches to bound memory
            }
        }
        try modelContext.save()
    }
}
```
**Talking points:**
- Run on a `@ModelActor` (off the main actor), decode JSON off the main actor too.
- Save in batches; consider recreating the context periodically for huge imports to release memory.
- Use unique constraints for upserts; avoid fetching each object individually (N queries).
- Report progress to the UI via `Sendable` values; support cancellation (`try Task.checkCancellation()` between batches).

### Q65. What's the problem with passing a model into a `Task` or actor? `[Senior]`
```swift
// ❌ Swift 6 error: non-Sendable 'Trip' crosses an actor boundary
let trip = trips.first!
Task.detached {
    await uploader.upload(trip)
}

// ✅ Pass the identifier (or a Sendable DTO)
let tripID = trip.persistentModelID
Task.detached {
    try await uploader.upload(tripID: tripID)
}
```
- In Swift 5 mode this may compile, but it's a data race: the model's context isn't thread-safe.

### Q66. How do you keep UI-bound code safe with SwiftData in Swift 6? `[Lead/Expert]`
**Key points:**
- Keep `mainContext` usage on the main actor (SwiftUI views and `@MainActor` view models).
- Do heavy work in `@ModelActor` services that accept and return Sendable types.
- Avoid `@unchecked Sendable` wrappers around models or contexts; they silence the compiler without fixing races.

## 8. Schema Migration

### Q67. Which schema changes are handled by lightweight migration? `[Senior]`
**Key points:**
- Generally automatic (no migration plan needed):
  - Adding a property that is optional or has a default value.
  - Removing a property.
  - Renaming a property with `@Attribute(originalName:)`.
  - Adding a new model or a new optional relationship.
  - Changing delete rules.
- Require a **custom** migration:
  - Adding a uniqueness constraint when duplicates may exist.
  - Changing a property's type, splitting/merging properties, or transforming data.
  - Restructuring relationships with data that must be moved.

### Q68. How do you version schemas and write a migration plan? `[Lead/Expert]`
```swift
enum TripSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [Trip.self] }

    @Model
    final class Trip {
        var name: String
        var destination: String
        init(name: String, destination: String) {
            self.name = name
            self.destination = destination
        }
    }
}

enum TripSchemaV2: VersionedSchema {
    static let versionIdentifier = Schema.Version(2, 0, 0)
    static var models: [any PersistentModel.Type] { [Trip.self] }

    @Model
    final class Trip {
        @Attribute(.unique) var name: String     // new: unique names
        var destination: String
        var notes: String = ""                   // new: property with default
        init(name: String, destination: String) {
            self.name = name
            self.destination = destination
        }
    }
}

enum TripMigrationPlan: SchemaMigrationPlan {
    static var schemas: [any VersionedSchema.Type] { [TripSchemaV1.self, TripSchemaV2.self] }
    static var stages: [MigrationStage] { [migrateV1toV2] }

    static let migrateV1toV2 = MigrationStage.custom(
        fromVersion: TripSchemaV1.self,
        toVersion: TripSchemaV2.self,
        willMigrate: { context in
            // Remove duplicate names BEFORE the unique constraint is applied
            let trips = try context.fetch(FetchDescriptor<TripSchemaV1.Trip>())
            var seen = Set<String>()
            for trip in trips where !seen.insert(trip.name).inserted {
                context.delete(trip)
            }
            try context.save()
        },
        didMigrate: nil
    )
}

// The rest of the app uses the latest version through a typealias
typealias Trip = TripSchemaV2.Trip

let container = try ModelContainer(for: Trip.self, migrationPlan: TripMigrationPlan.self)
```
- `willMigrate` runs with the **old** schema; `didMigrate` runs with the **new** schema (e.g. to populate new fields).
- Use `MigrationStage.lightweight(fromVersion:toVersion:)` for stages that need no custom code.

### Q69. Why use `VersionedSchema` even before you need a migration? `[Senior]`
**Key points:**
- Wrapping your first shipped models in `SchemaV1` from day one makes future migrations straightforward: you'll have a clear, frozen definition of what's on users' devices.
- Retrofitting versioning after several releases (when you don't have exact old definitions) is painful and error-prone.

### Q70. What happens if you rename a property without `originalName`? `[Senior]`
**Key points:**
- SwiftData treats it as **deleting** the old property and **adding** a new one, so existing data in that column is lost (silently, if the new property has a default).
- Always use `@Attribute(originalName: "oldName")` for renames, or a custom migration.

### Q71. How do you change a property's type (e.g. `String` price → `Decimal`)? `[Lead/Expert]`
**Key points:**
- A multi-step custom migration:
  1. V2 adds a new property (`priceDecimal: Decimal?`) alongside the old one.
  2. `didMigrate` converts values from the old property to the new one.
  3. V3 removes the old property (and optionally renames the new one with `originalName`).
- Test migrations against **real copies of production-like stores** from each shipped version, not just fresh installs.

### Q72. How do you test migrations? `[Lead/Expert]`
**Talking points:**
- Keep sample store files created by each shipped app version in your test bundle.
- In tests: copy the old store to a temp URL, open it with the new container + migration plan, and assert data integrity (counts, values, relationships).
- Test upgrade paths that skip versions (V1 → V3), since users don't update every release.
- Run migration tests in CI.

### Q73. What should happen if a migration fails in production? `[Lead/Expert]`
**Talking points:**
- Never ship `fatalError` on container creation without a plan: users get a crash on every launch.
- Strategy: log the error (with breadcrumbs) → back up the store file → attempt recovery (e.g. retry, or fall back to a fresh store if the data can be resynced from the server or iCloud) → inform the user if data might be lost.
- Prevention: migration tests, staged rollouts, and monitoring launch crash rates after each release.

## 9. CloudKit Sync

### Q74. How do you enable iCloud sync with SwiftData? `[Fundamental]`
**Key points:**
1. Add the **iCloud** capability with **CloudKit** and a container (e.g. `iCloud.com.example.Trips`).
2. Add **Background Modes → Remote notifications** (for push-triggered sync).
3. SwiftData automatically syncs the private database when these entitlements exist (`cloudKitDatabase: .automatic`), or specify it explicitly:

```swift
let configuration = ModelConfiguration(cloudKitDatabase: .private("iCloud.com.example.Trips"))
let container = try ModelContainer(for: Trip.self, configurations: configuration)
```
- Use `cloudKitDatabase: .none` for stores that must stay local.

### Q75. What model constraints does CloudKit sync impose? `[Senior]`
**Key points:**
- **No unique constraints** (`@Attribute(.unique)` / `#Unique`), because CloudKit can't enforce uniqueness across devices.
- All properties must be **optional or have default values**.
- All relationships must be **optional** (e.g. `var activities: [Activity]? = []`).
- No `.deny` delete rule.
- Schema changes must be additive once deployed to the production CloudKit environment (you can't delete or rename fields there), so plan carefully.

```swift
@Model
final class Trip {
    var name: String = ""
    var startDate: Date = Date.now
    @Relationship(deleteRule: .cascade, inverse: \Activity.trip)
    var activities: [Activity]? = []
    init(name: String, startDate: Date) {
        self.name = name
        self.startDate = startDate
    }
}
```

### Q76. Which CloudKit databases does SwiftData support? `[Senior]`
**Key points:**
- SwiftData syncs the user's **private** database.
- For **public** or **shared** databases (collaboration, sharing records between users), you still need Core Data with `NSPersistentCloudKitContainer` (or CloudKit APIs directly). Check the latest SwiftData release notes, as this may change.

### Q77. How do you handle duplicates and conflicts with CloudKit sync? `[Lead/Expert]`
**Talking points:**
- Sync is **eventually consistent**, and conflicts resolve as last-writer-wins at the record level.
- Without unique constraints, duplicates can appear (e.g. seed data inserted on two devices before syncing). Mitigations:
  - Don't insert seed/default data on every device; or use deterministic IDs and deduplicate after sync (e.g. using history tracking to detect inserts, then merge duplicates).
  - Prefer user-created data over app-generated defaults in synced stores.
- You can't control exactly when sync happens; design UI to tolerate data arriving later.

### Q78. How do you debug CloudKit sync issues? `[Senior]`
**Talking points:**
- Use the CloudKit Console to inspect records and schema in Development vs Production environments.
- Remember to **deploy the schema to Production** before App Store release; otherwise sync works in development but fails for users.
- Test with two devices signed into the same iCloud account; check device logs for CloudKit/Core Data mirroring messages.
- Verify the user is signed into iCloud and has iCloud Drive enabled for the app.

## 10. Performance

### Q79. What are the most common SwiftData performance problems? `[Senior]`
**Key points:**
- Fetching far more data than needed (large `@Query` results without limits, loading big blobs in lists).
- N+1 relationship faulting in lists.
- Filtering/sorting in memory instead of in the predicate.
- Missing indexes on frequently queried properties.
- Doing imports or heavy processing on the main context.
- Saving after every single insert in large loops.

### Q80. How do you add indexes? `[Senior]`
```swift
@Model
final class Trip {
    #Index<Trip>([\.name], [\.startDate, \.endDate])   // iOS 18: single and compound indexes

    var name: String
    var startDate: Date
    var endDate: Date

    init(name: String, startDate: Date, endDate: Date) {
        self.name = name
        self.startDate = startDate
        self.endDate = endDate
    }
}
```
- Index the properties you filter or sort by often. Indexes speed up reads but slow down writes slightly and increase file size, so don't index everything.

### Q81. Why filter in the predicate rather than in Swift? `[Fundamental]`
```swift
// ❌ Loads every trip into memory, then filters
@Query private var allTrips: [Trip]
var favorites: [Trip] { allTrips.filter(\.isFavorite) }

// ✅ The database returns only matching rows
@Query(filter: #Predicate<Trip> { $0.isFavorite }) private var favorites: [Trip]
```

### Q82. How do you keep large binary data from slowing things down? `[Senior]`
**Key points:**
- `@Attribute(.externalStorage)` for big `Data`.
- Store thumbnails separately from full-size images.
- Put heavy data in a separate related model (e.g. `PhotoAsset`) so list queries don't touch it.
- Use `propertiesToFetch` for list screens that need only a few columns.

### Q83. How do you avoid N+1 queries? `[Senior]`
```swift
var descriptor = FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate)])
descriptor.relationshipKeyPathsForPrefetching = [\.activities]   // load activities with the trips
let trips = try modelContext.fetch(descriptor)
```

### Q84. How do you measure SwiftData performance? `[Senior]`
**Talking points:**
- Enable SQL logging with the launch argument `-com.apple.CoreData.SQLDebug 1` (SwiftData's default store is built on Core Data) to see generated SQL, query counts, and timings.
- Instruments: Time Profiler for main-thread hot spots; Allocations for memory during imports.
- Measure with realistic data volumes (thousands to hundreds of thousands of rows), on older devices.

### Q85. When would you denormalize data in SwiftData? `[Lead/Expert]`
**Key points:**
- When a list needs a value derived from relationships (e.g. activity count, last activity date) and computing it per row triggers faulting.
- Store `activityCount` or `lastUpdated` on the parent and update it when children change. Trade-off: you must keep it consistent (update in one place, e.g. a repository method).

## 11. Architecture & SwiftData Outside SwiftUI

### Q86. Should views use `@Query` directly, or should data go through view models? `[Lead/Expert]`
**Key points (show both sides):**
- **`@Query` in views**: least code, automatic updates, animations, Apple's recommended path for SwiftUI. Downside: views are coupled to persistence; logic in views is harder to unit test.
- **View models / repositories**: testable logic, persistence hidden behind protocols, works for UIKit too. Downside: you lose automatic updates and must refetch on changes; more boilerplate.
- **Common hybrid**: `@Query` for read-only lists in views; mutations and business rules in services/`@ModelActor`s; complex screens use view models that fetch on demand.

### Q87. How would you abstract SwiftData behind a repository? `[Lead/Expert]`
```swift
struct TripSummary: Sendable, Identifiable, Hashable {
    let id: PersistentIdentifier
    let name: String
    let startDate: Date
}

protocol TripRepository: Sendable {
    func upcomingTrips() async throws -> [TripSummary]
    func addTrip(name: String, startDate: Date) async throws
    func deleteTrip(id: PersistentIdentifier) async throws
}

@ModelActor
actor SwiftDataTripRepository: TripRepository {
    func upcomingTrips() throws -> [TripSummary] {
        let now = Date.now
        let descriptor = FetchDescriptor<Trip>(
            predicate: #Predicate { $0.startDate > now },
            sortBy: [SortDescriptor(\.startDate)]
        )
        return try modelContext.fetch(descriptor).map {
            TripSummary(id: $0.persistentModelID, name: $0.name, startDate: $0.startDate)
        }
    }

    func addTrip(name: String, startDate: Date) throws {
        modelContext.insert(Trip(name: name, startDate: startDate))
        try modelContext.save()
    }

    func deleteTrip(id: PersistentIdentifier) throws {
        try modelContext.delete(model: Trip.self, where: #Predicate { $0.persistentModelID == id })
        try modelContext.save()
    }
}
```
- Benefits: domain code never touches `@Model` types; easy mocking; the persistence layer could be swapped (e.g. GRDB, server). Cost: mapping code, and manual change propagation.

### Q88. Is it a good idea to use `@Model` types as your domain models everywhere? `[Lead/Expert]`
**Key points:**
- **Pros**: no mapping layer; models are observable; quick development.
- **Cons**: non-`Sendable` models leak into every layer (Swift 6 friction); domain logic becomes coupled to persistence and context lifetimes; harder to test without a container.
- Senior answer: for small/medium apps, using `@Model` types in the UI layer is pragmatic. For larger apps or complex domains, map to `Sendable` value types at the boundary.

### Q89. How do you use SwiftData in a UIKit app? `[Senior]`
**Key points:**
- Create the container (e.g. in the app or scene delegate) and use `container.mainContext` on the main actor, or `@ModelActor`s for background work.
- No `@Query` and no fetched results controller: fetch manually and refresh when data changes, for instance by observing `ModelContext.didSave`.
- `PersistentIdentifier` is `Hashable` and `Sendable`, so it works well as a diffable data source item identifier.

```swift
final class TripsViewController: UIViewController {
    private let context: ModelContext
    private var dataSource: UICollectionViewDiffableDataSource<Int, PersistentIdentifier>!
    private var saveObserver: NSObjectProtocol?

    init(container: ModelContainer) {
        self.context = container.mainContext
        super.init(nibName: nil, bundle: nil)
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() {
        super.viewDidLoad()
        // ... configure collection view and dataSource ...
        saveObserver = NotificationCenter.default.addObserver(
            forName: ModelContext.didSave, object: nil, queue: .main
        ) { [weak self] _ in
            MainActor.assumeIsolated { self?.reload() }
        }
        reload()
    }

    deinit {
        if let saveObserver { NotificationCenter.default.removeObserver(saveObserver) }
    }

    private func reload() {
        let ids = (try? context.fetchIdentifiers(
            FetchDescriptor<Trip>(sortBy: [SortDescriptor(\.startDate)]))) ?? []
        var snapshot = NSDiffableDataSourceSnapshot<Int, PersistentIdentifier>()
        snapshot.appendSections([0])
        snapshot.appendItems(ids)
        dataSource.apply(snapshot, animatingDifferences: true)
    }
}
```
- Since iOS 18/26, UIKit's automatic observation tracking also works with `@Model` objects (they're `Observable`), so cells can update when a model's properties change.

### Q90. How do you inject the model context into non-view code? `[Senior]`
**Key points:**
- Pass the `ModelContainer` (Sendable) to services and create `@ModelActor`s from it.
- For main-actor services, pass `container.mainContext` explicitly through initializers.
- In SwiftUI, a view can read `@Environment(\.modelContext)` and pass `modelContext.container` to services it creates.

### Q91. How do you sync SwiftData with a REST backend? `[Lead/Expert]`
**Talking points:**
- **DTOs**: decode server JSON into `Sendable`, `Decodable` structs; map to models inside a `@ModelActor`.
- **Upserts**: unique `remoteID` so re-imports update instead of duplicating.
- **Deletions**: server tombstones or full-sync diffs to delete local records missing on the server.
- **Outgoing changes**: an outbox (pending changes table) or history tracking (Q96) to find local inserts/updates/deletes since the last sync token.
- **Conflict policy**: server-wins, client-wins, or per-field merge based on timestamps.
- **Scheduling**: on launch, pull-to-refresh, push notifications, `BGAppRefreshTask`.

## 13. Advanced Features (History, App Groups, Custom Stores, Inheritance)

### Q96. What is SwiftData history tracking, and why use it? `[Lead/Expert]`
**Key points:**
- iOS 18 API to fetch a log of transactions (inserts, updates, deletes) made to the store, including by other processes (widgets, extensions) or other contexts.
- Uses: syncing local changes to a server, updating UI or caches after an extension changed data, and processing changes since a saved **history token**.
- `@Attribute(.preserveValueOnDeletion)` keeps chosen values in the **tombstone** of deleted records (e.g. the remote ID needed to delete it on the server).

```swift
func changes(since token: DefaultHistoryToken?) throws -> (inserted: [PersistentIdentifier], newToken: DefaultHistoryToken?) {
    var descriptor = HistoryDescriptor<DefaultHistoryTransaction>()
    if let token {
        descriptor.predicate = #Predicate { $0.token > token }
    }

    let transactions = try modelContext.fetchHistory(descriptor)
    var inserted: [PersistentIdentifier] = []

    for transaction in transactions {
        for change in transaction.changes {
            switch change {
            case .insert(let insert):
                inserted.append(insert.changedPersistentIdentifier)
            case .update, .delete:
                break   // handle updates and deletions (tombstones) as needed
            @unknown default:
                break
            }
        }
    }
    return (inserted, transactions.last?.token)
}
```
- Persist the latest token (e.g. in `UserDefaults`) and periodically delete old history with `deleteHistory(_:)` to save space.

### Q97. How do you share SwiftData with widgets and app extensions? `[Senior]`
```swift
// Shared configuration used by both the app and the widget extension
enum SharedStore {
    static let container: ModelContainer = {
        let configuration = ModelConfiguration(groupContainer: .identifier("group.com.example.trips"))
        do {
            return try ModelContainer(for: Trip.self, configurations: configuration)
        } catch {
            fatalError("Shared container failed: \(error)")
        }
    }()
}

// In the app, after saving changes that affect the widget
try modelContext.save()
WidgetCenter.shared.reloadAllTimelines()
```
- Add the same App Group capability to the app and extension targets.
- Widgets should read only; heavy writes from extensions can conflict with the app. History tracking helps the app notice changes made by extensions or App Intents.

### Q98. What is a custom `DataStore`? `[Lead/Expert]`
**Key points:**
- iOS 18 lets you plug in your own storage backend by implementing the `DataStore` protocol (with a matching `DataStoreConfiguration`), while keeping SwiftData's modeling and querying APIs.
- Examples: a JSON or document-based file store, or a store backed by an existing database format.
- Trade-off: you must implement fetch/save semantics correctly; it's powerful but advanced, and most apps should use the default store.

### Q99. Does SwiftData support model inheritance? `[Senior]`
**Key points:**
- Yes, starting with **iOS 26**: a `@Model` class can subclass another `@Model` class. Querying the base type returns instances of all subclasses.
- Use it for true "is-a" hierarchies with shared queries (e.g. `Media` → `Movie`, `Podcast`). Prefer composition or an enum type property when subclasses differ only slightly, as inheritance adds schema complexity.

```swift
@available(iOS 26, *)
@Model
class Media {
    var title: String
    init(title: String) { self.title = title }
}

@available(iOS 26, *)
@Model
final class Movie: Media {
    var durationMinutes: Int
    init(title: String, durationMinutes: Int) {
        self.durationMinutes = durationMinutes
        super.init(title: title)
    }
}

// @Query private var allMedia: [Media]   // includes Movie instances
```

### Q100. How would you seed initial data? `[Senior]`
**Key points:**
- Option 1: on first launch, insert seed data if the store is empty (`fetchCount == 0`), on a background actor if large.
- Option 2: ship a prebuilt read-only store in the bundle (`ModelConfiguration(url:allowsSave: false)`), or copy it to Application Support on first launch if it needs to be writable.
- With CloudKit, avoid inserting seed data on every device (it creates duplicates after sync).

### Q101. How do you implement Spotlight search for SwiftData content? `[Senior]`
**Key points:**
- `@Attribute(.spotlight)` marks properties to be indexed for Spotlight.
- For richer control (custom titles, thumbnails, deep links), index items yourself with Core Spotlight (`CSSearchableItem`) or App Intents / App Entities, using a stable identifier to open the right screen.

### Q102. How do you protect sensitive data stored with SwiftData? `[Senior]`
**Key points:**
- iOS Data Protection encrypts files at rest; choose an appropriate protection class for the store's directory (e.g. "complete until first user authentication" is the default for most app data).
- Don't store secrets (tokens, passwords) in SwiftData; use the Keychain.
- With CloudKit, mark sensitive properties `@Attribute(.allowsCloudEncryption)`.
- For extra-sensitive data, encrypt specific fields at the application level before storing.

## 14. SwiftData vs Core Data

### Q103. Compare SwiftData and Core Data. `[Senior]`
| | SwiftData | Core Data |
|---|---|---|
| Minimum OS | iOS 17 | iOS 3+ |
| Model definition | Swift code with `@Model` | `.xcdatamodeld` editor (+ generated classes) |
| Queries | Type-safe `#Predicate`, `FetchDescriptor` | `NSPredicate` format strings, `NSFetchRequest` |
| SwiftUI | `@Query`, Observation | `@FetchRequest`, `@SectionedFetchRequest`, `ObservableObject` |
| UIKit | Manual fetch + notifications | `NSFetchedResultsController` |
| Concurrency | `@ModelActor`, Swift 6 checking | `perform`/`performAndWait`, contexts per queue |
| Child contexts | No | Yes (parent/child) |
| Batch operations | Batch delete | Batch insert/update/delete |
| CloudKit | Private database | Private, public, and shared databases |
| Migration | `VersionedSchema` + `MigrationStage` | Lightweight, mapping models, staged migration (iOS 17) |
| Maturity | Newer, evolving yearly | 20 years, very mature |

### Q104. When would you still choose Core Data for a new project? `[Lead/Expert]`
**Talking points:**
- You must support iOS 16 or earlier.
- You need CloudKit **sharing** or the **public** database.
- You need `NSFetchedResultsController`-driven UIKit lists, sectioned fetches, batch inserts/updates, or derived attributes.
- You have very large datasets and need fine-grained performance control.
- Your team already has deep Core Data expertise and a stable stack.
- Otherwise, SwiftData is usually the better default for new Swift/SwiftUI apps.

### Q105. How do you migrate an existing Core Data app to SwiftData? `[Lead/Expert]`
**Talking points:**
1. Generate `@Model` classes from the existing model (Xcode: open the `.xcdatamodeld`, then **Editor → Create SwiftData Code**).
2. Keep **entity names, attribute names, and types identical** to the current Core Data model version.
3. Point the SwiftData `ModelConfiguration(url:)` at the **existing store file**.
4. Wrap the generated models in a `VersionedSchema` as V1 for future migrations.
5. Migrate screens incrementally; test with real store copies from production-like devices.

### Q106. Can Core Data and SwiftData use the same store at the same time? `[Lead/Expert]`
**Key points:**
- Yes, coexistence is supported, which allows gradual migration.
- Requirements: both stacks point to the same store URL; entity names and schemas match; enable **persistent history tracking** on the Core Data side (`NSPersistentHistoryTrackingKey`), since SwiftData relies on it.
- Avoid class name clashes: name the Core Data `NSManagedObject` subclasses differently (e.g. `CDTrip`) while keeping the entity name `Trip`.

### Q107. What alternatives to SwiftData and Core Data exist, and when might you pick them? `[Lead/Expert]`
**Talking points:**
- **GRDB / SQLite**: full SQL control, excellent performance, value-type records, robust migrations, great for complex queries or large datasets.
- **Realm**: object database with its own sync story. Note that MongoDB deprecated Atlas Device Sync, which affects Realm's long-term sync future.
- **Plain files / Codable**: small, simple data (settings, caches).
- **Server-first with a cache**: when the source of truth is remote and local storage is just a cache.
- Decision factors: data size, query complexity, sync needs, OS targets, team expertise, long-term vendor risk.

## 15. Debugging & Common Crashes

### Q108. How do you inspect what SwiftData is doing? `[Senior]`
**Key points:**
- Launch argument `-com.apple.CoreData.SQLDebug 1` (or `3` for more detail) logs the SQL executed.
- Print the store location (`container.configurations.first?.url`) and open the SQLite file in a database browser. Tables are Core Data-style (`ZTRIP`, `Z_PK`, etc.).
- Add logging around `save()` calls and catch errors instead of using `try?` everywhere.

### Q109. What are the most common SwiftData crashes and their causes? `[Senior]`
| Symptom | Likely cause | Fix |
|---|---|---|
| "Failed to find any currently loaded container" | Model created before any container exists | Create the container first (tests, previews, static data) |
| Crash accessing a model's property | Model was deleted (or its context deallocated) | Check `isDeleted`, drive UI from `@Query`, keep context alive |
| "Illegal attempt to establish a relationship…" | Models from different contexts connected | Refetch both in the same context via IDs |
| Crash on launch after an update | Failed migration (e.g. unique constraint with duplicates, type change) | Versioned schemas, custom migration, migration tests |
| Runtime crash on fetch | Unsupported `#Predicate` expression or sort | Simplify predicate, use stored properties, test predicates |
| Data races / random crashes | Models or contexts used across threads | Use `@ModelActor`, pass `PersistentIdentifier`s, enable Swift 6 checking |

### Q110. Why might a model created in a local `ModelContext` crash later? `[Lead/Expert]`
**Key points:**
- If you create a `ModelContext` inside a function, fetch or insert models, and return those models, the context may be deallocated while the models are still used. Models depend on their context for backing data.
- Keep the context alive for as long as its models are used (store it), or return IDs/DTOs instead.

### Q111. Why isn't my data saved after the app is killed? `[Senior]`
**Key points:**
- Changes in contexts with autosave disabled (background contexts, `ModelActor`s) are lost unless `save()` is called.
- Even with autosave on the main context, killing the app shortly after a change (e.g. during debugging with Xcode's stop button) can lose the latest changes. Call `save()` explicitly after important operations.

### Q112. Why does my UI not update after a background import? `[Senior]`
**Talking points:**
- Did the background context actually call `save()`? Unsaved changes are invisible to other contexts.
- Is the UI using `@Query` (auto-updating) or a one-time manual fetch (needs refresh on `ModelContext.didSave`)?
- On older OS versions, merging background changes into `@Query` had bugs; test on your minimum OS and consider triggering a refresh as a fallback.

## 16. "What's the Output?" Questions

### Q113. Relationship order `[Senior]`
```swift
let playlist = Playlist(name: "Road Trip")
modelContext.insert(playlist)
playlist.songs.append(contentsOf: [songA, songB, songC])   // songs: [Song]
try modelContext.save()
// App relaunches, playlist is fetched again
print(playlist.songs.map(\.title))
```
**Answer:** The order is **not guaranteed** to be `[A, B, C]`. To-many relationships are unordered in the store. Add a `position` property and sort.

### Q114. Unique constraint `[Senior]`
```swift
@Model final class Product {
    @Attribute(.unique) var sku: String
    var price: Decimal
    init(sku: String, price: Decimal) { self.sku = sku; self.price = price }
}

modelContext.insert(Product(sku: "A1", price: 10))
try modelContext.save()
modelContext.insert(Product(sku: "A1", price: 12))
try modelContext.save()

print(try modelContext.fetchCount(FetchDescriptor<Product>()))
```
**Answer:** `1`. The second insert is an **upsert**: the existing `A1` record now has price `12`.

### Q115. Function call inside a predicate `[Fundamental]`
```swift
let upcoming = #Predicate<Trip> { $0.startDate > Date.now }
```
**Answer:** Not supported: `Date.now` is a function call inside the predicate. Capture it first: `let now = Date.now` and compare with `now`.

### Q116. Computed property in a predicate `[Senior]`
```swift
@Model final class Trip {
    var startDate: Date
    var endDate: Date
    var durationDays: Int { Calendar.current.dateComponents([.day], from: startDate, to: endDate).day ?? 0 }
    // ...
}
let longTrips = #Predicate<Trip> { $0.durationDays > 7 }
```
**Answer:** Fails (at compile time or at runtime when translated to SQL), because computed properties aren't stored columns. Persist `durationDays` as a real property, or filter in memory for small datasets.

### Q117. `@Transient` after refetch `[Senior]`
```swift
trip.isSelected = true          // @Transient var isSelected = false
try modelContext.save()
// Later, the trip is fetched in a new context
print(otherContextTrip.isSelected)
```
**Answer:** `false`. Transient properties aren't persisted, so they reset to their default when the model is materialized again.

### Q118. Background insert without saving `[Senior]`
```swift
@ModelActor
actor Importer {
    func addSample() {
        modelContext.insert(Trip(name: "Sample", startDate: .now))
    }
}

try await Importer(modelContainer: container).addSample()
// A view uses @Query private var trips: [Trip]
```
**Answer:** The new trip doesn't appear in the view, and it's lost when the actor is released. Background contexts must call `try modelContext.save()`.

### Q119. `@Query` in a view model `[Senior]`
```swift
@Observable
final class TripsViewModel {
    @Query var trips: [Trip]
}
```
**Answer:** Doesn't work. `@Query` only functions inside SwiftUI views (it needs the view's environment). Fetch manually with a `ModelContext` in the view model, or keep `@Query` in the view.

### Q120. Passing a model to another actor `[Senior]`
```swift
let trip = trips[0]
Task.detached {
    await syncService.upload(trip)
}
```
**Answer:** In Swift 6 mode: a compile error, because `Trip` isn't `Sendable`. In Swift 5 mode: compiles but is a data race. Pass `trip.persistentModelID` and refetch on the other actor.

### Q121. Temporary identifiers `[Lead/Expert]`
```swift
let trip = Trip(name: "Lisbon", startDate: .now)
modelContext.insert(trip)
let tripID = trip.persistentModelID

let name = try await backgroundService.tripName(for: tripID)   // fetches by ID in its own context
print(name ?? "not found")
```
**Answer:** Likely `not found`. Before saving, the identifier is **temporary** and the unsaved object exists only in the main context. Call `try modelContext.save()` before passing IDs to other contexts.

### Q122. Renaming a property `[Senior]`
```swift
// Version 1 shipped with:  var title: String
// Version 2 changes it to: var name: String = ""
```
**Answer:** After updating, every existing record's `name` is `""`. SwiftData sees a removed `title` and a new `name`, so the old data is dropped. Use `@Attribute(originalName: "title") var name: String`.

### Q123. `rollback()` on the main context `[Senior]`
```swift
// Screen A edits trip.name (unsaved). Screen B, still open, edits another trip's notes (unsaved).
// The user taps Cancel on Screen A, which calls:
modelContext.rollback()
```
**Answer:** **Both** sets of unsaved edits are discarded, including Screen B's. `rollback()` affects the whole context. Use drafts or a separate editing context for cancellable edits.

### Q124. Deleted model in a detail view `[Senior]`
```swift
// TripDetailView(trip: trip) is on screen.
// Meanwhile, a background sync deletes that trip and saves.
// The user taps a button that reads trip.name.
```
**Answer:** Risk of a crash or invalid data, because the model's backing data no longer exists. Check `trip.isDeleted` / `trip.modelContext == nil`, and dismiss or update the detail screen when its model is removed.

## 18. Senior / Lead Scenario Questions

### Q125. You're starting a new app. How do you choose a persistence technology? `[Lead/Expert]`
**Talking points:**
- **Requirements first**: data volume, query complexity, offline needs, sync (iCloud private? sharing? custom backend?), minimum OS, extensions/widgets.
- **SwiftData** if: iOS 17+ target, SwiftUI-centric app, moderate data sizes, private iCloud sync or custom backend sync.
- **Core Data** if: older OS support, CloudKit sharing/public DB, `NSFetchedResultsController`-heavy UIKit, batch operations.
- **GRDB/SQLite** if: complex SQL, very large datasets, maximum control and predictable performance.
- Prototype the riskiest requirement (e.g. sync or a complex query) before committing; record the decision in an ADR.

### Q126. Your Core Data app has 2 million users. How would you migrate to SwiftData? `[Lead/Expert]`
**Talking points:**
- **Why migrate?** Quantify benefits (developer speed, Swift 6 safety, SwiftUI integration) vs risk. "Not migrating" is a valid answer.
- **Plan**: generate matching `@Model` classes; coexistence on the same store with persistent history tracking enabled; migrate read-only screens first, then writes; keep Core Data for unsupported features.
- **Safety**: test with real store copies from every shipped schema version; staged rollout with feature flags; monitor launch crashes and data integrity metrics; rollback plan.
- **Team**: training, coding guidelines for contexts/actors, review checklist.

### Q127. Design an offline-first app backed by a REST API. `[Lead/Expert]`
**Talking points:**
- SwiftData is the **local source of truth**; the UI reads only from it (`@Query`).
- **Pull sync** in a `@ModelActor`: DTOs → upsert by `remoteID`; handle server deletions; store a sync cursor.
- **Push sync**: an outbox of pending mutations or history tracking since the last token; retry with exponential backoff; idempotent requests.
- **Conflicts**: version numbers or `updatedAt` timestamps; a clear policy (server-wins by default, user-visible merge for important data).
- **Triggers**: app launch, foreground, pull-to-refresh, silent push, background refresh.
- **Testing**: in-memory containers, mocked API, tests for conflict and deletion cases.

### Q128. After a release, crash reports spike with launch crashes in `ModelContainer` creation. What do you do? `[Lead/Expert]`
**Talking points:**
1. **Contain**: pause the phased rollout; assess how many users are affected.
2. **Diagnose**: check the error (migration failure? unique constraint violation? missing version in the migration plan?); reproduce with a store from the previous version.
3. **Fix**: add/repair the migration stage (e.g. de-duplicate before applying uniqueness), and replace `fatalError` with recovery handling (back up store, recreate, resync).
4. **Prevent**: migration tests with stored fixtures for every shipped version in CI; a release checklist item for schema changes; better launch crash monitoring.
5. **Communicate**: status updates to stakeholders and, if data loss is possible, to users.

### Q129. A list of 100,000 records is slow. How do you fix it? `[Lead/Expert]`
**Talking points:**
- Measure with SQL debug logging and Instruments.
- Push filtering and sorting into predicates; add `#Index` for those properties.
- Limit results (pagination with `fetchLimit`, or keyset pagination); use `fetchCount` for totals.
- Fetch only needed properties; move heavy data (images, long text) to separate models or external storage.
- Avoid N+1 by prefetching relationships or denormalizing summary values.
- Keep row views cheap; avoid computing derived values per row in `body`.

### Q130. How would you design data sharing between the app, widgets, and App Intents? `[Lead/Expert]`
**Talking points:**
- A shared Swift package with the models and a single `ModelContainer` factory using an App Group configuration.
- Writes mainly from the app and App Intents (which run in-process or in an extension); widgets read only.
- After writes, reload widget timelines; use history tracking in the app to react to changes made by intents/extensions.
- Keep the shared schema versioned; all targets must ship with the same schema version.

### Q131. What do you look for when reviewing SwiftData code? `[Lead/Expert]`
**Talking points:**
- **Concurrency**: no models/contexts crossing actors; background work in `@ModelActor`; IDs or DTOs passed across boundaries.
- **Saving**: explicit `save()` in background contexts and after critical operations; errors handled, not swallowed with `try?`.
- **Queries**: filtering/sorting in predicates; no unsupported expressions; limits on large result sets; indexes where needed.
- **Modeling**: correct delete rules and inverses; explicit ordering where needed; unique constraints (unless CloudKit); defaults for new properties.
- **Migrations**: schema changes wrapped in a new `VersionedSchema`; renames use `originalName`; migration tests added.
- **Testability**: in-memory containers in tests; repositories or services for business logic.

### Q132. How would you explain `ModelContext` and `ModelActor` to a junior engineer? `[Senior]`
**Talking points:**
- Analogy: the `ModelContainer` is the **library**. A `ModelContext` is a **desk** where you take books out and write notes; nothing changes in the library until you return them (`save()`). Each desk belongs to one person (actor); you can't hand your open book to someone at another desk, but you can give them the **catalog number** (`PersistentIdentifier`) so they fetch their own copy.
- A `@ModelActor` is a colleague with their own desk working in another room (background), so the front desk (main actor/UI) stays free for customers.

### Final Tips
- SwiftData interviews reward **production experience**: unordered relationships, temporary IDs, `@ModelActor` threading behavior, migration failures, CloudKit constraints. Prepare a story for at least two of these.
