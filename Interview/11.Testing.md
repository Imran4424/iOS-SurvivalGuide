## 1. Testing Fundamentals

### Q1. Why do we write automated tests? `[Fundamental]`
**Key points:**
- **Confidence to change code**: refactor and add features without breaking existing behavior.
- **Faster feedback** than manual testing; regressions caught before users see them.
- **Documentation** of intended behavior ("this is how checkout handles an expired coupon").
- **Better design**: code that's easy to test is usually loosely coupled and well-structured.
- **Lower cost of bugs**: the earlier a bug is found, the cheaper it is to fix.

### Q2. What are the main types of tests in an iOS project? `[Fundamental]`
| Type | Scope | Speed | Example |
|---|---|---|---|
| **Unit** | One type/function in isolation | Milliseconds | `CartTotalCalculator`, view model state transitions |
| **Integration** | Several real components together | Fast–medium | API client + `URLProtocol` stub; repository + in-memory database |
| **Snapshot** | Rendered UI compared to a reference image | Medium | Product card in light/dark, large text |
| **UI (end-to-end)** | The whole app driven like a user | Slow (seconds–minutes) | Log in → add to cart → checkout |
| **Performance** | Timing/memory of code paths | Medium–slow | Launch time, parsing a large feed |
| **Contract** | Client and API agree on the schema | Fast | Fixtures validated against an OpenAPI spec |
| **Manual / exploratory** | Human testing | Slow | New feature exploration, usability |

### Q3. What is the test pyramid? `[Fundamental]`
```
           ▲   UI tests: a few critical user journeys
          ▲▲▲  Snapshot tests: key screens and components
        ▲▲▲▲▲▲ Integration tests: networking, persistence, feature flows
    ▲▲▲▲▲▲▲▲▲▲▲ Unit tests: business logic, view models, mappers, formatters
```
**Key points:**
- Many fast, reliable unit tests at the base; fewer, slower, more brittle tests at the top.
- Anti-pattern: the **ice-cream cone** (mostly manual and UI tests, few unit tests), which leads to slow, flaky feedback.
- Some teams prefer a "testing trophy" emphasizing integration tests. The principle is the same: maximize confidence per second of test time.

### Q4. What makes a good unit test? `[Fundamental]`
**Key points:** The **FIRST** principles:
- **Fast**: milliseconds, so developers run them constantly.
- **Isolated / Independent**: no shared state; any order; can run in parallel.
- **Repeatable**: same result every time (no real network, time, randomness without seeds).
- **Self-validating**: passes or fails automatically, with no manual inspection.
- **Timely**: written alongside (or before) the code.
- Plus: tests **one behavior**, has a **descriptive name**, and fails with a **clear message**.

### Q5. What is the Arrange-Act-Assert pattern? `[Fundamental]`
```swift
@Test func applyingCouponReducesTotal() {
    // Arrange
    var cart = Cart(items: [.fixture(price: 100)])
    let coupon = Coupon(code: "SAVE10", percentOff: 10)

    // Act
    cart.apply(coupon)

    // Assert
    #expect(cart.total == 90)
}
```
- Also called **Given-When-Then**. Keeping the three parts visually separate makes tests easy to read and review.

### Q6. What should (and shouldn't) be unit tested? `[Senior]`
**Key points:**
- **Test**: business rules, calculations, validation, state machines, view model state transitions, mapping/decoding, error handling, edge cases, and bug fixes (regression tests).
- **Usually don't unit test**: trivial getters/setters, Apple framework behavior, pure layout code (use snapshot tests), or private implementation details (test through the public API).
- Prioritize by **risk and change frequency**: checkout logic deserves more tests than a static About screen.

### Q7. What is the difference between testing behavior and testing implementation? `[Senior]`
**Key points:**
- **Behavior tests** check **what** the code does (outputs, state changes, side effects at boundaries). They survive refactoring.
- **Implementation tests** check **how** it does it (which private methods were called, in which order, internal data structures). They break on every refactor even when behavior is unchanged, which discourages improving the code.
- Prefer behavior tests; verify interactions (mocks) only at **boundaries** where the interaction itself is the behavior (e.g. "payment was charged once", "analytics event was sent").

### Q8. What is the difference between verification and validation? `[Senior]`
**Key points:**
- **Verification**: "Are we building the product right?" Does the code meet its specification? (Unit, integration, and UI tests.)
- **Validation**: "Are we building the right product?" Does it meet users' needs? (Usability testing, beta feedback, A/B tests, product reviews.)
- Automated tests mostly verify; validation needs real users and product feedback.

### Q9. How do testing responsibilities split between developers and QA? `[Lead/Expert]`
**Key points:**
- **Developers** own automated tests for their code (unit, integration, snapshot, and key UI tests) as part of the definition of done ("shift left").
- **QA engineers** focus on test strategy, exploratory testing, edge cases, test automation infrastructure, release testing, and representing the user's perspective.
- Close collaboration: QA joins planning to define acceptance criteria early; developers write tests against them; repetitive manual regression is progressively automated.

### Q10. How do you decide how much testing is enough? `[Lead/Expert]`
**Key points:**
- Based on **risk**: impact of a failure (payments, data loss, privacy) × likelihood (complex logic, frequent changes, many contributors).
- Signals of sufficiency: low escaped-defect rate, confidence to refactor, fast CI, few hotfixes.
- Coverage numbers are an input, not a goal (Q128).
- Balance against delivery speed: tests should make the team **faster** over time; if they slow it down, they're the wrong tests (too brittle, too slow, testing implementation).

## 2. Designing Testable Code

### Q11. What makes code hard to test? `[Fundamental]`
**Key points:**
- **Hidden dependencies**: singletons (`APIClient.shared`), `UserDefaults.standard`, `Date()`, `UUID()`, `URLSession.shared` used directly inside logic.
- **Logic inside UI classes** (view controllers, SwiftUI views) that require rendering to exercise.
- **Global mutable state** shared between tests.
- **Large types with many responsibilities**.
- **Non-deterministic behavior**: real time, randomness, concurrency without control.
- **Side effects mixed with logic** (computing and saving/sending in the same function).

### Q12. How does dependency injection improve testability? `[Fundamental]`
```swift
// ❌ Hard to test: hidden network and storage dependencies
@MainActor
final class ProfileViewModel {
    func load() async {
        let profile = try? await APIClient.shared.fetchProfile()
        UserDefaults.standard.set(profile?.name, forKey: "lastName")
    }
}

// ✅ Testable: dependencies are explicit and replaceable
@MainActor
final class ProfileViewModelTestable {
    private let api: ProfileAPI
    private let store: ProfileCache

    init(api: ProfileAPI, store: ProfileCache) {
        self.api = api
        self.store = store
    }
}
```
- Tests pass stubs/fakes; production passes real implementations from the composition root (Architecture file, Q71–Q80).

### Q13. How do you control time, randomness, and identifiers in tests? `[Senior]`
```swift
struct CouponValidator: Sendable {
    var now: @Sendable () -> Date = { .now }

    func isValid(_ coupon: Coupon) -> Bool {
        coupon.expiresAt > now()
    }
}

struct DraftFactory: Sendable {
    var makeID: @Sendable () -> UUID = { UUID() }
    var now: @Sendable () -> Date = { .now }

    func makeDraft(title: String) -> Draft {
        Draft(id: makeID(), title: title, createdAt: now())
    }
}

@Test func expiredCouponIsInvalid() {
    let fixedNow = Date(timeIntervalSince1970: 1_700_000_000)
    let validator = CouponValidator(now: { fixedNow })
    let coupon = Coupon(code: "OLD", expiresAt: fixedNow.addingTimeInterval(-1))
    #expect(validator.isValid(coupon) == false)
}
```
- For async waiting, inject a `Clock` (Q61). For randomness, inject a seeded `RandomNumberGenerator` (Q118).

### Q14. What is the "Humble Object" pattern? `[Senior]`
**Key points:**
- Split code that's hard to test (UI, system frameworks) into a **thin, "humble" layer** with almost no logic, and a **testable layer** containing the logic.
- Examples: a view controller that only renders a view model's state and forwards events; a `CLLocationManager` delegate wrapper that only forwards updates to a testable `LocationTracker`.
- The humble layer is covered by a few UI/snapshot tests; the logic layer by many fast unit tests.

### Q15. What is "functional core, imperative shell"? `[Lead/Expert]`
```swift
// Functional core: pure, deterministic, trivially testable
enum CartReducer {
    static func total(items: [CartItem], coupon: Coupon?, taxRate: Decimal) -> Decimal {
        let subtotal = items.reduce(0) { $0 + $1.price * Decimal($1.quantity) }
        let discounted = coupon.map { subtotal * (1 - Decimal($0.percentOff) / 100) } ?? subtotal
        return (discounted * (1 + taxRate)).rounded(scale: 2)
    }
}

// Imperative shell: performs I/O and calls the core
@MainActor
final class CartViewModel {
    private(set) var total: Decimal = 0
    private let api: CartAPI

    init(api: CartAPI) { self.api = api }

    func refresh() async throws {
        let cart = try await api.fetchCart()                       // side effect
        total = CartReducer.total(items: cart.items, coupon: cart.coupon, taxRate: cart.taxRate)
    }
}

extension Decimal {
    func rounded(scale: Int) -> Decimal {
        var value = self, result = Decimal()
        NSDecimalRound(&result, &value, scale, .bankers)
        return result
    }
}
```
- Most logic lives in pure functions with exhaustive unit tests; the thin shell needs only a few integration tests.

### Q16. How do you make system APIs (UserDefaults, FileManager, NotificationCenter) testable? `[Senior]`
**Key points:**
- **Inject instances** instead of using globals: pass `UserDefaults(suiteName:)`, a `FileManager`, a `NotificationCenter()` instance, a temporary directory URL.
- **Wrap behind small protocols** when you need fakes or the API is awkward (location, notifications authorization, biometrics).

```swift
// Inject a dedicated UserDefaults suite per test
@Suite final class SettingsStoreTests {
    let suiteName = "SettingsStoreTests-\(UUID().uuidString)"
    let defaults: UserDefaults

    init() {
        defaults = UserDefaults(suiteName: suiteName)!
    }

    deinit {
        defaults.removePersistentDomain(forName: suiteName)     // clean up after each test
    }

    @Test func persistsDarkModePreference() {
        let store = SettingsStore(defaults: defaults)
        store.isDarkModeEnabled = true
        #expect(SettingsStore(defaults: defaults).isDarkModeEnabled)
    }
}
```

### Q17. Should you create protocols just for testing? `[Lead/Expert]`
**Key points:**
- Protocols at **real boundaries** (network, persistence, analytics, payments, system services) are worth it: they enable test doubles and decouple layers.
- Protocols for **pure logic** with a single implementation add indirection without benefit. Test the real type directly.
- Alternatives: closure-based dependencies (`struct Client { var fetch: () async throws -> Data }`), injecting values instead of services, and using real lightweight implementations (in-memory stores) as fakes.

### Q18. How do you test code that uses singletons you can't remove yet? `[Senior]`
**Key points:**
- Introduce a **seam**: constructor injection with the singleton as the **default argument**, so existing call sites don't change.

```swift
final class ReceiptPrinter {
    private let taxes: TaxCalculating
    private let printer: Printing

    init(taxes: TaxCalculating = TaxService.shared,       // production default unchanged
         printer: Printing = PrinterSDKAdapter()) {
        self.taxes = taxes
        self.printer = printer
    }

    func printReceipt(for order: Order) {
        printer.print("Total: \(taxes.total(for: order))")
    }
}

// Tests inject fakes
let printer = SpyPrinter()
ReceiptPrinter(taxes: FixedTaxes(rate: 0.1), printer: printer).printReceipt(for: .fixture())
```
- Then migrate call sites to explicit injection over time (see Section 20).

### Q19. Does `@testable import` make testing private code acceptable? `[Senior]`
**Key points:**
- `@testable import` exposes `internal` (not `private`/`fileprivate`) declarations to tests.
- Testing `internal` helpers is fine when they represent meaningful units (a parser, a formatter). But if you feel the need to test a **private** method, it's often a sign the logic deserves its **own type** with a public/internal API.
- Prefer testing through the public interface; extract classes rather than making things non-private just for tests.

### Q20. How does architecture affect testability? `[Senior]`
**Key points:**
- MVVM/MVP/TCA/Clean architectures move logic out of views into plain objects or reducers, testable without UI.
- Coordinators/routers make navigation testable as data (route arrays) rather than view controller pushes.
- Repositories and protocols at data boundaries enable fakes.
- Modularization lets tests build and run per module quickly.
- (See the Architecture file, Section 17.)

## 3. Test Doubles & Mocking

### Q21. What kinds of test doubles exist? `[Senior]`
| Double | Purpose | Example |
|---|---|---|
| **Dummy** | Fills a parameter; never used | `DummyLogger` passed to satisfy an initializer |
| **Stub** | Returns canned responses | `StubWeatherAPI(result: .success(.sunny))` |
| **Spy** | Records calls for later assertions | `SpyAnalytics` capturing tracked events |
| **Mock** | Pre-programmed expectations; verifies interactions itself | Mock that fails if `charge` is called twice |
| **Fake** | Working lightweight implementation | In-memory repository, in-memory database |

- Colloquially, many people call all of these "mocks." Using precise terms in an interview shows depth. (Examples: Architecture file, Q117.)

### Q22. Write a configurable stub-and-spy for a protocol. `[Senior]`
```swift
protocol PaymentGateway: Sendable {
    func charge(amount: Decimal, token: String) async throws -> Receipt
}

actor PaymentGatewaySpy: PaymentGateway {
    enum Call: Equatable { case charge(amount: Decimal, token: String) }

    private(set) var calls: [Call] = []
    private let result: Result<Receipt, Error>

    init(result: Result<Receipt, Error> = .success(.fixture())) {
        self.result = result
    }

    func charge(amount: Decimal, token: String) async throws -> Receipt {
        calls.append(.charge(amount: amount, token: token))
        return try result.get()
    }
}

@Test func checkoutChargesExactlyOnce() async throws {
    let gateway = PaymentGatewaySpy()
    let checkout = CheckoutService(gateway: gateway)

    _ = try await checkout.placeOrder(cart: .fixture(total: 42), token: "tok_test")

    #expect(await gateway.calls == [.charge(amount: 42, token: "tok_test")])
}
```
- Using an `actor` keeps the spy `Sendable` and race-free in Swift 6.

### Q23. Why doesn't Swift have Mockito-style mocking frameworks like Java? `[Senior]`
**Key points:**
- Swift has limited runtime reflection and no dynamic proxies for pure Swift types, so frameworks can't generate mocks at runtime.
- Options:
  - **Hand-written doubles** (clear, flexible, most common).
  - **Code generation** (e.g. Sourcery, Mockolo) or **macros** (libraries offering a `@Mockable`-style macro on protocols).
  - **Closure-based dependencies**, which make doubles trivial without generation.
- Objective-C-based mocking (OCMock) works only for `NSObject`-based APIs.

### Q24. What is the closure-based dependency approach, and how does it simplify testing? `[Lead/Expert]`
```swift
struct WeatherClient: Sendable {
    var forecast: @Sendable (_ city: String) async throws -> Forecast
}

extension WeatherClient {
    static let live = WeatherClient { city in try await LiveWeatherAPI().forecast(city: city) }
    static let failing = WeatherClient { _ in throw URLError(.notConnectedToInternet) }
}

import Synchronization

/// A tiny thread-safe recorder for values captured inside @Sendable closures
final class Recorder<Value: Sendable>: Sendable {
    private let storage = Mutex<[Value]>([])
    func record(_ value: Value) { storage.withLock { $0.append(value) } }
    var values: [Value] { storage.withLock { $0 } }
}

@MainActor
@Test func showsForecastForCity() async {
    let requestedCities = Recorder<String>()
    let client = WeatherClient { city in
        requestedCities.record(city)                       // inline spy
        return Forecast(temperature: 21, condition: .sunny)
    }
    let viewModel = WeatherViewModel(client: client)

    await viewModel.load(city: "Lisbon")

    #expect(requestedCities.values == ["Lisbon"])
    #expect(viewModel.temperatureText == "21°")
}
```
- Each test builds exactly the behavior it needs inline, with no extra mock types. In Swift 6, `@Sendable` closures can't mutate captured local `var`s, hence the small `Mutex`-backed recorder (libraries such as swift-concurrency-extras offer a similar `LockIsolated` type).

### Q25. What is over-mocking, and why is it harmful? `[Senior]`
**Key points:**
- Mocking every collaborator, including value types and simple helpers, so tests verify a web of interactions instead of outcomes.
- Problems: tests break on refactors, pass even when the real integration is broken, and become hard to read.
- Guidelines: use **real objects** for value types and pure logic; **fakes** for complex boundaries (in-memory DB); **mocks/spies** only where the interaction is the observable behavior.

### Q26. When should you use a fake instead of a mock? `[Senior]`
**Key points:**
- When the collaborator has **state and behavior** that matter across multiple calls (repositories, key-value stores, caches, sync engines).
- A fake (e.g. `InMemoryOrderRepository`) supports realistic sequences (save then fetch) without scripting every call, making tests read like real usage.
- Fakes need their own tests or contract tests to stay faithful to the real implementation.

### Q27. What are contract tests for test doubles? `[Lead/Expert]`
**Key points:**
- A shared test suite that runs against **both** the real implementation and the fake, ensuring the fake behaves like the real thing.

```swift
protocol NoteStore: Sendable {
    func save(_ note: Note) async throws
    func note(id: Note.ID) async throws -> Note?
}

enum NoteStoreContract {
    static func savesAndLoads(_ store: some NoteStore) async throws {
        let note = Note.fixture()
        try await store.save(note)
        #expect(try await store.note(id: note.id) == note)
    }
}

@Test func inMemoryStoreSatisfiesContract() async throws {
    try await NoteStoreContract.savesAndLoads(InMemoryNoteStore())
}

@Test func sqliteStoreSatisfiesContract() async throws {
    try await NoteStoreContract.savesAndLoads(try SQLiteNoteStore.inMemory())
}
```

### Q28. How do you build test data efficiently? `[Senior]`
```swift
extension Product {
    static func fixture(
        id: String = "p_1",
        name: String = "Desk Lamp",
        price: Decimal = 49.99,
        isAvailable: Bool = true
    ) -> Product {
        Product(id: id, name: name, price: price, isAvailable: isAvailable)
    }
}

// Each test specifies only what matters for its scenario
let soldOut = Product.fixture(isAvailable: false)
let expensive = Product.fixture(price: 1_999)
```
**Key points:**
- **Fixture factories / test data builders** with sensible defaults keep tests short and resilient to model changes (adding a property updates one place).
- **JSON fixtures** captured from real API responses for decoding and networking tests.
- Avoid huge shared "object mothers" that every test depends on; keep fixtures close to the domain they describe.

## 4. XCTest

### Q29. What is the structure of an XCTest test case? `[Fundamental]`
```swift
import XCTest
@testable import Shop

final class CartTests: XCTestCase {
    private var cart: Cart!

    override func setUp() {
        super.setUp()
        cart = Cart()                         // fresh state before each test
    }

    override func tearDown() {
        cart = nil
        super.tearDown()
    }

    func test_addItem_increasesTotal() {
        cart.add(.fixture(price: 10), quantity: 2)
        XCTAssertEqual(cart.total, 20)
    }

    func test_checkout_withEmptyCart_throwsEmptyError() {
        XCTAssertThrowsError(try cart.checkout()) { error in
            XCTAssertEqual(error as? CartError, .empty)
        }
    }
}
```
- Test methods must start with `test`. XCTest creates a **new instance of the test case class for each test method**, and `setUp`/`tearDown` run around each test.

### Q30. What are the most important XCTest assertions? `[Fundamental]`
```swift
XCTAssertEqual(total, 20)                          // equality (with a clear failure message)
XCTAssertEqual(price, 9.99, accuracy: 0.001)       // floating point
XCTAssertTrue(isValid); XCTAssertFalse(isLoading)
XCTAssertNil(error); XCTAssertNotNil(user)
let user = try XCTUnwrap(optionalUser)             // fails (doesn't crash) if nil
XCTAssertThrowsError(try parse(bad)) { error in XCTAssertEqual(error as? ParseError, .invalid) }
XCTAssertNoThrow(try parse(good))
XCTFail("Should not reach here")
```
- Prefer `XCTAssertEqual(a, b)` over `XCTAssertTrue(a == b)`: it prints both values on failure.
- Use `XCTUnwrap` instead of force unwraps, which would crash the whole test run.

### Q31. How do you write async tests in XCTest? `[Fundamental]`
```swift
final class ProfileServiceTests: XCTestCase {
    override func setUp() async throws {             // async setUp is supported
        try await super.setUp()
    }

    func test_fetchProfile_decodesName() async throws {
        let service = ProfileService(api: StubProfileAPI(json: Fixtures.profile))
        let profile = try await service.fetchProfile()
        XCTAssertEqual(profile.name, "Ana")
    }

    @MainActor
    func test_viewModel_load_setsState() async {
        let viewModel = ProfileViewModel(api: StubProfileAPI(json: Fixtures.profile))
        await viewModel.load()
        XCTAssertEqual(viewModel.name, "Ana")
    }
}
```

### Q32. How do expectations work in XCTest? `[Senior]`
```swift
func test_uploader_callsCompletionOnce() async {
    let completion = expectation(description: "completion called")
    completion.expectedFulfillmentCount = 1
    completion.assertForOverFulfill = true            // fail if called more than once

    let uploader = Uploader(api: StubUploadAPI())
    uploader.upload(.fixture()) { _ in completion.fulfill() }

    await fulfillment(of: [completion], timeout: 1)   // use this in async tests, not wait(for:)
}

func test_cancelledRequest_neverCallsCompletion() {
    let notCalled = expectation(description: "completion should not be called")
    notCalled.isInverted = true                       // passes only if NOT fulfilled within the timeout

    let task = Loader().load { _ in notCalled.fulfill() }
    task.cancel()

    wait(for: [notCalled], timeout: 0.5)
}
```
**Key points:**
- Expectations are for **callback-based** code. For `async` code, just `await` the result.
- `wait(for:)` blocks the thread and must not be used inside `async` test methods (it can deadlock); use `await fulfillment(of:timeout:)`.
- Keep timeouts short with controlled dependencies; long timeouts hide slowness and flakiness.

### Q33. How do `setUp`, `tearDown`, and `addTeardownBlock` differ? `[Senior]`
**Key points:**
- `setUp()` / `setUpWithError()` / `setUp() async throws`: run before each test.
- `tearDown()` variants: run after each test.
- `addTeardownBlock { }`: registers cleanup from inside a test or helper, run after the test (in reverse order of registration). Great for helpers that create resources (temporary files, leak checks).
- `class func setUp()` / `tearDown()`: once per test class (use sparingly; shared state risks order dependence).

### Q34. How do you skip tests or mark expected failures in XCTest? `[Senior]`
```swift
func test_widgetRendering() throws {
    try XCTSkipUnless(ProcessInfo.processInfo.isiOSAppOnMac == false, "Not supported on Mac")
    // ...
}

func test_knownBug() {
    XCTExpectFailure("Rounding bug tracked in JIRA-123") {
        XCTAssertEqual(PriceRounder.round(2.675), 2.68)
    }
}
```
- `XCTSkip` reports the test as skipped (not passed or failed). `XCTExpectFailure` documents known issues without hiding them, and alerts you when the bug is fixed (the expected failure stops failing).

### Q35. What does `continueAfterFailure` do? `[Fundamental]`
**Key points:**
- Default `true`: the test continues after an assertion fails, reporting multiple failures.
- Set to `false` (common in UI tests) to stop at the first failure, avoiding cascades of meaningless failures after the app is in an unexpected state.
- In Swift Testing, `#require` provides this behavior per assertion.

### Q37. How do you test that code calls `fatalError` or `precondition`? `[Lead/Expert]`
**Key points:**
- In XCTest on iOS, a trap crashes the test process, so you can't assert on it directly.
- Options: refactor to throw errors for recoverable conditions; inject the failure handler (e.g. a closure that defaults to `fatalError` but can be replaced in tests); or, on platforms that support it (macOS/Linux), Swift Testing **exit tests** (Swift 6.2) run the code in a child process and assert on how it exited. Exit tests aren't available on iOS.

### Q38. Can XCTest and Swift Testing coexist? `[Fundamental]`
**Key points:**
- Yes. Both can live in the **same test target** and run together in Xcode and CI. Teams typically write new unit tests in Swift Testing and migrate XCTest gradually.
- **Don't mix assertion APIs** within one test (no `XCTAssert` inside `@Test`, no `#expect` inside an `XCTestCase` method).
- UI tests (XCUITest) and performance tests (`measure`) still require XCTest.

## 5. Swift Testing

### Q39. What is Swift Testing, and why was it introduced? `[Fundamental]`
**Key points:**
- Apple's modern, open-source testing library (Xcode 16+), designed around Swift features: **macros**, **async/await**, **concurrency**, and **value types**.
- Improvements over XCTest:
  - One expressive `#expect` macro that captures the full expression and sub-values on failure (no family of `XCTAssert*` functions).
  - Tests are plain functions marked `@Test`, optionally grouped in `@Suite` types (structs are fine).
  - Built-in **parameterized tests**, **traits** (tags, conditions, time limits, bugs), and **parallel execution by default**.
  - Works on Apple platforms, Linux, and Windows.

### Q40. Show a basic Swift Testing test and suite. `[Fundamental]`
```swift
import Testing
@testable import Shop

@Suite("Cart")
struct CartTests {
    @Test("Adding items increases the total")
    func addingItemsIncreasesTotal() {
        var cart = Cart()
        cart.add(.fixture(price: 10), quantity: 2)
        #expect(cart.total == 20)
    }

    @Test func emptyCartHasZeroTotal() {
        #expect(Cart().total == 0)
    }
}
```
- A **new suite instance** is created for each test, so stored properties initialized in the suite are fresh per test.
- Display names (`@Test("…")`) appear in Xcode's test navigator and reports.

### Q41. What is the difference between `#expect` and `#require`? `[Fundamental]`
```swift
@Test func decodesFirstProduct() throws {
    let products = try JSONDecoder().decode([Product].self, from: Fixtures.productsJSON)

    #expect(products.count == 3)                 // records a failure, test continues

    let first = try #require(products.first)     // unwraps; stops the test if nil
    try #require(first.price > 0)                // stops if the condition is false
    #expect(first.name == "Desk Lamp")
}
```
**Key points:**
- `#expect` records a failure and **continues**, good for checking several independent properties.
- `#require` **throws** on failure, ending the test. Use it for preconditions (unwrapping optionals, required state) where continuing makes no sense.
- Both show the **expression and actual values** on failure (e.g. `products.count → 2 == 3`).

### Q43. What are parameterized tests, and how do you write them? `[Senior]`
```swift
@Test("Email validation", arguments: [
    ("ana@example.com", true),
    ("no-at-sign.com", false),
    ("", false),
    ("ana@", false),
])
func emailValidation(input: String, isValid: Bool) {
    #expect(EmailValidator.isValid(input) == isValid)
}

// Two collections: runs every combination (cartesian product)
@Test(arguments: [Currency.usd, .eur, .jpy], [0, 1, 1_000_000])

    #expect(!PriceFormatter(currency: currency).format(Decimal(amount)).isEmpty)
}
```

**Key points:**

- Replaces copy-pasted tests and `for` loops inside one test (which stop at the first failure and hide which input broke).
- Arguments must be `Sendable`; enums conforming to `CaseIterable` work nicely (`arguments: Theme.allCases`).

### Q44. How do setup and teardown work in Swift Testing? `[Senior]`
```swift
@Suite final class TemporaryDirectoryTests {
    let directory: URL

    init() throws {                                  // setup before each test
        directory = FileManager.default.temporaryDirectory.appending(path: UUID().uuidString)
        try FileManager.default.createDirectory(at: directory, withIntermediateDirectories: true)
    }

    deinit {                                         // teardown after each test (class/actor suites)
        try? FileManager.default.removeItem(at: directory)

        let exporter = CSVExporter(outputDirectory: directory)
```

**Key points:**
- `init` (can be `async throws`) replaces `setUp`; `deinit` (only in classes and actors, synchronous) replaces `tearDown`.
- For reusable or async setup/teardown, use a **custom trait** with `TestScoping` (Q51).

### Q45. What are traits? `[Senior]`
**Key points:** Traits customize tests or suites declaratively:

| Trait | Purpose |
|---|---|
| `.tags(.networking)` | Categorize tests for filtering and reporting |
| `.disabled("reason")` | Skip with an explanation |
| `.enabled(if: condition)` | Run only when a runtime condition holds |
| `.bug("URL or ID")` | Link a test to a bug tracker issue |
| `.timeLimit(.minutes(1))` | Fail if the test runs too long |
| `.serialized` | Run a suite's tests (or parameterized cases) one at a time |
| Custom traits | Shared setup/teardown via `TestScoping` (Q51) |

```swift
@Test("Syncs large accounts", .tags(.integration, .slow), .timeLimit(.minutes(2)))

```

### Q47. How do you conditionally run, disable, or time-limit tests? `[Senior]`

### Q48. How does parallel execution work in Swift Testing? `[Senior]`
**Key points:**
- Swift Testing runs tests **in parallel by default** (including parameterized cases), within the same process, and doesn't guarantee order.
- Consequences: tests must not share **mutable global or static state** (singletons, `UserDefaults.standard`, the same files or keychain items). Otherwise they interfere randomly.
- Fixes: inject dependencies per test; use unique resources (temporary directories, suite-specific `UserDefaults`); or mark suites that genuinely need exclusivity with `.serialized`.

```swift
@Suite(.serialized)                 // these tests share the device keychain
struct KeychainStoreTests {
    @Test func savesToken() throws { /* ... */ }
    @Test func deletesToken() throws { /* ... */ }
}
```

### Q49. How do you test callbacks or events with `confirmation`? `[Senior]`
```swift
@Test func savingDraftNotifiesObserverOnce() async {
    await confirmation("save notification", expectedCount: 1) { saved in
        let store = DraftStore(onSave: { _ in saved() })
        await store.save(.fixture())                 // the event must happen before this closure returns
    }
}

@Test func cancelledUploadNeverCompletes() async {
    await confirmation("completion", expectedCount: 0) { completed in
        let uploader = Uploader(onComplete: { completed() })
        let task = uploader.start(.fixture())
        task.cancel()
        await task.waitUntilFinished()
    }
}
```
**Key points:**
- `confirmation` asserts an event happens a specific number of times (including zero; ranges are supported in newer versions).
- Unlike XCTest expectations, it **doesn't wait** with a timeout: the event must occur before the closure returns, so the code under test should be awaitable. For callback APIs, wrap them with a continuation or await a completion signal.

### Q51. How do you create reusable setup and teardown with custom traits? `[Lead/Expert]`
```swift
enum AppEnvironment {
    @TaskLocal static var current: Dependencies = .live
}

/// Runs each test with mock dependencies installed as a task-local value (Swift 6.1+)
struct MockDependenciesTrait: TestTrait, SuiteTrait, TestScoping {
    func provideScope(
        for test: Test,
        testCase: Test.Case?,
        performing function: @Sendable () async throws -> Void
    ) async throws {
        try await AppEnvironment.$current.withValue(.mock) {
            try await function()                     // the test runs inside this scope
        }
        // teardown (if any) goes here
    }
}

extension Trait where Self == MockDependenciesTrait {
    static var mockDependencies: Self { Self() }
}

@Suite(.mockDependencies)
struct CheckoutFlowTests {
    @Test func placesOrder() async throws { /* uses AppEnvironment.current */ }
}
```
- Scoping traits provide shared, async-capable setup/teardown without base classes, and compose with other traits.

### Q54. How do XCTest concepts map to Swift Testing? `[Senior]`
| XCTest | Swift Testing |
|---|---|
| `class FooTests: XCTestCase` | `@Suite struct FooTests` (or just top-level `@Test` functions) |
| `func testSomething()` | `@Test func something()` |

| `measure { }` | No equivalent: keep in XCTest |
| XCUITest | No equivalent: keep in XCTest |

### Q55. What are Swift Testing's current limitations? `[Senior]`
**Key points:**
- No UI testing (use XCUITest) and no performance `measure` API (use XCTest).
- `confirmation` doesn't wait with a timeout, so callback-based code needs adapting.
- Exit tests (asserting on crashes/`fatalError`) aren't available on iOS.
- Parallel-by-default execution exposes hidden shared state in legacy tests during migration.
- Some third-party tools assume XCTest (although popular libraries like snapshot testing now support Swift Testing).

### Q56. How should you organize and name Swift Testing tests? `[Senior]`
**Key points:**
- One suite per type or feature, nested suites for sub-behaviors (`@Suite struct CartTests { @Suite struct Coupons { … } }`).
- Descriptive display names that read as behavior: `@Test("Expired coupons are rejected")`.
- Tags for cross-cutting categories (networking, persistence, slow, integration).
- Shared fixtures in extensions near the domain types; helpers as free functions or extensions rather than base classes.

## 6. Testing Async Code & Concurrency

### Q57. How do you test async functions? `[Fundamental]`
```swift
@Test func fetchesAndMapsProducts() async throws {
    let repository = ProductRepository(api: StubProductAPI(products: [.fixtureDTO(title: "Lamp")]))
    let products = try await repository.products()
    #expect(products.map(\.name) == ["Lamp"])

```
- Mark the test `async` (and `throws`) and `await` the result directly. No expectations, sleeps, or polling needed.
- This is one of the biggest benefits of adopting async/await: tests become simpler than callback-based ones.

### Q58. How do you test a `@MainActor` view model? `[Senior]`
**Key points:**
- Isolate the test (or suite) to `@MainActor` (Q53), inject stub dependencies, call the async method, and assert the resulting state.
- Test **every state**: loading, loaded, empty, error, and transitions (e.g. retry after failure).
- (Examples: Async/Await file Q117–Q118; SwiftUI file Q121.)

### Q59. How do you test code that starts its own `Task` internally? `[Lead/Expert]`
**Key points:**
- **Preferred**: refactor so the logic lives in an `async` method that the internal task calls; test the method directly.
- **Otherwise**: expose the task handle (internal visibility) and await it in tests.

```swift
@MainActor
@Observable
final class SearchViewModel {
    var query = "" { didSet { scheduleSearch() } }
    private(set) var results: [Movie] = []
    private(set) var searchTask: Task<Void, Never>?        // internal: visible to @testable tests
    private let api: MovieAPI
    private let clock: any Clock<Duration>

    init(api: MovieAPI, clock: any Clock<Duration> = ContinuousClock()) {
        self.api = api
        self.clock = clock
    }

    private func scheduleSearch() {
        searchTask?.cancel()
        let query = query
        searchTask = Task {
            try? await clock.sleep(for: .milliseconds(300))
            guard !Task.isCancelled else { return }
            results = (try? await api.search(query)) ?? []
        }
    }
}

@MainActor
@Test func searchPublishesResults() async {
    let viewModel = SearchViewModel(api: StubMovieAPI(results: [.fixture()]), clock: ImmediateClock())
    viewModel.query = "Dune"
    await viewModel.searchTask?.value                      // deterministic: wait for the internal task
    #expect(viewModel.results == [.fixture()])
}
```
- Never use `Task.sleep` in tests to "wait a bit." It's slow and flaky.

### Q60. How do you assert intermediate states like "loading" during an async operation? `[Lead/Expert]`
```swift
/// A dependency whose response the test controls, so the operation can be paused mid-flight
actor ControllableProductAPI: ProductAPI {
    private var continuation: CheckedContinuation<[ProductDTO], Error>?
    var isWaiting: Bool { continuation != nil }

    func fetchProducts() async throws -> [ProductDTO] {
        try await withCheckedThrowingContinuation { continuation = $0 }
    }

    func respond(with result: Result<[ProductDTO], Error>) {
        continuation?.resume(with: result)
        continuation = nil
    }
}

@MainActor
@Test func showsLoadingThenContent() async {
    let api = ControllableProductAPI()
    let viewModel = ProductListViewModel(api: api)

    let load = Task { await viewModel.load() }
    while await !api.isWaiting { await Task.yield() }       // wait until the request is in flight

    #expect(viewModel.state == .loading)

    await api.respond(with: .success([.fixtureDTO()]))
    await load.value

    #expect(viewModel.state == .loaded([Product(dto: .fixtureDTO())]))
}
```
- The same technique tests race conditions and reentrancy deterministically (Swift Concurrency file, Q128).

### Q61. How do you test time-based logic (debounce, timeout, retry, polling)? `[Lead/Expert]`
**Key points:**
- **Inject a clock** (`any Clock<Duration>`) instead of calling `Task.sleep` directly.
- In tests, use a **test clock** you advance manually (e.g. `TestClock` from Point-Free's swift-clocks) or an **immediate clock** that skips waits.

```swift
import Clocks

@MainActor
@Test func debounceWaitsBeforeSearching() async {
    let clock = TestClock()
    let api = SpyMovieAPI()
    let viewModel = SearchViewModel(api: api, clock: clock)

    viewModel.query = "Du"
    viewModel.query = "Dune"                                 // cancels the first pending search

    await clock.advance(by: .milliseconds(299))
    #expect(await api.queries.isEmpty)                      // still debouncing

    await clock.advance(by: .milliseconds(1))
    await viewModel.searchTask?.value
    #expect(await api.queries == ["Dune"])                  // only the latest query was sent
}
```
- Tests run instantly and deterministically, even for logic that waits for minutes in production.

### Q62. How do you test `AsyncSequence` and `AsyncStream` producers? `[Senior]`

### Q63. How do you test cancellation? `[Senior]`
```swift
@Test func cancellingImportStopsProcessing() async {
```

### Q64. How do you test actors and concurrent behavior? `[Senior]`
**Key points:**
- **Functional behavior**: call actor methods and assert results like any async code.
- **Concurrency properties**: launch many concurrent operations (task groups) and assert invariants (no lost updates, single network request for deduplicated work).
- **Reentrancy**: use controllable dependencies to force interleavings at suspension points (Swift Concurrency file, Q128).

```swift
@Test func concurrentRequestsForSameImageDownloadOnce() async throws {
    let api = CountingImageAPI(delay: .milliseconds(50))
    let loader = ImageLoader(api: api)

    try await withThrowingTaskGroup(of: Void.self) { group in
        for _ in 0..<10 {
            group.addTask { _ = try await loader.image(for: .fixtureURL) }
        }
        try await group.waitForAll()
    }

    #expect(await api.requestCount == 1)
}
```

### Q65. How do you avoid nondeterminism in async tests? `[Lead/Expert]`
**Key points:**
- Replace real time with injected clocks; real network with stubs; randomness with seeded generators.
- Await completion explicitly (task handles, async methods) instead of sleeping.
- Use `Task.yield()` loops only to wait for **observable conditions** (like `isWaiting` in Q60), never fixed durations.
- For code whose interleaving is inherently scheduler-dependent, tools like `withMainSerialExecutor` (swift-concurrency-extras) can serialize async work onto the main thread during tests to make ordering deterministic.
- Run suspicious tests many times (test repetitions) to expose flakiness before merging.

### Q66. How do you test thread safety of code not covered by Swift 6 checks? `[Senior]`
**Key points:**
- Stress tests: hammer the shared object from many threads/tasks (`DispatchQueue.concurrentPerform`, task groups) and assert invariants.
- Run them under **Thread Sanitizer** (a test plan configuration) so races are reported even if the test happens to pass.
- Prefer migrating the code to Swift 6 language mode with actors or `Mutex` so the compiler guarantees safety.

## 8. Testing Networking

### Q70. At which levels do you test networking code? `[Senior]`
**Key points:**
1. **Request building** (pure): endpoints produce the correct `URLRequest` (path, query, headers, body).
2. **Response handling** (pure): decoding, status code handling, and error mapping from fixture data.
3. **Client integration**: the real `URLSession`-based client with a stubbed transport (`URLProtocol`).
4. **Higher layers**: repositories and view models with stubbed API protocols (no HTTP at all).
5. **Contract tests** against the real API schema; a few **live smoke tests** against staging (separate, optional).

### Q71. How do you test request building? `[Fundamental]`
```swift
@Test func searchEndpointBuildsRequest() throws {

    #expect(request.url?.absoluteString == "https://api.example.com/v1/search?q=desk%20lamp&page=2")
    #expect(request.value(forHTTPHeaderField: "Accept") == "application/json")
}
```
- Keeping request construction as a **pure function** makes it trivially testable and catches encoding bugs (spaces, special characters, missing headers).

### Q74. How do you test retries, timeouts, and error mapping? `[Senior]`
```swift
@Suite(.serialized)
struct RetryingClientTests {
```

### Q75. Should tests ever hit a real backend? `[Lead/Expert]`
**Key points:**
- Not in the main unit/integration suite: real backends make tests slow, flaky, and dependent on data and availability.
- A **small, separate smoke suite** against a staging environment (run nightly or before release) catches integration issues such as auth configuration, contract drift, and certificates.
- **Contract tests** (validating fixtures/clients against the API schema, or consumer-driven contracts) catch most mismatches without live calls.

## 9. Testing Persistence

### Q76. How do you test SwiftData code? `[Senior]`
**Key points:**
- Create a **fresh in-memory `ModelContainer`** per test (fast, isolated), insert data, exercise the code, and assert with fetches.
- Test predicates against the real store, since predicate translation errors only appear at runtime.
- Test `@ModelActor` services by constructing them with the in-memory container.
- (Examples: SwiftData file, Q92–Q93.)

### Q77. How do you test Core Data code? `[Senior]`
```swift
func makeTestContainer() throws -> NSPersistentContainer {
    let container = NSPersistentContainer(name: "Shop")
    let description = NSPersistentStoreDescription()
    description.url = URL(fileURLWithPath: "/dev/null")   // SQLite store that isn't persisted to disk
    container.persistentStoreDescriptions = [description]

    var loadError: Error?
    container.loadPersistentStores { _, error in loadError = error }
    if let loadError { throw loadError }
    return container
}

@Test func archivingNoteHidesItFromInbox() throws {
    let container = try makeTestContainer()
    let context = container.viewContext
    let note = Note(context: context)
    note.title = "Groceries"
    try context.save()

    try NoteService(context: context).archive(note)

    let inbox = try context.fetch(Note.inboxFetchRequest())
    #expect(inbox.isEmpty)
}
```
- Using a `/dev/null` SQLite URL keeps SQLite semantics (unlike the legacy in-memory store type, which behaves differently for some features). Load the model **once** per test run if many containers are created (loading the same model repeatedly can cause entity-description conflicts).

### Q78. How do you test database migrations? `[Lead/Expert]`
**Key points:**
- Keep **fixture store files** created by each shipped app version in the test bundle.
- In a test: copy the old store to a temporary location, open it with the current schema and migration plan, and assert data integrity (counts, transformed values, relationships).
- Test version jumps (v1 → v4), not just consecutive versions.
- Run migration tests in CI; a failed migration in production often means a launch crash.

### Q79. How do you test code that uses the Keychain? `[Senior]`
**Key points:**
- Keychain tests require a **host app** (entitlements) and touch shared device state, so use unique service names per test run, clean up in teardown, and run them `.serialized`.
- Most code should depend on a `SecureStore` protocol; test business logic with an in-memory fake and keep a few integration tests for the real Keychain wrapper.

### Q80. How do you test file system code? `[Fundamental]`
**Key points:**
- Inject the base directory; create a unique **temporary directory per test** and delete it in teardown (Q44).
- Inject `FileManager` only if you need to simulate errors (e.g. disk full) via a wrapper protocol.
- Never write to the real `Documents` directory in tests; it leaks state between tests and runs.

### Q81. What should view model tests cover? `[Senior]`
**Key points:**

## 12. Testing SwiftUI

### Q92. How do you test SwiftUI code? `[Senior]`
**Key points:**
- **Unit test the logic** (models, view models, routers, formatters): most bugs live there.
- **Snapshot tests** for visual states (light/dark, Dynamic Type, locales).
- **Previews** for quick visual verification during development (not automated).
- **UI tests** for critical flows.
- SwiftUI views themselves have no public API to inspect their hierarchy; third-party libraries (e.g. ViewInspector) can introspect views but are tied to SwiftUI internals and can break across OS versions.

- Keep `body` declarative; move decisions into models (`viewModel.isSubmitEnabled` rather than complex conditions in `body`).
- Inject dependencies (initializer or environment) so previews and tests can use stubs.

- Add `accessibilityIdentifier`s to key elements for UI tests.

### Q95. How do you test environment-dependent behavior in SwiftUI? `[Senior]`

- Inject custom environment values (`@Entry`) for dependencies and test the behavior of views via their models.

## 13. UI Testing with XCUITest

### Q96. How does XCUITest work? `[Fundamental]`
**Key points:**
- UI tests run in a **separate process** that drives your app through the **accessibility layer**, like an automated user: launching, tapping, typing, swiping, and querying elements.
- Tests can't access app code or state directly (black-box). Configuration is passed through **launch arguments and environment variables**.
- Slow compared with unit tests (seconds per test) and more prone to flakiness, so reserve them for critical end-to-end journeys.

### Q97. Show a well-structured UI test. `[Senior]`
```swift

        app.launchEnvironment = ["MOCK_SCENARIO": "login_success"]   // app uses stubbed backend
        app.launch()

    func testSuccessfulLoginShowsHome() {
        let home = LoginScreen(app: app)
            .typeEmail("ana@example.com")
            .typePassword("correct-password")
            .tapLogin()

    }
}
```

### Q98. What is the Page Object (Screen Object) pattern? `[Senior]`
```swift
struct LoginScreen {
    let app: XCUIApplication

    private var emailField: XCUIElement { app.textFields["login.email"] }
    private var passwordField: XCUIElement { app.secureTextFields["login.password"] }
    private var loginButton: XCUIElement { app.buttons["login.submit"] }

}
```
**Key points:**
- Encapsulates element queries and interactions per screen; tests read like user stories.
- When the UI changes, only the screen object changes, not every test.

### Q99. How should the app support UI testing? `[Senior]`
```swift
@main
struct ShopApp: App {
    @State private var container: AppContainer

    init() {
        let arguments = ProcessInfo.processInfo.arguments
        let environment = ProcessInfo.processInfo.environment

        if arguments.contains("-disableAnimations") {
            UIView.setAnimationsEnabled(false)
        }
        if arguments.contains("-uiTesting") {

        }

    }

```
**Key points:**
- Launch arguments select **mock backends/scenarios** (deterministic data), reset state (clear the database/keychain), skip onboarding or permission prompts, and disable animations.
- Keep UI-testing hooks in the composition root; never ship code paths that weaken security in Release (guard with build configurations where needed).

### Q100. Why use accessibility identifiers in UI tests? `[Fundamental]`

**Key points:**
- Identifiers are **stable** across localization and copy changes, unlike labels ("Log In" vs "Iniciar sesión").

### Q101. How do you wait for elements reliably? `[Senior]`
```swift
// Wait for appearance
XCTAssertTrue(app.staticTexts["order.confirmation"].waitForExistence(timeout: 10))

// Wait for disappearance (e.g. a loading spinner)
let spinner = app.activityIndicators["loading"]
let gone = XCTNSPredicateExpectation(predicate: NSPredicate(format: "exists == false"), object: spinner)
XCTAssertEqual(XCTWaiter().wait(for: [gone], timeout: 10), .completed)

// Wait for a property (e.g. a button becoming enabled)
let enabled = XCTNSPredicateExpectation(predicate: NSPredicate(format: "isEnabled == true"),
                                        object: app.buttons["checkout.pay"])
XCTAssertEqual(XCTWaiter().wait(for: [enabled], timeout: 5), .completed)
```
- Never use `sleep()` in UI tests; wait for **conditions**. Fixed sleeps are both slow and flaky.

### Q102. How do you handle system alerts and permissions in UI tests? `[Senior]`
**Key points:**
- Best: **avoid** permission prompts in most UI tests by stubbing permission services via launch arguments.

```swift

```

### Q104. How do you make UI tests fast? `[Lead/Expert]`
**Key points:**
- Test only **critical journeys** end to end; push detail checks down to unit/snapshot tests.
- Launch directly into the screen under test with launch arguments (deep-link-like setup) instead of navigating through onboarding each time.
- Mock the backend (fast, deterministic responses) and disable animations.
- Run in **parallel** on multiple simulator clones (test plans / `-parallel-testing-enabled YES`).
- Use `build-for-testing` once, then `test-without-building` across shards.

### Q105. What are common causes of flaky UI tests? `[Senior]`
**Key points:**
- Fixed sleeps instead of waiting for conditions.
- Real network or shared backend data.
- Animations and transitions in progress during taps.
- State leaking between tests (keychain, database, `UserDefaults`, logged-in sessions).
- Unexpected system alerts, keyboard state, or hardware keyboard settings in simulators.
- Element queries matching multiple elements (ambiguous identifiers).
- Test order dependence.

### Q106. How do you debug a failing UI test? `[Senior]`
**Key points:**
- Inspect the **test report**: automatic screenshots, activity logs, and (in newer Xcode versions) video recordings of the run.
- Print the element tree with `print(app.debugDescription)` at the failure point to see what's actually on screen and which identifiers exist.
- Run the test repeatedly ("Run until failure") to reproduce intermittent failures.
- Check the app's logs (launch environment can enable verbose logging in UI test mode).

## 14. Snapshot Testing

### Q108. What is snapshot testing, and when is it valuable? `[Senior]`
**Key points:**
- Renders a view (or serializes data) and compares it with a stored **reference** (image or text). Differences fail the test with a diff.
- Valuable for: design system components, complex layouts, many state combinations (light/dark, Dynamic Type, RTL, locales, device sizes), and catching unintended visual regressions in refactors.
- Popular library: Point-Free's **swift-snapshot-testing** (supports XCTest and Swift Testing).

### Q109. Show snapshot tests for a component in several configurations. `[Senior]`
```swift
import SnapshotTesting
import SwiftUI
import Testing

@MainActor
@Suite struct ProductCardSnapshotTests {
    @Test func productCardVariants() {
        let card = ProductCard(product: .fixture(name: "Desk Lamp", price: 49.99))
            .frame(width: 375)

        assertSnapshot(of: card, as: .image(layout: .sizeThatFits), named: "default")
        assertSnapshot(of: card.preferredColorScheme(.dark), as: .image(layout: .sizeThatFits), named: "dark")
        assertSnapshot(of: card.environment(\.dynamicTypeSize, .accessibility3),
                       as: .image(layout: .sizeThatFits), named: "a11y-xxxl")
        assertSnapshot(of: card.environment(\.layoutDirection, .rightToLeft),
                       as: .image(layout: .sizeThatFits), named: "rtl")
    }

    @Test func checkoutScreenOnDevices() {
        let controller = UIHostingController(rootView: CheckoutView(viewModel: .preview))
        assertSnapshot(of: controller, as: .image(on: .iPhone13))
        assertSnapshot(of: controller, as: .image(on: .iPadPro11), named: "ipad")
    }
}
```
- To (re)record references, run with recording enabled (e.g. `withSnapshotTesting(record: .all) { … }` or the library's environment/configuration options), review the new images in code review, and commit them.

### Q110. What are the pitfalls of snapshot testing? `[Senior]`
**Key points:**
- **Environment sensitivity**: different simulator models, OS versions, or rendering details cause false failures. Pin the simulator and OS in CI and locally.
- **Over-snapshotting**: snapshots of whole screens with dynamic data (dates, remote images) break constantly. Use fixed data and snapshot focused components.
- **Rubber-stamping**: engineers re-record failing snapshots without reviewing diffs. Make snapshot diffs part of code review.
- **Repository size**: many large PNGs; use reasonable sizes, consider Git LFS.
- Snapshots test **appearance**, not behavior; they complement, not replace, unit and UI tests.

### Q111. Can snapshot testing be used for non-visual data? `[Lead/Expert]`
```swift
@Test func encodesOrderRequestStably() throws {
    let request = OrderRequestDTO(order: .fixture(), paymentToken: "tok_test")
    assertSnapshot(of: request, as: .json)                   // stored JSON reference
}

@Test func analyticsEventsForCheckout() {
    assertSnapshot(of: CheckoutAnalytics.events(for: .fixture()), as: .dump)   // textual dump
}
```
- Text snapshots (JSON, dumps, `URLRequest`s, accessibility hierarchies) catch unintended changes in serialized output, request formats, or analytics payloads, and diffs are easy to review.

## 15. Specialized Testing

### Q112. How do you test accessibility beyond automated audits? `[Senior]`
**Key points:**
- Unit test accessibility properties computed by view models (e.g. `accessibilityLabel` strings like "Rated 4.5 stars from 120 reviews").
- Snapshot tests at the largest Dynamic Type sizes and with Bold Text / Increase Contrast.
- `performAccessibilityAudit()` in UI tests (Q107).
- Manual VoiceOver and Voice Control passes on key flows before release; involve users with disabilities in usability testing where possible.

### Q113. How do you test localization? `[Senior]`
**Key points:**
- **Test Plans** with configurations per language/region (e.g. English, German for long strings, Arabic for RTL, Japanese) to run UI/snapshot tests across locales.
- **Pseudolanguages** (double-length, right-to-left, accented) to catch truncation and hard-coded strings early.
- Unit test pluralization and formatting with explicit locales:

```swift
@Test(arguments: [(1, "1 item"), (2, "2 items"), (0, "0 items")])
func itemCountPluralization(count: Int, expected: String) {
    // Relies on the plural variants defined in the app's String Catalog
    let text = String(localized: "\(count) items", locale: Locale(identifier: "en_US"))
    #expect(text == expected)
}

@Test func priceFormattingFollowsLocale() {
    let price = Decimal(1234.5)
    #expect(price.formatted(.currency(code: "EUR").locale(Locale(identifier: "de_DE"))) == "1.234,50 €")
}
```
- Note: exact formatted strings can change between OS versions (e.g. space characters in currency formats); assert on stable aspects or update expectations when upgrading.

### Q114. How do you test push notification and deep link handling? `[Senior]`
**Key points:**
- Keep handling logic in plain types that accept `userInfo` dictionaries or URLs (not `UNNotificationResponse`, which is hard to construct) and unit test them with parameterized payloads.
- UI test deep links with `app.open(_:)` (Q103); test notification permission flows manually or with Springboard interactions.
- Test edge cases: unknown notification types, missing fields, deep links requiring login, links received during cold vs warm launch.

### Q115. How do performance tests fit into the testing strategy? `[Senior]`
**Key points:**
- XCTest `measure` blocks with metrics and baselines for critical code paths (parsing, launch, scrolling), run on consistent hardware in CI (Performance & Debugging file, Section 19).
- Keep them separate from fast unit test suites (different test plans/schedules) because they're slower and noisier.

### Q116. How do you test security-related behavior? `[Lead/Expert]`
**Key points:**
- Unit test security logic: token refresh flows, logout clearing all user data and caches, input validation, permission checks, PKCE generation, keychain wrapper behavior.
- Test that sensitive data isn't logged or persisted where it shouldn't be (e.g. assert caches are empty after logout; scan logs in tests).
- Static analysis (Xcode Analyze, linters), dependency vulnerability scanning in CI, and periodic penetration testing or mobile security scanners for the built app.
- Verify ATS configuration and certificate pinning behavior in integration tests or staged environments.

### Q117. What is API contract testing? `[Lead/Expert]`
**Key points:**
- Verifies that the client and server agree on the API's shape and semantics, without full end-to-end tests:
  - **Schema validation**: validate fixtures and generated models against the OpenAPI/GraphQL schema in CI; regenerate client code from schemas.
  - **Consumer-driven contracts** (e.g. Pact): the app publishes the requests/responses it relies on; the backend verifies it still satisfies them before deploying.
- Catches breaking API changes before they reach users of older app versions.

### Q118. What is property-based testing, and how can you apply it in Swift? `[Lead/Expert]`
**Key points:**
- Instead of hand-picked examples, generate **many random inputs** and assert **properties** that must always hold (e.g. "encoding then decoding returns the original value," "sorting is idempotent," "a merged cart total equals the sum of item totals").
- Use a **seeded** random generator so failures are reproducible.

```swift
struct SeededGenerator: RandomNumberGenerator {
    private var state: UInt64
    init(seed: UInt64) { state = seed }

    mutating func next() -> UInt64 {                    // SplitMix64
        state &+= 0x9E37_79B9_7F4A_7C15
        var z = state
        z = (z ^ (z >> 30)) &* 0xBF58_476D_1CE4_E5B9
        z = (z ^ (z >> 27)) &* 0x94D0_49BB_1331_11EB
        return z ^ (z >> 31)
    }
}

extension Note {
    static func random(using rng: inout some RandomNumberGenerator) -> Note {
        Note(id: UUID(), title: String((0..<Int.random(in: 0...40, using: &rng)).map { _ in
                 "abcxyz éü😀 ".randomElement(using: &rng)! }),
             isPinned: Bool.random(using: &rng))
    }
}

@Test(arguments: 0..<200)
func noteEncodingRoundTrips(seed: Int) throws {
    var rng = SeededGenerator(seed: UInt64(seed))
    let note = Note.random(using: &rng)
    let decoded = try JSONDecoder().decode(Note.self, from: JSONEncoder().encode(note))
    #expect(decoded == note)                            // a failing seed is reported and reproducible
}
```

### Q119. What is fuzz testing, and when is it useful? `[Lead/Expert]`
**Key points:**
- Feeding malformed, random, or extreme inputs to code that parses untrusted data (deep links, push payloads, file formats, JSON, QR codes) to find crashes and hangs.
- In Swift apps: generate random/mutated inputs in tests (like Q118) for parsers; for C/C++ components, coverage-guided fuzzers (libFuzzer) are available.
- Valuable where untrusted input could crash the app or cause security issues.

### Q120. What is mutation testing? `[Lead/Expert]`
**Key points:**
- A tool deliberately introduces small bugs ("mutants") into your code (flip `>` to `>=`, remove a line, negate a condition) and runs the tests. If tests still pass, the mutant "survived," meaning the tests didn't catch that bug.
- Measures **test effectiveness**, not just coverage: 100% line coverage with weak assertions can still let mutants survive.
- Tools exist for Swift (e.g. Muter). It's slow, so run it periodically on critical modules rather than on every build.

## 16. TDD, BDD & Test Design

### Q121. What is Test-Driven Development (TDD)? `[Fundamental]`
**Key points:** The **red–green–refactor** cycle:
1. **Red**: write a small failing test for the next bit of behavior.
2. **Green**: write the simplest code that makes it pass.
3. **Refactor**: clean up the code (and tests) while keeping them green.
- Benefits: testable design by construction, high-value coverage, small steps, and executable specifications.
- Costs: discipline and upfront time; awkward for exploratory UI work or unfamiliar APIs (spike first, then TDD).

### Q122. Walk through a short TDD example. `[Senior]`
```swift
// 1. RED: describe the first behavior
@Test func weakPasswordIsTooShort() {
    #expect(PasswordStrength.evaluate("abc") == .weak)
}

// 2. GREEN: simplest implementation
enum PasswordStrength: Equatable {
    case weak, medium, strong
    static func evaluate(_ password: String) -> PasswordStrength { .weak }
}

// 3. RED: next behavior forces real logic
@Test(arguments: [("abcdefgh", PasswordStrength.medium), ("abcdefgh1!", .strong), ("abc", .weak)])
func strengthLevels(password: String, expected: PasswordStrength) {
    #expect(PasswordStrength.evaluate(password) == expected)
}

// 4. GREEN + REFACTOR: replace the placeholder implementation with real logic
//    static func evaluate(_ password: String) -> PasswordStrength {
//        guard password.count >= 8 else { return .weak }
//        let hasDigit = password.contains(where: \.isNumber)
//        let hasSymbol = password.contains { !$0.isLetter && !$0.isNumber }
//        return hasDigit && hasSymbol ? .strong : .medium
//    }
```
- Interview tip: emphasize **small steps** and letting tests drive the design (the evaluator stayed a pure function because tests made that natural).

### Q123. What is BDD, and how does it relate to TDD? `[Senior]`
**Key points:**
- **Behavior-Driven Development** expresses tests as behavior specifications in a shared language with product/QA ("Given a cart with an expired coupon, when the user checks out, then they see a coupon error").
- In Swift: Given/When/Then naming, nested suites describing contexts, or libraries like Quick/Nimble.
- Main benefit: tests double as **acceptance criteria** agreed upon before implementation.

### Q124. How should tests be named? `[Fundamental]`
**Key points:**
- Names should state the **scenario and expected outcome**, so a failure explains itself without reading the code:
  - XCTest: `test_checkout_withExpiredCoupon_showsCouponError()`.
  - Swift Testing: `@Test("Checkout with an expired coupon shows a coupon error")`.
- Avoid vague names like `testCheckout1` or `testViewModel`.

### Q125. How many assertions should a test have? `[Senior]`
**Key points:**
- One **behavior** per test, not necessarily one assertion. Asserting several facets of a single outcome (state updated, loading cleared, event tracked) is fine.
- Split tests that verify unrelated behaviors, so failures pinpoint the problem.
- Parameterized tests replace "one test, many inputs" loops.

### Q126. What makes tests maintainable over time? `[Senior]`
**Key points:**
- Test **behavior through public APIs**, not implementation details.
- Use **fixtures/builders** with defaults; keep each test's relevant data visible in the test.
- Extract helpers for repeated setup, but avoid deep inheritance hierarchies of base test classes.
- Keep tests **independent** (no order dependence, no shared mutable state).
- Treat test code with the same quality standards as production code (review, refactoring).

### Q127. How do you test a bug fix? `[Fundamental]`
**Key points:**
- First write a test that **reproduces the bug** and fails; then fix the code and watch it pass. The test prevents the bug from returning (regression test).
- Name the test after the behavior, and optionally reference the issue (`.bug("SHOP-482")` in Swift Testing).

## 17. Coverage, Metrics & Test Health

### Q128. What does code coverage tell you, and what doesn't it? `[Senior]`
**Key points:**
- Coverage shows which lines/branches **executed** during tests. Low coverage reliably reveals **untested** code.
- High coverage does **not** prove quality: tests can execute code without meaningful assertions, miss edge cases, or test trivial code while critical paths stay weak.
- Use it to find gaps in important code (business logic, view models), not as a target to game. Mutation testing (Q120) measures assertion quality better.

### Q129. How do you use coverage effectively on a team? `[Lead/Expert]`
**Key points:**
- Enable coverage in the test plan and report it in CI (per module, per layer).
- Set expectations per area: high coverage for domain logic, view models, and parsers; lower for UI glue.
- **Diff coverage** on pull requests ("new or changed lines are tested") is more actionable than a global percentage and prevents backsliding without blocking legacy code.
- Review untested critical paths periodically rather than chasing 100%.

### Q130. Which metrics indicate a healthy test suite? `[Lead/Expert]`
| Metric | Why it matters |
|---|---|
| Suite duration (unit, UI) | Fast feedback keeps developers running tests |
| Flaky test rate | Flakiness destroys trust in CI |
| Escaped defects (bugs found in production) | Measures real effectiveness |
| Coverage of critical modules / diff coverage | Finds gaps |
| Mean time to fix broken builds | CI discipline |
| Test count by layer (pyramid shape) | Detects over-reliance on slow UI tests |
| Time from bug report to regression test | Learning culture |

### Q131. How fast should tests be? `[Senior]`
**Key points:**
- Unit tests: milliseconds each; a module's suite in seconds; the whole unit suite in a few minutes at most.
- If tests are slow, developers stop running them locally. Common causes: real I/O, sleeps, heavyweight setup per test (launching the full app, large fixtures), unit tests hosted in the app unnecessarily.
- Speed-ups: run logic tests **without a host app** (or in SPM packages), parallelize, mock I/O, use in-memory stores, inject clocks.

### Q132. Should unit tests run inside a host app? `[Senior]`
**Key points:**
- **Hosted tests** (bundle injected into the running app) are needed for code requiring the app environment: UIKit windows, Keychain entitlements, some system services.
- **Non-hosted tests** (logic tests, SPM package tests) start faster and avoid app launch side effects (SDK initialization, network calls, singletons).
- Modularizing code into packages makes most tests non-hosted and much faster. If tests must be hosted, ensure the app skips heavy launch work when running tests (detect via a launch argument or environment variable).

## 18. Flaky Tests

### Q133. What makes tests flaky? `[Senior]`
**Key points:**
- **Time**: real clocks, `sleep`-based waits, timeouts too tight on slow CI machines, time zones/DST.
- **Concurrency**: unawaited async work, races, unordered task execution.
- **Shared state**: singletons, `UserDefaults.standard`, files, Keychain, static stubs used by parallel tests.
- **External dependencies**: real network, backend data, third-party services.
- **Order dependence**: a test relying on state left by another.
- **Randomness** without fixed seeds.
- **UI specifics**: animations, alerts, simulator state, keyboard settings.

### Q134. How do you find and fix flaky tests? `[Senior]`
**Key points:**
- **Detect**: run tests repeatedly (Xcode test repetitions: "Run until failure", fixed iterations; `xcodebuild -test-iterations` with `-run-tests-until-failure`), track CI failure history per test, randomize order.
- **Diagnose**: look for the causes above; reproduce under load (parallel runs, slow machines); add logging to see the actual sequence.
- **Fix**: remove the source of nondeterminism (inject clocks, await completion, isolate state, stub network) rather than increasing timeouts or adding retries.

### Q135. Should CI automatically retry failing tests? `[Lead/Expert]`
**Key points:**
- Retries (e.g. Xcode's "retry on failure" repetition mode) can keep the pipeline green short term, but they **hide** real flakiness and occasionally real bugs (race conditions that users will hit).
- Acceptable as a temporary measure **with tracking**: record which tests needed retries, quarantine and fix them with owners and deadlines.
- Goal: zero tolerated flakiness in unit tests; minimal and tracked in UI tests.

### Q136. How do you quarantine flaky tests? `[Lead/Expert]`
```swift
@Test(.disabled("Quarantined: intermittent timeout on CI"), .bug("https://jira.example.com/browse/SHOP-911"))
func syncResumesAfterReconnect() async throws { /* ... */ }

// Or keep it running but tolerated while you investigate
@Test func syncResumesAfterReconnectTolerated() async throws {
    try await withKnownIssue("Intermittent: SHOP-911", isIntermittent: true) {
        try await runReconnectScenario()
    }
}
```
**Key points:**
- Quarantine quickly so the main pipeline stays trustworthy, but keep quarantined tests **visible and owned**: a ticket, an owner, and a deadline. A quarantine that's never emptied is just deleted coverage.

## 19. CI, Test Plans & Infrastructure

### Q137. What are Xcode Test Plans? `[Senior]`
**Key points:**
- A configuration file (`.xctestplan`) describing **which tests run and how**, with multiple **configurations** in one plan:
  - Included/excluded tests and tags; test targets.
  - Launch arguments and environment variables.
  - Language and region (localization runs).
  - Sanitizers and runtime checks (ASan, TSan, UBSan, Main Thread Checker).
  - Code coverage settings, execution order (random), parallelization, repetitions, timeouts.
- Teams typically have plans like **Unit** (fast, every PR), **UI** (critical flows), **Nightly** (sanitizers, localization, slow tests), and **Performance**.

### Q138. How do you run tests from the command line in CI? `[Senior]`
```bash
# Build once
xcodebuild build-for-testing \
  -scheme Shop \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -derivedDataPath build

# Run a specific test plan in parallel, producing a result bundle
xcodebuild test-without-building \
  -scheme Shop \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -derivedDataPath build \
  -testPlan Unit \
  -parallel-testing-enabled YES \
  -resultBundlePath results/Unit.xcresult

# Run a subset
xcodebuild test-without-building ... -only-testing:ShopTests/CartTests

# Swift packages (macOS host)
swift test --parallel
```
- Parse `.xcresult` bundles (`xcrun xcresulttool`) for reports, failure annotations on pull requests, and attachments.

### Q139. How do you keep CI test times manageable as the suite grows? `[Lead/Expert]`
**Key points:**
- **Modularize** so tests run per module, and **select tests affected by a change** (dependency graph analysis).
- **Parallelize**: multiple simulators per machine, sharding across machines (`build-for-testing` once, `test-without-building` per shard).
- **Tiered pipelines**: fast unit tests on every PR; UI tests on merge; sanitizers, localization, and performance nightly.
- **Caching**: build caches for dependencies and unchanged modules.
- Monitor suite duration as a metric; set budgets ("PR checks under 15 minutes").

### Q140. What is a good quality gate for pull requests? `[Lead/Expert]`
**Key points:**
- Builds for all targets; linting/formatting passes.
- Unit tests (and affected integration/snapshot tests) pass.
- Diff coverage threshold for changed logic.
- No new warnings in modules with "warnings as errors."
- Snapshot diffs reviewed when references change.
- Optional: UI smoke test of critical flows; static analysis.
- Keep the gate fast and reliable; otherwise people work around it.

### Q141. How do you test across devices and OS versions? `[Senior]`
**Key points:**
- Run unit tests on one simulator (logic rarely depends on the device); run UI and snapshot tests on a small **matrix** (smallest and largest iPhone, an iPad, minimum supported iOS, latest iOS).
- Use real devices (device farms or in-house labs) for performance, camera, Bluetooth, push notifications, and hardware-specific behavior.
- Beta test with **TestFlight** to cover real-world diversity before release.

### Q142. How does TestFlight fit into the testing process? `[Senior]`
**Key points:**
- Internal testers (team members) get builds quickly for dogfooding; external testers (beta users) need a beta review.
- Collects crash reports and feedback (screenshots with comments) from real devices and networks.
- Combine with feature flags to test risky features with a subset of testers before the App Store release.

## 20. Testing Legacy Code

### Q143. How do you start testing a legacy codebase with almost no tests? `[Lead/Expert]`
**Key points:**
1. **Protect critical flows first** with a few UI or high-level integration tests (login, purchase, core content).
2. **Characterization tests**: capture current behavior (even if odd) before changing code, so refactors don't change it unintentionally.
3. **Add seams** to break dependencies (Q144), then unit test logic as you touch it.
4. **Boy scout rule**: every bug fix or feature change comes with tests for the code touched.
5. Track progress (coverage of critical modules, escaped defects) and celebrate improvements.

### Q144. What are seams, and how do you create them in Swift? `[Lead/Expert]`
**Key points:**
- A **seam** is a place where you can change behavior without editing the code under test (Michael Feathers, *Working Effectively with Legacy Code*).
- Common Swift seams:
  - **Constructor/parameter injection with defaults** (production call sites unchanged; Q18).
  - **Extract protocol** around a concrete dependency.
  - **Closure properties** for side effects (`var now: () -> Date = Date.init`).
  - **Subclass and override** (for non-final classes) as a temporary technique.

```swift
// Legacy: hard-coded dependencies
final class OrderHistoryLoader {
    func load() -> [Order] {
        let data = try? Data(contentsOf: FileManager.default.urls(for: .documentDirectory,
                                                                  in: .userDomainMask)[0].appending(path: "orders.json"))
        return data.flatMap { try? JSONDecoder().decode([Order].self, from: $0) } ?? []
    }
}

// With a seam: same default behavior, testable input
final class OrderHistoryLoaderTestable {
    private let readData: () throws -> Data

    init(readData: @escaping () throws -> Data = {
        try Data(contentsOf: FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]
            .appending(path: "orders.json"))
    }) {
        self.readData = readData
    }

    func load() -> [Order] {
        (try? JSONDecoder().decode([Order].self, from: readData())) ?? []
    }
}

@Test func corruptFileReturnsEmptyHistory() {
    let loader = OrderHistoryLoaderTestable(readData: { Data("not json".utf8) })
    #expect(loader.load().isEmpty)
}
```

### Q145. What are characterization tests? `[Lead/Expert]`
```swift
/// Documents what the legacy price formatter does today (including quirks) before refactoring it
@Test("Legacy formatter characterization", arguments: [
    (Decimal(0), "$0.00"),
    (Decimal(1234.5), "$1,234.50"),
    (Decimal(-5), "-$5.00"),
    (Decimal(string: "0.005")!, "$0.01"),     // rounds half up: keep this behavior intentionally
])
func legacyFormatterBehavior(input: Decimal, expected: String) {
    #expect(LegacyPriceFormatter().string(from: input) == expected)
}
```
- They describe **actual** behavior, not intended behavior. After refactoring, intentional behavior changes are made explicitly by updating these tests.

### Q146. How do you test a massive view controller you can't rewrite yet? `[Lead/Expert]`
**Key points:**
- Start with **UI or snapshot tests** around the screen to lock in behavior.
- Extract logic step by step into testable types (formatters, validators, a view model) with characterization tests for each extracted piece.
- Inject dependencies through new initializers with defaults so the screen still works unchanged.
- Each extraction is a small, shippable refactor, not a big-bang rewrite.

## 21. "Spot the Problem" Questions

### Q147. A test that hits the real network `[Fundamental]`
```swift
@Test func loadsProducts() async throws {
    let products = try await ProductRepository(api: LiveProductAPI()).products()
    #expect(!products.isEmpty)
}
```
**Problem:** depends on network availability, backend uptime, and server data; slow and flaky.
**Fix:** inject a stub API or use a `URLProtocol` stub with fixture data; keep live checks in a separate smoke suite.

### Q148. Sleeping to wait for async work `[Fundamental]`
```swift
func testSearchShowsResults() {
    viewModel.query = "lamp"
    sleep(2)                                     // wait for debounce + network
    XCTAssertEqual(viewModel.results.count, 3)
}
```
**Problem:** slow (2 s per test) and still flaky on slow machines.
**Fix:** inject a test clock and stub API, await the search task, or make the method `async` and await it.

### Q149. Shared mutable state with parallel tests `[Senior]`
```swift
enum TestState {
    static var currentUser: User?                // shared by all tests
}

@Test func profileShowsName() { TestState.currentUser = .fixture(name: "Ana"); /* … */ }
@Test func guestSeesLoginPrompt() { TestState.currentUser = nil; /* … */ }
```
**Problem:** Swift Testing runs these in parallel; they overwrite each other's state randomly (and Swift 6 flags the global mutable state).
**Fix:** inject the user into the type under test per test; avoid global state; use `.serialized` only when sharing is unavoidable.

### Q150. A test without meaningful assertions `[Fundamental]`
```swift
@Test func checkoutWorks() async throws {
    let viewModel = CheckoutViewModel(api: StubCheckoutAPI())
    try await viewModel.placeOrder()             // passes as long as nothing throws
}
```
**Problem:** it only checks that nothing crashes or throws; it would pass even if the order was never placed or the state is wrong.
**Fix:** assert the outcome: confirmation state, API called with the right payload, cart cleared, navigation event emitted.

### Q151. Testing implementation details `[Senior]`
```swift
@Test func loadCallsPrivateHelpersInOrder() async {
    let spy = InternalCallSpy()
    let viewModel = FeedViewModel(api: StubFeedAPI(), callSpy: spy)   // injected only for this test
    await viewModel.load()
    #expect(spy.calls == ["prepareRequest", "decode", "sortByDate", "updateState"])
}
```
**Problem:** breaks whenever internals are refactored, even if behavior is identical; adds test-only hooks to production code.
**Fix:** assert observable behavior: `viewModel.posts` are sorted by date after loading.

### Q152. Force unwrapping in tests `[Fundamental]`
```swift
@Test func parsesFirstOrder() throws {
    let orders = try OrderParser().parse(Fixtures.ordersJSON)
    #expect(orders.first!.id == "o_1")            // crashes the test process if empty
}
```
**Problem:** a crash aborts the test run (other tests may not run, and the failure message is unclear).
**Fix:** `let first = try #require(orders.first)` (or `XCTUnwrap` in XCTest).

### Q153. Weak assertion diagnostics `[Fundamental]`
```swift
XCTAssertTrue(cart.total == 90)                  // failure message: "XCTAssertTrue failed"
```
**Problem:** the failure doesn't show the actual value.
**Fix:** `XCTAssertEqual(cart.total, 90)` or Swift Testing's `#expect(cart.total == 90)`, which shows `cart.total → 100 == 90`.

### Q154. Nondeterministic dates `[Senior]`
```swift
@Test func trialIsActive() {
    let trial = Trial(startedAt: Date())
    #expect(trial.daysRemaining == 14)            // fails around midnight / DST changes
}
```
**Problem:** depends on the current time and calendar boundaries.
**Fix:** inject a fixed "now" and calendar/time zone into `Trial` and the test.

### Q155. Using `wait(for:)` in an async test `[Senior]`
```swift
func testUploadCompletes() async {
    let done = expectation(description: "done")
    uploader.upload(.fixture()) { _ in done.fulfill() }
    wait(for: [done], timeout: 5)                // blocks the thread inside an async context
}
```
**Problem:** blocking waits inside async tests can deadlock or starve the executor (Xcode warns about it).
**Fix:** `await fulfillment(of: [done], timeout: 5)`, or better, test an `async` version of `upload`.

### Q156. Real `UserDefaults.standard` in tests `[Senior]`
```swift
@Test func onboardingIsShownOnce() {
    let store = OnboardingStore(defaults: .standard)
    store.markCompleted()
    #expect(store.shouldShowOnboarding == false)
}
```
**Problem:** state persists across tests and runs (and in hosted tests, pollutes the app's real defaults), causing order-dependent results.
**Fix:** a unique `UserDefaults(suiteName:)` per test, removed in teardown (Q16).

### Q157. UI test relying on labels and coordinates `[Senior]`
```swift
app.buttons["Continue to Payment"].tap()
app.coordinate(withNormalizedOffset: CGVector(dx: 0.5, dy: 0.9)).tap()
```
**Problem:** breaks with copy changes, localization, different screen sizes, and layout changes.
**Fix:** stable accessibility identifiers (`app.buttons["checkout.continue"]`) and element-based interactions.

### Q158. A test verifying too many behaviors `[Senior]`
```swift
@Test func everything() async throws {
    // logs in, browses, adds to cart, applies coupon, checks out, edits profile, logs out...
}
```
**Problem:** a failure doesn't tell you what broke; the test is slow and fragile; later steps never run after an early failure.
**Fix:** split into focused tests per behavior; keep one or two end-to-end journeys as UI tests.

### Q159. Over-mocking simple collaborators `[Senior]`
```swift
let formatterMock = PriceFormatterMock()
formatterMock.stubbedResult = "$10.00"
let viewModel = ProductViewModel(product: .fixture(price: 10), formatter: formatterMock)
#expect(viewModel.priceText == "$10.00")
```
**Problem:** the test only checks that the view model returns what the mock returns; the real formatting (the interesting part) is never tested.
**Fix:** use the real `PriceFormatter` with a fixed locale.

### Q160. Random test data without a seed `[Senior]`
```swift
@Test func sortingKeepsAllItems() {
    let items = (0..<100).map { _ in Item(score: Int.random(in: 0...1000)) }
    #expect(Sorter.sort(items).count == items.count)
}
```
**Problem:** if it ever fails, the input can't be reproduced.
**Fix:** use a seeded generator and include the seed in the test case (Q118).

### Q161. Snapshot tests that always pass "after re-recording" `[Lead/Expert]`
**Scenario:** Engineers routinely set record mode to `.all` whenever snapshots fail, commit the new images, and move on.
**Problem:** snapshots lose their purpose; real visual regressions get recorded as the new truth.
**Fix:** require snapshot diffs to be reviewed in pull requests (images visible in the diff), pin rendering environments to avoid noise, and keep snapshot scopes small so failures are meaningful.

## 23. Senior / Lead Scenario Questions

### Q162. You're defining the testing strategy for a new app and a team of 8. What do you propose? `[Lead/Expert]`
**Talking points:**
- **Principles**: tests are part of the definition of done; test behavior, not implementation; fast feedback first.
- **Pyramid**: Swift Testing unit tests for domain logic, view models, mappers (most tests); integration tests for networking (`URLProtocol`) and persistence (in-memory stores); snapshot tests for the design system and key screens; XCUITest for 5–10 critical journeys with mocked backends.
- **Architecture support**: dependency injection, injected clocks, protocols at boundaries, modular packages for fast non-hosted tests.
- **CI**: test plans (Unit on every PR, UI on merge, nightly sanitizers/localization/performance), diff coverage, flaky test policy.
- **Collaboration**: QA defines acceptance criteria early, focuses on exploratory testing and automation strategy; TestFlight dogfooding.
- **Metrics**: escaped defects, suite time, flaky rate, crash-free rate.

### Q163. The codebase has 5% coverage and frequent regressions. How do you improve quality without stopping feature work? `[Lead/Expert]`
**Talking points:**
- Identify **hotspots**: modules with the most bugs and changes; protect them first.
- Add **UI smoke tests** for critical journeys (fast win against severe regressions).
- Require tests for **all new code and bug fixes** (diff coverage) instead of a big testing project.
- Introduce seams and DI incrementally while touching code; pair and provide examples.
- Make tests easy: fixtures, helpers, fast package-based targets, CI feedback within minutes.
- Report outcomes monthly (regressions, hotfixes, escaped defects) to keep stakeholder support.

### Q164. The CI test suite takes 45 minutes. How do you bring it down? `[Lead/Expert]`
**Talking points:**
- **Measure** where time goes (per test/target durations from `.xcresult`).
- Move logic tests out of hosted app targets into **packages** (no app launch); remove sleeps; replace real I/O with stubs.
- **Parallelize** (simulator clones, sharding across machines with `test-without-building`).
- **Tier** pipelines: run affected modules' tests on PRs; full suite on merge; heavy suites nightly.
- Trim redundant UI tests whose coverage is duplicated by faster tests.
- Set a budget (e.g. PR checks < 15 minutes) and track it.

### Q165. UI tests fail randomly and engineers ignore red builds. What do you do? `[Lead/Expert]`
**Talking points:**
- Restore trust first: **quarantine** flaky tests with owners and tickets so the main pipeline is reliable again.
- Fix root causes: mocked backends and deterministic data, condition-based waits, disabled animations, state reset on launch, stable identifiers, page objects.
- Reduce the UI suite to critical journeys; move detailed checks to unit/snapshot tests.
- Track flakiness per test; make "red build" ownership clear (whoever broke it, or a rotating build cop).

### Q166. How would you migrate a large XCTest suite to Swift Testing? `[Lead/Expert]`
**Talking points:**
- No big bang: write **new** unit tests in Swift Testing; migrate existing ones opportunistically (when touching a file) or module by module.
- Watch for **parallelism issues**: tests relying on shared state or order will start failing; fix by isolating state or using `.serialized` temporarily.
- Replace `setUp`/`tearDown` with `init`/`deinit` or scoping traits; expectations with `confirmation` or direct `await`.
- Keep UI and performance tests in XCTest.
- Provide guidelines and examples; measure suite time and flakiness before and after.

### Q167. Manual regression testing takes QA three days per release. How do you reduce it? `[Lead/Expert]`
**Talking points:**
- Inventory the manual test cases; rank by risk and frequency of failure.
- Automate high-value, stable flows (UI tests with mocked data), and push detailed checks into unit/snapshot tests.
- Use feature flags and phased releases to reduce the blast radius of what's not covered.
- Shift QA effort to exploratory testing of new features and risk-based testing of changed areas.
- Track release cycle time and escaped defects to show progress.

### Q168. How would you convince management to invest in testing? `[Lead/Expert]`
**Talking points:**
- Use data: hotfix count, time spent on regressions, incident costs, release delays caused by manual testing, crash-free rate trends.
- Frame tests as **speed**: fewer regressions, safer refactors, faster releases, and quicker onboarding.
- Propose an incremental plan with measurable milestones (e.g. "critical flows automated in 6 weeks, regression testing time halved in a quarter").
- Report results to maintain support.

### Q169. How would you test an offline-first sync feature? `[Lead/Expert]`
**Talking points:**
- **Unit**: conflict resolution (three-way merge cases), outbox ordering, idempotency, retry/backoff with injected clocks, token handling.
- **Integration**: sync engine with an in-memory database and a fake server (scripted responses for conflicts, partial failures, tombstones, expired tokens).
- **Scenario tests**: offline edits then reconnect; edits on two "devices" (two sync engine instances against one fake server); app termination mid-sync (persisted outbox resumes).
- **Property-based**: random sequences of operations converge to the same state on all clients.
- **UI**: a few journeys with network toggled via mock scenarios; manual testing with Network Link Conditioner.

### Q170. A serious bug escaped to production. How do you improve the process? `[Lead/Expert]`
**Talking points:**
- **Blameless post-mortem**: timeline, root cause, why tests, reviews, and QA didn't catch it.
- Add the **regression test** at the right level (often unit or integration, plus a UI test if a journey was broken).
- Fix systemic gaps: missing test category (e.g. migration tests), unclear acceptance criteria, missing monitoring/alerting, risky rollout (no feature flag).
- Share learnings with the team; track action items to completion.

### Q171. How do you mentor engineers to write better tests? `[Senior]`
**Talking points:**
- Review tests as carefully as production code; comment on naming, behavior focus, determinism, and readability.
- Pair on TDD for a small feature to demonstrate the rhythm.
- Provide templates and examples (fixtures, controllable stubs, clock injection, page objects).
- Run short sessions on Swift Testing features, async testing, and flaky test debugging.
- Celebrate tests that caught real bugs, which reinforces their value.

### Final Tips
- **Testability is a design property**: dependency injection, controlled time and randomness, logic out of views (Section 2). Interviewers often probe this first.
- Know **Swift Testing** well (Section 5): `#expect` vs `#require`, parameterized tests, traits and tags, parallelism and `.serialized`, `confirmation`, `withKnownIssue`, and the XCTest mapping (Q54).
- Be able to test **async code deterministically** (Section 6): controllable stubs, injected clocks, awaiting task handles, never sleeping.
- Explain the **pyramid and its trade-offs**, how you keep **UI tests reliable** (Section 13), and how you handle **flaky tests** (Section 18).
- For Lead roles, have a **testing strategy story**: how you improved quality on a real team (metrics before/after, what you automated, how you changed habits).
