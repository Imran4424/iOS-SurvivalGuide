## 1. Fundamentals

### Q1. What is SwiftUI, and how does declarative UI differ from imperative UI? `[Fundamental]`
SwiftUI is Apple's **declarative** UI framework: you describe what the screen should look like for the current data, and SwiftUI updates the screen for you when the data changes.

- **Declarative (SwiftUI):** "When `count` is 5, the label shows 5." You only change the data.
- **Imperative (UIKit):** You change the screen yourself, step by step, like `label.text = "5"`. If you forget a step, the screen and the data no longer match.

```swift
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("Count: \(count)")             // always shows the current count
            Button("Increment") { count += 1 }  // we only change the data
        }
    }
}
```

**Follow-ups:**
- **What is the main benefit?** The screen always matches the data, so "the UI shows old data" bugs mostly disappear.
- **What is the cost?** You must understand how SwiftUI tracks data and views. If you don't, you get surprising resets or extra updates.
- **Can you mix SwiftUI and UIKit?** Yes. `UIHostingController` puts SwiftUI inside UIKit. `UIViewRepresentable` puts UIKit inside SwiftUI.

### Q2. What is the `View` protocol? `[Fundamental]`
`View` is the protocol every SwiftUI screen element follows, and its only requirement is a `body` property that describes what to show.

- `body` returns `some View`, which means "one specific kind of view."
- Built-in views like `Text` and `Image` are drawn by SwiftUI directly.
- Since the iOS 18 SDK, `View` is marked `@MainActor`, so view code runs on the main thread.

```swift
struct Greeting: View {
    let name: String

    var body: some View {          // the only requirement
        Text("Hello, \(name)")
    }
}
```

**Follow-ups:**
- **What is the `body` type of `Text`?** `Never`. `Text` is a built-in view that SwiftUI draws itself, so it has no `body` of its own.
- **What does `@MainActor` on `View` mean for you?** Your view code runs on the main thread, so it can update UI data without `await`.
- **Can your own view skip `body`?** No. Every view you write must have a `body`.

### Q3. Why are SwiftUI views structs instead of classes? `[Senior]`
SwiftUI views are **cheap descriptions** of the UI, not the real things on screen, so SwiftUI can create and throw them away very often, and structs make that fast.

- A view struct is like a recipe. SwiftUI reads the recipe and updates the real screen.
- Data that must last, like `@State`, is **not stored inside the struct**. SwiftUI keeps it somewhere safe and gives it back each time the struct is recreated.

```swift
struct Badge: View {
    let count: Int                         // comes from the parent, recreated each time
    @State private var isPulsing = false   // kept by SwiftUI, survives recreation

    var body: some View {
        Text("\(count)")
            .scaleEffect(isPulsing ? 1.2 : 1)
    }
}
```

**Follow-ups:**
- **Where is `@State` really stored?** In SwiftUI's own internal storage, linked to the view's place on screen. Not inside the struct.
- **Why can't you use a normal `var` to store data in a view?** The struct is recreated when the parent updates, so the value is lost. Changing it also doesn't update the screen.
- **Can views cause memory leaks?** The view structs can't. But the classes they hold, like view models, still can.

### Q4. Why does `body` return `some View`? `[Senior]`
`some View` means "this returns one specific view type, but I won't write out its long name," and the compiler still knows the exact type.

- The real type of a body can be very long, like `VStack<TupleView<(Text, Button<Text>)>>`. `some View` hides that.
- Because SwiftUI still knows the exact type, it can compare the old and new screen quickly and know which views are the same.

```swift
struct ProfileHeader: View {
    var body: some View {     // real type: VStack<TupleView<(Text, Button<Text>)>>
        VStack {
            Text("Sam")
            Button("Follow") {}
        }
    }
}
```

**Follow-ups:**
- **Can an `if/else` in `body` return two different view types?** Yes, because `@ViewBuilder` wraps both branches into one combined type.
- **Why not return `AnyView` instead?** `AnyView` hides the type from SwiftUI too. Then SwiftUI can't compare views well, which hurts performance.
- **What is the difference between `some View` and `any View`?** `some View` is one fixed type the compiler knows. `any View` would be a box that can hold different types, which is slower.

### Q5. What is `@ViewBuilder`? `[Fundamental]`
`@ViewBuilder` lets you list several views, and use `if` or `switch`, inside a closure or property, and it combines them into **one** view.

- `body` is a view builder automatically.
- You can add `@ViewBuilder` to your own properties, functions, and closure parameters.
- It also allows an `if` with no `else`: if the condition is false, nothing is shown.

```swift
struct ProfileView: View {
    let user: User?

    var body: some View {
        VStack {
            header
            if let user { Text(user.name) } else { Text("Guest") }
        }
    }

    @ViewBuilder                             // lets this property use if/else
    private var header: some View {
        if user?.isPremium == true {
            Label("Premium", systemImage: "star.fill")
        }                                    // no else needed
    }
}
```

**Follow-ups:**
- **What does an `if/else` become inside a view builder?** One combined view that holds either the first branch or the second.
- **What changed in Xcode 27?** `ViewBuilder` is now exposed as `ContentBuilder`, which Apple says makes builds much faster.
- **When do you need to write `@ViewBuilder` yourself?** When a property or function outside `body` needs to return different views with `if` or `switch`.

### Q6. Why does modifier order matter? `[Fundamental]`
Each modifier **wraps** the view in a new layer, so the order you write them in changes the result.

- Read the chain from top to bottom: each line wraps everything above it.
- In the example, padding then background means the yellow covers the padding too. Background then padding means the padding is outside the yellow.

```swift
Text("Hello")
    .padding()
    .background(.yellow)   // yellow covers text + padding

Text("Hello")
    .background(.yellow)   // yellow covers only the text
    .padding()             // padding is added outside the yellow
```

**Follow-ups:**
- **Which other modifiers are order-sensitive?** `.frame` with `.border`, `.clipShape` with `.shadow`, and `.padding` with `.onTapGesture` (it changes the tap area).
- **Why put `.shadow` after `.clipShape`?** If the shadow comes first, the clip cuts it off.
- **What is a simple way to think about it?** Boxes inside boxes. Each modifier is a new box around the previous ones.

### Q7. What are `Group`, `EmptyView`, and `AnyView`? `[Fundamental]`
They are three helper views: `Group` **groups** views without changing the layout, `EmptyView` **shows nothing**, and `AnyView` **hides** a view's real type.

- **`Group`:** handy to apply one modifier to several views at once.
- **`EmptyView`:** a placeholder when there is nothing to show.
- **`AnyView`:** avoid it when you can. It hides the type from SwiftUI, so SwiftUI can't compare views efficiently.

```swift
Group {
    Text("Title")
    Text("Subtitle")
}
.font(.headline)            // applies to both texts

func makeBadge(isNew: Bool) -> some View {
    isNew ? AnyView(Text("NEW")) : AnyView(EmptyView())   // ❌ works, but hides the type
}
```

**Follow-ups:**
- **What should you use instead of `AnyView`?** `@ViewBuilder` with `if/else`, `Group`, or generics. They keep the real type.
- **When is `AnyView` acceptable?** Rarely. For example, a plugin system where view types are unknown until runtime.
- **Does `Group` change the layout?** No. Its children are laid out as if `Group` wasn't there.

### Q8. What happens when a `@State` value changes? `[Senior]`
SwiftUI finds the views that **read** that value, runs their `body` again to get a new description, compares it with the old one, and updates **only what changed** on screen.

- Running `body` again is cheap. It only builds a description, not the real screen.
- Views that don't read the changed value are skipped.
- Several changes in the same moment are combined into one update.

```swift
struct Screen: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("\(count)")        // reads count → updated
            StaticFooter()          // doesn't read count → skipped
            Button("+1") { count += 1 }
        }
    }
}
```

**Follow-ups:**
- **Does the screen update instantly?** It updates in the next frame. Many changes made together become one update.
- **Does running `body` again redraw the whole screen?** No. SwiftUI only changes the parts that are different.
- **Why does this matter for performance?** The fewer views that read a fast-changing value, the less work each change causes.

## 2. View Identity, Lifetime & Dependencies

> This is the most important topic for senior SwiftUI interviews. Apple's WWDC21 session "Demystify SwiftUI" explains it well.

### Q9. What is view identity, and why does it matter? `[Senior]`
Identity is **how SwiftUI knows that a view after an update is the same view as before**, and it decides whether the view keeps its state or starts fresh.

- **Same identity:** SwiftUI updates the view in place. Its `@State` is kept, and changes can animate smoothly.
- **New identity:** SwiftUI removes the old view and inserts a new one. Its `@State` is reset, and you see a fade instead of a smooth change.
- Think of it like a person's ID card: a new haircut is still the same person, but a different ID card means a different person.

```swift
// Same identity: only the color changes, so it animates smoothly
Circle()
    .fill(isOn ? .green : .red)
    .animation(.default, value: isOn)
```

**Follow-ups:**
- **What happens to `@State` when identity changes?** It is thrown away. The new view starts with its default values.
- **What are the two kinds of identity?** Structural (from the view's type and position in code) and explicit (an ID you give, like `.id` or `ForEach` IDs).
- **What does a change of identity look like on screen?** The old view disappears and a new one appears, with a fade by default.

### Q10. What are structural identity and explicit identity? `[Senior]`
**Structural** identity comes from a view's type and its position in your code, while **explicit** identity comes from an ID you give it yourself.

- **Structural:** SwiftUI's default. The two branches of an `if/else` are in different positions, so they are two different views.
- **Explicit:** you give the ID, with `.id(_:)` or with the IDs in `ForEach` and `List`. Same ID means same view.

```swift
// Structural: two different views, each with its own state
if isLoggedIn {
    HomeView()
} else {
    LoginView()
}

// Explicit: each row's identity is its message ID
ForEach(messages) { message in      // uses message.id
    MessageRow(message: message)
}
```

**Follow-ups:**
- **Which one does SwiftUI use by default?** Structural. Explicit identity is used only where you give IDs.
- **Why does `AnyView` break structural identity?** Structural identity needs the view's type, and `AnyView` hides it.
- **Does `if #available` create two identities?** Yes, but that's fine. The iOS version never changes while the app runs.

### Q11. When should you use a conditional modifier instead of `if/else`? `[Senior]`
When it's **the same view** and only one property changes, put the condition **inside the modifier** (a ternary `? :`), so the view keeps one identity and keeps its state.

- **Ternary in the modifier:** one view, state kept, change animates smoothly.
- **`if/else` around the view:** two different views. Switching destroys one and creates the other, so state is lost.

```swift
// ❌ Two identities: state resets, views cross-fade
if isHighlighted {
    CardView().background(.yellow)
} else {
    CardView()
}

// ✅ One identity: state is kept, background animates
CardView()
    .background(isHighlighted ? Color.yellow : Color.clear)
```

**Follow-ups:**
- **What's wrong with the popular `.if(condition) { ... }` helper?** It hides an `if/else` inside, so it has the same state-reset problem.
- **When is `if/else` correct?** When the two branches are truly different screens, like Login and Home.
- **How do you hide a view but keep its state?** Use `.opacity(0)` or `.hidden()` instead of removing it with `if`.

### Q12. What does `.id(_:)` do, and when would you use it? `[Senior]`
`.id(_:)` gives a view an explicit identity, and **when the ID changes, SwiftUI throws the view away and creates a fresh one**, resetting all its state.

- **Use it to reset a view on purpose.** For example, clear an editor's state when the user picks a different document.
- **Use it as a scroll target** with `ScrollViewReader`.

```swift
// When a different document is selected, the editor starts fresh
DocumentEditor(document: selectedDocument)
    .id(selectedDocument.id)
```

**Follow-ups:**
- **What is the common mistake?** Using a value that changes every time, like `.id(UUID())`. The view is rebuilt on every update and loses its state.
- **Does a new ID run `.task` and `.onAppear` again?** Yes, because SwiftUI treats it as a brand-new view.
- **How else can you scroll to a view?** `ScrollViewReader` with `proxy.scrollTo(id)`, or `scrollPosition(id:)` on iOS 17+.

### Q13. What is the difference between a view's lifetime and its identity? `[Senior]`
The view **struct** lives for a very short time, but the view's **lifetime** is how long its identity stays on screen, and that's what `@State` and `.task` follow.

- The struct is recreated every time the parent's `body` runs, maybe many times a second.
- The lifetime starts when the view first appears with an identity, and ends when that identity is removed.
- `@State`, `@StateObject`, and `.task` live for the **lifetime**, not for one struct.

```swift
struct Row: View {
    let title: String
    init(title: String) {
        self.title = title
        print("init")      // may print many times while the row stays on screen
    }
    var body: some View { Text(title) }
}
```

**Follow-ups:**
- **Why avoid heavy work in a view's `init`?** It can run many times for the same view on screen.
- **Where should setup work go?** In `.task` or `.onAppear`, which run when the view appears.
- **When does a view's lifetime end?** When its identity leaves the screen, for example an `if` branch switches or a row is deleted.

### Q14. Why must `ForEach` identifiers be stable and unique? `[Senior]`
SwiftUI uses the IDs to **match each row with its old version**, so if IDs change or repeat, rows can lose their state, animate wrongly, or show the wrong data.

- **Stable:** the same item keeps the same ID forever, like a database ID.
- **Unique:** no two items share an ID.
- Using the array **index** as the ID is risky: delete the first row and every other row gets a new index, so SwiftUI thinks they all changed.

```swift
// ❌ Index as ID: deleting row 0 changes every row's ID
ForEach(items.indices, id: \.self) { index in
    ItemRow(item: items[index])
}

// ✅ Stable, unique ID from the data
ForEach(items) { item in        // Item is Identifiable, id comes from the server
    ItemRow(item: item)
}
```

**Follow-ups:**
- **Is `id: \.self` ever fine?** Yes, for a fixed list of unique values like `["S", "M", "L"]`.
- **Why not create a `UUID()` inside the model for server data?** Each fetch creates new IDs for the same items. Use the server's ID instead.
- **What happens with duplicate IDs?** SwiftUI logs a warning, and rows can show or update the wrong content.

### Q15. What are a view's dependencies? `[Senior]`
A view's dependencies are **all the changing data it reads in `body`**, and when any of them changes, SwiftUI runs that view's `body` again.

- Its input properties (what the parent passed in).
- Its `@State` and `@Binding` values.
- Environment values it reads, like `locale`.
- Properties of observed models that `body` reads.

```swift
struct PriceLabel: View {
    let price: Decimal                         // input from the parent
    @Environment(\.locale) private var locale  // environment value
    @State private var showDetails = false     // local state

    var body: some View {
        Text(price, format: .currency(code: "USD"))
    }
}
```

**Follow-ups:**
- **How do you reduce a view's dependencies?** Pass only what it needs, like `item.title` instead of the whole model.
- **Are values used only inside a button action dependencies?** No. Only values read while `body` runs count.
- **How do you see which dependency changed?** Add `let _ = Self._printChanges()` inside `body` while debugging.

### Q16. Does SwiftUI re-run `body` for a child when its parent's `body` runs? `[Lead/Expert]`
**Not always**: the child struct is recreated, but SwiftUI compares the child's inputs with the old ones, and if nothing changed, it can skip the child's `body`.

- Simple values like `String` and `Int` are easy to compare, so skipping works well.
- **Closures can't be compared.** A child that takes a closure is often treated as "changed," so its `body` runs again.
- Skipping is an optimization, not a promise. Your code must still be correct if `body` runs more often.

```swift
struct Parent: View {
    @State private var tick = 0
    var body: some View {
        VStack {
            Button("Tick \(tick)") { tick += 1 }
            Avatar(name: "Sam")      // same input each time → body can be skipped
        }
    }
}
```

**Follow-ups:**
- **How can you control the comparison yourself?** Make the view `Equatable` and compare only the fields that matter (see Q102).
- **Why do closures cause extra updates?** SwiftUI can't tell whether two closures do the same thing, so it assumes they're different.
- **Is skipping guaranteed?** No. Write code that works even if `body` runs more often.

## 3. State Management & Property Wrappers

### Q17. What is `@State`? `[Fundamental]`
`@State` stores a value that **a view owns and changes itself**, and when the value changes, SwiftUI updates the view.

- **Use it for** simple local UI values: a toggle, text in a text field, the selected tab.
- **Mark it `private`**, because only this view should change it.
- **Since iOS 17**, you also use `@State` to own an `@Observable` model object.

```swift
struct SearchBar: View {
    @State private var text = ""        // this view owns it

    var body: some View {
        TextField("Search", text: $text)   // $text gives the text field a binding
    }
}
```

**Follow-ups:**
- **How does another view change this value?** The owner passes it down as a binding with `$text`.
- **Can `@State` hold a class?** Yes, since iOS 17, for `@Observable` classes. That's how a view owns its model.
- **What happens to `@State` when the view leaves the screen?** It is thrown away.

### Q18. What is `@Binding`? `[Fundamental]`
`@Binding` gives a child view **read and write access to a value that its parent owns**, without copying it.

- The parent owns the value with `@State`.
- The parent passes `$value` to the child.
- When the child changes it, the parent's value changes too.
- Think of it as a remote control for someone else's TV.

```swift
struct SettingsView: View {
    @State private var notificationsEnabled = true        // parent owns it
    var body: some View {
        NotificationToggle(isOn: $notificationsEnabled)  // pass a binding with $
    }
}

struct NotificationToggle: View {
    @Binding var isOn: Bool                               // child can read and change it
    var body: some View { Toggle("Notifications", isOn: $isOn) }
}
```

**Follow-ups:**
- **Does a binding copy the value?** No. It reads and writes the parent's original value.
- **When should a child use a plain `let` instead?** When it only shows the value and never changes it.
- **How do you preview a view that needs a binding?** Use `.constant(true)`, or `@Previewable @State` in iOS 18 previews.

### Q19. How do you create custom, derived, and constant bindings? `[Senior]`
There are four common ways to make a binding: **custom** with `get` and `set`, **to each array element** with `List($items)`, **to a property** with `$model.property`, and **fixed** with `.constant(value)`.

- **Custom (`Binding(get:set:)`):** when the value must be converted, like "dark mode on/off" to a theme enum.
- **Per element:** each row gets a binding to its own item.
- **Constant:** for previews or read-only cases.

```swift
// Custom: convert a theme enum to a Bool for the toggle
Toggle("Dark Mode", isOn: Binding(
    get: { settings.theme == .dark },
    set: { settings.theme = $0 ? .dark : .light }
))

// Per element (iOS 15+): each row edits its own todo
List($todos) { $todo in
    Toggle(todo.title, isOn: $todo.isDone)
}

// Constant: never changes
Toggle("Preview", isOn: .constant(true))
```

**Follow-ups:**
- **What is the downside of `Binding(get:set:)`?** It's recreated on every update and can't be compared, so it can cause extra updates. Use `$model.property` when you can.
- **How does `$profile.name` work?** A binding to the whole `profile` can create a binding to just its `name`.
- **Can you turn a `Binding<String?>` into a `Binding<String>`?** Yes, with `Binding($optionalValue)`. It returns `nil` if the value is `nil`.

### Q20. What is the difference between `@StateObject` and `@ObservedObject`? `[Senior]`
`@StateObject` is for an object the view **creates and owns**, while `@ObservedObject` is for an object the view **receives from someone else**.

- **`@StateObject`:** SwiftUI creates the object **once** and keeps it alive while the view is on screen, even when the struct is recreated.
- **`@ObservedObject`:** the view only watches the object. The parent must keep it alive.
- Both are for `ObservableObject` classes (the older system before iOS 17).

```swift
struct ProfileScreen: View {
    @StateObject private var model = ProfileModel()   // created once, owned here
    var body: some View { ProfileDetails(model: model) }
}

struct ProfileDetails: View {
    @ObservedObject var model: ProfileModel           // received from the parent
    var body: some View { Text(model.name) }
}
```

**Follow-ups:**
- **What is the classic bug?** Writing `@ObservedObject var model = Model()`. A new model is created every time the parent updates, so data resets.
- **How does `@StateObject` create the object only once?** It stores the creation code and runs it only the first time.
- **What replaces these with `@Observable` (iOS 17+)?** `@State` to own it, and a plain property or `@Bindable` to receive it.

### Q21. What is `@EnvironmentObject`? `[Fundamental]`
`@EnvironmentObject` lets **any view deep in the tree read a shared object** that an ancestor view put into the environment, without passing it through every level.

- An ancestor adds it with `.environmentObject(object)`.
- Any child below reads it with `@EnvironmentObject`.
- **If no ancestor added it, the app crashes** when the view reads it.

```swift
ContentView()
    .environmentObject(AppSettings())      // put it in the environment

struct ThemeLabel: View {
    @EnvironmentObject var settings: AppSettings   // read it anywhere below
    var body: some View { Text(settings.themeName) }
}
```

**Follow-ups:**
- **What is the iOS 17+ version?** `.environment(object)` to add it and `@Environment(Type.self)` to read it.
- **Why does it crash instead of failing to compile?** The compiler can't check at build time that an ancestor added it.
- **What is the downside of using it a lot?** Dependencies are hidden, and previews crash unless you add every object.

### Q22. What are the rules for choosing the right property wrapper? `[Senior]`
First ask **"Who owns this data?"**: the owner uses `@State`, and everyone else either just reads it or gets a binding.

| Situation | Use |
|---|---|
| Simple value this view owns | `@State` |
| Value the parent owns, and I need to change it | `@Binding` |
| Model object this view owns (iOS 17+) | `@State` + `@Observable` class |
| Model object passed in, read only | plain `let`/`var` |
| Model object passed in, I need `$` bindings | `@Bindable` |
| Model shared deep in the app | `@Environment(Model.self)` |
| System value (dismiss, color scheme) | `@Environment(\.key)` |

```swift
struct EditorScreen: View {
    @State private var isPreviewing = false          // simple, owned
    @State private var model = EditorModel()         // @Observable model, owned
    @Environment(\.dismiss) private var dismiss      // system value
    @Environment(Session.self) private var session   // shared model

    var body: some View { EditorForm(model: model) }
}

struct EditorForm: View {
    @Bindable var model: EditorModel                 // passed in, needs $ bindings
    var body: some View { TextField("Title", text: $model.title) }
}
```

**Follow-ups:**
- **What is the iOS 13–16 version of this table?** `@StateObject` to own, `@ObservedObject` to receive, `@EnvironmentObject` to share.
- **When do you need `@Bindable` instead of a plain property?** Only when you need `$` bindings, for example for a `TextField`.
- **Why is "who owns it?" the key question?** There should be exactly one owner. Everyone else reads it or gets a binding.

### Q23. How do you initialize `@State` from a value passed into the view? What's the catch? `[Senior]`
You set it in `init` with `_draft = State(initialValue: value)`, but **the value is used only the first time**, so later changes from the parent are ignored.

- `@State` belongs to the view. After the first time, SwiftUI keeps its own copy.
- So if the parent later passes a new value, the `@State` keeps the old one.
- This is fine for a **local draft** you edit and save later.

```swift
struct NameEditor: View {
    @State private var draft: String

    init(initialName: String) {
        _draft = State(initialValue: initialName)   // used only the first time
    }

    var body: some View { TextField("Name", text: $draft) }
}
```

**Follow-ups:**
- **What if the child should always show the parent's latest value?** Use a plain `let` or a `@Binding` instead of `@State`.
- **What if it should reset when the input changes?** Add `.id(initialName)` to the child, or update it in `.onChange(of:)`.
- **When is this pattern a good idea?** For an editable copy, like a form draft that is saved only when the user taps Save.

### Q24. What is a "single source of truth," and why does it matter? `[Senior]`
It means **each piece of data is stored in exactly one place**, and every other view reads it from there or gets a binding to it.

- If the same data is copied into two places, the copies can get out of sync.
- Instead of storing a second copy, **calculate** it from the original (a "derived" value).

```swift
struct CartView: View {
    @State private var items: [Item] = []            // stored once: the source of truth

    private var total: Decimal {                     // calculated, not stored
        items.reduce(0) { $0 + $1.price }
    }

    var body: some View { Text(total, format: .currency(code: "USD")) }
}
```

**Follow-ups:**
- **How do you notice two sources of truth?** Code that copies a value and then "syncs" it back in `onChange`.
- **When is storing a calculated value OK?** When it's expensive to calculate. Store it in the model and update it when the source changes.
- **How do bindings help?** A binding lets a child change the data without making its own copy.

### Q25. What is `@AppStorage` and `@SceneStorage`? `[Fundamental]`
`@AppStorage` saves a small value in **`UserDefaults`** for the whole app, and `@SceneStorage` saves a small value **for one window** so it can be restored later.

- **`@AppStorage`:** settings and preferences, like "has seen onboarding." The view updates when the value changes.
- **`@SceneStorage`:** UI state for one window, like the selected tab or a text draft. The system restores it if the window is recreated.

```swift
@AppStorage("hasSeenOnboarding") private var hasSeenOnboarding = false
@SceneStorage("selectedTab") private var selectedTab = Tab.home
```

**Follow-ups:**
- **Can you store a login token in `@AppStorage`?** No. `UserDefaults` is not secure. Use the Keychain for secrets.
- **What types can `@AppStorage` store?** Simple ones: `Bool`, `Int`, `Double`, `String`, `URL`, `Data`, and enums with `String` or `Int` raw values.
- **When is `@SceneStorage` restored?** When the system recreates the window, for example after the app was closed in the background.

### Q26. What is `@FocusState`? `[Fundamental]`
`@FocusState` tracks **which text field is active** (has the keyboard), and you can change it to move the cursor or hide the keyboard.

- Connect each field with `.focused($focusedField, equals: .email)`.
- Set the value to move focus to another field.
- Set it to `nil` to hide the keyboard.

```swift
struct LoginForm: View {
    enum Field { case email, password }
    @State private var email = ""
    @State private var password = ""
    @FocusState private var focusedField: Field?

    var body: some View {
        Form {
            TextField("Email", text: $email)
                .focused($focusedField, equals: .email)
                .onSubmit { focusedField = .password }   // Return → go to password
            SecureField("Password", text: $password)
                .focused($focusedField, equals: .password)
                .onSubmit { focusedField = nil }          // Return → hide keyboard
        }
        .onAppear { focusedField = .email }               // start in the email field
    }
}
```

**Follow-ups:**
- **How do you change the Return key's label?** With `.submitLabel(.next)` or `.submitLabel(.go)`.
- **Can you use a `Bool` for one field?** Yes: `@FocusState private var isFocused: Bool` with `.focused($isFocused)`.
- **Why might setting focus in `onAppear` not work?** The field may not be ready yet. Setting it in `.task` or a moment later usually works.

### Q27. What is `DynamicProperty`? `[Lead/Expert]`
`DynamicProperty` is the protocol behind `@State`, `@Environment`, and `@Query`, and you can use it to build **your own property wrapper that works inside views**.

- SwiftUI updates dynamic properties right before it runs `body`.
- Inside your wrapper you can use `@State` or `@Environment`.
- This lets you package reusable view logic, like reading a feature flag.

```swift
@propertyWrapper
struct FeatureFlag: DynamicProperty {
    @Environment(\.featureFlags) private var flags   // reads the environment
    let name: String

    var wrappedValue: Bool { flags.isEnabled(name) }
}

struct CheckoutView: View {
    @FeatureFlag(name: "applePay") var showApplePay
    var body: some View { if showApplePay { Text("Apple Pay") } }
}
```

**Follow-ups:**
- **Is there a hook that runs before `body`?** Yes, `update()`. SwiftUI calls it before each `body` run.
- **Why not just write a helper function?** A function can't hold `@State` or read the environment. The wrapper can.
- **Where does it work?** Only inside views, because SwiftUI is what updates it.

## 4. The Observation Framework (`@Observable`)

### Q28. What is `@Observable`, and how does it differ from `ObservableObject`? `[Senior]`
`@Observable` is the iOS 17 way to make a model class that SwiftUI watches, and the big difference is that **SwiftUI only updates the views that read the property that changed**.

- **`ObservableObject` (old):** you mark properties with `@Published`. When **any** of them changes, **every** view watching the object updates.
- **`@Observable` (new):** every stored property is watched automatically. A view updates only if it **reads** the property that changed.
- Less code, and fewer unnecessary updates.

```swift
// Old (iOS 13+)
final class CartStore: ObservableObject {
    @Published var items: [Item] = []
    @Published var couponCode = ""
}

// New (iOS 17+)
@Observable
final class CartStore {
    var items: [Item] = []
    var couponCode = ""
}
```

**Follow-ups:**
- **Do you still need `@Published`?** No. Every stored property is watched. Use `@ObservationIgnored` to skip one.
- **Is it built on Combine?** No. It uses Swift's Observation framework, so `$property` publishers don't exist anymore.
- **Does it work with nested objects and arrays?** Yes. It tracks whatever the view reads, even through nested `@Observable` objects.

### Q29. Why is `@Observable` better for performance? `[Senior]`
Because SwiftUI tracks **exactly which properties each view reads**, so a change to one property only updates the views that use that property.

- In the example, the badge reads only `items`.
- If `couponCode` changes, the badge does **not** update.
- With `ObservableObject`, the badge **would** update, because any `@Published` change notifies everyone.

```swift
struct CartBadge: View {
    let cart: CartStore              // @Observable
    var body: some View {
        Text("\(cart.items.count)")  // reads only items → updates only when items change
    }
}
```

**Follow-ups:**
- **Does reading a property inside a button action count?** No. Only reads inside `body` are tracked.
- **Can you still get too many updates?** Yes, if one big view reads many properties. Splitting it into smaller views still helps.
- **How do you prove it got better?** Count `body` updates with `Self._printChanges()` or the SwiftUI instrument, before and after.

### Q30. What is `@Bindable`? `[Senior]`
`@Bindable` lets a view **create `$` bindings to an `@Observable` object that it doesn't own**, for example to connect a `TextField` to a model property.

- Use it as a property wrapper when the object is passed in by a parent.
- Or create it as a local variable inside `body` when the object comes from the environment.
- You only need it for `$` bindings. Just reading values needs nothing special.

```swift
@Observable final class Profile { var name = ""; var bio = "" }

struct ProfileEditor: View {
    @Bindable var profile: Profile          // passed in by the parent
    var body: some View {
        TextField("Name", text: $profile.name)
    }
}

struct SettingsScreen: View {
    @Environment(Profile.self) private var profile
    var body: some View {
        @Bindable var profile = profile     // make it bindable inside body
        TextField("Name", text: $profile.name)
    }
}
```

**Follow-ups:**
- **Do you need `@Bindable` just to show values?** No. A plain property is enough to read and track changes.
- **Why can't you write `$profile` with `@Environment(Profile.self)`?** The environment gives read access only. Wrap it in a local `@Bindable` to get bindings.
- **What if the view owns the object with `@State`?** Then `$model.name` already works. `@State` gives bindings.

### Q31. How do you own an `@Observable` model in a view, and what's the pitfall? `[Lead/Expert]`
You own it with `@State private var model = Model()`, and the pitfall (before Xcode 27) is that **`Model()` can be created many times**, because the view struct is recreated often.

- Before Xcode 27: each time the parent updates, `Model()` runs again. SwiftUI keeps the first one and throws the extra ones away.
- If `Model.init` starts network calls or timers, that wasted work can cause bugs.
- **Xcode 27:** `@State` became a macro, and it now creates a stored class **only once** per view lifetime.
- **Best practice either way:** keep `init` cheap and start work in `.task`.

```swift
struct FeedScreen: View {
    @State private var model = FeedModel()   // keep FeedModel.init cheap

    var body: some View {
        FeedList(model: model)
            .task { await model.loadIfNeeded() }   // start work here, not in init
    }
}
```

**Follow-ups:**
- **Why didn't `@StateObject` have this problem?** It stores the creation code and runs it only the first time.
- **How do you avoid it on older Xcode versions?** Keep `init` cheap, create the model in a parent and pass it down, or create it in `.task` into an optional `@State`.
- **Did the Xcode 27 change break any code?** Yes, one case. A property with a default value that is also set in `init` now gives a "used before being initialized" error. Remove the default value.

### Q32. What does `@ObservationIgnored` do? `[Senior]`
`@ObservationIgnored` tells Observation **not to watch a property**, so changing it never updates any view.

- Use it for things the UI doesn't show: caches, formatters, internal counters, and services.
- This avoids pointless view updates.

```swift
@Observable
final class SearchModel {
    var query = ""                                              // watched
    var results: [Result] = []                                  // watched
    @ObservationIgnored private var cache: [String: [Result]] = [:]   // not watched
    @ObservationIgnored private let api: SearchAPI                    // not watched

    init(api: SearchAPI) { self.api = api }
}
```

**Follow-ups:**
- **What happens if you don't ignore a cache?** Every cache write can update views that read it, for no visible reason.
- **Do computed properties need it?** No. They're tracked through the stored properties they use.
- **Is a `let` property watched?** No. It can never change, so there's nothing to watch.

### Q33. How do you share an `@Observable` object through the environment? `[Fundamental]`
You **add it** with `.environment(object)` near the top of the app, and **read it** with `@Environment(Type.self)` in any view below.

- Keep the object in `@State` in the `App` (or a root view) so it lives for the whole app.
- Any view below can read it without passing it through every level.

```swift
@main
struct ShopApp: App {
    @State private var cart = Cart()          // owned once for the whole app
    var body: some Scene {
        WindowGroup {
            ContentView().environment(cart)   // add it to the environment
        }
    }
}

struct CartBadge: View {
    @Environment(Cart.self) private var cart  // read it anywhere below
    var body: some View { Text("\(cart.items.count)") }
}
```

**Follow-ups:**
- **What happens if no ancestor added it?** The app crashes. Use `@Environment(Cart.self) private var cart: Cart?` if it might be missing.
- **Why keep it in `@State`?** So one single instance is created and kept alive.
- **Can you add two objects of the same type?** A view only sees the nearest one. Use a custom key (`@Entry`) if you need two.

### Q34. How do you observe changes to `@Observable` properties outside SwiftUI? `[Lead/Expert]`
Use **`withObservationTracking`** for a one-time "tell me when this changes" callback, or, from Swift 6.2 (iOS 26), **`Observations`**, which gives you new values as an async stream.

- **`withObservationTracking`:** reads the properties in the first closure, then calls `onChange` **once**, just **before** the next change. To keep watching, call it again.
- **`Observations`:** a loop that gets every new value, which is easier to use.
- Useful in UIKit code, services, or tests.

```swift
// One-time: called once, right before total changes
withObservationTracking {
    _ = cart.total
} onChange: {
    print("total is about to change")
}

// Swift 6.2: a stream of new values
for await total in Observations({ cart.total }) {
    print("New total: \(total)")
}
```

**Follow-ups:**
- **Why doesn't `onChange` give you the new value?** It runs before the change happens, so the new value isn't set yet.
- **When would you need this?** When UIKit code or a service must react to a model that SwiftUI also uses.
- **If several properties change at once, how many values does `Observations` give?** One. It groups changes from the same update.

### Q35. How would you migrate a codebase from `ObservableObject` to `@Observable`? `[Lead/Expert]`
First make sure the app's minimum version is **iOS 17**, then convert **one model at a time** and update the places that use it.

1. In the class: replace `ObservableObject` with `@Observable` and remove `@Published`.
2. `@StateObject` → `@State`.
3. `@ObservedObject` → a plain property, or `@Bindable` if you need `$` bindings.
4. `.environmentObject(x)` → `.environment(x)`, and `@EnvironmentObject` → `@Environment(Type.self)`.

```swift
// Before
@StateObject private var model = ProfileModel()
.environmentObject(session)
@EnvironmentObject var session: Session

// After
@State private var model = ProfileModel()
.environment(session)
@Environment(Session.self) private var session
```

**Follow-ups:**
- **What breaks most often?** Code that listened to `$property` Combine publishers. They don't exist with `@Observable`.
- **What else should you add?** `@MainActor` on UI models, so Swift 6 checks that changes happen on the main thread.
- **In what order?** Start with small models used in few places, measure, then move to bigger ones step by step.

## 5. Environment & Preferences

### Q36. What is the SwiftUI environment? `[Fundamental]`
The environment is a set of shared values that **flows down automatically to all child views**, like color scheme, language, text size, and the `dismiss` action.

- You set a value once on a parent, and every view below can read it.
- Any child can override it for its own part of the tree.
- You can add your own values too.

```swift
struct DetailView: View {
    @Environment(\.dismiss) private var dismiss          // an action
    @Environment(\.colorScheme) private var colorScheme  // light or dark

    var body: some View {
        Button("Close") { dismiss() }
            .foregroundStyle(colorScheme == .dark ? .white : .black)
    }
}
```

**Follow-ups:**
- **Does changing an environment value update every view?** No. Only views that read that value update.
- **Can a child change the value for its children?** Yes. Apply the modifier again lower in the tree.
- **Which useful actions come from the environment?** `dismiss`, `openURL`, `refresh`, and `modelContext`.

### Q37. How do you define a custom environment value? `[Senior]`
Since Xcode 16, you add an **`@Entry`** property in an extension of `EnvironmentValues`, with a default value.

- Set it with `.environment(\.theme, .dark)`.
- Read it with `@Environment(\.theme)`.
- `@Entry` works on older iOS versions too, because it's just generated code.

```swift
extension EnvironmentValues {
    @Entry var theme: Theme = .standard      // default value
}

ContentView().environment(\.theme, .dark)   // set it

struct ThemedButton: View {
    @Environment(\.theme) private var theme  // read it
    var body: some View { Button("Buy") {}.tint(theme.accent) }
}
```

**Follow-ups:**
- **How was it done before `@Entry`?** You made a struct conforming to `EnvironmentKey` with a `defaultValue`, plus a computed property with `get` and `set`.
- **Why is a default value required?** So a view always gets a value, even when no parent set one.
- **Can you make a nicer modifier for it?** Yes: `func theme(_ t: Theme) -> some View { environment(\.theme, t) }`.

### Q38. When should you use the environment vs passing values through initializers? `[Senior]`
**Pass values through the initializer by default**, because it's clear and checked by the compiler, and use the **environment** for things many views need at different levels.

- **Initializer:** data a child clearly needs, like `ProductRow(product:)`.
- **Environment:** app-wide things like a theme, services, feature flags, or a router.

```swift
// Initializer: the parent gives the child its data directly
ProductRow(product: product)

// Environment: shared things needed deep in the tree
ContentView()
    .environment(\.theme, .dark)
    .environment(router)
```

**Follow-ups:**
- **What's the risk of using the environment too much?** You can't see what a view depends on, and a missing object crashes at runtime.
- **What is "prop drilling"?** Passing a value through many views that don't use it, just to reach a deep child. The environment avoids that.
- **Which is easier to test?** The initializer, because you can see everything the view needs.

### Q39. What are preference keys? `[Senior]`
Preference keys send data **up** from child views to a parent, which is the **opposite** direction of the environment.

- A child sets a value, for example its width.
- The parent reads it with `.onPreferenceChange`.
- If many children set the same key, `reduce` decides how to combine them, for example keep the largest.
- SwiftUI itself uses this for things like `navigationTitle`.

```swift
struct MaxWidthKey: PreferenceKey {
    static let defaultValue: CGFloat = 0
    static func reduce(value: inout CGFloat, nextValue: () -> CGFloat) {
        value = max(value, nextValue())     // keep the largest width
    }
}

// Child: report its width
Text(title)
    .background(GeometryReader { proxy in
        Color.clear.preference(key: MaxWidthKey.self, value: proxy.size.width)
    })

// Parent: receive it
.onPreferenceChange(MaxWidthKey.self) { labelWidth = $0 }
```

**Follow-ups:**
- **Why `static let` for `defaultValue`?** `static var` is shared mutable state, which Swift 6 reports as an error.
- **What does `reduce` do?** Combines values when several children report the same key.
- **Is there an easier way to read a size?** Yes, `onGeometryChange` (see Q51).

## 6. Layout System

### Q40. How does SwiftUI's layout system work? `[Senior]`
Layout is a **three-step conversation** between parent and child: the parent **offers** a size, the child **chooses** its own size, and the parent **places** the child.

1. Parent: "You can have up to 300 × 400."
2. Child: "I only need 50 × 20." (The child decides.)
3. Parent: places the child, centered by default.

- That's why `Text` stays small (it only needs its text) and `Color` fills everything (it takes all it's offered).

```swift
HStack {
    Text("Hi")          // takes only what it needs
    Color.blue          // takes all the remaining space
}
.frame(height: 44)
```

**Follow-ups:**
- **Are `.frame` and `.padding` part of this?** Yes. They change what is offered to the child or where it's placed.
- **Can a child be bigger than what it was offered?** Yes. It can choose a bigger size and overflow.
- **What is an "ideal size"?** The size a view wants when there's no limit. `.fixedSize()` tells a view to use it.

### Q41. How does `.frame` actually work? `[Senior]`
`.frame` puts the view **inside an invisible box** of that size. It doesn't stretch the view itself.

- The box offers its size to the view inside.
- The view can still be smaller, and it's centered in the box by default.
- `.frame(maxWidth: .infinity)` makes the box as wide as possible. Use `alignment:` to move the view inside it.

```swift
Text("Hi")
    .frame(width: 200, height: 100)   // a 200×100 box; the text stays small, centered
    .background(.blue)                // blue fills the whole box

Text("Left aligned")
    .frame(maxWidth: .infinity, alignment: .leading)   // full-width box, text on the left
```

**Follow-ups:**
- **Why doesn't `.frame` make the text bigger?** The frame is a separate box. The text inside still chooses its own size.
- **What does `.frame(minHeight: 44)` do?** Makes the box at least 44 points tall, a common size for easy tapping.
- **Why does `.background` after `.frame` fill the whole box?** Because the background is applied to the box, not to the text.

### Q42. How do stacks distribute space? What are `layoutPriority` and `fixedSize`? `[Senior]`
A stack gives space to the **least flexible children first**, then shares what's left with the flexible ones, and you can change this with `layoutPriority` and `fixedSize`.

- **`.layoutPriority(1)`:** this child gets space before the others (default priority is 0).
- **`.fixedSize()`:** this view uses its ideal size and ignores the space offered.

```swift
HStack {
    Text("A very long product title that might truncate")
        .lineLimit(1)
    Spacer()
    Text("$1,299.00")
        .layoutPriority(1)     // the price gets space first, so it never gets cut off
}
```

**Follow-ups:**
- **How do you let text wrap onto as many lines as it needs?** `.fixedSize(horizontal: false, vertical: true)`.
- **What is the default priority?** `0`. Higher numbers get space first.
- **What is the risk of `fixedSize()`?** The view may overflow its container, because it ignores the space it's given.

### Q43. Compare `VStack`, `LazyVStack`, and `List`. `[Senior]`
`VStack` creates **all** its rows at once, `LazyVStack` creates rows **only when they scroll into view**, and `List` is also lazy and gives you **built-in features** like swipe actions and selection.

- **`VStack`:** small, fixed content, like a form section.
- **`LazyVStack` (inside a `ScrollView`):** long feeds with a custom look.
- **`List`:** long lists with system features: swipe actions, selection, edit mode, and reused rows.

```swift
ScrollView {
    LazyVStack(spacing: 12) {       // rows are created as you scroll
        ForEach(posts) { PostCard(post: $0) }
    }
}

List(posts) { PostRow(post: $0) }   // lazy, reuses rows, built-in features
```

**Follow-ups:**
- **Which uses less memory for very large data?** `List`, because it reuses rows. `LazyVStack` doesn't recycle rows the same way.
- **Does a `VStack` inside a `ScrollView` become lazy?** No. It still creates every row immediately.
- **What changed for swipe actions in iOS 27?** The new `swipeActionsContainer()` modifier lets swipe actions work in `ScrollView` and lazy stacks, not only `List`.

### Q44. What is `Spacer`, and what are common layout mistakes with it? `[Fundamental]`
`Spacer` is an empty, flexible view that **takes up all the free space** in a stack and pushes other views apart.

- In an `HStack` it pushes sideways. In a `VStack` it pushes up and down.
- **Mistake 1:** using it in a `ZStack`. A `ZStack` has no direction, so it does nothing useful.
- **Mistake 2:** using it in a `ScrollView` to fill the screen. A scroll view has unlimited space, so there's nothing to fill.

```swift
HStack {
    Text("Name")
    Spacer()             // pushes "Sam" to the right edge
    Text("Sam")
}

Spacer(minLength: 0)     // removes the small default minimum gap
```

**Follow-ups:**
- **How do you make content fill the screen inside a `ScrollView`?** Use `.containerRelativeFrame(.vertical)` or a `minHeight` based on the container size.
- **Is `Spacer` the same as padding?** No. Padding is a fixed amount. `Spacer` takes whatever space is left.
- **What does `Spacer` do in a `VStack`?** It grows vertically, pushing views to the top or bottom.

### Q45. What is `GeometryReader`, and what are its pitfalls? `[Senior]`
`GeometryReader` **tells you the size and position** available to it, but it has side effects that often break layouts.

- **Pitfall 1:** it takes **all** the space it's offered.
- **Pitfall 2:** it puts its content in the **top-left** corner, not the center.
- **Pitfall 3:** saving its size into `@State` can cause a loop: size changes → layout changes → size changes again.
- Often there's a simpler modern tool for the job.

```swift
GeometryReader { proxy in
    Text("Width: \(Int(proxy.size.width))")   // placed at the top-left
}
.frame(height: 44)                            // limit it, or it takes all the space
```

**Follow-ups:**
- **What are modern alternatives?** `containerRelativeFrame`, `onGeometryChange`, `ViewThatFits`, a custom `Layout`, and `visualEffect`.
- **Why put it in a `.background`?** There it measures the view without changing the layout.
- **What is a layout loop?** A measured size updates state, which changes the layout, which changes the size, again and again.

### Q46. What is `ViewThatFits`? `[Senior]`
`ViewThatFits` takes **several versions** of a view and shows **the first one that fits** in the available space.

- Great for small screens and very large accessibility text.
- If none fit, it shows the last one.

```swift
ViewThatFits(in: .horizontal) {
    HStack { actionButtons }            // 1st choice: buttons side by side
    VStack { actionButtons }            // 2nd choice: buttons stacked
    Menu("Actions") { actionButtons }   // last resort: a menu
}
```

**Follow-ups:**
- **What if none fit?** It uses the last option.
- **What does `in: .horizontal` mean?** Only the width is checked. The height can grow.
- **How is it different from `AnyLayout`?** `ViewThatFits` picks by available space. `AnyLayout` switches by your own condition and keeps the children's state.

### Q47. What is `AnyLayout`, and why use it instead of `if/else`? `[Lead/Expert]`
`AnyLayout` lets you **switch between layouts**, like a row and a column, **without changing the children's identity**, so they keep their state and animate to their new places.

- With `if/else`, switching from `HStack` to `VStack` creates new views, so state is lost.
- With `AnyLayout`, only the arrangement changes. The children stay the same.

```swift
struct AdaptiveStack<Content: View>: View {
    @Environment(\.dynamicTypeSize) private var dynamicTypeSize
    @ViewBuilder var content: Content

    var body: some View {
        let layout = dynamicTypeSize.isAccessibilitySize
            ? AnyLayout(VStackLayout(alignment: .leading))   // big text → column
            : AnyLayout(HStackLayout())                      // normal → row
        layout { content }
    }
}
```

**Follow-ups:**
- **Why is `AnyLayout` fine when `AnyView` isn't?** `AnyLayout` hides only the arrangement, not the children, so their identity is kept.
- **Can the switch animate?** Yes. Change the condition inside `withAnimation`.
- **What can you put in `AnyLayout`?** Any `Layout`: `HStackLayout`, `VStackLayout`, `ZStackLayout`, `GridLayout`, or your own.

### Q48. How do you build a custom layout with the `Layout` protocol? `[Lead/Expert]`
Since iOS 16, you write a type that conforms to `Layout` and implement **two methods**: one says **how big** the container is, the other says **where each child goes**.

- **`sizeThatFits`:** measure the children and return the container's total size.
- **`placeSubviews`:** put each child at its position.
- The classic interview task is a **flow layout**: tags that wrap to the next line when a row is full.

```swift
struct FlowLayout: Layout {
    var spacing: CGFloat = 8

    // 1. How big is the whole container?
    func sizeThatFits(proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) -> CGSize {
        let maxWidth = proposal.width ?? .infinity
        var x: CGFloat = 0, y: CGFloat = 0, rowHeight: CGFloat = 0, widest: CGFloat = 0
        for subview in subviews {
            let size = subview.sizeThatFits(.unspecified)
            if x + size.width > maxWidth, x > 0 {          // no room → new row
                x = 0; y += rowHeight + spacing; rowHeight = 0
            }
            x += size.width + spacing
            rowHeight = max(rowHeight, size.height)
            widest = max(widest, x - spacing)
        }
        return CGSize(width: widest, height: y + rowHeight)
    }

    // 2. Where does each child go?
    func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) {
        var x = bounds.minX, y = bounds.minY, rowHeight: CGFloat = 0
        for subview in subviews {
            let size = subview.sizeThatFits(.unspecified)
            if x + size.width > bounds.maxX, x > bounds.minX {   // no room → new row
                x = bounds.minX; y += rowHeight + spacing; rowHeight = 0
            }
            subview.place(at: CGPoint(x: x, y: y), proposal: ProposedViewSize(size))
            x += size.width + spacing
            rowHeight = max(rowHeight, size.height)
        }
    }
}

// Usage: FlowLayout { ForEach(tags, id: \.self) { TagView(text: $0) } }
```

**Follow-ups:**
- **What is the `cache` parameter for?** Saving measurements so you don't calculate the same thing twice.
- **Why not use `GeometryReader` for this?** It needs measure-then-update cycles. `Layout` measures and places in one pass.
- **How would you center each row?** First group children into rows and measure each row, then start each row at half of the leftover space.

### Q49. What are alignment guides? `[Lead/Expert]`
Alignment guides decide **which line views line up on** inside a stack, and you can move that line or create your own.

- By default, an `HStack` lines views up by their centers.
- `.alignmentGuide` moves the line for one view.
- A **custom alignment** lets you line up views that are inside **different** stacks, like an icon with only the first line of a text block.

```swift
extension VerticalAlignment {
    private enum IconCenter: AlignmentID {
        static func defaultValue(in d: ViewDimensions) -> CGFloat { d[VerticalAlignment.center] }
    }
    static let iconCenter = VerticalAlignment(IconCenter.self)   // our own alignment line
}

HStack(alignment: .iconCenter) {
    Image(systemName: "bell")                                    // lines up with the title
    VStack(alignment: .leading) {
        Text("Title").font(.headline)
            .alignmentGuide(.iconCenter) { $0[VerticalAlignment.center] }
        Text("A longer subtitle on a second line")
    }
}
```

**Follow-ups:**
- **When do you need a custom alignment?** When views in different stacks must line up.
- **How do you line up text by its baseline?** Use `HStack(alignment: .firstTextBaseline)`.
- **What does the `alignmentGuide` closure return?** The position of the line inside that view, usually based on its size.

### Q50. How does the safe area work in SwiftUI? `[Fundamental]`
The safe area is the part of the screen **not covered** by the notch, status bar, home indicator, or bars, and SwiftUI keeps your content inside it by default.

- **`.ignoresSafeArea()`:** let a view extend under those areas. Use it on **backgrounds only**, so text stays readable.
- **`.safeAreaInset(edge:)`:** add your own bar (like a message box) and shrink the safe area, so scrolling content isn't hidden behind it.

```swift
ScrollView {
    MessagesList()
}
.safeAreaInset(edge: .bottom) {
    MessageComposer()          // stays at the bottom; the list scrolls above it
        .padding()
        .background(.bar)
}
```

**Follow-ups:**
- **Why use `.ignoresSafeArea()` on the background only?** So buttons and text stay away from the notch and home indicator.
- **What does `.safeAreaPadding` do?** Added in iOS 17, it adds extra space to the safe area itself.
- **How do you keep content above the keyboard?** SwiftUI does it automatically. Use `.ignoresSafeArea(.keyboard)` to turn it off.

### Q51. How do you read a view's size without breaking layout? `[Senior]`
Use **`onGeometryChange`**: it reads a value from the view's size or position and calls your code **only when that value changes**, without changing the layout.

- Unlike `GeometryReader`, it doesn't take extra space.
- It only fires when the value actually changes, so it avoids loops.
- Works back to iOS 16.

```swift
struct CollapsingHeader: View {
    @State private var headerHeight: CGFloat = 0

    var body: some View {
        HeaderView()
            .onGeometryChange(for: CGFloat.self) { proxy in
                proxy.size.height              // 1. what to read
            } action: { newHeight in
                headerHeight = newHeight       // 2. what to do when it changes
            }
    }
}
```

**Follow-ups:**
- **Which iOS versions support it?** It came with the iOS 18 SDK and works back to iOS 16.
- **Why is it better than `GeometryReader` in a background?** It only fires when the value changes, so fewer updates and no loops.
- **Can you read the position on screen?** Yes, use `proxy.frame(in: .global)` in the first closure.

### Q52. What is `containerRelativeFrame`? `[Senior]`
`containerRelativeFrame` (iOS 17) sizes a view **relative to its container**, like "as wide as the scroll view," without `GeometryReader`.

- Common use: a horizontal carousel where each card is exactly one screen wide.
- Add `scrollTargetBehavior(.viewAligned)` to make scrolling snap to each card.

```swift
ScrollView(.horizontal) {
    LazyHStack(spacing: 16) {
        ForEach(items) { item in
            CardView(item: item)
                .containerRelativeFrame(.horizontal)   // one card = one screen width
        }
    }
    .scrollTargetLayout()                              // the cards are snap targets
}
.scrollTargetBehavior(.viewAligned)                    // snap to each card
.contentMargins(.horizontal, 24, for: .scrollContent)
```

**Follow-ups:**
- **How do you show two cards per screen?** `.containerRelativeFrame(.horizontal, count: 2, spacing: 16)`.
- **What does `.paging` do instead of `.viewAligned`?** It snaps by a full page of the scroll view, not by each card.
- **Why is `.scrollTargetLayout()` needed?** It tells the scroll view which views to snap to.

### Q53. What is `Grid`, and how does it differ from `LazyVGrid`? `[Senior]`
`Grid` (iOS 16) creates **all** cells at once so columns line up perfectly, while `LazyVGrid` creates cells **only as you scroll**.

- **`Grid`:** small tables and forms. Supports a cell spanning several columns.
- **`LazyVGrid`:** big collections, like a photo gallery. You describe the columns with `GridItem`.

```swift
let columns = [GridItem(.adaptive(minimum: 100), spacing: 8)]   // as many columns as fit

ScrollView {
    LazyVGrid(columns: columns, spacing: 8) {
        ForEach(photos) { photo in
            PhotoThumbnail(photo: photo)
                .frame(height: 100)
                .clipped()
        }
    }
}
```

**Follow-ups:**
- **What are the three `GridItem` kinds?** `.fixed` (exact width), `.flexible` (share the space), `.adaptive` (fit as many as possible).
- **How do you make a cell span two columns in `Grid`?** `.gridCellColumns(2)`.
- **When is `Grid` a bad choice?** For hundreds of items, because it creates every cell up front.

## 7. Lists, ScrollViews & Grids

### Q54. Show common `List` features: swipe actions, delete, move, refresh, search. `[Fundamental]`
`List` gives you common list features with **one modifier each**: `.swipeActions` for swiping, `.onMove` for reordering, `.refreshable` for pull-to-refresh, and `.searchable` for a search bar.

- They all use the standard system look and work with VoiceOver for free.

```swift
List {
    ForEach(model.filteredTodos) { todo in
        TodoRow(todo: todo)
            .swipeActions(edge: .trailing) {                       // swipe left
                Button("Delete", role: .destructive) { model.delete(todo) }
            }
            .swipeActions(edge: .leading) {                        // swipe right
                Button("Done") { model.toggle(todo) }.tint(.green)
            }
    }
    .onMove { model.move(from: $0, to: $1) }                       // drag to reorder
}
.refreshable { await model.reload() }                              // pull to refresh
.searchable(text: $model.query)                                    // search bar
.toolbar { EditButton() }
```

**Follow-ups:**
- **What does `role: .destructive` do?** Makes the button red, and a full swipe runs it.
- **How do you stop the full swipe?** `.swipeActions(allowsFullSwipe: false)`.
- **What's new for reordering in iOS 27?** `.reorderContainer(for:)` and `.reorderable()` add drag-to-reorder to `List`, `ScrollView`, and lazy stacks.

### Q55. How do you implement pagination in a SwiftUI list? `[Senior]`
When the **last row appears**, ask the model to load the next page, and inside the model **ignore the request if a page is already loading** or there are no more pages.

- The trigger: `.onAppear` on the last row.
- The guard: `isLoading` and `hasMore` stop duplicate requests.

```swift
List(model.items) { item in
    ItemRow(item: item)
        .onAppear {
            if item.id == model.items.last?.id {           // last row is visible
                Task { await model.loadNextPage() }
            }
        }
}

// In the @MainActor @Observable model
func loadNextPage() async {
    guard !isLoading, hasMore else { return }   // don't load twice
    isLoading = true
    defer { isLoading = false }
    if let page = try? await api.fetch(cursor: nextCursor) {
        items.append(contentsOf: page.items)
        nextCursor = page.nextCursor
        hasMore = page.nextCursor != nil
    }
}
```

**Follow-ups:**
- **How do you make it feel faster?** Start loading a few rows before the end, and show a spinner row while loading.
- **Why use a cursor instead of a page number?** If new items are added while scrolling, page numbers can skip or repeat items. A cursor doesn't.
- **How do you show an error?** Save the error in the model and show a "Retry" row at the bottom.

### Q56. How do you scroll programmatically? `[Senior]`
On iOS 14+ use **`ScrollViewReader`** and call `proxy.scrollTo(id)`, and on iOS 17+ you can bind **`scrollPosition(id:)`** to a state variable.

- **`ScrollViewReader`:** gives you a `proxy`. Call `scrollTo` with a view's ID.
- **`scrollPosition(id:)`:** a binding that both shows where you are and lets you jump somewhere.

```swift
// iOS 14+: scroll to the newest message
ScrollViewReader { proxy in
    ScrollView {
        LazyVStack { ForEach(messages) { MessageRow(message: $0).id($0.id) } }
    }
    .onChange(of: messages.count) {
        guard let lastID = messages.last?.id else { return }
        withAnimation { proxy.scrollTo(lastID, anchor: .bottom) }
    }
}

// iOS 17+: position is a binding
ScrollView {
    LazyVStack { ForEach(messages) { MessageRow(message: $0) } }
        .scrollTargetLayout()
}
.scrollPosition(id: $scrolledID)
.defaultScrollAnchor(.bottom)        // a chat starts at the bottom
```

**Follow-ups:**
- **Why unwrap the ID before calling `scrollTo`?** An optional ID won't match any view's ID, so nothing happens.
- **What does `.scrollTargetLayout()` do here?** Tells the scroll view which views to track for `scrollPosition(id:)`.
- **What is iOS 18's `ScrollPosition` type?** One value that can scroll to an ID, an edge, or an exact point.

### Q57. How do you react to scroll position and visibility? `[Lead/Expert]`
iOS 18 added three modifiers: **`onScrollGeometryChange`** (react to how far you've scrolled), **`onScrollVisibilityChange`** (know when a view comes on screen), and **`onScrollPhaseChange`** (know if the user is dragging or the scroll is slowing down).

- Turn the scroll offset into a simple value like a `Bool` first, so your code runs only when it crosses a line, not on every pixel.

```swift
// Show a "scroll to top" button after scrolling down 600 points
ScrollView { content }
    .onScrollGeometryChange(for: Bool.self) { geometry in
        geometry.contentOffset.y > 600
    } action: { _, isFarDown in
        showScrollToTop = isFarDown          // runs only when the Bool flips
    }

// Play a video only while at least half of it is visible
VideoPlayerView(url: url)
    .onScrollVisibilityChange(threshold: 0.5) { isVisible in
        isVisible ? player.play() : player.pause()
    }
```

**Follow-ups:**
- **Why convert the offset to a `Bool`?** So the action runs once when crossing 600, not on every frame of scrolling.
- **What's wrong with saving the raw offset in `@State`?** It changes every frame, so every view that reads it updates every frame.
- **What did people use before iOS 18?** A `GeometryReader` plus a preference key, which was more work and slower.

### Q58. How do you add section headers and pinned headers? `[Fundamental]`
Wrap rows in a **`Section`** with a header, and in a `LazyVStack` add **`pinnedViews: [.sectionHeaders]`** so each header sticks to the top while its section scrolls.

```swift
ScrollView {
    LazyVStack(pinnedViews: [.sectionHeaders]) {      // headers stick to the top
        ForEach(groups) { group in
            Section {
                ForEach(group.contacts) { ContactRow(contact: $0) }
            } header: {
                Text(group.letter)
                    .frame(maxWidth: .infinity, alignment: .leading)
                    .background(.bar)                   // so rows don't show through
            }
        }
    }
}
```

**Follow-ups:**
- **Do `List` headers stick automatically?** In the plain list style, yes. In grouped styles, they scroll away.
- **Why give the header a background?** Without one, rows show through it while it's pinned.
- **Can footers stick too?** Yes, add `.sectionFooters` to `pinnedViews`.

### Q59. How do you handle selection in a `List`? `[Fundamental]`
Pass a binding to **`List(selection:)`**: a **`Set`** of IDs for multiple selection, or a **single optional ID** for one selection.

- Multiple selection on iPhone needs edit mode, so add an `EditButton`.
- Single selection is common with `NavigationSplitView` on iPad.

@State private var selection = Set<Mail.ID>()      // many rows can be selected

List(mails, selection: $selection) { mail in

**Follow-ups:**
- **Why does iPhone need edit mode?** On iPhone, rows can only be selected in edit mode. On iPad and Mac it works directly.
- **How do you act on the selected rows?** Read the IDs from `selection` and find the matching items.
- **What type must the selection be?** The same type as the row IDs, like `Mail.ID`.

## 8. Navigation & Presentation

### Q60. What is `NavigationStack`, and how does it improve on `NavigationView`? `[Fundamental]`
`NavigationStack` (iOS 16) replaces `NavigationView` with **data-driven navigation**: a link pushes a **value**, and `.navigationDestination` decides **which screen** to show for that value.

- Because navigation is just data, you can push, pop, and deep link by changing an array.
- Destination screens are created only when pushed, not in advance.

```swift
NavigationStack {
    List(products) { product in
        NavigationLink(product.name, value: product)          // push a value
    }
    .navigationDestination(for: Product.self) { product in    // value → screen
        ProductDetailView(product: product)
    }
    .navigationTitle("Products")
}
```

**Follow-ups:**
- **Why is it faster than the old way?** The old `NavigationLink(destination:)` built the destination screen for every row in advance.
- **How do you go back to the first screen?** Bind the stack to a path array and empty it: `path.removeAll()`.
- **Do pushed values need to be `Hashable`?** Yes.

### Q61. How do you implement a router for programmatic navigation? `[Senior]`
Create an **`@Observable` router class that holds the navigation path** as an array of route values, connect the `NavigationStack` to it, and put the router in the environment so **any screen can push or pop**.

- `Route` is an enum listing every screen you can navigate to.
- To navigate, a screen just calls `router.push(.cart)`.

```swift
enum Route: Hashable { case product(Product.ID), cart, orderConfirmation(orderID: String) }

@MainActor @Observable
final class Router {
    var path: [Route] = []
    func push(_ route: Route) { path.append(route) }
    func popToRoot() { path.removeAll() }
}

struct RootView: View {
    @State private var router = Router()
    var body: some View {
        NavigationStack(path: $router.path) {                 // the stack follows the array
            HomeView()
                .navigationDestination(for: Route.self) { route in
                    switch route {
                    case .product(let id): ProductDetailView(productID: id)
                    case .cart: CartView()
                    case .orderConfirmation(let id): ConfirmationView(orderID: id)
                    }
                }
        }
        .environment(router)                                  // any screen can use it
    }
}
```

**Follow-ups:**
- **How does a child screen navigate?** `@Environment(Router.self) private var router`, then `router.push(.cart)`.
- **Why is it easy to test?** You check the array: `router.path == [.cart]`, no UI needed.
- **Why store IDs, not whole objects, in routes?** IDs are small and stable, and the screen can load fresh data.

### Q62. What is `NavigationPath`, and when would you use it over a typed array? `[Senior]`
`NavigationPath` is a path that can hold **values of different types** (like a `Product` and a `User`), while a typed array like `[Route]` holds **one type** but is easier to read and test.

- **Typed array:** my default when one enum can describe every screen.
- **`NavigationPath`:** when different features push their own types into one stack.

```swift
@State private var path = NavigationPath()

NavigationStack(path: $path) {
    HomeView()
        .navigationDestination(for: Product.self) { ProductDetailView(product: $0) }
        .navigationDestination(for: User.self) { ProfileView(user: $0) }
}

path.append(product)   // a Product
path.append(user)      // and a User, in the same path
```

**Follow-ups:**
- **Can you see what's inside a `NavigationPath`?** Not really, only `count`. That's why a typed array is easier to debug.
- **How do you save and restore it?** Use `path.codable`, if every value in it is `Codable`.
- **When would a modular app prefer it?** When each feature module has its own route types but they share one stack.

### Q63. How do you handle deep links in SwiftUI? `[Senior]`
Receive the URL with **`.onOpenURL`**, **turn it into a route**, reset the navigation, and push the route through the router.

- Also: switch to the right tab, close any open sheet, and if the user isn't logged in, save the link and open it after login.

```swift
RootView()
    .onOpenURL { url in                          // e.g. myshop://product/42
        guard let route = Route(url: url) else { return }
        router.popToRoot()                       // start from a clean state
        router.push(route)
    }

extension Route {
    init?(url: URL) {                            // URL → route
        let parts = url.pathComponents.filter { $0 != "/" }
        switch (url.host(), parts.first) {
        case ("product", let id?): self = .product(id)
        case ("cart", _):          self = .cart
        default:                   return nil
        }
    }
}
```

**Follow-ups:**
- **How do you handle universal links (https links)?** With `.onContinueUserActivity(NSUserActivityTypeBrowsingWeb)` and its `webpageURL`.
- **What if the user isn't logged in?** Save the route, show login, then open the route after login.
- **How do you test it?** Unit test `Route(url:)` with many URLs, including bad ones.

### Q64. Where must `navigationDestination` be placed? `[Senior]`
Put it **inside the `NavigationStack`, on a view that is always there**, like the `List` itself, and **not inside a lazy row**.

- Lazy rows are created only when visible. If the destination lives in a row that isn't loaded, SwiftUI doesn't know it.

```swift
NavigationStack {
    List(items) { item in
        NavigationLink(item.name, value: item)
        // ❌ don't put .navigationDestination here (inside a lazy row)
    }
    .navigationDestination(for: Item.self) { ItemDetail(item: $0) }   // ✅ on the List
}
```

**Follow-ups:**
- **What happens if it's inside a row?** SwiftUI logs a warning, and tapping the link may do nothing.
- **Can you register the same type twice in one stack?** You shouldn't. Only one will be used.
- **Can a pushed screen add its own destinations?** Yes, for links pushed from that screen.

### Q65. How do you present sheets, full-screen covers, and popovers? `[Fundamental]`
Use **`.sheet(item:)`** when the sheet needs data, and **`.sheet(isPresented:)`** or **`.fullScreenCover(isPresented:)`** when a simple `Bool` is enough.

- **`sheet(item:)`:** the sheet opens when the item is set and closes when it's `nil`. The item is passed in, so data is never missing.
- **Detents:** `.presentationDetents([.medium, .large])` makes a half-height sheet.

```swift
@State private var selectedProduct: Product?
@State private var showFilters = false

List(products) { product in
    Button(product.name) { selectedProduct = product }       // opens the sheet
}
.sheet(item: $selectedProduct) { product in                   // data-driven
    ProductDetailView(product: product)
        .presentationDetents([.medium, .large])
}
.fullScreenCover(isPresented: $showFilters) {                  // Bool-driven
    FiltersView()
}
```

**Follow-ups:**
- **Why is `sheet(item:)` safer than a `Bool` plus a separate optional?** With two values, the sheet can open before the data is set and show nothing.
- **How do you stop the user from swiping the sheet away?** `.interactiveDismissDisabled(hasUnsavedChanges)`.
- **How do you keep a popover a popover on iPhone?** On iOS 16.4+, add `.presentationCompactAdaptation(.popover)`.

### Q66. How does a presented view dismiss itself? `[Fundamental]`
It reads **`dismiss` from the environment** and calls it, which closes the sheet or goes back one screen, depending on how it was shown.

```swift
struct EditProfileView: View {
    @Environment(\.dismiss) private var dismiss

    var body: some View {
        NavigationStack {
            Form { /* fields */ }
                .toolbar {
                    ToolbarItem(placement: .cancellationAction) { Button("Cancel") { dismiss() } }
                    ToolbarItem(placement: .confirmationAction) { Button("Save") { save(); dismiss() } }
                }
        }
    }
}
```

**Follow-ups:**
- **Why read `dismiss` in the presented view, not the parent?** It closes the view that reads it.
- **What was used before iOS 15?** `@Environment(\.presentationMode)`, now deprecated.
- **How can the parent close it instead?** Set the item to `nil` or the `Bool` to `false`.

### Q67. How do you show alerts and confirmation dialogs with data? `[Fundamental]`
Use the **`presenting:`** version of `.alert`, which passes the selected item into the buttons and message, and on **iOS 27** you can simply pass an **optional item binding**, like with sheets.

- **Alert:** an important message or a yes/no question.
- **Confirmation dialog:** a list of actions the user can pick from, like "Delete" or "Archive."

```swift
@State private var itemToDelete: Item?

List(items) { item in
    Text(item.name)
        .swipeActions { Button("Delete", role: .destructive) { itemToDelete = item } }
}
.alert("Delete item?",
       isPresented: Binding(get: { itemToDelete != nil }, set: { if !$0 { itemToDelete = nil } }),
       presenting: itemToDelete) { item in                    // item is passed in
    Button("Delete", role: .destructive) { delete(item) }
    Button("Cancel", role: .cancel) { }
} message: { item in
    Text("\(item.name) will be permanently removed.")
}
```

**Follow-ups:**
- **What does the iOS 27 version look like?** `.confirmationDialog("Delete?", item: $itemToDelete) { item in ... }`. No `Bool` needed.
- **When use a confirmation dialog instead of an alert?** When the user picks between actions they started.
- **What does `role: .cancel` do?** Marks the cancel button, so the system places and styles it correctly.

### Q68. How does `TabView` work with the iOS 18 `Tab` API? `[Senior]`
In iOS 18 you build a `TabView` from **`Tab` items**, each with a title, icon, and value, and bind the selection to state so code can switch tabs.

- **Give each tab its own `NavigationStack`**, so each tab keeps its own back history.
- `.sidebarAdaptable` shows a tab bar on iPhone and can become a sidebar on iPad.

```swift
enum AppTab: Hashable { case home, search, profile }
@State private var selectedTab: AppTab = .home

TabView(selection: $selectedTab) {                 // set selectedTab to switch tabs
    Tab("Home", systemImage: "house", value: .home) {
        NavigationStack { HomeView() }              // own history
    }
    Tab("Profile", systemImage: "person", value: .profile) {
        NavigationStack { ProfileView() }
    }
    Tab(value: .search, role: .search) {
        NavigationStack { SearchView() }
    }
}
.tabViewStyle(.sidebarAdaptable)
```

**Follow-ups:**
- **How were tabs built before iOS 18?** With `.tabItem { Label(...) }` and `.tag(...)` on each view.
- **Why not one `NavigationStack` around the whole `TabView`?** All tabs would share one history, and the tab bar would get pushed away.
- **What's new in iOS 27?** A `.prominent` tab role, for a separated tab on the trailing side.

### Q69. What is `NavigationSplitView`? `[Senior]`
`NavigationSplitView` builds **two- or three-column layouts** (sidebar, list, detail) for iPad and Mac, and on iPhone it **automatically becomes a normal stack**.

- Selecting a row in one column decides what the next column shows.

```swift
NavigationSplitView {
    List(folders, selection: $selectedFolder) { folder in          // column 1: folders
        NavigationLink(folder.name, value: folder)
    }
} content: {
    if let folder = selectedFolder {                                // column 2: mails
        List(folder.mails, selection: $selectedMail) { MailRow(mail: $0) }
    }
} detail: {
    if let id = selectedMail { MailDetailView(mailID: id) }        // column 3: the mail
    else { Text("Select a message") }
}
```

**Follow-ups:**
- **How do you control which columns show?** Bind `columnVisibility` to a `NavigationSplitViewVisibility` value.
- **Can the detail column push more screens?** Yes, put a `NavigationStack` inside it.
- **What do you show when nothing is selected?** A placeholder, often `ContentUnavailableView`.

### Q70. What is the zoom navigation transition? `[Senior]`
The zoom transition (iOS 18) makes a new screen **grow out of the item you tapped**, and shrink back into it when you go back.

- Mark the tapped thumbnail with `.matchedTransitionSource(id:in:)`.
- Mark the new screen with `.navigationTransition(.zoom(sourceID:in:))`.
- Both use the **same ID and namespace**.

```swift
@Namespace private var namespace

NavigationLink(value: photo) {
    PhotoThumbnail(photo: photo)
        .matchedTransitionSource(id: photo.id, in: namespace)      // zoom starts here
}

.navigationDestination(for: Photo.self) { photo in
    PhotoDetailView(photo: photo)
        .navigationTransition(.zoom(sourceID: photo.id, in: namespace))   // zoom ends here
}
```

**Follow-ups:**
- **Does it work for sheets too?** Yes, also for sheets and full-screen covers.
- **How is it different from `matchedGeometryEffect`?** It's built into navigation and supports swiping back. `matchedGeometryEffect` doesn't.
- **What did iOS 27 add?** A `.crossFade` navigation transition.

## 9. Async Work, Lifecycle Modifiers & Concurrency

### Q71. What is the difference between `.onAppear` and `.task`? `[Senior]`
`.onAppear` runs **normal (non-async)** code when the view appears, while `.task` runs **async** code and **cancels it automatically** when the view disappears.

- Use `.task` for loading data.
- Use `.onAppear` for quick things, like logging an analytics event.

```swift
List(items) { ItemRow(item: $0) }
    .onAppear { analytics.track("list_shown") }   // quick, not async
    .task { await model.load() }                  // async, cancelled when the view goes away
```

**Follow-ups:**
- **Do both run again when you come back from another screen?** Yes, on every appearance. Add a check if you don't want to reload.
- **Does cancelling stop the work immediately?** It sends a "please stop" signal. `URLSession` stops, but your own loops must check `Task.isCancelled`.
- **Why is `onAppear { Task { ... } }` worse?** That task isn't cancelled when the view disappears.

### Q72. What does `.task(id:)` do? Show a debounced search. `[Senior]`
`.task(id:)` **cancels and restarts** the task every time the `id` value changes, and adding a short sleep at the start turns it into a **debounce** (wait until the user stops typing).

- The user types "s", "sw", "swi"... Each keystroke changes `query`, which cancels the previous task during its sleep.
- Only when typing pauses for 300 ms does the search actually run.

```swift
struct SearchView: View {
    @State private var query = ""
    @State private var results: [Movie] = []

    var body: some View {
        List(results) { Text($0.title) }
            .searchable(text: $query)
            .task(id: query) {                                   // restarts when query changes
                try? await Task.sleep(for: .milliseconds(300))   // wait a little
                guard !Task.isCancelled, !query.isEmpty else { return }
                results = (try? await api.search(query)) ?? []
            }
    }
}
```

**Follow-ups:**
- **Why check `Task.isCancelled` after the sleep?** `try?` hides the cancellation error, so without the check the code would continue.
- **Does it run when the view first appears?** Yes, once on appear, then again each time `id` changes.
- **What type can `id` be?** Any `Equatable` value.

### Q73. How does `onChange(of:)` work in iOS 17+? `[Fundamental]`
`onChange(of:)` runs your code **after a value changes**, and in iOS 17 it can give you **both the old and the new value**.

- Add `initial: true` to also run it once when the view appears.

```swift
.onChange(of: selectedTab) { oldValue, newValue in
    analytics.track(from: oldValue, to: newValue)
}

.onChange(of: searchText, initial: true) {
    filter()                 // also runs when the view first appears
}
```

**Follow-ups:**
- **What must the value conform to?** `Equatable`.
- **What is the risk of many `onChange`s?** One changes state that triggers another, causing extra updates or loops. Calculate values instead.
- **Which thread does it run on?** The main thread (main actor).

### Q74. How do you consume an `AsyncSequence` in a view? `[Senior]`
Loop over it with **`for await` inside `.task`**, and the loop stops automatically when the view disappears.

```swift
.task {
    for await _ in NotificationCenter.default.notifications(named: .cartUpdated) {
        await model.refreshCart()        // runs for each notification
    }
}                                        // loop ends when the view disappears
```

**Follow-ups:**
- **How do you listen to a Combine publisher instead?** `.onReceive(publisher) { value in ... }`.
- **What if you start the loop in `onAppear { Task { } }`?** It keeps running after the view is gone. That's a leak.
- **How do you listen to two streams?** Use two `.task` modifiers, or a task group inside one.

### Q75. On which thread does SwiftUI view code run? `[Senior]`
SwiftUI view code runs on the **main thread**: since the iOS 18 SDK, `View` is `@MainActor`, so `body` and `.task` closures run there.

- **Waiting with `await` is fine.** It pauses without blocking the screen.
- **Heavy work without `await` is not fine.** It freezes the UI. Move it to another actor or a background function.

```swift
.task {
    let thumbnails = await ThumbnailRenderer.shared.render(photos)   // heavy work on another actor
    self.thumbnails = thumbnails                                      // back on the main thread
}
```

**Follow-ups:**
- **How do you move work off the main thread?** A separate `actor`, a `nonisolated` or `@concurrent` async function, or `Task.detached`.
- **Does `await` mean "runs in the background"?** No. It only means "may pause here." Where it runs depends on the function.
- **How do you find UI freezes?** With the Hangs instrument or the Time Profiler.

### Q76. How should UI-bound `@Observable` models handle concurrency? `[Lead/Expert]`
Mark them **`@MainActor`**, so every change that affects the UI happens on the main thread, and the Swift 6 compiler checks this for you.

- The model's `async` methods can still wait for network calls without blocking the UI.
- Ignore `CancellationError`: it just means the view went away.

```swift
@MainActor @Observable
final class ProfileModel {
    private(set) var profile: Profile?          // views can read, only the model can write
    private(set) var errorMessage: String?
    private let api: ProfileAPI

    init(api: ProfileAPI) { self.api = api }

    func load() async {
        do {
            profile = try await api.fetchProfile()
        } catch is CancellationError {
            // the view disappeared, nothing to show
        } catch {
            errorMessage = error.localizedDescription
        }
    }
}
```

**Follow-ups:**
- **Does `@MainActor` make the network request run on the main thread?** No. The request runs elsewhere. Only the property updates happen on the main thread.
- **Why `private(set)`?** Views can read the state, but only the model can change it.
- **What did Swift 6.2 add here?** A setting that makes new app code main-actor by default, so you write `@MainActor` less often.

### Q77. How do you model loading, loaded, empty, and error states? `[Senior]`
Use **one enum for the screen state** and `switch` over it in the view, so the screen can only be in **one state at a time**.

- With separate `isLoading`, `items`, and `error` properties, you can get impossible mixes, like "loading" and "error" at once.
- `ContentUnavailableView` gives you ready-made empty and error screens.

```swift
enum LoadState<Value> { case idle, loading, loaded(Value), failed(String) }

switch model.state {
case .idle, .loading:
    ProgressView()
case .loaded(let articles) where articles.isEmpty:
    ContentUnavailableView("No Articles", systemImage: "doc.text")
case .loaded(let articles):
    List(articles) { ArticleRow(article: $0) }
case .failed(let message):
    ContentUnavailableView {
        Label("Couldn't Load", systemImage: "wifi.exclamationmark")
    } description: { Text(message) } actions: {
        Button("Retry") { Task { await model.load() } }
    }
}
```

**Follow-ups:**
- **How do you show old data while refreshing?** Keep the data in `.loaded` with a small spinner, or add a `.refreshing(Value)` case.
- **What is `ContentUnavailableView.search`?** A ready-made "No results" screen for search, added in iOS 17.
- **Why is an enum easier to test?** You only check one value, like `state == .failed`.

### Q78. How do you react to app lifecycle changes in SwiftUI? `[Fundamental]`
Read **`scenePhase`** from the environment and react with `onChange` when it becomes `.active`, `.inactive`, or `.background`.

- **`.active`:** the app is on screen and usable.
- **`.inactive`:** visible but not usable, like when the app switcher or Control Center is open.
- **`.background`:** not visible. Save data here.
- For app delegate callbacks (like push notification tokens), use **`@UIApplicationDelegateAdaptor`**.

```swift
@Environment(\.scenePhase) private var scenePhase

ContentView()
    .onChange(of: scenePhase) { _, newPhase in
        switch newPhase {
        case .active:     model.resumeUpdates()
        case .background: model.saveDraft()      // save before the app may be closed
        default:          break
        }
    }
```

**Follow-ups:**
- **Is `scenePhase` different in the `App` vs a view?** In the `App` it combines all windows. In a view it's that view's window only.
- **How do you get the push notification token?** Write an `AppDelegate` and connect it with `@UIApplicationDelegateAdaptor(AppDelegate.self)`.
- **When should you save data?** When the phase becomes `.background`, because the app may be closed after that.

## 10. Animations & Transitions

### Q79. What is the difference between implicit and explicit animations? `[Fundamental]`
An **implicit** animation is attached to a view with `.animation(_:value:)` and runs whenever that value changes, while an **explicit** animation wraps a state change in `withAnimation { }` and animates everything that change affects.

- **Implicit:** "this view always animates when `isExpanded` changes."
- **Explicit:** "animate everything caused by this button tap."

```swift
// Implicit: animates whenever isExpanded changes
RoundedRectangle(cornerRadius: 16)
    .frame(height: isExpanded ? 300 : 100)
    .animation(.spring(duration: 0.4, bounce: 0.3), value: isExpanded)

// Explicit: animates everything this change affects
Button("Toggle") {
    withAnimation(.snappy) { isExpanded.toggle() }
}
```

**Follow-ups:**
- **Why was `.animation(_:)` without `value` deprecated?** It animated every change in the view, even ones you didn't want.
- **Which do you prefer?** Explicit for user actions, because it's clear what's animated. Implicit for one view that always animates one value.
- **What are `.snappy`, `.smooth`, and `.bouncy`?** Ready-made spring animations added in iOS 17.

### Q80. What are transitions, and why doesn't my transition animate? `[Senior]`
A transition describes **how a view appears or disappears** (fade, slide, scale), and it only animates when the view is **added or removed inside an animation**, like `withAnimation`.

- Without an animation, the view just pops in or out.

```swift
ZStack(alignment: .bottom) {
    Button("Show toast") {
        withAnimation(.spring) { showToast.toggle() }     // ✅ needed for the transition
    }
    if showToast {
        ToastView(message: "Saved!")
            .transition(.move(edge: .bottom).combined(with: .opacity))   // slide + fade
    }
}
```

**Follow-ups:**
- **What is the most common mistake?** Putting `.animation` on the view being removed. The modifier disappears with the view, so nothing animates.
- **How do you use different transitions for in and out?** `.transition(.asymmetric(insertion: .scale, removal: .opacity))`.
- **Why does a view in a `ZStack` sometimes vanish without animating?** Its layer order can change while it's removed. Add `.zIndex(1)` to keep it on top.

### Q81. What is `matchedGeometryEffect`? `[Senior]`
`matchedGeometryEffect` makes **two different views look like one view moving** from one place and size to another, which is how you build "hero" animations.

- Give both views the **same `id`** and the **same `@Namespace`**.
- Show only **one of them at a time**. SwiftUI animates between their positions and sizes.

```swift
@Namespace private var namespace
@State private var isExpanded = false

VStack {
    if isExpanded {
        RoundedRectangle(cornerRadius: 24).fill(.blue)
            .matchedGeometryEffect(id: "card", in: namespace)    // big version
            .frame(height: 400)
    } else {
        RoundedRectangle(cornerRadius: 12).fill(.blue)
            .matchedGeometryEffect(id: "card", in: namespace)    // small version
            .frame(width: 100, height: 100)
    }
}
.onTapGesture { withAnimation(.spring(duration: 0.5)) { isExpanded.toggle() } }
```

**Follow-ups:**
- **Does modifier order matter here?** Yes. Putting it before or after `.frame` changes which size is matched.
- **What if both views are visible at once?** Mark one with `isSource: true`. Otherwise the result is unpredictable.
- **What should you use for navigation on iOS 18+?** The built-in zoom transition (see Q70).

### Q82. How do you make a custom shape animatable? `[Lead/Expert]`
Expose the value you want to animate through **`animatableData`**, so SwiftUI can calculate the in-between values frame by frame.

- Without it, the shape jumps straight from the old value to the new one.
- For two values, use `AnimatablePair`.
- iOS 26 added an `@Animatable` macro that writes this code for you.

```swift
struct PieSlice: Shape {
    var progress: Double   // 0...1

    var animatableData: Double {          // SwiftUI changes this a little each frame
        get { progress }
        set { progress = newValue }
    }

    func path(in rect: CGRect) -> Path {
        let center = CGPoint(x: rect.midX, y: rect.midY)
        var path = Path()
        path.move(to: center)
        path.addArc(center: center, radius: min(rect.width, rect.height) / 2,
                    startAngle: .degrees(-90), endAngle: .degrees(-90 + 360 * progress),
                    clockwise: false)
        path.closeSubpath()
        return path
    }
}
```

**Follow-ups:**
- **What happens without `animatableData`?** The shape jumps to the final value with no animation.
- **How do you animate two values?** Use `AnimatablePair<Double, Double>` and map `first` and `second` to your properties.
- **Can a `ViewModifier` be animatable?** Yes, make it conform to `Animatable` and add `animatableData`.

### Q83. What are `PhaseAnimator` and `KeyframeAnimator`? `[Senior]`
Both (iOS 17) build **multi-step animations**: `phaseAnimator` moves through a **list of steps** one after another, while `keyframeAnimator` animates **several properties on their own timelines**.

- **Phase animator:** simple sequences, like "grow, then shrink back" (a pulse).
- **Keyframe animator:** complex motion, like "scale up quickly while moving up, then settle down."

```swift
// Phase: pulse each time likeCount changes (normal → big → normal)
Image(systemName: "heart.fill")
    .phaseAnimator([false, true], trigger: likeCount) { content, isBig in
        content.scaleEffect(isBig ? 1.3 : 1.0)
    } animation: { _ in .spring(duration: 0.25, bounce: 0.5) }

// Keyframes: scale and move on separate timelines
Image(systemName: "bell.fill")
    .keyframeAnimator(initialValue: BellValues(), trigger: notificationCount) { content, value in
        content.scaleEffect(value.scale).offset(y: value.verticalOffset)
    } keyframes: { _ in
        KeyframeTrack(\.scale) { SpringKeyframe(1.3, duration: 0.15); SpringKeyframe(1.0, duration: 0.3) }
        KeyframeTrack(\.verticalOffset) { LinearKeyframe(-10, duration: 0.15); SpringKeyframe(0, duration: 0.3) }
    }
```

**Follow-ups:**
- **What happens without a `trigger`?** The phase animator loops forever.
- **What kinds of keyframes exist?** `LinearKeyframe`, `SpringKeyframe`, `CubicKeyframe`, and `MoveKeyframe`.
- **When pick keyframes over phases?** When different properties need different timing.

### Q84. What is a `Transaction`? `[Lead/Expert]`
A transaction is the **"package" that carries the animation** for a state change, and you can read or change it to control animations for part of the screen.

- `withAnimation` just puts an animation into the transaction.
- `.transaction { $0.animation = nil }` turns off animation for one view, even if the change was animated.
- iOS 17's scoped `.animation(_:body:)` animates **only** the modifiers inside its closure.

```swift
// This badge never animates, even inside withAnimation
BadgeView(count: count)
    .transaction { $0.animation = nil }

// iOS 17: only the opacity animates; the frame change doesn't
Rectangle()
    .animation(.smooth) { content in
        content.opacity(isVisible ? 1 : 0)
    }
    .frame(width: isWide ? 300 : 100)
```

**Follow-ups:**
- **How do you turn off animation for one change?** `var t = Transaction(); t.disablesAnimations = true; withTransaction(t) { state = newValue }`.
- **Why is the scoped `.animation` useful?** It avoids animating things you didn't mean to.
- **Can you send your own data through a transaction?** Yes, with a custom `TransactionKey` (iOS 17).

### Q85. How do you run code when an animation completes? `[Fundamental]`
Since iOS 17, **`withAnimation` has a `completion` closure** that runs when the animation finishes.

```swift
withAnimation(.easeOut(duration: 0.3)) {
    isCardVisible = false
} completion: {
    removeCard()           // runs after the animation ends
}
```

**Follow-ups:**
- **How was this done before iOS 17?** With `DispatchQueue.main.asyncAfter` and the same duration, which was unreliable.
- **When does it run for a spring?** By default when the spring is "close enough," which can be a bit before it fully stops. Use `completionCriteria: .removed` to wait until it's completely done.
- **Is there a completion for implicit animations?** Not directly. Use a `Transaction` with `addAnimationCompletion`.

### Q86. How do you animate text and SF Symbols? `[Fundamental]`
For changing numbers, use **`.contentTransition(.numericText())`** so the digits roll, and for SF Symbols use **`.symbolEffect`** for effects like bounce, or **`.contentTransition(.symbolEffect(.replace))`** to animate swapping icons.

```swift
Text("\(score)")
    .contentTransition(.numericText(value: Double(score)))   // digits roll
    .animation(.snappy, value: score)

Image(systemName: "wifi")
    .symbolEffect(.variableColor.iterative, isActive: isSearching)   // pulsing bars

Image(systemName: isMuted ? "speaker.slash" : "speaker.wave.2")
    .contentTransition(.symbolEffect(.replace))                     // smooth icon swap
```

**Follow-ups:**
- **Why does `.numericText` need an animation?** The content transition only plays when the change is animated.
- **How do you bounce an icon once?** `.symbolEffect(.bounce, value: count)` bounces each time `count` changes.
- **Do symbol effects respect Reduce Motion?** Yes, automatically.

### Q87. How do you add haptic feedback? `[Fundamental]`
Since iOS 17, add **`.sensoryFeedback`**: it plays a vibration whenever a **trigger value changes**.

- Types include `.success`, `.error`, `.selection`, and `.impact`.

```swift
Button("Add to cart") { cartCount += 1 }
    .sensoryFeedback(.success, trigger: cartCount)    // vibrates when cartCount changes
```

**Follow-ups:**
- **How do you vibrate only for some changes?** Add a condition: `.sensoryFeedback(.success, trigger: value) { old, new in new > old }`.
- **What was used before iOS 17?** UIKit's `UIImpactFeedbackGenerator` and `UINotificationFeedbackGenerator`.
- **Should every tap vibrate?** No. Use haptics for meaningful moments only.

## 11. Custom Views, Modifiers, Styles & Containers

### Q88. How do you create a custom `ViewModifier`? `[Fundamental]`
Make a struct that conforms to **`ViewModifier`** and returns the styled view from `body(content:)`, then add a **`View` extension** so you can use it like a built-in modifier.

- `content` is whatever view the modifier is applied to.
- A `ViewModifier` can have its own `@State` and read the environment.

```swift
struct CardStyle: ViewModifier {
    var cornerRadius: CGFloat = 16

    func body(content: Content) -> some View {
        content
            .padding()
            .background(.background, in: RoundedRectangle(cornerRadius: cornerRadius))
            .shadow(color: .black.opacity(0.1), radius: 8, y: 4)
    }
}

extension View {
    func cardStyle(cornerRadius: CGFloat = 16) -> some View {
        modifier(CardStyle(cornerRadius: cornerRadius))
    }
}

Text("Hello").cardStyle()       // reads like a built-in modifier
```

**Follow-ups:**
- **When is a simple `View` extension enough?** When you only chain existing modifiers and need no state.
- **Can a modifier have `@State`?** Yes, for example a "shake" modifier that tracks its own animation.
- **What is `Content`?** A placeholder for the view the modifier is applied to.

### Q89. How do you create a custom `ButtonStyle`? `[Senior]`
Conform to **`ButtonStyle`** and build the look in `makeBody(configuration:)`, using `configuration.label` (the button's content) and `configuration.isPressed` (is it being pressed).

- You only change the **look**. Tapping, VoiceOver, and keyboard support stay built in.
- Apply it to a container, and every button inside gets the style.

```swift
struct PrimaryButtonStyle: ButtonStyle {
    @Environment(\.isEnabled) private var isEnabled

    func makeBody(configuration: Configuration) -> some View {
        configuration.label
            .font(.headline)
            .frame(maxWidth: .infinity)
            .padding()
            .background(isEnabled ? Color.accentColor : .gray, in: RoundedRectangle(cornerRadius: 12))
            .foregroundStyle(.white)
            .scaleEffect(configuration.isPressed ? 0.97 : 1)   // shrink a bit when pressed
    }
}

extension ButtonStyle where Self == PrimaryButtonStyle {
    static var primary: PrimaryButtonStyle { PrimaryButtonStyle() }   // enables .primary
}

VStack { Button("Continue") {}; Button("Skip") {}.disabled(true) }
    .buttonStyle(.primary)
```

**Follow-ups:**
- **Why not use `onTapGesture` on a custom view?** You'd lose VoiceOver, keyboard support, and the pressed state.
- **What is `PrimitiveButtonStyle`?** A style that also controls **when** the action fires, like only on a long press.
- **What other styles exist?** `LabelStyle`, `ToggleStyle`, `TextFieldStyle`, `ProgressViewStyle`, and more.

### Q90. How do you build a generic container view that accepts content? `[Senior]`
Make the view **generic over `Content: View`** and store the content with **`@ViewBuilder`**, so callers can pass any views in a closure, like with `VStack`.

```swift
struct Card<Content: View>: View {
    let title: String
    @ViewBuilder let content: Content          // any views the caller passes

    var body: some View {
        VStack(alignment: .leading, spacing: 8) {
            Text(title).font(.headline)
            content
        }
        .frame(maxWidth: .infinity, alignment: .leading)
        .cardStyle()
    }
}

Card(title: "Shipping") {
    Text("Arrives Tuesday")
    Text("Free delivery").foregroundStyle(.secondary)
}
```

**Follow-ups:**
- **Why store `Content` instead of a closure?** A stored value can be compared, and the closure doesn't run again on every update.
- **How do you accept a header and a body?** Use two generic types, like `Card<Header: View, Content: View>`.
- **How do you make the content optional?** Add an extra `init` for when `Content == EmptyView`.

### Q91. How do you build custom containers that inspect their subviews? `[Lead/Expert]`
Since iOS 18, **`Group(subviews:)`** and **`ForEach(subviews:)`** give you each child view separately, so you can build containers like your own `List`, for example one that adds a divider between children.

- It even splits up views created by a `ForEach` inside the content.

```swift
struct DividedStack<Content: View>: View {
    @ViewBuilder var content: Content

    var body: some View {
        VStack(spacing: 12) {
            Group(subviews: content) { subviews in         // get each child separately
                ForEach(subviews) { subview in
                    subview
                    if subview.id != subviews.last?.id { Divider() }   // divider between
                }
            }
        }
    }
}

DividedStack {
    Text("First")
    ForEach(["Second", "Third"], id: \.self) { Text($0) }
}
```

**Follow-ups:**
- **`ForEach(subviews:)` vs `Group(subviews:)`?** `ForEach` gives one child at a time. `Group` gives the whole list, so you can count or index it.
- **How do you handle `Section`s?** Use `ForEach(sections:)` to get each section's header, footer, and content.
- **How can children send extra info to the container?** With container values, declared with `@Entry` in `ContainerValues`.

### Q92. When should you extract a subview vs a computed property vs a function? `[Senior]`
A **separate `View` struct** can be skipped by SwiftUI when its inputs don't change, but a **computed property or function** is just code organization and runs every time the parent does.

- **Extract a struct** for parts that have their own state, read fast-changing data, or are reused.
- **Use a computed property** for small parts, just to keep `body` readable.

```swift
// Just organization: runs every time the parent's body runs
private var header: some View { Text(title).font(.largeTitle) }

// Separate view: SwiftUI can skip it when title hasn't changed
struct Header: View {
    let title: String
    var body: some View { Text(title).font(.largeTitle) }
}
```

**Follow-ups:**
- **When do you extract a struct?** When the part has its own state, reads fast-changing data, or is reused.
- **When is a computed property better?** For small pieces that use the same data as the parent.
- **Do many small structs slow SwiftUI down?** No. View structs are cheap, and smaller views usually mean fewer updates.

### Q93. How do you create a reusable style system / theme? `[Lead/Expert]`
Define **design tokens** (colors, fonts, spacing) in one shared place, use **asset catalog colors** so dark mode works, provide **styles and modifiers** for common looks, and pass the theme through the **environment**.

- Tokens: named values like `Spacing.medium` instead of magic numbers.
- Styles like `.buttonStyle(.primary)` are easy to find with autocomplete.

```swift
enum Spacing { static let small: CGFloat = 8; static let medium: CGFloat = 16 }

extension Color {
    static let brandPrimary = Color("BrandPrimary")   // asset catalog: light + dark versions
}

extension EnvironmentValues {
    @Entry var theme: Theme = .standard
}

Button("Continue") {}
    .buttonStyle(.primary)
    .padding(Spacing.medium)
```

**Follow-ups:**
- **Why prefer styles over big configurable components?** Styles keep built-in behavior and accessibility, and they combine easily.
- **How do custom fonts scale with the user's text size?** `.font(.custom("Brand", size: 17, relativeTo: .body))`.
- **How do you keep everyone consistent?** A catalog app showing every component, plus snapshot tests.

## 12. Gestures

### Q94. How do you implement a draggable view? What is `@GestureState`? `[Senior]`
Add a **`DragGesture`** and move the view by the drag distance, using **`@GestureState`** for the temporary drag offset because it **resets automatically** when the drag ends.

- **`@GestureState`:** the offset **while dragging**. Goes back to zero by itself.
- **`@State`:** the final position, saved in `onEnded`.

```swift
struct DraggableCard: View {
    @State private var position: CGSize = .zero            // final position
    @GestureState private var dragOffset: CGSize = .zero   // offset during the drag

    var body: some View {
        RoundedRectangle(cornerRadius: 16).fill(.blue)
            .frame(width: 200, height: 120)
            .offset(x: position.width + dragOffset.width,
                    y: position.height + dragOffset.height)
            .gesture(
                DragGesture()
                    .updating($dragOffset) { value, state, _ in state = value.translation }
                    .onEnded { value in                    // save where it was dropped
                        position.width += value.translation.width
                        position.height += value.translation.height
                    }
            )
    }
}
```

**Follow-ups:**
- **Why not use `@State` for the drag offset?** If the gesture is cancelled, `@State` doesn't reset. `@GestureState` does.
- **How do you make swipe-to-dismiss?** In `onEnded`, check if the drag (or `predictedEndTranslation`) passed a limit, then animate the card away.
- **How do you make it spring back?** Add `.animation(.spring, value: dragOffset)`.

### Q95. How do you combine gestures? `[Senior]`
There are three ways: **`.simultaneously(with:)`** runs two gestures **at the same time**, **`.sequenced(before:)`** runs them **one after another**, and **`.exclusively(before:)`** lets **only one** of them win.

- **Simultaneously:** pinch to zoom and rotate together.
- **Sequenced:** long press, then drag.
- **Exclusively:** double tap wins over single tap.

```swift
// Pinch and rotate at the same time
Image("photo")
    .scaleEffect(scale)
    .rotationEffect(angle)
    .gesture(
        MagnifyGesture().onChanged { scale = $0.magnification }
            .simultaneously(with: RotateGesture().onChanged { angle = $0.rotation })
    )

// Double tap wins over single tap
let taps = TapGesture(count: 2).onEnded { zoom() }
    .exclusively(before: TapGesture().onEnded { toggleControls() })
```

**Follow-ups:**
- **What do `.highPriorityGesture` and `.simultaneousGesture` do?** The first makes your gesture beat the child's gesture. The second lets both run together.
- **What replaced `MagnificationGesture` and `RotationGesture`?** `MagnifyGesture` and `RotateGesture` (iOS 17).
- **Why does a drag inside a `ScrollView` block scrolling?** Your drag wins. Use `.simultaneousGesture` or a minimum drag distance.

### Q96. Why isn't my tap gesture firing on empty areas of a view? `[Fundamental]`
Because **only the visible parts** of a view respond to taps by default, and empty space like a `Spacer` is invisible. Add **`.contentShape(Rectangle())`** to make the whole area tappable.

```swift
HStack {
    Text("Settings")
    Spacer()                        // empty: not tappable by default
    Image(systemName: "chevron.right")
}
.contentShape(Rectangle())          // now the whole row is tappable
.onTapGesture { openSettings() }
```

**Follow-ups:**
- **Should this be a `Button` instead?** Usually yes. A `Button` works with VoiceOver and keyboards automatically.
- **Does the same apply to buttons with `.plain` style?** Yes, add `.contentShape` there too.
- **How do you make a view ignore taps?** `.allowsHitTesting(false)`. Taps go through to the view behind it.

## 13. Performance

### Q97. What are the most common causes of poor SwiftUI performance? `[Senior]`
Most slow SwiftUI screens come from **views updating more often than needed** or **doing too much work each time they update**.

- Views that read more data than they show.
- IDs that change (unstable identity).
- Heavy work in `body` or `init`, like sorting or creating formatters.
- `AnyView` everywhere.
- Non-lazy stacks for long lists.
- Too many `GeometryReader`s.
- State that changes very often, like a scroll offset.

```swift
// ❌ Sorts and creates a formatter on every update
var body: some View {
    List(events.sorted { $0.date < $1.date }) { event in
        Text(DateFormatter().string(from: event.date))
    }
}
```

**Follow-ups:**
- **What do you check first?** Views that read too much data, because that multiplies every other cost.
- **How does a big `ObservableObject` hurt?** Any `@Published` change updates every view watching it.
- **Where do you test performance?** In a Release build on an older real device, not the simulator.

### Q98. How do you find out why a view's `body` re-ran? `[Senior]`
Add **`let _ = Self._printChanges()`** inside `body` while debugging, and it prints **which value caused the update**.

- For a bigger picture, use Instruments: the **SwiftUI** instrument, **Time Profiler**, and **Hangs**.

```swift
var body: some View {
    let _ = Self._printChanges()   // debug only
    Text(model.title)
}
// Prints something like: "ProductRow: @self, _model changed."
```

**Follow-ups:**
- **What does `@self` mean in the output?** The parent passed new input values.
- **Can you ship `_printChanges` in the app?** No. It's a private debug tool. Remove it or wrap it in `#if DEBUG`.
- **What did Xcode 26 add?** A new SwiftUI instrument that shows slow updates and why views updated.

### Q99. How do you reduce unnecessary view updates? `[Senior]`
Make each view **depend on as little data as possible**: split big views into small ones, and pass each child **only the values it shows**.

- Use `@Observable` so views only track what they read.
- Calculate derived data in the model, not in `body`.
- Keep fast-changing values (timers, scroll offsets) in small views only.

```swift
// ❌ Every row depends on the whole store
struct Row: View {
    let store: Store
    let id: Item.ID
    var body: some View { Text(store.items[id]?.title ?? "") }
}

// ✅ Each row depends only on its own title
struct Row: View {
    let title: String
    var body: some View { Text(title) }
}
```

**Follow-ups:**
- **How do you handle a timer that changes every second?** Read it only inside a tiny view, so only that view updates.
- **Is passing a whole `@Observable` model to a row bad?** Less bad than with `ObservableObject`, because the row only tracks what it reads.
- **How do you prove it helped?** Count `body` updates before and after, with `_printChanges` or Instruments.

### Q100. Why is `AnyView` bad for performance? `[Senior]`
`AnyView` **hides the real view type from SwiftUI**, so SwiftUI can't tell whether the old and new views are the same kind, and it may **rebuild** that part of the screen, losing state and animations.

- Use `@ViewBuilder` with `if/else`, `Group`, or generics instead. They keep the type.

```swift
// ❌ Hides the type
func icon(for status: Status) -> AnyView {
    status == .done ? AnyView(Image(systemName: "checkmark")) : AnyView(ProgressView())
}

// ✅ Keeps the type
@ViewBuilder
func icon(for status: Status) -> some View {
    if status == .done { Image(systemName: "checkmark") } else { ProgressView() }
}
```

**Follow-ups:**
- **When is `AnyView` OK?** Rarely, like a plugin system where view types are unknown in advance.
- **Is one `AnyView` at the top of the app a problem?** Usually not. It hurts when used in many rows or when the type changes often.
- **How do you show a list of different view types?** Store **data**, not views, and use `ForEach` with a `switch` to pick the view.

### Q101. How do you avoid expensive work in `body`? `[Senior]`
**Move heavy work out of `body` into the model**, where it's done once when the data changes, and use **`FormatStyle`** (like `.dateTime`) instead of creating formatters.

- `body` can run many times per second. Sorting or creating formatters there is wasted work.

```swift
// ✅ Sorted once in the model; FormatStyle is cached by the system
var body: some View {
    List(model.sortedEvents) { event in
        Text(event.date, format: .dateTime.day().month().year())
    }
}
```

**Follow-ups:**
- **Why is creating a `DateFormatter` in `body` slow?** Formatters are expensive to create, and `body` runs often.
- **What if the result depends on a filter the user types?** Recalculate it in the model when the filter changes, not on every `body` run.
- **Is the view's `init` a good place for heavy work?** No. It also runs many times. Use `.task` or the model.

### Q102. How does `Equatable` conformance help view performance? `[Lead/Expert]`
If a view is **`Equatable`**, SwiftUI can use **your `==`** to decide whether the view changed, which helps when the view has inputs SwiftUI can't compare, like closures.

- In the example, `==` compares only `points` and ignores the closure.
- So the chart only updates when the points actually change.

```swift
struct ChartView: View, Equatable {
    let points: [Double]
    let onSelect: (Int) -> Void           // closures can't be compared

    static func == (lhs: Self, rhs: Self) -> Bool {
        lhs.points == rhs.points          // only compare what affects the UI
    }

    var body: some View { Text("\(points.count) points") }
}

// Usage: ChartView(points: data, onSelect: select).equatable()
```

**Follow-ups:**
- **What does `.equatable()` do?** Tells SwiftUI explicitly to use your `==`.
- **What is the risk?** If `==` ignores something the UI shows, the view won't update when it should.
- **Is this needed with `@Observable` models?** Less often, because Observation already limits updates.

### Q103. How do you optimize long lists and image-heavy feeds? `[Lead/Expert]`
Keep **rows small and cheap**, give them **stable IDs**, and load images **at the size they're shown** with a **cache**.

- Use `List` or lazy stacks.
- Precompute row text in the model.
- Avoid heavy effects per row, like big blurs and shadows.
- Load the next page early.
- **Before iOS 27**, `AsyncImage` had no cache, so feeds needed a custom image loader. **In iOS 27**, it uses normal HTTP caching by default.

```swift
// iOS 27: control AsyncImage caching with your own URLSession
AsyncImage(url: post.imageURL) { image in
    image.resizable().scaledToFill()
} placeholder: {
    Color.gray.opacity(0.2)
}
.asyncImageURLSession(imageSession)     // a session set up with a URLCache
```

**Follow-ups:**
- **What is downsampling?** Decoding an image at the size it's shown, not full size. It saves a lot of memory.
- **Which image libraries do teams use?** Nuke or Kingfisher, or a small custom loader with `NSCache`.
- **Why are big shadows slow in rows?** Each one needs extra drawing work for every row.

### Q104. What does `drawingGroup()` do? `[Lead/Expert]`
`drawingGroup()` **draws a group of views into one image using the GPU (Metal)** before showing it, which is faster when you have **many overlapping shapes**, like charts or particles.

- For simple views or text, it can be slower, so measure first.

```swift
ZStack {
    ForEach(0..<300) { i in
        Circle()
            .fill(.blue.opacity(0.1))
            .frame(width: 20, height: 20)
            .offset(x: CGFloat(i % 20) * 12, y: CGFloat(i / 20) * 12)
    }
}
.drawingGroup()      // draw all 300 circles as one image
```

**Follow-ups:**
- **Why can text look worse?** It becomes a picture, so it can lose sharpness.
- **What's an alternative for custom drawing?** `Canvas`, which draws many shapes efficiently in one view.
- **How do you know it helped?** Compare frame times in Instruments with and without it.

## 14. Accessibility, Dynamic Type & Localization

### Q105. How do you make SwiftUI views accessible? `[Senior]`
Standard controls like `Button` and `Toggle` are **accessible automatically**, and for custom views you **group related parts, give clear labels, hide decorative images, and add custom actions**.

- **Group:** `.accessibilityElement(children: .combine)` makes VoiceOver read a row as one item.
- **Label:** `.accessibilityLabel` says what something is in plain words.
- **Hide:** `.accessibilityHidden(true)` for purely decorative images.
- **Actions:** `.accessibilityAction(named:)` for things that are hard to do with VoiceOver, like a swipe.

```swift
HStack {
    Image(systemName: "star.fill")
    Text("4.5")
    Text("(120 reviews)")
}
.accessibilityElement(children: .combine)                   // read as one item
.accessibilityLabel("Rated 4.5 stars from 120 reviews")     // clear sentence

Image("decorative-wave").accessibilityHidden(true)          // skip decoration

ProductCard(product: product)
    .accessibilityAction(named: "Add to cart") { addToCart(product) }
```

**Follow-ups:**
- **What if you use `onTapGesture` on a custom view?** VoiceOver won't know it's a button. Add `.accessibilityAddTraits(.isButton)`, or better, use a `Button`.
- **`.combine` vs `.ignore`?** `.combine` merges the children's text. `.ignore` hides them so you write the label yourself.
- **How do you label an icon-only button?** `.accessibilityLabel("Add to favorites")`. Describe the action, not the picture.

### Q106. How do you support Dynamic Type? `[Senior]`
Use **system text styles** like `.body` that grow with the user's text size, scale custom sizes with **`@ScaledMetric`**, and **change the layout** (for example, row to column) at very large sizes.

- Limit text size with `.dynamicTypeSize(...)` only when a layout truly can't adapt.

```swift
struct ProfileRow: View {
    @ScaledMetric(relativeTo: .body) private var avatarSize: CGFloat = 40   // grows with text
    @Environment(\.dynamicTypeSize) private var dynamicTypeSize

    var body: some View {
        let layout = dynamicTypeSize.isAccessibilitySize
            ? AnyLayout(VStackLayout(alignment: .leading))   // huge text → stack vertically
            : AnyLayout(HStackLayout())
        layout {
            Image(systemName: "person.circle").resizable()
                .frame(width: avatarSize, height: avatarSize)
            Text("Taylor").font(.body)
        }
    }
}
```

**Follow-ups:**
- **How do you scale a custom font?** `.font(.custom("Avenir", size: 17, relativeTo: .body))`.
- **When is limiting text size OK?** For small fixed parts, like a tab label: `.dynamicTypeSize(...DynamicTypeSize.accessibility2)`.
- **What else should change at large sizes?** Text should wrap, not get cut off, and rows often become columns.

### Q107. How does localization work in SwiftUI? `[Senior]`
`Text("Hello")` with a **string literal is translated automatically** from the String Catalog, but `Text(someVariable)` with a **`String` variable is not**, so you translate variables with `String(localized:)`.

- Values inside `\( )` become placeholders, which also support plurals.
- Use `FormatStyle` for dates, numbers, and money, so they match the user's region.

```swift
Text("Welcome back, \(user.name)!")                     // translated, with a placeholder
Text(price, format: .currency(code: "EUR"))             // formatted for the user's region
let title = String(localized: "settings.title", comment: "Settings screen title")
Text(verbatim: "v1.2.3")                                // never translated
```

**Follow-ups:**
- **What is a String Catalog?** The `.xcstrings` file (Xcode 15+) that holds all your strings and their translations.
- **How do you handle "1 item" vs "2 items"?** Write `Text("\(count) items")` and add plural versions in the String Catalog.
- **How do you translate strings inside a Swift package?** Pass the package bundle: `String(localized: "title", bundle: .module)`.

### Q108. How do you test accessibility and localization in previews? `[Fundamental]`
Make **previews with different environment settings**: large text, dark mode, right-to-left layout, and another language.

- Also use the **Accessibility Inspector** and the canvas **Variants** mode.

```swift
#Preview("Large text, dark, RTL") {
    ProfileRow()
        .environment(\.dynamicTypeSize, .accessibility3)        // very large text
        .preferredColorScheme(.dark)                           // dark mode
        .environment(\.layoutDirection, .rightToLeft)          // right-to-left
        .environment(\.locale, Locale(identifier: "ar"))       // Arabic
}
```

**Follow-ups:**
- **What does Variants mode show?** The same preview in many text sizes, color schemes, or orientations side by side.
- **How do you test long translations without real ones?** Use the "Double-Length Pseudolanguage" option in the scheme.
- **Does `locale` in a preview change the translations?** Yes for `Text` with string literals, if translations exist. Strings already made with `String(localized:)` keep the app's language.

## 15. Previews & Tooling

### Q109. How do you write previews effectively? `[Fundamental]`
Write **one preview for each important state** (loaded, empty, error) using **sample data and fake services**, so you can see every state without running the app.

- In iOS 18, `@Previewable` lets you use `@State` right inside a preview.

```swift
#Preview("Loaded") {
    ProductListView(model: .preview(products: Product.samples))
}

#Preview("Empty") {
    ProductListView(model: .preview(products: []))
}

#Preview {
    @Previewable @State var isOn = true       // real state inside the preview
    Toggle("Wi-Fi", isOn: $isOn)
}
```

**Follow-ups:**
- **What makes a view easy to preview?** Dependencies passed in (so you can use fakes) and ready-made sample data.
- **How do you preview just a row at its natural size?** `#Preview(traits: .sizeThatFitsLayout) { ProductRow(product: .sample) }`.
- **Can previews show UIKit views?** Yes, `#Preview` can return a `UIView` or `UIViewController`.

### Q110. How do you share setup (like a SwiftData container) across previews? `[Senior]`
In iOS 18, make a **`PreviewModifier`** that builds the setup **once** (for example, a SwiftData database in memory with sample data) and turn it into a **preview trait** any preview can use.

- `makeSharedContext` builds the setup once and caches it.
- `body` applies it to each preview.

```swift
struct SampleData: PreviewModifier {
    // 1. Build once, shared by all previews
    static func makeSharedContext() async throws -> ModelContainer {
        let container = try ModelContainer(for: Trip.self,
            configurations: ModelConfiguration(isStoredInMemoryOnly: true))
        Trip.samples.forEach { container.mainContext.insert($0) }
        return container
    }

    // 2. Apply it to a preview
    func body(content: Content, context: ModelContainer) -> some View {
        content.modelContainer(context)
    }
}

extension PreviewTrait where T == Preview.ViewTraits {
    @MainActor static var sampleData: Self = .modifier(SampleData())
}

#Preview(traits: .sampleData) { TripListView() }
```

**Follow-ups:**
- **Why "shared"?** It's built once and reused, so previews load faster.
- **Why store the data in memory?** Previews start clean every time and never touch real data.
- **How was this done before iOS 18?** A static `previewContainer` property you passed to each preview by hand.

### Q111. Why do previews crash or become slow, and how do you fix it? `[Senior]`
Previews usually break because the view **does real work** (network, database, singletons, app startup code) or a **required environment object is missing**. Fix it by giving the preview **fake services and every object it needs**.

- Smaller modules (Swift packages) also make previews build faster.

```swift
#Preview {
    CartView()
        .environment(Cart.preview)                                       // required object
        .environment(\.productAPI, MockProductAPI(products: .samples))    // fake network
}
```

**Follow-ups:**
- **How do you see why a preview crashed?** Open the preview diagnostics in Xcode to read the crash log.
- **Why do packages preview faster?** Xcode only builds the small package, not the whole app.
- **How do you stop startup code from running in previews?** Move it out of view `init`s. As a last resort, check the `XCODE_RUNNING_FOR_PREVIEWS` environment variable.

## 16. Architecture & Dependency Injection

### Q112. Do you need MVVM in SwiftUI? `[Lead/Expert]`
**Not always**: simple screens can use shared models directly, while complex screens benefit from a **view model** that holds the screen's logic and can be tested without UI.

- **Argument against MVVM ("MV"):** SwiftUI views already react to data, so a view model per screen can be extra code.
- **Argument for MVVM:** logic is testable without UI, and a big team gets one consistent structure.
- **My rule:** business logic never lives in views. Small screens bind to models directly. Complex screens get an `@Observable` view model.

```swift
// Simple screen: use the shared model directly
struct CartBadge: View {
    @Environment(Cart.self) private var cart
    var body: some View { Text("\(cart.items.count)") }
}

// Complex screen: a view model that can be tested
@MainActor @Observable
final class CheckoutViewModel {
    var state: CheckoutState = .editing
    func placeOrder() async { /* validation, API call, error handling */ }
}
```

**Follow-ups:**
- **What does Apple's sample code usually do?** Shares `@Observable` models through the environment, without a view model per screen.
- **What belongs in a view model?** Formatting, validation, loading states, and service calls. Not layout.
- **What matters most for a team?** Consistency, so every screen is built the same way.

### Q113. Show an MVVM screen with `@Observable` and dependency injection. `[Senior]`
The **view model** is a `@MainActor @Observable` class that gets its **API service passed in** and exposes a **state enum**, and the **view** owns it with `@State`, starts loading in `.task`, and shows each state.

- **Dependency injection** means passing the service in from outside, so tests can pass a fake one.
- `loadIfNeeded` stops the list from reloading every time the user comes back to it.

```swift
protocol ProductAPI: Sendable { func fetchProducts() async throws -> [Product] }

@MainActor @Observable
final class ProductListViewModel {
    enum State { case idle, loading, loaded([Product]), failed(String) }
    private(set) var state: State = .idle
    private let api: ProductAPI
    init(api: ProductAPI) { self.api = api }            // service is passed in

    func loadIfNeeded() async {
        guard case .idle = state else { return }        // load only the first time
        await load()
    }

    func load() async {
        state = .loading
        do { state = .loaded(try await api.fetchProducts()) }
        catch { state = .failed(error.localizedDescription) }
    }
}

struct ProductListView: View {
    @State private var viewModel: ProductListViewModel
    init(api: ProductAPI) { _viewModel = State(initialValue: ProductListViewModel(api: api)) }

    var body: some View {
        content                                          // switches over viewModel.state (see Q77)
            .task { await viewModel.loadIfNeeded() }
            .refreshable { await viewModel.load() }
    }
}
```

**Follow-ups:**
- **Why not just call `load()` in `.task`?** `.task` runs every time the view appears, so the list would reload each time you come back.
- **Why is the API a protocol?** So tests and previews can pass a fake version.
- **Why keep the view model's `init` cheap?** On Xcode versions before 27, `@State` can create it many times (see Q31).

### Q114. How do you inject services through the environment? `[Senior]`
Add an **`@Entry` environment value** whose default is the **real service**, read it with `@Environment` where needed, and replace it with a **fake** in previews and tests.

```swift
extension EnvironmentValues {
    @Entry var productAPI: any ProductAPI = LiveProductAPI()   // real service by default
}

struct ProductsScreen: View {
    @Environment(\.productAPI) private var api
    var body: some View { ProductListView(api: api) }
}

#Preview {
    ProductsScreen()
        .environment(\.productAPI, MockProductAPI(products: Product.samples))   // fake one
}
```

**Follow-ups:**
- **What's good about it?** You don't pass the service through every view, and swapping in fakes is easy.
- **What's the downside?** You can't see a view's dependencies in its `init`.
- **Can a view model read the environment?** No, only views can. The view reads the service and passes it to the view model.

### Q115. What is The Composable Architecture (TCA), and what are its trade-offs? `[Lead/Expert]`
TCA is a **third-party architecture** (from Point-Free) where all screen data is in a **State**, every event is an **Action**, and a **Reducer** decides how each action changes the state.

- **Pros:** predictable state changes, very thorough testing, the same pattern everywhere.
- **Cons:** learning curve, more code, slower builds, and you depend on an outside library.

```swift
@Reducer
struct Counter {
    @ObservableState
    struct State: Equatable { var count = 0 }      // all the screen's data
    enum Action { case incrementTapped }           // everything that can happen

    var body: some ReducerOf<Self> {
        Reduce { state, action in                  // how each action changes state
            switch action {
            case .incrementTapped:
                state.count += 1
                return .none                       // no side work to run
            }
        }
    }
}
```

**Follow-ups:**
- **When would you choose TCA?** A large team that wants strict, fully testable state changes and is ready to learn it.
- **What is an "effect"?** Async work, like a network call, that the reducer returns. It can send new actions later.
- **What's the risk?** You depend on the library's updates and API changes, and new hires need time to learn it.

### Q116. How do you structure a large SwiftUI app into modules? `[Lead/Expert]`
Split the app into **Swift packages**: one per **feature** (like Checkout, Profile) plus **shared** ones (Design System, Networking, Models), and let the **app target connect them**.

- Features don't import each other. They share only small "interface" packages.
- Benefits: faster builds and previews, and clear ownership for teams.

```swift
// Package.swift (excerpt)
.target(name: "CheckoutFeature", dependencies: ["DesignSystem", "Models", "NetworkingInterface"]),
.target(name: "ProfileFeature",  dependencies: ["DesignSystem", "Models"]),

// The app target connects the features
NavigationStack(path: $router.path) {
    HomeView()
        .navigationDestination(for: AppRoute.self) { route in
            switch route {
            case .checkout: CheckoutFeature.RootView()
            case .profile:  ProfileFeature.RootView()
            }
        }
}
```

**Follow-ups:**
- **How do features navigate to each other without importing each other?** They use route enums, and the app target turns routes into screens.
- **What goes in an "interface" package?** Only protocols and models, not the heavy code.
- **How do you know a module is too big?** Small changes cause long builds and slow previews.

### Q117. Where should navigation logic live in SwiftUI? `[Lead/Expert]`
In a small app, **inside the views** with `NavigationLink(value:)`. In a bigger app, in a **router object** (see Q61) so deep links, login checks, and analytics live in one place and can be **tested without UI**.

```swift
@Test @MainActor func checkoutFlowPushesConfirmation() {
    let router = Router()
    router.push(.cart)
    router.push(.orderConfirmation(orderID: "A123"))
    #expect(router.path == [.cart, .orderConfirmation(orderID: "A123")])   // no UI needed
}
```

**Follow-ups:**
- **What's wrong with `NavigationLink` everywhere in a big app?** Navigation logic is scattered, hard to test, and hard to drive from deep links.
- **Where does TCA keep navigation?** In the feature's state, as a stack of child screen states.
- **How do you handle sheets in a router?** Add an optional `sheet` property (an enum) and use `.sheet(item:)`.

## 17. SwiftData & UIKit Integration (Quick Reference)

> SwiftData and UIKit have their own detailed files. These are the SwiftUI-side essentials.

### Q118. How do you use SwiftData in a SwiftUI view? `[Fundamental]`
Mark your model class with **`@Model`**, add a database with **`.modelContainer(for:)`**, read data with **`@Query`**, and add or delete through **`modelContext`**.

- `@Query` keeps the list up to date automatically when data changes.

```swift
@Model
final class Trip {                                   // a saved model
    var name: String
    var startDate: Date
    init(name: String, startDate: Date) { self.name = name; self.startDate = startDate }
}

struct TripListView: View {
    @Query(sort: \Trip.startDate, order: .reverse) private var trips: [Trip]   // read
    @Environment(\.modelContext) private var modelContext                      // write

    var body: some View {
        List {
            ForEach(trips) { Text($0.name) }
                .onDelete { $0.forEach { modelContext.delete(trips[$0]) } }
        }
        .toolbar {
            Button("Add") { modelContext.insert(Trip(name: "New Trip", startDate: .now)) }
        }
    }
}
// In the App: WindowGroup { TripListView() }.modelContainer(for: Trip.self)
```

**Follow-ups:**
- **How do you filter by something the user typed?** Build the query in the view's `init` with a `#Predicate`, like `_trips = Query(filter: #Predicate { $0.name.contains(search) })`.
- **Do you need to call `save()`?** Usually not. SwiftData saves automatically, but you can call `try modelContext.save()` for important changes.
- **Can a view model use `@Query`?** No, only views. A view model uses `modelContext.fetch` instead.

### Q119. How do you wrap a UIKit view controller for SwiftUI? `[Senior]`
Conform to **`UIViewControllerRepresentable`**: `makeUIViewController` **creates** the UIKit controller once, and `updateUIViewController` **passes new SwiftUI data** into it when things change.

- A **`Coordinator`** acts as the UIKit delegate and sends events back to SwiftUI.

```swift
import SafariServices

struct SafariView: UIViewControllerRepresentable {
    let url: URL

    func makeUIViewController(context: Context) -> SFSafariViewController {
        SFSafariViewController(url: url)               // created once
    }

    func updateUIViewController(_ controller: SFSafariViewController, context: Context) { }
}

// Usage: .sheet(item: $link) { SafariView(url: $0.url).ignoresSafeArea() }
```

**Follow-ups:**
- **What is the `Coordinator` for?** It's the UIKit delegate, and it sends changes back to SwiftUI, often through a binding.
- **How do you put SwiftUI inside UIKit?** `UIHostingController`, or `UIHostingConfiguration` for table and collection view cells.
- **Why not create the controller in `update`?** `update` runs many times. You'd rebuild it on every change.

### Q120. When would you drop down to UIKit inside a SwiftUI app? `[Lead/Expert]`
When **SwiftUI can't do it yet** on your minimum iOS version, when a screen needs **very fine performance control**, or when you can **reuse a solid UIKit component** you already have.

- Examples: advanced text editing before iOS 26's rich `TextEditor`, some camera or scanner screens.
- Keep the wrapper small, so it's easy to remove later.

```swift
// A thin wrapper: SwiftUI-friendly outside, UIKit inside
struct RichTextView: UIViewRepresentable {
    @Binding var text: NSAttributedString

    func makeUIView(context: Context) -> UITextView { UITextView() }

    func updateUIView(_ view: UITextView, context: Context) {
        if view.attributedText != text { view.attributedText = text }   // only set if different
    }
}
```

**Follow-ups:**
- **Why check before setting the text?** Setting it again resets the cursor and can cause update loops.
- **How do UIKit changes get back to SwiftUI?** A `Coordinator` acts as the `UITextView` delegate and writes to the binding.
- **When do you remove the wrapper?** When your minimum iOS version has a SwiftUI version that does the job.

## 18. Testing SwiftUI

### Q121. How do you test SwiftUI code? `[Senior]`
**Test the logic, not the views**: unit test view models, models, and routers, because that's where most bugs are and those tests are fast.

- Add **snapshot tests** to catch visual changes.
- Add a **few UI tests** for the most important flows.
- Libraries that inspect SwiftUI views exist, but they break easily.

```swift
import Testing
@testable import Shop

struct MockProductAPI: ProductAPI {                       // fake service
    var result: Result<[Product], Error>
    func fetchProducts() async throws -> [Product] { try result.get() }
}

@MainActor
struct ProductListViewModelTests {
    @Test func loadSuccessShowsProducts() async {
        let viewModel = ProductListViewModel(api: MockProductAPI(result: .success([.sample])))
        await viewModel.load()
        guard case .loaded(let products) = viewModel.state else {
            Issue.record("Expected loaded state"); return
        }
        #expect(products.count == 1)
    }
}
```

**Follow-ups:**
- **Why put `@MainActor` on the test suite?** The view model runs on the main actor, so the tests must too.
- **How do you test the error case?** Pass a fake that returns `.failure(...)` and check that the state is `.failed`.
- **What makes view models easy to test?** Services passed in through protocols, and state stored as simple values.

### Q122. How do you write UI tests for SwiftUI views? `[Fundamental]`
Give important elements an **`.accessibilityIdentifier`**, launch the app in a **test mode**, find elements **by those IDs**, and **wait** for results before checking them.

```swift
// In the app
Button("Add to cart") { model.add(product) }
    .accessibilityIdentifier("product.addToCart")

// In the UI test
@MainActor
func testAddToCartUpdatesBadge() {
    let app = XCUIApplication()
    app.launchArguments = ["-uiTesting"]              // app uses fake data in this mode
    app.launch()

    app.buttons["product.addToCart"].tap()
    XCTAssertTrue(app.staticTexts["cart.badge"].waitForExistence(timeout: 2))
    XCTAssertEqual(app.staticTexts["cart.badge"].label, "1")
}
```

**Follow-ups:**
- **Why IDs instead of the visible text?** Text changes with translations and copy edits. IDs stay the same.
- **What does `-uiTesting` do?** The app checks for it at launch and switches to fake services and clean data.
- **Why keep UI tests few?** They're slow and can be flaky, so cover only the most important flows.

### Q123. How do you snapshot test SwiftUI views? `[Senior]`
Use a library like **SnapshotTesting** to **render the view to an image** and compare it with a saved "correct" image, in several versions like large text and dark mode.

- If something looks different, the test fails and shows you the difference.

```swift
import SnapshotTesting
import XCTest

final class ProductRowSnapshotTests: XCTestCase {
    @MainActor
    func testProductRowVariants() {
        let view = ProductRow(product: .sample).frame(width: 375)
        assertSnapshot(of: view, as: .image(layout: .sizeThatFits))                       // normal
        assertSnapshot(of: view.environment(\.dynamicTypeSize, .accessibility3),
                       as: .image(layout: .sizeThatFits), named: "a11y-large")            // big text
        assertSnapshot(of: view.preferredColorScheme(.dark),
                       as: .image(layout: .sizeThatFits), named: "dark")                  // dark mode
    }
}
```

**Follow-ups:**
- **Why do snapshot tests sometimes fail on CI for no reason?** Different simulators or iOS versions draw slightly differently. Use the same ones everywhere.
- **How do you update the saved image on purpose?** Run in record mode, check the new image, and commit it.
- **What don't snapshot tests catch?** Behavior, like what a tap does. That needs unit or UI tests.

## 19. Modern SwiftUI (iOS 17 → iOS 27)

### Q124. What were the key SwiftUI additions in iOS 17? `[Senior]`
iOS 17's biggest additions were **`@Observable`** (a simpler, faster way to share data) and **SwiftData** (saving data with very little code), plus many smaller tools.

- **Data:** `@Observable`, `@Bindable`, SwiftData.
- **Scrolling:** `scrollTargetBehavior` (snapping), `scrollPosition(id:)`, `containerRelativeFrame`, `scrollTransition`.
- **Animation:** phase and keyframe animators, and `withAnimation` completion.
- **Other:** `ContentUnavailableView`, two-value `onChange`, `sensoryFeedback`, the `#Preview` macro.

```swift
@Observable final class Store { var items: [Item] = [] }

ScrollView(.horizontal) {
    LazyHStack { ForEach(items) { CardView(item: $0).containerRelativeFrame(.horizontal) } }
        .scrollTargetLayout()
}
.scrollTargetBehavior(.viewAligned)       // snaps to each card
```

**Follow-ups:**
- **Which iOS 17 feature changed app architecture the most?** `@Observable`, because it changed how models are owned and shared.
- **What does `scrollTransition` do?** Changes a view (like scale or opacity) based on where it is while scrolling.
- **What replaced `MagnificationGesture`?** `MagnifyGesture`, along with `RotateGesture`.

### Q125. What were the key SwiftUI additions in iOS 18? `[Senior]`
iOS 18 added the **new `Tab` API**, the **zoom navigation transition**, tools to **build custom containers**, and new **scroll** and **macro** helpers.

- **Navigation:** `Tab` with `.sidebarAdaptable`, zoom transition.
- **Containers:** `ForEach(subviews:)` and `Group(subviews:)`.
- **Macros:** `@Entry` (custom environment values), `@Previewable` (state in previews).
- **Scrolling:** `onScrollGeometryChange`, `onScrollVisibilityChange`.
- **Concurrency:** the `View` protocol became `@MainActor`.

```swift
TabView {
    Tab("Home", systemImage: "house") { HomeView() }
    Tab(role: .search) { SearchView() }
}
.tabViewStyle(.sidebarAdaptable)

extension EnvironmentValues { @Entry var theme: Theme = .standard }
```

**Follow-ups:**
- **What graphics features arrived?** `MeshGradient` and `TextRenderer` (custom text drawing).
- **Which iOS 18 API also works on older iOS versions?** `onGeometryChange`, back to iOS 16.
- **Why did `View` becoming `@MainActor` matter?** The compiler now checks view code as main-thread code, which affects Swift 6 migrations.

### Q126. What changed in SwiftUI with iOS 26? `[Senior]`
iOS 26 introduced the **Liquid Glass** design: system bars, tab bars, toolbars, and sheets get the new glass look **automatically**, and `.glassEffect()` adds it to your own views.

- **Glass tools:** `.glassEffect()`, `GlassEffectContainer`, `.buttonStyle(.glass)`.
- **Other additions:** a native `WebView`, rich text editing in `TextEditor` with `AttributedString`, the `@Animatable` macro, and a new SwiftUI instrument in Xcode 26.

```swift
GlassEffectContainer {                        // glass shapes inside blend together
    HStack(spacing: 12) {
        Button("Edit", systemImage: "pencil") { edit() }
            .buttonStyle(.glass)
        Image(systemName: "star.fill")
            .padding()
            .glassEffect()
    }
}
```

**Follow-ups:**
- **Why use `GlassEffectContainer`?** Glass shapes inside it are drawn together, so they can blend and morph into each other.
- **Do apps get Liquid Glass without code changes?** Yes, standard bars, toolbars, and sheets update automatically with the new SDK.
- **What did iOS 27 add?** `@State` became a macro that creates classes only once, `ViewBuilder` became `ContentBuilder` (faster builds), alerts and dialogs accept an item binding, swipe actions and reordering work outside `List`, `AsyncImage` caches by default, and toolbars got overflow and pinning options.

### Q127. How do you adopt new APIs while supporting older iOS versions? `[Lead/Expert]`
Put each **`if #available` check inside a small helper modifier**, so the rest of the code stays clean and you can delete the old branch easily when you raise the minimum iOS version.

- The two branches are different views, but that's fine: the iOS version never changes while the app runs.

```swift
extension View {
    @ViewBuilder
    func cardBackground() -> some View {
        if #available(iOS 26, *) {
            self.glassEffect(in: .rect(cornerRadius: 16))                              // new look
        } else {
            self.background(.ultraThinMaterial, in: RoundedRectangle(cornerRadius: 16)) // fallback
        }
    }
}
```

**Follow-ups:**
- **How do you choose the minimum iOS version?** With data: how many users are on each version, and how much each old version costs to support.
- **What's the risk of `#available` checks everywhere?** Two versions of the code to test and maintain, and harder cleanup.
- **What does Swift 6.4 add?** An `anyAppleOS` shorthand to cover all Apple platforms in one availability check.

## 20. "What's the Output?" Questions

> For these, read the code, say the answer, then give the one-sentence reason.

### Q128. Modifier order `[Fundamental]`
```swift
Text("Hi")
    .background(.red)
    .padding(20)
    .background(.blue)
```
**Answer:** Red tightly behind the text, then a 20-point blue border around it.

**Why:** Each modifier wraps everything above it. Red wraps the text, padding wraps that, and blue wraps all of it.

**Follow-ups:**
- **How would you make the whole area red?** Put `.padding(20)` before `.background(.red)`.
- **What if you added `.frame(width: 200)` at the end?** The blue box stays the same size, centered inside an invisible 200-point-wide box.

### Q129. `if/else` and state `[Senior]`
```swift
struct CounterView: View {
    @State private var count = 0
    var body: some View { Button("Count: \(count)") { count += 1 } }
}

struct Parent: View {
    @State private var isHighlighted = false
    var body: some View {
        VStack {
            if isHighlighted { CounterView().background(.yellow) } else { CounterView() }
            Toggle("Highlight", isOn: $isHighlighted)
        }
    }
}
```
**Question:** You tap the counter up to 5, then flip the toggle. What does the counter show?

**Answer:** `Count: 0`.

**Why:** The two `if/else` branches are two different views. Flipping the toggle removes one and creates a new one, with a fresh `count`. Fix: `CounterView().background(isHighlighted ? Color.yellow : .clear)`.

**Follow-ups:**
- **What do you see on screen when toggling?** A fade between the two views, because one is removed and another added.
- **Another way to keep the count?** Store `count` in the parent and pass a binding down.

### Q130. `@ObservedObject` created inline `[Senior]`
```swift
final class CounterModel: ObservableObject { @Published var count = 0 }

struct Child: View {
    @ObservedObject var model = CounterModel()
    var body: some View { Button("Child: \(model.count)") { model.count += 1 } }
}

struct Parent: View {
    @State private var tick = 0
    var body: some View {
        VStack {
            Button("Parent: \(tick)") { tick += 1 }
            Child()
        }
    }
}
```
**Question:** Tap the child up to 3, then tap the parent button. What does the child show?

**Answer:** `Child: 0`.

**Why:** Tapping the parent re-runs its `body`, which creates a new `Child` with a **new** `CounterModel()`. `@ObservedObject` doesn't keep the old one. Fix: use `@StateObject`, or `@State` with `@Observable`.

**Follow-ups:**
- **Why does the bug only appear after tapping the parent?** The model is only recreated when the parent's `body` runs again.
- **Is `@ObservedObject` with a default value ever right?** No. If the view creates the object, it owns it, so use `@StateObject`.

### Q131. `@State` initialized from an input `[Senior]`
```swift
struct Greeting: View {
    @State private var name: String
    init(name: String) { _name = State(initialValue: name) }
    var body: some View { Text("Hello, \(name)") }
}

// The parent shows Greeting(name: selectedUser.name), then selectedUser changes from "Ana" to "Ben"
```
**Answer:** It still shows `Hello, Ana`.

**Why:** `@State` uses the starting value only the first time. After that, SwiftUI keeps its own copy and ignores new values. Fix: use a plain `let name: String`, a binding, or `.id(selectedUser.id)`.

**Follow-ups:**
- **Which fix would you pick here?** A plain `let`, because `Greeting` never changes the name.
- **When is `.id(selectedUser.id)` better?** When the view has other local state that should also reset for a new user.

### Q132. How often does `init` run? `[Senior]`
```swift
struct Row: View {
    let title: String
    init(title: String) {
        self.title = title
        print("Row init")
    }
    var body: some View { Text(title) }
}
// Row is inside a parent whose body re-runs every second because of a @State timer.
```
**Answer:** `Row init` prints every second.

**Why:** Every time the parent's `body` runs, it creates a new `Row` struct. So a view's `init` must stay cheap.

**Follow-ups:**
- **Does `Row`'s `body` also run every second?** Not necessarily. If `title` didn't change, SwiftUI can skip it.
- **How do you stop `Row` from being recreated?** Move the timer into its own small view, so the parent's `body` stops re-running.

### Q133. Animation placement `[Lead/Expert]`
```swift
Circle()
    .fill(isOn ? .green : .red)
    .animation(.easeInOut, value: isOn)
    .scaleEffect(isOn ? 1.5 : 1.0)
```
**Question:** When `isOn` changes (without `withAnimation`), what animates?

**Answer:** The color animates, but the size jumps.

**Why:** `.animation` only affects the modifiers **above** it. `.scaleEffect` is **below** it, so it isn't animated.

**Follow-ups:**
- **How do you animate both?** Move `.animation(...)` below `.scaleEffect`, or change `isOn` inside `withAnimation`.
- **What if you also use `withAnimation(.spring)`?** Both animate. The color uses `.easeInOut` (the closer modifier wins), the size uses the spring.

### Q134. Localization surprise `[Senior]`
```swift
let key = "welcome_message"
Text("welcome_message")   // A
Text(key)                 // B
```
**Answer:** A is translated. B shows the raw text `welcome_message`.

**Why:** A string written directly in `Text("...")` is looked up for translation. A `String` variable is shown as-is.

**Follow-ups:**
- **How do you translate B?** `Text(LocalizedStringKey(key))`, or create the string with `String(localized:)`.
- **How do you show text that must never be translated?** `Text(verbatim: "welcome_message")`.

### Q135. Binding to an `@Observable` property `[Senior]`
```swift
@Observable final class Profile { var name = "" }

struct Editor: View {
    let profile: Profile
    var body: some View {
        TextField("Name", text: $profile.name)
    }
}
```
**Answer:** It doesn't compile.

**Why:** A plain property has no `$` version. Fix: declare it as `@Bindable var profile: Profile`.

**Follow-ups:**
- **Would it work if the view only showed `profile.name`?** Yes. A plain property is enough for reading.
- **What if `Editor` owned the profile?** Use `@State private var profile = Profile()`. Then `$profile.name` works.

### Q136. Duplicate IDs `[Senior]`
```swift
let tags = ["swift", "ios", "swift"]
ForEach(tags, id: \.self) { Text($0) }
```
**Answer:** Unpredictable behavior.

**Why:** Two rows have the same ID, `"swift"`, so SwiftUI can't tell them apart. It logs a warning, and rows may show or update incorrectly.

**Follow-ups:**
- **How do you fix it if duplicates are real data?** Wrap each tag in an `Identifiable` struct with its own unique ID.
- **Would using the indices fix it?** It removes duplicate IDs, but index IDs break animations and state when the array changes.

### Q137. `onChange` on first appearance `[Fundamental]`
```swift
Text(filter)
    .onChange(of: filter) { print("changed") }
```
**Question:** Does it print when the view first appears?

**Answer:** No.

**Why:** `onChange` only runs when the value **changes** after the view appears. Add `initial: true` to also run it on appear.

**Follow-ups:**
- **Does it run if `filter` is set to the same value again?** No. The value must actually be different.
- **How do you get the old and new values?** `.onChange(of: filter) { oldValue, newValue in ... }`.

### Q138. `.task` and navigation `[Senior]`
```swift
List(model.items) { item in NavigationLink(item.name, value: item) }
    .task { await model.load() }
```
**Question:** The user opens a detail screen, then goes back. What happens?

**Answer:** `load()` runs again.

**Why:** `.task` runs every time the view appears, and coming back counts as appearing. Fix: use a "load if needed" check, or `.task(id:)` with a meaningful value.

**Follow-ups:**
- **Is the first load cancelled when the detail screen opens?** It can be, because the list disappears. Handle `CancellationError` quietly.
- **When is reloading on return actually wanted?** When the detail screen can change the data, like editing an item.

### Q139. `GeometryReader` in a stack `[Senior]`
```swift
VStack {
    GeometryReader { proxy in
        Text("Width: \(proxy.size.width)")
    }
    Text("Footer")
}
```
**Answer:** The first text is in the top-left corner, and the footer is pushed to the bottom of the screen.

**Why:** `GeometryReader` takes all the space it can get and puts its content in the top-left corner. Fix: limit it with `.frame(height:)`, or use `onGeometryChange`.

**Follow-ups:**
- **How do you center the text inside the reader?** Add `.frame(maxWidth: .infinity, maxHeight: .infinity)` to the text.
- **How do you read the width without changing the layout?** `onGeometryChange`, or a `GeometryReader` inside `.background`.

### Q140. Fine-grained observation `[Lead/Expert]`
```swift
@Observable final class Cart {
    var items: [Item] = []
    var couponCode = ""
}

struct CartBadge: View {
    let cart: Cart
    var body: some View { Text("\(cart.items.count)") }
}
```
**Question:** Does `CartBadge` update when `couponCode` changes?

**Answer:** No.

**Why:** `CartBadge` only reads `items`, and `@Observable` only updates views that read the changed property. With `ObservableObject`, it **would** update.

**Follow-ups:**
- **Does it update when an item is added?** Yes, because it reads `items`.
- **What if it read `couponCode` only inside a button action?** Still no. Only reads in `body` count.

## 22. Senior / Lead Scenario Questions

> These have no single correct answer. Interviewers look at how you think and explain trade-offs. Give the short answer first, then the steps.

### Q141. A SwiftUI screen feels sluggish. Walk through how you'd fix it. `[Lead/Expert]`
I **measure first, then fix the biggest cause, then measure again**.

1. **Measure:** Release build, older real device, SwiftUI instrument and Time Profiler.
2. **Find the cause:** `Self._printChanges()` shows which views update too often.
3. **Fix:** split big views, pass less data to each view, move to `@Observable`, use stable IDs, move work out of `body`.
4. **Measure again**, and add a check so it doesn't come back.

```swift
// Before: one big view reads the whole store, and each row gets the store too
struct FeedScreen: View {
    @ObservedObject var store: FeedStore
    var body: some View {
        let _ = Self._printChanges()          // step 2: find out why it updates
        List(store.posts) { PostRow(post: $0, store: store) }
    }
}

// After: each row gets only what it shows
List(store.posts) { PostRow(title: $0.title, likes: $0.likes) }
```

**Follow-ups:**
- **Why test on an older device?** Slowness that you can't see on a new iPhone is obvious on old hardware.
- **What do you look for in the SwiftUI instrument?** Views that update very often, or take long to update.
- **How do you stop it from coming back?** Performance tests or monitoring, and checking performance in code review.

### Q142. Should a new app in 2026 be SwiftUI-first or UIKit-first? `[Lead/Expert]`
**SwiftUI-first, with UIKit where needed**, because most new Apple features (Observation, widgets, visionOS, Liquid Glass) are built around SwiftUI.

- **Things that can change the answer:** the minimum iOS version, the team's experience, very custom or performance-critical screens, and existing UIKit code worth reusing.
- Plan for clean SwiftUI–UIKit bridges from day one.

```swift
// A SwiftUI app, with one UIKit screen where it makes sense
@main
struct ShopApp: App {
    var body: some Scene {
        WindowGroup {
            TabView {
                Tab("Home", systemImage: "house") { HomeView() }        // SwiftUI
                Tab("Scan", systemImage: "barcode") { ScannerView() }   // UIKit, wrapped
            }

}
```

**Follow-ups:**
- **What minimum iOS version makes SwiftUI-first easy?** iOS 17 or later, because Observation and newer scroll and navigation tools fill many old gaps.
- **When would you still choose UIKit-first?** A UIKit-expert team building very custom, performance-critical UI on an old iOS version.
- **How do you share design between SwiftUI and UIKit?** A shared design-token package that both can use.

### Q143. Design the navigation for a large app with tabs, deep links, and authentication. `[Lead/Expert]`
A **root view** shows **login or the main app** based on the session. Inside the main app, **each tab has its own `NavigationStack` and router**, and **one deep link handler** turns a URL into "which tab + which screens."

- The deep link handler: picks the tab, closes open sheets, sets the path.
- If the user isn't logged in, it saves the link and opens it after login.

```swift
struct RootView: View {
    @Environment(Session.self) private var session
    @State private var appRouter = AppRouter()   // selected tab + one router per tab

    var body: some View {
        Group {
            if session.isLoggedIn { MainTabView() } else { LoginView() }
        }
        .environment(appRouter)
        .onOpenURL { appRouter.handle($0, isLoggedIn: session.isLoggedIn) }
    }
}
```

**Follow-ups:**
- **What happens to a deep link while logged out?** It's saved, then opened after login.
- **How are sheets handled?** `sheet(item:)` bound to an enum of sheets in the router.
- **How do you test it?** Unit test `AppRouter.handle` with URLs, and check the selected tab and paths.

### Q144. How would you choose a state management approach for a team of 10 engineers? `[Lead/Expert]`
I **compare a few options on clear criteria, try the best ones on a real feature, then write down the decision** and give the team templates.

1. **Options:** `@Observable` models (with view models where needed), TCA, or a small custom store.
2. **Criteria:** app complexity, team experience, testing, minimum iOS version, how fast new people learn it.
3. **Try it:** a short spike (a small time-boxed trial) on one real feature.
4. **Decide and document:** an ADR (Architecture Decision Record) plus templates.

```swift
// Template every new screen follows
@MainActor @Observable
final class <#Feature#>ViewModel {
    enum State { case idle, loading, loaded(<#Value#>), failed(String) }
    private(set) var state: State = .idle
    private let service: <#Service#>
    init(service: <#Service#>) { self.service = service }
}
```

**Follow-ups:**
- **What do you measure in the spike?** Readability, how easy it is to test, build times, and how fast a new person understands it.
- **How do you handle disagreement?** Decide with data from the spike, write it down, and agree to review it later.
- **How do you keep everyone consistent afterward?** Xcode templates, example code, and a code review checklist.

### Q145. Your app supports iOS 16, but you want Observation and new APIs. What's your plan? `[Lead/Expert]`
First **check the data** on how many users are still on iOS 16. If it must stay, **keep `ObservableObject`** for now, put iOS 17 features behind `#available`, and **set a date** to raise the minimum and migrate.

- Avoid running two architectures (`ObservableObject` and `@Observable`) side by side for long.
- After raising the minimum, migrate step by step (see Q35).

```swift
if #available(iOS 17, *) {
    ContentUnavailableView("No Results", systemImage: "magnifyingglass")
} else {
    LegacyEmptyStateView(title: "No Results")      // fallback for iOS 16
}
```

**Follow-ups:**
- **Why not keep both model styles?** Double the code, double the bugs, and two patterns for the team to learn.
- **What data convinces the business?** The share of users and revenue on iOS 16, compared with the engineering cost.
- **What do you do on the day you raise the minimum?** Delete the `#available` fallbacks and start the `@Observable` migration.

### Q146. How would you build a design system in SwiftUI? `[Lead/Expert]`
I build a **`DesignSystem` package** with **tokens** (colors, fonts, spacing), **styles** (like `ButtonStyle`), and a **few shared components**, and pass the theme through the **environment**.

- **Tokens:** colors with dark mode, fonts that scale with Dynamic Type, spacing, and corner radii.
- **Prefer styles over many components.** They keep built-in behavior and accessibility.
- **Support it with:** a catalog app, snapshot tests, and DocC documentation.

```swift
public enum DS {
    public enum Spacing { public static let s: CGFloat = 8; public static let m: CGFloat = 16 }
    public enum Font { public static let title = SwiftUI.Font.system(.title2, weight: .semibold) }
}

public extension ButtonStyle where Self == DSPrimaryButtonStyle {
    static var dsPrimary: DSPrimaryButtonStyle { .init() }
}

// Usage in a feature
Button("Continue") {}.buttonStyle(.dsPrimary).padding(DS.Spacing.m)
```

**Follow-ups:**
- **How do you make it accessible?** Scalable fonts, `@ScaledMetric`, good color contrast, and labels built into components.
- **How do teams find components?** A catalog app showing every component and state.
- **How do you support UIKit screens too?** Provide the same tokens as `UIColor` and `UIFont`.

### Q147. How can memory leaks happen in SwiftUI, and how do you find them? `[Senior]`
SwiftUI views (structs) can't leak, but **the classes behind them can**: models with closures that capture `self`, tasks that never end, timers, observers, and Combine subscriptions.

- **Find them:** Xcode's Memory Graph Debugger, Instruments, `deinit` print statements, and tests that check an object is freed.
- **Prevent them:** start long-running work in `.task`, because it's cancelled when the view disappears.

```swift
@MainActor @Observable
final class ChatModel {
    var messages: [Message] = []

    // ❌ Leaks: the loop never ends, and the task keeps the model alive
    func start() {
        Task {
            for await message in MessageStream.shared.messages {
                messages.append(message)
            }
        }
    }

    // ✅ Let the view control how long it runs
    func listen() async {
        for await message in MessageStream.shared.messages {
            messages.append(message)
        }
    }
}

// In the view: .task { await model.listen() }   // stops when the view disappears
```

**Follow-ups:**
- **Why is `.task` safer than `Task { }` in `onAppear`?** `.task` is cancelled automatically when the view disappears. A manual `Task` keeps running.
- **Would `[weak self]` alone stop that loop?** No. The loop keeps waiting for messages. You must cancel the task.
- **How do you test that a model is freed?** Keep a `weak` reference, remove the strong one, and check the weak one is `nil`.

### Q148. What do you look for when reviewing SwiftUI code? `[Lead/Expert]`
I check **six things**: state ownership, identity, performance, async code, accessibility and localization, and testability.

- **Ownership:** right property wrappers, `@State` is private, no `@ObservedObject var x = X()`.
- **Identity:** stable IDs, no `UUID()` in `body`.
- **Performance:** no heavy work in `body` or `init`, small views, little `AnyView`.
- **Async:** `.task` instead of `onAppear { Task {} }`, cancellation handled, `@MainActor` models.
- **Accessibility and localization:** labels, Dynamic Type, translatable text.
- **Testability:** logic outside views, services passed in, previews for each state.

```swift
// Typical review comments
ForEach(items, id: \.self) { ... }           // ❓ are items unique? prefer Identifiable
@ObservedObject var model = Model()          // ❌ should be @StateObject or @State
.onAppear { Task { await load() } }          // ❌ use .task so it's cancelled automatically
Text(someString)                             // ❓ should this be translated?
```

**Follow-ups:**
- **Which problem is most serious?** Wrong state ownership. It causes lost data and bugs that are hard to reproduce.
- **How do you avoid nitpicking?** Let tools handle formatting. Comment on behavior and design.
- **How do you teach these rules?** A written checklist, good examples in the codebase, and short explanations in comments.

### Q149. How would you explain SwiftUI view identity to a junior engineer? `[Senior]`
I'd use a **theater seat** analogy: if the same person stays in seat 12, SwiftUI just updates them and they keep their memory, but if an `if/else` swaps in a different person, the old one leaves with their memory and the new one starts fresh.

- Then I'd show the counter example (Q129) live and fix it with a ternary.
- Here the interviewer is checking how well you **teach and explain**, not just what you know.

```swift
// "Different person in the seat": state resets
if isHighlighted { CounterView().background(.yellow) } else { CounterView() }

// "Same person, new outfit": state is kept
CounterView().background(isHighlighted ? Color.yellow : .clear)
```

**Follow-ups:**
- **What would you explain next?** `ForEach` IDs and `.id()`, which are seat numbers you assign yourself.
- **How do you check they understood?** Ask them to predict what a new example does before running it.
- **What is the interviewer really testing?** Your ability to explain and mentor.

### Q150. How would you build an offline-first feed screen in SwiftUI? `[Lead/Expert]`
The screen **only reads from the local database** (like SwiftData), and a **sync service updates that database from the server in the background**, so the user always sees saved content, even offline.

- The local database is the single source of truth.
- Show saved data immediately, with a small "syncing" indicator.
- Sync uses cursor pagination, retries with increasing delays, and a rule for conflicts.
- A sync error never deletes the saved content.

```swift
struct FeedView: View {
    @Query(sort: \Post.createdAt, order: .reverse) private var posts: [Post]   // local data only
    @Environment(FeedSync.self) private var sync

    var body: some View {
        List(posts) { PostRow(post: $0) }
            .overlay(alignment: .top) { if sync.isSyncing { ProgressView() } }
            .task { await sync.refresh() }        // saves to SwiftData; the list updates itself
            .refreshable { await sync.refresh() }
    }
}
```

**Follow-ups:**
- **What about changes the user makes offline?** Save them locally in a queue (an "outbox") and send them when the network returns.
- **How do you show that data might be old?** A "last updated" label, or a small banner if the last sync failed.
- **How do you refresh in the background?** Schedule a `BGAppRefreshTask` that runs the same sync code.
