## 1. Fundamentals

### Q1. What is software architecture in the context of an iOS app? `[Fundamental]`
**Key points:**
- The **high-level structure** of the app: how code is divided into components (screens, view models, services, repositories, modules), what each is responsible for, and **how they depend on and communicate with each other**.
- It covers decisions that are **expensive to change later**: UI pattern (MVC, MVVM, TCA), navigation approach, dependency management, data flow, module boundaries, persistence and networking layers.
- Good architecture makes the most common changes (adding a feature, changing a screen, swapping an API) **cheap and safe**.

### Q2. What are the goals of a good iOS architecture? `[Fundamental]`
**Key points:**
- **Separation of concerns**: UI, presentation logic, business rules, and data access live in different places.
- **Testability**: business and presentation logic can be tested without UI or network.
- **Changeability**: features can be added or modified without ripple effects across the codebase.
- **Readability and consistency**: new engineers can find things and follow patterns quickly.
- **Scalability for the team**: multiple engineers or teams can work in parallel without constant conflicts.
- **Performance and reliability** are not sacrificed for abstraction.
- Interview tip: add that architecture should fit the **team size and product stage**. A startup MVP and a 50-engineer banking app need different trade-offs.

### Q3. What are coupling and cohesion? `[Fundamental]`
**Key points:**
- **Coupling**: how much one component depends on the internals of another. **Low coupling** means you can change one without changing the other.
- **Cohesion**: how closely related the responsibilities inside one component are. **High cohesion** means a component does one focused job.
- Goal: **low coupling, high cohesion**. A `ProfileViewController` that parses JSON, caches images, and formats dates has low cohesion; a view model that creates its own `URLSession` is tightly coupled to networking.

### Q4. What layers does a typical iOS app have? `[Fundamental]`
```
┌───────────────────────────────────────────────┐
│ Presentation: Views, ViewControllers,         │  UIKit / SwiftUI
│ ViewModels / Presenters, Coordinators         │
├───────────────────────────────────────────────┤
│ Domain: Entities, Use Cases / Business rules, │  Pure Swift, no frameworks
│ Repository protocols                          │
├───────────────────────────────────────────────┤
│ Data: Repository implementations, API client, │  URLSession, SwiftData,
│ persistence, DTOs and mappers, caches         │  Keychain, SDKs
└───────────────────────────────────────────────┘
       Dependencies point inward (toward Domain)
```
- Small apps may merge Domain into the data or presentation layer; large apps often add explicit domain and feature modules.

### Q5. What does bad architecture cost a team? `[Senior]`
**Key points:**
- Slower feature delivery as every change touches many files; frequent regressions.
- Low test coverage because logic is tangled with UI and networking.
- Merge conflicts and long build times in large monolithic targets.
- Hard onboarding: "only Alex understands checkout."
- Fear of refactoring, leading to more accumulated tech debt.
- Lead-level framing: architecture is an **economic decision**; it trades upfront structure for lower long-term cost of change.

### Q6. Is there a "best" iOS architecture? `[Senior]`
**Key points:**
- No. Each pattern optimizes for different things: MVC for simplicity, MVVM for testable presentation logic, VIPER/Clean for strict separation in large teams, TCA for predictable state and exhaustive testing.
- The right choice depends on **team size and experience, app complexity, UI framework (UIKit vs SwiftUI), testing goals, and expected lifespan**.
- Consistency across the codebase often matters more than which pattern you chose.

### Q7. What is the difference between architecture, design patterns, and frameworks? `[Fundamental]`
| Term | Scope | Examples |
|---|---|---|
| Architecture | Overall structure of the app | Layered/Clean architecture, MVVM + Coordinators, modular features |
| Architectural (UI) pattern | How a screen's code is organized | MVC, MVVM, MVP, VIPER, TCA |
| Design pattern | Reusable solution to a local problem | Delegate, Observer, Factory, Strategy, Decorator |
| Framework | Library you build on | UIKit, SwiftUI, SwiftData, TCA (library) |

### Q8. How do Swift language features shape iOS architecture? `[Senior]`
**Key points:**
- **Value types** make state immutable and easy to reason about (state structs, Sendable models).
- **Protocols and generics** enable dependency inversion and test doubles without class hierarchies.
- **Enums with associated values** model states and routes precisely ("make impossible states impossible").
- **async/await and actors** define clear concurrency boundaries between layers.
- **Observation (`@Observable`)** and SwiftUI favor lighter presentation layers.
- **Swift packages and access control** (`public`, `package`, `internal`) enforce module boundaries at compile time.
- **Macros** reduce boilerplate (e.g. `@Observable`, `@Reducer`, dependency macros).

## 2. Design Principles (SOLID & Friends)

### Q9. What is SOLID? `[Fundamental]`
| Principle | Meaning |
|---|---|
| **S**ingle Responsibility | A type should have one reason to change |
| **O**pen/Closed | Open for extension, closed for modification |
| **L**iskov Substitution | Subtypes/conformers must be usable wherever the base type is expected |
| **I**nterface Segregation | Prefer small, focused protocols over large ones |
| **D**ependency Inversion | Depend on abstractions, not concrete implementations |

### Q10. Explain the Single Responsibility Principle with an iOS example. `[Fundamental]`
```swift
// ❌ One type, many reasons to change: networking, parsing, caching, formatting, UI
final class ProfileViewController: UIViewController {
    func loadProfile() {
        URLSession.shared.dataTask(with: profileURL) { data, _, _ in
            let json = try? JSONSerialization.jsonObject(with: data ?? Data())
            // parse, cache to UserDefaults, format dates, update labels...
        }.resume()
    }
}

// ✅ Each type has one job
protocol ProfileRepository { func profile() async throws -> Profile }   // data access
struct ProfileFormatter { func joinedText(for date: Date) -> String { ... } }  // formatting
@MainActor final class ProfileViewModel { ... }                          // presentation state
final class ProfileViewController: UIViewController { ... }             // rendering + user input
```
- Senior nuance: "one reason to change" means one **stakeholder or concern**, not "one method." Over-splitting creates fragmentation.

### Q11. Explain the Open/Closed Principle. `[Senior]`
```swift
// ❌ Every new payment method requires editing this function
enum PaymentMethod { case card, applePay, paypal }

func fee(for method: PaymentMethod, amount: Decimal) -> Decimal {
    switch method {
    case .card: amount * 0.029
    case .applePay: amount * 0.025
    case .paypal: amount * 0.034
    }
}

// ✅ New methods are added by adding new types, without modifying existing code
protocol PaymentProcessor {
    var id: String { get }
    func fee(for amount: Decimal) -> Decimal
    func pay(_ amount: Decimal) async throws -> Receipt
}

struct CardProcessor: PaymentProcessor { /* ... */ }
struct ApplePayProcessor: PaymentProcessor { /* ... */ }
```
- Senior nuance: for a **closed, stable** set of cases, an enum with a `switch` is often better (exhaustive checking). Use protocols when the set is **open** (plugins, third parties, frequently added cases).

### Q12. Explain the Liskov Substitution Principle. `[Senior]`
```swift
protocol KeyValueStore {
    func value(for key: String) -> String?
    func set(_ value: String, for key: String)
}

// ❌ Violates LSP: code that accepts any KeyValueStore will crash with this one
struct BundledDefaultsStore: KeyValueStore {
    func value(for key: String) -> String? { /* read from bundle */ nil }
    func set(_ value: String, for key: String) { fatalError("Read-only store") }
}

// ✅ Model capabilities honestly
protocol ReadableStore { func value(for key: String) -> String? }
protocol WritableStore: ReadableStore { func set(_ value: String, for key: String) }

struct BundledDefaults: ReadableStore { /* ... */ }
struct UserDefaultsStore: WritableStore { /* ... */ }
```

### Q13. Explain the Interface Segregation Principle. `[Fundamental]`
```swift
// ❌ A fat protocol: every conformer and mock must implement everything
protocol UserService {
    func login(email: String, password: String) async throws -> User
    func logout() async
    func fetchProfile() async throws -> Profile
    func updateAvatar(_ image: Data) async throws
    func deleteAccount() async throws
    func fetchFriends() async throws -> [User]
}

// ✅ Small, focused protocols; types depend only on what they use
protocol Authenticating {
    func login(email: String, password: String) async throws -> User
    func logout() async
}

protocol ProfileProviding {
    func fetchProfile() async throws -> Profile
}

// A login screen depends on Authenticating only, so its test mock is tiny
```

### Q14. Explain the Dependency Inversion Principle. `[Fundamental]`
```swift
// ❌ High-level policy depends on a low-level detail
@MainActor
final class OrdersViewModel {
    private let api = URLSessionOrdersAPI()          // concrete, hidden, untestable
}

// ✅ Both depend on an abstraction owned by the high-level layer
protocol OrdersLoading: Sendable {
    func loadOrders() async throws -> [Order]
}

@MainActor
final class OrdersViewModelFixed {
    private let loader: OrdersLoading
    init(loader: OrdersLoading) { self.loader = loader }
}

struct RemoteOrdersLoader: OrdersLoading {          // detail implements the abstraction
    let client: APIClient
    func loadOrders() async throws -> [Order] { try await client.send(.orders) }
}
```
- Key insight: the **abstraction belongs to the consumer** (domain/presentation layer), not to the networking layer.

### Q15. What does "composition over inheritance" mean in iOS? `[Senior]`
**Key points:**
- Build behavior by combining small objects or protocols rather than deep class hierarchies (e.g. `BaseViewController` with loading, analytics, keyboard handling, and error alerts all baked in).
- Problems with base classes: every subclass inherits everything, changes ripple to all screens, and you can't mix behaviors flexibly.
- Alternatives: child view controllers, protocol extensions, helper objects, view modifiers (SwiftUI), and dependency injection.

```swift
// ❌ class BaseViewController: UIViewController { showLoading(), trackScreen(), handleKeyboard(), showError() }

// ✅ Compose focused helpers
@MainActor
protocol ErrorPresenting: UIViewController {}

extension ErrorPresenting {
    func presentError(_ message: String) {
        let alert = UIAlertController(title: "Error", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default))
        present(alert, animated: true)
    }
}

final class CheckoutViewController: UIViewController, ErrorPresenting {
    private let keyboardHandler = KeyboardInsetHandler()     // composed helper object
}
```

### Q16. How do DRY, KISS, and YAGNI apply, and when do they conflict? `[Senior]`
**Key points:**
- **DRY** (Don't Repeat Yourself): avoid duplicating *knowledge* (business rules, constants).
- **KISS** (Keep It Simple): prefer the simplest design that works.
- **YAGNI** (You Aren't Gonna Need It): don't build abstractions for hypothetical future needs.
- Conflict: aggressive DRY creates premature shared abstractions that couple unrelated features. Two screens that look similar today may diverge tomorrow. A common heuristic is the **rule of three**: abstract after the third real duplication.

### Q17. What is the Law of Demeter? `[Senior]`
```swift
// ❌ Reaching through several objects couples the caller to the whole chain
let city = order.customer.shippingAddress.city

// ✅ Ask the nearest object for what you need
extension Order {
    var shippingCity: String { customer.shippingAddress.city }
}
let city2 = order.shippingCity
```
- "Talk only to your immediate friends." It reduces coupling to object graph structure. Don't apply it dogmatically to plain data structs.

### Q18. When do protocols help architecture, and when do they hurt? `[Lead/Expert]`
**Key points:**
- **Help**: at real boundaries (networking, persistence, analytics, third-party SDKs, platform APIs), for test doubles, and for multiple genuine implementations.
- **Hurt**: "a protocol for every class" with a single implementation forever adds indirection, slows navigation in Xcode, and makes refactoring harder without benefit.
- Alternatives for testability without protocols: closure-based dependencies (Q120), injecting values instead of services, or testing through real lightweight implementations (fakes).

### Q19. Why are value types important in architecture? `[Senior]`
**Key points:**
- Immutable state structs prevent accidental shared mutation between screens or threads.
- Models passed between layers as value types are automatically `Sendable`, simplifying Swift 6 concurrency.
- State snapshots are easy to compare (`Equatable`), log, persist, and test.
- Reference types are reserved for **identity and lifecycle**: view models, services, coordinators, actors.

### Q20. What is Command-Query Separation (CQS)? `[Senior]`
**Key points:**
- A method should either **change state** (command) or **return data** (query), not both.
- Makes code easier to reason about and test: queries are safe to call anytime; commands are explicit.

```swift
// ❌ Query with a hidden side effect
func nextItem() -> Item? { currentIndex += 1; return items[safe: currentIndex] }

// ✅ Separate command and query
func advance() { currentIndex += 1 }          // command
var currentItem: Item? { items[safe: currentIndex] }   // query
```
- Pragmatic exceptions exist (e.g. `popLast()`, `insert` returning a result), but follow it by default in domain code.

## 3. MVC

### Q21. What is Apple's MVC? `[Fundamental]`
**Key points:**
- **Model**: data and business logic.
- **View**: displays data, forwards user actions (`UIView`s).
- **Controller**: mediates between model and view (`UIViewController`).
- In UIKit, the view controller is tightly bound to its view (it owns the view lifecycle), so in practice "view" and "controller" merge into one large class.

```
User action → View → Controller → Model
                     Controller ← Model (notifications/KVO/callbacks)
              View ← Controller (updates UI)
```

### Q22. Why does MVC often become "Massive View Controller"? `[Fundamental]`
**Key points:**
- The view controller is the default place for everything: networking, persistence, formatting, validation, navigation, table view data sources and delegates, keyboard handling, analytics.
- There's no built-in place for presentation logic, so it ends up in the controller, making it hard to test (requires UIKit) and hard to reuse.

### Q23. How do you do MVC well and avoid massive view controllers? `[Senior]`
**Key points:**
- **Custom root views** (`loadView`) for layout code.
- **Child view controllers** for distinct screen regions.
- **Separate data source and delegate objects** for tables and collections.
- **Model controllers / services** for networking, persistence, and business rules (injected).
- **Formatter types** for presentation transformations.
- **Coordinators** for navigation.
- Done well, "MVC + services + coordinators" is a perfectly valid architecture for small and medium apps.

### Q24. When is plain MVC a reasonable choice? `[Senior]`
**Key points:**
- Small apps, prototypes, internal tools, or simple screens with little logic.
- Teams new to iOS (lowest learning curve, Apple's samples).
- When screens are mostly static or thin wrappers around system components.
- Senior answer: "I'd start simple and introduce view models where presentation logic becomes complex enough to need tests."

### Q25. Does MVC apply to SwiftUI? `[Senior]`
**Key points:**
- Not directly. SwiftUI has no controller layer: views are value types that declare UI as a function of state, and SwiftUI handles updates.
- SwiftUI apps typically use views + observable models (often called "MV"), MVVM with `@Observable` view models, or unidirectional architectures like TCA (Sections 8–9).

## 4. MVVM

### Q26. What is MVVM? `[Fundamental]`
**Key points:**
- **Model**: domain data and business logic (often via services/repositories).
- **View**: UI (view controller + views in UIKit, SwiftUI views). Renders state and forwards user intents.
- **ViewModel**: presentation logic. Transforms models into display-ready state, handles user intents, coordinates async work, and exposes state for the view to bind to.
- The view model **doesn't know about the view** (no references to `UIView`/`UIViewController`), so it can be unit-tested without UI.

```
View ──(user intents)──▶ ViewModel ──(calls)──▶ Services / Repositories
View ◀──(state binding)── ViewModel ◀──(data)──
```

### Q27. What belongs in the view vs the view model vs the model? `[Senior]`
| View | ViewModel | Model / Services |
|---|---|---|
| Layout, styling, animations | Screen state (loading, content, error) | Entities, business rules |
| Forwarding user actions | Handling intents (`refresh()`, `submit()`) | Networking, persistence |
| Rendering state | Formatting for display (dates, prices) | Validation rules shared across screens |
| Platform APIs tied to UI (keyboard, haptics) | Input validation for this screen | Caching, sync |
| | Emitting navigation events | |

### Q28. Show MVVM in UIKit. `[Senior]`
```swift
@MainActor
final class LoginViewModel {
    struct State: Equatable {
        var email = ""
        var password = ""
        var isLoading = false
        var errorMessage: String?

        var isLoginEnabled: Bool {
            email.contains("@") && password.count >= 8 && !isLoading
        }
    }

    private(set) var state = State() {
        didSet { onStateChange?(state) }
    }

    var onStateChange: ((State) -> Void)?
    var onLoginSuccess: ((User) -> Void)?       // navigation event, handled by a coordinator

    private let authService: Authenticating

    init(authService: Authenticating) {
        self.authService = authService
    }

    func emailChanged(_ email: String) { state.email = email }
    func passwordChanged(_ password: String) { state.password = password }

    func loginTapped() async {
        guard state.isLoginEnabled else { return }
        state.isLoading = true
        state.errorMessage = nil
        defer { state.isLoading = false }

        do {
            let user = try await authService.login(email: state.email, password: state.password)
            onLoginSuccess?(user)
        } catch {
            state.errorMessage = "Login failed. Please check your email and password."
        }
    }
}

final class LoginViewController: UIViewController {
    private let viewModel: LoginViewModel
    private let emailField = UITextField()
    private let passwordField = UITextField()
    private let loginButton = UIButton(configuration: .filled())
    private let errorLabel = UILabel()

    init(viewModel: LoginViewModel) {
        self.viewModel = viewModel
        super.init(nibName: nil, bundle: nil)
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() {
        super.viewDidLoad()
        // Inputs: forward user intents
        emailField.addAction(UIAction { [weak self] _ in
            self?.viewModel.emailChanged(self?.emailField.text ?? "")
        }, for: .editingChanged)
        passwordField.addAction(UIAction { [weak self] _ in
            self?.viewModel.passwordChanged(self?.passwordField.text ?? "")
        }, for: .editingChanged)
        loginButton.addAction(UIAction { [weak self] _ in
            Task { await self?.viewModel.loginTapped() }
        }, for: .touchUpInside)

        // Output: render state
        viewModel.onStateChange = { [weak self] in self?.render($0) }
        render(viewModel.state)
    }

    private func render(_ state: LoginViewModel.State) {
        loginButton.isEnabled = state.isLoginEnabled
        loginButton.configuration?.showsActivityIndicator = state.isLoading
        errorLabel.text = state.errorMessage
        errorLabel.isHidden = state.errorMessage == nil
    }
}
```
- A single `State` struct plus one `render(_:)` method keeps the UI consistent with state (similar to how SwiftUI works).

### Q29. What are the options for binding a view model to a view? `[Senior]`
| Approach | Pros | Cons |
|---|---|---|
| Closures (`onStateChange`) | Simple, no dependencies | Manual wiring; one listener |
| Delegate protocol | Explicit, familiar | Boilerplate |
| Combine (`@Published`, publishers) | Powerful operators | Learning curve; Swift 6 friction |
| Observation (`@Observable`) | Automatic in SwiftUI; automatic in UIKit with iOS 18 (opt-in) / iOS 26 (default) tracking | Requires recent OS for UIKit tracking |
| `AsyncStream` of states | Swift Concurrency native | Single consumer; manual lifecycle |

- Senior answer: pick **one** approach per codebase and document it.

### Q30. Show MVVM in SwiftUI. `[Fundamental]`
```swift
@MainActor
@Observable
final class ProductListViewModel {
    enum State { case loading, loaded([Product]), empty, failed(String) }

    private(set) var state: State = .loading
    private let repository: ProductRepository

    init(repository: ProductRepository) { self.repository = repository }

    func load() async {
        state = .loading
        do {
            let products = try await repository.products()
            state = products.isEmpty ? .empty : .loaded(products)
        } catch {
            state = .failed("Couldn't load products.")
        }
    }
}

struct ProductListView: View {
    @State var viewModel: ProductListViewModel

    var body: some View {
        Group {
            switch viewModel.state {
            case .loading: ProgressView()
            case .empty: ContentUnavailableView("No Products", systemImage: "bag")
            case .loaded(let products): List(products) { Text($0.name) }
            case .failed(let message): Text(message)
            }
        }
        .task { await viewModel.load() }
    }
}
```

### Q31. What is the Input/Output view model pattern? `[Lead/Expert]`
**Key points:**
- The view model exposes a pure `transform(input) -> output` function (popular in RxSwift/Combine codebases). All inputs are streams; all outputs are streams. This makes data flow explicit and easy to test.

```swift
import Combine

final class MovieSearchViewModel {
    struct Input {
        let query: AnyPublisher<String, Never>
        let selection: AnyPublisher<Int, Never>          // tapped row index
    }

    struct Output {
        let results: AnyPublisher<[Movie], Never>
        let selectedMovie: AnyPublisher<Movie, Never>    // navigation event
    }

    private let api: MovieAPI

    init(api: MovieAPI) { self.api = api }

    func transform(_ input: Input) -> Output {
        let results = input.query
            .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { [api] query in api.search(query).replaceError(with: []) }
            .switchToLatest()
            .share()                                     // two subscribers below
            .eraseToAnyPublisher()

        let selectedMovie = results
            .map { movies in
                input.selection.compactMap { movies.indices.contains($0) ? movies[$0] : nil }
            }
            .switchToLatest()
            .eraseToAnyPublisher()

        return Output(results: results, selectedMovie: selectedMovie)
    }
}
```
- Trade-off: very explicit and testable, but verbose and harder for newcomers than a simple state-based view model.

### Q32. Should a view model import UIKit or SwiftUI? `[Senior]`
**Key points:**
- Ideally **no**: it should depend only on Foundation and domain types, so it's portable (iOS, macOS, widgets) and testable without UI frameworks.
- Expose display-ready **values** (strings, booleans, enums, `URL`s) rather than `UIColor`, `UIImage`, or `View`s. Let the view map semantic values to visuals.
- Pragmatic exceptions: `Observation` is fine (not UI-specific); some teams accept SwiftUI types like `LocalizedStringKey` in SwiftUI-only view models.

```swift
// ❌ View model decides visuals
var statusColor: UIColor { order.isLate ? .systemRed : .systemGreen }

// ✅ View model exposes meaning; the view decides visuals
enum OrderStatusStyle { case onTime, late }
var statusStyle: OrderStatusStyle { order.isLate ? .late : .onTime }
```

### Q33. Who handles navigation in MVVM? `[Senior]`
**Key points:**
- Not the view model directly (it shouldn't hold `UINavigationController` or present views).
- The view model **emits navigation intents** (closures, a route enum, an event stream); a **coordinator/router** (UIKit) or a **router object / navigation state** (SwiftUI) performs the navigation.

```swift
@MainActor
final class ProductDetailViewModel {
    enum Route { case cart, review(productID: String), share(URL) }
    var onRoute: ((Route) -> Void)?

    func addToCartTapped() async {
        try? await cart.add(product)
        onRoute?(.cart)                   // the coordinator decides how to show the cart
    }
}
```

### Q34. How do you avoid "massive view models"? `[Senior]`
**Key points:**
- Move business rules into **domain services / use cases** shared across screens.
- Extract **formatters** and **validators** into small types.
- Split complex screens into **child view models** per section (header, list, filters).
- Keep the view model focused on **screen state and intents**; it orchestrates but doesn't implement everything.
- Watch for signals: > ~400 lines, many dependencies (> 5–6), unrelated state properties.

### Q35. What are the pros and cons of MVVM? `[Senior]`
| Pros | Cons |
|---|---|
| Presentation logic testable without UI | Binding boilerplate in UIKit |
| Clear separation of view and logic | Can become a "massive view model" |
| Natural fit for SwiftUI and Observation | No standard for navigation; needs coordinators/routers |
| Familiar to most iOS engineers | Some argue it duplicates state in SwiftUI |
| Reusable logic across platforms | Inconsistent implementations across teams without guidelines |

## 5. MVP

### Q36. What is MVP? Show an example. `[Senior]`
**Key points:**
- **Model**, **View** (passive, implements a view protocol), **Presenter** (holds presentation logic and tells the view exactly what to display through the protocol).
- The presenter holds a **weak reference to the view protocol** and calls imperative methods on it.

```swift
@MainActor
protocol ProductDetailView: AnyObject {
    func display(title: String, price: String)
    func setLoading(_ isLoading: Bool)
    func displayError(_ message: String)
}

@MainActor
final class ProductDetailPresenter {
    private weak var view: ProductDetailView?
    private let productID: String
    private let repository: ProductRepository
    private let priceFormatter: PriceFormatter
```

### Q37. What is the difference between MVP and MVVM? `[Senior]`
| MVP | MVVM |
|---|---|

## 6. VIPER & Clean Swift (VIP)

### Q39. What is VIPER? `[Senior]`
| Component | Responsibility |
|---|---|
| **V**iew | Displays what the presenter tells it; forwards user actions |
| **I**nteractor | Business logic for one use case; talks to services/repositories |
| **P**resenter | Presentation logic; formats data for the view; reacts to view events; asks the router to navigate |
| **E**ntity | Plain data models |
| **R**outer (Wireframe) | Navigation and module assembly |

```
View ⇄ Presenter ⇄ Interactor → Services/Repositories
          ↓
        Router → other modules
```

### Q40. Show a VIPER module skeleton. `[Senior]`
```swift
// Entity
struct Article: Sendable { let id: Int; let title: String }

// Interactor: business logic
protocol ArticleListInteracting: Sendable {
    func fetchArticles() async throws -> [Article]
}

struct ArticleListInteractor: ArticleListInteracting {
    let repository: ArticleRepository
    func fetchArticles() async throws -> [Article] {
        try await repository.articles().filter { !$0.title.isEmpty }
    }
}

// View contract
@MainActor
protocol ArticleListViewProtocol: AnyObject {
    func show(titles: [String])
    func showError(_ message: String)
}

// Router: navigation + assembly
@MainActor
protocol ArticleListRouting {
    func showDetail(for article: Article)
}

@MainActor
final class ArticleListRouter: ArticleListRouting {
    weak var viewController: UIViewController?

    static func makeModule(repository: ArticleRepository) -> UIViewController {
        let view = ArticleListViewController()
        let router = ArticleListRouter()
        let presenter = ArticleListPresenter(
            interactor: ArticleListInteractor(repository: repository),
            router: router
        )
        view.presenter = presenter          // view → presenter (strong)
        presenter.view = view               // presenter → view (weak)
        router.viewController = view        // router → view (weak)
        return view
    }

    func showDetail(for article: Article) {
        viewController?.navigationController?.pushViewController(
            ArticleDetailRouter.makeModule(article: article), animated: true)
    }
}

// Presenter: presentation logic
@MainActor
final class ArticleListPresenter {
    weak var view: ArticleListViewProtocol?
    private let interactor: ArticleListInteracting
    private let router: ArticleListRouting
    private var articles: [Article] = []

    init(interactor: ArticleListInteracting, router: ArticleListRouting) {
        self.interactor = interactor
        self.router = router
    }

    func viewDidLoad() async {
        do {
            articles = try await interactor.fetchArticles()
            view?.show(titles: articles.map(\.title))
        } catch {
            view?.showError("Couldn't load articles.")
        }
    }

    func didSelectRow(at index: Int) {
        router.showDetail(for: articles[index])
    }
}
```
- Ownership is a frequent interview follow-up: the **view** owns the presenter; the presenter owns the interactor and router; back-references (presenter → view, router → view controller) are **weak** to avoid cycles.

### Q41. What are VIPER's pros and cons? When is it appropriate? `[Senior]`
| Pros | Cons |
|---|---|
| Very clear responsibilities; strict separation | Lots of boilerplate (5+ files and many protocols per screen) |
| Highly testable components | Slower development for simple screens |
| Scales to large teams with consistent structure | Over-engineering risk for small apps |
| Navigation separated from presentation | Awkward with SwiftUI |

- Appropriate for large UIKit codebases with many engineers that value strict uniformity, often with code generation templates. Less common in new SwiftUI projects.

### Q42. What is Clean Swift (VIP), and how does it differ from VIPER? `[Lead/Expert]`
**Key points:**
- Clean Swift (VIP cycle): **View → Interactor → Presenter → View**, a **unidirectional** loop. The view controller sends requests to the interactor; the interactor sends responses to the presenter; the presenter sends view models back to the view controller. A **Router** handles navigation and a **Worker** handles reusable business logic.
- Difference: VIPER's presenter sits in the middle and communicates both ways; VIP's flow is a one-way cycle with explicit `Request`/`Response`/`ViewModel` data types per use case.

### Q43. Can VIPER be used with SwiftUI? `[Senior]`
**Key points:**
- It's possible (the presenter becomes an observable object the SwiftUI view reads), but it fights the framework: SwiftUI views are value types without a lifecycle to hold a presenter reference, and navigation is state-driven rather than imperative.
- Most SwiftUI teams use MVVM-style observable models, "MV," or TCA instead.

## 7. Clean Architecture

### Q44. What is Clean Architecture? `[Senior]`
**Key points:**
- Robert C. Martin's concentric-layer architecture with one central rule: **source code dependencies point inward**, toward business rules.
- Layers (inner to outer): **Entities** (enterprise rules) → **Use Cases** (application rules) → **Interface Adapters** (presenters, view models, repository implementations, mappers) → **Frameworks & Drivers** (UIKit, SwiftUI, URLSession, SwiftData, SDKs).
- Inner layers define **protocols** (ports) that outer layers implement, so business logic never imports UI or networking frameworks.

```
        ┌──────────────────────────────────────────┐
        │ Frameworks: UIKit/SwiftUI, URLSession,   │
        │  ┌────────────────────────────────────┐  │
        │  │ Adapters: ViewModels, Repositories │  │
        │  │  ┌──────────────────────────────┐  │  │
        │  │  │ Use Cases                    │  │  │
        │  │  │  ┌────────────────────────┐  │  │  │
        │  │  │  │ Entities               │  │  │  │
        │  │  │  └────────────────────────┘  │  │  │
        │  │  └──────────────────────────────┘  │  │
        │  └────────────────────────────────────┘  │
        └──────────────────────────────────────────┘
                 dependencies point inward →
```

### Q45. Show entities, use cases, and repositories in Swift. `[Senior]`
```swift
// MARK: Domain layer (pure Swift: no UIKit, SwiftUI, URLSession, or SwiftData imports)

struct LineItem: Sendable, Equatable {
    let productID: String
    let quantity: Int
    let unitPrice: Decimal
}

struct Order: Sendable, Equatable {
    let id: UUID
    let items: [LineItem]
    var total: Decimal { items.reduce(0) { $0 + $1.unitPrice * Decimal($1.quantity) } }

}

    func authorize(amount: Decimal) async throws -> PaymentToken
}

// Use case: one application-specific business operation
struct PlaceOrderUseCase: Sendable {
    let orders: OrderRepository
    let payments: PaymentGateway

    func execute(_ order: Order) async throws -> OrderConfirmation {
        guard !order.items.isEmpty else { throw OrderError.emptyCart }
        let token = try await payments.authorize(amount: order.total)
        return try await orders.submit(order, paymentToken: token)
    }
}

// MARK: Data layer (implements domain ports)

struct RemoteOrderRepository: OrderRepository {
    let client: APIClient

    func submit(_ order: Order, paymentToken: PaymentToken) async throws -> OrderConfirmation {
        let request = SubmitOrderRequestDTO(order: order, token: paymentToken.value)
        let response = try await client.send(.submitOrder(request))
        return OrderConfirmation(orderNumber: response.order_number)
    }
}

// MARK: Presentation layer
@MainActor
@Observable
final class CheckoutViewModel {
    private let placeOrder: PlaceOrderUseCase
    init(placeOrder: PlaceOrderUseCase) { self.placeOrder = placeOrder }
    // calls placeOrder.execute(...) and maps results/errors into screen state
}
```

### Q46. Do you always need a use case layer? `[Lead/Expert]`
**Key points:**
- No. Many use cases end up as **pass-throughs** (`GetProductsUseCase` just calls `repository.products()`), adding files and indirection without value.
- Introduce use cases when there's **real business logic**: combining multiple repositories, enforcing rules, orchestrating steps (place order = validate + authorize payment + submit + clear cart), or logic shared by several screens.
- Pragmatic rule: view models may call repositories directly for simple reads; use cases appear where business rules live.

### Q47. Where do DTOs and mapping live? `[Senior]`
**Key points:**
- **DTOs** (Data Transfer Objects) mirror the API/database format and live in the **data layer**.
- The data layer maps DTOs into **domain models** before returning them, so API changes (renamed fields, nested structures) don't leak into business logic or UI.

```swift
// Data layer
struct ProductDTO: Decodable {
    let id: String
    let title: String
    let price_cents: Int
    let image_url: String?
}

// Domain layer
struct Product: Sendable, Identifiable, Equatable {
    let id: String
    let name: String
    let price: Decimal
    let imageURL: URL?
}

// Mapping (data layer)
extension Product {
    init(dto: ProductDTO) {
        self.init(id: dto.id,
                  name: dto.title,
                  price: Decimal(dto.price_cents) / 100,
                  imageURL: dto.image_url.flatMap(URL.init(string:)))
    }
}
```
- Trade-off: mapping code is boilerplate. For small apps, decoding directly into domain models (with `CodingKeys`) can be acceptable.

### Q48. How do Clean Architecture and MVVM fit together? `[Senior]`
**Key points:**
- They operate at different levels: MVVM organizes the **presentation layer**; Clean Architecture organizes the **whole app**.
- Typical combination: **View → ViewModel → UseCase → Repository protocol ← Repository implementation → API/DB**, plus coordinators for navigation.

```
Features/Checkout/
├── Presentation/   CheckoutView, CheckoutViewModel, CheckoutCoordinator
├── Domain/         PlaceOrderUseCase, Order, OrderRepository (protocol)
└── Data/           RemoteOrderRepository, OrderDTOs, mappers
```

### Q49. What is hexagonal architecture (ports and adapters)? `[Lead/Expert]`
**Key points:**
- Similar idea to Clean Architecture: the **core** (domain) defines **ports** (protocols); **adapters** implement them for specific technologies (REST, GraphQL, SwiftData, mock, analytics SDK).
- Emphasizes that the app core should be drivable by many inputs (UI, tests, widgets, App Intents) and connectable to many outputs, without changing core logic.

### Q50. What are the risks of applying Clean Architecture strictly in an iOS app? `[Lead/Expert]`
**Key points:**
- Boilerplate explosion: protocol + implementation + use case + DTO + mapper for every trivial feature.
- Slower iteration, harder navigation through code, and onboarding friction.
- Abstractions guessed upfront may not match real future needs.
- Senior answer: apply the **dependency rule** (domain doesn't depend on frameworks) and keep **boundaries at real seams** (network, persistence, third-party SDKs), but add layers only where they pay for themselves.

## 8. Unidirectional Data Flow, Redux & TCA

### Q51. What is unidirectional data flow? `[Senior]`
**Key points:**
- State flows in **one direction**: the view renders **state**; user events become **actions**; a **reducer** computes new state from (state, action); **effects** perform side work and feed results back as new actions.
- Benefits: a single source of truth, predictable state changes, easy debugging (log every action), and testability (reducers are pure functions).

```
        ┌──────── action ────────┐
        │                        ▼
      View                    Reducer ──▶ Effects (network, timers)
        ▲                        │              │
        └──────── state ◀────────┘◀── action ───┘
```

### Q52. Implement a minimal Redux-style store in Swift. `[Lead/Expert]`
```swift
struct Effect<Action: Sendable>: Sendable {
    let run: @Sendable () async -> Action?
}

@MainActor
@Observable
final class Store<State, Action: Sendable> {
    private(set) var state: State
    private let reduce: (inout State, Action) -> [Effect<Action>]

    init(initialState: State, reduce: @escaping (inout State, Action) -> [Effect<Action>]) {
        self.state = initialState
        self.reduce = reduce
    }

    func send(_ action: Action) {
        let effects = reduce(&state, action)          // pure state transition
        for effect in effects {
            Task {
                if let next = await effect.run() {    // side effect feeds back an action
                    send(next)
                }
            }
        }
    }
}

// Feature definition
struct CounterState { var count = 0; var fact: String?; var isLoading = false }

enum CounterAction: Sendable {
    case increment
    case factRequested
    case factLoaded(String)
}

func counterReducer(api: NumberFactAPI) -> (inout CounterState, CounterAction) -> [Effect<CounterAction>] {
    { state, action in
        switch action {
        case .increment:
            state.count += 1
            return []
        case .factRequested:
            state.isLoading = true
            let number = state.count
            return [Effect { .factLoaded((try? await api.fact(for: number)) ?? "No fact") }]
        case .factLoaded(let fact):
            state.isLoading = false
            state.fact = fact
            return []
        }
    }
}

// let store = Store(initialState: CounterState(), reduce: counterReducer(api: liveAPI))
// Button("+") { store.send(.increment) }
```

### Q53. How are side effects handled in unidirectional architectures? `[Lead/Expert]`
**Key points:**
- Reducers stay **pure** (no network calls, no `Date.now`, no randomness). They return **effect descriptions**; the store runs them and sends resulting actions back.
- Dependencies used by effects (API clients, clocks, UUID generators) are **injected**, so tests can control time, randomness, and responses.
- Effects need identifiers for **cancellation** (e.g. cancel a previous search when a new query arrives).

### Q54. What is The Composable Architecture (TCA)? Show a feature. `[Lead/Expert]`
**Key points:**
- An open-source library by Point-Free implementing unidirectional data flow with **State**, **Action**, **Reducer**, **Effects**, a **Store**, built-in **dependency management**, composition of features, navigation tools, and exhaustive testing.

```swift
import ComposableArchitecture
import SwiftUI

@Reducer
struct CounterFeature {
    @ObservableState
    struct State: Equatable {
        var count = 0
        var fact: String?
        var isLoading = false
    }

    enum Action {
        case incrementTapped
        case factButtonTapped
        case factResponse(String)
    }

    @Dependency(\.numberFact) var numberFact

    var body: some ReducerOf<Self> {
        Reduce { state, action in
            switch action {
            case .incrementTapped:
                state.count += 1
                state.fact = nil
                return .none

            case .factButtonTapped:
                state.isLoading = true
                return .run { [count = state.count] send in
                    let fact = try await numberFact.fetch(count)
                    await send(.factResponse(fact))
                }

            case let .factResponse(fact):
                state.isLoading = false
                state.fact = fact
                return .none
            }
        }
    }
}

struct CounterView: View {
    let store: StoreOf<CounterFeature>

    var body: some View {
        VStack(spacing: 12) {
            Text("\(store.count)").font(.largeTitle)
            Button("Increment") { store.send(.incrementTapped) }
            Button("Get fact") { store.send(.factButtonTapped) }
            if store.isLoading { ProgressView() }
            if let fact = store.fact { Text(fact) }
        }
    }
}
```
(Syntax reflects TCA 1.x; check the current version's documentation.)

### Q55. How do dependencies and testing work in TCA? `[Lead/Expert]`

### Q56. What are TCA's pros and cons? `[Lead/Expert]`
| Pros | Cons |
|---|---|
| Predictable state changes; single source of truth | Steep learning curve |
| Exhaustive, deterministic tests (`TestStore`) | Third-party dependency; major version migrations |
| Feature composition and modularity built in | Boilerplate and verbosity for simple screens |
| First-class dependency injection, navigation, and effect cancellation | Compile-time and performance overhead in very large reducers |
| Strong documentation and community | Team-wide buy-in required; hard to adopt partially without friction |

### Q57. Compare MVVM and TCA. `[Lead/Expert]`
| | MVVM (`@Observable`) | TCA |
|---|---|---|
| State | In view model properties | In a `State` struct |
| Mutations | Methods mutate state directly | Only reducers mutate state, via actions |
| Side effects | `async` methods in the view model | Returned effects run by the store |
| Testing | Call methods, assert state | `TestStore`: exhaustive assertions of state and actions |
| Composition | Manual (child view models) | Built-in (`Scope`, child features) |
| Learning curve | Low | High |
| Dependencies | None beyond Apple frameworks | Library dependency |

- Senior answer: MVVM is a great default; TCA pays off when state is complex and shared, features are deeply composed, and the team values exhaustive testing and is willing to invest in the library.

### Q58. When would you avoid unidirectional architectures? `[Senior]`
**Key points:**
- Small apps or teams without experience, where the ceremony outweighs benefits.
- Very performance-sensitive screens where routing every keystroke through a central store adds overhead (mitigated by scoping state).
- Codebases heavily invested in another pattern, where a partial adoption would create inconsistency.

## 9. SwiftUI-Native Architecture ("MV")

### Q59. What is the "MV" pattern in SwiftUI? `[Senior]`
**Key points:**
- "Model–View": SwiftUI views bind **directly** to observable models (domain stores/services) shared through the environment, without a dedicated view model per screen. Views hold only local UI state (`@State`).
- Rationale: SwiftUI views already behave like view models (they derive UI from state and react to changes), so an extra layer can duplicate state and add boilerplate. Apple's sample code often follows this style.

```swift
@MainActor
@Observable
final class CartStore {                  // app-level model (domain logic + state)
    private(set) var items: [CartItem] = []
    private let api: CartAPI

    init(api: CartAPI) { self.api = api }

    var total: Decimal { items.reduce(0) { $0 + $1.price * Decimal($1.quantity) } }

    func add(_ product: Product) async throws {
        items = try await api.add(productID: product.id)
    }
}

struct CartBadge: View {
    @Environment(CartStore.self) private var cart
    var body: some View { Text("\(cart.items.count)") }
}

struct ProductRow: View {
    @Environment(CartStore.self) private var cart
    @State private var isAdding = false            // local UI state only
    let product: Product

    var body: some View {
        Button(isAdding ? "Adding…" : "Add to cart") {
            Task {
                isAdding = true
                defer { isAdding = false }
                try? await cart.add(product)
            }
        }
        .disabled(isAdding)
    }
}
```

### Q60. Where does business logic go if there's no view model? `[Senior]`
**Key points:**
- In **observable model objects / stores** (e.g. `CartStore`, `SessionStore`) and **services** they use, which are shared across screens and tested directly.
- Screen-specific logic that's simple stays in the view (local `@State`); if a screen's logic grows complex (validation, multi-step forms, coordination of several stores), introduce a dedicated screen model (which is a view model by another name).

### Q61. What are the trade-offs of MV vs MVVM in SwiftUI? `[Lead/Expert]`
| MV (models in environment) | MVVM (view model per screen) |
|---|---|
| Less code, no duplicated state | Clear home for screen logic |
| Shared stores keep data consistent across screens | Screen logic testable in isolation |
| Screen logic can leak into views (hard to test) | Risk of duplicating or syncing state from shared stores |
| Environment dependencies are implicit | Dependencies explicit via init |

- Many teams use a **hybrid**: shared stores for app-wide state plus view models only for complex screens.

### Q62. How do you keep SwiftUI views testable without view models? `[Senior]`
**Key points:**
- Keep views thin: move logic into models/stores and pure functions (formatters, validators) that are unit-tested.
- Use previews for visual states, snapshot tests for layout, and UI tests for critical flows.
- Avoid putting async orchestration in views beyond calling a single model method.

## 10. Navigation Architecture

### Q63. Why decouple navigation from screens? `[Senior]`
**Key points:**
- Screens that push other screens directly know about each other, which creates tight coupling and makes reuse, deep linking, A/B testing flows, and testing difficult.
- Centralizing navigation (coordinators, routers, navigation state) lets screens emit **intents** while a separate component decides **where to go**.

### Q64. How do coordinators pass results back from a flow? `[Lead/Expert]`
**Key points:**
- A flow coordinator exposes a completion callback (or `async` result) to its parent, and the parent removes the child when it finishes. (A basic coordinator implementation is in the UIKit file, Q73.)
- An async/await flow API reads naturally:

```swift
@MainActor
final class AddressPickerFlow: NSObject, UIAdaptivePresentationControllerDelegate {
    private let presenter: UIViewController
    private var continuation: CheckedContinuation<Address?, Never>?

    init(presenter: UIViewController) { self.presenter = presenter }

    /// Presents the picker and returns the chosen address (nil if cancelled)
    func run() async -> Address? {
        await withCheckedContinuation { continuation in
            self.continuation = continuation

            let picker = AddressPickerViewController()
            picker.onComplete = { [weak self] address in
                self?.presenter.dismiss(animated: true)
                self?.finish(with: address)
            }

            let navigation = UINavigationController(rootViewController: picker)
            navigation.presentationController?.delegate = self     // handle swipe-to-dismiss too
            presenter.present(navigation, animated: true)
        }
    }

    func presentationControllerDidDismiss(_ presentationController: UIPresentationController) {
        finish(with: nil)
    }

    private func finish(with address: Address?) {
        continuation?.resume(returning: address)    // resume exactly once
        continuation = nil
    }
}

// Usage in a coordinator
if let address = await AddressPickerFlow(presenter: checkoutViewController).run() {
    checkoutViewModel.setShippingAddress(address)
}
```

### Q65. How do you architect navigation in SwiftUI? `[Senior]`
**Key points:**
- Model navigation as **data**: a router object owning a `NavigationStack` path of typed routes, plus optional sheet/alert state (see the SwiftUI file, Q61).
- One router per tab (each with its own stack); a root view switching between auth and main flows.
- Features expose **routes** (enums) and **destination builders**; the app layer maps routes to views, so features don't import each other.

### Q66. How do you design deep link handling? `[Lead/Expert]`
```swift
enum DeepLink: Equatable {
    case product(id: String)
    case cart
    case order(id: String)
    case settings(section: String?)

    /// myshop://product/42, myshop://order/A1B2, myshop://settings/notifications
    init?(url: URL) {
        guard let components = URLComponents(url: url, resolvingAgainstBaseURL: false) else { return nil }
        let path = components.path.split(separator: "/").map(String.init)

        switch (components.host, path.first) {
        case ("product"?, let id?): self = .product(id: id)
        case ("cart"?, _): self = .cart
        case ("order"?, let id?): self = .order(id: id)
        case ("settings"?, let section): self = .settings(section: section)
        default: return nil
        }
    }
}
```
**Talking points:**
- **Parse at the edge** (scene delegate, `onOpenURL`, push notification handler) into a typed enum; the parser is pure and unit-tested.
- **Route centrally**: the root coordinator/router dismisses modals, selects the tab, and builds the stack.
- **Auth gating**: if login is required, store the pending link, show login, and replay it after success.
- Handle cold start, warm start, universal links, push notifications, widgets, and Spotlight with the **same** `DeepLink` type.

### Q67. Why model navigation state as data? `[Senior]`
**Key points:**
- Navigation becomes **testable without UI** (`#expect(router.homePath == [.product(id: "42")])`), restorable (`Codable` paths), loggable, and controllable from deep links.
- It's natural in SwiftUI (`NavigationStack(path:)`, `sheet(item:)`) and achievable in UIKit with coordinators that rebuild stacks from route arrays.

### Q68. How do you handle authentication-gated navigation? `[Senior]`
**Key points:**
- A root component observes **session state** and shows either the auth flow or the main app.
- Features that require login request it through an abstraction (`AuthGate.requireLogin() async -> Bool`) rather than presenting the login screen themselves.
- On logout, tear down the authenticated flow and its session-scoped dependencies entirely (Q80), so no user data lingers.

### Q69. How do you navigate between features in different modules? `[Lead/Expert]`
**Key points:**
- Feature modules shouldn't import each other. Options:
  - **Interface modules**: `CartInterface` defines `protocol CartFeatureBuilding { func makeCartScreen() -> UIViewController }`; `CatalogFeature` depends only on the interface; the app target injects `CartFeature`'s implementation.
  - **Route enums** owned by a shared navigation module; the app layer maps routes to features.
  - **Closure injection**: a feature exposes `onCheckoutRequested: () -> Void`, and the app wires it.

```swift
// CartInterface module
public protocol CartFeatureBuilding {
    @MainActor func makeCartScreen() -> UIViewController
}

// CatalogFeature module (depends on CartInterface, not CartFeature)
public final class ProductDetailViewController: UIViewController {
    private let cartBuilder: CartFeatureBuilding

    public init(cartBuilder: CartFeatureBuilding) {
        self.cartBuilder = cartBuilder
        super.init(nibName: nil, bundle: nil)
    }

    @available(*, unavailable)
    required init?(coder: NSCoder) { fatalError() }

    private func showCart() {
        navigationController?.pushViewController(cartBuilder.makeCartScreen(), animated: true)
    }
}
```

### Q70. How do you represent one-time navigation events vs state? `[Senior]`
**Key points:**
- **State-based** (SwiftUI-friendly): navigation is a property (`destination: Route?`); setting it navigates, clearing it dismisses. Survives re-renders and is testable.
- **Event-based** (UIKit-friendly): a closure or stream fires once (`onRoute(.cart)`); the coordinator reacts.
- Pitfall: modeling one-time events (show toast, navigate) as plain stored state in UIKit can re-trigger them on re-render; modeling them as fire-and-forget events in SwiftUI can lose them if no view is listening. Choose based on the UI framework.

## 11. Dependency Injection

### Q71. What is dependency injection, and why does it matter? `[Fundamental]`
**Key points:**
- Giving an object its dependencies **from the outside** instead of having it create or look them up itself.
- Benefits: testability (inject mocks), flexibility (swap implementations per environment), explicit dependencies (visible in the initializer), and looser coupling.

```swift
// ❌ Hidden, hard-coded dependencies
@MainActor
final class SettingsViewModel {
    private let api = APIClient.shared
    private let defaults = UserDefaults.standard
}

// ✅ Injected dependencies
@MainActor
final class SettingsViewModelInjected {
    private let api: SettingsAPI
    private let preferences: PreferencesStore

    init(api: SettingsAPI, preferences: PreferencesStore) {
        self.api = api
        self.preferences = preferences
    }
}
```

### Q72. What are the types of dependency injection? `[Fundamental]`
| Type | How | When |
|---|---|---|
| **Constructor injection** | Passed in `init` | Default choice: dependencies are required and immutable |
| **Property injection** | Set after creation (`vc.viewModel = ...`) | Storyboard-created objects, optional dependencies, breaking cycles |
| **Method injection** | Passed to the method that needs it (`func render(using formatter:)`) | Dependency needed only for one operation or varies per call |
| **Ambient / environment** | Read from a context (SwiftUI `@Environment`, task-locals) | Cross-cutting values used deep in a hierarchy |

- Property injection risks forgetting to set the dependency (crash with implicitly unwrapped optionals). Prefer constructor injection whenever you control object creation.

### Q73. What is a composition root? Show one. `[Senior]`
**Key points:**
- The **single place** (usually at app launch) where the object graph is assembled: concrete implementations are created and wired together. The rest of the code only sees abstractions.

```swift
enum AppEnvironment {
    case production, staging, uiTesting
}

@MainActor
```

### Q74. What role do factories play in DI? `[Senior]`
**Key points:**
- Screens are often created later (navigation), with runtime parameters (e.g. a product ID) plus app dependencies. Factories combine both without passing the whole container around.

```swift
@MainActor
protocol CatalogScreenFactory {
    func makeProductList(onSelect: @escaping (Product.ID) -> Void) -> UIViewController
    func makeProductDetail(productID: Product.ID) -> UIViewController
}

@MainActor
```

- Coordinators receive a factory, so they never construct dependencies themselves and can be tested with a fake factory.

### Q75. What is a DI container? What are its pros and cons? `[Senior]`
```swift
@MainActor
final class Container {
    private var factories: [ObjectIdentifier: () -> Any] = [:]

    func register<T>(_ type: T.Type, factory: @escaping () -> T) {
        factories[ObjectIdentifier(type)] = factory
    }

    func resolve<T>(_ type: T.Type = T.self) -> T {
        guard let factory = factories[ObjectIdentifier(type)], let instance = factory() as? T else {
            fatalError("No registration for \(T.self)")          // fails at runtime, not compile time
        }
        return instance
    }
}

// Registration at launch
let container = Container()
container.register(ProductRepository.self) { RemoteProductRepository(client: apiClient) }
let repository: ProductRepository = container.resolve()
```
| Pros | Cons |
|---|---|
| Centralized registration; easy to swap implementations | Missing registrations crash at **runtime** |
| Handles lifetimes (singleton, transient) | Dependencies become implicit if `resolve` is called everywhere |
| Less manual wiring in large graphs | Extra library/abstraction to learn |

- Popular libraries: Swinject (runtime), Factory (property-wrapper based), Point-Free's swift-dependencies (TCA-style), Needle (compile-time safe, code generation).

### Q76. Why is the Service Locator often considered an anti-pattern? `[Senior]`
**Key points:**
- A service locator lets any object fetch dependencies globally (`ServiceLocator.shared.resolve(...)`), so **dependencies are hidden** inside implementation code, not visible in initializers.
- Consequences: unclear what a type needs; tests must configure global state (and can interfere with each other when run in parallel); runtime crashes when something isn't registered.
- Using a container **only at the composition root** (to build objects that receive dependencies via `init`) is fine. Using it **inside** view models and services is the anti-pattern.

```swift
// ❌ Service locator inside business code
final class CheckoutViewModel {
    func pay() async {
        let gateway = Container.shared.resolve(PaymentGateway.self)    // hidden dependency
    }
}

// ✅ Explicit dependency
final class CheckoutViewModelExplicit {
    private let gateway: PaymentGateway
    init(gateway: PaymentGateway) { self.gateway = gateway }
}
```

### Q77. How does dependency injection work in SwiftUI? `[Senior]`
**Key points:**
- **Initializer injection** for direct parent-to-child dependencies (explicit, preferred for view models).
- **Environment** for cross-cutting dependencies (`@Entry var apiClient`, `.environment(store)`), handy for previews and tests but implicit.
- **Composition root** in the `App` struct creates live services and injects them.
- (Code examples: SwiftUI file, Q113–Q114.)

### Q78. Compare compile-time and runtime DI. `[Lead/Expert]`
| Compile-time (manual DI, Needle, factories) | Runtime (containers like Swinject) |
|---|---|
| Missing dependencies are compile errors | Missing registrations crash at runtime |
| More explicit wiring code | Less boilerplate |
| Easy to follow in code | Harder to trace where instances come from |
| Scales with code generation for huge graphs | Flexible (dynamic registration, plugins) |

- Senior default: **manual constructor injection with factories**; adopt a library when the graph becomes painful to wire by hand, preferring compile-time safety.

### Q79. Are default parameter values a valid form of DI? `[Senior]`

**Key points:**
- Yes, as a **lightweight** technique: production call sites stay short, and tests can still inject doubles.

### Q80. How do you manage dependency lifetimes and scopes? `[Lead/Expert]`
**Key points:**
- **App scope**: lives for the app's lifetime (API client, analytics, feature flags, image cache).
- **Session scope**: lives while a user is logged in (user-specific repositories, cart, notification settings). **Recreate on login, discard on logout**, so no data leaks between accounts.
- **Flow/screen scope**: lives for one flow or screen (view models, flow coordinators).

```swift
@MainActor
final class SessionContainer {
    let user: User
    let cart: CartStore
    let orders: OrdersRepository

    init(user: User, app: AppContainer) {
        self.user = user
        self.cart = CartStore(api: CartAPI(client: app.apiClient), userID: user.id)
        self.orders = RemoteOrdersRepository(client: app.apiClient, userID: user.id)
    }
}

@MainActor
@Observable
final class AppSession {
    private(set) var current: SessionContainer?
    private let app: AppContainer

    init(app: AppContainer) { self.app = app }

    func didLogIn(_ user: User) { current = SessionContainer(user: user, app: app) }
    func didLogOut() { current = nil }      // all user-scoped state is released at once
}
```
- Interview follow-up: "What bug does session scoping prevent?" Showing user A's cart or cached orders to user B after logout/login on the same device.

### Q81. How do you avoid initializers with too many dependencies? `[Senior]`
**Key points:**
- Many dependencies (> 5–6) often signal that the type has **too many responsibilities**: split it.
- Group related dependencies into a focused facade or use case (`CheckoutDependencies`/`PlaceOrderUseCase`) rather than passing ten services.
- Avoid passing the entire container ("god dependency"): it hides what's needed.

## 12. Modularization

### Q82. Why modularize an iOS app? `[Senior]`
**Key points:**
- **Build times**: incremental builds recompile only changed modules; parallel compilation.
- **Boundaries**: access control (`public`/`package`/`internal`) enforces architecture at compile time; features can't reach into each other's internals.
- **Ownership**: teams own modules; fewer merge conflicts.
- **Reuse**: share modules between the app, widgets, App Clips, watchOS, and extensions.
- **Faster previews and tests**: small targets build quickly; feature demo apps.
- Cost: more setup, dependency graph management, possible app-size/launch-time impact if many dynamic frameworks.

### Q83. How do you decide how to split modules? `[Lead/Expert]`
**Key points:**
- **Horizontal (by layer)**: `Networking`, `Persistence`, `DesignSystem`, `Analytics`, `Models`. Good foundation modules.
- **Vertical (by feature)**: `CatalogFeature`, `CartFeature`, `ProfileFeature`. Good for team ownership and build isolation.
- Most mature apps combine both: **core/foundation modules** at the bottom, **feature modules** in the middle, and a thin **app target** on top that composes everything.

```
                    App (composition root, navigation wiring)
          ┌──────────────┼──────────────┬───────────────┐
   CatalogFeature   CartFeature   ProfileFeature   CheckoutFeature
          │    ╲         │    ╱          │               │
          │   CartInterface (protocols)  │               │
          └──────────────┴───────┬───────┴───────────────┘
        DesignSystem · Networking · Persistence · Analytics · Models
```

### Q84. Show a `Package.swift` for a modular app. `[Senior]`

- SwiftPM refuses imports of modules that aren't declared dependencies, so the graph doubles as an **enforced architecture diagram**.

### Q85. What are interface (API) modules, and why use them? `[Lead/Expert]`
**Key points:**
- A lightweight module containing only **protocols and shared types** for a feature (`CartInterface`), separate from its implementation (`CartFeature`).
- Other features depend on the interface, never on the implementation, which:
  - Prevents feature-to-feature coupling and cyclic dependencies.
  - Improves build times: changing `CartFeature`'s implementation doesn't rebuild modules that depend only on `CartInterface`.
  - Allows feature demo apps to use mock implementations.
- The app target wires concrete implementations into interfaces (dependency inversion at module level).

### Q86. Static vs dynamic linking: what are the trade-offs? `[Lead/Expert]`
| Static libraries/frameworks | Dynamic frameworks |
|---|---|
| Linked into the app binary at build time | Loaded at launch (dyld) |
| Faster app launch (no dyld cost per framework) | Each framework adds launch time |
| Code can be duplicated if linked into multiple targets (app + extensions) | Shared between app and extensions without duplication |
| Default for SwiftPM targets (Xcode decides) | Needed for some resource/sharing scenarios |

- Xcode 15+ **mergeable libraries** let you use dynamic frameworks in debug (fast iteration) and merge them into the binary for release (fast launch).

### Q87. How do access levels support modular architecture? `[Senior]`
**Key points:**
- `internal` (default): implementation details hidden inside a module.
- `public`: the module's API. Keep it minimal; everything public is a commitment.
- `package` (Swift 5.9): visible to other modules in the **same package** but not to external clients. Useful for sharing helpers between modules without making them truly public.
- `open`: only when subclassing from other modules is intended.
- Rule of thumb: start `internal`, promote to `public` deliberately.

### Q88. How do you prevent cyclic dependencies and enforce module rules? `[Lead/Expert]`
**Key points:**
- SwiftPM and Xcode reject direct cycles, but **logical** coupling can still creep in via shared "Common" or "Utilities" modules that grow into dumping grounds.
- Enforcement tools:
  - Define allowed dependency directions (features → interfaces → foundation; never feature → feature).
  - Project generators like **Tuist** or XcodeGen that describe the graph in code, with checks.
  - CI scripts or lint rules that fail on forbidden imports (e.g. `import UIKit` in `Domain`).
  - Code ownership (`CODEOWNERS`) for foundation modules so changes get reviewed.
- Break cycles by extracting shared protocols into an interface module or inverting a dependency with a closure/protocol.

### Q89. What are feature demo apps (sample apps)? `[Lead/Expert]`
**Key points:**
- A tiny app target per feature module that launches just that feature with mock dependencies.
- Benefits: build and run in seconds, develop UI in isolation, easier QA of a single feature, enforced independence (if the demo app needs half the codebase, the feature is too coupled).

### Q90. How do you migrate a monolithic app to modules? `[Lead/Expert]`
**Talking points:**
1. **Map the dependency graph**: find leaf code (models, utilities, design system) with few dependencies.
2. **Extract foundation modules first** (Models, DesignSystem, Networking), fixing access control as you go.
3. **Extract one pilot feature** with clear boundaries; introduce its interface module; measure build-time improvement.
4. **Strangler approach**: new features start as modules; old code moves out opportunistically when touched.
5. **Guardrails**: dependency rules in CI, module templates, documentation.
6. Expect friction: singletons and global state block extraction; replace them with injected dependencies as you go.

## 13. Data Layer

### Q91. What is the Repository pattern? `[Fundamental]`
**Key points:**
- A repository provides a **collection-like interface to domain data**, hiding where the data comes from (network, database, cache, files).
- Consumers ask for `products()` or `save(order)` without knowing about `URLSession`, JSON, or SwiftData.

```swift
protocol ProductRepository: Sendable {
    func products() async throws -> [Product]
    func product(id: Product.ID) async throws -> Product
}

struct RemoteProductRepository: ProductRepository {
    let client: APIClient

    func products() async throws -> [Product] {
        try await client.send(.products).map(Product.init(dto:))
    }

    func product(id: Product.ID) async throws -> Product {
        Product(dto: try await client.send(.product(id: id)))
    }
}
```

### Q92. Why separate DTOs from domain models? `[Senior]`
**Key points:**
- **Stability**: API changes (field renames, nesting, versioning) are absorbed in mapping code; domain and UI code stay untouched.
- **Correctness**: domain models can enforce invariants (non-optional fields, typed IDs, `Decimal` prices) that raw API data can't.
- **Multiple sources**: the same domain model can be built from REST, GraphQL, or a database record.
- (See the mapping example in Q47.)

### Q93. How do you implement caching policies in a repository? `[Senior]`
```swift
enum CachePolicy {
    case cacheFirst       // return cache if available, otherwise network
    case networkFirst     // try network, fall back to cache on failure
    case cacheOnly
    case networkOnly
}

actor CachedProductRepository {
    private let api: ProductAPI
    private let store: ProductStore            // local persistence (SwiftData, file, etc.)

    init(api: ProductAPI, store: ProductStore) {
        self.api = api
        self.store = store
    }

    func products(policy: CachePolicy = .cacheFirst) async throws -> [Product] {
        switch policy {
        case .cacheOnly:
            return try await store.products()
        case .networkOnly:
            return try await refresh()
        case .cacheFirst:
            let cached = try await store.products()
            return cached.isEmpty ? try await refresh() : cached
        case .networkFirst:
            do {
                return try await refresh()
            } catch {
                return try await store.products()
            }
        }
    }

    private func refresh() async throws -> [Product] {
        let fresh = try await api.fetchProducts().map(Product.init(dto:))
        try await store.replaceAll(with: fresh)
        return fresh
    }
}
```
- A **stale-while-revalidate** variant returns an `AsyncSequence` that emits cached data immediately, then fresh data (see the Combine file, Q132, for the Combine version).

### Q94. What is a single source of truth in the data layer? `[Senior]`
**Key points:**
- One authoritative place for each piece of data. Commonly, the **local database is the source of truth**: network responses are written to the database, and the UI observes the database.
- Benefits: consistent data across screens, offline support for free, no conflicting copies in different view models.
- Anti-pattern: each screen fetching and holding its own copy of the same entity, which then diverge after edits.

### Q95. How would you architect an offline-first app? `[Lead/Expert]`
**Talking points:**
- **Local store as source of truth** (SwiftData/Core Data/SQLite); the UI reads only from it.
- **Sync engine** (an actor): pulls server changes (with a cursor/token), upserts locally, and handles deletions; pushes local changes from an **outbox** of pending mutations with retries and idempotency keys.
- **Conflict resolution** policy (server wins, last-write-wins with timestamps, or field-level merge).
- **Optimistic UI**: apply changes locally immediately; roll back or flag on failure.
- **Connectivity awareness** (`NWPathMonitor`), background refresh, and clear UI states (syncing, offline, failed).
- **Testing**: inject API and clock; simulate offline, conflicts, and partial failures.

### Q96. How can the Decorator pattern add caching or logging to repositories? `[Lead/Expert]`
```swift
import os

protocol ProductLoading: Sendable {
    func products() async throws -> [Product]
}

struct RemoteProductLoader: ProductLoading {
    let client: APIClient
    func products() async throws -> [Product] {
        try await client.send(.products).map(Product.init(dto:))
    }
}

// Adds logging without changing the wrapped loader
struct LoggingProductLoader: ProductLoading {
    let wrapped: ProductLoading
    let logger: Logger

    func products() async throws -> [Product] {
        let start = ContinuousClock.now
        do {
            let result = try await wrapped.products()
            logger.info("Loaded \(result.count) products in \(String(describing: ContinuousClock.now - start))")
            return result
        } catch {
            logger.error("Product load failed: \(error.localizedDescription)")
            throw error
        }
    }
}

// Adds in-memory caching with expiry
actor CachingProductLoader: ProductLoading {
    private let wrapped: ProductLoading
    private let maxAge: Duration
    private var cache: (products: [Product], storedAt: ContinuousClock.Instant)?

    init(wrapped: ProductLoading, maxAge: Duration) {
        self.wrapped = wrapped
        self.maxAge = maxAge
    }

    func products() async throws -> [Product] {
        if let cache, ContinuousClock.now - cache.storedAt < maxAge {
            return cache.products
        }
        let fresh = try await wrapped.products()
        cache = (fresh, .now)
        return fresh
    }
}

// Composition at the composition root
let loader: ProductLoading = LoggingProductLoader(
    wrapped: CachingProductLoader(wrapped: RemoteProductLoader(client: apiClient), maxAge: .seconds(300)),
    logger: Logger(subsystem: "com.example.shop", category: "products")
)
```
- Each concern (network, caching, logging) is separately testable and composable, which is the Open/Closed Principle in action.

### Q97. Where should persistence frameworks (SwiftData, Core Data) live in the architecture? `[Lead/Expert]`
**Key points:**
- Ideally behind repository protocols in the **data layer**, mapping persisted records to domain models, so the rest of the app doesn't depend on the framework.
- Pragmatic alternative for SwiftUI apps: use `@Query` in views for read-heavy lists (fast development, automatic updates) while keeping writes and business rules in services/`@ModelActor`s.
- The trade-off is abstraction vs. framework features (live queries, change tracking). Make the choice explicit per project (see the SwiftData file, Section 11).

### Q98. How do you design pagination in the data layer? `[Senior]`
```swift
struct Page<Item: Sendable>: Sendable {
    let items: [Item]
    let nextCursor: String?
    var hasMore: Bool { nextCursor != nil }
}

protocol FeedRepository: Sendable {
    func feed(cursor: String?) async throws -> Page<Post>
}

@MainActor
@Observable
final class FeedViewModel {
    private(set) var posts: [Post] = []
    private(set) var isLoadingMore = false
    private var nextCursor: String?
    private var hasMore = true
    private let repository: FeedRepository

    init(repository: FeedRepository) { self.repository = repository }

    func loadNextPageIfNeeded(currentPost: Post) async {
        guard currentPost.id == posts.last?.id, hasMore, !isLoadingMore else { return }
        isLoadingMore = true
        defer { isLoadingMore = false }

        guard let page = try? await repository.feed(cursor: nextCursor) else { return }
        let existingIDs = Set(posts.map(\.id))
        posts.append(contentsOf: page.items.filter { !existingIDs.contains($0.id) })   // dedupe
        nextCursor = page.nextCursor
        hasMore = page.hasMore
    }
}
```
- Prefer **cursor-based** pagination (stable under inserts/deletes) over offset-based.

## 14. Networking Layer

### Q99. How do you structure a networking layer? `[Senior]`
```
Feature repositories  (ProductRepository, OrdersRepository)
        │  domain models
        ▼
API client            (typed Endpoint<Response> → decoded Response)
        │
        ▼
HTTP client           (URLRequest → (Data, HTTPURLResponse)), interceptors
        │
        ▼
URLSession / transport
```
**Key points:**
- **Endpoints** describe requests declaratively.
- **API client** builds requests, decodes responses, and maps errors.
- **Interceptors/middleware** add auth headers, logging, retries, and metrics.
- **Repositories** map DTOs to domain models.
- Each layer is testable independently; the transport can be replaced with stubs.

### Q100. How do you model endpoints? `[Senior]`
```swift
struct Endpoint<Response: Decodable>: Sendable {
    enum Method: String, Sendable { case get = "GET", post = "POST", put = "PUT", delete = "DELETE" }

    var path: String
    var method: Method = .get
    var queryItems: [URLQueryItem] = []

    var requiresAuth = true
```

### Q101. How do request interceptors (middleware) work? `[Lead/Expert]`
```swift
protocol RequestInterceptor: Sendable {
    func intercept(_ request: URLRequest) async throws -> URLRequest
}

struct DefaultHeadersInterceptor: RequestInterceptor {
    let appVersion: String
    func intercept(_ request: URLRequest) async throws -> URLRequest {
        var request = request
        request.setValue("application/json", forHTTPHeaderField: "Accept")
        request.setValue("iOS/\(appVersion)", forHTTPHeaderField: "X-Client-Version")
        return request
    }
}

struct AuthInterceptor: RequestInterceptor {
    let tokenStore: TokenStore          // actor that refreshes tokens once (Async/Await file, Q100)
    func intercept(_ request: URLRequest) async throws -> URLRequest {
        var request = request
        let token = try await tokenStore.validToken()
        request.setValue("Bearer \(token.accessToken)", forHTTPHeaderField: "Authorization")
        return request
    }
}

struct HTTPClient: Sendable {
    let session: URLSession
    let interceptors: [any RequestInterceptor]

    func data(for request: URLRequest) async throws -> (Data, HTTPURLResponse) {
        var request = request
        for interceptor in interceptors {
            request = try await interceptor.intercept(request)
        }
        let (data, response) = try await session.data(for: request)
        guard let http = response as? HTTPURLResponse else { throw APIError.invalidResponse }
        return (data, http)
    }
}
```
- New cross-cutting behavior (tracing headers, request signing) is added as a new interceptor without changing existing code.

### Q102. Where should authentication and token refresh live? `[Lead/Expert]`
**Key points:**
- In the **networking layer**, not in view models: an auth interceptor attaches tokens; a token store (actor) refreshes expired tokens **once** for concurrent requests; the client retries a request once after a 401 refresh.
- If refresh fails, emit a **session-expired** event that the app layer handles (log out, show login). The networking layer shouldn't present UI.
- Tokens are stored in the **Keychain**, never in `UserDefaults`.

### Q104. How do you keep the app resilient to API changes? `[Lead/Expert]`
**Key points:**
- **Tolerant decoding**: optional fields where the server may omit them; unknown enum values mapped to `.unknown` instead of failing the whole payload; lossy decoding of arrays (skip invalid elements, log them).
- **Versioning**: send the app version in headers; support API versioning (`/v2/`); coordinate deprecations with backend teams.
- **Feature flags / remote config** to disable features depending on unstable endpoints.
- **Minimum supported version / force-update** mechanism for breaking changes.
- Contract tests or shared schemas (OpenAPI code generation) to catch mismatches early.

## 15. State Management

### Q105. How should you model screen state? `[Senior]`
**Key points:**
- Use **enums** (with associated values) for mutually exclusive states instead of independent booleans and optionals, so invalid combinations can't be represented.

```swift
// ❌ 2^3 combinations, many invalid (loading AND error? data AND error?)
var isLoading = false
var products: [Product]?
var errorMessage: String?

// ✅ Exactly one state at a time
enum ProductsState: Equatable {
    case idle
    case loading
    case loaded([Product])
    case empty
    case failed(message: String)
}

// ✅ When content and a secondary status coexist (e.g. refreshing while showing data)
struct FeedState: Equatable {
    var posts: [Post] = []
    var phase: Phase = .idle

    enum Phase: Equatable { case idle, loading, refreshing, loadingMore, failed(String) }
}
```

### Q106. How do you distinguish local, shared, and global state? `[Lead/Expert]`
| Kind | Examples | Where it lives |
|---|---|---|
| **Local UI state** | Text field contents, expanded/collapsed, focus | The view (`@State`) or view controller |
| **Screen state** | Loading phase, list content, validation errors | View model / screen model / feature reducer |
| **Shared feature state** | Cart contents, selected filters shared by several screens | A shared observable store or actor, injected |
| **Session/global state** | Logged-in user, auth tokens, feature flags | Session container / app-level services |

- Keep state as **local as possible** and lift it only when multiple consumers need it. Global mutable state is the hardest to reason about and test.

### Q107. Where should session (logged-in user) state live? `[Senior]`
**Key points:**
- In a dedicated, observable **session object** owned by the app layer (e.g. `AppSession` in Q80), not scattered across `UserDefaults` reads and singletons.
- The root of the UI observes it to switch between auth and main flows; features receive the user (or session-scoped services) via injection.
- Logout resets everything session-scoped by discarding one object.

### Q108. Should derived values be stored or computed? `[Senior]`
**Key points:**
- **Compute** derived values (`total`, `isFormValid`, `filteredItems`) from source state whenever reasonable. Stored copies can drift out of sync.
- **Store** them only when computing is expensive and you have a clear invalidation strategy (memoization), or when the value must persist independently.

```swift
struct CartState {
    var items: [CartItem]
    var discount: Decimal

    var subtotal: Decimal { items.reduce(0) { $0 + $1.price * Decimal($1.quantity) } }   // derived
    var total: Decimal { max(0, subtotal - discount) }                                 // derived
}
```

### Q109. How do you architect state restoration? `[Senior]`
**Key points:**
- Represent navigation and key screen state as **`Codable` data** (route arrays, selected tab, draft identifiers), not as view hierarchies.
- Save it per scene (`NSUserActivity` in UIKit, `@SceneStorage` in SwiftUI) and rebuild screens from it on launch.
- Store **identifiers**, not full models; refetch data on restore so it's fresh and small.

### Q110. How do you handle one-time events such as alerts, toasts, and haptics? `[Lead/Expert]`
**Key points:**
- **As state** (preferred in SwiftUI): `var alert: AlertState?`; the view presents it and clears it on dismissal. Survives re-renders and is easy to test.
- **As events** (common in UIKit/Combine): a closure or `PassthroughSubject`/`AsyncStream` that fires once.
- Pitfalls: events can be lost if nobody is subscribed yet; state-modeled events can re-fire if not cleared. Pick one approach per framework and document it.

```swift
@MainActor
@Observable
final class SettingsViewModel {

        let id = UUID()
        let title: String
        let message: String
    }

    var alert: AlertState?                      // view: .alert(item: $viewModel.alert)

        alert = AlertState(title: "Couldn't delete account", message: "Please try again later.")
```

## 16. Cross-Cutting Concerns (Errors, Logging, Feature Flags, Concurrency)

### Q111. How do you design error handling across layers? `[Lead/Expert]`
**Key points:**
- **Data layer**: catch transport/decoding errors (`URLError`, `DecodingError`, HTTP status) and map them to meaningful **domain errors**.
- **Domain layer**: define business errors (`OrderError.paymentDeclined`, `.outOfStock`).
- **Presentation layer**: map domain errors to **user-facing state** (message, retry option); never show raw technical errors.
- **Cross-cutting**: log technical details (with privacy in mind) and report non-fatal errors to monitoring.

```swift
// Domain
enum CheckoutError: Error, Equatable {
    case offline
    case paymentDeclined
    case itemUnavailable(productID: String)
    case unknown
}

// Data layer mapping
extension CheckoutError {
    init(_ error: Error) {
        switch error {
        case let urlError as URLError where urlError.code == .notConnectedToInternet: self = .offline
        case APIError.httpStatus(402, _): self = .paymentDeclined
        case APIError.httpStatus(409, let data): self = .itemUnavailable(productID: String(decoding: data, as: UTF8.self))
        default: self = .unknown
        }
    }
}

// Presentation mapping
extension CheckoutError {
    var userMessage: String {
        switch self {
        case .offline: "You're offline. Check your connection and try again."
        case .paymentDeclined: "Your payment was declined. Try another card."
        case .itemUnavailable: "An item in your cart is no longer available."
        case .unknown: "Something went wrong. Please try again."
        }
    }
    var isRetryable: Bool { self == .offline || self == .unknown }
}
```

### Q112. How do you architect logging and analytics? `[Senior]`
**Key points:**
- Define app-owned protocols (`AnalyticsTracking`, `Logging`) with typed events; implement adapters for vendors (Firebase, Amplitude, `os.Logger`).
- A **composite** tracker can forward events to several vendors; a **no-op** implementation is used in tests and previews.
- Avoid scattering vendor SDK calls across features. Swapping vendors then requires changing only adapters.

```swift
    let parameters: [String: String]

    static func checkoutCompleted(total: Decimal) -> Self {
        .init(name: "checkout_completed", parameters: ["total": "\(total)"])
    }
}

}

struct CompositeAnalytics: AnalyticsTracking {
    let trackers: [any AnalyticsTracking]
    func track(_ event: AnalyticsEvent) { trackers.forEach { $0.track(event) } }
}

struct NoOpAnalytics: AnalyticsTracking {

```

### Q113. How does concurrency influence architecture? `[Lead/Expert]`
**Key points:**
- Define **isolation domains per layer**: UI and view models on the main actor; shared services as actors; data as `Sendable` value types crossing between them; heavy computation in `@concurrent` functions.
- Keep the number of actors small and their APIs coarse-grained.
- Swift 6's data-race checking turns these decisions into compile-time guarantees.
- (Full discussion: Swift Concurrency file, Q119 and Section 15.)

### Q114. How do you architect background work (sync, uploads, refresh)? `[Lead/Expert]`
**Key points:**
- A dedicated **service/actor** (e.g. `SyncEngine`, `UploadQueue`) owns the work, independent of screens; screens observe its status.
- Persist pending work (outbox) so it survives app termination.
- Triggers come from the app layer: foreground, connectivity changes, push notifications, `BGTaskScheduler`.
- Cancellation and expiration handling for background time limits; idempotent server APIs for safe retries.

### Q115. How do you architect feature flags and remote configuration? `[Senior]`
```swift
enum FeatureFlag: String, CaseIterable, Sendable {
    case newCheckout = "new_checkout"
    case searchV2 = "search_v2"
}

protocol FeatureFlagProviding: Sendable {
    func isEnabled(_ flag: FeatureFlag) -> Bool
}

struct LayeredFeatureFlags: FeatureFlagProviding {
    let localOverrides: [FeatureFlag: Bool]     // debug menu, UI tests
    let remote: [String: Bool]                  // fetched remote config, cached on disk
    let defaults: [FeatureFlag: Bool]           // shipped safe defaults

    func isEnabled(_ flag: FeatureFlag) -> Bool {
        localOverrides[flag] ?? remote[flag.rawValue] ?? defaults[flag] ?? false
    }
}

// Composition root chooses implementations based on a flag, so features stay unaware
@MainActor
func makeCheckoutScreen(flags: FeatureFlagProviding, container: AppContainer) -> UIViewController {
    flags.isEnabled(.newCheckout)
        ? NewCheckoutViewController(viewModel: container.makeNewCheckoutViewModel())
        : LegacyCheckoutViewController(viewModel: container.makeLegacyCheckoutViewModel())
}
```
**Talking points:**
- Evaluate flags at **boundaries** (composition root, routing) rather than sprinkling `if` checks deep inside features.
- Use flags as **kill switches** for risky features; define an owner and an expiry for each flag, and remove stale flags (flag debt).
- Cache remote config and apply safe defaults so the app works offline or if the config service is down.

## 17. Testable Architecture

### Q116. What makes code testable? `[Fundamental]`
**Key points:**
- **Injected dependencies** (no hidden singletons, `Date()`, `UUID()`, or `URLSession.shared` inside logic).
- **Pure functions** for business rules and formatting (same input → same output).
- **Separation from UI frameworks**: logic in view models/use cases, not view controllers.
- **Deterministic time and concurrency**: injected clocks, awaitable async methods.
- **Small units** with clear inputs and outputs.

```swift
// ❌ Untestable: hidden time dependency
func isExpired(_ coupon: Coupon) -> Bool { coupon.expiry < Date() }

// ✅ Testable: time is a parameter (or an injected clock/`now` closure)
func isExpired(_ coupon: Coupon, now: Date) -> Bool { coupon.expiry < now }
```

### Q118. What does a healthy iOS test pyramid look like? `[Senior]`
```
            ▲   UI tests (XCUITest): a few critical end-to-end flows
           ▲▲▲  Snapshot tests: key screens/components in key states
         ▲▲▲▲▲▲ Integration tests: API client + stubs, repositories + in-memory stores
```

### Q120. Protocols vs closure-based dependencies: what are the trade-offs? `[Lead/Expert]`

## 18. Design Patterns in iOS

### Q122. When is a Singleton acceptable? `[Senior]`
**Key points:**
- Acceptable for genuinely **single, stateless or app-wide resources** where only one instance makes sense (Apple uses `URLSession.shared`, `FileManager.default`, `UIApplication.shared`).
- Problems when abused: hidden global mutable state, hard-to-test code, implicit dependencies, concurrency hazards (Swift 6 flags non-`Sendable` shared instances).
- Best practice: it's fine to **have** a single instance, but **inject** it instead of calling `.shared` everywhere.

```swift
// Single instance created once at the composition root, injected everywhere
let analytics: AnalyticsTracking = FirebaseAnalyticsAdapter()
let viewModel = ProductViewModel(analytics: analytics)
```

### Q124. What is the Builder pattern? `[Senior]`
```swift
struct RequestBuilder {
    private var components: URLComponents
    private var method = "GET"
    private var headers: [String: String] = [:]
    private var body: Data?

    init(baseURL: URL, path: String) {
        components = URLComponents(url: baseURL.appending(path: path), resolvingAgainstBaseURL: false)!
    }

    func method(_ method: String) -> Self { var copy = self; copy.method = method; return copy }
    func header(_ name: String, _ value: String) -> Self { var copy = self; copy.headers[name] = value; return copy }
    func query(_ name: String, _ value: String) -> Self {
        var copy = self
        copy.components.queryItems = (components.queryItems ?? []) + [URLQueryItem(name: name, value: value)]
        return copy
    }
    func jsonBody<T: Encodable>(_ value: T) throws -> Self {
        var copy = self
        copy.body = try JSONEncoder().encode(value)
        copy.headers["Content-Type"] = "application/json"
        return copy
    }

    func build() -> URLRequest {
        var request = URLRequest(url: components.url!)
        request.httpMethod = method
        request.httpBody = body
        headers.forEach { request.setValue($1, forHTTPHeaderField: $0) }
        return request
    }
}

let request = try RequestBuilder(baseURL: apiURL, path: "orders")
    .method("POST")
    .header("Idempotency-Key", UUID().uuidString)
    .jsonBody(orderRequest)
    .build()
```

### Q129. What is the Command pattern? Show undo support. `[Senior]`
```swift
struct Document {
    var text = ""
}

protocol EditCommand {
    func apply(to document: inout Document)
    func revert(on document: inout Document)
}

struct InsertText: EditCommand {
    let text: String
    let index: Int

    func apply(to document: inout Document) {
        let position = document.text.index(document.text.startIndex, offsetBy: index)
        document.text.insert(contentsOf: text, at: position)
    }

    func revert(on document: inout Document) {
        let start = document.text.index(document.text.startIndex, offsetBy: index)
        let end = document.text.index(start, offsetBy: text.count)
        document.text.removeSubrange(start..<end)
    }
}

struct Editor {
    private(set) var document = Document()
    private var history: [EditCommand] = []

    mutating func perform(_ command: EditCommand) {
        command.apply(to: &document)
        history.append(command)
    }

    mutating func undo() {
        guard let last = history.popLast() else { return }
        last.revert(on: &document)
    }
}
```
- Commands encapsulate actions as values: useful for undo/redo, queuing, logging, and replay. (UIKit's `UndoManager` builds on the same idea.)

### Q130. What is the State pattern, and how does Swift usually express it? `[Senior]`
```swift
enum PlayerState: Equatable {
    case idle
    case loading(URL)
    case playing(position: TimeInterval)
    case paused(position: TimeInterval)
    case failed(String)

    enum Event { case load(URL), loaded, play, pause, fail(String) }

    /// Explicit transitions: invalid events are ignored (or could be asserted)
    func handling(_ event: Event) -> PlayerState {
        switch (self, event) {
        case (_, .load(let url)): .loading(url)
        case (.loading, .loaded): .paused(position: 0)
        case (.paused(let position), .play): .playing(position: position)
        case (.playing(let position), .pause): .paused(position: position)
        case (_, .fail(let message)): .failed(message)
        default: self
        }
    }
}
```
- In Swift, an **enum state machine** with a transition function is usually clearer and safer than the classic OOP State pattern (a class per state).

### Q131. What is the Decorator pattern? `[Senior]`
**Key points:**
- Wraps an object conforming to a protocol with another object conforming to the **same** protocol, adding behavior (caching, logging, retry, metrics) without modifying the original.
- Great for cross-cutting concerns in data and networking layers (see Q96 for a full example).

### Q132. Which patterns are overused or misused in iOS codebases? `[Lead/Expert]`
**Key points:**
- **Singletons** with mutable global state accessed everywhere.
- **"Manager" classes** (`DataManager`, `AppManager`) that accumulate unrelated responsibilities.
- **Protocols for everything**, even with one implementation and no tests needing doubles.
- **Deep inheritance** (`BaseViewController`, `BaseViewModel`) instead of composition.
- **Heavyweight architectures** (VIPER/Clean with all layers) for small apps or simple screens.
- **NotificationCenter** as a general-purpose event bus, making data flow invisible.

## 19. Architecture at Scale

### Q133. How does architecture change when many teams work on one app? `[Lead/Expert]`
**Key points:**
- **Clear ownership**: feature modules owned by teams (`CODEOWNERS`), platform/foundation modules owned by a platform team.
- **Stable contracts** between modules (interface modules, versioned internal APIs) so teams don't block each other.
- **Consistency**: shared patterns, templates, and guidelines; a design system module.
- **Build infrastructure**: modularization, caching, CI parallelization; build times become a top productivity metric.
- **Governance**: architecture reviews/RFCs for cross-cutting changes, ADRs to record decisions.
- **Release coordination**: feature flags to decouple deployment from release; trunk-based development.

### Q134. What is an Architecture Decision Record (ADR)? `[Lead/Expert]`
**Key points:**
- A short document capturing an important decision, its context, and consequences, stored in the repository. It explains **why** things are the way they are to future engineers.

```markdown
# ADR-014: Adopt SwiftPM feature modules with interface modules

- **Status:** Accepted (2026-03-10)
- **Context:** Clean builds take 14 minutes; incremental builds after touching Cart take 3 minutes;
  features import each other freely, causing frequent merge conflicts across 5 teams.
- **Decision:** Split the app into foundation, interface, and feature SwiftPM modules. Features may
  depend only on foundation and interface modules. The app target composes implementations.
- **Consequences:** Faster incremental builds and enforced boundaries; one-time migration cost
  (estimated 6 weeks across teams); new features require an interface module when shared.
- **Alternatives considered:** Tuist-generated frameworks (deferred), status quo with lint rules (rejected:
  not enforceable).
```

### Q135. How do you enforce architectural rules? `[Lead/Expert]`
**Key points:**
- **Compiler-enforced**: module boundaries and access control (strongest guarantee).
- **Automated checks**: SwiftLint custom rules (e.g. no `import UIKit` in domain targets, no `.shared` in view models), dependency-graph checks in CI, Danger rules on pull requests.
- **Templates and scaffolding**: Xcode file templates or generators so the "right way" is the easy way.
- **Code review** with a checklist; **CODEOWNERS** for core modules.
- **Documentation** with examples, plus onboarding sessions.

### Q136. How do you measure architectural health? `[Lead/Expert]`
**Key points:**
- **Build metrics**: clean/incremental build times, CI duration.
- **Change metrics**: how many modules/files a typical feature touches; PR size and cycle time.
- **Quality metrics**: crash-free rate, regression rate, test coverage of logic layers, flaky test rate.
- **Code metrics**: file/type size outliers, dependency counts, cyclic dependencies, number of escape hatches (`@unchecked Sendable`, force unwraps).
- **People metrics**: onboarding time to first meaningful PR; developer satisfaction surveys.

### Q137. How do you architect a white-label (multi-brand) app? `[Lead/Expert]`
**Talking points:**
- **One codebase**, multiple app targets/schemes; per-brand `xcconfig` files, asset catalogs, and Info.plist values.
- A **`BrandConfiguration`** value (colors, fonts, copy, feature availability, API endpoints) injected at the composition root, not `if brand == .acme` checks scattered across features.
- **Design tokens** in the design system resolve per brand; feature flags enable/disable features per brand.
- CI builds and tests all brands; snapshot tests per brand for key screens.

```swift
struct BrandConfiguration: Sendable {
    let displayName: String
    let apiBaseURL: URL
    let theme: Theme
    let enabledFeatures: Set<FeatureFlag>
    let supportEmail: String
}
```

### Q138. How would you design a "super app" or plugin architecture? `[Lead/Expert]`
**Talking points:**
- A **host app** providing shared capabilities (auth, networking, payments, analytics, design system) through stable interface modules.
- **Mini-apps/plugins** implement a common protocol (identifier, entry screen factory, supported deep links, required capabilities) and register with the host.
- Strict isolation: plugins can't access each other directly; communication goes through the host's routing and capability APIs.
- Lazy initialization of plugins to protect launch time; per-plugin feature flags and kill switches; independent team ownership.

```swift
@MainActor
protocol MiniApp {
    static var identifier: String { get }
    func canHandle(_ link: DeepLink) -> Bool
    func makeEntryScreen(context: HostContext) -> UIViewController
}

struct HostContext {
    let session: SessionContainer
    let router: HostRouting
    let analytics: AnalyticsTracking
}
```

## 20. Choosing & Migrating Architectures

### Q139. Compare the major iOS architectures. `[Senior]`
| | MVC | MVVM | MVP | VIPER | Clean Arch. | TCA |
|---|---|---|---|---|---|---|
| Learning curve | Low | Low–Medium | Medium | High | Medium–High | High |
| Boilerplate | Low | Medium | Medium | Very high | High | Medium–High |
| Testability | Low (in practice) | High | High | Very high | Very high | Very high |
| SwiftUI fit | Poor | Good | Fair | Poor | Good (with MVVM) | Excellent |
| Navigation story | Ad hoc | Needs coordinators/routers | Needs coordinators | Built in (Router) | Varies | Built in |
| Best for | Small apps, prototypes | Most apps | UIKit apps wanting explicit view contracts | Large UIKit teams | Complex domains, long-lived apps | Complex state, strong testing culture |

### Q140. How do you choose an architecture for a new project? `[Lead/Expert]`
**Talking points:**
- **Context**: team size and experience; app complexity and lifespan; UI framework; regulatory/quality requirements; release cadence.
- **Constraints**: minimum iOS version, third-party dependency policy, hiring market.
- **Process**: shortlist 2–3 options → build the same representative feature (list + detail + network + error states) as a spike → compare readability, tests, and effort → decide and record an ADR.
- **Principle**: choose the simplest architecture that handles your hardest known requirement, with seams that allow evolution.

### Q141. How do you migrate an MVC codebase to MVVM incrementally? `[Lead/Expert]`
**Talking points:**
1. Start with screens that change often or have the most bugs (highest return).
2. Extract services/repositories from view controllers first (networking, persistence), injected via initializers.
3. Introduce a view model per screen, moving presentation logic and state out of the controller; add unit tests as you go.
4. Introduce coordinators when navigation logic starts tangling.
5. Apply the pattern to all **new** screens immediately; migrate old screens when touched ("boy scout rule").
6. Track progress (e.g. percentage of screens migrated, test coverage of view models).

### Q142. What changes architecturally when moving from UIKit to SwiftUI? `[Lead/Expert]`
**Key points:**
- View code becomes declarative and state-driven; imperative `render(_:)` methods and bindings disappear.
- View models become `@Observable` objects (or are replaced by shared stores in "MV" style).
- Navigation moves from imperative coordinators to **navigation state** (routers with paths and sheet state).
- Dependency injection uses initializers plus the environment.
- During migration, keep **domain and data layers framework-agnostic** so both UIKit and SwiftUI screens share them; host SwiftUI screens in UIKit coordinators via `UIHostingController` first.

### Q143. What is the Strangler Fig pattern? `[Lead/Expert]`
**Key points:**
- Incrementally replace a legacy system by building new functionality around it and routing more and more traffic to the new parts, until the old system can be removed, instead of a risky big-bang rewrite.
- iOS examples: new screens in SwiftUI hosted inside a UIKit app; a new networking layer used by new features while old code keeps the old one, with adapters bridging both; a modular feature replacing a legacy screen behind a feature flag.

## 21. "Spot the Problem" Code Review Questions

> Interviewers increasingly show a snippet and ask "What would you change?" Practice explaining the problem, its consequences, and the fix.

### Q144. A view model that knows about UIKit `[Senior]`
```swift
@MainActor
final class ProfileViewModel {
    weak var viewController: ProfileViewController?

    func load() async {
        let profile = try? await api.fetchProfile()
        viewController?.nameLabel.text = profile?.name
        viewController?.avatarView.backgroundColor = profile?.isPremium == true ? .systemYellow : .systemGray
    }
}
```
**Problems:** the view model manipulates views directly, so it's coupled to one concrete view controller, can't be unit-tested without UIKit, and can't be reused with SwiftUI.
**Fix:** expose state (`name`, `badgeStyle: .premium/.standard`) and let the view render it.

### Q145. Hidden dependencies `[Senior]`
```swift
@MainActor
final class OrdersViewModel {
    func refresh() async {
        let token = UserDefaults.standard.string(forKey: "token")
        let orders = try? await APIClient.shared.fetchOrders(token: token)
        AnalyticsManager.shared.track("orders_refreshed")
        self.orders = orders ?? []
    }
    var orders: [Order] = []
}
```
**Problems:** three hidden singletons (tests can't control them), a token read from `UserDefaults` (insecure; belongs in Keychain and the networking layer), and errors silently swallowed.
**Fix:** inject an `OrdersRepository` (which handles auth internally) and an `AnalyticsTracking` dependency; model loading/error state explicitly.

### Q146. The "Manager" god object `[Senior]`
```swift
final class DataManager {
    static let shared = DataManager()
    var currentUser: User?
    var cart: [CartItem] = []
    func login(email: String, password: String) async throws { }
    func fetchProducts() async throws -> [Product] { [] }
    func saveImageToDisk(_ image: UIImage) { }
    func formatPrice(_ value: Decimal) -> String { "" }
    func trackEvent(_ name: String) { }
}
```
**Problems:** low cohesion (auth, catalog, cart, files, formatting, analytics), global mutable state (data races, session leakage between users), impossible to test in isolation, and every feature depends on it.
**Fix:** split into focused services (`AuthService`, `ProductRepository`, `CartStore`, `ImageStore`, `PriceFormatter`, `AnalyticsTracking`), with session state in a session-scoped container, injected where needed.

### Q147. Service locator inside business logic `[Senior]`
```swift
struct PlaceOrderUseCase {
    func execute(_ order: Order) async throws {
        let payments = DIContainer.shared.resolve(PaymentGateway.self)
        let orders = DIContainer.shared.resolve(OrderRepository.self)
        let token = try await payments.authorize(amount: order.total)
        _ = try await orders.submit(order, paymentToken: token)
    }
}
```
**Problems:** dependencies are invisible from the outside; tests must configure a global container (and parallel tests interfere); missing registrations crash at runtime.
**Fix:** constructor injection (`PlaceOrderUseCase(orders:payments:)`), resolving from the container only at the composition root.

### Q148. Booleans for state `[Fundamental]`
```swift
@Observable
final class SearchViewModel {
    var isLoading = false
    var results: [Movie] = []
    var error: String?
    var isEmpty = false
}
```
**Problems:** many invalid combinations (loading + error, empty + results); every update must remember to reset the other flags, causing UI bugs.
**Fix:** a single `enum State { case idle, loading, results([Movie]), empty, failed(String) }`.

### Q149. Feature modules importing each other `[Lead/Expert]`
```swift
// In CatalogFeature
import CartFeature        // to push CartViewController
import ProfileFeature     // to show login when needed
```
**Problems:** feature-to-feature coupling, build-time ripple effects (changing Cart rebuilds Catalog), risk of cycles, and teams blocking each other.
**Fix:** depend on interface modules (`CartInterface`) or emit navigation intents/routes that the app layer resolves.

### Q150. Leaking child coordinators `[Senior]`
```swift
final class AppCoordinator: Coordinator {
    var childCoordinators: [Coordinator] = []

    func showCheckout() {
        let checkout = CheckoutCoordinator(navigationController: navigationController)
        childCoordinators.append(checkout)
        checkout.start()
    }
}
```
**Problems:** the child is never removed when checkout finishes or the user swipes back, so coordinators (and their view models) leak and may keep reacting to events.
**Fix:** provide an `onFinish` callback that removes the child, and detect back-navigation (`UINavigationControllerDelegate.didShow` or `isMovingFromParent`).

### Q151. DTOs and persistence objects leaking into the UI `[Senior]`
```swift
struct ProductRow: View {
    let product: ProductDTO               // raw API model with snake_case fields and optionals
    var body: some View {
        Text(product.title ?? "")
        Text("$\(Double(product.price_cents ?? 0) / 100)")
    }
}
```
**Problems:** API format changes break UI code; formatting and fallback logic duplicated in views; `Double` for money; optionals everywhere.
**Fix:** map DTOs to domain models in the data layer (`Product` with `Decimal` price), and format with a shared formatter or view model.

### Q152. A protocol for every type `[Lead/Expert]`
```swift
protocol DateFormatterServiceProtocol { func format(_ date: Date) -> String }
final class DateFormatterService: DateFormatterServiceProtocol { /* ... */ }

protocol StringValidatorProtocol { func isValidEmail(_ value: String) -> Bool }
final class StringValidator: StringValidatorProtocol { /* ... */ }
```
**Problems:** abstractions with a single implementation and no I/O add files and indirection without benefit; pure logic like formatting and validation doesn't need test doubles.
**Fix:** use concrete types (or plain functions) for pure logic and test them directly; reserve protocols for real boundaries (network, persistence, SDKs, system services).

### Q153. Domain layer depending on UI frameworks `[Senior]`
```swift
// Domain/Order.swift
import SwiftUI

struct Order {
    let id: String
    let statusColor: Color
    let thumbnail: Image
}
```
**Problems:** the domain can't be reused in widgets, macOS, server-side Swift, or UIKit screens without SwiftUI; visual decisions are mixed with business data.
**Fix:** keep domain types framework-free (`status: OrderStatus`, `thumbnailURL: URL?`) and map them to colors and images in the presentation layer.

### Q154. Navigation performed by a view model `[Senior]`
```swift
@MainActor
final class ProductListViewModel {
    weak var navigationController: UINavigationController?

    func didSelect(_ product: Product) {
        let detail = ProductDetailViewController(product: product)
        navigationController?.pushViewController(detail, animated: true)
    }
}
```
**Problems:** the view model depends on UIKit and on concrete destination screens; navigation can't be reused (e.g. iPad split view or deep links) or tested without UIKit.
**Fix:** emit an intent (`onSelect(product.id)` or a `Route`), and let a coordinator/router decide how to present it.

### Q155. VIPER for a two-screen app `[Lead/Expert]`
**Scenario:** A startup's MVP has a login screen and a list screen. The codebase has 14 files and 10 protocols for these two screens (View, Presenter, Interactor, Router, Entity, builders, and protocols for each).

**Problems:** the architecture's cost (boilerplate, onboarding, slower iteration) far outweighs its benefits at this scale; the team is optimizing for a future that may never come.
**Fix:** start with a simpler structure (SwiftUI + `@Observable` view models or MVVM in UIKit, a repository per data source, injected dependencies) with clear seams that can evolve. Revisit when the team and app grow.

## 23. Senior / Lead Scenario Questions

### Q156. You're the first iOS lead on a new app with a team of 8. How do you set up the architecture? `[Lead/Expert]`
**Talking points:**
- **Clarify context**: product scope, expected lifespan, team experience, minimum iOS version (likely iOS 17+, enabling SwiftUI + Observation + SwiftData if they fit).
- **Proposal**: SwiftUI with `@Observable` view models for complex screens; routers for navigation; repositories over a typed networking layer; constructor injection with a composition root and factories; Swift 6 language mode with main-actor UI and a few actors for shared services.
- **Modularization from day one, but light**: foundation modules (Models, Networking, DesignSystem) + a few feature modules; add interface modules as features need to talk.
- **Quality**: unit tests for view models and repositories, snapshot tests for the design system, a few UI tests for critical flows; CI with linting and module-boundary checks.
- **Process**: ADRs for key decisions, a short architecture guide with a reference feature, templates, and regular architecture reviews.
- **Evolve**: revisit decisions after the first few features based on real friction.

### Q157. You inherit a 300k-line MVC app with massive view controllers and few tests. What's your modernization plan? `[Lead/Expert]`
**Talking points:**
1. **Assess**: identify hotspots (files changed most often, most crashes, most bugs) and slowest build areas.
2. **Stabilize**: add characterization tests and UI tests around critical flows before refactoring.
3. **Set the target architecture** (e.g. MVVM + coordinators + repositories, SwiftUI for new screens) and document it with a reference implementation.
4. **Strangler approach**: all new features follow the target architecture; legacy screens are refactored when touched, prioritized by hotspot data.
5. **Extract foundations**: networking, persistence, and design system into modules; replace singletons with injected services gradually.
6. **Measure and communicate**: track test coverage of logic, crash rate, build times, and lead time for changes; report progress to stakeholders.
7. **Avoid** a big-bang rewrite unless the codebase is truly unsalvageable and the business accepts the risk.

### Q158. Your team is split between MVVM and TCA. How do you decide? `[Lead/Expert]`
**Talking points:**
- Frame the decision around **problems**, not preferences: complex shared state? exhaustive testing needs? team experience? third-party dependency policy? onboarding speed?
- Run a **time-boxed spike**: both approaches implement the same non-trivial feature (search with debouncing, pagination, error handling, navigation).
- Compare readability, test quality, build times, and how new team members cope; gather input from the whole team.
- Decide, write an ADR (including why the other option wasn't chosen), and commit to **consistency**. Mixing paradigms per feature usually costs more than either choice alone.

### Q159. Clean builds take 20 minutes and incremental builds 4 minutes. How do you fix it architecturally? `[Lead/Expert]`
**Talking points:**
- **Measure**: Xcode Build Timeline, `-warn-long-function-bodies`, find slow-compiling files and modules that rebuild too often.
- **Modularize**: extract foundation modules; split feature modules; introduce **interface modules** so implementation changes don't cascade.
- **Reduce coupling** to frequently changing modules (e.g. a huge `Common` module that everything imports).
- **Code-level fixes**: explicit types in complex expressions, smaller files, fewer `@objc` and large generated files.
- **Infrastructure**: remote/build caching, CI parallelization, mergeable libraries for faster debug iteration.
- Track build-time metrics over time to prevent regressions.

### Q160. Multiple teams constantly break each other's features. What do you change? `[Lead/Expert]`
**Talking points:**
- **Ownership boundaries**: feature modules owned by teams, `CODEOWNERS`, and clear contracts via interface modules.
- **Contract tests** for shared modules; versioned or deprecation-friendly APIs for core components.
- **Feature flags** and trunk-based development so unfinished work doesn't affect others.
- **CI**: required tests for affected modules, impact analysis, faster feedback.
- **Communication**: RFCs for cross-team changes, a platform team owning foundations, regular architecture syncs.

### Q161. How would you architect an app that must work fully offline? `[Lead/Expert]`
**Talking points:**
- Local database as the **single source of truth**; UI reads only from it.
- Sync engine actor with an outbox for local changes, cursor-based pulls, retries with backoff, idempotency keys, and a clear conflict policy.
- Domain models independent of persistence and API formats; mappers at the boundaries.
- UX: optimistic updates, sync status indicators, conflict resolution UI where needed.
- Testing: deterministic tests for sync scenarios (offline, partial failure, conflict), with injected clocks and network stubs.
- (See Q95 and the SwiftData file, Q127.)

### Q162. Test coverage is 5%, and management wants faster releases with fewer regressions. What do you do? `[Lead/Expert]`
**Talking points:**
- Don't chase a coverage number first; target **risk**: add UI tests for the 3–5 most critical flows (login, purchase, onboarding) to catch major regressions quickly.
- Make code testable where it changes most: extract logic from view controllers into view models/services with injected dependencies, and require tests for new and modified logic.
- Add snapshot tests for the design system; add contract/integration tests for networking.
- Automate in CI with fast feedback; quarantine and fix flaky tests.
- Report outcomes (escaped defects, crash rate, release frequency) rather than coverage alone.

### Q163. How do you explain architecture decisions to non-technical stakeholders? `[Lead/Expert]`
**Talking points:**
- Translate into **business outcomes**: "Modularizing will cut build times by about 60%, which gives each engineer roughly an hour back per day," "Moving login to the new architecture lets us ship SSO in two weeks instead of six."
- Present options with costs, risks, and timelines; recommend one.
- Propose incremental delivery with checkpoints instead of large, opaque refactors.
- Follow up with metrics showing the result.

### Q164. How would you design authentication so it works cleanly across all features? `[Lead/Expert]`
**Talking points:**
- An `AuthService` (login, logout, refresh) and a **`TokenStore` actor** in the networking layer; tokens in the Keychain.
- An observable **`AppSession`** owning session-scoped dependencies; the root UI switches between auth and main flows based on it.
- An auth interceptor attaches tokens; 401s trigger a single shared refresh; refresh failure emits a session-expired event that the app layer handles (log out and show login).
- Features never talk to the login UI directly; they use an `AuthGate` abstraction when an action requires login, and pending deep links are replayed after login.
- Logout discards the session container, clears caches, and resets navigation.

### Q165. How would you mentor a team that's new to architecture concepts? `[Senior]`
**Talking points:**
- Start from **pain points** the team already feels (bugs from shared state, untestable view controllers) rather than abstract patterns.
- Provide a **reference feature** implemented end to end, with tests, that people can copy.
- Pair programming and code review comments that explain the *why*, linking to the team's architecture guide.
- Introduce concepts gradually: dependency injection → view models → repositories → modules → advanced patterns.
- Celebrate improvements (a flaky area becoming stable, a feature shipped faster) to build buy-in.

### Final Tips
- There's rarely a single right answer in architecture interviews. Interviewers want to hear **trade-offs, context, and reasoning**: "For a team of 3 shipping an MVP, I'd do X; for 40 engineers, Y, because…"
- Know the **classics** cold: SOLID with Swift examples (Q9–Q14), MVVM vs MVP vs VIPER vs TCA (Q35, Q37, Q41, Q57, Q139), coordinators and deep links (Q63–Q69), DI and the composition root (Q71–Q80), and modularization with interface modules (Q82–Q90).
- Practice **"spot the problem"** reviews (Section 21). They test practical judgment better than definitions.
- Prepare **two stories**: an architecture decision you made (with the ADR-style context, decision, and consequences), and a migration or refactor you led, including what you'd do differently.
