## 1. Fundamentals

### Q1. What is SwiftUI, and how does declarative UI differ from imperative UI? `[Fundamental]`
**Key points:**
- **Imperative (UIKit)**: you create views and mutate them step by step (`label.text = ...`, `view.isHidden = ...`). You must keep UI and state in sync manually.
- **Declarative (SwiftUI)**: you describe what the UI should look like **for a given state**. When state changes, SwiftUI recomputes the description and updates the screen.
- Benefit: a whole class of "UI out of sync with data" bugs disappears. Cost: you must understand how SwiftUI tracks state and identity.

```swift
// Declarative: UI is a function of state
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("Count: \(count)")
            Button("Increment") { count += 1 }
        }
    }
}
```

### Q2. What is the `View` protocol? `[Fundamental]`
**Key points:**
- A type that conforms to `View` provides a `body` property returning `some View`.
- `associatedtype Body: View`, so `body`'s concrete type is inferred.
- Primitive views like `Text`, `Image`, `Color` have `Body == Never`; SwiftUI renders them directly.
- Since the iOS 18 SDK, `View` is annotated `@MainActor`, so `body` and view methods run on the main actor.

### Q3. Why are SwiftUI views structs instead of classes? `[Senior]`
**Key points:**
- Views are **lightweight descriptions**, not the actual on-screen objects. SwiftUI creates and throws them away constantly; structs make that cheap (no heap allocation or reference counting for the view itself).
- Value semantics avoid shared mutable state and make diffing straightforward.
- The persistent state lives in SwiftUI's internal storage (the attribute graph), not in the struct. That's why you need `@State` and friends to persist data across `body` evaluations.

### Q4. Why does `body` return `some View`? `[Senior]`
**Key points:**
- `some View` is an opaque type: one specific concrete type, hidden from the caller but known to the compiler.
- The real type is usually a deeply nested generic like `VStack<TupleView<(Text, Button<Text>)>>`.
- Knowing the exact static type lets SwiftUI diff efficiently and determine **structural identity** (see Section 2).
- All code paths must return the same type, which is why `@ViewBuilder` exists.

### Q5. What is `@ViewBuilder`? `[Fundamental]`
**Key points:**
- A result builder that turns multiple statements into a single view (`TupleView`), and `if`/`switch` into `_ConditionalContent` or `Optional` views.
- `body` is implicitly a `@ViewBuilder`. You can mark your own properties, functions, and closure parameters with it.

```swift
struct ProfileView: View {
    let user: User?

    var body: some View {
        VStack {
            header
            if let user {
                Text(user.name)
            } else {
                Text("Guest")
            }
        }
    }

    @ViewBuilder
    private var header: some View {
        if user?.isPremium == true {
            Label("Premium", systemImage: "star.fill")
        }
        // An empty branch is allowed here thanks to @ViewBuilder
    }
}
```

### Q6. Why does modifier order matter? `[Fundamental]`
**Key points:**
- Each modifier wraps the view in a new view. Modifiers apply from the inside out, in the order written.

```swift
Text("Hello")
    .padding()
    .background(.yellow)   // yellow covers text + padding

Text("Hello")
    .background(.yellow)   // yellow covers only the text
    .padding()             // padding is added outside the yellow area
```
- Same for `.frame` + `.border`, `.clipShape` + `.shadow`, `.onTapGesture` + `.padding` (tap area).

### Q7. What are `Group`, `EmptyView`, and `AnyView`? `[Fundamental]`
**Key points:**
- `Group`: groups views without affecting layout; applies modifiers to all children; helps work around builder limits.
- `EmptyView`: a view that displays nothing.
- `AnyView`: a type-erased view. It hides the concrete type, which prevents SwiftUI from using structural identity and efficient diffing. Prefer `@ViewBuilder`, `Group`, or generics.

### Q8. What happens when a `@State` value changes? `[Senior]`
**Key points:**
1. SwiftUI marks views that **depend on** that state as invalid.
2. On the next render pass, it re-evaluates their `body`.
3. It **diffs** the new view description against the previous one using identity.
4. It applies only the minimal changes to the rendered output.
- Views that don't read the changed state aren't re-evaluated. This is the foundation of SwiftUI performance (see Section 13).

## 2. View Identity, Lifetime & Dependencies

> This is the single most important topic for senior SwiftUI interviews. Apple's WWDC21 session "Demystify SwiftUI" is the canonical reference.

### Q9. What is view identity, and why does it matter? `[Senior]`
**Key points:**
- Identity is how SwiftUI recognizes that a view in the new render is "the same" view as in the previous render.
- Identity determines:
  - **State lifetime**: `@State` lives exactly as long as the view's identity.
  - **Animations and transitions**: same identity animates changes; new identity triggers insertion/removal transitions.
  - **Performance**: stable identity enables minimal updates.

### Q10. What are structural identity and explicit identity? `[Senior]`
**Key points:**
- **Structural identity**: derived from the view's type and position in the view hierarchy. For example, the two branches of an `if/else` are different views.
- **Explicit identity**: assigned via `.id(_:)` or the identifiers in `ForEach` / `List`.

```swift
// Structural: two distinct views with separate identities and separate state
if isLoggedIn {
    HomeView()
} else {
    LoginView()
}

// Explicit: identity tied to data
ForEach(messages) { message in   // uses message.id
    MessageRow(message: message)
}
```

### Q11. When should you use a conditional modifier instead of `if/else`? `[Senior]`
**Key points:**
- `if/else` creates **two different identities**: switching branches destroys one view (and its state) and creates another, with a transition (fade by default).
- A ternary inside a modifier keeps **one identity**: state persists, and the change animates smoothly.

```swift
// ❌ Different identities: state resets, cross-fade transition
if isHighlighted {
    CardView().background(.yellow)
} else {
    CardView()
}

// ✅ Same identity: state preserved, background animates
CardView()
    .background(isHighlighted ? Color.yellow : Color.clear)
```
- Beware of the popular `.if(condition) { $0.modifier() }` extension: it hides an `if/else` and causes the same identity problem.

### Q12. What does `.id(_:)` do, and when would you use it? `[Senior]`
**Key points:**
- Assigns an explicit identity. **Changing the ID destroys the view and creates a new one**, resetting all its state.
- Uses: resetting a form or scroll position when switching to another item, forcing a fresh view when input data changes, and targeting views with `ScrollViewReader`.
- Misuse: using a value that changes on every render (like `UUID()`), which recreates the view every time, destroying state and performance.

```swift
// Reset the editor's internal state when a different document is selected
DocumentEditor(document: selectedDocument)
    .id(selectedDocument.id)
```

### Q13. What is the difference between a view's lifetime and its identity? `[Senior]`
**Key points:**
- The **view value** (the struct) is short-lived: recreated every time the parent's `body` runs.
- The view's **lifetime** is the duration of its identity in the hierarchy. `@State`, `@StateObject`, and `.task` are tied to this lifetime, not to the struct.
- That's why you shouldn't do expensive work in a view's `init`: it may run many times for one on-screen view.

### Q14. Why must `ForEach` identifiers be stable and unique? `[Senior]`
**Key points:**
- SwiftUI uses them to match rows between updates. Unstable IDs (array indices for a mutable list, random UUIDs generated in `body`) cause wrong animations, lost state in rows, and poor performance.
- Duplicate IDs cause undefined behavior: wrong rows displayed or updated.
- Prefer `Identifiable` models with persistent IDs (e.g. from the server or database).

```swift
// ❌ Index identity: deleting row 0 shifts every row's identity
ForEach(items.indices, id: \.self) { index in
    ItemRow(item: items[index])
}

// ❌ Unstable identity: new IDs on every render
ForEach(items.map { (UUID(), $0) }, id: \.0) { _, item in ItemRow(item: item) }

// ✅ Stable, unique identity
ForEach(items) { item in   // Item: Identifiable
    ItemRow(item: item)
}
```

### Q15. What are a view's dependencies? `[Senior]`
**Key points:**
- Anything a view reads that can change: its stored properties (inputs from the parent), `@State`, `@Binding`, `@Environment` values, observed objects/properties.
- When a dependency changes, the view's `body` is re-evaluated.
- Reducing dependencies (passing only what a view needs) reduces unnecessary updates.

### Q16. Does SwiftUI re-run `body` for a child when its parent's `body` runs? `[Lead/Expert]`
**Key points:**
- The child's struct is recreated, but SwiftUI compares the child's inputs with the previous ones. If they're equal (SwiftUI compares stored properties, using `Equatable` where available or a field-wise comparison), the child's `body` can be skipped.
- Closures and non-equatable reference types defeat this comparison, so children holding closures often get re-evaluated.
- You can make a view `Equatable` to define custom comparison (see Q102).

## 3. State Management & Property Wrappers

### Q17. What is `@State`? `[Fundamental]`
**Key points:**
- Declares a source of truth **owned by the view**. SwiftUI stores the value outside the struct and keeps it for the view's lifetime.
- Use for simple, local UI state: toggles, text input, selection, presentation flags. Since iOS 17 also for owning `@Observable` model objects.
- Mark it `private`: it should be initialized and mutated only by the owning view.

### Q18. What is `@Binding`? `[Fundamental]`
**Key points:**
- A two-way reference to a source of truth owned by someone else. The child can read and write without owning the data.
- Create with the `$` prefix: `$isOn`.

```swift
struct SettingsView: View {
    @State private var notificationsEnabled = true

    var body: some View {
        NotificationToggle(isOn: $notificationsEnabled)
    }
}

struct NotificationToggle: View {
    @Binding var isOn: Bool

    var body: some View {
        Toggle("Notifications", isOn: $isOn)
    }
}
```

### Q19. How do you create custom, derived, and constant bindings? `[Senior]`
```swift
// Derived binding with custom get/set
Toggle("Dark Mode", isOn: Binding(
    get: { settings.theme == .dark },
    set: { settings.theme = $0 ? .dark : .light }
))

// Binding to an element in a collection (iOS 15+)
List($todos) { $todo in
    Toggle(todo.title, isOn: $todo.isDone)
}

// Binding to a property via dynamic member lookup
TextField("Name", text: $profile.name)

// Constant binding (previews, read-only usage)
Toggle("Preview", isOn: .constant(true))
```

### Q20. What is the difference between `@StateObject` and `@ObservedObject`? `[Senior]`
| `@StateObject` | `@ObservedObject` |
|---|---|
| The view **owns** the object | The view **doesn't own** it; someone else passes it in |
| Created once per view identity (initializer is an autoclosure evaluated once) | Not retained across view re-creation by SwiftUI |
| Use where the object is created | Use where the object is received |

- Classic bug: `@ObservedObject var model = Model()` creates a new model every time the parent re-renders, resetting its data.
- Both are for `ObservableObject` (Combine-based). With `@Observable` (iOS 17+), use `@State` for ownership and plain properties (or `@Bindable`) for received objects.

### Q21. What is `@EnvironmentObject`? `[Fundamental]`
**Key points:**
- Injects an `ObservableObject` into the environment so any descendant can read it without passing it through every level.
- Inject with `.environmentObject(object)`; read with `@EnvironmentObject var settings: AppSettings`.
- If an ancestor didn't inject it, the app **crashes** at runtime when the view accesses it.
- With `@Observable`, the replacement is `.environment(object)` + `@Environment(Type.self)`.

### Q22. What are the rules for choosing the right property wrapper? `[Senior]`
| Situation | iOS 17+ (`@Observable`) | iOS 13–16 (`ObservableObject`) |
|---|---|---|
| Simple value owned by this view | `@State` | `@State` |
| Value owned by a parent, need read/write | `@Binding` | `@Binding` |
| Reference model owned by this view | `@State` | `@StateObject` |
| Reference model passed in | plain `let`/`var` | `@ObservedObject` |
| Need bindings to a passed-in model's properties | `@Bindable` | `@ObservedObject` (gives `$`) |
| Model shared deep in the hierarchy | `@Environment(Model.self)` | `@EnvironmentObject` |
| System values (color scheme, dismiss, locale) | `@Environment(\.key)` | `@Environment(\.key)` |

### Q23. How do you initialize `@State` from a value passed into the view? What's the catch? `[Senior]`
```swift
struct NameEditor: View {
    @State private var draft: String

    init(initialName: String) {
        _draft = State(initialValue: initialName)
    }

    var body: some View {
        TextField("Name", text: $draft)
    }
}
```
**The catch:**
- The initial value is used **only the first time** the view's identity is created. If the parent later passes a different `initialName`, `draft` doesn't change.
- If you want the child to follow the parent's value, use a `@Binding` instead. If you want to reset when the input changes, add `.id(initialName)` or react with `.onChange`.

### Q24. What is a "single source of truth," and why does it matter? `[Senior]`
**Key points:**
- Each piece of data should have exactly one owner. Everyone else reads it or gets a binding.
- Duplicated state (copying a parent value into a child's `@State`) leads to values drifting out of sync.
- Derive values instead of storing them: computed properties over stored duplicates.

### Q25. What is `@AppStorage` and `@SceneStorage`? `[Fundamental]`
**Key points:**
- `@AppStorage("key")`: reads/writes `UserDefaults` and updates views on change. For small preferences only, never secrets (use the Keychain).
- `@SceneStorage("key")`: per-scene state restoration (e.g. selected tab, draft text), saved and restored by the system.

```swift
@AppStorage("hasSeenOnboarding") private var hasSeenOnboarding = false
@SceneStorage("selectedTab") private var selectedTab = Tab.home
```

### Q26. What is `@FocusState`? `[Fundamental]`
```swift
struct LoginForm: View {
    enum Field { case email, password }

    @State private var email = ""
    @State private var password = ""
    @FocusState private var focusedField: Field?

    var body: some View {
        Form {
            TextField("Email", text: $email)
                .focused($focusedField, equals: .email)
                .submitLabel(.next)
                .onSubmit { focusedField = .password }

            SecureField("Password", text: $password)
                .focused($focusedField, equals: .password)
                .submitLabel(.go)
                .onSubmit(login)
        }
        .onAppear { focusedField = .email }
    }

    private func login() { focusedField = nil }
}
```

### Q27. What is `DynamicProperty`? `[Lead/Expert]`
**Key points:**
- The protocol behind `@State`, `@Environment`, `@Query`, etc. SwiftUI updates dynamic properties before calling `body`.
- You can build custom property wrappers that conform to `DynamicProperty` and internally use `@State` or `@Environment`, encapsulating reusable view logic (e.g. a `@Debounced` or feature-flag wrapper).

## 4. The Observation Framework (`@Observable`)

### Q28. What is `@Observable`, and how does it differ from `ObservableObject`? `[Senior]`
| `ObservableObject` + `@Published` | `@Observable` (iOS 17+) |
|---|---|
| Combine-based | Swift Observation framework, macro-based |
| Any `@Published` change invalidates **every** view observing the object | Only views that **read the changed property** are invalidated |
| Needs `@StateObject` / `@ObservedObject` / `@EnvironmentObject` | Uses `@State`, plain properties, `@Bindable`, `@Environment` |
| Must mark each property `@Published` | All stored properties tracked by default |
| Tracks nested objects poorly | Tracks properties of nested observable objects, arrays, optionals |

```swift
// Before
final class CartStore: ObservableObject {
    @Published var items: [Item] = []
    @Published var couponCode = ""
}

// After
@Observable
final class CartStore {
    var items: [Item] = []
    var couponCode = ""
}
```

### Q29. Why is `@Observable` better for performance? `[Senior]`
**Key points:**
- Tracking is **per property, per view**, based on what `body` actually reads.
- Example: a badge view showing `cart.items.count` won't re-render when `couponCode` changes. With `ObservableObject`, it would.
- Reads inside closures that run later (e.g. button actions) are not tracked, which avoids unnecessary dependencies.

### Q30. What is `@Bindable`? `[Senior]`
**Key points:**
- Creates bindings to properties of an `@Observable` object that the view doesn't own.
- Can be a property wrapper on a view property, or a local variable inside `body` (useful with environment objects).

```swift
@Observable
final class Profile {
    var name = ""
    var bio = ""
}

struct ProfileEditor: View {
    @Bindable var profile: Profile    // passed in by a parent

    var body: some View {
        Form {
            TextField("Name", text: $profile.name)
            TextField("Bio", text: $profile.bio)
        }
    }
}

struct SettingsScreen: View {
    @Environment(Profile.self) private var profile

    var body: some View {
        @Bindable var profile = profile   // local bindable for environment objects
        TextField("Name", text: $profile.name)
    }
}
```

### Q31. How do you own an `@Observable` model in a view, and what's the pitfall? `[Lead/Expert]`
**Key points:**
- Use `@State private var model = Model()`.
- Pitfall: unlike `@StateObject` (which uses an autoclosure), `@State`'s initial value expression is evaluated **every time the view struct is initialized**. SwiftUI keeps only the first instance, but the others are still created and discarded.
- If the model's `init` is expensive or has side effects (network calls, subscriptions), this causes wasted work or bugs.
- Fixes: keep `init` cheap and start work in `.task`; create the model in a parent and pass it down; or lazily create it in `.task` into an optional `@State`.

```swift
struct FeedScreen: View {
    @State private var model = FeedModel()   // FeedModel.init must be cheap

    var body: some View {
        FeedList(model: model)
            .task { await model.loadIfNeeded() }   // side effects belong here
    }
}
```

### Q32. What does `@ObservationIgnored` do? `[Senior]`
**Key points:**
- Excludes a stored property from tracking: caches, formatters, internal bookkeeping, or dependencies that shouldn't trigger UI updates.

```swift
@Observable
final class SearchModel {
    var query = ""
    var results: [Result] = []
    @ObservationIgnored private var cache: [String: [Result]] = [:]
    @ObservationIgnored private let api: SearchAPI

    init(api: SearchAPI) { self.api = api }
}
```

### Q33. How do you share an `@Observable` object through the environment? `[Fundamental]`
```swift
@main
struct ShopApp: App {
    @State private var cart = Cart()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(cart)
        }
    }
}

struct CartBadge: View {
    @Environment(Cart.self) private var cart

    var body: some View {
        Text("\(cart.items.count)")
    }
}
```
- Reading a non-optional type that wasn't injected crashes. Declare `@Environment(Cart.self) private var cart: Cart?` if it may be absent.

### Q34. How do you observe changes to `@Observable` properties outside SwiftUI? `[Lead/Expert]`
**Key points:**
- `withObservationTracking(_:onChange:)`: tracks properties read in the first closure; `onChange` fires **once**, **before** the next change (will-set semantics). Re-register to keep observing.
- Swift 6.2 (iOS 26) adds `Observations`, an `AsyncSequence` that emits values transactionally as they change.

```swift
// One-shot tracking
withObservationTracking {
    _ = cart.total
} onChange: {
    print("total is about to change")
}

// Swift 6.2: async stream of values
for await total in Observations({ cart.total }) {
    print("New total: \(total)")
}
```

### Q35. How would you migrate a codebase from `ObservableObject` to `@Observable`? `[Lead/Expert]`
**Key points:**
- Requires iOS 17+ deployment target (or keep both paths behind `#available`).
- Steps per type: replace `ObservableObject` with `@Observable`, remove `@Published`, then update call sites: `@StateObject` → `@State`, `@ObservedObject` → plain property or `@Bindable`, `@EnvironmentObject` → `@Environment(Type.self)`, `.environmentObject()` → `.environment()`.
- Watch out for: code subscribing to `$property` publishers (Combine) which no longer exist; the `@State` init pitfall (Q31); thread-safety (mark models `@MainActor` if UI-bound).
- Migrate leaf types first, measure performance gains, and migrate incrementally.

## 5. Environment & Preferences

### Q36. What is the SwiftUI environment? `[Fundamental]`
**Key points:**
- A set of values that flows **down** the view hierarchy implicitly: color scheme, locale, Dynamic Type size, `dismiss`, `openURL`, `modelContext`, and your own values.
- A modifier like `.environment(\.locale, ...)` or `.font(...)` affects all descendants unless overridden.

```swift
struct DetailView: View {
    @Environment(\.dismiss) private var dismiss
    @Environment(\.colorScheme) private var colorScheme
    @Environment(\.openURL) private var openURL

    var body: some View {
        Button("Close") { dismiss() }
    }
}
```

### Q37. How do you define a custom environment value? `[Senior]`
```swift
// iOS 18 SDK / Xcode 16+: @Entry macro (back-deploys)
extension EnvironmentValues {
    @Entry var theme: Theme = .standard
}

// Older style
private struct ThemeKey: EnvironmentKey {
    static let defaultValue: Theme = .standard
}
extension EnvironmentValues {
    var legacyTheme: Theme {
        get { self[ThemeKey.self] }
        set { self[ThemeKey.self] = newValue }
    }
}

// Usage
ContentView().environment(\.theme, .dark)

struct ThemedButton: View {
    @Environment(\.theme) private var theme
    var body: some View { Button("Buy") {}.tint(theme.accent) }
}
```

### Q38. When should you use the environment vs passing values through initializers? `[Senior]`
**Key points:**
- **Initializers**: explicit, compile-time checked, easy to reason about. Default for direct parent → child data.
- **Environment**: cross-cutting concerns used by many views at different depths (theme, services, feature flags, the router).
- Overusing the environment hides dependencies and causes runtime crashes when values are missing (for `@Environment(Type.self)`).

### Q39. What are preference keys? `[Senior]`
**Key points:**
- Preferences send data **up** from children to ancestors (the opposite of the environment).
- Used by SwiftUI itself for `navigationTitle`, `toolbar`, and others.
- Define a `PreferenceKey` with a `defaultValue` and a `reduce` function to combine values from multiple children.

```swift
struct MaxWidthKey: PreferenceKey {
    static let defaultValue: CGFloat = 0     // `let` avoids Swift 6 global mutable state errors
    static func reduce(value: inout CGFloat, nextValue: () -> CGFloat) {
        value = max(value, nextValue())
    }
}

struct AlignedLabels: View {
    @State private var labelWidth: CGFloat = 0

    var body: some View {
        VStack(alignment: .leading) {
            ForEach(["Name", "Email address", "Phone"], id: \.self) { title in
                Text(title)
                    .background(GeometryReader { proxy in
                        Color.clear.preference(key: MaxWidthKey.self, value: proxy.size.width)
                    })
                    .frame(width: labelWidth > 0 ? labelWidth : nil, alignment: .leading)
            }
        }
        .onPreferenceChange(MaxWidthKey.self) { labelWidth = $0 }
    }
}
```
- For simply reading a size, `onGeometryChange` (Q51) is now simpler.

## 6. Layout System

### Q40. How does SwiftUI's layout system work? `[Senior]`
**Key points:**
A three-step negotiation:
1. The **parent proposes** a size to the child.
2. The **child chooses** its own size (it may ignore the proposal).
3. The **parent places** the child in its coordinate space.
- Views are ultimately in control of their own size; that's why `Text` stays as small as its content and `Color` fills everything offered.
- Modifiers like `.frame` and `.padding` are themselves layout views that change the proposal or the placement.

### Q41. How does `.frame` actually work? `[Senior]`
**Key points:**
- `.frame(width: 100, height: 50)` creates a container that proposes exactly that size to its child and reports that size to its parent. The child may still be smaller and is centered by default.
- `.frame(maxWidth: .infinity)` makes the container as wide as offered; use `alignment` to position the child.

```swift
Text("Hi")
    .frame(width: 200, height: 100)   // the frame is 200×100; the text is still small, centered
    .background(.blue)                // blue fills 200×100

Text("Left aligned")
    .frame(maxWidth: .infinity, alignment: .leading)
```

### Q42. How do stacks distribute space? What are `layoutPriority` and `fixedSize`? `[Senior]`
**Key points:**
- Stacks offer space to their least flexible children first, then divide what remains among more flexible ones.
- `.layoutPriority(1)`: a child with higher priority gets space before others.
- `.fixedSize()`: the view uses its ideal size and ignores the proposal (e.g. prevents text truncation).
- `fixedSize(horizontal: false, vertical: true)`: let text wrap to as many lines as needed.

```swift
HStack {
    Text("A very long product title that might truncate")
        .lineLimit(1)
    Spacer()
    Text("$1,299.00")
        .layoutPriority(1)   // price never truncates
}
```

### Q43. Compare `VStack`, `LazyVStack`, and `List`. `[Senior]`
| | `VStack` | `LazyVStack` | `List` |
|---|---|---|---|
| Creates rows | All at once | On demand as they scroll into view | On demand, backed by a platform list (cell reuse) |
| Scrolling | Needs `ScrollView` | Needs `ScrollView` | Built in |

| Built-in features | None | Pinned headers | Swipe actions, edit mode, selection, separators |

### Q44. What is `Spacer`, and what are common layout mistakes with it? `[Fundamental]`
**Key points:**
- A flexible view that expands along the stack's axis, pushing other views apart.
- `Spacer(minLength: 0)` removes the default minimum spacing.
- Mistakes: putting a `Spacer` in a `ZStack` (no axis), or inside a `ScrollView` expecting it to fill the screen (scroll views offer unlimited space on their axis).

### Q45. What is `GeometryReader`, and what are its pitfalls? `[Senior]`
**Key points:**
- Gives a `GeometryProxy` with the proposed size, safe area insets, and frames in coordinate spaces.
- Pitfalls:
  - It **takes all available space** offered to it and places children at the top-leading corner, often breaking layouts.
  - Using it to measure and then writing to `@State` can cause layout loops.
  - Overused for things the layout system already does.
- Modern alternatives: `containerRelativeFrame` (iOS 17), `onGeometryChange` (iOS 16+ back-deployed), `ViewThatFits`, custom `Layout`, `visualEffect` (iOS 17) for geometry-based effects.

### Q48. How do you build a custom layout with the `Layout` protocol? `[Lead/Expert]`
**Key points:**
- iOS 16: implement `sizeThatFits(proposal:subviews:cache:)` and `placeSubviews(in:proposal:subviews:cache:)`.
- Classic interview task: a **flow layout** (tags that wrap to the next line).

```swift
struct FlowLayout: Layout {
    var spacing: CGFloat = 8

    func sizeThatFits(proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) -> CGSize {
        let maxWidth = proposal.width ?? .infinity
        var x: CGFloat = 0, y: CGFloat = 0, rowHeight: CGFloat = 0, widest: CGFloat = 0

        for subview in subviews {
            let size = subview.sizeThatFits(.unspecified)
            if x + size.width > maxWidth, x > 0 {      // wrap to next row
                x = 0
                y += rowHeight + spacing
                rowHeight = 0
            }
            x += size.width + spacing
            rowHeight = max(rowHeight, size.height)
            widest = max(widest, x - spacing)
        }
        return CGSize(width: widest, height: y + rowHeight)
    }

    func placeSubviews(in bounds: CGRect, proposal: ProposedViewSize, subviews: Subviews, cache: inout ()) {
        var x = bounds.minX, y = bounds.minY, rowHeight: CGFloat = 0

        for subview in subviews {
            let size = subview.sizeThatFits(.unspecified)
            if x + size.width > bounds.maxX, x > bounds.minX {
                x = bounds.minX
                y += rowHeight + spacing
                rowHeight = 0
            }
            subview.place(at: CGPoint(x: x, y: y), proposal: ProposedViewSize(size))
            x += size.width + spacing
            rowHeight = max(rowHeight, size.height)
        }
    }
}

// Usage
FlowLayout {
    ForEach(tags, id: \.self) { tag in
        Text(tag)
            .padding(.horizontal, 12)
            .padding(.vertical, 6)
            .background(.blue.opacity(0.15), in: Capsule())
    }
}
```

### Q60. What is `NavigationStack`, and how does it improve on `NavigationView`? `[Fundamental]`
**Key points:**
- iOS 16 replacement for `NavigationView` (deprecated).

```swift
                ProductDetailView(product: product)
            }

        }
    }
}
```

### Q61. How do you implement a router for programmatic navigation? `[Senior]`
```swift
enum Route: Hashable {
    case product(Product.ID)
    case cart
    case orderConfirmation(orderID: String)
}

@MainActor
@Observable
final class Router {
    var path: [Route] = []

    func push(_ route: Route) { path.append(route) }
    func pop() { _ = path.popLast() }
    func popToRoot() { path.removeAll() }
}

struct RootView: View {
    @State private var router = Router()

    var body: some View {
        NavigationStack(path: $router.path) {
            HomeView()
                .navigationDestination(for: Route.self) { route in
                    switch route {
                    case .product(let id): ProductDetailView(productID: id)
                    case .cart: CartView()
                    case .orderConfirmation(let orderID): ConfirmationView(orderID: orderID)
                    }
                }
        }
        .environment(router)
    }
}

// Anywhere below
struct CartView: View {
    @Environment(Router.self) private var router
    var body: some View {
        Button("Place order") { router.push(.orderConfirmation(orderID: "A123")) }
    }
}
```

### Q62. What is `NavigationPath`, and when would you use it over a typed array? `[Senior]`
**Key points:**
- A type-erased collection of `Hashable` values, so the stack can contain **different types** (e.g. `Product` and `User` destinations).
- A typed array (`[Route]`) is simpler, inspectable, and testable. Prefer it when one enum can represent all routes.
- `NavigationPath.codable` gives a `CodableRepresentation` (when all elements are `Codable`) for state restoration.

## 9. Async Work, Lifecycle Modifiers & Concurrency

### Q71. What is the difference between `.onAppear` and `.task`? `[Senior]`
| `.onAppear` | `.task` |
|---|---|
| Synchronous closure | Async closure |
| You must manage any `Task` you start | Task is **automatically cancelled** when the view disappears |
| Fine for quick synchronous setup | Preferred for async work (loading data, streams) |

```swift
.task {
    await model.load()   // cancelled automatically if the user leaves the screen
}
```
- Both run each time the view appears (e.g. returning from a pushed screen). Guard against reloading if not desired.

### Q72. What does `.task(id:)` do? Show a debounced search. `[Senior]`
**Key points:**
- Restarts the task whenever `id` changes, **cancelling** the previous one. Ideal for work that depends on a value.

```swift
struct SearchView: View {
    @State private var query = ""
    @State private var results: [Movie] = []

    var body: some View {
        List(results) { Text($0.title) }
            .searchable(text: $query)
            .task(id: query) {
                try? await Task.sleep(for: .milliseconds(300))   // debounce
                guard !Task.isCancelled, !query.isEmpty else { return }
                results = (try? await api.search(query)) ?? []
            }
    }
}
```
- If the user keeps typing, each keystroke cancels the previous task during the sleep, so only the final query hits the network.

### Q73. How does `onChange(of:)` work in iOS 17+? `[Fundamental]`
```swift
.onChange(of: selectedTab) { oldValue, newValue in
    analytics.track(from: oldValue, to: newValue)
}

.onChange(of: searchText, initial: true) {
    // also runs when the view first appears
    filter()
}
```
- The value must be `Equatable`. The closure runs on the main actor after the change.
- Avoid chains where `onChange` mutates other state that triggers another `onChange`; prefer deriving values.

### Q74. How do you consume an `AsyncSequence` in a view? `[Senior]`

- Combine publishers can still be consumed with `.onReceive(publisher)`.

### Q75. On which thread does SwiftUI view code run? `[Senior]`
**Key points:**
- `View` is `@MainActor` (iOS 18 SDK onward), so `body`, view methods, and `.task` closures run on the main actor by default.
- `await`ing an async function from a nonisolated context or another actor suspends the main actor rather than blocking it. But **CPU-heavy synchronous work** in `.task` still blocks the UI.
- Move heavy work off the main actor (a separate actor, a `nonisolated` async function, or `Task.detached`) and assign results back on the main actor.

```swift
.task {
    let thumbnails = await ThumbnailRenderer.shared.render(photos)  // runs on another actor
    self.thumbnails = thumbnails                                     // back on the main actor
}
```

### Q76. How should UI-bound `@Observable` models handle concurrency? `[Lead/Expert]`
**Key points:**
- Mark them `@MainActor` so property mutations that drive UI always happen on the main actor, and Swift 6 can verify it.
- Network/database calls inside `async` methods suspend without blocking.
- With Swift 6.2's "approachable concurrency" settings, new Xcode projects can make main-actor isolation the default for app targets.

```swift
@MainActor
@Observable
final class ProfileModel {
    private(set) var profile: Profile?
    private(set) var errorMessage: String?
    private let api: ProfileAPI

    init(api: ProfileAPI) { self.api = api }

    func load() async {
        do {
            profile = try await api.fetchProfile()   // network happens off the main actor inside the API
        } catch is CancellationError {
            // view disappeared; ignore
        } catch {
            errorMessage = error.localizedDescription
        }
    }
}
```

## 10. Animations & Transitions

### Q79. What is the difference between implicit and explicit animations? `[Fundamental]`
**Key points:**
- **Implicit**: `.animation(_:value:)` animates changes to modifiers **above it in the chain** whenever `value` changes.
- **Explicit**: `withAnimation { }` animates **all** view changes caused by the state mutations inside the block.
- The old `.animation(_:)` without a `value` is deprecated because it animated unexpected changes.

```swift
struct ExpandingCard: View {
    @State private var isExpanded = false

    var body: some View {
        VStack {
            // Implicit
            RoundedRectangle(cornerRadius: 16)
                .frame(height: isExpanded ? 300 : 100)
                .animation(.spring(duration: 0.4, bounce: 0.3), value: isExpanded)

            // Explicit
            Button("Toggle") {
                withAnimation(.snappy) {
                    isExpanded.toggle()
                }
            }
        }
    }
}
```

### Q80. What are transitions, and why doesn't my transition animate? `[Senior]`
**Key points:**
- Transitions describe how a view is **inserted or removed** (identity appears/disappears), e.g. `.opacity`, `.slide`, `.move(edge:)`, `.scale`, `.push(from:)`, or combinations.
- They only animate when the insertion/removal happens inside an animation (`withAnimation` or an `.animation` on a **parent** that stays in the hierarchy).
- Common mistake: putting `.animation` on the view that's being removed. It disappears along with its modifier.

```swift
struct ToastHost: View {
    @State private var showToast = false

    var body: some View {
        ZStack(alignment: .bottom) {
            Button("Show toast") {
                withAnimation(.spring) { showToast.toggle() }
            }

            if showToast {
                ToastView(message: "Saved!")
                    .transition(.move(edge: .bottom).combined(with: .opacity))
            }
        }
    }
}

// Asymmetric
.transition(.asymmetric(insertion: .scale.combined(with: .opacity), removal: .opacity))
```

### Q81. What is `matchedGeometryEffect`? `[Senior]`
**Key points:**
- Animates a view smoothly between two positions/sizes in different parts of the hierarchy, as if it were the same view (hero animations).
- Both views share an `id` and a `@Namespace`. Only one should be visible at a time (or set `isSource` properly).

```swift
struct HeroExample: View {
    @Namespace private var namespace
    @State private var isExpanded = false

    var body: some View {
        VStack {
            if isExpanded {
                RoundedRectangle(cornerRadius: 24)
                    .fill(.blue)
                    .matchedGeometryEffect(id: "card", in: namespace)
                    .frame(height: 400)
            } else {
                RoundedRectangle(cornerRadius: 12)
                    .fill(.blue)
                    .matchedGeometryEffect(id: "card", in: namespace)
                    .frame(width: 100, height: 100)
            }
        }
        .onTapGesture {
            withAnimation(.spring(duration: 0.5)) { isExpanded.toggle() }
        }
    }
}
```
- For navigation and sheets in iOS 18+, prefer the built-in zoom transition (Q70).

### Q82. How do you make a custom shape animatable? `[Lead/Expert]`
**Key points:**
- SwiftUI interpolates `animatableData` between old and new values. Shapes and modifiers conforming to `Animatable` expose the property to interpolate.
- For multiple values, use `AnimatablePair`. (iOS 26 adds an `@Animatable` macro that synthesizes `animatableData`.)

```swift
struct PieSlice: Shape {
    var progress: Double   // 0...1

    var animatableData: Double {
        get { progress }
        set { progress = newValue }
    }

    func path(in rect: CGRect) -> Path {
        let center = CGPoint(x: rect.midX, y: rect.midY)
        var path = Path()
        path.move(to: center)
        path.addArc(center: center,
                    radius: min(rect.width, rect.height) / 2,
                    startAngle: .degrees(-90),
                    endAngle: .degrees(-90 + 360 * progress),
                    clockwise: false)
        path.closeSubpath()
        return path
    }
}

// PieSlice(progress: value).animation(.easeInOut, value: value)
```
- Without `animatableData`, the shape would jump from the old to the new value.

### Q83. What are `PhaseAnimator` and `KeyframeAnimator`? `[Senior]`
**Key points (iOS 17):**
- `phaseAnimator`: cycles through discrete phases, each with its own animation. Good for multi-step effects.
- `keyframeAnimator`: independent tracks of keyframes for different properties over time. Good for complex, choreographed motion.

```swift
// Phase animator: pulse when `likeCount` changes
Image(systemName: "heart.fill")
    .foregroundStyle(.red)
    .phaseAnimator([false, true], trigger: likeCount) { content, isScaledUp in
        content.scaleEffect(isScaledUp ? 1.3 : 1.0)
    } animation: { _ in
        .spring(duration: 0.25, bounce: 0.5)
    }

// Keyframe animator: bounce a bell
struct BellValues {
    var scale = 1.0
    var verticalOffset = 0.0
}

Image(systemName: "bell.fill")
    .keyframeAnimator(initialValue: BellValues(), trigger: notificationCount) { content, value in
        content
            .scaleEffect(value.scale)
            .offset(y: value.verticalOffset)
    } keyframes: { _ in
        KeyframeTrack(\.scale) {
            SpringKeyframe(1.3, duration: 0.15)
            SpringKeyframe(1.0, duration: 0.3)
        }
        KeyframeTrack(\.verticalOffset) {
            LinearKeyframe(-10, duration: 0.15)
            SpringKeyframe(0, duration: 0.3)
        }
    }
```

### Q84. What is a `Transaction`? `[Lead/Expert]`
**Key points:**
- Every state change happens within a transaction that carries animation information. `withAnimation` sets `transaction.animation`.
- `withTransaction` and `.transaction { }` let you inspect or override animations for a subtree, e.g. disable animations for one view.

```swift
// Disable animation for this subtree even if the parent change is animated
BadgeView(count: count)
    .transaction { transaction in
        transaction.animation = nil
    }

// Scoped animation (iOS 17): only modifiers inside the closure animate
Rectangle()
    .animation(.smooth) { content in
        content.opacity(isVisible ? 1 : 0)
    }
    .frame(width: isWide ? 300 : 100)   // not animated by the scoped animation
```

### Q89. How do you create a custom `ButtonStyle`? `[Senior]`

```swift
struct PrimaryButtonStyle: ButtonStyle {
```

### Q90. How do you build a generic container view that accepts content? `[Senior]`
```swift
struct Card<Content: View>: View {

    @ViewBuilder let content: Content
```

### Q91. How do you build custom containers that inspect their subviews? `[Lead/Expert]`
**Key points:**
- iOS 18: `ForEach(subviews:)` and `Group(subviews:)` give access to the individual subviews of a content parameter, including those produced by `ForEach` and sections.
- Enables custom containers that behave like `List` or `VStack`.

```swift
struct DividedStack<Content: View>: View {
    @ViewBuilder var content: Content

    var body: some View {
        VStack(spacing: 12) {
            Group(subviews: content) { subviews in
                ForEach(subviews) { subview in
                    subview
                    if subview.id != subviews.last?.id {
                        Divider()
                    }
                }
            }
        }
    }
}

// Usage
DividedStack {
    Text("First")
    ForEach(["Second", "Third"], id: \.self) { Text($0) }
}
```

### Q92. When should you extract a subview vs a computed property vs a function? `[Senior]`
**Key points:**
- **Separate `View` struct**: has its own identity and dependency tracking, so SwiftUI can skip its `body` when its inputs haven't changed. Best for performance and reuse.
- **Computed property / `@ViewBuilder` function**: just code organization. It's still part of the parent's `body` and is re-evaluated every time the parent is.
- Rule of thumb: extract a struct when a part has its own state, reads frequently changing data, or is reused.

### Q93. How do you create a reusable style system / theme? `[Lead/Expert]`
**Key points:**
- Define design tokens (colors, fonts, spacing) in a package; use asset catalog colors for Dark Mode.
- Provide styles (`ButtonStyle`, `LabelStyle`) and modifiers (`.cardStyle()`) rather than parameter-heavy components.
- Pass themes via the environment (`@Entry var theme`).
- Use static member syntax (`.buttonStyle(.primary)`) for discoverability.

## 12. Gestures

### Q94. How do you implement a draggable view? What is `@GestureState`? `[Senior]`
**Key points:**
- `@GestureState` holds transient state during a gesture and **automatically resets** when the gesture ends or is cancelled.

```swift
struct DraggableCard: View {
    @State private var position: CGSize = .zero
    @GestureState private var dragOffset: CGSize = .zero

    var body: some View {
        RoundedRectangle(cornerRadius: 16)
            .fill(.blue)
            .frame(width: 200, height: 120)
            .offset(x: position.width + dragOffset.width,
                    y: position.height + dragOffset.height)
            .gesture(
                DragGesture()
                    .updating($dragOffset) { value, state, _ in
                        state = value.translation
                    }
                    .onEnded { value in
                        position.width += value.translation.width
                        position.height += value.translation.height
                    }
            )
            .animation(.spring, value: dragOffset)
    }
}
```

### Q95. How do you combine gestures? `[Senior]`
```swift
// Simultaneous: pinch and rotate at the same time
@State private var scale = 1.0
@State private var angle = Angle.zero

Image("photo")
    .scaleEffect(scale)
    .rotationEffect(angle)
    .gesture(
        MagnifyGesture()
            .onChanged { scale = $0.magnification }
            .simultaneously(with:
                RotateGesture().onChanged { angle = $0.rotation }
            )
    )

// Sequenced: long press, then drag
let longPressThenDrag = LongPressGesture(minimumDuration: 0.5)
    .sequenced(before: DragGesture())

// Exclusive: double tap wins over single tap
let taps = TapGesture(count: 2).onEnded { zoom() }
    .exclusively(before: TapGesture().onEnded { toggleControls() })
```
- `.highPriorityGesture` makes a gesture win over child gestures; `.simultaneousGesture` lets it run alongside them (e.g. inside a `ScrollView`).
- `MagnifyGesture` and `RotateGesture` (iOS 17) replace `MagnificationGesture` and `RotationGesture`.

### Q96. Why isn't my tap gesture firing on empty areas of a view? `[Fundamental]`
**Key points:**
- Only visible content is hit-testable by default; transparent space between items in a stack isn't.
- Fix: `.contentShape(Rectangle())` to define the tappable area.

```swift
HStack {
    Text("Settings")
    Spacer()
    Image(systemName: "chevron.right")
}
.contentShape(Rectangle())   // the Spacer area becomes tappable
.onTapGesture { openSettings() }
```
- If it should behave like a button, use `Button` instead for accessibility.

## 13. Performance

### Q97. What are the most common causes of poor SwiftUI performance? `[Senior]`
**Key points:**
- Views depending on more data than they need (big `ObservableObject`s invalidating many views).
- Unstable identity (`id: \.self` on non-unique values, `UUID()` in `body`, index-based IDs).
- Expensive work in `body` or view initializers (formatting, filtering/sorting big arrays, creating formatters).
- `AnyView` and type erasure everywhere.
- Non-lazy stacks for long content; `GeometryReader` overuse.
- Frequent, unnecessary state updates (e.g. updating `@State` on every scroll offset change).

### Q98. How do you find out why a view's `body` re-ran? `[Senior]`
```swift
var body: some View {
    let _ = Self._printChanges()   // debug only: logs which dependency changed
    Text(model.title)
}
```
- Prints e.g. `ProductRow: @self, _model changed.`
- Instruments: the SwiftUI template (Xcode 26 adds a redesigned SwiftUI instrument showing long body updates and why views updated), plus Time Profiler and Hangs/Hitches.

### Q99. How do you reduce unnecessary view updates? `[Senior]`
**Key points:**
- Split large views into smaller structs so each depends on less data.
- Pass only the values a child needs (e.g. `item.title`), not a whole model.
- Use `@Observable` for fine-grained tracking.
- Precompute derived data in the model, not in `body`.
- Avoid storing rapidly changing values (scroll offsets, timers) in state read by large views.

```swift
// ❌ Every row depends on the entire store
struct Row: View {
    let store: Store          // ObservableObject with many @Published properties
    let id: Item.ID
    var body: some View { Text(store.items[id]?.title ?? "") }
}

// ✅ Row depends only on what it displays
struct Row: View {
    let title: String
    var body: some View { Text(title) }
}
```

### Q100. Why is `AnyView` bad for performance? `[Senior]`
**Key points:**
- It erases the view's type, so SwiftUI can't use structural identity. Changing the wrapped view type means SwiftUI must tear down and rebuild, losing state and animations, and diffing is less efficient.
- Use `@ViewBuilder`, `Group`, generics, or `some View` instead. `AnyView` is acceptable in rare places, such as heterogeneous plugin systems.

### Q101. How do you avoid expensive work in `body`? `[Senior]`
```swift
// ❌ Sorting and creating a formatter on every body evaluation
var body: some View {
    let formatter = DateFormatter()
    formatter.dateStyle = .medium
    return List(events.sorted { $0.date < $1.date }) { event in
        Text(formatter.string(from: event.date))
    }
}

// ✅ Precompute in the model; use FormatStyle (cached by the system)
var body: some View {
    List(model.sortedEvents) { event in
        Text(event.date, format: .dateTime.day().month().year())
    }
}
```

### Q102. How does `Equatable` conformance help view performance? `[Lead/Expert]`
**Key points:**
- If a view conforms to `Equatable`, SwiftUI can use your `==` to decide whether to re-evaluate `body` when the parent updates. `.equatable()` makes this explicit.
- Useful when a view has inputs SwiftUI can't compare well (closures) but you know which fields matter.

```swift
struct ChartView: View, Equatable {
    let points: [Double]
    let onSelect: (Int) -> Void          // closures aren't comparable

    static func == (lhs: Self, rhs: Self) -> Bool {
        lhs.points == rhs.points         // ignore the closure
    }

    var body: some View { /* expensive drawing */ Text("\(points.count) points") }
}

// ChartView(points: data, onSelect: select).equatable()
```

### Q103. How do you optimize long lists and image-heavy feeds? `[Lead/Expert]`
**Key points:**
- Use `List` or lazy stacks with stable `Identifiable` IDs.
- Keep row views small and cheap; precompute display strings.
- `AsyncImage` has no persistent cache. For feeds, use a custom loader with `NSCache` + downsampling (or Nuke/Kingfisher).
- Avoid heavy modifiers per row (large shadows, blurs, `drawingGroup` misuse).
- Prefetch the next page before the end of the list.
- Profile on an older device in Release builds.

### Q104. What does `drawingGroup()` do? `[Lead/Expert]`
**Key points:**
- Flattens a complex view subtree into a single offscreen bitmap rendered with Metal before display.
- Helps when you have many overlapping shapes/gradients (charts, particle effects).
- Hurts for simple views or text (extra offscreen pass, and it rasterizes text). Measure before using.

### Q107. How does localization work in SwiftUI? `[Senior]`


## 16. Architecture & Dependency Injection

### Q112. Do you need MVVM in SwiftUI? `[Lead/Expert]`
**Key points (this is a popular debate question; show you can argue both sides):**
- **"MV" / model-driven argument**: SwiftUI views already act like view models (they hold state and derive UI). Adding a view model per screen can duplicate state and add boilerplate. Apple's sample code often uses `@Observable` models shared through the environment.
- **MVVM argument**: separates presentation logic (formatting, validation, loading states) from views, making it unit-testable without UI, and helps teams with consistent structure, especially in large codebases and UIKit/SwiftUI hybrids.
- **Senior answer**: choose based on complexity. Simple screens can bind directly to models; complex screens benefit from a dedicated `@Observable` screen model. Be consistent across the team and keep business logic out of views either way.

### Q113. Show an MVVM screen with `@Observable` and dependency injection. `[Senior]`
```swift
protocol ProductAPI: Sendable {
    func fetchProducts() async throws -> [Product]
}

@MainActor
@Observable
final class ProductListViewModel {
    enum State { case idle, loading, loaded([Product]), failed(String) }

    private(set) var state: State = .idle
    private let api: ProductAPI

    init(api: ProductAPI) { self.api = api }

    func loadIfNeeded() async {
        guard case .idle = state else { return }   // .task re-runs on each appearance
        await load()
    }

    func load() async {
        state = .loading
        do {
            state = .loaded(try await api.fetchProducts())
        } catch {
            state = .failed(error.localizedDescription)
        }
    }
}

struct ProductListView: View {
    @State private var viewModel: ProductListViewModel

    init(api: ProductAPI) {
        _viewModel = State(initialValue: ProductListViewModel(api: api))   // keep init cheap (see Q31)
    }

    var body: some View {
        content
            .task { await viewModel.loadIfNeeded() }
            .refreshable { await viewModel.load() }
    }

    @ViewBuilder
    private var content: some View {
        switch viewModel.state {
        case .idle, .loading:
            ProgressView()
        case .loaded(let products):
            List(products) { Text($0.name) }
        case .failed(let message):
            ContentUnavailableView("Error", systemImage: "exclamationmark.triangle",
                                   description: Text(message))
        }
    }
}
```

### Q115. What is The Composable Architecture (TCA), and what are its trade-offs? `[Lead/Expert]`
**Key points:**
- A third-party (Point-Free) unidirectional architecture: **State** (struct), **Action** (enum), **Reducer** (pure state transitions + effects), **Store** (runtime), with built-in dependency management and exhaustive testing.
- **Pros**: predictable state changes, powerful testing (assert every state change and effect), composition of features, consistent patterns for large teams.
- **Cons**: learning curve, boilerplate, dependency on a third-party library and its release cadence, compile-time cost.
- A good answer compares it with plain `@Observable` models and explains when you'd pick each.

### Q116. How do you structure a large SwiftUI app into modules? `[Lead/Expert]`
**Key points:**
- Swift packages per feature (`ProfileFeature`, `CheckoutFeature`) plus shared packages (`DesignSystem`, `Networking`, `Models`).
- Features depend on **interfaces** (protocols) rather than each other; the app target composes them.
- Benefits: faster incremental builds, faster previews (small preview targets), clear ownership, enforced boundaries.
- Navigation across features via routes/enums the app layer maps to views, so features don't import each other.

### Q117. Where should navigation logic live in SwiftUI? `[Lead/Expert]`
**Key points:**
- Options: inside views with `NavigationLink(value:)` (simple apps); a `Router` `@Observable` object owning the path (Q61); coordinator-like objects per flow; or the architecture's state (TCA's stack state).
- For deep links, auth gating, and analytics, centralizing the path in a router makes navigation testable: you can assert `router.path == [.cart, .checkout]` without UI.

## 17. SwiftData & UIKit Integration (Quick Reference)

> SwiftData and UIKit have their own detailed files. These are the SwiftUI-side essentials.

### Q118. How do you use SwiftData in a SwiftUI view? `[Fundamental]`
```swift
@Model
final class Trip {
    var name: String
    var startDate: Date
    init(name: String, startDate: Date) {
        self.name = name
        self.startDate = startDate
    }
}

@main
struct TravelApp: App {
    var body: some Scene {
        WindowGroup { TripListView() }
            .modelContainer(for: Trip.self)
    }
}

struct TripListView: View {
    @Query(sort: \Trip.startDate, order: .reverse) private var trips: [Trip]
    @Environment(\.modelContext) private var modelContext

    var body: some View {
        List {
            ForEach(trips) { Text($0.name) }
                .onDelete { offsets in
                    offsets.forEach { modelContext.delete(trips[$0]) }
                }
        }
        .toolbar {
            Button("Add") { modelContext.insert(Trip(name: "New Trip", startDate: .now)) }
        }
    }
}
```
- `@Query` keeps results in sync automatically. For dynamic filters, create the query in the view's `init` with a `#Predicate`.

### Q119. How do you wrap a UIKit view controller for SwiftUI? `[Senior]`
```swift
import SafariServices

struct SafariView: UIViewControllerRepresentable {
    let url: URL

    func makeUIViewController(context: Context) -> SFSafariViewController {
        SFSafariViewController(url: url)
    }

    func updateUIViewController(_ controller: SFSafariViewController, context: Context) { }
}

// .sheet(item: $linkToOpen) { link in SafariView(url: link.url).ignoresSafeArea() }
```
- `makeUIView(Controller)` runs once; `update...` syncs SwiftUI state into UIKit; a `Coordinator` handles delegates (see the UIKit file, Q140).
- Embed SwiftUI in UIKit with `UIHostingController` or `UIHostingConfiguration` for cells.

### Q120. When would you drop down to UIKit inside a SwiftUI app? `[Lead/Expert]`
**Key points:**
- Missing or limited SwiftUI APIs on your deployment target (advanced text editing before iOS 26's rich `TextEditor`, some camera/document scanner flows, complex collection view layouts or gesture interplay).
- Performance-critical screens where you need precise control (huge, complex feeds).
- Reusing mature, well-tested UIKit components.
- Keep the bridge thin and well-encapsulated so it can be replaced later.

## 18. Testing SwiftUI

### Q121. How do you test SwiftUI code? `[Senior]`
**Key points:**
- **Unit test the logic**, not the view: models/view models, routers, formatters. This is where most bugs live and tests are fast.
- **Snapshot tests** for visual regressions (Dynamic Type, Dark Mode, locales).
- **UI tests** (XCUITest) for critical flows.
- Third-party view inspection (e.g. ViewInspector) exists but is brittle; use sparingly.

```swift
struct MockProductAPI: ProductAPI {

        let viewModel = ProductListViewModel(api: MockProductAPI(result: .success([.sample])))

            Issue.record("Expected failed state")
            return
        }
    }
}
```

### Q124. What were the key SwiftUI additions in iOS 17? `[Senior]`

### Q126. What changed in SwiftUI with iOS 26? `[Senior]`

- A native `WebView` (WebKit for SwiftUI).

### Q127. How do you adopt new APIs while supporting older iOS versions? `[Lead/Expert]`
```swift
extension View {
    @ViewBuilder
    func cardBackground() -> some View {
        if #available(iOS 26, *) {
            self.glassEffect(in: .rect(cornerRadius: 16))
        } else {
            self.background(.ultraThinMaterial, in: RoundedRectangle(cornerRadius: 16))
        }
    }
}
```
- Wrap availability checks in small modifiers so call sites stay clean and the fallback can be deleted when the deployment target rises.
- Note: `if #available` inside a builder creates a conditional (two identities). That's fine here because the OS version doesn't change at runtime.
- Track the minimum deployment target decision with data (OS adoption stats), and plan when to drop old versions.

## 20. "What's the Output?" Questions

### Q128. Modifier order `[Fundamental]`
```swift
Text("Hi")
    .background(.red)
    .padding(20)
    .background(.blue)
```
**Answer:** Red tightly behind the text, surrounded by a 20 pt blue border. Each modifier wraps the previous result.

### Q129. `if/else` and state `[Senior]`
```swift
struct CounterView: View {
    @State private var count = 0
    var body: some View { Button("Count: \(count)") { count += 1 } }
}

struct Parent: View {
    @State private var isHighlighted = false
    var body: some View {
        VStack {
            if isHighlighted {
                CounterView().background(.yellow)
            } else {
                CounterView()
            }
            Toggle("Highlight", isOn: $isHighlighted)
        }
    }
}
```
**Question:** You tap the counter to 5, then flip the toggle. What does the counter show?

**Answer:** `Count: 0`. The branches are different identities, so the new `CounterView` has fresh state. Use `.background(isHighlighted ? Color.yellow : .clear)` to keep it.

### Q130. `@ObservedObject` created inline `[Senior]`
```swift
final class CounterModel: ObservableObject { @Published var count = 0 }

struct Child: View {
    @ObservedObject var model = CounterModel()
    var body: some View { Button("Child: \(model.count)") { model.count += 1 } }
}

struct Parent: View {
    @State private var tick = 0
    var body: some View {
        VStack {
            Button("Parent: \(tick)") { tick += 1 }
            Child()
        }
    }
}
```
**Question:** Tap the child to 3, then tap the parent button. What does the child show?

**Answer:** `Child: 0`. The parent's `body` re-runs, creating a new `Child` struct and a new `CounterModel`. Fix: `@StateObject` (or `@State` with `@Observable`).

### Q131. `@State` initialized from an input `[Senior]`
```swift
struct Greeting: View {
    @State private var name: String
    init(name: String) { _name = State(initialValue: name) }
    var body: some View { Text("Hello, \(name)") }
}

// Parent shows Greeting(name: selectedUser.name), then selectedUser changes from "Ana" to "Ben"
```
**Answer:** Still shows `Hello, Ana`. `@State`'s initial value is only used the first time. Use a plain `let name: String`, a binding, or `.id(selectedUser.id)`.

### Q132. How often does `init` run? `[Senior]`
```swift
struct Row: View {
    let title: String
    init(title: String) {
        self.title = title
        print("Row init")
    }
    var body: some View { Text(title) }
}
// Row is inside a parent whose body re-runs every time a @State timer ticks each second.
```
**Answer:** `Row init` prints every second. View structs are recreated on every parent `body` evaluation. Keep initializers trivial.

### Q133. Animation placement `[Lead/Expert]`
```swift
Circle()
    .fill(isOn ? .green : .red)
    .animation(.easeInOut, value: isOn)
    .scaleEffect(isOn ? 1.5 : 1.0)
```
**Question:** When `isOn` toggles (without `withAnimation`), what animates?

**Answer:** The color animates, but the scale **jumps**. `.animation` applies to the modifiers inside it (above it in the chain), not to `scaleEffect` applied after it.

### Q134. Localization surprise `[Senior]`
```swift
let key = "welcome_message"
Text("welcome_message")   // A
Text(key)                 // B
```
**Answer:** A is localized (string literal → `LocalizedStringKey`). B shows the raw text `welcome_message` (a `String` variable uses the non-localizing initializer).

### Q135. Binding to an `@Observable` property `[Senior]`
```swift
@Observable final class Profile { var name = "" }

struct Editor: View {
    let profile: Profile
    var body: some View {
        TextField("Name", text: $profile.name)
    }
}
```
**Answer:** Compile error: `$profile` doesn't exist for a plain property. Mark it `@Bindable var profile: Profile`.

### Q136. Duplicate IDs `[Senior]`
```swift
let tags = ["swift", "ios", "swift"]
ForEach(tags, id: \.self) { Text($0) }
```
**Answer:** Undefined behavior: SwiftUI logs a warning, and rows may display or update incorrectly because two rows share the identity `"swift"`. Use unique identifiers.

### Q137. `onChange` on first appearance `[Fundamental]`
```swift
Text(filter)
    .onChange(of: filter) { print("changed") }
```
**Question:** Does it print when the view first appears?

**Answer:** No. It only fires on subsequent changes. Use `.onChange(of: filter, initial: true)` to run on appear as well.

### Q138. `.task` and navigation `[Senior]`
```swift
List(model.items) { item in NavigationLink(item.name, value: item) }
    .task { await model.load() }
```
**Question:** The user opens a detail screen and goes back. What happens?

**Answer:** `load()` runs again, because `.task` runs on every appearance. Guard with a "load if needed" check or use `.task(id:)` with a meaningful value.

### Q139. `GeometryReader` in a stack `[Senior]`
```swift
VStack {
    GeometryReader { proxy in
        Text("Width: \(proxy.size.width)")
    }
    Text("Footer")
}
```
**Answer:** The `GeometryReader` expands to take all available space, so the first text appears at the top-leading corner and the footer is pushed to the bottom. Constrain it with `.frame(height:)` or use `onGeometryChange`.

### Q140. Fine-grained observation `[Lead/Expert]`
```swift
@Observable final class Cart {
    var items: [Item] = []
    var couponCode = ""
}

struct CartBadge: View {
    let cart: Cart
    var body: some View { Text("\(cart.items.count)") }
}
```
**Question:** Does `CartBadge`'s `body` re-run when `couponCode` changes?

**Answer:** No. It only reads `items`. With `ObservableObject` + `@Published`, it **would** re-run, because any published change notifies all observers.

## 22. Senior / Lead Scenario Questions

### Q141. A SwiftUI screen feels sluggish. Walk through how you'd fix it. `[Lead/Expert]`
**Talking points:**
1. **Reproduce and measure**: Release build on an older device; Instruments SwiftUI template (body update counts and durations), Time Profiler, Hitches.
2. **Find excess updates**: `Self._printChanges()` on suspicious views; look for large `ObservableObject`s, broad dependencies, unstable IDs.
3. **Fix**: split views; narrow inputs; migrate to `@Observable`; stable `Identifiable` IDs; move sorting/filtering/formatting out of `body`; remove `AnyView`; use lazy containers; downsample images.
4. **Verify** with the same measurements; add a performance test or tracking to prevent regressions.

### Q142. Should a new app in 2026 be SwiftUI-first or UIKit-first? `[Lead/Expert]`
**Talking points:**
- Default today: **SwiftUI-first** with UIKit where needed. Most new APIs (Observation, widgets, visionOS, Liquid Glass components) are SwiftUI-centric.
- Deciding factors: minimum iOS version (iOS 17+ makes SwiftUI much more capable), team skills, complex custom UI requirements, performance-critical screens, existing UIKit components to reuse.
- Plan for interop from day one: clean boundaries, shared models, design tokens usable from both.

### Q143. Design the navigation for a large app with tabs, deep links, and authentication. `[Lead/Expert]`
**Talking points:**
- A root view switches between unauthenticated and authenticated flows based on session state.
- `TabView` with one `NavigationStack` per tab, each with its own router/path (typed `[Route]` enums per tab).
- A central deep link handler parses URLs/notifications into `(tab, [Route])`, selects the tab, dismisses sheets, and sets the path. If logged out, store the pending link and replay it after login.
- Routers are `@MainActor @Observable`, injected via the environment, and unit-tested without UI.
- Sheets are state-driven (`sheet(item:)` with an enum of sheet destinations).

### Q144. How would you choose a state management approach for a team of 10 engineers? `[Lead/Expert]`
**Talking points:**
- Criteria: app complexity, team experience, testability goals, deployment target, onboarding speed, third-party dependency tolerance.
- Options: `@Observable` models (+ optional per-screen view models), TCA, or a lightweight custom unidirectional store.
- Run a time-boxed spike on one real feature, compare readability, test coverage, and build times; document the decision in an ADR; create templates and examples so everyone follows the same patterns.

### Q145. Your app supports iOS 16, but you want Observation and new APIs. What's your plan? `[Lead/Expert]`
**Talking points:**
- Check adoption data: what share of users are on iOS 16? What's the business cost of dropping it?
- If you must keep iOS 16: use `ObservableObject` in shared code, or isolate iOS 17+ features behind `#available` with fallbacks; avoid maintaining two architectures long-term.
- Set a clear date to raise the minimum to iOS 17/18, then migrate to `@Observable` incrementally (Q35).

### Q146. How would you build a design system in SwiftUI? `[Lead/Expert]`
**Talking points:**
- A `DesignSystem` package: tokens (colors with Dark Mode, typography mapped to Dynamic Type text styles, spacing, radii).
- Styles over components where possible (`ButtonStyle`, `LabelStyle`, `ToggleStyle`), plus a few composite components (cards, empty states, banners).
- Theme via `@Entry` environment values; accessibility built in (scalable metrics, labels, contrast).
- A catalog app with previews of every component state; snapshot tests for each.
- Versioning, documentation (DocC), contribution guidelines, and UIKit bridges if the app is hybrid.

### Q147. How can memory leaks happen in SwiftUI, and how do you find them? `[Senior]`
**Talking points:**
- Views are structs and don't leak, but **reference types** do:
  - `@Observable` models storing closures that capture `self` (or capturing other models strongly in both directions).
  - Unstructured `Task`s started in models that loop forever (`for await` on a stream) without cancellation.
  - Timers, `NotificationCenter` observers, Combine `sink`s capturing `self`.
  - Singletons or environment objects holding references to screen-level models.
- Find them: Memory Graph Debugger, Instruments Leaks/Allocations, `deinit` logs in models, tests asserting deallocation.
- Prefer `.task` (auto-cancelled) over unstructured tasks started from `onAppear`.

### Q148. What do you look for when reviewing SwiftUI code? `[Lead/Expert]`
**Talking points:**
- **State ownership**: correct wrappers (`@State` private, no inline `@ObservedObject`), single source of truth, no duplicated state.
- **Identity**: stable IDs, no `UUID()` in `body`, no conditional-modifier `if` extensions hiding identity changes.
- **Performance**: no heavy work in `body`/`init`, small focused views, minimal `AnyView`.
- **Async**: `.task` instead of `onAppear { Task { } }`, cancellation handled, `@MainActor` models.
- **Accessibility and localization**: labels, Dynamic Type, `LocalizedStringKey` usage.
- **Testability**: logic outside views; dependencies injectable; previews for each state.

### Q149. How would you explain SwiftUI view identity to a junior engineer? `[Senior]`
**Talking points:**
- Analogy: identity is like a seat number in a theater. If the same person stays in seat 12, SwiftUI updates them in place (and keeps their memory/state). If the `if/else` swaps them for a different person, the old one leaves (state lost) and a new one arrives (transition).
- Show the counter-reset example (Q129) live; then fix it with a ternary.
- Follow with `ForEach` IDs and `.id()` as explicit seat numbers.

### Q150. How would you build an offline-first feed screen in SwiftUI? `[Lead/Expert]`
**Talking points:**
- **Data layer**: a repository that reads from a local store (SwiftData) and syncs with the server in the background; the UI observes the local store only (single source of truth).
- **UI**: `@Query` or an `@Observable` model fed by the repository; show cached data immediately, with a subtle refreshing indicator.
- **Sync**: cursor-based pagination, conflict resolution policy, retry with backoff, background refresh (`BGAppRefreshTask`).
- **Edge cases**: stale data indicators, pending local changes (outbox pattern), error states that don't wipe cached content.
