## 1. Fundamentals

### Q1. What problem does async/await solve? `[Fundamental]`
**Key points:**
- Before async/await, asynchronous code used **completion handlers**, which led to:
  - "Pyramid of doom" nesting.
  - Easy-to-miss paths where the completion is never called (or called twice).
  - Awkward error handling (`Result` everywhere) and manual thread hopping.
- async/await lets you write asynchronous code that **reads like synchronous code**, with normal control flow (`if`, loops, `try/catch`, `defer`), compiler-checked error propagation, and built-in cancellation.

```swift
// Completion handlers
func loadProfile(completion: @escaping (Result<Profile, Error>) -> Void) {
    fetchUser { userResult in
        switch userResult {
        case .failure(let error): completion(.failure(error))
        case .success(let user):
            fetchAvatar(for: user) { avatarResult in
                switch avatarResult {
                case .failure(let error): completion(.failure(error))
                case .success(let avatar): completion(.success(Profile(user: user, avatar: avatar)))
                }
            }
        }
    }
}

// async/await
func loadProfile() async throws -> Profile {
    let user = try await fetchUser()
    let avatar = try await fetchAvatar(for: user)
    return Profile(user: user, avatar: avatar)
}
```

### Q2. What does the `async` keyword mean? `[Fundamental]`
**Key points:**
- Marks a function (or closure, property getter, initializer) that **can suspend** while it waits for something.
- An `async` function can only be called from an asynchronous context, using `await`.
- `async` is part of the function's type: `() async -> Int` differs from `() -> Int`.

### Q3. What does `await` mean? `[Fundamental]`
**Key points:**
- Marks a **potential suspension point**: execution may pause here until the awaited work completes.
- While suspended, the **thread is freed** to run other work. The function resumes later, possibly on a different thread (unless it's isolated to an actor such as the main actor).
- `await` makes suspension visible in code, warning readers that state may have changed by the time execution resumes.

### Q4. What is the difference between suspending and blocking? `[Senior]`
| Blocking (e.g. `semaphore.wait()`, `sleep()`) | Suspending (`await`) |
|---|---|
| The thread sits idle, waiting | The thread is released to do other work |
| Wastes a scarce resource (threads) | Cheap: the function's state is saved on the heap |
| On the main thread: freezes the UI | On the main actor: UI stays responsive while waiting |
| Can deadlock or starve the cooperative pool | Designed for the cooperative thread pool |

- Interview phrase: **"`await` gives up the thread; blocking holds it hostage."**

### Q5. What is a suspension point, and what can happen at one? `[Senior]`
**Key points:**
- Only explicit `await` expressions can suspend (plus implicit points like the end of an `async let` scope).
- At a suspension point:
  - Other code may run on the same actor, so **actor state can change** (reentrancy; see the Concurrency file).
  - The task may be **cancelled**.
  - Execution may resume on a **different thread** (for non-actor-isolated code).
- Synchronous code between suspension points runs without interruption by other tasks on the same actor.

### Q6. How does async/await work under the hood (at a high level)? `[Lead/Expert]`
**Key points:**
- The compiler splits an async function into **partial functions** (continuations) at each suspension point.
- The function's local state lives in a heap-allocated **async frame** instead of the thread's stack, so the thread can be reused while the function is suspended.
- When the awaited operation finishes, the runtime schedules the continuation on the appropriate **executor**: the main actor's executor, an actor's serial executor, or the global concurrent executor (a cooperative thread pool roughly sized to the number of CPU cores).

### Q7. What is a `Task`? `[Fundamental]`
**Key points:**
- The **unit of asynchronous work** in Swift Concurrency. Every async function runs as part of some task.
- Tasks have a priority, cancellation state, and task-local values, and form a **hierarchy** (parent and child tasks) in structured concurrency.
- Kinds of tasks:
  - **Child tasks** (structured): `async let`, task groups.
  - **Unstructured tasks**: `Task { }` (inherits context) and `Task.detached { }` (doesn't).

### Q8. What is structured concurrency? `[Senior]`
**Key points:**
- Concurrency where the **lifetime of child tasks is bound to a scope**, like local variables:
  - A parent can't finish until all its children finish.
  - Cancelling a parent automatically cancels its children.
  - Errors propagate from children to the parent.
- Tools: `async let` and task groups.
- Benefits: no forgotten or leaked work, automatic cancellation propagation, and easier reasoning ("when this function returns, all its work is done").

```
loadDashboard()            ← parent task
 ├── async let profile     ← child task
 ├── async let orders      ← child task
 └── async let promotions  ← child task
(the function can't return until all three complete or are cancelled)
```

### Q9. How does async/await compare with GCD, completion handlers, and Combine? `[Senior]`
| | GCD + completion handlers | Combine | async/await |
|---|---|---|---|
| Readability | Nested callbacks | Operator chains | Linear, sequential-looking code |
| Errors | Manual (`Result`) | Typed `Failure`, terminates stream | `throws`, `try/catch` |
| Cancellation | Manual flags | `AnyCancellable` | Built in, cooperative, propagates to children |
| Threading | Manual queue hopping | Schedulers | Executors + actors, compiler-checked isolation |
| Thread explosion risk | Yes (many blocked threads) | Depends on schedulers | Cooperative pool avoids it |
| Best for | Legacy code, low-level control | Streams over time, reactive bindings | Most async work; streams via `AsyncSequence` |

### Q10. What are the minimum OS requirements for async/await? `[Fundamental]`
**Key points:**
- The language feature back-deploys to **iOS 13** (with Xcode 13.2+).
- Many system async APIs (`URLSession.data(from:)`, etc.) require **iOS 15+**. Some newer APIs (`Task.sleep(for:)`, `Clock`) require iOS 16+.
- On older targets, wrap callback APIs with continuations (Section 9).

## 2. Async Functions, Properties, Initializers & Protocols

### Q11. How do you declare async functions, throwing async functions, and async closures? `[Fundamental]`
```swift
func fetchTemperature() async -> Double { ... }                 // can suspend, can't throw
func fetchForecast(for city: String) async throws -> Forecast { ... }   // can suspend and throw

let loader: (URL) async throws -> Data = { url in
    let (data, _) = try await URLSession.shared.data(from: url)
    return data
}
```
- Order of keywords: `async throws` in declarations, `try await` at call sites.

### Q12. Can properties and subscripts be async? `[Senior]`
**Key points:**
- Read-only computed properties and subscripts can have `async` (and `throws`) getters. Setters can't be async.

```swift
struct RemoteDocument {
    let url: URL

    var contents: String {
        get async throws {
            let (data, _) = try await URLSession.shared.data(from: url)
            return String(decoding: data, as: UTF8.self)
        }
    }
}

let text = try await document.contents
```

### Q13. Can initializers be async? `[Senior]`
```swift
final class DatabaseConnection {
    private let handle: Handle

    init(url: URL) async throws {
        handle = try await Handle.open(url)   // initialization that needs async work
    }
}

let connection = try await DatabaseConnection(url: dbURL)
```
- Useful for types that can't exist until async setup completes. Alternatives: a static async factory method (`static func connect(...) async throws -> Self`), or a lightweight init plus an async `start()`.

### Q14. Can protocols declare async requirements? `[Senior]`
```swift
protocol UserRepository {
    func user(id: User.ID) async throws -> User
    var currentUser: User? { get async }
}

// A synchronous implementation can satisfy an async requirement
struct InMemoryUserRepository: UserRepository {
    var users: [User.ID: User]

    func user(id: User.ID) throws -> User {           // no async needed
        guard let user = users[id] else { throw RepositoryError.notFound }
        return user
    }

    var currentUser: User? { users.values.first }
}
```
- Making protocol requirements `async` gives implementations flexibility (network, database, cache, mocks).

### Q15. Can you overload a function on `async`? `[Senior]`
**Key points:**
- Yes. You can have a synchronous and an async version with the same name. The compiler prefers the **async** version in async contexts and the sync version in sync contexts.
- This is how many APIs offer both (and how Xcode's "Add Async Alternative" refactoring works).

### Q16. Why can't you use `await` inside `map`, `filter`, or `forEach`? `[Fundamental]`
**Key points:**
- Standard library higher-order functions take **synchronous** closures. An async closure can't be passed to them.
- Options: a `for` loop (sequential), a task group (concurrent), or an `AsyncSequence` with async `map`.

```swift
// ❌ Compile error: 'async' call in a function that does not support concurrency
let images = try urls.map { try await loadImage(from: $0) }

// ✅ Sequential
var images: [UIImage] = []
for url in urls {
    images.append(try await loadImage(from: url))
}

// ✅ Concurrent (see Section 5)
let concurrentImages = try await withThrowingTaskGroup(of: UIImage.self) { group in
    for url in urls { group.addTask { try await loadImage(from: url) } }
    return try await group.reduce(into: []) { $0.append($1) }   // completion order
}
```

### Q17. Can `defer` and `async` be used together? `[Senior]`
**Key points:**
- `defer` works normally in async functions: it runs when the scope exits, including after errors or cancellation.
- In mainstream Swift 6 releases, a `defer` block body **can't contain `await`**. Do async cleanup explicitly before returning or in a `catch`, or start a separate `Task` for non-critical async cleanup.

```swift
func refresh() async {
    isLoading = true
    defer { isLoading = false }          // runs no matter how the function exits
    await reloadData()
}
```

### Q18. What is the difference between `async` functions and functions that return a `Task`? `[Senior]`
**Key points:**
- An `async` function lets the **caller** decide how to run it (awaited in place, in `async let`, in a group) and keeps it part of the caller's task tree, so cancellation and errors propagate.
- A function that internally creates and returns `Task { }` starts **unstructured** work: the caller loses automatic cancellation, and the work keeps running even if the caller is cancelled.
- Prefer `async` functions in APIs; create `Task`s at the edges (UI event handlers, app entry points).

## 3. Calling Async Code

### Q19. How do you call an async function from synchronous code? `[Fundamental]`
**Key points:**
- Create a `Task`, which provides an async context.

```swift
// UIKit button action (synchronous)
@objc private func refreshTapped() {
    Task {
        await viewModel.refresh()
    }
}
```
- The synchronous function returns immediately; the task runs asynchronously.
- In SwiftUI, prefer `.task { }` for view-lifetime work (Section 14).

### Q20. What async entry points exist besides `Task`? `[Fundamental]`
```swift
// 1. An async main
@main
struct Tool {
    static func main() async throws {
        let data = try await fetchReport()
        print(data.count)
    }
}

// 2. Top-level code in main.swift / scripts can use await directly
let report = try await fetchReport()

// 3. SwiftUI's .task, .refreshable; async test methods; App Intents' perform() async
```

### Q21. Can you call a synchronous function from an async function? `[Fundamental]`
**Key points:**
- Yes, always. But a **long-running synchronous** call (heavy computation, blocking I/O) holds the thread for its whole duration. On the main actor it freezes the UI; on the cooperative pool it reduces available threads.
- Move heavy synchronous work off the main actor (Section 11) and avoid blocking calls in async code.

### Q22. Can you wait synchronously for an async function's result? `[Senior]`
**Key points:**
- Not safely. Patterns like blocking a semaphore until a `Task` finishes:
  - **Deadlock** if called on the main thread while the task needs the main actor.
  - **Starve** the cooperative thread pool if done inside async code.
- Redesign so the caller is async, or deliver the result via callback/state update.

```swift
// ❌ Deadlock risk: blocks the main thread while the Task needs the main actor
func loadSync() -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result = Data()
    Task { @MainActor in
        result = await loadData()
        semaphore.signal()
    }
    semaphore.wait()     // main thread blocked forever
    return result
}
```

### Q23. What does `await` on a `Task`'s `value` do? `[Fundamental]`
```swift
let task = Task { try await api.fetchConfig() }

// Later, anywhere async:
let config = try await task.value      // waits for completion, rethrows errors
let outcome = await task.result        // Result<Config, Error>, never throws
```
- Several callers can await the same task's value; the work runs once. This is useful for deduplicating requests (Q114).

### Q24. When should you create a `Task` vs make the function `async`? `[Senior]`
**Key points:**
- Make the function `async` when the caller is already async and should wait for the result, or when cancellation/errors should propagate.
- Create a `Task` only at boundaries where you **can't** be async: UI event handlers, delegate callbacks, notification handlers, app lifecycle callbacks.
- Code-review smell: `Task { }` sprinkled deep inside business logic ("fire and forget"), which makes testing, ordering, and cancellation unpredictable.

### Q25. What is the ordering of tasks created in sequence? `[Senior]`
**Key points:**
- Unstructured tasks have **no guaranteed execution order**, even when created one after another, unless they're isolated to the same actor (where they're enqueued roughly in order but can still interleave at suspension points).
- If order matters, do the work sequentially in **one** task, or use an `AsyncStream` as a serial queue of work items.

```swift
// ❌ No guarantee "save" finishes before "upload" starts
Task { await store.save(draft) }
Task { await uploader.upload(draft) }

// ✅ Explicit ordering
Task {
    await store.save(draft)
    await uploader.upload(draft)
}
```

## 4. Structured Concurrency: `async let`

### Q26. What is `async let`? `[Fundamental]`
**Key points:**
- Starts a **child task** that runs concurrently with the current code. You `await` its value later.
- Best for a **fixed, known number** of independent operations.

```swift
func loadDashboard() async throws -> Dashboard {
    async let profile = api.fetchProfile()          // starts immediately
    async let orders = api.fetchOrders()            // runs concurrently
    async let promotions = api.fetchPromotions()    // runs concurrently

    return try await Dashboard(profile: profile, orders: orders, promotions: promotions)
}
// Total time ≈ the slowest request, not the sum of all three
```

### Q27. What's the difference between sequential `await`s and `async let`? `[Fundamental]`
```swift
// Sequential: ~3 seconds if each call takes ~1 second
let a = try await fetchA()
let b = try await fetchB()
let c = try await fetchC()

// Concurrent: ~1 second
async let a2 = fetchA()
async let b2 = fetchB()
async let c2 = fetchC()
let results = try await (a2, b2, c2)
```
- Only use concurrency for **independent** work. If `fetchB` needs `a`'s result, it must be sequential.

### Q28. What happens if you never await an `async let`? `[Senior]`
**Key points:**
- When the scope exits, the child task is **implicitly cancelled and awaited**. The function doesn't return until it finishes, and its result (or error) is discarded.
- This guarantees no child outlives its scope, but it can surprise you: an unawaited slow `async let` still delays the function's return (until it responds to cancellation).

### Q29. How do errors work with `async let`? `[Lead/Expert]`
**Key points:**
- An error from a child surfaces only when you **await that child**.
- `async let` doesn't fail fast on its own: if you await `a` first and `b` fails early, you still wait for `a` to finish before you see `b`'s error. When the error propagates out of the scope, remaining children are cancelled and awaited.
- If you need **fail-fast** behavior (cancel everything as soon as any child fails), use a throwing task group and consume results with `next()`.

```swift
async let slow = fetchSlow()     // takes 5s
async let fast = fetchFast()     // fails after 0.1s

// Awaiting `slow` first: you see fast's error only after ~5s
let result = try await (slow, fast)
```

### Q30. Can you use `async let` in a loop or with a dynamic number of operations? `[Senior]`
**Key points:**
- No. Each `async let` is a fixed binding in a scope; you can't create an array of them. For a dynamic count, use a **task group**.

### Q31. Does `async let` inherit the current actor and priority? `[Senior]`
**Key points:**
- Child tasks inherit **priority** and **task-local values**, and they're cancelled with the parent.
- The child's work runs according to the isolation of the function being called: a `@MainActor` function still runs on the main actor; a nonisolated async function runs per the rules in Q86–Q87.

## 5. Task Groups

### Q32. What is a task group? `[Fundamental]`
**Key points:**
- A structured way to run a **dynamic number** of child tasks concurrently and collect their results.
- All child tasks must finish (or be cancelled) before the group returns.

```swift
func fetchThumbnails(for ids: [Photo.ID]) async throws -> [Photo.ID: UIImage] {
    try await withThrowingTaskGroup(of: (Photo.ID, UIImage).self) { group in
        for id in ids {
            group.addTask {
                (id, try await thumbnailService.thumbnail(for: id))
            }
        }

        var thumbnails: [Photo.ID: UIImage] = [:]
        for try await (id, image) in group {      // results arrive in completion order
            thumbnails[id] = image
        }
        return thumbnails
    }
}
```
- Swift 6.1 can often infer the child result type, so `of:` may be omitted.

### Q33. What is the difference between `withTaskGroup` and `withThrowingTaskGroup`? How do errors behave? `[Senior]`
**Key points:**
- `withTaskGroup`: child tasks can't throw.
- `withThrowingTaskGroup`: child tasks can throw. A child's error propagates **when you observe that child's result** (`next()`, `for try await`, `waitForAll()`).
- If the group's body throws (for example, rethrowing a child error from `next()`), the group **cancels all remaining children** and waits for them before rethrowing.
- Child errors you never observe are not propagated, so always consume results (or call `waitForAll()`) in throwing groups.

### Q34. In what order do task group results arrive? How do you preserve input order? `[Senior]`
**Key points:**
- Results arrive in **completion order**, not the order tasks were added.
- To preserve order, return the index with each result and reassemble.

```swift
func loadAll(_ urls: [URL]) async throws -> [Data] {
    try await withThrowingTaskGroup(of: (Int, Data).self) { group in
        for (index, url) in urls.enumerated() {
            group.addTask { (index, try await download(url)) }
        }

        var results = [Data?](repeating: nil, count: urls.count)
        for try await (index, data) in group {
            results[index] = data
        }
        return results.compactMap { $0 }
    }
}
```

### Q35. How do you limit the number of concurrent child tasks? `[Lead/Expert]`
**Key points:**
- Start only N tasks; each time one finishes, add the next. This avoids flooding the network or memory with thousands of simultaneous operations.

```swift
func downloadAll(_ urls: [URL], maxConcurrent: Int = 4) async throws -> [URL: Data] {
    try await withThrowingTaskGroup(of: (URL, Data).self) { group in
        var results: [URL: Data] = [:]
        var pending = urls.makeIterator()

        // Start the first batch
        for _ in 0..<maxConcurrent {
            guard let url = pending.next() else { break }
            group.addTask { (url, try await download(url)) }
        }

        // Each completion frees a slot for the next URL
        while let (url, data) = try await group.next() {
            results[url] = data
            if let nextURL = pending.next() {
                group.addTask { (nextURL, try await download(nextURL)) }
            }
        }
        return results
    }
}
```

### Q36. What do `cancelAll()` and `addTaskUnlessCancelled` do? `[Senior]`
**Key points:**
- `group.cancelAll()`: cancels all running children (cooperatively) and marks the group cancelled.
- `group.addTaskUnlessCancelled { }`: adds a child only if the group (or parent task) isn't cancelled. Returns `false` otherwise, avoiding pointless new work.
- Adding a task to a cancelled group with `addTask` still starts it, but it begins already cancelled.

### Q37. What are discarding task groups? `[Lead/Expert]`
**Key points:**
- `withDiscardingTaskGroup` / `withThrowingDiscardingTaskGroup` (Swift 5.9): child results are **discarded** as soon as each task finishes, so memory doesn't grow with completed tasks.
- Ideal for long-running "fire many side effects" work, such as handling incoming connections or processing a stream of events.
- In the throwing version, the **first child error** cancels the whole group and is rethrown, giving fail-fast behavior without manually calling `next()`.

```swift
try await withThrowingDiscardingTaskGroup { group in
    for try await connection in server.connections {
        group.addTask { try await handle(connection) }   // results not collected
    }
}
```

### Q38. How do you get the first result and cancel the rest (racing)? `[Senior]`
```swift
func fastestMirror(_ mirrors: [URL]) async throws -> Data {
    try await withThrowingTaskGroup(of: Data.self) { group in
        for mirror in mirrors {
            group.addTask { try await download(mirror) }
        }
        guard let first = try await group.next() else {
            throw DownloadError.noMirrors
        }
        group.cancelAll()            // stop the slower downloads
        return first
    }
}
```
- Note: if the first child to finish **throws**, `next()` rethrows and the whole group fails. To return the first **successful** result, catch errors inside each child (return an optional or `Result`) and keep calling `next()` until you get a success.

### Q39. Can child tasks mutate a shared variable? `[Senior]`
**Key points:**
- No. `addTask` closures are `@Sendable`/`sending`, so they can't capture and mutate local `var`s, which prevents data races at compile time.
- Instead, **return** values from children and collect them in the group's body, which runs serially.

```swift
// ❌ Compile error: mutation of captured var in concurrently-executing code
var total = 0
await withTaskGroup(of: Void.self) { group in
    for file in files { group.addTask { total += await size(of: file) } }
}

// ✅ Return values and aggregate in the body
let total2 = await withTaskGroup(of: Int.self) { group in
    for file in files { group.addTask { await size(of: file) } }
    return await group.reduce(0, +)
}
```

### Q40. When do you use `async let`, a task group, or `Task`? `[Senior]`
| Tool | Number of tasks | Structured? | Typical use |
|---|---|---|---|
| `async let` | Fixed, known at compile time | ✅ | Load profile + orders + settings concurrently |
| Task group | Dynamic | ✅ | Download N images; process a list in parallel |
| Discarding task group | Dynamic, results unneeded | ✅ | Handle a stream of events/connections |
| `Task { }` | One | ❌ (inherits context) | Start async work from sync code (UI events) |
| `Task.detached { }` | One | ❌ (no inheritance) | Rare: independent work that must not inherit actor/priority |

- Rule of thumb: **prefer structured concurrency**; use unstructured tasks only at boundaries.

## 6. Unstructured Tasks: `Task` & `Task.detached`

### Q41. What does `Task { }` inherit from its creator? `[Senior]`
**Key points:**
- **Actor isolation** (e.g. created on the main actor → the closure body runs on the main actor).
- **Priority**.
- **Task-local values**.
- It does **not** inherit cancellation, and it's not a child: cancelling the creating task doesn't cancel it, and the creator doesn't wait for it.

```swift
@MainActor
final class ProfileViewModel {
    var name = ""

    func load() {
        Task {                                   // runs on the main actor (inherited)
            let profile = try await api.fetchProfile()  // suspends; main thread stays free
            name = profile.name                  // safe: back on the main actor
        }
    }
}
```

### Q42. What is `Task.detached`, and how does it differ? `[Senior]`
**Key points:**
- Creates an unstructured task that inherits **nothing**: no actor isolation, no priority, no task-local values.
- Runs on the global concurrent executor.

```swift
@MainActor
func exportTapped() {
    Task.detached(priority: .utility) { [document] in
        let pdf = PDFRenderer.render(document)   // CPU-heavy, off the main actor
        await MainActor.run {
            self.shareSheet(for: pdf)            // hop back explicitly for UI
        }
    }
}
```

### Q43. When should you use `Task.detached`? `[Lead/Expert]`
**Key points:**
- Rarely. Apple's guidance is to prefer `Task { }` or structured concurrency.
- Valid cases: work that must not inherit the current actor (e.g. heavy synchronous CPU work started from the main actor), or that must not inherit task-local values or priority (e.g. a low-priority cleanup job started from a high-priority context).
- In Swift 6.2+, a `@concurrent` async function (Q86) is often a clearer way to say "run this off the actor" than `Task.detached`.

### Q44. How do you store and cancel an unstructured task? `[Fundamental]`
```swift
final class SearchController {
    private var searchTask: Task<Void, Never>?

    func search(_ query: String) {
        searchTask?.cancel()                    // cancel the previous search
        searchTask = Task {
            let results = (try? await api.search(query)) ?? []
            guard !Task.isCancelled else { return }
            render(results)
        }
    }

    deinit {
        searchTask?.cancel()
    }
}
```

### Q45. What's new for creating tasks in Swift 6.2? `[Lead/Expert]`
**Key points (verify against the latest release notes):**
- **Task names**: `Task(name: "LoadFeed") { ... }` makes tasks identifiable in debugging and Instruments.
- **`Task.immediate`**: starts running **synchronously** on the current executor until its first suspension point, instead of being enqueued. Useful when work must begin right away (e.g. updating UI state immediately in an event handler before the first `await`).

```swift
@MainActor
func likeTapped() {
    Task.immediate {
        isLiked = true                  // runs right now, before likeTapped() returns
        try? await api.like(postID)     // then suspends like a normal task
    }
}
```

### Q46. Is an unstructured `Task` cancelled when the task that created it is cancelled? `[Senior]`
**Key points:**
- **No.** This is a common misconception. Unstructured tasks are independent; you must cancel them yourself (keep a handle).
- Child tasks from `async let` and task groups **are** cancelled with their parent.

### Q47. What are the problems with "fire-and-forget" tasks? `[Senior]`
**Key points:**
- Errors thrown inside them are **silently discarded** unless someone awaits `value` (Q62).
- No cancellation: work continues after the screen or object is gone.
- No ordering guarantees between multiple tasks (Q25).
- Hard to test: tests can't await completion.
- They keep captured objects alive until they finish (Section 15).

### Q48. What happens to a running `Task` when the object that created it is deallocated? `[Senior]`
**Key points:**
- Nothing, by default: the task keeps running until it completes. If it captured `self` strongly, `self` **can't be deallocated** until the task finishes.
- Dropping the `Task` handle doesn't cancel it (unlike Combine's `AnyCancellable`). Cancel explicitly when the owner goes away, or use structured APIs like SwiftUI's `.task` that cancel automatically.

## 7. Cancellation

### Q49. How does cancellation work in Swift Concurrency? `[Fundamental]`
**Key points:**
- Cancellation is **cooperative**: calling `task.cancel()` only sets a flag. Nothing is forcibly stopped.
- Code must check the flag and stop early, typically by throwing `CancellationError` or returning partial results.
- Cancellation **propagates to child tasks** (structured), but not to unstructured tasks.

### Q50. How do you check for cancellation? `[Fundamental]`
```swift
func processAll(_ items: [Item]) async throws -> [Output] {
    var outputs: [Output] = []
    for item in items {
        try Task.checkCancellation()            // throws CancellationError if cancelled
        outputs.append(try await process(item))
    }
    return outputs
}

func loadPreview() async -> Preview? {
    guard !Task.isCancelled else { return nil } // non-throwing check: return early
    return await renderPreview()
}
```
- Use `checkCancellation()` in throwing contexts; `Task.isCancelled` when you want to return partial results or clean up gracefully.

### Q51. Which APIs respond to cancellation automatically? `[Senior]`
**Key points:**
- `Task.sleep` throws `CancellationError` immediately.
- `URLSession` async methods cancel the underlying request and throw **`URLError(.cancelled)`**, not `CancellationError`.
- `AsyncStream` iteration ends (returns `nil`) when the consuming task is cancelled.
- Task groups and `async let` propagate cancellation to children.
- Your own CPU-bound loops do **not** stop unless you check.

```swift
func isCancellation(_ error: Error) -> Bool {
    error is CancellationError || (error as? URLError)?.code == .cancelled
}
```

### Q52. What is `withTaskCancellationHandler`? `[Lead/Expert]`
**Key points:**
- Runs an `onCancel` closure **immediately** when the task is cancelled, even while the operation is suspended. Used to cancel non-Swift-Concurrency work (callback APIs, `URLSessionTask`, custom operations).
- `onCancel` may run concurrently with the operation, on any thread, so it must be thread-safe.

```swift
func download(_ url: URL) async throws -> Data {
    let box = TaskBox()   // thread-safe holder for the URLSessionDataTask (e.g. using a lock)

    return try await withTaskCancellationHandler {
        try await withCheckedThrowingContinuation { continuation in
            let task = URLSession.shared.dataTask(with: url) { data, _, error in
                if let error {
                    continuation.resume(throwing: error)
                } else {
                    continuation.resume(returning: data ?? Data())
                }
            }
            box.set(task)
            task.resume()
        }
    } onCancel: {
        box.cancel()    // cancelling the URLSessionDataTask makes its callback fire with an error
    }
}
```
- If cancellation happens before `onCancel` is installed, it runs immediately. Handle the race where `onCancel` runs before `box.set(task)` (e.g. the box remembers it was cancelled and cancels the task when it's set).

### Q53. How does cancellation propagate in structured vs unstructured concurrency? `[Senior]`
```
Task A (cancelled)
 ├── async let B        → cancelled automatically
 ├── group child C      → cancelled automatically
 │    └── async let D   → cancelled automatically
 └── Task { E }         → NOT cancelled (unstructured)
```
- Cancellation flows **down** the tree, never up: a cancelled child doesn't cancel its parent (but its thrown `CancellationError` may propagate up as an error).

### Q54. How should UI code treat cancellation errors? `[Senior]`
**Key points:**
- Cancellation is usually **expected** (user left the screen, typed a new query). Don't show an error alert for it.

```swift
func load() async {
    do {
        items = try await api.fetchItems()
    } catch is CancellationError {
        // superseded or view disappeared: ignore
    } catch let error as URLError where error.code == .cancelled {
        // URLSession cancellation: ignore
    } catch {
        errorMessage = error.localizedDescription
    }
}
```

### Q55. How do you clean up when a task is cancelled? `[Senior]`
**Key points:**
- `defer` runs on every exit path, including cancellation errors.
- For resources managed outside Swift Concurrency, use `withTaskCancellationHandler`.
- For streams, use `AsyncStream`'s `onTermination` (Q76).

```swift
func record() async throws {
    let session = try AudioSession.start()
    defer { session.stop() }               // runs even if cancelled
    while true {
        try Task.checkCancellation()
        try await session.captureNextBuffer()
    }
}
```

### Q56. How do you make a CPU-bound loop cancellable and cooperative? `[Lead/Expert]`
```swift
func computeHashes(for chunks: [Data]) async throws -> [String] {
    var hashes: [String] = []
    for (index, chunk) in chunks.enumerated() {
        if index.isMultiple(of: 100) {
            try Task.checkCancellation()   // respond to cancellation
            await Task.yield()             // let other tasks use this thread
        }
        hashes.append(sha256(chunk))
    }
    return hashes
}
```
- Without these checks, a cancelled task keeps burning CPU, and a long loop monopolizes a cooperative-pool thread.

### Q57. What's wrong with `try? await Task.sleep(...)`? `[Senior]`
**Key points:**
- `Task.sleep` throws `CancellationError` when cancelled. `try?` **swallows** it, so the code continues immediately as if the sleep completed, defeating cancellation.

```swift
// ❌ After cancellation, this immediately continues and fetches anyway
try? await Task.sleep(for: .seconds(0.3))
let results = try await api.search(query)

// ✅ Let cancellation propagate (or check explicitly)
try await Task.sleep(for: .seconds(0.3))
let results2 = try await api.search(query)
```

## 8. Error Handling

### Q58. How do errors propagate in async code? `[Fundamental]`
**Key points:**
- Exactly like synchronous throwing code: `try await` propagates errors to the caller; `do/catch` handles them.
- In structured concurrency, child errors propagate to the parent when awaited (Q29, Q33).

```swift
func loadSettings() async -> Settings {
    do {
        return try await api.fetchSettings()
    } catch {
        logger.error("Settings failed: \(error)")
        return .defaults
    }
}
```

### Q59. Can async functions use typed throws? `[Senior]`
```swift
enum ProfileError: Error {
    case notFound
    case network(URLError)
}

func fetchProfile(id: String) async throws(ProfileError) -> Profile {
    do {
        let (data, _) = try await URLSession.shared.data(from: profileURL(id))
        guard let profile = try? JSONDecoder().decode(Profile.self, from: data) else {
            throw ProfileError.notFound
        }
        return profile
    } catch let error as URLError {
        throw .network(error)
    } catch let error as ProfileError {
        throw error
    } catch {
        throw .notFound
    }
}
```
- Swift 6 supports typed throws in async functions. As with sync code, prefer untyped `throws` for most public APIs, and typed throws for closed, internal error sets.

### Q60. How do `Task.value` and `Task.result` differ? `[Fundamental]`
**Key points:**
- `try await task.value` rethrows the task's error.
- `await task.result` returns a `Result<Success, Failure>` without throwing, which is useful for collecting outcomes of several tasks.

### Q61. How do you allow partial failures when running many tasks? `[Senior]`
```swift
func loadWidgets(_ ids: [Widget.ID]) async -> [Widget.ID: Result<Widget, Error>] {
    await withTaskGroup(of: (Widget.ID, Result<Widget, Error>).self) { group in
        for id in ids {
            group.addTask {
                do { return (id, .success(try await api.fetchWidget(id))) }
                catch { return (id, .failure(error)) }      // a failure doesn't cancel siblings
            }
        }
        var results: [Widget.ID: Result<Widget, Error>] = [:]
        for await (id, result) in group {
            results[id] = result
        }
        return results
    }
}
```
- A non-throwing group with `Result` values lets the screen render successful widgets and show placeholders for failed ones.

### Q62. What happens to an error thrown inside `Task { }` that nobody awaits? `[Senior]`
**Key points:**
- It's **silently discarded**. The compiler doesn't force you to handle it, because `Task<Success, Error>` stores the error until someone reads `value`.
- Always handle errors inside fire-and-forget tasks (log, update UI state), or keep the handle and await it.

```swift
// ❌ Errors vanish silently
Task {
    try await syncService.sync()
}

// ✅ Handle errors explicitly
Task {
    do {
        try await syncService.sync()
    } catch {
        logger.error("Sync failed: \(error)")
        syncStatus = .failed
    }
}
```

## 9. Continuations: Bridging Callbacks & Delegates

### Q63. What is a continuation? `[Fundamental]`
**Key points:**
- An object representing the **rest of a suspended async function**. You receive it from `withCheckedContinuation` (and friends), hand it to callback-based code, and call `resume` when the result is ready.
- It's how you convert completion-handler and delegate APIs into `async` functions.

### Q64. How do you wrap a completion-handler API with a continuation? `[Fundamental]`
```swift
// Legacy API
func fetchUser(id: Int, completion: @escaping (Result<User, Error>) -> Void) { ... }

// Async wrapper
func fetchUser(id: Int) async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        fetchUser(id: id) { result in
            continuation.resume(with: result)      // resumes exactly once
        }
    }
}

// Non-throwing variant
func currentBatteryLevel() async -> Float {
    await withCheckedContinuation { continuation in
        deviceMonitor.readBattery { level in
            continuation.resume(returning: level)
        }
    }
}
```

### Q65. What is the difference between checked and unsafe continuations? `[Senior]`
| `withCheckedContinuation` / `withCheckedThrowingContinuation` | `withUnsafeContinuation` / `withUnsafeThrowingContinuation` |
|---|---|
| Runtime checks for misuse | No checks |
| Resuming twice → **crash** with a clear message | Undefined behavior |
| Never resuming → runtime **warning** logged (task leaks) | Silent leak |
| Tiny overhead | Slightly faster |

- Use **checked** by default. Switch to unsafe only for proven hot paths after the code is well tested.

### Q66. What are the rules for resuming a continuation? `[Senior]`
**Key points:**
- Resume **exactly once** on every code path.
  - **Never resuming**: the awaiting task hangs forever (a leaked task); checked continuations log a "leaked its continuation" warning.
  - **Resuming twice**: crash (checked) or undefined behavior (unsafe).
- Watch for callback APIs that may call back **multiple times** (progress + completion) or **never** (on some error paths). Guard with a flag or use `AsyncStream` for multi-value callbacks.

```swift
func requestPermission() async -> Bool {
    await withCheckedContinuation { continuation in
        permissionManager.request { granted, error in
            // ❌ Bug: if both `error` and the fallthrough path execute, we resume twice
            // ✅ Make every path resume exactly once
            if error != nil {
                continuation.resume(returning: false)
                return
            }
            continuation.resume(returning: granted)
        }
    }
}
```

### Q67. How do you bridge a one-shot delegate API to async? `[Lead/Expert]`
```swift
@MainActor
final class LocationProvider: NSObject, CLLocationManagerDelegate {
    private let manager = CLLocationManager()
    private var continuation: CheckedContinuation<CLLocation, Error>?

    override init() {
        super.init()
        manager.delegate = self
    }

    func currentLocation() async throws -> CLLocation {
        guard continuation == nil else { throw LocationError.requestInProgress }   // one request at a time
        return try await withCheckedThrowingContinuation { continuation in
            self.continuation = continuation
            manager.requestLocation()
        }
    }

    nonisolated func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
        MainActor.assumeIsolated {     // the manager calls back on the thread that created it (main)
            guard let location = locations.last else { return }
            continuation?.resume(returning: location)
            continuation = nil         // prevent double resume
        }
    }

    nonisolated func locationManager(_ manager: CLLocationManager, didFailWithError error: Error) {
        MainActor.assumeIsolated {
            continuation?.resume(throwing: error)
            continuation = nil
        }
    }
}

enum LocationError: Error { case requestInProgress }
```
**Talking points:** store the continuation, resume it from delegate callbacks, set it to `nil` after resuming, and reject concurrent requests (or queue them).
- On iOS 17+, `CLLocationUpdate.liveUpdates()` provides a native `AsyncSequence`.

### Q68. How do you support cancellation in a continuation-based wrapper? `[Lead/Expert]`
**Key points:**
- Continuations don't know about cancellation. Wrap them in `withTaskCancellationHandler` and cancel the underlying operation in `onCancel`; the underlying API's callback then resumes the continuation with an error (see Q52).
- Make sure cancellation still results in **exactly one** resume.

### Q69. How are Objective-C completion-handler APIs imported into Swift? `[Senior]`
**Key points:**
- Objective-C methods whose last parameter is a completion block are automatically imported with an `async` variant.

```swift
// Objective-C: - (void)requestAuthorizationWithOptions:(...) completionHandler:(void (^)(BOOL, NSError *))handler;
let granted = try await UNUserNotificationCenter.current()
    .requestAuthorization(options: [.alert, .badge, .sound])

// PhotoKit, HealthKit, StoreKit, Contacts, and many other frameworks gained async methods this way
```

## 10. `AsyncSequence` & `AsyncStream`

### Q70. What is an `AsyncSequence`? `[Fundamental]`
**Key points:**
- Like `Sequence`, but each element is produced **asynchronously**. You iterate with `for await` (or `for try await` if it can throw).
- The iterator's `next()` is `async` and returns `nil` when the sequence ends.
- The loop suspends between elements, so it doesn't block.

```swift
for try await line in fileURL.lines {
    print(line)
}
```

### Q71. What built-in async sequences exist? `[Fundamental]`
```swift
// Lines and bytes from files and URLs
for try await line in url.lines { }
let (bytes, _) = try await URLSession.shared.bytes(from: url)
for try await byte in bytes { }

// Notifications
for await notification in NotificationCenter.default.notifications(named: .NSCalendarDayChanged) { }

// Combine publishers (iOS 15+)
for await value in publisher.values { }

// Framework APIs: StoreKit Transaction.updates, CLLocationUpdate.liveUpdates(),
// CLMonitor events, Network framework, MusicKit, etc.
for await update in Transaction.updates { }
```

### Q72. What operators can you use on an `AsyncSequence`? `[Senior]`
```swift
let errorLines = logURL.lines
    .filter { $0.contains("ERROR") }
    .map { $0.uppercased() }
    .prefix(10)

for try await line in errorLines { print(line) }

let firstMatch = try await logURL.lines.first { $0.hasPrefix("FATAL") }
let lineCount = try await logURL.lines.reduce(0) { count, _ in count + 1 }
let hasWarnings = try await logURL.lines.contains { $0.contains("WARN") }
```
- Built in: `map`, `compactMap`, `flatMap`, `filter`, `prefix`, `dropFirst`, `drop(while:)`, `first(where:)`, `contains`, `reduce`, `min`, `max`, `allSatisfy`.
- Apple's **swift-async-algorithms** package adds time- and combination-based operators: `debounce`, `throttle`, `merge`, `combineLatest`, `zip`, `chunked`, `AsyncChannel`, `AsyncTimerSequence`.

### Q73. What is `AsyncStream`, and how do you create one from callbacks? `[Senior]`
**Key points:**
- The easiest way to create your own `AsyncSequence`: you get a **continuation** and call `yield(_:)` for each value and `finish()` at the end.
- Ideal for bridging **multi-value** callbacks, delegates, and notifications.

```swift
final class BatteryMonitor {
    func levels() -> AsyncStream<Float> {
        AsyncStream { continuation in
            UIDevice.current.isBatteryMonitoringEnabled = true
            let observer = NotificationCenter.default.addObserver(
                forName: UIDevice.batteryLevelDidChangeNotification, object: nil, queue: .main
            ) { _ in
                continuation.yield(UIDevice.current.batteryLevel)
            }
            continuation.onTermination = { _ in
                NotificationCenter.default.removeObserver(observer)   // cleanup when the consumer stops
            }
        }
    }
}

// Consumer
for await level in monitor.levels() {
    batteryLabel.text = "\(Int(level * 100))%"
}
```

### Q74. What is `AsyncStream.makeStream(of:)`? `[Senior]`
**Key points:**
- Swift 5.9 API that returns the stream **and** its continuation as a pair. It's cleaner when the producer lives outside the stream's closure (e.g. a class that yields events from several methods).

```swift
final class ChatConnection {
    let messages: AsyncStream<Message>
    private let continuation: AsyncStream<Message>.Continuation

    init() {
        (messages, continuation) = AsyncStream.makeStream(of: Message.self,
                                                          bufferingPolicy: .bufferingNewest(100))
    }

    func didReceive(_ message: Message) {   // called by the socket delegate
        continuation.yield(message)
    }

    func close() {
        continuation.finish()
    }
}
```

### Q75. What buffering policies does `AsyncStream` support? `[Senior]`
| Policy | Behavior when the consumer is slower than the producer |
|---|---|
| `.unbounded` (default) | Buffers everything; memory can grow without limit |
| `.bufferingOldest(n)` | Keeps the oldest n values; drops new ones when full |
| `.bufferingNewest(n)` | Keeps the newest n values; drops old ones when full |

- `.bufferingNewest(1)` is ideal for "latest state" streams (location, progress), where only the most recent value matters.
- `yield` returns a `YieldResult` (`.enqueued`, `.dropped`, `.terminated`) if you need to know what happened.

### Q76. What is `onTermination`, and why is it important? `[Senior]`
**Key points:**
- Called when the stream ends: either the producer calls `finish()`, or the **consumer stops** (breaks out of the loop or its task is cancelled).
- Use it to stop the underlying work: remove observers, stop sensors, cancel network tasks. Forgetting it leaks resources that keep producing values nobody reads.

### Q77. Build an `AsyncThrowingStream` that reports download progress. `[Lead/Expert]`
```swift
enum DownloadEvent: Sendable {
    case progress(Double)
    case finished(Data)
}

func download(_ url: URL) -> AsyncThrowingStream<DownloadEvent, Error> {
    AsyncThrowingStream { continuation in
        let task = Task {
            do {
                let (bytes, response) = try await URLSession.shared.bytes(from: url)
                let expected = response.expectedContentLength
                var data = Data()
                if expected > 0 { data.reserveCapacity(Int(expected)) }

                for try await byte in bytes {
                    data.append(byte)
                    if expected > 0, data.count.isMultiple(of: 64 * 1024) {
                        continuation.yield(.progress(Double(data.count) / Double(expected)))
                    }
                }
                continuation.yield(.finished(data))
                continuation.finish()
            } catch {
                continuation.finish(throwing: error)
            }
        }
        continuation.onTermination = { _ in task.cancel() }   // consumer stopped → cancel download
    }
}

// Consumer
for try await event in download(fileURL) {
    switch event {
    case .progress(let fraction): progressView.progress = Float(fraction)
    case .finished(let data): save(data)
    }
}
```
- Byte-by-byte iteration is simple but slow for large files; production code would use a `URLSessionDownloadDelegate` (or the per-task `delegate:` parameter) for progress.

### Q78. How do you write a custom `AsyncSequence`? `[Lead/Expert]`
```swift
/// Fetches pages until the API returns an empty page
struct PagedResults<Item: Sendable>: AsyncSequence {
    typealias Element = [Item]
    let fetchPage: @Sendable (Int) async throws -> [Item]

    struct AsyncIterator: AsyncIteratorProtocol {
        let fetchPage: @Sendable (Int) async throws -> [Item]
        var page = 0
        var isFinished = false

        mutating func next() async throws -> [Item]? {
            guard !isFinished else { return nil }
            try Task.checkCancellation()
            let items = try await fetchPage(page)
            if items.isEmpty {
                isFinished = true
                return nil
            }
            page += 1
            return items
        }
    }

    func makeAsyncIterator() -> AsyncIterator {
        AsyncIterator(fetchPage: fetchPage)
    }
}

// Usage
for try await page in PagedResults(fetchPage: { try await api.products(page: $0) }) {
    products.append(contentsOf: page)
}
```
- Swift 6 adds a `Failure` associated type to `AsyncSequence` (typed throws), so non-throwing sequences no longer need `try`.

### Q79. Can multiple consumers iterate the same `AsyncStream`? `[Lead/Expert]`
**Key points:**
- No. `AsyncStream` is designed for a **single consumer**. Concurrent iteration from multiple tasks isn't supported and can trap at runtime.
- For broadcasting to several consumers: create one stream per consumer (the producer keeps a list of continuations), or use a library solution. `@Observable` state (with Swift 6.2's `Observations`) also works for "latest value" broadcasting.

```swift
actor EventBroadcaster<Event: Sendable> {
    private var continuations: [UUID: AsyncStream<Event>.Continuation] = [:]

    func subscribe() -> AsyncStream<Event> {
        let (stream, continuation) = AsyncStream.makeStream(of: Event.self)
        let id = UUID()
        continuations[id] = continuation
        continuation.onTermination = { [weak self] _ in
            Task { await self?.remove(id) }
        }
        return stream
    }

    func send(_ event: Event) {
        for continuation in continuations.values { continuation.yield(event) }
    }

    private func remove(_ id: UUID) { continuations[id] = nil }
}
```

### Q80. How do you create a polling stream? `[Senior]`
```swift
// AsyncStream(unfolding:) produces the next value on demand
func statusUpdates(every interval: Duration) -> AsyncStream<OrderStatus> {
    AsyncStream {
        try? await Task.sleep(for: interval)
        guard !Task.isCancelled else { return nil }          // nil ends the stream
        return try? await api.fetchOrderStatus()
    }
}

for await status in statusUpdates(every: .seconds(10)) {
    render(status)
    if status == .delivered { break }    // leaving the loop ends polling
}
```
- Returning `nil` from the unfolding closure (including when a fetch fails, as written here) **finishes** the stream. Return a wrapper value instead if errors shouldn't stop polling.

## 11. Threads, Executors & the Main Actor

### Q81. Which thread does async code run on? `[Senior]`
**Key points:**
- It depends on **isolation**, not on where you called from:
  - `@MainActor` code runs on the **main thread**.
  - Actor-isolated code runs on that actor's serial executor (some pool thread, one at a time).
  - Nonisolated async code runs on the **global concurrent executor** (cooperative pool) — or, with Swift 6.2's new default, on the caller's actor (Q86).
- After an `await`, non-main-actor code may resume on a **different thread** than before.
- Think in terms of **actors and isolation**, not threads.

### Q82. What is the cooperative thread pool, and why must you never block it? `[Lead/Expert]`
**Key points:**
- Swift Concurrency runs tasks on a small pool of threads (about one per CPU core). Tasks **cooperate** by suspending at `await` instead of blocking.
- This avoids GCD-style **thread explosion** (hundreds of blocked threads, memory overhead, context switching).
- The runtime requires **forward progress**: blocking a pool thread (semaphores, `sleep()`, synchronous waits on other tasks) removes it from the pool. Block enough threads and the app can **deadlock**, because the tasks that would unblock them can't get a thread.

```swift
// ❌ Never do this in async code
func badFetch() async -> Data {
    let semaphore = DispatchSemaphore(value: 0)
    var result = Data()
    Task {
        result = await fetch()
        semaphore.signal()
    }
    semaphore.wait()        // blocks a cooperative thread; can deadlock under load
    return result
}

// ✅ Just await
func goodFetch() async -> Data {
    await fetch()
}
```

### Q83. How do you run code on the main actor? `[Fundamental]`
```swift
// 1. Annotate the function or type
@MainActor
func updateUI(with items: [Item]) {
    tableView.reloadData()
}

// 2. Hop to the main actor from nonisolated async code
await MainActor.run {
    progressView.isHidden = true
}

// 3. Start a main-actor task from anywhere
Task { @MainActor in
    statusLabel.text = "Done"
}

// 4. Calling a @MainActor function from elsewhere requires await (it may hop)
await updateUI(with: items)
```
- Prefer annotating types and functions with `@MainActor` (compile-time guarantee) over sprinkling `MainActor.run` calls (Concurrency file has full details).

### Q84. After an `await` in a `@MainActor` function, where does execution resume? `[Senior]`
**Key points:**
- Back on the **main actor**. Isolation is preserved across suspension points, so you can safely update UI after awaiting a network call without manually dispatching to the main queue.

```swift
@MainActor
func refresh() async {
    spinner.startAnimating()                     // main actor
    let items = try? await api.fetchItems()      // suspends; main thread stays free
    spinner.stopAnimating()                      // main actor again
    self.items = items ?? []
}
```

### Q85. Why does wrapping heavy work in `Task { }` still freeze the UI? `[Senior]`
**Key points:**
- `Task { }` **inherits the actor**. Created from main-actor code, its body runs on the main actor. Synchronous heavy work inside it blocks the main thread just like before.
- `async` doesn't mean "background." Only work that **suspends** (awaits) frees the thread.

```swift
@MainActor
func applyFilterTapped() {
    // ❌ Still on the main actor: UI freezes during the filter
    Task {
        let filtered = ImageFilter.apply(to: image)   // synchronous, CPU-heavy
        imageView.image = filtered
    }

    // ✅ Run the heavy work off the main actor
    Task {
        let filtered = await ImageFilter.applyInBackground(to: image)
        imageView.image = filtered                   // back on the main actor
    }
}

enum ImageFilter {
    static func apply(to image: UIImage) -> UIImage { /* heavy work */ image }

    @concurrent   // Swift 6.2: always runs on the global concurrent executor
    static func applyInBackground(to image: UIImage) async -> UIImage {
        apply(to: image)
    }
}
```
- Before Swift 6.2 (or without the new default), a plain `nonisolated` async function also ran off the main actor. `Task.detached` is another option.

### Q86. How did Swift 6.2 change where nonisolated async functions run? `[Lead/Expert]`
**Key points:**
- **Before (Swift 5.7–6.1)**: a `nonisolated` async function always hopped **off** the caller's actor to the global concurrent executor. This surprised developers and caused data-race errors when non-`Sendable` values were passed from the main actor.
- **Swift 6.2 (`NonisolatedNonsendingByDefault` upcoming feature, enabled by "Approachable Concurrency" in Xcode 26)**: nonisolated async functions **run on the caller's actor** by default (`nonisolated(nonsending)` semantics). Calling one from the main actor keeps it on the main actor.
- To explicitly run on the concurrent pool, mark the function **`@concurrent`**.

```swift
// Swift 6.2 with approachable concurrency enabled
struct ImageProcessor {
    // Runs on whatever actor calls it (e.g. the main actor)
    nonisolated func metadata(for data: Data) async -> ImageMetadata { ... }

    // Always runs on the global concurrent executor: use for heavy work
    @concurrent
    nonisolated func thumbnail(for data: Data) async -> UIImage { ... }
}
```
- **Interview tip:** explain both behaviors and check which one your project uses (build settings), since the same code runs on different executors depending on the setting.

### Q87. What is default main-actor isolation? `[Lead/Expert]`
**Key points:**
- Swift 6.2 lets a module make **all declarations `@MainActor` by default** (build setting "Default Actor Isolation = MainActor"). App targets are mostly UI code, so this removes most annotations and data-race errors.
- You then opt specific code **out** with `nonisolated`, `@concurrent`, or dedicated actors for background work.
- New Xcode 26 app projects enable approachable concurrency settings by default; check your build settings, because existing projects keep their old behavior until changed.

### Q88. Can you rely on thread-local storage or `Thread.current` in async code? `[Lead/Expert]`
**Key points:**
- No. A task can resume on different threads, so thread-local state (thread dictionaries, `Thread.current` checks, thread-bound locks like `pthread_mutex` held across `await`) is unreliable. Swift 6 marks `Thread.current` unavailable from async contexts.
- Use **task-local values** (`@TaskLocal`, Q91) for per-operation context, and actors for shared state.
- Never hold a lock (`NSLock`, `os_unfair_lock`) across an `await`.

### Q89. What does `Task.yield()` do? `[Senior]`
**Key points:**
- Voluntarily suspends the current task, giving other tasks a chance to run on the thread, then resumes.
- Useful in long-running loops of synchronous work inside async functions, to keep the system responsive (see Q56). It's not a substitute for moving heavy work off the main actor.

## 12. Priorities, Task-Local Values, Clocks & Sleeping

### Q90. How do task priorities work? `[Senior]`
**Key points:**
- `TaskPriority`: `.high` / `.userInitiated`, `.medium`, `.low` / `.utility`, `.background`.
- `Task { }` inherits the creator's priority; `Task(priority: .background) { }` sets it explicitly; child tasks inherit the parent's priority.
- **Priority escalation**: if a high-priority task awaits a lower-priority task (or an actor running lower-priority work), the runtime raises the lower priority to avoid priority inversion.
- Priority is a scheduling **hint**, not a guarantee of ordering.

```swift
Task(priority: .background) {
    await cache.pruneExpiredEntries()
}
print(Task.currentPriority)
```

### Q91. What are task-local values? `[Lead/Expert]`
**Key points:**
- Values bound to a task (and inherited by its child tasks and `Task { }`), similar to thread-local storage but safe for async code.
- Good for request IDs, logging context, tracing, or test configuration. Not a general dependency-injection or state-sharing mechanism.
- `Task.detached` does **not** inherit them.

```swift
enum RequestContext {
    @TaskLocal static var requestID: String?
}

func handleCheckout() async throws {
    try await RequestContext.$requestID.withValue(UUID().uuidString) {
        try await validateCart()     // can read RequestContext.requestID
        try await chargeCard()       // child tasks see the same value
    }
}

func log(_ message: String) {
    print("[\(RequestContext.requestID ?? "-")] \(message)")
}
```

### Q92. How do you sleep in async code? `[Fundamental]`
```swift
try await Task.sleep(for: .seconds(2))                 // iOS 16+
try await Task.sleep(for: .milliseconds(300), tolerance: .milliseconds(50))
try await Task.sleep(nanoseconds: 2_000_000_000)       // iOS 13+
try await Task.sleep(until: .now + .seconds(5), clock: .continuous)
```
- `Task.sleep` **suspends** (doesn't block a thread) and throws `CancellationError` if the task is cancelled. Never use `Thread.sleep` or `sleep()` in async code.

### Q93. What is the difference between `ContinuousClock` and `SuspendingClock`? `[Senior]`
**Key points:**
- `ContinuousClock`: keeps counting while the device is asleep. Use for real-world timeouts and wall-clock durations.
- `SuspendingClock`: pauses while the device sleeps. Use for measuring active work.
- Clocks can measure elapsed time:

```swift
let elapsed = try await ContinuousClock().measure {
    try await api.fetchCatalog()
}
print("Catalog loaded in \(elapsed)")
```

### Q94. How do you make time-based async code testable? `[Lead/Expert]`
**Key points:**
- Inject a clock (`any Clock<Duration>`) instead of calling `Task.sleep` directly. Production uses `ContinuousClock()`; tests use a controllable clock (e.g. `TestClock` or `ImmediateClock` from Point-Free's swift-clocks) to advance time instantly.

```swift
@MainActor
@Observable
final class OTPViewModel {
    private(set) var secondsRemaining = 30
    private let clock: any Clock<Duration>

    init(clock: any Clock<Duration> = ContinuousClock()) {
        self.clock = clock
    }

    func startCountdown() async {
        while secondsRemaining > 0 {
            do {
                try await clock.sleep(for: .seconds(1))
            } catch {
                return                       // cancelled
            }
            secondsRemaining -= 1
        }
    }
}
```
(Test example in Q122.)

### Q95. How do you run periodic work with async/await? `[Senior]`
```swift
@MainActor
final class LiveScoresViewModel {
    private var pollingTask: Task<Void, Never>?

    func startPolling() {
        pollingTask?.cancel()
        pollingTask = Task { [weak self] in
            while !Task.isCancelled {
                await self?.refreshScores()
                try? await Task.sleep(for: .seconds(15))   // returns early on cancellation; loop then exits
            }
        }
    }

    func stopPolling() {
        pollingTask?.cancel()
        pollingTask = nil
    }

    private func refreshScores() async { /* fetch and update state */ }
}
```
- Here `try?` is acceptable because the `while !Task.isCancelled` check ends the loop right after. In SwiftUI, prefer `.task { }` so the loop is cancelled automatically when the view disappears.
- AsyncAlgorithms' `AsyncTimerSequence` is an alternative: `for await _ in AsyncTimerSequence(interval: .seconds(15), clock: .continuous) { ... }`.

### Q96. What async APIs does `URLSession` provide? `[Fundamental]`

### Q97. Write a generic async API client. `[Senior]`
```swift
enum APIError: Error {
    case invalidResponse
    case httpStatus(Int, Data)
    case decoding(Error)
}

struct Endpoint<Response: Decodable> {
    var path: String
    var method = "GET"
    var body: Data?
}

struct APIClient {
    let baseURL: URL
    var session: URLSession = .shared
    var decoder = JSONDecoder()

    func send<Response>(_ endpoint: Endpoint<Response>) async throws -> Response {
        var request = URLRequest(url: baseURL.appending(path: endpoint.path))
        request.httpMethod = endpoint.method
        request.httpBody = endpoint.body
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")

        let (data, response) = try await session.data(for: request)

        guard let http = response as? HTTPURLResponse else { throw APIError.invalidResponse }
        guard (200..<300).contains(http.statusCode) else {
            throw APIError.httpStatus(http.statusCode, data)
        }

        do {
            return try decoder.decode(Response.self, from: data)
        } catch {
            throw APIError.decoding(error)
        }
    }
}

// Usage
extension Endpoint where Response == [Product] {
    static var products: Endpoint { Endpoint(path: "products") }   // generic types can't have static stored properties
}
let products = try await client.send(.products)
```

### Q99. How do you report upload or download progress with async/await? `[Senior]`
**Key points:**
- `data(for:)` doesn't report progress. Options:
  - Pass a per-task `delegate:` (`URLSessionTaskDelegate`) and observe progress in delegate callbacks (or the task's `progress` object).
  - Use `bytes(for:)` and compute progress while iterating (Q77).
  - Use a classic `URLSessionDownloadTask` with a delegate, bridged into an `AsyncStream` of progress events.

### Q100. How do you refresh an expired auth token only once when many requests fail together? `[Lead/Expert]`
**Key points:**
- Use an **actor** holding the in-flight refresh `Task`. All callers await the same task, so only one refresh request happens.

```swift
actor TokenStore {
    private var token: Token
    private var refreshTask: Task<Token, Error>?
    private let authAPI: AuthAPI

    init(initialToken: Token, authAPI: AuthAPI) {
        self.token = initialToken
        self.authAPI = authAPI
    }

    func validToken() async throws -> Token {
        if let refreshTask { return try await refreshTask.value }   // join an in-flight refresh
        if !token.isExpired { return token }
        return try await refresh()
    }

    func refresh() async throws -> Token {
        if let refreshTask { return try await refreshTask.value }

        let task = Task { [authAPI, token] in
            try await authAPI.refresh(using: token.refreshToken)
        }
        refreshTask = task
        defer { refreshTask = nil }

        token = try await task.value
        return token
    }
}

// In the API client: on a 401, call tokenStore.refresh(), then retry the request once.
```
- Storing the `Task` **before** the first `await` is what prevents duplicate refreshes when the actor is re-entered (actor reentrancy is explained in the Concurrency file).

### Q101. Can you use async/await with background URLSession transfers? `[Lead/Expert]`
**Key points:**
- No. Background sessions (transfers that continue while the app is suspended or terminated) require the **delegate-based** API; the async convenience methods aren't supported for them.
- Use a background `URLSessionConfiguration` with a delegate, handle `application(_:handleEventsForBackgroundURLSession:completionHandler:)`, and expose results to the rest of the app via an `AsyncStream` or state updates if desired.

## 15. Memory Management with Tasks

### Q107. Does a `Task` retain the objects it captures? `[Senior]`
**Key points:**
- Yes. A `Task` closure strongly captures what it references, including `self`. `Task` closures allow **implicit** `self`, so the capture is easy to miss. The objects stay alive **until the task finishes**.
- For short tasks that finish soon, this is usually fine (it just delays deallocation a little).
- For **long-running** tasks (infinite loops, stream iteration, polling), strong captures mean the object can **never** be deallocated.

### Q108. How do you avoid leaks in long-running tasks? `[Lead/Expert]`
```swift
final class FeedViewModel {
    private var updatesTask: Task<Void, Never>?

    func startObserving(_ updates: AsyncStream<FeedUpdate>) {
        updatesTask = Task { [weak self] in
            for await update in updates {
                guard let self else { return }   // strong reference only for this iteration
                self.apply(update)
            }
        }
    }

    deinit {
        updatesTask?.cancel()                    // possible because self isn't retained by the task
    }

    private func apply(_ update: FeedUpdate) { }
}
```
**Common mistake:**
```swift
updatesTask = Task { [weak self] in
    guard let self else { return }   // ❌ strong `self` for the WHOLE loop: leak returns
    for await update in updates {
        self.apply(update)
    }
}
```

### Q109. Why might `deinit { task.cancel() }` never run? `[Senior]`
**Key points:**
- If the task strongly captures `self`, `self` can't deallocate while the task runs, so `deinit` (where you planned to cancel the task) never executes: a circular dependency.
- Fixes: capture `self` weakly (Q108), or cancel based on lifecycle events (`viewDidDisappear`, SwiftUI `.task`), not `deinit`.

### Q110. Do you always need `[weak self]` in a `Task`? `[Senior]`
**Key points:**
- **No.** For short, finite work (a single network call, then update state), a strong capture is fine and often clearer: the object lives until the request finishes.
- Use `[weak self]` (with correct placement) when the task is long-lived or infinite, or when the work should stop being useful once the owner is gone (e.g. a dismissed screen).
- SwiftUI's `.task` and structured concurrency usually make manual memory management unnecessary.

## 16. Common Patterns (Timeout, Retry, Debounce, Deduplication, Limited Concurrency)

### Q111. How do you add a timeout to an async operation? `[Lead/Expert]`
```swift
struct TimeoutError: Error {}

func withTimeout<T: Sendable>(
    _ duration: Duration,
    operation: @escaping @Sendable () async throws -> T
) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask { try await operation() }
        group.addTask {
            try await Task.sleep(for: duration)
            throw TimeoutError()
        }
        defer { group.cancelAll() }          // cancel whichever child is still running
        guard let result = try await group.next() else { throw TimeoutError() }
        return result
    }
}

// Usage
let config = try await withTimeout(.seconds(5)) {
    try await api.fetchConfig()
}
```
- The operation must respond to cancellation; otherwise the group still waits for it before returning, even after the timeout fires.

### Q112. How do you retry with exponential backoff? `[Senior]`
```swift
func withRetry<T>(
    maxAttempts: Int = 3,
    initialDelay: Duration = .seconds(1),
    shouldRetry: (Error) -> Bool = { _ in true },
    operation: () async throws -> T
) async throws -> T {
    var attempt = 0
    var delay = initialDelay

    while true {
        attempt += 1
        do {
            return try await operation()
        } catch {
            let isCancellation = error is CancellationError
            guard attempt < maxAttempts, !isCancellation, shouldRetry(error) else { throw error }
            try await Task.sleep(for: delay)      // cancellation stops retrying
            delay *= 2
        }
    }
}

// Retry only transient failures
let feed = try await withRetry(shouldRetry: { ($0 as? URLError)?.code == .timedOut }) {
    try await api.fetchFeed()
}
```
- In production, add jitter, cap the maximum delay, and avoid retrying non-idempotent requests.

### Q113. How do you debounce with async/await (without Combine)? `[Senior]`
```swift
@MainActor
@Observable
final class SearchViewModel {
    var query = "" { didSet { scheduleSearch() } }
    private(set) var results: [Movie] = []
    private(set) var searchTask: Task<Void, Never>?   // internal visibility lets tests await it

    private let api: MovieAPI
    private let clock: any Clock<Duration>

    init(api: MovieAPI, clock: any Clock<Duration> = ContinuousClock()) {
        self.api = api
        self.clock = clock
    }

    private func scheduleSearch() {
        searchTask?.cancel()                       // cancel the previous pending search
        let currentQuery = query
        searchTask = Task {
            do {
                try await clock.sleep(for: .milliseconds(300))   // the debounce window
                results = try await api.search(currentQuery)
            } catch {
                // CancellationError: superseded by a newer query; ignore
            }
        }
    }
}
```
- In SwiftUI, `.task(id: query)` with a short sleep gives the same effect with less code (Q102).

### Q114. How do you deduplicate concurrent requests for the same resource? `[Lead/Expert]`
```swift
actor ImageLoader {
    private var cache: [URL: UIImage] = [:]
    private var inFlight: [URL: Task<UIImage, Error>] = [:]

    func image(for url: URL) async throws -> UIImage {
        if let cached = cache[url] { return cached }
        if let existing = inFlight[url] { return try await existing.value }   // join the existing request

        let task = Task<UIImage, Error> {
            let (data, _) = try await URLSession.shared.data(from: url)
            guard let image = UIImage(data: data) else { throw URLError(.cannotDecodeContentData) }
            return image
        }
        inFlight[url] = task                       // register BEFORE awaiting (handles reentrancy)
        defer { inFlight[url] = nil }

        let image = try await task.value
        cache[url] = image
        return image
    }
}
```
- Ten cells requesting the same avatar trigger **one** download. In production, use `NSCache` for memory-pressure eviction and downsample images.

### Q115. How do you process work items serially in order? `[Senior]`
```swift
/// Runs submitted jobs one at a time, in submission order
final class SerialJobQueue: Sendable {
    private let continuation: AsyncStream<@Sendable () async -> Void>.Continuation

    init() {
        let (stream, continuation) = AsyncStream.makeStream(of: (@Sendable () async -> Void).self)
        self.continuation = continuation
        Task {
            for await job in stream {
                await job()                     // next job starts only after this one finishes
            }
        }
    }

    func enqueue(_ job: @escaping @Sendable () async -> Void) {
        continuation.yield(job)
    }
}

// Usage: analytics events are uploaded strictly in order
queue.enqueue { await analytics.upload(eventA) }
queue.enqueue { await analytics.upload(eventB) }
```
- Unlike separate `Task`s (Q25), the order is guaranteed. Note that **actors don't guarantee** this kind of ordering across suspension points.

```swift
        let viewModel = ProfileViewModel(api: MockProfileAPI(result: .success(.sample)))
        await viewModel.load()
        #expect(viewModel.profile == .sample)          // no await needed: same actor

```
- Marking the test suite `@MainActor` keeps tests on the same actor as the view model.

### Q119. How do you test code that starts its own internal `Task`? `[Lead/Expert]`
**Key points:**
- Preferred: refactor so the work is an `async` method you can await (Q104).
- Otherwise: expose the task handle (internal visibility) and await it in tests.

```swift
@MainActor
@Test func searchShowsResultsAfterDebounce() async {
    let viewModel = SearchViewModel(api: MockMovieAPI(results: [.sample]), clock: ImmediateClock())
    viewModel.query = "Dune"
    await viewModel.searchTask?.value       // wait for the internal task to finish
    #expect(viewModel.results == [.sample])
}
```
- Avoid `Task.sleep` in tests to "wait a bit." It's slow and flaky.

### Q120. How do you test callback-based or event-based code in Swift Testing? `[Senior]`
```swift
@Test func uploaderReportsCompletionOnce() async {
    await confirmation("completion called", expectedCount: 1) { confirm in
        let uploader = Uploader(onComplete: { confirm() })
        await uploader.upload(.sample)     // confirm() must be called before this closure returns
    }
}
```
- `confirmation` replaces `XCTestExpectation` for "this event happened N times" checks. The event must occur before the closure returns, so the code under test should be awaitable.

### Q121. How do you test cancellation behavior? `[Lead/Expert]`

```swift
@Test func cancellingStopsTheDownload() async {
```

### Q122. How do you test time-based code without waiting in real time? `[Lead/Expert]`

## 18. Migration & Interoperability

### Q123. How do you migrate completion-handler APIs to async/await? `[Senior]`
**Key points:**
- Xcode refactorings (right-click → **Refactor**):
  - **Convert Function to Async**: rewrites the function.
  - **Add Async Alternative**: adds an async version and makes the old one call it.
  - **Add Async Wrapper**: adds an async version wrapping the old one via a continuation.
- Mark old APIs deprecated with a rename hint so the compiler guides callers:

```swift
// New primary API
func fetchUser(id: Int) async throws -> User {
    let (data, _) = try await session.data(from: userURL(id))
    return try decoder.decode(User.self, from: data)
}

// Old API kept temporarily for existing callers
@available(*, deprecated, renamed: "fetchUser(id:)")
func fetchUser(id: Int, completion: @escaping @Sendable (Result<User, Error>) -> Void) {
    Task {
        do { completion(.success(try await fetchUser(id: id))) }
        catch { completion(.failure(error)) }
    }
}
```

### Q124. What are async/await equivalents of common GCD patterns? `[Senior]`
| GCD | Swift Concurrency |
|---|---|
| `DispatchQueue.main.async { }` | `@MainActor` functions/types, `await MainActor.run { }` |
| `DispatchQueue.global().async { }` | `@concurrent` async function, `Task.detached`, nonisolated async (pre-6.2 default) |
| `DispatchGroup` (wait for many) | `async let`, task groups |
| Serial queue protecting state | `actor` |
| `DispatchSemaphore` limiting concurrency | Task group with N in flight (Q35) |
| `asyncAfter(deadline:)` | `try await Task.sleep(for:)` |
| `DispatchWorkItem.cancel()` | `task.cancel()` + cooperative checks |
| Barrier for reader/writer | `actor` (or a lock for synchronous, non-async access) |

### Q125. How do you bridge between Combine and async/await? `[Senior]`
**Key points:**
- Publisher → async: `publisher.values` (an `AsyncSequence`), or a `firstValue()` helper.
- Async → publisher: `Deferred { Future { promise in Task { ... } } }`.
- Watch for dropped values when using `.values` on hot publishers, and lost cancellation when wrapping tasks in `Future`.
- (Full examples are in the Combine file, Section 19.)

### Q126. How do you modernize a delegate-heavy SDK wrapper? `[Lead/Expert]`
**Key points:**
- **One-shot** delegate callbacks (request → single response) → `async` functions with continuations (Q67).
- **Multi-value** callbacks (updates, events) → `AsyncStream` with `onTermination` cleanup (Q73).
- Keep the delegate object internal; expose only async APIs. Handle concurrency explicitly (one request at a time, or queue requests).

### Q127. Does async/await replace every completion handler? `[Senior]`
**Key points:**
- Mostly, for **one-shot** async results. But:
  - **Multiple values over time** → `AsyncSequence` (or Combine).
  - **Synchronous APIs** that callers can't await (e.g. `UITableViewDataSource`) stay synchronous.
  - Some system APIs (background `URLSession`, certain delegate protocols) remain delegate-based.
  - Libraries that support older OS versions may need to keep completion-handler APIs.

## 19. Debugging & Performance

### Q128. How do you debug async code? `[Senior]`
**Key points:**
- Xcode shows **async backtraces** (the logical chain of awaits), not just the current thread's stack.
- Instruments **Swift Concurrency** template: Swift Tasks (task counts, states, lifetimes) and Swift Actors (actor queue lengths, contention).
- Name tasks (Swift 6.2 `Task(name:)`) so they're identifiable.
- Thread Sanitizer catches remaining data races (especially in code not yet checked by Swift 6 mode).
- Checked continuations log leaked or double-resumed continuations.

### Q129. What are the performance considerations of async/await? `[Lead/Expert]`
**Key points:**
- Async calls are cheap, but each suspension allocates/uses an async frame; don't make tight inner loops async without need.
- **Creating tasks** has overhead. Avoid one task per tiny item; batch work or use a task group with limited concurrency.
- **Actor and main-actor hops** cost context switches. Group work into fewer hops (e.g. compute everything off the main actor, then update UI once).
- **Never block** the cooperative pool (Q82).
- Long synchronous CPU work should run off the main actor and periodically check cancellation and yield (Q56).

### Q130. How does Swift Concurrency avoid thread explosion compared with GCD? `[Lead/Expert]`
**Key points:**
- In GCD, blocking work on concurrent queues makes GCD spawn **more threads** to keep queues moving. Under load, apps could have hundreds of threads (memory and scheduling overhead, risk of hitting thread limits).
- Swift Concurrency's cooperative pool keeps threads ≈ CPU cores. Tasks suspend instead of blocking, so threads stay busy with useful work.
- The trade-off is the **forward progress requirement**: code must never block, or the fixed pool can be exhausted.

### Q131. When is async/await **not** the right tool? `[Lead/Expert]`
**Key points:**
- **Synchronous, fast operations**: making them async adds complexity and suspension points for no benefit.
- **High-frequency event streams with complex time-based combination logic**: Combine or AsyncAlgorithms may be clearer.
- **Real-time or low-latency work** (audio render callbacks, Metal frame callbacks) that must not allocate or suspend.
- **Fine-grained synchronous locking** for tiny critical sections: a lock (`Mutex` in Swift 6's Synchronization module, `OSAllocatedUnfairLock`) can be simpler and faster than an actor.

## 20. "What's the Output?" Questions

### Q132. `async let` ordering `[Fundamental]`
```swift
func work(_ name: String, seconds: Double) async -> String {
    try? await Task.sleep(for: .seconds(seconds))
    print("finished \(name)")
    return name
}

async let a = work("A", seconds: 2)
async let b = work("B", seconds: 1)
print("started")
let results = await [a, b]
print(results)
```
**Output:**
```
started
finished B
finished A
["A", "B"]
```
- Both children start immediately; `B` finishes first, but results are assembled in the order you await them.

### Q133. Sequential vs concurrent timing `[Fundamental]`
```swift
let start = ContinuousClock.now
let x = await work("X", seconds: 1)
let y = await work("Y", seconds: 1)
print(ContinuousClock.now - start)        // ?

let start2 = ContinuousClock.now
async let p = work("P", seconds: 1)
async let q = work("Q", seconds: 1)
_ = await (p, q)
print(ContinuousClock.now - start2)       // ?
```
**Answer:** About **2 seconds** for the sequential version, about **1 second** for the `async let` version.

### Q134. When does a new `Task` run? `[Senior]`
```swift
@MainActor
func handleTap() {
    Task { print("2: inside task") }
    print("1: after creating task")
}
```
**Output:** `1: after creating task`, then `2: inside task`. The task is enqueued on the main actor and can only run after `handleTap()` returns.
- Follow-up: with Swift 6.2's `Task.immediate { ... }`, `2` prints **first**, because the task body starts synchronously until its first suspension point.

### Q135. Cancellation is cooperative `[Senior]`
```swift
let task = Task {
    for i in 1...5 {
        print(i)
        expensiveSynchronousWork()      // no cancellation checks, no awaits
    }
}
task.cancel()
```
**Output:** `1 2 3 4 5`. Cancelling only sets a flag; the loop never checks it. Add `try Task.checkCancellation()` (and make the closure throwing) to stop early.

### Q136. `Task.sleep` and cancellation `[Fundamental]`
```swift
let task = Task {
    do {
        try await Task.sleep(for: .seconds(5))
        print("woke up")
    } catch {
        print("caught: \(error)")
    }
}
task.cancel()
```
**Output:** `caught: CancellationError()`, printed immediately rather than after 5 seconds.

### Q137. Swallowing cancellation with `try?` `[Senior]`
```swift
let task = Task {
    try? await Task.sleep(for: .seconds(5))
    print("still running, cancelled = \(Task.isCancelled)")
}
task.cancel()
```
**Output:** `still running, cancelled = true`, immediately. The sleep threw, `try?` swallowed it, and execution continued.

### Q138. Child vs unstructured task cancellation `[Lead/Expert]`
```swift
func report(_ label: String) async {
    try? await Task.sleep(for: .seconds(1))
    print("\(label) cancelled: \(Task.isCancelled)")
}

let parent = Task {
    Task { await report("unstructured") }   // not a child
    async let child: Void = report("child") // a child task
    await child
}
parent.cancel()
```
**Output:**
```
child cancelled: true          ← immediately (inherits the parent's cancellation, sleep throws)
unstructured cancelled: false  ← after ~1 second (independent task)
```

### Q139. Task group result order `[Fundamental]`
```swift
let values = await withTaskGroup(of: Int.self) { group in
    for seconds in [3, 1, 2] {
        group.addTask {
            try? await Task.sleep(for: .seconds(seconds))
            return seconds
        }
    }
    var collected: [Int] = []
    for await value in group { collected.append(value) }
    return collected
}
print(values)
```
**Output:** `[1, 2, 3]`: completion order, not insertion order.

### Q140. Heavy work inside a main-actor `Task` `[Senior]`
```swift
@MainActor
func generateReportTapped() {
    spinner.startAnimating()
    Task {
        let report = ReportBuilder.buildSynchronously()   // 3 seconds of CPU work
        spinner.stopAnimating()
        show(report)
    }
}
```
**Question:** Does the spinner animate during those 3 seconds?

**Answer:** No. The `Task` inherits the main actor, so the synchronous work blocks the main thread and the spinner freezes. Move the work off the main actor (`@concurrent` async function, `Task.detached`, or a background actor).

### Q141. `await` inside `map` `[Fundamental]`
```swift
let users = try ids.map { try await api.fetchUser(id: $0) }
```
**Answer:** Compile error: `map` takes a synchronous closure. Use a `for` loop (sequential) or a task group (concurrent).

### Q142. Which error does a cancelled `URLSession` request throw? `[Senior]`
```swift
let task = Task {
    do {
        _ = try await URLSession.shared.data(from: url)
    } catch is CancellationError {
        print("CancellationError")
    } catch {
        print("Other: \(error)")
    }
}
task.cancel()
```
**Output:** `Other: Error Domain=NSURLErrorDomain Code=-999 "cancelled"…` URLSession throws `URLError(.cancelled)`, not `CancellationError`. Check for both when filtering cancellation.

### Q143. Continuation misuse `[Senior]`
```swift
func value() async -> Int {
    await withCheckedContinuation { continuation in
        legacy.fetch { result in
            continuation.resume(returning: result)
            continuation.resume(returning: result)   // A
        }
    }
}
```
**Question:** What happens at line A? What if the callback were never called?

**Answer:** Resuming twice **crashes** (checked continuation misuse). If the callback never fires, the caller **hangs forever** and the runtime logs a warning that the continuation leaked.

### Q144. Unobserved error in a `Task` `[Senior]`
```swift
Task {
    try await api.deleteAccount()      // throws URLError(.notConnectedToInternet)
}
print("requested")
```
**Output:** `requested`, and nothing else. The error is stored in the task and silently discarded because nobody awaits it. Handle errors inside the task.

### Q145. Strong `self` in a long-running task `[Lead/Expert]`
```swift
final class TickerViewModel {
    private var task: Task<Void, Never>?

    init(prices: AsyncStream<Double>) {
        task = Task {
            for await price in prices {
                self.latestPrice = price      // strong self, loop never ends
            }
        }
    }

    var latestPrice = 0.0
    deinit { task?.cancel(); print("deinit") }
}

var viewModel: TickerViewModel? = TickerViewModel(prices: priceStream)
viewModel = nil
```
**Output:** Nothing. `deinit` never runs: the task retains `self` for as long as the stream is open. Use `[weak self]` with `guard let self` **inside** the loop (Q108).

### Q146. An `async let` that is never awaited `[Lead/Expert]`
```swift
func refresh() async {
    async let analytics: Void = sendAnalytics()   // takes 3 seconds, ignores cancellation
    print("refresh done")
}

await refresh()
print("returned")
```
**Output:** `refresh done`, then `returned` about 3 seconds later. At scope exit, the unawaited child is cancelled and **implicitly awaited**; because `sendAnalytics()` ignores cancellation, `refresh()` waits for it. For true fire-and-forget, use an unstructured `Task` (deliberately).

## 22. Senior / Lead Scenario Questions

### Q147. How would you migrate a large completion-handler networking layer to async/await? `[Lead/Expert]`
**Talking points:**
1. **Bottom-up**: convert the lowest layer (HTTP client) first, implemented with `URLSession`'s async APIs.
2. **Compatibility**: keep completion-handler wrappers marked `@available(*, deprecated, renamed:)` so existing callers compile and the compiler lists remaining work.
3. **Feature by feature**: migrate services and view models, replacing callback chains with linear async code and `async let`/task groups for parallel requests.
4. **Tests first**: characterization tests for error mapping, retries, and cancellation; async tests become simpler than callback tests.
5. **Guidelines**: where tasks may be created, cancellation handling, main-actor rules, no blocking.
6. **Finish**: remove wrappers once unused; enable stricter concurrency checking module by module.

### Q148. Design an image loading pipeline for a large feed using async/await. `[Lead/Expert]`
**Talking points:**
- An `ImageLoader` **actor** with a memory cache (`NSCache`), disk cache, and **in-flight request deduplication** (Q114).
- **Downsampling/decoding off the main actor** (`@concurrent` function or `byPreparingThumbnail(ofSize:)`).
- **Cancellation**: each cell's load task is cancelled in `prepareForReuse` (UIKit) or automatically via `.task(id: url)` (SwiftUI).
- **Concurrency limits**: avoid hundreds of simultaneous downloads (a limited task group or a semaphore-like actor).
- **Prefetching** upcoming rows; priority lowered for prefetches.
- **Metrics**: cache hit rate, decode time, memory footprint; tested with a mock URLProtocol.

### Q149. After adopting async/await, users report the app freezing. How do you investigate? `[Lead/Expert]`
**Talking points:**
- **Main actor blocked by synchronous work** inside `Task { }` or `@MainActor` functions (the most common cause, Q85, Q140). Check with Time Profiler / Hangs instrument.
- **Blocking calls in async code** (semaphores, `DispatchGroup.wait`, synchronous I/O) causing cooperative-pool starvation or deadlocks (Q82).
- **Continuations never resumed**, leaving tasks waiting forever (look for "leaked its continuation" logs).
- **Actor contention**: one busy actor serializing too much work (Swift Actors instrument).
- **Swift 6.2 behavior change**: a nonisolated async function that used to run in the background now runs on the main actor (Q86). Mark heavy functions `@concurrent`.
- Fix, add regression tests, and monitor hang rates in Xcode Organizer.

### Q150. Design a sync engine that uploads pending changes and downloads updates. `[Lead/Expert]`
**Talking points:**
- A `SyncEngine` actor coordinating sync runs; only one run at a time (store the current run's `Task`; new requests join it).
- Each run: upload pending changes with a **limited-concurrency task group**, then download updates; `withRetry` for transient failures; idempotent requests.
- **Cancellation**: respect app backgrounding and user sign-out; check cancellation between batches; persist progress so the next run resumes.
- **Errors**: partial failures recorded per item (`Result`), not failing the whole run.
- **Triggers**: app foreground, push notification, `BGAppRefreshTask`, connectivity restored (an `AsyncStream` from `NWPathMonitor`).
- **Testability**: injected API, store, and clock; deterministic tests for retry and cancellation paths.

### Q151. What do you look for when reviewing async/await code? `[Lead/Expert]`
**Talking points:**
- **Structure**: prefer `async` functions and structured concurrency; `Task { }` only at boundaries; no `Task.detached` without justification.
- **Cancellation**: long loops check cancellation; no `try?` swallowing `Task.sleep` cancellation; cancellation errors not shown as user-facing errors; stored tasks cancelled appropriately.
- **Errors**: no silently dropped errors in fire-and-forget tasks.
- **Threading**: no heavy synchronous work on the main actor; no blocking (semaphores, sleep) in async code; no locks held across `await`.
- **Memory**: long-running tasks don't capture `self` strongly; `weak self` placed correctly.
- **Continuations**: resumed exactly once on every path.
- **State across `await`**: assumptions re-validated after suspension (actor reentrancy).
- **Tests**: async methods awaited directly; clocks injected; no sleeping in tests.

### Q152. How do you finish important async work when the app moves to the background? `[Lead/Expert]`
```swift
@MainActor
func sceneDidEnterBackground(_ scene: UIScene) {
    var saveTask: Task<Void, Never>?
    let backgroundID = UIApplication.shared.beginBackgroundTask(withName: "SaveDraft") {
        saveTask?.cancel()                         // time expired: stop cooperatively
    }

    saveTask = Task {
        await draftStore.flushPendingChanges()     // must respond to cancellation
        UIApplication.shared.endBackgroundTask(backgroundID)
    }
}
```
**Talking points:**
- `beginBackgroundTask` buys a short amount of extra time; always end it, and cancel the work in the expiration handler.
- For deferrable work, use `BGTaskScheduler` (cancel the `Task` in the task's `expirationHandler`, then call `setTaskCompleted`), or SwiftUI's `.backgroundTask(.appRefresh("id")) { await ... }` scene modifier.
- For large transfers, use background `URLSession` (delegate-based, Q101).

### Q153. How would you explain async/await to a junior engineer? `[Senior]`
**Talking points:**
- Analogy: ordering at a restaurant. **Blocking** is standing at the counter staring at the kitchen until your food is ready, so nobody else can order. **Awaiting** is taking a buzzer and sitting down; the cashier (thread) serves other customers, and you're called back when your food is ready.
- Show a completion-handler pyramid next to the async version.
- Then teach the three rules: **don't block**, **check cancellation in long work**, and **know which actor your code runs on** (main actor for UI).

### Q154. Where should tasks be created in a well-architected app? `[Lead/Expert]`
**Talking points:**
- **Lower layers** (networking, persistence, services) expose `async` functions and `AsyncSequence`s; they almost never create unstructured tasks (except for intentional background coordination like a sync engine or a deduplicating cache).
- **View models** expose `async` methods for user intents (`load()`, `refresh()`, `save()`), plus a few owned, cancellable tasks for debounce or observation.
- **UI layer** creates tasks at the boundary: SwiftUI `.task`/`.refreshable`, UIKit event handlers, delegate callbacks.
- This keeps cancellation, error handling, and testing predictable: most code is plain `async` functions that tests can `await`.
