## 1. The Backend System Design Interview

### Q1. Why are iOS engineers asked backend system design questions? `[Fundamental]`
**Key points:**
- Senior and lead mobile engineers **design API contracts**, negotiate with backend teams, and own features end to end. Interviewers want to see you understand what happens after the request leaves the phone.
- Client decisions change server load: polling vs push, retry storms, cache headers, pagination style, payload size, idempotency keys.
- You are rarely expected to know database internals. You are expected to know **the standard building blocks, when to use each, and what each costs**.

```
What the interviewer wants to hear from a mobile engineer
Client  ── HTTPS ──▶ CDN ──▶ Load balancer ──▶ Stateless API servers ──▶ Cache ──▶ Database
                                                     │                                  ▲
                                                     └──▶ Message queue ──▶ Workers ─────┘
"I know why each box exists, what fails, and how my app's behaviour affects every box."
```

### Q2. How should you structure a backend design answer? `[Fundamental]`
| Step | Time (of ~45 min) | What you do |
|---|---|---|
| 1. **Requirements** | 5 min | Functional (what it does) and non-functional (scale, latency, availability, consistency) |
| 2. **Estimation** | 3–5 min | QPS, storage, bandwidth; read/write ratio |
| 3. **API** | 5 min | Endpoints or messages with request/response shapes |
| 4. **High-level design** | 10 min | Boxes and arrows: clients, LB, services, cache, DB, queues, CDN |
| 5. **Data model** | 5 min | Tables/collections, keys, indexes, partition key |
| 6. **Deep dives** | 12–15 min | Scaling the bottleneck, caching, consistency, failure modes |
| 7. **Wrap-up** | 2 min | Trade-offs, monitoring, what you'd do next |

**Sample opening:** "Let me first pin down what the system must do and at what scale. Then I'll estimate load, define the API, sketch the architecture, and spend most of the time on whichever part breaks first at that scale."

### Q3. What non-functional requirements should you always ask about? `[Fundamental]`
- **Scale**: daily active users, requests per second at peak, data growth per day.
- **Read/write ratio**: a feed is ~100:1 reads; a logging system is write-heavy. This decides caching and database choices.
- **Latency**: p99 target (e.g. < 200 ms for an API, < 1 s for search).
- **Availability**: "three nines" (99.9%) or more; what may be down without hurting users.
- **Consistency**: must users see their own writes immediately? Is it money (strong) or likes (eventual)?
- **Durability**: can we lose a few seconds of data on a crash? (Analytics: maybe; payments: never.)
- **Geography**: one region or global? Data residency laws?

### Q4. How do you do back-of-the-envelope estimation? `[Senior]`
```
Useful constants
1 day ≈ 86,400 s ≈ 10^5 s (round up for easy math)
1M requests/day ≈ 12 req/s average;  peak ≈ 2–5× average
1 KB × 1M = 1 GB;  1 KB × 1B = 1 TB

Example: photo-sharing app, 10M DAU
Reads:  10M users × 50 feed requests/day = 500M/day ≈ 5,800 req/s avg → ~20,000 req/s peak
Writes: 10M × 0.2 posts/day = 2M posts/day ≈ 23 posts/s
Metadata: 2M posts × 1 KB = 2 GB/day → ~730 GB/year (fits one large DB; still plan sharding)
Photos: 2M × 2 MB = 4 TB/day → object storage + CDN, never the database
Egress: 500M feed loads × 20 thumbnails × 50 KB ≈ 500 TB/day → CDN cache hit rate is the whole game
```
**What the numbers tell you:** reads dominate (cache aggressively, add read replicas), media dominates bandwidth (CDN), writes are small (a single primary DB is fine for a while).

### Q5. What are the "latency numbers every engineer should know"? `[Senior]`
| Operation | Approximate time |
|---|---|
| L1 cache reference | ~1 ns |
| Main memory reference | ~100 ns |
| Read 1 MB sequentially from memory | ~5–10 µs |
| SSD random read | ~20–100 µs |
| Read 1 MB sequentially from SSD | ~0.2–1 ms |
| Round trip inside a data center | ~0.5 ms |
| Redis GET (same data center, incl. network) | ~0.2–1 ms |
| Simple indexed DB query | ~1–5 ms |
| HDD seek | ~5–10 ms |
| Round trip US East ↔ US West | ~60–70 ms |
| Round trip US ↔ Europe | ~80–150 ms |
| Mobile network round trip (LTE) | ~50–100 ms; 3G 200+ ms |

**Takeaways:** memory is ~100× faster than SSD, which is far faster than a cross-continent round trip. So: cache in memory, avoid sequential round trips, put data near users.

### Q6. What do availability "nines" mean? `[Fundamental]`
| Availability | Downtime per year | Per month |
|---|---|---|
| 99% | 3.65 days | 7.3 hours |
| 99.9% | 8.8 hours | 43.8 minutes |
| 99.99% | 52.6 minutes | 4.4 minutes |
| 99.999% | 5.3 minutes | 26 seconds |

- Components in **series** multiply: three services each at 99.9% in a chain give 0.999³ ≈ 99.7%.
- Components in **parallel** (redundant) improve it: two independent instances at 99% give 1 − 0.01² = 99.99%.
- That is the mathematical reason for redundancy and for keeping the critical path short.

## 2. Scalability Fundamentals

### Q7. What is the difference between vertical and horizontal scaling? `[Fundamental]`
| | Vertical (scale up) | Horizontal (scale out) |
|---|---|---|
| How | Bigger machine (more CPU/RAM/disk) | More machines behind a load balancer |
| Limit | Hardware ceiling; cost grows steeply | Practically unlimited |
| Downtime | Often needs a restart to resize | Add/remove nodes live |
| Failure | Single point of failure | Survives node loss |
| Complexity | Simple; no code changes | Needs statelessness, load balancing, data partitioning |
| Good for | Databases early on, quick wins | Stateless web/API tiers, large scale |

**Senior answer:** "Scale up first while it's cheap and simple, especially for the database. Design the application tier to be stateless from day one so scaling out is just adding instances."

### Q8. What does "stateless service" mean, and why does it matter? `[Fundamental]`
- A stateless server keeps **no client-specific data in memory between requests**. Any instance can serve any request.
- Session data, carts, uploads in progress move to shared stores: Redis, the database, object storage, or a signed token (JWT) carried by the client.
- Benefits: any instance can die or be added; the load balancer needs no sticky sessions; autoscaling and deploys are simple.

```
❌ Stateful: user's session lives in server A's memory → if A dies, the user is logged out;
             LB must always route that user to A (sticky sessions)
✅ Stateless: session in Redis (or a signed token) → any server handles any request
```

```swift
// Stateless request handling: everything needed comes from the request or shared stores
struct OrdersHandler {
    let sessions: SessionStore      // Redis-backed, shared by all instances
    let orders: OrderRepository     // database

    func listOrders(_ request: Request) async throws -> [Order] {
        guard let token = request.bearerToken,
              let session = try await sessions.lookup(token) else { throw HTTPError.unauthorized }
        return try await orders.recent(for: session.userID, limit: 20)
    }
}
```

### Q9. What are the typical stages of scaling a system? `[Senior]`
```
Stage 1  1 server: app + DB on one box                         (prototype, < 1k users)
Stage 2  Separate DB server; vertical scaling                   (~10k users)
Stage 3  Load balancer + several stateless app servers          (~100k users)
Stage 4  Cache (Redis) + CDN for static/media                   (reads explode)
Stage 5  DB read replicas; move slow work to queues + workers   (~1M users)
Stage 6  Shard the database; split services by domain           (~10M+ users)
Stage 7  Multi-region: geo DNS, regional replicas, data locality (global, high availability)
```
Each step solves the **current** bottleneck. In an interview, say which bottleneck triggers the next step ("DB CPU at 80% from reads → add replicas and a cache").

### Q10. What is the difference between latency and throughput? `[Fundamental]`
- **Latency**: time for one request (ms). Users feel it. Measure **percentiles** (p50, p95, p99), not averages, because averages hide the slow tail.
- **Throughput**: requests handled per second. Capacity planning cares about it.
- They interact: as utilization approaches 100%, queues form and latency rises sharply. Keep servers at ~60–70% at peak to leave headroom.
- **Little's Law**: concurrent requests = throughput × latency. At 1,000 req/s and 200 ms latency, ~200 requests are in flight at once; that sizes thread pools and DB connection pools.

### Q11. What is autoscaling, and what can go wrong? `[Senior]`
- Add/remove instances automatically based on CPU, request rate, queue depth, or a schedule.
- **Pitfalls**:
  - **Slow start**: new instances take minutes (boot, warm caches, JIT); scale before the peak (scheduled or predictive scaling).
  - **Thrashing**: scaling up and down repeatedly; use cooldowns and different up/down thresholds.
  - **The bottleneck moves**: 50 more app servers each opening 20 DB connections = 1,000 new connections, which can take down the database. Use connection pooling (PgBouncer) and limits.
  - **Scaling on the wrong metric**: CPU looks fine while requests wait on a slow dependency.

### Q12. How do you find the bottleneck in a system? `[Senior]`
1. Measure end to end: where does request time go? (Distributed tracing.)
2. Check the **USE** method per resource: **U**tilization, **S**aturation (queues), **E**rrors.
3. Usual suspects in order: database (slow queries, missing indexes, lock contention, connection limits) → external calls → CPU-heavy code → network/bandwidth.
4. Fix the biggest one; re-measure. The bottleneck always moves.

## 3. Load Balancing

### Q13. What does a load balancer do? `[Fundamental]`
- Distributes incoming requests across multiple servers.
- **Health checks**: stops sending traffic to unhealthy instances.
- **High availability**: no single server is a single point of failure.
- Often also: TLS termination, connection reuse to backends, compression, request routing, rate limiting, WAF.

```
                     ┌──────────────┐
 Clients ──HTTPS──▶  │ Load balancer│──▶ App server 1 (healthy)
                     │  (TLS ends)  │──▶ App server 2 (healthy)
                     └──────────────┘──✗ App server 3 (failed health check: removed)
```

### Q14. What is the difference between L4 and L7 load balancing? `[Senior]`
| | Layer 4 (transport) | Layer 7 (application) |
|---|---|---|
| Sees | IP addresses, ports, TCP/UDP | Full HTTP: path, headers, cookies, body |
| Routing | Per connection | Per request (`/api/*` → API, `/img/*` → media) |
| Speed | Very fast, low overhead | More CPU (parses HTTP, terminates TLS) |
| Features | Simple forwarding | Path/host routing, header rewrites, auth, caching, retries, gRPC/HTTP2 awareness |
| Examples | AWS NLB, HAProxy (TCP mode), LVS | AWS ALB, NGINX, Envoy, HAProxy (HTTP mode) |

Common setup: an L4 balancer at the edge in front of a fleet of L7 proxies.

### Q15. Which load-balancing algorithms exist, and when do you use each? `[Senior]`
| Algorithm | How | Good for | Watch out |
|---|---|---|---|
| Round robin | Next server in order | Identical servers, similar requests | Ignores current load |
| Weighted round robin | Bigger servers get more | Mixed instance sizes, canaries (5% weight) | Static weights |
| Least connections | Server with fewest open connections | Long or uneven requests (WebSockets, uploads) | Needs connection tracking |
| Least response time | Fastest, least-loaded server | Latency-sensitive APIs | Feedback loops |
| IP hash / consistent hashing | Same key → same server | Cache affinity, sticky routing without cookies | Uneven if keys are skewed |
| Random with two choices | Pick 2 at random, choose the less loaded | Large fleets, distributed LBs | Needs load info |

```swift
/// Weighted round robin (smooth, as used by NGINX): spreads picks evenly instead of in bursts
struct WeightedRoundRobin {
    struct Server { let name: String; let weight: Int; var current = 0 }
    private var servers: [Server]

    init(_ weighted: [(String, Int)]) { servers = weighted.map { Server(name: $0.0, weight: $0.1) } }

    mutating func next() -> String {
        let total = servers.reduce(0) { $0 + $1.weight }
        for i in servers.indices { servers[i].current += servers[i].weight }
        let best = servers.indices.max { servers[$0].current < servers[$1].current }!
        servers[best].current -= total
        return servers[best].name
    }
}
// weights A=5, B=1, C=1 → A A B A C A A …  (A never gets 5 in a row)
```

### Q16. How do health checks work? `[Fundamental]`
- **Active**: the LB calls `GET /health` every few seconds; N failures → remove, M successes → add back.
- **Passive**: the LB watches real traffic (errors, timeouts) and ejects bad instances (outlier detection).
- **Liveness vs readiness**:
  - *Liveness*: "is the process alive?" Failing → restart it.
  - *Readiness*: "can it serve traffic now?" (DB reachable, caches warm). Failing → stop routing, don't restart.
- Pitfall: a health check that calls the database marks **every** instance unhealthy when the DB blips, emptying the pool. Keep readiness checks shallow, or degrade instead of failing.

```nginx
upstream api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 backup;                 # only used if the others are down
    keepalive 64;                                 # reuse connections to backends
}
server {
    listen 443 ssl http2;
    location /api/ {
        proxy_pass http://api;
        proxy_next_upstream error timeout http_502 http_503;   # retry another backend (idempotent requests only!)
        proxy_read_timeout 10s;
    }
}
```

### Q17. What are sticky sessions, and why avoid them? `[Senior]`
- The LB pins a client to one server (cookie or IP hash), usually because that server holds session state.
- Problems: uneven load (one heavy user overloads a server), lost sessions when the server dies, harder deploys and autoscaling.
- Preferred: stateless servers with session data in Redis or a token. Stickiness is acceptable for **WebSockets** (the connection itself is stateful) or cache affinity, and even then the system must survive a reconnect to a different server.

### Q18. How do you avoid the load balancer becoming a single point of failure? `[Senior]`
- Run LBs in **pairs or clusters**: active-passive with a floating virtual IP (keepalived/VRRP), or active-active.
- Managed cloud LBs are already distributed across availability zones.
- Above that, **DNS** spreads traffic across LB addresses, and **anycast** announces the same IP from many locations so routing picks the nearest healthy one.

### Q19. How does global (multi-region) load balancing work? `[Lead/Expert]`
```
User in Dhaka ──DNS query──▶ GeoDNS / latency-based DNS ──▶ returns Singapore region IP
User in Paris ──DNS query──▶ GeoDNS                     ──▶ returns Frankfurt region IP
Each region: regional LB → app servers → regional cache → regional DB replica
```
- **GeoDNS / latency-based routing**: answer DNS with the nearest healthy region. Limited by DNS TTL caching (failover takes as long as clients cache the old answer).
- **Anycast**: one IP announced from many points of presence; BGP routes to the nearest. Used by CDNs and global edge LBs (fast failover).
- **Hard part is data, not traffic**: where do writes go? Options: single write region (simple, higher write latency far away), per-user home region (data locality), or multi-leader with conflict resolution.

### Q20. What is a reverse proxy, an API gateway, and how do they relate to a load balancer? `[Senior]`
| Component | Main job |
|---|---|
| Reverse proxy | Sits in front of servers: TLS termination, compression, caching, routing (NGINX, Envoy) |
| Load balancer | Spreads traffic across instances, health checks (often a reverse proxy feature) |
| API gateway | Reverse proxy + API concerns: auth, rate limits, API keys, request transformation, versioning, analytics (Kong, AWS API Gateway, Apigee) |
| Service mesh | Sidecar proxies between internal services: mTLS, retries, circuit breaking, tracing (Istio, Linkerd) |

For a mobile app, the gateway is where **app version headers, rate limits per user, and auth token validation** usually happen.

## 4. Databases & Data Scaling

### Q21. SQL or NoSQL? `[Senior]`
| | Relational (PostgreSQL, MySQL) | Key-value / wide-column (DynamoDB, Cassandra) | Document (MongoDB) |
|---|---|---|---|
| Model | Tables, joins, schema | Partition key → items | JSON documents |
| Transactions | Multi-row ACID | Limited (single partition, or costly) | Per document; multi-doc newer/limited |
| Queries | Flexible SQL, ad hoc | Only by key/partition (design around access patterns) | By fields with indexes |
| Scaling writes | Vertical, then sharding (manual or Citus/Vitess) | Horizontal by design | Horizontal (sharding) |
| Best for | Money, orders, relationships, most products | Huge write volume, simple access patterns (chat messages, events, sessions) | Flexible, nested data |

**Senior answer:** "I default to PostgreSQL: transactions, constraints and flexible queries cover most products, and it scales further than people think with replicas and caching. I'd pick a wide-column store for a specific high-volume access pattern, like chat messages keyed by conversation and time."

### Q22. What do ACID and BASE mean? `[Fundamental]`
- **ACID** (relational transactions):
  - **Atomicity**: all or nothing.
  - **Consistency**: constraints hold before and after.
  - **Isolation**: concurrent transactions don't see each other's partial work (levels: read committed, repeatable read, serializable).
  - **Durability**: committed data survives crashes (write-ahead log).
- **BASE** (many distributed NoSQL stores): **B**asically **A**vailable, **S**oft state, **E**ventual consistency. Trades immediate consistency for availability and scale.

```sql
-- Transfer money atomically: both rows change or neither does
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100;
-- application checks that exactly 1 row was updated, else ROLLBACK
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

### Q23. How do indexes speed up queries, and what do they cost? `[Fundamental]`
- An index (usually a **B-tree**) lets the DB find rows in O(log n) instead of scanning the whole table.
- **Composite index** order matters: an index on `(user_id, created_at)` serves `WHERE user_id = ? ORDER BY created_at DESC` but not `WHERE created_at > ?` alone.
- **Costs**: slower writes (every index is updated on insert/update), more storage, more memory.

```sql
-- The feed query
SELECT id, text, created_at FROM posts
WHERE author_id = $1 AND created_at < $2
ORDER BY created_at DESC LIMIT 20;

-- The index that makes it fast (and enables cursor pagination on created_at)
CREATE INDEX posts_author_created ON posts (author_id, created_at DESC);

-- Verify the plan uses it
EXPLAIN ANALYZE SELECT ...;   -- look for "Index Scan", not "Seq Scan"
```

### Q24. What is database replication? `[Fundamental]`
- Keep copies of the data on several machines for **read scaling, availability, and durability**.

```
             writes
App ───────────────────▶ Primary (leader) ──replication log──▶ Replica 1 ──▶ reads
App ──────────────── reads ──────────────────────────────────▶ Replica 2 ──▶ reads
```

| Model | How | Pros | Cons |
|---|---|---|---|
| Leader–follower (primary–replica) | One node takes writes, others copy | Simple, read scaling | Single write node; failover needed |
| Multi-leader | Several nodes accept writes (e.g. one per region) | Local writes in each region | Write conflicts to resolve |
| Leaderless (Dynamo-style) | Write to N nodes, read from R, need W | Highly available | Tunable/eventual consistency, read repair |

- **Synchronous** replication: the write waits for a replica (no data loss on failover, higher latency).
- **Asynchronous**: faster, but a failover can lose the last few writes.
- Common: one synchronous standby for failover + async replicas for reads.

### Q25. What is replication lag, and how do you handle "read your own writes"? `[Senior]`
- Async replicas are behind the primary by milliseconds to seconds. A user edits their profile, the next read hits a replica, and the old value shows up.
- Fixes:
  - **Read your own writes from the primary** for a short window (e.g. 10 s after a write, or for the user's own profile always).
  - **Session consistency**: remember the write's log position (LSN); route reads to a replica only once it has caught up to that position.
  - **Client-side**: the mobile app keeps its optimistic value instead of overwriting it with a stale read.

```swift
struct ReadRouter {
    let primary: Database
    let replicas: [Database]
    let recentWrites: RecentWriteTracker      // e.g. Redis key "wrote:<userID>" with a 10 s TTL

    func database(forReadBy userID: String) async -> Database {
        if await recentWrites.contains(userID) { return primary }   // read your own writes
        return replicas.randomElement() ?? primary
    }
}
```

### Q26. What is sharding (partitioning), and how do you choose a shard key? `[Senior]`
Sharding splits one dataset across many databases so each holds a subset; writes and storage scale horizontally.

| Strategy | How | Pros | Cons |
|---|---|---|---|
| Range | `user_id 1–1M → shard 1`, … | Range scans are easy | Hot spots (new users all on the last shard) |
| Hash | `hash(user_id) % N` | Even spread | Range queries hit all shards; resharding moves most keys |
| Consistent hashing | Keys and nodes on a ring (Q28) | Adding a node moves ~1/N of keys | More complex |
| Directory / lookup | A table maps key → shard | Full flexibility, easy moves | Lookup service is critical |
| Geo | By region/country | Data locality, residency laws | Uneven sizes |

**Choosing the shard key:**
- Spread load evenly (high cardinality, no hot keys).
- Keep data accessed together on the same shard (shard chat by `conversation_id` so a conversation's messages are together).
- Avoid cross-shard queries and transactions on hot paths.

### Q27. What problems does sharding create? `[Lead/Expert]`
- **Cross-shard queries**: "top 10 posts globally" must scatter to every shard and gather results; often precomputed instead.
- **Cross-shard transactions**: no simple ACID across shards → sagas (Q71) or design so one transaction stays in one shard.
- **Joins** across shards are expensive; denormalize.
- **Hot shards**: a celebrity's data overwhelms one shard → split hot keys (e.g. append a suffix `user123#0..9`) or cache them.
- **Resharding**: moving data while serving traffic (double writes, backfill, cut over) is a project in itself.
- **Global unique IDs**: auto-increment no longer works → UUIDs, ULIDs, or Snowflake-style IDs (Q30).

**Interview line:** "Sharding is the last resort for write scaling. Before it, I'd use replicas, caching, archiving old data, and vertical scaling."

### Q28. How does consistent hashing work? `[Lead/Expert]`
- Hash both nodes and keys onto a ring (0 … 2⁶⁴). A key belongs to the first node clockwise from its position.
- Adding or removing a node only moves the keys between it and its neighbour (~1/N of keys), unlike `hash % N` where almost every key moves.
- **Virtual nodes**: each physical node appears many times on the ring, smoothing the distribution and spreading a failed node's load across many others.

```swift
/// Consistent hash ring with virtual nodes
struct HashRing {
    private var ring: [(hash: UInt64, node: String)] = []     // sorted by hash
    private let virtualNodes: Int

    init(nodes: [String], virtualNodes: Int = 150) {
        self.virtualNodes = virtualNodes
        nodes.forEach { add($0) }
    }

    mutating func add(_ node: String) {
        for i in 0..<virtualNodes { ring.append((Self.fnv1a("\(node)#\(i)"), node)) }
        ring.sort { $0.hash < $1.hash }
    }

    mutating func remove(_ node: String) { ring.removeAll { $0.node == node } }

    func node(for key: String) -> String? {
        guard !ring.isEmpty else { return nil }
        let h = Self.fnv1a(key)
        // binary search: first virtual node with hash >= h, wrapping around the ring
        var low = 0, high = ring.count
        while low < high {
            let mid = (low + high) / 2
            if ring[mid].hash < h { low = mid + 1 } else { high = mid }
        }
        return ring[low == ring.count ? 0 : low].node
    }

    /// Stable 64-bit FNV-1a (never use `hashValue`: it changes every process launch)
    static func fnv1a(_ string: String) -> UInt64 {
        var hash: UInt64 = 0xcbf29ce484222325
        for byte in string.utf8 { hash = (hash ^ UInt64(byte)) &* 0x100000001b3 }
        return hash
    }
}

// let ring = HashRing(nodes: ["cache-a", "cache-b", "cache-c"])
// ring.node(for: "user:42")   // same answer on every server and every launch
```
Used by: distributed caches (Memcached clients), Cassandra/DynamoDB partitioning, load balancers with cache affinity.

### Q29. What is denormalization, and when is it worth it? `[Senior]`
- **Normalized**: each fact stored once; joins at read time. Correct and compact.
- **Denormalized**: duplicate data to make reads cheap (store `author_name` on each post; keep a `like_count` column instead of `COUNT(*)`).
- Worth it for **read-heavy hot paths** at scale. Cost: writes must update every copy, and copies can drift (fix with background reconciliation or events).

```sql
-- Instead of COUNT(*) over a huge likes table on every feed load:
UPDATE posts SET like_count = like_count + 1 WHERE id = $1;   -- in the same transaction as the INSERT into likes
```
For very hot counters, buffer increments in Redis (`INCR`) and flush to the DB periodically.

### Q30. How do you generate unique IDs in a distributed system? `[Senior]`
| Approach | Pros | Cons |
|---|---|---|
| DB auto-increment | Simple, ordered | Single point; breaks with sharding; leaks volume |
| UUIDv4 (random) | No coordination; client can generate | 128 bits; random order hurts B-tree index locality |
| UUIDv7 / ULID | No coordination **and** time-ordered (good index locality) | 128 bits |
| Snowflake (Twitter) | 64-bit, time-ordered, compact | Needs machine IDs; clock skew handling |

```
Snowflake 64-bit layout
| 1 bit unused | 41 bits ms since epoch (~69 years) | 10 bits machine ID (1024) | 12 bits sequence (4096/ms) |
→ up to ~4M IDs per second per machine, sortable by time
```
**Mobile tie-in:** client-generated UUIDs double as idempotency keys and allow offline creation (Mobile System Design Q44).

### Q31. What is connection pooling, and why does it matter at scale? `[Senior]`
- Opening a DB connection is expensive (TCP + TLS + auth + a backend process per connection in PostgreSQL).
- A pool keeps a fixed set of open connections that requests borrow and return.
- At scale, **many app instances × pool size** can exceed the DB's connection limit. Put a pooler (PgBouncer, RDS Proxy) between them so thousands of app connections share ~100 real DB connections.
- Size pools from Little's Law (Q10): if queries take 5 ms and you run 2,000 queries/s, you need ~10 busy connections, plus headroom.

### Q32. What is the N+1 query problem? `[Fundamental]`


### Q33. How do you store large files and media? `[Fundamental]`

## 5. Caching

### Q34. Where can caches live in a system? `[Fundamental]`
```
Client cache (app memory/disk, HTTP cache)
   ↓
CDN / edge cache (static assets, images, public API responses)
   ↓
Reverse proxy cache (NGINX/Varnish)
   ↓
Application cache (in-process memory, or distributed: Redis / Memcached)
   ↓
Database buffer cache (pages in RAM)
```
- The closer to the user, the faster and the harder to invalidate.
- Interview answer: name **which data** is cached at **which layer** and **how stale it may be**.

### Q35. Which caching patterns exist? `[Senior]`
| Pattern | Read | Write | Pros | Cons |
|---|---|---|---|---|
| **Cache-aside** (lazy loading) | App checks cache → on miss reads DB and fills cache | App writes DB, then deletes the cache key | Simple; only cache what's read; cache failure isn't fatal | First read is slow; stale window possible |
| **Read-through** | Cache library loads from DB on miss | — | App code simpler | Cache layer must know the DB |
| **Write-through** | — | Write cache and DB together | Cache always fresh | Write latency; caches unread data |
| **Write-behind** (write-back) | — | Write cache; flush to DB asynchronously | Very fast writes, batching | Data loss risk if cache dies |
| **Refresh-ahead** | Refresh hot keys before expiry | — | No miss latency for hot keys | Wasted refreshes |

Cache-aside is the default answer.

```swift
struct ProductService {
    let cache: RedisClient
    let db: ProductRepository
    let ttl: Duration = .seconds(600)

    func product(id: String) async throws -> Product {
        let key = "product:\(id)"
        if let cached: Product = try? await cache.get(key) { return cached }    // 1. hit
        let product = try await db.product(id: id)                               // 2. miss → DB
        try? await cache.set(key, product, ttl: ttl.withJitter(percent: 10))     // 3. fill (failure is OK)
        return product
    }

    func update(_ product: Product) async throws {
        try await db.save(product)                       // 1. source of truth first
        try? await cache.delete("product:\(product.id)") // 2. invalidate (delete, don't set)
    }
}
```
**Why delete instead of set on update?** Two concurrent updates can set the cache in the opposite order from the DB writes, leaving the cache permanently wrong. Deleting makes the next read reload the truth.

### Q36. Which eviction policies exist? `[Fundamental]`
- **LRU** (least recently used): default for most caches (Redis `allkeys-lru`).
- **LFU** (least frequently used): keeps long-term popular items; better when popularity is stable.
- **TTL**: expire after a fixed time regardless of use.
- **FIFO / random**: simple, rarely best.
- Redis: set `maxmemory` and `maxmemory-policy` (e.g. `allkeys-lru`, `volatile-ttl`); without them Redis grows until it's killed or rejects writes.

### Q37. What is a cache stampede (thundering herd), and how do you prevent it? `[Lead/Expert]`
A hot key expires; thousands of concurrent requests miss at once and all hit the database together.

Prevention:
1. **Request coalescing (single flight)**: only one request per key loads from the DB; others wait for its result.
2. **Distributed lock**: the first instance takes a short lock (`SET lock:key NX PX 5000`); others serve stale data or wait briefly.
3. **TTL jitter**: randomize expiries (600 s ± 10%) so many keys don't expire at the same moment.
4. **Stale-while-revalidate / soft TTL**: serve the stale value and refresh in the background.
5. **Probabilistic early refresh**: each read has a small chance to refresh before expiry, rising as expiry approaches.

```swift
/// Single flight: concurrent callers for the same key share one load (per server instance)
actor SingleFlight<Value: Sendable> {
    private var inFlight: [String: Task<Value, Error>] = [:]

    func run(key: String, _ load: @escaping @Sendable () async throws -> Value) async throws -> Value {
        if let existing = inFlight[key] { return try await existing.value }
        let task = Task { try await load() }
        inFlight[key] = task
        defer { inFlight[key] = nil }
        return try await task.value
    }
}

extension Duration {
    /// 600 s with 10% jitter → somewhere in 540–660 s, so keys set together don't expire together
    func withJitter(percent: Double) -> Duration {
        let seconds = Double(components.seconds)
        return .seconds(seconds * Double.random(in: (1 - percent / 100)...(1 + percent / 100)))
    }
}
```
```
# Distributed lock in Redis so only ONE server rebuilds the value
SET lock:product:42 <random-token> NX PX 5000     # NX: only if absent; PX: auto-expire in 5 s
# ... rebuild cache ...
# release only if we still own it (Lua script compares the token, then DEL)
```

### Q38. What are cache penetration and cache avalanche? `[Senior]`
| Problem | Cause | Fix |
|---|---|---|
| **Penetration** | Requests for keys that **don't exist** (bad IDs, attacks) always miss and hit the DB | Cache negative results ("not found" for 60 s); **Bloom filter** of valid IDs in front |
| **Stampede** | One **hot key** expires | Single flight, locks, soft TTL (Q37) |
| **Avalanche** | **Many keys** expire at once, or the cache cluster restarts empty | TTL jitter, warm-up before traffic, replicated cache, rate-limit DB fallback |

A **Bloom filter** answers "definitely not present" or "possibly present" in a few bytes per item, with no false negatives. If it says "not present", skip the DB entirely.

### Q39. How do you keep the cache consistent with the database? `[Lead/Expert]`
- Perfect consistency between two systems without distributed transactions is impossible; choose an acceptable staleness.
- Techniques, from simple to robust:
  1. **TTL** bounds staleness ("at most 60 s old").
  2. **Delete on write** (cache-aside, Q35).
  3. **Delayed double delete**: delete, write DB, wait ~500 ms, delete again (covers a reader that refilled the cache with old data between the two steps).
  4. **Change data capture (CDC)**: a process tails the DB's change log (Debezium) and invalidates keys, so invalidation can't be forgotten by any code path.
  5. **Versioned values**: store a version with the value; only overwrite if newer.
- For money or inventory, read from the DB (or use the DB's own cache) on the critical path; cache only for display.

### Q40. Redis or Memcached? `[Senior]`
| | Redis | Memcached |
|---|---|---|
| Data types | Strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog | Strings only |
| Persistence | Optional (RDB snapshots, AOF log) | None |
| Replication / HA | Replicas, Sentinel, Cluster | Client-side sharding only |
| Extra uses | Rate limiting, leaderboards, queues, pub/sub, locks, sessions | Pure cache |
| Threading | Mostly single-threaded command execution | Multi-threaded |

Redis is the usual default because one tool covers caching, sessions, rate limiting and leaderboards.

```

ZREVRANGE leaderboard:weekly 0 9 WITHSCORES        # top 10
ZREVRANK leaderboard:weekly "user:42"              # my rank

# Session with expiry

```

### Q41. What is a CDN, and what should it cache? `[Fundamental]`
- A network of edge servers near users that cache content from your origin.
- **Cache**: images, video segments, JS/CSS, app config files, public API responses (`Cache-Control: public, max-age=60`).
- **Don't cache** (or cache carefully): personalized or authenticated responses (`Cache-Control: private, no-store`), unless the cache key includes the user.
- Invalidation: **versioned URLs** (`/app.v42.js`, `image.jpg?v=7`) are better than purge APIs, which are slow and rate-limited.
- Mobile tie-in: device-sized image URLs (`?w=750`) must use a **small set of sizes**, or the CDN cache fragments and hit rate drops.

### Q42. How do you cache hot keys at very high load? `[Lead/Expert]`
- One Redis shard can do ~100k+ simple ops/s; a single viral key can exceed that.
- Options:
  - **Local in-process cache** (L1) in front of Redis (L2) with a short TTL (1–5 s). Thousands of app servers each serve the key from memory.
  - **Key replication**: store `post:42#0` … `post:42#9`; readers pick a random suffix.
  - **Read replicas** of the cache shard.
- Detect hot keys with Redis `--hotkeys` (LFU policy) or client-side sampling.

```
L1 (in-process, 2 s TTL, per server) → L2 (Redis cluster, 10 min TTL) → Database
```

### Q43. What is the difference between caching and memoization at the request level? `[Fundamental]`
- **Memoization**: reuse a result within one request or one computation (e.g. the same user loaded twice while building one response). No invalidation needed; it dies with the request.
- **Caching**: shared across requests and time; needs TTLs and invalidation.
- Request-scoped memoization (like GraphQL DataLoader) removes duplicate DB calls safely and is often the first optimization.

### Q44. When should you NOT add a cache? `[Senior]`
- The data changes on almost every read (low hit rate; you pay for cache operations and still hit the DB).
- Correctness requires the latest value (balances, inventory decrements, permission checks after revocation).
- The DB isn't the bottleneck yet: an index or query fix is cheaper than a new moving part.
- You can't explain the invalidation strategy. A cache without a staleness story causes subtle bugs.

## 6. Message Queues & Asynchronous Processing

### Q45. Why use a message queue? `[Fundamental]`
A queue sits between a **producer** that creates work and a **consumer** that does it.

```
          synchronous (user waits for everything)
App ──▶ API ──▶ save order ──▶ send email ──▶ update analytics ──▶ resize images ──▶ 200 OK   (2.5 s)

          asynchronous (user waits only for what matters)
App ──▶ API ──▶ save order ──▶ publish "OrderPlaced" ──▶ 202/201 OK                          (80 ms)
                                      │
                                      ▼
                                ┌───────────┐──▶ Email worker
                                │   Queue   │──▶ Analytics worker
                                └───────────┘──▶ Image worker
```
Benefits:
- **Decoupling**: producers don't know or care who consumes.
- **Load leveling**: a traffic spike fills the queue instead of overwhelming workers; workers drain it at their own pace.
- **Resilience**: if the email service is down, messages wait and are retried; the order still succeeds.
- **Independent scaling**: add workers for the slow part only.

Costs: eventual consistency, duplicate delivery, harder debugging (trace IDs across the queue), and one more system to run.

### Q46. What is the difference between a queue, pub/sub, and a log (stream)? `[Senior]`
| Model | Delivery | After consumption | Example | Use for |
|---|---|---|---|---|
| **Queue** (point-to-point) | Each message to **one** consumer in the pool | Deleted when acknowledged | SQS, RabbitMQ queue | Jobs/tasks: "send this email" |
| **Pub/sub** | Each message to **every** subscriber | Gone once delivered | SNS, Redis Pub/Sub, RabbitMQ fanout | Notify many services of an event |
| **Log / stream** | Consumers read at their own **offset** | **Kept** for a retention period; can replay | Kafka, Kinesis, Redis Streams | Event streams, many independent consumers, replay, analytics |

Combination you'll see: **SNS → several SQS queues** (fan-out, one durable queue per consuming service), or **Kafka topic → several consumer groups**.

### Q47. Kafka, RabbitMQ, or SQS? `[Senior]`
| | Kafka | RabbitMQ | Amazon SQS |
|---|---|---|---|
| Model | Partitioned, replicated log | Broker with exchanges + queues | Managed queue |
| Throughput | Very high (millions msg/s per cluster) | High (tens of thousands/s per node) | Effectively unlimited (standard) |
| Ordering | Per partition | Per queue (single consumer) | Standard: best effort; FIFO queues: per message group |
| Replay | Yes (offsets, retention) | No (once acked, gone) | No |
| Routing | By topic + partition key | Rich (direct, topic, fanout, headers) | None (use SNS for fan-out) |
| Ops | Heavy (or managed: MSK, Confluent) | Moderate | None (fully managed) |
| Pick when | Event streaming, many consumers, replay, analytics, CDC | Complex routing, task queues, RPC-style work | Simple reliable job queues on AWS |

**Interview line:** "For background jobs on AWS I'd start with SQS plus a dead-letter queue. If many services need the same events or we want replay, Kafka."

### Q48. Explain Kafka's core concepts. `[Senior]`
```
Topic "orders" (3 partitions, replication factor 3)

Partition 0: [o1][o4][o7][o9] ...  ──▶ Consumer A ┐
Partition 1: [o2][o5][o8]      ...  ──▶ Consumer B ├─ consumer group "email-service"
Partition 2: [o3][o6]          ...  ──▶ Consumer C ┘
                       ▲
                offset = position in a partition

Same topic, another group "analytics" reads all partitions independently at its own offsets.
```
- **Topic**: named stream of records. **Partition**: an ordered, append-only log; the unit of parallelism and ordering.
- **Partition key**: `hash(key) % partitions` → all events for `order_id=42` go to one partition, so they stay **in order**.
- **Consumer group**: each partition is read by exactly one consumer in the group. Max useful consumers = number of partitions.
- **Offset**: each group commits how far it has read. Commit **after** processing for at-least-once.
- **Replication**: each partition has a leader and followers; `acks=all` + `min.insync.replicas=2` means a write survives a broker loss.
- **Retention**: by time or size; consumers can rewind to reprocess (e.g. after fixing a bug).

### Q49. What delivery guarantees exist? `[Senior]`
| Guarantee | How | Risk | Typical use |
|---|---|---|---|
| **At-most-once** | Ack/commit **before** processing | A crash loses the message | Metrics, logs where loss is OK |
| **At-least-once** | Ack/commit **after** processing | A crash after processing but before ack → **duplicate** | Default for almost everything |
| **Exactly-once** | Transactions within one system (Kafka transactions read-process-write) | Only holds inside that system; side effects outside (email, payment API) can still repeat | Stream processing pipelines |

**The key senior insight:** end-to-end exactly-once delivery across systems isn't achievable in general. What you build is **at-least-once delivery + idempotent processing = effectively-once**.

```swift
// At-least-once consumer loop: process, THEN acknowledge
for try await message in queue.messages() {
    do {
        try await handle(message)            // must be idempotent (Section 7)
        try await queue.ack(message)
    } catch {
        try await queue.nack(message, retryAfter: backoff(for: message.attempt))   // redelivered later
    }
}
```

### Q50. How do you guarantee ordering? `[Lead/Expert]`
- Global ordering means one partition / one consumer → no parallelism. Usually you only need ordering **per entity** (per user, per order, per conversation).
- Use the entity ID as the **partition key** (Kafka) or **message group ID** (SQS FIFO).
- Ordering breaks when:
  - A failed message is retried later while the next one proceeds (a retry queue reorders events).
  - Consumers process one partition's messages concurrently.
  - The producer retries a send (Kafka: enable the idempotent producer, `enable.idempotence=true`).
- Defensive consumer: carry a **version or sequence number** per entity and ignore stale events.

```swift
func apply(_ event: OrderStatusChanged) async throws {
    // Only apply if this event is newer than what we stored (out-of-order safe)
    let updated = try await db.execute("""
        UPDATE orders SET status = $1, version = $2
        WHERE id = $3 AND version < $2
        """, event.status, event.version, event.orderID)
    if updated == 0 { logger.info("Skipped stale event v\(event.version) for \(event.orderID)") }
}
```

### Q51. What is a dead-letter queue, and how do you handle poison messages? `[Senior]`
- A **poison message** always fails (bad data, a bug). With infinite retries it blocks the partition or burns CPU forever.
- **Retry policy**: retry with exponential backoff and jitter, up to N attempts (e.g. 5).
- After N failures, move it to a **dead-letter queue (DLQ)**: alert, inspect, fix, then **redrive** (replay) it.
- Distinguish errors:
  - **Transient** (timeout, 503, lock conflict) → retry.
  - **Permanent** (validation failure, 404 for a deleted entity) → DLQ or drop immediately; retrying won't help.

```swift
enum ProcessingError: Error { case transient(Error), permanent(String) }

func consume(_ message: Message) async {
    do {
        try await handle(message)
        try? await queue.ack(message)
    } catch ProcessingError.permanent(let reason) {
        await deadLetters.send(message, reason: reason)              // no point retrying
        try? await queue.ack(message)
    } catch {
        if message.attempt >= 5 {
            await deadLetters.send(message, reason: "\(error)")
            try? await queue.ack(message)
        } else {
            let delay = min(300.0, pow(2, Double(message.attempt))) * Double.random(in: 0.5...1.0)
            try? await queue.nack(message, retryAfter: .seconds(delay))
        }
    }
}
```
**DLQ must be monitored.** An unmonitored DLQ is a silent data-loss bin.

### Q52. What are consumer lag and backpressure? `[Senior]`
- **Consumer lag**: how far consumers are behind producers (Kafka: latest offset − committed offset; SQS: `ApproximateNumberOfMessagesVisible` and age of oldest message).
- **Age of oldest message** is the best user-facing metric: "emails are 12 minutes late".
- Responses to growing lag:
  - Scale consumers (up to the partition count in Kafka).
  - Batch work (write 500 rows in one insert).
  - Find the slow dependency (a consumer bound by a slow DB won't go faster with more consumers; it'll make the DB slower).
- **Backpressure**: slow the producer when the system can't keep up (bounded queues, rejecting with 429/503, pausing intake) rather than letting memory grow until something crashes.

### Q53. What is the dual-write problem, and how does the transactional outbox solve it? `[Lead/Expert]`
A handler must **save to the DB** and **publish an event**. These are two systems; no shared transaction.

```
❌ save order → (crash) → publish never happens         → payment service never hears about the order
❌ publish    → (crash) → save never happens            → event about an order that doesn't exist
```

**Transactional outbox:** write the event into an `outbox` table **in the same DB transaction** as the business change. A separate relay publishes outbox rows to the broker and marks them sent.

```
┌─────────── one DB transaction ───────────┐
│ INSERT INTO orders ...                    │
│ INSERT INTO outbox (event_type, payload)  │
└───────────────────────────────────────────┘
                 │
        Relay (polls outbox, or CDC tails the log)
                 │  publish, then mark published
                 ▼
               Broker ──▶ consumers (must be idempotent: relay may publish twice)
```

```sql
CREATE TABLE outbox (
    id            BIGSERIAL PRIMARY KEY,
    aggregate_id  TEXT NOT NULL,          -- used as the partition key, keeps per-order ordering
    event_type    TEXT NOT NULL,
    payload       JSONB NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at  TIMESTAMPTZ
);
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;
```
```swift
func placeOrder(_ input: PlaceOrder) async throws -> Order {
    try await db.transaction { tx in
        let order = try await tx.insertOrder(input)
        try await tx.insertOutbox(aggregateID: order.id, type: "OrderPlaced", payload: OrderPlaced(order))
        return order
    }   // both rows committed, or neither
}

/// Relay: runs on one instance at a time (or uses SKIP LOCKED to share work)
func relayOutbox() async throws {
    try await db.transaction { tx in
        let rows = try await tx.query("""
            SELECT * FROM outbox WHERE published_at IS NULL
            ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED
            """)
        for row in rows {
            try await broker.publish(topic: row.eventType, key: row.aggregateID, payload: row.payload)
            try await tx.execute("UPDATE outbox SET published_at = now() WHERE id = $1", row.id)
        }
    }
}
```
**Mobile tie-in:** this is the same idea as the client-side offline outbox (Mobile System Design Q41): persist the intent first, deliver it later, and make delivery safe to repeat.

### Q54. How does a consumer handle duplicate messages? `[Senior]`
At-least-once delivery means duplicates **will** happen. Options:
1. **Naturally idempotent operations**: `SET status = 'shipped'` is safe to repeat; `balance = balance + 10` is not.
2. **Dedupe table**: record processed message IDs **in the same transaction** as the side effect.
3. **Conditional writes** with versions (Q50).

```sql
CREATE TABLE processed_messages (
    consumer    TEXT NOT NULL,
    message_id  TEXT NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer, message_id)
);
```
```swift
func handle(_ message: PaymentCaptured) async throws {
    try await db.transaction { tx in
        // Claim the message; 0 rows inserted means we already processed it
        let inserted = try await tx.execute("""
            INSERT INTO processed_messages (consumer, message_id) VALUES ('ledger', $1)
            ON CONFLICT DO NOTHING
            """, message.id)
        guard inserted == 1 else { return }                     // duplicate → skip silently
        try await tx.execute("UPDATE wallets SET balance = balance + $1 WHERE user_id = $2",
                             message.amount, message.userID)
    }
}
```
Side effects outside the DB (sending an email, calling a payment API) need the downstream API's own idempotency key (Q63).

### Q55. What is a visibility timeout? `[Senior]`
- In SQS, a received message becomes **invisible** to other consumers for the visibility timeout (e.g. 30 s). If not deleted in time, it reappears and another consumer gets it.
- Set it longer than the worst-case processing time; for long jobs, **extend it** periodically (heartbeat with `ChangeMessageVisibility`).
- Too short → duplicates as two workers process the same job. Too long → slow recovery after a worker crash.
- RabbitMQ equivalent: unacked messages are redelivered when the consumer's channel closes; `prefetch` limits how many unacked messages each consumer holds.

### Q56. What is the difference between events and commands, and how do you version event schemas? `[Senior]`
| | Command | Event |
|---|---|---|
| Meaning | "Do this" (`SendEmail`) | "This happened" (`OrderPlaced`) |
| Receivers | One handler | Zero or more subscribers |
| Can be rejected? | Yes | No, it's a fact in the past |
| Naming | Imperative | Past tense |

Schema evolution rules (same as API versioning):
- **Add** optional fields; never rename or remove fields that consumers read; never change a field's meaning or type.
- Include `event_type`, `event_version`, `event_id`, `occurred_at`, and a `trace_id` in every envelope.
- Use a schema registry (Avro/Protobuf with compatibility checks) at scale.

```swift
struct EventEnvelope<Payload: Codable & Sendable>: Codable, Sendable {
    let eventID: UUID            // dedupe key for consumers
    let eventType: String        // "OrderPlaced"
    let eventVersion: Int        // bump only for breaking changes; publish both versions during migration
    let occurredAt: Date
    let traceID: String          // follow one request across services
    let payload: Payload
}
```

### Q57. What are event sourcing and CQRS? `[Lead/Expert]`
- **Event sourcing**: store the **sequence of events** (`Deposited 100`, `Withdrew 30`) as the source of truth; current state is derived by replaying them.
  - Pros: full audit trail, time travel, rebuild new views from history.
  - Cons: complexity, event schema evolution forever, snapshots needed for long histories, hard to query current state directly.
- **CQRS** (Command Query Responsibility Segregation): separate **write model** from **read models**. Writes go to a normalized store; events update denormalized read stores (a search index, a feed cache).
- They are often used together but are independent ideas.
- **When:** ledgers, audit-heavy domains, collaborative editing. **Not** a default for CRUD apps.

```
Commands ──▶ Write model (DB / event store) ──events──▶ Projector ──▶ Read models
                                                                    ├─ Elasticsearch (search)
                                                                    ├─ Redis (feed)
                                                                    └─ Warehouse (analytics)
```

### Q58. How do you fan out one event to many services? `[Senior]`
- **SNS topic → one SQS queue per service**: each service gets its own durable copy, its own retry/DLQ, and can't slow the others.
- **Kafka**: one topic, one consumer group per service.
- Anti-pattern: one shared queue read by different services; each message reaches only one of them.

```
OrderPlaced ──▶ SNS "orders" ──┬──▶ SQS "email-orders"      ──▶ Email service      (+DLQ)
```

### Q59. How do you implement delayed and scheduled jobs? `[Senior]`
| Need | Approach |
|---|---|
| Short delay (≤ 15 min) | SQS `DelaySeconds`, RabbitMQ delayed-message plugin |
| "Remind user in 3 days" | Store `run_at` in a `jobs` table; a scheduler polls `WHERE run_at <= now()` with `FOR UPDATE SKIP LOCKED` |

| Recurring (nightly reports) | Cron/managed scheduler (EventBridge Scheduler, Kubernetes CronJob) that **enqueues** work rather than doing it |

Make scheduled jobs **idempotent** and **lockable**: two scheduler instances must not both send the reminder.

```sql
-- Many workers can pull due jobs safely; each row goes to exactly one worker
UPDATE jobs SET status = 'running', locked_at = now()
WHERE id IN (
    SELECT id FROM jobs
    WHERE status = 'pending' AND run_at <= now()
    ORDER BY run_at LIMIT 50
    FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

### Q60. Design an asynchronous processing pipeline (e.g. media uploads). `[Lead/Expert]`

## 7. Idempotency

### Q61. What is idempotency? Which HTTP methods are idempotent? `[Fundamental]`
An operation is **idempotent** if performing it once or many times has the same effect on the server's state.

| Method | Idempotent? | Safe (no state change)? | Note |
|---|---|---|---|
| GET, HEAD, OPTIONS | Yes | Yes | |
| PUT | Yes | No | Replace the resource with this full state |
| DELETE | Yes | No | Second delete returns 404 or 204; the **state** is the same |
| POST | **No** | No | "Create" twice → two orders |
| PATCH | Not guaranteed | No | `{"name": "A"}` is; `{"op": "increment"}` isn't |

Idempotency is about **effects**, not identical responses: a repeated DELETE can return 404 and still be idempotent.

### Q62. Why does a reliable system need idempotency? `[Fundamental]`
Because of **timeout ambiguity**: when a request times out, the client can't know whether the server did the work.

```
App ── POST /payments ──▶ Server charges the card ✅
App ◀── response lost (tunnel, app suspended, LB timeout) ── ✗
App: "Did it work?" → retries → second charge ❌
```
Every layer retries: the user taps again, `URLSession` waits for connectivity, the mobile outbox replays, the load balancer retries, the queue redelivers. **Retries are only safe if the operation is idempotent.** That makes idempotency the price of reliability.

### Q63. How do you design an idempotency-key API (Stripe-style)? `[Lead/Expert]`
The client generates a unique key per **logical operation** and sends it as a header. The server stores the key with the result; a retry with the same key returns the stored result instead of repeating the work.

```
POST /v1/payments
Idempotency-Key: 6f1c0a8e-3c1d-4b8e-9f9a-2d4b1e7c5a10
{ "amount": 4999, "currency": "usd", "source": "card_123" }
```

```sql
CREATE TABLE idempotency_keys (
    user_id         TEXT NOT NULL,
    key             TEXT NOT NULL,
    request_hash    TEXT NOT NULL,               -- SHA-256 of method + path + body
    status          TEXT NOT NULL,               -- 'in_progress' | 'completed'
    response_code   INT,
    response_body   JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    locked_until    TIMESTAMPTZ,                 -- lets a crashed attempt be retried later
    PRIMARY KEY (user_id, key)                   -- keys are scoped per user/account
);
-- Expire after 24 h (Stripe keeps keys for at least 24 hours)
```

**Flow:**

| Situation | Response |
|---|---|
| New key | Insert `in_progress`, do the work, store response, mark `completed`, return it |
| Same key, same request, **completed** | Return the stored response (same status code and body) |
| Same key, same request, **in progress** | `409 Conflict` (client retries later) |
| Same key, **different** request body | `422 Unprocessable Entity` (client bug: key reused) |

```swift
struct IdempotentPayments {
    let db: Database
    let paymentProvider: PaymentProvider

    func create(_ req: CreatePayment, key: String, userID: String) async throws -> HTTPResponse {
        let hash = req.sha256()

        // 1. Claim the key atomically. The primary key makes concurrent duplicates lose the race.
        let claimed = try await db.execute("""
            INSERT INTO idempotency_keys (user_id, key, request_hash, status, locked_until)
            VALUES ($1, $2, $3, 'in_progress', now() + interval '60 seconds')
            ON CONFLICT (user_id, key) DO NOTHING
            """, userID, key, hash)

        if claimed == 0 {
            let existing = try await db.idempotencyRecord(userID: userID, key: key)
            guard existing.requestHash == hash else {
                return .init(status: 422, body: ["error": "Idempotency-Key reused with a different request"])
            }
            if existing.status == "completed" {
                return .init(status: existing.responseCode!, body: existing.responseBody!)   // replay
            }
            return .init(status: 409, body: ["error": "Request with this key is in progress"])
        }

        // 2. Do the work. Pass the SAME key downstream so the provider also dedupes.
        do {
            let payment = try await paymentProvider.charge(req, idempotencyKey: "\(userID):\(key)")
            let response = HTTPResponse(status: 201, body: payment.json)
            // 3. Store the result
            try await db.execute("""
                UPDATE idempotency_keys SET status = 'completed', response_code = $3, response_body = $4
                WHERE user_id = $1 AND key = $2
                """, userID, key, response.status, response.body)
            return response
        } catch let error as PaymentError where error.isDefinitive {
            // A definitive business failure (card declined) is a result too: store and replay it
            let response = HTTPResponse(status: 402, body: error.json)
            try await db.completeIdempotencyKey(userID: userID, key: key, response: response)
            return response
        } catch {
            // Unknown outcome (timeout): release the key so a retry can resume;
            // the provider-side key prevents a double charge
            try await db.execute("DELETE FROM idempotency_keys WHERE user_id = $1 AND key = $2", userID, key)
            throw error
        }
    }
}
```
Key points interviewers look for:
- **Atomic claim** (unique constraint), not "check then insert" (race condition).
- Keys scoped per user; validated as UUIDs; expire (24 h–7 days).
- Store and replay **definitive** results, including errors like "card declined".
- Propagate the key to downstream calls.
- For multi-step operations, Stripe records **recovery points** so a retry resumes after the last completed step.

### Q64. What happens if two requests with the same key arrive at the same time? `[Senior]`
- Both try `INSERT ... ON CONFLICT DO NOTHING`. The DB's unique index lets exactly **one** succeed; the other gets 0 rows and sees `in_progress` → 409.
- Wrong approaches:
  - `SELECT` to check, then `INSERT` → both see "not found" and both proceed.
  - A Redis `GET` check without `SET NX` → same race.
- With Redis: `SET idem:<user>:<key> in_progress NX EX 86400` is atomic; still store the final response durably if correctness matters.

### Q65. How do you make operations naturally idempotent without keys? `[Senior]`
| Non-idempotent | Idempotent alternative |
|---|---|
| `POST /orders` (server generates ID) | `PUT /orders/{clientGeneratedUUID}` |
| `balance = balance + 10` | Insert a ledger entry with a unique `transaction_id`; balance = sum of entries |
| `INSERT` a like | `INSERT ... ON CONFLICT (user_id, post_id) DO NOTHING` |
| `toggle favorite` | `PUT /favorites/{id}` (set) and `DELETE /favorites/{id}` (unset) |
| Update with last write wins | Conditional update: `WHERE version = $expected` or `If-Match: "etag"` → 412 if changed |

```http
PUT /v1/posts/42/like            ← "make it liked" (repeatable)
POST /v1/posts/42/toggle-like    ← ❌ a retry flips it back
```

### Q66. How do you prevent duplicate processing in background jobs and webhooks? `[Senior]`
- **Webhooks** (Stripe, Apple App Store Server Notifications) are delivered at least once and possibly out of order:
  - Verify the signature.
  - Dedupe by the provider's event ID (`processed_messages` table, Q54).
  - Return 2xx quickly; process asynchronously via a queue.
  - Don't trust ordering: fetch the current state from the provider's API if needed.
- **Jobs**: deterministic job IDs (`send-receipt:<orderID>`) so enqueuing twice creates one job; idempotent handlers; "already sent" flags written in the same transaction as the side effect record.

### Q67. What must the mobile client do for idempotency to work? `[Senior]`
- Generate the key **once per user intent** (tap "Pay"), not per HTTP attempt.
- **Persist** the key with the pending operation (outbox) so it survives app termination and is reused on the retry after relaunch.
- Reuse the same key for automatic retries; generate a new key only when the user starts a **new** operation (e.g. edits the amount).
- Treat `409` as "still processing, retry later" and `422` as a client bug.

```swift
struct PendingPayment: Codable, Sendable {
    let idempotencyKey: UUID          // created when the user tapped "Pay", saved to disk
    let amount: Int
    let currency: String
}

func submit(_ payment: PendingPayment) async throws -> Receipt {

    request.httpBody = try JSONEncoder().encode(payment)

        try await api.send(request, as: Receipt.self)
    }
}
```

## 8. Consistency & Distributed Systems

### Q68. What is the CAP theorem? `[Fundamental]`
In a distributed data store, when a **network partition** happens, you must choose between:
- **Consistency (C)**: every read sees the latest write (or gets an error).
- **Availability (A)**: every request gets a non-error response (possibly stale).

```
       Region A  ✂ network partition ✂  Region B
   user writes x=2                   user reads x
   CP: B refuses (error/timeout) until it can confirm the latest value
   AP: B answers x=1 (stale), reconciles later
```
- **P is not optional**: networks partition. So the real choice is **CP or AP during a partition**.
- CP examples: bank balances, inventory reservations, leader election (ZooKeeper, etcd, Spanner).
- AP examples: likes counts, feeds, shopping cart (Dynamo-style), DNS.
- Systems can choose per operation: checkout is CP, product reviews are AP.

### Q69. What is PACELC, and what consistency models exist? `[Lead/Expert]`
**PACELC**: if **P**artition, choose **A** or **C**; **E**lse (normal operation), choose **L**atency or **C**onsistency. Even without failures, strong consistency costs latency (waiting for replicas or a quorum across regions).

| Model | Guarantee | Example |
|---|---|---|
| **Linearizable** (strong) | Behaves like a single copy; reads see the latest completed write | etcd, Spanner, single-leader DB reading from the leader |
| **Sequential** | All nodes see operations in the same order | |
| **Causal** | Causally related writes are seen in order (a reply appears after its message) | Some geo-replicated stores |
| **Read-your-writes** | You always see your own updates | Session stickiness to the leader |
| **Monotonic reads** | You never see time go backwards | Pin a user to one replica |
| **Eventual** | Replicas converge if writes stop | DNS, Cassandra (ONE), counters |

**Interview line:** "Most features are fine with eventual consistency plus read-your-writes for the user's own actions. Money, inventory and uniqueness constraints need strong consistency."

### Q70. What is two-phase commit, and why is it often avoided? `[Lead/Expert]`
```
Coordinator ──1. PREPARE──▶ DB A: "yes, I can commit" (locks held)
            ──1. PREPARE──▶ DB B: "yes"
            ──2. COMMIT───▶ DB A, DB B
```
- Atomic commit across several resources.
- Problems:
  - **Blocking**: if the coordinator dies after PREPARE, participants hold locks until it recovers.
  - Latency: two round trips, locks held across the network.
  - Many modern systems (Kafka, most NoSQL stores, third-party APIs like Stripe) don't support participating in XA transactions.
- Used inside some databases (distributed SQL like Spanner/CockroachDB use variants internally). Between microservices, prefer **sagas** (Q71) and the outbox (Q53).

### Q71. What is the saga pattern? `[Lead/Expert]`
A saga is a sequence of **local transactions**; if a step fails, earlier steps are undone by **compensating actions**.

```
Order saga (happy path):
 1. Order service:     create order (PENDING)
 2. Payment service:   charge card
 3. Inventory service: reserve items
 4. Order service:     mark CONFIRMED

Failure at step 3 (out of stock):
 3 fails → compensate 2: refund card → compensate 1: mark order CANCELLED
```

| | Choreography | Orchestration |
|---|---|---|
| How | Each service reacts to events and emits the next | A central orchestrator tells each service what to do |
| Pros | Loose coupling, no central component | Flow visible in one place; easier timeouts and compensation |
| Cons | Hard to follow and debug as steps grow | Orchestrator is extra infrastructure |
| Tools | Kafka/SNS events | Temporal, AWS Step Functions, a state machine in your DB |

```swift
enum OrderSagaState: String, Codable {
    case started, paymentCharged, inventoryReserved, confirmed
    case compensating, cancelled
}

/// Orchestrated saga: each step is idempotent and has a compensation
struct OrderSaga {
    let payments: PaymentClient
    let inventory: InventoryClient
    let store: SagaStore                  // persists state so a crash resumes, not restarts

    func run(_ order: Order) async throws {
        var state = try await store.state(for: order.id) ?? .started
        do {
            if state == .started {
                try await payments.charge(order, idempotencyKey: "charge:\(order.id)")
                state = .paymentCharged; try await store.save(state, for: order.id)
            }
            if state == .paymentCharged {
                try await inventory.reserve(order.items, idempotencyKey: "reserve:\(order.id)")
                state = .inventoryReserved; try await store.save(state, for: order.id)
            }
            state = .confirmed; try await store.save(state, for: order.id)
        } catch {
            try await store.save(.compensating, for: order.id)
            if state == .paymentCharged || state == .inventoryReserved {
                try await payments.refund(order, idempotencyKey: "refund:\(order.id)")
            }
            try await store.save(.cancelled, for: order.id)
        }
    }
}
```
- Compensation isn't a rollback: the customer may have seen the charge; a refund is a new business action.
- Every step and compensation must be **idempotent** (the saga can retry after a crash).
- Isolation is weaker than ACID: other requests can see intermediate states ("payment taken, not yet reserved"). Design states the UI can explain.

### Q72. How do quorums work (N, W, R)? `[Lead/Expert]`
- **N** replicas per key; a write succeeds when **W** acknowledge; a read queries **R** replicas and takes the newest version.
- If **W + R > N**, every read set overlaps the latest write set → read sees the latest value (with caveats around concurrent writes and failures).
- N=3, W=2, R=2: tolerates one node down for both reads and writes.
- W=1, R=1: fastest, eventual consistency. W=N: slow writes, any failure blocks writes.
- Cassandra exposes this as consistency levels (`ONE`, `QUORUM`, `LOCAL_QUORUM`, `ALL`) per query.

### Q73. How do distributed locks work, and what are fencing tokens? `[Lead/Expert]`
Use case: only one worker should run the nightly billing job, or rebuild a cache key.

```
# Acquire: atomic set-if-absent with expiry (expiry prevents deadlock if the holder crashes)
SET lock:billing <random-token> NX PX 30000

# Release: only if we still own it (Lua makes check+delete atomic)
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end
```
**The trap:** a holder pauses (GC pause, network stall) past the expiry; another worker takes the lock; now **two** think they hold it.

**Fencing token:** the lock service hands out an increasing number with each grant; the protected resource rejects writes with an older token.

```
Worker 1 gets lock, token 33 ── long pause ──────────────▶ write(token 33) → REJECTED (already saw 34)
Worker 2 gets lock (expired), token 34 ──▶ write(token 34) → accepted
```
- For correctness-critical locks, use a consensus-backed store (etcd, ZooKeeper, a DB row lock) and fencing. Redis locks are fine for **efficiency** (avoid duplicate work), not for **correctness**.
- Often simpler: a DB `SELECT ... FOR UPDATE SKIP LOCKED` or a unique constraint does the job without a lock service.

### Q74. What are leader election and consensus? `[Lead/Expert]`
- **Consensus**: several nodes agree on a value (who the leader is, the order of log entries) even when some fail. Algorithms: **Raft**, Paxos.
- Raft in one breath: nodes elect a leader by majority vote for a numbered **term**; the leader appends entries to its log and replicates them; an entry is committed once a **majority** has it; if the leader fails, a new election starts.
- A cluster of **2f + 1** nodes tolerates **f** failures (3 nodes → 1 failure, 5 → 2).
- You rarely implement this; you use **etcd, ZooKeeper, Consul**, or a managed DB that does it internally. Know what it's for: leader election, config, locks, service discovery.

### Q75. Why can't you trust timestamps across machines? `[Lead/Expert]`
- Wall clocks drift and get corrected by NTP (they can jump backwards); skew of tens of milliseconds between servers is normal, and devices can be off by hours.
- **Last-write-wins** by timestamp can silently discard the actual latest write.
- Alternatives:
  - **Server-assigned sequence numbers** from a single authority (a DB sequence per conversation).
  - **Lamport clocks**: counter incremented on each event and on receive (`max(local, received) + 1`) → a consistent total order (ties broken by node ID).
  - **Vector clocks**: detect concurrent writes (neither happened before the other) so they can be merged instead of one being lost.
  - **Hybrid logical clocks** (HLC): physical time plus a logical counter (CockroachDB).
- **Mobile tie-in:** never order chat messages by the device clock (Mobile System Design Q45, Q49); the server assigns order.

```swift
struct LamportClock {
    private(set) var time: UInt64 = 0
    mutating func tick() -> UInt64 { time += 1; return time }                       // local event / send
    mutating func receive(_ remote: UInt64) -> UInt64 { time = max(time, remote) + 1; return time }
}
```

### Q76. Optimistic or pessimistic concurrency control? `[Senior]`
| | Pessimistic | Optimistic |
|---|---|---|
| How | Lock the row before changing it (`SELECT ... FOR UPDATE`) | Read a version; update only if unchanged (`WHERE version = $v`) |
| Best when | High contention (seat booking for a hot concert) | Low contention (editing a profile) |
| Cost | Waiting, deadlock risk, lock held across slow work | Retries on conflict |
| HTTP form | — | `ETag` + `If-Match` → `412 Precondition Failed` |

```sql
-- Optimistic: 0 rows updated means someone else changed it → reload and retry, or show a conflict
UPDATE documents SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;

-- Pessimistic: hold the row while deciding (keep the transaction short)
BEGIN;
SELECT available FROM seats WHERE id = $1 FOR UPDATE;
UPDATE seats SET available = false, holder = $2 WHERE id = $1;
COMMIT;

-- Often best: a single atomic conditional statement, no read needed
UPDATE inventory SET stock = stock - 1 WHERE sku = $1 AND stock > 0;   -- 0 rows → sold out
```

## 9. Reliability, Rate Limiting & Resilience

### Q77. How do you remove single points of failure? `[Fundamental]`
Walk the request path and ask "what if this box dies?" for each component.

| Component | Redundancy |
|---|---|
| DNS | Managed DNS with anycast (Route 53, Cloudflare) |
| Load balancer | Managed LB across availability zones (Q18) |
| App servers | ≥ 2 per AZ, stateless, autoscaled |

### Q78. Why are timeouts so important, and how do you set them? `[Senior]`
- Without a timeout, a slow dependency holds threads/connections until the whole service runs out and fails too (**cascading failure**).
- Set timeouts on **every** network call: connect timeout (short, ~1 s) and request timeout (based on the dependency's p99.9, e.g. 2× p99).
- **Deadline propagation**: the edge sets a total budget (e.g. 3 s); each hop passes the remaining time down (gRPC deadlines do this automatically). No point continuing work the client has already given up on.

```
Client budget 3 s ──▶ API (spent 50 ms) ──▶ remaining 2.95 s ──▶ Feed service (spent 400 ms) ──▶ remaining 2.55 s ──▶ DB
```

```swift
/// Run an operation with a deadline; the losing task is cancelled
func withTimeout<T: Sendable>(_ timeout: Duration, _ operation: @escaping @Sendable () async throws -> T) async throws -> T {
    try await withThrowingTaskGroup(of: T.self) { group in
        group.addTask { try await operation() }
        group.addTask {
            try await Task.sleep(for: timeout)
            throw TimeoutError()
        }
        defer { group.cancelAll() }
        return try await group.next()!
    }
}
struct TimeoutError: Error {}
```

### Q79. How should retries work, and how can they make things worse? `[Senior]`
- Retry only **transient** failures (timeouts, 502/503/504, connection reset, 429 after `Retry-After`) and only **idempotent** operations (Section 7).
- **Exponential backoff with jitter**: without jitter, all clients retry in sync and hit the recovering service in waves.
- **Cap attempts** (3–5) and total time.
- **Retry storms**: if every layer retries 3×, a 4-layer call chain can multiply load by 3⁴ = 81× on the failing service. Retry at **one layer** (usually the edge or the caller nearest the failure), and use a **retry budget** (e.g. retries ≤ 10% of requests).

```swift
/// Exponential backoff with "full jitter" (AWS Architecture Blog recommendation)
func withRetry<T: Sendable>(
    maxAttempts: Int = 4,
    baseDelay: Duration = .milliseconds(100),
    maxDelay: Duration = .seconds(5),
    isRetryable: @Sendable (Error) -> Bool = { ($0 as? HTTPError)?.isTransient ?? ($0 is TimeoutError) },
    _ operation: @Sendable () async throws -> T
) async throws -> T {
    var attempt = 0
    while true {
        do {
            return try await operation()
        } catch {
            attempt += 1
            guard attempt < maxAttempts, isRetryable(error), !Task.isCancelled else { throw error }
            if let retryAfter = (error as? HTTPError)?.retryAfter {          // server knows best
                try await Task.sleep(for: retryAfter)
                continue
            }
            let exponential = baseDelay * (1 << (attempt - 1))               // 100, 200, 400 ms…
            let capped = min(exponential, maxDelay)
            let jittered = capped * Double.random(in: 0...1)                // full jitter
            try await Task.sleep(for: jittered)
        }
    }
}
```

### Q80. What is a circuit breaker? `[Senior]`
Stops calling a dependency that is failing, so callers fail fast (or use a fallback) and the dependency gets time to recover.

```
         failures ≥ threshold
 CLOSED ─────────────────────▶ OPEN  (reject immediately, no calls)
   ▲                            │
   │ trial succeeds             │ after cool-down
   │                            ▼
   └──────────────────────── HALF-OPEN (let a few trial calls through)
              trial fails → back to OPEN
```

```swift
actor CircuitBreaker {
    enum State { case closed(failures: Int), open(until: ContinuousClock.Instant), halfOpen }
    struct OpenError: Error {}

    private var state: State = .closed(failures: 0)
    private let failureThreshold: Int
    private let coolDown: Duration
    private let clock = ContinuousClock()

    init(failureThreshold: Int = 5, coolDown: Duration = .seconds(30)) {
        self.failureThreshold = failureThreshold
        self.coolDown = coolDown
    }

    /// Ask before calling the dependency
    func allowRequest() throws {
        switch state {
        case .closed, .halfOpen:
            return
        case .open(let until):
            guard clock.now >= until else { throw OpenError() }
            state = .halfOpen                       // let one trial through
        }
    }

    func recordSuccess() { state = .closed(failures: 0) }

    func recordFailure() {
        switch state {
        case .closed(let failures) where failures + 1 < failureThreshold:
            state = .closed(failures: failures + 1)
        default:                                    // threshold reached, or the half-open trial failed
            state = .open(until: clock.now + coolDown)
        }
    }
}

// Usage: keep the network call OUTSIDE the actor so the breaker isn't blocked while waiting
func recommendations(for userID: String) async -> [Item] {
    do {
        try await breaker.allowRequest()
        let items = try await withTimeout(.milliseconds(300)) { try await recsService.fetch(userID) }
        await breaker.recordSuccess()
        return items
    } catch is CircuitBreaker.OpenError {
        return popularItemsCache.value               // fallback while open
    } catch {
        await breaker.recordFailure()
        return popularItemsCache.value
    }
}
```
Production breakers use a **failure rate over a sliding window** (e.g. > 50% of the last 100 calls) rather than consecutive failures, and limit half-open trials to a few requests. Libraries: Resilience4j (Java), Polly (.NET), Envoy outlier detection (service mesh).

### Q81. What is the bulkhead pattern? `[Senior]`
- Named after ship compartments: isolate resources so one failing part can't sink everything.
- Separate connection pools / thread pools / concurrency limits **per dependency**: if the recommendations service hangs, it can use at most its 20 slots, and checkout keeps working.
- Separate worker pools or queues per priority or tenant.

```swift
/// Limit concurrent calls to one dependency (a semaphore for async code)
actor ConcurrencyLimiter {
    private let limit: Int
    private var running = 0
    init(limit: Int) { self.limit = limit }

    func run<T: Sendable>(_ work: @Sendable () async throws -> T) async throws -> T {
        guard running < limit else { throw OverloadedError() }      // shed instead of queueing forever
        running += 1
        defer { running -= 1 }
        return try await work()
    }
}
struct OverloadedError: Error {}

let recsBulkhead = ConcurrencyLimiter(limit: 20)
let paymentsBulkhead = ConcurrencyLimiter(limit: 100)
```
Note: `run` is actor-isolated, so `work` executes while the actor is suspended at `await`; other callers can enter and the counter stays correct because all mutations happen on the actor.

### Q82. What are graceful degradation and load shedding? `[Lead/Expert]`
- **Graceful degradation**: when a non-critical dependency fails, return a reduced response instead of an error.
  - Feed without "people you may know"; product page without reviews; cached prices with a "may be outdated" flag.
  - Mark which features are **critical** (login, checkout) and which are **optional**.
- **Load shedding**: when overloaded, reject some requests early (fast 503/429) so the rest succeed, rather than everyone timing out.
  - Shed by priority: drop analytics and prefetch traffic before user-initiated requests; drop free-tier before paid.
  - Mobile clients can send a priority header (`X-Request-Priority: background`).
- **Mobile tie-in:** the app should treat optional sections as optional too: render the screen when a secondary call fails.

### Q83. Why rate limit, and where? `[Fundamental]`
Why:
- Protect services from overload (bugs, retry storms, traffic spikes).
- Prevent abuse: credential stuffing on login, scraping, spam, SMS-pumping fraud on OTP endpoints.
- Fairness between tenants; enforce paid plan quotas; control cost of expensive calls.

Where:
- **Edge** (CDN/WAF, API gateway): per IP, coarse, cheap.
- **Application**: per user / API key / endpoint, with business rules ("5 OTP SMS per phone per hour").
- **Before expensive dependencies**: protect a third-party API with its own quota.

Response contract:
```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
```
Clients must honor `Retry-After` (the `withRetry` in Q79 does).

### Q84. Compare rate-limiting algorithms. `[Senior]`
| Algorithm | How | Pros | Cons |
|---|---|---|---|
| **Fixed window counter** | Count per window (`user:42:12:05`), reset each minute | Simplest; one Redis `INCR` | Bursts at boundaries: 100 at 12:05:59 + 100 at 12:06:00 = 200 in 2 s |
| **Sliding window log** | Store each request timestamp; count those in the last 60 s | Exact | Memory per request |
| **Sliding window counter** | Weighted mix of current and previous window counts | Smooth, cheap, approximate | Approximation |
| **Token bucket** | Bucket refills at rate r up to capacity b; each request takes a token | Allows bursts up to b, steady rate r; very common (AWS, Stripe) | Two parameters to tune |
| **Leaky bucket** | Requests queue and leave at a fixed rate | Smooth output rate | Adds queueing delay; bursts wait |

Sliding window counter estimate:
```
count ≈ current_window_count + previous_window_count × (1 − elapsed_fraction_of_current_window)
e.g. 30 s into the minute: 40 + 80 × 0.5 = 80
```

### Q85. Implement a token bucket. `[Senior]`
```swift
/// In-process token bucket per key (one server). For many servers, see Q86.
actor TokenBucketLimiter {
    private struct Bucket { var tokens: Double; var lastRefill: ContinuousClock.Instant }

    private let capacity: Double              // max burst
    private let refillPerSecond: Double       // steady rate
    private var buckets: [String: Bucket] = [:]
    private let clock = ContinuousClock()

    init(capacity: Int, refillPerSecond: Double) {
        self.capacity = Double(capacity)
        self.refillPerSecond = refillPerSecond
    }

    /// Returns nil if allowed, or how long to wait before retrying
    func acquire(key: String, cost: Double = 1) -> Duration? {
        let now = clock.now
        var bucket = buckets[key] ?? Bucket(tokens: capacity, lastRefill: now)

        // Refill based on elapsed time (not a timer, so no drift and no background work)
        let elapsed = bucket.lastRefill.duration(to: now)
        let elapsedSeconds = Double(elapsed.components.seconds) + Double(elapsed.components.attoseconds) / 1e18
        bucket.tokens = min(capacity, bucket.tokens + elapsedSeconds * refillPerSecond)
        bucket.lastRefill = now

        defer { buckets[key] = bucket }
        if bucket.tokens >= cost {
            bucket.tokens -= cost
            return nil
        }
        let missing = cost - bucket.tokens
        return .seconds(missing / refillPerSecond)
    }
}

// 10 requests burst, 2 per second sustained
let limiter = TokenBucketLimiter(capacity: 10, refillPerSecond: 2)
if let wait = await limiter.acquire(key: "user:42") {
    throw HTTPError.tooManyRequests(retryAfter: wait)
}
```
Production note: evict idle buckets (an LRU or TTL) or the dictionary grows with every user ever seen.

### Q86. How do you rate limit across many servers? `[Lead/Expert]`
Counters must be shared, so they live in **Redis** (fast, atomic ops, TTLs).

```
# Fixed window: atomic increment, set expiry on first hit
MULTI
INCR   rl:user:42:202611021205
EXPIRE rl:user:42:202611021205 60
EXEC
# allowed if the INCR result ≤ limit
```

```lua
-- Sliding window log with a sorted set (exact), run atomically as one Lua script
-- KEYS[1] = rl:user:42   ARGV = now_ms, window_ms, limit, unique_request_id
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])     -- drop entries older than the window
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1                                                        -- allowed
end
return 0                                                          -- limited
```
Design considerations:
- **Atomicity**: use Lua scripts or `MULTI`; a GET-then-SET races between servers.
- **Latency**: one Redis round trip per request (~0.5 ms in-region). For extreme scale, keep a local token bucket per server and sync to Redis periodically (approximate but cheaper).
- **Redis down**: **fail open** (allow traffic, log it) for general APIs; **fail closed** for abuse-sensitive endpoints like login or OTP.
- **Keys**: by user ID when authenticated, by IP (careful with carrier NAT: many mobile users share one IP) or device ID otherwise.
- Return the headers from Q83 so well-behaved clients slow down.

### Q87. What are RPO and RTO, and how do they shape disaster recovery? `[Senior]`
- **RPO** (Recovery Point Objective): how much data you can afford to lose (e.g. 5 minutes of writes).
- **RTO** (Recovery Time Objective): how long you can be down (e.g. 1 hour).

| Strategy | RPO | RTO | Cost |
|---|---|---|---|
| Backups restored to a new region | Hours | Hours–days | $ |
| Pilot light (DB replicated, minimal app infra off) | Minutes | Tens of minutes | $$ |
| Warm standby (scaled-down copy running) | Seconds–minutes | Minutes | $$$ |
| Active-active multi-region | ~0 | ~0 (traffic shifts) | $$$$ + data conflict complexity |

**Backups you never restored aren't backups.** Test restores regularly; point-in-time recovery for databases.

### Q88. How do you deploy safely, including database changes? `[Senior]`
| Strategy | How | Rollback |
|---|---|---|
| Rolling | Replace instances a few at a time | Roll forward/back gradually |
| Blue-green | Bring up a full new environment; switch traffic at the LB | Switch back instantly |
| Canary | Send 1% → 10% → 50% → 100% with automated checks on error rate/latency | Stop and route back |
| Feature flags | Deploy dark; enable per user/percentage | Flip the flag off |

**Expand/contract migrations** (old and new code run at the same time during a deploy, and **old mobile apps live for years**):
1. **Expand**: add the new column/table (nullable); deploy code that writes **both** old and new.
2. **Backfill** existing rows in batches.
3. Switch reads to the new column.
4. **Contract**: stop writing the old one; drop it **much later** (after every client and service version that reads it is gone).

Never rename a column or change its type in one step; never run a long table-locking migration at peak (use online schema change tools, `CREATE INDEX CONCURRENTLY`).

### Q89. How do you survive a reconnect storm after an outage? `[Lead/Expert]`
When the service recovers, millions of mobile clients reconnect and resync at the same moment, and the spike can knock it over again.

- **Client side**: exponential backoff **with jitter** on reconnect; randomized delay before a full resync; honor `Retry-After`.
- **Server side**: admission control (accept N new connections/s per node), load shedding of low-priority sync, warm caches before reopening traffic, increase capacity before flipping traffic back.
- **Push**: never send a "please sync" silent push to all users at once; stagger it.
- **Sync design**: delta sync from a cursor, not "download everything".

### Q90. What are SLIs, SLOs, SLAs and error budgets? `[Senior]`
| Term | Meaning | Example |
|---|---|---|
| **SLI** (indicator) | A measured metric of user experience | % of `GET /feed` requests that succeed in < 300 ms |
| **SLO** (objective) | Target for the SLI | 99.9% over 30 days |
| **SLA** (agreement) | Contract with consequences (credits) | 99.5%, refund if missed |
| **Error budget** | 100% − SLO | 0.1% ≈ 43 min/month of "bad" requests allowed |

- When the error budget is healthy, ship faster; when it's spent, freeze risky launches and fix reliability.
- SLOs should measure what **users** feel (successful requests, latency at p99), ideally including client-side measurements from the app.

### Q91. REST, gRPC, or GraphQL on the backend? `[Senior]`
| | REST + JSON | gRPC + Protobuf | GraphQL |
|---|---|---|---|
| Transport | HTTP/1.1 or 2 | HTTP/2 | HTTP (usually POST) |

### Q92. How do you version and evolve APIs when old mobile apps never update? `[Senior]`
- Mobile clients stay in use for **years**; you can't break them.
- Rules:
  - **Additive changes only** within a version: new optional fields, new endpoints.
  - Clients **ignore unknown fields** and handle unknown enum values (`case unknown`).
  - Never remove or rename a field, change its type, or change its meaning.
  - Breaking change → new version (`/v2/...` or header `API-Version: 2026-11-01`, Stripe-style date versions).
- Track usage by app version (`User-Agent: MyApp/5.2.1 iOS/26.0`) before deprecating anything.
- Keep a **minimum supported version** and a force-update path for security issues.

```swift
// Client side: survive new enum values the server adds later
enum OrderStatus: Decodable {
    case pending, shipped, delivered, unknown(String)
    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)
        switch raw {
        case "pending": self = .pending
        case "shipped": self = .shipped
        case "delivered": self = .delivered
        default: self = .unknown(raw)
        }
    }
}
```

### Q93. How should the backend implement pagination? `[Senior]`
```sql
-- ❌ Offset: the DB still reads and discards 100,000 rows; inserts shift pages (duplicates/skips)
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

-- ✅ Keyset (cursor): seek directly using the index; stable under inserts
SELECT * FROM posts
WHERE (created_at, id) < ($1, $2)          -- the last item of the previous page; id breaks ties
ORDER BY created_at DESC, id DESC
LIMIT 21;                                  -- fetch one extra to know if there's a next page
```
- Encode `(created_at, id)` into an **opaque cursor** (base64 JSON) so clients don't build or depend on it.
- Response: `{ "items": [...], "next_cursor": "eyJ0IjoiMjAyNi0xMS0wMlQxMDowMDowMFoiLCJpZCI6NDJ9" }`, or `null` at the end.
- Offset is acceptable for small, admin-style lists with page numbers.

### Q94. Sessions or JWTs for authentication? `[Senior]`
| | Server sessions (opaque token) | JWT (self-contained, signed) |
|---|---|---|
| Validation | Look up token in Redis/DB | Verify signature locally, no lookup |
| Revocation | Delete the session: instant | Hard until expiry (needs a denylist) |
| Size | Small | Larger (claims in every request) |
| Scaling | Shared session store (Q8) | Stateless across services |

**Common mobile setup:**
- **Short-lived access token** (JWT, 5–15 min) sent on every request; services verify locally.
- **Long-lived refresh token** (opaque, stored server-side, **rotated** on every use, stored in the Keychain on device) to get new access tokens.
- Revocation (logout, stolen device): delete the refresh token; access tokens expire soon. Detect refresh-token **reuse** (an old rotated token used again) → revoke the whole session family.
- Sign JWTs with asymmetric keys (RS256/ES256) so services verify with a public key; validate `exp`, `aud`, `iss`; never accept `alg: none`.

### Q95. How do you design an API for long-running operations? `[Senior]`
Don't hold an HTTP request open for minutes (load balancers and mobile networks will cut it).

```http
POST /v1/exports            → 202 Accepted
Location: /v1/exports/exp_123
{ "id": "exp_123", "status": "queued" }

GET /v1/exports/exp_123     → 200 { "status": "running", "progress": 0.4 }
GET /v1/exports/exp_123     → 200 { "status": "succeeded", "download_url": "https://cdn…/exp_123.zip?sig=…" }
```
- Notify completion with a **push notification** (mobile) or a **webhook** (server clients) instead of tight polling.
- Make the `POST` idempotent (Section 7) so a retried request doesn't start two exports.

### Q96. How do you scale WebSockets / real-time delivery on the backend? `[Lead/Expert]`
- Each connection is long-lived state on one server; a server holds ~50k–500k+ connections depending on tuning.
- Architecture:

```
Mobile ──WSS──▶ LB (L4 or L7 with WebSocket support, long idle timeouts)
                 │
        ┌────────┼────────┐
     Gateway 1  Gateway 2  Gateway 3     (only manage connections; no business logic)
        │          │          │
        └──── Pub/Sub (Redis / Kafka / NATS) ────┘
                        ▲
                 Chat/Notification services publish "deliver to user 42"

Presence registry (Redis): user 42 → gateway 2, connection c-91 (TTL refreshed by heartbeats)
```
- Route messages to the right gateway via a **connection registry** or by publishing to a per-user channel that the owning gateway subscribes to.
- Heartbeats (ping/pong every ~30 s) detect dead connections; clean up the registry on disconnect and on TTL expiry.
- **Deploys** drain gateways gradually; clients reconnect with jitter (Q89) and **resume from the last event ID** (no lost messages).
- If the user is offline, fall back to **push notifications** and store messages for sync.
- Simpler alternatives: **SSE** for server-to-client only streams; **long polling** as a fallback.

### Q97. Monolith or microservices? `[Lead/Expert]`
| | Modular monolith | Microservices |
|---|---|---|
| Deploy | One unit | Many independent units |
| Calls | In-process function calls | Network calls (latency, failures, retries) |
| Data | One DB (modules own their tables) | Database per service |
| Team scaling | Fine to ~dozens of engineers | Needed when many teams must ship independently |
| Ops cost | Low | High: service discovery, tracing, CI/CD per service, distributed transactions |

**Lead answer:** "Start with a well-modularized monolith with clear boundaries. Extract a service when there's a concrete reason: a different scaling profile (video transcoding), a different reliability need (payments), or a team that's blocked by shared deploys." Same thinking as app modularization: boundaries first, separate deployment only when it pays off.

### Q98. How do services find and call each other? `[Senior]`
- **Service discovery**: services register their addresses; callers look them up. Kubernetes Services + DNS (`http://orders.default.svc.cluster.local`), Consul, or a service mesh.
- **Sync calls** (REST/gRPC): simple, but couple availability (if B is down, A's request fails); need timeouts, retries, circuit breakers.
- **Async events** (queues): decoupled availability; eventual consistency.
- **Service mesh** (Istio, Linkerd): sidecar proxies give mTLS, retries, timeouts, circuit breaking and metrics without changing app code.
- Rule of thumb: synchronous for reads the user waits on; asynchronous for side effects ("after an order is placed, also…").

### Q99. What are the three pillars of observability? `[Fundamental]`
| Pillar | Answers | Example |
|---|---|---|
| **Metrics** | "Is something wrong? How much?" (aggregated numbers) | Request rate, error rate, p99 latency, queue depth |
| **Logs** | "What exactly happened in this case?" | Structured JSON event with request ID, user ID, error |
| **Traces** | "Where did the time go across services?" | One request's spans across API → feed → DB → cache |

### Q100. How does distributed tracing work? `[Senior]`
- The edge creates a **trace ID**; each service creates **spans** (operation, start, duration, parent span) and passes the context on in headers.
- Standard: **W3C Trace Context** (`traceparent: 00-<32 hex trace id>-<16 hex parent span id>-01`), implemented by **OpenTelemetry**.
- Propagate through queues too: put the trace context in message headers so a consumer's work links back to the request.
- **Mobile tie-in:** the app can start the trace and send `traceparent` (Mobile System Design Q90), so a slow screen load can be followed end to end.

```swift
/// Middleware: continue an incoming trace or start a new one; echo the ID for support tickets
struct TracingMiddleware {
    func handle(_ request: Request, next: (Request) async throws -> Response) async throws -> Response {
        let incoming = request.headers["traceparent"].flatMap(TraceParent.init(header:))
        let traceID = incoming?.traceID ?? TraceParent.randomHex(bytes: 16)
        let spanID = TraceParent.randomHex(bytes: 8)              // new span, independent of the trace ID

        var request = request
        request.context.trace = .init(traceID: traceID, spanID: spanID, parentSpanID: incoming?.spanID)

        let start = ContinuousClock.now
        var response = try await next(request)
        response.headers["X-Request-ID"] = traceID
        metrics.recordDuration(route: request.route, status: response.status, ContinuousClock.now - start)
        return response
    }
}
```

### Q101. What should you alert on? `[Senior]`
- Alert on **symptoms users feel**: error rate, latency SLO burn, queue age (Q52), not on causes like "CPU at 80%" (that's a dashboard item).
- **SLO burn-rate alerts**: page when the error budget is burning fast (e.g. 14× normal over 1 h), ticket when it's burning slowly.
- Every page must be **actionable** with a **runbook** link; noisy alerts get ignored, and then real ones do too.
- Dashboards per service: RED metrics, dependencies, saturation, deploy markers.

### Q102. What backend security basics should you mention in a design? `[Senior]`
- **TLS everywhere**, including internal traffic (mTLS in a mesh); HSTS at the edge.
- **AuthN/AuthZ on every request**: verify the token, then check the user may access **this** resource (object-level authorization is the #1 API vulnerability in the OWASP API Top 10: `GET /orders/123` must check that order 123 is the caller's).
- **Input validation** and parameterized queries (no SQL injection); limit body sizes and page sizes.
- **Secrets** in a secrets manager (AWS Secrets Manager, Vault), never in code or the app binary; rotate them.
- **Encryption at rest** (managed DB/storage encryption, KMS keys); field-level encryption for very sensitive data.
- **Least privilege** IAM roles per service; separate production access with audit logs.
- **Rate limiting and abuse protection** (Q83–Q86); **App Attest / Play Integrity** to check requests come from your genuine app.
- **PII minimization**: don't log tokens, passwords, card numbers; set data retention and deletion paths (GDPR "delete my account").

### Q103. Design a URL shortener (like bit.ly). `[Senior]`
**Requirements**
- Functional: create short link for a long URL (optional custom alias, expiry); redirect short → long; basic click counts.
- Non-functional: redirects very fast (p99 < 50 ms) and highly available; read-heavy; links never collide.

**Estimates**
- 100M new links/month ≈ 40 writes/s; 100:1 read ratio ≈ 4,000 redirects/s average, ~20k/s peak.
- 5 years × 1.2B links/year = 6B links × ~500 bytes ≈ 3 TB.
- Key length: base62, 7 characters = 62⁷ ≈ 3.5 trillion combinations. Plenty.

**API**
```http
POST /v1/links   { "url": "https://example.com/very/long", "alias": null, "expires_at": null }
→ 201 { "code": "aZ3kP9q", "short_url": "https://sho.rt/aZ3kP9q" }

GET /aZ3kP9q     → 301 (permanent, browsers cache it; fewer hits but no click stats)
                 or 302 (temporary, every click reaches us; needed for analytics)
```

**Data model**
```sql
CREATE TABLE links (
    code        VARCHAR(10) PRIMARY KEY,
    long_url    TEXT NOT NULL,
    owner_id    TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ
);
```
A key-value store (DynamoDB) fits equally well: the only access pattern is lookup by code.

**High-level design**
```
Create:   App ──▶ API ──▶ ID generator ──▶ base62 encode ──▶ DB
Redirect: Browser ──▶ CDN/edge ──▶ Redirect service ──▶ Redis (hot codes) ──miss──▶ DB
                                          │
                                          └──▶ click event ──▶ Kafka ──▶ analytics aggregator
```

**Deep dive: generating codes**
| Approach | How | Trade-off |
|---|---|---|
| Hash the URL (MD5 → first 7 chars) | Deterministic | Collisions must be checked and resolved; same URL from two users gets the same code |
| Counter + base62 | Unique number → encode | Needs a distributed counter; sequential codes are guessable |
| **Pre-allocated ranges** | Each server takes a block of 1M IDs from a coordinator (DB/ZooKeeper) | No per-request coordination; a crash wastes part of a block (fine) |
| Random 7 chars + insert with unique constraint | Retry on conflict | Simple; conflicts are rare at this key space |

```swift
enum Base62 {
    static let alphabet = Array("0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ")

    static func encode(_ value: UInt64) -> String {
        guard value > 0 else { return "0" }
        var n = value, chars: [Character] = []
        while n > 0 { chars.append(alphabet[Int(n % 62)]); n /= 62 }
        return String(chars.reversed())
    }
}

/// Each server leases a block of IDs, so creating a link needs no network call for the ID
actor IDRangeAllocator {
    private var next: UInt64 = 0, end: UInt64 = 0
    private let coordinator: RangeCoordinator         // e.g. UPDATE counters SET value = value + 1000000 RETURNING value

    init(coordinator: RangeCoordinator) { self.coordinator = coordinator }

    func nextID() async throws -> UInt64 {
        if next >= end {
            let block = try await coordinator.leaseBlock(size: 1_000_000)
            next = block.lowerBound; end = block.upperBound
        }
        defer { next += 1 }
        return next
    }
}
```
Note: the `await` inside the actor allows re-entrancy; two callers could both lease a block when the range runs out. That only wastes IDs (still unique), which is acceptable here; a stricter version stores the in-flight lease `Task` and lets later callers await it.

**Other deep dives**
- **Caching**: redirects are extremely cacheable; ~20% of links get ~80% of traffic. Redis cache-aside with LRU; negative caching for unknown codes (Q38).
- **Analytics**: never write to the DB on the redirect path; emit an event and aggregate asynchronously.
- **Abuse**: malicious URL scanning (Safe Browsing), rate limiting on creation, unguessable codes for private links.
- **Expiry**: check `expires_at` on read; a background job deletes expired links.

### Q104. Design a distributed rate limiter. `[Senior]`
**Requirements**
- Limit requests per user/API key/IP with configurable rules per endpoint ("100 req/min per user on `/search`, 5 OTP per phone per hour").
- Low latency (< 1–2 ms added), accurate enough across all API servers, highly available.
- Return `429` with `Retry-After` and rate-limit headers.

**High-level design**
```
Client ──▶ API Gateway / middleware ──▶ Rate limiter ──▶ Redis cluster (counters, sharded by key)
                                             │
                                       Rules cache (loaded from config service, refreshed every 30 s)
         allowed → forward to service
         limited → 429 + headers (and log/metric for abuse detection)
```

**Deep dives**
- **Algorithm**: token bucket for bursty-but-bounded traffic (Q85), sliding window counter for simple per-minute quotas (Q84).
- **Atomicity**: Lua script per check (Q86); keys `rl:{rule}:{subject}` with TTLs so idle keys disappear.
- **Sharding**: Redis Cluster shards by key; a single hot key (one abusive IP) stays on one shard, so block it earlier at the WAF.
- **Failure mode**: Redis unavailable → fail open for normal endpoints, fail closed for login/OTP; circuit breaker around Redis so the limiter itself doesn't add timeouts.
- **Multi-region**: limits per region (simple, slightly generous) or asynchronous global sync (approximate).
- **Client behavior**: mobile SDKs must honor `Retry-After` and back off with jitter; otherwise 429s turn into a retry storm.

### Q105. Design the backend for a news feed (like Instagram/Twitter home timeline). `[Lead/Expert]`
**Requirements**
- Post (text + media), follow users, see a home feed of followed users' posts (newest or ranked), paginated, fast (p99 < 300 ms).
- 200M DAU, average 200 follows, a few celebrities with 100M followers.

**Estimates**
- Feed reads: 200M × 10 opens/day ≈ 23k/s average, ~70k/s peak.
- Posts: 200M × 0.2/day ≈ 460 posts/s, but fan-out multiplies writes by follower count.

**Data model**
```
users(id, name, ...)
follows(follower_id, followee_id, created_at)          -- index both directions
posts(id (Snowflake, time-ordered), author_id, text, media_keys, created_at)
feed cache (Redis): feed:<userID> → sorted set of post IDs (score = time), capped at ~800
```

**The core decision: fan-out on write vs fan-out on read**
| | Fan-out on write (push) | Fan-out on read (pull) |
|---|---|---|
| How | When X posts, insert the post ID into each follower's feed cache | When I open the app, fetch recent posts from everyone I follow and merge |
| Read cost | O(1): read my precomputed list | O(follows): many queries + merge |
| Write cost | O(followers): 100M writes for a celebrity post | O(1) |
| Wasted work | Feeds of inactive users are updated anyway | None |

**Hybrid (what real systems do):** push for normal users; for celebrities (followers > threshold), **don't fan out**: at read time, merge my precomputed feed with recent posts from the celebrities I follow.

```
Post created ──▶ posts DB ──▶ event "PostCreated" ──▶ Fan-out workers
                                                        │ author is normal: for each follower → ZADD feed:<follower>
                                                        │ author is celebrity: skip
Read feed ──▶ Feed service: ZREVRANGE feed:<me> + recent posts of my celebrity follows
          ──▶ merge, rank, hydrate (post bodies, authors, like counts from caches) ──▶ response with cursor
```

**Deep dives**
- **Hydration**: feed caches store IDs only; bodies come from a post cache (multi-get), so edits/deletes apply everywhere.
- **Ranking**: candidate generation (followed + recommended) → ML scoring service → re-ranking for diversity. Ranked feeds paginate with a **session snapshot** (store the ranked list for this session) so pages don't shuffle.
- **Inactive users**: skip fan-out for users not active in 30 days; rebuild their feed on next login.
- **Deletes and blocks**: filter at read time (cheap), clean caches asynchronously.
- **Media**: object storage + CDN; feed returns several sizes or a URL template (Q41).
- **Mobile tie-in:** cursor-based pagination, prefetch of the next page, "new posts" pill instead of reshuffling what the user is reading, and image size hints from the client.

### Q106. Design the backend for a chat application (like WhatsApp/Messenger). `[Lead/Expert]`
**Requirements**
- 1:1 and group chats (up to 500 members), text + media, delivered/read receipts, online presence, push when offline, history sync across devices.
- Low latency (< 200 ms delivery when online), **no lost or duplicated messages**, per-conversation ordering.
- 100M DAU, 50 messages/user/day ≈ 5B/day ≈ 58k msgs/s average.

**High-level design**
```
Mobile ──WSS──▶ Gateways (connections, auth, heartbeats) ──▶ Chat service
                    ▲                                          │ 1. assign seq per conversation
                    │                                          │ 2. persist message (Cassandra/ScyllaDB)
                    │                                          │ 3. publish to recipients
                    │                    Connection registry ◀─┤
                    └────── deliver to online recipients ◀─────┤
                                                               └──▶ offline recipients → Push service → APNs/FCM
Media: presigned upload to object storage; message carries the media key.
```

**Data model (wide-column, partitioned by conversation)**
```
messages
  partition key: conversation_id
  clustering key: seq (DESC)                  -- server-assigned, monotonic per conversation
  columns: message_id (client UUID), sender_id, body/encrypted payload, media_key, created_at

user_conversations (partition: user_id) → conversation_id, last_read_seq, muted, ...
```

**Deep dives**
- **Ordering**: a per-conversation sequence number assigned by the server (one owner per conversation, or a counter in Redis/DB). Clients order by `seq`, never by device time (Q75).
- **Exactly-once for the user**: the client generates `message_id` (UUID); the server dedupes on it (Section 7); retries after a reconnect are safe. The client ACKs by `seq`; the server redelivers anything unacked.
- **Sync / missed messages**: each device keeps `last_seq` per conversation; on reconnect: "give me everything after seq N" (delta sync).
- **Groups**: fan-out on write to each member's inbox for small groups; for large groups, members read from the conversation partition.
- **Receipts and typing**: ephemeral events go through the real-time path only, not persisted per keystroke; read receipts update `last_read_seq` (one write, not per message).
- **Presence**: heartbeat-based with TTL in Redis; publish changes only to users who are currently viewing (presence fan-out is expensive).
- **End-to-end encryption** (Signal protocol): the server stores and routes ciphertext; it can't read, search or moderate content; multi-device needs per-device keys.
- **Mobile tie-in:** local DB as the UI's source of truth, outbox for unsent messages, reconnect with jitter, Notification Service Extension to decrypt push content.

### Q107. Design a notification service. `[Senior]`
**Requirements**
- Internal services request "notify user X about Y"; deliver via push (APNs/FCM), email, SMS, in-app.
- Respect user preferences, quiet hours, rate limits ("max 3 marketing pushes/day"); templates and localization; track delivery and opens.
- Millions per minute during campaigns; transactional notifications (OTP, payment) must not wait behind marketing.

**High-level design**
```
Services ──▶ Notification API (validate, idempotency key) ──▶ Queue (priority: transactional / social / marketing)
                                                                     │
                                                              Router/workers:
                                                              - load preferences + quiet hours (cache)

                     │

```

**Deep dives**

### Q108. Design a payment system. `[Lead/Expert]`
**Requirements**
- Users pay for orders with cards (via a payment service provider such as Stripe/Adyen); refunds; history; payouts to sellers.
- **Correctness above all**: never double charge, never lose a payment, full audit trail; reconcile with the provider daily.
- Moderate throughput (a few thousand TPS at peak); availability matters but consistency matters more (CP choices).

**High-level design**
```
App ──(Idempotency-Key)──▶ Payment API ──▶ Payment service ──▶ PSP (Stripe/Adyen)
                                │                  │                  │
                                │           payments table      webhooks (async results:
                                │           (state machine)       3-D Secure, settlement)
                                │                  │                  │
                                │             Ledger service ◀────────┘
                                │          (double-entry, append-only)
                                └──▶ Outbox ──▶ Kafka ──▶ Order service, notifications, payouts
Nightly: Reconciliation job compares ledger ↔ PSP settlement reports → alerts on mismatch
```

**Payment state machine**
```
created ──▶ requires_action (3-D Secure) ──▶ processing ──▶ succeeded ──▶ (partially_)refunded
   │                                              │
   └────────────────────────────────────────────▶ failed
```
Transitions are conditional updates (`WHERE status = 'processing'`), so a late or duplicate webhook can't move a payment backwards.

**Double-entry ledger**
```sql
-- Every movement is two (or more) entries that sum to zero. Never UPDATE or DELETE entries.
CREATE TABLE ledger_entries (
    id              BIGSERIAL PRIMARY KEY,
    transaction_id  UUID NOT NULL,           -- groups the entries of one movement
    account_id      TEXT NOT NULL,           -- 'user:42:card', 'merchant:7:pending', 'platform:fees'
    amount_minor    BIGINT NOT NULL,         -- integer minor units (cents); never floating point
    currency        CHAR(3) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (transaction_id, account_id)      -- replaying the same transaction can't double-post
);
-- $49.99 payment with a $1.50 fee:
--   user:42:card          -4999
--   merchant:7:pending    +4849
--   platform:fees          +150
```

**Deep dives**
- **Idempotency end to end**: client key → payment API (Q63) → PSP idempotency key → webhook dedupe by event ID (Q66).
- **Unknown outcomes** (PSP timeout): never assume failure; mark `processing`, query the PSP or wait for the webhook; a reconciler resolves stuck payments.
- **Money types**: integers in minor units with currency; `Decimal` for calculations in Swift, never `Double`.
- **Security/compliance**: card data never touches your servers (PSP SDK tokenizes on device: Apple Pay, Stripe iOS SDK) → minimal PCI scope.
- **Mobile tie-in:** idempotency key persisted with the pending payment, disable the pay button while in flight, show "processing" honestly, and refresh status from the server rather than trusting the client's view.

### Q109. Design a video upload and streaming pipeline (like YouTube). `[Lead/Expert]`
**Requirements**
- Upload large videos (up to several GB) from mobile on flaky networks; process into multiple resolutions; stream with adaptive bitrate globally; thumbnails; view counts.
- 500 hours of video uploaded per minute (YouTube scale) or, for a typical interview, 1M uploads/day.

**High-level design**
```
Upload:
App ──▶ API: create upload session ──▶ presigned multipart URLs (S3 multipart, 5–100 MB parts)
App ──▶ Object storage (raw) ── resumable, parts retried individually ──▶ complete upload
                       │ event
                       ▼
             Processing orchestrator (workflow: Step Functions/Temporal)
               ├─ validate + malware/content scan
               ├─ split into segments ──▶ parallel transcode workers (GPU) ──▶ 240p…4K renditions
               ├─ package as HLS (.m3u8 + .m4s / fMP4 segments, 2–6 s each)
               └─ thumbnails, captions (speech-to-text)
                       ▼
             Object storage (processed) ──▶ CDN ──▶ AVPlayer (adaptive bitrate)

Metadata DB: videos(id, owner, status, renditions, duration, ...)
Views: player events ──▶ Kafka ──▶ stream aggregation ──▶ counters (approximate in real time, exact in batch)
```

**Deep dives**
- **Resumable uploads**: client stores upload ID + completed part ETags; resumes after app termination; background `URLSession` upload tasks for large files (Mobile System Design Q67).
- **Parallel transcoding**: split by GOP/segments so a 2-hour video transcodes in minutes across many workers; each segment task is idempotent (deterministic output keys).
- **Adaptive bitrate (HLS)**: a master playlist lists renditions; the player switches based on measured bandwidth; segments are cached at the CDN edge.
- **Cost**: storage tiers (move rarely watched renditions to cold storage, or re-transcode on demand), CDN egress dominates cost.
- **View counts**: dedupe per user/session window, aggregate in streams; never `UPDATE views = views + 1` per view on a hot row.
- **Mobile tie-in:** compress/transcode on device before upload when appropriate (smaller upload, faster), show processing state, and use push when the video is ready.

## 12. "Spot the Problem" Questions

### Q110. What's wrong with this "check then create" for idempotency? `[Senior]`
```swift
func createOrder(_ req: CreateOrder, key: String) async throws -> Order {
    if let existing = try await db.order(idempotencyKey: key) {
        return existing
    }
    return try await db.insertOrder(req, idempotencyKey: key)
}
```
**Problems:**
1. **Race condition**: two concurrent requests with the same key both find nothing and both insert → two orders.
2. No check that the retried request matches the original (same key, different cart).

**Fix:** a `UNIQUE` constraint on `(user_id, idempotency_key)` and an atomic claim (`INSERT … ON CONFLICT DO NOTHING`), then return the stored result on conflict (Q63, Q64). Validate a request hash.

### Q111. What's wrong with this cache update? `[Senior]`
```swift
func updatePrice(productID: String, price: Decimal) async throws {
    try await cache.set("product:\(productID)", price)       // 1
    try await db.updatePrice(productID, price)                // 2
}
```
**Problems:**
1. If step 2 fails, the cache holds a price that was never saved.
2. Two concurrent updates can interleave (A sets cache, B sets cache, B writes DB, A writes DB) → cache and DB disagree **permanently** (no TTL).
3. Cache errors fail the whole update even though the cache is optional.

**Fix:** write the DB first, then **delete** the key (cache-aside); set a TTL on all entries; treat cache errors as non-fatal; for strict needs use CDC-driven invalidation (Q35, Q39).

### Q112. What's wrong with this event publishing? `[Lead/Expert]`
```swift
func placeOrder(_ input: PlaceOrder) async throws -> Order {
    let order = try await db.transaction { tx in
        let order = try await tx.insertOrder(input)
        try await kafka.publish("OrderPlaced", order)        // inside the transaction
        return order
    }
    return order
}
```
**Problems:**
1. **Dual write**: if the transaction rolls back (or the commit fails) after publishing, consumers process an order that doesn't exist.
2. Publishing after commit instead would lose the event if the process crashes in between.
3. A slow broker holds the DB transaction (and its locks) open.

**Fix:** transactional outbox (Q53): insert an outbox row in the same transaction; a relay publishes it; consumers are idempotent.

### Q113. What's wrong with this consumer? `[Senior]`
```swift
for try await message in queue.messages() {
    try await queue.ack(message)
    let event = try JSONDecoder().decode(PaymentCaptured.self, from: message.body)
    try await wallets.credit(event.userID, amount: event.amount)
}
```
**Problems:**
1. **Ack before processing** = at-most-once: a crash after the ack loses the credit.
2. One undecodable message throws out of the loop and **stops the consumer entirely** (poison message).
3. `credit` isn't idempotent; moving the ack after processing would cause double credits on redelivery.

**Fix:** decode and process, then ack; catch errors per message with retry/DLQ policy (Q51); dedupe with a processed-messages table in the same transaction as the credit (Q54).

### Q114. What's wrong with this rate limiter? `[Senior]`
```swift
func isAllowed(userID: String) async throws -> Bool {
    let key = "rl:\(userID)"
    let count = try await redis.get(key).flatMap(Int.init) ?? 0
    guard count < 100 else { return false }
    try await redis.set(key, String(count + 1))
    return true
}
```
**Problems:**
1. **Race**: get-then-set across many servers lets bursts through (everyone reads 99, everyone writes 100).
2. **No expiry and no window**: after 100 requests the user is blocked forever.
3. No `Retry-After` information for the client; no decision for Redis failures.

**Fix:** atomic `INCR` + `EXPIRE` for a fixed window, or a Lua script for sliding window/token bucket (Q86); return remaining quota and reset time; fail open/closed deliberately.

### Q115. What's wrong with this retry logic? `[Senior]`
```swift
func fetchProfile(_ id: String) async throws -> Profile {
    for _ in 0..<10 {
        if let profile = try? await profileService.get(id) { return profile }
        try await Task.sleep(for: .milliseconds(100))
    }
    throw ServiceUnavailable()
}
```
**Problems:**
1. **No backoff or jitter**: all instances retry every 100 ms in lockstep, hammering a struggling service.
2. **Retries every error**, including 404 and 401, which will never succeed.
3. **10 attempts** at this layer, multiplied by retries in callers → retry storm (Q79).
4. No overall deadline; the caller may have given up seconds ago.

**Fix:** `withRetry` with capped exponential backoff + full jitter, retryable-error classification, 3–4 attempts, deadline propagation, and a circuit breaker (Q78–Q80).

### Q116. What's wrong with this pagination endpoint? `[Senior]`
```sql
-- GET /v1/feed?page=500
SELECT * FROM posts WHERE author_id IN (...) ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
```
**Problems:**
1. `OFFSET 10000` reads and discards 10,000 rows on each request; gets slower the deeper you go.
2. New posts shift every page → the client sees duplicates or skips items.
3. `ORDER BY created_at` alone isn't a total order (ties) → unstable pages.
4. `SELECT *` sends columns nobody needs.

**Fix:** keyset pagination on `(created_at, id)` with an opaque cursor and a matching index (Q93).

### Q117. What's wrong with this distributed lock usage? `[Lead/Expert]`
```swift
func runNightlyBilling() async throws {
    let acquired = try await redis.setNX("lock:billing", "1")
    guard acquired else { return }
    try await chargeAllSubscriptions()          // takes ~20 minutes
    try await redis.del("lock:billing")
}
```
**Problems:**
1. **No expiry**: if the process crashes, the lock is held forever; billing never runs again.
2. Adding a short expiry without renewal means a 20-minute job outlives the lock → a second instance starts billing too.
3. `del` doesn't check ownership: it can delete another holder's lock.
4. Correctness depends on the lock; a GC pause or network partition can still produce two holders.

**Fix:** a lock with TTL + a random owner token + renewal (watchdog) + compare-and-delete release; more importantly, make the **work itself idempotent** (charge per subscription per billing period with a unique constraint: `UNIQUE(subscription_id, period)`), so a double run can't double charge. Use fencing tokens if a lock guards a resource (Q73).

### Q118. What's wrong with storing sessions like this? `[Fundamental]`
```swift
final class SessionManager {
    static var sessions: [String: UserSession] = [:]      // token → session, in server memory
}
```
**Problems:**
1. **Not shared**: behind a load balancer, the next request may hit another instance → random logouts (or sticky sessions become mandatory, Q17).
2. **Lost on every deploy/restart/scale-in**.
3. **Data race**: a mutable static dictionary accessed from concurrent requests (Swift 6 rejects it: global mutable state isn't concurrency-safe).
4. Grows without bound; no expiry.

**Fix:** a shared session store (Redis with TTL) or stateless signed tokens (JWT access + rotating refresh), keeping app servers stateless (Q8, Q94).

### Q119. What's wrong with this "like" endpoint? `[Senior]`
```http
POST /v1/posts/42/like
```
```sql
UPDATE posts SET like_count = like_count + 1 WHERE id = 42;
```
**Problems:**
1. **Not idempotent**: a retried request (or double tap) adds two likes.
2. No record of **who** liked → can't unlike, can't show "liked by you", can't prevent duplicates.
3. A viral post makes `posts.id = 42` a **hot row**: thousands of concurrent updates contend for one row lock.

**Fix:** `PUT /v1/posts/42/like` with `INSERT INTO likes (user_id, post_id) … ON CONFLICT DO NOTHING`; increment the counter only if a row was inserted; for hot posts, buffer counts in Redis (`INCR`) or sharded counters and flush periodically; show approximate counts (Q29, Q65).

## 13. Senior / Lead Scenario Questions

### Q120. Your API's p99 latency jumped from 200 ms to 2 s after a release. What do you do? `[Senior]`
1. **Mitigate first**: is it correlated with the deploy? Roll back or turn off the feature flag. Restore service, then investigate.
2. **Scope**: all endpoints or one? All regions? One app version? (Dashboards by route, region, client version.)
3. **Traces** for slow requests: which span grew? DB query, cache miss, a new downstream call?
4. **Common causes**: a new N+1 query, a missing index on a new query, a cache key change (hit rate dropped to 0), a synchronous call added to the hot path, connection pool exhaustion.
5. **Prevent**: canary with automated latency checks, query plans reviewed for new queries, load tests on key paths, SLO burn alerts.

### Q121. The database is at 90% CPU and traffic doubles next month. What's your plan? `[Lead/Expert]`
In order of cost and risk:
1. **Find the expensive queries** (`pg_stat_statements`): often 3 queries cause most load. Add indexes, fix N+1s, remove `SELECT *`.
2. **Cache** hot, read-heavy data (Redis cache-aside); add **read replicas** and move read-only traffic there (with read-your-writes handling, Q25).
3. **Connection pooling** (PgBouncer) if connection count is part of the problem.
4. **Vertical scaling**: a bigger instance buys time quickly.
5. **Move work off the request path**: queues for non-urgent writes, batch writes, precomputed aggregates.
6. **Archive** old data; partition big tables by time.
7. **Shard** only if writes still don't fit, with a clear shard key (Q26).
Communicate the timeline and risk; run a load test at 2× before the date.

### Q122. Users report being charged twice. How do you investigate and fix it? `[Lead/Expert]`
1. **Stop the bleeding**: identify affected payments (ledger vs PSP reconciliation), refund duplicates proactively, tell support.
2. **Trace** a few cases: same idempotency key twice? Different keys for one tap? Webhook processed twice?
3. **Typical root causes**:
   - Client generates a **new key per attempt** (or doesn't persist it across app relaunch) → Q67.
   - Server checks-then-inserts instead of an atomic claim → Q110.
   - Server doesn't pass its key to the PSP, so a server-side retry charges again.
   - Webhook handler not idempotent → Q66.
4. **Fix** at each layer, add a unique constraint as a final safety net (`UNIQUE(order_id)` on successful charges), and add a reconciliation alert for "two successful charges for one order".
5. **Blameless postmortem** with timeline, root cause, and action items.

### Q123. A downstream dependency (e.g. recommendations) is flaky and is taking your whole API down. What do you change? `[Senior]`
- **Timeouts** tight enough that a slow dependency can't hold threads (Q78).
- **Circuit breaker** with a fallback (popular items, cached results) (Q80).
- **Bulkhead**: cap concurrent calls to that dependency (Q81).
- **Make it optional**: the response is still useful without recommendations (Q82); the app renders the section only if present.
- **Move it off the critical path**: precompute recommendations asynchronously and serve from cache.
- Talk to the owning team about their SLO; agree on what "degraded" looks like.

### Q124. Product wants a "Black Friday" sale with 50× normal traffic for one hour. How do you prepare? `[Lead/Expert]`
- **Estimate** peak RPS per endpoint, and identify the critical path (browse → cart → checkout → payment).
- **Load test** at 1.5× the expected peak in a production-like environment; find the first bottleneck, fix, repeat.
- **Pre-scale** (autoscaling is too slow for a cliff-edge spike); warm caches; raise DB/PSP/third-party quotas in advance.
- **Protect the core**: rate limits, a **virtual waiting room / queue** for checkout, load-shed non-critical features (recommendations, analytics), static pages served from the CDN.
- **Inventory correctness**: atomic decrements (`UPDATE … WHERE stock > 0`), reservation with expiry, no overselling.
- **Mobile**: feature flags to disable heavy features, remote config to tune polling, staggered push campaigns (don't send 10M pushes at 00:00:00).
- **Operations**: code freeze, war room, runbooks, dashboards, rollback plans.

### Q125. How do you migrate a large table to a new schema with zero downtime? `[Lead/Expert]`
Example: split `users.address` (text) into a structured `addresses` table, with 200M users and old app versions still in use.
1. **Expand**: create `addresses`; deploy code that writes both old and new (dual write).
2. **Backfill** in batches (10k rows, throttled, resumable via a checkpoint), off-peak.
3. **Verify**: a job compares old vs new for a sample/all rows; fix drift.
4. **Switch reads** to the new table behind a flag, gradually (1% → 100%).
5. **Stop writing** the old column once nothing reads it, including **old app versions via the API layer** (the API maps new storage to the old response shape).
6. **Contract**: drop the column weeks/months later.
Same pattern for moving to a new database: dual write (or CDC) → backfill → shadow reads → cut over → decommission.

### Q126. Your team wants to split the monolith into microservices. How do you lead that decision? `[Lead/Expert]`
- Ask **what problem we're solving**: deploy contention? scaling one hot component? reliability isolation? If none is concrete, invest in modularizing the monolith instead.
- If yes: identify **bounded contexts** with clear data ownership; start with one service that has a clear boundary and real benefit (e.g. notifications, media processing).
- **Strangler fig**: route one capability at a time to the new service behind the same API; keep the old path until the new one is proven.
- Put the platform basics in place first: CI/CD per service, tracing, centralized logging, service templates, on-call ownership.
- Set expectations: microservices trade code complexity for operational complexity; latency and consistency get harder.

### Q127. How would you explain eventual consistency to a product manager? `[Senior]`
"When someone posts, it's saved immediately, but it can take a second or two to show up for their followers, the way a bank transfer shows 'pending' before it appears in the other account. In return, the app stays fast and keeps working even when part of the system is having trouble. For the person's own actions we make it look instant, and for money we always wait for the confirmed answer."
- Pair it with concrete product decisions: which screens can show slightly old data, which must be exact, and what the UI shows while things are pending.

### Building blocks in one line each
| Block | Remember |
|---|---|
| Load balancer | L4 = fast TCP; L7 = HTTP routing, TLS, retries; least connections for uneven work; health checks (liveness ≠ readiness) |
| Stateless services | State in DB/Redis/object storage → any instance can serve any request → horizontal scaling |
| Replication | Leader–follower for reads + failover; async lag → read-your-writes fixes |
| Sharding | Last resort for writes; shard key = even spread + locality; consistent hashing moves ~1/N keys |
| Cache | Cache-aside, delete on write, TTL + jitter; stampede → single flight/lock; penetration → negative cache/Bloom filter |
| CDN | Static and public content, versioned URLs, few image sizes |
| Queue | Decouple, buffer, retry; at-least-once + idempotent consumer; DLQ monitored |
| Kafka | Partition key = ordering per entity; consumers ≤ partitions; replay via offsets |
| Outbox | DB change + event row in one transaction; relay publishes |
| Idempotency key | Client UUID per intent, persisted; server atomic claim (unique key), store response, 409 in progress, 422 mismatch |
| CAP | During a partition choose C or A; money = CP, feeds = AP |
| Saga | Local transactions + compensations; every step idempotent |
| Rate limiting | Token bucket (burst + rate); Redis + Lua for many servers; 429 + Retry-After; fail open vs closed |
| Resilience | Timeouts everywhere, retries with backoff + jitter at one layer, circuit breaker, bulkhead, degrade gracefully |
| Observability | Metrics (RED/USE, percentiles), structured logs, traces (W3C traceparent); alert on symptoms/SLO burn |
