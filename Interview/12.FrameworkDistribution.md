## 1. Libraries, Frameworks & Modules

### Q1. What is the difference between a library, a framework, an SDK and a package? `[Fundamental]`
| Term | What it is | Example |
|---|---|---|
| **Library** | Compiled code (object files) other code links against. No resources, no headers by itself. | `libFoo.a` (static), `libFoo.dylib` (dynamic) |
| **Framework** | A **bundle** (folder) containing a library binary **plus** headers, Swift module files, resources and an `Info.plist`. Can be static or dynamic. | `Foo.framework` |
| **XCFramework** | A container of several frameworks/libraries, **one per platform and architecture variant** (device, simulator, Mac Catalyst…). | `Foo.xcframework` |
| **Package** | A **source** distribution unit for Swift Package Manager (`Package.swift`), which may also point to a binary XCFramework. | `swift-collections` |
| **SDK** | A product you give to other developers: the framework(s) + public API + docs + sample app + support + versioning promise. | Firebase, Stripe iOS SDK |

**Interview line:** "A framework is a packaging format; an SDK is a product. Building the binary is the easy part; the hard part is a stable public API, small footprint, and not breaking clients for years."

### Q2. What is the difference between a static and a dynamic library? `[Fundamental]`
| | Static (`.a`, static framework) | Dynamic (`.dylib`, dynamic framework) |
|---|---|---|
| When linked | At **build time**: the linker copies the needed object code into the app binary | At **launch/run time**: `dyld` loads it and binds symbols |
| Where the code lives | Inside the app executable | Separate file in `MyApp.app/Frameworks/` |
| Launch time | Faster (no extra image to load) | Each dynamic framework adds load/bind/sign-check work |
| Binary size | Dead code can be stripped across the whole app | Whole framework shipped; can't strip unused code |
| Shared between app and extensions | Duplicated in each target that links it | One copy shared by the app and its extensions |
| Resources | Static libraries can't carry resources → need a separate resource bundle | Framework bundle carries its own resources |
| Duplicate-symbol risk | Higher (two static libs containing the same code) | Lower (two-level namespace) |
| `Embed` setting in Xcode | **Do Not Embed** | **Embed & Sign** |

Rules of thumb:
- Default for app modules and most SDKs: **static** (better launch time and size).
- Choose **dynamic** when the code must be shared by the app **and** its extensions without duplication, or when you need runtime loading/plugins (macOS).
- Details of how linking works: see the OS Fundamentals & Linker file.

### Q3. What's inside a `.framework` bundle? `[Fundamental]`
```
MySDK.framework/
├── MySDK                              ← the binary (static archive or dynamic Mach-O)
├── Info.plist                         ← bundle ID, version, minimum OS
├── Headers/
│   ├── MySDK.h                        ← umbrella header (Objective-C)
│   └── MySDK-Swift.h                  ← generated header exposing @objc Swift API
├── Modules/
│   ├── module.modulemap               ← tells clang which headers form module "MySDK"
│   └── MySDK.swiftmodule/
│       ├── arm64-apple-ios.swiftinterface        ← textual, stable interface (library evolution)
│       ├── arm64-apple-ios.private.swiftinterface
│       ├── arm64-apple-ios.swiftdoc
│       └── arm64-apple-ios.abi.json
├── PrivacyInfo.xcprivacy              ← privacy manifest (Section 6)
├── _CodeSignature/                    ← signature (dynamic frameworks are signed when embedded)
└── Assets.car, *.lproj, *.storyboardc ← resources (dynamic frameworks)
```
On macOS, frameworks use a versioned layout (`Versions/A/…` with symlinks); iOS frameworks are "shallow" (flat) bundles.

### Q4. What is a module, a module map and an umbrella header? `[Senior]`
- A **module** is the unit you `import`. Swift modules are described by `.swiftmodule` / `.swiftinterface`; C/Objective-C modules by a **module map**.
- **Module map** (`module.modulemap`): tells clang which headers belong to the module, so `@import MySDK;` / `import MySDK` works without textual `#include` chains.
- **Umbrella header**: one header that imports all public headers of the framework.

```
// Modules/module.modulemap
framework module MySDK {
    umbrella header "MySDK.h"
    export *
    module * { export * }
}
```
```objc
// Headers/MySDK.h
#import <Foundation/Foundation.h>
FOUNDATION_EXPORT double MySDKVersionNumber;
FOUNDATION_EXPORT const unsigned char MySDKVersionString[];
#import <MySDK/MSDKClient.h>
#import <MySDK/MSDKConfiguration.h>
```
For a mixed Swift/Objective-C framework, Xcode generates `MySDK-Swift.h` with every `@objc public` Swift declaration so Objective-C clients can use them.

### Q5. How do resources work in static vs dynamic frameworks? `[Senior]`
- A **dynamic** framework is a bundle at runtime, so its resources are found with `Bundle(for: SomeClassInTheFramework.self)`.
- A **static** library/framework's code is merged into the app binary; at runtime `Bundle(for:)` returns the **main app bundle**, and the framework's resource files aren't copied anywhere. So static SDKs ship resources in a separate **resource bundle** (`MySDKResources.bundle`).
- **Swift Package Manager** handles this automatically: resources declared in `Package.swift` get a generated `Bundle.module` accessor.

```swift
// Works in SwiftPM targets (generated), and in frameworks via a small helper
extension Bundle {
    static var mySDK: Bundle {
        #if SWIFT_PACKAGE
        return .module
        #else
        // dynamic framework: the framework bundle itself
        // static framework: look for the resource bundle next to the main bundle
        let frameworkBundle = Bundle(for: BundleToken.self)
        if let url = frameworkBundle.url(forResource: "MySDKResources", withExtension: "bundle"),
           let resources = Bundle(url: url) {
            return resources
        }
        return frameworkBundle
        #endif
    }
}
private final class BundleToken {}

// Usage
let image = UIImage(named: "logo", in: .mySDK, compatibleWith: nil)
let title = String(localized: "checkout.title", bundle: .mySDK)
```
**Common bug:** `UIImage(named: "logo")` inside an SDK looks in the **app's** bundle and returns `nil` in client apps, while it works in the SDK's own demo app.

### Q6. What do "Embed & Sign", "Embed Without Signing" and "Do Not Embed" mean? `[Fundamental]`
| Setting | Use for | Effect |
|---|---|---|
| **Do Not Embed** | Static libraries/frameworks, system frameworks | Linked at build time only; nothing copied into `Frameworks/` |
| **Embed & Sign** | Dynamic frameworks (third-party or your own) | Copied into `MyApp.app/Frameworks/` and re-signed with the app's identity |
| **Embed Without Signing** | Rare: frameworks already signed in a way you must keep | Copied without re-signing |

Typical errors:
- Dynamic framework set to **Do Not Embed** → crash on launch: `dyld: Library not loaded: @rpath/MySDK.framework/MySDK`.
- Static framework set to **Embed & Sign** → App Store validation error or a useless copy in the bundle.

### Q7. What are mergeable libraries? `[Lead/Expert]`
- Introduced in **Xcode 15**: a dynamic library built as **mergeable** contains extra metadata so that, in Release builds, the linker can **merge** it into the app binary like a static library.
- Gives the **best of both**: dynamic linking in Debug (faster incremental builds and linking) and static-like launch performance in Release.
- Build settings: `MERGEABLE_LIBRARY = YES` on the framework; `MERGED_BINARY_TYPE = automatic` (or `manual` with `-merge_framework`) on the app target.
- Resources of merged frameworks are still accessible because Xcode keeps the framework bundle for resources.
- Useful for large modularized apps with dozens of internal frameworks; less relevant for a third-party SDK you distribute as a binary.

### Q8. When should a framework be dynamic vs static in a modular app? `[Senior]`
| Situation | Choice |
|---|---|
| Many internal feature modules in one app | Static (or mergeable dynamic) for launch time |
| Code shared by app + widget + notification extension, large | Dynamic (one copy on disk and in memory), or accept duplication if small |
| Third-party SDK you ship as a binary | Usually static XCFramework; offer dynamic if clients need extension sharing |
| Debug build speed with 50+ modules | Dynamic in Debug (or mergeable) to reduce link time |
| Plug-in loaded at runtime (macOS) | Dynamic (`dlopen` / `Bundle.load()`) |

Apple's guidance: keep the number of dynamic frameworks small; each one adds launch cost (loading, rebasing/binding, code-signature checks). See Section 7.

## 2. XCFrameworks

### Q9. Why do XCFrameworks exist? What was wrong with "fat" frameworks? `[Fundamental]`
- Before XCFrameworks, vendors used `lipo` to merge architectures (`arm64` device + `x86_64` simulator) into one **fat/universal** binary.
- Apple Silicon Macs broke this: the **simulator is also `arm64`**, and a fat binary can't contain two `arm64` slices (device and simulator are different **platforms** with the same architecture).
- Fat frameworks also had to be stripped of simulator slices before App Store submission (the infamous "strip frameworks" run script).
- **XCFramework** (Xcode 11+) stores **separate frameworks per platform variant**, each of which may contain multiple architectures:

```
MySDK.xcframework/
├── Info.plist                                   ← lists the variants (AvailableLibraries)
├── ios-arm64/
│   └── MySDK.framework
├── ios-arm64_x86_64-simulator/
│   └── MySDK.framework                          ← fat across architectures, same platform: allowed
├── ios-arm64_x86_64-maccatalyst/
│   └── MySDK.framework
└── xros-arm64/                                  ← visionOS, if supported
    └── MySDK.framework
```
Xcode picks the right slice automatically for each build destination.

### Q10. How do you build an XCFramework? `[Senior]`
```bash
#!/usr/bin/env bash
set -euo pipefail
SCHEME="MySDK"
OUT="build"

archive() {   # $1 destination, $2 archive name
  xcodebuild archive \
    -scheme "$SCHEME" \
    -destination "$1" \
    -archivePath "$OUT/$2" \
    SKIP_INSTALL=NO \
    BUILD_LIBRARY_FOR_DISTRIBUTION=YES \
    DEBUG_INFORMATION_FORMAT=dwarf-with-dsym
}

archive "generic/platform=iOS"             "ios"
archive "generic/platform=iOS Simulator"   "ios-sim"
archive "generic/platform=macOS,variant=Mac Catalyst" "catalyst"

xcodebuild -create-xcframework \
  -archive "$OUT/ios.xcarchive"      -framework MySDK.framework \
  -archive "$OUT/ios-sim.xcarchive"  -framework MySDK.framework \
  -archive "$OUT/catalyst.xcarchive" -framework MySDK.framework \
  -output "$OUT/MySDK.xcframework"
# -archive + -framework also picks up each archive's dSYMs automatically (Xcode 12+)

# Sign it so clients can verify who built it (Xcode 15+)
codesign --timestamp -s "Apple Distribution: My Company (TEAMID)" "$OUT/MySDK.xcframework"

# Zip for distribution and compute the SwiftPM checksum
(cd "$OUT" && zip -ry MySDK.xcframework.zip MySDK.xcframework)
swift package compute-checksum "$OUT/MySDK.xcframework.zip"
```
Key settings:
- `SKIP_INSTALL=NO`: otherwise the framework isn't included in the archive's `Products`.
- `BUILD_LIBRARY_FOR_DISTRIBUTION=YES`: enables **library evolution** and emits `.swiftinterface` files so clients on **newer Swift compilers** can import it (Q14, Q16).
- `MACH_O_TYPE = staticlib` to produce a static framework (otherwise dynamic).

### Q11. What is `BUILD_LIBRARY_FOR_DISTRIBUTION`, and what does it change? `[Senior]`
It turns on two things:
1. **Module stability**: the compiler emits a textual `.swiftinterface` instead of relying only on the binary `.swiftmodule`, which is tied to the exact compiler version.
2. **Library evolution** (resilience): the binary is compiled so that the library can later add stored properties, enum cases, and methods **without breaking** already-compiled clients (Section 3).

Consequences:
- Without it, a client using Xcode 26 gets: *"Module compiled with Swift 6.0 cannot be imported by the Swift 6.2 compiler"*.
- Slight runtime cost: clients access non-`@frozen` types indirectly (Q17).
- **Every** dependency of a library-evolution module must also be built for distribution (you can't publicly expose a type from a non-resilient module).
- Not needed for source distribution (SPM source packages compile with the client's compiler) or internal frameworks built in the same workspace.

### Q12. How do you handle dSYMs and crash symbolication for a binary SDK? `[Senior]`
- **dSYM** = debug symbols, used to turn crash addresses into function names and line numbers.
- Build with `DEBUG_INFORMATION_FORMAT=dwarf-with-dsym`; `-create-xcframework` with `-archive` includes each slice's dSYMs inside the XCFramework (or use `-debug-symbols <path>` with `-library`).
- The client's archive then contains your dSYMs, so their crash reporter (Xcode Organizer, Crashlytics, Sentry) can symbolicate frames inside your SDK.
- If you don't ship dSYMs (to protect implementation details), keep them yourself and symbolicate crash reports clients send you, matched by the binary's **UUID** (`dwarfdump --uuid MySDK.framework/MySDK`).
- **Bitcode** is deprecated since Xcode 14; don't build with it and don't ask clients for it.

### Q13. What is XCFramework signature verification? `[Senior]`
- Since **Xcode 15**, XCFrameworks can be code-signed by their vendor. Xcode records the signer identity when you add the framework and **warns/errors** if a later update is signed by someone else or unsigned.
- Protects clients from a tampered binary (supply-chain attack via a compromised download server).
- Sign with an Apple Development/Distribution certificate (self-signed is possible but shows as unverified), and timestamp it.
- Apple requires **signatures** for the SDKs on its list of commonly used third-party SDKs (Section 6).

### Q14. Can you check what's inside a binary framework from the command line? `[Senior]`
```bash
# Which architectures does a binary contain?
lipo -info MySDK.framework/MySDK
# → Architectures in the fat file: x86_64 arm64

# Static or dynamic?
file MySDK.framework/MySDK
# → "current ar archive" = static; "Mach-O 64-bit dynamically linked shared library" = dynamic

# Which platform was it built for (device vs simulator), and its minimum OS?
vtool -show-build MySDK.framework/MySDK     # or: otool -l ... | grep -A4 LC_BUILD_VERSION

# Which dynamic libraries does it depend on, and its install name?
otool -L MySDK.framework/MySDK

# Public symbols it exports (demangled)
nm -gU MySDK.framework/MySDK | swift demangle | head

# Is it signed, and by whom?
codesign -dv --verbose=4 MySDK.xcframework
```
These are the first commands to run when debugging "Undefined symbols", "building for iOS Simulator, but linking in object file built for iOS", or launch crashes (Section 9).

### Q15. Should you ship an XCFramework or source code? `[Lead/Expert]`
| | Binary (XCFramework) | Source (Swift package) |
|---|---|---|
| Protects implementation | Yes (not perfectly: binaries can be disassembled) | No |
| Client build time | Faster | Slower (compiles your code) |
| Compiler compatibility | Needs library evolution + `.swiftinterface` | Always compiles with client's compiler |
| Debuggability for clients | Limited (unless dSYMs shipped) | Full: step into code |
| Build settings / flags | Fixed by you | Client's settings apply |
| Trust / auditability | Lower (black box) → needs signing | Higher (clients can read it) |
| Your release work | Build matrix per platform, signing, hosting | Tag a release |

Typical choices: open-source libraries ship source; commercial SDKs with proprietary logic (analytics, fraud detection, payments, ad SDKs) ship binaries, often **with** a source-available public API wrapper.

## 3. Swift ABI, Module Stability & Library Evolution

### Q16. What is the difference between ABI stability, module stability and library evolution? `[Senior]`
| Concept | Since | Meaning | Why it matters |
|---|---|---|---|
| **ABI stability** | Swift 5.0 (2019) | The Swift **runtime and standard library** have a stable binary interface and ship **inside the OS** | Apps no longer bundle the Swift runtime; binaries from different compiler versions can **run** together |
| **Module stability** | Swift 5.1 | A module's interface can be written as a **textual `.swiftinterface`** that any later compiler can read | A framework built with Swift 6.0 can be **imported** by a client using Swift 6.2 |
| **Library evolution** (resilience) | Swift 5.1 | A library can **change** (add properties, cases, methods) without recompiling clients | You can ship SDK 2.1 as a drop-in binary replacement for 2.0 |

- ABI stability alone isn't enough for a binary SDK: without module stability, clients get "module compiled with Swift X cannot be imported by Swift Y".
- `BUILD_LIBRARY_FOR_DISTRIBUTION=YES` (Q11) gives you module stability + library evolution.

### Q17. How does library evolution affect performance, and what do `@frozen` and `@inlinable` do? `[Lead/Expert]`
With library evolution on, clients can't assume the **layout** of your public types (size, stored properties, enum cases), because the library may change them later. So:
- Public structs are accessed **indirectly** through runtime metadata (size queried at runtime, values passed by reference).
- Public enums are treated as **non-frozen**: clients must handle unknown future cases (`@unknown default`).
- Calls can't be inlined across the module boundary.

Opt-outs (each is a **promise you can never break** without a major version):

```swift
/// @frozen: layout is fixed forever → clients access fields directly (fast)
@frozen
public struct Money: Sendable, Hashable {
    public let amountMinor: Int64
    public let currencyCode: String
    public init(amountMinor: Int64, currencyCode: String) {
        self.amountMinor = amountMinor
        self.currencyCode = currencyCode
    }
}

/// @frozen enum: you promise never to add a case → clients can switch exhaustively
@frozen
public enum Environment: Sendable { case sandbox, production }

/// Non-frozen (the default under library evolution): you CAN add cases later
public enum PaymentStatus: Sendable { case pending, succeeded, failed }

/// @inlinable: the body is copied into the .swiftinterface and may be inlined into clients
extension Money {
    @inlinable
    public var isZero: Bool { amountMinor == 0 }
    // ⚠️ Clients may keep the OLD body compiled into their app even after they update your SDK.
}

/// @usableFromInline: an internal declaration that inlinable code is allowed to call
@usableFromInline
internal func validate(_ code: String) -> Bool { code.count == 3 }
```
**Rule:** don't use `@frozen` or `@inlinable` unless profiling shows a real need. They trade future flexibility for speed.

### Q18. What changes are binary compatible under library evolution? `[Lead/Expert]`
| ✅ Safe (minor version) | ❌ Breaking (major version) |
|---|---|
| Add a new public type, function, method, property | Remove or rename any public declaration |
| Add a stored property to a **non-frozen** struct/class | Change a function signature, parameter label or type |
| Add a case to a **non-frozen** enum | Add a case to a `@frozen` enum, or a stored property to a `@frozen` struct |
| Add a protocol requirement **with a default implementation** | Add a protocol requirement without a default |
| Add a new initializer or a default argument value | Change a class from `open` to `public`, or make something less visible |
| Reorder members of non-frozen types | Change `@inlinable` code semantics (old clients keep the old body) |
| Add conformances (careful: can conflict with clients' own retroactive conformances) | Change a `struct` to a `class` or vice versa; change a type's generic parameters |

Tooling to catch mistakes before release:
```bash
# SwiftPM: compare the API against the last release tag
swift package diagnose-api-breaking-changes 2.3.0

# Binary frameworks: compare ABI baselines (swift-api-digester under the hood)
xcrun swift-api-digester -diagnose-sdk -baseline-path api-2.3.0.json \
  -module MySDK -I build/ios/MySDK.framework/Modules -target arm64-apple-ios15.0
```

### Q19. What is `@_implementationOnly import`, and what replaced it? `[Lead/Expert]`
- Problem: your SDK uses a dependency internally (e.g. a networking library). If you `import` it normally, its module becomes part of your public interface: clients need its `.swiftmodule` to compile, and you may leak its types.
- `@_implementationOnly import Dependency` (underscored, unofficial) hid it, but was fragile.
- **Swift 6 (SE-0409) access-level imports** make this official:

```swift
// MySDK/Sources/Networking.swift
internal import Alamofire          // not visible to clients; can't appear in public API
public import Foundation          // re-exported as part of our public interface

public final class Client {
    let session: Session            // OK: internal property may use an internally imported type
    // public let session: Session  // ❌ error: cannot use internally imported type in public API
}
```
- Enable `InternalImportsByDefault` (upcoming feature) so imports are internal unless marked `public`.
- Note: the dependency's **binary code** is still needed at link time (static libs are linked in; dynamic ones must be present at runtime). Hiding the import isn't the same as removing the dependency.

### Q20. How do you keep an Objective-C-compatible API in a Swift SDK? `[Senior]`
- Many clients (and React Native/Flutter/Unity bridges) still call SDKs from Objective-C.
- Expose an `@objc` surface: classes inheriting `NSObject`, `@objc(MSDKClient)` names with a prefix, no Swift-only types (generic structs, enums with associated values, `async` without a completion variant) in that surface.

```swift
@objc(MSDKClient)
public final class Client: NSObject, Sendable {     // immutable state (or an internal actor) so `shared` is safe
    @objc public static let shared = Client()

    // Swift-first API
    public func track(_ event: Event) async throws { /* ... */ }

    // Objective-C bridge: completion handler + NSError
    @objc(trackEventNamed:properties:completion:)
    public func track(name: String,
                      properties: [String: String],
                      completion: (@Sendable (Error?) -> Void)? = nil) {
        let event = Event(name: name, properties: properties)   // build Sendable values before the Task
        Task {
            do {
                try await track(event)
                completion?(nil)            // documented: called on a background thread
            } catch {
                completion?(error)          // Swift Error bridges to NSError
            }
        }
    }
}
```
Swift `async` methods marked `@objc` are also exposed to Objective-C as completion-handler methods automatically, but an explicit wrapper gives you control over naming and threading.

### Q21. Why must public enums in an SDK be handled with `@unknown default`? `[Senior]`
- Under library evolution, public enums are non-frozen: version 2.1 may add a case.
- A client's `switch` without a default becomes a compile **warning** ("switch must be exhaustive; add `@unknown default`") and, at runtime, an unknown case would trap if not handled.
- `@unknown default` handles future cases while still warning the client at compile time when a **known** case is missing.

```swift
switch result.status {
case .succeeded: showReceipt()
case .pending:   showSpinner()
case .failed:    showError()
@unknown default: showGenericState()       // future cases from a newer SDK version
}
```

### Q22. What is the "module name equals type name" problem in `.swiftinterface` files? `[Lead/Expert]`
- If the module and a public type have the same name (module `Analytics` with a `public class Analytics`), the generated `.swiftinterface` qualifies types as `Analytics.Event`, which the compiler then resolves as **the type** `Analytics`, not the module. Clients get errors like *"'Event' is not a member type of class 'Analytics.Analytics'"* when importing the binary.
- Fixes: never name a public type the same as its module (`AnalyticsSDK` module, `Analytics` class), or rely on newer compilers' module aliasing/`-alias-module-names-in-module-interface` workarounds.
- Interview value: it shows you've actually shipped a binary Swift framework.

## 4. Swift Package Manager

### Q23. Why is Swift Package Manager the standard way to share iOS code? `[Fundamental]`
| Capability | How SwiftPM does it |
|---|---|
| Built into the toolchain | Part of Swift and Xcode; no extra tools, no generated workspace, no changes to your `.xcodeproj` beyond a package reference |
| Manifest | `Package.swift`, written in Swift and type-checked |
| Source and binary | Source targets, or `binaryTarget` for signed XCFrameworks with a checksum |
| Resources | Declared per target; generated `Bundle.module` accessor |
| Reproducible builds | `Package.resolved` pins exact versions and revisions |
| Products and modularity | One package can expose several libraries; clients pick only what they need |
| Extensibility | Build tool and command **plugins** (code generation, linting), **macros**, **package traits** (Q30) |
| Private hosting | Any Git server, or a **package registry** (SE-0292) |
| Cross-platform | Same manifest for iOS, macOS, watchOS, tvOS, visionOS, and Linux/server targets |

**Interview line:** "I ship SDKs and internal modules as Swift packages: source packages for open or internal code, a binary XCFramework behind a thin wrapper target for closed-source SDKs."

**If an interviewer asks about CocoaPods:** it's legacy. Its central registry (trunk) stops accepting new versions on 2 December 2026, so the answer is "migrate the project to SwiftPM": podspec subspecs become products/targets, `resource_bundles` become `resources` with `Bundle.module`, and `vendored_frameworks` become `binaryTarget`s.

### Q24. Write a `Package.swift` for an SDK. `[Senior]`
```swift
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "MySDK",
    defaultLocalization: "en",
    platforms: [.iOS(.v15), .macOS(.v12)],
    products: [
        // What clients can depend on. Keep this list small and stable.
        .library(name: "MySDK", targets: ["MySDK"]),
        .library(name: "MySDKUI", targets: ["MySDKUI"]),          // optional UI layer, separate product
    ],
    dependencies: [
        // Avoid third-party deps in SDKs where possible (Q38); if needed, use wide version ranges
        .package(url: "https://github.com/apple/swift-log.git", from: "1.5.0"),
    ],
    targets: [
        .target(
            name: "MySDK",
            dependencies: [.product(name: "Logging", package: "swift-log")],
            resources: [.process("Resources")],              // generates Bundle.module
            swiftSettings: [.enableUpcomingFeature("InternalImportsByDefault")]
        ),
        .target(name: "MySDKUI", dependencies: ["MySDK"]),
        .testTarget(name: "MySDKTests", dependencies: ["MySDK"]),
    ]
)
```
- The privacy manifest goes in the target's resources (`Resources/PrivacyInfo.xcprivacy`, Section 6).
- Splitting `MySDK` (core) and `MySDKUI` lets clients who build their own UI avoid pulling in UI code.
- Releases are **Git tags** with semantic versions (`2.3.0`); clients choose rules like `from: "2.3.0"` (up to next major).

### Q25. How do you distribute a binary XCFramework with Swift Package Manager? `[Senior]`
```swift
// swift-tools-version: 5.9
import PackageDescription

let package = Package(
    name: "MySDK",
    platforms: [.iOS(.v15)],
    products: [
        .library(name: "MySDK", targets: ["MySDKWrapper"]),
    ],
    targets: [
        // Remote binary: URL must point to a .zip; checksum from `swift package compute-checksum`
        .binaryTarget(
            name: "MySDKBinary",
            url: "https://downloads.example.com/mysdk/2.3.0/MySDK.xcframework.zip",
            checksum: "6c7a0e3f5c3b1f2d9a8e7d6c5b4a39281706f5e4d3c2b1a0f9e8d7c6b5a49382"
        ),
        // Optional thin source target: lets you add resources, a privacy manifest
        // and dependencies, which a binaryTarget alone can't declare
        .target(
            name: "MySDKWrapper",
            dependencies: ["MySDKBinary"],
            resources: [.copy("PrivacyInfo.xcprivacy")]
        ),
    ]
)
```
Notes:
- The checksum makes downloads tamper-evident: if the zip changes, resolution fails.
- A binary target **can't declare dependencies**; the wrapper target pattern adds them.
- Binary targets work only for Apple platforms (and artifact bundles for executables/plugins).
- Never replace a published zip at the same URL: create a new version (clients' `Package.resolved` pins the checksum).

### Q26. How do clients depend on a package, and how are versions pinned? `[Senior]`
```swift
dependencies: [
    .package(url: "https://github.com/example/mysdk-ios", from: "2.3.0"),              // 2.3.0 ..< 3.0.0 (default, recommended)
    .package(url: "https://github.com/example/charts", .upToNextMinor(from: "1.4.0")), // 1.4.0 ..< 1.5.0
    .package(url: "https://github.com/example/legacy", exact: "0.9.2"),               // avoid: blocks shared resolution
    .package(url: "https://github.com/example/beta", branch: "main"),                 // never in releases
    .package(path: "../Packages/DesignSystem"),                                       // local package in a monorepo
]
```
- **SwiftPM resolves one version per package for the whole graph.** If two packages need incompatible ranges of the same dependency, resolution fails. That's why SDKs should use wide `from:` ranges (Q28).
- **`Package.resolved`** records the exact version and commit of every package. **Commit it** for apps so every developer and CI build uses the same versions; libraries usually don't commit it (clients resolve for themselves).
- Updating: Xcode → *File → Packages → Update to Latest Package Versions*, or `swift package update` for command-line packages.
- **CI settings** for reproducible, fast builds:

```bash
# Resolve exactly what Package.resolved says (fail instead of silently changing versions),
# into a directory that CI caches between runs
xcodebuild -resolvePackageDependencies \
  -onlyUsePackageVersionsFromResolvedFile \
  -clonedSourcePackagesDirPath .spm-cache

xcodebuild build -scheme MyApp \
  -disableAutomaticPackageResolution \
  -clonedSourcePackagesDirPath .spm-cache
```
- Private repos: CI needs Git credentials (SSH keys or a token in `~/.netrc`); binary targets on authenticated servers also read `~/.netrc`.

### Q27. How do internal (private) SDKs get distributed inside a company? `[Senior]`
| Option | How | Good for |
|---|---|---|
| Monorepo, local packages | `.package(path: "../Packages/Payments")` | One app or a few apps in one repo; fastest iteration |
| Private Git repos + SwiftPM | Tags on private repos; CI has Git credentials | Several apps across repos |
| Swift package registry (SE-0292) | `swift package-registry publish`; resolve by ID `mycompany.payments` (Artifactory, GitHub Packages, Nexus) | Many packages, faster resolution than Git clones, immutable releases |
| Binary XCFrameworks on an artifact server | `binaryTarget(url:checksum:)` | Speeding up builds of large, stable modules; hiding code from other teams |

Lead-level concerns: who **owns** each SDK, a versioning policy, a deprecation window, compatibility with each app's Xcode/Swift version, and CI that builds every consumer app against the new SDK version before release.

### Q28. How should an SDK handle its own third-party dependencies? `[Lead/Expert]`
**Avoid them** where you can. An SDK's dependency becomes the **client's** problem:
- **Version conflicts** ("diamond dependency"): the app needs Alamofire 5.9, your SDK pins 5.4 → resolution fails.
- **Duplicate symbols**: if you statically link (vendor) a library into your binary and the app also links it → duplicate symbols or, worse, two copies with different behavior at runtime.
- Size, security and license exposure.

Options, best first:
1. **No dependency**: use `URLSession`, `Codable`, `CryptoKit`, `OSLog`. Most SDKs need nothing else.
2. **Declare** the dependency in `Package.swift` with a **wide version range** (`from: "5.0.0"`) so the client's resolver picks one shared copy (works for source packages; binaries can't declare dependencies except via a wrapper target, Q25).
3. **Vendor with renamed symbols** ("namespacing"): copy the source into your SDK with prefixed names (e.g. `MySDK_Alamofire`), and update it yourself. Last resort.
4. **Protocol injection**: define a protocol (`HTTPTransport`) and let the client plug in their own implementation.

### Q29. What does a SwiftPM release pipeline for a closed-source binary SDK look like? `[Senior]`
```
Private source repo                                Public distribution repo (what clients add)
─────────────────────                              ─────────────────────────────────────────────
tag v2.4.0                                         Package.swift   ← binaryTarget URL + checksum
  └─ CI: build all slices (BUILD_LIBRARY_FOR_          Sources/MySDKWrapper/  (privacy manifest, resources)
        DISTRIBUTION), create XCFramework,              README, LICENSE, CHANGELOG
        codesign, zip, upload to                        tag 2.4.0
        /mysdk/2.4.0/MySDK.xcframework.zip
  └─ swift package compute-checksum ──────────────▶ commit updated URL + checksum, tag 2.4.0
  └─ smoke-test apps resolve the new tag and build (SwiftUI app, UIKit app, Objective-C app)
  └─ publish DocC docs + release notes
```
- The **distribution repo** contains no implementation source, so clients don't clone your private code; its tags mirror SDK versions.
- **One source of truth** for the version (a `VERSION` file or the tag) that also feeds the runtime `MySDK.version` constant.
- Artifacts at **immutable, versioned URLs**; a re-uploaded zip would break every client's checksum (Q76).
- Keep dSYMs inside the XCFramework (or archived privately) so crashes can be symbolicated (Q12).

### Q30. What are package traits? `[Lead/Expert]`
- **Swift 6.1 (SE-0450)** added **package traits**: named, optional features a package declares and clients enable, similar to Cargo features.
- Use them to make heavy parts optional (an SDK's SwiftUI components, a crypto backend, logging integrations) without splitting into many products.

```swift
// In the SDK's Package.swift (swift-tools-version: 6.1)
traits: [
    .trait(name: "SwiftUIComponents"),
    .default(enabledTraits: []),                 // nothing extra by default
],
// In code
#if SwiftUIComponents
import SwiftUI
public struct PayButton: View { /* ... */ }
#endif

// In the client's Package.swift
.package(url: "https://github.com/example/mysdk-ios", from: "3.0.0", traits: ["SwiftUIComponents"])
```

### Q31. How do you choose the minimum iOS version for an SDK? `[Senior]`
- An SDK's minimum must be **≤ the lowest minimum among its clients**; otherwise they can't integrate it.
- Typical: support the current OS and the 2–3 previous major versions; check what your biggest clients support.
- Use `@available` / `if #available` for newer APIs rather than raising the floor:

```swift
public func presentCheckout(from viewController: UIViewController) {
    if #available(iOS 17.0, *) {
        presentModernCheckout(from: viewController)     // uses newer APIs
    } else {
        presentLegacyCheckout(from: viewController)
    }
}
```
- Raising the minimum is a **breaking change** for clients still on older versions → do it in a major version, with notice.
- Xcode itself drops support for old deployment targets over time; that forces the floor up periodically.

## 5. SDK Public API Design

### Q32. What makes a good SDK API? `[Senior]`
1. **Small surface**: everything `internal` by default; each `public` symbol is a long-term promise.
2. **Easy first integration**: one configure call and one main entry point; sensible defaults.
3. **Hard to misuse**: types instead of strings, required parameters in initializers, no "call A before B" rules the compiler can't check.
4. **Thread-safe**: callable from any thread or clearly `@MainActor`.
5. **Doesn't own the app**: no swizzling, no global UI changes, no surprises in app lifecycle, no crashing the host app.
6. **Observable and debuggable**: log levels, error types with useful messages, a debug mode.
7. **Evolvable**: configuration objects instead of long parameter lists, non-frozen enums, protocols with default implementations.
8. **Swift-first, Objective-C-compatible** if the client base needs it.

### Q33. How should an SDK be initialized and configured? `[Senior]`
```swift
public struct Configuration: Sendable {
    public var apiKey: String
    public var environment: Environment = .production
    public var logLevel: LogLevel = .warning
    public var networkTimeout: Duration = .seconds(30)
    public var enableCrashReporting = true          // new options can be added later without breaking callers

    public init(apiKey: String) { self.apiKey = apiKey }
}

public final class PaymentsClient: Sendable {
    public init(configuration: Configuration) throws {
        guard configuration.apiKey.hasPrefix("pk_") else {
            throw PaymentsError.invalidConfiguration("Use a publishable key (pk_…), never a secret key.")
        }
        // ... store configuration, create internal services
    }
}

// Client app
var config = Configuration(apiKey: "pk_live_123")
config.environment = .production
let payments = try PaymentsClient(configuration: config)
```
**Instance vs singleton:**
- Prefer an **instance** the client owns and injects (testable, supports multiple configurations, no hidden global state).
- A `shared` convenience is acceptable for SDKs that are naturally app-wide (analytics, crash reporting), but keep an instance-based API underneath and make `configure` idempotent and safe to call once.
- Never do heavy work in `configure` on the main thread; it runs during app launch.

### Q34. How do you make an SDK thread-safe in Swift 6? `[Lead/Expert]`
- Public types should be **`Sendable`**; public mutable state lives behind an **actor** or a lock.
- Choose an isolation model and document it:
  - UI components: `@MainActor`.
  - Services: `async` methods on an actor or a `Sendable` final class with internal actors.
- Don't call client callbacks while holding a lock (deadlock risk), and say which thread/actor callbacks run on.

```swift
public final class AnalyticsClient: Sendable {
    private let queue: EventQueue           // actor holding mutable state

    public init(configuration: Configuration) {
        self.queue = EventQueue(configuration: configuration)
    }

    /// Safe to call from any thread; returns immediately (fire-and-forget)
    public func track(_ name: String, properties: [String: String] = [:]) {
        let event = Event(name: name, properties: properties, timestamp: .now)
        Task { await queue.enqueue(event) }
    }

    /// For callers who need to know events were handed off (e.g. before logout)
    public func flush() async { await queue.flush() }
}

actor EventQueue {
    private var pending: [Event] = []
    private let configuration: Configuration
    init(configuration: Configuration) { self.configuration = configuration }
    func enqueue(_ event: Event) { pending.append(event); if pending.count >= 20 { Task { await flush() } } }
    func flush() async { /* batch upload; on failure keep events and persist them */ }
}
```
Note on ordering: `Task { await queue.enqueue(event) }` from many threads doesn't guarantee events arrive in call order. If order matters, use an `AsyncStream` continuation (yield is synchronous and ordered) feeding one consumer task, or a lock-protected buffer.

### Q35. Delegates, closures, Combine or async/await for an SDK's callbacks? `[Senior]`
| Style | Use for | Notes |
|---|---|---|
| `async throws` | One-shot results (`fetchBalance()`) | Swift-first default |
| `AsyncStream` / `AsyncSequence` | Ongoing events (connection state, payment status) | Document buffering policy and termination |
| Delegate protocol (`weak`) | Many related callbacks, Objective-C clients, UI flows | Familiar to UIKit developers; must be optional methods or have defaults |
| Completion closures | Objective-C compatibility, older clients | State the callback queue |
| Combine publishers | Only if clients are Combine-based | Don't force Combine on everyone; keep it in an optional product |

```swift
public protocol CheckoutDelegate: AnyObject {
    @MainActor func checkoutDidComplete(_ result: CheckoutResult)
    @MainActor func checkoutDidCancel()
}
public extension CheckoutDelegate {
    func checkoutDidCancel() {}            // default → adding methods later isn't breaking
}

public extension PaymentsClient {
    /// Ongoing status updates for one payment
    func statusUpdates(for paymentID: String) -> AsyncStream<PaymentStatus> {
        AsyncStream(bufferingPolicy: .bufferingNewest(1)) { continuation in
            let task = Task {
                for await status in self.poll(paymentID) { continuation.yield(status) }
                continuation.finish()
            }
            continuation.onTermination = { _ in task.cancel() }     // stop work when the client stops listening
        }
    }
}
```

### Q36. How should an SDK model errors? `[Senior]`
- A **public error type** with stable, meaningful cases; a human-readable description; and the underlying error for debugging.
- Distinguish **client mistakes** (invalid configuration, called before configure), **retryable** failures (network) and **definitive** failures (card declined).
- Don't expose internal dependency error types in the public API.

```swift
public enum PaymentsError: Error, Sendable {
    case invalidConfiguration(String)
    case network(underlying: any Error)          // Error is Sendable in Swift 6
    case declined(code: String, message: String)
    case rateLimited(retryAfter: Duration?)
    case unexpected(String)

    public var isRetryable: Bool {
        switch self {
        case .network, .rateLimited: true
        default: false
        }
    }
}

extension PaymentsError: LocalizedError {
    public var errorDescription: String? {
        switch self {
        case .invalidConfiguration(let reason): "MySDK configuration error: \(reason)"
        case .network: "The network connection failed."
        case .declined(_, let message): message
        case .rateLimited: "Too many requests. Try again shortly."
        case .unexpected(let detail): "Unexpected error: \(detail)"
        }
    }
}
```
Typed throws (`throws(PaymentsError)`, Swift 6) is tempting, but it locks the error type into the API forever; many SDKs keep untyped `throws` and document the error type.

### Q37. How do you avoid naming collisions in an SDK? `[Senior]`
- Swift types are namespaced by module (`MySDK.Configuration`), but:
  - Generic names (`Configuration`, `Event`, `Result`, `Logger`) clash with the **client's own** types and force them to write `MySDK.Event` everywhere. Prefer specific names (`PaymentsConfiguration`) or nest types (`Payments.Configuration`).
  - **Objective-C runtime names are global**: two classes named `Logger` from different frameworks collide at runtime ("Class Logger is implemented in both…, one of the two will be used"). Prefix `@objc` names: `@objc(MSDKLogger)`.
  - **Category/extension methods** on Foundation/UIKit types can collide with the app's or another SDK's extensions. Avoid public extensions on system types; if necessary, prefix (`msdk_`) or use a wrapper (`view.mySDK.applyTheme()`).
  - **Resource names** (images, strings tables) in a shared bundle: use your own bundle (Q5).
  - **UserDefaults keys, Keychain service names, notification names, file paths**: prefix with your bundle ID (`com.example.mysdk.`).

### Q38. What must an SDK never do to its host app? `[Lead/Expert]`
- **Crash the app**: no `fatalError`, force unwraps or `precondition` on paths reachable in production; report errors instead. (A debug-only `assertionFailure` for misuse is acceptable.)
- **Block the main thread**: no synchronous network, disk or Keychain work on main during configure or calls.
- **Swizzle** app or system methods without an opt-out (breaks other SDKs, App Store risk, hard to debug). If you must (e.g. automatic screen tracking), make it opt-in and documented.
- **Change global state**: `UINavigationBar.appearance()`, `URLCache.shared`, `URLSession.shared` configuration, `NSSetUncaughtExceptionHandler` without chaining the previous handler, the app's `UNUserNotificationCenter.delegate`.
- **Collect data silently**: everything must match the privacy manifest and the client's disclosures.
- **Grow unbounded**: caches and event queues need limits; disk files need cleanup.
- **Make network calls before consent** where the client needs consent first (offer a `consent` / `isEnabled` switch).

### Q39. How do you deprecate and evolve SDK APIs? `[Senior]`
```swift
public extension PaymentsClient {
    @available(*, deprecated, renamed: "createPayment(amount:currency:)",
               message: "Use createPayment(amount:currency:). Will be removed in 4.0.")
    func makePayment(amount: Int, currency: String) async throws -> Payment {
        try await createPayment(amount: Money(amountMinor: Int64(amount), currencyCode: currency))
    }

    func createPayment(amount: Money) async throws -> Payment { /* new API */ }
}
```
Policy:
- Deprecate in a **minor** version; remove only in the next **major**, with at least one release cycle (or a time window, e.g. 6 months) between.
- The `renamed:` argument gives clients an Xcode **fix-it**.
- Document migrations in a changelog and a migration guide.
- Track which deprecated APIs clients still call (server-side, via SDK version + feature usage telemetry) before removing them.

### Q40. How do you design an SDK's UI components so clients can customize them? `[Senior]`
- Offer layers: a **drop-in UI** (fastest integration), a **customizable UI** (theme, fonts, colors, strings), and a **headless API** (clients build their own UI).
- Theme via a value type, not subclassing:

```swift
public struct CheckoutTheme: Sendable {
    public var primaryColor: Color = .accentColor
    public var cornerRadius: CGFloat = 12
    public var font: Font = .body
    public init() {}
}

public struct CheckoutView: View {
    private let session: CheckoutSession
    private let theme: CheckoutTheme
    public init(session: CheckoutSession, theme: CheckoutTheme = .init()) {
        self.session = session
        self.theme = theme
    }
    public var body: some View { /* uses theme */ EmptyView() }
}
```
- Support Dynamic Type, Dark Mode, VoiceOver and right-to-left layouts: you're shipping UI into someone else's accessible app.
- Provide UIKit wrappers (`UIHostingController`-based) for UIKit clients.
- Localize strings in your bundle, with a way for the client to override.

### Q41. How do you add logging and debugging support to an SDK? `[Senior]`
- Use `OSLog`/`Logger` with your own **subsystem** (`com.example.mysdk`) so clients can filter in Console.
- Configurable log level, default `warning` (quiet). A `debug` level for integration problems.
- **Never log** secrets, tokens, card data, or personal data; use `privacy: .private` for values.
- Optional **log handler** so clients can forward SDK logs to their own system.
- A **debug/diagnostics screen or method** (`client.diagnostics()`) reporting configuration, SDK version, last errors: saves support tickets.

```swift
import OSLog

enum SDKLog {
    static let network = Logger(subsystem: "com.example.mysdk", category: "network")
}

SDKLog.network.debug("POST \(path, privacy: .public) took \(ms) ms")
SDKLog.network.error("Auth failed for key \(apiKeySuffix, privacy: .private)")
```

### Q42. How do you make an SDK testable for its clients? `[Senior]`
- Expose **protocols** for the main client (`PaymentsClientProtocol`) or provide an official **test double** (`MockPaymentsClient` in a `MySDKTesting` product).
- Offer a **sandbox environment** and test keys/cards.
- Avoid singletons that can't be reset; if `shared` exists, allow injecting an instance instead.
- Make time, network and storage injectable internally so **your** tests are deterministic.

```swift
// In the MySDK product
public protocol PaymentsClientProtocol: Sendable {
    func createPayment(amount: Money) async throws -> Payment
}
extension PaymentsClient: PaymentsClientProtocol {}

// In a separate MySDKTesting product (never linked into release builds)
public final class MockPaymentsClient: PaymentsClientProtocol, @unchecked Sendable {
    public var result: Result<Payment, Error>
    public init(result: Result<Payment, Error>) { self.result = result }
    public func createPayment(amount: Money) async throws -> Payment { try result.get() }
}
```
`@unchecked Sendable` is acceptable in a test double that tests configure before use; production types should be checked `Sendable`.

## 6. Resources, Privacy & App Store Compliance

### Q43. What is a privacy manifest, and why does an SDK need one? `[Senior]`
- `PrivacyInfo.xcprivacy` is a property list describing **what data your code collects, why, whether it tracks users, which tracking domains it contacts, and which "required reason" APIs it uses**.
- Xcode merges the app's and all SDKs' manifests into a **privacy report** the developer uses for the App Store privacy "nutrition label".
- Each SDK's manifest must describe **only that SDK's** practices; apps must not copy SDK practices into their own manifest.
- Since **12 February 2025**, if a new app or an update adds an SDK from Apple's list of **privacy-impacting third-party SDKs**, that SDK must include a privacy manifest (rejection **ITMS-91061: Missing privacy manifest**), and a valid **signature** if distributed as a binary.
- Every app and SDK must declare approved **reasons** for "required reason" APIs (enforced since May 2024; email **ITMS-91053: Missing API declaration**).

### Q44. What does an SDK's privacy manifest look like? `[Senior]`
```xml

Required-reason API categories: **UserDefaults, file timestamps, system boot time, disk space, active keyboards**. Reason codes are listed in Apple's documentation; pick the narrowest accurate one.

- Dynamic framework: in the framework bundle root.
- Static framework/library: in a resource bundle that ships with it.
- SwiftPM: in the target's resources; for a binary target, use the wrapper-target pattern (Q25).

### Q45. What App Tracking Transparency rules apply to SDKs? `[Senior]`
- **Tracking** = linking data from your app with data from other companies' apps/websites for advertising or measurement, or sharing it with data brokers.
- If the SDK tracks, the **app** must ask the user via `ATTrackingManager.requestTrackingAuthorization` before tracking; the SDK must honor the result.
- Domains listed in `NSPrivacyTrackingDomains` are **blocked by the system** when the user hasn't granted tracking permission, so separate tracking and non-tracking endpoints (e.g. `analytics.example.com` vs `ads-tracking.example.com`).
- Reading the IDFA (`ASIdentifierManager.advertisingIdentifier`) returns zeros without permission.
- **Fingerprinting** (deriving an ID from device signals) is prohibited regardless of permission.

```swift
import AppTrackingTransparency

public func setTrackingAuthorized() {
    // Let the APP request permission at a moment that makes sense; the SDK only reads the status
    let status = ATTrackingManager.trackingAuthorizationStatus
    isTrackingEnabled = (status == .authorized)
}
```

### Q46. What other App Store rules affect SDKs? `[Senior]`
- **No private APIs**: App Review scans binaries; an SDK using private selectors gets every client rejected.
- **No downloading executable code** (no dynamic code loading of native code; JavaScript in a WebView/JavaScriptCore is allowed).
- **Minimum deployment target and supported architectures**: arm64 only on device; no simulator slices in the submitted app (XCFrameworks handle this).
- **Nested frameworks** aren't allowed: a framework containing its own `Frameworks/` folder → **ITMS-90206 / "Invalid Bundle… contains disallowed file 'Frameworks'"** (Q66).
- **Usage descriptions**: if the SDK uses the camera, location, Bluetooth, etc., the **app** must provide `NS…UsageDescription` strings; document this in the integration guide.
- **Required device capabilities and background modes** the SDK needs must be declared by the app.

### Q47. How do you handle localization in an SDK? `[Fundamental]`
- Strings live in the SDK's bundle (`Localizable.xcstrings` string catalog), looked up with the SDK's bundle:

```swift
let title = String(localized: "checkout.pay_button", defaultValue: "Pay", bundle: .mySDK,
                   comment: "Title of the main payment button")
```
- Set `defaultLocalization` in `Package.swift`.
- Let clients override strings (a closure or dictionary in configuration) for brand voice.
- An SDK can only show languages that **both** it and the app support: if the app doesn't list a language, iOS won't select it for the app's bundles.

### Q48. How do you protect API keys and secrets in an SDK? `[Senior]`
- **Anything shipped in an app binary is public**: strings, plist values, obfuscated constants can all be extracted.
- SDKs should only accept **publishable / restricted keys** that are safe to expose (Stripe's `pk_…`), with sensitive operations done by the client's **backend** using secret keys.
- Protect the API from abuse with server-side measures: rate limits per key, allowed bundle IDs, **App Attest** / DeviceCheck to verify requests come from the genuine app.
- Store tokens the SDK obtains in the **Keychain** with an SDK-specific service name and appropriate accessibility (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`).

## 7. Binary Size & Launch Performance

### Q49. How do dynamic frameworks affect app launch time? `[Senior]`
At launch, `dyld` must, for **each** dynamic framework:
1. Find and map the file (with code-signature validation of its pages).
2. Apply **rebases and binds** (fix up pointers, resolve symbols from other images).
3. Run **initializers** (Objective-C `+load`, C++ static constructors, `__attribute__((constructor))`).

dyld 3/4 cache much of this work in **launch closures**, but every image still has a cost. Apple's long-standing advice: keep the number of embedded dynamic frameworks small; prefer static linking or mergeable libraries (Q7).

Measure with the **App Launch** template in Instruments (the old `DYLD_PRINT_STATISTICS` environment variable no longer prints anything with dyld 4 on current OS versions), and wrap your own SDK's startup work in `os_signpost` intervals so it shows up as a named region.

### Q50. What should an SDK do (and not do) at app launch? `[Senior]`
- **No `+load` methods** or static initializers that do work: they run before `main`, for every launch, even if the SDK is never used.
- `configure()` should be cheap: store configuration, schedule heavier work **after** the first frame (`Task(priority: .utility)`), avoid synchronous disk/network/Keychain on the main thread.
- Lazy-load heavy subsystems on first use.
- Publish your SDK's **launch cost budget** (e.g. "< 5 ms on main thread") and measure it in CI on a reference device.

```swift
private static let state = OSAllocatedUnfairLock<Configuration?>(initialState: nil)   // iOS 16+; NSLock box for older

public static func configure(_ configuration: Configuration) {
    // Cheap and synchronous: validate and store
    state.withLock { $0 = configuration }
    // Deferred: everything else, off the main thread
    Task.detached(priority: .utility) {
        await DiskQueue.shared.restorePendingEvents()
        await RemoteConfig.shared.refreshIfStale()
    }
}
```

### Q51. How do you measure and reduce an SDK's binary size? `[Senior]`
Measure:
- Build a **sample app with and without** the SDK; compare the **App Thinning Size Report** (Xcode Organizer → Distribute → Export with thinning for a specific device) for download and install size.
- Generate a **linker map** (`LD_GENERATE_MAP_FILE = YES`) to see which object files and symbols contribute.
- Don't judge by the XCFramework zip size: it contains all slices, dSYMs and unstripped symbols.

Reduce:
- Static linking + **dead code stripping** (`DEAD_CODE_STRIPPING = YES`) so unused code is removed from client apps.
- Split into **optional products** (core vs UI vs extras) or **package traits** (Q30).
- Avoid heavy dependencies and large bundled assets (download fonts/ML models on demand, use SF Symbols, compress images, asset catalogs).
- Watch Swift generics and `@inlinable` explosion (specializations duplicate code).
- Strip debug symbols from the shipped binary (`STRIP_INSTALLED_PRODUCT`, `STRIP_STYLE = non-global` for static libs); ship dSYMs separately.

### Q52. What are `-ObjC`, `-all_load` and `-force_load`, and why do they matter for static SDKs? `[Lead/Expert]`
- The linker only pulls object files from a static library if they define a symbol that's **referenced**. Objective-C **categories** and classes looked up dynamically (`NSClassFromString`) aren't referenced by symbol, so their object files get dropped → runtime crash "unrecognized selector sent to instance".
- `-ObjC`: load **every object file that defines an Objective-C class or category** from all static libraries.
- `-all_load`: load **every object file** from all static libraries (bigger binary, more duplicate-symbol risk).
- `-force_load path/libFoo.a`: load everything from **one** library only.
- Many SDK integration guides say "add `-ObjC` to Other Linker Flags". Swift-only static frameworks usually don't need it, unless they rely on Objective-C runtime lookups.
- Details on symbol resolution: OS Fundamentals & Linker file.

### Q53. How do static frameworks cause duplicate code in apps with extensions, and what do you do about it? `[Senior]`
- A static SDK linked into the **app** and into a **widget** and a **notification service extension** is copied into **each** binary: 3× size on disk; each process loads its own copy (separate memory and separate singleton state, which is often fine since they're separate processes anyway).
- If the shared code is large, put it in **one dynamic framework** embedded in the app and linked by the extensions (extensions find it via `@executable_path/../../Frameworks` in their runpath search paths).
- **Trap:** linking the same static library into **both** a dynamic framework and the app → two copies in **one process**: "Class X is implemented in both … One of the two will be used. Which one is undefined." Singletons and type checks (`as?`) break subtly. Link each static library into exactly one image per process.

## 8. Versioning, Testing, Documentation & Release

### Q54. How do you version an SDK? `[Fundamental]`
**Semantic Versioning: `MAJOR.MINOR.PATCH`**
| Bump | When | Example |
|---|---|---|
| MAJOR | Breaking API or behavior change, raised minimum OS, removed deprecated APIs | 3.0.0 |
| MINOR | New features, new APIs, deprecations (backward compatible) | 2.4.0 |
| PATCH | Bug fixes only, no API change | 2.3.1 |

- Pre-releases: `3.0.0-beta.1`, `3.0.0-rc.1` (SwiftPM won't pick pre-releases unless asked explicitly).
- Expose the version at runtime (`MySDK.version`) and send it in a request header (`X-MySDK-Version: 2.3.1`) so your backend can see adoption and target fixes.
- Behavior changes count as breaking too (e.g. changing the default timeout from 60 s to 10 s).

### Q55. What should an SDK's CI pipeline do? `[Lead/Expert]`
```
On every PR:
  ├─ Build all platforms/slices (iOS device + simulator, Catalyst, visionOS…)
  ├─ Unit tests + snapshot tests (UI components) on 2 OS versions (oldest supported + latest)
  ├─ Swift 6 strict concurrency; warnings as errors
  ├─ API breakage check vs last release (Q18)
  ├─ Lint: `swift package resolve`, SwiftLint/swift-format, privacy manifest validation
  └─ Size check: sample app size delta vs main branch (fail if > budget)

On release tag:
  ├─ Build XCFramework(s) with BUILD_LIBRARY_FOR_DISTRIBUTION, sign, zip
  ├─ Integration apps build & run UI smoke tests:
  │     SwiftUI app · UIKit app · Objective-C app · Xcode N and N-1
  ├─ Upload artifacts + dSYMs; compute checksum; update Package.swift in the distribution repo; tag
  ├─ Generate DocC documentation; publish
  └─ Publish release notes + changelog; notify clients of breaking changes
```

### Q56. How do you test an SDK? `[Senior]`
- **Unit tests** for internal logic with injected network/storage/clock.
- **Contract tests** against the backend sandbox (request formats, error codes).
- **Integration tests** through the **public API only**: a test target that imports the module without `@testable` catches accidentally internal APIs and awkward usage.
- **Sample/demo app** using the SDK the way clients do, built from the **binary** artifact (not the source) to catch packaging issues (missing resources, wrong `Bundle`, missing symbols).
- **Compatibility**: oldest supported iOS version, latest beta, Objective-C usage, apps with and without app extensions.
- **Concurrency**: Thread Sanitizer runs, Swift 6 strict concurrency.
- **Dogfooding**: internal apps adopt beta versions first.

```swift
import Testing
import MySDK              // no @testable: only what clients can see

@Test func clientCanCreatePaymentWithPublicAPI() async throws {
    let client = try PaymentsClient(configuration: .init(apiKey: "pk_test_123"))
    let payment = try await client.createPayment(amount: Money(amountMinor: 1_000, currencyCode: "USD"))
    #expect(payment.status == .pending)
}
```

### Q57. How should an SDK be documented? `[Fundamental]`
- **Quick start** (≤ 10 minutes to first success): install, configure, one call.
- **Integration guide**: required capabilities, Info.plist keys, permissions, privacy manifest notes, ATT.
- **API reference** generated with **DocC** from `///` comments (`swift package generate-documentation`), hosted for each version.
- **Migration guides** for every major version; **changelog** for every release.
- **Sample app** in the repo; **troubleshooting** page listing common integration errors (Section 9).

```swift
/// Creates a payment for the given amount.
///
/// - Parameter amount: The amount in minor units (cents) and an ISO 4217 currency code.
/// - Returns: A ``Payment`` in the `.pending` state. Observe ``statusUpdates(for:)`` for changes.
/// - Throws: ``PaymentsError/declined(code:message:)`` if the card is declined.

### Q58. How do you roll out SDK changes safely when you can't control when clients update? `[Lead/Expert]`
- Once a client app ships with your SDK, that version runs on users' devices **for years**.
- So:
  - **Remote kill switches / remote config** for risky features (with safe defaults when config can't be fetched).
  - **Server-side compatibility**: the backend must support every SDK version still in use (track by the version header).
  - **Staged adoption**: beta channel, then GA; ask large clients to test release candidates.
  - **Never break the host app**: catch errors at the SDK boundary, degrade features rather than crash.
  - Have a **security patch process**: notify clients, publish a patch for the last few minors, use the server to block vulnerable versions if necessary.

### Q59. How do you support multiple Xcode and Swift versions? `[Senior]`
- Binary SDKs: built with library evolution, a `.swiftinterface` from compiler X can be read by compiler **≥ X**. Build releases with the **oldest Xcode you support** (the newest compilers can import older interfaces, not the reverse).
- But App Store submission requires recent Xcode/SDK versions, and clients move to new Xcodes quickly: test each release on the current Xcode and the latest beta.
- Source SDKs: guard newer language features with `#if compiler(>=6.0)` / `#if swift(>=6.0)` if you must support older toolchains; set `swift-tools-version` to the oldest you support.

### Q60. What does an SDK support policy include? `[Lead/Expert]`
- Supported OS versions, Xcode/Swift versions, platforms, languages (Swift / Objective-C).
- Which SDK versions get **security fixes** and for how long (e.g. last 2 majors for 12 months).
- Deprecation timelines (minimum notice before removal).
- Response times for issues by severity.
- How clients get notified (release notes, email, a status page, deprecation warnings in debug logs).

## 9. Debugging Integration Errors

### Q61. "dyld: Library not loaded: @rpath/MySDK.framework/MySDK". What's wrong? `[Fundamental]`
The app was linked against a **dynamic** framework that isn't present at runtime.
- The framework is set to **Do Not Embed** → change to **Embed & Sign**.
- The runpath is wrong: the app target needs `LD_RUNPATH_SEARCH_PATHS = @executable_path/Frameworks` (default for apps); extensions need `@executable_path/../../Frameworks` to find frameworks embedded in the containing app.
- A framework's own dependency (another dynamic framework) isn't embedded.
- Check: `otool -L MyApp.app/MyApp` (what it expects) and `ls MyApp.app/Frameworks` (what's there).

### Q62. "Undefined symbols for architecture arm64". What are the usual causes? `[Fundamental]`
```
Undefined symbols for architecture arm64:
  "_OBJC_CLASS_$_MSDKClient", referenced from: ...
ld: symbol(s) not found for architecture arm64
```
- The library/framework isn't **linked** at all (missing from "Link Binary With Libraries" / not added as a package product to this target).
- The binary has **no arm64 slice for this platform** (e.g. old framework without arm64-simulator) → check with `lipo -info` / `vtool -show-build`.
- A **system framework** the SDK needs isn't linked (static SDKs need clients to link their system dependencies, unless autolinking covers it: `-Xlinker -no_auto_link` disables it).
- C++ code without linking `libc++`; Swift static library without Swift runtime libs (rare now).
- Symbols declared but compiled out by an `#if` for this configuration.

### Q63. "Building for iOS Simulator, but linking in object file built for iOS". `[Fundamental]`
- A **fat framework** containing only device `arm64` (and maybe `x86_64` simulator) is being used on an **Apple Silicon** simulator. The `arm64` slice is for the device **platform**, not the simulator.
- Old workaround: `EXCLUDED_ARCHS[sdk=iphonesimulator*] = arm64` (forces Rosetta simulator) → slows everything, avoid.
- **Fix:** distribute an **XCFramework** with an `ios-arm64_x86_64-simulator` slice (Q9, Q10).

### Q64. "Module compiled with Swift 6.0 cannot be imported by the Swift 6.2 compiler". `[Senior]`
- The binary framework was built **without** `BUILD_LIBRARY_FOR_DISTRIBUTION`, so it has a compiler-specific `.swiftmodule` only.
- Fix (vendor side): rebuild with `BUILD_LIBRARY_FOR_DISTRIBUTION=YES` so it ships a `.swiftinterface` (Q11).
- Related: **"Failed to build module 'MySDK' from its module interface"**: the interface exists but can't be compiled. Causes: a type named like its module (Q22), a dependency module that isn't available to the client, or an interface emitted with a newer compiler than the client's.

### Q65. "duplicate symbol" errors or "Class X is implemented in both". `[Senior]`
- Two static libraries contain the **same code** (e.g. both vendor the same open-source library) → `duplicate symbol '_OBJC_CLASS_$_Reachability'`.
- `-all_load` pulls in code that would otherwise not be linked, exposing hidden duplicates.
- Runtime warning "Class X is implemented in both A and B": the same Objective-C class exists in two loaded images (static library linked into both an app and a dynamic framework, Q53).
- Fixes: let SwiftPM resolve one shared copy of each dependency; namespace vendored copies (Q28); link each static library into exactly one image.

### Q66. App Store upload fails with "Invalid Bundle… contains disallowed file 'Frameworks'" (ITMS-90206). `[Senior]`
- A **framework or extension contains its own embedded `Frameworks/` folder** (nested frameworks). iOS apps may only embed frameworks in the **app's** `Frameworks/` directory.
- Typical cause: a dynamic framework target has a dependency set to **Embed & Sign** inside the framework target, or an app extension embeds a framework.
- Fix: frameworks and extensions should **link** (Do Not Embed) their dynamic dependencies; only the **app target** embeds them.

### Q67. SDK images/strings/storyboards are `nil` or crash in the client app but work in the demo. `[Senior]`
- Code uses `Bundle.main` (or `UIImage(named:)` without a bundle) instead of the SDK's bundle (Q5).
- Static framework: resources weren't packaged into a resource bundle, or the bundle wasn't copied into the app.
- SwiftPM: resources not declared in `Package.swift`, or code uses `Bundle(for:)` instead of `Bundle.module`.
- Storyboards/XIBs: the `bundle:` parameter or the custom class's **Module** field in Interface Builder is wrong (set "Inherit Module From Target" off and specify the SDK module).
- Asset catalog colors: `Color("Brand", bundle: .mySDK)`.

### Q68. A client reports "unrecognized selector sent to instance" from inside your static SDK. `[Senior]`
- Most likely an **Objective-C category** in a static library whose object file the linker dropped, because nothing referenced it by symbol.
- Fixes: ask clients to add `-ObjC` to Other Linker Flags (Q52), or avoid categories in the SDK / add a dummy referenced symbol in the category's file (a known workaround), or ship a dynamic framework.
- Also possible: a selector name collision with another SDK's category on the same system class (Q37).

## 10. Full SDK Design Problems

> Answer structure for "design an SDK": **clients & constraints → public API → internal architecture → packaging & distribution → privacy & performance → versioning & support**. Show the client's code first: interviewers judge an SDK by how it feels to integrate.

### Q69. Design an analytics SDK. `[Lead/Expert]`
**Constraints**
- Used by thousands of apps; must never crash or slow the host app; works offline; batches to save battery and data; respects consent and ATT; small (< 500 KB added).

**Public API (what the client writes)**
```swift
import Analytics

// App launch
Analytics.configure(.init(writeKey: "wk_live_123"))

// Anywhere, any thread
Analytics.shared.track("checkout_started", properties: ["cart_value": "49.99"])
Analytics.shared.identify(userID: "u_42")          // after login
Analytics.shared.reset()                            // on logout
Analytics.shared.setConsent(.denied)                // stops collection, drops queued events
```

**Internal architecture**
```
Public API (Sendable facade, returns immediately)
      │  AsyncStream (ordered handoff)
      ▼
Event pipeline actor
  ├─ enrich: timestamp, session ID, app version, SDK version, locale (no fingerprinting)
  ├─ consent / sampling filters
  ├─ persistent queue (SQLite or append-only file; capped at e.g. 10,000 events / 5 MB)
  └─ uploader: batch 50–100 events or every 30 s, gzip, URLSession background-capable,
       retry with backoff + jitter, honor 429 Retry-After, drop on 4xx validation errors
Lifecycle observer: flush on willResignActive; resume on launch
Remote config: sampling rate, kill switch, endpoint
```

**Key decisions**
- Thread-safe facade; work off the main thread; ordered handoff (Q34).
- Each event gets a **UUID** so the backend dedupes retried batches (idempotency).
- Bounded storage; oldest events dropped first when full; metrics on drops.
- **Plugin/middleware protocol** so clients can enrich, filter or forward events (to their own destinations) without the SDK depending on other vendors.
- Distribution: static XCFramework via SwiftPM (binary + wrapper target with privacy manifest), signed. Optional `AnalyticsUI` product for automatic screen tracking (opt-in, no swizzling by default).
- Privacy manifest: collected data types (product interaction, device ID if any), tracking domains separated.

### Q70. Design a payments SDK (card entry + Apple Pay + 3-D Secure). `[Lead/Expert]`
**Constraints**
- Card data must **never touch the client's servers** (reduces their PCI scope): the SDK tokenizes card details directly with your API.
- Drop-in UI **and** headless API; SwiftUI + UIKit; Objective-C bridge for older apps and cross-platform wrappers (React Native, Flutter).
- Payment correctness: idempotent requests, no double charges, clear results.

**Public API**
```swift
// Client backend creates a PaymentIntent with the SECRET key and sends its client secret to the app
let client = try PaymentsClient(configuration: .init(apiKey: "pk_live_123"))

// Drop-in UI
let sheet = PaymentSheet(clientSecret: secret, configuration: .init(merchantName: "Shop", applePay: .init(merchantID: "merchant.com.shop")))
let result = await sheet.present(from: viewController)     // .completed, .canceled, .failed(PaymentsError)

// Headless
let method = try await client.createPaymentMethod(card: CardParams(number: n, expMonth: 12, expYear: 2030, cvc: c))
let outcome = try await client.confirmPayment(clientSecret: secret, paymentMethodID: method.id)
```

**Internal architecture & decisions**
- Card fields are **SDK-owned UI components** so raw numbers stay inside the SDK; never logged; memory cleared after tokenization.
- **3-D Secure / bank authentication**: SDK presents a web or native challenge, handles the redirect back via a **return URL** (universal link or custom scheme) the client configures.
- **Idempotency key** generated per confirm attempt and reused on retries (Backend System Design Q63).
- Apple Pay: `PKPaymentAuthorizationController`, merchant ID configured by the client, token sent to your API.
- Certificate pinning **with** a rotation plan (or none, relying on TLS + App Attest); pinning failures must not brick old SDK versions when certificates rotate.
- Separate products: `Payments` (core, headless), `PaymentsUI` (sheet), `PaymentsApplePay`.
- Heavy testing: snapshot tests across Dynamic Type sizes, VoiceOver, RTL; sandbox test cards for every flow.

### Q71. Design an internal feature SDK shared across several company apps (e.g. a "Login & Account" module). `[Lead/Expert]`
**Constraints**
- 4 apps, different teams, different release trains; shared backend; consistent login UX and security; each app has its own branding.

**Decisions**
- **Ownership**: one platform team owns the module, with a public roadmap, SLA for bug fixes, and an RFC process for API changes.
- **API**: headless `AuthService` (token storage in Keychain with an **access group** if apps share login), plus a themable `LoginView`; navigation callbacks instead of the module pushing screens itself.
- **Dependency inversion**: the module defines protocols for analytics, logging and feature flags; each app injects its implementations, so the module doesn't depend on any app's infrastructure.
- **Distribution**: source SwiftPM package in a private repo or registry with semver tags; binary XCFramework only if build times demand it.
- **Compatibility**: CI builds all 4 apps against each release candidate; deprecations follow a 2-release window.
- **Configuration**: per-app config (client ID, scopes, branding) via a configuration struct; remote kill switch for new login methods.

### Q72. Design the package layout for a modular SDK. `[Senior]`
**Goal:** clients take only what they need; internals stay hidden; the core stays small and dependency-free.

```
mysdk-ios/
├── Package.swift
├── Sources/
│   ├── MySDK/              ← product: core, headless API (networking, models, errors), no UI
│   ├── MySDKUI/            ← product: SwiftUI + UIKit components, depends on MySDK
│   ├── MySDKTesting/       ← product: test doubles for clients' unit tests
│   ├── Internal/           ← target only (NOT a product): shared helpers used by the products
│   └── MySDKObjC/          ← optional product: @objc bridge for Objective-C / cross-platform wrappers
├── Tests/
│   ├── MySDKTests/         ← unit tests (@testable)
│   └── PublicAPITests/     ← no @testable: compiles only against the public API (Q56)
├── Examples/DemoApp/       ← sample app depending on the package by local path
└── Plugins/                ← optional: e.g. a command plugin that validates the privacy manifest
```
```swift
products: [
    .library(name: "MySDK", targets: ["MySDK"]),
    .library(name: "MySDKUI", targets: ["MySDKUI"]),
    .library(name: "MySDKTesting", targets: ["MySDKTesting"]),
],
targets: [
    .target(name: "Internal"),                                         // not listed in products → clients can't import it
    .target(name: "MySDK", dependencies: ["Internal"], resources: [.process("Resources")]),
    .target(name: "MySDKUI", dependencies: ["MySDK"], resources: [.process("Resources")]),
    .target(name: "MySDKTesting", dependencies: ["MySDK"]),
    .testTarget(name: "MySDKTests", dependencies: ["MySDK"]),
    .testTarget(name: "PublicAPITests", dependencies: ["MySDK", "MySDKUI"]),
]
```
Decisions to explain:
- **Products are the public contract**; targets are implementation details you can reorganize freely.
- Core has **no third-party dependencies** (Q28); UI is optional so headless clients don't pay for it (or use a package trait, Q30).
- Use the **`package` access modifier** (Swift 5.9, SE-0386) for APIs shared between your own targets but invisible to clients.

```swift
// In Internal: visible to MySDK and MySDKUI (same package), invisible to client apps
package struct RequestSigner {
    package init(secret: Data) { /* ... */ }
    package func sign(_ request: inout URLRequest) { /* ... */ }
}
```
- For closed-source: compile `MySDK` into the XCFramework and keep `MySDKUI` as source on top of it, so clients can read and debug UI code.

## 11. "Spot the Problem" Questions

### Q73. What's wrong with loading this SDK image? `[Fundamental]`
```swift
public final class BrandBadgeView: UIView {
    private let imageView = UIImageView(image: UIImage(named: "badge"))
}
```
**Problem:** `UIImage(named:)` searches the **main app bundle**. In the SDK's demo app (where assets may sit in the app target) it works; in client apps it returns `nil`.

**Fix:** `UIImage(named: "badge", in: .mySDK, compatibleWith: nil)` with a bundle helper that supports dynamic frameworks, static resource bundles and `Bundle.module` (Q5, Q67).

### Q74. What's wrong with this public enum in a binary SDK? `[Senior]`
```swift
@frozen
public enum PaymentMethodType: String, Codable {
    case card, applePay
}
```
**Problems:**
1. `@frozen` promises **no new cases ever**. Adding `.bankTransfer` in 2.4 breaks binary compatibility (clients compiled against 2.3 may switch exhaustively and miscompile/trap).
2. Decoding a server value the SDK doesn't know (`"klarna"`) throws and fails the whole response.

**Fix:** leave it non-frozen (clients handle `@unknown default`), and decode leniently (an `unknown(String)` case or a fallback) so new server values don't break older SDK versions (Q17, Q21).

### Q75. What's wrong with this SDK configuration? `[Senior]`
```swift
public class MySDK {
    public static var apiKey: String = ""
    public static var isDebug = false

    public static func start() {
        let data = try! Data(contentsOf: configURL)                 // read cached config
        let config = try! JSONDecoder().decode(RemoteConfig.self, from: data)
        URLSession.shared.configuration.timeoutIntervalForRequest = 10
        apply(config)
    }
}
```
**Problems:**
1. **Global mutable statics** (`static var`) are data races; Swift 6 rejects them as not concurrency-safe.
2. **`try!` crashes the host app** when the cache file is missing (first launch!) or corrupt.
3. **Synchronous disk I/O** in `start()`, likely called from `application(_:didFinishLaunchingWithOptions:)` on the main thread → slower launch.
4. Tries to change `URLSession.shared` configuration: it has no effect (the configuration is copied), and changing shared global state wouldn't be OK anyway; use your own `URLSession`.
5. Stringly-typed setup with an empty default API key: misuse only fails later at runtime. `public class` (not `final`) allows subclassing you didn't design for.

**Fix:** a `Configuration` struct passed to `configure(_:)` (Q33), validation with a thrown error, defaults when cache is missing, deferred async loading off main (Q50), own `URLSession`, `Sendable` state behind an actor or lock.

### Q76. What's wrong with this Package.swift for a binary SDK? `[Senior]`
```swift
.binaryTarget(
    name: "MySDK",
    url: "https://downloads.example.com/mysdk/latest/MySDK.xcframework.zip",
    checksum: "3f1e…"
)
```
**Problems:**
1. A **`latest`** URL: when you upload a new zip, the checksum no longer matches and **every client build fails** (and builds aren't reproducible).
2. No place for a privacy manifest or dependencies (binary targets can't declare them).

**Fix:** immutable, versioned URLs (`/2.3.0/MySDK.xcframework.zip`), a new tag per release with its checksum, and a wrapper target for resources/dependencies (Q25).

### Q77. What's wrong with this delegate API? `[Senior]`
```swift
public protocol ScannerDelegate {
    func scannerDidFinish(_ result: ScanResult)
    func scannerDidFail(_ error: Error)
    func scannerDidCancel()
}

public final class Scanner {
    public var delegate: ScannerDelegate?
}
```
**Problems:**
1. Delegate is a **strong** reference (protocol isn't `AnyObject`) → typical retain cycle: view controller → scanner → delegate (the view controller).
2. Every method is **required**: adding a method later (e.g. `scannerDidDetectBlur`) is a **breaking change** for every client.
3. No statement of **which thread/actor** callbacks run on; UI clients will update UIKit from a background thread.

**Fix:**
```swift
public protocol ScannerDelegate: AnyObject {
    @MainActor func scannerDidFinish(_ result: ScanResult)
    @MainActor func scannerDidFail(_ error: Error)
    @MainActor func scannerDidCancel()
}
public extension ScannerDelegate {
    func scannerDidCancel() {}            // defaults make future additions non-breaking
}
public final class Scanner {
    public weak var delegate: ScannerDelegate?
}
```

### Q78. What's wrong with exposing this dependency? `[Lead/Expert]`
```swift
import Alamofire

public final class APIClient {
    public let session: Session                  // Alamofire's type in our public API
    public func request(_ url: URLConvertible) async throws -> Data { /* ... */ }
}
```
**Problems:**
1. Alamofire's types are part of your **public API**: clients must import it, are tied to your Alamofire version, and a major Alamofire update becomes a **major** version of your SDK.
2. Conflicts with the client's own Alamofire version (diamond dependency).
3. If the SDK is a binary built with library evolution, Alamofire must also be built for distribution.

**Fix:** `internal import Alamofire` (Q19) behind your own types, or (better for an SDK) drop the dependency and use `URLSession` directly (Q28).

### Q79. What's wrong with this static framework setup? `[Senior]`
App structure: `MyApp` (app) links `CoreKit.framework` (dynamic, embedded). Both `MyApp` and `CoreKit` link `Networking.a` (static).

**Problems:**
1. `Networking` exists **twice in the same process** (once in the app binary, once inside `CoreKit`) → "Class X is implemented in both" warnings, two singletons, type checks failing across the boundary (`as? Networking.Response` fails for an object created by the other copy).
2. Larger binary.

**Fix:** link `Networking` into exactly one image (only `CoreKit`, and the app uses it through `CoreKit`), or make `Networking` dynamic, or merge everything statically (Q53, Q65).

### Q80. What's wrong with this SDK method? `[Senior]`
```swift
public func fetchOffers() -> [Offer] {
    let semaphore = DispatchSemaphore(value: 0)
    var offers: [Offer] = []
    Task {
        offers = (try? await api.offers()) ?? []
        semaphore.signal()
    }
    semaphore.wait()
    return offers
}
```
**Problems:**
1. **Blocks the caller's thread** (often main) for a network round trip → UI hangs, watchdog kills at launch.
2. Can **deadlock** if the `Task` needs the blocked thread/actor (e.g. called on the main actor while `api.offers()` hops to main), and blocking a Swift concurrency thread with a semaphore violates the forward-progress contract.
3. Mutating `offers` from the task is a **data race** (Swift 6 error).
4. Swallows errors: clients can't tell "no offers" from "network failed".

**Fix:** `public func fetchOffers() async throws -> [Offer]`, plus a completion-handler variant for Objective-C (Q20, Q35).

## 12. Senior / Lead Scenario Questions

### Q81. A large client says your SDK added 400 ms to their app launch. What do you do? `[Senior]`
1. **Reproduce** with their setup (SDK version, configuration, device class); measure with the App Launch instrument; look for `+load`/static initializers, synchronous disk/Keychain/network in `configure`, and dynamic framework load time.
2. **Quick mitigation**: guidance to call `configure` after first frame if acceptable; a patch release that defers non-essential work.
3. **Fix**: lazy initialization, background work after launch, static linking, remove initializers (Q49–Q50).
4. **Prevent**: a launch-time budget test in CI on a reference device; signposts in the SDK; document the cost.

### Q82. You need to make a breaking change to a widely used SDK. How do you manage it? `[Lead/Expert]`
- Confirm it's necessary: can it be **additive** (new API alongside old, deprecate the old)?
- If breaking: bundle breaking changes into **one major release** rather than several.
- Ship the new API in a **minor** version first with the old one **deprecated** (`renamed:` fix-its), so clients migrate gradually.
- Publish a **migration guide**, examples, and a timeline; support the previous major with security fixes for a defined period.
- Measure adoption by version header; reach out directly to the largest clients; consider a codemod/script for mechanical changes.

### Q83. Your binary SDK crashes in some client apps but you can't reproduce it. How do you investigate? `[Senior]`
- Get **symbolicated** crash reports: clients need your dSYMs (shipped in the XCFramework) or you symbolicate with your archived dSYMs by binary UUID (Q12).
- Look for patterns: OS version, device, client app, other SDKs present (swizzling conflicts, duplicate classes), app extensions (memory limits), background launch states (protected data unavailable → Keychain/file errors).
- Add **defensive handling** at the crash site and **breadcrumbs** (internal ring-buffer log attached to SDK error reports, with client consent).
- Build a test app that mimics the client's integration: same Xcode version, linker flags, static/dynamic setup, app extensions.

### Q84. Product wants the SDK to auto-collect screen views by swizzling `viewDidAppear`. Your position? `[Lead/Expert]`
- Risks: conflicts with other SDKs swizzling the same method, unexpected behavior in client apps, SwiftUI screens don't map to `UIViewController` lifecycles, hard-to-debug crashes, App Review/trust concerns.
- Proposal: **explicit API** (`Analytics.screen("Checkout")`, a SwiftUI `.trackScreen("Checkout")` modifier); offer swizzling-based auto-tracking only as an **opt-in** feature with a clear off switch, implemented carefully (call the original implementation, swizzle once, document it).
- Decide with data: what percentage of clients actually need auto-tracking vs reliability complaints.

### Q85. Your team maintains 15 internal Swift packages used by 3 apps, and builds are slow. What do you change? `[Lead/Expert]`
- **Measure first**: Xcode build timeline, `-Xfrontend -warn-long-function-bodies`, which modules rebuild on small changes.
- Reduce coupling: interface modules (protocols) separate from implementation modules, so a change in an implementation doesn't rebuild every dependent.
- Use **binary caching** for stable, rarely changing modules (prebuilt XCFrameworks from CI, or a remote build cache with Bazel/Tuist).
- Use dynamic or **mergeable** libraries in Debug to shorten link times.
- Remove unused dependencies; avoid "umbrella" modules everything depends on.
- Try explicitly built modules (`SWIFT_ENABLE_EXPLICIT_MODULES`) for more parallel, cacheable module builds, and keep package dependency graphs shallow.

### Q86. A client asks for your SDK's source code "to audit it" but your company ships a closed binary. How do you respond? `[Senior]`
- Understand the need: security review, compliance (privacy, PCI), debugging, or supply-chain policy.
- Options: source access under NDA/escrow for enterprise clients; publish a **source-available public API layer** with the binary core; provide the privacy manifest, data-flow documentation, third-party security audit reports, signed binaries with published checksums, SBOM (software bill of materials), and dSYMs.
- Escalate the commercial decision to product/legal, with a recommendation.

## 13. Last-Day Cheat Sheet

### Formats
| Format | What | Remember |
|---|---|---|
| `.a` | Static library | Code copied into the app at link time; no resources |
| `.dylib` | Dynamic library | Loaded by dyld at launch; not allowed standalone in iOS apps except inside frameworks/system |
| `.framework` | Bundle: binary + headers + modules + resources | Static or dynamic |
| `.xcframework` | One framework/library per platform variant | Fixes device-arm64 vs simulator-arm64; Xcode picks the slice |
| Swift package | Source (or `binaryTarget`) | `Bundle.module` for resources; tags = versions |

### Static vs dynamic in one line
Static = faster launch, dead-code stripping, no resources, duplicated per binary. Dynamic = shared by app + extensions, launch cost per framework, must be **Embed & Sign**. Mergeable = dynamic in Debug, static-like in Release.

### Building a distributable binary
```
xcodebuild archive (per platform) SKIP_INSTALL=NO BUILD_LIBRARY_FOR_DISTRIBUTION=YES
→ xcodebuild -create-xcframework -archive … -framework …
→ codesign the .xcframework → zip → swift package compute-checksum → versioned URL
```

### Swift stability
| | Gives you |
|---|---|
| ABI stability (5.0) | Swift runtime in the OS; binaries interoperate at runtime |
| Module stability (5.1) | `.swiftinterface`: newer compilers can import your binary |
| Library evolution | Add properties/cases/methods without breaking compiled clients |
| `@frozen` / `@inlinable` | Speed in exchange for promises you can never break |
| `internal import` (Swift 6) | Hide implementation dependencies from your public API |

### Swift Package Manager
- Source package, or `binaryTarget(url:checksum:)` + a thin wrapper target (privacy manifest, resources, dependencies).
- Products = public contract; non-product targets + the `package` modifier for internals.
- Clients use `from:` ranges; apps commit `Package.resolved`; CI uses `-onlyUsePackageVersionsFromResolvedFile`.
- Versioned, immutable artifact URLs; a separate distribution repo for closed-source SDKs.
- Private sharing: local packages (monorepo), private Git repos, or a package registry.
- CocoaPods is legacy (trunk read-only from 2 Dec 2026); the answer is "migrate to SwiftPM".

### Public API checklist
- [ ] Minimal `public` surface; specific type names; `@objc` names prefixed
- [ ] Configuration struct + `configure` that is cheap and doesn't throw away errors
- [ ] `Sendable` types, documented callback threads, `@MainActor` UI
- [ ] `async` first + completion/Objective-C bridge if needed
- [ ] Public error enum with retryable vs definitive cases
- [ ] Non-frozen enums, delegate methods with defaults, deprecations with `renamed:`
- [ ] No crashes, no main-thread blocking, no swizzling by default, no global state changes
- [ ] Own bundle for resources; own `URLSession`; prefixed defaults/Keychain keys
- [ ] Privacy manifest (only the SDK's practices) + signature for binaries
- [ ] Test doubles/protocols for clients; sample app built from the binary

### Error → cause
| Error | Likely cause |
|---|---|
| `Library not loaded: @rpath/…` | Dynamic framework not embedded / wrong runpath |
| `Undefined symbols for architecture arm64` | Not linked / missing slice / missing system framework |
| `Building for iOS Simulator, but linking in object file built for iOS` | Fat framework; use an XCFramework |
| `Module compiled with Swift X cannot be imported by Swift Y` | Built without `BUILD_LIBRARY_FOR_DISTRIBUTION` |
| `Failed to build module from its module interface` | Module/type name clash, missing dependency |
| `duplicate symbol` / `Class X is implemented in both` | Same static code linked twice |
| `unrecognized selector` from a static SDK | Category dropped by linker → `-ObjC` |
| ITMS-90206 `disallowed file 'Frameworks'` | Nested frameworks; only the app embeds |
| ITMS-91061 / ITMS-91053 | Missing SDK privacy manifest / missing required-reason declaration |
| Resources `nil` in client app | `Bundle.main` used instead of SDK bundle |

### Phrases that show seniority
- "Every `public` symbol is a promise; I start internal and open up deliberately."
- "The SDK must never crash or slow the host app; errors stop at our boundary."
- "Binary SDKs need library evolution, a signed XCFramework, dSYMs and a privacy manifest."
- "I avoid third-party dependencies in an SDK, because our dependency becomes the client's conflict."
- "Additive changes in minors, deprecate with fix-its, remove only in majors."
- "Once a version ships inside a client app, it lives on devices for years, so the backend and kill switches must account for it."
