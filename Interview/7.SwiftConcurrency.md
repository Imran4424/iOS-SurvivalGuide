## 1. Fundamentals: Data Races & Isolation

### Q1. What does "Swift Concurrency" include beyond async/await? `[Fundamental]`
**Key points:**
- **async/await and tasks**: writing and running asynchronous code (covered in the Async/Await file).
- **Actors**: reference types that protect their mutable state from concurrent access.
- **Global actors**, especially `@MainActor`: isolating code to a shared executor such as the main thread.
- **`Sendable`**: marking types that are safe to share across concurrency domains.
- **Compile-time data-race checking**: in Swift 6 mode, the compiler rejects code that could race.
- Together they form Swift's **data-race safety** model: the compiler proves that mutable state is never accessed concurrently without protection.

### Q2. What is a data race? `[Fundamental]`
**Key points:**
- Two or more threads access the **same memory** at the same time, at least one access is a **write**, and there's **no synchronization**.
- Results are undefined: corrupted values, crashes (e.g. `EXC_BAD_ACCESS` when a dictionary or array is mutated concurrently), and bugs that appear only under load.

```swift
final class Counter {
    var value = 0
}

let counter = Counter()
DispatchQueue.concurrentPerform(iterations: 1_000) { _ in
    counter.value += 1      // ❌ data race: unsynchronized concurrent writes
}
print(counter.value)        // often less than 1000, sometimes a crash
```

### Q3. What is the difference between a data race and a race condition? `[Senior]`
**Key points:**
- **Data race**: unsynchronized concurrent memory access (a low-level memory-safety problem). Swift 6 **prevents these at compile time**.
- **Race condition**: the program's correctness depends on the **timing or ordering** of events (a logic problem). Swift 6 does **not** prevent these.
- Example: an actor method that checks a balance, awaits a fraud check, then subtracts. There's no data race (the actor serializes access), but a **race condition** exists because another withdrawal can run during the `await` (see Q23).
- Interview phrase: **"Swift 6 makes data races impossible, not logic races."**

### Q4. What is an isolation domain? `[Senior]`
**Key points:**
- A region of code whose mutable state is protected by a single mechanism, so only one piece of code can access it at a time:
  - **The main actor** (`@MainActor` code and data).
  - **Each actor instance** (its own state).
  - **Other global actors** (custom `@globalActor`s).
  - **Nonisolated** code, which can't touch any isolated mutable state directly.
  - **Task-isolated / disconnected regions** for non-`Sendable` values owned by a single task (Section 6).
- Crossing from one domain to another requires `await` (a possible hop), and values crossing must be `Sendable` (or safely transferred with `sending`).

### Q5. How does Swift prevent data races at compile time? `[Senior]`
**Key points:**
Two complementary rules:
1. **Isolation**: mutable state belongs to an isolation domain (an actor, the main actor). Code outside that domain must `await` to access it, and the domain runs one piece of code at a time.
2. **`Sendable` checking**: only values that are safe to share (`Sendable`) can cross between domains. Non-`Sendable` values can cross only if the compiler can prove the sender no longer uses them (region-based isolation, `sending`).
- If both rules hold everywhere, no two domains can ever touch the same mutable memory concurrently.

### Q6. Why did Swift introduce actors instead of relying on locks and serial queues? `[Senior]`
**Key points:**
- Locks and queues work, but **the compiler can't verify** that you used them correctly: it's easy to forget a lock, lock the wrong one, or deadlock.
- Actors make protection **part of the type**: the compiler forces every external access to go through the actor (`await`), so forgetting to synchronize becomes a compile error.
- Actors integrate with async/await: callers **suspend** instead of blocking threads while waiting for the actor.
- Locks still have a place for small, synchronous critical sections (Section 12).

### Q7. What does "crossing an isolation boundary" mean? `[Fundamental]`
**Key points:**
- Calling into, or passing a value to, a different isolation domain: main actor → actor, actor → nonisolated async function, one actor → another.
- Consequences: the call must be `await`ed (it may hop executors), and arguments/results must be `Sendable` or transferable.

```swift
@MainActor
func showStats(using store: StatsStore) async {
    let stats = await store.currentStats()   // crossing main actor → StatsStore actor
    statsLabel.text = stats.summary          // back on the main actor
}
```

### Q8. How does Swift's approach compare with GCD-based thread safety? `[Senior]`
| | GCD + locks | Swift Concurrency |
|---|---|---|
| Protection | By convention (developer remembers the queue/lock) | By type (compiler-enforced isolation) |
| Waiting | Blocks threads (`sync`, `lock()`) | Suspends (`await`), threads stay free |
| Verification | Runtime only (Thread Sanitizer, crashes) | Compile time (Swift 6 mode) |
| Deadlocks | Possible (`sync` on own queue, lock ordering) | Actors are reentrant, so actor-to-actor deadlocks are avoided |
| Logic races | Possible | Still possible (reentrancy) |

## 2. Actors

### Q9. What is an actor? `[Fundamental]`
**Key points:**
- A **reference type** that protects its mutable state by ensuring only **one task at a time** runs code isolated to it.
- From outside, you access its isolated members with `await`; inside, access is synchronous.
- Actors are implicitly `Sendable`, so they can be shared freely across tasks.

```swift
actor BankAccount {
    let accountNumber: String
    private(set) var balance: Decimal

    init(accountNumber: String, balance: Decimal) {
        self.accountNumber = accountNumber
        self.balance = balance
    }

    func deposit(_ amount: Decimal) {
        balance += amount            // synchronous inside the actor
    }

    func withdraw(_ amount: Decimal) throws {
        guard balance >= amount else { throw BankError.insufficientFunds }
        balance -= amount
    }
}

enum BankError: Error { case insufficientFunds }

// Outside the actor
let account = BankAccount(accountNumber: "123", balance: 100)
await account.deposit(50)                    // await: may wait for the actor
let balance = await account.balance          // reading isolated state also needs await
print(account.accountNumber)                 // immutable Sendable `let`: no await needed (same module)
```

### Q10. Why do you need `await` to access an actor from outside? `[Fundamental]`
**Key points:**
- The actor may be busy running another task's code. `await` lets the caller **suspend** until the actor is free, instead of blocking a thread.
- Even a synchronous actor method becomes "implicitly async" when called from outside.

### Q11. Compare actors, classes, and structs. `[Senior]`
| | `struct` | `class` | `actor` |
|---|---|---|---|
| Semantics | Value (copied) | Reference (shared) | Reference (shared) |
| Thread safety | Each copy is independent | None by default | Built in: serialized access |
| `Sendable` | Implicitly, if all members are | Only if final + immutable (or manually synchronized) | Always |
| Inheritance | No | Yes | No |
| External access | Direct | Direct | `await` for isolated members |
| Best for | Data/models | Identity, UIKit, `@MainActor` UI state | Shared mutable state across tasks |

### Q12. What can be accessed on an actor without `await`? `[Senior]`
**Key points:**
- **Immutable `let` properties of `Sendable` types**: they can never change, so reading them is safe (synchronous access within the same module).
- Members marked **`nonisolated`**: they can't touch the actor's mutable state, so they don't need isolation.

```swift
actor UserSession {
    let userID: UUID                         // immutable + Sendable: readable without await
    private var authToken: String

    init(userID: UUID, authToken: String) {
        self.userID = userID
        self.authToken = authToken
    }

    nonisolated var debugIdentifier: String {
        "Session(\(userID))"                 // only uses immutable state
    }

    func token() -> String { authToken }     // isolated: requires await from outside
}
```

### Q13. How do actor initializers and `deinit` work? `[Lead/Expert]`
**Key points:**
- Actor initializers can set stored properties synchronously. Once `self` is fully initialized, an async initializer can call isolated methods; a synchronous initializer is nonisolated and shouldn't let `self` escape to other tasks before initialization finishes.
- An actor's `deinit` runs when the last reference goes away. It can read the actor's stored properties (nobody else can reference the actor at that point), but it can't call isolated async methods or `await`.
- For **global-actor-isolated classes** (e.g. `@MainActor` view controllers), Swift 6 doesn't let a normal `deinit` touch isolated state; Swift 6.2 adds **`isolated deinit`** (Q97).

### Q14. How does an actor conform to a protocol with synchronous requirements? `[Senior]`
**Key points:**
- A synchronous protocol requirement can be called from any context, so an actor can't satisfy it with an isolated method. Options:
  - Implement it as `nonisolated`, using only immutable state.
  - Make the protocol requirement `async` (then an isolated method can satisfy it).

```swift
actor DownloadTask: CustomStringConvertible, Hashable {
    let id: UUID
    private var progress = 0.0

    init(id: UUID) { self.id = id }

    // Synchronous requirements implemented as nonisolated, using only immutable state
    nonisolated var description: String { "DownloadTask(\(id))" }

    static func == (lhs: DownloadTask, rhs: DownloadTask) -> Bool { lhs.id == rhs.id }   // static members aren't instance-isolated
    nonisolated func hash(into hasher: inout Hasher) { hasher.combine(id) }
}

protocol ProgressReporting {
    func currentProgress() async -> Double      // async requirement
}

extension DownloadTask: ProgressReporting {
    func currentProgress() -> Double { progress }   // isolated method satisfies the async requirement
}
```

### Q15. Can actors inherit from other actors or classes? `[Fundamental]`
**Key points:**
- No. Actors don't support inheritance (and can't subclass `NSObject`). Share behavior through **protocols** and protocol extensions (including the `Actor` protocol), or composition.

### Q16. Does an actor run on a dedicated thread? `[Senior]`
**Key points:**
- No. By default an actor has a **serial executor** that runs its jobs one at a time on threads from the shared cooperative pool. Consecutive jobs for the same actor may run on **different threads**.
- Exceptions: the main actor runs on the main thread; an actor with a **custom executor** (e.g. backed by a `DispatchSerialQueue`) runs where that executor runs (Q108).
- Think "one task at a time," not "one thread."

### Q17. Do actors process calls in the order they were made? `[Lead/Expert]`
**Key points:**
- Calls made **sequentially from one task** are processed in order (each `await` completes before the next call starts).
- Calls from **different tasks** have **no guaranteed order**: the runtime schedules actor jobs with priorities, and higher-priority work may run first. Actors are not FIFO queues.
- If strict ordering matters (e.g. ordered log writes), funnel work through a single task, such as an `AsyncStream` consumer (Q121).

### Q18. Does an actor need `await` to call its own methods or another instance of the same actor type? `[Senior]`
**Key points:**
- Calling its **own** isolated members: no `await` (same isolation domain).
- Accessing **another instance** of the same actor type: `await` is required, because isolation is **per instance**.

```swift
actor Account {
    var balance: Decimal = 0

    func transfer(_ amount: Decimal, to other: Account) async {
        balance -= amount                 // own state: synchronous
        await other.deposit(amount)       // different instance: different isolation domain
    }

    func deposit(_ amount: Decimal) { balance += amount }
}
```

### Q19. What does an actor hop cost, and how do you design actor APIs to minimize hops? `[Lead/Expert]`
**Key points:**
- Each cross-actor call may involve a context switch and scheduling. Cheap, but not free, and many tiny calls add up (and add suspension points that create reentrancy windows).
- Design **coarse-grained** actor methods that do a whole unit of work in one call, rather than chatty getters and setters.

```swift
// ❌ Chatty: three hops and two reentrancy windows
let items = await cart.items
let discount = await cart.discount
await cart.setTotal(items.reduce(0) { $0 + $1.price } - discount)

// ✅ One hop, atomic from the caller's perspective
await cart.recalculateTotal()
```

### Q20. Should every shared object be an actor? `[Lead/Expert]`
**Key points:**
- No. Actors force callers to be async, add hops, and introduce reentrancy.
- Prefer:
  - **Value types** for data (immutable, `Sendable`).
  - **`@MainActor`** for UI-related state (most app state is read and written by the UI anyway).
  - **Actors** for genuinely shared mutable state accessed from multiple concurrent tasks (caches, network coordination, file I/O, sync engines).
  - **`Mutex`/locks** for tiny synchronous critical sections that must be callable without `await` (Section 12).
- Anti-pattern: "an actor for every service" in an app where all callers are on the main actor anyway.

## 3. Actor Reentrancy

### Q21. What is actor reentrancy? `[Senior]`
**Key points:**
- When an actor method hits an `await`, it **suspends** and the actor becomes free to run **other** calls (including another call to the same method) before the first one resumes.
- Code between suspension points runs atomically, but **state may change across any `await`** inside an actor.

```
withdraw(80) starts  ── checks balance (100 ≥ 80 ✓) ── await fraudCheck ──┐
                                                                            │  actor is free:
withdraw(50) starts  ── checks balance (100 ≥ 50 ✓) ── await fraudCheck ──┤  both checks passed
                                                                            │
withdraw(80) resumes ── balance = 20                                        │
withdraw(50) resumes ── balance = -30   ❌ overdrawn                         ┘
```

### Q22. Why are actors reentrant instead of blocking other calls during an `await`? `[Lead/Expert]`
**Key points:**
- Non-reentrant actors would hold the actor while waiting, which causes **deadlocks** (actor A awaits B while B awaits A) and poor throughput (the actor sits idle during long network calls).
- Reentrancy avoids deadlocks and keeps actors responsive, at the cost of requiring developers to reason about state changes across suspension points.

### Q23. Show a reentrancy bug and how to fix it. `[Senior]`
```swift
actor BankAccount {
    private(set) var balance: Decimal
    private let fraudService: FraudService

    init(balance: Decimal, fraudService: FraudService) {
        self.balance = balance
        self.fraudService = fraudService
    }

    // ❌ Bug: the check happens before the suspension point and isn't re-validated
    func withdrawBuggy(_ amount: Decimal) async throws {
        guard balance >= amount else { throw BankError.insufficientFunds }
        try await fraudService.verify(amount)    // other withdrawals can run here
        balance -= amount                         // balance may now be insufficient
    }

    // ✅ Fix 1: do the async work first, then check and mutate with no await in between
    func withdraw(_ amount: Decimal) async throws {
        try await fraudService.verify(amount)
        guard balance >= amount else { throw BankError.insufficientFunds }
        balance -= amount
    }

    // ✅ Fix 2: reserve the funds before suspending, roll back on failure
    func withdrawReserving(_ amount: Decimal) async throws {
        guard balance >= amount else { throw BankError.insufficientFunds }
        balance -= amount                         // reserve synchronously
        do {
            try await fraudService.verify(amount)
        } catch {
            balance += amount                     // compensate if verification fails
            throw error
        }
    }
}
```

### Q24. How do you prevent duplicate work caused by reentrancy (e.g. two identical downloads)? `[Senior]`
**Key points:**
- Record the in-flight work **before** the first `await`, typically by storing a `Task` that later callers can await.

```swift
actor ProfileCache {
    private var profiles: [User.ID: Profile] = [:]
    private var inFlight: [User.ID: Task<Profile, Error>] = [:]

    func profile(for id: User.ID, using api: ProfileAPI) async throws -> Profile {
        if let cached = profiles[id] { return cached }
        if let task = inFlight[id] { return try await task.value }   // join existing work

        let task = Task { try await api.fetchProfile(id: id) }
        inFlight[id] = task                       // registered before suspending
        defer { inFlight[id] = nil }

        let profile = try await task.value
        profiles[id] = profile
        return profile
    }
}
```
- Without the `inFlight` dictionary, two calls for the same ID would both miss the cache, both suspend on the network, and both download.

### Q25. What are the rules of thumb for writing reentrancy-safe actor code? `[Senior]`
**Key points:**
- Treat **every `await` inside an actor** as a point where any isolated state may have changed.
- Keep **check-and-mutate** sequences synchronous (no `await` between reading state and writing based on it).
- **Re-validate** assumptions after an `await` (re-read state; don't use values read before suspending).
- Record "work in progress" (tasks, flags, reservations) **before** suspending.
- Prefer small synchronous actor methods plus async orchestration outside, or do all async work first and then apply results in one synchronous step.

### Q26. Can you make an actor non-reentrant? `[Lead/Expert]`
**Key points:**
- There's no built-in non-reentrant actor. Options when you need strict one-at-a-time processing of async operations:
  - Chain operations: store the previous `Task` and make each new task await it before starting.
  - Use an `AsyncStream` as a work queue consumed by a single task (Q121).
  - Use explicit state (e.g. `enum State { idle, running }`) and reject or queue calls while running.

```swift
actor OperationChain {
    private var lastTask: Task<Void, Never>?

    func enqueue(_ operation: @escaping @Sendable () async -> Void) {
        let previous = lastTask
        lastTask = Task {
            await previous?.value      // wait for everything submitted before
            await operation()
        }
    }
}
```

### Q27. How do you perform an atomic operation across two actors (e.g. transferring money)? `[Lead/Expert]`
**Key points:**
- You **can't** hold two actors at once. A function can be isolated to at most one actor, so any change to the second actor happens after a hop, and other code may run in between.
- Options:
  - **Restructure** so one actor owns all the related state (a `Bank` actor owning all accounts).
  - **Compensating actions**: withdraw from A, deposit to B; if the deposit fails, refund A (a saga pattern).
  - **Persist in a transactional store** (database transactions) and let the store guarantee atomicity.

```swift
actor Bank {
    private var balances: [AccountID: Decimal] = [:]

    func transfer(_ amount: Decimal, from source: AccountID, to destination: AccountID) throws {
        guard let sourceBalance = balances[source], sourceBalance >= amount else {
            throw BankError.insufficientFunds
        }
        balances[source] = sourceBalance - amount          // both changes happen
        balances[destination, default: 0] += amount        // in one synchronous step
    }
}
```

## 4. The Main Actor & Global Actors

### Q28. What is `@MainActor`? `[Fundamental]`
**Key points:**
- A **global actor** whose executor is the **main thread**. Code and state marked `@MainActor` can only be accessed on the main actor, and the compiler enforces it.
- It replaces "remember to dispatch to the main queue" with a compile-time guarantee for UI code.

```swift
@MainActor
final class ProfileViewModel {
    private(set) var name = ""

    func load(using api: ProfileAPI) async {
        let profile = try? await api.fetchProfile()   // network work happens elsewhere; main thread is free
        name = profile?.name ?? ""                    // guaranteed main actor: safe UI state update
    }
}
```

### Q29. Where can you apply `@MainActor`? `[Fundamental]`
```swift
@MainActor final class SettingsViewModel { }       // whole type: all members isolated

final class ImageCacheMonitor {
    @MainActor var statusText = ""                   // a single property
    @MainActor func refreshBadge() { }               // a single method
}

@MainActor protocol Screen { func render() }         // protocol: conformers' requirements are main-actor

let onUpdate: @MainActor (Int) -> Void = { count in  // closure type
    badgeLabel.text = "\(count)"
}

Task { @MainActor in                                  // task body
    spinner.stopAnimating()
}

@MainActor var currentTheme = Theme.light            // global variable
```

### Q30. Which SDK types are `@MainActor`? `[Senior]`
**Key points:**
- `UIView`, `UIViewController`, `UIApplication`, and most of UIKit/AppKit.
- SwiftUI's `View` protocol (iOS 18 SDK onward), `App`, and `Scene`; many environment actions.
- Types conforming to or subclassing them inherit main-actor isolation. Your `UIViewController` subclass is `@MainActor` automatically.

### Q31. How do you call `@MainActor` code from nonisolated code? `[Fundamental]`
```swift
// From an async nonisolated context: await (hops to main)
func refresh(viewModel: ProfileViewModel, api: ProfileAPI) async {
    await viewModel.load(using: api)
}

// From synchronous nonisolated code: start a main-actor task
func didReceiveNotification() {
    Task { @MainActor in
        badgeView.update()
    }
}

// From async code, run a block on the main actor
await MainActor.run {
    progressView.isHidden = true
}
```

### Q32. How do you keep heavy work off the main actor inside a `@MainActor` type? `[Senior]`
**Key points:**
- Move the heavy work into a `nonisolated` (or `@concurrent`, in Swift 6.2) async function, another actor, or a separate service, and apply results back on the main actor.

```swift
@MainActor
final class ReportViewModel {
    private(set) var report: Report?

    func generate(from entries: [Entry]) async {
        report = await Self.buildReport(from: entries)    // heavy work off the main actor
    }

    @concurrent                                          // Swift 6.2: always runs on the concurrent pool
    nonisolated private static func buildReport(from entries: [Entry]) async -> Report {
        Report(entries: entries)                         // CPU-heavy; Entry and Report are Sendable
    }
}
```
- Before Swift 6.2 (or without the `NonisolatedNonsendingByDefault` feature), a plain `nonisolated` async function already ran off the main actor.

### Q33. When do you use `@MainActor` functions, `MainActor.run`, or `Task { @MainActor in }`? `[Senior]`
| Approach | Use when |
|---|---|
| `@MainActor` on the type/function | Default: the code always belongs on the main actor (compile-time guarantee for every caller) |
| `await MainActor.run { }` | You're in nonisolated async code and need a short main-actor section, then continue |
| `Task { @MainActor in }` | You're in synchronous code (e.g. a callback) and need to schedule main-actor work |
| `MainActor.assumeIsolated { }` | You **know** you're already on the main thread (e.g. a delegate documented to call back on main) but the compiler doesn't |

- Overusing `MainActor.run` is often a sign that types should simply be annotated `@MainActor`.

### Q34. How is global actor isolation inferred? `[Lead/Expert]`
**Key points:**
- **Subclasses** of `@MainActor` classes are `@MainActor`.
- Types conforming to a `@MainActor` protocol **in the type's primary declaration** are inferred `@MainActor` (conformances added in extensions affect only that extension's members).
- **Overrides** and protocol witnesses inherit isolation from what they override/implement.
- Swift 6 **removed** inference from property wrappers: a type is no longer implicitly `@MainActor` just because it uses `@StateObject` or `@ObservedObject` (a common migration surprise in SwiftUI code before `View` itself became `@MainActor`).
- With Swift 6.2 default isolation set to `MainActor`, everything in the module is `@MainActor` unless marked otherwise (Q94).

### Q35. How and when do you create a custom global actor? `[Lead/Expert]`
```swift
@globalActor
actor DatabaseActor {
    static let shared = DatabaseActor()
}

@DatabaseActor
final class LocalStore {
    private var connection = SQLiteConnection()

    func save(_ record: Record) throws { try connection.insert(record) }
    func records() throws -> [Record] { try connection.selectAll() }
}

@DatabaseActor
func runMigrations(on store: LocalStore) throws {
    // synchronous access: same global actor
}
```
**When to use:**
- Several types and free functions must share **one** isolation domain (e.g. everything touching a non-thread-safe database connection, or an SDK that requires serialized access).
- If only one type needs protection, a plain `actor` is simpler. Don't create global actors casually; each one is another domain that callers must hop to.

### Q36. Is `@MainActor` the same as `DispatchQueue.main.async`? `[Senior]`
**Key points:**
- Both run code on the main thread, but:
  - `@MainActor` is checked **at compile time**: callers must be on the main actor or `await`.
  - `DispatchQueue.main.async` is a runtime convention; nothing stops you from touching UI state off the main thread elsewhere.
  - Code already on the main actor calling a `@MainActor` function runs **synchronously**, whereas `DispatchQueue.main.async` always defers to a later run loop iteration.
- In Swift 6 code, prefer `@MainActor` isolation over manual dispatch.

### Q37. What are `@MainActor` closure types, and when are they useful? `[Lead/Expert]`
```swift
final class DownloadController {
    // The callback is guaranteed to be called on the main actor
    var onProgress: (@MainActor (Double) -> Void)?

    func reportProgress(_ value: Double) async {
        await onProgress?(value)          // calling it from nonisolated code requires await
    }
}

// The caller can touch UI directly inside the closure
controller.onProgress = { progress in
    progressView.progress = Float(progress)
}
```
- Annotating callback types documents and enforces the thread they run on, replacing comments like "always called on the main queue."

### Q38. Should view models be `@MainActor`? `[Senior]`
**Key points:**
- Usually **yes**. View models hold UI state read by views (which are `@MainActor`), and most of their mutations come from UI events.
- Benefits: no data races on UI state, no manual dispatching, simpler tests (mark tests `@MainActor`).
- Keep heavy work off the main actor by calling `async` services (network, database actors) or `@concurrent` helpers. Awaiting them doesn't block the main thread.

## 5. `Sendable`

### Q39. What is `Sendable`? `[Fundamental]`
**Key points:**
- A marker protocol meaning **"values of this type can be safely shared across isolation domains"** (passed between tasks, actors, or the main actor) without causing data races.
- It has no methods; the compiler **checks** conformance based on the type's structure.
- Values crossing isolation boundaries (actor method arguments and results, `Task.detached` captures, `@Sendable` closure captures) must be `Sendable` (or safely transferred, Section 6).

### Q40. Which types are implicitly `Sendable`? `[Senior]`
**Key points:**
- Value types (`struct`, `enum`, tuples) whose stored properties / associated values are all `Sendable`: for non-public types, conformance is **inferred** automatically.
- Standard library basics: `Int`, `String`, `Bool`, `Double`, `Array`/`Dictionary`/`Set`/`Optional` of `Sendable` elements, `Date`, `URL`, `UUID`, `Data`.
- **Actors** (always).
- **Global-actor-isolated classes** (e.g. `@MainActor final class`): safe because all access is serialized on that actor.
- Metatypes and `@Sendable` function types.

```swift
struct User {                      // inferred Sendable (internal type, Sendable members)
    let id: UUID
    var name: String
}

enum LoadState {                   // inferred Sendable
    case idle
    case loaded([User])
    case failed(String)
}

@MainActor
final class ProfileViewModel { }   // Sendable because it's main-actor isolated
```

### Q41. Do public types get implicit `Sendable` conformance? `[Lead/Expert]`
**Key points:**
- No. For **public** (non-frozen) structs and enums, the compiler doesn't infer `Sendable`, because doing so would make it part of your API contract implicitly. You must declare it explicitly.
- Adding `Sendable` to a public type is an API promise: removing it later is a source-breaking change for clients. Only declare it when the type will remain safe to share.

```swift
public struct Coordinate: Sendable {     // explicit for public types
    public let latitude: Double
    public let longitude: Double
}
```

### Q42. How can a class be `Sendable`? `[Senior]`
**Key points:**
- A class can conform to `Sendable` (checked by the compiler) if it's **`final`** and all stored properties are **immutable `let`s of `Sendable` types**.
- Otherwise, it can be made safe by isolating it to a global actor, by internal synchronization with `Mutex`-wrapped state, or (as a last resort) `@unchecked Sendable`.

```swift
final class APIConfiguration: Sendable {
    let baseURL: URL
    let timeout: Duration
    let defaultHeaders: [String: String]

    init(baseURL: URL, timeout: Duration, defaultHeaders: [String: String]) {
        self.baseURL = baseURL
        self.timeout = timeout
        self.defaultHeaders = defaultHeaders
    }
}

// ❌ Error: stored property 'retryCount' of 'Sendable'-conforming class is mutable
final class RetryPolicy: Sendable {
    var retryCount = 3
}
```

### Q43. What is `@unchecked Sendable`, and when is it acceptable? `[Lead/Expert]`
**Key points:**
- Tells the compiler "trust me, this type is thread-safe" and **disables checking**. If you're wrong, you get real data races with no compiler help.
- Acceptable when the type is genuinely synchronized internally in a way the compiler can't verify (e.g. a lock-protected class on an OS version without `Mutex`, or a wrapper around a thread-safe C library), and that safety is documented and reviewed.
- Prefer, in order: value types → actors / `@MainActor` → `Mutex`-wrapped state (checked `Sendable`) → `@unchecked Sendable`.

```swift
// Acceptable: all mutable state is protected by the lock
final class LegacyCache: @unchecked Sendable {
    private let lock = NSLock()
    private var storage: [String: Data] = [:]

    func value(for key: String) -> Data? {
        lock.withLock { storage[key] }
    }

    func setValue(_ data: Data, for key: String) {
        lock.withLock { storage[key] = data }
    }
}

// ✅ Better on iOS 18+: Mutex makes the class checked-Sendable with no "unchecked"
import Synchronization

final class ModernCache: Sendable {
    private let storage = Mutex<[String: Data]>([:])

    func value(for key: String) -> Data? { storage.withLock { $0[key] } }
    func setValue(_ data: Data, for key: String) { storage.withLock { $0[key] = data } }
}
```

### Q44. How do you make a generic type conditionally `Sendable`? `[Senior]`
```swift
struct Page<Item> {
    let items: [Item]
    let nextCursor: String?
}

extension Page: Sendable where Item: Sendable {}   // Sendable only when its contents are

enum Loadable<Value> {
    case loading
    case loaded(Value)
    case failed(any Error)
}

extension Loadable: Sendable where Value: Sendable {}
```

### Q45. Do error types need to be `Sendable`? `[Senior]`
**Key points:**
- Yes. The `Error` protocol **refines `Sendable`**, because errors routinely cross isolation boundaries (thrown from an actor to the main actor, rethrown from tasks).
- Error enums and structs with `Sendable` payloads conform automatically. Error **classes** must satisfy `Sendable` rules (final and immutable, or synchronized), and errors carrying non-`Sendable` payloads (e.g. an `NSManagedObject`) produce warnings or errors.

### Q46. How do you handle non-`Sendable` types from the SDK or third-party libraries? `[Lead/Expert]`
**Key points:**
- Don't share them across domains. Instead:
  - Keep them **inside one isolation domain** (e.g. use `NSManagedObject` only inside its context's `perform`; keep `DateFormatter` inside one actor or create one per use).
  - **Convert** to `Sendable` representations at the boundary (pass `NSManagedObjectID`, a value-type DTO, or primitive data).
  - Use `sending` / region-based isolation to transfer ownership when the value isn't used afterwards (Section 6).
  - Use `@preconcurrency import` for modules not yet annotated (Q72).
- Wrapping them in `@unchecked Sendable` boxes just to silence errors hides real races.

### Q47. What makes a type non-`Sendable`? `[Fundamental]`
**Key points:**
- **Shared mutable state without synchronization**: a non-final class or a class with `var` properties; a struct containing a non-`Sendable` class reference; closures that capture mutable state.
- Copying a struct that contains a class reference copies only the **reference**, so two copies share and can mutate the same object, which is why such structs aren't `Sendable`.

```swift
final class Settings { var volume = 0.5 }   // non-Sendable (mutable class)

struct Player {                              // non-Sendable: contains a non-Sendable reference
    let name: String
    let settings: Settings
}
```

### Q48. Is `Sendable` a runtime guarantee of thread safety? `[Senior]`
**Key points:**
- No. It's a **compile-time** marker. The compiler verifies it for checked conformances, but `@unchecked Sendable` (and `nonisolated(unsafe)`) are promises the compiler can't verify.
- Sendable also says nothing about **logic** races: a `Sendable` value can still be used in code with race conditions (e.g. reentrancy bugs).

### Q49. Should you mark every type `Sendable`? `[Lead/Expert]`
**Key points:**
- Mark types `Sendable` when they genuinely **cross isolation boundaries** (models passed from services to the UI, DTOs, errors, configuration).
- Internal types are inferred anyway. For public API, `Sendable` is a long-term commitment.
- Don't make types `Sendable` that conceptually belong to one domain (UI objects, database managed objects). Isolate them instead.

### Q50. Can a struct containing a closure be `Sendable`? `[Senior]`
```swift
struct Validator: Sendable {
    let name: String
    let rule: @Sendable (String) -> Bool      // closure must be @Sendable for the struct to be Sendable
}

let emailValidator = Validator(name: "email") { $0.contains("@") }
```
- Stored closures must be `@Sendable` (they can't capture mutable state), otherwise the struct isn't `Sendable`.

## 6. `@Sendable` Closures, `sending` & Region-Based Isolation

### Q51. What is a `@Sendable` closure? `[Senior]`
**Key points:**
- A closure that may be called **concurrently** or from another isolation domain. The compiler checks that:
  - It captures only `Sendable` values.
  - It doesn't capture **mutable** local variables (`var`) by reference.
- `Task.detached`, task group `addTask`, `withTaskCancellationHandler`'s `onCancel`, and many concurrency APIs require `@Sendable` (or `sending`) closures.

### Q52. Why can't a `@Sendable` closure capture a mutable variable? `[Fundamental]`
```swift
var count = 0
Task.detached {
    count += 1        // ❌ Mutation of captured var 'count' in concurrently-executing code
}
count += 1            // the original scope could write at the same time → data race
```
- Capturing a `var` shares it by reference between the closure and the enclosing scope, which could run concurrently. Fix: capture an immutable copy (`[count]`), return a value instead, or protect the state with an actor.

### Q53. What is region-based isolation? `[Lead/Expert]`
**Key points:**
- A Swift 6 feature (SE-0414) where the compiler tracks **regions** of non-`Sendable` values. A non-`Sendable` value that's **disconnected** (no other references to it remain in the current domain) can be **sent** to another isolation domain safely.
- After sending, using the value again in the original domain is an error, because ownership has moved.
- This removes many false-positive errors from earlier Swift versions, where any non-`Sendable` value crossing a boundary was rejected.

```swift
final class ImageBatch {                  // non-Sendable class
    var images: [UIImage] = []
}

actor Uploader {
    func upload(_ batch: ImageBatch) async { /* ... */ }
}

func uploadNewBatch(_ images: [UIImage], with uploader: Uploader) async {
    let batch = ImageBatch()              // created locally: a disconnected region
    batch.images = images
    await uploader.upload(batch)          // ✅ allowed: batch is sent to the actor
    // batch.images.removeAll()           // ❌ error: 'batch' used after being sent
}
```

### Q54. What does the `sending` keyword do? `[Lead/Expert]`
**Key points:**
- Marks a parameter or result whose value is **transferred** to a different isolation domain. The caller must pass a value in a disconnected region (and can't use it afterwards); the callee gets exclusive ownership.
- It's the API-level spelling of region-based isolation, allowing non-`Sendable` values to cross boundaries safely.

```swift
actor JobQueue {
    private var jobs: [Job] = []                  // Job is a non-Sendable class

    func enqueue(_ job: sending Job) {            // caller gives up ownership
        jobs.append(job)
    }

    func takeNext() -> sending Job? {             // result is transferred to the caller
        jobs.isEmpty ? nil : jobs.removeFirst()
    }
}

let job = Job(name: "resize")
await queue.enqueue(job)
// job.name = "other"   // ❌ error: 'job' used after being sent
```
- Standard library examples: `Task.init`'s operation closure, `CheckedContinuation.resume(returning:)`, and `Mutex` initializers use `sending`.

### Q55. Why can a `Task { }` closure capture non-`Sendable` values in Swift 6? `[Lead/Expert]`
**Key points:**
- `Task.init` takes its closure as **`sending`**. Captured non-`Sendable` values are transferred into the task, as long as the original scope doesn't use them afterwards.

```swift
@MainActor
final class ExportController {
    func exportTapped(rows: [Row]) {             // Row is Sendable
        let formatter = CSVFormatter()           // non-Sendable class, created locally
        Task.detached {
            let csv = formatter.format(rows)     // ✅ formatter was sent into the task
            await self.share(csv)                // self is @MainActor, therefore Sendable
        }
        // formatter.delimiter = ";"             // ❌ would be an error: used after being sent
    }

    func share(_ csv: String) { /* present share sheet */ }
}
```
- If the captured value is still referenced elsewhere (e.g. it's a stored property of `self`), the compiler reports a data-race risk.

### Q56. How do capture rules differ between `Task { }` and `Task.detached { }`? `[Senior]`
**Key points:**
- `Task { }` created on an actor **inherits** that actor's isolation, so its body can access the actor's state synchronously (it runs on that actor). Captures of isolated state stay within the same domain.
- `Task.detached { }` is **nonisolated**: accessing the creating actor's state requires `await`, and captured values must be `Sendable` or transferable.

```swift
actor Library {
    private var books: [Book] = []

    func refreshInBackground(api: BookAPI) {
        Task {                                        // isolated to Library
            let fetched = (try? await api.fetchBooks()) ?? []
            books = fetched                           // synchronous: same actor
        }

        Task.detached {                               // nonisolated
            let count = await self.books.count        // must await the actor
            print(count)
        }
    }
}
```

### Q57. What does "non-Sendable type returned by actor-isolated call cannot cross actor boundary" mean? `[Lead/Expert]`
**Key points:**
- An actor method returns a non-`Sendable` value (e.g. a class instance from its internal state) to a caller in another domain. Both the actor and the caller could then reference the same mutable object.
- Fixes:
  - Return a `Sendable` copy (value type / DTO) instead of internal references.
  - Return a **newly created**, disconnected value marked `-> sending T`.
  - Keep the work inside the actor (pass a closure to run inside, or add a method that performs the operation).

```swift
actor DocumentStore {
    private var documents: [Document] = []        // Document is a non-Sendable class

    // ❌ Returns internal references to another domain
    func allDocuments() -> [Document] { documents }

    // ✅ Return Sendable snapshots
    func summaries() -> [DocumentSummary] {
        documents.map { DocumentSummary(id: $0.id, title: $0.title) }
    }

    // ✅ Return a freshly created object, transferring ownership
    func makeDraft() -> sending Document {
        Document(title: "Untitled")
    }
}
```

## 7. Controlling Isolation

### Q58. What does `nonisolated` do? `[Senior]`
**Key points:**
- Opts a member of an actor (or global-actor-isolated type) **out** of isolation. It can be called synchronously from anywhere, but it can't access isolated mutable state.
- Uses: protocol conformances (`Hashable`, `CustomStringConvertible`), computed properties derived from immutable state, and functions that should run off the actor.

```swift
@MainActor
final class ThumbnailViewModel {
    let photoID: UUID                         // immutable Sendable
    private(set) var thumbnail: UIImage?

    init(photoID: UUID) { self.photoID = photoID }

    nonisolated var cacheKey: String {        // callable from any thread
        "thumb-\(photoID)"
    }

    nonisolated func logDescription() -> String {
        // ❌ Can't read `thumbnail` here: it's main-actor isolated
        "ThumbnailViewModel(\(photoID))"
    }
}
```

### Q59. What is `nonisolated(unsafe)`? `[Lead/Expert]`
**Key points:**
- Disables isolation checking for a specific **stored variable** (often a global or static). You promise the compiler it's accessed safely (e.g. written once during launch and only read afterwards, or protected by external synchronization).
- It's an escape hatch for migration and legacy code. Every use should have a comment explaining why it's safe, and ideally be tracked as tech debt.

```swift
// Set once at launch before any concurrent access, read-only afterwards
nonisolated(unsafe) var launchArguments: [String] = []
```

### Q60. What are `isolated` parameters? `[Lead/Expert]`
**Key points:**
- A function parameter of actor type marked `isolated` makes the function run **isolated to that actor**, so it can access the actor's state synchronously, as if it were a method of the actor.
- Useful for writing free functions or extensions that operate on an actor's state in one atomic step.

```swift
actor Inventory {
    var stock: [String: Int] = [:]
}

func restock(_ items: [String: Int], in inventory: isolated Inventory) {
    for (sku, quantity) in items {
        inventory.stock[sku, default: 0] += quantity   // synchronous: we're isolated to `inventory`
    }
}

await restock(["A1": 10, "B2": 5], in: inventory)       // callers still await (hop to the actor)
```
- A function can have **at most one** `isolated` parameter (it can't be isolated to two actors at once).

### Q61. What is `#isolation`, and how do you inherit the caller's isolation? `[Lead/Expert]`
**Key points:**
- `#isolation` expands to the current isolation (`(any Actor)?`): the main actor, the current actor, or `nil` if nonisolated.
- As a default argument for an `isolated (any Actor)?` parameter, it lets a generic async utility **run on its caller's actor**. Non-`Sendable` values and closures can then be used without crossing a boundary.

```swift
extension Sequence {
    /// Runs on the caller's actor, so `transform` doesn't need to be @Sendable
    func asyncMap<T>(
        isolation: isolated (any Actor)? = #isolation,
        _ transform: (Element) async throws -> T
    ) async rethrows -> [T] {
        var results: [T] = []
        for element in self {
            results.append(try await transform(element))
        }
        return results
    }
}

@MainActor
func loadNames(ids: [Int]) async throws -> [String] {
    try await ids.asyncMap { id in
        try await api.fetchUser(id: id).name     // closure stays on the main actor
    }
}
```
- Swift 6.2's `nonisolated(nonsending)` (Q95) achieves the same "run on the caller's actor" behavior for any nonisolated async function, without the extra parameter.

### Q62. What is `@isolated(any)`? `[Lead/Expert]`
**Key points:**
- A function type attribute meaning "this closure may be isolated to **some** actor, and the callee can find out which one" via its `.isolation` property.
- APIs like `Task.init` take `@isolated(any)` closures, so the runtime can start a task **directly on the right actor** (e.g. a `Task { @MainActor in }` is enqueued on the main actor immediately, avoiding an extra hop).

```swift
func schedule(_ work: @escaping @Sendable @isolated(any) () async -> Void) {
    print("Will run on:", work.isolation.map { "\($0)" } ?? "nonisolated")
    Task(operation: work)          // the task starts on the closure's own isolation
}

schedule { @MainActor in
    statusLabel.text = "Updated"
}
```

### Q63. What are `assumeIsolated`, `preconditionIsolated`, and `assertIsolated`? `[Senior]`
**Key points:**
- **`MainActor.assumeIsolated { }`**: synchronously runs main-actor code when you **know** you're on the main thread but the compiler doesn't (e.g. a nonisolated delegate method documented to be called on main). **Crashes** if the assumption is wrong.
- **`MainActor.preconditionIsolated()`** / **`actor.preconditionIsolated()`**: crash (in all builds) if not running on that actor.
- **`assertIsolated()`**: the same check, but only in debug builds.

```swift
@MainActor
final class MapViewController: UIViewController, CLLocationManagerDelegate {
    private let locationLabel = UILabel()

    nonisolated func locationManager(_ manager: CLLocationManager, didUpdateLocations locations: [CLLocation]) {
        // CLLocationManager calls back on the thread it was created on (main, here)
        MainActor.assumeIsolated {
            locationLabel.text = locations.last.map { "\($0.coordinate.latitude)" }
        }
    }
}
```

### Q64. How does `Task { }` decide which actor it runs on? `[Senior]`
**Key points:**
- It inherits the isolation of the **context where it's created**: inside `@MainActor` code → main actor; inside an actor method → that actor; in nonisolated code → nonisolated (global concurrent executor).
- In Swift 6, the task inherits an actor's isolation only if the closure **captures** the actor (`self` inside an actor method, or an `isolated` parameter). Writing `Task { @MainActor in }` or `Task { @SomeGlobalActor in }` sets isolation explicitly.
- `Task.detached` never inherits isolation.

### Q65. What isolation do closures have? `[Lead/Expert]`
**Key points:**
- A **non-`@Sendable`, non-escaping or non-concurrent** closure inherits the isolation of the context where it's written (e.g. a closure passed to `map` inside a `@MainActor` method runs on the main actor).
- A **`@Sendable`** closure is nonisolated unless annotated (`@MainActor`) because it may run concurrently.
- An explicit global actor annotation (`{ @MainActor in ... }`) sets its isolation.
- Swift 6 infers isolation for closures passed to APIs taking `@isolated(any)` or `sending` closures (like `Task.init`) from their context and captures.

### Q66. How do you handle global and static mutable variables in Swift 6? `[Senior]`
**Key points:**
- Swift 6 rejects global/static `var`s (and `let`s of non-`Sendable` types) as **"not concurrency-safe because it is nonisolated global shared mutable state."**
- Fixes, from best to worst:

```swift
// ❌ Swift 6 error
var requestCount = 0
static var shared = NetworkMonitor()          // non-Sendable type

// ✅ 1. Make it an immutable Sendable constant
let maxRetries = 3

// ✅ 2. Isolate it to a global actor
@MainActor var currentTheme = Theme.light

// ✅ 3. Move the state into an actor or a Mutex
actor RequestStats { var count = 0 }
let requestCountStorage = Mutex(0)            // Mutex is Sendable (iOS 18+)

// ⚠️ 4. Escape hatch: you guarantee safety manually
nonisolated(unsafe) var legacyDebugFlag = false
```

## 8. Swift 6 Language Mode & Strict Concurrency

### Q67. What does the Swift 6 language mode change? `[Senior]`
**Key points:**
- **Complete data-race checking becomes errors**: isolation violations, non-`Sendable` values crossing boundaries, unsafe global state, and more.
- Several upcoming features become default (e.g. region-based isolation, `any` required for existentials, removal of global-actor inference from property wrappers).
- The **Swift 6 compiler** can still build code in **Swift 5 mode**. The language mode is chosen **per module/target**, so adoption can be gradual.

### Q68. What are the strict concurrency checking levels in Swift 5 mode? `[Senior]`
| Level (`SWIFT_STRICT_CONCURRENCY`) | What's checked |
|---|---|
| `minimal` | Only code that explicitly adopts concurrency features (`Sendable`, actors) |
| `targeted` | Also code that uses concurrency (async, tasks) |
| `complete` | Everything Swift 6 would check, as **warnings** |

- Typical migration: turn on `complete` in Swift 5 mode, fix warnings module by module, then switch the module to Swift 6 mode so they become errors and stay fixed.

### Q69. What does Swift 6 **not** protect against? `[Lead/Expert]`
**Key points:**
- **Race conditions / logic races**: actor reentrancy bugs, ordering assumptions between tasks, check-then-act across `await`.
- **Deadlocks** from blocking (semaphores, `DispatchQueue.sync` onto the main queue from the main thread).
- **Unsafe escape hatches**: `@unchecked Sendable`, `nonisolated(unsafe)`, `assumeIsolated` misuse, unsafe pointers, and code in modules still compiled in Swift 5 mode.
- **Non-Swift code**: Objective-C/C libraries with their own threading.
- Swift 6 removes a whole class of bugs, but concurrent design still needs care.

### Q70. Can Swift 5 and Swift 6 mode modules be mixed? `[Senior]`
**Key points:**
- Yes. Each module chooses its language mode, and modules interoperate.
- Imported declarations carry their concurrency annotations; a Swift 6 module importing an unannotated Swift 5 module may see many diagnostics, which `@preconcurrency import` can downgrade (Q72).
- This enables **bottom-up** migration: leaf modules first, app target last.

### Q71. What are upcoming feature flags? `[Lead/Expert]`
**Key points:**
- Individual future language behaviors you can enable early in Swift 5 mode (or opt into in Swift 6), e.g. `-enable-upcoming-feature InferSendableFromCaptures`, `GlobalActorIsolatedTypesUsability`, `NonisolatedNonsendingByDefault` (Swift 6.2).
- In SwiftPM: `swiftSettings: [.enableUpcomingFeature("NonisolatedNonsendingByDefault")]`.
- Teams use them to adopt Swift 6 behaviors incrementally and reduce the size of the final switch.

### Q72. What does `@preconcurrency import` do? `[Senior]`
**Key points:**
- Imports a module that hasn't adopted concurrency annotations yet and **suppresses or downgrades** `Sendable`-related diagnostics for its types, treating them as if they might be `Sendable`.
- Useful for third-party SDKs (or older Apple frameworks) not yet audited. Remove it once the dependency ships proper annotations (the compiler warns when it's no longer needed).

```swift
@preconcurrency import LegacyAnalyticsSDK
```

### Q73. What are `@preconcurrency` conformances and dynamic isolation checks? `[Lead/Expert]`
**Key points:**
- Conforming a `@MainActor` type to a **nonisolated** protocol (e.g. an SDK delegate) would normally be an error, since the protocol's requirements can be called from any thread.
- `@preconcurrency` on the conformance allows it, but Swift 6 inserts **runtime checks**: if the requirement is actually called off the main actor, the app **crashes** with an isolation assertion instead of silently racing.

```swift
@MainActor
final class PlayerViewController: UIViewController {}

extension PlayerViewController: @preconcurrency LegacyPlayerDelegate {
    func playerDidFinish() {          // treated as main-actor; checked at runtime
        showReplayButton()
    }
}
```
- If the SDK calls it on a background thread, use a `nonisolated` implementation that hops to the main actor instead.

### Q74. What does the crash "Incorrect actor executor assumption" mean? `[Lead/Expert]`
**Key points:**
- A runtime isolation check failed: code the compiler believed was isolated to an actor (often the main actor) was actually executed on a different executor/thread.
- Common causes during Swift 6 migration:
  - A `@preconcurrency` conformance whose method is called from a background queue (Q73).
  - A callback/closure inferred as `@MainActor` but invoked by an Objective-C or C API from another thread.
  - `MainActor.assumeIsolated` called off the main thread.
- Fix: find the call stack in the crash log, make the receiving method `nonisolated`, and hop explicitly (`Task { @MainActor in }`) or make the API deliver on the main queue.

## 9. Common Swift 6 Errors & How to Fix Them

### Q75. "Main actor-isolated property 'x' can not be referenced from a nonisolated context" `[Fundamental]`
```swift
@MainActor final class ViewModel { var title = "" }

func update(_ viewModel: ViewModel) {
    viewModel.title = "Hi"            // ❌ nonisolated function touching main-actor state
}

// ✅ Fix A: isolate the function
@MainActor func updateA(_ viewModel: ViewModel) { viewModel.title = "Hi" }

// ✅ Fix B: make it async and await the hop
func updateB(_ viewModel: ViewModel) async { await MainActor.run { viewModel.title = "Hi" } }
```

### Q76. "Call to main actor-isolated instance method in a synchronous nonisolated context" `[Fundamental]`
**Key points:**
- Same root cause from a synchronous function (e.g. a delegate callback or `deinit`). Options: mark the caller `@MainActor` (if it is always called on main), use `MainActor.assumeIsolated` (if you're certain it's main), or `Task { @MainActor in ... }` (if it may be any thread and asynchronous delivery is fine).

### Q77. "Sending 'value' risks causing data races" `[Senior]`
**Key points:**
- A non-`Sendable` value is passed to another isolation domain while the current domain may still access it.

```swift
final class Draft { var text = "" }           // non-Sendable

@MainActor
final class EditorViewModel {
    var draft = Draft()

    func save(using store: DraftStore) async {
        await store.save(draft)                // ❌ draft is still referenced by self (main actor)
    }
}

// ✅ Fix A: send a Sendable snapshot
struct DraftSnapshot: Sendable { let text: String }
// await store.save(DraftSnapshot(text: draft.text))

// ✅ Fix B: make the type Sendable (value type, or immutable final class)
// ✅ Fix C: keep the work in one isolation domain (make DraftStore @MainActor, if appropriate)
```

### Q78. "Capture of 'self' with non-sendable type in a `@Sendable` closure" `[Senior]`
**Key points:**
- A `@Sendable` closure (e.g. `Task.detached`, task group child, `onCancel`) captures a non-`Sendable` object.
- Fixes: capture only the `Sendable` values you need (`[id = self.id]`); make the type `Sendable` (actor, `@MainActor`, immutable, `Mutex`); or use a non-detached `Task` that stays in the same isolation domain.

### Q79. "Static property 'shared' is not concurrency-safe because non-'Sendable' type 'X' may have shared mutable state" `[Senior]`
```swift
// ❌
final class SessionManager {
    static let shared = SessionManager()
    var token: String?
}

// ✅ Option A: main-actor singleton (most app-level managers)
@MainActor final class SessionManagerA {
    static let shared = SessionManagerA()
    var token: String?
}

// ✅ Option B: actor
actor SessionManagerB {
    static let shared = SessionManagerB()
    var token: String?
}

// ✅ Option C: synchronous, thread-safe class (iOS 18+)
final class SessionManagerC: Sendable {
    static let shared = SessionManagerC()
    private let tokenStorage = Mutex<String?>(nil)
    var token: String? { tokenStorage.withLock { $0 } }
    func setToken(_ token: String?) { tokenStorage.withLock { $0 = token } }
}
```

### Q80. "Non-sendable type returned by implicitly asynchronous call to actor-isolated function cannot cross actor boundary" `[Lead/Expert]`
**Key points:**
- An actor returns a non-`Sendable` value to another domain. Return a `Sendable` snapshot, return a freshly created value with `-> sending T`, or perform the work inside the actor (see Q57).

### Q81. "Main actor-isolated conformance of 'X' to 'Protocol' cannot be used in nonisolated context" / protocol witness isolation errors `[Lead/Expert]`
**Key points:**
- A `@MainActor` type implements a nonisolated protocol requirement (e.g. `Equatable`, `Hashable`, `Codable`, a delegate) using main-actor state.
- Fixes:
  - Implement the requirement as `nonisolated` using only immutable/`Sendable` state.
  - Swift 6.2: declare an **isolated conformance** (`extension Model: @MainActor Equatable`), usable only on the main actor (Q96).
  - `@preconcurrency` conformance with runtime checks (Q73).
  - Move the conformance to a `Sendable` value type that represents the data.

### Q82. "Mutation of captured var in concurrently-executing code" `[Fundamental]`
**Key points:**
- A `@Sendable` closure (task group child, detached task) mutates a captured `var`. Return values instead and aggregate in one place, or protect the state with an actor/`Mutex` (see the Async/Await file, Q39).

### Q83. "Stored property 'x' of 'Sendable'-conforming class 'Y' is mutable" `[Senior]`
**Key points:**
- A class declared `Sendable` has a `var` (or non-`Sendable` `let`). Make properties immutable `let`s of `Sendable` types, wrap mutable state in a `Mutex`, convert the class to an actor or value type, or (with justification) use `@unchecked Sendable`.

### Q84. "Task or actor isolated value cannot be sent" / "passing argument of non-sendable type outside of main actor-isolated context" `[Lead/Expert]`
**Key points:**
- A value that belongs to an isolation domain (e.g. a stored property of a `@MainActor` object, or a parameter of an actor method) is passed to a `@Sendable`/`sending` context or another actor.
- Because the value is reachable from the domain's state, region-based isolation can't prove it's safe to transfer.
- Fixes: copy the relevant data into a `Sendable` value; create a new, disconnected instance to send; or keep the operation inside the original domain.

## 10. Migration Strategy

### Q85. How would you migrate a large app to Swift 6 strict concurrency? `[Lead/Expert]`
**Talking points:**
1. **Prepare**: update to the latest Xcode/Swift; update dependencies to concurrency-annotated versions; decide whether to adopt Swift 6.2 approachable concurrency settings (Section 11), since they change the volume and kind of errors.
2. **Measure**: enable `SWIFT_STRICT_CONCURRENCY = complete` in Swift 5 mode, module by module; record warning counts.
3. **Bottom-up**: start with leaf modules (models, utilities, networking), then services, then features, then the app target.
4. **Common fixes**: make models `Sendable` value types; mark UI layers and view models `@MainActor`; convert shared mutable singletons to actors, `@MainActor`, or `Mutex`-protected types; isolate globals.
5. **Boundaries**: `@preconcurrency import` for unannotated SDKs; `nonisolated` delegate methods that hop to the main actor.
6. **Flip**: switch each clean module to the Swift 6 language mode so regressions become errors.
7. **Track**: count `@unchecked Sendable`, `nonisolated(unsafe)`, and `@preconcurrency` as tech debt with owners.
8. **Ship safely**: test thoroughly for runtime isolation crashes (Q74); staged rollout; monitor crash rates.

### Q86. In what order should modules be migrated, and why? `[Lead/Expert]`
**Key points:**
- **Leaf modules first** (those with no internal dependencies): models, utilities, design system. Their annotations (`Sendable` models, `@MainActor` UI components) flow upward, so higher modules see fewer diagnostics.
- Migrating the app target first produces a flood of warnings caused by unannotated lower layers.
- Within the app target, migrate feature by feature.

### Q87. How do you handle third-party dependencies that aren't concurrency-ready? `[Lead/Expert]`
**Talking points:**
- Upgrade to a version with concurrency annotations if available.
- `@preconcurrency import` to suppress diagnostics from their types.
- **Wrap** the SDK behind your own protocol/adapter, isolated to an actor or the main actor, exposing only `Sendable` types and async APIs. The rest of your app depends on your safe wrapper, not the SDK.
- Verify the SDK's threading behavior (which queue it calls back on) to avoid runtime isolation crashes.
- Contribute fixes upstream or track the dependency as a migration risk.

### Q88. How do you migrate singletons and shared managers? `[Senior]`
**Key points:**
- Decide per singleton based on how it's used:
  - Mostly used from UI → `@MainActor`.
  - Shared state accessed from background work and needing async coordination → `actor`.
  - Must be callable synchronously from anywhere, with tiny critical sections → `final class: Sendable` with `Mutex` (Q79).
  - Immutable configuration → `let` properties, `Sendable`.
- Converting to an actor changes every call site to `await`; budget for that ripple effect.

### Q89. How do you handle delegates and callbacks that arrive on background queues? `[Senior]`
```swift
@MainActor
final class DownloadViewController: UIViewController, URLSessionDownloadDelegate {
    private let progressView = UIProgressView()

    // URLSession calls this on its delegate queue (background), so it must be nonisolated
    nonisolated func urlSession(_ session: URLSession,
                                downloadTask: URLSessionDownloadTask,
                                didWriteData bytesWritten: Int64,
                                totalBytesWritten: Int64,
                                totalBytesExpectedToWrite: Int64) {
        let fraction = Float(totalBytesWritten) / Float(max(totalBytesExpectedToWrite, 1))
        Task { @MainActor in
            self.progressView.progress = fraction     // hop to the main actor with a Sendable value
        }
    }

    nonisolated func urlSession(_ session: URLSession,
                                downloadTask: URLSessionDownloadTask,
                                didFinishDownloadingTo location: URL) {
        // Move the file synchronously here: it's deleted when this method returns
        let destination = FileManager.default.temporaryDirectory.appending(path: UUID().uuidString)
        try? FileManager.default.moveItem(at: location, to: destination)
        Task { @MainActor in self.showFile(at: destination) }
    }

    private func showFile(at url: URL) { }
}
```
- Pattern: `nonisolated` callback → extract `Sendable` values → hop with `Task { @MainActor in }`. Use `assumeIsolated` only when the API guarantees main-thread delivery.

### Q90. When is `@unchecked Sendable` acceptable during migration? `[Lead/Expert]`
**Key points:**
- When a type is **genuinely thread-safe** (protected by a lock or serial queue) but the compiler can't see it, and converting it to an actor or `Mutex` isn't feasible yet.
- Require: a comment explaining the synchronization, review by someone familiar with concurrency, and a tracking ticket.
- **Not acceptable**: adding it just to silence an error on a type with unsynchronized mutable state. That converts a compile-time error into a production crash.

### Q91. How do you run a Swift 6 migration as a team? `[Lead/Expert]`
**Talking points:**
- Write a short **concurrency guide**: isolation defaults (UI = `@MainActor`), when to use actors vs `Mutex`, rules for `Task` creation, banned shortcuts without review.
- Run training sessions with real examples from your codebase.
- Assign modules to owners; track warning counts per module on a dashboard; celebrate modules that flip to Swift 6 mode.
- Prevent regressions: once a module is in Swift 6 mode, CI enforces it; lint for new `@unchecked Sendable`/`nonisolated(unsafe)`.
- Time-box migration work alongside feature work instead of a big-bang freeze.

### Q92. What runtime problems appear after migrating, and how do you catch them early? `[Lead/Expert]`
**Key points:**
- **Isolation assertion crashes** (`@preconcurrency` conformances or `@MainActor` closures called off main), **behavior changes** (work that used to run in the background now runs on the main actor, causing hangs, especially with Swift 6.2 defaults), and **ordering changes** (`Task`s replacing synchronous dispatches).
- Catch them with: thorough QA on real devices, Thread Sanitizer runs in CI, the Main Thread Checker, internal/beta builds, staged rollout, and crash/hang monitoring (Xcode Organizer, MetricKit).

## 11. Approachable Concurrency (Swift 6.2)

### Q93. What is "approachable concurrency"? `[Senior]`
**Key points:**
- A set of Swift 6.2 changes (surfaced as Xcode 26 build settings) that make data-race safety easier to adopt, especially for app code that's mostly single-threaded UI:
  - **Default actor isolation**: a module can make everything `@MainActor` by default (Q94).
  - **`nonisolated(nonsending)` by default**: nonisolated async functions run on the caller's actor; `@concurrent` opts into running on the concurrent pool (Q95).
  - **Isolated conformances**: `@MainActor` types can conform to protocols like `Equatable` (Q96).
  - **Isolated `deinit`** (Q97), plus quality-of-life additions such as `Task.immediate` and task names.
- Philosophy: **start single-threaded (main actor), and introduce concurrency deliberately** where it helps performance.

### Q94. What does default main-actor isolation do, and what are its pitfalls? `[Lead/Expert]`
**Key points:**
- With "Default Actor Isolation = MainActor" (or SwiftPM `.defaultIsolation(MainActor.self)`), every declaration in the module without explicit isolation is treated as `@MainActor`: types, functions, global variables.
- Benefits: most UI-centric code compiles without annotations or `Sendable` errors, because everything shares one isolation domain.
- Pitfalls:
  - **Model types** become main-actor isolated too. Types that must be used from background actors (DTOs, parsers, database records) need `nonisolated` (e.g. `nonisolated struct Product: Codable { ... }`).
  - Heavy work now runs on the main actor unless you move it with `@concurrent` or a dedicated actor. Watch for new hangs.
  - Library/framework modules usually **shouldn't** use main-actor default isolation; it's intended for app targets and UI modules.

```swift
// App target with default MainActor isolation
final class FeedViewModel {           // implicitly @MainActor
    var posts: [Post] = []
}

nonisolated struct Post: Codable, Sendable {   // opted out: usable from any isolation
    let id: Int
    let title: String
}

actor FeedCache { /* explicit actor: its own isolation */ }
```

### Q95. What are `nonisolated(nonsending)` and `@concurrent`? `[Lead/Expert]`
**Key points:**
- `nonisolated(nonsending)`: a nonisolated async function that **runs on the caller's actor** and doesn't "send" its arguments across a boundary. Non-`Sendable` arguments are fine, and calling it from the main actor doesn't hop.
- `@concurrent`: a nonisolated async function that **always runs on the global concurrent executor** (the pre-6.2 behavior). Use it for CPU-heavy work you deliberately want off the caller's actor.
- With the `NonisolatedNonsendingByDefault` feature (enabled by Approachable Concurrency), plain `nonisolated` async functions get `nonsending` behavior automatically.

```swift
struct ImagePipeline {
    // Runs wherever it's called from; can take non-Sendable arguments safely
    nonisolated(nonsending) func validate(_ image: UIImage) async -> Bool {
        image.size.width > 0
    }

    // Always runs on the concurrent pool; arguments must be Sendable (UIImage is)
    @concurrent
    func resize(_ image: UIImage, to size: CGSize) async -> UIImage {
        UIGraphicsImageRenderer(size: size).image { _ in
            image.draw(in: CGRect(origin: .zero, size: size))
        }
    }
}
```
- Interview tip: explain **why** the change was made. The old behavior (always hopping off the actor) caused surprising thread switches and `Sendable` errors whenever main-actor code passed non-`Sendable` values to helper async functions.

### Q96. What are isolated conformances? `[Lead/Expert]`
**Key points:**
- Swift 6.2 lets a global-actor-isolated type conform to a nonisolated protocol **with isolation**: `extension Model: @MainActor Equatable`. The conformance can then use main-actor state.
- The compiler ensures the conformance is only **used** from the main actor. For example, you can't pass the type to generic code that might call `==` from a background thread.

```swift
@MainActor
final class ProfileModel {
    var name = ""
    var email = ""
}

// Before 6.2: error, because `==` must be nonisolated but reads main-actor state
extension ProfileModel: @MainActor Equatable {
    static func == (lhs: ProfileModel, rhs: ProfileModel) -> Bool {
        lhs.name == rhs.name && lhs.email == rhs.email
    }
}
```
- With the `InferIsolatedConformances` feature (part of Approachable Concurrency), conformances of global-actor-isolated types are inferred as isolated automatically.

### Q97. What is `isolated deinit`? `[Lead/Expert]`
**Key points:**
- Swift 6.2 allows `isolated deinit` in actors and global-actor-isolated classes. The deinitializer runs **on the type's actor**, so it can safely access isolated state and call isolated synchronous methods.
- Before this, a `@MainActor` class's `deinit` was nonisolated and couldn't touch main-actor properties (a common Swift 6 migration error when invalidating timers or removing observers in `deinit`).

```swift
@MainActor
final class LiveScoreViewController: UIViewController {
    private var displayLink: CADisplayLink?

    isolated deinit {
        displayLink?.invalidate()     // allowed: deinit runs on the main actor
    }
}
```
- Isolated deinit may be scheduled asynchronously onto the actor if the last reference is released elsewhere, so don't rely on exact timing.

### Q98. What other Swift 6.2 concurrency improvements are worth knowing? `[Senior]`
**Key points:**
- **`Task.immediate`**: starts a task synchronously on the current executor until its first suspension (see the Async/Await file, Q45).
- **Task names**: `Task(name:)` for debugging and Instruments.
- **`Observations`**: an `AsyncSequence` that streams changes from `@Observable` types transactionally.
- Better diagnostics and debugging (stepping through async code, isolation shown in the debugger).
- Verify details against the official release notes; interviewers mainly look for understanding of **why** the defaults changed.

### Q99. Should an existing project turn on approachable concurrency settings? How? `[Lead/Expert]`
**Talking points:**
- **New app projects** in Xcode 26 enable these settings by default; existing projects keep their old behavior until you change them.
- Benefits for an app target: far fewer annotations and errors, simpler mental model.
- Risks: **behavior changes**. Nonisolated async functions that used to run in the background now run on the caller's actor (possible main-thread hangs); model types become main-actor isolated (errors when used from background actors).
- Approach: enable per module, starting with UI modules; audit heavy async functions and mark them `@concurrent`; mark background-used models `nonisolated`; profile for hangs; keep library modules nonisolated by default.

## 12. Locks, `Mutex`, Atomics & When Not to Use Actors

### Q100. When should you use a lock instead of an actor? `[Lead/Expert]`
**Key points:**
- **Use a lock (`Mutex`)** when:
  - The state must be accessible **synchronously** (from non-async code, e.g. a property getter, `UITableViewDataSource`, a C callback).
  - Critical sections are **tiny** (read/write a value or dictionary entry) and never involve `await`.
  - You want to avoid making every caller async.
- **Use an actor** when:
  - Operations involve **async work** (network, file I/O) and need coordination.
  - You want compiler-enforced isolation for a larger component.
- **Never hold a lock across an `await`**: it blocks the thread and can deadlock the cooperative pool.

### Q101. What is `Mutex` from the Synchronization module? `[Senior]`
**Key points:**
- iOS 18+ / Swift 6: a `Sendable`, non-copyable lock that **owns the protected value**, so you can only access the value inside `withLock`. The compiler checks it, and a class holding only `Mutex`-wrapped state can be `Sendable` without `@unchecked`.

```swift
import Synchronization

final class RequestMetrics: Sendable {
    private let counts = Mutex<[String: Int]>([:])

    func record(_ endpoint: String) {
        counts.withLock { $0[endpoint, default: 0] += 1 }
    }

    func count(for endpoint: String) -> Int {
        counts.withLock { $0[endpoint, default: 0] }
    }

    func snapshot() -> [String: Int] {
        counts.withLock { $0 }           // copy out under the lock
    }
}
```

### Q102. What locks can you use on OS versions before iOS 18? `[Senior]`
```swift
import os

// iOS 16+: OSAllocatedUnfairLock (owns its state, like Mutex)
final class TokenStore: Sendable {
    private let token = OSAllocatedUnfairLock<String?>(initialState: nil)

    var current: String? { token.withLock { $0 } }
    func update(_ newValue: String?) { token.withLock { $0 = newValue } }
}

// Any version: NSLock with @unchecked Sendable (document the invariant)
final class LegacyCounter: @unchecked Sendable {
    private let lock = NSLock()
    private var value = 0                       // protected by `lock`

    func increment() { lock.withLock { value += 1 } }
}
```
- Prefer the `withLock` style over manual `lock()`/`unlock()`: it's exception-safe and Swift 6 discourages manual locking in async contexts.

### Q103. What are atomics, and when would you use them? `[Lead/Expert]`
```swift
import Synchronization

final class IDGenerator: Sendable {
    private let nextID = Atomic<Int>(0)

    func makeID() -> Int {
        nextID.add(1, ordering: .relaxed).newValue
    }
}
```
**Key points:**
- `Atomic<Value>` (iOS 18+) provides lock-free operations on single values (counters, flags).
- Use for simple counters or flags in performance-sensitive code. For anything involving multiple related values or invariants, use a `Mutex` or actor. Atomics are easy to misuse (memory ordering subtleties).

### Q104. What are the rules for using locks in async code? `[Senior]`
**Key points:**
- Never `await` while holding a lock. `withLock`'s closure is synchronous, which enforces this naturally.
- Keep critical sections short and free of callbacks into unknown code (avoid deadlocks).
- Don't use semaphores or condition variables to **wait** for async work inside tasks (blocks the cooperative pool).

```swift
// ❌ Lock held across a suspension point
lock.lock()
let data = try await download()   // thread blocked holding the lock; other tasks may deadlock
cache[key] = data
lock.unlock()

// ✅ Do async work outside the lock, then update under the lock
let data2 = try await download()
cacheStorage.withLock { $0[key] = data2 }
```

### Q105. Are serial `DispatchQueue`s still valid in Swift 6 code? `[Lead/Expert]`
**Key points:**
- Yes, GCD still works, but the compiler can't verify queue-based protection, so classes guarded by a queue need `@unchecked Sendable`, and `DispatchQueue` closures are `@Sendable` (captures must be `Sendable`).
- Options when modernizing: replace with an actor; keep the queue but expose it as an actor's **custom executor** (Q108), which is handy when an API needs a specific queue; or keep GCD in well-encapsulated legacy code.

### Q106. How do you choose between a struct, `@MainActor` class, actor, and `Mutex`-protected class? `[Lead/Expert]`
| Need | Choose |
|---|---|
| Plain data passed around | **struct/enum** (`Sendable`) |
| UI state, view models, coordinators | **`@MainActor` class** |
| Shared mutable state used by concurrent tasks, with async operations | **actor** |
| Shared state that must be readable/writable **synchronously** from any thread | **`final class: Sendable` + `Mutex`** |
| Several types sharing one non-thread-safe resource | **custom global actor** |
| Simple lock-free counters/flags | **`Atomic`** |

## 13. Executors & Runtime Internals

### Q107. What is an executor? `[Senior]`
**Key points:**
- The object that actually **runs jobs** (pieces of async work between suspension points).
- **Serial executors** back actors (one job at a time); the **main actor's executor** runs jobs on the main thread; the **global concurrent executor** runs nonisolated work on the cooperative thread pool.
- When code `await`s a call to another isolation domain, the runtime enqueues the continuation on that domain's executor ("hopping").

### Q108. How do you give an actor a custom executor? `[Lead/Expert]`
**Key points:**
- Swift 5.9 lets an actor provide its own `unownedExecutor`. A common use is backing an actor with a `DispatchSerialQueue` (iOS 17+), so its code runs on a specific queue required by a legacy API, a C library, or Core Data-style threading rules.

```swift
actor SQLiteDatabase {
    private let queue = DispatchSerialQueue(label: "com.example.sqlite")
    private let connection: OpaquePointer?

    nonisolated var unownedExecutor: UnownedSerialExecutor {
        queue.asUnownedSerialExecutor()       // all actor-isolated code runs on `queue`
    }

    init(connection: OpaquePointer?) {
        self.connection = connection
    }

    func execute(_ sql: String) throws {
        // Runs on `queue`: safe for a library that requires a single dedicated queue
    }
}
```

### Q109. What is a task executor preference? `[Lead/Expert]`
**Key points:**
- Swift 6 lets you prefer a specific **task executor** for nonisolated async code in a task (`withTaskExecutorPreference(_:operation:)`, or a `Task` initializer parameter). Nonisolated work and child tasks in that scope then run on your executor instead of the global pool.
- Mostly relevant for servers and specialized systems (e.g. keeping work on an event-loop thread). Rarely needed in typical iOS apps, but good to recognize.

### Q110. How are actors implemented at runtime? `[Lead/Expert]`
**Key points:**
- An actor is a heap object with a lightweight **job queue** (not a dedicated thread). When a job is enqueued and the actor is idle, the runtime schedules it on an available thread; the actor runs jobs one at a time.
- Jobs are prioritized; when higher-priority work waits on an actor, the runtime **escalates** the priority of jobs ahead of it.
- If a thread finishes a job on actor A and the next job is also for A, the runtime can keep running on the same thread ("switching" is cheap compared with thread context switches).

### Q111. What are distributed actors? `[Lead/Expert]`
**Key points:**
- Swift 5.7 feature extending the actor model across process or network boundaries: `distributed actor` types with `distributed func` methods that may execute on another machine via an `ActorSystem` (e.g. Apple's open-source cluster library).
- Arguments and results must be `Codable` (serializable), and calls are `async throws` (network failures).
- Mainly used on the server side or for multi-device/peer systems; uncommon in typical iOS apps, but shows breadth if mentioned.

## 14. Concurrency with Apple Frameworks

### Q112. How does SwiftUI fit into Swift Concurrency? `[Senior]`
**Key points:**
- `View` is `@MainActor`, so `body`, view methods, and `.task` closures run on the main actor.
- `@Observable` models used by views are typically `@MainActor`.
- Heavy work belongs in actors, `@concurrent` functions, or services; awaiting them doesn't block the UI.
- Environment keys and preference keys need concurrency-safe default values (use `@Entry`, or `static let` with `Sendable` types).

```swift
@MainActor
@Observable
final class GalleryModel {
    private(set) var thumbnails: [UIImage] = []
    private let renderer = ThumbnailRenderer()     // an actor

    func load(_ urls: [URL]) async {
        thumbnails = await renderer.render(urls)   // rendering happens on the actor
    }
}

struct GalleryView: View {
    @State private var model = GalleryModel()
    let urls: [URL]

    var body: some View {
        ScrollView { /* thumbnails */ }
            .task { await model.load(urls) }        // main actor; cancelled on disappear
    }
}
```

### Q113. How do you use timers and display links safely in Swift 6? `[Senior]`
```swift
@MainActor
final class StopwatchViewController: UIViewController {
    private var timer: Timer?
    private var elapsed = 0

    override func viewDidLoad() {
        super.viewDidLoad()
        // The block is @Sendable; it's scheduled on the main run loop, so assume main-actor isolation
        timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
            MainActor.assumeIsolated {
                self?.tick()
            }
        }
    }

    private func tick() { elapsed += 1 }
}

// Often simpler: a main-actor task loop, cancelled when the screen goes away
// tickTask = Task { while !Task.isCancelled { try? await Task.sleep(for: .seconds(1)); tick() } }
```

### Q114. How do you use Core Data safely with Swift Concurrency? `[Lead/Expert]`
**Key points:**
- `NSManagedObject` and `NSManagedObjectContext` are **not `Sendable`**: a managed object must only be used on its context's queue.
- Pass **`NSManagedObjectID`** (which is `Sendable`) across domains and refetch inside the target context.
- Use the async `perform` API (iOS 15+) to run work on the context's queue.

```swift
func archive(noteID: NSManagedObjectID, in container: NSPersistentContainer) async throws {
    let context = container.newBackgroundContext()
    try await context.perform {
        guard let note = try context.existingObject(with: noteID) as? Note else { return }
        note.isArchived = true
        try context.save()
    }
}

// Calling side (main actor)
try await archive(noteID: note.objectID, in: container)
```

### Q115. How does SwiftData handle concurrency? `[Senior]`
**Key points:**
- `ModelContainer` is `Sendable`; `ModelContext` and `@Model` instances are not. `mainContext` is main-actor bound.
- Use `@ModelActor` actors for background work, passing `PersistentIdentifier`s (Sendable) across actors.
- (Full details are in the SwiftData file, Section 7.)

### Q116. How does Combine work with Swift 6 strict concurrency? `[Lead/Expert]`
**Key points:**
- Most Combine types aren't annotated `Sendable`, and `receive(on: DispatchQueue.main)` isn't visible to the compiler as main-actor isolation.
- Result: `sink` closures touching main-actor state produce isolation diagnostics; teams use `MainActor.assumeIsolated` inside sinks, bridge to async with `.values` consumed in `@MainActor` tasks, or gradually replace Combine with async sequences and Observation.
- (See the Combine file, Q62 and Section 19.)

### Q117. How do notifications work with Swift 6 concurrency? `[Lead/Expert]`
**Key points:**
- `Notification` (with its `userInfo: [AnyHashable: Any]`) isn't `Sendable`, and observer closures may run on any queue, which causes diagnostics when handlers touch main-actor state.
- Patterns: `NotificationCenter.default.notifications(named:)` consumed in a `@MainActor` task (extract `Sendable` values before crossing); `queue: .main` observers with `MainActor.assumeIsolated`.
- iOS 26's Foundation adds concurrency-safe, strongly typed notification **messages** (main-actor and async message protocols) so posting and observing can be checked by the compiler. Check the current API before relying on it.

### Q118. How do you deal with Objective-C or C APIs that call back on arbitrary threads? `[Lead/Expert]`
**Key points:**
- Treat every callback as **nonisolated** unless the API documents the thread. Implement callbacks as `nonisolated` functions or `@Sendable` closures.
- Extract `Sendable` values inside the callback, then hop: `Task { @MainActor in ... }` or call into an actor.
- Use `assumeIsolated` only with documented guarantees; otherwise you risk runtime isolation crashes.
- Wrap such APIs once (an adapter actor or `AsyncStream`) so the rest of the app sees a clean, isolated, `async` interface.

## 15. Design Patterns with Actors & Isolation

### Q119. How do you design isolation domains for an app? `[Lead/Expert]`
**Key points (a common Lead question):**
```
┌──────────────────────────── Main actor ───────────────────────────┐
│  Views, view controllers, @Observable view models, coordinators   │
└───────────────▲───────────────────────────────────┬───────────────┘
                │ Sendable DTOs / snapshots          │ await
┌───────────────┴───────────── Actors ──────────────▼────────────────┐
│  APIClient/TokenStore, ImageCache, SyncEngine, @ModelActor stores  │
└───────────────▲───────────────────────────────────┬────────────────┘
                │                                    │
        Sendable value types (models, requests, errors) flow between layers
        Nonisolated pure functions for parsing/formatting; @concurrent for heavy CPU work
```
- **UI = main actor**; **shared mutable services = actors** (few, coarse-grained); **data = `Sendable` value types**; **heavy computation = `@concurrent`** or dedicated actors.
- Keep the number of isolation domains small. Every boundary costs hops, `await`s, and `Sendable` requirements.

### Q120. Implement a rate limiter actor. `[Lead/Expert]`
```swift
actor RateLimiter {
    private let minimumInterval: Duration
    private let clock = ContinuousClock()
    private var nextAvailable: ContinuousClock.Instant?

    init(minimumInterval: Duration) {
        self.minimumInterval = minimumInterval
    }

    /// Suspends until the caller may proceed; requests are spaced by `minimumInterval`
    func waitForTurn() async throws {
        let now = clock.now
        let slot = max(now, nextAvailable ?? now)
        nextAvailable = slot + minimumInterval      // reserve the slot BEFORE suspending (reentrancy-safe)
        if slot > now {
            try await clock.sleep(until: slot)
        }
    }
}

// Usage: at most one request every 500 ms
let limiter = RateLimiter(minimumInterval: .milliseconds(500))
try await limiter.waitForTurn()
let result = try await api.search(query)
```
- The key detail is updating `nextAvailable` before the `await`. Otherwise concurrent callers would all compute the same slot during the sleep (a reentrancy bug).

### Q121. How do you build a logger that writes entries in order? `[Senior]`
**Key points:**
- An actor alone doesn't guarantee order when many tasks call it (Q17), and `Task { await logger.log(...) }` from synchronous code creates independent tasks with no ordering.
- Funnel entries through an `AsyncStream` consumed by a single task, which guarantees FIFO order and lets synchronous code log without `await`.

```swift
final class OrderedLogger: Sendable {
    private let continuation: AsyncStream<String>.Continuation

    init(fileURL: URL) {
        let (stream, continuation) = AsyncStream.makeStream(of: String.self)
        self.continuation = continuation
        let writer = LogFileWriter(url: fileURL)      // an actor that appends to the file

        Task.detached(priority: .utility) {
            for await line in stream {
                await writer.append(line)             // one at a time, in submission order
            }
        }
    }

    func log(_ message: String) {                     // synchronous, callable from anywhere
        continuation.yield("\(Date.now.ISO8601Format()) \(message)")
    }
}
```

### Q122. How do you expose an actor's changing state to the UI? `[Lead/Expert]`
```swift
actor DownloadManager {
    private var progress: [URL: Double] = [:]
    private var subscribers: [UUID: AsyncStream<[URL: Double]>.Continuation] = [:]

    func progressUpdates() -> AsyncStream<[URL: Double]> {
        let (stream, continuation) = AsyncStream.makeStream(of: [URL: Double].self,
                                                            bufferingPolicy: .bufferingNewest(1))
        let id = UUID()
        subscribers[id] = continuation
        continuation.yield(progress)                         // current snapshot first
        continuation.onTermination = { [weak self] _ in
            Task { await self?.removeSubscriber(id) }
        }
        return stream
    }

    func setProgress(_ value: Double, for url: URL) {
        progress[url] = value
        for subscriber in subscribers.values { subscriber.yield(progress) }   // Sendable snapshots
    }

    private func removeSubscriber(_ id: UUID) { subscribers[id] = nil }
}

@MainActor
@Observable
final class DownloadsViewModel {
    private(set) var progress: [URL: Double] = [:]

    func observe(_ manager: DownloadManager) async {
        for await snapshot in await manager.progressUpdates() {
            progress = snapshot                              // main-actor UI state
        }
    }
}
// SwiftUI: .task { await viewModel.observe(manager) }  (stops automatically on disappear)
```
- The actor owns the truth; the UI receives **immutable `Sendable` snapshots** and mirrors them in main-actor state.

### Q123. Write a generic "single-flight" helper that coalesces identical concurrent work. `[Lead/Expert]`
```swift
actor SingleFlight<Key: Hashable & Sendable, Value: Sendable> {
    private var inFlight: [Key: Task<Value, Error>] = [:]

    func run(
        key: Key,
        operation: @escaping @Sendable () async throws -> Value
    ) async throws -> Value {
        if let existing = inFlight[key] {
            return try await existing.value      // join the in-flight call
        }
        let task = Task { try await operation() }
        inFlight[key] = task                     // registered before suspending
        defer { inFlight[key] = nil }
        return try await task.value
    }
}

// Usage: many callers asking for the same config share one request
let configFlight = SingleFlight<String, AppConfig>()
let config = try await configFlight.run(key: "config") { try await api.fetchConfig() }
```

### Q124. How do you model a connection state machine safely in an actor? `[Lead/Expert]`
```swift
actor ConnectionManager {
    private enum State {
        case disconnected
        case connecting(Task<Void, Error>)
        case connected
    }

    private var state: State = .disconnected
    private let socket: WebSocketClient

    init(socket: WebSocketClient) { self.socket = socket }

    func connect() async throws {
        switch state {
        case .connected:
            return
        case .connecting(let attempt):
            try await attempt.value                    // join the attempt already in progress
        case .disconnected:
            let attempt = Task { try await socket.open() }
            state = .connecting(attempt)               // update state BEFORE suspending
            do {
                try await attempt.value
                state = .connected
            } catch {
                state = .disconnected
                throw error
            }
        }
    }
}
```
- An explicit state enum makes reentrancy visible: every entry point checks the current state, and in-progress work is recorded before any `await`.

### Q125. Show an end-to-end feature with correct isolation. `[Senior]`
```swift
// 1. Sendable data
struct Article: Sendable, Identifiable, Decodable {
    let id: Int
    let title: String
}

// 2. Actor service: shared state + async work
actor ArticleRepository {
    private var cache: [Article] = []
    private let client: APIClient            // Sendable

    init(client: APIClient) { self.client = client }

    func articles(forceRefresh: Bool = false) async throws -> [Article] {
        if !forceRefresh, !cache.isEmpty { return cache }
        let fresh: [Article] = try await client.send(.articles)
        cache = fresh
        return fresh                           // [Article] is Sendable: safe to return
    }
}

// 3. Main-actor view model: UI state

@Observable
final class ArticlesViewModel {

    private(set) var errorMessage: String?
    private let repository: ArticleRepository

    init(repository: ArticleRepository) { self.repository = repository }

    func load(forceRefresh: Bool = false) async {
        do {
            articles = try await repository.articles(forceRefresh: forceRefresh)
            errorMessage = nil
        } catch {
            errorMessage = error.localizedDescription
        }
    }
}

// 4. View: main actor, lifetime-bound tasks
struct ArticlesView: View {
    @State var viewModel: ArticlesViewModel

    var body: some View {
        List(viewModel.articles) { Text($0.title) }
            .task { await viewModel.load() }
```

### Q127. How does Swift Testing's parallel execution affect concurrency tests? `[Senior]`
**Key points:**
- Swift Testing runs tests **in parallel by default** (unlike XCTest's default serial execution within a process). Tests that share global or static state can interfere with each other.
- Fixes: avoid shared mutable globals (inject dependencies); use the `.serialized` trait for suites that must run one at a time; mark suites `@MainActor` when testing main-actor code.

```swift
@Suite(.serialized)
struct KeychainTests {           // all touch the same keychain items
    @Test func savesToken() async throws { /* ... */ }
    @Test func deletesToken() async throws { /* ... */ }
}
```

### Q128. How do you deterministically test a reentrancy bug? `[Lead/Expert]`
**Key points:**
- Inject a dependency whose async method **suspends until the test releases it**, forcing two calls to interleave at the `await`.

```swift
actor ControlledFraudService: FraudService {
    private var pending: [CheckedContinuation<Void, Error>] = []
    var pendingCount: Int { pending.count }

    func verify(_ amount: Decimal) async throws {
        try await withCheckedThrowingContinuation { continuation in
            pending.append(continuation)               // suspend until approved
        }
    }

    func approveAll() {
        pending.forEach { $0.resume() }
        pending.removeAll()
    }
}

@Test func concurrentWithdrawalsNeverOverdraw() async throws {
    let fraud = ControlledFraudService()
    let account = BankAccount(balance: 100, fraudService: fraud)

    async let first: Void = account.withdraw(80)
    async let second: Void = account.withdraw(50)

    while await fraud.pendingCount < 2 { await Task.yield() }   // both are suspended at the await
    await fraud.approveAll()

    _ = try? await first
    _ = try? await second
    #expect(await account.balance >= 0)                         // fails for withdrawBuggy (Q23)
}
```

### Q129. How does Thread Sanitizer fit into a Swift 6 codebase? `[Senior]`
**Key points:**
- Thread Sanitizer (TSan) detects data races **at runtime**. Swift 6 catches most races at compile time, but TSan is still valuable for:
  - Modules still in Swift 5 mode.
  - Code using `@unchecked Sendable`, `nonisolated(unsafe)`, or unsafe pointers.
  - Objective-C/C code.
- Run test suites with TSan enabled in CI regularly (it slows execution, so not on every build).

### Q130. What tools help diagnose concurrency performance problems? `[Lead/Expert]`
**Key points:**
- Instruments **Swift Concurrency** template:
  - **Swift Tasks**: how many tasks exist, their states (running, suspended, waiting), and lifetimes.
  - **Swift Actors**: actor queue sizes, showing **contention** (many tasks waiting on one actor).
- **Hangs** / **Time Profiler**: main-actor work blocking the UI (common after adopting default main-actor isolation).
- Fixes for contention: split a "god actor" into smaller ones, move pure computation out of the actor (nonisolated/`@concurrent`), make actor methods coarser to reduce hops.

### Q131. How do you investigate data-race crashes reported in production? `[Lead/Expert]`
**Talking points:**
- Symptoms: crashes inside `Dictionary`/`Array` mutation, `EXC_BAD_ACCESS` in collection internals, "object was probably modified after being freed," random crashes with no clear pattern.
- Locate the shared state in the crash's stack; check whether that module is in Swift 6 mode and whether escape hatches (`@unchecked Sendable`, `nonisolated(unsafe)`) protect it.
- Reproduce under load with Thread Sanitizer; add stress tests.
- Fix by isolating the state (actor, `@MainActor`, `Mutex`) rather than adding ad hoc locks, then move the module to Swift 6 mode so the compiler prevents regressions.

### Q132. Accessing actor state without `await` `[Fundamental]`
```swift
actor Scoreboard {
    var score = 0
}

```
**Answer:** Compile error: "actor-isolated property 'score' can not be referenced from a nonisolated context." Use `await board.score` from an async context.

### Q133. Reentrancy and a lost update `[Senior]`
```swift
actor Counter {
    var value = 0

    func incrementSlowly() async {
        let current = value
        try? await Task.sleep(for: .milliseconds(100))   // suspension point
        value = current + 1
    }
}

let counter = Counter()
async let first: Void = counter.incrementSlowly()
async let second: Void = counter.incrementSlowly()
_ = await (first, second)
print(await counter.value)
```
**Output:** `1`, not `2`. Both calls read `value == 0` before either resumes from the sleep. There's no data race, but there **is** a race condition. Fix: read and write without an `await` in between (`value += 1` after the sleep).

### Q134. Order of calls from different tasks `[Senior]`
```swift
actor Log {
    var entries: [String] = []
    func append(_ entry: String) { entries.append(entry) }
}

let log = Log()
Task { await log.append("A") }
Task { await log.append("B") }
try await Task.sleep(for: .seconds(1))
print(await log.entries)
```
**Answer:** Either `["A", "B"]` or `["B", "A"]`. Independent tasks have no ordering guarantee, and actors aren't FIFO queues across tasks.

### Q138. Using a value after sending it `[Lead/Expert]`

### Q141. Swift 6.2 default: where does this run? `[Lead/Expert]`

### Q145. `Task` vs `Task.detached` inside an actor `[Senior]`

## 19. Senior / Lead Scenario Questions

### Q147. You lead the Swift 6 migration of a 500k-line app with 40 modules. What's your plan? `[Lead/Expert]`
**Talking points:**
1. **Baseline**: latest Xcode; inventory dependencies and their concurrency readiness; enable `complete` checking (warnings) everywhere to size the work per module.
2. **Decide defaults**: UI modules use main-actor default isolation (Swift 6.2) or explicit `@MainActor`; library modules stay nonisolated with explicit `Sendable` APIs.
3. **Guidelines and training**: a one-page concurrency guide (isolation choices, `Task` rules, banned shortcuts without review), examples from your codebase, and office hours.
4. **Bottom-up execution**: leaf modules → services → features → app target; each module flips to Swift 6 mode when clean and stays enforced in CI.
5. **Third parties**: wrap unannotated SDKs behind isolated adapters; `@preconcurrency import` only as a temporary measure.
6. **Debt tracking**: dashboard of warnings per module and counts of `@unchecked Sendable`/`nonisolated(unsafe)`/`@preconcurrency`, with owners.
7. **Risk management**: TSan in CI, QA focus on runtime isolation crashes and new main-thread hangs, staged rollouts, crash and hang monitoring.
8. **Communication**: regular status to stakeholders; migration work interleaved with features, not a freeze.

### Q148. A cache must be read synchronously by UI code and written by background tasks. How do you design it? `[Lead/Expert]`
**Talking points:**
- An actor would force UI reads to be `async`, which doesn't fit synchronous APIs like `cellForRowAt`.
- Option A: `final class ImageMemoryCache: Sendable` with a `Mutex<[URL: UIImage]>` (or `NSCache`, which is thread-safe), with synchronous `image(for:)` and `insert(_:for:)`.
- Option B: keep the cache `@MainActor` (all reads and writes on main), and have background tasks produce values that are inserted on the main actor. This is simple and safe if writes are infrequent.
- Discuss trade-offs: lock contention vs main-thread work; memory pressure handling; deduplicating downloads in a separate actor that writes to the cache when done.

### Q149. Design a thread-safe analytics system used from everywhere in the app. `[Lead/Expert]`
**Talking points:**
- **API**: a synchronous `track(_ event: AnalyticsEvent)` callable from any isolation (no `await` at call sites); `AnalyticsEvent` is a `Sendable` value type.
- **Pipeline**: `track` yields into an `AsyncStream` (ordered, non-blocking); a single consumer task batches events (by count or time) and hands them to an `Uploader` actor.
- **Uploader actor**: persistence of unsent batches, retries with backoff, network-reachability awareness, flushing on backgrounding.
- **Isolation**: no shared mutable state outside the actor and stream; compiles cleanly in Swift 6 mode without escape hatches.
- **Testing**: inject the uploader and clock; verify ordering, batching, and retry behavior.

### Q150. Crash reports show random crashes in dictionary mutation inside a legacy `SessionManager`. What do you do? `[Lead/Expert]`
**Talking points:**
- Likely a data race: the manager's dictionary is mutated from multiple threads (network callbacks + UI).
- Short term: confirm with Thread Sanitizer and a stress test; patch by protecting the state (`Mutex` or `OSAllocatedUnfairLock`), and ship a hotfix.
- Long term: decide the right isolation (actor or `@MainActor`), remove any `@unchecked Sendable` that hid the problem, move the module to Swift 6 mode so the compiler prevents recurrence, and add the stress test to CI.
- Share the post-mortem with the team to reinforce guidelines.

### Q151. A critical third-party SDK isn't `Sendable` and calls back on random threads. How do you integrate it safely? `[Lead/Expert]`
**Talking points:**
- **Isolate the SDK** inside one adapter (an actor, or a custom global actor if multiple types use it). Only the adapter touches SDK objects.
- **Callbacks**: implement delegate methods as `nonisolated`, extract `Sendable` data, then hop into the adapter actor or main actor.
- **Expose** a clean API: `async` functions and `AsyncStream`s of `Sendable` values.
- `@preconcurrency import` limited to the adapter's file.
- Document the SDK's threading assumptions, add runtime assertions (`preconditionIsolated`) in debug, and monitor for isolation crashes.
- Reassess when the vendor ships concurrency-annotated versions.

### Q152. Should your team adopt Swift 6.2's approachable concurrency settings? `[Lead/Expert]`
**Talking points:**
- **For**: app/UI modules become dramatically simpler (most code is main-actor by default); fewer `Sendable` errors; aligns with Apple's guidance and new project templates.
- **Against / risks**: behavior changes in existing code (functions moving onto the main actor, possible hangs); model types needing `nonisolated`; team must learn `@concurrent`; libraries shouldn't default to main actor.
- **Decision process**: pilot in one feature module; measure diagnostics before/after and profile for hangs; document rules (when to use `@concurrent`, which types are `nonisolated`); roll out module by module.

### Q153. What do you look for when reviewing concurrent Swift code? `[Lead/Expert]`
**Talking points:**
- **Isolation choice**: UI on `@MainActor`; actors only for shared mutable state with async needs; no needless actors.
- **Reentrancy**: no check-then-act across `await`; in-flight work recorded before suspending; assumptions re-validated after `await`.
- **`Sendable`**: data types are value types; no `@unchecked Sendable`/`nonisolated(unsafe)` without a documented, reviewed justification.
- **Boundaries**: delegate callbacks `nonisolated` with explicit hops; `assumeIsolated` only with documented guarantees.
- **Blocking**: no locks held across `await`; no semaphores waiting for async work; heavy work not on the main actor (`@concurrent` where needed).
- **Ordering**: no reliance on ordering between independent tasks or actor calls.
- **API design**: coarse-grained actor methods; `Sendable` snapshots returned rather than internal references.
- **Tests**: concurrency behavior tested (deduplication, interleavings), Swift Testing parallelism considered.

### Q154. How would you explain actors and `Sendable` to a junior engineer? `[Senior]`
**Talking points:**
- **Actor analogy**: a bank teller with a single window. Customers (tasks) queue up, and the teller serves one at a time, so the cash drawer (state) is never touched by two people at once. But if the teller steps away to call head office (`await`), the next customer can be served in the meantime. That's reentrancy, so recheck the drawer after the call.
- **`Sendable` analogy**: what can be safely handed over a counter: a photocopy (value type) or a sealed envelope (immutable object) is fine; a shared notebook both people keep writing in (mutable class) is not.
- **Main actor**: the one teller allowed to talk to customers in the lobby (the UI).
- Show one compile error from Swift 6 and how the fix maps to the analogy.

### Q155. How would you design the concurrency architecture of a brand-new app in 2026? `[Lead/Expert]`
**Talking points:**
- **Swift 6 language mode from day one**, with approachable concurrency in the app/UI modules (default main-actor isolation) and nonisolated library modules with explicit `Sendable` APIs.
- **Layers**: SwiftUI views and `@Observable` view models on the main actor; a few coarse-grained actors for shared services (API/token store, caches, sync engine, persistence via `@ModelActor`); `Sendable` value types for all data crossing layers; `@concurrent` functions for heavy CPU work.
- **Rules**: tasks created at UI boundaries (`.task`, event handlers); services expose `async` functions and `AsyncSequence`s; no global mutable state; escape hatches require review.
- **Testing**: injected clocks and dependencies, deterministic tests for interleavings, TSan runs in CI, Instruments profiling for hangs and actor contention before release.
