# iOS App Architecture Interview Guide (Expanded)

Nov 2, 2026 · @Imran Hossain

## How to use this guide

Architecture interviews test how you reason about trade-offs, not whether you recite one correct pattern. This guide keeps the original 165 questions, fixes the bugs found in them, adds a worked Swift example wherever an answer was only bullet points, and adds two new sections (Modern Swift 6.x, and a revision cheat sheet).

**Difficulty legend:** `[Fundamental]` · `[Senior]` · `[Lead/Expert]`

**Assumed baseline:** Swift 6 language mode, iOS 17+ (SwiftUI + Observation), Swift Testing (`@Test`, `#expect`). Notes call out where something needs iOS 18 or iOS 26.

### The 4-step answer framework

Use this shape for almost every architecture question. It is what interviewers listen for.

1. **Define** the concept in one sentence.
2. **Show** a small concrete example (code or a sketch).
3. **Trade-offs:** what it costs, and when you would not use it.
4. **Context:** how team size, product stage, or UI framework changes your choice.

Example, for "What is MVVM?": "MVVM moves presentation logic into a view model that exposes state and never references the view (define). For a login screen, the view model owns `email`, `password`, `isLoginEnabled` and `login()` (show). It makes logic unit-testable, but needs a binding mechanism in UIKit and can grow into a massive view model (trade-offs). For a 3-person SwiftUI team I'd use `@Observable` view models only for complex screens (context)."

## Shared reference types

Every example below compiles against these definitions, so the questions stay consistent. Read this once; you can also present it in an interview as "the core of my networking and domain layer".

```swift
import Foundation

// MARK: Domain models (pure Swift, Sendable value types)

struct Product: Sendable, Identifiable, Equatable, Hashable {
    let id: String
    let name: String
    let price: Decimal          // never Double for money
    let imageURL: URL?
}

struct CartItem: Sendable, Identifiable, Equatable {
    let id: String
    let product: Product
    var quantity: Int
    var price: Decimal { product.price }
}

struct User: Sendable, Equatable { let id: String; let name: String }

// MARK: Repository port (owned by the domain)

protocol ProductRepository: Sendable {
    func products() async throws -> [Product]
    func product(id: Product.ID) async throws -> Product
}

enum RepositoryError: Error, Equatable { case notFound }

// One stub used everywhere in tests and previews
struct StubProductRepository: ProductRepository {
    var result: Result<[Product], Error>

    init(products: [Product] = []) { result = .success(products) }
    init(error: Error) { result = .failure(error) }

    func products() async throws -> [Product] { try result.get() }

    func product(id: Product.ID) async throws -> Product {
        guard let match = try result.get().first(where: { $0.id == id }) else {
            throw RepositoryError.notFound          // no force unwrap
        }
        return match
    }
}

extension Product {
    /// Test data builder (Q121). Money from a String, not a float literal.
    static func fixture(id: String = "1", name: String = "Desk Lamp",
                        price: String = "49.99", imageURL: URL? = nil) -> Product {
        Product(id: id, name: name, price: Decimal(string: price)!, imageURL: imageURL)
    }
    static let samples: [Product] = [.fixture(id: "1"), .fixture(id: "2", name: "Chair", price: "129.00")]
}

// MARK: Networking core

enum APIError: Error, Equatable {
    case invalidResponse
    case httpStatus(Int, Data)
    case decoding(String)
}

struct Endpoint<Response: Decodable & Sendable>: Sendable {
    enum Method: String, Sendable { case get = "GET", post = "POST", put = "PUT", delete = "DELETE" }
    var path: String
    var method: Method = .get
    var queryItems: [URLQueryItem] = []
    var body: Data? = nil
    var requiresAuth = true
}

protocol RequestInterceptor: Sendable {
    func intercept(_ request: URLRequest) async throws -> URLRequest
}

struct APIClient: Sendable {
    let baseURL: URL
    let session: URLSession
    let interceptors: [any RequestInterceptor]
    let decoder: JSONDecoder

    init(baseURL: URL, session: URLSession = .shared,
         interceptors: [any RequestInterceptor] = [], decoder: JSONDecoder = JSONDecoder()) {
        self.baseURL = baseURL
        self.session = session
        self.interceptors = interceptors
        self.decoder = decoder
    }

    func send<Response>(_ endpoint: Endpoint<Response>) async throws -> Response {
        var components = URLComponents(url: baseURL.appending(path: endpoint.path),
                                       resolvingAgainstBaseURL: false)
        if !endpoint.queryItems.isEmpty { components?.queryItems = endpoint.queryItems }
        guard let url = components?.url else { throw APIError.invalidResponse }

        var request = URLRequest(url: url)
        request.httpMethod = endpoint.method.rawValue
        request.httpBody = endpoint.body
        if endpoint.body != nil { request.setValue("application/json", forHTTPHeaderField: "Content-Type") }
        for interceptor in interceptors { request = try await interceptor.intercept(request) }

        let (data, response) = try await session.data(for: request)
        guard let http = response as? HTTPURLResponse else { throw APIError.invalidResponse }
        guard (200..<300).contains(http.statusCode) else { throw APIError.httpStatus(http.statusCode, data) }

        do { return try decoder.decode(Response.self, from: data) }
        catch { throw APIError.decoding(String(describing: error)) }
    }
}

// MARK: DTO + mapping (data layer)

struct ProductDTO: Decodable, Sendable {
    let id: String
    let title: String
    let priceCents: Int
    let imageURL: String?

    enum CodingKeys: String, CodingKey {
        case id, title
        case priceCents = "price_cents"
        case imageURL = "image_url"
    }
}

extension Product {
    init(dto: ProductDTO) {
        self.init(id: dto.id, name: dto.title,
                  price: Decimal(dto.priceCents) / 100,      // exact: integer cents
                  imageURL: dto.imageURL.flatMap(URL.init(string:)))
    }
}

extension Endpoint where Response == [ProductDTO] {
    static func products(category: String? = nil) -> Self {
        Endpoint(path: "products",
                 queryItems: category.map { [URLQueryItem(name: "category", value: $0)] } ?? [])
    }
}

extension Endpoint where Response == ProductDTO {
    static func product(id: String) -> Self { Endpoint(path: "products/\(id)") }
}

// MARK: Analytics port

struct AnalyticsEvent: Sendable, Equatable { let name: String; let parameters: [String: String] }
protocol AnalyticsTracking: Sendable { func track(_ event: AnalyticsEvent) }
struct NoOpAnalytics: AnalyticsTracking { func track(_ event: AnalyticsEvent) {} }

// MARK: Helpers

extension Collection {
    subscript(safe index: Index) -> Element? { indices.contains(index) ? self[index] : nil }
}
```

Why these choices matter in an interview: value types are automatically `Sendable`; `Endpoint<Response>` makes decoding type-safe; the repository protocol lives with the domain, not with networking (dependency inversion).

## 1. Fundamentals

### Q1. What is software architecture in the context of an iOS app? `[Fundamental]`

**Answer:** Architecture is the high-level structure of the app: how code is split into components (views, view models, services, repositories, modules), what each owns, and how they depend on and talk to each other. It covers the decisions that are **expensive to change later**: UI pattern, navigation, dependency management, data flow, module boundaries, persistence and networking.

**Concrete example:** "Our app is SwiftUI with `@Observable` view models; navigation is a router per tab; view models depend on repository protocols; repositories wrap a typed `APIClient` and SwiftData; everything is wired in an `AppContainer` at launch." That one sentence is an architecture description.

**Litmus test:** good architecture makes the *most common* changes cheap. Ask: how many files does adding a field to the product screen touch? How many to swap the analytics vendor? (Ideally: 2–4, and 1.)

### Q2. What are the goals of a good iOS architecture? `[Fundamental]`

- **Separation of concerns:** UI, presentation logic, business rules and data access live in different places.
- **Testability:** logic is tested without UI, network or the clock.
- **Changeability:** features change without ripple effects.
- **Readability and consistency:** new engineers find things fast.
- **Team scalability:** parallel work without constant conflicts.
- **Performance and reliability** are not sacrificed for abstraction.

**Interview tip:** add that architecture must fit the **team size and product stage**. A 2-person MVP optimises for speed of learning; a 50-engineer banking app optimises for safety, ownership and auditability.

### Q3. What are coupling and cohesion? `[Fundamental]`

**Coupling** is how much one component depends on another's internals. **Cohesion** is how related the responsibilities inside one component are. Aim for **low coupling, high cohesion**.

```swift
// ❌ Low cohesion + tight coupling
final class ProfileViewController: UIViewController {
    let session = URLSession.shared                 // coupled to networking
    let dateFormatter = DateFormatter()             // formatting
    func cacheAvatar(_ data: Data) { /* disk IO */ }  // caching
    func parse(_ data: Data) -> User? { nil }       // parsing
}

// ✅ High cohesion, low coupling: each type has one job, depends on an abstraction
protocol ProfileLoading: Sendable { func profile() async throws -> User }

@MainActor @Observable
final class ProfileViewModel {
    private let loader: ProfileLoading              // swap in tests
    private(set) var name = ""
    init(loader: ProfileLoading) { self.loader = loader }
    func load() async { name = (try? await loader.profile().name) ?? "" }
}
```

**How to measure coupling quickly:** count imports and initializer parameters; ask "if I change X, what else must change?"

### Q4. What layers does a typical iOS app have? `[Fundamental]`

```
┌───────────────────────────────────────────────┐
│ Presentation: Views, ViewControllers,         │  UIKit / SwiftUI
│ ViewModels / Presenters, Coordinators/Routers │
├───────────────────────────────────────────────┤
│ Domain: Entities, Use Cases / Business rules, │  Pure Swift, no frameworks
│ Repository protocols (ports)                  │
├───────────────────────────────────────────────┤
│ Data: Repository implementations, API client, │  URLSession, SwiftData,
│ persistence, DTOs and mappers, caches         │  Keychain, SDKs
└───────────────────────────────────────────────┘
       Dependencies point inward (toward Domain)
```

Trace one request through the layers: `ProductListView` → `ProductListViewModel.load()` → `ProductRepository.products()` (protocol, domain) → `RemoteProductRepository` (data) → `APIClient.send(.products())` → `[ProductDTO]` mapped to `[Product]` → back up as `State.loaded(products)`.

Small apps may merge Domain into Data; large apps split each layer into modules (Section 12).

### Q5. What does bad architecture cost a team? `[Senior]`

- Slower delivery: every change touches many files; regressions are frequent.
- Low test coverage because logic is tangled with UI and networking.
- Merge conflicts and long build times in one big target.
- Knowledge silos: "only Alex understands checkout."
- Fear of refactoring, so tech debt compounds.

**Lead-level framing:** architecture is an **economic decision**. Upfront structure is a cost you pay to lower the long-term cost of change. Quote numbers when you can: "Incremental builds went from 4 minutes to 40 seconds; that is roughly 30 engineer-hours a week across 10 people."

### Q6. Is there a "best" iOS architecture? `[Senior]`

No. Each pattern optimises for something different:

| Pattern | Optimises for |
| --- | --- |
| MVC | Simplicity, lowest learning curve |
| MVVM | Testable presentation logic, SwiftUI fit |
| VIPER / Clean | Strict separation for large teams |
| TCA | Predictable state, exhaustive testing, composition |

The choice depends on team size and experience, app complexity, UI framework, testing goals and expected lifespan. **Consistency across the codebase often matters more than which pattern you picked.**

### Q7. Architecture vs design patterns vs frameworks? `[Fundamental]`

| Term | Scope | Examples |
| --- | --- | --- |
| Architecture | Overall structure of the app | Layered/Clean, MVVM + Coordinators, modular features |
| Architectural (UI) pattern | How a screen's code is organised | MVC, MVVM, MVP, VIPER, TCA |
| Design pattern | Reusable solution to a local problem | Delegate, Observer, Factory, Strategy, Decorator |
| Framework | Library you build on | UIKit, SwiftUI, SwiftData, TCA (the library) |

Note that TCA is both an architectural pattern and a framework, which is why it appears twice.

### Q8. How do Swift language features shape iOS architecture? `[Senior]`

```swift
// Enums with associated values: impossible states are unrepresentable
enum LoadState<Value> { case idle, loading, loaded(Value), failed(String) }

// Protocols + generics: dependency inversion without class hierarchies
@MainActor func makeViewModel(repo: some ProductRepository) -> ProductListViewModel { .init(repository: repo) }

// Actors: a concurrency boundary around shared mutable state
actor ImageCache { private var store: [URL: Data] = [:] }

// Access control: `package` shares across modules in one package, hidden from clients
package func makeDefaultDecoder() -> JSONDecoder { JSONDecoder() }
```

- **Value types:** immutable state, automatically `Sendable`.
- **Protocols/generics:** abstractions and test doubles.
- **Enums:** precise states and routes.
- **async/await + actors:** clear concurrency boundaries; Swift 6 makes data races compile errors.
- **Observation (`@Observable`):** lighter presentation layers.
- **Packages + access control:** module boundaries enforced by the compiler.
- **Macros:** less boilerplate (`@Observable`, `@Reducer`, `@Entry`).
- **Swift 6.2:** approachable concurrency and default `MainActor` isolation (Section 24).

## 2. Design Principles (SOLID & Friends)

### Q9. What is SOLID? `[Fundamental]`

| Principle | Meaning | One-line iOS example |
| --- | --- | --- |
| **S**ingle Responsibility | One reason to change | Formatter separate from view model |
| **O**pen/Closed | Extend without modifying | New `PaymentProcessor` type, no edits to checkout |
| **L**iskov Substitution | Conformers usable wherever the protocol is expected | A read-only store must not conform to a writable protocol |
| **I**nterface Segregation | Small focused protocols | `Authenticating` vs a fat `UserService` |
| **D**ependency Inversion | Depend on abstractions | View model takes `OrdersLoading`, not `URLSession` |

### Q10. Single Responsibility Principle `[Fundamental]`

```swift
// ❌ Networking, parsing, caching, formatting and UI in one type
final class ProfileViewController: UIViewController {
    func loadProfile() {
        URLSession.shared.dataTask(with: profileURL) { data, _, _ in
            let json = try? JSONSerialization.jsonObject(with: data ?? Data())
            // parse, cache to UserDefaults, format dates, update labels...
        }.resume()
    }
}

// ✅ Each type has one job
protocol ProfileRepository: Sendable { func profile() async throws -> Profile }  // data access

struct ProfileFormatter {                                                        // formatting
    func joinedText(for date: Date) -> String {
        "Joined " + date.formatted(.dateTime.month(.wide).year())
    }
}

@MainActor @Observable final class ProfileViewModel { /* screen state + intents */ }
final class ProfileViewController: UIViewController { /* render + forward input */ }
```

**Senior nuance:** "one reason to change" means one **stakeholder or concern** (design team, backend contract, business rule), not "one method". Over-splitting creates 30 tiny files nobody can navigate.

### Q11. Open/Closed Principle `[Senior]`

```swift
// ❌ Every new payment method edits this switch (and its tests)
enum PaymentMethod { case card, applePay, paypal }

func fee(for method: PaymentMethod, amount: Decimal) -> Decimal {
    switch method {
    case .card:     amount * Decimal(string: "0.029")!   // FIX: not a float literal
    case .applePay: amount * Decimal(string: "0.025")!
    case .paypal:   amount * Decimal(string: "0.034")!
    }
}

// ✅ Add a method by adding a type
protocol PaymentProcessor: Sendable {
    var id: String { get }
    var feeRate: Decimal { get }
    func pay(_ amount: Decimal) async throws -> Receipt
}

extension PaymentProcessor {
    func fee(for amount: Decimal) -> Decimal { amount * feeRate }
}

struct CardProcessor: PaymentProcessor {
    let id = "card"
    let feeRate = Decimal(string: "0.029")!
    func pay(_ amount: Decimal) async throws -> Receipt { /* ... */ Receipt() }
}

// Checkout depends on [any PaymentProcessor]; a new processor needs zero edits here
struct CheckoutService {
    let processors: [any PaymentProcessor]
    func availableMethods() -> [String] { processors.map(\.id) }
}
```

**Why `Decimal(string:)`:** `let d: Decimal = 0.029` goes through `Double` and is not exactly 0.029. For money, use strings or integer cents.

**Senior nuance:** for a **closed, stable** set, an enum + `switch` is better: the compiler forces you to handle new cases everywhere. Use protocols when the set is **open** (plugins, third parties, frequent additions).

### Q12. Liskov Substitution Principle `[Senior]`

```swift
protocol KeyValueStore {
    func value(for key: String) -> String?
    func set(_ value: String, for key: String)
}

// ❌ Violates LSP: any code accepting KeyValueStore crashes with this one
struct BundledDefaultsStore: KeyValueStore {
    func value(for key: String) -> String? { nil }
    func set(_ value: String, for key: String) { fatalError("Read-only store") }
}

// ✅ Model capabilities honestly
protocol ReadableStore { func value(for key: String) -> String? }
protocol WritableStore: ReadableStore { func set(_ value: String, for key: String) }

struct BundledDefaults: ReadableStore { func value(for key: String) -> String? { nil } }
struct UserDefaultsStore: WritableStore {
    let defaults: UserDefaults
    func value(for key: String) -> String? { defaults.string(forKey: key) }
    func set(_ value: String, for key: String) { defaults.set(value, forKey: key) }
}
```

Other LSP smells in iOS: a subclass that overrides `viewDidLoad` without calling `super`; a mock that ignores a protocol's documented contract (e.g. returns results in a different order than promised).

### Q13. Interface Segregation Principle `[Fundamental]`

```swift
// ❌ Fat protocol: every conformer and mock implements six methods
protocol UserService {
    func login(email: String, password: String) async throws -> User
    func logout() async
    func fetchProfile() async throws -> Profile
    func updateAvatar(_ image: Data) async throws
    func deleteAccount() async throws
    func fetchFriends() async throws -> [User]
}

// ✅ Small protocols; one implementation can still conform to all of them
protocol Authenticating: Sendable {
    func login(email: String, password: String) async throws -> User
    func logout() async
}
protocol ProfileProviding: Sendable { func fetchProfile() async throws -> Profile }

final class LiveUserService: Authenticating, ProfileProviding { /* ... */ }

// The login screen's mock is now 2 methods, not 6
struct StubAuth: Authenticating {
    var user = User(id: "1", name: "Ana")
    func login(email: String, password: String) async throws -> User { user }
    func logout() async {}
}
```

### Q14. Dependency Inversion Principle `[Fundamental]`

```swift
// ❌ High-level policy depends on a low-level detail
@MainActor
final class OrdersViewModel {
    private let api = URLSessionOrdersAPI()          // concrete, hidden, untestable
}

// ✅ Both depend on an abstraction owned by the high-level layer
protocol OrdersLoading: Sendable {
    func loadOrders() async throws -> [Order]
}

@MainActor
final class OrdersViewModelDI {
    private let loader: OrdersLoading
    init(loader: OrdersLoading) { self.loader = loader }
}

struct RemoteOrdersLoader: OrdersLoading {          // detail implements the abstraction
    let client: APIClient
    func loadOrders() async throws -> [Order] { try await client.send(.orders()) }
}
```

**Key insight:** the **abstraction belongs to the consumer** (domain/presentation), not to the networking module. In a modular app, `OrdersLoading` lives in the feature or domain module; the networking module depends on it, not the reverse.

### Q15. Composition over inheritance `[Senior]`

```swift
// ❌ class BaseViewController: UIViewController { showLoading(), trackScreen(), handleKeyboard(), showError() }

// ✅ Compose focused helpers
@MainActor
protocol ErrorPresenting: UIViewController {}

extension ErrorPresenting {
    func presentError(_ message: String) {
        let alert = UIAlertController(title: "Error", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default))
        present(alert, animated: true)
    }
}

@MainActor
final class KeyboardInsetHandler {
    private var observers: [NSObjectProtocol] = []
    func attach(to scrollView: UIScrollView) { /* observe keyboard notifications, adjust insets */ }
}

final class CheckoutViewController: UIViewController, ErrorPresenting {
    private let keyboard = KeyboardInsetHandler()     // composed helper object
}
```

SwiftUI equivalent: a `ViewModifier` (`.errorAlert($error)`, `.trackScreen("checkout")`) instead of a base view.

### Q16. DRY, KISS, YAGNI and when they conflict `[Senior]`

- **DRY:** don't duplicate *knowledge* (business rules, constants). Duplicate code is fine if it represents different knowledge.
- **KISS:** prefer the simplest design that works.
- **YAGNI:** don't build abstractions for imagined future needs.

```swift
// Looks duplicated, but these are DIFFERENT rules that will diverge:
func isValidSignupPassword(_ p: String) -> Bool { p.count >= 8 }
func isValidPIN(_ p: String) -> Bool { p.count >= 8 }   // security may change this to 6 digits
// Merging them into isValid(_:) couples two business rules. Leave them separate.
```

Heuristic: the **rule of three**. Abstract on the third real duplication.

### Q17. Law of Demeter `[Senior]`

```swift
// ❌ Caller depends on the whole object graph
let city = order.customer.shippingAddress.city

// ✅ Ask the nearest object
extension Order { var shippingCity: String { customer.shippingAddress.city } }
let city2 = order.shippingCity
```

Apply it to **objects with behaviour** (services, view models). Don't apply it dogmatically to plain data structs; reading nested value types is fine.

### Q18. When do protocols help, and when do they hurt? `[Lead/Expert]`

**Help:** real boundaries (network, persistence, analytics, SDKs, clock, system APIs), test doubles, multiple genuine implementations.

**Hurt:** a protocol for every class with one implementation forever: extra files, "Jump to Definition" lands on the protocol, harder refactors.

```swift
// ❌ No I/O, deterministic: no need for a protocol
protocol PriceFormatting { func format(_ d: Decimal) -> String }

// ✅ Concrete value type, test it directly
struct PriceFormatter {
    let locale: Locale
    func format(_ d: Decimal) -> String { d.formatted(.currency(code: "USD").locale(locale)) }
}
```

Alternatives for testability: closure-based dependencies (Q120), injecting values (a `now: Date`) instead of services, or real lightweight fakes.

### Q19. Why are value types important in architecture? `[Senior]`

```swift
struct CartState: Equatable, Sendable { var items: [CartItem] = [] }

var a = CartState()
var b = a                    // independent copy
b.items.append(item)
// a.items is still empty: no accidental shared mutation between screens
```

- No shared mutable state between screens or threads.
- Automatically `Sendable` when all stored properties are, simplifying Swift 6.
- `Equatable` snapshots are easy to compare, log, persist and assert in tests.
- Use reference types only for **identity and lifecycle**: view models, services, coordinators, actors.

### Q20. Command-Query Separation `[Senior]`

```swift
struct Playlist {
    var items: [Item]
    private(set) var currentIndex = 0

    // ❌ Query with a hidden side effect
    // mutating func nextItem() -> Item? { currentIndex += 1; return items[safe: currentIndex] }

    // ✅ Command and query separated
    mutating func advance() { currentIndex += 1 }          // command

```

Pragmatic exceptions exist (`popLast()`, `insert` returning `(inserted, memberAfterInsert)`), but follow CQS by default in domain code: queries are safe to call any number of times.

## 3. MVC

### Q21. What is Apple's MVC? `[Fundamental]`

- **Model:** data and business logic.
- **View:** displays data, forwards user actions (`UIView`).
- **Controller:** mediates between model and view (`UIViewController`).

```
User action → View → Controller → Model
                     Controller ← Model (callbacks / notifications / KVO)
              View ← Controller (updates UI)
```

In UIKit the view controller owns its view's lifecycle (`loadView`, `viewDidLoad`, rotation, appearance), so in practice V and C merge into one class. That is the root of the "Massive View Controller" problem.

### Q22. Why does MVC become "Massive View Controller"? `[Fundamental]`

Because there is no designated home for presentation logic, the view controller collects everything:

```swift
final class OrdersViewController: UIViewController, UITableViewDataSource, UITableViewDelegate {
    // networking, JSON parsing, caching, date formatting, validation,
    // navigation, table data source + delegate, keyboard handling,
    // pull-to-refresh, analytics, error alerts...
    // → 1,500 lines, impossible to unit test without UIKit
}
```

### Q23. How do you do MVC well? `[Senior]`

Five techniques, each with a small example:

```swift
// 1. Custom root view: layout code leaves the controller
final class OrdersRootView: UIView {
    let tableView = UITableView()
    let emptyLabel = UILabel()
    override init(frame: CGRect) { super.init(frame: frame); /* constraints */ }
    required init?(coder: NSCoder) { fatalError() }
}

// 2. Separate data source object (diffable)
@MainActor
final class OrdersDataSource {
    private let dataSource: UITableViewDiffableDataSource<Int, Order.ID>
    private var ordersByID: [Order.ID: Order] = [:]

    init(tableView: UITableView) {
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "cell")
        var lookup: (Order.ID) -> Order? = { _ in nil }
        dataSource = .init(tableView: tableView) { tableView, indexPath, id in
            let cell = tableView.dequeueReusableCell(withIdentifier: "cell", for: indexPath)
            var content = cell.defaultContentConfiguration()
            content.text = lookup(id)?.title
            cell.contentConfiguration = content
            return cell
        }
        lookup = { [unowned self] in ordersByID[$0] }
    }

    func apply(_ orders: [Order]) {
        ordersByID = Dictionary(uniqueKeysWithValues: orders.map { ($0.id, $0) })
        var snapshot = NSDiffableDataSourceSnapshot<Int, Order.ID>()
        snapshot.appendSections([0])
        snapshot.appendItems(orders.map(\.id))
        dataSource.apply(snapshot)
    }
}

// 3. Injected model controller / service
protocol OrdersService: Sendable { func orders() async throws -> [Order] }

// 4. Thin controller: wires pieces, handles lifecycle
final class OrdersViewController: UIViewController {
    private let service: OrdersService
    var onSelectOrder: ((Order.ID) -> Void)?      // 5. navigation delegated to a coordinator
    private lazy var rootView = OrdersRootView()
    private lazy var dataSource = OrdersDataSource(tableView: rootView.tableView)

    init(service: OrdersService) { self.service = service; super.init(nibName: nil, bundle: nil) }
    required init?(coder: NSCoder) { fatalError() }

    override func loadView() { view = rootView }

    override func viewDidLoad() {
        super.viewDidLoad()
        Task {
            let orders = (try? await service.orders()) ?? []
            dataSource.apply(orders)
            rootView.emptyLabel.isHidden = !orders.isEmpty
        }
    }
}
```

Also useful: **child view controllers** for distinct regions (header, list, footer), and **formatter types** for presentation transforms. Done this way, "MVC + services + coordinators" is a valid architecture for small and medium apps.

### Q24. When is plain MVC reasonable? `[Senior]`

- Small apps, prototypes, internal tools, settings-like screens with little logic.
- Teams new to iOS (Apple samples use it).
- Screens that are thin wrappers around system components.

**Model answer:** "I'd start with MVC plus injected services, and introduce a view model for a screen when its presentation logic needs unit tests. The services are already injected, so the step is small."

### Q25. Does MVC apply to SwiftUI? `[Senior]`

Not directly. SwiftUI has no controller: views are value types that describe UI as a function of state, and the framework re-renders on change.

```swift
// The "controller" responsibilities are split:
// - state: @State / @Observable model
// - actions: closures in the view calling model methods
// - lifecycle: .task, .onAppear, .onChange
struct OrdersView: View {
    @State private var model = OrdersModel()
    var body: some View {
        List(model.orders) { Text($0.title) }
            .task { await model.load() }
    }
}
```

SwiftUI apps use MV (Section 9), MVVM with `@Observable` (Section 4), or unidirectional architectures like TCA (Section 8).

## 4. MVVM

### Q26. What is MVVM? `[Fundamental]`

- **Model:** domain data and business rules (via services/repositories).
- **View:** UI; renders state and forwards user intents.
- **ViewModel:** presentation logic; turns models into display-ready state, handles intents, runs async work.

The view model **never references the view**, so it is unit-testable without UIKit or SwiftUI.

```
View ──(user intents)──▶ ViewModel ──(calls)──▶ Services / Repositories
View ◀──(state binding)── ViewModel ◀──(data)──
```

### Q27. What belongs where? `[Senior]`

| View | ViewModel | Model / Services |
| --- | --- | --- |
| Layout, styling, animation | Screen state (loading, content, error) | Entities, business rules |
| Forwarding user actions | Intents (`refresh()`, `submit()`) | Networking, persistence |
| Rendering state | Display formatting (dates, prices) | Rules shared across screens |
| UI-bound platform APIs (keyboard, haptics) | Screen-level input validation | Caching, sync |
|  | Emitting navigation intents |  |

Quick test: if it needs `UIKit`/`SwiftUI` types, it's the view. If another screen also needs it, it's a service or use case. Otherwise it's the view model.

### Q28. MVVM in UIKit `[Senior]`

```swift
@MainActor
final class LoginViewModel {
    struct State: Equatable {
        var email = ""
        var password = ""
        var isLoading = false
        var errorMessage: String?

        var isLoginEnabled: Bool {
            email.contains("@") && password.count >= 8 && !isLoading
        }
    }

    private(set) var state = State() {
        didSet { if state != oldValue { onStateChange?(state) } }   // skip no-op renders
    }

    var onStateChange: ((State) -> Void)?
    var onLoginSuccess: ((User) -> Void)?       // navigation event, handled by a coordinator

    private let authService: Authenticating
    init(authService: Authenticating) { self.authService = authService }

    func emailChanged(_ email: String) { state.email = email }
    func passwordChanged(_ password: String) { state.password = password }

    func loginTapped() async {
        guard state.isLoginEnabled else { return }   // also blocks double taps: isLoading is set before the first await
        state.isLoading = true
        state.errorMessage = nil
        defer { state.isLoading = false }

        do {
            let user = try await authService.login(email: state.email, password: state.password)
            onLoginSuccess?(user)
        } catch {
            state.errorMessage = String(localized: "Login failed. Check your email and password.")
        }
    }
}

final class LoginViewController: UIViewController {
    private let viewModel: LoginViewModel
    private let emailField = UITextField()
    private let passwordField = UITextField()
    private let loginButton = UIButton(configuration: .filled())
    private let errorLabel = UILabel()

    init(viewModel: LoginViewModel) {
        self.viewModel = viewModel
        super.init(nibName: nil, bundle: nil)
    }
    @available(*, unavailable) required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() {
        super.viewDidLoad()
        // (layout of the four subviews omitted)
        emailField.addAction(UIAction { [weak self] _ in
            self?.viewModel.emailChanged(self?.emailField.text ?? "")
        }, for: .editingChanged)
        passwordField.addAction(UIAction { [weak self] _ in
            self?.viewModel.passwordChanged(self?.passwordField.text ?? "")
        }, for: .editingChanged)
        loginButton.addAction(UIAction { [weak self] _ in
            Task { await self?.viewModel.loginTapped() }
        }, for: .touchUpInside)

        viewModel.onStateChange = { [weak self] in self?.render($0) }
        render(viewModel.state)
    }

    private func render(_ state: LoginViewModel.State) {
        loginButton.isEnabled = state.isLoginEnabled
        loginButton.configuration?.showsActivityIndicator = state.isLoading
        errorLabel.text = state.errorMessage
        errorLabel.isHidden = state.errorMessage == nil
    }
}
```

One `State` struct and one `render(_:)` keep the UI consistent with state, the same mental model as SwiftUI.

### Q29. Options for binding a view model to a view `[Senior]`

| Approach | Pros | Cons |
| --- | --- | --- |
| Closures (`onStateChange`) | Simple, no dependencies | Manual wiring; one listener |
| Delegate protocol | Explicit, familiar | Boilerplate |
| Combine (`@Published`) | Rich operators | Learning curve; Swift 6 `Sendable` friction |
| Observation (`@Observable`) | Automatic in SwiftUI; automatic UIKit tracking on iOS 18 (opt-in) and iOS 26 (default) | Needs a recent OS for UIKit |
| `AsyncStream` of states | Concurrency-native | Single consumer; manual lifecycle |

**New in UIKit (iOS 26):** UIKit tracks `@Observable` reads made in `updateProperties()` (and layout methods) and re-runs them when those properties change. No manual binding at all:

```swift
@MainActor @Observable
final class CounterModel { var count = 0 }

final class CounterViewController: UIViewController {
    private let model = CounterModel()
    private let label = UILabel()

    override func updateProperties() {      // iOS 26: called again when model.count changes
        super.updateProperties()
        label.text = "\(model.count)"
    }
}
// iOS 18: same tracking in viewWillLayoutSubviews/layoutSubviews
// after setting UIObservationTrackingEnabled = YES in Info.plist.
```

**Senior answer:** pick **one** binding approach per codebase and document it.

### Q30. MVVM in SwiftUI `[Fundamental]`

```swift
@MainActor @Observable
final class ProductListViewModel {
    enum State: Equatable { case loading, loaded([Product]), empty, failed(String) }

    private(set) var state: State = .loading
    private let repository: ProductRepository

    init(repository: ProductRepository) { self.repository = repository }

    func load() async {
        state = .loading
        do {
            let products = try await repository.products()
            state = products.isEmpty ? .empty : .loaded(products)
        } catch is CancellationError {
            // view disappeared; keep current state
        } catch {
            state = .failed(String(localized: "Couldn't load products."))
        }
    }
}

struct ProductListView: View {
    @State private var viewModel: ProductListViewModel      // FIX: private, created once

    init(repository: ProductRepository) {
        _viewModel = State(initialValue: ProductListViewModel(repository: repository))
    }

    var body: some View {
        Group {
            switch viewModel.state {
            case .loading: ProgressView()
            case .empty: ContentUnavailableView("No Products", systemImage: "bag")
            case .loaded(let products): List(products) { Text($0.name) }
            case .failed(let message):
                ContentUnavailableView {
                    Label(message, systemImage: "exclamationmark.triangle")
                } actions: {
                    Button("Retry") { Task { await viewModel.load() } }
                }
            }
        }
        .task { await viewModel.load() }     // cancelled automatically when the view disappears
    }
}

#Preview { ProductListView(repository: StubProductRepository(products: Product.samples)) }
```

**Pitfall worth mentioning:** `@State` keeps only the *first* value, but the `init` expression still runs on every parent re-render. Creating a heavy object there is wasted work (and side effects in its `init` would repeat). Keep view model `init`s cheap and start work in `.task`.

### Q31. The Input/Output view model pattern `[Lead/Expert]`

The view model exposes a pure `transform(input) -> output`; all inputs and outputs are streams. Popular in RxSwift/Combine codebases.

```swift
import Combine

final class MovieSearchViewModel {
    struct Input {
        let query: AnyPublisher<String, Never>
        let selection: AnyPublisher<Int, Never>
    }
    struct Output {
        let results: AnyPublisher<[Movie], Never>
        let selectedMovie: AnyPublisher<Movie, Never>
    }

    private let api: MovieAPI
    init(api: MovieAPI) { self.api = api }

    func transform(_ input: Input) -> Output {
        let results = input.query
            .debounce(for: .milliseconds(300), scheduler: DispatchQueue.main)
            .removeDuplicates()
            .map { [api] query in api.search(query).replaceError(with: []) }
            .switchToLatest()                 // cancels the previous request
            .share()
            .eraseToAnyPublisher()

        let selectedMovie = results
            .map { movies in input.selection.compactMap { movies[safe: $0] } }
            .switchToLatest()
            .eraseToAnyPublisher()

        return Output(results: results, selectedMovie: selectedMovie)
    }
}
```

The async/await equivalent of the debounced search uses `.task(id: query)` in SwiftUI with `try await Task.sleep(for: .milliseconds(300))`: changing `query` cancels the previous task automatically.

Trade-off: explicit and testable, but verbose and harder for newcomers than a state-based view model.

### Q32. Should a view model import UIKit or SwiftUI? `[Senior]`

Ideally **no**: only Foundation and domain types, so it works on iOS, macOS and widgets and tests without UI frameworks. Expose meaning, not visuals.

```swift
// ❌ View model decides visuals
var statusColor: UIColor { order.isLate ? .systemRed : .systemGreen }

// ✅ View model exposes meaning; the view maps it
enum OrderStatusStyle { case onTime, late }
var statusStyle: OrderStatusStyle { order.isLate ? .late : .onTime }

// In the view
extension OrderStatusStyle { var color: Color { self == .late ? .red : .green } }
```

Pragmatic exceptions: `Observation` is fine (not UI-specific); some SwiftUI-only teams accept `LocalizedStringResource`.

### Q33. Who handles navigation in MVVM? `[Senior]`

Not the view model directly. It **emits intents**; a coordinator (UIKit) or router (SwiftUI) acts on them.

```swift
final class ProductDetailViewModel {

    private let product: Product
    private let cart: CartStore

            try await cart.add(product)

    }
}
```

### Q34. How do you avoid massive view models? `[Senior]`

Split by section with child view models, and push rules into services.

```swift
@MainActor @Observable
final class ProductPageViewModel {
    let header: ProductHeaderViewModel         // title, price, images
    let reviews: ReviewsSectionViewModel       // paging, sorting
    let recommendations: RecommendationsViewModel

    init(productID: String, deps: ProductPageDependencies) {
        header = .init(productID: productID, repository: deps.products)
        reviews = .init(productID: productID, repository: deps.reviews)
        recommendations = .init(productID: productID, service: deps.recommendations)
    }

    func load() async {
        async let a: Void = header.load()
        async let b: Void = reviews.load()
        async let c: Void = recommendations.load()
        _ = await (a, b, c)                     // sections load in parallel
    }
}
```

Signals of a massive view model: over \~400 lines, more than 5–6 dependencies, state properties that are never read together.

### Q35. Pros and cons of MVVM `[Senior]`

| Pros | Cons |
| --- | --- |
| Presentation logic testable without UI | Binding boilerplate in UIKit (before iOS 26) |
| Clear view/logic separation | Can become a massive view model |
| Natural fit for SwiftUI + Observation | No standard navigation story |
| Familiar to most iOS engineers | Can duplicate state from shared stores in SwiftUI |

## 5. MVP

### Q36. What is MVP? `[Senior]`

**Model**, a **passive View** that implements a view protocol, and a **Presenter** that holds presentation logic and tells the view exactly what to show. The presenter holds a **weak** reference to the view protocol; the view controller holds the presenter strongly.

```swift
@MainActor
protocol ProductDetailView: AnyObject {
    func display(title: String, price: String)
    func setLoading(_ isLoading: Bool)
    func displayError(_ message: String)
}

struct PriceFormatter {
    let locale: Locale
    func format(_ value: Decimal) -> String {
        value.formatted(.currency(code: "USD").locale(locale))
    }
}

@MainActor
final class ProductDetailPresenter {
    weak var view: ProductDetailView?
    private let productID: String
    private let repository: ProductRepository
    private let priceFormatter: PriceFormatter

    init(productID: String, repository: ProductRepository, priceFormatter: PriceFormatter) {
        self.productID = productID
        self.repository = repository
        self.priceFormatter = priceFormatter
    }

    func viewDidLoad() async {
        view?.setLoading(true)
        defer { view?.setLoading(false) }
        do {
            let product = try await repository.product(id: productID)
            view?.display(title: product.name, price: priceFormatter.format(product.price))
        } catch {
            view?.displayError(String(localized: "Couldn't load the product."))
        }
    }
}

final class ProductDetailViewController: UIViewController, ProductDetailView {
    private let presenter: ProductDetailPresenter          // strong: the view owns the presenter
    private let titleLabel = UILabel(), priceLabel = UILabel()
    private let spinner = UIActivityIndicatorView(style: .medium)

    init(presenter: ProductDetailPresenter) {
        self.presenter = presenter
        super.init(nibName: nil, bundle: nil)
        presenter.view = self                              // weak back-reference
    }
    @available(*, unavailable) required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() {
        super.viewDidLoad()
        Task { await presenter.viewDidLoad() }
    }

    func display(title: String, price: String) { titleLabel.text = title; priceLabel.text = price }
    func setLoading(_ isLoading: Bool) { isLoading ? spinner.startAnimating() : spinner.stopAnimating() }
    func displayError(_ message: String) {
        let alert = UIAlertController(title: nil, message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default))
        present(alert, animated: true)
    }
}
```

Improvement over the original: constructor injection of the presenter instead of an implicitly unwrapped `var presenter: ProductDetailPresenter!`, which crashes if someone forgets to set it.

### Q37. MVP vs MVVM `[Senior]`

| MVP | MVVM |
| --- | --- |
| Presenter **knows** the view (through a protocol) and calls it imperatively | View model **doesn't know** the view; the view observes state |
| No binding mechanism needed | Needs binding (closures, Combine, Observation) |
| Tested with a spy view (records calls) | Tested by inspecting state |
| Natural for UIKit | Natural for SwiftUI |
| Order of calls matters (`setLoading` before `display`) | Only the final state matters |

One-liner for interviews: "In MVP the presenter **pushes** commands to the view; in MVVM the view **pulls** state from the view model."

## 6. VIPER & Clean Swift (VIP)

### Q39. What is VIPER? `[Senior]`

| Component | Responsibility |
| --- | --- |
| **V**iew | Displays what the presenter says; forwards user actions |
| **I**nteractor | Business logic for one use case; talks to services/repositories |
| **P**resenter | Formats data for the view; reacts to view events; asks the router to navigate |
| **E**ntity | Plain data models |
| **R**outer (Wireframe) | Navigation and module assembly |

```
View ⇄ Presenter ⇄ Interactor → Services/Repositories
          ↓
        Router → other modules
```

### Q40. A VIPER module skeleton `[Senior]`

```swift
// Entity
struct Article: Sendable, Equatable { let id: Int; let title: String }

protocol ArticleRepository: Sendable { func articles() async throws -> [Article] }

// Interactor: business logic
protocol ArticleListInteracting: Sendable {
    func fetchArticles() async throws -> [Article]
}

struct ArticleListInteractor: ArticleListInteracting {
    let repository: ArticleRepository
    func fetchArticles() async throws -> [Article] {
        try await repository.articles().filter { !$0.title.isEmpty }   // a business rule
    }
}

// View contract
@MainActor
protocol ArticleListViewProtocol: AnyObject {
    func show(titles: [String])
    func showError(_ message: String)
}

// Router: navigation + assembly
@MainActor
protocol ArticleListRouting { func showDetail(for article: Article) }

@MainActor
final class ArticleListRouter: ArticleListRouting {
    weak var viewController: UIViewController?

    static func makeModule(repository: ArticleRepository) -> UIViewController {
        let router = ArticleListRouter()
        let presenter = ArticleListPresenter(
            interactor: ArticleListInteractor(repository: repository), router: router)
        let view = ArticleListViewController(presenter: presenter)   // view → presenter (strong)
        presenter.view = view                                         // presenter → view (weak)
        router.viewController = view                                  // router → view (weak)
        return view
    }

    func showDetail(for article: Article) {
        viewController?.navigationController?.pushViewController(
            ArticleDetailRouter.makeModule(article: article), animated: true)
    }
}

// Presenter: presentation logic
@MainActor
final class ArticleListPresenter {
    weak var view: ArticleListViewProtocol?
    private let interactor: ArticleListInteracting
    private let router: ArticleListRouting
    private var articles: [Article] = []

    init(interactor: ArticleListInteracting, router: ArticleListRouting) {
        self.interactor = interactor
        self.router = router
    }

    func viewDidLoad() async {
        do {
            articles = try await interactor.fetchArticles()
            view?.show(titles: articles.map(\.title))
        } catch {
            view?.showError(String(localized: "Couldn't load articles."))
        }
    }

    func didSelectRow(at index: Int) {
        guard let article = articles[safe: index] else { return }      // FIX: bounds-safe
        router.showDetail(for: article)
    }
}

// View
final class ArticleListViewController: UITableViewController, ArticleListViewProtocol {
    private let presenter: ArticleListPresenter
    private var titles: [String] = []

    init(presenter: ArticleListPresenter) { self.presenter = presenter; super.init(style: .plain) }
    @available(*, unavailable) required init?(coder: NSCoder) { fatalError() }

    override func viewDidLoad() { super.viewDidLoad(); Task { await presenter.viewDidLoad() } }
    func show(titles: [String]) { self.titles = titles; tableView.reloadData() }
    func showError(_ message: String) { /* alert */ }
    override func tableView(_ t: UITableView, didSelectRowAt i: IndexPath) { presenter.didSelectRow(at: i.row) }
}
```

**Ownership (frequent follow-up):** the view owns the presenter; the presenter owns the interactor and router; back-references (presenter → view, router → view controller) are **weak**. Draw this on the whiteboard:

```
UINavigationController ──strong──▶ View ──strong──▶ Presenter ──strong──▶ Interactor
                                    ▲                   │  └────strong──▶ Router
                                    └──────weak─────────┘                   │
                                    ▲───────────────────weak────────────────┘
```

**Testing the presenter:** inject a stub interactor and a spy router, then assert `router.shownArticles == [article]` after `didSelectRow(at: 0)`.

### Q41. VIPER pros, cons, and fit `[Senior]`

| Pros | Cons |
| --- | --- |
| Very clear responsibilities | 5+ files and many protocols per screen |
| Highly testable components | Slow for simple screens |

### Q42. Clean Swift (VIP) and how it differs from VIPER `[Lead/Expert]`

VIP is a **one-way cycle**: View → Interactor → Presenter → View, with explicit `Request` / `Response` / `ViewModel` types per use case. A Router handles navigation and a Worker holds reusable business logic.

```swift
enum ListOrders {                          // one "scene" namespace per use case
    struct Request {}
    struct Response { let orders: [Order] }
    struct ViewModel { struct Row { let title: String; let subtitle: String }; let rows: [Row] }
}

@MainActor protocol ListOrdersBusinessLogic { func fetchOrders(_ request: ListOrders.Request) async }
@MainActor protocol ListOrdersPresentationLogic { func present(_ response: ListOrders.Response) }
@MainActor protocol ListOrdersDisplayLogic: AnyObject { func display(_ viewModel: ListOrders.ViewModel) }

@MainActor
final class ListOrdersInteractor: ListOrdersBusinessLogic {
    var presenter: ListOrdersPresentationLogic?
    let worker: OrdersWorker
    init(worker: OrdersWorker) { self.worker = worker }

    func fetchOrders(_ request: ListOrders.Request) async {
        let orders = (try? await worker.fetchOrders()) ?? []
        presenter?.present(.init(orders: orders))          // one direction only
    }
}

@MainActor
final class ListOrdersPresenter: ListOrdersPresentationLogic {
    weak var viewController: ListOrdersDisplayLogic?
    func present(_ response: ListOrders.Response) {
        let rows = response.orders.map { .init(title: $0.title, subtitle: $0.date.formatted(date: .abbreviated, time: .omitted)) }
        viewController?.display(.init(rows: rows))
    }
}
```

|  | VIPER | VIP (Clean Swift) |
| --- | --- | --- |
| Flow | Presenter in the middle, two-way | One-way cycle |
| Data types | Ad hoc | Request / Response / ViewModel per use case |
| Who calls the interactor | Presenter | View controller |

### Q43. Can VIPER be used with SwiftUI? `[Senior]`

Yes, but it fights the framework. The presenter becomes an observable object the view reads; the router can't push imperatively because SwiftUI navigation is state-driven.

```swift
@MainActor @Observable
final class ArticleListPresenterUI {
    private(set) var titles: [String] = []
    var path: [Article] = []                         // "router" collapses into navigation state
    private let interactor: ArticleListInteracting
    init(interactor: ArticleListInteracting) { self.interactor = interactor }

```

Notice the result is essentially MVVM with a use case. That's the honest answer: most SwiftUI teams use `@Observable` view models, MV, or TCA instead.

## 7. Clean Architecture

### Q44. What is Clean Architecture? `[Senior]`

Robert C. Martin's concentric-layer architecture with one rule: **source code dependencies point inward**, toward business rules. Inner layers define protocols (ports); outer layers implement them.

```
        ┌──────────────────────────────────────────┐
        │ Frameworks: UIKit/SwiftUI, URLSession,   │
        │  ┌────────────────────────────────────┐  │
        │  │ Adapters: ViewModels, Repositories │  │
        │  │  ┌──────────────────────────────┐  │  │
        │  │  │ Use Cases                    │  │  │
        │  │  │  ┌────────────────────────┐  │  │  │
        │  │  │  │ Entities               │  │  │  │
        │  │  │  └────────────────────────┘  │  │  │
        │  │  └──────────────────────────────┘  │  │
        │  └────────────────────────────────────┘  │
        └──────────────────────────────────────────┘
                 dependencies point inward →
```

**How to verify the rule:** the Domain target has no `import UIKit`, `SwiftUI`, `SwiftData` or vendor SDK, and it compiles and tests on its own (ideally even on Linux).

### Q45. Entities, use cases and repositories in Swift `[Senior]`

```swift
    let unitPrice: Decimal

}

}

// Use case: one application-specific operation with real rules
struct PlaceOrderUseCase: Sendable {

    let payments: PaymentGateway
    let cart: CartClearing

        guard !order.items.isEmpty else { throw OrderError.emptyCart }
        let token = try await payments.authorize(amount: order.total)
        let confirmation = try await orders.submit(order, paymentToken: token)
        await cart.clear()                                  // only after success
        return confirmation

// MARK: Data layer (implements domain ports)

    enum CodingKeys: String, CodingKey { case orderNumber = "order_number" }   // FIX: camelCase property

extension Endpoint where Response == OrderConfirmationDTO {

    }
}

@MainActor @Observable
```

### Q46. Do you always need a use case layer? `[Lead/Expert]`

No. Many use cases are **pass-throughs** that add a file and nothing else:

```swift
struct GetEligibleCouponsUseCase {
```

### Q47. Where do DTOs and mapping live? `[Senior]`

DTOs mirror the API and live in the **data layer**, which maps them to domain models before returning. See `ProductDTO` and `Product.init(dto:)` in Shared reference types.

### Q48. How do Clean Architecture and MVVM fit together? `[Senior]`

Different levels: MVVM organises the **presentation layer**; Clean Architecture organises the **whole app**. Combined: View → ViewModel → UseCase → Repository protocol ← Repository implementation → API/DB.

### Q49. Hexagonal architecture (ports and adapters) `[Lead/Expert]`

The core defines **ports**; **adapters** connect specific technologies. The same core is driven by many inputs and talks to many outputs.

### Q50. Risks of applying Clean Architecture strictly `[Lead/Expert]`

- Boilerplate explosion: protocol + implementation + use case + DTO + mapper for every trivial feature.
- Slower iteration and harder code navigation.
- Abstractions guessed upfront that don't match future needs.

**Senior answer:** keep the **dependency rule** (domain imports no frameworks) and put boundaries at **real seams** (network, persistence, SDKs). Add layers only where they pay for themselves, and say which ones you'd skip on a small team.

## 8. Unidirectional Data Flow, Redux & TCA

### Q51. What is unidirectional data flow? `[Senior]`

State flows one way: the view renders **state**; user events become **actions**; a **reducer** computes new state from (state, action); **effects** do side work and feed results back as actions.

```
        ┌──────── action ────────┐
        │                        ▼
      View                    Reducer ──▶ Effects (network, timers)
        ▲                        │              │
        └──────── state ◀────────┘◀── action ───┘
```

Benefits: one source of truth, every change is a logged action ("why is the cart empty?" → read the action log), reducers are pure functions you test with plain values.

### Q52. A minimal Redux-style store in Swift `[Lead/Expert]`

```swift
struct Effect<Action: Sendable>: Sendable {
    let run: @Sendable () async -> Action?
}

@MainActor @Observable
final class Store<State, Action: Sendable> {
    private(set) var state: State
    private let reduce: (inout State, Action) -> [Effect<Action>]

    init(initialState: State, reduce: @escaping (inout State, Action) -> [Effect<Action>]) {
        self.state = initialState
        self.reduce = reduce
    }

    func send(_ action: Action) {
        let effects = reduce(&state, action)          // pure, synchronous state transition
        for effect in effects {
            Task {                                    // inherits MainActor isolation
                if let next = await effect.run() { send(next) }
            }
        }
    }
}

struct CounterState: Equatable { var count = 0; var fact: String?; var isLoading = false }

enum CounterAction: Sendable, Equatable {
    case increment
    case factRequested
    case factLoaded(String)
}

protocol NumberFactAPI: Sendable { func fact(for n: Int) async throws -> String }

func counterReducer(api: NumberFactAPI) -> (inout CounterState, CounterAction) -> [Effect<CounterAction>] {
    { state, action in
        switch action {
        case .increment:
            state.count += 1
            return []
        case .factRequested:
            state.isLoading = true
            let number = state.count                  // capture a value, not state
            return [Effect { .factLoaded((try? await api.fact(for: number)) ?? "No fact") }]
        case .factLoaded(let fact):
            state.isLoading = false
            state.fact = fact
            return []
        }
    }
}
```

**Testing the reducer is plain function calls:**

```swift
@Test func incrementIsPure() {
    var state = CounterState()
    let effects = counterReducer(api: StubFactAPI())(&state, .increment)
    #expect(state.count == 1)
    #expect(effects.isEmpty)
}
```

### Q53. How are side effects handled? `[Lead/Expert]`

- Reducers stay **pure**: no network, no `Date.now`, no randomness. They return effect *descriptions*; the store runs them.
- Effect dependencies (API, clock, UUID) are **injected**, so tests control time and responses.
- Effects need **IDs for cancellation**. Example: cancel the previous search when a new query arrives.

```swift
// Cancellation in the hand-rolled store: keep tasks by ID
@MainActor
final class EffectRunner<Action: Sendable> {
    private var tasks: [String: Task<Void, Never>] = [:]

    func run(id: String, _ work: @escaping @Sendable () async -> Action?, send: @escaping @MainActor (Action) -> Void) {
        tasks[id]?.cancel()                               // cancel in-flight effect with same ID
        tasks[id] = Task {
            guard let action = await work(), !Task.isCancelled else { return }
            send(action)
        }
    }
}
// In TCA: return .run { ... }.cancellable(id: CancelID.search, cancelInFlight: true)
```

### Q54. What is The Composable Architecture (TCA)? `[Lead/Expert]`

A Point-Free library implementing UDF with **State**, **Action**, **Reducer**, **Effects**, a **Store**, dependency management, feature composition, navigation tools and exhaustive testing.

```swift
import ComposableArchitecture
import SwiftUI

@Reducer
struct CounterFeature {
    @ObservableState
    struct State: Equatable {
        var count = 0
        var fact: String?
        var isLoading = false
        var errorMessage: String?
    }

    enum Action {
        case incrementTapped
        case factButtonTapped
        case factResponse(String)
        case factFailed                                     // FIX: handle errors
    }

    @Dependency(\.numberFact) var numberFact

    var body: some ReducerOf<Self> {
        Reduce { state, action in
            switch action {
            case .incrementTapped:
                state.count += 1
                state.fact = nil
                return .none

            case .factButtonTapped:
                state.isLoading = true
                state.errorMessage = nil
                return .run { [count = state.count] send in
                    await send(.factResponse(try await numberFact.fetch(count)))
                } catch: { _, send in
                    await send(.factFailed)                 // FIX: otherwise UI stays loading
                }

            case let .factResponse(fact):
                state.isLoading = false
                state.fact = fact
                return .none

            case .factFailed:
                state.isLoading = false
                state.errorMessage = "Couldn't load a fact."
                return .none
            }
        }
    }
}

struct CounterView: View {
    let store: StoreOf<CounterFeature>

    var body: some View {
        VStack(spacing: 12) {
            Text("\(store.count)").font(.largeTitle)
            Button("Increment") { store.send(.incrementTapped) }
            Button("Get fact") { store.send(.factButtonTapped) }
            if store.isLoading { ProgressView() }
            if let fact = store.fact { Text(fact) }
            if let error = store.errorMessage { Text(error).foregroundStyle(.red) }
        }
    }
}
```

(TCA 1.x syntax. Check the current major version before the interview.)

**Composition** is the main reason teams pick TCA. A parent embeds a child with `Scope`:

```swift
@Reducer
struct AppFeature {
    @ObservableState struct State: Equatable { var counter = CounterFeature.State() }
    enum Action { case counter(CounterFeature.Action) }
    var body: some ReducerOf<Self> {
        Scope(state: \.counter, action: \.counter) { CounterFeature() }
        Reduce { state, action in .none }                 // parent can observe child actions here
    }
}
// View: CounterView(store: store.scope(state: \.counter, action: \.counter))
```

### Q55. Dependencies and testing in TCA `[Lead/Expert]`

```swift
struct NumberFactClient: Sendable {
    var fetch: @Sendable (Int) async throws -> String
}

extension NumberFactClient: DependencyKey {
    static let liveValue = NumberFactClient { number in
        // Note: numbersapi.com is HTTP-only, which needs an App Transport Security exception.
        let url = URL(string: "http://numbersapi.com/\(number)")!
        let (data, _) = try await URLSession.shared.data(from: url)
        return String(decoding: data, as: UTF8.self)
    }
    static let testValue = NumberFactClient(fetch: unimplemented("NumberFactClient.fetch"))
}

extension DependencyValues {
    var numberFact: NumberFactClient {
        get { self[NumberFactClient.self] }
        set { self[NumberFactClient.self] = newValue }
    }
}

@MainActor
@Test func factFlow() async {
    let store = TestStore(initialState: CounterFeature.State()) {
        CounterFeature()
    } withDependencies: {
        $0.numberFact.fetch = { "\($0) is a good number." }
    }

    await store.send(.incrementTapped) { $0.count = 1 }
    await store.send(.factButtonTapped) { $0.isLoading = true }
    await store.receive(\.factResponse) {
        $0.isLoading = false
        $0.fact = "1 is a good number."
    }
}

@MainActor
@Test func factFailure() async {
    struct Boom: Error {}
    let store = TestStore(initialState: CounterFeature.State()) { CounterFeature() }
```

### Q56. TCA pros and cons `[Lead/Expert]`

| Pros | Cons |
| --- | --- |
| Predictable changes; single source of truth | Steep learning curve |
| Exhaustive, deterministic tests | Third-party dependency; major-version migrations |
| Composition and modularity built in | Verbose for simple screens |
| DI, navigation, effect cancellation included | Compile-time cost in very large reducers |
| Strong docs and community | Needs team-wide buy-in |

### Q57. MVVM vs TCA `[Lead/Expert]`

|  | MVVM (`@Observable`) | TCA |
| --- | --- | --- |
| State | View model properties | `State` struct |
| Mutations | Methods mutate directly | Only reducers, via actions |
| Side effects | `async` methods | Effects run by the store |
| Testing | Call methods, assert state | `TestStore`, exhaustive |
| Composition | Manual child view models | `Scope`, child features |
| Learning curve | Low | High |
| Dependencies | Apple frameworks only | Library |

**Senior answer:** MVVM is a strong default; TCA pays off with complex shared state, deeply composed features, and a team that values exhaustive tests and will invest in the library.

### Q58. When would you avoid unidirectional architectures? `[Senior]`

- Small apps or inexperienced teams: ceremony outweighs benefit.
- Very hot paths (every keystroke or scroll offset through a store); mitigate by keeping such state local (`@State`) and scoping stores.
- Codebases committed to another pattern, where partial adoption creates two mental models.

## 9. SwiftUI-Native Architecture ("MV")

### Q59. What is the "MV" pattern? `[Senior]`

Views bind **directly** to observable models (domain stores/services) shared through the environment, with no per-screen view model. Views keep only local UI state (`@State`). Rationale: a SwiftUI view already derives UI from state, so an extra layer can duplicate state.

```swift
protocol CartAPI: Sendable { func add(productID: String) async throws -> [CartItem] }

@MainActor @Observable
final class CartStore {                         // app-level model: state + domain logic
    private(set) var items: [CartItem] = []
    private let api: CartAPI

    init(api: CartAPI) { self.api = api }

    var total: Decimal { items.reduce(0) { $0 + $1.price * Decimal($1.quantity) } }

    func add(_ product: Product) async throws {
        items = try await api.add(productID: product.id)
    }
}

struct CartBadge: View {
    @Environment(CartStore.self) private var cart
    var body: some View { Text("\(cart.items.count)") }
}

struct ProductRow: View {
    @Environment(CartStore.self) private var cart
    @State private var isAdding = false             // local UI state only
    @State private var addFailed = false
    let product: Product

    var body: some View {
        Button(isAdding ? "Adding…" : "Add to cart") {
            Task {
                isAdding = true
                defer { isAdding = false }
                do { try await cart.add(product) }
                catch { addFailed = true }           // FIX: error surfaced, not swallowed by try?
            }
        }
        .disabled(isAdding)
        .alert("Couldn't add to cart", isPresented: $addFailed) { Button("OK") {} }
    }
}

// Composition root
@main
struct ShopApp: App {
    @State private var cart = CartStore(api: LiveCartAPI())
    var body: some Scene {
        WindowGroup { RootView().environment(cart) }
    }
}
```

### Q60. Where does business logic go without view models? `[Senior]`

In **observable stores** (`CartStore`, `SessionStore`) and the **services** they use, shared across screens and tested directly. Simple screen logic stays in the view; when it grows (multi-step form, validation, coordinating several stores) introduce a screen model.

```swift
// A multi-step form outgrew @State → a screen model (a view model by another name)
@MainActor @Observable
final class CheckoutFormModel {
    var step: Step = .address
    var address = Address()
    var card = CardInput()
    enum Step { case address, payment, review }

    var canContinue: Bool {
        switch step {
        case .address: address.isComplete
        case .payment: card.isValid
        case .review: true
        }
    }
    func next() { step = step == .address ? .payment : .review }
}
```

### Q61. MV vs MVVM trade-offs `[Lead/Expert]`

| MV (models in environment) | MVVM (view model per screen) |
| --- | --- |
| Less code, no duplicated state | Clear home for screen logic |
| Shared stores keep screens consistent | Screen logic tested in isolation |
| Screen logic can leak into views | Risk of copying state from shared stores |
| Environment dependencies implicit (crash if missing) | Dependencies explicit via `init` |

Most teams use a **hybrid**: shared stores for app-wide state, view models only for complex screens. Say this explicitly; it signals pragmatism.

**State duplication pitfall in MVVM:**

```swift
// ❌ The view model copies cart items: now two sources of truth that drift

// ✅ Derive from the shared store instead of copying
@MainActor @Observable final class CartScreenVM {
    let cart: CartStore
    init(cart: CartStore) { self.cart = cart }
    var subtotalText: String { cart.total.formatted(.currency(code: "USD")) }  // derived, never stale
}
```

## 10. Navigation Architecture

### Q63. Why decouple navigation from screens? Show a coordinator. `[Senior]`

Screens that push other screens know about each other: tight coupling, hard reuse, hard deep linking, hard A/B tests of flows. Centralise it: screens emit **intents**; a coordinator decides **where to go**.

```swift
@MainActor
protocol Coordinator: AnyObject {
    var childCoordinators: [Coordinator] { get set }
    func start()
}

extension Coordinator {
    func addChild(_ child: Coordinator) { childCoordinators.append(child) }
    func removeChild(_ child: Coordinator) { childCoordinators.removeAll { $0 === child } }
}

@MainActor
final class CatalogCoordinator: Coordinator {
    var childCoordinators: [Coordinator] = []
    private let navigationController: UINavigationController
    private let factory: CatalogScreenFactory               // Q74

    init(navigationController: UINavigationController, factory: CatalogScreenFactory) {
        self.navigationController = navigationController
        self.factory = factory
    }

    func start() {
        let list = factory.makeProductList { [weak self] id in self?.showDetail(id) }
        navigationController.setViewControllers([list], animated: false)
    }

    private func showDetail(_ id: Product.ID) {
        navigationController.pushViewController(factory.makeProductDetail(productID: id), animated: true)
    }
}
```

The product list doesn't know the detail screen exists. Swap the flow (e.g. present detail as a sheet on iPad) by changing one method.

### Q64. How do coordinators return results from a flow? `[Lead/Expert]`

A child flow exposes a completion (or an `async` result) to its parent, which removes the child when it finishes.

```swift
@MainActor
final class AddressPickerFlow: NSObject, UIAdaptivePresentationControllerDelegate {
    private let presenter: UIViewController
    private var continuation: CheckedContinuation<Address?, Never>?

    init(presenter: UIViewController) { self.presenter = presenter }

    /// Presents the picker; returns the chosen address, or nil if cancelled/swiped away.
    func run() async -> Address? {
        await withCheckedContinuation { continuation in
            self.continuation = continuation

            let picker = AddressPickerViewController()
            picker.onComplete = { [weak self] address in
                self?.presenter.dismiss(animated: true)
                self?.finish(with: address)
            }

            let navigation = UINavigationController(rootViewController: picker)
            navigation.presentationController?.delegate = self    // swipe-to-dismiss
            presenter.present(navigation, animated: true)
        }
    }

    func presentationControllerDidDismiss(_ presentationController: UIPresentationController) {
        finish(with: nil)
    }

    private func finish(with address: Address?) {
        continuation?.resume(returning: address)    // resume exactly once
        continuation = nil
    }
}

// Usage in a coordinator
if let address = await AddressPickerFlow(presenter: checkoutViewController).run() {
    checkoutViewModel.setShippingAddress(address)
}
```

**Edge cases to mention:** a checked continuation must resume exactly once (resuming twice traps; never resuming leaks the awaiting task). If the parent task can be cancelled, wrap `run()` in `withTaskCancellationHandler` and dismiss + `finish(with: nil)` on cancel. The `await` keeps the flow object alive while it runs.

### Q65. Navigation architecture in SwiftUI `[Senior]`

Navigation is **data**: a router owns a `NavigationStack` path of typed routes, plus sheet state. One path per tab. Features expose route enums; the app maps routes to views.

```swift
enum HomeRoute: Hashable, Codable { case product(id: String), cart }

@MainActor @Observable
final class AppRouter {
    enum Tab: Hashable { case home, search, profile }
    enum Sheet: Identifiable, Hashable {
        case login, share(URL)
        var id: Self { self }
    }

    var selectedTab: Tab = .home
    var homePath: [HomeRoute] = []
    var sheet: Sheet?

    func open(_ link: DeepLink) {
        sheet = nil
        switch link {
        case .product(let id): selectedTab = .home; homePath = [.product(id: id)]
        case .cart:            selectedTab = .home; homePath = [.cart]
        case .order, .settings: selectedTab = .profile   // profile router handles the rest
        }
    }
}

struct HomeTab: View {
    @Environment(AppRouter.self) private var router

    var body: some View {
        @Bindable var router = router
        NavigationStack(path: $router.homePath) {
            HomeView()
                .navigationDestination(for: HomeRoute.self) { route in
                    switch route {
                    case .product(let id): ProductDetailView(productID: id)
                    case .cart: CartView()
                    }
                }
        }
        .sheet(item: $router.sheet) { sheet in
            switch sheet {
            case .login: LoginView()
            case .share(let url): ShareLink(item: url)
            }
        }
    }
}
```

### Q66. Deep link handling `[Lead/Expert]`

```swift
enum DeepLink: Equatable {
    case product(id: String)
    case cart
    case order(id: String)
    case settings(section: String?)

    /// Handles myshop://product/42 AND https://shop.example.com/product/42 (universal link)
    init?(url: URL) {
        guard let components = URLComponents(url: url, resolvingAgainstBaseURL: false) else { return nil }
        var parts = components.path.split(separator: "/").map(String.init)

        switch components.scheme {
        case "myshop":                                       // host is the first segment
            guard let host = components.host else { return nil }
            parts.insert(host, at: 0)
        case "https" where components.host == "shop.example.com":
            break                                            // FIX: universal links
        default:
            return nil
        }

        switch (parts.first, parts.dropFirst().first) {
        case ("product"?, let id?): self = .product(id: id)
        case ("cart"?, _):          self = .cart
        case ("order"?, let id?):   self = .order(id: id)
        case ("settings"?, let s):  self = .settings(section: s)
        default:                    return nil
        }
    }
}

@Test(arguments: [
    ("myshop://product/42", DeepLink.product(id: "42")),
    ("https://shop.example.com/product/42", .product(id: "42")),
    ("myshop://settings", .settings(section: nil)),
])
func parsesLinks(url: String, expected: DeepLink) {
    #expect(DeepLink(url: URL(string: url)!) == expected)
}
```

**Talking points:**

- **Parse at the edge** (`onOpenURL`, scene delegate, push handler, widget URL) into one typed enum; the parser is pure and unit-tested.
- **Route centrally:** the root router dismisses modals, selects the tab, builds the stack.
- **Auth gating:** if login is needed, store the pending link, show login, replay after success (Q68).
- One `DeepLink` type for cold start, warm start, universal links, push, widgets and Spotlight.

### Q68. Authentication-gated navigation `[Senior]`

```swift
@MainActor
protocol AuthGate {

@MainActor @Observable
```

## 11. Dependency Injection

### Q71. What is dependency injection and why does it matter? `[Fundamental]`

Giving an object its dependencies **from outside** instead of having it create or look them up. Benefits: testability, swappable implementations per environment, explicit dependencies, looser coupling.

```swift
// ❌ Hidden, hard-coded dependencies
@MainActor
final class SettingsViewModel {
    private let api = APIClient.shared
    private let defaults = UserDefaults.standard
}

// ✅ Injected dependencies, visible in the initializer
@MainActor
final class SettingsViewModelInjected {
    private let api: SettingsAPI
    private let preferences: PreferencesStore
    init(api: SettingsAPI, preferences: PreferencesStore) {
        self.api = api
        self.preferences = preferences
    }
}
```

### Q72. Types of dependency injection `[Fundamental]`

```swift
// 1. Constructor injection (default): required, immutable
final class OrdersVM { private let repo: OrdersLoading; init(repo: OrdersLoading) { self.repo = repo } }

// 2. Property injection: storyboard-created objects, optional deps, breaking cycles
final class LegacyVC: UIViewController { var analytics: AnalyticsTracking = NoOpAnalytics() }  // safe default, no `!`

// 3. Method injection: dependency used by one operation or varies per call
struct ReceiptRenderer { func render(_ order: Order, using formatter: PriceFormatter) -> String { "" } }

// 4. Ambient / environment: cross-cutting values deep in a hierarchy
extension EnvironmentValues { @Entry var analytics: AnalyticsTracking = NoOpAnalytics() }
struct BuyButton: View {
    @Environment(\.analytics) private var analytics
    var body: some View { Button("Buy") { analytics.track(.init(name: "buy", parameters: [:])) } }
}
```

| Type | When |
| --- | --- |
| Constructor | Default whenever you control creation |
| Property | Storyboards, optional deps, cycles (give it a safe default) |
| Method | One-off or per-call dependency |
| Environment | Cross-cutting values used deep in SwiftUI trees |

### Q75. What is a DI container? `[Senior]`

```swift
@MainActor
final class Container {
    private var factories: [ObjectIdentifier: () -> Any] = [:]
    private var singletons: [ObjectIdentifier: Any] = [:]

    func register<T>(_ type: T.Type, factory: @escaping () -> T) {
        factories[ObjectIdentifier(type)] = factory
    }

    func registerSingleton<T>(_ type: T.Type, factory: @escaping () -> T) {
        let key = ObjectIdentifier(type)
        factories[key] = { [unowned self] in
            if let existing = singletons[key] { return existing }
            let made = factory(); singletons[key] = made; return made
        }
    }

    func resolve<T>(_ type: T.Type = T.self) -> T {
        guard let instance = factories[ObjectIdentifier(type)]?() as? T else {
            fatalError("No registration for \(T.self)")       // runtime, not compile time
        }
        return instance
    }
}

let container = Container()
container.registerSingleton(APIClient.self) { APIClient(baseURL: URL(string: "https://api.example.com")!) }
container.register(ProductRepository.self) { RemoteProductRepository(client: container.resolve()) }
```

| Pros | Cons |
| --- | --- |
| Central registration; easy swaps | Missing registration crashes at **runtime** |
| Lifetimes (singleton, transient) | Dependencies implicit if `resolve` is everywhere |
| Less manual wiring in big graphs | Another abstraction to learn |

Libraries: Swinject (runtime), Factory (property-wrapper based), swift-dependencies (Point-Free), Needle (compile-time safe, code generation).

### Q76. Why is a Service Locator an anti-pattern? `[Senior]`

Any object can fetch dependencies globally, so they're **hidden** in implementation code. Tests must configure global state (parallel tests interfere); missing registrations crash at runtime.

```swift
// ❌ Service locator inside business code
final class CheckoutViewModel {
    func pay() async {
        let gateway = Container.shared.resolve(PaymentGateway.self)   // hidden dependency
    }
}

// ✅ Explicit dependency; resolve from the container only at the composition root
final class CheckoutViewModelExplicit {
    private let gateway: PaymentGateway
    init(gateway: PaymentGateway) { self.gateway = gateway }
}
```

The line to draw: a container used **only at the composition root** is fine; used **inside** view models and services, it's a service locator.

## 12. Modularization

### Q82. Why modularize an iOS app? `[Senior]`

- **Build times:** incremental builds recompile only changed modules; modules compile in parallel.
- **Boundaries:** access control (`public`/`package`/`internal`) enforces architecture at compile time.
- **Ownership:** teams own modules; fewer merge conflicts.
- **Reuse:** share code between app, widgets, App Clips, watchOS, extensions.
- **Fast feedback:** small targets build and preview quickly; feature demo apps.

Cost: setup, dependency-graph management, and possible launch-time impact from many dynamic frameworks (Q86).

**Concrete example:** a widget extension needs `Models` and `Networking`, not the whole app. Without modules you duplicate files into the widget target; with modules it depends on two small libraries.

### Q83. How do you split modules? `[Lead/Expert]`

- **Horizontal (by layer):** `Networking`, `Persistence`, `DesignSystem`, `Analytics`, `Models`.
- **Vertical (by feature):** `CatalogFeature`, `CartFeature`, `ProfileFeature`.
- Mature apps combine both: foundation at the bottom, features in the middle, a thin app target on top.

```
                    App (composition root, navigation wiring)
          ┌──────────────┼──────────────┬───────────────┐
   CatalogFeature   CartFeature   ProfileFeature   CheckoutFeature
          │    ╲         │    ╱          │               │
          │   CartInterface (protocols)  │               │
          └──────────────┴───────┬───────┴───────────────┘
        DesignSystem · Networking · Persistence · Analytics · Models
```

Rule of thumb for granularity: a module should be something one team can own and that changes for one reason. If two modules always change together, merge them.

### Q85. Interface (API) modules `[Lead/Expert]`

A lightweight module with only **protocols and shared types** for a feature, separate from its implementation.

### Q86. Static vs dynamic linking `[Lead/Expert]`

| Static | Dynamic |
| --- | --- |
| Linked into the binary at build time | Loaded at launch by dyld |
| Faster launch | Each framework adds launch cost |
| Can be duplicated across app + extensions | Shared between app and extensions |
| Usual result for SwiftPM `.automatic` libraries | Explicit `.dynamic` product type |

Xcode 15+ **mergeable libraries** let you build dynamic frameworks in debug (fast iteration) and merge them into the app binary in release (fast launch).

### Q87. Access levels in modular architecture `[Senior]`

```swift
// Networking module
public struct APIClient { public func send<R>(_ e: Endpoint<R>) async throws -> R { /* ... */ } }  // the API
package func makeDebugLogger() -> Logger { Logger() }   // visible to other targets in this package only
struct RetryPolicy { }                                   // internal: implementation detail
open class BaseRequestOperation { }                       // only if subclassing outside is intended
```

- `internal` (default): hidden in the module.
- `public`: the module's API. Everything public is a commitment; keep it small.
- `package` (Swift 5.9): shared across modules in the **same package**, not external clients.
- `open`: subclassable outside the module.

Rule: start `internal`, promote deliberately.

### Q93. Caching policies in a repository `[Senior]`

```swift
enum CachePolicy { case cacheFirst, networkFirst, cacheOnly, networkOnly }

protocol ProductAPI: Sendable { func fetchProducts() async throws -> [ProductDTO] }
protocol ProductStore: Sendable {
    func products() async throws -> [Product]
    func replaceAll(with products: [Product]) async throws
}

actor CachedProductRepository {
    private let api: ProductAPI
    private let store: ProductStore

    init(api: ProductAPI, store: ProductStore) { self.api = api; self.store = store }

    func products(policy: CachePolicy = .cacheFirst) async throws -> [Product] {
        switch policy {
        case .cacheOnly: return try await store.products()
        case .networkOnly: return try await refresh()
        case .cacheFirst:
            let cached = try await store.products()
            return cached.isEmpty ? try await refresh() : cached
        case .networkFirst:
            do { return try await refresh() }
            catch { return try await store.products() }
        }
    }

    /// Stale-while-revalidate: emit cache immediately, then fresh data.
    nonisolated func productsStream() -> AsyncThrowingStream<[Product], Error> {
        AsyncThrowingStream { continuation in
            let task = Task {
                do {
                    let cached = try await self.store.products()
                    if !cached.isEmpty { continuation.yield(cached) }
                    continuation.yield(try await self.refresh())
                    continuation.finish()
                } catch { continuation.finish(throwing: error) }
            }
            continuation.onTermination = { _ in task.cancel() }
        }
    }

    private func refresh() async throws -> [Product] {
        let fresh = try await api.fetchProducts().map(Product.init(dto:))
        try await store.replaceAll(with: fresh)
        return fresh
    }
}
```

Consumer: `for try await products in repo.productsStream() { state = .loaded(products) }` shows cached data instantly, then updates.

### Q95. Architecting an offline-first app `[Lead/Expert]`

```
UI ──reads──▶ Local DB (source of truth) ◀──writes── SyncEngine (actor)
UI ──writes─▶ Local DB + Outbox ────────────────────▶ push (retry, idempotency key)
                                     server ──pull (cursor)──▶ upsert / delete
```

```swift
struct PendingMutation: Codable, Sendable, Identifiable {
    let id: UUID                        // doubles as the idempotency key
    let kind: Kind
    let payload: Data
    var attempts = 0
    enum Kind: String, Codable, Sendable { case createNote, updateNote, deleteNote }
}

protocol OutboxStore: Sendable {
    func pending() async throws -> [PendingMutation]
    func remove(_ id: UUID) async throws
    func update(_ m: PendingMutation) async throws
}

protocol SyncAPI: Sendable {
    func push(_ m: PendingMutation) async throws          // server dedupes by m.id
    func pull(since cursor: String?) async throws -> (changes: [NoteChange], cursor: String)
}

actor SyncEngine {
    private let api: SyncAPI
    private let outbox: OutboxStore
    private let db: NotesDatabase
    private var cursor: String?
    private var isSyncing = false

    init(api: SyncAPI, outbox: OutboxStore, db: NotesDatabase) { self.api = api; self.outbox = outbox; self.db = db }

    func sync() async {
        guard !isSyncing else { return }       // actor reentrancy: guard before the first await
        isSyncing = true
        defer { isSyncing = false }

        // 1. Push local changes in order
        for var mutation in (try? await outbox.pending()) ?? [] {
            do {
                try await api.push(mutation)
                try await outbox.remove(mutation.id)
            } catch {
                mutation.attempts += 1
                try? await outbox.update(mutation)
                break                            // keep order; retry later with backoff
            }
        }
        // 2. Pull server changes
        if let result = try? await api.pull(since: cursor) {
            await db.apply(result.changes, conflictPolicy: .serverWinsUnlessLocalPending)
            cursor = result.cursor
        }
    }
}
```

Talking points: optimistic UI (write locally first), conflict policy (server wins / last-write-wins / field merge), `NWPathMonitor` triggers, `BGAppRefreshTask`, clear UI states (syncing, offline, failed), deterministic tests with injected API and clock.

```swift
        nextCursor = nil
        await load(replacing: true)
    }

    func onAppear(of post: Post) async {
        guard post.id == posts.last?.id, phase == .idle else { return }   // also blocks concurrent loads
        phase = .loadingMore
        await load(replacing: false)

    private func load(replacing: Bool) async {

            let page = try await repository.feed(cursor: nextCursor)
            if replacing { posts = page.items }
            else {
                let existing = Set(posts.map(\.id))
                posts += page.items.filter { !existing.contains($0.id) }      // dedupe
            }
            nextCursor = page.nextCursor
            phase = page.hasMore ? .idle : .exhausted
        } catch {
            phase = .failed(String(localized: "Couldn't load more posts."))   // FIX: not swallowed
        }
    }
```

### Q102. Where do authentication and token refresh live? `[Lead/Expert]`

In the **networking layer**, never in view models. The classic bug: five requests get 401 at once and fire five refreshes. An actor that shares one in-flight refresh task fixes it.

```swift
struct Token: Codable, Sendable {
    let accessToken: String
    let refreshToken: String
    let expiresAt: Date
    var isValid: Bool { expiresAt > .now.addingTimeInterval(30) }      // 30 s safety margin
}

enum AuthError: Error { case notLoggedIn, refreshFailed }

actor TokenStore {
    private let keychain: KeychainStoring
    private let refresher: @Sendable (String) async throws -> Token
    private var refreshTask: Task<Token, Error>?

    init(keychain: KeychainStoring, refresher: @escaping @Sendable (String) async throws -> Token) {
        self.keychain = keychain
        self.refresher = refresher
    }

    func validToken() async throws -> Token {
        if let task = refreshTask { return try await task.value }      // join the in-flight refresh
        guard let token = keychain.loadToken() else { throw AuthError.notLoggedIn }
        if token.isValid { return token }
        return try await refresh(using: token.refreshToken)
    }

    func forceRefresh() async throws -> Token {                         // after a 401
        if let task = refreshTask { return try await task.value }
        guard let token = keychain.loadToken() else { throw AuthError.notLoggedIn }
        return try await refresh(using: token.refreshToken)
    }

    private func refresh(using refreshToken: String) async throws -> Token {
        let task = Task { try await refresher(refreshToken) }
        refreshTask = task                       // set BEFORE awaiting: reentrancy-safe
        defer { refreshTask = nil }
        do {
            let new = try await task.value
            keychain.save(new)
            return new
        } catch {
            keychain.deleteToken()
            throw AuthError.refreshFailed        // app layer observes → logout + show login
        }
    }
}
```

- Retry the original request **once** after a successful refresh; never loop.
- On refresh failure emit **session expired**; the app layer logs out. The networking layer never presents UI.
- Tokens live in the **Keychain**, never `UserDefaults`.

### Q104. Staying resilient to API changes `[Lead/Expert]`

```swift
// 1. Unknown enum values don't fail the whole payload
enum OrderStatus: String, Decodable, Sendable {
    case pending, shipped, delivered, unknown
    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)
        self = OrderStatus(rawValue: raw) ?? .unknown
    }
}

// 2. Lossy arrays: skip invalid elements instead of failing the list
struct LossyArray<Element: Decodable>: Decodable {
    var elements: [Element] = []
    init(from decoder: Decoder) throws {
        var container = try decoder.unkeyedContainer()
        while !container.isAtEnd {
            if let element = try? container.decode(Element.self) { elements.append(element) }
            else { _ = try? container.decode(AnyDecodable.self) }   // advance past the bad element
        }
    }
}
private struct AnyDecodable: Decodable {}
```

- **Tolerant decoding:** optionals where the server may omit fields; `.unknown` enum fallbacks; lossy arrays (log what was skipped).
- **Versioning:** app version header; `/v2/` paths; coordinated deprecations.
- **Feature flags / remote config** to switch off features on unstable endpoints.
- **Minimum supported version** / force-update screen for breaking changes.
- **Contract tests** or OpenAPI code generation (e.g. Swift OpenAPI Generator) to catch mismatches early.

## 16. Cross-Cutting Concerns (Errors, Logging, Feature Flags, Concurrency)

### Q111. Error handling across layers `[Lead/Expert]`

- **Data layer:** catch transport/decoding/HTTP errors, map to **domain errors**.
- **Domain:** business errors (`paymentDeclined`, `outOfStock`).
- **Presentation:** map domain errors to **user-facing state** (message + retry). Never show raw technical errors.
- **Cross-cutting:** log technical detail (privacy-aware), report non-fatals.

```swift
// Domain
enum CheckoutError: Error, Equatable {
    case offline
    case paymentDeclined
    case itemUnavailable(productID: String)
    case unknown
}

// Data layer mapping
private struct APIErrorBody: Decodable { let code: String; let productId: String? }

extension CheckoutError {
    init(_ error: Error) {
        switch error {
        case let urlError as URLError
            where [.notConnectedToInternet, .networkConnectionLost, .timedOut].contains(urlError.code):
            self = .offline                                            // FIX: more connectivity codes
        case APIError.httpStatus(402, _):
            self = .paymentDeclined
        case APIError.httpStatus(409, let data):
            // FIX: decode a structured error body instead of treating raw bytes as an ID
            if let body = try? JSONDecoder().decode(APIErrorBody.self, from: data), let id = body.productId {
                self = .itemUnavailable(productID: id)
            } else {
                self = .unknown
            }
        default:
            self = .unknown
        }
    }
}

// Presentation mapping (localised)
extension CheckoutError {
    var userMessage: String {
        switch self {
        case .offline: String(localized: "You're offline. Check your connection and try again.")
        case .paymentDeclined: String(localized: "Your payment was declined. Try another card.")
        case .itemUnavailable: String(localized: "An item in your cart is no longer available.")
        case .unknown: String(localized: "Something went wrong. Please try again.")
        }
    }
    var isRetryable: Bool { self == .offline || self == .unknown }
}
```

Swift 6 also offers **typed throws** (`func submit() throws(CheckoutError)`), useful at internal boundaries where the error set is closed. Keep untyped `throws` at public module APIs so new error cases don't break clients.

### Q115. Feature flags and remote config `[Senior]`

### Q116. What makes code testable? `[Fundamental]`

### Q120. Protocols vs closure-based dependencies `[Lead/Expert]`

```swift
// Protocol-based
protocol WeatherService: Sendable { func forecast(for city: String) async throws -> Forecast }

// Closure-based ("struct of closures")
struct WeatherClient: Sendable {
    var forecast: @Sendable (_ city: String) async throws -> Forecast
}

extension WeatherClient {
    static let live = WeatherClient { city in try await LiveWeatherAPI().fetchForecast(city: city) }
    static let sunny = WeatherClient { _ in .sample }
    static let failing = WeatherClient { _ in throw URLError(.notConnectedToInternet) }

client.forecast = { _ in Forecast(temperature: 30, condition: .sunny) }
```

| Protocols | Closure structs |
| --- | --- |
| Familiar; good for stateful objects | Lightweight; no new type per double |
| New type per mock | Override single endpoints inline |
| Natural for several full implementations | Easy variants (`.live`, `.failing`) |
| Self-documenting capabilities | Less discoverable; no protocol extensions |

## 18. Design Patterns in iOS

### Q122. When is a Singleton acceptable? `[Senior]`

For genuinely single, app-wide resources (Apple: `URLSession.shared`, `FileManager.default`, `UIApplication.shared`). Problems come from **global mutable state accessed everywhere**: hidden dependencies, hard tests, data races (Swift 6 flags non-`Sendable` globals).

```swift
// ❌ Reached for everywhere
AnalyticsManager.shared.track("x")

// ✅ One instance, created at the composition root, injected
let analytics: AnalyticsTracking = FirebaseAnalyticsAdapter()
let viewModel = ProductViewModel(analytics: analytics)

// Swift 6: a global must be Sendable or isolated
@MainActor let sharedImageCache = ImageCacheUI()        // OK: main-actor isolated
var requestCount = 0                                    // ❌ Swift 6 error: global mutable state is not concurrency-safe
```

Rule: it's fine to **have** one instance; inject it rather than calling `.shared`.

### Q124. Builder `[Senior]`

```swift
struct RequestBuilder {
    enum BuildError: Error { case invalidURL }
    private var components: URLComponents?
    private var method = "GET"
    private var headers: [String: String] = [:]
    private var body: Data?

    init(baseURL: URL, path: String) {
        components = URLComponents(url: baseURL.appending(path: path), resolvingAgainstBaseURL: false)
    }

    func method(_ method: String) -> Self { var c = self; c.method = method; return c }
    func header(_ name: String, _ value: String) -> Self { var c = self; c.headers[name] = value; return c }
    func query(_ name: String, _ value: String) -> Self {
        var c = self
        c.components?.queryItems = (components?.queryItems ?? []) + [URLQueryItem(name: name, value: value)]
        return c
    }
    func jsonBody<T: Encodable>(_ value: T) throws -> Self {
        var c = self
        c.body = try JSONEncoder().encode(value)
        c.headers["Content-Type"] = "application/json"
        return c
    }

    func build() throws -> URLRequest {                     // FIX: throws instead of force unwraps
        guard let url = components?.url else { throw BuildError.invalidURL }
        var request = URLRequest(url: url)
        request.httpMethod = method
        request.httpBody = body
        headers.forEach { request.setValue($1, forHTTPHeaderField: $0) }
        return request
    }
}
```

### Q128. Facade `[Senior]`

```swift
/// Small, intention-revealing API over AVFoundation
```

### Q129. Command (with undo) `[Senior]`

```swift
struct Document { var text = "" }

protocol EditCommand {
    func apply(to document: inout Document)
    func revert(on document: inout Document)
}

struct InsertText: EditCommand {
    let text: String
    let index: Int

    func apply(to document: inout Document) {
        let position = document.text.index(document.text.startIndex, offsetBy: index)
        document.text.insert(contentsOf: text, at: position)
    }
    func revert(on document: inout Document) {
        let start = document.text.index(document.text.startIndex, offsetBy: index)
        let end = document.text.index(start, offsetBy: text.count)
        document.text.removeSubrange(start..<end)
    }
}

struct Editor {
    private(set) var document = Document()
    private var undoStack: [EditCommand] = []
    private var redoStack: [EditCommand] = []

    mutating func perform(_ command: EditCommand) {
        command.apply(to: &document)
        undoStack.append(command)
        redoStack.removeAll()                     // a new edit invalidates redo history
    }
    mutating func undo() {
        guard let last = undoStack.popLast() else { return }
        last.revert(on: &document)
        redoStack.append(last)
    }
    mutating func redo() {
        guard let next = redoStack.popLast() else { return }
        next.apply(to: &document)
        undoStack.append(next)
    }
}

@Test func undoRedo() {
    var editor = Editor()
    editor.perform(InsertText(text: "Hello", index: 0))
    editor.undo();  #expect(editor.document.text == "")
    editor.redo();  #expect(editor.document.text == "Hello")
}
```

Commands as values enable undo/redo, queues, logging and replay. UIKit's `UndoManager` builds on the same idea.

### Q130. State pattern in Swift `[Senior]`

```swift
enum PlayerState: Equatable {
    case idle
    case loading(URL)
    case playing(position: TimeInterval)
    case paused(position: TimeInterval)
    case failed(String)

    enum Event { case load(URL), loaded, play, pause, fail(String) }

    func handling(_ event: Event) -> PlayerState {
        switch (self, event) {
        case (_, .load(let url)): .loading(url)
        case (.loading, .loaded): .paused(position: 0)
        case (.paused(let p), .play): .playing(position: p)
        case (.playing(let p), .pause): .paused(position: p)
        case (_, .fail(let message)): .failed(message)
        default: self                                   // invalid transitions ignored
        }
    }
}

@Test func cannotPlayWhileLoading() {

    #expect(state == .loading(URL(string: "https://x.test/v.mp4")!))
}
```

An enum state machine with a pure transition function is clearer and safer in Swift than the classic class-per-state pattern, and every transition is unit-testable.

### Q131. Decorator `[Senior]`

```swift
            do { return try await wrapped.products() }
```

### Q132. Overused or misused patterns `[Lead/Expert]`

- **Singletons** with mutable global state accessed everywhere.
- **"Manager" classes** (`DataManager`, `AppManager`) that collect unrelated responsibilities.
- **Protocols for everything**, even with one implementation and no test doubles.
- **Deep inheritance** (`BaseViewController`, `BaseViewModel`).
- **Heavyweight architectures** (full VIPER/Clean) for small apps.
- **NotificationCenter** as a general event bus.

For each one, be ready to name the replacement: injection, focused services, concrete types, composition, simpler patterns, typed streams.

### Q134. Architecture Decision Records `[Lead/Expert]`

### Q138. Super app / plugin architecture `[Lead/Expert]`

```swift
@MainActor
protocol MiniApp {
    static var identifier: String { get }
    var requiredCapabilities: Set<Capability> { get }
    func canHandle(_ link: DeepLink) -> Bool
    func makeEntryScreen(context: HostContext) -> UIViewController
}

enum Capability: Hashable { case payments, location, camera }

struct HostContext {
    let session: SessionContainer
    let router: HostRouting
    let analytics: AnalyticsTracking
}

@MainActor
final class MiniAppRegistry {
    private var factories: [String: () -> any MiniApp] = [:]        // lazy: protects launch time
    private var loaded: [String: any MiniApp] = [:]

            loaded[id] = app

    }
}
```

### Q140. Choosing an architecture for a new project `[Lead/Expert]`

**Context:** team size and experience, app complexity and lifespan, UI framework, regulatory needs, release cadence. **Constraints:** minimum iOS, third-party policy, hiring market.

**Process:**

1. Shortlist 2–3 options.
2. Build the same **representative feature** in each (list + detail + network + loading/empty/error + one navigation event + tests). Time-box to 2–3 days.
3. Compare readability, test quality, effort, and how a newer engineer copes.
4. Decide and record an ADR.

**Principle:** the simplest architecture that handles your hardest known requirement, with seams that allow evolution.

Worked example: "Fintech, 8 engineers, iOS 17+, strict audit trail. I'd pick SwiftUI + `@Observable` view models + use cases for money movement (rules must be isolated and tested) + repositories + routers. I'd skip TCA: the team is new to it and the audit need is met by use-case tests and logging."

### Q143. The Strangler Fig pattern `[Lead/Expert]`

### Worked solution sketch for task 7 (a common live-coding ask)

```swift
actor RefreshCounter { var count = 0; func increment() { count += 1 } }

@Test func concurrentCallersShareOneRefresh() async throws {
    let counter = RefreshCounter()
    let keychain = InMemoryKeychain(token: Token(accessToken: "old", refreshToken: "r", expiresAt: .distantPast))
    let store = TokenStore(keychain: keychain) { _ in
        await counter.increment()
        try await Task.sleep(for: .milliseconds(50))          // widen the race window
        return Token(accessToken: "new", refreshToken: "r2", expiresAt: .now.addingTimeInterval(3600))
    }

    let tokens = try await withThrowingTaskGroup(of: String.self) { group in
        for _ in 0..<5 { group.addTask { try await store.validToken().accessToken } }
        return try await group.reduce(into: []) { $0.append($1) }
    }

    #expect(tokens == Array(repeating: "new", count: 5))
    #expect(await counter.count == 1)                           // one refresh, not five
}
```

What the interviewer looks for: you set `refreshTask` **before** the first `await` inside the actor (reentrancy), and you test the race rather than assume it.

### Q156. First iOS lead on a new app, team of 8. How do you set up the architecture? `[Lead/Expert]`

- **Process:** ADRs, a one-page architecture guide with a **reference feature**, Xcode templates, monthly architecture review.
- **Evolve:** revisit after the first 3 features based on real friction.

### Q161. An app that must work fully offline `[Lead/Expert]`

### Q162. 5% coverage; management wants faster releases with fewer regressions `[Lead/Expert]`

```
LoginView ─▶ AuthService.login ─▶ TokenStore (actor, Keychain)
                                          ▲
APIClient ─▶ AuthInterceptor ─────────────┘   401 → forceRefresh() once → retry once
                                          │   refresh fails → sessionExpired event
AppSession (observable) ◀── didLogIn / didLogOut ◀── app layer handles sessionExpired
   │
   └─▶ RootView: LoginFlow  |  MainTabs(environment: SessionContainer)
Features ─▶ AuthGate.requireLogin() ─▶ shows login, replays pending deep link
```

- `AuthService` + `TokenStore` actor in networking (Q102); tokens in Keychain.
- Observable `AppSession` owns session-scoped dependencies; root switches flows (Q80, Q107).
- One shared refresh for concurrent 401s; refresh failure → logout handled by the app layer.
- Features use `AuthGate` (Q68); pending deep links replayed after login.
- Logout discards the session container, clears caches, resets navigation.

- Pair programming and review comments that explain the *why*, linking to the guide.
- Introduce gradually: DI → view models → repositories → modules → advanced patterns.
- Celebrate wins (a flaky area stabilised, a feature shipped faster) to build buy-in.

## 24. Modern Swift 6.x Architecture Notes (new section)

Swift 6.2 (Xcode 26) changed concurrency defaults in ways that directly affect architecture. Interviewers increasingly ask about them. Check the release notes of the Swift version your target company uses, since later releases may add to this list.

### Q166. What is "approachable concurrency" and default `MainActor` isolation? `[Senior]`

App targets can opt into **default actor isolation = MainActor** (new Xcode 26 app projects turn it on). Every declaration without an explicit isolation becomes `@MainActor`, so UI code no longer needs annotations everywhere. You opt **out** for background work.

```swift
// With default MainActor isolation on, this is implicitly @MainActor:
@Observable final class ProductListViewModel { var products: [Product] = [] }

// Explicitly opt out for code that must not run on the main actor
nonisolated struct ProductMapper {
    func map(_ dtos: [ProductDTO]) -> [Product] { dtos.map(Product.init(dto:)) }
}

actor SyncEngine { /* actors are unaffected: they keep their own isolation */ }
```

**Architecture impact:** UI layers get simpler; shared modules (Networking, Domain) usually keep **nonisolated** defaults because they're used from many contexts. Choose the default **per module**.

### Q167. `nonisolated(nonsending)` vs `@concurrent` `[Lead/Expert]`

In Swift 6.2 with the `NonisolatedNonsendingByDefault` feature, a `nonisolated async` function runs on the **caller's** actor instead of hopping to the global executor. Use `@concurrent` when you really want parallel background execution.

```swift
struct ImageProcessor {
    // Runs on the caller's actor (no hop, no Sendable requirements on arguments)
    nonisolated(nonsending) func thumbnailName(for url: URL) async -> String { url.lastPathComponent }

    // Always runs off the caller's actor: right for CPU-heavy work
    @concurrent func resize(_ data: Data, to size: CGSize) async -> Data { data }
}

// From a @MainActor view model:
let small = await processor.resize(data, to: CGSize(width: 200, height: 200))   // main thread stays free
```

|  | `nonisolated(nonsending)` (6.2 default with the feature) | `@concurrent` |
| --- | --- | --- |
| Where it runs | Caller's actor | Global concurrent executor |
| Arguments must be `Sendable` | No | Yes |
| Use for | Light async helpers, I/O wrappers | Parsing, image work, heavy computation |

### Q168. Isolated conformances and `isolated deinit` `[Lead/Expert]`

```swift
// Isolated conformance: a @MainActor type can conform to a nonisolated protocol,
// usable only on the main actor
@MainActor final class ThemeStore {}
extension ThemeStore: @MainActor CustomStringConvertible {
    var description: String { "ThemeStore" }
}

// isolated deinit: clean up main-actor state safely (Q128)
@MainActor final class PlayerController {
    private var observer: Any?
    isolated deinit { /* remove observers on the main actor */ }
}
```

### Q169. Observing `@Observable` outside SwiftUI `[Senior]`

Swift 6.2 adds the `Observations` async sequence, which turns observable property reads into a stream. Useful for services and UIKit code on older patterns.

```swift
let counts = Observations { cart.items.count }          // re-evaluated on change
Task {
    for await count in counts { badgeLabel.text = "\(count)" }
}
```

### Q170. How do these defaults change the layered architecture? `[Lead/Expert]`

| Layer / module | Recommended default isolation | Why |
| --- | --- | --- |
| App target, feature UI modules | `MainActor` | Views, view models, coordinators are main-actor anyway |
| Domain | nonisolated, `Sendable` values | Pure logic used from anywhere |
| Networking / persistence | nonisolated + actors where state is shared | Called from many contexts; heavy work `@concurrent` |
| Tests | Match the module under test | `@MainActor` test functions for UI-layer tests |

Model answer: "I set MainActor default isolation for the app and UI feature modules, keep Domain and Networking nonisolated with Sendable value types, use actors only for shared mutable services like the token store and sync engine, and mark CPU-heavy functions `@concurrent`."
