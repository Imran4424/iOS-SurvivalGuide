## 1. Basics & Type System

### Q1. What is the difference between `let` and `var`? `[Fundamental]`
**Key points:**
- `let` creates an immutable binding; `var` a mutable one.
- For **value types**, `let` makes the entire value (and all its properties) immutable.
- For **reference types**, `let` only fixes the reference; the object's `var` properties can still change.
- Prefer `let` by default: it communicates intent and lets the compiler optimize.

### Q2. What are value types and reference types? Give examples. `[Fundamental]`
**Key points:**
- **Value types** are copied on assignment or when passed: `struct`, `enum`, tuples, and standard types like `Int`, `String`, `Array`, `Dictionary`.
- **Reference types** share a single instance: `class`, `actor`, closures.
- Value semantics make reasoning local: no one else can mutate your copy.

### Q3. What are the differences between a struct and a class? `[Fundamental]`
| Struct | Class |
|---|---|
| Value type (copied) | Reference type (shared) |
| No inheritance | Supports inheritance |
| Free memberwise initializer | Must write initializers |
| No `deinit` (except noncopyable structs) | Has `deinit` |
| Methods that modify need `mutating` | Can mutate through any reference |
| No identity (`===` not available) | Has identity (`===`) |
| No reference counting for the struct itself | Managed by ARC |

### Q4. When would you choose a class over a struct? `[Senior]`
**Key points:**
- You need **identity** (two references must point to the same thing).
- You need **shared mutable state** observed by multiple owners.
- You need **inheritance** or Objective-C interop (`NSObject` subclasses).
- You need a **`deinit`** to clean up resources.
- Apple's guidance: start with a struct; use a class when you need the above. For shared mutable state accessed concurrently, consider an **actor**.

### Q5. Are value types always stored on the stack? `[Senior]`
**Key points:**
- No. This is a common misconception.
- Value types can live on the heap when: 
    - they're a property of a class
    - captured by an escaping closure
    - stored in an existential (`any Protocol`) that doesn't fit the inline buffer, or are large/indirect (`indirect enum`).
- `Array`, `String`, `Dictionary` are structs, but their **storage buffer** lives on the heap.
- The important property is **semantics** (copy behavior), not location.

### Q6. What is copy-on-write (CoW)? How would you implement it for a custom type? `[Senior]`
**Key points:**
- CoW delays copying until a mutation happens on shared storage. `Array`, `Dictionary`, `Set`, and `String` use it.
- Custom structs **do not** get CoW automatically. If a struct wraps a class, copies share the class instance.
- Implement it with `isKnownUniquelyReferenced(_:)`:

```swift
final class Storage {
    var values: [Int]
    init(values: [Int]) { self.values = values }
}

struct CoWList {
    private var storage: Storage

    init(_ values: [Int] = []) { storage = Storage(values: values) }

    var values: [Int] { storage.values }

    mutating func append(_ value: Int) {
        if !isKnownUniquelyReferenced(&storage) {
            storage = Storage(values: storage.values) // copy only when shared
        }
        storage.values.append(value)
    }
}
```

### Q7. Why do struct methods need the `mutating` keyword? `[Fundamental]`
**Key points:**
- `self` inside a struct method is immutable by default.
- `mutating` makes `self` an `inout` parameter, so the method can change properties or replace `self` entirely.
- You can't call a `mutating` method on a `let` constant.

### Q8. How do `inout` parameters work? `[Senior]`
**Key points:**
- Semantically **copy-in, copy-out**: the value is copied in, modified, and written back when the function returns.
- The compiler may optimize to pass-by-reference, but you must not rely on that.
- You pass with `&`. You can't pass a `let` constant or a literal.
- `inout` parameters can't be captured by escaping closures.

### Q9. What is the Law of Exclusivity? `[Lead/Expert]`
**Key points:**
- Since Swift 5, a variable can't be accessed for **writing** while any other access (read or write) to it overlaps.
- Enforced at compile time where possible, at runtime otherwise (in debug and release builds).
- Example violation: passing the same variable as two `inout` arguments, or modifying an array while a `mutating` method on it is running.
- It enables optimizations and is a foundation for Swift's memory and concurrency safety.

```swift
var count = 1
func increment(_ a: inout Int, by b: inout Int) { a += b }
increment(&count, by: &count) // ❌ Overlapping accesses to 'count'
```

### Q10. When would you use a tuple vs a struct? `[Fundamental]`
**Key points:**
- Tuples: lightweight, temporary grouping, e.g. returning multiple values from a private function.
- Structs: when the data has meaning in your domain, crosses API boundaries, needs methods, or must conform to protocols (tuples can't conform to protocols).

### Q11. What is the difference between `Any`, `AnyObject`, and `AnyHashable`? `[Fundamental]`
**Key points:**
- `Any`: any type at all, including value types, functions, and optionals.
- `AnyObject`: any class instance; also used to constrain protocols to classes.
- `AnyHashable`: a type-erased wrapper for any `Hashable` value, useful for heterogeneous dictionary keys.

### Q12. Explain `is`, `as`, `as?`, and `as!`. `[Fundamental]`

Swift provides four type casting operators to check the type of an instance or to cast it to a different type. Consider this standard hierarchy for the examples below:

```swift
class Animal {}
class Dog: Animal { func bark() { print("Woof!") } }
class Cat: Animal {}
```

---

#### 1. `is` (Type Checking)
The `is` operator checks whether an instance is of a specific subclass type or conforms to a protocol. **It returns a `Bool` (`true` or `false`)** and does not change the underlying type or return a new value.

* **Purpose:** Checking a type before execution.
* **Example:**
  ```swift
  let myAnimal: Animal = Dog()

  if myAnimal is Dog {
      print("It's a dog!") // This will print
  }
  ```

---

#### 2. `as` (Guaranteed Upcast / Bridging)
The `as` operator performs type conversions that the compiler can **guarantee will succeed at compile-time**. 

* **Purpose:** Upcasting a subclass to a superclass, or bridging established types (like Swift's `String` to Foundation's `NSString`).
* **Example:**
  ```swift
  let myDog = Dog()

  // Upcasting: Dog is guaranteed to be an Animal
  let animalRef = myDog as Animal 

  // Bridging: Swift String to Foundation NSString
  let swiftString = "Hello"
  let nsString = swiftString as NSString 
  ```

---

#### 3. `as?` (Conditional Downcast)
The `as?` operator attempts to downcast an expression to a more specific subclass. Because downcasting can fail, **it returns an optional value** (`Type?`). If the cast fails, it gracefully returns `nil`.

* **Purpose:** Safe downcasting when the underlying type is uncertain. Usually unwrapped using `if let` or `guard let`.
* **Example:**
  ```swift
  let mixedArray: [Animal] = [Dog(), Cat()]

  for animal in mixedArray {
      // Safely attempt to downcast to Dog
      if let dog = animal as? Dog {
          dog.bark() // Only called for the Dog instance
      } else {
          print("Not a dog.")
      }
  }
  ```

---

#### 4. `as!` (Forced Downcast)
The `as!` operator forces a downcast to a specific subclass. **If the cast fails, your application will crash at runtime.** 

* **Purpose:** Downcasting when you are 100% certain of the type due to pre-existing application logic, where a failure implies a critical programmer error.
* **Rule of Thumb:** Avoid `as!` unless an immediate crash is the preferred behavior if the type is incorrect (e.g., dequeuing a specific storyboard `ViewController` or custom `UITableViewCell`).
* **Example:**
  ```swift
  let animal: Animal = Dog()

  // Success: The compiler trusts you, and the instance happens to be a Dog
  let forcedDog = animal as! Dog 
  forcedDog.bark() 

  let anotherAnimal: Animal = Cat()
  // CRASH: "Could not cast value of type 'Cat' to 'Dog'"
  let brokenDog = anotherAnimal as! Dog 
  ```

---

### Summary Matrix

| Operator | Action | Return Type | Failure Point |
| :--- | :--- | :--- | :--- |
| **`is`** | Checks type | `Bool` | Never (returns `false`) |
| **`as`** | Upcasts / Bridges | Target Type | Compile-time (won't compile if invalid) |
| **`as?`** | Downcasts safely | Optional (`TargetType?`) | Never (returns `nil`) |
| **`as!`** | Forces downcast | Target Type | Runtime (**Crashes app**) |

### Q13. Where do actors fit among Swift's types? `[Senior]`

**Actors are a first-class nominal type** introduced in Swift 5.5 to solve data races in concurrent code. They sit alongside **structures, classes, and enumerations** but are architected specifically for safe concurrent access to shared mutable state.

---

#### 1. Architectural Fit: Reference Types with Protection
Like classes, **actors are reference types**. They are passed around by reference (sharing the same underlying instance), making them ideal for managing shared state. However, they differ radically from classes in how they enforce thread safety.

* **The Problem with Classes:** Multiple threads can modify a class instance's memory simultaneously, causing data races and data corruption.
* **The Actor Solution:** Actors introduce **actor isolation**. They wrap their mutable state in a protective boundary, automatically ensuring that **only one task can execute code inside or mutate the actor's state at any given time**.

---

#### 2. Structural Differences from Classes & Structs

| Feature | Struct | Class | Actor |
| :--- | :--- | :--- | :--- |
| **Type Category** | Value type | Reference type | Reference type |
| **Inheritance** | No | Yes | **No** (Cannot inherit from other actors or classes) |
| **Polymorphism** | Via Protocols | Via Inheritance & Protocols | **Via Protocols only** |
| **Deinitializers** | No | Yes | **Yes** (`deinit` is supported) |
| **Thread Safety** | Safe via copying | Unsafe by default | **Safe by design (Isolated)** |

---

#### 3. Key Behavioral Traits

##### A. Actor Isolation & `await`
When you access an actor's mutable properties or functions from the *outside*, you are crossing an isolation boundary. Because the actor might be busy executing another task, you must use the `await` keyword to suspend your current task until the actor is ready to process your request.

```swift
actor BankAccount {
    var balance: Double = 0.0 // Isolated mutable state

    func deposit(amount: Double) {
        balance += amount // Safe: Synchronous, internal access
    }
}

// External Access
let account = BankAccount()
Task {
    // Requires 'await' because it enters the actor's isolation boundary
    await account.deposit(amount: 100.0) 
    
    // CRASH / Compile Error: Cannot read isolated property directly without await
    // print(account.balance) 
    
    print(await account.balance) // Allowed
}
```

##### B. Reentrancy
Actor functions are **reentrant**. When an actor function encounters an `await` expression, it suspends itself. While suspended, the actor can start executing *other* incoming tasks. 

* **The Trap:** Senior developers must remember that the actor's state can change across an `await` boundary. You should never assume your state remains identical before and after a suspension point.

##### C. The `nonisolated` Escape Hatch
If an actor has a property or method that doesn't touch its mutable state (like a static identifier or a constant name), you can mark it as `nonisolated`. This allows external code to access it instantly without using `await`.

```swift
actor UserCache {
    let cacheID: String // Immutable (let) constant
    private var data: [String: Any] = [:] // Mutable state

    // Synchronous external access allowed without await
    nonisolated var identifier: String { cacheID } 
}
```

---

#### Summary Takeaway
Use **structs** by default for model data. Use **classes** when you explicitly need inheritance or object identity in single-threaded contexts. Choose **actors** exclusively to manage **shared mutable state** that must be safely accessed across multiple concurrent asynchronous tasks.

## 2. Optionals

### Q14. What is an optional under the hood? `[Fundamental]`
Under the hood, a Swift **`Optional` is implemented as a generic enumeration (`enum`) with two cases**:

```swift
@frozen public enum Optional<Wrapped>: ExpressibleByNilLiteral {
    case none
    case some(Wrapped)
}
```

#### Core Architecture

* **Syntactic Sugar:** When you declare a type using a question mark (e.g., `T?`), the compiler translates it directly to **`Optional<T>`**. 
* **The Meaning of `nil`:** The keyword **`nil` is literal shorthand for `Optional.none`**. The enum conforms to the `ExpressibleByNilLiteral` protocol, allowing you to use `nil` directly in code.
* **Values as Associated Data:** When a value exists, it is stored inside the **`.some(Wrapped)`** case as an associated value. 

#### Behavioral Advantages

Because optionals are true enums, they inherit functional capabilities beyond simple null pointers:

* **Pattern Matching:** You can `switch` or use `if case` patterns directly on optionals without unwrapping them first.
* **Functional Transforms:** They implement functional standard library methods like **`map` and `flatMap`**. 
  * `map` opens the `.some` case, applies a transformation to the wrapped value, and packs it back into a new optional.
  * `flatMap` behaves similarly but prevents nested optionals (e.g., `T??`) when the transformation itself returns an optional.

### Q15. What are the different ways to unwrap an optional? `[Fundamental]`
**Key points:**
- An optional is an enum (`.none` / `.some(Wrapped)`, Q14), so every unwrapping technique is a way of asking "is there a value, and if so, what is it?"
- Choose by **what should happen when the value is `nil`**: skip some code, exit early, use a default, propagate `nil`, throw an error, or crash (a programmer error).

| Technique | Use when | Result if `nil` |
|---|---|---|
| `if let` | Do something only when a value exists | Skips the block (or runs `else`) |
| `guard let` | The rest of the function needs the value | Must exit the scope (`return`, `throw`, `break`, `continue`) |
| `??` | A sensible default exists | Uses the default |
| Optional chaining `?.` | Access a member through a possibly-`nil` value | Whole expression becomes `nil` |
| `switch` / `if case` | Several cases, or matching together with other values | Matches `.none` / `nil` case |
| `map` / `flatMap` | Transform the value but keep it optional | Stays `nil` |
| `while let` / `for case let x?` | Loops over optionals | Loop ends / element skipped |
| `!` force unwrap | `nil` is impossible, and a crash is the right response if it happens | **Crash** |

**1. Optional binding: `if let`**
```swift
let input: String? = "42"

if let input, let number = Int(input), number > 0 {   // shorthand `if let input` (Swift 5.7+)
    print("Positive number:", number)                 // conditions are evaluated left to right;
} else {                                              // all must succeed
    print("Missing or invalid")
}
```
- The shorthand `if let name` means `if let name = name` and works for any identifier, including properties referenced without `self.`. `if let self.name` isn't allowed.
- The unwrapped value exists only **inside** the `if` block.

**2. Early exit: `guard let`**
```swift
func greet(_ user: User?) {
    guard let user, !user.name.isEmpty else {
        print("No user")
        return                                   // the compiler forces an exit here
    }
    print("Hello, \(user.name)")                 // `user` is non-optional for the rest of the function
}
```
- Keeps the "happy path" unindented; the unwrapped value stays in scope **after** the `guard` (see Q16).
- Common with `throw`: `guard let token else { throw AuthError.missingToken }`.

**3. Nil-coalescing: `??`**
```swift
let displayName = user?.nickname ?? user?.name ?? "Guest"    // chains left to right
let count = cache[key] ?? 0
let settings = loadSavedSettings() ?? makeDefaultSettings()  // called only if needed
```
- The right side is an **autoclosure**: it's evaluated only when the left side is `nil` (so an expensive default isn't computed unnecessarily).
- If the right side is also optional, the result stays optional: `a ?? b` where `b: Int?` gives `Int?`.

**4. Optional chaining: `?.`**
```swift
let city = user?.address?.city                 // String? — nil if user OR address is nil
let length = user?.name.count                  // Int? — even though `count` itself isn't optional
user?.logout()                                 // method called only if user isn't nil; result is Void?
if user?.logout() != nil { print("Logged out") }
```
- The chain **short-circuits** at the first `nil`; nothing after it runs.
- The result is always optional (one level, even through several `?.`s).

**5. Pattern matching: `switch`, `if case`, `for case`**
```swift
switch statusCode {                             // statusCode: Int?
case .some(200):              print("OK")
case let code? where code >= 500: print("Server error \(code)")   // `code?` is shorthand for .some(code)
case .some(let code):         print("Other status \(code)")
case nil:                     print("No response")              // nil is .none
}

// Matching several optionals at once
switch (username, password) {
case let (name?, pass?): login(name, pass)
case (nil, _):           showError("Username required")
case (_, nil):           showError("Password required")
}

// Loop only over non-nil elements
let scores: [Int?] = [10, nil, 30]
for case let score? in scores { print(score) }   // 10, 30
```

**6. Transforming without unwrapping: `map` and `flatMap`**
```swift
let input: String? = "42"

let length = input.map { $0.count }            // Int? = 2       (closure returns a non-optional)
let number = input.flatMap { Int($0) }         // Int? = 42      (closure returns an optional → flattened)
let nested = input.map { Int($0) }             // Int?? — map wraps the optional result again

let url = urlString.flatMap(URL.init(string:)) // common in parsing code
```
- `map`: use when the transform can't fail. `flatMap`: use when the transform itself returns an optional, to avoid `T??`.
- For **collections** of optionals, use `compactMap` to unwrap and drop `nil`s: `["1", "x", "3"].compactMap(Int.init)` → `[1, 3]`.

**7. Loops: `while let`**
```swift
var stack = [1, 2, 3]
while let top = stack.popLast() {              // stops when popLast() returns nil
    print(top)
}
```

**8. Force unwrap: `!`**
```swift
let url = URL(string: "https://example.com")!         // a literal you control: nil would be a programmer error
let cell = tableView.dequeueReusableCell(withIdentifier: "Cell")!   // misconfiguration should be caught in development
```
- If the value is `nil`, the app **crashes** ("Unexpectedly found nil while unwrapping an Optional value").
- Acceptable only when `nil` would mean a **programmer error**, not a runtime condition (user input, network data, files). Prefer a message that explains the assumption:
```swift
guard let url = URL(string: endpoint) else {
    preconditionFailure("Invalid endpoint URL: \(endpoint)")   // documents why it can't be nil
}
```
- Related: **implicitly unwrapped optionals** (`var label: UILabel!`) unwrap automatically on use and crash if `nil` (Q17).

**9. Optional `try?`**
```swift
let data = try? Data(contentsOf: fileURL)     // Data? — nil if the call throws (the error is discarded)
if let data, let image = UIImage(data: data) { show(image) }
```
- Converts an error into `nil`. Use it only when you don't care **why** it failed.

**Interview answer in one line:** "I use `guard let` to unwrap values the rest of the function needs, `if let` for optional work, `??` for defaults, `?.` to access members, `map`/`flatMap` to transform without unwrapping, and pattern matching when I need to match several optionals or cases. I force unwrap only when `nil` would be a programmer error."

**Common follow-ups:**
- *What does `?.` return when the method returns `Void`?* `Void?`, so you can check `!= nil` to know whether the call happened.
- *Difference between `map` and `flatMap` on an optional?* `flatMap` flattens `T??` to `T?` when the closure returns an optional.
- *Is `x!` faster than `if let`?* Not in any meaningful way; both check for `nil`. The difference is crash vs handling it.
- *What's `unsafelyUnwrapped`?* Like `!`, but in optimized `-O` builds it skips the `nil` check. Unwrapping `nil` is then undefined behavior, so it's almost never worth it.

### Q16. When do you use `guard let` vs `if let`? `[Fundamental]`
**Key points:**
- `guard let` for early exit; the unwrapped value stays in scope for the rest of the function, avoiding the "pyramid of doom."
- `if let` when the unwrapped value is only needed in a small block, or both branches do meaningful work.
- `guard`'s `else` must exit scope (`return`, `throw`, `break`, `continue`, or a `Never` call).

### Q17. What are implicitly unwrapped optionals, and when are they appropriate? `[Senior]`
**Key points:**
- Declared with `T!`. An implicitly unwrapped optional (IUO) **is a regular `Optional<T>`**, marked so that the compiler **force-unwraps it automatically** wherever a non-optional `T` is needed. If it's `nil` at that moment, the app **crashes**.
- Since Swift 4.2 (SE-0054), `T!` isn't a separate type: it's `T?` plus an attribute on the **declaration**. So the "implicit" part doesn't travel with the value, which leads to the inference rules below.
- Use it for values that **can't be set in `init`** but are **guaranteed to be set before first use**, where a missing value is a programmer error.
- In modern Swift, prefer making the value non-optional (inject it through `init`), a real optional with explicit handling, or `lazy var`.

**How it behaves:**
```swift
var name: String! = "Taylor"          // declared IUO: Optional<String> underneath

let length: Int = name.count          // implicitly force-unwrapped (crashes if nil)
let copy = name                       // ⚠️ inferred as String? (NOT String!): the IUO "magic" doesn't propagate
let forced: String = name             // force-unwrapped because a non-optional type is required

if let name { print(name) }           // still works like a normal optional
print(name?.uppercased() as Any)      // optional chaining works too
if name == nil { print("not set") }   // comparing to nil works

name = nil
print(name.count)                     // 💥 Fatal error: Unexpectedly found nil while implicitly unwrapping an Optional value
```
- Rule: the compiler **first** tries to treat the IUO as an ordinary optional; it only force-unwraps when the code wouldn't type-check otherwise.
- `var x: T!` starts out as `nil`; `let x: T!` must be assigned once.

**When IUOs are (still) appropriate:**

1. **`@IBOutlet`s**: the storyboard/XIB sets them **after** `init`, before `viewDidLoad`. A `nil` outlet means a broken connection, which you want to find immediately in development.
```swift
final class ProfileViewController: UIViewController {
    @IBOutlet private weak var nameLabel: UILabel!     // Xcode generates outlets this way

    override func viewDidLoad() {
        super.viewDidLoad()
        nameLabel.text = "Taylor"                      // no unwrapping noise; crash = disconnected outlet
    }
}
```

2. **Two-phase initialization with mutual references** (Apple's classic example): an object must pass `self` to another object it owns, which isn't possible before all stored properties are set.
```swift
final class Country {
    let name: String
    var capitalCity: City!                             // default nil lets phase 1 finish…

    init(name: String, capitalName: String) {
        self.name = name
        self.capitalCity = City(name: capitalName, country: self)   // …so `self` can be used here
    }
}

final class City {
    let name: String
    unowned let country: Country
    init(name: String, country: Country) { self.name = name; self.country = country }
}
```

3. **XCTest properties set in `setUp`** (common in older tests):
```swift
final class CartTests: XCTestCase {
    private var sut: Cart!                             // created fresh for every test
    override func setUp() { super.setUp(); sut = Cart() }
    override func tearDown() { sut = nil; super.tearDown() }
}
```
With **Swift Testing**, use `init` instead and make it a `let` (no IUO needed):
```swift
struct CartTests {
    let sut = Cart()                                   // a new instance for each test
    @Test func startsEmpty() { #expect(sut.items.isEmpty) }
}
```

4. **Objective-C APIs without nullability annotations** are imported as IUOs (`_Null_unspecified` / unannotated pointers). The fix is to add `nullable`/`nonnull` annotations (or `NS_ASSUME_NONNULL_BEGIN`) in the header.

**Why to avoid them elsewhere:**
- They turn a **compile-time check** into a **runtime crash**, often far from the line that forgot to set the value.
- They hide required dependencies: `var viewModel: ViewModel!` on a view controller says "something must set this before use", but nothing enforces it.
- Assigning them to new variables silently produces `T?` (inference rule above), which confuses readers.

**Better alternatives:**
| Situation | Instead of IUO |
|---|---|
| Dependency a view controller needs | **Inject it in `init`** (non-optional `let`). For storyboards: `instantiateViewController(identifier:creator:)` (iOS 13+) passes it into a custom `init?(coder:viewModel:)` |
| Expensive value created on first use | `lazy var` |
| Value that can legitimately be missing | A regular optional, handled with `guard let` / `??` |
| UI built in code | Create views in `init` or declare `private let label = UILabel()` |
| Test fixtures | Swift Testing `init` / `let` properties |
| Two-phase init | IUO is acceptable, or restructure so the child doesn't need `self` in `init` |

```swift
// ❌ Property injection: crashes at runtime if someone forgets to set it
final class OrderViewController: UIViewController {
    var viewModel: OrderViewModel!
}

// ✅ Constructor injection: forgetting it is a compile error
final class OrderViewController: UIViewController {
    private let viewModel: OrderViewModel

    init?(coder: NSCoder, viewModel: OrderViewModel) {
        self.viewModel = viewModel
        super.init(coder: coder)
    }
    required init?(coder: NSCoder) { fatalError("Use init(coder:viewModel:)") }
}

// Creating it from a storyboard (iOS 13+)
let controller = storyboard.instantiateViewController(identifier: "Order") { coder in
    OrderViewController(coder: coder, viewModel: OrderViewModel(order: order))
}
```

**Interview answer in one line:** "`T!` is a normal optional that the compiler force-unwraps when a non-optional is needed, so it crashes if it's `nil`. I use it only when a value is set right after initialization and missing it is a programmer error, like `@IBOutlet`s or two-phase init. Otherwise I inject dependencies through `init`, use `lazy var`, or handle a real optional."

**Common follow-ups:**
- *What type is `let y = x` when `x: Int!`?* `Int?`. The force-unwrap only happens when a non-optional is required.
- *Why are outlets `weak`?* The view hierarchy (the superview) already owns the subviews. Apple now says outlets can be strong too; `weak` matters when you remove views and expect them to be released.
- *Is `T!` different from `T?` at runtime?* No. Same type, same memory layout. The difference is only in how the compiler treats uses of that declaration.
- *Can a function return `T!`?* Yes (mostly seen in imported Objective-C APIs), with the same rules: callers get `T?` unless they need a `T`.

### Q18. What is the difference between `map` and `flatMap` on an optional? `[Senior]`
**Key points:**
- `map` transforms the wrapped value: `Int?` + `(Int) -> String` → `String?`.
- `flatMap` is used when the transform itself returns an optional, avoiding `String??`.

```swift
let input: String? = "42"
let a = input.map { Int($0) }      // Int??
let b = input.flatMap { Int($0) }  // Int?
```

## 3. Properties

### Q19. What is the difference between stored and computed properties? `[Fundamental]`
**Key points:**
- A **stored property** is a constant (`let`) or variable (`var`) that is **part of the instance's memory**; its value is kept until changed.
- A **computed property** has **no storage**: it runs a getter (and optionally a setter) **every time** it's accessed, usually deriving its value from other properties.
- Computed properties must be declared with `var` (even read-only ones) and must have an explicit type.
- Enums and extensions **can't add stored instance properties** (it would change the type's memory layout). They **can** add computed properties, and they **can** add `static` stored properties.

| | Stored | Computed |
|---|---|---|
| Memory | Part of the instance's layout | None (code only) |
| Declared with | `let` or `var` | `var` only |
| Evaluated | Once when set; read directly | On **every** access |
| Allowed in | Classes, structs; `static` in enums/extensions too | Classes, structs, enums, extensions, protocols (as requirements) |
| Property observers (`willSet`/`didSet`) | Yes | No (put the logic in `set` instead); subclasses **can** add observers to an inherited computed property |
| `lazy` | Yes (`lazy var`) | Not applicable |
| Synthesized `Codable`, `Equatable`, `Hashable` | Included | Ignored |
| Must be initialized in `init` | Yes (unless optional `var` or has a default) | No |

**Stored properties:**
```swift
struct User {
    let id: UUID                       // stored constant: set once in init
    var firstName: String              // stored variable
    var lastName: String
    var loginCount = 0 {               // stored with a default value and observers
        willSet { print("Will change from \(loginCount) to \(newValue)") }
        didSet  { if loginCount > 100 { loginCount = 100 } }   // can adjust the value; no infinite loop
    }
    lazy var avatar: Data = loadAvatar()   // stored, but computed on first access only (Q20)
    static var maxNameLength = 50          // type-level stored property (lazily initialized, thread-safe)
}
```

**Computed properties:**
```swift
struct User {
    var firstName: String
    var lastName: String

    // Read-only computed property (shorthand: no `get` keyword)
    var fullName: String { "\(firstName) \(lastName)" }

    // Read-write computed property
    var displayName: String {
        get { "\(firstName) \(lastName)" }
        set {                                      // `newValue` is the implicit parameter name
            let parts = newValue.split(separator: " ", maxSplits: 1)
            firstName = parts.first.map(String.init) ?? ""
            lastName = parts.count > 1 ? String(parts[1]) : ""
        }
    }
}

var user = User(firstName: "Taylor", lastName: "Swift")
user.displayName = "Ada Lovelace"                  // runs the setter: updates the stored properties
print(user.fullName)                               // "Ada Lovelace" — recomputed on access
```

**Memory layout shows the difference:**
```swift
struct Rectangle {
    var width: Double                    // 8 bytes
    var height: Double                   // 8 bytes
    var area: Double { width * height }  // 0 bytes: it's a function
}
print(MemoryLayout<Rectangle>.size)      // 16
```

**Enums and extensions:**
```swift
enum Direction {
    case north, south, east, west
    var isVertical: Bool { self == .north || self == .south }   // ✅ computed
    static let all: [Direction] = [.north, .south, .east, .west] // ✅ static stored
    // var visits = 0                                            // ❌ enums can't have stored instance properties
}

extension Date {
    var isInFuture: Bool { self > .now }                         // ✅ computed
    static let unixEpoch = Date(timeIntervalSince1970: 0)        // ✅ static stored
    // var note: String = ""                                     // ❌ extensions can't add stored instance properties
}
```

**Effectful (async/throwing) computed properties** (Swift 5.5+, getter only):
```swift
struct RemoteImage {
    let url: URL
    var data: Data {
        get async throws { try await URLSession.shared.data(from: url).0 }
    }
}
let bytes = try await RemoteImage(url: imageURL).data
```

**Protocol requirements don't care which kind satisfies them:**
```swift
protocol Shape {
    var area: Double { get }           // can be satisfied by a stored `let`/`var` OR a computed property
    var name: String { get set }       // must be settable: a stored `var` or a computed property with a setter
}
```

**Performance and design guidelines:**
- A computed property runs its code on **every access**. Callers assume property access is cheap, so Apple's API Design Guidelines say to **document** any computed property that isn't `O(1)`.
- If it's expensive and the inputs rarely change, either **cache** it (`lazy var` if the inputs never change, or a stored property updated in `didSet` of its inputs), or make it a **method** (`func calculateTotal()`), which signals that real work happens.

```swift
// ❌ O(n) work hidden behind a property, called in a loop → O(n²)
var total: Decimal { items.reduce(0) { $0 + $1.price } }
for _ in items { print(order.total) }

// ✅ Keep a stored total in sync with its input
var items: [Item] = [] { didSet { total = items.reduce(0) { $0 + $1.price } } }
private(set) var total: Decimal = 0
```

**Value types: setters are `mutating`:**
```swift
struct Counter {
    var count = 0
    var doubled: Int {
        get { count * 2 }
        set { count = newValue / 2 }           // implicitly mutating: needs a `var` Counter
    }
}
let fixed = Counter()
// fixed.doubled = 10                          // ❌ cannot assign: `fixed` is a let constant
```
(`nonmutating set` exists for setters that write somewhere else, such as `UserDefaults` or a reference-type box, for example in property wrappers.)

**Inheritance:**
- A subclass can **override** any inherited property (stored or computed) with a **computed** override (`override var`), or add `willSet`/`didSet` observers to it.
- It can't override a property with a **stored** property, and it can't make a read-write property read-only.

```swift
class Vehicle { var speed: Double = 0 }
class Car: Vehicle {
    override var speed: Double {
        didSet { print("Car speed is now \(speed)") }   // observer added to an inherited stored property
    }
}
```

**Related concepts interviewers connect to this:**
- **Property wrappers** (`@State`, `@Published`, custom wrappers) generate a hidden **stored** backing property (`_name`) plus a **computed** `name` that reads and writes it through `wrappedValue`.
- **SwiftUI's `body`** is a computed property: it's re-evaluated whenever the view's state changes, so it must be cheap and side-effect free.
- **`@Observable`** tracks stored properties; a computed property that reads tracked stored properties updates the UI automatically, because its getter accesses them.

**Interview answer in one line:** "Stored properties are part of the instance's memory; computed properties are code that runs on every access, usually derived from stored ones. Enums and extensions can add computed properties and static stored properties, but not stored instance properties, because that would change the type's layout."

**Common follow-ups:**
- *Can a computed property be a `let`?* No. It must be `var`, even if it's read-only.
- *Can you add a stored property in an extension?* Not an instance one. Workarounds: a `static` dictionary keyed by an identifier, a wrapper type, or (for Objective-C classes only) associated objects with `objc_setAssociatedObject`.
- *Can a computed property have `didSet`?* Not its own; put the logic in the `set` block. A subclass can add observers when **overriding** an inherited computed property.
- *Does `didSet` run during `init`?* No. Observers don't fire when a class or struct sets its **own** properties in its initializer (they do fire in a subclass init that sets a superclass property after `super.init`).
- *What's the difference between a computed property and a method?* Mostly semantics: properties should feel like cheap attributes of the value with no side effects; methods signal work, parameters or side effects.

### Q20. What are `lazy` properties? What are their caveats? `[Senior]`
**Key points:**
- Initialized on first access. Useful for expensive setup or values depending on `self`.
- Must be `var` (they're mutated on first access).
- **Not thread-safe**: concurrent first access can initialize twice.
- Accessing a lazy property on a struct requires a mutable instance.
- `lazy var x = { ... }()` is executed once, so referencing `self` in it doesn't create a cycle. But storing a **closure** in a lazy property that captures `self` does.

### Q21. How do `willSet` and `didSet` behave during initialization? `[Senior]`
**Key points:**
- Property observers are **not called** when a type's own initializer assigns its own properties directly, in **classes and structs**. Initial default values don't trigger them either.
- They **are called** when a **subclass** initializer sets an **inherited** property after `super.init` (the superclass is fully initialized by then).
- Assignments inside a **method** called from `init`, or in a **`defer`** block in `init`, **do** trigger them.
- `willSet` receives the incoming value as `newValue`; `didSet` receives the previous value as `oldValue`. Both names can be customized.

**Why:** during initialization the instance isn't fully formed. Observers might read other properties that aren't set yet, or have side effects (UI updates, notifications) that make no sense before the object exists. So the initializer writes **directly to storage**.

**1. The type's own initializer: no observers**
```swift
final class Thermostat {
    var temperature: Double = 20 {                   // default value: no observers
        willSet { print("willSet: \(temperature) → \(newValue)") }
        didSet  { print("didSet: \(oldValue) → \(temperature)") }
    }

    init(temperature: Double) {
        self.temperature = temperature               // ❌ no willSet/didSet here
    }
}

let thermostat = Thermostat(temperature: 22)         // prints nothing
thermostat.temperature = 25                          // willSet: 22.0 → 25.0
                                                     // didSet: 22.0 → 25.0
```
Same for structs:
```swift
struct Score {
    var value: Int { didSet { print("Score changed to \(value)") } }
    init(value: Int) { self.value = value }          // no observer call
}
var score = Score(value: 10)                         // prints nothing
score.value = 11                                     // "Score changed to 11"
```

**2. Subclass initializer setting an inherited property: observers fire**
```swift
class Vehicle {
    var speed: Double = 0 {
        didSet { print("Vehicle.didSet speed: \(oldValue) → \(speed)") }
    }
}

final class Car: Vehicle {
    override var speed: Double {                       // a subclass can add observers to inherited properties
        willSet { print("Car.willSet speed → \(newValue)") }
        didSet  { print("Car.didSet speed: \(oldValue) → \(speed)") }
    }

    init(initialSpeed: Double) {
        super.init()                                   // phase 1 complete: superclass is initialized
        speed = initialSpeed                           // ✅ observers fire (inherited property, after super.init)
    }
}

_ = Car(initialSpeed: 50)
// Car.willSet speed → 50.0
// Vehicle.didSet speed: 0.0 → 50.0
// Car.didSet speed: 0.0 → 50.0
```
- Order with overriding observers: **subclass `willSet` → superclass `willSet` → store → superclass `didSet` → subclass `didSet`**. The subclass's override wraps the superclass's setter.
- Before `super.init()` you can't touch inherited properties at all (two-phase initialization), so the question doesn't arise there.
- A **superclass** initializer assigning its own property doesn't trigger the **subclass's** overriding observers either.

**3. Indirect assignments in `init`: observers fire**
```swift
final class Profile {
    var name: String {
        didSet { print("name didSet: \(oldValue) → \(name)") }
    }

    init(name: String) {
        self.name = "placeholder"                     // direct: no observer
        defer { self.name = name }                    // ✅ fires (a known trick)
    }

    convenience init() {
        self.init(name: "Guest")
        name = "Anonymous"                            // ✅ fires: the designated init has finished
    }

    func rename(_ newName: String) { name = newName } // calling this from init → ✅ fires
}
```
- `defer` runs at the **end** of `init`, after everything is set up. Its assignments are treated as normal sets. It works, but it's subtle; many teams prefer the explicit approach below.
- Assignments in a **convenience** initializer after `self.init(...)` are regular sets → observers fire.

**Clearer alternative: call the shared logic explicitly**
```swift
final class ProgressView: UIView {
    var progress: Double = 0 {
        didSet { updateBar() }                        // runs on every later change
    }

    init(progress: Double) {
        self.progress = progress                      // observer won't run here…
        super.init(frame: .zero)
        updateBar()                                   // …so apply the same logic explicitly
    }

    required init?(coder: NSCoder) { fatalError("init(coder:) is not supported") }

    private func updateBar() { /* resize the fill layer to match progress */ }
}
```
This is the most readable way to say "the setup needed after a change is also needed at creation".

**4. `newValue`, `oldValue` and custom names**
```swift
var volume: Int = 5 {
    willSet(newVolume) { print("Changing to \(newVolume)") }      // custom name instead of newValue
    didSet(previous)   {
        if volume > 10 { volume = 10 }                            // ✅ setting it inside its own didSet
        print("Changed from \(previous)")                         //    does NOT re-trigger observers (no loop)
    }
}
```

**Other behaviors interviewers like to probe:**
- **Observers fire even when the new value equals the old one.** Compare explicitly if needed: `didSet { guard oldValue != value else { return } … }`.
- **Mutating part of a value type triggers the whole property's observers**: `items.append(x)` on an observed array property fires `willSet` and `didSet` (for the whole array).
- **`inout` arguments**: passing an observed property as `inout` (e.g. `increment(&counter)`) calls **both** observers when the function returns (copy-in/copy-out), even if the function doesn't change it.
- **Swift 5.3 (SE-0268)**: if `didSet` doesn't refer to `oldValue`, Swift skips reading the old value, which allows in-place mutation of collections (no copy) for "simple" `didSet` observers.
- **Lazy properties** can have observers (Swift 5.3+); the first lazy initialization doesn't trigger them.
- **Computed properties** can't have their own observers (put logic in `set`); a subclass **can** add observers when overriding an inherited computed property.
- `let` properties can't have observers; neither can a property declared in a **protocol** (conformers decide).
- **`@Published`** fires its publisher in **`willSet`**, so subscribers that read the property synchronously see the **old** value. A common SwiftUI/Combine surprise.

**Interview answer in one line:** "A type's own initializer writes its properties directly, so `willSet`/`didSet` don't run, in classes and structs alike. A subclass initializer setting an inherited property after `super.init` does trigger them, as do assignments in a method or `defer` called from `init`. If the observer's work is also needed at creation, I call that logic explicitly in `init`."

**Common follow-ups:**
- *Why aren't observers called in `init`?* The instance may be partially initialized, and observers could read uninitialized state or cause side effects too early.
- *How do you make the observer logic run for the initial value?* Call the same helper explicitly at the end of `init` (preferred), or assign in a `defer` block.
- *Does `didSet` run when assigning the same value?* Yes. Observers don't compare values.
- *What order do overridden observers run in?* Subclass `willSet`, superclass `willSet`, superclass `didSet`, subclass `didSet`.

### Q22. What is the difference between `static` and `class` for properties and methods? `[Fundamental]`
**Key points:**
- Both declare **type-level** members (called on the type, not an instance: `Vehicle.create()`).
- `class` members can be **overridden** by subclasses; `static` members **can't**. In a class, `static` means `final class`.
- `class` is allowed **only in classes**, and only for **methods and computed properties**. **Stored** type properties must be `static`.
- Structs, enums and protocols use `static` only. A class conforming to a protocol's `static` requirement may implement it with `class` so subclasses can override it.

```swift
class Vehicle {
    static let wheelsKey = "wheels"                  // stored type property: must be static
    static func make() -> Vehicle { Vehicle() }      // can't be overridden (= final class)
    class var category: String { "Vehicle" }         // computed: overridable
    class func describe() -> String { "A \(category)" }
}

final class Car: Vehicle {
    override class var category: String { "Car" }    // ✅ overriding a class property
    // override static func make() -> Vehicle { … }  // ❌ static can't be overridden
}

print(Car.describe())                                // "A Car": dynamic dispatch on the type
```

| | `static` | `class` |
|---|---|---|
| Available in | Classes, structs, enums, protocols | Classes only |
| Stored properties | ✅ | ❌ |
| Overridable | ❌ | ✅ |
| Dispatch | Static (`final`) | Dynamic (via the class's type) |

**Interview answer in one line:** "Both are type-level; `class` members can be overridden by subclasses and only exist on classes for methods and computed properties, while `static` works everywhere, supports stored properties, and in a class is equivalent to `final class`."

### Q23. Are `static let` properties thread-safe? Why are they used for singletons? `[Senior]`
**Key points:**
- `static` stored properties and global variables are **lazily initialized on first access, exactly once**, and that initialization is **thread-safe**: the runtime uses `swift_once` (like `dispatch_once`), so concurrent first accesses wait for the single initializer to finish.
- That's why `static let shared = Manager()` is the standard singleton: lazy, created once, no locking code. Add `private init()` so no one can create a second instance.
- Only the **initialization** is thread-safe. **Mutable state inside** the singleton isn't, so protect it yourself (actor, `@MainActor`, `Mutex`).
- Exception: top-level globals in `main.swift` (or a top-level code file) are initialized **eagerly**, in order, not lazily.

```swift
// ❌ Safe creation, unsafe use: two threads calling add() race on `items`
final class Cart {
    static let shared = Cart()
    private init() {}
    var items: [String] = []
    func add(_ item: String) { items.append(item) }
}

// ✅ Swift 6: the singleton is an actor, so its state is isolated
actor CartStore {
    static let shared = CartStore()
    private init() {}
    private var items: [String] = []
    func add(_ item: String) { items.append(item) }
}

// ✅ UI-related singleton: isolate it to the main actor
@MainActor
final class ThemeManager {
    static let shared = ThemeManager()
    private init() {}
    var accentColor = "blue"
}
```

**Swift 6 strict concurrency rules:**
| Declaration | Swift 6 result |
|---|---|
| `static let shared = Cart()` where `Cart` isn't `Sendable` | ❌ Error: not concurrency-safe (shared non-Sendable state) |
| `static var counter = 0` | ❌ Error: global mutable state |
| `static let` of a `Sendable` type (actor, immutable struct, `Mutex`-protected class) | ✅ |
| Property isolated to a global actor (`@MainActor static var …`) | ✅ |
| `nonisolated(unsafe) static var …` | ✅ compiles, but you take responsibility (last resort) |

**Interview answer in one line:** "`static let` is lazily initialized exactly once in a thread-safe way, which makes it a safe singleton constructor; but that only covers creation, so in Swift 6 the singleton must also be `Sendable`, an actor or main-actor isolated to make using it safe."

### Q24. What are property wrappers? Write one. `[Senior]`
**Key points:**
- A type annotated `@propertyWrapper` with a `wrappedValue` that encapsulates storage logic, reusable across properties.
- Examples: `@State`, `@Published`, `@AppStorage`.

```swift
@propertyWrapper
struct Clamped<Value: Comparable> {
    private var value: Value
    let range: ClosedRange<Value>

    init(wrappedValue: Value, _ range: ClosedRange<Value>) {
        self.range = range
        self.value = min(max(wrappedValue, range.lowerBound), range.upperBound)
    }

    var wrappedValue: Value {
        get { value }
        set { value = min(max(newValue, range.lowerBound), range.upperBound) }
    }
}

struct Player {
    @Clamped(0...100) var health: Int = 100
}
```

### Q25. What is `projectedValue` in a property wrapper? `[Senior]`
**Key points:**
- A property wrapper can expose a **second value** besides `wrappedValue`, accessed with the **`$` prefix**. You define it as `var projectedValue: SomeType` in the wrapper.
- It's for **extra functionality** about the property (a binding, a publisher, validation state), while `wrappedValue` is the value itself.
- `$name` has the **same access level** as `name`. `_name` is the **wrapper instance** itself and is always `private`.

**Built-in examples:**
| Declaration | `name` (wrapped value) | `$name` (projected value) |
|---|---|---|
| `@State var name: String` | `String` | `Binding<String>` |
| `@Binding var name: String` | `String` | `Binding<String>` (itself) |
| `@Published var name: String` | `String` | `Published<String>.Publisher` |
| `@StateObject var model: Model` / `@ObservedObject` | `Model` | Wrapper with dynamic member lookup: `$model.title` is a `Binding<String>` |
| `@Bindable var model: Model` (Observation) | `Model` | `$model.title` is a `Binding<String>` |

**Custom example:**
```swift
@propertyWrapper
struct Clamped<Value: Comparable> {
    private var value: Value
    private let range: ClosedRange<Value>
    private(set) var projectedValue = false            // $property: "was the last value clamped?"

    init(wrappedValue: Value, _ range: ClosedRange<Value>) {
        self.range = range
        self.value = min(max(wrappedValue, range.lowerBound), range.upperBound)
    }

    var wrappedValue: Value {
        get { value }
        set {
            value = min(max(newValue, range.lowerBound), range.upperBound)
            projectedValue = (value != newValue)
        }
    }
}

struct Player {
    @Clamped(0...100) var health = 100
}

var player = Player()
player.health = 150
print(player.health)     // 100      — wrappedValue
print(player.$health)    // true     — projectedValue
// player._health        // the Clamped<Int> wrapper itself (private, only inside Player)
```

**Interview answer in one line:** "`projectedValue` is an optional extra value a property wrapper exposes through `$name`, like `Binding` for `@State` or a publisher for `@Published`. It's different from `_name`, which is the private wrapper instance."

## 4. Initialization

### Q26. What are designated and convenience initializers? `[Fundamental]`
**Key points:**
- **Designated**: the primary initializer. It initializes **all** stored properties introduced by its class, then calls a **superclass designated** initializer.
- **Convenience** (`convenience init`): a secondary shortcut. It must call **another initializer of the same class** (`self.init`), which ultimately reaches a designated one.
- Rule: **designated delegates up, convenience delegates across.**
- Only **classes** have this distinction. Struct initializers can simply call `self.init(...)`.

```swift
class Vehicle {
    let wheels: Int
    init(wheels: Int) { self.wheels = wheels }                 // designated
}

class Bike: Vehicle {
    let brand: String
    init(brand: String) {                                      // designated: own properties, then up
        self.brand = brand
        super.init(wheels: 2)
    }
    convenience init() { self.init(brand: "Generic") }         // convenience: across
}
```
**Initializer inheritance** (a follow-up favorite): a subclass inherits **all** superclass designated inits if it defines none of its own (and its new properties have defaults); it inherits the **convenience** inits if it provides (or inherits) all superclass designated inits.

### Q27. Explain two-phase initialization. `[Senior]`
**Key points:**
- **Phase 1 (going up):** each class initializes **its own** stored properties, then calls `super.init`. Until the top of the chain is reached, `self` can't be used (no method calls, no reading properties, no passing `self`).
- **Phase 2 (going down):** once every stored property in the hierarchy has a value, each initializer can **customize** the instance: call methods, read properties, pass `self`.
- **What it guarantees:** no property is read before it's initialized. Because the subclass sets its own properties **before** calling `super.init`, a superclass initializer can safely call a method the subclass overrides. (In Objective-C and some other languages, that method would see uninitialized subclass state.)

```swift
class Base {
    init() { setup() }                                    // phase 2 of Base: calling an overridable method is OK
    func setup() {}
}

final class Child: Base {
    let name: String
    override init() {
        name = "child"                                    // phase 1: own properties first
        // print(self)                                    // ❌ self not available yet
        super.init()                                      // phase 1 completes up the chain
        print("Ready:", name)                             // phase 2: self is usable
    }
    override func setup() { print("Setting up", name) }   // safe: name is already set
}
```

### Q28. What are failable initializers? `[Fundamental]`
**Key points:**
- `init?` returns **`nil`** when the instance can't be created from the given input: `Int("abc")`, `URL(string:)`, enum `init?(rawValue:)`.
- Use it for simple validation where **why** it failed doesn't matter. When callers need the reason, use a **throwing** `init(...) throws`.
- `init!` also exists (it produces an implicitly unwrapped optional); it's rare.

```swift
struct Email {
    let value: String
    init?(_ value: String) {
        guard value.contains("@") else { return nil }    // failure: no instance created
        self.value = value
    }
}

enum Size: String { case small, large }
let size = Size(rawValue: "medium")                      // nil: synthesized failable init

struct Password {
    enum ValidationError: Error { case tooShort }
    init(_ text: String) throws {                        // richer failure information
        guard text.count >= 8 else { throw ValidationError.tooShort }
    }
}
```
A failable init can delegate to another failable init; if that one fails, initialization fails immediately.

### Q29. What does `required` mean on an initializer? `[Senior]`
**Key points:**
- Every subclass **must implement** (or inherit) that initializer, so it's available on **every** subclass.
- A subclass's implementation is also marked `required` (and needs no `override`).
- Common cases:
  - **`init?(coder:)`** in `UIView`/`UIViewController` subclasses (storyboards and archiving need it).
  - **Protocol initializer requirements** implemented by a non-`final` class (so subclasses also satisfy the protocol). A `final` class doesn't need `required`.
  - Factory code that calls `T.init()` on a metatype (`type.init()`).

```swift
protocol Configurable { init(config: [String: String]) }

class Widget: Configurable {
    required init(config: [String: String]) {}           // `required` so subclasses also conform
}

final class CustomView: UIView {
    init() { super.init(frame: .zero) }
    required init?(coder: NSCoder) { fatalError("init(coder:) has not been implemented") }
}
```

### Q30. How do you keep a struct's memberwise initializer while adding a custom one? `[Fundamental]`
**Key points:**
- Defining **any** initializer in the struct's **main declaration** removes the synthesized memberwise initializer.
- Put custom initializers in an **extension** to keep both.
- Access level: the memberwise init is at most **`internal`**, and **`private`/`fileprivate`** if any stored property is. Public types in a framework need an explicit `public init`.
- Properties with default values become **optional parameters** of the memberwise init (`var`s only; `let`s with defaults aren't parameters at all).

```swift
struct Point {
    var x: Double
    var y: Double = 0
}

extension Point {
    init(polarRadius r: Double, angle: Double) {         // custom init in an extension
        self.init(x: r * cos(angle), y: r * sin(angle))  // memberwise init is still available
    }
}

let a = Point(x: 1, y: 2)                                // ✅ memberwise
let b = Point(x: 1)                                      // ✅ y defaults to 0
let c = Point(polarRadius: 1, angle: .pi / 2)            // ✅ custom
```

### Q31. When is `deinit` called? `[Fundamental]`
**Key points:**
- Automatically, right **before a class instance is deallocated**: when the last **strong** reference goes away. You never call it yourself.
- Use it for **cleanup** that ARC doesn't do: invalidating timers, cancelling tasks, removing block-based observers, closing files or sockets.
- Subclass `deinit` runs first, then the superclass's automatically.
- It **never runs** if the object is kept alive by a **retain cycle**, which is why "deinit not called" is the first sign of a leak.
- **Structs and enums** don't have `deinit`, except **noncopyable** (`~Copyable`) types (Swift 5.9+). **Actors** do have `deinit`.

```swift
final class LivePriceFeed {
    private var timer: Timer?
    private var task: Task<Void, Never>?

    func start() {
        // [weak self]: the timer's closure must not keep the feed alive, or deinit never runs
        timer = Timer.scheduledTimer(withTimeInterval: 1, repeats: true) { [weak self] _ in
            self?.refresh()
        }
        task = Task { /* streaming work */ }
    }

    deinit {
        timer?.invalidate()        // the run loop retains a scheduled timer until it's invalidated
        task?.cancel()             // unstructured tasks keep running unless cancelled
        print("LivePriceFeed deallocated")
    }

    private func refresh() {}
}
```
**Follow-ups:**
- *Is `deinit` immediate?* It runs synchronously when the last strong reference is released, on **whichever thread** released it. So in Swift 6, `deinit` of a `@MainActor` class is **nonisolated** by default. Swift 6.2 adds `isolated deinit` (SE-0371) to run it on the actor.
- *Do `unowned` references delay `deinit`?* No. `deinit` runs when strong references reach zero; accessing an `unowned` reference afterwards crashes.

## 5. Enums

### Q32. What is the difference between raw values and associated values? `[Fundamental]`
**Key points:**
- **Raw values**: one **fixed, compile-time** value per case, all of the **same type** (`String`, `Character`, integer or floating-point). The enum gets `rawValue` and a failable `init?(rawValue:)`.
- **Implicit raw values**: `String` raw values default to the case name; `Int` raw values count up from 0 (or from the previous explicit value).
- **Associated values**: data attached to a case **per instance**, decided at runtime; each case can carry **different types**.
- An enum declared with a raw type (`enum E: String`) **can't** have associated values.

```swift
enum Planet: Int {                       // raw values: 1, 2, 3 (implicit after the first)
    case mercury = 1, venus, earth
}
let p = Planet(rawValue: 3)              // .earth (Optional: may be nil)
print(Planet.venus.rawValue)             // 2

enum Barcode {                           // associated values: different data per instance
    case upc(Int, Int, Int, Int)
    case qrCode(String)
}
let code = Barcode.qrCode("ABC-123")
if case .qrCode(let text) = code { print(text) }
```
| | Raw values | Associated values |
|---|---|---|
| Set | At compile time, per **case** | At runtime, per **instance** |
| Type | Same for all cases | Can differ per case |
| Gives you | `rawValue`, `init?(rawValue:)` | Pattern matching to extract data |
| Typical use | Mapping to API strings, persistence | Modeling states/results with data |

### Q33. What is an `indirect` enum? `[Senior]`
**Key points:**
- Enums are value types, so their size must be known at compile time. A case that contains **the enum itself** would make the size infinite.
- `indirect` tells the compiler to store that case's associated values **in a heap box**, which makes **recursive** enums possible.
- Mark the whole enum `indirect`, or only the recursive cases (`indirect case`).
- Cost: a heap allocation per indirect case value (and reference counting), like a class instance.

```swift
enum Expression {
    case number(Int)
    indirect case add(Expression, Expression)
    indirect case multiply(Expression, Expression)

    func evaluate() -> Int {
        switch self {
        case .number(let value):        return value
        case .add(let l, let r):        return l.evaluate() + r.evaluate()
        case .multiply(let l, let r):   return l.evaluate() * r.evaluate()
        }
    }
}

// (2 + 3) × 4
let expr = Expression.multiply(.add(.number(2), .number(3)), .number(4))
print(expr.evaluate())                  // 20
```
Typical uses: expression trees, linked lists, JSON values, file-system trees.

### Q34. What is `@unknown default`? `[Senior]`
**Key points:**
- For switching over **non-frozen** enums that may gain cases in future versions: most Apple SDK enums (e.g. `UNAuthorizationStatus`) and public enums of libraries built with library evolution.
- At **runtime** it behaves like `default`: it handles cases that didn't exist when you compiled.
- At **compile time** it's better than `default`: the compiler **warns** if any **currently known** case isn't handled explicitly. So when you update the SDK and a new case appears, you notice.
- Not needed for your **own** enums in the same module (the compiler requires exhaustive switches anyway), or for `@frozen` enums.

```swift
import UserNotifications

func describe(_ status: UNAuthorizationStatus) -> String {
    switch status {
    case .notDetermined: "Not asked yet"
    case .denied:        "Denied"
    case .authorized:    "Allowed"
    case .provisional:   "Quietly allowed"
    case .ephemeral:     "App Clip, temporary"
    @unknown default:    "Unknown status"     // future cases; warning if a known case above is missing
    }
}
```

### Q35. How would you use an enum to model screen state? `[Senior]`
**Key points:**
- **Make invalid states unrepresentable**: a screen is in **exactly one** state at a time, and each state carries only the data that makes sense for it.
- With separate `isLoading`, `data` and `error` properties, nothing stops "loading **and** failed **and** showing data". Every view then needs to guess which flag wins.
- A `switch` over the state forces the UI to handle **every** case, and the compiler flags new cases.

```swift
enum ViewState<Value> {
    case idle
    case loading
    case loaded(Value)
    case empty
    case failed(message: String)        // store what the UI needs; `Error` isn't Equatable
}

@MainActor @Observable
final class ProfileViewModel {
    private(set) var state: ViewState<Profile> = .idle

    func load() async {
        state = .loading
        do {
            let profile = try await api.fetchProfile()
            state = .loaded(profile)
        } catch {
            state = .failed(message: error.localizedDescription)
        }
    }
}

struct ProfileView: View {
    let model: ProfileViewModel
    var body: some View {
        switch model.state {
        case .idle, .loading:            ProgressView()
        case .loaded(let profile):       Text(profile.name)
        case .empty:                     Text("No profile yet")
        case .failed(let message):       Text(message).foregroundStyle(.red)
        }
    }
}
```
Variations: `.refreshing(Value)` to keep showing old data while reloading; `extension ViewState: Equatable where Value: Equatable {}` for easy testing.

### Q36. Can enums have stored properties, methods, and conformances? `[Fundamental]`
**Key points:**
- **No stored instance properties**: per-instance data goes in **associated values**.
- **Yes** to: computed properties, methods (including **`mutating`** methods that change `self` to another case), `static` stored properties, initializers, subscripts, nested types, protocol conformances and extensions.
- `CaseIterable` synthesizes `allCases` for enums **without associated values**. `Equatable`/`Hashable` are synthesized when all associated values conform (automatic for enums without associated values). `Codable` is synthesized too.

```swift
enum TrafficLight: CaseIterable {
    case red, yellow, green

    static let cycleDuration = 90                  // ✅ static stored property

    var canGo: Bool { self == .green }             // ✅ computed property

    init(isSafe: Bool) { self = isSafe ? .green : .red }    // ✅ custom initializer

    mutating func next() {                          // ✅ mutating method changes the case
        switch self {
        case .red:    self = .green
        case .green:  self = .yellow
        case .yellow: self = .red
        }
    }
}

var light = TrafficLight(isSafe: false)            // .red
light.next()                                       // .green
print(TrafficLight.allCases.count)                 // 3
```

## 6. Functions & Closures

### Q37. What is a closure? Are closures value or reference types? `[Fundamental]`
**Key points:**
- A **closure** is a self-contained block of code that can be passed around and **captures** (keeps access to) variables from the context where it was created.
- Three forms: **global functions** (named, capture nothing), **nested functions** (named, capture from the enclosing function), and **closure expressions** (`{ (x: Int) -> Int in x * 2 }`).
- Closures are **reference types**: assigning one to another variable doesn't copy it, so both refer to the **same** closure and the **same** captured state.

```swift
func makeCounter() -> () -> Int {
    var count = 0                       // captured: lives on after makeCounter returns
    return { count += 1; return count }
}

let counterA = makeCounter()
let counterB = counterA                 // same closure, same captured `count`
print(counterA())                       // 1
print(counterB())                       // 2: shared state proves reference semantics
let counterC = makeCounter()            // a new closure with its own `count`
print(counterC())                       // 1
```
Note: closures aren't `AnyObject`, so you can't compare them with `===`. To identify or remove a callback, store it with an ID (`[UUID: () -> Void]`).

### Q38. What is the difference between escaping and non-escaping closures? `[Fundamental]`
**Key points:**
- **Non-escaping** (the default for closure parameters): guaranteed to run **before the function returns** and not be stored. The compiler can skip heap allocation and reference counting, and you can use `self` implicitly.
- **`@escaping`**: may be **called after the function returns** (stored in a property, called asynchronously, passed to an escaping API). It must be heap-allocated; in classes you must write `self.` explicitly (or `[self]` / `[weak self]`) so captures are visible.
- **Optional closure parameters** (`completion: (() -> Void)?`) are **implicitly escaping**.
- Escaping closures that capture `self` strongly while `self` stores them are the classic **retain cycle**.

```swift
final class Downloader {
    private var completionHandlers: [() -> Void] = []

    func transform(_ values: [Int], using f: (Int) -> Int) -> [Int] {
        values.map(f)                                    // non-escaping: used before returning
    }

    func download(completion: @escaping () -> Void) {
        completionHandlers.append(completion)           // stored → must be @escaping
    }

    func start() {
        download { [weak self] in                       // escaping + self → avoid a cycle
            self?.finish()
        }
    }

    private func finish() {}
}
```
`withoutActuallyEscaping(_:do:)` lets you pass a non-escaping closure to an API that requires escaping, as long as it really doesn't escape.

### Q39. What is `@autoclosure`? `[Senior]`
**Key points:**
- Automatically wraps an **argument expression** in a closure, so the caller writes a plain expression but it's **evaluated lazily** (only if and when the function calls it).
- Used by `assert`/`precondition` (message isn't built in release builds), `??` (default evaluated only when needed), `&&` and `||` (short-circuit).
- Combine with `@escaping` if you store it: `@autoclosure @escaping () -> T`.
- Use sparingly: callers can't see that their expression might **never run** (or run later, or more than once).

```swift
func log(_ message: @autoclosure () -> String, enabled: Bool) {
    if enabled { print(message()) }
}
log(expensiveDescription(), enabled: false)     // expensiveDescription() never runs

// What `??` looks like, simplified
func orDefault<T>(_ value: T?, _ fallback: @autoclosure () -> T) -> T {
    if let value { return value }
    return fallback()                              // evaluated only when value is nil
}
```

### Q40. What are capture lists, and how do they change capture behavior? `[Senior]`
**Key points:**
- By default a closure captures **variables** themselves (by reference): it sees changes made after it was created, and can modify them.
- A capture list `[x]` captures a **copy of the current value** when the closure is **created**, as an immutable constant.
- For a **class reference**, `[object]` copies the **reference**, not the object: the closure still sees changes to the object's properties.
- Capture lists also set **ownership**: `[weak self]` (optional, becomes `nil` when deallocated), `[unowned self]` (non-optional, crashes if used after deallocation).

```swift
var x = 10
let byReference = { print(x) }
let byValue = { [x] in print(x) }
x = 20
byReference()        // 20: sees the variable's current value
byValue()            // 10: captured value at creation

final class Box { var value = 1 }
let box = Box()
let readBox = { [box] in print(box.value) }   // copies the reference only
box.value = 2
readBox()            // 2: same object

final class ViewModel {
    var title = ""
    func observe(_ service: Service) {
        service.onUpdate = { [weak self] newTitle in
            guard let self else { return }    // Swift 5.7+ shorthand; self is strong only inside
            self.title = newTitle
        }
    }
}
```

### Q41. What are higher-order functions? Explain `map`, `compactMap`, `flatMap`, `filter`, `reduce`. `[Fundamental]`
**Key points:**
- **Higher-order functions** take functions as parameters or return them.

| Function | Does | Example | Result |
|---|---|---|---|
| `map` | Transform each element | `[1, 2, 3].map { $0 * 2 }` | `[2, 4, 6]` |
| `compactMap` | Transform and **drop `nil`s** | `["1", "x", "3"].compactMap(Int.init)` | `[1, 3]` |
| `flatMap` | Transform each element into a sequence and **flatten** | `[[1, 2], [3]].flatMap { $0 }` | `[1, 2, 3]` |
| `filter` | Keep elements matching a predicate | `[1, 2, 3, 4].filter { $0.isMultiple(of: 2) }` | `[2, 4]` |
| `reduce` | Combine all elements into one value | `[1, 2, 3].reduce(0, +)` | `6` |

- On **optionals**, `map`/`flatMap` transform the wrapped value (Optional's `flatMap` avoids `T??`). Sequence `flatMap` that dropped `nil`s was renamed **`compactMap`** in Swift 4.1.
- Prefer **`reduce(into:)`** when building a collection: it mutates **one** accumulator. `reduce` with `+` copies the accumulator every step, which is `O(n²)`.

```swift
let words = ["swift", "ios", "swift", "xcode"]
let counts = words.reduce(into: [:]) { $0[$1, default: 0] += 1 }   // ["swift": 2, "ios": 1, "xcode": 1]

let totalPrice = cart.items
    .filter { $0.isAvailable }
    .map(\.price)                          // key path as a function
    .reduce(0, +)
```
Each step is `O(n)` and allocates an array. For long chains you only partly consume, `lazy` avoids intermediate arrays.

### Q42. What is the difference between `forEach` and `for-in`? `[Fundamental]`
**Key points:**
- `forEach` is a method that calls a closure for each element. Inside it, **`return` only exits the current call** (like `continue`). There's no `break` or `continue`, and you **can't `await`** (the closure isn't async).
- `for-in` is a language loop: it supports `break`, `continue`, labeled loops, `where` clauses, `for case` patterns, and `await` / `for try await` in async code.
- `forEach` reads well at the end of a chain for simple side effects; use `for-in` for anything with control flow.

```swift
let numbers = [1, 2, 3, 4, 5]

numbers.forEach { n in
    if n == 3 { return }            // skips only 3; the loop continues
    print(n)                        // 1 2 4 5
}

for n in numbers where n.isMultiple(of: 2) {
    if n > 3 { break }              // ✅ stops the loop
    print(n)                        // 2
}

for await message in chatStream { show(message) }   // ✅ only for-in supports async iteration
```

### Q43. How does `defer` work? `[Fundamental]`
**Key points:**
- A `defer` block runs when the **current scope exits**, however it exits: `return`, `throw`, `break`, the end of a loop iteration, or reaching the end.
- Multiple `defer`s run in **reverse order** (last declared runs first, LIFO).
- It reads variables' values **at the time it runs** (scope exit), not when it was declared.
- A `defer` block can't `return`, `break` or `throw` out of the scope.
- Typical uses: unlock a lock, close a file, end a background task, reset `isLoading`. Cleanup stays next to the setup it pairs with.

```swift
@MainActor
func loadProfile() async {
    isLoading = true
    defer { isLoading = false }               // runs on success AND on error

    do {
        profile = try await api.fetchProfile()
    } catch {
        errorMessage = error.localizedDescription
    }
}

func process() {
    defer { print("first declared, runs last") }
    defer { print("second declared, runs first") }
    print("body")
}
// body → second declared, runs first → first declared, runs last

lock.lock()
defer { lock.unlock() }                       // never forget to unlock, even on early return
```

### Q44. What is `rethrows`? `[Senior]`
**Key points:**
- A function marked `rethrows` **throws only if the closure passed to it throws**. It doesn't throw errors of its own (except rethrowing the closure's error, possibly from a `catch`).
- Callers passing a **non-throwing** closure don't need `try`; with a throwing closure, they do. One function serves both cases.
- Standard library examples: `map`, `filter`, `reduce`, `forEach`, `first(where:)`, `sorted(by:)`, `contains(where:)`.
- **Swift 6 typed throws** generalizes it: `func f<E: Error>(_ body: () throws(E) -> Void) throws(E)` also preserves the **error type**, and non-throwing closures infer `E = Never`.

```swift
func measure<T>(_ label: String, _ work: () throws -> T) rethrows -> T {
    let start = ContinuousClock.now
    defer { print(label, ContinuousClock.now - start) }
    return try work()                              // throws only if `work` throws
}

let sum = measure("sum") { (1...1_000).reduce(0, +) }          // no `try` needed
let data = try measure("load") { try Data(contentsOf: url) }   // `try` required
```

## 7. Memory Management (ARC)

### Q45. How does ARC work? `[Fundamental]`
**Key points:**
- **Automatic Reference Counting** keeps a **strong reference count** for every class instance (also actors and closure contexts). Each new strong reference increments it; each one that goes away decrements it. At **zero**, `deinit` runs and the instance is destroyed.
- The compiler **inserts** the retain/release calls at compile time (and the optimizer removes redundant ones), so deallocation is **deterministic**: it happens exactly when the last strong reference disappears. There's no background collector.
- Reference counts are updated **atomically**, so retaining/releasing from several threads is safe (but the object's own state isn't automatically thread-safe).
- **Value types** (structs, enums) aren't reference counted themselves; their heap buffers (`Array`, `String` storage) are.
- **Weak references** go through a **side table** created on demand. After the object is deinitialized, reading a weak reference returns `nil`. **Unowned** references use a separate unowned count: the object's memory stays allocated (but unusable) until unowned references are gone, and accessing one after `deinit` traps.

```swift
final class Person {
    let name: String
    init(name: String) { self.name = name; print("\(name) init") }
    deinit { print("\(name) deinit") }
}

var a: Person? = Person(name: "Ada")   // count 1
var b = a                              // count 2
a = nil                                // count 1
b = nil                                // count 0 → "Ada deinit" runs immediately
```

### Q46. What is a retain cycle? Give common examples in iOS. `[Fundamental]`
**Key points:**
- Two or more objects hold **strong references to each other** (directly or through a chain), so no count ever reaches zero: they leak, and `deinit` never runs.
- A related leak: an object kept alive by something **long-lived** (the run loop, `NotificationCenter`, a never-ending task) even without a cycle.

| Cause | Chain that keeps `self` alive | Fix |
|---|---|---|
| Strong delegate | `self → tableView → delegate (self)` | `weak var delegate` |
| Stored escaping closure capturing `self` | `self → closure → self` | `[weak self]` |
| Combine `sink` stored in `self.cancellables` | `self → cancellables → sink closure → self` | `[weak self]` in `sink`, or `assign(to: &$property)` |
| Selector-based `Timer` | `run loop → timer → target (self)` | Block-based timer with `[weak self]` + `invalidate()` |
| `CADisplayLink` | `run loop → display link → target (self)` | `invalidate()` / weak proxy target |
| Block-based `NotificationCenter` observer | `center → block → self` | `[weak self]` and remove the token |
| `URLSession(configuration:delegate:delegateQueue:)` | `session → delegate (self)` strongly, until invalidated | `finishTasksAndInvalidate()` / `invalidateAndCancel()` |
| Long-running `Task` stored on `self` | `self → task → closure → self` (e.g. `for await` loop that never ends) | Cancel the task in `deinit`/`onDisappear`, `[weak self]` |
| Parent ↔ child graph | `parent → child → parent` | `weak var parent` |

```swift
final class ProfileViewModel {
    var onUpdate: (() -> Void)?
    private var cancellables = Set<AnyCancellable>()

    func bind(_ publisher: AnyPublisher<String, Never>) {
        publisher
            .sink { [weak self] value in self?.apply(value) }   // without [weak self]: cycle
            .store(in: &cancellables)
    }

    private func apply(_ value: String) {}
}
```

### Q47. What is the difference between `weak` and `unowned`? `[Senior]`
| | `weak` | `unowned` |
|---|---|---|
| Type | Optional `var` (`weak var x: T?`) | Usually non-optional (optional allowed since Swift 5) |
| After the object deallocates | Reads as `nil` (safe) | **Trap/crash** when accessed |
| Keeps the object alive? | No | No |
| Cost | Side table (allocated on the first weak reference) | Unowned count, no side table: slightly cheaper |
| Use when | The referenced object **may be deallocated first** (delegates, callbacks) | The referenced object **always outlives** the reference (a child that can't exist without its parent) |

```swift
final class Customer {
    var card: CreditCard?
}

final class CreditCard {
    unowned let owner: Customer          // a card never exists without its customer
    init(owner: Customer) { self.owner = owner }
}
```
- `unowned(unsafe)` skips the runtime check entirely: a dangling access is **undefined behavior** instead of a clean crash. Rarely justified (extreme hot paths).
- When unsure, use `weak`. A crash from a wrong `unowned` guess is worse than an `if let`.

### Q48. Why should delegates be `weak`, and what does that require of the protocol? `[Fundamental]`
**Key points:**
- The delegating object usually **belongs to** its delegate: a view controller owns a table view, and the table view's delegate is that view controller. A **strong** back-reference creates a cycle: `VC → tableView → delegate → VC`.
- `weak` works only with **class** instances, so the protocol must be class-constrained: `protocol MyDelegate: AnyObject`.

```swift
protocol DownloaderDelegate: AnyObject {             // AnyObject: only classes can conform
    func downloaderDidFinish(_ downloader: Downloader)
}

final class Downloader {
    weak var delegate: DownloaderDelegate?           // doesn't keep the delegate alive
}

final class LibraryViewController: UIViewController, DownloaderDelegate {
    private let downloader = Downloader()            // VC owns the downloader (strong)
    override func viewDidLoad() {
        super.viewDidLoad()
        downloader.delegate = self                   // weak back-reference: no cycle
    }
    func downloaderDidFinish(_ downloader: Downloader) {}
}
```
Exceptions where the system holds delegates **strongly** on purpose: `URLSession` (until invalidated) and `CAAnimation`. Know them, because they're common leak sources.

### Q49. Do you always need `[weak self]` in closures? `[Senior]`
**Key points:**
- **No.** A cycle only forms when `self` to own (directly or indirectly) the closure that owns `self`. A memory leak only happens if there is a complete circle of ownership. 
- **Not needed:**
  - **Non-escaping** closures (`map`, `filter`, `forEach`, `withLock`): they finish before the function returns.
  - **Short-lived escaping** closures that `self` doesn't store: `UIView.animate`, `DispatchQueue.main.async`, a one-shot network completion. At most they keep `self` alive a little longer.
- **Needed:**
  - `self` **stores** the closure, or something `self` owns stores it (properties, `cancellables`, an observer token, a stored `Task`).
  - Keeping `self` alive is **undesirable**: a slow request shouldn't keep a dismissed screen alive and then update it.
- **Pitfall in async code:** `guard let self` at the **start** of a long `Task` makes `self` strong for the **entire** task, which defeats `[weak self]`. Unwrap only when needed, or rely on **task cancellation**.

```swift
// ✅ No [weak self] needed: not stored, finishes quickly
UIView.animate(withDuration: 0.3) { self.view.alpha = 0 }

// ❌ Defeats weak capture: self is strong for as long as the stream runs
task = Task { [weak self] in
    guard let self else { return }
    for await event in events { self.handle(event) }
}

// ✅ Re-check self per event, and cancel the task when the owner goes away
task = Task { [weak self] in
    for await event in events {
        guard let self else { return }
        self.handle(event)
    }
}
// deinit { task?.cancel() }
```
**Senior answer:** "I reason about the ownership graph: who stores the closure, how long it lives, and whether keeping `self` alive is acceptable, rather than adding `[weak self]` everywhere."

### Q50. How do you detect memory leaks? `[Senior]`
**Key points:**
- **Xcode Memory Graph Debugger**: pause the app after repeating a flow; leaked objects get purple warnings, and the graph shows **who holds** each object. Enable **Malloc Stack Logging** (scheme → Diagnostics) to see where each object was allocated.
- **Instruments**: **Leaks** (unreachable memory), **Allocations** with **Mark Generation** (repeat a flow such as open/close a screen several times; anything that keeps growing per generation is retained).
- **`deinit` logging** in development: if closing a screen doesn't print its `deinit`, something holds it.
- **Automated deallocation tests**, ideally after **using** the object (a leak usually appears only after a closure is stored):

```swift
final class ProfileViewModelTests: XCTestCase {
    func testViewModelIsDeallocatedAfterLoading() async {
        var sut: ProfileViewModel? = ProfileViewModel(api: MockAPI())
        await sut?.load()                       // exercise the code that stores closures/tasks
        weak var weakSUT = sut
        sut = nil
        XCTAssertNil(weakSUT, "ProfileViewModel leaked")
    }
}

// Reusable helper: every test that creates `object` also checks it's freed
extension XCTestCase {
    func trackForMemoryLeaks(_ object: AnyObject, file: StaticString = #filePath, line: UInt = #line) {
        addTeardownBlock { [weak object] in
            XCTAssertNil(object, "Potential memory leak", file: file, line: line)
        }
    }
}
```
In production: MetricKit memory metrics and memory-limit terminations (OS Fundamentals & Linker Q12, Q77).

### Q51. When would you use `autoreleasepool` in Swift? `[Senior]`
**Key points:**
- Some Objective-C APIs return **autoreleased** objects, which are freed only when the surrounding **autorelease pool drains**: on the main thread, at the end of each run loop iteration.
- In a **tight loop** that creates many such objects (images, `Data`/`NSString` from Foundation, Core Graphics work), memory piles up until the loop ends. A peak like that can get the app **killed** (jetsam).
- Wrapping **each iteration** in `autoreleasepool { }` drains the temporary objects early, which lowers **peak** memory.
- Pure Swift objects aren't autoreleased; this matters only for Objective-C-based APIs. GCD queues can drain per work item: `DispatchQueue(label:autoreleaseFrequency: .workItem)`.

```swift
for url in imageURLs {                           // thousands of large images
    autoreleasepool {
        guard let image = UIImage(contentsOfFile: url.path) else { return }
        let thumbnail = image.preparingThumbnail(of: CGSize(width: 200, height: 200))
        save(thumbnail)
    }                                            // temporaries released here, every iteration
}
```

### Q52. How does ARC differ from garbage collection? `[Fundamental]`
| | ARC (Swift, Objective-C) | Tracing GC (JVM, .NET, Go, JavaScript) |
|---|---|---|
| When memory is freed | Deterministically, when the last strong reference goes away | Later, when the collector runs |
| How | Retain/release calls inserted at **compile time** | Runtime traces reachable objects from roots |
| Pauses | None (small, spread-out cost per retain/release) | Collection pauses (reduced by concurrent collectors) |
| Memory overhead | Low: no headroom needed | Higher: needs extra headroom to collect efficiently |
| Reference cycles | **Leak** unless broken with `weak`/`unowned` | Collected automatically |
| `deinit`/finalizers | Predictable timing: good for releasing resources | Unpredictable timing |
| Fit for iOS | Predictable performance and footprint on devices without swap | Needs more RAM |

**Interview line:** "ARC trades automatic cycle collection for predictability: no pauses and low memory overhead, but I have to break cycles with `weak` or `unowned`."

## 8. Protocols & Protocol-Oriented Programming

### Q53. What is protocol-oriented programming, and how does it compare with OOP inheritance? `[Senior]`
**Key points:**
- **Protocol-oriented programming (POP)** means describing behavior with **protocols** (what a type can do) and sharing implementations with **protocol extensions** (default methods), instead of building **class hierarchies** (what a type *is*).
- Works with **value types**: structs and enums can't inherit, but they can conform to protocols. Swift's standard library is built this way (`Sequence`, `Collection`, `Equatable`, `Codable`).
- A type can conform to **many** protocols but inherit from only **one** class, which avoids fragile base classes and "god" superclasses (`BaseViewController` with 2,000 lines that every screen inherits).
- Enables **composition** and **testability**: depend on a protocol, inject the real implementation in the app and a mock in tests.
- Trade-off: a protocol for every type "just in case" adds indirection without benefit. Introduce one when there are **two real implementations** (including a test double) or a genuine abstraction.

**Inheritance vs composition of capabilities:**
```swift
// OOP: behavior comes from the class hierarchy
class Animal { func move() { print("moves") } }
class Bird: Animal { override func move() { print("flies") } }
class Penguin: Bird { override func move() { print("swims") } }   // inherits "flying" it shouldn't have

// POP: types pick the capabilities they actually have
protocol Walker { func walk() }
protocol Swimmer { func swim() }
protocol Flyer { func fly() }

extension Walker { func walk() { print("walks") } }               // default implementations
extension Swimmer { func swim() { print("swims") } }

struct Penguin: Walker, Swimmer {}                                 // no fly(): nothing to override away
struct Duck: Walker, Swimmer, Flyer { func fly() { print("flies") } }

func race(_ participants: [any Swimmer]) { participants.forEach { $0.swim() } }
```

**Testability through protocol-typed dependencies:**
```swift
protocol ProfileLoading: Sendable {
    func loadProfile(id: String) async throws -> Profile
}

struct APIProfileLoader: ProfileLoading {                         // production
    func loadProfile(id: String) async throws -> Profile { /* network call */ fatalError("omitted") }
}

struct StubProfileLoader: ProfileLoading {                        // tests and previews
    let profile: Profile
    func loadProfile(id: String) async throws -> Profile { profile }
}

@MainActor @Observable
final class ProfileViewModel {
    private let loader: any ProfileLoading                        // depends on the capability, not the type
    init(loader: any ProfileLoading) { self.loader = loader }
}
```

**Powerful POP features:**
- **Constrained extensions**: add behavior only where it makes sense (`extension Collection where Element: Numeric { var sum: Element { reduce(0, +) } }`).
- **Conditional conformance**: `Array: Equatable where Element: Equatable`.
- **Retroactive modeling**: make existing types (even Apple's) conform to your protocols in an extension.
- **Protocol composition**: require several capabilities at once (`some Codable & Sendable`).
- **Generics with `some`** are statically dispatched and can be specialized (fast). **Existentials with `any`** box the value and use dynamic dispatch (flexible, slower). Prefer `some` unless you need mixed types in one collection.

**The classic gotcha: extension methods that aren't requirements are statically dispatched**
```swift
protocol Greeter { func greet() -> String }                    // requirement
extension Greeter {
    func greet() -> String { "Hello" }                         // default for the requirement
    func farewell() -> String { "Bye" }                        // NOT a requirement
}

struct French: Greeter {
    func greet() -> String { "Bonjour" }
    func farewell() -> String { "Au revoir" }
}

let g: any Greeter = French()
print(g.greet())     // "Bonjour"  — requirement: dynamic dispatch to French
print(g.farewell())  // "Bye"      — not a requirement: the extension's version is called statically
```
Fix: declare the method in the protocol itself if conforming types should be able to customize it.

**Comparison:**
| | Class inheritance | Protocols + extensions |
|---|---|---|
| Works with | Classes only | Classes, structs, enums, actors |
| How many | One superclass | Any number of protocols |
| Shares stored state | ✅ Subclasses inherit stored properties | ❌ Protocols can't add stored properties (conformers declare them) |
| Shares implementation | ✅ Override methods | ✅ Default implementations in extensions |
| Retroactive | ❌ Can't add a superclass to an existing type | ✅ Conform existing types in an extension |
| Coupling | High: subclasses depend on base class internals ("fragile base class") | Low: types depend only on the protocol's requirements |
| Conflicts | — | Two protocols with the same default → the type must implement it explicitly |
| Dispatch | Dynamic (vtable) unless `final` | Static with generics (`some`), dynamic with existentials (`any`) |

**When class inheritance is still the right choice:**
- Frameworks built on it: `UIViewController`, `UIView`, `NSObject` subclasses, `NSManagedObject`.
- Several types genuinely share **stored state and identity** (reference semantics), and the hierarchy is shallow and stable.
- Senior answer: "Prefer protocols and composition by default; use a shallow inheritance hierarchy when a framework requires it or when subclasses truly share state."

**Interview answer in one line:** "POP models capabilities with protocols and shares behavior with protocol extensions, so it works for value types, allows many conformances instead of one superclass, and makes dependencies easy to swap in tests. I watch for the static-dispatch gotcha with extension-only methods, and I don't create protocols until there's a real second implementation."

### Q54. What are protocol extensions and default implementations? `[Fundamental]`
**Key points:**
- Extensions on protocols can provide method implementations shared by all conformers.
- Conformers can override a default implementation **only if the method is declared as a requirement** in the protocol (see next question).

### Q55. Explain static vs dynamic dispatch with protocol extensions. `[Senior]`
**Key points:**
- Methods declared as **protocol requirements** use dynamic dispatch (witness table): the conformer's implementation is called.
- Methods only defined in a **protocol extension** (not requirements) are statically dispatched based on the **static type** of the variable.

```swift
protocol Greeter { func greet() }

extension Greeter {
    func greet() { print("Hello") }
    func farewell() { print("Bye") }   // not a requirement
}

struct Person: Greeter {
    func greet() { print("Hi") }
    func farewell() { print("See ya") }
}

let p: Greeter = Person()
p.greet()     // "Hi"   (dynamic)
p.farewell()  // "Bye"  (static, uses the extension)

let q = Person()
q.farewell()  // "See ya"
```

### Q56. What are associated types? `[Senior]`
**Key points:**
- An **associated type** is a **placeholder type inside a protocol**. The protocol says "there is some type here", and each **conformer decides** which concrete type it is.
- It lets a protocol describe **generic relationships** without making the protocol itself generic. Protocols use `associatedtype`, while structs, classes and functions use `<T>`.
- Examples in the standard library: `Sequence.Element`, `Collection.Index`, `Identifiable.ID`, `IteratorProtocol.Element`, `RawRepresentable.RawValue`.
- The compiler usually **infers** the associated type from the conformer's method signatures. You can also pin it explicitly with a `typealias`.
- You can **constrain** an associated type (`associatedtype ID: Hashable`, `associatedtype Entity: Codable & Sendable`) so protocol code can rely on those capabilities.
- A **default** is allowed: `associatedtype Output = String`.
- A protocol with associated types (or `Self` requirements) can't be used as a plain type like `[Repository]`. Use `some`, `any`, or generic constraints.

**Basic example with inference:**
```swift
protocol Repository {
    associatedtype Entity: Sendable
    func fetchAll() async throws -> [Entity]
}

struct User: Sendable { let id: Int; let name: String }
struct Post: Sendable { let id: Int; let title: String }

struct UserRepository: Repository {
    func fetchAll() async throws -> [User] { [User(id: 1, name: "Ana")] }   // Entity inferred as User
}

struct PostRepository: Repository {
    typealias Entity = Post                                                  // explicit (optional here)
    func fetchAll() async throws -> [Post] { [] }
}
```

**Using the associated type in generic code:**
```swift
func count<R: Repository>(in repo: R) async throws -> Int {
    try await repo.fetchAll().count               // R.Entity is known per call site
}

func firstEntity<R: Repository>(of repo: R) async throws -> R.Entity? {
    try await repo.fetchAll().first               // return type refers to R.Entity
}
```

**Constraining relationships between associated types (`where` clause):**
```swift
// Two repositories whose entities are the same type
func migrate<S: Repository, D: Repository>(from source: S, to destination: D) async throws
    where S.Entity == D.Entity { /* ... */ }

// Extension available only for some conformers
extension Repository where Entity: Identifiable {
    func fetch(id: Entity.ID) async throws -> Entity? {
        try await fetchAll().first { $0.id == id }
    }
}
```

**Why `[Repository]` doesn't compile and what to use instead:**
```swift
let repos: [Repository] = [...]            // ❌ the compiler doesn't know what `Entity` is

// 1. Generic constraint: one concrete type, resolved at compile time (fastest)
func load<R: Repository>(_ repo: R) async throws { _ = try await repo.fetchAll() }

// 2. some P: opaque, one concrete type chosen by the implementation
func makeRepo() -> some Repository { UserRepository() }

// 3. any P: existential box, can hold different conformers (dynamic dispatch, a bit slower)
let repos: [any Repository] = [UserRepository(), PostRepository()]
for repo in repos {
    let items = try await repo.fetchAll()   // type: Any (the associated type is erased)
}

// 4. Primary associated types (Swift 5.7+): constrain Entity in the type itself
protocol Store<Entity> {                       // `Entity` declared as primary
    associatedtype Entity
    func fetchAll() async throws -> [Entity]
}

let userStores: [any Store<User>] = []         // every element has Entity == User
func show(_ store: some Store<User>) {}        // opaque with a constraint
```
Standard library examples: `any Collection<Int>`, `some Sequence<String>`.

**Associated type vs generic parameter:**
| | Associated type | Generic parameter on a type |
|---|---|---|
| Syntax | `protocol P { associatedtype T }` | `struct S<T>` |
| Who chooses `T` | The **conformer** (one choice per conformance) | The **user** at each use site |
| Can one type conform with several `T`s? | ❌ one `T` per conformance | ✅ `S<Int>` and `S<String>` are different types |
| Typical use | "A Collection has an Element", where the type decides | "A Box that holds anything", where the user decides |

**Type erasure (the older workaround):** before `any` with primary associated types, you wrote wrappers like `AnyPublisher` or `AnySequence` to hide the concrete type behind a generic struct. Prefer `any P<T>` now. Hand-written erasure is mainly seen in older code and in Combine.

**Common mistakes:**
- Using the protocol as a type (`var repo: Repository`) and getting "protocol can only be used as a generic constraint". Use `some`, `any`, or a generic parameter.
- Forgetting that `any Repository` returns **erased** associated types (`Any`), so you lose type information. Use a primary associated type (`any Repository<User>`) or a generic function.
- Expecting one type to conform twice with different associated types. It can't (e.g. a type can't be a `Repository` of both `User` and `Post`). Use two types or a generic parameter.
- Overusing `any` when `some` or a generic would do. Existentials cost an allocation or boxing and block some optimizations.

**Interview answer in one line:** "An associated type is a placeholder in a protocol that each conformer fills in, like `Element` in `Collection`. It's usually inferred, can be constrained, and means the protocol can't be used as a plain type, so I use generics or `some` when the concrete type is fixed, and `any P<T>` with primary associated types when I need a heterogeneous collection."

### Q57. What is protocol composition? `[Fundamental]`
**Key points:**
- Combining protocols into one requirement with `&`: `func save(_ item: Codable & Identifiable)`.
- Can include a class: `UIViewController & Coordinatable`.
- Encourages small focused protocols (Interface Segregation).

### Q58. What is conditional conformance? `[Senior]`
**Key points:**
- A generic type conforms to a protocol only when its type arguments meet conditions.

```swift
extension Array: Equatable where Element: Equatable { } // how the stdlib does it
```
- Enables composing behaviors: `[[Int]]` is `Equatable` because `[Int]` is, because `Int` is.

### Q59. How do you make protocol methods optional? `[Fundamental]`
**Key points:**
- `@objc optional` requirements (requires `@objc protocol`, class-only, ObjC interop).
- The Swifty approach: provide a default (often empty) implementation in a protocol extension.
- Alternatively, split into smaller protocols.

### Q60. What does `Self` mean in a protocol? `[Senior]`
**Key points:**
- Refers to the conforming type. Example: `Equatable`'s `static func == (lhs: Self, rhs: Self) -> Bool`.
- `self` is the instance; `Self` is the type.
- In classes, `Self` refers to the dynamic type (useful for factory methods returning `Self`).

### Q61. What is the contract between `Equatable` and `Hashable`? `[Senior]`
**Key points:**
- If `a == b`, then `a.hashValue == b.hashValue` must hold. The reverse need not.
- Hash only the properties used in `==`; otherwise `Set`/`Dictionary` will behave incorrectly.
- Swift synthesizes conformance for structs/enums whose members all conform.
- Hash values are seeded per launch, so never persist them.

### Q62. What is retroactive conformance, and why does Swift 6 warn about it? `[Lead/Expert]`
**Key points:**
- Conforming a type you don't own to a protocol you don't own (e.g. `extension Date: Identifiable`).
- Risky: if the owner adds the same conformance later, behavior becomes ambiguous.
- The Swift 6 toolchain warns, and you can acknowledge intent with `@retroactive`: `extension Date: @retroactive Identifiable`.
- Safer alternative: wrap the type in your own struct.

## 9. Generics

### Q63. Why use generics? Give an example. `[Fundamental]`
**Key points:**
- Write reusable, type-safe code once for many types, without casting to `Any`.

```swift
struct Stack<Element> {
    private var items: [Element] = []
    mutating func push(_ item: Element) { items.append(item) }
    mutating func pop() -> Element? { items.popLast() }
    var top: Element? { items.last }
}
```

### Q64. How do generic constraints and `where` clauses work? `[Senior]`
```swift
func findIndex<T: Equatable>(of value: T, in array: [T]) -> Int? { ... }

func merge<C1: Collection, C2: Collection>(_ a: C1, _ b: C2) -> [C1.Element]
    where C1.Element == C2.Element { Array(a) + Array(b) }

extension Collection where Element: Numeric {
    var total: Element { reduce(0, +) }
}
```

### Q65. What is the difference between `some` and `any`? `[Senior]`
| `some P` (opaque type) | `any P` (existential) |
|---|---|
| One specific concrete type, hidden from the caller | Any conforming type, can change at runtime |
| Fixed by the implementation (return) or caller (parameter) | Stored in an existential container ("box") |
| Static dispatch, specializable, faster | Dynamic dispatch, possible heap allocation |
| Type identity preserved | Type identity lost |
| `func make() -> some View` | `var shapes: [any Shape]` |

- Default to `some`; use `any` when you genuinely need heterogeneity (e.g. an array of different types).
- Since Swift 5.6 `any` is spelled explicitly; in Swift 6 language mode it's required for existentials.

### Q66. Why does SwiftUI use `some View`? `[Senior]`
**Key points:**
- `body` returns a deeply nested generic type (e.g. `VStack<TupleView<(Text, Image)>>`) that's impractical to write.
- `some View` hides it while keeping the concrete type known to the compiler, which SwiftUI needs for efficient diffing and identity.
- Implication: all branches must return the same type, hence `@ViewBuilder` (which wraps branches in `_ConditionalContent`) or `AnyView` (which erases types and hurts diffing).

### Q67. What is type erasure? Implement a type-erased wrapper. `[Lead/Expert]`
**Key points:**
- Hiding a concrete type behind a wrapper with a uniform interface. Examples: `AnyPublisher`, `AnyView`, `AnyHashable`, `AnySequence`.
- Historically needed for protocols with associated types. Since Swift 5.7, `any Protocol<Type>` with primary associated types often replaces hand-written wrappers.

```swift
protocol DataLoader {
    associatedtype Output
    func load() async throws -> Output
}

struct AnyDataLoader<Output>: DataLoader {
    private let _load: () async throws -> Output

    init<L: DataLoader>(_ loader: L) where L.Output == Output {
        _load = loader.load
    }

    func load() async throws -> Output { try await _load() }
}
```

### Q68. What are primary associated types? `[Senior]`
**Key points:**
- Swift 5.7: protocols can declare associated types in angle brackets: `protocol Repository<Entity>`.
- Enables constrained opaque/existential types: `some Collection<Int>`, `any Repository<User>`.
- Reduces the need for manual type erasure and `where` clauses.

### Q69. How do generics affect performance? `[Lead/Expert]`
**Key points:**
- The compiler can **specialize** generic code for concrete types, giving static dispatch and inlining.
- Across module boundaries specialization isn't possible unless the code is `@inlinable` (or whole-module/cross-module optimization applies); otherwise generics go through witness tables at runtime.
- Unspecialized generics and existentials have overhead from dynamic dispatch and boxing.

### Q70. What are parameter packs? `[Lead/Expert]`
**Key points:**
- Swift 5.9 variadic generics: `each T` declares a pack, `repeat` expands it.
- Lets APIs accept any number of differently typed arguments while preserving types, e.g. it's how SwiftUI's `ViewBuilder` dropped the old 10-child limit.

```swift
func describe<each T>(_ values: repeat each T) {
    for value in repeat each values {   // pack iteration, Swift 6
        print(value)
    }
}
describe(1, "two", 3.0)
```

## 10. Error Handling

### Q71. How does Swift's error handling work? Is it like exceptions? `[Fundamental]`
**Key points:**
- Errors conform to `Error` (often enums). Functions mark `throws`; callers use `try` inside `do-catch` or propagate.
- Not like C++/ObjC exceptions: no expensive stack unwinding. A thrown error is essentially a special return path, so it's cheap.
- `try` is required at every call site, making failure points visible.

### Q72. What is the difference between `try`, `try?`, and `try!`? `[Fundamental]`
**Key points:**
- `try`: propagate or handle in `do-catch`.
- `try?`: convert to optional, discarding the error (lose diagnostic info; use carefully).
- `try!`: crash on error. Only for errors that indicate programmer mistakes (e.g. loading a bundled resource).

### Q73. When would you use `Result` instead of `throws`? `[Senior]`
**Key points:**
- `Result<Success, Failure>` represents an outcome as a **value** you can store, pass around, or deliver through completion handlers.
- With async/await, `throws` is generally preferred for control flow; `Result` is still useful for storing outcomes, caching, or batching results.
- Convert: `Result { try work() }` and `try result.get()`.

### Q74. What are typed throws? When would you use them? `[Lead/Expert]`
**Key points:**
- Swift 6: `func f() throws(MyError)` declares the exact error type, so `catch` gets `MyError` instead of `any Error`.

```swift
enum ValidationError: Error { case empty, tooShort }

func validate(_ s: String) throws(ValidationError) {
    if s.isEmpty { throw .empty }
    if s.count < 3 { throw .tooShort }
}

do {
    try validate("")
} catch {
    // error is ValidationError here, can switch exhaustively
}
```
- Good for: closed error sets in internal modules, generic code that forwards errors, embedded/performance-sensitive code (no boxing).
- Swift's guidance: untyped `throws` remains the better default for most public APIs, because adding error cases later breaks clients.

### Q75. How do you give errors user-friendly descriptions? `[Fundamental]`
**Key points:**
- Conform to `LocalizedError` and provide `errorDescription` (and optionally `failureReason`, `recoverySuggestion`).
- Keep user-facing messages separate from developer diagnostics.

### Q76. How would you design an error-handling strategy for an app? `[Lead/Expert]`
**Key points:**
- Layered errors: networking errors → domain errors → UI-presentable states. Map at boundaries; don't leak `URLError` into views.
- Decide which errors are **recoverable** (retry, re-auth), **user-facing** (show message), or **programmer errors** (`assert`/`precondition`).
- Centralize logging and crash reporting; attach context.
- Avoid swallowing errors with `try?` without a reason.

## 11. Collections & Strings

### Q77. Compare `Array`, `Set`, and `Dictionary`. `[Fundamental]`
| | Array | Set | Dictionary |
|---|---|---|---|
| Ordered | Yes | No | No |
| Duplicates | Allowed | Not allowed | Unique keys |
| Lookup | O(n) by value, O(1) by index | O(1) average | O(1) average by key |
| Requirement | None | `Hashable` elements | `Hashable` keys |

### Q78. What is the difference between `Sequence`, `Collection`, and `IteratorProtocol`? `[Senior]`
**Key points:**
- `IteratorProtocol`: provides `next()`.
- `Sequence`: can produce an iterator; may be single-pass and even infinite.
- `Collection`: multi-pass, finite, indexed access, non-destructive iteration, `count`.
- Further refinements: `BidirectionalCollection`, `RandomAccessCollection`, `MutableCollection`.

```swift
struct Countdown: Sequence, IteratorProtocol {
    var current: Int
    mutating func next() -> Int? {
        guard current > 0 else { return nil }
        defer { current -= 1 }
        return current
    }
}
for n in Countdown(current: 3) { print(n) } // 3 2 1
```

### Q79. What are lazy sequences? `[Senior]`
**Key points:**
- `.lazy` defers transformations until elements are requested, avoiding intermediate arrays.

```swift
let firstBigSquare = (1...1_000_000).lazy.map { $0 * $0 }.first { $0 > 1000 }
```
- Caveat: transforms re-run each time elements are accessed, so don't store a lazy chain and iterate it many times if the work is expensive.

### Q80. Why can't you index a `String` with an `Int`? `[Senior]`
**Key points:**
- A `Character` is an **extended grapheme cluster**, which can be multiple Unicode scalars and a variable number of bytes (e.g. "👨‍👩‍👧" is one Character but five scalars).
- Integer indexing would hide O(n) cost. Swift uses `String.Index` to make that explicit.
- Use `index(_:offsetBy:)`, `prefix`, `dropFirst`, or convert to `Array` if heavy random access is needed.

### Q81. What is a `Substring`, and what is the memory concern? `[Senior]`
**Key points:**
- A `Substring` shares storage with the original `String` (no copy, fast).
- Holding a small `Substring` long-term keeps the **entire** original string in memory.
- Convert with `String(substring)` before storing.

```swift

let grouped = Dictionary(grouping: users, by: \.department)
let merged = a.merging(b) { current, new in new }
```

## 12. Access Control & Modules

### Q83. Explain Swift's access levels. `[Fundamental]`
From most to least open:
- `open`: accessible and **subclassable/overridable** outside the module.
- `public`: accessible outside the module, but not subclassable/overridable there.
- `package` (Swift 5.9): accessible across modules in the same Swift package.
- `internal` (default): within the module.
- `fileprivate`: within the file.
- `private`: within the enclosing declaration and its extensions **in the same file**.

### Q84. What's the difference between `private` and `fileprivate` today? `[Fundamental]`
**Key points:**
- Since Swift 4, `private` members are visible in extensions of the same type in the same file.
- `fileprivate` is needed when *other types* in the same file need access.

### Q85. What does `@testable import` do? `[Fundamental]`
**Key points:**
- Gives a test target access to `internal` declarations of a module compiled with testing enabled.
- Doesn't expose `private`/`fileprivate`. Testing via public/internal behavior is generally better than reaching into internals.

### Q86. What are ABI stability, module stability, and library evolution? `[Lead/Expert]`
**Key points:**
- **ABI stability** (Swift 5.0): binaries compiled with different Swift versions interoperate; the runtime ships with the OS, so apps don't bundle it.
- **Module stability** (Swift 5.1): `.swiftinterface` files let a framework built with one compiler be imported by a newer compiler.
- **Library evolution** (`BUILD_LIBRARY_FOR_DISTRIBUTION`): binary frameworks can change without breaking clients. `@frozen` promises a type's layout won't change, trading flexibility for performance.
- Relevant when shipping XCFrameworks/SDKs.

## 13. Method Dispatch & Performance

### Q87. What types of method dispatch does Swift use? `[Senior]`
**Key points:**
- **Static (direct)**: struct/enum methods, `final` and `private` class methods, protocol-extension non-requirements. Fastest, can be inlined.
- **Table (vtable)**: overridable class methods.
- **Witness table**: protocol requirements called through a generic or existential.
- **Message dispatch**: `@objc dynamic` methods through the Objective-C runtime (`objc_msgSend`). Needed for KVO and method swizzling.

### Q88. How do `final`, `private`, and whole-module optimization help performance? `[Senior]`
**Key points:**
- They let the compiler prove a method can't be overridden, so it uses static dispatch and can inline.
- Whole-module optimization (default in Release) can infer `final` for `internal` classes with no subclasses in the module.
- Mark classes `final` by default unless designed for inheritance; it also communicates intent.

### Q89. What do `@objc` and `dynamic` do? `[Senior]`
**Key points:**
- `@objc` exposes a declaration to the Objective-C runtime (selectors, `#selector`, target-action).
- `dynamic` forces message dispatch so the implementation can be changed at runtime (KVO, swizzling).
- `@objc` alone doesn't guarantee message dispatch when called from Swift.

### Q90. How would you improve compile times in a large Swift project? `[Lead/Expert]`
**Key points:**
- Measure first: `-Xfrontend -warn-long-function-bodies=100`, `-warn-long-expression-type-checking`, Xcode's Build Timeline.
- Add explicit types to complex literals and long chained expressions; break up giant expressions.
- Modularize into SPM packages so incremental builds recompile less, and keep module interfaces small.
- Mark things `private`/`final`, reduce `@objc` surface, avoid huge files that change often.
- Watch macro and SwiftSyntax build costs (prebuilt swift-syntax helps).

### Q91. What runtime performance pitfalls do you watch for in Swift? `[Lead/Expert]`
**Key points:**
- Existentials (`any P`) in hot paths: boxing and dynamic dispatch.
- Structs containing many reference-type properties: every copy triggers retain/release (ARC traffic).
- Accidental copies of large value types, e.g. mutating an array through a non-unique reference triggers a full CoW copy.
- String operations in loops (`count` is O(n)).
- Using `AnyView` widely in SwiftUI.
- Profile with Instruments before optimizing.

## 14. Advanced & Modern Swift

### Q92. What are result builders? Write a simple one. `[Lead/Expert]`
**Key points:**
- `@resultBuilder` types turn a sequence of statements in a closure into a single value. SwiftUI's `@ViewBuilder` is one.
- Key methods: `buildBlock`, `buildExpression`, `buildOptional` (for `if`), `buildEither` (for `if/else`, `switch`), `buildArray` (for `for` loops).

```swift
@resultBuilder
struct ListBuilder {
    static func buildExpression(_ expression: String) -> [String] { [expression] }
    static func buildBlock(_ components: [String]...) -> [String] { components.flatMap { $0 } }
    static func buildOptional(_ component: [String]?) -> [String] { component ?? [] }
    static func buildEither(first component: [String]) -> [String] { component }
    static func buildEither(second component: [String]) -> [String] { component }
}

func makeList(@ListBuilder _ content: () -> [String]) -> [String] { content() }

let showExtras = true
let items = makeList {
    "Swift"
    "SwiftUI"
    if showExtras { "Combine" }
}
// ["Swift", "SwiftUI", "Combine"]
```

### Q93. What are Swift macros? `[Lead/Expert]`
**Key points:**
- Swift 5.9: compile-time code generation built on SwiftSyntax. They run in a sandbox and only **add** code (they don't modify existing code).
- **Freestanding** (`#`): produce an expression or declarations, e.g. `#Preview`, `#Predicate`, `#expect`.
- **Attached** (`@`): attach to a declaration, e.g. `@Observable`, `@Model`.
- You can inspect expansions in Xcode ("Expand Macro").
- Trade-offs: build-time cost, debugging complexity, learning curve for the team.

### Q94. What are key paths, and how are they useful? `[Senior]`
**Key points:**
- Type-safe references to properties: `\User.name`.
- Types: `KeyPath` (read-only), `WritableKeyPath` (value types), `ReferenceWritableKeyPath` (classes).
- Since Swift 5.2, key paths can be used as functions: `users.map(\.name)`.

```swift
extension Sequence {
    func sorted<T: Comparable>(by keyPath: KeyPath<Element, T>) -> [Element] {
        sorted { $0[keyPath: keyPath] < $1[keyPath: keyPath] }
    }
}
let byName = users.sorted(by: \.name)
```

### Q95. What is `@dynamicMemberLookup`? `[Lead/Expert]`
**Key points:**
- Lets a type respond to arbitrary property-style access via a `subscript(dynamicMember:)`.
- With key paths it stays type-safe; used by SwiftUI's `Binding` (`$model.name`) and wrapper types.

```swift
@dynamicMemberLookup
struct Wrapper<T> {
    var value: T
    subscript<U>(dynamicMember keyPath: KeyPath<T, U>) -> U {
        value[keyPath: keyPath]
    }
}
let w = Wrapper(value: user)
print(w.name) // forwards to user.name
```

### Q96. What is `callAsFunction`? `[Senior]`
**Key points:**
- A method that lets instances be called like functions: `validator(input)`.
- SwiftUI uses it for `DismissAction` (`dismiss()`) and `OpenURLAction`.

### Q97. What are noncopyable types (`~Copyable`)? `[Lead/Expert]`
**Key points:**
- Swift 5.9: types that can't be copied, only moved. Model unique ownership of resources (file descriptors, locks, tokens).
- Noncopyable structs can have a `deinit`.
- `consuming` methods take ownership of `self`; `discard self` skips the `deinit`.

```swift
struct FileDescriptor: ~Copyable {
    private let fd: Int32
    init(fd: Int32) { self.fd = fd }

    consuming func close() {
        // close(fd)
        discard self   // already closed, skip deinit
    }

    deinit {
        // close(fd)
    }
}
```

### Q98. What do `consume`, `borrowing`, and `consuming` mean? `[Lead/Expert]`
**Key points:**
- Ownership modifiers that control copies explicitly.
- `borrowing` parameter: read-only access, caller keeps ownership.
- `consuming` parameter: callee takes ownership.
- `consume x`: ends the lifetime of a local variable, allowing the compiler to move instead of copy.
- Mostly relevant for performance-critical code and noncopyable types.

### Q99. What are `if` and `switch` expressions? `[Fundamental]`
**Key points:**
- Swift 5.9: `if` and `switch` can produce values directly.

```swift
let label = if score > 90 { "A" } else if score > 75 { "B" } else { "C" }

let color: Color = switch status {
case .active: .green
case .inactive: .gray
}
```

### Q100. What does the Swift 6 language mode change? `[Senior]`
**Key points:**
- **Complete data-race safety** checking becomes errors instead of warnings (Sendable, actor isolation, global mutable state).
- `any` is required for existential types.
- Adopt incrementally: per-module language mode, `-strict-concurrency=complete` in Swift 5 mode first.
- Details covered in the Swift Concurrency file.

### Q101. What notable features arrived in Swift 6.x? `[Lead/Expert]`
**Key points (be ready to discuss the ones you've used):**
- Typed throws, pack iteration, noncopyable generics (Swift 6.0).
- `InlineArray` (fixed-size, inline storage) and `Span` (safe, non-escaping view of contiguous memory) (Swift 6.2).
- "Approachable concurrency": option to make code main-actor isolated by default and changes to how nonisolated async functions run (Swift 6.2 / Xcode 26).
- Swift Testing (`@Test`, `#expect`) as the modern testing framework.
- Tip: check the latest Swift release notes before the interview, since interviewers like asking "what's new and have you adopted it?"

## 15. Codable

### Q102. How does `Codable` work? `[Fundamental]`
**Key points:**
- `Codable = Encodable & Decodable`. The compiler synthesizes conformance when all properties are `Codable`.
- `JSONDecoder`/`JSONEncoder`, `PropertyListEncoder`, etc. use encoder/decoder containers (keyed, unkeyed, single value).

### Q103. How do you handle mismatched keys, missing values, and custom formats? `[Senior]`
```swift
struct User: Decodable {
    let id: Int
    let name: String
    let isPremium: Bool

    enum CodingKeys: String, CodingKey {
        case id, name
        case isPremium = "is_premium"
    }

    init(from decoder: Decoder) throws {
        let c = try decoder.container(keyedBy: CodingKeys.self)
        id = try c.decode(Int.self, forKey: .id)
        name = try c.decode(String.self, forKey: .name)
        isPremium = try c.decodeIfPresent(Bool.self, forKey: .isPremium) ?? false
    }
}
```
- Alternatives: `decoder.keyDecodingStrategy = .convertFromSnakeCase`, `dateDecodingStrategy = .iso8601`.
- Nested JSON: `nestedContainer(keyedBy:forKey:)`.

### Q104. How do you decode an enum safely when the server may add new values? `[Senior]`
**Key points:**
- A plain `String` raw-value enum throws on unknown values, failing the whole payload.
- Add a fallback case:

```swift
enum Status: Decodable {
    case active, suspended, unknown(String)

    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)
        switch raw {
        case "active": self = .active
        case "suspended": self = .suspended
        default: self = .unknown(raw)
        }
    }
}
```

### Q105. How would you decode a heterogeneous array (e.g. a feed with different item types)? `[Lead/Expert]`
**Key points:**
- Decode a `type` discriminator first, then decode the matching payload into an enum with associated values.

```swift
enum FeedItem: Decodable {
    case post(Post)
    case ad(Ad)
    case unsupported

    private enum CodingKeys: String, CodingKey { case type }

    init(from decoder: Decoder) throws {
        let type = try decoder.container(keyedBy: CodingKeys.self).decode(String.self, forKey: .type)
        switch type {
        case "post": self = .post(try Post(from: decoder))
        case "ad":   self = .ad(try Ad(from: decoder))
        default:     self = .unsupported
        }
    }
}
```

## 16. "What's the Output?" Questions

### Q106. Closure capture `[Senior]`
```swift
var x = 10
let a = { print(x) }
let b = { [x] in print(x) }
x = 20
a()
b()
```
**Output:** `20` then `10`. `a` captures the variable; `b` captures the value at creation.

### Q107. Struct vs class copy `[Fundamental]`
```swift
struct PointS { var x = 0 }
class PointC { var x = 0 }

var s1 = PointS(); var s2 = s1; s2.x = 5
let c1 = PointC(); let c2 = c1; c2.x = 5
print(s1.x, c1.x)
```
**Output:** `0 5`.

### Q108. Classes inside an array `[Senior]`
```swift
class Box { var value = 0 }
var a = [Box()]
var b = a
b[0].value = 5
print(a[0].value)
```
**Output:** `5`. The array is copied, but its elements are references to the same `Box`.

### Q109. Protocol extension dispatch `[Senior]`
```swift
protocol Animal { func sound() -> String }
extension Animal {
    func sound() -> String { "..." }
    func describe() -> String { "Generic animal" }
}
struct Dog: Animal {
    func sound() -> String { "Woof" }
    func describe() -> String { "Dog" }
}
let pet: Animal = Dog()
print(pet.sound(), pet.describe())
```
**Output:** `Woof Generic animal`. `describe()` isn't a requirement, so it's statically dispatched on `Animal`.

### Q110. `defer` order `[Fundamental]`
```swift
func test() {
    defer { print("1") }
    defer { print("2") }
    print("3")
}
test()
```
**Output:** `3 2 1`.

### Q111. `defer` and return values `[Senior]`
```swift
func value() -> Int {
    var x = 1
    defer { x = 100 }
    return x
}
print(value())
```
**Output:** `1`. The return value is computed before `defer` runs.

### Q112. Property observers during init `[Senior]`
```swift
class Counter {
    var value = 0 { didSet { print("didSet \(value)") } }
    init() { value = 10 }
}
let c = Counter()
c.value = 20
```
**Output:** only `didSet 20`. Observers don't fire for a class's own properties during its own `init`.

### Q113. Generic overload resolution `[Lead/Expert]`
```swift
func describe<T>(_ v: T) { print("generic") }
func describe(_ v: Int) { print("Int") }
func wrapper<T>(_ v: T) { describe(v) }

describe(5)
wrapper(5)
```
**Output:** `Int` then `generic`. Overloads are resolved at compile time; inside `wrapper`, `v` is just `T`.

### Q114. Mutating an array while iterating `[Senior]`
```swift
var nums = [1, 2, 3]
for n in nums { nums.append(n) }
print(nums)
```
**Output:** `[1, 2, 3, 1, 2, 3]`. The loop iterates over a copy (value semantics), so no infinite loop or crash.

### Q115. Lazy closure retain cycle `[Senior]`
```swift
class ViewModel {
    var name = "A"
    lazy var greet: () -> String = { "Hello \(self.name)" }
    deinit { print("deinit") }
}
var vm: ViewModel? = ViewModel()
_ = vm?.greet()
vm = nil
```
**Output:** nothing. `deinit` never runs: `self` stores a closure that strongly captures `self`. Fix with `{ [unowned self] in ... }` or `[weak self]`.

### Q116. String counting `[Senior]`
```swift
let family = "👨‍👩‍👧"
print(family.count, family.unicodeScalars.count)
```
**Output:** `1 5`. One grapheme cluster made of three emoji joined by two zero-width joiners.

### Q117. `let` with reference vs value types `[Fundamental]`
```swift
class User { var name = "A" }
struct Config { var name = "A" }

let u = User()
u.name = "B"      // ?
let c = Config()
c.name = "B"      // ?
```
**Answer:** The class mutation compiles; the struct mutation is a compile error.

## 18. Senior / Lead Scenario Questions

These have no single correct answer. Interviewers evaluate reasoning, trade-offs, and communication.

### Q118. How do you decide between struct, class, enum, and actor in a large codebase? `[Senior]`
**Talking points:**
- Default to **struct** for models and value-like data.
- **Enum** for finite states and variants (make invalid states unrepresentable).
- **Class** for identity, lifecycle, UIKit/ObjC interop, or shared reference semantics on one thread (often `@MainActor`).
- **Actor** for shared mutable state accessed from multiple concurrent contexts.
- Mention how the choice affects testability, thread-safety, and Swift 6 `Sendable` requirements.

### Q119. Design a type-safe networking layer using Swift features. `[Lead/Expert]`
**Talking points:** protocols + associated types, generics, async/await, error mapping, testability (inject `URLSession` or a protocol).

```swift
protocol Endpoint {
    associatedtype Response: Decodable
    var path: String { get }
    var method: String { get }
}

struct APIClient {
    let baseURL: URL
    var session: URLSession = .shared

    func send<E: Endpoint>(_ endpoint: E) async throws -> E.Response {
        var request = URLRequest(url: baseURL.appending(path: endpoint.path))
        request.httpMethod = endpoint.method
        let (data, response) = try await session.data(for: request)
        guard let http = response as? HTTPURLResponse,
              (200..<300).contains(http.statusCode) else {
            throw URLError(.badServerResponse)
        }
        return try JSONDecoder().decode(E.Response.self, from: data)
    }
}
```
Follow-ups to prepare: auth token refresh, retries with backoff, request cancellation, caching, mocking for tests.

### Q120. How would you plan migrating a large app to Swift 6 language mode? `[Lead/Expert]`
**Talking points:**
- Audit: enable `-strict-concurrency=targeted`, then `complete`, module by module; measure warning counts.
- Migrate leaf modules (models, utilities) first, then features, then the app target.
- Make models `Sendable`, isolate UI code to `@MainActor`, convert shared mutable singletons into actors or protect them properly.
- Use `@preconcurrency import` for dependencies not yet updated; track remaining `@unchecked Sendable` as tech debt.
- Avoid big-bang migration; keep shipping features; get team training and shared guidelines.

### Q121. How do you enforce code quality and consistency across a team? `[Lead/Expert]`
**Talking points:**
- Automated: SwiftLint, SwiftFormat, CI checks, required tests, danger bots for PR hygiene.
- Human: code review guidelines (focus on design and correctness, not style nits machines can catch), architecture decision records (ADRs), DocC documentation.
- Shared conventions: access control defaults, `final` by default, error-handling patterns, no force unwraps outside tests.

### Q122. Your team wants to adopt macros (or another new Swift feature). How do you evaluate it? `[Lead/Expert]`
**Talking points:**
- What problem does it solve, and how much boilerplate/bug risk does it remove?
- Costs: build time, debuggability, onboarding, tooling support, minimum deployment target or toolchain requirements.
- Run a time-boxed spike in one module, measure, write an ADR, then decide.
- Reversibility: how hard is it to back out?

### Q123. How would you design a public Swift SDK used by other teams or companies? `[Lead/Expert]`
**Talking points:**
- Follow the Swift API Design Guidelines (clarity at the point of use, argument labels).
- Minimal public surface; `public` vs `open` deliberately; `package` for internal sharing.
- Library evolution for binary distribution; `@frozen` only when layout is truly fixed.
- Semantic versioning, deprecation with `@available(*, deprecated, renamed:)`.
- Sendable-correct API, async-first APIs, clear error types, documentation with DocC.
- Distribution: SPM, XCFramework.

### Q124. Production has crashes from force unwraps and `fatalError`s. What do you do as a lead? `[Lead/Expert]`
**Talking points:**
- Short term: triage via crash reports, hotfix the top offenders.
- Root cause: why were invalid states possible? Fix the model (non-optional types, enums for states, validation at boundaries).
- Prevent: lint rules for force unwrap/try!, review checklist, tests for edge cases, decoding fallbacks.
- Distinguish `precondition` for true programmer errors vs recoverable errors that should be handled.

### Q125. How would you explain value semantics to a junior developer? `[Senior]`
**Talking points:**
- Use an analogy: a value type is like handing someone a photocopy; a reference type is like sharing a Google Doc link.
- Show a 5-line code example, then show the bug value semantics prevents (unexpected shared mutation).
- Interviewers are evaluating your mentoring and communication skills here, not just correctness.
