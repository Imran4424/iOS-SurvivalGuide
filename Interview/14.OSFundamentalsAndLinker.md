## 1. Operating System Basics

### Q1. What does an operating system do? `[Fundamental]`
- **Abstracts hardware**: apps use files, sockets and windows instead of disk blocks, network cards and framebuffers.
- **Manages resources**: CPU time (scheduling), memory (virtual memory), storage, power, network.
- **Isolates and protects**: each process gets its own address space and permissions; one app can't read another's memory or files.
- **Provides services**: file systems, networking stacks, IPC, security (code signing, sandboxing), drivers.

On iOS the OS also enforces **policy**: which apps may run (code signing), what they can access (sandbox, entitlements, privacy permissions), and when they run (background limits, termination).

### Q2. What is the difference between kernel space and user space? `[Fundamental]`
| | Kernel space | User space |
|---|---|---|
| Who runs there | The kernel (XNU) and drivers | Apps, extensions, system daemons, frameworks |
| CPU privilege | Privileged mode (EL1 on ARM) | Unprivileged (EL0) |
| Memory access | All physical memory, hardware | Only its own virtual address space |
| A bug causes | Kernel panic (whole device reboots) | That process crashes |

- User code reaches the kernel only through **system calls** (Q3) or **Mach traps/messages**.
- Most of what iOS developers call "the OS" (UIKit, Foundation, SpringBoard, daemons) is **user space**.

### Q3. What is a system call? `[Fundamental]`
- A controlled entry point from user space into the kernel to request a privileged operation: `open`, `read`, `write`, `mmap`, `socket`, `kevent`, Mach `mach_msg`.
- The CPU switches to privileged mode (a trap instruction, `svc` on ARM), the kernel validates arguments and permissions, does the work, and returns.
- **Cost**: much more than a normal function call (mode switch, checks, cache effects). That's why I/O is buffered (`FileHandle`, `Data` reads in large chunks) and why chatty I/O on the main thread hurts.

```
Swift: try Data(contentsOf: url)
  └─ Foundation ─▶ libsystem (open, fstat, read, close) ─▶ svc ─▶ XNU: VFS → APFS → storage driver
```

### Q4. What is Darwin, and how is XNU structured? `[Senior]`
**Darwin** is the open-source core shared by iOS, macOS, watchOS, tvOS and visionOS: the **XNU** kernel plus basic user-space libraries (libSystem, dyld, launchd).

**XNU** ("X is Not Unix") is a **hybrid kernel**:
| Component | Provides |
|---|---|
| **Mach** (microkernel heritage) | Tasks and threads, scheduling, virtual memory, IPC via Mach ports and messages |
| **BSD layer** | POSIX processes and APIs, users and permissions, file systems (VFS), networking stack, signals, sandbox policy hooks |
| **IOKit** | Object-oriented driver framework (C++ subset) |
| **libkern / Platform Expert** | Kernel runtime, hardware abstraction |

- "Task" (Mach) ≈ "process" (BSD); a BSD process wraps a Mach task.
- Mach messages underlie **XPC**, which apps use indirectly for almost every system service (Threads & Processes Q16).

### Q5. Monolithic, microkernel or hybrid: what's the difference? `[Senior]`
| Design | Idea | Pros | Cons | Example |
|---|---|---|---|---|
| Monolithic | Drivers, file systems, networking all in kernel space | Fast (function calls) | A driver bug can crash the kernel | Linux |
| Microkernel | Minimal kernel (IPC, scheduling, memory); services run as user processes | Isolation, reliability | IPC overhead | Mach (pure), QNX, seL4 |
| Hybrid | Microkernel structure, but services run in kernel space for speed | Balance | Complexity | XNU, Windows NT |

XNU combines Mach's abstractions with BSD and drivers in one kernel address space, for performance.

### Q6. How are iOS frameworks layered? `[Fundamental]`
```
┌───────────────────────────────────────────────────────────────┐
│ Cocoa Touch / UI: UIKit, SwiftUI, MapKit, UserNotifications   │
├───────────────────────────────────────────────────────────────┤
│ Media: Core Animation, Metal, AVFoundation, Core Image        │
├───────────────────────────────────────────────────────────────┤
│ Core Services: Foundation, Core Data, CloudKit, Network       │
├───────────────────────────────────────────────────────────────┤
│ Core OS: Security, Accelerate, libSystem (libc, libdispatch,  │
│          libobjc, Swift runtime), dyld, Mach/BSD APIs         │
├───────────────────────────────────────────────────────────────┤
│ XNU kernel + drivers                                          │
└───────────────────────────────────────────────────────────────┘
```
- Higher layers are built on lower ones (e.g. UIKit → Core Animation → Metal → GPU driver).
- System frameworks live in the **dyld shared cache** (Q49), so every app shares one copy in memory.

### Q7. What is launchd? `[Senior]`
- The first user-space process (**PID 1**), started by the kernel at boot.
- Launches and supervises daemons and agents (on demand, when a Mach service or XPC connection is requested), and restarts them if they crash.
- Apps are launched through the system's process management (SpringBoard asks RunningBoard/launchd to spawn the app process); launchd plays the role that `init`/`systemd` plays on Linux.

### Q8. What are interrupts, traps and exceptions? `[Senior]`
| Event | Source | Example |
|---|---|---|
| **Interrupt** | Hardware, asynchronous | Timer tick (enables preemptive scheduling), touch controller, network packet |
| **Trap** | Deliberate instruction | `svc` for a system call; Swift runtime traps use `brk` (shows as `EXC_BREAKPOINT`) |
| **Fault / exception** | Error during an instruction | Access to unmapped memory → page fault → either loads the page or delivers `EXC_BAD_ACCESS` |

- On Darwin, hardware exceptions become **Mach exceptions** (`EXC_BAD_ACCESS`, `EXC_BREAKPOINT`, `EXC_CRASH`), translated to BSD **signals** (`SIGSEGV`, `SIGBUS`, `SIGTRAP`, `SIGABRT`). That's why crash reports show both, e.g. `EXC_BAD_ACCESS (SIGSEGV)`.
- Crash reporters register Mach exception handlers or signal handlers to capture these.

## 2. Memory Management on iOS

### Q9. What is virtual memory? `[Fundamental]`
- Each process sees its own large, contiguous **virtual address space**; the CPU's **MMU** translates virtual addresses to physical RAM using **page tables** managed by the kernel.
- Memory is managed in **pages**: **16 KB** on Apple arm64 devices (4 KB on Intel Macs).
- Benefits:
  - **Isolation**: a process can't even name another process's physical memory.
  - **Lazy loading**: pages are mapped on first touch (a **page fault** brings them in).
  - **Sharing**: the same physical page (system frameworks, the dyld shared cache) can appear in many processes.
  - **Protection**: per-page permissions (read/write/execute); code pages are read-only + executable; data pages aren't executable (W^X).

```
Process A virtual          Physical RAM            Process B virtual
0x1000_0000 ─────────┐      ┌──────────┐      ┌──── 0x1800_0000
 (UIKit __TEXT)      └────▶ │ shared   │ ◀────┘   (UIKit __TEXT)     same physical page, mapped twice
0x2000_0000 ───────────────▶│ A's heap │
                            │ B's heap │ ◀──────── 0x2400_0000
                            └──────────┘
```

### Q10. Does iOS swap memory to disk? `[Senior]`
- **No swap file on iPhone** (flash wear, power, latency). iPadOS 16+ added swap on M-series iPads; macOS swaps.
- Instead, iOS uses:
  - **Clean pages** discarded and re-read from disk when needed (code, read-only mapped files).
  - **Memory compression**: dirty pages that haven't been used recently are **compressed** in RAM.
  - **Memory warnings**, then **jetsam** (killing processes) when compression isn't enough.
- This is why an iOS app's limiting resource is its **dirty + compressed memory** (its **footprint**), not virtual size.

### Q11. What are clean, dirty and compressed memory? `[Senior]`
| Type | Meaning | Examples | Counts toward footprint? |
|---|---|---|---|
| **Clean** | Unmodified pages that can be re-read from disk | Your binary's code (`__TEXT`), memory-mapped read-only files, framework code | No (can be discarded) |
| **Dirty** | Pages written by the process | Heap allocations, decoded images, globals, `__DATA` after fixups | **Yes** |
| **Compressed** | Dirty pages the OS compressed because they weren't used recently | Old cache contents | **Yes** (at their uncompressed size for accounting) |

- **Footprint ≈ dirty + compressed**. Jetsam limits apply to footprint.
- Freeing compressed memory requires decompressing it first, which is why memory warnings can briefly **increase** CPU and memory use.
- Practical consequence: a 4000×3000 image is ~2 MB as JPEG on disk but **~48 MB dirty** once decoded (4 bytes per pixel). Downsample to display size.

### Q12. What is jetsam, and how do memory limits work? `[Senior]`
- **Jetsam** is the iOS mechanism that **kills processes** when the system runs low on memory, in priority order: suspended background apps first, then background apps doing work, and finally the foreground app if it exceeds **its own footprint limit**.
- Limits depend on the device's RAM and the process type; extensions have much lower limits than apps (Threads & Processes Q14).
- No crash report: a **JetsamEvent** log, MetricKit `MXAppExitMetric` (memory-limit exits), Xcode Organizer terminations.
- Check how much headroom you have at runtime:

```swift
import os

let available = os_proc_available_memory()                  // bytes left before hitting this process's limit
if available < 200 * 1024 * 1024 {
    imageCache.removeAllObjects()                           // shed caches before decoding something big
}
```
- Apps can request higher limits on some devices with the **Increased Memory Limit** entitlement (`com.apple.developer.kernel.increased-memory-limit`), but must still behave on devices where it isn't granted.

### Q13. How should an app respond to memory warnings? `[Fundamental]`
- Signals: `UIApplication.didReceiveMemoryWarningNotification`, `applicationDidReceiveMemoryWarning(_:)`, `UIViewController.didReceiveMemoryWarning()`, and `DispatchSource.makeMemoryPressureSource` (`.warning`, `.critical`).
- Respond by freeing **rebuildable** memory: image caches, prefetched data, off-screen view controllers' heavy resources.
- `NSCache` evicts automatically under pressure; a `Dictionary` cache doesn't.
- A warning means you're close; a background app that holds a big footprint is likely to be **jetsammed** next. Reduce footprint when entering the background as well.

```swift
final class MemoryPressureObserver: @unchecked Sendable {
    private let source = DispatchSource.makeMemoryPressureSource(eventMask: [.warning, .critical], queue: .main)

    init(onPressure: @escaping @MainActor @Sendable () -> Void) {
        source.setEventHandler { MainActor.assumeIsolated { onPressure() } }   // queue is .main
        source.activate()
    }
    deinit { source.cancel() }
}
```

### Q14. What is the difference between the stack and the heap? `[Fundamental]`
| | Stack | Heap |
|---|---|---|
| Per | Thread | Process (shared) |
| Allocation | Moving the stack pointer: almost free | `malloc`: search free lists, possible locking |
| Lifetime | Automatic, ends with the function | Until freed (ARC for Swift classes) |
| Size | Small and fixed (iOS: 1 MB main thread, 512 KB others) | Large (limited by footprint) |
| Swift contents | Value types whose size is known and that don't escape | Class instances, escaping closure contexts, large/indirect values, array/string/dictionary storage |
| Failure | Stack overflow (deep recursion) → `EXC_BAD_ACCESS` | Leaks, fragmentation, jetsam |

- "Structs are on the stack" is a simplification: a struct stored in a class property lives in the heap with the object; `Array`'s buffer is always on the heap; the optimizer may also promote small class allocations to the stack.

### Q15. What is ASLR? `[Senior]`
- **Address Space Layout Randomization**: the kernel loads the executable, libraries, heap and stacks at **random addresses** each launch (with randomized "slide").
- Makes exploits harder (attackers can't hardcode addresses of code or data).
- Consequences:
  - Pointers inside the binary must be **fixed up** at load time (rebasing, done by dyld; Q48).
  - Crash report addresses must be **symbolicated** using the binary's load address and the dSYM (Q66).
- Position-independent code (PIE) is mandatory for iOS executables.

### Q16. What is copy-on-write at the OS level? `[Senior]`
- Pages shared between mappings are marked read-only; on the first **write**, the kernel copies the page privately for the writer.
- Used for: framework `__DATA` pages shared from the dyld shared cache until written; `fork` on macOS/Linux; memory-mapped files opened privately.
- Don't confuse with Swift's **copy-on-write collections** (a library-level optimization where `Array`/`Dictionary` share a buffer until one copy is mutated, checked with `isKnownUniquelyReferenced`). Same idea, different layer.

### Q17. What are memory-mapped files, and when are they useful? `[Lead/Expert]`
- `mmap` maps a file into the address space; pages are read **lazily on access** and are **clean** (the OS can drop and re-read them), so they don't count toward footprint like heap copies do.
- Great for **large, read-mostly data**: ML models, dictionaries, map tiles, large JSON/binary assets read selectively.

```swift
// Maps the file instead of copying it into the heap
let data = try Data(contentsOf: largeFileURL, options: .alwaysMapped)
// Reading a slice only pages in the touched 16 KB pages
let header = data.prefix(64)
```
- Caveats: if the file is modified or deleted while mapped, reads can fail (`SIGBUS`); not for files on network volumes; Data Protection can make the file unreadable when the device is locked.

### Q18. How does ARC differ from garbage collection, from the OS's perspective? `[Senior]`
| | ARC (Swift/Objective-C) | Tracing GC (Java, Kotlin/JVM, C#) |
|---|---|---|
| When memory is freed | Deterministically, when the last strong reference goes away | Later, when the collector runs |
| Pauses | None (small, spread-out retain/release cost) | Collection pauses (mitigated by concurrent collectors) |
| Memory overhead | Low (no need for headroom) | Needs headroom (often 2–3× live data) for efficiency |
| Cycles | Leak unless broken with `weak`/`unowned` | Collected automatically |
| Fit for iOS | Predictable, low footprint (no swap, jetsam limits) | Needs more RAM |

Interview angle: ARC's predictability is part of why iOS apps run in less RAM; the trade-off is that you must manage reference cycles.

### Q19. What tools do you use to investigate memory? `[Senior]`
| Tool | Shows |
|---|---|
| Xcode **Memory Report** (debug gauge) | Live footprint |
| **Memory Graph Debugger** | Object graph, leaks, retain cycles (with backtraces when Malloc Stack Logging is on) |
| Instruments **Allocations** | Heap growth over time, generations ("mark generation" between repeated actions) |
| Instruments **Leaks** | Unreachable allocations |
| Instruments **VM Tracker** | Dirty / swapped (compressed) / resident memory by region |
| `footprint`, `vmmap`, `heap`, `leaks`, `malloc_history` (command line, on `.memgraph` files) | Detailed breakdowns, scriptable in CI |
| MetricKit `MXMemoryMetric`, Xcode Organizer | Field data: peak memory, memory-limit terminations |

```bash
# Export a memory graph from Xcode (File → Export Memory Graph), then:
footprint MyApp.memgraph            # dirty/compressed per category
vmmap --summary MyApp.memgraph      # regions: MALLOC, IOSurface, CG image, __DATA...
leaks MyApp.memgraph                # leaked objects and cycles
```

### Q20. What usually dominates an iOS app's memory, and how do you reduce it? `[Senior]`
1. **Decoded images**: downsample to the displayed size (ImageIO thumbnails, `preparingThumbnail(of:)`), use appropriate formats, release off-screen images, `NSCache` with a cost limit.
2. **Caches** without limits (dictionaries of models, responses): bound them; purge on warnings and on backgrounding.
3. **Leaks/retain cycles**: closures capturing `self`, delegates not `weak`, timers retaining targets.
4. **Large data loaded at once**: stream or memory-map instead of `Data(contentsOf:)` into the heap.
5. **Views and layers**: offscreen rendering, huge layer backing stores, many web views (each `WKWebView` has its own processes, but your app still pays for some).
6. **Frameworks' `__DATA`**: dynamic frameworks add dirty pages after fixups; fewer frameworks and static linking reduce it.

### Q21. What is a page fault, and why do they matter for launch time? `[Lead/Expert]`
- A **page fault** happens when code touches a virtual page that isn't currently mapped to RAM: the kernel loads it from disk (for file-backed pages), zero-fills it (new memory), or decompresses it.
- A cold launch touches many pages of your binary; each fault from disk costs time (and code-signature validation of each page).
- Reducing faults speeds up launch:
  - Smaller binaries and less code run at launch.
  - **Order files** (`ORDER_FILE` build setting) group functions used during launch onto the same pages.
  - Fewer fixups (chained fixups, fewer dynamic frameworks) dirty fewer pages (Q51).
- Instruments **App Launch** shows "File Backed Page In" events.

## 3. File System, Storage & Security

### Q22. What is APFS, and what features matter to app developers? `[Senior]`
**APFS** (Apple File System), used on all Apple devices:
- **Copy-on-write metadata and clones**: copying a file on the same volume (`FileManager.copyItem`) creates a **clone** instantly, sharing blocks until either copy changes.
- **Atomic safe-save**: writing to a temporary file and renaming over the original is atomic (`Data.write(to:options: .atomic)` does this).
- **Snapshots** (used for backups and updates).
- **Native encryption**, with per-file keys (the basis of Data Protection, Q24).
- **Space sharing** between volumes; **sparse files**.

```swift
// Atomic write: readers see either the old file or the new one, never a half-written file
try data.write(to: fileURL, options: [.atomic, .completeFileProtectionUntilFirstUserAuthentication])
```

### Q23. What is the app sandbox's directory layout, and what gets backed up? `[Fundamental]`
| Location | Purpose | Backed up (iCloud/Finder) | Purged by the system |
|---|---|---|---|
| `Documents/` | User-created content (visible in Files if you enable file sharing) | Yes | No |
| `Library/Application Support/` | App data the user didn't create directly (databases, downloaded content needed offline) | Yes | No |
| `Library/Caches/` | Rebuildable data (image cache, responses) | **No** | **Yes**, when storage is low |
| `tmp/` | Short-lived files | No | Yes, any time the app isn't running |
| App bundle (`MyApp.app`) | Code and resources | — | Read-only, signed |
| App Group container | Shared with extensions/other apps of the team | Yes | No |

- Mark large re-downloadable files in Application Support with `isExcludedFromBackup` (App Review checks backup size).
- Don't store user data in Caches or tmp: it can disappear.

```swift
var url = FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)[0]
    .appending(path: "Models/large-model.bin")
var values = URLResourceValues()
values.isExcludedFromBackup = true                 // re-downloadable; don't bloat backups
try url.setResourceValues(values)
```

### Q24. What are the Data Protection classes? `[Senior]`
| Class | File readable when | Use for |
|---|---|---|
| `.complete` | Only while the device is **unlocked** (key discarded ~10 s after lock) | Most sensitive data |
| `.completeUnlessOpen` | Files already open stay writable after lock; new files can be created while locked | Downloads that finish while locked |
| `.completeUntilFirstUserAuthentication` (**default**) | After the first unlock since boot, until reboot | Data needed by background launches |
| `.none` | Always (still encrypted at rest with the device key) | Data needed before first unlock (rare) |

- Same idea for the **Keychain** with `kSecAttrAccessible…` values (`WhenUnlocked`, `AfterFirstUnlock`, `…ThisDeviceOnly`).
- Interaction with background execution: a background launch while locked can't read `.complete` files (Threads & Processes Q18).

### Q25. What is code signing, and what does it protect? `[Senior]`
- Every executable page on iOS must be **signed** by Apple or a developer certificate trusted through a **provisioning profile**; the kernel checks signatures as pages are loaded and **kills** the process if a page doesn't match.
- The signature covers: the executable's pages (code directory hashes), resources (`_CodeSignature/CodeResources`), **entitlements**, and the bundle identifier/team.
- Consequences:
  - Apps can't modify their own code or download and execute native code; **JIT** (writable + executable memory) isn't allowed for normal apps.
  - Every embedded framework is signed (Embed & Sign).
  - Tampering (re-signing a modified app) changes the identity; App Attest can detect it server-side.

```bash
codesign -dvvv MyApp.app                         # identity, team, hashes
codesign -d --entitlements :- MyApp.app          # entitlements baked into the signature
security cms -D -i MyApp.app/embedded.mobileprovision   # the provisioning profile
```

### Q26. What are entitlements? `[Fundamental]`
- Key-value **capabilities** embedded in the code signature that the OS checks before granting access: `aps-environment` (push), `com.apple.security.application-groups`, `keychain-access-groups`, `com.apple.developer.associated-domains`, HealthKit, iCloud containers, Increased Memory Limit…
- They must be **allowed by the provisioning profile** (enabled for the App ID in the developer account); otherwise the app won't install or the feature silently fails.
- Different from **privacy permissions** (camera, location), which the user grants at runtime and which need `NS…UsageDescription` strings.

### Q27. What is the app sandbox, and how is it enforced? `[Senior]`
- A kernel-enforced policy (the **Sandbox** kernel extension using MAC hooks in the BSD layer) that restricts each app to: its container, its entitlements' resources, and allowed system services.
- Every file open, Mach lookup or network operation is checked against the profile; violations are denied (and logged as "Sandbox: deny").
- Defense in depth with: code signing (only approved code runs), entitlements (only approved capabilities), privacy permissions (user consent), Data Protection (encryption), and **pointer authentication / memory tagging** on newer hardware (Q28).

### Q28. What hardware security features protect iOS apps? `[Lead/Expert]`
| Feature | What it does |
|---|---|
| **Secure Enclave** | Separate processor holding keys that never leave it (Face ID/Touch ID templates, `SecureEnclave.P256` keys in CryptoKit, Apple Pay) |
| **Data Protection keys** | Per-file keys wrapped by class keys derived from the passcode and hardware UID |
| **Pointer Authentication (PAC, arm64e)** | Signs pointers (return addresses, function pointers, vtables) and checks them before use, blocking many control-flow hijacks |
| **Memory Integrity Enforcement / memory tagging** (A19 / M5 and later) | Tags allocations and pointers; mismatches (use-after-free, out-of-bounds) crash instead of being exploitable |
| **Kernel integrity protection, W^X** | Kernel code and app code pages can't be modified at runtime |

- Apple's system binaries have used **arm64e** with PAC for years. **Xcode 26's Enhanced Security capability** lets third-party apps opt into these protections: building for `arm64e` with pointer authentication, typed allocators, hardware memory tagging on supported devices, zero-initialized stack variables, C++ library hardening, and extra security warnings.
- Swift code benefits from memory safety by default; these features mainly harden C, C++ and Objective-C code (including in your dependencies).

### Q29. How should an app store secrets and sensitive data? `[Senior]`
| Data | Where |
|---|---|
| Tokens, passwords, keys | **Keychain**, with the narrowest accessibility that still works (`…AfterFirstUnlockThisDeviceOnly` for tokens used in the background) |
| Private keys that must never be exported | **Secure Enclave** (`SecureEnclave.P256.Signing.PrivateKey`), optionally requiring biometrics |
| Sensitive files | Files with `.complete` protection; exclude from backup if device-bound |
| Settings | `UserDefaults` (plain plist in the container, **not** for secrets) |
| Secrets in the app binary | Nowhere: anything in the binary can be extracted (Framework Distribution Q48) |

## 4. From Source Code to Executable

### Q30. What happens when you press Build in Xcode? `[Fundamental]`
```
Swift files ──▶ swift-frontend: parse → type-check → SIL (Swift Intermediate Language, optimizations,
                ARC, ownership checks) → LLVM IR → machine code ──▶ .o (one per file or per batch)
C/ObjC files ─▶ clang: preprocess → parse → LLVM IR → machine code ─────────────────────────────▶ .o
Swift modules also produce .swiftmodule / .swiftinterface (for importers) and ObjC headers (-Swift.h)

.o files + static libraries (.a) + references to dynamic libraries (.dylib/.tbd/.framework)
        │
        ▼
Static linker (ld): resolve symbols, lay out segments, apply relocations, record dyld fixups ──▶ executable (Mach-O)
        │
        ▼
Resource steps: compile asset catalogs (actool → Assets.car), storyboards (ibtool), string catalogs, Info.plist
        │
        ▼
Embed frameworks/extensions → generate dSYM (dsymutil) → code sign (codesign) ──▶ MyApp.app
```
- **Compile errors** come from the frontend (types, syntax). **Link errors** come from `ld` (missing or duplicate symbols). **Load errors** come from dyld at launch (missing libraries/symbols). Knowing which stage failed narrows the cause immediately (Q36).

### Q31. What's inside an object file? `[Senior]`
- **Machine code** and data in **sections** (`__TEXT,__text` for code, `__TEXT,__cstring` for C strings, `__DATA,__data` for initialized globals…).
- A **symbol table**: symbols it **defines** (functions, globals, type metadata) and symbols it **needs** (undefined references to other files or libraries).
- **Relocations**: places in the code/data that must be patched once the final addresses are known (calls to other functions, pointers to globals).

```bash
$ nm -m Networking.o | swift demangle
                 (undefined) external _OBJC_CLASS_$_NSURLSession (from Foundation) ← needed from elsewhere
0000000000000120 (__TEXT,__text) external MyApp.APIClient.send(_:) -> ...          ← defined here, exported
0000000000000000 (__TEXT,__text) non-external MyApp.(helper in _3F2A...)()         ← file-private
```
`nm` flags to know: `U` = undefined, `T`/`t` = defined in text (uppercase = external), `D`/`d` = data, `S`/`s` = other sections.

### Q32. What is the Mach-O format? `[Senior]`
Mach-O is the executable format for Apple platforms (executables, dylibs, bundles, object files).

```
┌──────────────────────────────┐
│ Header                       │  magic 0xfeedfacf (64-bit), CPU type (arm64), file type (EXECUTE, DYLIB…)
├──────────────────────────────┤
│ Load commands                │  instructions for the kernel and dyld:
│   LC_SEGMENT_64 (×N)         │    segment layout and permissions
│   LC_LOAD_DYLIB (×N)         │    dynamic libraries to load (install names)
│   LC_RPATH                   │    runpath search paths
│   LC_MAIN                    │    entry point
│   LC_DYLD_CHAINED_FIXUPS     │    pointer fixups for dyld (Q51)
│   LC_CODE_SIGNATURE          │    where the signature is
│   LC_BUILD_VERSION, LC_UUID  │    platform/min OS; unique build ID (matches the dSYM)
├──────────────────────────────┤
│ __PAGEZERO                   │  unmapped first 4 GB: null-pointer dereferences crash
│ __TEXT        (r-x)          │  code (__text), stubs, C strings, Swift/ObjC read-only metadata
│ __DATA_CONST  (r-- after fixups) │ pointers fixed up at launch, then made read-only (GOT, ObjC class lists)
│ __DATA        (rw-)          │  mutable globals, ObjC class data, lazy pointers
│ __LINKEDIT    (r--)          │  symbol tables, fixup info, export trie, code signature
└──────────────────────────────┘
```
```bash
otool -h MyApp                 # header
otool -l MyApp | less          # all load commands (segments, LC_LOAD_DYLIB, LC_RPATH...)
otool -L MyApp                 # linked libraries (install names)
size -m MyApp                  # sizes per segment/section
dyld_info -fixups MyApp        # what dyld will patch at launch
```
A **universal (fat)** file (magic `0xcafebabe`) wraps several Mach-O slices for different architectures; `lipo` creates and inspects them.

### Q33. What are symbols, and how does name mangling work? `[Senior]`
- A **symbol** is a name the linker uses for a function, global variable or metadata record.
- **C**: the name with a leading underscore (`main` → `_main`).
- **Objective-C**: classes as `_OBJC_CLASS_$_MyClass`, metaclasses `_OBJC_METACLASS_$_MyClass`; methods are found at runtime by selector, not by symbol.
- **C++ and Swift**: **mangled** names encode module, type, function name and signature, so overloads get unique symbols.

```bash
$ nm MyApp | grep APIClient | head -2
0000000100004a10 T _$s5MyApp9APIClientC4sendyxAA7RequestVyxGYaKlF
$ swift demangle '_$s5MyApp9APIClientC4sendyxAA7RequestVyxGYaKlF'
MyApp.APIClient.send<A>(MyApp.Request<A>) async throws -> A
```
**Visibility:**
- Swift `public`/`open` declarations are **exported** from a dynamic library; `internal`/`fileprivate`/`private` ones aren't visible outside the module's binary.
- That's why `@testable import` needs the module built with **testing enabled** (`-enable-testing`, the Debug default): it makes internal symbols linkable from the test bundle.
- C/Objective-C: `__attribute__((visibility("hidden")))` or `-fvisibility=hidden` keeps symbols internal.

### Q34. What is the two-level namespace? `[Lead/Expert]`
- When linking against a dynamic library, Apple's linker records **both** the symbol name **and** the library it came from ("`_foo` from `libA.dylib`").
- At runtime, dyld looks for the symbol **only in that library**.
- Benefits: two dylibs can export the same symbol name without conflict; lookups are faster.
- Contrast: Linux uses a flat namespace by default (first definition found wins), which enables symbol interposition (`LD_PRELOAD` tricks) and also accidental conflicts.
- Objective-C classes are still global at runtime (registered by name in the ObjC runtime), which is why duplicate class names across images produce "Class X is implemented in both…" (Framework Distribution Q65).

### Q35. What is weak linking, and how does it relate to `#available`? `[Senior]`
- If you call an API introduced in iOS 18 while your deployment target is iOS 16, the symbol (or the whole framework) **doesn't exist** on iOS 16.
- The linker marks such symbols as **weak imports** automatically (based on availability annotations): dyld sets them to `NULL` if missing instead of refusing to launch.
- `if #available(iOS 18, *)` checks the OS version at runtime so you never call the missing symbol.
- For a whole framework that doesn't exist on older OS versions, link it **optional** (weak: `-weak_framework Foo`, "Optional" status in older Xcode), or dyld fails at launch with "Library not loaded".

```swift
if #available(iOS 18.0, *) {
    let mutex = Mutex(0)              // symbol from Synchronization: weak-imported when targeting iOS 17
    useMutex(mutex)
} else {
    useLegacyLock()
}
```
**Classic crash:** "dyld: Symbol not found: _OBJC_CLASS_$_SomeNewClass" on an older OS, usually from a precompiled library built against a newer SDK without availability checks, or a deployment-target mismatch (Q63).

### Q36. How do you tell compile-time, link-time and load-time errors apart? `[Fundamental]`
| Stage | Tool | Example errors | Typical cause |
|---|---|---|---|
| Compile | swift-frontend / clang | `Cannot find 'Foo' in scope`, `No such module 'Foo'` | Missing import, module not built/visible, wrong search paths |
| Link | `ld` | `Undefined symbols for architecture arm64`, `duplicate symbol`, `library not found for -lFoo`, `framework not found Foo` | Library not linked, missing slice, duplicate definitions, wrong library search paths |
| Load (launch) | dyld | `Library not loaded: @rpath/Foo.framework/Foo`, `Symbol not found` | Framework not embedded, wrong rpath, OS too old for a symbol |
| Runtime | ObjC/Swift runtime | `unrecognized selector`, `Could not cast value`, missing class from `NSClassFromString` | Category dropped at link time (`-ObjC`), duplicate classes, dynamic lookup |

### Q37. What are whole-module optimization and link-time optimization? `[Senior]`
| | Whole-Module Optimization (Swift) | Link-Time Optimization (LLVM, C/ObjC/C++) |
|---|---|---|
| Scope | Optimizes **all files of a Swift module** together | Optimizes across **object files** at link time |
| Enables | Cross-file inlining, generic specialization, dead-code elimination of internal code, devirtualizing `final`/internal classes | Cross-file inlining and dead code removal in C-family code |
| Setting | `SWIFT_COMPILATION_MODE = wholemodule` (Release default) | `LLVM_LTO = YES` (monolithic) or `YES_THIN` |
| Cost | Slower incremental builds (Debug uses incremental mode) | Slower links, more memory |

Cross-**module** optimization in Swift is limited by module boundaries (`@inlinable` exposes bodies; recent compilers do some cross-module optimization automatically for packages).

## 5. Static Linking

### Q38. What does the static linker do? `[Fundamental]`
1. **Collect inputs**: object files, static libraries (`.a` archives), dynamic library stubs (`.tbd` text files describing a dylib's exports, from the SDK), frameworks.
2. **Resolve symbols**: match every undefined reference to exactly one definition (or to a dynamic library that exports it).
3. **Lay out** sections into segments, assign final addresses.
4. **Apply relocations** inside the output (calls and references between your own object files become direct).
5. **Record fixups** for what can only be resolved at launch: pointers that need the ASLR slide (**rebases**) and references into dynamic libraries (**binds**).
6. **Write** the Mach-O with load commands, symbol tables, export info; strip dead code if enabled.

### Q39. How does the linker decide what to take from a static library? `[Senior]`
- A static library (`.a`) is an **archive of object files** with an index of the symbols they define.
- The linker pulls in an object file from the archive **only if it defines a symbol that is currently undefined**; the whole object file comes in, not just that one function.
- Unreferenced object files are never linked. That's the root of:
  - Objective-C **categories** silently missing → `unrecognized selector` (fix: `-ObjC`; Framework Distribution Q52).
  - Classes used only via `NSClassFromString` or registration patterns being dropped.
- Order: GNU `ld` (Linux) processes archives once in command-line order (order-sensitive); Apple's linkers revisit archives as needed, so order rarely breaks linking, though **which definition wins** among duplicates can depend on order.

```bash
ar -t libAnalytics.a                         # list member object files
nm -A libAnalytics.a | grep ' T ' | head     # which member defines which symbol
```

### Q40. What do `-ObjC`, `-all_load` and `-force_load` do at the linker level? `[Senior]`
| Flag | Loads from static archives |
|---|---|
| (none) | Only object files that resolve undefined symbols |
| `-ObjC` | Additionally, every object file that defines an Objective-C class or category |
| `-all_load` | Every object file from **every** archive |
| `-force_load <path>` | Every object file from **one** archive |

Trade-off: more flags → bigger binary and more chances of duplicate symbols. Prefer `-force_load` for the one library that needs it over `-all_load`. Details from the SDK side: Framework Distribution Q52.

### Q41. What is dead-code stripping, and what keeps code alive? `[Senior]`
- `-dead_strip` (`DEAD_CODE_STRIPPING = YES`, default for apps) removes functions and data **not reachable** from the entry point and exported symbols.
- Code is kept alive by: references from reachable code, **exported** symbols (dylibs export `public` API), Objective-C metadata (classes and categories are registered at runtime, so the linker conservatively keeps them), Swift metadata needed for runtime features (protocol conformance records, reflection), and `@_used` / `__attribute__((used))`.
- So dead stripping helps a lot for **static** libraries linked into an app, and little for **dynamic** frameworks (all public API is exported and kept).

### Q42. What causes "duplicate symbol" errors, and how are they resolved? `[Senior]`
```
duplicate symbol '_kReachabilityChangedNotification' in:
    /…/libVendorA.a(Reachability.o)
    /…/libVendorB.a(Reachability.o)
ld: 1 duplicate symbol for architecture arm64
```
Causes:
- Two static libraries contain the **same source** (vendored copies of a popular library).
- A global defined in a **header** (not `extern` + one definition) included in several files.
- `-all_load` pulling in object files that would otherwise be skipped.
- The same Swift module linked twice through different paths.

Fixes: depend on a **single** copy via Swift Package Manager; namespace vendored copies; `extern` declarations in headers with one definition in a `.c/.m` file; avoid `-all_load`.

**Weak definitions** are the exception: C++ inline functions/templates and some compiler-generated symbols are emitted as weak in many object files, and the linker keeps one silently.

### Q43. How do you find what makes your binary big? `[Senior]`
```bash
# 1. Generate a link map: Build Settings → Write Link Map File (LD_GENERATE_MAP_FILE = YES)
#    Output lists every object file and symbol with its size and section.

# 2. Section sizes of the final binary
size -m MyApp.app/MyApp

# 3. Biggest symbols
nm --size-sort -S MyApp.app/MyApp | tail -20 | swift demangle
```
- Typical big contributors: large static SDKs, generic specializations, Swift metadata, embedded resources compiled into code (base64 strings), duplicated libraries across app + extensions.
- Measure **App Store download/install size** with an App Thinning Size Report, not the `.app` folder size.

### Q44. What changed with the new linker in Xcode 15? `[Lead/Expert]`
- Xcode 15 shipped a **rewritten linker ("ld-prime")** that replaced `ld64` by default: heavily **parallelized**, much faster links for large apps (Apple reported multiple-times speedups), lower memory use.
- It also enabled **mergeable libraries** (Framework Distribution Q7).
- The classic linker remained available for compatibility (`-ld_classic`) while projects resolved differences, such as stricter handling of some edge cases.
- Interview point: link time is often the **bottleneck of incremental builds** in large modular apps; the new linker plus dynamic/mergeable libraries in Debug cut it significantly.

### Q45. What is autolinking? `[Senior]`
- When you `import UIKit` (Swift) or `@import UIKit;` (Objective-C modules), the compiler records a **linker option** in the object file (`LC_LINKER_OPTION`: `-framework UIKit`).
- The linker then links those frameworks automatically, so you don't have to list system frameworks in "Link Binary With Libraries".
- Caveats: autolinking only works for **modules** (not plain `#import` of headers without modules); static libraries consumed by others may need clients to link system frameworks explicitly if autolinking is disabled (`CLANG_MODULES_AUTOLINK = NO`).

```bash
otool -l MyFeature.o | grep -A3 LC_LINKER_OPTION
#   string #1 -framework
#   string #2 UIKit
```

## 6. Dynamic Linking & dyld

### Q46. What is dyld, and what does it do at launch? `[Fundamental]`
**dyld** (the dynamic linker/loader) runs in your process before `main`:

```
kernel: create process, map the app executable and dyld, jump to dyld
dyld:
  1. Load dependencies recursively (LC_LOAD_DYLIB), from the dyld shared cache or the app's Frameworks/
  2. Map each image's segments; code-signature checks as pages are touched
  3. Apply fixups: REBASE pointers by the ASLR slide, BIND references to other images' symbols
  4. Notify runtimes: Objective-C registers classes/categories/selectors; Swift registers metadata/conformances
  5. Run initializers: ObjC +load, C/C++ static constructors (__attribute__((constructor)))
  6. Call main() → UIApplicationMain / @main App
```
Everything before step 6 is **pre-main** launch time, which your code influences through the number of dynamic libraries, fixups, and initializers.

### Q47. What are install names, `@rpath`, `@executable_path` and `@loader_path`? `[Senior]`
- A dynamic library's **install name** (`LC_ID_DYLIB`) is the path stored in every binary that links it; dyld uses it to find the library at runtime.
- System libraries use absolute paths (`/usr/lib/libSystem.B.dylib`, `/System/Library/Frameworks/UIKit.framework/UIKit`).
- Embedded frameworks use **`@rpath/MySDK.framework/MySDK`**; `@rpath` is replaced by each entry of the loading binary's **runpath search paths** (`LC_RPATH`), tried in order.

| Token | Expands to |
|---|---|
| `@executable_path` | Directory of the main executable (`MyApp.app/`) |
| `@loader_path` | Directory of the binary **doing the loading** (useful for frameworks loading their own dependencies) |
| `@rpath` | Each path in the runpath list |

Typical settings:
```
App target:        LD_RUNPATH_SEARCH_PATHS = @executable_path/Frameworks
App extension:     LD_RUNPATH_SEARCH_PATHS = @executable_path/Frameworks @executable_path/../../Frameworks
Framework target:  DYLIB_INSTALL_NAME_BASE = @rpath
```
```bash
otool -L MyApp.app/MyApp | grep rpath           # which @rpath libraries it needs
otool -l MyApp.app/MyApp | grep -A2 LC_RPATH    # where it will look
install_name_tool -add_rpath @executable_path/Frameworks MyTool    # patch (macOS tools, before signing)
```

### Q48. What are rebasing and binding? `[Senior]`
- **Rebasing**: the binary was linked assuming it loads at a fixed address; with ASLR it loads at `address + slide`, so every **internal pointer** stored in data (vtables, ObjC metadata, pointers to strings) must have the slide added.
- **Binding**: pointers to symbols in **other images** (`_objc_msgSend` in libobjc, `$sSSN` in libswiftCore, your framework's functions) must be set to the actual address where that image was loaded.
- Both **write** to `__DATA`/`__DATA_CONST` pages, which makes those pages **dirty** (counted in memory) and costs launch time. More pointers and more dynamic images → more fixups.
- Historically, symbols could be bound **lazily** on first call through stubs; modern binaries (chained fixups) bind at launch in a single efficient pass (Q51).

### Q49. What is the dyld shared cache? `[Senior]`
- A single, huge, **prelinked** file containing almost all system libraries and frameworks (UIKit, Foundation, SwiftUI, libSystem, the Swift runtime…), built when the OS is installed.
- Advantages:
  - Fixups between system libraries are **already done**; Objective-C selectors are pre-uniqued; many lookup tables precomputed.
  - Mapped into **every process** at the same address (per boot), so its pages are **shared** in physical memory.
  - Launch time is dominated by **your** binaries, not system ones.
- Individual system dylibs don't exist as separate files on the device; the SDK contains `.tbd` stubs for linking.
- Your embedded frameworks are **not** in the shared cache, which is one reason each one costs launch time.

### Q50. What are launch closures (dyld 3 and dyld 4)? `[Lead/Expert]`
- **dyld 3** (iOS 13 for apps) moved much of the launch work **out of process**: dependency resolution, symbol lookups and fixup plans are computed once and cached as a **launch closure**, which is validated and replayed on later launches.
- **dyld 4** (iOS 15+) kept the idea of precomputed launch information while restructuring dyld (prebuilt "PrebuiltLoaders" plus just-in-time fallback when no valid cache exists).
- Effect: **warm launches** are faster than the first launch after install or update; measuring the first launch after install shows the worst case.

### Q51. What are chained fixups and page-in linking? `[Lead/Expert]`
- **Chained fixups** (`LC_DYLD_CHAINED_FIXUPS`): instead of separate tables for rebases, binds and lazy binds, each `__DATA` page stores a **linked chain** of its pointers that need fixing; dyld fixes a page in **one pass**.
  - Used when the deployment target is new enough (iOS 15+ with Xcode 13+).
  - Smaller binaries (less fixup metadata) and faster launches; binaries with chained fixups don't run on OS versions older than the format.
- **Page-in linking** (WWDC 2022 "Link fast"): on newer OS versions the kernel can apply fixups **lazily as each page is first touched**, so pages never used during a session are never dirtied.
- Also: `__DATA_CONST` pages are made **read-only** after fixups, which hardens against memory corruption.

### Q52. What runs before `main`, and how can it slow launch? `[Senior]`
| Initializer | When | Cost |
|---|---|---|
| Objective-C `+load` | Pre-main, for every class/category that implements it, every launch | Runs even if the class is never used; blocks launch |
| C/C++ static constructors, `__attribute__((constructor))` | Pre-main | Same |
| Objective-C `+initialize` | **Lazily**, on the first message to the class | Not pre-main |
| Swift global and `static` variables | **Lazily**, on first access (thread-safe, `swift_once`) | Not pre-main (except top-level code in `main.swift`) |

```bash
# Find static initializers in your binary
otool -l MyApp | grep -A3 __mod_init_func      # C/C++ constructors
nm -m MyApp | grep '+\[.* load\]'              # ObjC +load methods
```
Guideline: no `+load` (move work to explicit setup or `+initialize`), no heavy C++ globals, and audit third-party SDKs for both.

### Q53. How do the Objective-C and Swift runtimes interact with dyld? `[Lead/Expert]`
- dyld notifies **libobjc** when images are mapped; the ObjC runtime registers classes, categories (attaching methods to classes), protocols and selectors. For shared-cache images this is mostly precomputed; for your images it's done at launch.
- The **Swift runtime** looks up type metadata and **protocol conformances** lazily (e.g. for `as?` casts to protocol types, `String(describing:)`, generic dynamic casts). Conformance lookups scan conformance records of all loaded images; recent OS versions **cache** these results (dyld prebuilds conformance tables for the shared cache and caches app results), but heavy dynamic casting at launch can still show up in profiles.
- Practical tips: fewer ObjC classes/categories in hot launch paths, avoid unnecessary `as? SomeProtocol` casts at startup, fewer dynamic images.

### Q54. Can an iOS app use `dlopen`? `[Senior]`
- `dlopen`/`dlsym` (and `Bundle.load()`) work for libraries **inside your signed app bundle** (and system libraries), e.g. loading an optional embedded framework only when a feature is used.
- **Not allowed**: loading code that wasn't shipped and signed with the app (downloaded plugins). Code signing enforcement prevents it, and App Review guidelines forbid downloading executable code.
- Use cases are rare on iOS: lazily loading a large embedded framework to shorten launch, or optional integrations. Mergeable libraries and static linking usually give better results.

```swift
// Load an embedded framework only when needed (it must still be embedded and signed)
if let bundle = Bundle(path: Bundle.main.privateFrameworksPath! + "/HeavyFeature.framework"),
   bundle.load(),
   let type = bundle.principalClass as? NSObject.Type {
    _ = type.init()
}
```

### Q55. What is symbol interposition, and can apps use it? `[Lead/Expert]`
- **Interposing** replaces a function in another library with your own version (e.g. wrapping `malloc` or `open`) via `DYLD_INSERT_LIBRARIES` or the `__interpose` section.
- On macOS it's used by debugging tools (for non-hardened binaries); on iOS, `DYLD_*` environment variables are ignored for App Store apps and the two-level namespace limits interposition to explicitly marked cases.
- Related app-level techniques: **method swizzling** (ObjC runtime, works only for ObjC-dispatched methods) and `@_dynamicReplacement` (Swift, needs `-enable-implicit-dynamic`, used by tools like SwiftUI previews/hot reload). Neither is something to rely on in production SDKs (Framework Distribution Q38).

### Q56. Static or dynamic linking: how do you decide? `[Senior]`
| Criterion | Static | Dynamic |
|---|---|---|
| Launch time | ✅ No extra images | ❌ Each framework: load, fixups, signature checks |
| Binary size | ✅ Dead-code stripping | ❌ Whole framework shipped |
| Memory | ✅ Fewer dirty `__DATA` pages | ❌ Each image adds dirty pages |
| Sharing code between app and extensions | ❌ Duplicated per binary | ✅ One copy |
| Build/link time in Debug | ❌ Relink everything | ✅ Faster incremental links |
| Resources | Need a separate bundle | Inside the framework |
| Duplicate-class risk | Higher if linked into several images | Lower |

**Answer to give:** "Static by default for app modules and SDK code; dynamic (or **mergeable**) when sharing a large module with extensions or to speed up Debug builds. Mergeable libraries give dynamic linking in Debug and static-like launch performance in Release." More: Framework Distribution Q2, Q7, Q8.

## 7. App Launch, End to End

### Q57. Walk through a cold launch from tap to first frame. `[Senior]`
```
User taps icon
  │ SpringBoard asks the system (RunningBoard/launchd) to launch the app
  ▼
Kernel: create process, set up address space (ASLR), map executable + dyld, start main thread
  ▼
dyld (pre-main):
  load dependencies (shared cache + embedded frameworks) → fixups → ObjC/Swift runtime setup
  → static initializers (+load, C++ constructors)
  ▼
main() → UIApplicationMain / @main App
  ▼
UIKit/SwiftUI setup: app delegate init, application(_:didFinishLaunchingWithOptions:),
scene connection (scene(_:willConnectTo:) / WindowGroup), root view created
  ▼
First layout + render: first Core Animation commit → first frame on screen
  ▼
(Extended launch) app loads real content: cached data shown, network refresh in background
```
- Apple's guidance: aim for the **first frame within ~400 ms** (the launch animation hides about that long). The watchdog kills launches that take far longer (`0x8badf00d`, Threads & Processes Q13).
- **Pre-main** is mostly about your binary structure (dynamic frameworks, fixups, initializers); **post-main** is about your code.

### Q58. What are cold, warm and resume launches? `[Fundamental]`
| Type | Situation | What's already in memory |
|---|---|---|
| **Cold** | After reboot, or after the app's pages were evicted | Nothing for your app: binaries read from storage |
| **Warm** | App was terminated recently; its pages are still in the file cache | Binary pages cached; dyld launch info cached; the process is new |
| **Resume** | App was suspended | The whole process: no launch at all, just `sceneWillEnterForeground` |
| **Prewarmed** | iOS 15+ ran the early launch stages ahead of time (Threads & Processes Q17) | Process partially launched before the tap |

Measure **cold and warm** separately; the first launch after install or update is the slowest (no cached launch closure).

### Q59. How do you measure launch time? `[Senior]`
| Tool | Measures |
|---|---|
| Instruments **App Launch** template | Phases (process creation, dyld, static initializers, UIKit init, initial frame), with Time Profiler samples |
| Xcode Organizer **Launch Time** | Field data: launch time percentiles per app version and device |
| **MetricKit** `MXAppLaunchMetric` | Time to first draw histogram, resume time, from real users |
| XCTest `XCTApplicationLaunchMetric` | Launch performance tests in CI with baselines |
| `os_signpost` intervals | Your own milestones (e.g. "home screen data shown") on the Instruments timeline |

```swift
import XCTest

final class LaunchPerformanceTests: XCTestCase {
    func testLaunchTime() throws {
        measure(metrics: [XCTApplicationLaunchMetric()]) {
            XCUIApplication().launch()
        }
    }
}
```
Measure on **real, older devices**, in **Release** configuration; simulator numbers are meaningless for launch.

### Q60. How do you reduce pre-main time? `[Senior]`
1. **Fewer dynamic frameworks**: link static, or use **mergeable libraries** (Q56). Each embedded framework costs loading, fixups and signature checks.
2. **Remove initializers**: no Objective-C `+load`, no heavy C++ globals or `__attribute__((constructor))`; audit third-party SDKs (Q52).
3. **Fewer fixups**: fewer Objective-C classes/selectors and C++ vtables; chained fixups (modern deployment target) (Q51).
4. **Smaller binary / fewer page faults**: dead stripping, order files, removing unused code and SDKs (Q21).
5. **Avoid unused framework links** (`otool -L` shows everything dyld must load).

### Q61. How do you reduce post-main launch time? `[Senior]`
- **Do less in `didFinishLaunching` / `App.init`**: defer SDK setup, analytics, migrations and remote config until after the first frame (`Task(priority: .utility)` or after the first `onAppear`).
- **No synchronous I/O or networking** on the main thread; no Keychain reads you can postpone.
- **Lazy initialization** of services (create on first use).
- **Show cached content immediately**, refresh in the background.
- **Simple first screen**: avoid building hidden tabs and heavy view hierarchies up front.
- **Measure each step** with signposts; set a launch budget in CI (XCTest launch metric).

```swift
@main
struct MyApp: App {
    @State private var services = AppServices()        // cheap: only stores configuration

    var body: some Scene {
        WindowGroup {
            RootView()
                .environment(services)
                .task(priority: .utility) {
                    await services.startDeferredWork()  // analytics, remote config, prefetch: after first frame
                }
        }
    }
}
```

## 8. Debugging Linker & Loader Errors

### Q62. How do you debug "Undefined symbols for architecture arm64"? `[Senior]`
```
Undefined symbols for architecture arm64:
  "_$s9Analytics6ClientC5trackyySSF", referenced from:
      _$s5MyApp15CheckoutViewC4buyyyF in CheckoutView.o
ld: symbol(s) not found for architecture arm64
```
1. **Demangle** the symbol to see what's missing: `swift demangle '$s9Analytics6ClientC5trackyySSF'` → `Analytics.Client.track(Swift.String) -> ()`.
2. **Is the library linked into this target?** (Package product added to the target? Framework in "Link Binary With Libraries"?) Test targets and extensions need their own links.
3. **Does the library define it for this platform/architecture?**
   ```bash
   lipo -info libAnalytics.a                       # architectures
   xcrun vtool -show-build libAnalytics.a | head   # platform: iOS vs iOS Simulator
   nm -gU libAnalytics.a | swift demangle | grep 'Client.track'
   ```
4. **Signature mismatch**: the header/interface you compiled against differs from the binary you link (stale build products, two versions of the SDK). Clean build folder, check search paths.
5. **Missing system libraries** for C/C++ code: `-lc++`, `-lz`, `-lsqlite3`, or frameworks when autolinking is off (Q45).
6. Symbols with `_OBJC_CLASS_$_` → Objective-C class not linked, or only available in a newer SDK.

### Q63. The app crashes at launch on older iOS versions with "Symbol not found". Why? `[Senior]`
```
dyld[512]: Symbol not found: _$s7SwiftUI4ViewPAAE15scrollPositionyQrAA14ScrollPositionVzF
  Referenced from: /…/MyApp.app/MyApp
  Expected in: /System/Library/Frameworks/SwiftUI.framework/SwiftUI
```
- The binary references a symbol that exists in the **newer OS** only, and it wasn't weak-linked or guarded:
  - A **prebuilt** binary dependency built with a higher deployment target than your app.
  - Objective-C code calling a new API without `@available` (only a **warning** in ObjC: `-Wunguarded-availability-new`; turn it into an error).
  - A framework you link that doesn't exist on that OS, not marked optional.
- Diagnose: `xcrun vtool -show-build` (each binary's minimum OS), `dyld_info -imports` / `nm -m` for the symbol, test on the **oldest supported OS** in CI.
- Swift itself enforces availability at compile time, so pure Swift app code rarely causes this.

### Q64. "library not found for -lFoo" or "framework not found Foo". What do you check? `[Fundamental]`
- The linker searched `LIBRARY_SEARCH_PATHS` / `FRAMEWORK_SEARCH_PATHS` and didn't find it:
  - Path is wrong for this **configuration or platform** (e.g. points to `Debug-iphoneos` while building for the simulator).
  - A stale reference to a library you removed (check "Other Linker Flags" for leftover `-lFoo` / `-framework Foo`).
  - The dependency target wasn't built first (missing target dependency, or an implicit dependency that Xcode didn't detect).
  - A Swift package product wasn't added to **this** target.
- Run the build with the full log (Report navigator) to see the exact linker command and search paths.

### Q65. What does "Could not find or use auto-linked library 'swiftCore'" mean? `[Senior]`
- An **Objective-C-only** target (often the app target or a test target) links a static library or object files that contain **Swift** code. Those object files autolink the Swift runtime libraries (`swiftCore`, `swiftFoundation`…), but the linking target has no Swift sources, so Xcode didn't add the Swift library search paths.
- Fixes:
  - Add an (even empty) **Swift file** to the target so Xcode configures Swift linking.
  - Or add the Swift library search path manually: `$(TOOLCHAIN_DIR)/usr/lib/swift/$(PLATFORM_NAME)` and `$(SDKROOT)/usr/lib/swift`.
- Similar warnings for other autolinked libraries mean the library isn't in any search path (Q45).

### Q66. How do you symbolicate a crash address manually? `[Senior]`
```
Binary Images:
0x100a28000 - 0x100d9ffff MyApp arm64  <3f1c9d2e8a7b4c51a2e0f6d8b9c4e1a7> /…/MyApp.app/MyApp

Thread 0 Crashed:
0   MyApp    0x0000000100a4c3a8 0x100a28000 + 148392
```
1. Find the matching **dSYM** by UUID:
   ```bash
   dwarfdump --uuid MyApp.app.dSYM          # must match <3f1c9d2e…> from the crash report
   mdfind "com_apple_xcode_dsym_uuids == 3F1C9D2E-8A7B-4C51-A2E0-F6D8B9C4E1A7"
   ```
2. Convert the address using the **load address** (ASLR slide):
   ```bash
   atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp -l 0x100a28000 0x0000000100a4c3a8
   # → CheckoutViewModel.submit() (in MyApp) (CheckoutViewModel.swift:87)
   ```
- Xcode Organizer and crash services do this automatically when they have the dSYMs: always **archive and upload dSYMs** for every build you ship (and get them from binary SDK vendors, Framework Distribution Q12).

### Q67. What can the faulting address tell you in an `EXC_BAD_ACCESS` crash? `[Lead/Expert]`
| Exception detail | Likely meaning |
|---|---|
| `KERN_INVALID_ADDRESS at 0x0000000000000000`–`0x…0FFF` | **Null dereference**, or a field read through a null pointer (small offset) |
| `KERN_INVALID_ADDRESS` at a random-looking address | **Use-after-free** / dangling pointer / data race corrupting a pointer |
| `KERN_PROTECTION_FAILURE` | Valid address, wrong permission: writing to read-only memory (`__TEXT`, `__DATA_CONST`, a string literal) or executing non-executable memory |
| Address with unusual high bits, "possible pointer authentication failure" | **PAC failure** on arm64e: corrupted or forged pointer (memory corruption) |
| `EXC_BAD_ACCESS` in `objc_msgSend` / `objc_release` / `swift_release` | Messaging or releasing an **already-freed object** (over-release, `unowned` reference to a dead object, race) |
| Stack address near the thread's stack limit, very deep stack | **Stack overflow** (infinite recursion) |

Tools: Address Sanitizer and Zombies (Debug) for use-after-free; Thread Sanitizer for races; malloc guard/scribble options in the scheme's Diagnostics.

## 9. "Spot the Problem" Questions

### Q68. What's wrong with this Objective-C setup code? `[Senior]`
```objc
@implementation AnalyticsBootstrap
+ (void)load {
    [[AnalyticsSDK shared] configureWithKey:@"key"];      // reads config file, opens database, starts network
    [[NSNotificationCenter defaultCenter] addObserver:self selector:@selector(appDidLaunch:)
        name:UIApplicationDidFinishLaunchingNotification object:nil];
}
@end
```
**Problems:**
1. `+load` runs **pre-main on every launch**, before UIKit exists, blocking launch (and the watchdog clock is running) (Q52).
2. File and database I/O and network setup before `main` slow every launch, including background launches and prewarming.
3. Order of `+load` across classes isn't something to depend on; other frameworks may not be ready.

**Fix:** explicit setup in `application(_:didFinishLaunchingWithOptions:)`, deferring heavy work until after the first frame (Q61); if an automatic hook is needed, `+initialize` (lazy) is a better choice.

### Q69. What's wrong with this thumbnail code? `[Senior]`
```swift
func thumbnail(for url: URL) -> UIImage? {
    guard let image = UIImage(contentsOfFile: url.path) else { return nil }   // 12 MP photo
    return image.preparingThumbnail(of: CGSize(width: 120, height: 120))
}
```
**Problem:** the full image is **decoded** first: a 4032×3024 photo is about **48 MB of dirty memory** (4 bytes per pixel) just to produce a 120-point thumbnail. Showing a grid of these can push the app over its **jetsam** limit (Q11–Q12).

**Fix:** downsample with ImageIO without decoding the full image:
```swift
import ImageIO
import UIKit

func downsampledImage(at url: URL, maxPixelSize: CGFloat) -> UIImage? {
    let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary         // don't decode yet
    guard let source = CGImageSourceCreateWithURL(url as CFURL, sourceOptions) else { return nil }
    let thumbnailOptions = [
        kCGImageSourceCreateThumbnailFromImageAlways: true,
        kCGImageSourceShouldCacheImmediately: true,                                 // decode now, at small size
        kCGImageSourceCreateThumbnailWithTransform: true,                           // respect EXIF orientation
        kCGImageSourceThumbnailMaxPixelSize: maxPixelSize                           // points × screen scale
    ] as CFDictionary
    guard let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, thumbnailOptions) else { return nil }
    return UIImage(cgImage: cgImage)
}
```

### Q70. What's wrong with where this app stores data? `[Fundamental]`
```swift
let url = FileManager.default.urls(for: .cachesDirectory, in: .userDomainMask)[0]
    .appending(path: "drafts.json")
try JSONEncoder().encode(drafts).write(to: url)
```
**Problems:**
1. **Caches can be purged** by the system when storage is low: users lose drafts.
2. Not written atomically: a crash or kill mid-write leaves a corrupt file.

**Fix:** store user data in **Application Support** (or Documents if users should see it), write with `.atomic`, and choose file protection deliberately (Q22–Q24).

### Q71. What's wrong with saving file paths like this? `[Senior]`
```swift
// Saved in the database when the user attaches a photo
attachment.path = fileURL.path      // "/var/mobile/Containers/Data/Application/6F1A…/Documents/photo1.jpg"
```
**Problem:** the app's **container path (UUID) can change** across updates, restores and reinstalls. Stored absolute paths then point nowhere, and attachments "disappear".

**Fix:** store a path **relative** to a known directory (`"photo1.jpg"` relative to Documents/Application Support) and rebuild the URL at runtime; or use bookmarks for user-picked files outside the container.

### Q72. Why does this app extension crash at launch with "Library not loaded"? `[Senior]`
```
Share extension target:
  Frameworks: SharedKit.framework  (dynamic, embedded in the main app only)
  LD_RUNPATH_SEARCH_PATHS = @executable_path/Frameworks
```
**Problem:** the extension lives at `MyApp.app/PlugIns/Share.appex/`. `@executable_path/Frameworks` points to `Share.appex/Frameworks/`, which doesn't contain `SharedKit`. The framework is in `MyApp.app/Frameworks/`.

**Fix:** add `@executable_path/../../Frameworks` to the extension's runpath search paths (Q47). Don't embed a second copy inside the extension (nested bundles are rejected by App Store validation, Framework Distribution Q66).

### Q73. Why does this push handler sometimes log the user out? `[Lead/Expert]`
```swift
// Called when a silent push launches the app in the background
func refreshFromPush() async {
    guard let token = Keychain.read("authToken") else {      // item saved with kSecAttrAccessibleWhenUnlocked
        await session.logOut()                                // "no token" → log out
        return
    }
    await sync(using: token)
}
```
**Problem:** the push can launch the app **while the device is locked**. A Keychain item with `WhenUnlocked` accessibility (or a file with `.complete` protection) **can't be read** then, so `read` fails with `errSecInteractionNotAllowed`, and the code treats "temporarily unavailable" as "missing" (Q24).

**Fix:** store tokens needed in the background with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; distinguish "not found" from "not accessible right now" errors; never log out on a read failure in a background launch; retry when `protectedDataDidBecomeAvailable` fires.

### Q74. What's wrong with loading this file? `[Senior]`
```swift
let data = try Data(contentsOf: offlineMapURL)        // 1.8 GB offline map package
let tile = parseTile(data, at: offset)
```
**Problem:** reads the **entire file into the heap**: 1.8 GB of dirty memory → immediate jetsam.

**Fix:** memory-map it (`Data(contentsOf:options: .alwaysMapped)`) so only touched pages are loaded and they stay clean and reclaimable (Q17), or read just the needed range with `FileHandle` (`seek` + `read(upToCount:)`), or store tiles in SQLite.

### Q75. What's wrong with this Objective-C call? `[Senior]`
```objc
// Deployment target: iOS 16
- (void)configureMenu {
    UIButton *button = [UIButton buttonWithType:UIButtonTypeSystem];
    button.someIOS18OnlyProperty = YES;      // property introduced in iOS 18
}
```
**Problem:** Objective-C only **warns** about unguarded availability. On iOS 16/17 this sends a message to a method that doesn't exist → `unrecognized selector` crash (or, for a new class/C function, a weak-linked `nil`/`NULL` used without a check, or "Symbol not found" at launch if not weak-linked).

**Fix:** guard with `if (@available(iOS 18.0, *)) { … }`, and turn `-Wunguarded-availability-new` into an **error** (`GCC_TREAT_WARNINGS_AS_ERRORS` or a targeted `-Werror=unguarded-availability-new`). Swift enforces this at compile time.

## 10. Senior / Lead Scenario Questions

### Q76. Launch time regressed by 300 ms after adding several SDKs. How do you investigate and fix it? `[Senior]`
1. **Measure** with the App Launch instrument on an older device, Release build, cold and warm; compare against the previous version.
2. **Pre-main**: `otool -L` for new dynamic frameworks; look for `+load` methods and static initializers in the SDKs (Q52); count fixups (`dyld_info -fixups | wc -l`).
3. **Post-main**: Time Profiler on the main thread during `didFinishLaunching`: synchronous `configure` calls, file/Keychain reads, network.
4. **Fix**: switch SDKs to static or mergeable linking, defer SDK initialization until after the first frame or first use, remove SDKs that aren't worth their cost, ask vendors for lazy initialization.
5. **Prevent**: launch performance test in CI with a budget (Q59), an SDK review checklist (size, launch cost, privacy manifest).

### Q77. MetricKit shows many memory-limit terminations in the foreground. What's your plan? `[Lead/Expert]`
1. **Find where**: MetricKit/Organizer by app version, device class (low-RAM devices first), and screen; add breadcrumbs with `os_proc_available_memory()` at key screens.
2. **Reproduce** on a low-memory device; record with Allocations + VM Tracker; export memgraphs (`footprint`, `vmmap`) at peaks (Q19).
3. **Common culprits**: full-size image decoding (Q69), unbounded caches, leaks in navigation flows (repeat a flow and check generations), large data loaded at once (Q74), many `WKWebView`s.
4. **Fix and guard**: downsampling, `NSCache` with cost limits, purge on memory warnings (Q13), streaming/mmap.
5. **Track**: memory-limit exits per 1,000 sessions as a release-health metric with an alert.

### Q78. A crash happens only on iOS 16 devices, at launch, with "Symbol not found". How do you approach it? `[Senior]`
- Read the message: **which symbol**, **referenced from** which binary (yours or an SDK), **expected in** which framework (Q63).
- If the referencing binary is a third-party SDK: check its minimum OS (`vtool -show-build`); it was probably built for a higher deployment target than it claims. Upgrade/downgrade or contact the vendor.
- If it's your Objective-C/C code: find unguarded new API usage; enforce availability warnings as errors.
- Add the **oldest supported OS** to CI device/simulator runs so this is caught before release.

### Q79. Your modular app has 80 dynamic frameworks. What would you change? `[Lead/Expert]`
- Measure first: pre-main time, number of images loaded (`DYLD_PRINT_LIBRARIES` on macOS/simulator, App Launch instrument), dirty `__DATA` from fixups.
- Options:
  - **Mergeable libraries**: keep dynamic frameworks in Debug (fast incremental links), merge them into the app in Release (static-like launch).
  - **Static linking** for most modules; keep dynamic only for code shared with extensions, if it's large.
  - Move resources into asset catalogs/bundles that don't require separate frameworks.
- Watch for side effects: duplicated static code across app and extensions (Framework Distribution Q53), `Bundle(for:)` resource lookups changing when frameworks become static (Framework Distribution Q5), and duplicate class warnings.
- Re-measure launch, size and build times; communicate trade-offs to the team.

### Q80. A security review asks how your app protects user data at rest and in memory. What do you cover? `[Lead/Expert]`
- **At rest**: Data Protection classes per file type (Q24), Keychain accessibility for each secret, `…ThisDeviceOnly` for device-bound tokens, no secrets in `UserDefaults` or the binary (Q29), excluded-from-backup decisions, cache contents (no sensitive responses in `URLCache`; set `.notAllowed` or a custom cache policy).
- **In transit**: TLS (App Transport Security), optional certificate pinning with a rotation plan.
- **In memory**: minimize the time secrets stay in memory; avoid logging them; screenshots/app switcher snapshots hide sensitive screens; clear the pasteboard for copied secrets (or use local-only, expiring pasteboard items).
- **Platform protections**: sandbox, code signing, Secure Enclave keys for high-value credentials, biometric gating (`LAContext`, Keychain access control flags), App Attest for server-side integrity, and **Enhanced Security** (pointer authentication, memory tagging) if the app's threat model justifies it (Q28).
- **Process**: dependency audits, privacy manifests, penetration testing, and incident response.

## 11. Last-Day Cheat Sheet

### OS in one table
| Concept | Remember |
|---|---|
| Kernel vs user space | Apps run unprivileged; system calls/Mach messages cross into XNU |
| XNU | Hybrid: Mach (tasks, threads, VM, IPC) + BSD (POSIX, files, network) + IOKit (drivers) |
| launchd | PID 1; starts daemons and apps on demand |
| Exceptions | Mach exception + BSD signal: `EXC_BAD_ACCESS (SIGSEGV)`, `EXC_BREAKPOINT (SIGTRAP)`, `EXC_CRASH (SIGABRT)` |

### Memory
- Virtual memory, **16 KB pages**, ASLR, W^X.
- **No swap on iPhone**: clean pages dropped, dirty pages **compressed**, then **jetsam**.
- **Footprint = dirty + compressed**; decoded images are the usual giant (width × height × 4 bytes).
- `os_proc_available_memory()`, memory warnings, `NSCache`, downsampling, mmap for big read-only files.
- Stack: per thread (1 MB main / 512 KB others); heap: shared, ARC-managed for classes.

### Storage & security
| | Remember |
|---|---|
| Documents / Application Support | User data; backed up |
| Caches / tmp | Purgeable; not backed up |
| Data Protection | `.complete` (unlocked only) … default `completeUntilFirstUserAuthentication` |
| Keychain | Accessibility class matters for background launches |
| Code signing + entitlements + sandbox | Only approved code, capabilities and resources |
| Enhanced Security (Xcode 26) | arm64e pointer authentication, typed allocators, memory tagging (A19/M5+) |

### Build pipeline
```
.swift/.m → compiler → .o (sections, symbols, relocations)
       → ld: resolve symbols, layout, relocations, record fixups → Mach-O
       → resources, embed frameworks, dSYM, codesign → .app
```
- Compile error = frontend; **link** error = `ld` (undefined/duplicate symbols, library not found); **load** error = dyld (library not loaded, symbol not found).

### Static linking
- Archives: only object files that resolve undefined symbols are linked → categories dropped → `-ObjC` / `-force_load`.
- Dead stripping removes unreachable code (great for static, little effect on dynamic public API).
- Duplicate symbols: same code in two archives, globals defined in headers, `-all_load`.
- Xcode 15+ linker (ld-prime) is much faster; mergeable libraries.

### Dynamic linking (dyld)
- Steps: load dependencies → rebase (ASLR slide) + bind (other images) → runtime registration → initializers → `main`.
- `@rpath` + `LD_RUNPATH_SEARCH_PATHS`: app `@executable_path/Frameworks`; extension adds `@executable_path/../../Frameworks`.
- Shared cache: system frameworks prelinked and shared by all processes.
- Chained fixups (iOS 15+ targets), launch closures, page-in linking → faster launches.
- Weak linking + `#available` for newer APIs; "Symbol not found" = OS too old for a referenced symbol.
- Initializers: `+load` and C++ constructors are pre-main (avoid); Swift globals and `+initialize` are lazy.

### Launch
- Cold vs warm vs resume vs prewarmed; aim for first frame ≲ 400 ms; watchdog `0x8badf00d`.
- Pre-main: fewer dynamic frameworks, no initializers, fewer fixups.
- Post-main: defer SDKs, no sync I/O on main, cached first screen, measure with App Launch + MetricKit + XCTest launch metric.

### Tool → question it answers
| Tool | Question |
|---|---|
| `otool -L` / `otool -l` | Which libraries and rpaths does this binary use? |
| `nm -gU` + `swift demangle` | Which symbols does it export? |
| `lipo -info`, `vtool -show-build` | Which architectures/platform/minimum OS? |
| `dyld_info -fixups` | How much work will dyld do? |
| `size -m`, link map | What makes the binary big? |
| `atos`, `dwarfdump --uuid` | Which line crashed? Does this dSYM match? |
| `footprint`, `vmmap`, `leaks` | Where did the memory go? |
| `codesign -d --entitlements :-` | What is this app allowed to do? |

### Phrases that show seniority
- "On iOS the constraint is dirty memory, not virtual memory: there's no swap, only compression and then jetsam."
- "Compile, link and load errors come from different tools; I start by identifying which one failed."
- "Static by default, dynamic only when sharing with extensions, mergeable to get both."
- "Nothing should run before `main` that doesn't have to."
- "Data needed in background launches must use a protection class that's readable while locked."
