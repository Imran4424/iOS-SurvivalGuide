## 1. The Mobile System Design Interview

### Q1. What is a mobile system design interview, and how does it differ from a backend one? `[Fundamental]`
**Key points:**
- You design a feature or app **end to end**, focusing on the **client**: architecture, data flow, networking, caching, offline behavior, performance, and the API contract with the backend.
- Backend interviews focus on servers, databases, sharding, and load balancing. Mobile interviews focus on **constraints unique to devices**:
  - Unreliable, slow, or expensive networks.
  - Limited battery, memory, storage, and CPU.
  - App lifecycle (suspension, termination) and OS background limits.
  - Slow release cycles (App Store review) and **old app versions in the wild**.
  - Privacy, permissions, and platform guidelines.
- You're still expected to sketch the backend at a high level and to design the API the app needs.

| Topic | Backend interview emphasis | Mobile interview emphasis |
|---|---|---|
| Scale | QPS, sharding, replication | Request volume per device, thundering herds, CDN use |
| Storage | DB choice, partitioning | Local DB, cache budgets, migrations, eviction |
| Failure | Node failures, failover | Offline, flaky network, app killed mid-operation |
| Deploys | Continuous, instant rollback | App Review, phased release, old versions, kill switches |
| Latency | p99 server time | Time to first content, perceived performance |

### Q2. How should you structure your answer? `[Fundamental]`
A reliable framework is **RADIO**: Requirements, Architecture, Data model, Interface, Optimizations.

| Step | Time (of ~45 min) | What you do |
|---|---|---|
| 1. **Requirements** | 5–8 min | Clarify functional and non-functional requirements, scope, and scale |
| 2. **High-level architecture** | 8–10 min | Draw client components and how they talk to the backend |
| 3. **Data model** | 5 min | Key entities, local storage schema, caching |
| 4. **API / interface** | 5–8 min | Endpoints, real-time channels, payloads, pagination |
| 5. **Deep dives & optimizations** | 15 min | Offline, sync, performance, security, edge cases, trade-offs |
| 6. **Wrap-up** | 2–3 min | Summarize, mention monitoring, testing, and what you'd do next |

Let the interviewer steer deep dives, but offer topics: "I could go deeper into offline sync or into image loading. Which is more interesting to you?"

**Sample opening (say this almost word for word):**
> "Before drawing anything, I'd like to spend about five minutes on requirements: which features are in scope, roughly how many users, whether it must work offline, and how fresh the data must be. Then I'll sketch the client architecture, define the API and local data model, and use the remaining time for the deep dives you care about most."

**Sample wrap-up:**
> "To summarize: the local database is the source of truth, the UI observes it, a sync engine with an outbox handles writes, and WebSockets plus push keep it fresh. The riskiest parts are conflict handling and media upload reliability. I'd ship v1 behind a feature flag, watch crash-free rate, sync failures and time to first content, and add CRDT-based editing only if collaboration becomes a requirement."

### Q3. What clarifying questions should you ask? `[Fundamental]`
- **Scope**: which features are in scope? ("For chat: 1:1 only or groups? Media? Voice/video?")
- **Users and scale**: DAU? Global? Data volume per user?
- **Platforms**: iPhone only, iPad, Mac, watchOS? Minimum iOS version?
- **Offline**: must it work offline? Read-only or read-write?
- **Real-time**: how fresh must data be (seconds, minutes)?
- **Constraints**: low-end devices, emerging markets (data costs), accessibility, localization?
- **Security/compliance**: payments, health data, end-to-end encryption?
- **Existing systems**: is there a backend already, or do we design the API too?

Write the answers on the whiteboard as a short list and refer back to it when justifying decisions:

```
Scope:  1:1 + groups (≤256), text + images, receipts, typing      OUT: calls, E2EE details
Scale:  50M DAU, global, ~40 msgs/user/day
Offline: read history + queue sends                Freshness: < 1 s when both online
Devices: iPhone + iPad, iOS 17+                    Must: no lost / duplicated messages
```

### Q4. What do interviewers evaluate at Senior vs Lead level? `[Senior]`
| Senior | Lead / Staff |
|---|---|
| Solid client architecture with clear components | Same, plus cross-team and cross-platform implications |
| Correct handling of networking, caching, offline, lifecycle | Explicit trade-offs with business impact |
| Good API design for the app's needs | Influences backend/API contracts, versioning strategy |
| Performance and memory awareness | Observability, rollout, experimentation, migration strategy |
| Identifies edge cases | Prioritizes and phases delivery (MVP → v2), risk management |
| Communicates clearly | Drives the conversation, aligns stakeholders, mentors through the design |

```
│  UI Layer:        Screens (SwiftUI/UIKit) ─▶ ViewModels ─▶ Router        │
│                          │                                               │

└──────────────────────────────────┬───────────────────────────────────────┘
```

- Name components after their **responsibilities**, and show the **direction of data flow** (UI reads from the local store; network writes into it).
- Draw arrows for **reads** and **writes** separately when offline matters. Interviewers notice when the UI never talks to the network directly.

### Q6. How deep should you go into the backend? `[Senior]`
- Enough to make the client design coherent: endpoints, real-time mechanism, CDN for media, push service, major data flows.
- Don't spend 20 minutes on sharding unless asked: "On the backend I'd assume a feed service with fan-out and a CDN for media; I'll focus on the client unless you'd like me to go deeper."
- Lead candidates should discuss **API contracts**, BFFs, and how backend choices affect the client (pagination style, consistency guarantees, payload size).

### Q7. How do you communicate trade-offs well? `[Senior]`
Use a fixed sentence shape: **options → criteria → choice → cost → mitigation**.

> "For real-time updates we could poll, use SSE, or WebSockets (options). We need bidirectional, sub-second messaging (criteria), so I'd use WebSockets in the foreground and APNs in the background (choice). The cost is connection management and battery (cost); I'd disconnect when backgrounded and gap-fill with delta sync on reconnect (mitigation)."

Tie each decision to a requirement you wrote down earlier, and say how you'd **measure** whether it was right.

### Q8. Which mobile-specific constraints should you always mention? `[Fundamental]`
- **Network**: offline, flaky, high latency, metered/Low Data Mode, captive portals.
- **Lifecycle**: the app can be suspended or killed at any time; background execution is limited and not guaranteed.
- **Resources**: battery, memory (jetsam terminations), storage, CPU/thermal limits on older devices.
- **Distribution**: App Review delays; users on old versions for months; no instant hotfix.
- **Platform**: permissions, privacy rules, background modes.
- **UX**: perceived performance, accessibility, localization, many screen sizes.

Memory hook: **"NLRDPU"** — Network, Lifecycle, Resources, Distribution, Platform, UX.

## 2. Requirements & Estimation

### Q9. How do you separate functional and non-functional requirements? `[Fundamental]`
**Example: a photo-sharing feed.**
- **Functional**: view a feed; like and comment; pull to refresh; infinite scroll; post a photo with a caption; view a profile.
- **Non-functional**: time to first content < 1 s on warm start; smooth 60/120 fps scrolling; usable offline (cached feed, queued likes); data-efficient on cellular; secure auth; accessible and localized; crash-free sessions > 99.8%.
- **Out of scope** (say it explicitly): stories, direct messages, video editing, ads.

Make non-functional requirements **measurable**. "Fast" is not a requirement; "p90 time to first content under 1 s on an iPhone 12 over LTE" is.

### Q10. What non-functional requirements matter most for mobile? `[Senior]`
| Requirement | Questions to consider | Typical target |
|---|---|---|
| **Performance** | Launch time, TTFC, scroll smoothness, memory | Cold launch < 400 ms to first frame; hitch rate < 5 ms/s |
| **Offline / resilience** | What works offline? How are writes queued? | Reads cached; writes never lost |
| **Freshness / consistency** | Real-time or eventual? | Chat < 1 s; feed minutes |
| **Battery & data** | Polling, background work, media sizes | No polling more often than needed; Low Data Mode honoured |
| **Security & privacy** | Auth, token storage, encryption, PII | Tokens in Keychain; no PII in logs |
| **Scalability (client)** | Large lists, large local DBs | 100k rows without jank |
| **Observability** | Crashes, metrics, logs | Crash-free users > 99.9% |
| **Accessibility & i18n** | Dynamic Type, VoiceOver, RTL | Every screen usable at AX5 text size |
| **Maintainability** | Modularity, testability, ownership | Feature modules per team |

### Q11. How do you do back-of-the-envelope estimation for a mobile app? `[Senior]`
**Example: feed data usage per session**
```
Feed page:        20 posts × ~1.5 KB JSON          ≈ 30 KB (≈ 8 KB gzipped)
Thumbnails:       20 images × ~60 KB (WebP/HEIC, sized for device) ≈ 1.2 MB
Typical session:  5 pages scrolled                 ≈ 6 MB images + 40 KB JSON
Daily (3 sessions):                                ≈ 18 MB/day
Monthly:                                           ≈ 540 MB/month
```
**What the numbers tell you:**
- **Images dominate**: device-appropriate sizes, modern formats and CDN resizing matter far more than JSON tweaks.
- In Low Data Mode, serve lower-quality images and disable autoplay/prefetching.
- A disk cache budget (e.g. 200 MB for images) with LRU eviction keeps storage bounded.

**Second example: backend load created by the client** (shows you think about the system, not just the app):
```
10M DAU × 3 app opens/day × 4 requests at launch       = 120M requests/day ≈ 1,400 req/s average
Peak factor ×5 (evening + push campaign)                ≈ 7,000 req/s
If every client retries 3× without jitter after an outage → bursts of ~20,000 req/s at the same instant
→ jittered backoff, conditional requests (304s), and one aggregated launch call matter.
```

### Q12. How do you estimate local storage needs? `[Senior]`
**Example: chat app**
```
Text message:        ~200 bytes (with metadata and indexes)
Active user:         ~500 messages/day → 100 KB/day → ~36 MB/year of text
Media:               thumbnails stored; full-size media on demand and evictable
Plan:                keep all text locally; cap media cache (e.g. 1 GB, user-configurable);
                     "Manage storage" screen; stream or re-download old media
```
- Mention indexes (conversation ID + sequence) and periodic cleanup of deleted or expired content.
- Know the order of magnitude of on-device limits: SQLite comfortably handles millions of rows with proper indexes; the problem is usually **unbounded media**, not text.

### Q13. Which success metrics would you define? `[Senior]`
- **Performance**: time to first content (TTFC), launch time, hang rate, scroll hitch rate.
- **Reliability**: crash-free sessions/users, API error rates, sync failure rate, message delivery latency.
- **Engagement / business**: adoption, session length, conversion, retention.
- **Efficiency**: data per session, battery impact, cache hit rate.

How you'd actually measure TTFC on device:

```swift
import os

enum Perf {
    static let signposter = OSSignposter(subsystem: "com.example.app", category: "perf")
}

@MainActor
final class FeedScreenMetrics {
    private var state: OSSignpostIntervalState?
    private let start = ContinuousClock.now

    func screenDidAppear() {
        state = Perf.signposter.beginInterval("TTFC")          // visible in Instruments
    }

    /// `report` sends the value to your analytics pipeline (segment by app version, device, network)
    func firstContentRendered(fromCache: Bool, report: (_ milliseconds: Int, _ fromCache: Bool) -> Void) {
        guard let state else { return }                          // report once per screen visit
        Perf.signposter.endInterval("TTFC", state)
        self.state = nil
        let elapsed = ContinuousClock.now - start
        report(Int(elapsed / .milliseconds(1)), fromCache)       // Duration / Duration = Double
    }
}
```

Mentioning metrics early shows you design for **observable outcomes**, not just code structure.

## 3. API Design & Communication Protocols

### Q14. Compare REST, GraphQL, and gRPC for mobile clients. `[Senior]`
| | REST (JSON) | GraphQL | gRPC (Protobuf) |
|---|---|---|---|
| Data fetching | Fixed responses per endpoint; may over/under-fetch | Client selects exactly the fields it needs; one request for nested data | Typed RPC methods; compact binary payloads |
| Caching | Excellent HTTP caching (ETag, CDN) | Harder (POST, single endpoint); needs a normalized client cache | No HTTP caching by default |
| Tooling on iOS | `URLSession`, `Codable` | Apollo iOS, code generation | grpc-swift, code generation |
| Versioning | URL/header versions | Schema evolution, field deprecation | Protobuf field numbers (backward compatible) |
| Best for | Most apps, CDN-cacheable content | Complex, nested UIs; many clients | High-performance internal APIs, streaming |

Senior answer: REST is the pragmatic default; GraphQL shines when many screens need different shapes of the same data; gRPC for performance-critical or streaming use. Many companies use a **BFF** (Q17) to tailor REST for mobile instead.

The same screen, two ways:
```
REST:     GET /users/42           → 2 KB (profile incl. 30 fields you don't show)
          GET /users/42/posts     → 15 KB
          GET /users/42/followers?count_only=1
          = 3 round trips (~3 × 150 ms on LTE)

GraphQL:  POST /graphql  { user(id: 42) { name avatarURL(size: 96) followerCount posts(first: 10) { id thumbnailURL } } }
          = 1 round trip, ~4 KB, but no CDN caching and a normalized cache on the client
```

### Q15. Which real-time mechanism would you choose? `[Senior]`
| Mechanism | How it works | Pros | Cons | Use for |
|---|---|---|---|---|
| **Short polling** | Request every N seconds | Simple, works everywhere | Wasteful, delayed, battery drain | Infrequent updates (order status every 30 s) |
| **Long polling** | Server holds the request until data is available | Near real-time over plain HTTP | Connection churn, server resources | Fallback when WebSockets are blocked |
| **Server-Sent Events** | One-way stream over HTTP | Simple, auto-reconnect semantics | Server → client only | Live scores, LLM token streaming |
| **WebSockets** | Persistent bidirectional connection | Low latency, bidirectional | Connection management, scaling, battery | Chat, collaboration, live location |
| **Push (APNs)** | Apple delivers to the device | Works when backgrounded/terminated | Not guaranteed, size- and rate-limited | Wake/alert users, trigger syncs |

Typical mobile design: **WebSocket in the foreground + APNs in the background + delta sync on reconnect** (so nothing is missed).

SSE on iOS needs no library; `URLSession.bytes` streams lines:

```swift
func streamEvents(from url: URL, session: URLSession = .shared) -> AsyncThrowingStream<String, Error> {
    AsyncThrowingStream { continuation in
        let task = Task {
            do {
                var request = URLRequest(url: url)
                request.setValue("text/event-stream", forHTTPHeaderField: "Accept")
                let (bytes, _) = try await session.bytes(for: request)
                for try await line in bytes.lines where line.hasPrefix("data:") {
                    continuation.yield(String(line.dropFirst(5)).trimmingCharacters(in: .whitespaces))
                }
                continuation.finish()
            } catch {
                continuation.finish(throwing: error)
            }
        }
        continuation.onTermination = { _ in task.cancel() }
    }
}
```

### Q16. What makes an API mobile-friendly? `[Senior]`
- **Small payloads**: only fields the screen needs; gzip/brotli; no deeply nested duplicates.
- **Fewer round trips**: one aggregated call per screen (latency dominates on mobile); batch endpoints.
- **Cursor pagination** and **delta sync** (`changes?since=token`).
- **Image URLs with size parameters** (or several renditions) plus `width`/`height` so the UI reserves space.
- **Idempotency** for writes (Q19); **consistent error format** (Q20).
- **Backward compatibility**: additive changes only.
- **Server-provided display strings** where localization or business rules change often (with care).

### Q17. What is the Backend for Frontend (BFF) pattern? `[Senior]`
A server layer for one client type that **aggregates** many microservice calls and **shapes** responses per screen.

```
iOS app ──▶ Mobile BFF ──┬──▶ User service
                         ├──▶ Feed service
                         ├──▶ Ads service
                         └──▶ Media service
```

- Benefits: fewer round trips, smaller payloads, logic changeable without an app release, isolation from backend refactors.
- Costs: another service to own and scale; risk of duplicated business logic across BFFs.

```json
GET /bff/v1/home   →  one call for the whole first screen
{
  "greeting": "Good evening, Ana",
  "continue_watching": [ { "id": "t_9", "title": "…", "progress": 0.42, "image": "https://cdn…?w=640" } ],
  "recommendations": [ … ],
  "badges": { "inbox": 3 }
}
```

### Q18. How do you version APIs when old app versions stay installed for months? `[Lead/Expert]`
- Assume **many versions in production at once**.
- Prefer **additive, backward-compatible changes**; never change a field's meaning or remove fields old clients use.
- Clients **tolerate unknown fields and enum values** (decode unknown enum cases as `.unknown`).
- Send `X-App-Version` and `X-Platform` headers so the backend can tailor or block responses.
- Breaking changes: `/v2/` endpoints, support old versions for a defined window, and a **minimum supported version** (Q96) as last resort.
- Track version adoption to know when old paths can go.

```swift
// Tolerant enum: a new server value never breaks old apps
enum PostKind: Decodable, Equatable {
    case text, image, video, unknown(String)

    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)
        switch raw {
        case "text": self = .text
        case "image": self = .image
        case "video": self = .video
        default: self = .unknown(raw)          // render a "Update to view" placeholder
        }
    }
}
```

### Q19. What are idempotency keys, and why do mobile apps need them? `[Senior]`
Mobile networks often fail **after** the server processed a request but **before** the client got the response. Retrying a non-idempotent request (create order, send money, post message) could duplicate it. The client sends a unique key per **logical operation**; the server stores the result for that key and returns it for duplicates.

```
Tap "Place order" ─▶ key K created and persisted with the pending order
POST /orders  Idempotency-Key: K  ──▶ server charges card, stores (K → order_77) ──X response lost
retry POST /orders  Idempotency-Key: K ──▶ server finds K → returns order_77 (no second charge)
```

```swift
import Foundation

enum HTTPError: Error, Equatable {
    case status(Int, retryAfter: Duration?, body: Data)
}

struct HTTPClient: Sendable {
    let session: URLSession
    let decoder = JSONDecoder()

    func send<T: Decodable>(_ request: URLRequest, as type: T.Type) async throws -> T {
        let (data, response) = try await session.data(for: request)
        guard let http = response as? HTTPURLResponse else { throw URLError(.badServerResponse) }
        guard (200..<300).contains(http.statusCode) else {
            let retryAfter = http.value(forHTTPHeaderField: "Retry-After")
                .flatMap(Double.init).map { Duration.seconds($0) }
            throw HTTPError.status(http.statusCode, retryAfter: retryAfter, body: data)
        }
        return try decoder.decode(T.self, from: data)
    }
}

struct CreateOrderRequest: Encodable { let items: [LineItemDTO]; let paymentMethodID: String }

func placeOrder(_ body: CreateOrderRequest, idempotencyKey: UUID,
                client: HTTPClient, baseURL: URL) async throws -> OrderDTO {
    var request = URLRequest(url: baseURL.appending(path: "orders"))
    request.httpMethod = "POST"
    request.setValue(idempotencyKey.uuidString, forHTTPHeaderField: "Idempotency-Key")
    request.setValue("application/json", forHTTPHeaderField: "Content-Type")
    request.httpBody = try JSONEncoder().encode(body)

    // Every retry reuses the SAME key, so the server processes the order at most once
    return try await withRetry(maxAttempts: 3) {       // defined in Q21
        try await client.send(request, as: OrderDTO.self)
    }
}
```

The key is created **once per user action** and persisted with the pending operation, so even a retry after an app restart reuses it. A new key means "this is a new order."

### Q20. How should API errors be designed for mobile clients? `[Senior]`
```json
{
  "error": {
    "code": "PAYMENT_DECLINED",
    "message": "Your card was declined.",
    "retryable": false,
    "retry_after_seconds": null,
    "request_id": "req_8f2a91c",
    "details": { "decline_reason": "insufficient_funds" }
  }
}
```
- A **stable machine-readable code** for client logic.
- An optional **user-displayable message** (localized server-side) and a client fallback.
- **Retry guidance** (`retryable`, `Retry-After`).
- A **request ID** for support and tracing.
- Status codes: 4xx = client error (don't retry, except 408/429); 5xx = server error (retry with backoff).

```swift
struct APIErrorBody: Decodable {
    struct Payload: Decodable { let code: String; let message: String?; let retryable: Bool; let requestId: String }
    let error: Payload
}

enum CheckoutFailure: Equatable {
    case paymentDeclined, outOfStock, retryable, unknown(requestID: String?)

    init(_ error: Error) {
        guard case HTTPError.status(_, _, let body) = error else { self = .retryable; return }
        let decoder = JSONDecoder()
        decoder.keyDecodingStrategy = .convertFromSnakeCase
        guard let payload = try? decoder.decode(APIErrorBody.self, from: body).error else {
            self = .unknown(requestID: nil); return
        }
        switch payload.code {
        case "PAYMENT_DECLINED": self = .paymentDeclined
        case "OUT_OF_STOCK": self = .outOfStock
        default: self = payload.retryable ? .retryable : .unknown(requestID: payload.requestId)
        }
    }
}
```

### Q21. How should the client retry with backoff? `[Senior]`
```swift
import Foundation

struct RetryPolicy: Sendable {
    var maxAttempts = 4
    var baseDelay: Double = 0.5        // seconds
    var maxDelay: Double = 20

    /// Exponential backoff with "full jitter" to avoid synchronized retry storms
    func delay(forAttempt attempt: Int) -> Duration {
        let exponential = min(maxDelay, baseDelay * pow(2, Double(attempt - 1)))
        return .seconds(Double.random(in: 0...exponential))
    }

    func shouldRetry(_ error: Error) -> Bool {
        if error is CancellationError { return false }
        if let urlError = error as? URLError {
            return [.timedOut, .networkConnectionLost, .notConnectedToInternet, .cannotConnectToHost]
                .contains(urlError.code)
        }
        if case HTTPError.status(let code, _, _) = error {
            return code == 408 || code == 429 || (500...599).contains(code)
        }
        return false
    }

    /// Server guidance wins over our own schedule
    func serverDelay(for error: Error) -> Duration? {
        if case HTTPError.status(_, let retryAfter?, _) = error { return min(retryAfter, .seconds(maxDelay)) }
        return nil
    }
}

/// Only wrap idempotent requests (GET/PUT/DELETE) or requests carrying an Idempotency-Key.
func withRetry<T>(maxAttempts: Int = 4,
                  policy: RetryPolicy = RetryPolicy(),
                  _ operation: () async throws -> T) async throws -> T {
    var attempt = 1
    while true {
        do {
            return try await operation()
        } catch {
            guard attempt < maxAttempts, policy.shouldRetry(error) else { throw error }
            try await Task.sleep(for: policy.serverDelay(for: error) ?? policy.delay(forAttempt: attempt))
            attempt += 1                       // Task.sleep throws on cancellation: retries stop
        }
    }
}
```

**Talking points:**
- **Jitter** matters at scale: after an outage, millions of clients retrying on the same exponential schedule overload the recovering backend (a "thundering herd").
- Respect `Retry-After` for 429/503.
- Combine with a **circuit breaker** so a dead endpoint isn't hammered:

```swift
actor CircuitBreaker {
    enum State: Equatable { case closed, open(until: ContinuousClock.Instant), halfOpen }

    private var state: State = .closed
    private var failures = 0
    private let threshold: Int
    private let coolDown: Duration

    init(threshold: Int = 5, coolDown: Duration = .seconds(30)) {
        self.threshold = threshold
        self.coolDown = coolDown
    }

    enum Rejection: Error { case circuitOpen }

    func run<T: Sendable>(_ operation: @Sendable () async throws -> T) async throws -> T {
        if case .open(let until) = state {
            guard ContinuousClock.now >= until else { throw Rejection.circuitOpen }  // fail fast, show cached UI
            state = .halfOpen                                                        // allow one probe
        }
        do {
            let value = try await operation()
            failures = 0
            state = .closed
            return value
        } catch {
            failures += 1
            if failures >= threshold || state == .halfOpen {
                state = .open(until: .now + coolDown)
            }
            throw error
        }
    }
}
```

### Q22. How do you prioritize and cancel network requests? `[Senior]`

```swift
/// One network call per key, shared by every concurrent caller
actor RequestCoalescer<Key: Hashable & Sendable, Value: Sendable> {
    private var inFlight: [Key: Task<Value, Error>] = [:]

    func value(for key: Key, load: @escaping @Sendable () async throws -> Value) async throws -> Value {
        if let existing = inFlight[key] { return try await existing.value }
        let task = Task { try await load() }
        inFlight[key] = task
        defer { inFlight[key] = nil }
        return try await task.value
    }
}
```

### Q23. How do HTTP/2, HTTP/3, and compression help mobile apps? `[Senior]`
- **HTTP/2**: many requests multiplexed over one TCP connection; header compression. Automatic in `URLSession`.
- **HTTP/3 (QUIC)**: faster connection setup, no TCP head-of-line blocking, better on lossy networks and Wi-Fi ↔ cellular switches. Supported by `URLSession` (iOS 15+) when the server advertises it; `URLRequest.assumesHTTP3Capable` skips the discovery round trip.
- **Compression**: gzip/brotli responses handled transparently; compress large uploads (analytics batches) explicitly.
- **Connection reuse**: share one `URLSession`; a session per request throws away warm connections.

### Q24. JSON or Protocol Buffers? `[Senior]`
| JSON | Protocol Buffers |

### Q27. How do you implement smooth infinite scrolling? `[Senior]`
```swift
struct Page<Item: Sendable>: Sendable { let items: [Item]; let nextCursor: String? }

protocol FeedAPI: Sendable { func feed(cursor: String?) async throws -> Page<Post> }

@MainActor
@Observable
final class FeedViewModel {
    enum Footer: Equatable { case idle, loading, failed, end }

    private(set) var posts: [Post] = []
    private(set) var footer: Footer = .idle
    private var nextCursor: String?
    private var seen = Set<Post.ID>()
    private let api: FeedAPI
    private let prefetchDistance = 5

    init(api: FeedAPI) { self.api = api }

    func refresh() async {
        nextCursor = nil
        seen = []
        posts = []
        footer = .idle
        await loadMore()
    }

    /// Call from each row's onAppear
    func rowAppeared(_ post: Post) async {
        guard let index = posts.firstIndex(where: { $0.id == post.id }),
              index >= posts.count - prefetchDistance else { return }
        await loadMore()
    }

    func loadMore() async {
        guard footer == .idle else { return }       // one request at a time; stops at .end
        footer = .loading
        do {
            let page = try await api.feed(cursor: nextCursor)
            let fresh = page.items.filter { seen.insert($0.id).inserted }   // dedupe by ID
            posts.append(contentsOf: fresh)
            nextCursor = page.nextCursor
            footer = page.nextCursor == nil ? .end : .idle
        } catch {
            footer = .failed                        // keep loaded posts; show inline Retry
        }
    }

    func retry() async {
        guard footer == .failed else { return }
        footer = .idle
        await loadMore()
    }
}
```
- Trigger **before** the end so the next page arrives in time.
- Inline **retry** cell on failure; never wipe loaded content.
- Prefetch images for upcoming rows; cancel when scrolling the other way.
- For very long sessions, window the in-memory list and reload older items from the local store when scrolling back.

### Q29. What is delta sync? `[Senior]`
The client asks **"what changed since my last sync token?"** The server returns created, updated and deleted items plus a new token.

```json
GET /v1/notes/changes?since=st_1042

{
  "changes": [
    { "type": "upsert", "note": { "id": "n_17", "title": "Groceries", "updated_at": "…", "version": 8 } },
    { "type": "delete", "id": "n_09" }
  ],
  "next_token": "st_1057",
  "has_more": false
}
```

```swift
struct ChangePage: Decodable, Sendable { let changes: [Change]; let nextToken: String; let hasMore: Bool }

actor DeltaSyncer {
    private let api: ChangesAPI
    private let db: NotesDatabase

    init(api: ChangesAPI, db: NotesDatabase) { self.api = api; self.db = db }

    func sync() async throws {
        var token = try await db.syncToken()
        var hasMore = true
        while hasMore {
            let page: ChangePage
            do {
                page = try await api.changes(since: token)
            } catch ChangesAPIError.tokenExpired {
                try await db.markNeedsFullResync()        // server compacted history beyond our token
                return
            }
            // Apply changes AND save the token in ONE transaction:
            // a crash between the two would otherwise skip or re-apply changes
            try await db.apply(page.changes, newToken: page.nextToken)
            token = page.nextToken
            hasMore = page.hasMore
        }
    }
}
```
Benefits: small payloads, fast syncs, battery-friendly. The server keeps change history or tombstones long enough; a too-old token gets "full resync required."

### Q31. What caching layers exist in a mobile app? `[Senior]`
```
Request for data
   │
   ├─▶ 1. In-memory cache (NSCache / dictionaries in actors)   ~ nanoseconds, lost on termination
   ├─▶ 2. Local database (SQLite / SwiftData / Core Data)      ~ milliseconds, structured, queryable
   ├─▶ 3. Disk file cache (images, media, JSON blobs)          ~ milliseconds, evictable
   ├─▶ 4. HTTP cache (URLCache, ETag / Cache-Control)          automatic for cacheable responses
   └─▶ 5. Network → CDN → backend                              ~ 100 ms – seconds
```
Each layer differs in **lifetime, capacity and consistency**. Say which layer each data type uses:

| Data | Layer | Why |
|---|---|---|
| Feed posts | Local DB | Queryable, survives relaunch, offline |
| Decoded images | Memory (`NSCache`) | Fast display, auto-evicted under pressure |
| Image bytes | Disk file cache | Large, regenerable |
| Remote config | Disk JSON + memory snapshot | Read synchronously at launch |
| Public catalog JSON | HTTP cache / CDN | Server controls freshness with headers |
| Auth tokens | Keychain | Secret, not a cache |

### Q32. How does HTTP caching work, and how do you configure it on iOS? `[Senior]`
- `Cache-Control: max-age=300` → reuse the response for 5 minutes without asking the server.
- `ETag` / `Last-Modified` → **conditional requests**: the client sends `If-None-Match`; the server answers `304 Not Modified` with no body (saves bandwidth, still a round trip).
- `URLSession` honours these headers through `URLCache`.

```swift
let cache = URLCache(memoryCapacity: 20 * 1024 * 1024,     // 20 MB
                     diskCapacity: 150 * 1024 * 1024)      // 150 MB
let configuration = URLSessionConfiguration.default
configuration.urlCache = cache
configuration.requestCachePolicy = .useProtocolCachePolicy  // follow server cache headers
let session = URLSession(configuration: configuration)
```
- `URLCache` skips responses that are large relative to its capacity (roughly > 5% of the disk capacity).
- Per-user responses should be `private` or `no-store`, especially on shared devices.

### Q33. How do you implement conditional requests manually? `[Senior]`
```swift
actor ConditionalFetcher {
    private struct Entry { let etag: String; let data: Data }
    private var entries: [URL: Entry] = [:]
    private let session: URLSession

    init(session: URLSession) { self.session = session }

    func data(from url: URL) async throws -> Data {
        var request = URLRequest(url: url)
        request.cachePolicy = .reloadIgnoringLocalCacheData      // we manage validation ourselves
        if let entry = entries[url] {
            request.setValue(entry.etag, forHTTPHeaderField: "If-None-Match")
        }

        let (data, response) = try await session.data(for: request)
        guard let http = response as? HTTPURLResponse else { throw URLError(.badServerResponse) }

        switch http.statusCode {
        case 304:
            guard let cached = entries[url] else { throw URLError(.resourceUnavailable) }
            return cached.data                                   // unchanged: reuse cached body
        case 200..<300:
            if let etag = http.value(forHTTPHeaderField: "ETag") {
                entries[url] = Entry(etag: etag, data: data)
            }
            return data
        default:
            throw URLError(.badServerResponse)
        }
    }
}
```
In production, persist ETags and bodies (database or disk) so validation survives relaunches.

### Q36. How do you implement an LRU cache with a size limit? `[Senior]`
```swift
/// Least-recently-used cache with a total cost limit (e.g. bytes). Not thread-safe by itself.
final class LRUCache<Key: Hashable, Value> {
    private final class Node {
        let key: Key
        var value: Value
        let cost: Int
        weak var previous: Node?      // FIX: weak, otherwise neighbours retain each other and the list leaks
        var next: Node?
        init(key: Key, value: Value, cost: Int) { self.key = key; self.value = value; self.cost = cost }
    }

    private var nodes: [Key: Node] = [:]
    private var head: Node?           // most recently used
    private var tail: Node?           // least recently used (kept alive by its predecessor's `next`)
    private var totalCost = 0
    private let costLimit: Int

    init(costLimit: Int) { self.costLimit = costLimit }

    func value(for key: Key) -> Value? {
        guard let node = nodes[key] else { return nil }
        moveToFront(node)
        return node.value
    }

    func insert(_ value: Value, for key: Key, cost: Int) {
        if let existing = nodes[key] { remove(existing) }
        let node = Node(key: key, value: value, cost: cost)
        nodes[key] = node
        addToFront(node)
        totalCost += cost
        while totalCost > costLimit, let lru = tail { remove(lru) }    // evict least recently used
    }

    private func addToFront(_ node: Node) {
        node.next = head
        node.previous = nil
        head?.previous = node
        head = node
        if tail == nil { tail = node }
    }

    private func moveToFront(_ node: Node) {
        guard head !== node else { return }
        detach(node)
        addToFront(node)
    }

    private func remove(_ node: Node) {
        detach(node)
        nodes[node.key] = nil
        totalCost -= node.cost
    }

    private func detach(_ node: Node) {
        node.previous?.next = node.next
        node.next?.previous = node.previous
        if head === node { head = node.next }
        if tail === node { tail = node.previous }
        node.previous = nil
        node.next = nil
    }
}

@Test func evictsLeastRecentlyUsed() {
    let cache = LRUCache<String, Int>(costLimit: 2)
    cache.insert(1, for: "a", cost: 1)
    cache.insert(2, for: "b", cost: 1)
    _ = cache.value(for: "a")                 // "a" is now most recent
    cache.insert(3, for: "c", cost: 1)        // evicts "b"
    #expect(cache.value(for: "b") == nil)
    #expect(cache.value(for: "a") == 1)
}
```
- O(1) get/insert using a dictionary plus a doubly linked list. The `nodes` dictionary keeps every node alive, so a `weak previous` is safe.
- In an app, wrap it in an actor or guard it with a `Mutex`, or use `NSCache` (thread-safe, evicts under memory pressure, but eviction order is not guaranteed).

### Q40. What does a sync architecture look like? `[Lead/Expert]`
```
          ┌──────────────── App ─────────────────┐
 UI ◀────▶│ Local DB (source of truth for UI)     │
          │   ▲                    │              │
          │   │ apply changes      │ local edits  │
          │   │                    ▼              │
          │ Sync Engine ◀──── Outbox (pending ops)│
          └───┬──────────────────────┬────────────┘
              │ pull: GET /changes?since=token
              │ push: POST /operations (idempotent, batched)
              ▼
          Backend (authoritative store, change feed)
```
- **UI reads only from the local database** and observes changes.
- **Local writes** update the database immediately (optimistic) and append an operation to the **outbox** — in the same transaction.
- **Push**: send outbox operations in order with idempotency keys; remove on acknowledgement.
- **Pull**: fetch changes since the last token; apply; resolve conflicts.
- **Triggers**: launch/foreground, connectivity restored, silent push, background refresh, debounced after local writes.

### Q41. How do you implement an outbox for offline writes? `[Lead/Expert]`
```swift
struct PendingOperation: Codable, Sendable, Identifiable {
    enum Kind: Codable, Sendable {
        case createNote(NoteDTO)
        case updateNote(id: String, changes: NoteChangesDTO, baseVersion: Int)
        case deleteNote(id: String)
    }

    let id: UUID                 // doubles as the idempotency key
    let kind: Kind
    let createdAt: Date
    var attemptCount = 0
}

actor SyncEngine {
    private let outbox: OutboxStore          // persisted (database table)
    private let api: SyncAPI
    private let localStore: NoteStore
    private var isPushing = false
    private let maxAttempts = 8

    init(outbox: OutboxStore, api: SyncAPI, localStore: NoteStore) {
        self.outbox = outbox
        self.api = api
        self.localStore = localStore
    }

    /// Called after local edits (debounced), on reconnect, and from background refresh
    func pushPendingOperations() async {
        guard !isPushing else { return }           // one push loop at a time (actor reentrancy guard)
        isPushing = true
        defer { isPushing = false }

        while let operation = try? await outbox.oldest() {
            do {
                let result = try await api.apply(operation, idempotencyKey: operation.id)
                try await localStore.applyServerResult(result)    // e.g. new version numbers
                try await outbox.remove(operation.id)
            } catch let error as SyncError where error.isConflict {
                // FIX: the conflict path must take the operation out of the queue,
                // otherwise the loop retries it forever
                try? await resolveConflict(for: operation, error: error)
            } catch let error as SyncError where error.isPermanent {
                // 4xx validation failure: retrying will never succeed
                try? await outbox.moveToDeadLetter(operation.id, reason: error.localizedDescription)
                try? await localStore.revertOptimisticChange(for: operation)
            } catch {
                let attempts = (try? await outbox.incrementAttempts(operation.id)) ?? maxAttempts
                if attempts >= maxAttempts {
                    try? await outbox.moveToDeadLetter(operation.id, reason: "max attempts")
                    continue                                   // FIX: one poison op must not block the queue
                }
                return                                         // transient: retry later with backoff
            }
        }
    }

    private func resolveConflict(for operation: PendingOperation, error: SyncError) async throws {
        // 1. Fetch the server version  2. Three-way merge (Q42)  3. Write merged result locally
        // 4. Remove this op and enqueue a new op based on the server version (or nothing if merged == server)
        let merged = try await localStore.mergeWithServerVersion(for: operation, serverRecord: error.serverRecord)
        try await outbox.replace(operation.id, with: merged.followUpOperation)
    }
}
```
**Talking points:** operations are persisted (survive termination), processed **in order**, idempotent (safe retries), removed only after acknowledgement, with a **dead-letter** path that surfaces "couldn't sync this change" in the UI instead of retrying forever.

### Q42. What conflict resolution strategies exist? `[Lead/Expert]`
| Strategy | How it works | Pros | Cons |
|---|---|---|---|
| **Last-write-wins** | Latest timestamp/version wins | Simple | Silently loses edits; clock skew |
| **Server wins / client wins** | One side always wins | Predictable | Loses the other side's changes |
| **Field-level merge** | Merge non-overlapping field changes | Preserves most edits | More complex |
| **Manual resolution** | Show both versions | No silent loss | Interrupts the user |
| **OT / CRDTs** | Mathematically mergeable structures | Real-time collaboration | Complex; extra metadata |

```swift
/// Three-way, field-level merge using the common ancestor (base) version
struct Note: Equatable, Sendable {
    var title: String
    var body: String
    var isPinned: Bool
}

func merge(base: Note, local: Note, remote: Note) -> (merged: Note, hasConflict: Bool) {
    var merged = remote
    var hasConflict = false

    func resolve<T: Equatable>(_ keyPath: WritableKeyPath<Note, T>) {
        let localChanged = local[keyPath: keyPath] != base[keyPath: keyPath]
        let remoteChanged = remote[keyPath: keyPath] != base[keyPath: keyPath]
        switch (localChanged, remoteChanged) {
        case (true, false):
            merged[keyPath: keyPath] = local[keyPath: keyPath]      // only we changed it
        case (true, true) where local[keyPath: keyPath] != remote[keyPath: keyPath]:
            hasConflict = true                                       // both changed differently
        default:
            break                                                    // keep remote
        }
    }

    resolve(\.title)
    resolve(\.body)
    resolve(\.isPinned)
    return (merged, hasConflict)
}

@Test func nonOverlappingEditsMerge() {
    let base = Note(title: "Shop", body: "Milk", isPinned: false)
    let local = Note(title: "Groceries", body: "Milk", isPinned: false)   // phone renamed
    let remote = Note(title: "Shop", body: "Milk", isPinned: true)       // iPad pinned
    let result = merge(base: base, local: local, remote: remote)
    #expect(result.merged == Note(title: "Groceries", body: "Milk", isPinned: true))
    #expect(!result.hasConflict)
}
```
For conflicting fields, apply a policy (e.g. remote wins but save the local text as a "Conflicted copy," as many notes apps do).

### Q43. How do you implement optimistic updates with rollback? `[Senior]`

```swift
@MainActor

        let desired = isLiked
```

### Q44. Should IDs be generated on the client or the server? `[Senior]`

### Q45. How do you handle ordering and clock skew? `[Lead/Expert]`
- Device clocks are unreliable (manual changes, drift). Don't use client timestamps for **ordering** or cross-device conflicts.
- Use **server-assigned sequence numbers** or timestamps for canonical order; **version numbers** per record for optimistic concurrency (`baseVersion`; the server rejects stale versions); **hybrid logical / vector clocks** for advanced multi-writer sync.
- Client timestamps are fine for **display** ("sent 2 min ago") and local ordering of pending items.

```
Device A clock: 10:05 (5 min fast)   edits note → "updated_at 10:05"
Device B clock: 10:01 (correct)      edits note → "updated_at 10:01"
Last-write-wins by client time keeps A's edit even though B edited later.
Version numbers: both based on v7 → first to reach the server becomes v8, the other gets a conflict.
```

### Q47. Design a WebSocket client with automatic reconnection. `[Lead/Expert]`
```swift
import Foundation

enum ServerEvent: Decodable, Sendable {
    case message(MessageDTO)
    case typing(conversationID: String, userID: String)
    case receipt(messageID: UUID, status: String)
    // Decoding by a "type" discriminator omitted for brevity
}

actor RealtimeConnection {
    let events: AsyncStream<ServerEvent>
    private let continuation: AsyncStream<ServerEvent>.Continuation
    private let url: URL
    private let session: URLSession
    private let decoder = JSONDecoder()

    private var socket: URLSessionWebSocketTask?
    private var receiveTask: Task<Void, Never>?
    private var heartbeatTask: Task<Void, Never>?
    private var connectionID = 0                  // ignores callbacks from sockets we already replaced
    private var reconnectAttempt = 0
    private var shouldBeConnected = false
    private var lastPong: ContinuousClock.Instant?

    init(url: URL, session: URLSession = .shared) {
        self.url = url
        self.session = session
        (events, continuation) = AsyncStream.makeStream(of: ServerEvent.self,
                                                        bufferingPolicy: .bufferingNewest(1_000))
    }

    func connect() {
        shouldBeConnected = true
        openSocket()
    }

    /// e.g. when the app moves to the background (push takes over)
    func disconnect() {
        shouldBeConnected = false
        closeCurrentSocket()
    }

    /// Final teardown (logout): ends every `for await` loop on `events`
    func shutdown() {
        disconnect()
        continuation.finish()                     // FIX: the stream was never finished
    }

    func send(_ data: Data) async throws {
        guard let socket else { throw URLError(.notConnectedToInternet) }
        try await socket.send(.data(data))
    }

    private func openSocket() {
        closeCurrentSocket()                      // FIX: never leave the old socket running
        connectionID += 1
        let id = connectionID
        let socket = session.webSocketTask(with: url)
        self.socket = socket
        socket.resume()
        receiveTask = Task { await self.receiveLoop(on: socket, id: id) }
        heartbeatTask = Task { await self.heartbeatLoop(on: socket, id: id) }
    }

    private func closeCurrentSocket() {
        receiveTask?.cancel()
        heartbeatTask?.cancel()
        socket?.cancel(with: .goingAway, reason: nil)
        socket = nil
    }

    private func receiveLoop(on socket: URLSessionWebSocketTask, id: Int) async {
        do {
            while !Task.isCancelled {
                let message = try await socket.receive()
                reconnectAttempt = 0                               // healthy connection
                let data: Data?
                switch message {
                case .data(let bytes): data = bytes
                case .string(let text): data = Data(text.utf8)     // FIX: most servers send JSON as text frames
                @unknown default: data = nil
                }
                if let data, let event = try? decoder.decode(ServerEvent.self, from: data) {
                    continuation.yield(event)
                }
            }
        } catch {
            guard id == connectionID else { return }               // an old socket failing: ignore
            await reconnectIfNeeded()
        }
    }

    /// Detects "zombie" connections (NAT timeouts, network switches) that never report an error
    private func heartbeatLoop(on socket: URLSessionWebSocketTask, id: Int) async {
        while !Task.isCancelled {
            try? await Task.sleep(for: .seconds(25))
            guard !Task.isCancelled, id == connectionID else { return }
            let sentAt = ContinuousClock.now
            socket.sendPing { [weak self] error in
                guard error == nil else { return }
                Task { await self?.recordPong(id: id) }
            }
            try? await Task.sleep(for: .seconds(10))
            guard id == connectionID else { return }
            if (lastPong ?? .now - .seconds(3600)) < sentAt {
                socket.cancel(with: .abnormalClosure, reason: nil)  // receive() throws → reconnect
                return
            }
        }
    }

    private func recordPong(id: Int) {
        if id == connectionID { lastPong = .now }
    }

    private func reconnectIfNeeded() async {
        guard shouldBeConnected else { return }
        reconnectAttempt += 1
        let maxDelay = min(30, pow(2, Double(reconnectAttempt)))
        try? await Task.sleep(for: .seconds(Double.random(in: 0...maxDelay)))   // backoff + jitter
        guard shouldBeConnected else { return }
        openSocket()
        // After reconnecting, the sync layer fetches missed events using the last sequence (Q51)
    }
}
```
**Talking points:**
- **Heartbeats** detect dead connections that never error (mobile NATs silently drop idle TCP connections).
- **Reconnect on network change** (`NWPathMonitor` path update → `connect()` immediately, resetting backoff).
- **Disconnect in the background**; rely on push; reconnect + delta sync on foreground.
- **Authenticate** in the handshake (`Authorization` header on the `URLRequest`); on a 401 close code, refresh the token before reconnecting.
- **Backpressure**: `bufferingNewest(1_000)` drops the oldest events if the consumer is slow; acceptable because the sync endpoint guarantees completeness.

### Q48. How do you guarantee message delivery? `[Lead/Expert]`
- Networks drop messages both ways, so aim for **at-least-once delivery + deduplication** (exactly-once from the user's point of view).
- **Client → server**: store locally as `pending` with a client UUID; retry until the server **acknowledges** that UUID; the server dedupes by UUID.
- **Server → client**: the client acknowledges (or the server infers from sync cursors); after reconnect, fetch everything after the last known sequence.
- **Status lifecycle**: `pending → sent (server ack) → delivered (recipient device ack) → read`.

```
Client                                   Server
  │ store pending (id=U1)                   │
  │── send(U1, "Hi") ─────────────────────▶│ persist, seq=1057
  │                ✗ ack lost               │
  │── send(U1, "Hi") (retry) ─────────────▶│ U1 already stored → same seq=1057
  │◀──────────────────── ack(U1, 1057) ─────│
  │ mark sent, seq=1057                     │
```

### Q49. How do you order messages correctly? `[Lead/Expert]`
- The **server assigns a monotonically increasing sequence number per conversation**; clients sort by it, so every participant sees the same order regardless of device clocks.
- Pending local messages (no sequence yet) appear at the bottom in local order; once acknowledged they take their server position.
- Detect **gaps** (received 105 after 102): fetch 103–104 first, or show a "loading" gap marker.

```swift
struct Message: Identifiable, Codable, Sendable {
    enum Status: String, Codable, Sendable { case pending, sent, delivered, read, failed }

    let id: UUID                    // client-generated; deduplication + idempotency
    let conversationID: String
    let senderID: String
    var sequence: Int64?            // server-assigned; canonical order
    let body: String
    let createdAt: Date             // client clock: display only
    var status: Status
}

extension Array where Element == Message {
    /// Server-ordered messages first, then pending ones in local order
    func displayOrdered() -> [Message] {
        sorted { lhs, rhs in
            switch (lhs.sequence, rhs.sequence) {
            case let (l?, r?): l < r
            case (_?, nil): true
            case (nil, _?): false
            case (nil, nil): lhs.createdAt < rhs.createdAt
            }
        }
    }
}

/// Gap detection when a live event arrives
actor ConversationSequencer {
    private var lastSequence: [String: Int64] = [:]
    private let history: HistoryAPI

    init(history: HistoryAPI) { self.history = history }

    func received(_ message: Message) async throws -> [Message] {
        guard let seq = message.sequence else { return [message] }
        let last = lastSequence[message.conversationID] ?? seq - 1
        var result: [Message] = []
        if seq > last + 1 {                                    // gap: fetch what we missed
            result += try await history.messages(conversationID: message.conversationID,
                                                 afterSequence: last, beforeSequence: seq)
        }
        if seq > last { lastSequence[message.conversationID] = seq }
        return result + [message]                              // duplicates (seq <= last) dedupe by id later
    }
}
```

### Q51. How does the client recover events missed during a disconnection? `[Lead/Expert]`

```swift
    repeat {

}
```

```swift
/// @unchecked Sendable: all mutable state is guarded by `lock`
final class NotificationService: UNNotificationServiceExtension, @unchecked Sendable {
    private let lock = NSLock()
    private var contentHandler: ((UNNotificationContent) -> Void)?
    private var bestAttempt: UNMutableNotificationContent?
    private var downloadTask: URLSessionDownloadTask?

    override func didReceive(_ request: UNNotificationRequest,
                             withContentHandler contentHandler: @escaping (UNNotificationContent) -> Void) {
        let content = request.content.mutableCopy() as? UNMutableNotificationContent
        lock.withLock {
            self.contentHandler = contentHandler
            self.bestAttempt = content
        }

        guard let urlString = content?.userInfo["image_url"] as? String,
              let url = URL(string: urlString) else {
            deliver()
            return
        }

        // FIX: completion-based download; no non-Sendable values captured in a Task
        let task = URLSession.shared.downloadTask(with: url) { [weak self] fileURL, response, _ in
            // The temp file is deleted when this closure returns, so move it now
            if let fileURL { self?.attach(fileURL, mimeType: response?.mimeType) }
            self?.deliver()
        }
        lock.withLock { downloadTask = task }
        task.resume()
    }

    override func serviceExtensionTimeWillExpire() {
        lock.withLock { downloadTask }?.cancel()
        deliver()                                   // deliver whatever we have before being killed
    }

    private func attach(_ tempFile: URL, mimeType: String?) {
        // FIX: the extension must match the real type, or the attachment is rejected
        let ext = mimeType.flatMap { UTType(mimeType: $0)?.preferredFilenameExtension } ?? "jpg"
        let destination = FileManager.default.temporaryDirectory.appending(path: "\(UUID().uuidString).\(ext)")
        guard (try? FileManager.default.moveItem(at: tempFile, to: destination)) != nil,
              let attachment = try? UNNotificationAttachment(identifier: "image", url: destination) else { return }
        lock.withLock { bestAttempt?.attachments = [attachment] }
    }

    /// FIX: called from the download callback AND from expiry; must run only once
    private func deliver() {
        let (handler, content) = lock.withLock { () -> (((UNNotificationContent) -> Void)?, UNNotificationContent?) in
            defer { contentHandler = nil }
            return (contentHandler, bestAttempt)
        }
        if let handler, let content { handler(content) }
    }
}
```

### Q57. What delivery guarantees does APNs provide? `[Senior]`
- **Best effort, no guarantee.** If the device is offline, APNs stores **only the most recent** notification per app (per collapse ID) for a limited time.
- Headers: `apns-expiration`, `apns-collapse-id` (replace older, e.g. score updates), `apns-priority` (10 immediate, 5 power-efficient), `apns-push-type`.
- Payload limit **4 KB** (5 KB for VoIP): send IDs, fetch details in the app or the extension.
- So **never rely on push as the only delivery channel** for important data; sync on launch.

### Q60. How do you schedule background refresh with `BGTaskScheduler`? `[Senior]`
```swift
import BackgroundTasks

/// Calls setTaskCompleted exactly once, whichever of "finished" or "expired" happens first
final class OnceCompleter: @unchecked Sendable {
    private let lock = NSLock()
    private var isDone = false
    private let task: BGTask
    init(_ task: BGTask) { self.task = task }

    func complete(success: Bool) {
        lock.withLock {
            guard !isDone else { return }
            isDone = true
            task.setTaskCompleted(success: success)
        }
    }
}

enum BackgroundRefresh {
    static let identifier = "com.example.app.refresh"   // also in Info.plist BGTaskSchedulerPermittedIdentifiers

    /// Call before the app finishes launching
    static func register(syncEngine: SyncEngine) {
        BGTaskScheduler.shared.register(forTaskWithIdentifier: identifier, using: nil) { task in
            handle(task, syncEngine: syncEngine)
        }
    }

    static func schedule() {
        let request = BGAppRefreshTaskRequest(identifier: identifier)
        request.earliestBeginDate = Date(timeIntervalSinceNow: 30 * 60)   // a hint, not a guarantee
        try? BGTaskScheduler.shared.submit(request)
    }

    private static func handle(_ task: BGTask, syncEngine: SyncEngine) {
        schedule()                                                        // keep the chain going
        let completer = OnceCompleter(task)

        let work = Task {
            await syncEngine.pushPendingOperations()
            let success = (try? await syncEngine.pullChanges()) != nil
            completer.complete(success: success)
        }

        task.expirationHandler = {          // FIX: expiry also completes the task (exactly once)
            work.cancel()
            completer.complete(success: false)
        }
    }
}
```

### Q62. How do you design features knowing background execution isn't guaranteed? `[Lead/Expert]`
- Background work is an **optimization**, never a correctness requirement. Every important sync also happens on launch/foreground.
- Persist intent (outbox, pending uploads) so work resumes whenever the app next runs.
- Make operations **idempotent and resumable** (chunked uploads, sync tokens).
- If the user **force-quits**, silent push and background refresh stop until they reopen the app.
- Show state in the UI ("Waiting to upload · 3 items").

```
Correctness path (always):      launch / foreground → push outbox → pull changes
Optimization paths (sometimes): silent push · BGAppRefreshTask · background URLSession completion
```

### Q66. How do you handle autoplaying video in a scrolling feed? `[Lead/Expert]`
- Play **only the most visible** video (e.g. > 60% on screen); pause others.
- **Reuse a small pool of `AVPlayer`s** (creating players is expensive).
- **Preload** the next video's first segments when it's about to appear; cancel when it scrolls away.
- Muted by default; poster frame until the first frame renders; respect Reduce Motion, Low Data Mode, "autoplay on Wi-Fi only".

```swift
import AVFoundation

@MainActor
final class VideoPlayerPool {
    private var idle: [AVPlayer] = []
    private var active: [String: AVPlayer] = [:]       // postID → player
    private let maxPlayers = 3

    func player(for postID: String, url: URL) -> AVPlayer? {
        if let existing = active[postID] { return existing }
        guard active.count < maxPlayers else { return nil }       // show the poster image instead
        let player = idle.popLast() ?? AVPlayer()
        player.isMuted = true
        player.replaceCurrentItem(with: AVPlayerItem(url: url))
        active[postID] = player
        return player
    }

    func release(_ postID: String) {
        guard let player = active.removeValue(forKey: postID) else { return }
        player.pause()
        player.replaceCurrentItem(with: nil)           // frees decoder and buffers
        idle.append(player)
    }

    /// Called on scroll with each visible post's visible fraction
    func updatePlayback(visibility: [String: Double]) {
        let winner = visibility.filter { $0.value > 0.6 }.max { $0.value < $1.value }?.key
        for (id, player) in active {
            id == winner ? player.play() : player.pause()
        }
    }
}
```

### Q67. How do you upload large files reliably? `[Lead/Expert]`
- **Presigned URLs**: get an upload URL from the backend, upload straight to object storage, then confirm. Large files never touch API servers.
- **Chunked / resumable uploads** (S3 multipart, tus): 5–10 MB chunks, retried independently, resumed from the last confirmed chunk.
- **Background `URLSession`** so uploads continue when suspended.
- **Idempotency**: a client upload ID ties chunks and the final "complete" call together.

```swift
struct UploadSession: Codable, Sendable {
    let uploadID: UUID
    let fileURL: URL
    let chunkSize: Int
    let totalChunks: Int
    var completedParts: [Int: String]          // FIX: part number → ETag (S3 needs them to complete)
}

actor ChunkedUploader {
    private let api: UploadAPI
    private let store: UploadSessionStore         // persisted so uploads resume after relaunch

    init(api: UploadAPI, store: UploadSessionStore) {
        self.api = api
        self.store = store
    }

    func upload(_ session: UploadSession) async throws -> RemoteMediaID {
        var session = session
        let handle = try FileHandle(forReadingFrom: session.fileURL)
        defer { try? handle.close() }

        for index in 0..<session.totalChunks where session.completedParts[index] == nil {
            try Task.checkCancellation()
            try handle.seek(toOffset: UInt64(index * session.chunkSize))
            guard let chunk = try handle.read(upToCount: session.chunkSize) else { break }

            let etag = try await withRetry(maxAttempts: 3) {
                // Presigned URLs expire: ask for one per attempt (cheap) rather than reusing a stale one
                let presignedURL = try await api.chunkURL(uploadID: session.uploadID, index: index)
                return try await api.put(chunk, to: presignedURL)          // returns the part's ETag header
            }

            session.completedParts[index] = etag
            try await store.save(session)            // checkpoint progress
        }

        let parts = session.completedParts.sorted { $0.key < $1.key }.map { (number: $0.key + 1, etag: $0.value) }
        return try await api.completeUpload(uploadID: session.uploadID, parts: parts)  // server assembles
    }
}
```
**Foreground vs background:** this loop runs in your process, so it stops when the app is suspended. For uploads that must continue in the background, write each chunk to its own file and enqueue one background-session `uploadTask(with:fromFile:)` per chunk (Q61), tracking ETags in the delegate.

### Q71. How should a mobile app authenticate users? `[Senior]`

```swift
struct PKCE {

    let challenge: String
    let state: String                                  // FIX: CSRF protection, checked on callback
```

### Q72. Where should tokens be stored? `[Fundamental]`
```swift
import Security

enum KeychainError: Error { case unexpectedStatus(OSStatus) }

enum Keychain {
    private static func baseQuery(account: String, service: String) -> [String: Any] {
        [kSecClass as String: kSecClassGenericPassword,
         kSecAttrService as String: service,
         kSecAttrAccount as String: account]
    }

    /// FIX: update in place, add if missing. Delete-then-add can lose the token if the app dies in between.
    static func save(_ data: Data, account: String, service: String = "com.example.app.auth") throws {
        let query = baseQuery(account: account, service: service)
        let update: [String: Any] = [kSecValueData as String: data]
        let status = SecItemUpdate(query as CFDictionary, update as CFDictionary)

        if status == errSecItemNotFound {
            var attributes = query
            attributes[kSecValueData as String] = data
            attributes[kSecAttrAccessible as String] = kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly
            let addStatus = SecItemAdd(attributes as CFDictionary, nil)
            guard addStatus == errSecSuccess else { throw KeychainError.unexpectedStatus(addStatus) }
        } else if status != errSecSuccess {
            throw KeychainError.unexpectedStatus(status)
        }
    }

    static func load(account: String, service: String = "com.example.app.auth") throws -> Data? {
        var query = baseQuery(account: account, service: service)
        query[kSecReturnData as String] = true
        query[kSecMatchLimit as String] = kSecMatchLimitOne
        var result: AnyObject?
        let status = SecItemCopyMatching(query as CFDictionary, &result)
        if status == errSecItemNotFound { return nil }
        guard status == errSecSuccess else { throw KeychainError.unexpectedStatus(status) }
        return result as? Data
    }

    static func delete(account: String, service: String = "com.example.app.auth") throws {
        let status = SecItemDelete(baseQuery(account: account, service: service) as CFDictionary)
        guard status == errSecSuccess || status == errSecItemNotFound else { throw KeychainError.unexpectedStatus(status) }
    }
}
```
- **Keychain**, never `UserDefaults` or plain files.
- `AfterFirstUnlockThisDeviceOnly`: background tasks can read tokens after the first unlock; `ThisDeviceOnly` keeps them out of backups restored to other devices.
- Share with extensions via a **Keychain access group**; Secure Enclave keys for high-security apps.
- Keychain items can **survive app deletion**: on the first launch after install (flag in `UserDefaults`, which *is* deleted), wipe stale tokens.

### Q73. How should token refresh work at the system level? `[Senior]`
- An interceptor attaches access tokens and refreshes shortly before expiry.
- On 401, **one shared refresh** runs (concurrent requests wait for it), then failed requests retry once (actor-based implementation: Architecture guide Q102).
- If refresh fails, clear credentials and route to login, preserving the user's place.
- Backend: rotate refresh tokens, detect reuse (possible theft), support remote revocation ("log out of all devices").

```
t=0   access token (15 min) + refresh token (30 days, rotating)
t=14  interceptor sees "expires in < 60 s" → refresh proactively
      5 requests in flight get 401 → all await ONE refresh Task → retry once each
      refresh returns 401 (revoked) → AppSession.logOut(reason: .sessionExpired) → login screen
```

### Q77. Should you implement jailbreak detection? `[Lead/Expert]`

### Q78. How does end-to-end encryption affect a chat app design? `[Lead/Expert]`
- Encrypted on the sender's device, decrypted only on recipients' devices; the server routes ciphertext.
- Usually the **Signal Protocol** (identity keys, prekeys, Double Ratchet for forward secrecy), per-device keys for multi-device.
- Design impacts:
  - No server-side search, moderation or previews on plaintext. Pushes carry ciphertext or IDs; the **Notification Service Extension** decrypts (it shares keys via a Keychain access group and the App Group container).
  - Key storage in Keychain/Secure Enclave; safety-number verification UI; encrypted backups need separate key management.
  - Groups need sender keys or pairwise encryption; adding a device needs key distribution.

```
Sender device                 Server                    Recipient device
plaintext ─encrypt(ratchet)─▶ ciphertext (routes only) ─▶ NSE: decrypt with key from shared Keychain
                              push: {"msg_id": "...", "ciphertext": "..."} ─▶ shows "Ana: See you at 8"
```

## 12. Performance & Resource Constraints

### Q80. How do you design for fast app launch? `[Senior]`
- Low pre-main work: fewer dynamic frameworks (or mergeable libraries), no heavy static initializers.
- `didFinishLaunching`: only essentials (crash reporting, DI container). Defer analytics, remote-config fetch, prefetch, non-critical SDKs until after the first frame.

- Measure cold/warm launch (Instruments App Launch, Xcode Organizer, MetricKit); set budgets; alert on regressions.

### Q81. How do you design within memory limits? `[Senior]`

- Downsampled images; `NSCache` instead of unbounded dictionaries; windowed lists; stream large files; release caches on memory warnings and in the background.
- Monitor: MetricKit exit reasons (memory-limit terminations), Instruments Allocations/Leaks, memory graph.

### Q82. How do you design for battery efficiency? `[Senior]`
- **Network**: batch requests, avoid polling, prefer push, discretionary background transfers, coalesce work while the radio is already on. (The cellular radio stays in a high-power state for several seconds after each request, so ten scattered requests cost far more than one batch.)
- **Location**: lowest accuracy that works; significant-change/visit monitoring instead of continuous GPS.
- **CPU/GPU**: no needless animations or timers; pause off-screen work.
- **Background**: respect system scheduling; don't abuse background modes.
- Measure: Xcode Energy gauge, Instruments Power Profiler, MetricKit energy metrics.

### Q83. How do you minimize network usage? `[Senior]`

- Prefetch on Wi-Fi only, and only what users likely view.

```swift
        let spanID = Self.randomHex(bytes: 8)            // FIX: independent 16 hex chars, not derived from traceID
```

### Q94. How do mobile release constraints differ from web? `[Senior]`
- **No instant deploys**: App Review; slow updates; old versions live for months.

### Q95. How do phased rollouts and kill switches work together? `[Senior]`

### Q96. How do you design a force-update / minimum-version mechanism? `[Senior]`

```swift
struct VersionPolicy: Decodable, Sendable {
    let minimumSupported: String     // below this: block with "Update required"
    let recommended: String          // below this: dismissible "Update available"
    let storeURL: URL
}

enum UpdateRequirement: Equatable { case none, recommended(URL), required(URL) }

/// FIX: compare numeric components so "2.10" == "2.10.0" and "2.10.0" > "2.9.3"
struct SemanticVersion: Comparable {
    let parts: [Int]
    init(_ string: String) {
        var parts = string.split(separator: ".").map { Int($0) ?? 0 }
        while parts.count < 3 { parts.append(0) }
        self.parts = parts
    }
    static func < (lhs: Self, rhs: Self) -> Bool { lhs.parts.lexicographicallyPrecedes(rhs.parts) }
}

func evaluate(policy: VersionPolicy, currentVersion: String) -> UpdateRequirement {
    let current = SemanticVersion(currentVersion)
    if current < SemanticVersion(policy.minimumSupported) { return .required(policy.storeURL) }
    if current < SemanticVersion(policy.recommended) { return .recommended(policy.storeURL) }
    return .none
}

@Test func versionComparison() {

    #expect(evaluate(policy: policy, currentVersion: "2.10") == .recommended(policy.storeURL))   // was .required before the fix
    #expect(evaluate(policy: policy, currentVersion: "2.9.3") == .required(policy.storeURL))
    #expect(evaluate(policy: policy, currentVersion: "3.0.1") == .none)
```

### Q97. How does A/B testing work on mobile? `[Lead/Expert]`

- **Delivery**: fetched with remote config, cached; apply before showing affected screens (or keep the previous assignment until next launch) to avoid flicker.
- **Exposure logging** when the user actually **sees** the variant, not when assigned.
- **Analysis**: predefined primary metric, sample size, guardrails (crashes, latency).
- **Hygiene**: owners and end dates; remove losing paths.

```swift
enum HomeComponent: Decodable, Identifiable {
    case banner(BannerModel)
    case productCarousel(CarouselModel)
    case unsupported(id: String)            // forward compatibility: old apps skip unknown types

    var id: String {
        switch self {
        case .banner(let model): model.id
        case .productCarousel(let model): model.id
        case .unsupported(let id): id
        }
    }

    private enum CodingKeys: String, CodingKey { case type, id }

    init(from decoder: Decoder) throws {
        let container = try decoder.container(keyedBy: CodingKeys.self)
        switch try container.decode(String.self, forKey: .type) {
        case "banner": self = .banner(try BannerModel(from: decoder))
        case "product_carousel": self = .productCarousel(try CarouselModel(from: decoder))
        default: self = .unsupported(id: (try? container.decode(String.self, forKey: .id)) ?? UUID().uuidString)
        }
    }
}

/// FIX: one malformed component must not blank the whole screen
struct HomeScreen: Decodable {

    private struct Skip: Decodable {}

        var result: [HomeComponent] = []

            if let component = try? list.decode(HomeComponent.self) { result.append(component) }
            else { _ = try? list.decode(Skip.self) }          // advance past the bad element (and log it)
        }
```

**Trade-offs:**
- Pros: faster iteration, consistency across platforms, experimentation.
- Cons: schema/versioning/testing complexity, weaker offline, harder performance tuning, risk of a "browser inside the app."

### Q101. What principles guide designing a third-party iOS SDK? `[Lead/Expert]`
- **Never crash or slow the host**: catch internally, work off the main thread, bounded memory/disk, nothing blocking at launch.

```swift
final class ImpressionTracker {

        }
    }

    /// App backgrounded: close all open intervals so they're counted
    func flushAll() { visibleSince.keys.forEach(postBecameHidden) }
}
```

```swift
actor ChatService {
    private let store: MessageStore
    private let outbox: MessageOutbox
    private let connection: RealtimeConnection
    private var inFlight: [UUID: ContinuousClock.Instant] = [:]     // sent but not yet acked

    init(store: MessageStore, outbox: MessageOutbox, connection: RealtimeConnection) {
        self.store = store
        self.outbox = outbox
        self.connection = connection
    }

    /// 1. Send: persist as pending first, so it survives crashes and shows instantly
    func send(text: String, conversationID: String, senderID: String) async {
        let message = Message(id: UUID(), conversationID: conversationID, senderID: senderID,
                              sequence: nil, body: text, createdAt: .now, status: .pending)
        try? await store.insert(message)          // insert + enqueue in one DB transaction in production
        await outbox.enqueue(message.id)
        await flushOutbox()
    }

    /// 2. Ack from server: assign canonical order and mark as sent
    func handleAck(clientID: UUID, sequence: Int64) async {
        try? await store.markSent(clientID, sequence: sequence)
        await outbox.remove(clientID)
        inFlight[clientID] = nil
    }

    /// 3. Incoming message: dedupe, store, acknowledge delivery
    func handleIncoming(_ dto: MessageDTO) async {
        if (try? await store.contains(dto.clientID)) == true { return }     // at-least-once → dedupe
        try? await store.insert(Message(dto: dto))
        try? await connection.send(ReceiptCommand.delivered(upTo: dto.sequence,
                                                            conversationID: dto.conversationID).encoded())
    }

    /// 4. Retry pending messages (on reconnect, foreground, or a timer)
    func flushOutbox() async {
        for id in await outbox.pendingIDs() {
            // Don't resend something sent < 10 s ago that's still awaiting its ack
            if let sentAt = inFlight[id], ContinuousClock.now - sentAt < .seconds(10) { continue }
            guard let message = try? await store.message(id: id) else { continue }
            inFlight[id] = .now
            try? await connection.send(SendMessageCommand(message).encoded())
        }
    }
}
```
- **Reconnect**: WebSocket reconnects → `GET /sync?since=token` fills gaps → dedupe → resume live events (Q51).
- **Background**: socket closes; APNs arrives; the NSE fetches/decrypts the preview; on open, delta sync.
- **Failure UX**: after ~24 h without an ack (or a permanent server rejection), mark `failed` with a "Tap to retry" affordance.

**6. Deep dives**
- **Ordering**: server sequence per conversation; pending at the bottom (Q49).
- **Delivery**: at-least-once with idempotent client IDs (Q48).
- **Media messages**: compress → presigned upload → message referencing `media_id`; show the local image immediately with progress.
- **Read receipts**: "read up to sequence N", one per conversation, throttled; never per message.
- **Groups**: server fan-out; aggregated receipts ("Read by 5"); throttled typing.
- **Multi-device**: per-device sync tokens; read state synced so notifications clear on other devices.
- **Storage**: text kept locally; bounded media cache with "Manage storage".
- **E2EE** (extension): Signal Protocol; NSE decrypts; no server indexing (Q78).

**7. Trade-offs**
- WebSocket vs long-polling fallback (corporate networks may block WebSockets).
- Full local history (fast, offline search) vs on-demand loading (less storage).
- Server search vs E2EE.

### Q107. Design an image loading and caching library (like Kingfisher / Nuke / SDWebImage). `[Lead/Expert]`

**1. Requirements**
- Functional: load by URL into UIKit and SwiftUI; placeholders; memory and disk caching; downsampling; request deduplication; cancellation on reuse; prefetching; priorities.
- Non-functional: no main-thread decoding; bounded memory and disk; thread-safe; simple API; high hit rate; small binary.
- Out of scope: animated GIFs, advanced transformations.

**2. Architecture**
```
Public API (UIImageView extension, SwiftUI RemoteImage, Prefetcher)
        │
        ▼
ImagePipeline (actor: coordinates, dedupes in-flight tasks, counts subscribers)
   ├── MemoryCache  (NSCache of decoded, downsampled images; key = URL + target size)
   ├── DiskCache    (files keyed by URL hash; LRU eviction by total bytes; expiry)
   ├── DataLoader   (URLSession; priorities; limited concurrency; HTTP cache headers)

```

**3. API design**
```swift
struct ImageRequest: Hashable, Sendable {

    let width: CGFloat          // target size in points
    let height: CGFloat
```

**4. Core pipeline**
```swift
import ImageIO
import UIKit

actor ImagePipeline {
    static let shared = ImagePipeline()

    /// One download shared by every view asking for the same key
    private final class InFlight {
        let id: UUID
        let task: Task<UIImage, Error>
        var subscribers = 0
        init(id: UUID, task: Task<UIImage, Error>) { self.id = id; self.task = task }
    }

    private let memoryCache = NSCache<NSString, UIImage>()
    private let diskCache: DiskCache                       // actor: get/set Data, LRU eviction
    private let session: URLSession
    private var inFlight: [String: InFlight] = [:]

    init(diskCache: DiskCache = DiskCache(name: "images", byteLimit: 200 * 1024 * 1024),
         session: URLSession = .shared) {
        self.diskCache = diskCache
        self.session = session
        memoryCache.totalCostLimit = 100 * 1024 * 1024     // ~100 MB of decoded images
    }

    func image(for request: ImageRequest) async throws -> UIImage {
        let key = request.cacheKey
        if let cached = memoryCache.object(forKey: key as NSString) { return cached }   // 1. memory

        let entry = inFlight[key] ?? startLoad(request, key: key)                        // 2. join or start
        entry.subscribers += 1
        let task = entry.task, entryID = entry.id          // Sendable values for the @Sendable onCancel

        // FIX: when this caller is cancelled (cell reused, view gone), drop its subscription;
        // the shared download is cancelled only when NO caller still wants it.
        return try await withTaskCancellationHandler {
            try await task.value
        } onCancel: {
            Task { await self.subscriberLeft(key: key, id: entryID) }
        }
    }

    private func startLoad(_ request: ImageRequest, key: String) -> InFlight {
        let id = UUID()
        let task = Task.detached(priority: .userInitiated) { [diskCache, session] () throws -> UIImage in
            let data: Data
            if let cachedData = await diskCache.data(forKey: request.url.absoluteString) {   // 3. disk
                data = cachedData
            } else {
                let (downloaded, response) = try await session.data(from: request.url)       // 4. network
                guard (response as? HTTPURLResponse)?.statusCode == 200 else { throw ImageError.badResponse }
                await diskCache.store(downloaded, forKey: request.url.absoluteString)
                data = downloaded
            }
            try Task.checkCancellation()
            guard let image = ImagePipeline.downsample(data, maxPixelSize: request.maxPixelSize) else {
                throw ImageError.decodingFailed
            }
            return image
        }
        let entry = InFlight(id: id, task: task)
        inFlight[key] = entry

        Task {                                              // bookkeeping when the download ends
            let image = try? await task.value
            self.finished(key: key, id: id, image: image)
        }
        return entry
    }

    private func finished(key: String, id: UUID, image: UIImage?) {
        if let image { memoryCache.setObject(image, forKey: key as NSString, cost: image.decodedByteCount) }
        if inFlight[key]?.id == id { inFlight[key] = nil }
    }

    private func subscriberLeft(key: String, id: UUID) {
        guard let entry = inFlight[key], entry.id == id else { return }
        entry.subscribers -= 1
        if entry.subscribers == 0 {
            entry.task.cancel()
            inFlight[key] = nil
        }
    }

    nonisolated static func downsample(_ data: Data, maxPixelSize: CGFloat) -> UIImage? {
        let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
        guard let source = CGImageSourceCreateWithData(data as CFData, sourceOptions) else { return nil }
        let options = [
            kCGImageSourceCreateThumbnailFromImageAlways: true,
            kCGImageSourceShouldCacheImmediately: true,          // decode now, off the main thread
            kCGImageSourceCreateThumbnailWithTransform: true,
            kCGImageSourceThumbnailMaxPixelSize: maxPixelSize,
        ] as CFDictionary
        guard let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, options) else { return nil }
        return UIImage(cgImage: cgImage)
    }
}

extension UIImage {
    var decodedByteCount: Int { Int(size.width * scale * size.height * scale * 4) }
}

// SwiftUI integration: cancellation comes from .task(id:)
struct RemoteImage: View {
    let url: URL?
    @State private var image: UIImage?
    @Environment(\.displayScale) private var displayScale

    var body: some View {
        GeometryReader { proxy in
            Group {
                if let image {
                    Image(uiImage: image).resizable().scaledToFill()
                } else {
                    Rectangle().fill(.quaternary)                   // placeholder
                }
            }
            .frame(width: proxy.size.width, height: proxy.size.height)
            .clipped()
            .task(id: url) {
                guard let url else { return }
                let request = ImageRequest(url: url, width: proxy.size.width,
                                           height: proxy.size.height, scale: displayScale)
                image = try? await ImagePipeline.shared.image(for: request)
            }
        }
    }
}
```

**5. Deep dives**
- **Cancellation with deduplication**: shown above. Two cells share one download; when one is reused, only its subscription ends.
- **Disk cache**: files named by a hash of the URL (`SHA256`), an index of size + last access, LRU eviction over the byte limit, max age or HTTP headers, stored in `Caches/`.
- **Memory pressure**: `NSCache` evicts automatically; also purge on memory warnings and trim when backgrounded (Q81).
- **Prefetching**: low priority; cancel when rows scroll away; skip in Low Data Mode.
- **Priorities and concurrency**: visible = high; limit concurrent downloads (~6).
- **Metrics**: memory/disk hit rate, decode time, bytes downloaded.

**6. Trade-offs**
- Caching decoded images (fast, memory-hungry) vs encoded bytes (small, decode cost).
- Size-specific keys (exact fit, more entries) vs one size per URL (fewer entries, extra resizing).
- Build vs adopt Nuke/Kingfisher (control vs maintenance).

- **Push**: server applies if `base_version == current_version`; otherwise `conflict` with the server note.
- **Conflict**: three-way merge (Q42); conflicting body edits keep the server version and create a "Conflicted copy" so nothing is lost.
- **Pull**: apply remote upserts unless the note has pending local ops (then merge); apply tombstones; save the token.
- **Deletes**: tombstones locally and on the server; purge after confirmed sync.

```
Phone (offline)  edits title  v7 → local "Groceries", op base=7
iPad (online)    pins note    v7 → server v8
Phone reconnects → push op base=7 → server: conflict (current v8)
Phone merges base(v7) + local + remote(v8) → title from phone, pin from iPad → op base=8 → server v9 ✓
```

**6. Deep dives**
- **Search**: SQLite FTS5 (or Core Spotlight), updated on writes, offline.
- **Attachments**: uploaded separately; notes reference attachment IDs; placeholders; lazy download on other devices.
- **New device**: paged `changes` from token 0, newest first so the UI is useful quickly.
- **Token expiry**: full resync, carefully merged with unsynced local changes.
- **Collaboration** (extension): CRDT text (Q139).
- **Encryption** (extension): client-side encryption means the server can't merge plaintext; merging moves entirely to clients.

**7. Trade-offs**
- Operation-based sync (precise, needs ordering) vs state-based (simpler, bigger payloads).
- Field-level merge + conflicted copies vs last-write-wins (safety vs simplicity).
- CRDTs (automatic merges) vs complexity and metadata.

```swift
@Observable
final class SearchViewModel {
    var query = "" {
        didSet { scheduleSuggestions(for: query) }
    }
    private(set) var suggestions: [Suggestion] = []

    private let api: SearchAPI
    private let clock: any Clock<Duration>
    private var cache = LRUCache<String, [Suggestion]>(costLimit: 200)   // Q36; cost 1 per entry
    private var suggestionTask: Task<Void, Never>?

    init(api: SearchAPI, clock: any Clock<Duration> = ContinuousClock()) {
        self.api = api
        self.clock = clock
    }

    private func scheduleSuggestions(for rawQuery: String) {
        suggestionTask?.cancel()                           // the newest query always wins
        let normalized = rawQuery.trimmingCharacters(in: .whitespaces).lowercased()

        guard normalized.count >= 2 else {
            suggestions = []
            return
        }
        if let cached = cache.value(for: normalized) {     // instant for repeated prefixes (backspace)
            suggestions = cached
            return
        }

        suggestionTask = Task {
            do {
                try await clock.sleep(for: .milliseconds(250))      // debounce
                let results = try await api.suggest(prefix: normalized, limit: 8)
                try Task.checkCancellation()                       // a newer keystroke arrived meanwhile
                cache.insert(results, for: normalized, cost: 1)
                suggestions = results
            } catch {
                // CancellationError: superseded; other errors: keep previous suggestions
            }
        }
    }
}
```

```swift
@Observable
final class CheckoutViewModel {
    enum Phase: Equatable {
        case reviewing, paying, verifying, requiresAction(URL), confirmed(orderID: String), failed(String)
    }

    private(set) var phase: Phase = .reviewing
    private let orders: OrderAPI
    private let payments: PaymentService
    private let pendingStore: PendingCheckoutStore      // persists the idempotency key per quote

    init(orders: OrderAPI, payments: PaymentService, pendingStore: PendingCheckoutStore) {
        self.orders = orders
        self.payments = payments
        self.pendingStore = pendingStore
    }

    func placeOrder(quote: Quote) async {
        guard phase == .reviewing || phase.isRetryableFailure else { return }   // prevent double taps
        phase = .paying

        // Same key for every retry of this quote, even after an app restart
        let idempotencyKey = await pendingStore.key(for: quote.id)

        do {
            let token = try await payments.authorize(amount: quote.total, currency: quote.currency)
            let result = try await withRetry(maxAttempts: 3) {
                try await orders.create(quoteID: quote.id, paymentToken: token, idempotencyKey: idempotencyKey)
            }
            await handle(result, quoteID: quote.id)
        } catch {
            // Unknown outcome (timeout after the request may have succeeded): look it up, never guess
            phase = .verifying
            if let existing = try? await orders.find(idempotencyKey: idempotencyKey) {
                await handle(existing, quoteID: quote.id)
            } else {
                phase = .failed("We couldn't place your order. You have not been charged.")
            }
        }
    }

    private func handle(_ result: OrderResult, quoteID: String) async {
        switch result {
        case .confirmed(let orderID):
            await pendingStore.clear(for: quoteID)
            phase = .confirmed(orderID: orderID)
        case .requiresAction(let url):
            phase = .requiresAction(url)           // present 3-D Secure, then poll the order status
        }
    }
}

private extension CheckoutViewModel.Phase {
    var isRetryableFailure: Bool { if case .failed = self { true } else { false } }
}
```

```swift
import CryptoKit

/// Stable across launches and platforms. Never use `hashValue`: Swift seeds it randomly per process.
func bucket(for userID: String, salt: String, buckets: Int = 10_000) -> Int {
    let digest = SHA256.hash(data: Data("\(salt):\(userID)".utf8))
    let value = digest.prefix(8).reduce(UInt64(0)) { ($0 << 8) | UInt64($1) }
    return Int(value % UInt64(buckets))
}

func isInRollout(userID: String, flagKey: String, percent: Double) -> Bool {
    Double(bucket(for: userID, salt: flagKey)) < percent / 100 * 10_000
}

func variant(for userID: String, experiment: String, variants: [(name: String, weight: Int)]) -> String {
    let totalWeight = variants.reduce(0) { $0 + $1.weight }
    var point = bucket(for: userID, salt: experiment, buckets: totalWeight)
    for variant in variants {
        if point < variant.weight { return variant.name }
        point -= variant.weight
    }
    return variants.last?.name ?? "control"
}

    let at25 = Set(users.filter { isInRollout(userID: $0, flagKey: "new_checkout", percent: 25) })
    #expect(at10.isSubset(of: at25))                     // raising the % never removes anyone
    #expect((800...1200).contains(at10.count))           // ≈ 10%
}
```
Salting by flag key means a user in the first 10% of one flag isn't automatically in the first 10% of every flag.

### Q116. Design Instagram-style Stories. `[Senior]`

**1. Requirements**
- Functional: tray of users with unseen rings; full-screen viewer with progress bars; auto-advance (5 s images, video length for videos); tap to skip, hold to pause, swipe to next user; seen state; replies (optional).
- Non-functional: next story instant (preloading); smooth gestures; bounded memory/data; 24-hour expiry.

**2. Architecture**
```
StoriesTray ─▶ StoriesRepository (tray order, seen state, expiry)
StoryViewer ─▶ StoryPlayerViewModel (current user/index, progress timer, gestures)
                 ├── MediaPreloader (next items of current user + first item of next users)
                 ├── ImagePipeline / VideoPlayerPool
                 └── SeenStateSync (optimistic local + batched POST /stories/seen)
```

**3. Deep dives**
- **Preloading**: on start, preload the next 2 items of this user and the first of the next user; cancel on exit; skip in Low Data Mode.
- **Timer**: pauses on hold, backgrounding, VoiceOver focus, and while video buffers (video progress follows playback time).
- **Seen state**: local immediately (ring updates), batched uploads; server is truth across devices.
- **Expiry**: `expires_at`; tray filters locally before refresh; cached media evicted after 24 h.
- **Memory**: only nearby stories decoded.

```swift
@MainActor
@Observable
final class StoryProgressController {
    private(set) var progress: Double = 0          // 0...1 for the current item
    private var accumulated: Duration = .zero      // time played before the last pause
    private var resumedAt: ContinuousClock.Instant?
    private var duration: Duration = .seconds(5)
    private var timerTask: Task<Void, Never>?
    var onFinished: (() -> Void)?

    func start(duration: Duration) {
        self.duration = duration
        accumulated = .zero
        progress = 0
        resume()
    }

    func pause() {                                  // hold gesture, app backgrounded, video buffering
        if let resumedAt { accumulated += ContinuousClock.now - resumedAt }
        resumedAt = nil
        timerTask?.cancel()
        timerTask = nil
    }

    func resume() {
        timerTask?.cancel()
        resumedAt = .now
        timerTask = Task { [weak self] in
            while !Task.isCancelled {
                try? await Task.sleep(for: .milliseconds(50))          // only drives redraws
                guard let self, !Task.isCancelled, let resumedAt = self.resumedAt else { return }
                // FIX: progress from the real clock, so sleep overshoot doesn't make stories run long
                let elapsed = self.accumulated + (ContinuousClock.now - resumedAt)
                self.progress = min(1, elapsed / self.duration)
                if self.progress >= 1 {
                    self.timerTask = nil
                    self.onFinished?()
                    return
                }
            }
        }
    }
}
```

```swift
import CoreLocation

@MainActor
final class RunRecorder {
    private var backgroundSession: CLBackgroundActivitySession?
    private var recordingTask: Task<Void, Never>?
    private let store: RouteStore
    private(set) var distanceMeters: Double = 0
    private var lastLocation: CLLocation?

    init(store: RouteStore) { self.store = store }

    func start(runID: UUID) {
        backgroundSession = CLBackgroundActivitySession()   // keeps updates flowing in the background (iOS 17+)
        recordingTask = Task {
            do {
                for try await update in CLLocationUpdate.liveUpdates(.fitness) {
                    guard let location = update.location,
                          location.horizontalAccuracy >= 0,
                          location.horizontalAccuracy <= 20 else { continue }   // drop inaccurate fixes

                    if let lastLocation {
                        let meters = location.distance(from: lastLocation)
                        let seconds = location.timestamp.timeIntervalSince(lastLocation.timestamp)
                        guard seconds > 0, meters / seconds < 12 else { continue }   // > 43 km/h: GPS jump, not running
                        distanceMeters += meters
                    }
                    lastLocation = location
                    try? await store.append(RoutePoint(location: location), to: runID)  // crash-safe persistence
                }
            } catch {
                // location services unavailable or denied: surface to the UI
            }
        }
    }

    func stop() {
        recordingTask?.cancel()
        recordingTask = nil
        backgroundSession?.invalidate()
        backgroundSession = nil
    }
}
```

## 17. Common Follow-Up Deep Dives

### Q119. "What happens if the user is offline for a week?" `[Senior]`
- **Reads**: cached data with "last updated"; stale content clearly labelled where it matters (prices, availability).
- **Writes**: queued in the outbox; some become invalid (expired coupons, sold-out items). The server rejects them with clear errors; the app explains and offers a fix (dead-letter UI, Q41).
- **Sync on return**: delta sync from the last token; if expired, full resync merged with unsynced local changes.
- **Auth**: refresh tokens may have expired. **Keep the queued data**, ask the user to log in again (same account), then resume sync. If a different account logs in, the old user's queue must not be uploaded to the new account.
- **Storage**: bounded outbox; large media queued for Wi-Fi.

### Q120. "How does your design change for 10× more users?" `[Senior]`
- Each device still serves one user, but **client behaviour drives backend load**:
  - Fewer requests: caching, conditional requests, delta sync, debouncing, batched analytics.
  - No thundering herds: jittered retries and background refresh; staggered config fetches after releases or push campaigns.
  - CDN-friendly public content; cursor pagination.
  - Graceful degradation when the backend sheds load (flags, cached fallbacks).
- Backend (briefly): horizontal scaling, sharding by user/conversation, queues, caching layers.

```
Push campaign to 20M users at 18:00 → everyone opens the app within ~2 minutes
→ ~170k launches/s × 4 launch calls = ~680k req/s spike
Mitigations: stagger sends over 15 min, launch from cache, 1 aggregated BFF call, CDN for the campaign content
```

### Q121. "What if the backend goes down?" `[Senior]`
- Cached content and offline-first features keep the core usable; writes queue.
- Circuit breakers stop hammering (Q21); retries with jittered backoff.
- Remote-config incident banners; kill switches for non-critical features.
- Launch never blocks on non-essential services.
- Afterwards: watch recovery, avoid synchronized retries, review incident metrics.

### Q122. "How would you cut the app's data usage in half?" `[Senior]`
1. **Measure**: bytes by request type (images, video, API, analytics) from production metrics (`URLSessionTaskMetrics` aggregated per category).
2. **Images/video** (usually the biggest share): device sizes, HEIC/WebP/AVIF, lower quality on cellular, no autoplay or lower bitrate in Low Data Mode, smarter prefetching.
3. **API**: BFF/GraphQL field trimming, gzip/brotli, delta sync, conditional requests.
4. **Analytics**: batching, compression, sampling verbose events.
5. **Caching**: better hit rates (larger disk cache, stable keys, longer TTLs for static assets).
6. Validate with an experiment; guard engagement.

## 18. Common Mistakes & Recovery

### Q129. What are the most common mistakes in mobile system design interviews? `[Senior]`
- Jumping into solutions without clarifying requirements and scope.
- Designing a backend and ignoring client concerns (offline, lifecycle, battery, memory, old versions).
- No API or data model, only boxes and arrows.
- Ignoring failure modes: no retries, idempotency, or conflict handling.
- Over-engineering (microservices, CRDTs, GraphQL federation) without justification.
- No trade-offs or alternatives.
- Running out of time before deep dives.
- Silent thinking.

### Q130. How do you know whether you're over- or under-engineering? `[Lead/Expert]`
- **Under-engineering signals**: no offline story for an app that obviously needs one (chat, notes); no pagination for feeds; no duplicate/retry handling for payments or messages.
- **Over-engineering signals**: complex technology not tied to a requirement; designing for scale the interviewer ruled out.
- Tie every major component to a requirement, and offer phased evolution: "For v1 I'd do X; if we see Y, we'd evolve to Z."

### Q131. What do you do if you get stuck or the interviewer challenges your design? `[Senior]`
- Restate the requirement, think aloud, list options with pros and cons.
- Treat challenges as collaboration: "Good point. With multiple devices, last-write-wins would lose edits; I'll switch to version-based conflict detection."
- If you don't know an API, describe the concept and how you'd find out ("the platform's background transfer API; on iOS a background `URLSession`").
- Watch the time; summarize and propose the next topic.

**Useful phrases:**
- "Let me make sure I'm solving the right problem: …"
- "There are two options here; I'll pick X because of requirement Y, and the cost is Z."
- "I'm going to park that and come back to it if we have time."
- "We have about 10 minutes left; would you rather go deeper on sync or on the media pipeline?"

### Q139. Design Google Docs-style collaborative editing on mobile. `[Lead/Expert]`

**1. Requirements**
- Functional: several people edit the same document at once; see others' cursors/presence; works offline and merges on reconnect; version history.
- Non-functional: edits appear for others in < 300 ms; **no lost edits ever**; convergence (everyone ends up with the same text); documents up to ~1 MB of text.
- Out of scope: rich media embeds, comments (mention as extensions).

**2. The key decision: OT vs CRDT**
| | Operational Transform (OT) | CRDT (e.g. Yjs, Automerge) |
|---|---|---|
| How | Server transforms concurrent ops against each other | Each character has a unique ID; merges are commutative |
| Server | Central server required to order ops | Server just relays and stores; peers can merge alone |
| Offline | Hard (long-diverged histories are expensive to transform) | Natural: merge any time, any order |
| Cost | Server complexity | Metadata overhead (IDs per character, tombstones) |
| Used by | Google Docs | Figma-style tools, many local-first apps |

For a **mobile** app with offline editing, a **CRDT** is the safer choice: the device can merge on its own after hours offline.

**3. Architecture**
```
EditorView (TextKit 2) ─▶ DocumentSession ─▶ CRDT document (in memory, persisted as updates)
                                 │                 │
                                 │                 └─▶ Local store: snapshot + pending update log
                                 ├─▶ CollabSocket (WebSocket): send local updates, receive remote updates + awareness
                                 └─▶ PresenceModel (cursors, names, colors; ephemeral)
Backend: Collab relay (per-document room) · Update log store · Snapshot compactor · Auth/ACL
```

**4. Protocol**
```json
// client → server
{ "type": "update", "doc_id": "d_7", "client_id": "c_42", "update": "<binary CRDT update, base64>", "seq": 118 }
{ "type": "awareness", "doc_id": "d_7", "cursor": { "anchor": "c_42:991", "head": "c_42:995" }, "name": "Ana" }

// on (re)connect: exchange state vectors so each side sends only what the other is missing
{ "type": "sync_step1", "state_vector": "<base64>" }
{ "type": "sync_step2", "update": "<missing updates, base64>" }
```

**5. How a sequence CRDT stays consistent (simplified)**
```swift
/// Every character gets a globally unique, ordered ID; inserts reference the ID they follow.
struct CharID: Hashable, Comparable, Codable, Sendable {
    let clock: Int            // Lamport clock
    let site: String          // client ID breaks ties deterministically
    static func < (a: Self, b: Self) -> Bool { (a.clock, a.site) < (b.clock, b.site) }
}

struct CharNode: Codable, Sendable {
    let id: CharID
    let after: CharID?        // insert position = "right after this character"
    let value: Character.UnicodeScalarView.Element
    var isDeleted = false     // tombstone: deletes never remove the node, so late inserts still find their anchor
}
// Concurrent inserts after the same anchor are ordered by CharID (higher first), on every device,
// so all replicas converge to the same text no matter the arrival order.
```
In practice use a proven library (Yjs via a Swift binding, or Automerge's Swift package) rather than writing one; the interview point is **why** it converges.

**6. Deep dives**
- **Offline**: local updates are appended to a persisted log and applied immediately; on reconnect, the state-vector handshake sends only the missing updates both ways.
- **Presence** is ephemeral (never persisted), throttled to ~10/s, and expires after a few seconds of silence.
- **Mapping to UIKit text**: convert CRDT positions ↔ `NSRange` on every change; apply remote updates while preserving the local cursor by anchoring it to a `CharID`, not an integer offset.
- **Growth**: tombstones and per-char metadata grow; the server periodically compacts into snapshots; clients load the snapshot + recent updates.
- **Permissions**: ACL checked by the relay per document; read-only viewers receive updates but their sends are rejected.
- **History**: periodic named snapshots enable "version history" and restore.

**7. Trade-offs**
- CRDT metadata overhead vs effortless offline merges.
- Character-level vs block-level (paragraph) CRDTs: block-level is lighter but merges coarser.
- Relay-only server (simple) vs server-side validation of every update (safer, costlier).

```swift
    struct ContentState: Codable, Hashable {

    private let api: TrackingAPI

    func startTracking(orderID: String, restaurant: String) async {
        guard ActivityAuthorizationInfo().areActivitiesEnabled else { return }
        do {
            let activity = try Activity.request(
                attributes: DeliveryAttributes(orderID: orderID, restaurantName: restaurant),
                content: .init(state: .init(status: "Order accepted", etaMinutes: 35, courierName: nil),
                               staleDate: .now.addingTimeInterval(20 * 60)),   // greys out if updates stop
                pushType: .token)                                             // server will update it via APNs

            for await token in activity.pushTokenUpdates {                   // tokens can rotate
                let hex = token.map { String(format: "%02x", $0) }.joined()
                try? await api.registerLiveActivityToken(orderID: orderID, token: hex)
            }
        } catch {
            // Too many activities, or disabled by the user: fall back to regular notifications
        }
    }
}
```

Server → APNs payload (`apns-push-type: liveactivity`, topic `<bundle-id>.push-type.liveactivity`):
```json
{
  "aps": {
    "timestamp": 1762075200,
    "event": "update",
    "content-state": { "status": "On the way", "etaMinutes": 12, "courierName": "Rafi" },
    "stale-date": 1762076400,
    "alert": { "title": "Your order is on the way", "body": "Rafi is 12 minutes away" }

```
When delivered: `"event": "end"` with a final state and `"dismissal-date"`.

**5. Deep dives**
- **Update budget**: the system limits frequent high-priority Live Activity updates. Send updates on **meaningful changes** (status, ETA change ≥ 1–2 min), not every GPS point; use priority 5 for minor updates.
- **Stale handling**: `staleDate` makes the UI show "Updating…" if pushes stop.
- **Recovery**: on foreground, `GET /orders/{id}` is the source of truth and reconciles the Live Activity (`activity.update(...)` locally).
- **Push-to-start** (iOS 17.2+): the server can start the Live Activity even if the app wasn't running when the order was accepted (`Activity<…>.pushToStartTokenUpdates`).
- **Privacy**: courier location only shown while the order is active; precision reduced until pickup.

**6. Trade-offs**
- Live Activity (glanceable, no app needed) vs frequent alert pushes (noisy).
- WebSocket while open (smooth map) vs polling every 10 s (simpler, choppier).

### Q141. Design a calendar app with offline edits, reminders, and external calendar sync. `[Lead/Expert]`

**1. Requirements**
- Functional: day/week/month views; create/edit events offline; recurring events with exceptions ("move only this Tuesday"); reminders; invite attendees; sync with Google/Outlook/iCloud calendars.
- Non-functional: reminders fire on time **even with no network**; correct across time zones and DST; fast scrolling through years of events.

**2. Architecture**
```
CalendarViews ─▶ CalendarViewModel ─▶ EventRepository ─▶ Local DB (events, recurrence rules, exceptions)
                                          │                    │
                                          │                    └─▶ Occurrence expander (rules → instances for visible range)
                                          ├─▶ SyncEngine (outbox + delta sync, Q40)
                                          └─▶ ReminderScheduler (local notifications, rolling window)
Backend: Calendar service · Connectors (Google Calendar API, Microsoft Graph, CalDAV) · Invite emails (iCalendar)
Optional on-device: EventKit to read/write the user's system calendars (with permission)
```

**3. Data model**
```swift
struct CalendarEvent: Codable, Sendable, Identifiable {
    let id: UUID                       // client-generated
    var title: String
    var start: Date                    // absolute instant (UTC)
    var end: Date
    var timeZone: String               // IANA ID, e.g. "Asia/Dhaka": needed to expand recurrences correctly
    var isAllDay: Bool                 // all-day = floating date, NOT midnight UTC
    var recurrence: String?            // RFC 5545 RRULE, e.g. "FREQ=WEEKLY;BYDAY=TU"
    var exceptions: [Date: EventOverride]   // occurrence start → changed/cancelled instance
    var reminderOffsets: [TimeInterval]     // e.g. [-600] = 10 min before
    var serverVersion: Int?
}
```

**4. Deep dives**
- **Recurrence**: store the rule, not every instance; expand occurrences only for the visible range (cache per month). Exceptions are overrides keyed by the original occurrence date.
- **Time zones/DST**: a weekly 9:00 meeting in New York must stay 9:00 New York time across DST, so expand recurrences in the event's time zone, then convert to the viewer's. All-day events are dates, not instants.
- **Reminders offline**: schedule local notifications on device; iOS keeps at most **64 pending** local notifications per app, so maintain a **rolling window** (next ~60 reminders) and refill on launch, after sync, and in background refresh.

```swift
import UserNotifications

actor ReminderScheduler {
    private let center = UNUserNotificationCenter.current()
    private let maxPending = 60                                // stay under the 64 limit

    func reschedule(upcoming occurrences: [ReminderOccurrence]) async {
        center.removeAllPendingNotificationRequests()
        for item in occurrences.sorted(by: { $0.fireDate < $1.fireDate }).prefix(maxPending) {
            let content = UNMutableNotificationContent()
            content.title = item.title
            content.body = item.fireDescription
            content.threadIdentifier = item.eventID.uuidString
            let components = Calendar.current.dateComponents([.year, .month, .day, .hour, .minute], from: item.fireDate)
            let trigger = UNCalendarNotificationTrigger(dateMatching: components, repeats: false)
            try? await center.add(UNNotificationRequest(identifier: item.id, content: content, trigger: trigger))
        }
    }
}
```
- **External sync**: done server-side through connectors (OAuth tokens stay on the server); the app syncs only with your backend. Use provider change tokens (Google `syncToken`, Microsoft delta queries) to stay incremental.
- **Conflicts**: field-level merge (Q42); for recurring series, an edit to "all future events" splits the series into two rules.
- **Invites**: iCalendar (`.ics`) with stable `UID`s so external clients update rather than duplicate events.

**5. Trade-offs**
- Expanding on the fly (small storage) vs materializing instances (fast queries, hard edits).
- Server-side connectors (one implementation, tokens safe) vs EventKit on device (works offline with the system calendar, but per-platform).

```swift
import LocalAuthentication
import Security

/// Refresh token readable only after Face ID / Touch ID, invalidated if biometrics change
func storeBiometricProtected(_ token: Data) throws {
    var error: Unmanaged<CFError>?
    guard let access = SecAccessControlCreateWithFlags(
        nil,
        kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,   // removed if the passcode is turned off
        .biometryCurrentSet,                                // new fingerprint/face enrolled → item invalid
        &error) else { throw error!.takeRetainedValue() as Error }

    let identity: [String: Any] = [
        kSecClass as String: kSecClassGenericPassword,
        kSecAttrAccount as String: "bank_refresh_token",
    ]
    SecItemDelete(identity as CFDictionary)        // access control can't be changed by SecItemUpdate
    var attributes = identity
    attributes[kSecValueData as String] = token
    attributes[kSecAttrAccessControl as String] = access
    let status = SecItemAdd(attributes as CFDictionary, nil)
    guard status == errSecSuccess else { throw KeychainError.unexpectedStatus(status) }
}

func readBiometricProtected(reason: String) throws -> Data? {
    let context = LAContext()
    context.localizedReason = reason                       // "Unlock your accounts"
    let query: [String: Any] = [
        kSecClass as String: kSecClassGenericPassword,
        kSecAttrAccount as String: "bank_refresh_token",
        kSecReturnData as String: true,
        kSecUseAuthenticationContext as String: context,   // system shows the Face ID prompt
    ]
    var result: AnyObject?
    let status = SecItemCopyMatching(query as CFDictionary, &result)
    return status == errSecSuccess ? result as? Data : nil
}
```

**Inactivity timeout:**

```swift
@MainActor
```

```swift
import AVFoundation
import MediaPlayer

@MainActor
final class PlaybackService {
    private let player = AVPlayer()

    func configureSession() throws {
        try AVAudioSession.sharedInstance().setCategory(.playback, mode: .spokenAudio)   // + "audio" background mode
        try AVAudioSession.sharedInstance().setActive(true)

        let commands = MPRemoteCommandCenter.shared()
        commands.playCommand.addTarget { [weak self] _ in self?.player.play(); return .success }
        commands.pauseCommand.addTarget { [weak self] _ in self?.player.pause(); return .success }
        commands.skipForwardCommand.preferredIntervals = [30]
        commands.skipForwardCommand.addTarget { [weak self] _ in self?.skip(by: 30); return .success }
        commands.skipBackwardCommand.preferredIntervals = [15]
        commands.skipBackwardCommand.addTarget { [weak self] _ in self?.skip(by: -15); return .success }
    }

    func play(_ episode: Episode, from position: Double, rate: Float) {
        let url = episode.localFileURL ?? episode.remoteURL            // downloaded first, else stream
        player.replaceCurrentItem(with: AVPlayerItem(url: url))
        player.seek(to: CMTime(seconds: position, preferredTimescale: 600))
        player.defaultRate = rate
        player.play()
        MPNowPlayingInfoCenter.default().nowPlayingInfo = [
            MPMediaItemPropertyTitle: episode.title,
            MPMediaItemPropertyArtist: episode.showTitle,
            MPMediaItemPropertyPlaybackDuration: episode.duration,
            MPNowPlayingInfoPropertyElapsedPlaybackTime: position,
            MPNowPlayingInfoPropertyPlaybackRate: rate,
        ]
    }

    private func skip(by seconds: Double) {
        let target = player.currentTime().seconds + seconds
        player.seek(to: CMTime(seconds: max(0, target), preferredTimescale: 600))
    }
}
```

### Q144. Design a ticket-booking app with seat selection under high contention. `[Lead/Expert]`

**1. Requirements**
- Functional: browse events; interactive seat map; select seats; hold them while paying; pay; receive tickets (Wallet passes); handle "on-sale" moments with huge traffic.
- Non-functional: **no seat sold twice**; fair access at on-sale; responsive seat map with thousands of seats; clear feedback when seats are taken.

**2. Architecture**
```
EventView ─▶ SeatMapView (Canvas/Metal-backed drawing) ─▶ SeatMapViewModel
                                                              ├─▶ SeatAPI (layout: cached, CDN; availability: live)
                                                              ├─▶ AvailabilitySocket (seat taken/released deltas)
                                                              └─▶ HoldManager (hold ID, expiry countdown)
CheckoutFlow (Q113 pattern) ─▶ Wallet pass (PassKit)
Backend: Waiting room / queue · Inventory service (atomic holds with TTL) · Payments · Ticket issuing
```

**3. API**
```
GET  /v1/events/{id}/layout          → static seat geometry (CDN-cached, versioned)
GET  /v1/events/{id}/availability    → bitset of available seats + version
WS   availability deltas             → { "version": 912, "taken": ["A12","A13"], "released": ["C4"] }
POST /v1/holds  { seat_ids }  Idempotency-Key  → 201 { hold_id, expires_at } | 409 { unavailable: ["A12"] }
POST /v1/orders { hold_id, payment_token }     Idempotency-Key
DELETE /v1/holds/{id}                          → release on cancel
```

**4. Deep dives**
- **No double-selling**: the server creates holds atomically (e.g. conditional update `WHERE status = 'available'`) with a TTL (e.g. 8 minutes). The client never "owns" a seat; it owns a **hold**.
- **Optimistic UI with honest conflict handling**: selecting a seat marks it locally, but a `409` returns which seats were lost; highlight them and suggest the nearest alternatives.
- **Live availability**: initial bitset + versioned deltas over WebSocket; if a delta's version skips, refetch the bitset (gap handling like Q49).
- **High contention / on-sale**: a **virtual waiting room** issues signed queue tokens; the app shows position and polls with jitter (or receives a push) when it's the user's turn. This protects the backend and is fairer than refresh-spamming.
- **Countdown**: computed from the server's `expires_at` (not a local timer started on tap), so it survives backgrounding; warn at 1 minute; release on cancel.
- **Seat map performance**: draw thousands of seats with `Canvas` (SwiftUI) or a single `CALayer`-based view, not thousands of views; hit-test by geometry.

```swift
@MainActor
@Observable
final class HoldManager {
    private(set) var hold: Hold?                       // { id, seatIDs, expiresAt (server time) }
    private(set) var lostSeats: Set<String> = []
    private let api: SeatAPI
    private var serverClockOffset: TimeInterval = 0    // server time - device time, from response Date header

    init(api: SeatAPI) { self.api = api }

    func holdSeats(_ seatIDs: [String], key: UUID) async {
        switch await api.createHold(seatIDs: seatIDs, idempotencyKey: key) {
        case .success(let newHold, let serverDate):
            serverClockOffset = serverDate.timeIntervalSinceNow
            hold = newHold
            lostSeats = []
        case .conflict(let unavailable):
            lostSeats = Set(unavailable)               // UI highlights these and suggests alternatives
        case .failure:
            break                                      // show retry; the same key makes the retry safe
        }
    }

    /// Remaining time based on the server's clock, so a wrong device clock can't extend the hold
    func remaining(now: Date = .now) -> TimeInterval {
        guard let hold else { return 0 }
        return max(0, hold.expiresAt.timeIntervalSince(now.addingTimeInterval(serverClockOffset)))
    }
}
```

**5. Trade-offs**
- Longer holds (less checkout pressure) vs inventory locked by abandoners.
- Real-time deltas (accurate map) vs periodic refresh (simpler, more 409s).
- Waiting room (fair, protects backend) vs open access (simpler, collapses at on-sale).

### Failure-mode checklist (say these unprompted)
- [ ] Request succeeded but response lost → idempotency key
- [ ] App killed mid-operation → persisted outbox / upload sessions
- [ ] Offline for a week → stale labels, expired tokens, token-expired full resync
